# ZEP-0000: Zeron Enhancement Proposal Process

## Status

Accepted

## Abstract

This document defines the lightweight process for proposing and recording significant changes to
the Zeron language, compiler, standard library, and project architecture. It establishes stable ZEP
numbering, proposal statuses, and the scope of changes that should use a ZEP.

## Motivation

Zeron's language and library surface is growing, and some changes affect semantics, compatibility,
multiple compiler phases, or future tooling. Recording the problem, intended behavior, alternatives,
and compatibility impact before implementation helps contributors make those decisions explicitly.

The process should provide that design record without creating unnecessary ceremony for routine
maintenance.

## Scope

A ZEP is expected for a proposed change that does one or more of the following:

- changes source-language syntax or semantics;
- adds, removes, or incompatibly changes public standard-library or compiler APIs;
- changes compatibility, versioning, or library artifact policy;
- introduces an architectural change spanning multiple compiler or runtime responsibilities;
- establishes a project-wide policy or a new contributor process.

Localized bug fixes, implementation details that follow an accepted design, documentation
corrections, and contained improvements may proceed through the normal issue and pull-request
workflow. A maintainer may request a ZEP if discussion shows that a change has broader design
consequences than initially apparent.

## Numbering and files

ZEPs use globally sequential, zero-padded decimal identifiers: `ZEP-0000`, `ZEP-0001`, and so on.
The identifier is permanent, sorts lexically, and carries no date, priority, or topic meaning.

Create ZEP documents in `documents/zeps/`, using the identifier as the filename, for example
`documents/zeps/ZEP-0002.md`. Assign the next unused number when a proposal is created. Never reuse
a number, including when its proposal is rejected, withdrawn, or superseded.

The title should describe the proposal; the identifier remains unchanged if the title is edited.
Refer to a proposal by its full identifier in documents and discussions.

## Proposal lifecycle

A ZEP records one of these statuses:

- **Draft** — open for design discussion; no direction has been approved.
- **Accepted** — the proposed direction is approved for implementation, subject to normal project
  prioritization and review.
- **Rejected** — the proposal was considered and will not proceed in its current form.
- **Deferred** — the proposal may be reconsidered later, but no decision to proceed has been made.
- **Implemented** — the accepted design has been implemented and the change has landed.
- **Withdrawn** — the author or maintainers have stopped pursuing the proposal.
- **Superseded** — a later ZEP replaces this proposal or its design direction.

Acceptance approves a design direction; it does not guarantee an implementation schedule, release,
or implementation by the proposal's author. Rejected and withdrawn ZEPs remain in the repository as
decision records. A materially different proposal should receive a new number and refer to the
earlier ZEP.

## Discussion and decisions

ZEP discussion takes place through the repository's normal public contribution channels, such as
issues and pull requests. A proposal should explain its alternatives and identify unresolved
questions. The author may revise a Draft in response to feedback.

A project maintainer records the disposition by updating the ZEP status and adding a short decision
note explaining the outcome. No committee, formal vote, or fixed review period is required. If
maintainers disagree or important questions remain unresolved, the proposal can stay Draft or be
Deferred rather than implying consensus.

Once Accepted, implementation work should follow the approved scope. A significant change in
behavior or compatibility impact should be discussed and recorded in the ZEP; if it changes the
design direction materially, create a new ZEP rather than silently rewriting the decision.

## Proposal format

New ZEPs should follow [ZEP-0001](./ZEP-0001.md). Keep proposals proportional to their scope:
sections that do not apply may be omitted or marked “Not applicable.” A focused proposal is better
than filling every section with boilerplate.

ZEP-0000 itself establishes this process. Changes to the process should be proposed in a later ZEP
that explicitly describes the process change.

## Initial decision

This process is accepted as the initial lightweight ZEP process. Its use should be reviewed after
experience with several proposals; process changes should be driven by demonstrated friction or
missing clarity, not by a desire to imitate a larger standards organization.
