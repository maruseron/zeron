## Abstract

This document defines the recommended structure and metadata for Zeron Enhancement Proposals. The
template is intended to make important design considerations visible while keeping the process
proportional to each proposal.

## Motivation

A consistent proposal structure makes it easier to understand a change, compare alternatives, and
find its compatibility and implementation implications. Requiring irrelevant sections, however,
would turn a lightweight design process into paperwork. This template therefore distinguishes
essential proposal information from optional detail.

## Template

Copy the following structure when creating a ZEP. Replace bracketed guidance with proposal content.
Delete guidance text and omit sections that do not apply.

```markdown
# ZEP-NNNN: Short descriptive title

| Field | Value |
|-------|-------|
| Status | Draft |
| Author | [Name or project handle] |
| Created | YYYY-MM-DD |
| Updated | YYYY-MM-DD |
| Related ZEPs | [ZEP-NNNN](./ZEP-NNNN.md) — [relationship], or — |

## Abstract

[A concise summary of the proposed change and its intended outcome.]

## Motivation

[Describe the problem, use case, or opportunity. Explain why this change is useful.]

## Goals

- [What this proposal intends to accomplish.]

## Non-goals

- [Related concerns intentionally left outside this proposal.]

## Proposal

[Describe the intended behavior or process. Include examples when they clarify the design.]

## Compatibility and impact

[Describe source, runtime, library/API-index, migration, and documentation impact as relevant.]

## Alternatives

- [Alternative considered] — [reason for accepting or rejecting it.]

## Implementation and validation

[Describe likely implementation stages and how the behavior will be verified. This is not an
implementation commitment or schedule.]

## Open questions

- [Unresolved decision, if any.]

## References

- [Related documentation, issues, prior art, or design discussions.]

## Decision

[Maintainer: record the disposition, date, and brief rationale when the proposal leaves Draft.]
```

## Required information

Every proposal must include:

- a stable identifier and descriptive title;
- a status;
- an abstract and motivation;
- the proposed direction;
- goals and non-goals, which may be brief;
- relevant compatibility or impact considerations;
- alternatives considered, or an explicit note that no reasonable alternatives were identified;
- a decision note when the proposal leaves Draft.

Author and date metadata should be kept current in the table. Use “—” when there are no related
ZEPs. Implementation and validation detail should match the proposal's scope; it need not prescribe
every code change or test case.

## Status changes and updates

Use the status values and lifecycle in [ZEP-0000](./ZEP-0000.md). Update the `Updated` date when a
substantive revision is made. Record accepted, rejected, deferred, withdrawn, implemented, or
superseded decisions in the Decision section, with a brief rationale and links to related proposals
or implementation changes when available.

An accepted proposal may be clarified without changing its design direction. If its goals,
semantics, or compatibility direction materially change, create a new ZEP and mark or reference the
relationship rather than obscuring the original decision.

## Guidance

Keep the document concise and focused on decisions that need to be made. Use examples to specify
observable behavior, and distinguish settled decisions from open questions. Sections that do not
apply may be omitted or marked “Not applicable”; do not add speculative detail solely to complete
the template.
