# ZEP-0002: Explicit Shared Mutable State in Lambdas

## Status

Draft

## Author

Marcelo Rodríguez

## Created

2026-10-13

## Related ZEPs

- None.

## Abstract

This proposal explores how lambdas can intentionally share mutable state with their enclosing
scope. The current capture implementation supports immutable captures and rejects implicit mutation
of captured stack-scoped locals. The goal is to preserve that safety rule while making explicit
shared-state patterns possible and well specified.

## Motivation

Lambda capture lowering currently copies captured values into the function object. This works for
immutable values and for references to already-shared objects, but it does not provide a direct,
language-defined way for multiple closures to share and update a local binding. The lambda roadmap
identifies explicit shared mutable cells as future work.

Without a defined mechanism, programmers may need to introduce an unrelated class solely to hold a
mutable value, or may incorrectly expect mutation of a captured local to behave as it does in
languages with implicit closure cells.

## Goals

- Define a deliberate, visible mechanism for closures to observe and update shared state.
- Preserve the rule that capturing a local does not silently change its stack-local binding into a
  shared mutable location.
- Specify creation, aliasing, mutation, and lifetime behavior in terms compatible with Zeron's
  reference and mutability rules.
- Keep ordinary immutable capture semantics and the current `LambdaMetafactory` lowering model
  unless implementation evidence requires a change.

## Non-goals

- Implicitly capturing and mutating arbitrary local variables.
- Introducing general ownership, borrowing, or garbage-collection semantics beyond the existing JVM
  reference model.
- Changing function-shape identity or making lambdas polymorphic.

## Proposal

Add or standardize an explicit heap-backed mutable cell that can be captured by value as a shared
reference. A closure that captures the cell may mutate its contents only through the cell's declared
mutable operations and only when it has the required mutable reference capability. Copying the cell
reference into multiple closures preserves shared identity; copying the contained value does not.

Capturing an ordinary mutable local remains invalid. Programmers opt into sharing by creating a cell
or another explicitly shared mutable object and capturing its reference. The source-level API and
syntax for the cell are intentionally not settled by this Draft.

The implementation should prefer a standard-library abstraction if existing classes and mutable
reference semantics can express it cleanly. A compiler intrinsic or special capture syntax should
only be considered if that cannot be implemented with ordinary Zeron declarations.

## Compatibility and impact

This is an additive language/library capability if implemented as a standard-library type. It should
not alter the semantics of existing captures or change lambda SAM descriptors. The API-index schema
or standard-library API version should change only if the chosen public representation requires it.

## Alternatives

- Implicitly capture mutable locals in compiler-generated cells — rejected as the default direction
  because it hides aliasing and changes ordinary local mutation semantics.
- Require users to define a custom mutable holder class — remains a viable implementation technique,
  but does not provide a canonical, discoverable pattern.
- Add a dedicated cell syntax — defer unless an ordinary standard-library abstraction cannot express
  the intended capability safely.

## Implementation and validation

The design phase should determine whether the existing mutable-reference model can support a
standard cell abstraction without special compiler treatment. Implementation tests should cover two
closures sharing one cell, independent cells, mutation through permitted and rejected reference
views, captured-cell lifetime after the defining function returns, and unchanged immutable capture
behavior. Inspect generated call-site and helper descriptors if lowering changes.

## Open questions

- Should the canonical abstraction be a generic `Cell<T>`, an explicitly mutable reference wrapper,
  or an existing ordinary class pattern?
- Should cell reads require an immutable view while writes require a mutable view, and how does that
  interact with references captured by immutable lambdas?
- Is a minimal value container sufficient, or should the API also expose atomic/concurrent behavior?
  The initial feature should likely avoid promising thread safety.
