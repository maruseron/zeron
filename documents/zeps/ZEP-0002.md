# ZEP-0002: Explicit Shared Mutable State in Lambdas

## Abstract

This proposal explores how lambdas can intentionally share mutable state with their enclosing
scope. The current capture implementation supports immutable captures and rejects implicit mutation
of captured stack-scoped locals. The goal is to preserve that safety rule while making explicit
shared-state patterns possible and well specified.

## Motivation

Lambda capture lowering currently copies captured values into the function object. This works for
immutable values and for references to already-shared objects, but it does not provide a direct,
language-defined way for multiple closures to share and update a local binding. The lambda roadmap
identifies explicit shared mutable cells as future work.

Without a defined mechanism, programmers may need to introduce an unrelated class solely to hold a
mutable value, or may incorrectly expect mutation of a captured local to behave as it does in
languages with implicit closure cells.

## Goals

- Define a deliberate, visible mechanism for closures to observe and update shared state.
- Preserve the rule that capturing a local does not silently change its stack-local binding into a
  shared mutable location.
- Specify creation, aliasing, mutation, and lifetime behavior in terms compatible with Zeron's
  reference and mutability rules.
- Keep ordinary immutable capture semantics and the current `LambdaMetafactory` lowering model
  unless implementation evidence requires a change.

## Non-goals

- Implicitly capturing and mutating arbitrary local variables.
- Introducing general ownership, borrowing, or garbage-collection semantics beyond the existing JVM
  reference model.
- Changing function-shape identity or making lambdas polymorphic.

## Proposal

Provide an ordinary generic `Cell<T>` class in the standard library, using existing class,
reference-view, and lambda-capture semantics. Do not add special capture syntax, compiler-generated
cells for mutable locals, or a new lambda-lowering path.

A cell binding can be immutable while holding a mutable reference to the cell. A lambda captures
that reference by value; multiple closures that capture the same reference therefore observe the
same cell object. Reads should be available through a read-only view, while changing the cell's
stored value should be an explicitly `mut` operation requiring a mutable receiver view. The cell
does not make the stored value deeply immutable or prevent other aliases to a mutable stored object.

Capturing an ordinary `let mut` binding remains invalid. A programmer opts into shared rebinding by
storing the value in a `Cell<T>` and capturing the cell reference. An ordinary user-defined holder
class remains possible; `Cell<T>` supplies a canonical, reusable standard-library pattern.

## Compatibility and impact

This is an additive language/library capability if implemented as a standard-library type. It should
not alter the semantics of existing captures or change lambda SAM descriptors, and should require no
special resolver or compiler support. The API-index schema or standard-library API version should
change only if the chosen public representation requires it.

## Alternatives

- Implicitly capture mutable locals in compiler-generated cells — rejected because it hides aliasing
  and changes ordinary local mutation semantics.
- Require users to define a custom mutable holder class — remains a viable implementation technique,
  but does not provide a canonical, discoverable pattern.
- Add dedicated cell or capture syntax — rejected for the initial scope because current classes,
  mutable references, and by-value reference capture can express the intended sharing.

## Implementation and validation

The implementation should use ordinary Zeron class and standard-library mechanisms, with no
compiler-specific lowering. Tests should cover two closures sharing one cell, independent cells,
read-only access, mutation through permitted and rejected reference views, captured-cell lifetime
after the defining function returns, and unchanged immutable capture behavior. Verify that a mutable
cell reference captured by a lambda remains usable while a read-only cell view cannot call mutating
operations.

## Implementation decisions

- The initial API is a generic `Cell<T>` with read access and a mutating `set` operation. Additional
  operations such as `update` are not part of this proposal.
- `Cell<T>` lives in `zeron.lang`.
- The cell is unsynchronized and makes no thread-safety, immutability, exclusivity, or atomicity
  guarantee. Concurrency primitives require a separate design.

## Decision

Accepted 2026-10-13. `zeron.lang.Cell<T>` is an ordinary generic standard-library cell using
existing mutable-reference capture semantics. It exposes `get` and a mutating `set(value)`; it
makes no thread-safety, immutability, exclusivity, or atomicity guarantee. This accepts the design
only; implementation remains subject to project prioritization and normal review.
