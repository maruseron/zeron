## Abstract

This proposal explores extending the existing rank-1 generalization of immutable let-bound lambdas
beyond identity and constant-result bodies. It focuses on soundly inferring and preserving contract
constraints needed by a lambda body, while keeping mutable bindings, higher-rank polymorphism, and
operator constraints outside the initial scope.

## Motivation

Zeron currently generalizes safe unresolved parameters of immutable let-bound lambdas for direct
identity and constant-result forms. A lambda that uses a contract member cannot currently generalize
that requirement into its scheme, because the compiler does not infer and carry the necessary
contract bound. Broader support would make reusable polymorphic callbacks more useful without
requiring an explicit generic function for each case.

The generic-functions and lambda design documents explicitly defer this expansion until a sound
constraint-inference rule is defined.

## Goals

- Define a sound rule for inferring type variables and contract constraints from a lambda body.
- Preserve inferred constraints in an immutable rank-1 scheme and instantiate them independently at
  each use.
- Resolve each instantiated constraint through existing nominal conformance and witness-selection
  rules, with clear diagnostics for missing or ambiguous evidence.
- Retain the current behavior for lambdas whose parameters are already fully contextually typed.

## Non-goals

- Polymorphism for mutable or reassignable bindings.
- Nested or higher-rank schemes, explicit `forall`, or polymorphic lambda values in arbitrary
  positions.
- Inferring operator constraints; operator-witness design is separate.
- Inferring arbitrary effects or changing raised-effect semantics.

## Proposal

Extend generalization for immutable let-bound lambdas using a constraint-aware rank-1 scheme. The
scheme may quantify unresolved type variables and record only those applied contract constraints
that are required to type the lambda body. Each use instantiates fresh type variables and resolves
the recorded constraints at that use site; one use must not mutate or specialize the stored scheme
for later uses.

Constraint collection includes both direct contract-member uses in the body and the applied bounds
required by generic functions called from the body. Those callee bounds are substituted through the
call's inferred type arguments and become requirements of the inferred scheme when they depend on a
generalized lambda parameter. This keeps the inferred contract with the operation that requires it,
instead of depending on which call site is analyzed first.

Generalization must remain sound with respect to the compiler's existing value and capture rules.
The feature should not silently invent constraints from unrelated call sites, infer a common
supertype, or defer evidence errors to runtime. The exact boundary for which expressions may be
generalized must be specified before implementation.

An illustrative intended capability is a reusable immutable lambda that invokes a method from a
contract on its argument, with the necessary bound inferred and checked independently for each
application. Concrete syntax and exact inference behavior should be settled in the design phase.

## Compatibility and impact

This is additive source-language behavior. It may affect inferred types, diagnostics, and static
evidence selection, but should not change the semantics of existing well-typed programs. If scheme
constraints cross compiled-library boundaries, the API index will need to preserve them; otherwise,
the feature should remain scoped to local bindings and avoid changing the library format.

## Alternatives

- Keep lambda generalization limited to identity and constant results — preserves simplicity but
  leaves common constrained callbacks monomorphic.
- Require explicit bounded lambda syntax or named generic functions — could make constraints more
  visible but adds syntax or verbosity; consider if inference proves ambiguous.
- Infer bounds from call sites rather than the body — reject as the primary rule because the inferred
  scheme should not depend on which use happens to be visited first.

## Implementation and validation

First define a generalization boundary and representation for constrained schemes. Then test multiple
independent instantiations, applied and multiple bounds, nominal conformance, explicit witnesses,
missing and ambiguous evidence, generic callback boundaries, nested function types that remain
rank-1, and deterministic diagnostics. Confirm mutable bindings and unsupported higher-rank
positions continue to be rejected. Extend separate-compilation metadata only if public function
values actually require constrained schemes across library boundaries.

## Decision

Accepted 2026-10-13. Implement constraint-aware rank-1 schemes only for lambdas written directly as
immutable `let` initializers. Infer multiple applied-contract bounds from direct member use and
substituted requirements of generic callees. Generalize only variables absent from the captured
environment; keep raised effects fixed in the function signature. Diagnose unsatisfied constraints at
the use site with a reference to the lambda binding.

## Discussion notes

- Constraint collection should include direct contract-member uses and substituted bounds required
  by generic callees. The inferred scheme must remain independent of call-site visitation order.
- Lambdas may capture values, but only type variables independent of the captured environment may
  be generalized. Variables occurring in captured values or reference types remain fixed in the
  scheme, preventing a mutable captured object from being observed at incompatible instantiations.
- Raised effects remain concrete parts of the inferred function signature. Only type variables are
  generalized; this proposal does not introduce effect-polymorphic schemes.
- A generalized type variable may carry multiple inferred applied-contract bounds, consistent with
  the existing generic-bound model.
- If a use cannot satisfy an inferred bound, diagnose at that use, name the required applied
  contract, and point back to the lambda binding that introduced the requirement.
- Only a lambda written directly as the initializer of an immutable `let` is eligible in the initial
  implementation. Assignments, returned lambdas, and other lambda-valued expressions retain their
  current monomorphic behavior.
- Generalized schemes are limited to local immutable `let` bindings and are not serialized as
  top-level library API values.
- The scheme is compile-time-only. At each use, specialize the lambda to a monomorphic closure and
  bind the required contract evidence into that closure. Reuse one closure for each specialization
  during a dynamic execution of the `let`; distinct instantiations use distinct closure variants.
- The accepted scope is implemented. A generated template captures the lexical environment and
  caches evidence-bound erased closures by function shape and selected evidence handles for the
  lifetime of the binding. Constrained schemes remain local-only and are not serialized in the library
  API index.
