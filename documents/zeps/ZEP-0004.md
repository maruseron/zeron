## Abstract

This proposal addresses the remaining gap in coherence validation for generic contract witnesses.
The compiler rejects witness-pattern overlaps it can currently identify, but the design records that
a complete overlap solver for accepted generic patterns remains future hardening.

## Motivation

Witness selection is static and must identify at most one applicable witness for a concrete type and
fully applied contract. Generic witnesses may include applied contract arguments and prerequisite
bounds, and their metadata is consumed across separately compiled libraries. Incomplete overlap
checking risks allowing declarations whose applicability cannot be resolved consistently or
deterministically in a consumer.

## Goals

- Define coherence for every generic witness pattern the language accepts.
- Detect overlaps consistently across source declarations, active import scopes, and compiled
  library metadata.
- Produce actionable diagnostics identifying the competing patterns and relevant scope.
- Preserve static selection, orphan rules, applied-type distinctions, and existing ambiguity behavior.

## Non-goals

- Changing witness import activation or member-lookup precedence.
- Adding specialization priorities, “most specific wins” selection, or runtime witness lookup.
- Adding witness features that are currently unsupported, including mutating witness methods.
- Requiring every valid program to have a witness; absence remains a use-site resolution error when
  evidence is needed.

## Proposal

Specify a pairwise overlap rule for generic witness declarations, including target type patterns,
fully applied contract patterns, and prerequisite bounds. A pair overlaps when there exists a valid
substitution under the language's type-application rules for which both witnesses could apply to
the same target and contract in the same active scope.

For each pair of witnesses active together in a compilation unit, alpha-rename their type variables
apart and structurally unify their target patterns and fully applied contract patterns. If a
substitution satisfies both patterns, reject the pair as overlapping. Applied type structure,
repeated variables, and reference/nullability qualifiers must be compared according to source type
identity; JVM erasure must not be used. Prerequisite bounds do not make otherwise unifiable patterns
disjoint. If the checker cannot establish disjointness, conservatively report a potential overlap.

Check the active witness scope when it is assembled for a unit, even if the unit does not currently
request the evidence. The same rule applies to source declarations and witnesses reconstructed from
the versioned library index. Never select one witness by declaration order, import order, or an
undocumented specificity heuristic.

The algorithm and any conservative limits require design review. If the accepted pattern language
makes exact overlap undecidable or impractical, the proposal should define a conservative,
documented rejection rule rather than claim complete checking while permitting unchecked ambiguous
cases.

## Compatibility and impact

This is primarily a validation and diagnostic change, but it may reject programs that currently
compile because their overlap was not detected. That is a source-compatibility impact and should be
documented. The binary API-index schema should change only if existing witness metadata is
insufficient to run the agreed checks after separate compilation.

## Alternatives

- Continue rejecting only overlaps found by the current partial checks — avoids new rejections but
  leaves coherence dependent on which patterns the compiler happens to recognize.
- Allow overlaps and select the most-specific witness — changes the language's stated ambiguity
  policy and makes selection rules more complex.
- Add explicit priorities or user-selected witness names — could resolve deliberate overlaps, but
  adds a new mechanism and should be proposed separately if a concrete need arises.

## Implementation and validation

Inventory the accepted witness-pattern grammar and existing overlap checks. Define a substitution-
based overlap test for target and applied contract types, then account for prerequisite-bound
satisfiability or conservatively reject cases the solver cannot establish as disjoint. Test identical,
partially overlapping, disjoint, nested-applied, and prerequisite-constrained patterns, including
patterns split across separately compiled libraries and activated by different import scopes.
Verify diagnostics are deterministic and report both declarations.

## Open questions

- None identified in the initial coherence rule. Validate the existing API-index round trip before
  deciding whether a schema change is needed.

## Decision

Accepted 2026-10-13. Compare active witness pairs by alpha-renaming their type variables and
structurally unifying their target and fully applied contract patterns. Prerequisite bounds do not
prove otherwise-unifiable patterns disjoint. Reject overlaps when witnesses become active together
in a compilation unit, even if unused; if the checker cannot establish disjointness, reject
conservatively. Preserve import-scoped witness availability and do not add selection priorities.
Validate source and compiled-library parity, retaining the existing API-index schema unless those
tests show required metadata is missing. This accepts the design only; implementation remains
subject to project prioritization and normal review.

## Discussion notes

- Determine overlap from unifiability of the target and fully applied contract patterns. Do not use
  prerequisite bounds to prove otherwise-unifiable patterns disjoint; this avoids requiring the
  overlap checker to prove arbitrary bound satisfiability.
- Reject overlapping patterns once both witnesses are present in a compilation unit's active witness
  scope, whether or not that unit currently uses the evidence. Different packages may keep separate
  overlapping witnesses when only one is active at a time.
- If the checker cannot prove patterns disjoint, treat them as potentially overlapping and reject
  them rather than permitting a possible ambiguity.
- The current API index appears to preserve witness type parameters and their bounds, plus applied
  contract and target patterns. The design direction is to keep the current schema unless a
  source-versus-compiled round-trip test demonstrates that required overlap metadata is missing.

## Implementation status

Implemented. The overlap checker alpha-renames witness variables while preserving higher-kinded
parameter kinds, structurally unifies ordinary and partially applied constructor patterns, and
tracks alternatives when an applied higher-kinded variable can match a generic type at more than one
argument position. Distinct unresolved higher-kinded applications are treated conservatively as
potentially overlapping; prerequisite bounds do not establish disjointness. Regression tests cover
overlapping and disjoint constructor patterns, applied higher-kinded parameters, active scopes, and
source/library-index round trips. The existing library-index schema preserves the required pattern
metadata.
