## Abstract

This proposal adds generic effect declarations and exact applied-effect identity for **closed**
applications. An effect such as `Failure<T>` may be applied as `Failure<Int>` in a `raise`,
`raises`, handler case, or function type. Applications are invariant, exact, and must be fully
written; a type parameter, `_`, or a wildcard cannot appear in an effect application.

Runtime identity uses the implemented descriptor from [ZEP-0015](./ZEP-0015.md). A generic effect
payload stores its application descriptor, and a handler compares that descriptor before binding
the payload. Non-generic effects remain unchanged and carry no descriptor.

The 2026-11-10 revision narrows the earlier proposal and settles its design. Generic propagation of
applied effects through type variables, reified effect variables in handlers, omitted handler
arguments, wildcards, and applied `under` edges are deferred. The first implementation is small
enough to validate exact identity without reopening the descriptor design or prematurely committing
to applied ancestry. All six former open questions are resolved in "Settled design decisions".

## Revision note

The 2026-11-09 text proposed generic effect identity through generic calls, forwarding, and handler
variables in one step. That scope depended on general descriptor forwarding and eventually on
applied ancestry. This revision starts with closed applications instead:

- generic effect declarations and payload typing are added;
- every effect application in an effect set or handler is closed and explicitly applied;
- construction at a closed site stores a ZEP-0015 descriptor in the payload;
- exact handler dispatch and separate compilation are implemented;
- generic effect forwarding, effect variables, omitted arguments, and applied `under` move to
  follow-up work.

## Motivation

The current effect system supports non-generic effect declarations and exact nominal matching.
An effect cannot encode a type parameter in its payload type, so a typed failure or request cannot
retain its payload type through raising and handling.

The earlier proposal treated generic effects as the first stress test for descriptor forwarding
through arbitrary generic code. With the descriptor facility now implemented and the ZEP-0104
existential consumer validated, the risky part is not descriptor construction. It is deciding how
applied effect identities flow through effect-kinded variables, handler coverage, and `under`.
Those decisions can be separated from the basic applied-payload feature, and they are now settled
below.

## Goals

- Allow effect declarations to declare type parameters used by their payload properties and
  methods.
- Give closed applications such as `Failure<Int>` exact, invariant runtime identity.
- Reuse the ZEP-0015 descriptor instead of introducing an effect-specific token.
- Preserve non-generic effects with no descriptor field and no added per-raise allocation.
- Keep exact matching and separate-compilation behavior deterministic.
- Provide a smaller first implementation that can be validated before generic effect propagation or
  applied ancestry is designed.

## Non-goals

- Constructing, raising, forwarding, or handling `Failure<T>` where `T` is a type parameter.
- Handler cases over `T: effect + reified`.
- Omitted effect arguments inferred from the protected expression.
- Wildcard or existential effect applications such as `Failure<_>` or `Failure<?>`.
- Applied `under` edges or ancestor-aware matching; see [ZEP-0107](./ZEP-0107.md).
- Effect-row polymorphism or inferred effect-set variables.
- Stored existentials, contract-bound runtime tests, asynchronous effects, or resumable
  continuations.
- Function types as effect type arguments.
- Generic `external` effect declarations, or generic effects declared over Java classes.
- Automatic conversion among Java exceptions, `Result`, and raised effects.

## Proposal

**Implementation status (2026-11-12).** The closed-application slice is implemented. Generic
effect declarations are accepted, applied effects are validated for closed arguments, payloads
carry one cached ZEP-0015 descriptor through canonical and named constructors, and handler cases
select by erased class plus exact descriptor equality before binding. `case Effect`, positional
payload patterns, `as` bindings, nullable and nested applications, OR alternatives, `E: effect`
instantiation with an applied effect, and separate-compilation round trips are covered by
`GenericEffectCompilationTest`. Non-generic payloads remain descriptor-free. Generic propagation
through type variables, effect-variable handlers, omitted arguments, wildcards, applied ancestry,
and generic `external` effects remain outside this slice as designed.

### Declaration and closed application

A generic effect declaration may declare type parameters used by its payload and members:

```zeron
public effect Failure<T> {
    public property value: T;
}
```

A generic effect application must supply every type argument, and every supplied argument must be a
closed source type:

```zeron
fn fail(): Unit raises Failure<Int> {
    raise Failure<Int>(42);
}
```

The following are rejected in this slice:

- `Failure<T>` or any other application mentioning a type parameter;
- `Failure<_>`;
- `Failure<?>` or any existential/wildcard application;
- an unapplied `Failure` where a generic effect is expected;
- an omitted type argument inferred from a handler's protected set.

Non-generic effect declarations and uses are unchanged. Effect declarations parsed as class
declarations currently reject type parameters outright; that restriction is relaxed for effects
while the closed-application rules below remain enforced during resolution.

### Admissible type arguments

An effect application's arguments are ordinary closed type descriptors, with these rules:

- Admitted: nominal classes and effects, primitives, arrays, nullable forms, and nested generic
  applications such as `Failure<List<Int>>` or `Failure<Pair<String, Int>>`.
- Rejected: type parameters, `effect`/`effect...` parameters and row variables, `_`, `?`, star and
  other type projections, raw or unapplied generic types, and function types.
- Ordinary generic bounds apply: a supplied argument must satisfy the declared bounds of the
  corresponding parameter, using the existing type-argument validation and its diagnostics.

An effect type used as an argument (`Failure<NotFound>`) is simply its nominal payload type; no
special reasoning about effects nested inside an identity is introduced.

### Exact identity and payload descriptor

Generic effect arguments are invariant and participate in exact applied-effect identity.
`Failure<Int>` and `Failure<String>` are different identities even though the JVM payload class is
erased to the same `Failure` class.

A generic effect payload carries a ZEP-0015 `AppliedTypeDescriptor` describing its application.
At a closed construction site the compiler stores a cached constant descriptor
(`AppliedTypeDescriptors.lookup`), so repeated construction of the same application reuses one
constant instance. The generated payload has one final descriptor field and one hidden constructor
parameter; canonical and named constructors forward the same descriptor unchanged. Non-generic
effects have no descriptor field. Raising, forwarding, or re-raising an already-constructed payload
does not allocate or recompute its descriptor.

Identity is the full structural descriptor: expanded owner name, recursively applied arguments, and
array, nullability, and mutability markers. Consequently `Failure<Int>`, `Failure<Int?>`, and
`Failure<List<Int>>` are three distinct identities, and aliases are expanded before comparison.

The descriptor is an identity value, not contract evidence. A generic effect's payload properties
remain statically typed from the application's type arguments at construction and handler sites;
the descriptor only establishes that the handler selected the same application.

### Matching rules

- **Exact matching.** A handler case for `Failure<Int>` covers only `Failure<Int>`. Argument
  variance, wildcard matching, and ancestor matching are not part of this slice.
- **Fully written cases.** A generic effect case must spell all type arguments. Omitting them is an
  error even when the protected expression contains only one application; inference is deferred.
- **Payload binding.** A case matches when the payload class is assignable to the case's erased
  effect class *and* the payload's descriptor equals the case's constant descriptor. Only then are
  the erased payload fields cast to the types implied by the handler's applied effect.
- **Coverage.** A handler removes exactly the closed applications named by its irrefutable cases.
  Other applications of the same effect declaration, and every other effect, remain in the residual
  row. Guarded or refutable cases do not establish coverage.
- **Row inclusion.** `raises` and function-type effect sets compare exact applied identities.
  `raises Failure<Int>` is not satisfied by `raises Failure<Int?>`, `raises Failure<String>`, or a
  bare `raises Failure`.
- **No applied ancestry.** Generic effects cannot participate in `under` in this slice. Nominal
  `under` behavior for non-generic effects is unchanged.
- **Top effect.** Every application is covered by `Effect` from [ZEP-0013](./ZEP-0013.md). An
  unguarded `case Effect` handles any application and binds the payload through the `Effect` view;
  that view exposes no descriptor and cannot be cast to the applied payload type.

### Handler case syntax

No new grammar is required. A handler case is already a match pattern plus an effect
`TypeDescriptor`, so the applied form reuses the existing spellings:

```zeron
handle (load(id)) with {
    case Failure<Int> as failure -> failure.value;
    case Failure<String>(_) -> -1;
    case Failure<List<Int>> as failure -> failure.value.count;
}
```

- `case Failure<Int> as failure -> …` binds the payload as the applied type, so member access is
  typed from the application's arguments after substitution.
- `case Failure<Int>(_) -> …` uses the existing extractor-pattern spelling for a payload pattern that
  ignores the payload.
- OR-pattern alternatives must denote the same applied type, compared as exact descriptors,
  matching the existing rule that handler alternatives name one effect type.
- An applied case whose arguments are not closed is a diagnostic, not a deferred inference site.

### Foreign and raw payloads

A descriptor is trusted only when it is present and matches the case. A payload produced outside
generated Zeron constructors (for example a Java object that implements the effect marker, or a
payload created reflectively) can carry a null or mismatched descriptor. Such a payload:

- matches no generic handler case;
- propagates like any unmatched effect;
- remains catchable by `case Effect`, which never casts it to an applied payload type.

No new runtime exception, reflection check, or fail-fast validation is introduced: the matching rule
is already fail-safe because a mismatch cannot bind a payload. Generic `external` effect
declarations are rejected, and a raw payload cannot be constructed as a generic application by the
compiler, so this rule only governs values that enter from outside the language.

### Generic propagation boundary

Generic code may continue to use effect-kinded parameters from
[ZEP-0055](./ZEP-0055.md) to propagate nominal effects. It cannot use those parameters to form a
generic effect application such as `Failure<E>`, and it cannot handle an applied effect whose
arguments are not known statically.

An `E: effect` parameter may be *instantiated* with a closed applied effect, because a closed
application is one nominal effect. `Failure<Int>` is therefore usable wherever a single effect type
is expected, including `raises E`. This is a validation requirement on effect-kind argument
checking, not a new inference rule.

This boundary avoids adding hidden descriptor parameters for effect construction, reified effect
variables in handlers, and inferred effect applications before their coverage rules are designed.

### Library index

Schema 13 is sufficient; no new record and no bump are required. The requirements are:

- generic effect declarations reuse the ordinary generic declaration export, which already carries
  type parameters, the `effect` flag, `underEffects`, payload members, and constructor metadata;
- closed applied effect entries in `raises`, function types, and handler types reuse the existing
  applied-type wire format (type code 9, base name plus arguments);
- the ZEP-0015 descriptor schema version is unchanged, so descriptors stay comparable across
  duplicate library copies.

Validation must still round-trip `raises Failure<Int>`, `raises Failure<List<Int>>`, handler case
types, and function-type effect sets through a separately compiled library. If that round trip
reveals a missing field, the fix is a coordinated schema revision with
[ZEP-0107](./ZEP-0107.md) and no separate effect-specific encoding.

### Diagnostics

| Situation | Result |
| --- | --- |
| `raises Failure<T>` in a generic body | Rejected: an effect application must be closed |
| `raises Failure` where an effect is expected | Rejected: missing type arguments |
| `Failure<_>`, `Failure<?>`, star projection argument | Rejected: effect applications are invariant and closed |
| `case Failure ->` (no arguments) | Rejected: a handler case must fully apply a generic effect |
| `under Failure` or `under Failure<Int>` | Rejected: a generic effect cannot be an effect supertype |
| Type argument violates a declared bound | Existing type-argument bound diagnostic |
| Argument is a function type | Rejected at descriptor construction, as in ZEP-0015 |
| Generic `external` effect declaration | Rejected: external effect declarations remain non-generic |

Diagnostics name the effect, the offending argument, and the expected closed application.

### Deferred broader generic effects

The following are intentionally outside this proposal and require follow-up designs:

- generic effect applications containing a type parameter;
- handler cases over reified effect variables;
- omitted handler arguments and inference from protected sets;
- wildcard/existential effect cases;
- applied `under` edges and ancestor-aware matching (ZEP-0107);
- effect-row polymorphism;
- function types as effect arguments.

A later proposal may build on the closed-application implementation and the descriptor facility
without changing this proposal's exact-identity rules.

## Compatibility and impact

Non-generic effect programs keep their current identity, dispatch, and performance behavior; the
existing acceptance test already asserts that their payloads have no descriptor field or constructor
parameter. Generic effect declarations add a descriptor field only to their own payload layouts and
constructor ABI, and they keep the erased class name, so existing nominal `instanceof` dispatch
remains the first part of every match.

The library index must preserve closed applied `raises` entries so separately compiled clients can
validate raised sets and handler coverage. Exact comparisons must remain stable across duplicate
library copies and index-schema versions.

Source compatibility: previously rejected programs (`effect Failure<T>`, applied `raises`, applied
handler cases) become valid; no valid program changes meaning, because no non-generic effect can be
named with type arguments and no existing handler case can match an applied effect.

## Alternatives

- **Original broad generic-effect scope** — allows generic propagation and handler variables, but
  depends on reified effect variables, applied coverage rules, and eventually applied ancestry.
  Deferred rather than rejected.
- **Nominal identity only for generic effect declarations** — simplest, but `Failure<Int>` and
  `Failure<String>` would be indistinguishable and a handler could bind the wrong payload type.
  Rejected for this slice.
- **Erased payload typing without identity** — permits typed construction but cannot safely match
  applications at runtime. Rejected.
- **Effect-specific descriptor** — duplicates ZEP-0015 and risks identity drift. Rejected.
- **Applied ancestry first** — broader and riskier than exact closed matching; remains in
  ZEP-0107.
- **Carry the descriptor on the `RaisedEffect` carrier instead of the payload** — works for raising
  but loses identity on stored or re-raised payload values, and would add a field to every raise,
  including non-generic ones. Rejected.
- **Infer omitted handler arguments from the protected set** — convenient for one-application
  bodies, but makes coverage depend on inference order and breaks the "fully written" rule that
  keeps dispatch exact. Deferred.
- **Fail fast on a null or forged descriptor** — would turn a foreign payload into a runtime error
  inside dispatch. Rejected in favor of letting it propagate to `case Effect`, which cannot
  misinterpret it.

## Implementation and validation

1. Relax the parser and resolver restriction on generic effect declarations while preserving
   existing effect rules (`effect` flag, `under`, payload members, constructors).
2. Enforce closed applications during type resolution for `raises`, function-type effect sets,
   handler cases, and construction sites, with the diagnostics table above.
3. Emit one descriptor field and hidden constructor parameter on generic effect payload classes,
   constant descriptors at closed construction sites, and descriptor forwarding through canonical and
   named constructors.
4. Implement dispatch as erased-class test plus descriptor equality before payload casting, and
   extend coverage and row inclusion to exact applied identities.
5. Preserve generic effect declarations and closed applied `raises` entries through the library
   index without a schema bump; verify separately compiled and duplicate-library round trips.
6. Test:
   - generic effect declaration, construction, raise, propagation, and handling;
   - exact matching between `Failure<Int>` and `Failure<String>`, and between `Failure<Int>` and
     `Failure<Int?>`;
   - nested application (`Failure<List<Int>>`) construction, matching, and index round trip;
   - payload typing and casts after a successful descriptor match, including member access on the
     bound alias;
   - `case Failure<Int>(_)` extractor and `as` binding forms, and OR-pattern alternatives that name
     the same versus different applications;
   - rejection of type-variable applications, `_`, wildcards, projections, function-type arguments,
     omitted arguments, unapplied handler cases, and applied `under`;
   - bound violations on effect type arguments;
   - `case Effect` catching an application, and the applied payload type being unavailable from that
     arm;
   - a null-descriptor or mismatched-descriptor payload matching no generic case and propagating;
   - duplicate identical applications normalized to one entry with first-occurrence order preserved,
     while `Failure<Int>` and `Failure<String>` remain distinct;
   - `E: effect` instantiated with `Failure<Int>` and used in `raises E`;
   - non-generic effects remaining descriptor-free;
   - separate-compilation and duplicate-library boundaries;
   - no descriptor allocation during re-raise/forwarding.
7. Measure construction, raise, exact handler dispatch, failed descriptor comparison, and
   separate-compilation costs; record the rows in the ZEP-0015 matrix as the applied-effect gates
   when implemented.

## Open questions

None. The six former open questions are resolved in "Settled design decisions"; anything still
undecided is listed under "Deferred broader generic effects" and owned by another proposal.

## Settled design decisions (2026-11-10)

- **Index schema.** Schema 13 is sufficient. Applied types already use wire type code 9, `raises`
  entries are written through the generic type writer, and generic declaration exports already carry
  type parameters plus the effect flag. No new record and no bump.
- **Handler case binding.** No new syntax: `case Failure<Int> as failure -> …` and
  `case Failure<Int>(_) -> …`. Handler arms already store an effect `TypeDescriptor`, so the parser
  stops rejecting applied base types for effects and resolution checks that arguments are closed and
  satisfy bounds. Member access is typed by substituting the application's arguments into the payload
  declaration.
- **`under` on generic effect declarations.** A generic effect may declare only non-generic effect
  parents. The parser already rejects type arguments after `under`; resolution must additionally
  reject a generic effect named as a parent, because a bare name would quantify over applications and
  contradict exact identity.
- **Generic effect as a parent.** Not allowed in this slice, for the same reason. A non-generic
  effect cannot declare `under Failure`; applied ancestry and any notion of "all applications of X"
  remain in ZEP-0107.
- **Foreign payloads.** Dispatch requires class assignability and a non-null descriptor equal to the
  case's constant. A null, forged, or mismatched descriptor matches no generic case, propagates, and
  is catchable only through `case Effect`, which never casts to the applied payload type. No new
  runtime exception or reflection check is added, and generic `external` effects are rejected.
- **Duplicate applications.** `EffectRows.normalize` already collapses identical entries through an
  insertion-ordered set, so duplicates keep the position of first appearance and distinct
  applications keep their relative order for diagnostics.
- **Admissible arguments.** Closed nominal types, primitives, arrays, nullable forms, nested
  applications, and effect types; never type parameters, row variables, `_`, `?`, projections, or
  function types; declared bounds are enforced with existing validation.
- **Identity strength.** Full structural descriptor equality, including nullability and mutability
  markers; aliases expanded; no variance or subtyping except coverage by `Effect`.
- **Descriptor exposure.** The descriptor is internal identity. No public accessor is added in this
  slice, and the `Effect` view does not expose it.
- **Descriptor ownership.** Generic payloads carry the descriptor; the carrier does not; non-generic
  payloads remain descriptor-free.

## Decision

Accepted 2026-11-10. The closed-application design above is approved as the direction for generic
effect payloads, with these fixed points:

- generic effect declarations declare type parameters used by their payload;
- applications are invariant, exact, fully written, and closed;
- identity is the shared ZEP-0015 structural descriptor carried by the payload;
- handlers compare the descriptor before binding, with the fail-safe foreign-payload rule;
- coverage and row inclusion use exact applied identity plus `Effect` coverage;
- `under` remains nominal-only and no generic effect may be an effect supertype;
- schema 13 introduced declarations, applied `raises` entries, and handler case types; ZEP-0106
  raises the wire version to schema 14 by adding stored-existential holder metadata, without
  changing these records.

The proposal is implemented and remains a `Candidate` for the `0.7.0` bundle, paired with
[ZEP-0122](./ZEP-0122.md). Generic propagation through type variables,
effect-variable handlers, omitted handler arguments, wildcards, applied ancestry, and generic
`external` effects remain outside this scope. Applied ancestry stays with ZEP-0107, which depends on this design.
