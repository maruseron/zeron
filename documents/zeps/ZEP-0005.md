# ZEP-0005: Typed Effect Subtyping and Generic Payloads

## Status

Draft

## Author

Marcelo Rodríguez

## Created

2026-10-13

## Related ZEPs

- None.

## Abstract

This proposal explores extending typed raised effects from exact, non-generic nominal identities to
support generic effect payload types and effect subtyping. It will define how these features
interact with `raises` sets, function-type compatibility, handler matching, and separately compiled
libraries before any implementation is approved.

## Motivation

The initial effect system supports non-generic effect declarations and exact nominal matching.
Consequently, an effect cannot encode a type parameter in its payload type, and a handler cannot
handle a declared super-effect in place of a particular subtype. The effect design lists both
generic payloads and effect subtyping as possible follow-up work.

These features are related: once effect identity includes applied arguments or subtype relations,
propagation, coverage, and function compatibility need rules that do not conflate ordinary value
subtyping with effect-set inclusion.

## Goals

- Define generic effect declaration and application semantics, if accepted.
- Define effect subtyping and the relationship between subtype matching and exact payload typing.
- Specify propagation, handler coverage, raised-set inclusion, inference, and separate-compilation
  metadata together.
- Preserve the distinction between typed control-flow effects and ordinary `Result` values or Java
  exceptions.

## Non-goals

- Effect-row polymorphism or inferred polymorphic effect variables.
- Asynchronous effects or resumable continuations; resumability is considered separately in
  [ZEP-0007](./ZEP-0007.md).
- Automatic conversion between Java exceptions, `Result`, and raised effects.

## Proposal

Design generic effects and effect subtyping as a coordinated extension. A generic effect would carry
one or more applied payload type arguments, and a subtype relation would permit a raised subtype to
satisfy an appropriate super-effect declaration or handler. The design must determine whether
subtyping applies to the effect declaration, its type arguments, or both, and whether ordinary class
inheritance can participate.

`raises` compatibility should remain a statically checked relation between effect sets. Function
values must be assignable only when the implementation's possible effects are permitted by the
expected function type. A handler removes only the effects it demonstrably covers; partial or
refutable payload patterns must not falsely establish coverage. Handler arms may still raise effects
in the enclosing scope.

The design phase should evaluate whether these capabilities should be one change or staged
independently. It must not assume covariance, contravariance, or matching by erased JVM class.

## Compatibility and impact

This changes source-level effect identity and may change function-type compatibility and handler
coverage. The compiled-library index must preserve enough information to revalidate generic effect
applications and subtype relationships in consumers. An index schema update is required if existing
metadata cannot represent the accepted model. Runtime dispatch must continue to distinguish effect
payloads safely after JVM erasure.

## Alternatives

- Retain exact nominal matching and non-generic effects — simplest and remains a valid choice if
  demonstrated use cases do not justify the added type-system complexity.
- Add generic effects first, postponing subtyping — reduces coupling but leaves the relationship
  between generic effect arguments and matching unresolved for later.
- Add subtyping first, postponing generic payloads — may address effect hierarchies but still cannot
  parameterize effect payload contracts.

## Implementation and validation

Inventory all effect-set operations in declarations, function types, calls, handlers, lambdas,
constructors, external mappings, and API-index serialization. Specify static matching and
subtyping before runtime representation. Tests should cover exact and subtype coverage, generic
argument substitution, function-type assignment, partial handlers, guarded patterns, nested
handlers, separately compiled libraries, and erased-runtime dispatch without accidental catches.

## Open questions

- Should effect subtyping be declared explicitly, derived from nominal class inheritance, or use a
  dedicated effect hierarchy?
- Are generic effect arguments invariant, or does any variance make semantic and runtime matching
  clearer?
- Does handling a super-effect cover every subtype, and how are subtype-specific payload patterns
  represented?
- Should generic effects and subtyping ship together or as independent increments?
- How are multiple inherited effect paths and ambiguous subtype relations diagnosed?
