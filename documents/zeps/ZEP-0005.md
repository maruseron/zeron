# ZEP-0005: Generic Effect Payloads

## Abstract

This proposal explores extending typed raised effects from exact, non-generic nominal identities to
support generic effect payload types. It defines exact applied-effect identity, propagation, handler
matching, and separately compiled metadata. Effect subtyping is considered separately in
[ZEP-0013](./ZEP-0013.md).

## Motivation

The initial effect system supports non-generic effect declarations and exact nominal matching.
Consequently, an effect cannot encode a type parameter in its payload type. Generic effects would
allow a raised effect to carry a statically typed payload while preserving exact matching and
Zeron's invariant generic type model.

## Goals

- Define generic effect declaration and application semantics.
- Specify exact matching, propagation, handler coverage, raised-set inclusion, and type-argument
  inference.
- Define a sound runtime identity representation after JVM erasure and preserve it in separately
  compiled-library metadata.
- Preserve the distinction between typed control-flow effects and ordinary `Result` values or Java
  exceptions.

## Non-goals

- Effect subtyping, which is addressed separately in [ZEP-0013](./ZEP-0013.md).
- Effect-row polymorphism or inferred polymorphic effect variables.
- Asynchronous effects or resumable continuations; resumability is considered separately in
  [ZEP-0007](./ZEP-0007.md).
- Automatic conversion between Java exceptions, `Result`, and raised effects.

## Proposal

Generic effect arguments are invariant and form part of exact applied-effect identity. Handler cases
name applied generic effect types; omitted arguments may be inferred only when the protected
expression uniquely determines them. A handler removes only effects it demonstrably covers;
partial or refutable payload patterns must not falsely establish coverage. Handler arms may still
raise effects in the enclosing scope.

`raises` compatibility remains a statically checked relation between effect sets. Function values
are assignable only when the implementation's possible effects are permitted by the expected
function type. The runtime representation must distinguish applied effect identities soundly after
JVM erasure, including effects propagated through generic calls and separately compiled libraries.
Matching only the erased JVM effect class is not sufficient; no particular type-token shortcut is
assumed.

## Compatibility and impact

This changes source-level effect identity and affects function-type compatibility and handler
coverage. The compiled-library index must preserve enough information to revalidate generic effect
applications in consumers. An index schema update is required if existing metadata cannot represent
the model. Runtime dispatch must distinguish applied effect identities safely after JVM erasure.

## Alternatives

- Retain exact nominal matching and non-generic effects — simplest and remains a valid choice if
  demonstrated use cases do not justify the added type-system complexity.
- Add effect subtyping first — independent hierarchies can be explored, but do not parameterize
  effect payloads; subtyping is tracked separately in ZEP-0013.

## Implementation and validation

Inventory all effect-set operations in declarations, function types, calls, handlers, lambdas,
constructors, external mappings, and API-index serialization. Specify exact applied-effect matching
and sound runtime identity before implementation. Tests should cover generic argument substitution,
function-type assignment, partial handlers, guarded patterns, nested handlers, separately compiled
libraries, and erased-runtime dispatch without accidental catches.

## Open questions

- What runtime representation preserves applied effect identity through direct raises, generic
  calls, handlers, and separately compiled consumers without relying on erased JVM classes alone?
- What library-index changes are required to carry this identity across compilation boundaries?

## Decision

Deferred until Zeron has a sound runtime type-reification strategy capable of preserving applied
effect identity. This prerequisite is explored in [ZEP-0015](./ZEP-0015.md). Effect subtyping is
scoped separately in [ZEP-0013](./ZEP-0013.md).

## Discussion notes

- Stage generic effect payloads independently from effect subtyping. The generic-effect stage keeps
  exact effect matching; subtyping remains a separate future design rather than a dependency.
- Generic effect arguments are invariant and participate in exact applied-effect identity, matching
  Zeron's existing generic type model.
- Handler cases name applied generic effect types. Type arguments may be omitted only when the
  protected expression uniquely determines them.
- Do not implement generic effects by matching only the erased JVM effect class or by adding runtime
  type tokens as an assumed shortcut. Defer implementation until applied effect identity has a sound
  runtime representation, including through generic calls.
- Park this proposal until the general runtime type-reification design in ZEP-0015 establishes a
  sound identity model; do not pursue an effect-specific runtime identity mechanism in isolation.
