# ZEP-0006: First-Class Reusable Typed-Effect Handlers

## Status

Draft

## Author

Marcelo Rodríguez

- [ZEP-0007](./ZEP-0007.md) — resumable algebraic effects are a separate runtime model.

## Abstract

This proposal explores representing handlers for the existing abortive typed-effect system as
first-class values that can be named and reused, instead of requiring every handler to be written
directly around one protected expression.

## Motivation

The current `handle (expression) with { ... }` form handles raised effects locally and synchronously.
The effects design identifies named, reusable handler values as a possible extension, while
explicitly distinguishing them from continuation-resuming algebraic handlers.

Reusable handlers could reduce repeated case definitions and let APIs accept handling policy as a
value, but their input, output, coverage, and propagation types need definition.

## Goals

- Determine a source-level model for naming, passing, composing, and applying effect handlers.
- Preserve the current abortive behavior unless a separate resumability design is accepted.
- Specify handler input/output types, handled-effect sets, and effects raised by handler cases.
- Preserve explicit coverage: unhandled effects continue outward rather than being silently erased.

## Non-goals

- Capturing or resuming continuations.
- Catch-all handling that silently converts every effect to a default value.
- Replacing ordinary `match` for value inspection.
- Introducing asynchronous or thread-local effect handling.

## Proposal

Explore an immutable first-class handler value that can be applied to an expression or computation
with a statically known effect set. The handler type must express which effects it can handle, the
normal result type it expects, the result type it produces, and the effects its own cases may raise.
The design must define how uncovered effects propagate and how a handler's coverage composes with
the current expression-scoped handler.

Handlers remain abortive in this proposal: a matched case receives the effect payload and produces a
result, but does not resume the suspended computation. Keep syntax provisional until the type model
is clear; do not add a handler function type solely to mirror the current `with` syntax.

## Compatibility and impact

This is additive but may extend function/type descriptors and API-index signatures if handlers cross
library boundaries. Existing `handle` expressions should retain their current coverage, result-type,
and runtime behavior. Generated handler values must not change JVM function-shape identity unless
the source-level callable signature itself requires it.

## Alternatives

- Keep handlers expression-scoped — avoids a new abstraction and remains sufficient for local use.
- Factor repeated handling into ordinary functions that contain `handle` expressions — uses existing
  language features but cannot pass a handler policy independently of the operation being performed.
- Use a general callback that receives an effect payload — loses typed coverage and propagation
  guarantees unless it recreates the handler semantics.

## Implementation and validation

Specify the handler type and application rules first. Validate named and passed handlers, generic
effect declarations if separately accepted, partial coverage, nested/reused handlers, handler-case
effects, generic functions accepting handler values, and compiled-library round trips. Confirm
unmatched carriers are rethrown unchanged and ordinary Java exceptions remain outside the handler.

## Open questions

- Does a reusable handler apply to one expression, a function invocation, or a delimited computation?
- How does its type encode the normal path and handler-arm result types?
- Are handler values partial by default, and how are their remaining effect sets represented?
- What is the simplest safe composition operation, if composition is included at all?
