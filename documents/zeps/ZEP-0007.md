## Abstract

This proposal explores whether Zeron should ever support fully resumable algebraic effects, in
which a handler can resume a suspended computation after handling an operation. It is an
architecture investigation, not an implementation commitment or an extension of the current
abortive `raise` behavior by assumption.

## Motivation

Current raised effects are implemented by throwing a runtime carrier and unwinding the JVM stack to
an expression handler. A handler returns a value but cannot resume the computation at the raise
site. Fully resumable effects would enable a different control abstraction, but require capturing
and invoking continuations and could substantially change compiler and runtime architecture.

## Goals

- Evaluate whether resumable effects provide concrete value beyond the existing abortive system.
- Identify semantic choices such as one-shot versus multi-shot resumption, deep versus shallow
  handlers, and behavior when a continuation escapes or is resumed more than once.
- Compare plausible implementation strategies, including compiler-managed CPS transformation.
- Document performance, debugging, stack-trace, interoperability, and separate-compilation costs.

## Non-goals

- Implementing resumable effects in this proposal.
- Treating virtual threads as arbitrary continuation capture.
- Changing existing `raise` or `handle` semantics before a compatible migration design exists.
- Conflating ordinary raised effects with `Result`, resource cleanup, or Java exceptions.

## Proposal

Conduct a bounded architecture and semantics exploration before deciding whether resumable effects
belong in Zeron. Begin with concrete use cases that cannot be expressed adequately with the current
abortive effects, callbacks, or ordinary control flow. Specify the continuation contract and handler
delimitation model before evaluating implementation feasibility.

Compare a compiler-managed continuation transformation, initially considering one-shot continuations,
against alternatives such as explicit continuation-passing APIs or retaining the current model.
Document how resumptions interact with mutable references, exceptions, resource scopes, nested
handlers, Java calls, lambdas, and generic functions. Do not promise arbitrary continuation capture
from JVM or Project Loom facilities without evidence that the required semantics are supported.

The exploration should conclude with a recommendation to proceed with a separate implementation
ZEP, defer the feature, or reject it for the foreseeable future.

## Compatibility and impact

A resumable system is likely to affect control-flow lowering, runtime support, debugging, and the
compiled ABI. It may require a distinct operation/handler model rather than changing the existing
exception-carrier implementation in place. No binary or source compatibility decision is made here.

## Alternatives

- Retain abortive typed effects — preserves the small, synchronous runtime model and may be adequate
  for the project's use cases.
- Use explicit callbacks or continuation-passing APIs in libraries — keeps control flow visible but
  does not offer language-managed resumption.
- Add reusable abortive handlers under ZEP-0056 and ZEP-0057 — improves reuse without continuation
  capture.

## Implementation and validation

The exploratory deliverable should be a written comparison with at least one representative use
case and one prototype or feasibility spike only if needed to resolve a concrete runtime question.
It should identify required compiler/runtime phases, ABI consequences, error handling and cleanup
semantics, and measurable performance constraints. A full implementation plan requires a later
proposal.

## Open questions

- Are continuations one-shot or multi-shot, and how is this enforced?
- Are handlers deep or shallow, and what happens when a resumed continuation raises again?
- How do `using` cleanup and other `finally`-like obligations behave across suspension and resumption?
- Can the feature support foreign Java frames, or are such calls continuation barriers?
- Is there a compelling use case that justifies transformation complexity and runtime overhead?

## Decision

Deferred 2026-10-13. Do not spend an architecture or implementation cycle on resumable effects
until a concrete use case demonstrates a need that the current abortive effects, callbacks, and
ordinary control flow do not meet. One-shot versus multi-shot, deep versus shallow handlers,
resource-cleanup behavior, and foreign-call boundaries remain intentionally undecided.
