## Abstract

This proposal explores whether Zeron should ever support fully resumable algebraic effects, in
which a handler can resume a suspended computation after handling an operation. It is an
architecture investigation, not an implementation commitment or an extension of the current
abortive `raise` behavior by assumption.

## Motivation

Current raised effects are implemented by throwing a runtime carrier and unwinding the JVM stack to
an expression handler. A handler returns a value but cannot resume the computation at the raise
site. Fully resumable effects would enable a different control abstraction, but require capturing
and invoking continuations and could substantially change compiler and runtime architecture.

## Goals

- Evaluate whether resumable effects provide concrete value beyond the existing abortive system.
- Identify semantic choices such as one-shot versus multi-shot resumption, deep versus shallow
  handlers, and behavior when a continuation escapes or is resumed more than once.
- Compare plausible implementation strategies, including compiler-managed CPS transformation.
- Document performance, debugging, stack-trace, interoperability, and separate-compilation costs.

## Non-goals

- Implementing resumable effects in this proposal.
- Treating virtual threads as arbitrary continuation capture.
- Changing existing `raise` or `handle` semantics before a compatible migration design exists.
- Conflating ordinary raised effects with `Result`, resource cleanup, or Java exceptions.

## Proposal

Conduct a bounded architecture and semantics exploration before deciding whether resumable effects
belong in Zeron. Begin with concrete use cases that cannot be expressed adequately with the current
abortive effects, callbacks, or ordinary control flow. Specify the continuation contract and handler
delimitation model before evaluating implementation feasibility.

Compare a compiler-managed continuation transformation, initially considering one-shot continuations,
against alternatives such as explicit continuation-passing APIs or retaining the current model.
Document how resumptions interact with mutable references, exceptions, resource scopes, nested
handlers, Java calls, lambdas, and generic functions. Do not promise arbitrary continuation capture
from JVM or Project Loom facilities without evidence that the required semantics are supported.

The exploration should conclude with a recommendation to proceed with a separate implementation
ZEP, defer the feature, or reject it for the foreseeable future.

## Mechanism: monadic lowering of a handled block

Recorded 2026-11-10. This section analyzes the most concrete proposal received so far: generalize a
block-bodied handler into a monadic chain, so the compiler rewrites a handled block into binds that
end in a handler-driven evaluation. It is recorded here because the encoding, not the surface
syntax, decides whether the feature is worth its price.

### Shape of the rewrite

The block surface in the first snippet is the one proposed in [ZEP-0110](./ZEP-0110.md); it is used
here only to fix the example. The rewrite below is illustrative and is not proposed syntax.

```zeron
handle {
    let record = db.find(id);
    let account = repo.account(record.owner);
    return account.user;
} with {
    case NotFound as missing -> guest(missing.id);
    case DbError as failure -> guest(0);
}
```

would become, in the proposal's own shape:

```zeron
EffectContinuation.pure(unit)
    .flatMap { _ -> db.find(id) }                    // row {DbError | R}
    .flatMap { record -> repo.account(record.owner) } // row {DbError, NotFound | R}
    .flatMap { account -> EffectContinuation.pure(account.user) }
    .evaluate(handler)                                // covered labels removed, R escapes
```

### What the rewrite means

`.flatMap { rest }` captures everything after the operation as a continuation, and `evaluate` runs
it. That is resumption. The current abortive handler returns the protected expression's result type
and never re-enters the raise site, so this rewrite is not an alternative surface over the existing
implementation; it is a new control mechanism expressed as data. It therefore inherits this
proposal's questions (one-shot versus multi-shot, deep versus shallow, escaping continuations) rather
than sidestepping them.

### The two effect kinds behave differently

- **Abortive effects.** When no handler case continues, every chain short-circuits and the monadic
  encoding is `Either` over a coproduct. It adds a wrapper type and one closure per bind without
  adding expressive power over the current carrier.
- **Suspending effects.** `await`, `yield`, and state-based protocols need the handler to continue
  with a value at the raise site. Only here is the continuation load-bearing, and only here is the
  encoding a genuine gain.

One lowering cannot serve both without charging the abortive case for the suspending case's
machinery. That split is the central finding of this section.

### Type-system requirements

A faithful encoding needs more than `Monad<M<_>>`:

1. **Every raise site changes type.** Today `raise` has type `Never`. In the encoding an operation
   produces `EffectContinuation<{L | R}, A>`, where `A` is the type the rest of the block expects, so
   the transform must rewrite the static type of each raise site and each enclosing expression, not
   just the handled block.
2. **A row-changing bind.** A correct `flatMap` is
   `EffectContinuation<R1, A> × (A -> EffectContinuation<R2, B>) -> EffectContinuation<R1 ∪ R2, B>`.
   The constructor has two varying parameters and the bind needs a type-level row join.
3. **A partially covering interpreter.** `evaluate` must accept a handler that covers some labels and
   leaves the rest, which requires residual-row polymorphism in the handler's type (informally
   `forall R. Handler<{NotFound | R}>`).

None of these exist today. [ZEP-0019](./ZEP-0019.md) supports one open slot with the remaining
arguments fixed (`Result<_, E>`); [ZEP-0086](./ZEP-0086.md) quantifies rows on declarations only and
explicitly excludes row quantifiers inside function types; handler types are structural, with no
subtyping or composition. Encoding the row in the constructor also means the encoding cannot use the
plain `Monad` contracts, because `Monad<M<_>>` fixes a single slot.

### Cost and ABI consequences

- One closure per bind plus one allocation per `pure`, against the current carrier allocation at the
  raise site. The difference must be measured per workload, not asserted.
- Every participating call returns the wrapper, so a call's compiled form depends on whether its
  caller handles the effect. That is a separate-compilation and library-index change, and it ends the
  property that handling an effect does not alter callee descriptors.
- Java methods cannot participate; a foreign frame is a continuation barrier. ZEP-0049's explicit
  mapping does not extend to resumption.
- `using` cleanup across suspension, suppressed-failure precedence, stack traces, and debugger
  stepping all need new rules.
- Source-to-bytecode correspondence degrades: the chain no longer reflects the block's nesting.

### Strategies compared

| Strategy | Resumption | Source shape | Main cost | Status in Zeron |
| --- | --- | --- | --- | --- |
| Exception carrier and stack unwind | none | direct style | carrier allocation per raise; cannot continue | implemented today |
| Compiler CPS or state-machine transform over `raise` | one-shot first | direct style, transformed bodies | descriptor and separate-compilation change; foreign frames unsafe | unexplored; this proposal's subject |
| Free-monad `EffectContinuation` with explicit `evaluate` | one-shot, multi-shot only with a continuation tree | explicit binds in lowered form | closure per step; needs two-slot HKT, row join, residual-row handlers | blocked on the type-system gaps above |
| Library-level `Task`-style monad with hand-written binds | one-shot | explicit binds in source | coloring at the library boundary; adapters for blocking interop | feasible today; see ZEP-0111 and ZEP-0112 |
| Virtual threads with structured concurrency | blocking suspension only | direct style | no multi-shot, no deterministic interleaving; not continuation capture | feasible today; see ZEP-0112 |

### Findings

- The abortive half of the effect system needs no monad; the suspending half needs one. Generalizing
  over both is the source of the cost.
- The block surface and the monadic mechanism are separable. [ZEP-0110](./ZEP-0110.md) supplies the
  block without touching semantics; [ZEP-0111](./ZEP-0111.md) supplies monadic notation at library
  level with a fixed constructor; [ZEP-0112](./ZEP-0112.md) supplies the blocking suspension mechanism
  for the async motivation. None of them requires this proposal's mechanism.
- Coloring does not disappear under a monadic lowering; it moves into the wrapper type along the
  whole call graph, which is the `async fn`/`impl Future` model. Languages that keep direct style
  while supporting resumable effects put the machinery in the runtime (evidence passing, fiber-local
  capture) rather than in signatures.
- The blocking requirement for any future implementation is the row-changing bind: either a constructor
  with two open slots plus a row join, or an erased/fixed row that abandons the effect bookkeeping
  the encoding was meant to preserve.
- Recommendation: do not adopt monadic lowering as the semantics of `raise`. If resumption is pursued,
  start with one-shot continuations and choose between a compiler-managed transform and a free monad
  with an explicit `evaluate`, measuring both against the current carrier.

## Compatibility and impact

A resumable system is likely to affect control-flow lowering, runtime support, debugging, and the
compiled ABI. It may require a distinct operation/handler model rather than changing the existing
exception-carrier implementation in place. No binary or source compatibility decision is made here.

## Alternatives

- Retain abortive typed effects — preserves the small, synchronous runtime model and may be adequate
  for the project's use cases.
- Use explicit callbacks or continuation-passing APIs in libraries — keeps control flow visible but
  does not offer language-managed resumption.
- Add reusable abortive handlers under ZEP-0056 and ZEP-0057 — improves reuse without continuation
  capture.

## Implementation and validation

The exploratory deliverable should be a written comparison with at least one representative use
case and one prototype or feasibility spike only if needed to resolve a concrete runtime question.
It should identify required compiler/runtime phases, ABI consequences, error handling and cleanup
semantics, and measurable performance constraints. A full implementation plan requires a later
proposal.

## Open questions

- Are continuations one-shot or multi-shot, and how is this enforced?
- Are handlers deep or shallow, and what happens when a resumed continuation raises again?
- How do `using` cleanup and other `finally`-like obligations behave across suspension and resumption?
- Can the feature support foreign Java frames, or are such calls continuation barriers?
- Is there a compelling use case that justifies transformation complexity and runtime overhead?
- If a raise site is resumed, what does the continuation receive, and is the resuming value supplied
  by the operation, the handler, or both?
- Can one handler mix aborting and resuming cases for the same operation, and how is that typed?
- Does `evaluate` return a residual monadic value or a plain value plus an escaping row, and which
  choice keeps the row bookkeeping sound?
- Is a two-slot higher-kinded constructor (row and value) required, or can a row-erased encoding be
  justified by showing that handlers alone need the row?

## Decision

Deferred 2026-10-13. Do not spend an architecture or implementation cycle on resumable effects
until a concrete use case demonstrates a need that the current abortive effects, callbacks, and
ordinary control flow do not meet. One-shot versus multi-shot, deep versus shallow handlers,
resource-cleanup behavior, and foreign-call boundaries remain intentionally undecided.
