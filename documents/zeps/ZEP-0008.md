## Abstract

This proposal defines opt-in compiler-generated `Eq` and `Hashable` evidence for eligible data
types. Other contracts such as `Display` may be considered only where their semantics can be
derived predictably from declared components.

## Motivation

Zeron currently synthesizes structural equality for sums and nominal products, while ordinary
classes require explicit evidence. `Hashable<T>` is available for selected built-ins and through
explicit implementations, and depends on equality. Manually implementing component-wise behavior is
repetitive and can make equality/hash consistency difficult to maintain.

Explicit derivation is requested at the type declaration rather than invented at a use site.

## Goals

- Define explicit syntax and eligibility rules for requesting a derived contract implementation.
- Specify participating components, declaration order, generic prerequisites, recursion, and
  separate-compilation representation.
- Preserve user control: derivation is opt-in and must not silently override an explicit
  implementation or witness.
- Ensure derived `Hashable` behavior is consistent with the selected equality semantics.

## Non-goals

- Automatically deriving arbitrary user contracts.
- Synthesizing evidence silently at a call site.
- Replacing explicit implementations where custom semantics are needed.
- Claiming that derivation alone makes mutable or aliased values safe as hash keys.

## Proposal

Use declaration-site `deriving Eq, Hashable` for products, sums, classes, and newtypes. A derived
implementation is based on source-declared stored components, not JVM reflection or generated
representation details. Generic component requirements are recorded as opaque contract/target type
pairs in the library index; private component names and declarations are not exported.

Classes and newtypes deriving `Hashable` must also derive `Eq`. Products and sums already provide
structural `Eq`, so deriving it is redundant and rejected. Any custom `Eq` implementation prevents
derived `Hashable`; the programmer must provide a matching explicit `Hashable` implementation.
Nullable and directly recursive components follow existing evidence-lifting and recursion rules.

Evaluate `Display` separately or as a later derivation target. Its user-facing formatting
conventions differ from equality and hashing, so generalizing derivation must not assume all
contracts can be synthesized by the same rule.

## Compatibility and impact

This is additive source behavior but creates generated public behavior that consumers may rely on.
The compiled-library format must identify derived evidence and its prerequisites, or otherwise
preserve enough exported metadata to reproduce selection consistently. Changing participating
components or derivation rules may alter equality/hash behavior and should be treated as a public API
compatibility concern.

## Alternatives

- Keep all class and contract implementations explicit — maximizes control and avoids generated
  semantics, at the cost of repeated boilerplate.
- Derive automatically at use sites — rejected because capabilities would vary by context and could
  conflict with explicit evidence.
- Derive only for products and sums — narrower and safer, but leaves ordinary nominal records with
  repetitive implementations.

## Implementation and validation

Implemented with compiler-generated evidence and private synthetic structural helpers. Validation
covers all four declaration forms, source-order state selection, direct recursion, generic opaque
prerequisites across separately compiled libraries, and runtime equality/hash consistency. Derived
behavior does not guarantee that mutable values remain stable while used as hash keys.

## Decision

Accepted 2026-10-13. Permit declaration-site opt-in for products, sums, ordinary classes, and
newtypes. Structural derivation uses all source-declared stored state in declaration order,
including private and initialized fields, and excludes compiler-generated bookkeeping. Derived
`Hashable` is allowed only with matching structural `Eq` (including existing built-in structural
`Eq` for products/sums); types with custom equality must provide `Hashable` explicitly. Preserve
current direct-recursion support, defer mutually recursive declaration groups, and promise no runtime
object-cycle detection. Keep `Display` derivation separate. This accepts the design direction;
implementation is complete for the 0.3.0 release-candidate cycle.

## Discussion notes

- The initial design should consider products, sums, ordinary classes, and newtypes as explicit
  derivation targets. Products and sums already provide structural `Eq`; this proposal would not
  silently change that behavior.
- Derived `Hashable` requires matching structural `Eq`; it is not paired with a custom equality
  implementation unless the programmer supplies `Hashable` explicitly.
- Structural derivation includes all source-declared stored state in declaration order, including
  private fields and fields with initializers; generated compiler bookkeeping is excluded.
- Preserve current recursive evidence limits in the initial design: direct self-recursion where
  already supported may be derived, mutually recursive declaration groups are deferred, and no
  runtime object-cycle detection is promised.
- Keep `Display` derivation outside this proposal; its human-facing formatting semantics warrant a
  separate design.
- Request derivation at the type declaration, so the capability is explicit and travels with the
  type's public API.   The selected spelling is `deriving Eq, Hashable`.
- Export generated evidence through the existing library metadata boundary without exposing private
  component details as source-level members.

## Implementation decisions

Use a declaration-site `deriving Eq, Hashable` clause. The `deriving` word is a soft keyword and is
recognized only in declaration-header positions. For classes it follows any `is` conformance list
and precedes the class body; for product, sum, and newtype declarations it follows the declared
name and type parameters and precedes `=`.

Derivation creates compiler-generated type-class witness evidence; it does not implicitly add
nominal `is` conformance to classes. Products and sums already have intrinsic structural `Eq`, so
listing `Eq` in their derive clause is rejected as redundant; `Hashable` may be derived using that
intrinsic equality. A type with custom `Eq` must provide `Hashable` explicitly rather than deriving
it.

Derived class equality and hashing inspect all source-declared stored fields and backing properties
in declaration order, including private and initialized state. Custom/computed properties and
compiler-generated fields are excluded. Hash combination uses a type's component hash evidence and
includes sum-case identity. The generated helpers are synthetic implementation details and do not
appear as source-level discovered members.
