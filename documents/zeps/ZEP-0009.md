# ZEP-0009: Public Member Discovery API

## Status

Draft

## Author

Marcelo Rodríguez

## Created

2026-10-13

## Related ZEPs

- None.

## Abstract

This proposal defines a public, read-only compiler API for discovering Zeron type members and
signatures from source and compiled libraries. It deliberately does not implement cursor-aware
completion, an LSP, or an editor integration.

## Motivation

Documentation generators, API browsers, build integrations, and future editors need a supported way
to discover public members. The existing library index contains substantial signature metadata, but
its binary format and reconstructed AST declarations are not an appropriate stable query API for
third-party consumers.

## Goals

- Expose an immutable, source-level model of public types and their discoverable members.
- Provide equivalent results for source declarations and compiled Zeron libraries.
- Preserve generic signatures, bounds, mutability, effects, properties, constructor metadata, and
  member origin where available.
- Keep type-level discovery independent of any editor protocol.

## Non-goals

- An LSP, VS Code semantic integration, or editor-specific completion protocol.
- Cursor-position scope resolution, incomplete-source recovery, hover, navigation, or refactoring.
- Reflective discovery of arbitrary Java members or expansion of current Java interop rules.
- Exposing private declarations, method bodies, AST implementation objects, or binary-index records
  as the public model.

## Proposal

Provide a compiler-owned query API that accepts a qualified type identity and relevant applied type
arguments, and returns immutable member records with source-level signatures. Keep direct
declarations, contract requirements/defaults, and extension methods distinguishable so a future
context-sensitive tool can apply imports, accessibility, and resolution precedence correctly.

Use resolved source declarations and validated `ZeronLibraryIndex` metadata as inputs to a shared
semantic representation. Compare the existing index against the required model before changing its
schema; add wire metadata only when an essential source-level fact is absent. The API should not
expose compiler internals merely to avoid defining the public model.

## Compatibility and impact

The public discovery API needs its own compatibility policy, distinct from the binary library-index
schema. The index and standard-library API versions should change only when their respective
compatibility contracts require it. Equivalent source and compiled inputs must produce equivalent
member records.

## Alternatives

- Expose `ZeronLibraryIndex` directly — reuses existing structures but couples consumers to a
  serialization-oriented internal representation.
- Expose resolver/AST nodes — avoids conversion but leaks compiler internals and source-only details
  that compiled libraries cannot provide.
- Defer all public discovery until an LSP is built — postpones a useful API and risks coupling the
  semantic query to an editor protocol.

## Implementation and validation

Inventory index metadata and resolved declarations, then define a small immutable query model and
API boundary. Test equivalent source and compiled-library queries for generic classes/contracts,
properties, mutating methods, effects, constructors, and extension metadata. Verify inaccessible
private members are excluded and ambiguous same-name declarations remain distinct rather than being
silently collapsed.

## Open questions

- Should discovery include contract-provided/default members in the first API, or report only direct
  declarations with explicit origins?
- What compatibility promise should the public Java API make across compiler versions?
- Should source documentation comments be included now or handled by a separate documentation API?
- How should explicitly imported extensions be represented when the query has no source import
  context?
