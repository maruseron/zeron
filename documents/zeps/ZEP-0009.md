## Abstract

This proposal defines a public, read-only compiler API for discovering Zeron type members and
signatures from source and compiled libraries. It deliberately does not implement cursor-aware
completion, an LSP, or an editor integration.

## Motivation

Documentation generators, API browsers, build integrations, and future editors need a supported way
to discover public members. The existing library index contains substantial signature metadata, but
its binary format and reconstructed AST declarations are not an appropriate stable query API for
third-party consumers.

## Goals

- Expose an immutable, source-level model of public types and their discoverable members.
- Provide equivalent results for source declarations and compiled Zeron libraries.
- Preserve generic signatures, bounds, mutability, effects, properties, constructor metadata, and
  member origin where available.
- Preserve declaration identity and optional source provenance so later tools can navigate to
  source-backed declarations without depending on compiler internals.
- Keep type-level discovery independent of any editor protocol.

## Non-goals

- An LSP, VS Code semantic integration, or editor-specific completion protocol.
- Cursor-position scope resolution, incomplete-source recovery, hover, navigation, or refactoring.
- Reflective discovery of arbitrary Java members or expansion of current Java interop rules.
- Exposing private declarations, method bodies, AST implementation objects, or binary-index records
  as the public model.

## Proposal

Provide a compiler-owned query API that accepts a qualified type identity and relevant applied type
arguments, and returns immutable member records with source-level signatures. Keep direct
declarations, contract requirements/defaults, and extension methods distinguishable so a future
context-sensitive tool can apply imports, accessibility, and resolution precedence correctly.

Use resolved source declarations and validated `ZeronLibraryIndex` metadata as inputs to a shared
semantic representation. Compare the existing index against the required model before changing its
schema; add wire metadata only when an essential source-level fact is absent. The API should not
expose compiler internals merely to avoid defining the public model.

Types and members need source-level declaration identities that distinguish same-named members and
overloads. Identity must not depend on AST object identity, source offsets, binary-index record order,
or generated JVM names. Source-backed declarations may include optional provenance consisting of a
source URI and range. Compiled-library declarations without source files still appear in the catalog;
their provenance is simply absent.

Declaration identity is derived from the canonical source-level owner, member kind, name, and
signature. It is the same for equivalent source and compiled-library declarations and may change
when the declaration's identity or signature changes; it is not a promise of stability across
renames or incompatible releases.

Source provenance uses a source URI and optional range. Range lines, characters, and offsets are
zero-based UTF-16 code units. Provenance is supplementary to semantic signatures, so equivalent
source and compiled declarations remain semantically equivalent. An editor adapter converts these
ranges to the position encoding negotiated with its client.

The catalog remains type-level: it does not answer cursor-position queries, maintain open-document
state, recover incomplete input, or rank completion items. A future LSP-facing layer can compose the
catalog with source maps and project/document analysis without requiring LSP protocol types in this
API.

## Compatibility and impact

The public discovery API needs its own compatibility policy, distinct from the binary library-index
schema. The index and standard-library API versions should change only when their respective
compatibility contracts require it. Equivalent source and compiled inputs must produce equivalent
member records.

## Alternatives

- Expose `ZeronLibraryIndex` directly — reuses existing structures but couples consumers to a
  serialization-oriented internal representation.
- Expose resolver/AST nodes — avoids conversion but leaks compiler internals and source-only details
  that compiled libraries cannot provide.
- Defer all public discovery until an LSP is built — postpones a useful API and risks coupling the
  semantic query to an editor protocol.

## Implementation and validation

Inventory index metadata and resolved declarations, then define a small immutable query model and
API boundary. Test equivalent source and compiled-library queries for generic classes/contracts,
properties, mutating methods, effects, constructors, and extension metadata. Verify declaration
identities distinguish overloads, source provenance is optional with explicit coordinate
conventions, inaccessible private members are excluded, and ambiguous same-name declarations remain
distinct rather than being silently collapsed.

## Decision

Accepted 2026-10-13. Provide a compiler-owned immutable type/member catalog with source and compiled
library parity. Include contract-provided defaults only when actually available and label their
origin; keep extensions separate and report their required explicit import. Expose signatures and
semantic metadata, not source documentation comments, compiler internals, or JVM reflection
results. Compatibility follows compiler artifact SemVer, with no independent API counter. This
accepts the API direction; implementation remains subject to project prioritization and normal
review.

## Discussion notes

- Include contract-provided/default members only when they are actually available on the queried
  type, and label their origin. Do not report an unimplemented abstract requirement as an available
  class member.
- Apply compiler artifact SemVer to the public Java discovery API: it may evolve before 1.0; after
  1.0, keep additions backward-compatible within a major series and reserve breaking API changes
  for a major increment. Do not add an independent API version counter.
- Exclude source documentation comments from the first model; expose semantic signatures only.
- Return exported extensions separately with their explicit activation import/namespace instead of
  presenting them as directly available type members.
- Give declarations source-level identities independent of AST and JVM representation, with optional
  source locations using zero-based UTF-16 coordinates. Keep cursor-sensitive queries and editor
  protocol concerns in a future adapter layer.
