# ZEP-0010: Generic Type-Admissibility Constraints

## Status

Draft

## Author

Marcelo Rodríguez

## Created

2026-10-13

## Related ZEPs

- None.

## Abstract

This proposal explores compiler-recognized generic type-admissibility constraints that restrict
which types may be supplied for a type parameter without exposing operations on values of that
parameter. Candidate constraints are `NonNull`, `Numeric`, and `Stable<T>`.

## Motivation

Some generic APIs need to restrict admissible type arguments for reasons that are not naturally
expressed as ordinary member-bearing contracts. Examples include excluding nullable types,
limiting a type argument to built-in numeric types, and requiring equality/hash-relevant state to
remain stable while a value is stored as a hash key.

These constraints are not equivalent to operator contracts or ordinary generic bounds. The
language overview calls out their syntax, inference, forwarding, and compiled-library
representation as unresolved.

## Goals

- Define whether and how each candidate constraint can be expressed on generic parameters.
- Ensure constraints restrict admissible type arguments without implicitly exposing operations.
- Define propagation through inference, generic calls, class/contract bounds, and separate
  compilation.
- Decide whether any candidate can be enforced soundly with current type and reference semantics.

## Non-goals

- Replacing ordinary contract bounds or the separate operator-witness design.
- Adding arithmetic operations to `Numeric` merely by admitting a type.
- Treating immutable references as proof that all reachable state is stable.
- Requiring every generic API to use these constraints.

## Proposal

Evaluate the candidates independently under a shared constraint model:

- `NonNull` would reject nullable type arguments while leaving ordinary non-null operations governed
  by existing type rules.
- `Numeric` would admit the explicitly specified built-in numeric types (initially the language's
  `Int` and `Float`) but would not by itself provide arithmetic operators or methods.
- `Stable<T>` would express a guarantee relevant to equality/hash-based storage: the equality- and
  hash-relevant state of values of `T` cannot change while they are used as keys. Its exact syntax,
  scope, and enforceability are unresolved.

The design must specify how constraints are inferred, checked at explicit and inferred type
arguments, forwarded by generic callers, serialized in library metadata, and diagnosed. A
constraint should not create runtime evidence unless the chosen semantics require it. The proposal
may recommend omitting or deferring any candidate that cannot be checked soundly or usefully.

## Compatibility and impact

This adds generic well-formedness rules and could reject type applications accepted today. If
constraints appear in exported signatures, the library index must preserve them and consumers must
validate them consistently. Any ABI representation or version changes should be justified by actual
runtime needs; constraints that exist only for static admissibility should not add unnecessary
runtime checks.

## Alternatives

- Use ordinary contracts for all constraints — suitable when the requirement is behavioral, but
  `NonNull` and exact built-in admissibility may not be well modeled as member-bearing contracts.
- Keep `Numeric` as an operator-witness/design concern — preserves one mechanism for permitted
  operations but does not necessarily express argument admissibility without operators.
- Document hash-key stability as a caller obligation — simple, but cannot offer a static guarantee
  for APIs that need stronger protection.
- Omit `Stable<T>` — preferable if aliasing and reachable mutable state make a sound guarantee
  impractical.

## Implementation and validation

Specify a common representation and static rules before implementation. Test explicit and inferred
arguments, nullable types, built-in and non-built-in numeric types, constraint forwarding through
generic functions and classes, compiled-library round trips, and useful negative diagnostics.
For `Stable<T>`, construct adversarial aliasing cases that mutate equality-relevant reachable state;
do not accept immutability of a view as sufficient evidence.

## Open questions

- What syntax distinguishes compiler-recognized admissibility constraints from ordinary contracts?
- Should `NonNull` be redundant with an existing non-null type variable rule, or a constraint on
  arbitrary type arguments?
- Is `Numeric` a fixed closed set of built-ins, or can user-defined numeric types opt in?
- Can `Stable<T>` be checked soundly without deep immutability, ownership, or copying reachable
  state? What exactly is the lifetime of the stability guarantee?
- Can constraints be forwarded or inferred without introducing runtime witness values?
- Should these candidates be separate proposals after exploration, especially if `Stable<T>` is
  substantially more complex?
