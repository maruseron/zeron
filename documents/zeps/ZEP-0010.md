# ZEP-0010: Generic Admissibility Markers

| Field | Value |
| ----- | ----- |
| Status | Implemented |
| Author | Marcelo Rodríguez |

| Updated | 2026-10-20 |

## Abstract

Define the first compiler-recognized generic admissibility markers: `nullable` and `effect`.
Generic parameters admit only non-null type arguments by default; `nullable` explicitly opts a
parameter into accepting nullable type arguments. Neither marker provides operations. A closed-set
`numeric` marker is not included; generic arithmetic requirements use operation-bearing contracts.

## Motivation

Some generic declarations need to restrict their type arguments without requiring a method-bearing
contract. A declaration may need to reject nullable arguments, or to state that a parameter stands
for an effect that can be propagated through `raise` and `raises`.

These properties are distinct from ordinary contract bounds. A contract provides operations;
admissibility markers constrain the kinds of type arguments a declaration accepts. Defaulting to
non-null arguments gives generic declarations the safer, more predictable baseline, while an
explicit `nullable` marker makes acceptance of nullable arguments visible at the declaration.

## Goals

- Make generic type parameters admit only non-null type arguments by default.
- Add a `nullable` opt-in marker and the `effect` marker using existing generic-bound syntax.
- Permit generic forwarding of exact effect identities while preserving the effect-only distinction.
- Enforce the effect-kind guarantee at generic `raise` sites despite JVM erasure and unchecked Java
  calls.
- Keep type admissibility separate from operation-bearing contract bounds.
- Defer a closed-set `numeric` marker unless a concrete use case establishes a need for it.

## Non-goals

- Providing operations through `nullable` or `effect`.
- Adding a compiler-recognized closed-set `numeric` constraint in this first set.
- Generic effect declarations or applied generic effect identity; see
  [ZEP-0005](./ZEP-0005.md).
- Effect-row polymorphism, generic handler cases on unresolved parameters, or runtime reification
  of arbitrary generic arguments.

## Proposal

Markers use the existing bound syntax and compose with ordinary contract bounds using `+`:

```zeron
fn render<T: Display<T>>(value: T): String = value.toString();

fn identityNullable<T: nullable>(value: T): T = value;

fn relay<E: effect>(failure: E) raises E {
    raise failure;
}
```

### `nullable`

An unconstrained type parameter admits only non-null type arguments. `T: nullable` opts into nullable
type arguments as well as non-null ones; it is an admissibility check, not an operation provider or
a type transformation. For example, `identityNullable(nullableString)` may infer `T` as `String?`.

The marker is distinct from a nullable occurrence of a type variable. `T?` remains nullable even
when `T` is constrained to non-null arguments. Conversely, `T: nullable` does not make every
instantiation nullable: when `T` is inferred as non-null, its occurrences remain non-null. A generic
caller can forward a possibly nullable type argument only to a parameter that admits nullable
arguments. Inference must reject a nullable type inferred for an unconstrained parameter rather than
silently removing nullability.

### `effect`

`E: effect` admits non-null declared effect types. If ZEP-0013 introduces a denotable top `Effect`
type, that type also satisfies the effect kind because it denotes only effect values. This decision
does not accept the rest of ZEP-0013. The `effect` marker is inherently non-null and cannot be
combined with `nullable`; nullable effect values can instead be represented by an occurrence such
as `E?` and must be proven non-null before being raised. The marker composes with ordinary contract
bounds, but contract conformance alone never makes a type an effect.

An effect-kinded parameter may appear in `raise` and in a callable's `raises` set. Substitution
preserves the exact source-level effect argument, and callers must handle it or declare it. When instantiated with `Effect`, the callable declares the broad top effect. A generic body cannot match
an unresolved `E` in a handler case: the marker proves effect admissibility but does not provide
the concrete identity needed for dispatch.

Because generic parameters erase on the JVM, each generated effect payload class must carry a
compiler-owned runtime effect marker. A `raise` whose value has an effect-kinded type parameter
must check that runtime marker before raising the value; a value supplied through an unchecked Java
or raw-generic boundary that fails the check produces `ClassCastException`. If introduced, the
denotable `Effect` type in ZEP-0013 uses the same runtime marker. This check validates effect-kind
membership; it does not reify generic arguments or determine a concrete handler case.

### Numeric requirements

Do not add a closed-set `numeric` admissibility marker in this proposal. A type allowlist alone
would not provide arithmetic operations, while generic algorithms that need operations can state
those requirements with contracts such as `Add<T>`, `Addition<T>`, `Mult<T>`, and
`Multiplication<T>`. Those contracts can admit user-defined types and make the required operations
explicit.

Reconsider a built-in-only numeric category separately if a concrete operation-independent use case
emerges, such as an API that must restrict type arguments to a specific numeric family without
requiring arithmetic.

## Compatibility and impact

Making non-null admissibility the default changes existing generic declarations that accept nullable
type arguments: those declarations must opt in with `T: nullable`. Existing signatures and
compiled-library metadata must preserve the admissibility marker, and inference must validate both
explicit and inferred arguments. This is a source-compatibility change for declarations or calls
that currently rely on nullable generic arguments.

Effect-kind constraints also affect raised-effect signatures and generic function types. Generated
effect payload classes gain a runtime marker, and generic raise sites with an abstract effect type
perform a membership check. The compiled-library index preserves the metadata in schema version 10. The standard-library API
version is 10 after nullable-admitting markers were added to public types that intentionally support
nullable arguments.

## Alternatives

- Allow nullable type arguments by default and opt out with `nonnull` — rejected because nullability
  is then an implicit capability of every generic parameter, making the safer contract less visible.
- Use an ordinary contract as the effect marker — rejected because any ordinary class could conform
  and become raisable.
- Add a closed-set `numeric` marker now — deferred because it would admit types without providing
  operations, which are more directly expressed by existing algebraic contracts.
- Permit handler cases on unresolved effect parameters — rejected because the kind marker provides
  no concrete runtime identity for selecting a case.

## Implementation and validation

Represent and serialize markers as generic parameter constraints, independently of contract
evidence. Validate:

- non-null default inference, `nullable` explicit/inferred arguments, `T?` occurrences, bounds,
  forwarding, and migration of existing generic declarations;
- `effect` substitutions, composition with contract bounds, and inclusion of top `Effect` if
  adopted by ZEP-0013;
- generic `raise`/`raises E` propagation through calls and function values, including escaping-effect
  diagnostics;
- runtime rejection of a non-effect value passed through an unchecked boundary to a generic raise;
- rejection of handler cases on unresolved `E`, and correct handler dispatch after specialization;
- compiled-library round trips and compatibility with ZEP-0013's runtime marker.

## Implementation

Implemented with `zeron.runtime.EffectValue` as the generated effect marker and
`zeron.runtime.EffectSupport` as the generic raise-site check. Both runtime classes are included in
generated outputs. Generic admissibility metadata is preserved in API-index schema version 10;
Java generic parameters retain their nullable-by-default interop behavior. Existing standard-library
containers and helpers that support nullable type arguments now declare `nullable` explicitly.

## Decision

Accepted and implemented 2026-10-20; revised 2026-10-20. Generic parameters admit only non-null type arguments by
default, with `T: nullable` as an explicit opt-in. Adopt `effect` for exact generic propagation and
runtime marker checks at generic raise sites; it is inherently non-null and admits the proposed top
`Effect` type if introduced. Defer closed-set `numeric`; use operation-bearing contracts for generic
arithmetic.
