## Abstract

This proposal defines compiler-recognized `NonNull` and `Numeric` admissibility constraints that
restrict which types may be supplied for a type parameter without exposing operations on values of
that parameter. The separate `Stable<T>` exploration is tracked in [ZEP-0014](./ZEP-0014.md).

## Motivation

Some generic APIs need to restrict admissible type arguments for reasons that are not naturally
expressed as ordinary member-bearing contracts. Examples include excluding nullable types and
limiting a type argument to built-in numeric types.

These constraints are not equivalent to operator contracts or ordinary generic bounds. The
language overview calls out their syntax, inference, forwarding, and compiled-library
representation as unresolved.

## Goals

- Define how `NonNull` and `Numeric` can be expressed on generic parameters.
- Ensure constraints restrict admissible type arguments without implicitly exposing operations.
- Define propagation through inference, generic calls, class/contract bounds, and separate
  compilation.
- Enforce these constraints soundly with current type and reference semantics.

## Non-goals

- Replacing ordinary contract bounds or the separate operator-witness design.
- Adding arithmetic operations to `Numeric` merely by admitting a type.
- Requiring every generic API to use these constraints.
- `Stable<T>`, which is explored separately in [ZEP-0014](./ZEP-0014.md).

## Proposal

Apply a shared constraint model to:

- `NonNull` would reject nullable type arguments while leaving ordinary non-null operations governed
  by existing type rules.
- `Numeric` would admit the explicitly specified built-in numeric types (initially the language's
  `Int` and `Float`) but would not by itself provide arithmetic operators or methods.
The design must specify how constraints are inferred, checked at explicit and inferred type
arguments, forwarded by generic callers, serialized in library metadata, and diagnosed. A
constraint should not create runtime evidence unless the chosen semantics require it. The proposal
may recommend omitting or deferring any candidate that cannot be checked soundly or usefully.

## Compatibility and impact

This adds generic well-formedness rules and could reject type applications accepted today. If
constraints appear in exported signatures, the library index must preserve them and consumers must
validate them consistently. Any ABI representation or version changes should be justified by actual
runtime needs; constraints that exist only for static admissibility should not add unnecessary
runtime checks.

## Alternatives

- Use ordinary contracts for all constraints — suitable when the requirement is behavioral, but
  `NonNull` and exact built-in admissibility may not be well modeled as member-bearing contracts.
- Keep `Numeric` as an operator-witness/design concern — preserves one mechanism for permitted
  operations but does not necessarily express argument admissibility without operators.

## Implementation and validation

Specify the common representation and static rules before implementation. Test explicit and
inferred arguments, nullable types, built-in and non-built-in numeric types, constraint forwarding
through generic functions and classes, compiled-library round trips, and useful negative diagnostics.

## Decision

Accepted 2026-10-13. Support static `NonNull` admissibility on the outer generic type argument and
closed-set `Numeric` admissibility for `Int` and `Float`. These constraints expose no operations,
require no runtime evidence, and are checked/forwarded through generic signatures and exported
metadata. Keep exact surface syntax to implementation, preserving clear distinction from
member-bearing contract bounds. Implementation remains subject to project prioritization and
normal review. `Stable<T>` is outside this proposal and is explored in ZEP-0014.

## Discussion notes

- `NonNull` constrains only the outer type argument's nullability and exposes no operations; a
  non-null container such as `Array<String?>` remains admissible.
- `Numeric` is initially a closed admissibility set containing `Int` and `Float`; user-defined
  opt-in and numeric operations are outside this proposal.
- Enforce and forward admissibility constraints statically at generic call sites. They require no
  runtime evidence and must be preserved in exported signatures when consumers need to validate
  them.
- Surface syntax remains an implementation decision; it may reuse generic-bound syntax if the
  parser and resolver can distinguish admissibility constraints unambiguously from contracts.
