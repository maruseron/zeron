## Abstract

This proposal reconsiders how generic nullability and numeric requirements should be expressed.
It compares an explicit `NonNull` admissibility constraint with rejecting nullable generic
arguments by default, and a closed-set `Numeric` constraint with operation-bearing contracts.
`Stable<T>` is explored separately in [ZEP-0014](./ZEP-0014.md).

## Motivation

Generic admissibility rules affect every generic function and type, so the default policy for
nullable type arguments has broad semantic and compatibility consequences. An explicit `NonNull`
constraint is local and opt-in, while making generic parameters non-null by default could provide a
stronger baseline and require nullable support to be requested explicitly.

Likewise, a compiler-recognized `Numeric` constraint can describe a closed set of built-in types
without exposing operations. Generic arithmetic, however, is more naturally expressed through
contracts that require the operations an algorithm uses. The language does not yet have settled
generic operator requirements, so the right boundary between numeric admissibility and behavioral
contracts remains open.

## Goals

- Compare an explicit `NonNull` constraint with non-null generic arguments by default and explicit
  opt-in for nullable arguments.
- Compare a closed-set `Numeric` admissibility constraint with operation-bearing contracts such as
  `Additive<T>` and `Multiplicative<T>`.
- Define the use cases and compatibility consequences before committing to either mechanism.
- If any mechanism is accepted, specify propagation through inference, generic calls,
  class/contract bounds, and separate compilation.

## Non-goals

- Resolving generic operator requirements as part of this proposal unless they prove necessary to
  decide between the alternatives.
- Requiring every generic API to use these constraints.
- `Stable<T>`, which is explored separately in [ZEP-0014](./ZEP-0014.md).

## Proposal

Evaluate nullability and numeric constraints independently; they need not share a representation.

For nullability, compare:

- **Explicit admissibility:** generic parameters may admit nullable type arguments unless they
  declare `NonNull`.
- **Non-null by default:** generic parameters reject nullable type arguments unless the declaration
  explicitly opts in. The spelling and meaning of this opt-in must be distinguished from a nullable
  occurrence of a type variable, such as a parameter of type `T?`.

Assess migration impact on existing generic functions and types, standard-library containers,
contract bounds, nullable lifting, inference, and separately compiled APIs.

For numeric requirements, compare:

- **Closed-set constraint:** a compiler-recognized constraint admits a fixed set of built-in
  numeric types but does not expose operations.
- **Behavioral contracts:** generic algorithms require contracts for the operations they use, for
  example an additive and a multiplicative contract. This can admit user-defined types, but
  operation signatures, generic operator support, and the distinction between required operations
  and mathematical laws need definition.

Do not assume either approach is needed without a concrete use case. The proposal may conclude that
one or both features should be deferred or omitted. If a static constraint is accepted, specify how
it is checked at explicit and inferred type arguments, forwarded by generic callers, serialized in
library metadata, and diagnosed. Do not add runtime evidence unless its semantics require it.

## Compatibility and impact

Changing generic nullability defaults could make existing signatures reject nullable type arguments
and require updates to source and exported library metadata. Numeric contracts could introduce
public evidence and operation requirements, while a closed-set constraint could add new static
well-formedness rules. Do not commit to compatibility or ABI changes until the selected model and
its concrete use cases are established.

## Alternatives

- Use `NonNull` only where needed — local and explicit, but leaves nullable type arguments as the
  generic default.
- Reject nullable generic arguments by default — stronger baseline, but has broader compatibility
  impact and needs clear opt-in syntax.
- Use a closed-set `Numeric` constraint — simple for built-in-only admissibility, but grants no
  operations and excludes user-defined numeric types.
- Use operation-bearing contracts — compositional and extensible, but requires stable operation
  contracts and does not by itself enforce mathematical laws.
- Defer both questions — avoids expanding the current language implementation before a demonstrated
  use case justifies the cost.

## Implementation and validation

Before implementation, identify concrete generic APIs that need each feature. For nullability, test
generic functions and containers with nullable and non-null arguments, nullable occurrences of type
variables, bounds, inference, and separate compilation under both candidate defaults. For numeric
support, compare generic algorithms expressed using built-in operations, proposed contracts, and any
closed-set constraint; include user-defined numeric types and boundary semantics. Add compiled-
library round trips and negative diagnostics only for a selected design.

## Open questions

- Should unconstrained generic parameters accept nullable type arguments, or reject them by default
  with an explicit nullable opt-in?
- If nullable generic arguments require opt-in, what syntax distinguishes that declaration-level
  choice from a nullable occurrence such as `T?`?
- Which current or planned APIs need non-null generic arguments, and is an explicit `NonNull`
  constraint useful if non-null is already the default?
- Is the numeric requirement about admitting only built-in numeric types, or about requiring
  arithmetic behavior from generic algorithms?
- If it is behavioral, what operation contracts are needed, and should operators work through those
  bounds or only named methods initially?
- Are there concrete use cases important enough to justify either feature in the current language
  implementation?

## Decision

Reopened 2026-10-13. The earlier decision to use explicit `NonNull` and closed-set `Numeric`
constraints is no longer settled. The nullability default and the distinction between numeric
admissibility and operation-bearing contracts require further design discussion. The proposal is
Draft and Unscheduled while concrete use cases and compatibility impact are evaluated.

## Discussion notes

- An explicit `NonNull` constraint is one alternative; the competing direction is to reject nullable
  generic arguments by default and require an opt-in for generic APIs that accept them.
- A compiler-recognized `Numeric` constraint would be an admissibility rule, not an operation
  provider. A contract hierarchy such as `Numeric<T>` requiring additive and multiplicative
  capabilities could instead express behavioral requirements, subject to operation and operator
  semantics.
- Neither choice is considered critical to the current language implementation; do not assign a
  release target until the design and use cases are settled.
