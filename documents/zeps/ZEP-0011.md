# ZEP-0011: Standard Library Phase 1: I/O, Environment, and Time

## Abstract

This proposal defines a first foundation phase for the Zeron standard library, centered on
cross-platform I/O abstractions, process and environment access, and basic time utilities. It
prioritizes immutable value types where practical and uses explicit mutable references for APIs that
must mutate a resource or cursor. A dedicated serialization API is deferred until Zeron's
serialization model is settled.

## Motivation

The standard library currently has a small I/O surface: printing, whole-file text reads and writes,
filesystem paths, and typed I/O and disposal failures. These are useful primitives but do not yet
form a general foundation for stream-oriented APIs or portable process and time facilities.

A coherent first phase can establish reusable abstractions for applications without prematurely
choosing serialization formats or adding platform-specific APIs without a clear compatibility
boundary.

## Goals

- Establish synchronous, blocking byte-oriented `Reader` and `Writer` abstractions for incremental
  I/O, with UTF-8 text adapters.
- Provide discoverable, read-only access to current-process arguments, environment variables, and
  working directory, plus process exit.
- Provide immutable `Instant` and `Duration` values with useful comparison and arithmetic semantics.
- Reuse typed raised effects for recoverable I/O and system failures where appropriate.
- Favor immutable values and read-only interfaces, using mutable reference capability only when an
  operation changes the state of a resource.
- Keep APIs portable where possible and make platform-dependent behavior explicit.
- Design the foundation so dedicated serialization libraries can be added later without binding
  their model prematurely to these primitives.

## Non-goals

- A JSON, XML, TOML, or other dedicated serialization API in this phase.
- A general asynchronous I/O or cancellation framework.
- Subprocess management, networking, device, or a general operating-system abstraction layer.
- Exposing arbitrary raw operating-system syscalls without a portability and safety policy.
- Mutation of environment variables or process properties.
- Wall-clock timestamps, civil dates, calendars, or time-zone handling.
- Replacing existing filesystem, text-I/O, or resource-management APIs without a migration plan.

## Proposal

Develop this phase as a coherent but staged standard-library foundation with the following areas:

### General I/O

Define synchronous, blocking byte-oriented `Reader` and `Writer` abstractions for incremental input
and output, with text readers and writers layered as adapters. Include minimal language/compiler
support for a byte value and bulk byte buffers; do not represent bytes as ordinary `Int` values.
Cursor-advancing operations are `mut` and follow existing reference-capability rules. A read may
return partial progress and reports EOF distinctly; a write completes the supplied buffer or raises
a declared I/O failure.

Resource-opening APIs return owning readers and writers. Their lifetime is explicit through
`Disposable` and `using`; operations do not close resources implicitly, and writer disposal flushes
before closing. Adapters own the resource they wrap and dispose it transitively. Disposal failures
follow the existing `Disposable` contract. These APIs do not imply that a reader or writer can be
safely shared concurrently.

Text adapters use UTF-8 and reject malformed input with `IoFailure` rather than silently replacing
it. Preserve the existing `readText` and `writeText` convenience APIs, including their signatures
and UTF-8 behavior, and implement them through the adapters.

Prefer immutable source and destination descriptions, configuration, and returned data. A cursor-
advancing reader or stateful writer may require `mut` operations and a mutable reference view. This
must follow Zeron's existing distinction between binding reassignment and receiver mutation:
`let mut` does not grant mutation capability, and `&T` is permission to mutate rather than a
guarantee of exclusive access. Raising an effect and mutating a receiver are independent properties.

### Environment and system access

Provide portable, typed APIs for:

- command-line arguments as an immutable ordered snapshot;
- read-only environment-variable lookup, representing missing values explicitly;
- querying the current working directory and exiting the current process.

Do not expose arbitrary raw system calls or platform-specific APIs in this phase. Defer environment
and process-property mutation as well as subprocess management.

### Time

Provide immutable `Duration` and `Instant` values for elapsed-time measurement only. `Instant` uses
a monotonic clock whose actual precision is platform-dependent and is meaningful only within its
clock domain; it is not a wall-clock timestamp. `Duration` stores signed 64-bit nanoseconds.
Duration arithmetic detects overflow and does not wrap or saturate silently. Defer wall-clock
timestamps, civil dates, calendars, and time zones.


## Compatibility and impact

This adds standard-library API surface and will require the normal standard-library API version
policy to be followed. Existing `zeron.io`, `zeron.io.text`, `zeron.fs`, and `zeron.resource`
behavior should remain compatible unless a separate migration is proposed.

Public abstractions should be designed for separately compiled consumers and represented through
the existing library API index. Java-backed implementations should remain behind explicit external
facades and must not make host implementation classes part of source-level API identity.

## Alternatives

- Continue adding one-off I/O helpers — small immediate changes, but does not provide composable
  stream abstractions.
- Use only byte I/O or only text I/O — either omits a needed layer; this proposal defines byte
  abstractions with UTF-8 text adapters.
- Expose raw system calls — maximally flexible but non-portable, unsafe, and difficult to version as
  a standard cross-platform API.
- Include serialization formats now — rejected for this phase because the serialization model and
  desired format/conversion semantics are not yet settled.
- Make all Reader/Writer operations immutable — does not naturally model advancing cursors or
  resource state; mutable references remain appropriate where state mutation is intrinsic.

## Implementation and validation

Before implementation, inventory existing Java facades and standard-library APIs, then settle exact
package names, signatures, and failure-effect declarations. Implement the minimal byte and bulk
buffer language/compiler support needed by the I/O abstractions.

Implement in small, independently testable slices. Validate in-memory readers/writers, partial reads,
explicit EOF, write-all behavior, strict UTF-8 decoding, failure propagation, adapter ownership,
flush/close behavior, and disposal through `using`. Also test command-line argument order, missing
and present environment variables, working-directory and process-exit APIs, duration overflow, and
monotonic instant differences. Add compiled-library API-index round trips and tests that verify
mutating operations require mutable receiver views while immutable data and queries remain usable
through read-only views. Keep format-specific serialization out of the acceptance tests for this
phase.

## Open questions

No remaining scope-level questions. Exact module names, signatures, and effect declarations are
implementation details to settle while preserving this proposal's semantics.

## Discussion notes

- Use a layered I/O model with byte-oriented core abstractions and text readers/writers as adapters.
- Keep initial I/O synchronous and blocking; asynchronous operations and cancellation are separate
  work.
- Resource-opening APIs return owning readers/writers. Their lifetime is explicit through
  `Disposable`/`using`; reads and writes do not close resources implicitly, and writer disposal
  flushes before closing.
- Environment-variable access is read-only initially; mutation of OS environment variables and
  process properties is out of scope.
- Expose portable OS services through typed APIs rather than arbitrary raw system calls; keep
  platform-specific APIs out of phase 1.
- Limit process APIs to the current process initially: arguments, environment lookup, working
  directory, and process exit. Defer subprocess management.
- Use a monotonic clock for elapsed-time `Instant`; represent `Duration` as signed 64-bit
  nanoseconds with checked overflow. Actual clock precision remains platform-dependent.
- Keep phase 1 time support to monotonic elapsed-time measurement; defer wall-clock timestamps,
  calendar dates, and time-zone handling.
- Preserve `readText`/`writeText` as UTF-8 convenience APIs and implement them through the text
  adapter layer.
- Include minimal language/compiler support for a byte value and bulk byte buffers so the
  byte-oriented APIs do not expose bytes as ordinary `Int` values.
- Make cursor-advancing reads and writes `mut` operations, following existing mutability and
  reference-capability rules.
- Bulk reads may return partial progress and report EOF distinctly; writes complete the supplied
  buffer or raise an I/O failure.
- UTF-8 text adapters reject malformed input with `IoFailure` rather than silently replacing it.
