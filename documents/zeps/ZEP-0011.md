# ZEP-0011: Standard Library Phase 1: I/O, Environment, and Time

## Status

Draft

## Author

Marcelo Rodríguez

## Created

2026-10-13

## Related ZEPs

- None.

## Abstract

This proposal defines a first foundation phase for the Zeron standard library, centered on
cross-platform I/O abstractions, process and environment access, and basic time utilities. It
prioritizes immutable value types where practical and uses explicit mutable references for APIs that
must mutate a resource or cursor. A dedicated serialization API is deferred until Zeron's
serialization model is settled.

## Motivation

The standard library currently has a small I/O surface: printing, whole-file text reads and writes,
filesystem paths, and typed I/O and disposal failures. These are useful primitives but do not yet
form a general foundation for stream-oriented APIs or portable process and time facilities.

A coherent first phase can establish reusable abstractions for applications without prematurely
choosing serialization formats or adding platform-specific APIs without a clear compatibility
boundary.

## Goals

- Establish general `Reader` and `Writer` abstractions for incremental I/O.
- Provide discoverable modules for command-line arguments, environment variables, and a carefully
  scoped set of operating-system interactions.
- Provide immutable `Instant` and `Duration` values with useful comparison and arithmetic semantics.
- Reuse typed raised effects for recoverable I/O and system failures where appropriate.
- Favor immutable values and read-only interfaces, using mutable reference capability only when an
  operation changes the state of a resource.
- Keep APIs portable where possible and make platform-dependent behavior explicit.
- Design the foundation so dedicated serialization libraries can be added later without binding
  their model prematurely to these primitives.

## Non-goals

- A JSON, XML, TOML, or other dedicated serialization API in this phase.
- A general asynchronous I/O or cancellation framework.
- A full process-management, networking, device, or operating-system abstraction layer.
- Exposing arbitrary raw operating-system syscalls without a portability and safety policy.
- Replacing existing filesystem, text-I/O, or resource-management APIs without a migration plan.

## Proposal

Develop this phase as a coherent but staged standard-library foundation with the following areas:

### General I/O

Define `Reader` and `Writer` abstractions for incremental input and output. The design must decide
whether the base abstractions operate on bytes, characters, or a small layered model with distinct
byte and text readers/writers. Whole-file text helpers should be expressible in terms of the
resulting abstractions where practical, but need not be rewritten if doing so would degrade their
behavior.

Reading and writing should report failures through declared typed effects rather than silently
returning success-shaped defaults. Resource ownership and closure should compose with the existing
`Disposable` and `using` behavior. The API should distinguish resource lifetime from a read/write
operation and should not imply that a reader or writer can be safely shared concurrently.

Prefer immutable source and destination descriptions, configuration, and returned data. A cursor-
advancing reader or stateful writer may require `mut` operations and a mutable reference view. This
must follow Zeron's existing distinction between binding reassignment and receiver mutation:
`let mut` does not grant mutation capability, and `&T` is permission to mutate rather than a
guarantee of exclusive access. Raising an effect and mutating a receiver are independent properties.

### Environment and system access

Provide modules for:

- command-line arguments, exposed as an immutable snapshot or immutable sequence where possible;
- environment-variable lookup and, if supported, mutation, with missing values represented
  explicitly rather than collapsed into empty strings;
- a deliberately bounded set of operating-system interactions needed by ordinary programs.

The phrase “syscalls” requires a scope decision. The initial API should prefer portable, typed
operations over a public mechanism for issuing arbitrary numeric OS syscall identifiers. Platform-
specific facilities, permissions, blocking behavior, and host failures must be documented and
represented explicitly. Any raw or unsafe interface should be separately scoped and opt-in.

### Time

Provide immutable `Duration` and `Instant` values. `Duration` should represent elapsed amounts and
support well-defined arithmetic and comparison. `Instant` should represent a point from a monotonic
clock suitable for measuring elapsed time, with subtraction producing a `Duration`; it should not be
implicitly treated as a wall-clock timestamp.

If wall-clock date/time is included in this phase, keep it distinct from monotonic `Instant` and
define timezone and calendar semantics separately. The initial phase may defer civil-time formatting
and parsing if those choices would expand the scope.

## Compatibility and impact

This adds standard-library API surface and will require the normal standard-library API version
policy to be followed. Existing `zeron.io`, `zeron.io.text`, `zeron.fs`, and `zeron.resource`
behavior should remain compatible unless a separate migration is proposed.

Public abstractions should be designed for separately compiled consumers and represented through
the existing library API index. Java-backed implementations should remain behind explicit external
facades and must not make host implementation classes part of source-level API identity.

## Alternatives

- Continue adding one-off I/O helpers — small immediate changes, but does not provide composable
  stream abstractions.
- Start with byte-only or text-only I/O — simpler, but risks prematurely fixing the abstraction
  layer; this proposal asks the design phase to choose based on real use cases.
- Expose raw system calls — maximally flexible but non-portable, unsafe, and difficult to version as
  a standard cross-platform API.
- Include serialization formats now — rejected for this phase because the serialization model and
  desired format/conversion semantics are not yet settled.
- Make all Reader/Writer operations immutable — does not naturally model advancing cursors or
  resource state; mutable references remain appropriate where state mutation is intrinsic.

## Implementation and validation

Before implementation, inventory existing Java facades and standard-library APIs, then settle
package names, byte/text layering, failure effects, resource ownership, environment mutation policy,
the precise syscall/platform boundary, and monotonic-time representation.

Implement in small, independently testable slices. Validate in-memory readers/writers, end-of-input,
partial reads/writes, failure propagation, disposal through `using`, command-line argument order,
missing and present environment variables, platform-specific behavior gates, duration arithmetic,
and monotonic instant differences. Add compiled-library API-index round trips and tests that verify
mutating operations require mutable receiver views while immutable data and queries remain usable
through read-only views. Keep format-specific serialization out of the acceptance tests for this
phase.

## Open questions

- Should `Reader` and `Writer` be byte-oriented, text-oriented, or layered into both abstractions?
- Are reads and writes synchronous and blocking in the initial API?
- Which operations close, flush, or retain ownership of an underlying resource?
- Which environment mutations are needed, and should they affect only the current process?
- What does “syscalls” mean for phase 1: a small portable system module, selected platform
  capabilities, or something else? Should arbitrary syscalls be explicitly prohibited?
- Which monotonic clock and precision should back `Instant`, and what overflow behavior should
  `Duration` arithmetic use?
- Does phase 1 include wall-clock/civil time, or only elapsed-time measurement?
- Which existing whole-file helpers should delegate to `Reader`/`Writer`, if any?
