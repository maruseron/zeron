## Abstract

This proposal defines an explicit effect-only subtype relation, inherited effect payload information,
and a denotable top `Effect` type. The `under` relation allows effect subtypes to satisfy broader
`raises` requirements and handler cases. It remains separate from ordinary contract conformance;
multiple effect parents are permitted without introducing multiple inheritance of payload state.

## Motivation

The current effect system uses exact nominal matching and has no common source-level effect type.
A function cannot declare a shared super-effect in place of several concrete effects, and a handler
cannot handle a family of effects through a broad case. The effect-kind and nominal-payload
directions in [ZEP-0054](./ZEP-0054.md) and [ZEP-0055](./ZEP-0055.md) make effect payloads more
ordinary but deliberately do not change raised-set inclusion or handler matching.

Effect subtyping and a top type would make those operations composable, but they must remain
explicitly effect-specific. Effect subtyping also needs a payload rule: a broad handler should be
able to inspect the state declared by its matched super-effect without claiming subtype-only
properties. Ordinary contract conformance describes behavior and does not by itself establish
raised-effect inclusion or handler coverage.

## Goals

- Define effect-only subtyping and a built-in top `Effect` type.
- Add `under` syntax for direct effect supertypes and define payload-property inheritance.
- Permit multiple effect supertypes while avoiding ambiguous or conflicting payload-state inheritance.
- Define how subtyping affects `raises` compatibility and function-type assignability.
- Define how subtype effects match handlers and when a handler removes an effect from the enclosing
  effect set.
- Specify most-specific selection, ambiguity diagnostics, runtime dispatch, and separately
  compiled-library metadata.

## Non-goals

- Generic effect payloads, which remain separately scoped in [ZEP-0005](./ZEP-0005.md).
- Effect-row polymorphism or inferred polymorphic effect variables; see [ZEP-0086](./ZEP-0086.md).
- Resumable effects or continuations; see [ZEP-0007](./ZEP-0007.md).
- Automatic conversion between Java exceptions, `Result`, and raised effects.
- Deriving effect subtyping from ordinary contracts or class inheritance.
- Making ordinary non-effect classes assignable to or raisable as `Effect`.

## Proposal

Provide a denotable built-in `zeron.lang.Effect` top type, declared in the standard library as an
ordinary effect with no payload properties. Every declared effect is a subtype of `Effect`; regular
classes cannot implement or extend it, and no effect names it as an `under` target. User code
cannot construct a bare `Effect`; the standard library supplies the constructors that wrap host
failures (illustratively `Effect.fromException(Exception)`, with `Exception` a library
`external class` over `java.lang.Exception`). Zeron effects therefore wrap host exceptions without
depending on the host exception hierarchy, and no mapping between host exceptions and effects is
implicit: only library code converts. `Effect` exposes no payload-specific members.

`Effect` may appear in `raises` lists and handler cases, and is also an ordinary value type
(variables, fields, parameters, generic arguments), for example to store an effect and raise it
again; raising a value of static type `Effect` adds `Effect` to the raised set. A separate
existential for "some effect" is unnecessary because subtyping already provides it. An unguarded,
irrefutable `case Effect` intentionally acts as an explicit catch-all for raised effects; it is not
an implicit handler or a wildcard pattern. `raises Effect` is maximally impure: documentation should
discourage it, but the language does not forbid it.

An effect may declare direct effect supertypes with `under`:

```zeron
public effect IOError {
    public property path: String;
}

public effect Retryable {}

public effect FileNotFound under IOError, Retryable {
    public property code: Int;
}
```

Every `under` target must be an effect type. The relation is independent of ordinary class
inheritance and contract conformance; its reflexive and transitive closure defines effect
subtyping. Cycles are rejected. The built-in `Effect` is the implicit top effect and is not named
as an `under` target.

The `under` relation is modeled on contract conformance. A child that names a payload-bearing
parent must itself declare, with the same name, type, and mutation capability, every payload
property that parent contributes, including those the parent inherits. The child's declaration
therefore states its complete payload, and the compiler derives the delegation to the parent's
constructor by matching those declarations; the child does not store a second copy of the state. The
child may add further properties. A missing or differing redeclaration is rejected. To avoid
multiple inheritance of mutable state, at most one direct parent may contribute payload properties
through its inheritance chain. Every other direct parent must be stateless, including its own
ancestors. Stateless effects can therefore express additional effect categories without introducing
a second payload-state path.

Every effect has an autogenerated canonical constructor `new` that takes its complete payload in
the order of its own declaration (see [ZEP-0054](./ZEP-0054.md)) and calls the parent's canonical
constructor with the matching properties. Named constructors, `constructor name(...)`, delegate to
the canonical constructor. Constructor lowering and library metadata must preserve the effective
payload shape.

`under` does not provide or imply contract behavior. Effect behavior remains separate and must be
provided through ordinary `is` contract conformance as supported by the relevant contract and
effect proposals. In particular, effect subtyping does not infer a subtype relation from a shared
contract.

Behavior is reachable through a parent-typed view by conformance: given
`effect IOError under Parent is Retryable`, a handler `case IOError e` may call `e.retryDelay()`. A
child such as `FileNotFound under IOError` satisfies a `T: Retryable` bound only if it also
declares `is Retryable`. This separation between subtyping and conformance is intentional.

Use the same relation for `raises`-set compatibility and handler matching and coverage: a raised
subeffect satisfies a required super-effect, and a super-effect case may handle its subeffects. An
implementation may only be assigned to a function type if every possible effect is covered by the
expected effect set. `raises Effect` permits any effect to escape through that callable boundary.

A handler case for a super-effect may match any raised subtype beneath it. Its payload is viewed as
the case's declared effect type, exposing that effect's inherited payload properties but not
properties introduced only by a concrete subtype. An unguarded, irrefutable `Effect` case covers
the complete raised-effect set. A handler may remove an effect only when its cases cover it under
the relation; guarded or refutable patterns must not falsely establish coverage. Effects raised in
handler guards or arms continue to escape into the enclosing scope.

When comparable handler cases both match, choose the most-specific effect case independent of
source order. Diagnose incomparable applicable cases as ambiguous; do not use declaration or
import-order priorities. Because effects are non-generic in this proposal, dispatch must use the
declared effect identity and explicit subtype metadata, not ordinary Java exception-class matching.
Do not infer a subtype edge from a shared ordinary contract.

### Runtime representation

The generated payload class of each effect realizes the relation. The single payload-bearing
parent, if any, is the JVM superclass; each stateless parent is a generated marker interface that
the child implements; `Effect` is the compiler-owned runtime marker of
[ZEP-0055](./ZEP-0055.md). An effect that is the target of an `under` edge therefore has a
non-final generated class; source-level finality is unchanged. Handler dispatch tests the payload
with `instanceof` against this generated hierarchy, never against class names or the carrier
exception's type. The library index records the direct `under` edges, each effect's effective
payload shape, and the top marker.

### Effect sets and rows

- Sets are compared in canonical form: duplicates and elements subsumed by another element are
  removed, `Effect` absorbs every other element, and the order is canonical for the index.
  `A ⊆ B` holds when every element of `A` is a subtype of some element of `B`.
- A handler case for effect `C` removes every element `e ≤ C` from the protected set. An element
  broader than `C` stays: handling `FileNotFound` does not remove `IOError`.
- For an open row `{IOError | R}`, handling `IOError` leaves `R`. This is a sound
  over-approximation, since `R` may contain subeffects the handler caught.
- Unifying an open row against a concrete set solves the row variable as the minimal remainder: the
  concrete elements not subsumed by the explicit ones. An explicit annotation overrides inference.
  There are no "lacks" predicates in this version.
- Ambiguity between incomparable handler cases is checked against the effects visible at compile
  time under the protected expression's set. A protected set that contains `Effect`, or an effect
  that later libraries may extend, is checked only against the visible hierarchy. This limit is
  accepted.

## Compatibility and impact

Effect subtyping changes source-level effect-set compatibility, handler behavior, and the generated
runtime representation. The compiled-library index must preserve explicit subtype edges, effective
payload properties, and the built-in top marker across compilation boundaries. Runtime dispatch
must select handlers without conflating unrelated effects or relying only on ordinary JVM class
names.

Adding or removing an `under` edge, or changing a parent's payload, breaks dependents. This is
accepted while Zeron is alpha; the library index is versioned by schema and by library API, which
makes the break detectable.

## Alternatives

- Retain exact nominal matching — simplest and remains valid if concrete use cases do not justify a
  hierarchy or a broad catch case.
- Derive effect subtyping directly from ordinary class inheritance — superficially familiar, but
  risks conflating value substitutability with effect-set inclusion and handler matching.
- Use only the non-denotable `effect` kind constraint — permits generic propagation but does not
  provide a value type or explicit broad handler case.
- Add implicit handler priorities — may hide ambiguous coverage and make behavior depend on
  declaration or import order.

## Implementation and validation

Implement effect-supertype declarations and inherited payload validation before changing effect-set
operations in declarations, function types, calls, handlers, lambdas, constructors, external
mappings, and API-index serialization. Define a runtime representation for explicit effect identity
and subtype dispatch that remains compatible with generated payload classes and Java exception
mappings.

Tests should cover exact and subtype propagation, `raises Effect`, function-type assignment,
complete and partial handler coverage, the explicit catch-all case, most-specific selection,
incomparable ambiguity, inherited payload access through handlers, inherited mutation capabilities,
rejection of conflicting payload-state paths, nested handlers, separately compiled libraries, and
dispatch without accidental catches. Generic effect payloads and effect-row polymorphism remain
outside this validation scope.

## Resolved design questions (2026-11-09)

- **Runtime representation.** Generated JVM hierarchy: superclass for the payload-bearing parent,
  marker interfaces for stateless parents, compiler-owned marker for `Effect`.
- **Inherited payload construction.** Children redeclare inherited properties; the canonical `new`
  delegates to the parent's by name.
- **Admissibility.** `Effect` satisfies `E: effect`. The single source-level top name is `Effect`;
  `AnyEffect` is not defined and no second public top is introduced.
- **Parent-declared members on a child-typed value.** `under` is not `is` and does not inherit
  behavior. A child-typed value exposes only members the child declares and behavior from contracts
  the child itself names with `is`. Members declared in a parent effect's body are available only
  through a view whose static type is the parent: a handler case that names the parent binds its
  payload as that parent type, and an assignment or parameter of the parent's type provides the same
  view. A child that wants that behavior on its own values either redeclares the member or declares
  the relevant `is` conformance. This keeps subtyping and conformance separate and preserves the
  existing rule that a child satisfies `T: Retryable` only when it declares `is Retryable`.
- **Late-declared common subtypes.** Compile-time ambiguity checking is limited to the hierarchy
  visible when the handler is compiled. If a payload matches two incomparable handler cases only
  because a subtype was declared in a later library, dispatch must not choose by source or import
  order: the runtime reports an ambiguity error naming the payload effect and both case effects and
  aborts the dispatch. Comparable cases still use most-specific selection. A later library adding a
  subtype of two effects named by one handler therefore produces a runtime ambiguity error, not a
  silent choice.
- **Index metadata.** Existing exported-class records cannot carry `under` edges: `ClassExport` has
  no such field and the record is positional. One schema revision adds each effect's direct `under`
  edges; the effective payload shape needs no separate field because `ClassExport` already records
  the complete canonical-constructor parameter types and names, including non-public payload state,
  as verified by ZEP-0054's library-index round-trip test. Bump `API_INDEX_SCHEMA_VERSION` once and
  share that revision with ZEP-0015 and ZEP-0005; ZEP-0054 needs no revision of its own.

## Decision

Accepted 2026-11-09. `under` defines effect-only subtyping modeled on contract conformance
(children redeclare inherited payload; at most one payload-bearing parent, other parents stateless);
canonical `new` plus delegating named constructors; JVM-hierarchy runtime representation with
marker interfaces; a denotable `Effect` top that is also a value type and wraps host exceptions
only through library constructors; canonical effect sets with minimal-remainder row unification;
and most-specific handler selection with ambiguity diagnostics. Parent-declared members remain
reachable only through a parent-typed view, late-declared incomparable matches are a runtime
ambiguity error, and the library index needs one schema revision for direct `under` edges, shared
with ZEP-0015 and ZEP-0005. Implemented 2026-11-09; the library index schema and standard-library
API versions are 12.

## Discussion notes

- Make effect subtyping an explicit effect-only relation independent of ordinary nominal class
  inheritance.
- Provide a denotable top `Effect` type that only effect payloads inhabit; an unguarded, irrefutable
  handler case for it is an explicit catch-all.
- Use `under` for effect supertypes; inherit payload properties and their mutation capabilities.
- Permit multiple effect parents only when at most one parent path contributes payload state;
  additional parents must be stateless.
- Keep contract behavior separate from `under`; behavior is supplied through ordinary `is` contract
  conformance.
- Give a broad handler case the payload view of its named effect, including inherited properties
  but excluding subtype-only properties.
- Use the same effect-subtyping relation for `raises`-set compatibility and handler matching and
  coverage.
- Permit multiple supertypes, but reject incomparable handler cases that can both match; do not use
  priorities based on declaration or import order.
- When comparable handler cases both match, select the most-specific effect case independent of
  source order.
- Require runtime dispatch and compiled-library metadata to preserve the explicit relation soundly;
  otherwise defer implementation rather than relying on JVM exception-class matching alone.
- Keep ordinary contract conformance separate from effect subtyping, even when effects gain ordinary
  contract support under ZEP-0054.
- Make the denotable `Effect` type and the `E: effect` admissibility marker share the runtime effect
  marker. The generic marker permits propagation, not handler matching on unresolved type variables.
- Model `under` on contract conformance: the child redeclares the inherited payload and the
  compiler derives constructor delegation to the parent.
- Behavior flows through `is` conformance, not `under`; a child satisfies a contract bound only if
  it declares the conformance itself.
- Allow `Effect` as an ordinary value type; discourage `raises Effect` in documentation without
  prohibiting it.
- Keep host exceptions out of the effect hierarchy: library constructors wrap them, and nothing
  maps implicitly.
