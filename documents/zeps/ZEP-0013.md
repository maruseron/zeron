# ZEP-0013: Effect Subtyping and the Top Effect Type

## Abstract

This proposal defines an explicit effect-only subtype relation and a denotable top `Effect` type.
Subtypes may satisfy broader `raises` requirements and handler cases; `Effect` may explicitly catch
or declare any raised effect. The relation remains distinct from ordinary contract conformance.

## Motivation

The current effect system uses exact nominal matching and has no common source-level effect type.
A function cannot declare a shared super-effect in place of several concrete effects, and a handler
cannot handle a family of effects through a broad case. The effect-kind and nominal-payload
directions in [ZEP-0054](./ZEP-0054.md) and [ZEP-0055](./ZEP-0055.md) make effect payloads more
ordinary but deliberately do not change raised-set inclusion or handler matching.

Effect subtyping and a top type would make those operations composable, but they must remain
explicitly effect-specific. Ordinary contract conformance describes value APIs and does not by
itself establish raised-effect inclusion or handler coverage.

## Goals

- Define effect-only subtyping and a built-in top `Effect` type.
- Define how subtyping affects `raises` compatibility and function-type assignability.
- Define how subtype effects match handlers and when a handler removes an effect from the enclosing
  effect set.
- Specify most-specific selection, ambiguity diagnostics, runtime dispatch, and separately
  compiled-library metadata.

## Non-goals

- Generic effect payloads, which remain separately scoped in [ZEP-0005](./ZEP-0005.md).
- Effect-row polymorphism or inferred polymorphic effect variables.
- Resumable effects or continuations; see [ZEP-0007](./ZEP-0007.md).
- Automatic conversion between Java exceptions, `Result`, and raised effects.
- Deriving effect subtyping from ordinary contracts or class inheritance.
- Making ordinary non-effect classes assignable to or raisable as `Effect`.

## Proposal

Provide a denotable built-in `zeron.lang.Effect` top type. Every declared effect is a subtype of
`Effect`; regular classes cannot implement or extend it. `Effect` is not constructible and exposes
no payload-specific members. It may appear in `raises` lists and handler cases. An unguarded,
irrefutable `case Effect` intentionally acts as an explicit catch-all for raised effects; it is not
an implicit handler or a wildcard pattern.

In addition to the built-in top type, effect declarations may name explicit effect-only supertypes.
These edges are independent of ordinary nominal class inheritance and contract conformance. Their
reflexive and transitive closure defines the relation; cycles are rejected and multiple supertypes
are allowed. The syntax for declaring the edges remains open.

Use the same relation for `raises`-set compatibility and handler matching and coverage: a raised
subeffect satisfies a required super-effect, and a super-effect case may handle its subeffects. An
implementation may only be assigned to a function type if every possible effect is covered by the
expected effect set. `raises Effect` permits any effect to escape through that callable boundary.

A handler case for a super-effect may match any raised subtype beneath it. An unguarded,
irrefutable `Effect` case covers the complete raised-effect set. A handler may remove an effect
only when its cases cover it under the relation; guarded or refutable patterns must not falsely
establish coverage. Effects raised in handler guards or arms continue to escape into the enclosing
scope. The payload type exposed by a broad super-effect case must not claim fields or methods that
are available only on a concrete subtype.

When comparable handler cases both match, choose the most-specific effect case independent of
source order. Diagnose incomparable applicable cases as ambiguous; do not use declaration or
import-order priorities. Because effects are non-generic in this proposal, dispatch must use the
declared effect identity and explicit subtype metadata, not ordinary Java exception-class matching.
Do not infer a subtype edge from a shared ordinary contract.

## Compatibility and impact

Effect subtyping changes source-level effect-set compatibility, handler behavior, and the generated
runtime representation. The compiled-library index must preserve explicit subtype edges and the
built-in top marker across compilation boundaries. Runtime dispatch must select handlers without
conflating unrelated effects or relying only on ordinary JVM class names.

## Alternatives

- Retain exact nominal matching — simplest and remains valid if concrete use cases do not justify a
  hierarchy or a broad catch case.
- Derive effect subtyping directly from ordinary class inheritance — superficially familiar, but
  risks conflating value substitutability with effect-set inclusion and handler matching.
- Use only the non-denotable `effect` kind constraint — permits generic propagation but does not
  provide a value type or explicit broad handler case.
- Add implicit handler priorities — may hide ambiguous coverage and make behavior depend on
  declaration or import order.

## Implementation and validation

Specify effect-supertype declaration syntax and the broad-case payload view. Inventory effect-set
operations in declarations, function types, calls, handlers, lambdas, constructors, external
mappings, and API-index serialization. Define a runtime representation for explicit effect identity
and subtype dispatch that remains compatible with generated payload classes and Java exception
mappings.

Tests should cover exact and subtype propagation, `raises Effect`, function-type assignment,
complete and partial handler coverage, the explicit catch-all case, most-specific selection,
incomparable ambiguity, nested handlers, separately compiled libraries, and dispatch without
accidental catches. Generic effect payloads remain outside this validation scope.

## Open questions

- What source syntax declares effect-only supertypes, and are those supertypes abstract categories
  or payload-bearing effect types?
- What type does a broad super-effect handler expose for the concrete payload? The binding must not
  claim subtype-only members.
- What runtime representation preserves effect identity and the subtype relation across separately
  compiled-library boundaries?
- The denotable `Effect` type satisfies the `E: effect` generic admissibility marker; see
  [ZEP-0055](./ZEP-0055.md).

## Decision

Draft for exploration. The explicit effect-only relation, top `Effect` type, common raised-set
compatibility, most-specific handler selection, and ambiguity diagnostics are the proposed
direction. Syntax, broad-case payload typing, and runtime/library-index representation remain open.

## Discussion notes

- Make effect subtyping an explicit effect-only relation independent of ordinary nominal class
  inheritance.
- Provide a denotable top `Effect` type that only effect payloads inhabit; an unguarded, irrefutable
  handler case for it is an explicit catch-all.
- Use the same effect-subtyping relation for `raises`-set compatibility and handler matching and
  coverage.
- Permit multiple supertypes, but reject incomparable handler cases that can both match; do not use
  priorities based on declaration or import order.
- When comparable handler cases both match, select the most-specific effect case independent of
  source order.
- Require runtime dispatch and compiled-library metadata to preserve the explicit relation soundly;
  otherwise defer implementation rather than relying on JVM exception-class matching alone.
- Keep ordinary contract conformance separate from effect subtyping, even when effects gain ordinary
  contract support under ZEP-0054.
- Make the denotable `Effect` type and the `E: effect` admissibility marker share the runtime effect
  marker. The generic marker permits propagation, not handler matching on unresolved type variables.
