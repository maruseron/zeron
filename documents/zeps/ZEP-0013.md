## Abstract

This proposal explores whether typed raised effects should support subtyping: a raised effect may
satisfy a broader effect requirement or be handled by a broader handler case. It will define the
effect relation and its interactions with `raises` sets, handler coverage, runtime dispatch, and
separately compiled libraries before any implementation is approved.

## Motivation

The current effect system uses exact nominal matching. A function declaring one effect cannot
declare a super-effect in its place, and a handler cannot handle a family of effects through a
shared super-effect. An effect hierarchy could make APIs more composable, but ordinary value
subtyping does not automatically define safe effect propagation or handler coverage.

Generic effect payloads are separately explored in [ZEP-0005](./ZEP-0005.md). This proposal does not
assume that generic effect arguments exist or that their variance follows ordinary value subtyping.

## Goals

- Determine whether effect subtyping is useful and sound for Zeron's typed raised-effect model.
- Define how subtyping affects `raises` compatibility and function-type assignability.
- Define how subtype effects match handlers and when a handler removes an effect from the enclosing
  effect set.
- Specify ambiguity diagnostics, runtime dispatch, and separately compiled-library metadata.

## Non-goals

- Generic effect payloads, which remain separately scoped in ZEP-0005.
- Effect-row polymorphism or inferred polymorphic effect variables.
- Resumable effects or continuations; see [ZEP-0007](./ZEP-0007.md).
- Automatic conversion between Java exceptions, `Result`, and raised effects.

## Proposal

If effect subtyping is adopted, define explicit effect-only subtype edges, independent of ordinary
nominal class inheritance. The subtype relation is their reflexive and transitive closure and must be
acyclic. Allow multiple supertypes.

Use the same relation for `raises`-set compatibility and handler matching and coverage: a raised
subtype satisfies a required super-effect, and a super-effect case may handle its subeffects. An
implementation may only be assigned to a function type if its possible effects are permitted by the
expected effect set. A handler may remove an effect only when its cases cover that effect under the
relation; partial or refutable payload patterns must not falsely establish coverage. Handler-arm
effects continue to escape into the enclosing scope.

When comparable handler cases both match, choose the most-specific effect case independent of
source order. Diagnose incomparable applicable cases as ambiguous; do not use declaration or
import-order priorities. Do not assume effect-argument variance or matching by erased JVM class.
Runtime dispatch and separately compiled-library metadata must preserve the explicit relation
soundly. If they cannot, defer implementation rather than silently weakening the relation.

## Compatibility and impact

Effect subtyping changes source-level effect-set compatibility and handler behavior. The
compiled-library index must preserve enough information to validate the relation across compilation
boundaries. Runtime dispatch must select handlers without conflating unrelated effects or relying
only on erased JVM classes.

## Alternatives

- Retain exact nominal matching — simplest and remains valid if concrete use cases do not justify a
  hierarchy.
- Derive effect subtyping directly from ordinary class inheritance — superficially familiar, but
  risks conflating value substitutability with effect-set inclusion and handler matching.
- Add implicit handler priorities — may hide ambiguous coverage and make behavior depend on
  declaration or import order.

## Implementation and validation

Inventory effect-set operations in declarations, function types, calls, handlers, lambdas,
constructors, external mappings, and API-index serialization. Specify the subtype relation and
runtime dispatch before implementation. Tests should cover exact and subtype propagation, function
type assignment, complete and partial handler coverage, ambiguous relations, nested handlers,
separately compiled libraries, and dispatch without accidental catches.

## Open questions

- What runtime and API-index representations preserve the explicit relation soundly, including when
  effects cross separately compiled-library boundaries?

## Decision

Draft for exploration. The static relation and matching rules below are agreed as the design
direction, but implementation remains blocked until a sound runtime and library-index
representation is established.

## Discussion notes

- If effect subtyping is adopted, make it an explicit effect-only relation independent of ordinary
  nominal class inheritance.
- Use the same effect-subtyping relation for `raises`-set compatibility and handler matching and
  coverage.
- Permit multiple supertypes, but reject incomparable handler cases that can both match; do not use
  priorities based on declaration or import order.
- When comparable handler cases both match, select the most-specific effect case independent of
  source order.
- Require runtime dispatch and compiled-library metadata to preserve the explicit relation soundly;
  otherwise defer implementation rather than relying on JVM exception-class matching alone.
