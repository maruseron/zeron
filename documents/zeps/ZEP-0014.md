# ZEP-0014: Stable Generic Type Admissibility

## Abstract

This proposal explores whether `Stable<T>` can provide a sound generic type-admissibility
constraint for values whose equality- or hash-relevant state must not change while used as keys.
It must define what stability guarantees, how aliases and reachable mutable state affect it, and
whether the guarantee is enforceable in Zeron.

## Motivation

Hash-based collections rely on keys retaining equality- and hash-relevant state while stored.
`Eq<T>` and `Hashable<T>` describe operations, but do not guarantee that a value or reachable state
will remain unchanged. A generic constraint could express a stronger requirement, but Zeron's
reference and mutability model permits aliases to mutate reachable state.

`NonNull` and `Numeric` in [ZEP-0010](./ZEP-0010.md) are closed, statically checkable admissibility
constraints. Stability is different: it may require reasoning about object graphs, aliasing,
mutation, or a restricted opt-in contract.

## Goals

- Define the observable guarantee required when a value is admitted as stable.
- Evaluate whether that guarantee can be checked soundly with Zeron's aliasing and mutability rules.
- Determine how user-defined types, equality/hash implementations, and reachable state affect the
  guarantee.
- Specify how any accepted constraint is declared, forwarded, diagnosed, and represented in
  separately compiled libraries.

## Non-goals

- Adding equality or hashing operations through `Stable<T>`; operation requirements remain the
  concern of `Eq<T>` and `Hashable<T>`.
- Treating an immutable reference or immutable binding as proof that all reachable state is stable.
- Assuming runtime freezing, ownership, or deep immutability without a separate design.
- Changing the accepted `NonNull` or `Numeric` semantics in ZEP-0010.

## Proposal

Explore `Stable<T>` as a generic admissibility constraint only if its guarantee can be stated and
enforced soundly. The design must account for every alias capable of changing equality- or
hash-relevant state during the period a value is relied upon as stable. A shallow immutable view is
not sufficient evidence when mutable aliases or reachable mutable objects remain.

Evaluate possible approaches, such as a compiler-proven transitive property, explicit opt-in with
verifiable restrictions, or a scoped ownership/freeze mechanism. Do not accept a marker assertion
that can silently invalidate hash collection behavior. If no sound, useful guarantee fits the
current language model, retain the constraint as deferred or reject it.

## Compatibility and impact

Any accepted constraint changes generic well-formedness and could reject type arguments currently
accepted. Exported signatures must preserve the constraint and its evidence rules in the library
index. If the guarantee depends on runtime ownership or freezing, its runtime and ABI consequences
must be explicit.

## Alternatives

- Keep key stability as a documented caller obligation — simple, but provides no static guarantee.
- Rely on `Eq<T>` and `Hashable<T>` — these contracts provide operations, not stability under
  mutation or aliasing.
- Omit `Stable<T>` — appropriate if no sound, useful guarantee can be enforced without a broader
  ownership or immutability model.

## Implementation and validation

Do not implement the constraint before defining its guarantee and evidence model. Construct
adversarial tests with aliases that mutate equality-relevant fields, reachable objects, and custom
equality/hash state while keys are stored. Test generic forwarding, separately compiled metadata,
and diagnostics for types that cannot establish the guarantee.

## Open questions

- Is stability transitive over all reachable state, or limited to state observed by equality and
  hashing, and how can that boundary be established soundly?
- Can compiler analysis prove the required property, or does it require explicit restrictions,
  ownership, or freezing?
- Can user-defined equality and hashing participate without allowing unverifiable stability claims?
- If the current language cannot enforce a useful guarantee, should `Stable<T>` remain deferred or
  be rejected?

## Decision

Rejected 2026-10-18. Under Zeron's current aliasing and mutation model, the proposal cannot offer a
sound generic guarantee that equality- or hash-relevant state remains unchanged. A marker contract
or opt-in assertion would not establish that guarantee, while compiler proof or enforcement would
require a broader ownership, freezing, or immutability model that is not otherwise designed. Do not
add `Stable<T>` on the current model. Revisit the problem only if such a model is proposed with a
concrete guarantee.
