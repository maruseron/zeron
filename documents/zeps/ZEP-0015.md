# ZEP-0015: Runtime Reification of Generic Type Witnesses

## Abstract

This proposal explores preserving generic source-type identity at runtime when JVM erasure would
otherwise remove applied type arguments. The immediate motivating use case is sound runtime
identity and dispatch for generic typed effects in ZEP-0005. The proposal must distinguish runtime
type identity witnesses from existing contract witnesses used to provide operations.

## Motivation

Generic type arguments are erased on the JVM. ZEP-0005 requires runtime dispatch to distinguish
applied effect identities, including through generic calls and separately compiled libraries;
matching only an erased effect class cannot distinguish different applications of the same generic
effect.

Zeron already uses the term “witness” for compile-time evidence satisfying contract bounds. Runtime
type identity is a different concern: it describes an applied source type and does not itself
provide the operations of a contract implementation. A reusable design may serve other language
features, but it must be justified without assuming general-purpose reflection is required.

## Goals

- Define what applied source-type identity must be preserved at runtime and in which contexts.
- Evaluate compiler-managed runtime type witnesses or equivalent reification strategies that survive
  generic calls and separately compiled-library boundaries.
- Define how generic type variables obtain and forward runtime identity without relying on erased JVM
  classes alone.
- Establish whether reification can support generic effect dispatch without conflating runtime type
  identity with contract-witness selection.

## Non-goals

- Designing generic effect payload semantics, which remain in ZEP-0005.
- Adding general reflection, runtime member discovery, or arbitrary inspection of program types
  unless required by an accepted reification model.
- Replacing compile-time contract witnesses or changing their selection rules.
- Effect subtyping, which is explored separately in ZEP-0013.

## Proposal

Explore a compiler-supported representation of applied source-type identity that can be propagated
through generic code and preserved across separately compiled libraries. The design must specify
which type distinctions are observable and necessary, how generic functions and declarations
receive or forward identity, and how runtime operations consume it.

Treat any runtime descriptor or witness as distinct from a contract witness: it represents type
identity and is not evidence that a type provides a contract's methods. Do not assume that JVM
`Class` objects, generated names, or ad hoc tokens are sufficient for nested and applied generic
types. ZEP-0005 remains blocked until a sound representation handles its required cases.

Keep the initial design focused on demonstrated runtime needs. If broader reflection or user-facing
type inspection is proposed, identify it as a separate scope decision.

## Compatibility and impact

Reification may add hidden runtime parameters, descriptors, generated support classes, or other ABI
changes. The library index must preserve the source-level type information needed to generate and
validate reified operations in consumers. The design must account for old and new compiled
libraries, runtime dispatch correctness, and overhead in generic calls.

## Alternatives

- Keep all generic identity static — preserves the current ABI, but cannot support runtime decisions
  that distinguish erased applied types such as ZEP-0005 requires.
- Use erased JVM classes alone — simple, but conflates distinct applied generic types.
- Add a feature-specific token only for generic effects — may unblock one use case but risks
  duplicating type-identity machinery and fails to establish a reusable model.
- Add general reflection — potentially broader than needed and does not by itself define sound
  identity propagation through generic code.

## Implementation and validation

Inventory generic call lowering, type descriptors, effect raising/handling, external boundaries,
and API-index serialization. Prototype candidate representations against nested generic
applications, generic pass-through functions, direct raises, handlers, and separately compiled
libraries. Measure generated code and runtime overhead. Validate that distinct applied types remain
distinct and that identity is not lost through forwarding or library boundaries.

## Open questions

- Which source-level type distinctions must have runtime identity, including nested generic
  arguments, nullability, arrays, aliases, and function types?
- How is a generic function supplied with the runtime identity of a type variable, and how is it
  forwarded through calls?
- What runtime representation and API-index encoding preserve identity without excessive overhead?
- How do external Java calls and Java-originated values interact with reified source-type identity?
- Is the reusable scope justified beyond the generic-effect use case?
