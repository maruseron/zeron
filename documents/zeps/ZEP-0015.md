## Abstract

This proposal defines an internal runtime representation of applied source-type identity that
survives JVM erasure. It is designed to be shared by two consumers:

- generic typed effects, which need exact applied-effect identity for handler dispatch;
- bounded existentials and type-bound pattern matching, which need to know the hidden or reified
  type at runtime.

The descriptor represents type identity only. It is not a contract witness, does not provide the
operations of a bound, and does not expose general reflection.

The 2026-11-10 implementation closes the descriptor facility and the ZEP-0104 existential/type-test
consumer. Generic-effect construction and handler dispatch are designed separately in the accepted
[ZEP-0005](./ZEP-0005.md) and are not claimed as implemented here.

## Motivation

Generic type arguments are erased on the JVM. ZEP-0005’s first slice needs to distinguish closed
applications such as `E<Int>` and `E<String>` through raising, handling, and separately compiled
libraries. A later generic-propagation slice may extend that identity through type variables.
ZEP-0104’s initial slice needs exact runtime tests for closed applied types and reified type
variables.

Building an effect-specific token would solve one case and leave the same machinery to be rebuilt
for existentials. A single internal descriptor also gives the project one place to define schema,
equality, caching, and separate-compilation behavior.

Zeron already uses “witness” for compile-time evidence satisfying contract bounds. Runtime type
identity is a different concern. This proposal uses “runtime type descriptor” for identity and
reserves “witness” and “evidence” for contract operations.

## Goals

- Define a shared, internal runtime descriptor for applied source types.
- Preserve owner, recursive type arguments, nullability, mutability markers, and arrays.
- Define exact structural equality and stable separate-compilation behavior.
- Define how generic declarations obtain and forward descriptors with a `reified` marker.
- Serve generic effect payload identity and type-bound pattern matching with the same descriptor.
- Keep contract evidence separate from type identity.
- Establish a benchmark and acceptance gate before implementation.

## Non-goals

- General reflection, member discovery, or arbitrary runtime type inspection.
- Replacing compile-time contract witnesses or evidence selection.
- Reifying class type parameters; these are excluded in this version.
- Stored existentials and holder ABI, covered by [ZEP-0106](./ZEP-0106.md).
- Ancestor-aware descriptors and generic effect subtyping, covered by
  [ZEP-0107](./ZEP-0107.md).
- Runtime contract-bound tests, covered by [ZEP-0108](./ZEP-0108.md).
- Function types as runtime type arguments in the first version.
- Designing generic effect payload semantics, which remain in [ZEP-0005](./ZEP-0005.md).

## Proposal

### One descriptor, two consumers

An applied type is represented by an immutable internal descriptor. A descriptor contains:

- the owner’s qualified source name;
- recursively represented type arguments;
- nullability;
- mutability or reference-capability markers that participate in source type identity;
- array element descriptors where applicable.

Aliases are expanded before a descriptor is built. Function types as type arguments are rejected
in the first version.

The descriptor is constructed and consumed by compiler-generated code. Source programs cannot
fabricate one, inspect it, or use it as a general-purpose `Class` replacement.

For effects, the descriptor is used for exact applied-effect identity. For existentials and
reified type variables, it is used for exact runtime type tests. In both cases, equality means
“same applied source type,” not “same JVM class” and not “satisfies this contract.”

### Identity is not evidence

A descriptor and a contract witness answer different questions:

```text
Runtime type descriptor  -> which applied source type is this?
Contract witness         -> which implementation provides this bound's operations?
```

An existential value carries the descriptor for its hidden type and the witnesses for its bounds.
An effect payload carries only the descriptor. A type-bound pattern test consults the descriptor;
calling a bound operation consults the witness. Neither operation substitutes for the other.

### The `reified` admissibility marker

`T: reified` is a generic admissibility marker like `nullable`, `mut`, and `effect`, and combines
with them. It states that the callee receives a runtime descriptor for `T`, passed like a hidden
parameter.

Policy:

1. **Exported declarations state it explicitly.** For anything in the library index—public and
   protected functions, methods, constructors, contract methods, and static functions—the
   compiler never infers `reified` from a body. A signature fully determines its ABI.
2. **Non-exported declarations infer it** transitively within the compilation unit for private and
   local functions and lambdas, because their parameters are not ABI-visible.
3. **Call sites.** When a callee requires `reified T`, the argument type must be fully describable.
   Concrete types yield constant descriptors. A type that mentions the caller’s type variables
   requires those variables to be `reified` (explicit if exported, inferred otherwise), and the
   descriptor is composed at runtime. Otherwise the call is an error that names the variable and
   suggests adding `reified`.
4. **Effect declarations.** The type parameters of an effect declaration are implicitly reified.
   Constructing `E<A>` stores the descriptor of `A` in the payload and follows rule 3 for `A`. No
   marker is written on the declaration.
5. **Handlers.** A handler case `E<T>` over a type variable `T` requires `T: reified`.
   Propagating, forwarding, or re-raising an `E<T>` payload requires nothing.
6. **Contracts and classes.** Contract methods may declare `reified` on method type parameters, and
   implementations must repeat the marker exactly. Class and contract type parameters cannot be
   `reified` in this version.
7. **Combination with `effect`.** `T: effect + reified` supplies the descriptor but does not permit
   handler matching on `T`: an exact descriptor cannot cover subeffects.
8. **Function values.** Generic function values stay rank-1. Reified parameters are specialized
   before conversion to a function type, and the descriptor is captured by the resulting value.

### Representation and propagation

A descriptor is an immutable object holding the owner, argument descriptors, and identity flags. It
is compared structurally with a cached hash. Monomorphic sites use constants.

- **Effects:** a raised payload carries its applied descriptor. Re-raising and forwarding need no
  hidden parameters because the payload already carries it. Hidden descriptor parameters are needed
  only where generic code constructs an effect whose type arguments mention a type variable or
  handles such an effect.
- **Existentials:** a hidden type’s descriptor is supplied at the implicit packing site and is
  available to exact type-bound pattern tests. Parameter-position existentials do not need a heap
  holder.
- **Stored existentials:** covered separately by [ZEP-0106](./ZEP-0106.md), which adds a descriptor
  field to the holder.
- **Handler matching:** a handler case compares the payload descriptor with its statically known
  descriptor. Exact equality only.

Two copies of a library in one program yield equal descriptors for the same owner name and
arguments. Compatibility remains governed by the library index schema and API versioning; a
program that loads incompatible copies should fail at the library boundary rather than treating
descriptors as interchangeable.

### Exact type tests

Type-bound pattern matching in [ZEP-0104](./ZEP-0104.md) lowers to a descriptor comparison followed
by the existing cast and flow-refinement machinery. The first version supports exact equality only:

- closed concrete applied types;
- types composed from reified type variables;
- arrays;
- nullability and mutability exactly as represented.

Subtype, interface, ancestor, and contract-bound matching are out of scope. They are separate
proposals because they require different metadata: descendants or ancestors, and evidence
selection, respectively.

### Host boundary

A descriptor is never inferred from a host object. External mappings to generic effects or
existential positions must state concrete type arguments statically. Host failures enter the effect
system only through library-declared constructors of the non-generic top `Effect` (see
[ZEP-0013](./ZEP-0013.md)).

### Library index

The index records:

- the `reified` marker on exported callable type parameters;
- the type parameters of generic effect declarations;
- applied effect types in `raises`;
- hidden type parameters and bounds introduced by [ZEP-0104](./ZEP-0104.md) anonymous
existentials, using the existing type-parameter encoding and the reserved hidden-name prefix.

The initial ZEP-0104 slice fit in the existing schema 13 type-parameter records; it introduced no
additional type code. ZEP-0106 now raises the wire version to schema 14 and adds a stored-existential
binder code and flag for holder metadata; the ZEP-0015 descriptor encoding itself is unchanged.
Consumers on older compilers reject newer indexes by schema version.

## Compatibility and impact

Reification may add hidden runtime parameters, descriptor fields, generated support classes, or
other ABI changes. The library index must preserve the source-level type information needed to
generate and validate reified operations in consumers. The design must account for old and new
compiled libraries, exact dispatch correctness, and overhead in generic calls.

No existing source program changes meaning. Programs that do not use `reified`, generic effects, or
existentials keep their current representation.

## Alternatives

- **Effect-only descriptor** — smaller first step, but duplicates the same identity machinery when
  existentials land and couples the descriptor format to effect dispatch. Rejected after the
  2026-11-09 scope review.
- **Keep all generic identity static** — preserves the current ABI, but cannot support runtime
  decisions that distinguish erased applied types. Rejected for the target use cases.
- **Erased JVM classes alone** — simple, but conflates distinct applied generic types.
- **General reflection** — broader than needed and does not define sound identity propagation
  through generic code.
- **Combine identity and contract evidence in one runtime value** — makes effect dispatch carry
  unnecessary evidence and confuses type tests with capability tests. Rejected.

## Implementation and validation

1. Define the internal descriptor representation and its equality/hash contract.
2. Implement `reified` parsing, bounds validation, index encoding, and hidden-parameter lowering.
3. Generic effect construction, forwarding, and exact handler matching are specified by the
   accepted [ZEP-0005](./ZEP-0005.md); they are not part of this implementation.
4. Prototype exact type-bound matching for reified type variables and parameter-position
   existentials.
5. Test nested applications, arrays, nullability and mutability markers, separate compilation, and
   duplicate library copies.
6. Measure the matrix in the acceptance criteria.

## Acceptance criteria

**Completion scope (2026-11-10).** The original criteria bundled the descriptor facility with
generic-effect integration. The facility and its ZEP-0104 consumer are now validated; generic
effect construction, propagation, and handler dispatch are acceptance gates for the accepted
[ZEP-0005](./ZEP-0005.md), not evidence claimed by this implementation.

- Zero added overhead for non-generic effects and non-generic code.
- Non-generic effects add no descriptor field and no per-raise allocation.
- Monomorphic generic sites use cached descriptors and do not allocate per raise or type test.
- Descriptor forwarding through a `reified` parameter is O(1).
- Exact tests use interned constants when the target is monomorphic; a source or target that
  mentions a reified parameter composes a descriptor only when that parameter is present.
- Distinct applied types remain distinct through forwarding, existentials, and library boundaries.
  Applied-effect identity is validated with the accepted ZEP-0005.
- The applicable overhead rows for monomorphic lookup, generic pass-through, nested applications,
  type tests, and separately compiled libraries are recorded before the release gate closes.
  Handler and applied-effect rows belong to ZEP-0005.

## Prototype validation (2026-11-10)

The implementation is `zeron.runtime.AppliedTypeDescriptor`, with correctness tests in
`AppliedTypeDescriptorTest` and a process-level microbenchmark in
`AppliedTypeDescriptorBenchmark`.

- The descriptor models expanded owner, recursive arguments, nullability, mutability, array
  component, structural equality, and a hash cached at construction.
- Equal descriptors built independently compare equal and share a hash; nullability, mutability,
  and array shape remain distinct identity components.
- Constant descriptor equality, hashing, cached lookup, and forwarding allocate no descriptor per
  operation. The benchmark's construction rows measure the non-constant path separately.
- Measurements on 2026-11-10 (JDK 25, Windows, 10,000,000 measured iterations after warmup):
  flat constant equality 2.67 ns/op, nested constant equality 7.88 ns/op, cached hash 3.62 ns/op,
  reified forwarding 3.82 ns/op, cached nested lookup 3.57 ns/op. Equality, hashing, forwarding,
  and cached lookup measured 0.000 bytes/op; flat and nested descriptor construction measured
  56.000 bytes/op. These are process-level microbenchmark numbers, not a JMH-grade matrix.
- The compiler lowering, library-index encoding, function-value capture, transitive inference,
  exact tests, and separately compiled consumers are validated by `RuntimeReificationTest`,
  `ExistentialGenericsTest`, and `Zep0015AcceptanceTest`.

## Implementation status (2026-11-10)

The implementation ships the declaration ABI, the applied-type identity facility, and the
ZEP-0104 consumer:

- `T: reified` is parsed as an admissibility marker, rejected on class and contract type
  parameters, preserved through substitutions and the versioned API index, and included in
  function-signature ABI equality. The API-index schema version is 13.
- Hidden descriptor parameters follow existing evidence parameters. Monomorphic sites load
  interned constant descriptors; sites whose arguments mention caller type parameters compose a
  descriptor from hidden parameters at runtime. Nested applications, arrays, nullability, and
  mutability are represented.
- Exported declarations require the marker explicitly. Non-exported functions, methods, and
  lambdas infer it transitively, with selections recomputed after resolution so declaration order
  does not change the inferred ABI. Generic function values specialize and capture descriptors.
- Contract methods and implementations preserve the marker, generic bridges omit hidden
  parameters, and separately compiled clients read the marker from the library index.
- ZEP-0104 reified values and hidden anonymous existentials carry exact descriptors. Exact tests
  use descriptor equality when the source carries a reified parameter; closed erased sources keep
  the existing static/erased test path.
- `RuntimeReificationTest` covers top-level and method calls, constant and composed descriptors,
  function values, inferred private forwarding, separate compilation, and class rejection.
  `AppliedTypeDescriptorTest` covers structural identity and interned lookup.
  `ExistentialGenericsTest` covers exact tests, existential descriptors, array targets, and index
  round-tripping.
  `Zep0015AcceptanceTest` verifies that non-generic effect payloads carry no descriptor field or
  descriptor parameters.

## Resolved design questions (2026-11-09)

- **Shared scope:** one internal applied-type descriptor serves generic effects and exact
  type-bound tests; it is not effect-only.
- **Identity versus evidence:** descriptors never provide contract operations; bound witnesses stay
  separate.
- **Which distinctions have runtime identity:** owner, arguments, nullability, mutability markers,
  and arrays; aliases expanded; function types rejected.
- **How generic code obtains identity:** explicit `reified` marker with the policy above.
- **Representation:** immutable structural descriptor with a cached hash, carried by effect
  payloads and supplied as a hidden parameter where generic construction or matching requires it.
- **Matching strength:** exact structural identity only in the first version.
- **Ancestors, storage, and contract-bound tests:** separate proposals
  ([ZEP-0107](./ZEP-0107.md), [ZEP-0106](./ZEP-0106.md), [ZEP-0108](./ZEP-0108.md)).
- **Java interaction:** descriptors are never inferred from host values; mappings state concrete
  arguments.
- **Overhead:** the overhead matrix is a release gate, not an open design question; a design that
  cannot meet it is revised rather than accepted.
- **Library index:** add explicit reification flags to exported type parameters, reuse the applied
  type wire format for generic `raises` entries, and encode anonymous existentials as hidden
  ordinary type parameters with the reserved name prefix and bounds. The initial ZEP-0104 slice
  fit schema 13 without a distinct binder code. ZEP-0005 confirmed that applied-effect `raises`
  entries also fit schema 13 with no new record. ZEP-0106 raises the wire version to schema 14 and
  adds an inline stored-existential binder record with its markers, bounds, and holder metadata.
- **Equality and library copies:** equality is structural and excludes library name or version;
  index-schema version enforcement prevents silently mixing incompatible encodings.
- **Class type parameters:** they remain non-reified; instance storage and constructor ABI are
  separate work.
- **Inferred markers:** inferred `reified` markers are visible in compiler dumps and diagnostics,
  not written into source.

## Decision

Implemented 2026-11-10 for the shared applied-type descriptor facility and its ZEP-0104
reified/existential consumer. The descriptor ABI, static and composed construction, cached
monomorphic lookup, forwarding, exact tests, library-index round-trip, and separately compiled
consumers are validated. Non-generic effects remain descriptor-free and the applicable overhead
rows are recorded in the validation matrix.

Generic-effect construction and handler dispatch are specified and implemented in
[ZEP-0005](./ZEP-0005.md) under its closed-application scope; its construction and descriptor
dispatch rows are recorded below. Deferred generic propagation remains owned by that proposal, not
by this one. The
release state remains `Candidate` for 0.7.0 in the tracker.

modifier, not an admissibility marker. Descriptor semantics and runtime behavior are unchanged.
