## Abstract

This proposal explores a second standard-library phase covering a `zeron.math` module, a possible
`Char` primitive for string inspection and manipulation, and a `zeron.net` module for network
sockets and a synchronous HTTP client. It will settle scope, language/runtime dependencies,
portability, and observable semantics before implementation.

## Motivation

The current standard library provides `Int`, `Float`, and basic `String` operations, but has no
dedicated math module, character value type, or networking API. String operations include length,
search, and substring, while character-level operations and their Unicode semantics are not yet
exposed. Networked programs likewise lack standard socket and HTTP abstractions.

These capabilities are related as standard-library expansion, but have distinct design costs:
mathematical behavior must specify numeric edge cases; a primitive character type affects the
language and string representation boundary; networking introduces blocking resources, protocol,
and transport-security decisions.

## Goals

- Explore a discoverable `zeron.math` API for common operations over built-in numeric types.
- Decide whether a `Char` primitive is warranted and define how it interacts with `String`.
- Explore a `zeron.net` API for network sockets and a synchronous HTTP client.
- Reuse the phase 1 I/O, failure, and resource-lifetime conventions where appropriate.
- Keep platform and protocol behavior explicit and portable where practical.

## Non-goals

- A general-purpose arbitrary-precision numeric system unless separately justified.
- Asynchronous networking, cancellation, or a general event-loop framework in the initial scope.
- A general web framework or server-side HTTP stack unless explicitly added to scope.
- Raw operating-system system calls or an unrestricted platform-specific networking API.
- Making `Char` imply grapheme-cluster segmentation or locale-aware text processing without an
  explicit design decision.

## Proposal

### Mathematics

Explore `zeron.math` for commonly needed operations over the language's built-in numeric types.
Specify which operations are functions versus primitive operators, how integer overflow and
floating-point special values behave, and how domain errors and rounding are represented. Keep
numeric admissibility and generic operator witnesses distinct from the module's runtime functions.

### Characters and strings

Determine whether Zeron should introduce a primitive `Char` for inspecting and manipulating
strings. Define whether a `Char` represents a Unicode scalar value, a UTF-16 code unit, or another
unit, and establish consistent behavior for iteration, indexing, substring boundaries, conversion,
equality, and malformed surrogate data. Distinguish character iteration from grapheme-cluster
segmentation.

If accepted, specify the compiler, runtime, Java interop, and standard-library changes required for
the primitive, including compatibility with existing `String.length`, search, and substring
operations. Do not assume that the JVM's string indexing unit is the desired public language
character model.

### Networking

Explore a `zeron.net` module for network sockets and a synchronous HTTP client. Define socket
protocol and role scope, connection and timeout behavior, resource ownership, failure effects, and
how network streams compose with the phase 1 `Reader`/`Writer` and `Disposable` abstractions.

Specify the HTTP client's supported protocol versions, request/response and body model, redirect
behavior, connection lifetime, and transport security. Any TLS support must use certificate
validation by default; insecure bypasses must not be implicit. Do not expose raw system calls.

## Compatibility and impact

`zeron.math` and `zeron.net` add public standard-library APIs and must be represented in compiled
library metadata. A `Char` primitive may additionally affect source syntax, type descriptors,
compiler lowering, Java interop, and existing string behavior. Any change to the interpretation of
current string indices or lengths requires a deliberate compatibility decision.

Network APIs should follow the synchronous resource and failure conventions accepted in ZEP-0011.
The design must not imply thread safety or resource sharing guarantees that the implementation
does not provide.

## Alternatives

- Leave callers to Java interop and external libraries — avoids committing to standard semantics,
  but leaves common operations less discoverable and less portable.
- Add `String` character helpers without a `Char` primitive — may be sufficient if the language
  lacks a stable, useful character-value model.
- Provide HTTP without public sockets — a smaller high-level API, but may not cover applications
  that need lower-level network protocols.
- Provide sockets only — preserves a small core, but requires each consumer to build its own HTTP
  behavior and error handling.

## Implementation and validation

Decide each area independently before implementation; this proposal does not require all areas to
ship together. Inventory existing numeric intrinsics, string operations, Java interop support, and
phase 1 I/O/resource APIs.

Validate math boundary cases and special values, character behavior across representative Unicode
and surrogate inputs, and compatibility of existing string operations. Test sockets using local,
deterministic endpoints and exercise connection failure, timeout, and disposal. Test HTTP behavior
with controlled local servers, including status handling, headers, bodies, redirects, transport
security, and failure propagation. Add compiled-library API-index round trips for public types and
functions.

## Open questions

- Which `Int` and `Float` operations belong in `zeron.math`, and what overflow, rounding, and
  floating-point special-value semantics should they expose?
- Is `Char` necessary, and if so, does it represent Unicode scalar values or UTF-16 code units?
- How should malformed surrogate data, string iteration, indexing, and slicing behave?
- Which socket protocols and roles are in scope, and should `zeron.net` expose TCP, UDP, or both?
- Does the synchronous HTTP client require HTTPS in its initial form, and which protocol versions,
  redirects, timeouts, and body-streaming behavior are supported?
- How should socket and HTTP resources compose with phase 1 ownership, disposal, and I/O failures?
- Should the three areas be implemented and released independently?

## Decision

Superseded 2026-10-18. The proposal combined three areas with distinct language, portability, and
runtime consequences. Continue the exploration independently in
[ZEP-0024](./ZEP-0024.md) (math), [ZEP-0025](./ZEP-0025.md) (characters), and
[ZEP-0026](./ZEP-0026.md) (networking). No feature direction was accepted by this proposal.
