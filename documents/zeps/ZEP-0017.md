## Abstract

This proposal explores the ability to declare and create anonymous object literals without the need
of a prior class declaration. These objects can implement one or more contracts simultaneously,
statically resolving members and allowing strict contract composition.

## Motivation

In contract-oriented languages with no inheritance (and even in those who do), it is often
necessary to create lightweight, "single-use" objects - for example, to mock test dependencies,
return data structures built inside a function, or to adapt some data to a contract quickly -
without polluting the a namespace or package with new identifiers.

## Goals

- Establish a statically-typed, strict mechanism to instance anonymous objects that conform to a
  contract.
- Ensure these objects are indistinguishable from normally-constructed instances: a consumer
  should not care or know whether an `Iterator` is an instance of a concrete class or a nominal
  type declared somewhere.
- Provide a clean way to instance these objects that isn't subject to substantial boilerplate.

## Non-goals

- Automatically implementing the declared contract.
- Introducing a structural-typing mechanism to Zeron.

## Proposal

### Instantiation syntax

An anonymous object can be created through the keyword `object`, followed by a `+`-separated list
of all the implemented contracts, just like an ordinary class declaration. Lastly, a block,
providing the implementations for all abstract members.

```zeron
let logger = object : Logger {
    public log(message: String): Unit = 
        println("[LOG] " + message);
}
```

### Contract composition

An anonymous object can conform to multiple independent contracts by using the `+` operator, just
like for ordinary class declarations:

```zeron
contract Renderable {
    render(): Unit;
}

contract Serializable {
    serialize(): Array<Int>;
}

let widget = object : Renderable + Serializable {
    public render(): String =
        // implementation

    public serialize(): Array<Int> =
        // implementation
}
```

### Type inference

An anonymous object has an anonymous compile-time type inferred by the compiler.
Whether this type should be denotable or not by Zeron syntax remains to be decided.

## Compatibility and impact

Internal anonymous object fields must follow Zeron's mutability and visibility semantics.
No reopening: anonymous objects cannot be extended after creation - their shape is static.
Type compatibility: two anonymous objects with the same declared contract requirements are mutually
assignable.

## Alternatives

- Do nothing. This feature adds no expressive power, only developer convenience. As such, it's not
  currently critical.
- Go further. Implement structurally-typed object literals. Deciding whether they allow methods
  or only fields would be one of the main design considerations.

## Implementation and validation

Define the resolution process first, then move onto compilation strategies.
The resolver must reject any object that doesn't fully conform to the declared contracts,
including transitive requirements from `requires` clauses.
The resolver must ensure closure transparency: capture semantics must work exactly like
the already existing capture model.
Prioritize efficient bytecode emission and clean synthetic classes, with final and private markers
where possible, and optimizing constructors to lessen unnecessary heap load.
For rejections, the compiler must emit clear diagnostics that point to the specific problem.

## Open questions

- Should structural anonymous types be included into the feature?
- Decide type denotability and existentiality.
- Decide member collision disambiguation policy.
- Should allocation optimization be included into the first slice of this feature?

## References

Prior art:

- JVM ecosystem: Java's `new Interface() { ... }`, Scala's `new Base with Trait { ... }`, Kotlin's `object : Interface { ... }`, Groovy's `[member: { ... }] as Interface`
- Functional languages: OCaml's structural typing
- Modern references: TypeScript's object literal type inference, Rust's `dyn Trait { ... }`, C#'s `new { ... }`.
