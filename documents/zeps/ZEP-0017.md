## Abstract

This proposal adds anonymous object expressions that implement one or more explicitly named
contracts without a separately declared class. Each expression has a unique compiler-generated
nominal implementation; it does not introduce structural typing.

## Motivation

Small, single-use contract implementations are useful for test doubles, adapters, and local policy
objects. Requiring a named class for each such value adds declarations to the package namespace
even when the implementation is used only once. Anonymous implementations should provide this
convenience while preserving Zeron's nominal contract and static conformance model.

## Goals

- Allow an object expression to conform strictly to one or more explicitly listed contracts.
- Give each expression a unique compiler-generated nominal class implementing exactly those
  contracts.
- Apply existing capture, visibility, contract-composition, and dispatch rules.
- Support contract properties and private initialized fields for per-object state.
- Keep anonymous implementation types non-denotable in source and prevent structural
  compatibility between distinct object expressions.

## Non-goals

- Structural typing, structural assignability, or compatibility between unrelated object
  expressions that happen to implement the same contracts.
- Constructors, inheritance, or extension of an anonymous implementation.
- Allocation-elision or other performance guarantees.

## Proposal

### Instantiation syntax

An anonymous object expression uses `object` followed by a `+`-separated list of implemented
contracts and a body providing implementations for all required abstract members:

```zeron
let logger: Logger = object : Logger {
    public log(message: String): Unit = 
        println("[LOG] " + message);
}
```

Contract composition follows the same conformance and conflict rules as a named class:

```zeron
contract Renderable {
    render(): Unit;
}

contract Serializable {
    serialize(): Array<Int>;
}

let widget = object : Renderable + Serializable {
    public render(): Unit =
        // implementation

    public serialize(): Array<Int> =
        // implementation
}
```

Object bodies may also declare additional methods and properties. Auto-properties and private
fields require initializers; custom properties use the ordinary getter/setter syntax. For example:

```zeron
import zeron.collections.Step;

let iterator = object : Iterator<Int> {
    index: Int = 0;

    public mut next(): Step<Int> {
        let current = this.index;
        this.index = this.index + 1;
        return Step.Yield(current);
    }
}
```

Initializers are evaluated once, at object creation, in canonical constructor order. They may use
the enclosing scope's permitted immutable captures. Methods and property accessors may capture
immutable local bindings; capturing mutable local bindings is rejected using the existing capture
rules.

The compiler emits a unique synthetic nominal class for each object expression. Its type is opaque
and non-denotable in source; it is assignable to the contracts explicitly listed on that
expression, not to unrelated structural types. An expected contract type may provide the target
type for the expression. Without an expected type, the declared contract list must determine an
unambiguous static view under the existing type rules.

## Compatibility and impact

Captured values are stored in synthetic fields under the existing lambda-capture and mutability
rules. Properties implement matching contract requirements and retain their declared read/write
semantics. Two object expressions have distinct nominal identities even when they list the same
contracts. Generated classes and members are implementation details and are not exported as named
library API types.

Anonymous objects cannot satisfy a listed contract whose transitive `requires` closure contains
named constructor requirements. Contract constructors are static, class-side capabilities and
cannot be implemented by an instance object; such expressions receive a diagnostic at the object
expression. User-written constructors and patterns are not allowed in object bodies.

## Alternatives

- Declare a named class — retains the existing semantics and remains appropriate for reusable or
  exported implementations, but adds namespace-level declarations for local one-off objects.
- Add structural object literals — more general, but would change Zeron's nominal type model and is
  outside this proposal.

## Implementation and validation

Resolve and validate each listed contract using the same signature, applied-bound, transitive
`requires`, and default-conflict rules as named class conformance. Reject transitive named
constructor requirements explicitly. Reuse existing capture semantics for referenced local values;
reject mutable-local capture. Emit a unique synthetic JVM class implementing the listed contract
interfaces and lower property accessors and methods according to the existing class model.
Diagnose missing, duplicate, incompatible, or conflicting members at the object expression.
Allocation optimization is not an acceptance requirement.

Structural typing, source-denotable anonymous types, constructors, patterns, and allocation
optimization remain out of scope. The generated type is internal and is not part of the public
library index.

## References

Prior art:

- JVM ecosystem: Java's `new Interface() { ... }`, Scala's `new Base with Trait { ... }`, Kotlin's `object : Interface { ... }`, Groovy's `[member: { ... }] as Interface`
- Functional languages: OCaml's structural typing
- Modern references: TypeScript's object literal type inference, Rust's `dyn Trait { ... }`, C#'s `new { ... }`.

## Decision

Accepted 2026-10-18. Add anonymous object expressions with one or more explicitly listed contracts,
backed by unique compiler-generated nominal classes. Keep the generated type opaque and
non-denotable; do not add structural typing or assignability between distinct object expressions.
Support properties, private initialized fields, and permitted immutable captures. Reject
constructor-bearing contract closures.

## Implementation status

Implemented with unique synthetic nominal classes, explicit contract conformance, property and
method support, private initialized state, and permitted immutable captures. Runtime tests cover
multiple contracts, generic contracts, properties, and captured values; resolver tests reject
mutable captures and constructor-bearing contracts.
