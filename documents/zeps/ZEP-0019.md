# ZEP-0019: Higher-Kinded Abstractions and Declarative Contracts

## Abstract

This proposal explores whether Zeron's generic functions, applied contract bounds, witnesses, and
specialized extensions can express useful abstractions over type constructors, or whether the
language needs higher-kinded types (HKTs) or another type-family mechanism. It will compare
operation-specific contracts, associated type constructors, and explicit HKT support, and determine
whether these should complement or replace Zeron's current declarative tools.

## Motivation

Zeron can express operations for specific applied types, including extensions on specializations
such as `List<List<T>>`. Contract witnesses and applied bounds can also describe an operation's
input/output relation without naming a type constructor. For example, a contract parameterized by
`Out` could require `join(): Out`, with a witness for `List<List<T>>` whose result is `List<T>`.
Generic code could then abstract over a `Nested: Join<Out>` bound.

That approach does not directly express a family-wide abstraction such as `F<A> -> F<B>` for an
arbitrary constructor `F`. This limits contracts for operations like generic `map` and `flatMap`,
where the same constructor must be applied to different element types. It is not yet clear whether
such abstractions are important enough to justify higher-kinded machinery, whether current tools
should be extended, or whether HKT support should replace some of those tools.

In this proposal, “contract constructor requirements” means class-side factory requirements on
contracts. These are distinct from higher-kinded type constructors such as `F<_>`.

## Goals

- Identify which abstractions over applied generic types are expressible with current generic
  functions, contract bounds, witnesses, and extensions.
- Evaluate concrete use cases that need a type constructor to be applied at multiple type arguments.
- Compare operation-specific relation contracts, associated type constructors, and HKT parameters.
- Decide whether any new type-family mechanism should complement or replace current contracts,
  witnesses, generic bounds, and extensions.
- Document consequences for inference, witness selection, specialization, separate compilation, and
  the versioned library index.

## Non-goals

- Accepting HKTs or any other type-family mechanism as the design direction in this proposal.
- Replacing ordinary applied contracts, contract witnesses, or class-side factory requirements
  before their relationship to the proposed abstraction is understood.
- Adding variance, type lambdas, arbitrary kinds, or runtime generic type reification by implication.
- Implementing a particular collection abstraction or changing the standard library.

## Proposal

Compare at least the following approaches using representative operations such as `join`, `map`,
`flatMap`, and `pure`:

1. **Current declarative tools:** use specialized extensions, ordinary contracts indexed by relevant
   input/output types, applied bounds, and witnesses. Establish where this is sufficient and whether
   improvements to witness or extension declarations would close useful gaps.
2. **Associated type constructors:** let a contract define an associated family such as `Apply<T>`,
   with an implementation associating that family with `List<T>`. Evaluate whether projections,
   substitution, and generic method signatures provide the required abstraction without passing a
   constructor as a type argument.
3. **Higher-kinded parameters:** allow a type parameter of kind `* -> *`, written illustratively as
   `F<_>`, so a contract can state operations in terms of `F<A>` and `F<B>`. Evaluate a minimal
   first-order kind system separately from arbitrary kinds and type-level functions.

For each approach, determine how a generic declaration obtains its evidence, how implementations
are declared and selected, and whether ordinary static evidence passing remains suitable. Assess
both directly declared nominal conformance and witness-based implementations, including the
existing orphan and coherence rules. Specify how the design interacts with generic method bounds,
type inference, erased JVM descriptors, generated helpers, and separately compiled library
metadata.

The proposal should explicitly determine whether the current tools remain the foundation for
declaration, implementation, and dispatch when an abstraction over constructors is added. Do not
assume that HKTs require abandoning those tools: compare an additive design with a replacement
design, and state the compatibility and migration costs of either direction.

## Compatibility and impact

Operation-specific contracts using ordinary applied types may fit the existing source and evidence
models, subject to validation of the exact use cases. Associated type constructors or HKT
parameters would change type syntax and generic well-formedness, and may affect inference,
substitution, witness matching, compiler lowering, and API-index encoding. The proposal must
identify whether existing declarations can remain source- and binary-compatible and whether any
new metadata requires an index schema change.

HKT support need not imply runtime reification: compile-time constructor identity and contract
evidence are separate from runtime identity of applied generic types, as discussed in
[ZEP-0015](./ZEP-0015.md).

## Alternatives

- **Keep only the current tools** — avoids additional type-system complexity and may be sufficient
  for operation-specific relationships such as `join`; it does not provide a single abstraction
  over arbitrary `F<A>` and `F<B>`.
- **Add associated type constructors** — can express a type family through a contract implementation
  without passing `F` explicitly; projections and their interaction with generic inference and
  evidence still require design.
- **Add HKTs** — gives generic APIs a direct way to abstract over constructors and compose
  constructor-polymorphic operations; it adds kind checking, constructor-level implementation and
  witness rules, and metadata requirements.
- **Replace current declarative tools with HKTs** — may unify some generic abstractions, but risks
  losing or complicating useful concrete witnesses, static factories, and specialized extensions.
  The proposal must establish a concrete benefit before recommending replacement.

## Implementation and validation

First inventory current expression of representative operations using source-level examples and
small compile probes. Include both `List<List<T>>`-specific `join` and constructor-polymorphic
`map`/`flatMap`; distinguish a one-operation input/output relation from a reusable abstraction
over `F`.

For any candidate model, prototype syntax and type checking before committing to bytecode lowering.
Test generic inference and explicit arguments, witness selection and ambiguity, generic methods,
nominal and non-nominal implementations, separately compiled libraries, and metadata compatibility.
Compare the smallest useful kind system with associated type constructors and with the existing
applied-contract model. No implementation schedule is implied by this exploration.

## Open questions

- Which real or planned Zeron APIs require the same constructor to appear at multiple type
  arguments, rather than only a relationship between concrete input and output types?
- Can the `Join<Out>`-style contract-and-witness approach express the desired `join` API cleanly,
  including implementation ownership, visibility, and use-site evidence?
- Is the primary goal abstraction over a constructor supplied as a generic argument, or associating
  one constructor family with a contract implementation?
- If HKTs are added, should the initial system be limited to constructors of kind `* -> *`, or must
  it support other arities or constructor composition?
- How should constructor-level conformance and witnesses interact with current type-target
  witnesses, orphan rules, coherence, and static evidence passing?
- Can associated type constructors meet the motivating needs with less complexity, and what
  limitations would they impose compared with HKTs?
- Should a new mechanism be additive to existing contracts and extensions, or is there evidence
  that the existing tools should be deprecated or replaced?
- What source, JVM ABI, API-index, Java interop, and migration guarantees are required?
