# ZEP-0019: Higher-Kinded Abstractions and Declarative Contracts

## Abstract

This proposal develops a candidate first-order higher-kinded abstraction for operations that
preserve a type constructor while changing its element type. It specifies illustrative syntax,
grammar changes, kinding and dispatch semantics, and an erased-evidence compilation strategy, then
compares the candidate with operation-specific contracts and associated type constructors.

## Motivation

Current APIs demonstrate both the value and the limit of the existing tools:

- `Option.map` and `Result.map<U>` are generic methods on known concrete constructors.
- `Result.andThen<U>` preserves the error type while changing the success type.
- `Stream.map` and `Stream.flatMap` are concrete lazy operations; `Stream.flatMap` accepts an
  `Iterable` callback result.
- The `list_monad` sample implements `fmap`, `bind`, and `join` specifically for `List`, with
  `bind` expressed as `fmap` followed by `join`.

These are useful APIs, but they do not let one generic declaration express the same constructor
before and after a type change: `F<A> -> F<B>`. An applied relation such as `Join<Out>` can describe
one operation for a known source/output relationship; it does not identify a reusable constructor
family. `Result<T, E>` also shows why a useful first-order design must support a constructor with
one changing argument and another fixed argument, represented here as `Result<_, E>`.

Here, “contract constructor requirements” refers to existing class-side factory requirements.
Those are separate from HKT constructor parameters.

The existing constructor-requirement feature also creates friction with anonymous objects.
Anonymous objects implement instance behavior but have no source-level class name or named
constructor to satisfy or map to a class-side factory requirement. This is a sign that construction
and value-level behavior should be independently constrainable, rather than making every behavioral
contract require a factory.

An HKT constructor operation can generalize factories for actual type families such as `List<_>`,
but it does not make an anonymous object into a constructor family. The design therefore separates
family-level operations from instance behavior on `F<A>`. Ordinary behavioral contracts describe
what an existing value can do; HKT contracts describe statically dispatched operations over a
constructor family, with optional receiver syntax for operations on `F<A>`.
APIs that only need a value should accept that value. A factory for a non-generic target is passed
explicitly as a function or factory object rather than being inferred from a contract constructor
requirement. This avoids requiring anonymous objects to provide a class-side constructor.

## Goals

- Specify a first-order `F<_>` candidate for constructor-preserving `map`, `flatMap`, and `pure`.
- Preserve current contracts, witnesses, applied bounds, and extensions as the evidence and dispatch
  foundation rather than replacing them.
- Bound the initial kind system, including partial application needed by `Result<T, E>`.
- Describe kind checking, inference, witness selection, generic erasure, and library metadata
  consequences well enough to judge implementation cost.
- Compare this candidate with operation-specific relations and associated type constructors.

## Non-goals

- Arbitrary kinds, constructor composition, type lambdas, or constructor values at runtime.
- Constructors with more than one unfilled argument slot in the first iteration.
- Variance, subtyping, or runtime generic type reification.
- Implementing a particular collection abstraction or changing the standard library.

## Proposal

### Candidate surface syntax

An HKT contract parameter is declared with one kind slot. Its operations are statically dispatched
requirements over the constructor family. An operation may mark its first parameter with `this:`
to make it callable as `value.operation(...)`; the marker does not change static evidence dispatch.
The first parameter remains explicit in the contract signature and in calls such as
`F.operation(value, ...)`. Operations without a receiver marker, such as factories, are called
through the constructor bound, e.g. `F.pure(value)`.

```zeron
public contract Functor<F<_>> {
    map<A, B>(this: F<A>, transform: (A) -> B): F<B>;
}

public contract FlatMap<F<_>> {
    flatMap<A, B>(this: F<A>, transform: (A) -> F<B>): F<B>;
}

public contract Pure<F<_>> {
    pure<A>(value: A): F<A>;
}

public contract SinkFactory<F<_>> {
    empty<A>(): F<A>;
}

public contract Monad<F<_>> requires Functor<F> + FlatMap<F> + Pure<F> {}
```

The existing `Sink<T>` remains a value-level behavioral contract containing `mut add(value: T)`.
Its `empty()` contract constructor is removed. A generic family can expose construction through a
separate HKT capability such as `SinkFactory<F<_>>`; a function needing a factory for a non-generic
target receives `() -> C` (or a factory object) explicitly. HKT support does not make anonymous
object values into constructor families.

A generic function binds the constructor and its evidence through an applied contract bound:

```zeron
fn map<F<_>: Functor<F>, A, B>(
    source: F<A>,
    transform: (A) -> B
): F<B> = source.map(transform);

fn mapStatically<F<_>: Functor<F>, A, B>(
    source: F<A>,
    transform: (A) -> B
): F<B> = F.map(source, transform);

fn join<F<_>: FlatMap<F>, A>(source: F<F<A>>): F<A> =
    source.flatMap(inner -> inner);
```

The candidate witness syntax generalizes existing witness targets from fully applied types to
constructor patterns. A unary constructor uses one hole; a multi-parameter declaration may fix all
but one argument:

```zeron
witness Functor<List<_>> for List<_> {
    fn map<A, B>(this: List<A>, transform: (A) -> B): List<B> =
        this.fmap(transform);
}

witness<E> Functor<Result<_, E>> for Result<_, E> {
    fn map<A, B>(this: Result<A, E>, transform: (A) -> B): Result<B, E> =
        this.map(transform);
}

witness<E> FlatMap<Result<_, E>> for Result<_, E> {
    fn flatMap<A, B>(
        this: Result<A, E>,
        transform: (A) -> Result<B, E>
    ): Result<B, E> = this.andThen(transform);
}
```

`Result<_, E>` means “the `Result` constructor with its success slot open and error type fixed to
`E`.” It is a constructor pattern, not a value type. The `for` target must denote the same
constructor pattern as the constructor argument of the HKT contract. Constructor witnesses contain
static implementations; they do not have a runtime receiver. Existing nominal instance conformance
and ordinary witness methods keep their current meaning.

Generic classes may declare constructor-level conformance at the type declaration and provide its
static operations in a dedicated implementation block:

```zeron
public class Stream<T> is Iterable<T>,
        Functor<Stream<_>>, FlatMap<Stream<_>> {
    source: Iterable<T>;

    implementation Functor<Stream<_>> {
        fn map<A, B>(this: Stream<A>, transform: (A) -> B): Stream<B> =
            MappedStream.new(this, transform);
    }

    implementation FlatMap<Stream<_>> {
        fn flatMap<A, B>(
            this: Stream<A>,
            transform: (A) -> Stream<B>
        ): Stream<B> = FlatMappedStream.new(this, transform);
    }
}
```

The `is` entries above denote constructor-wide conformance, not that each `Stream<T>` instance
implements an ordinary runtime `Functor` interface. The implementation blocks are statically
dispatched bodies checked against the corresponding HKT contract requirements. Receiver-marked
operations take the receiver as their first explicit parameter; helpers are emitted in the class so
they may access private state. The class header makes this conformance available wherever the class
declaration is visible, without requiring a witness import. Ordinary
nominal methods keep precedence over HKT receiver operations. An implementation helper is emitted
inside its implementing class so it can use that class's private members; it is not a new ordinary
instance method. Existing witnesses remain the implementation path for non-nominal targets and for declarations, such as
current sum types, that do not declare nominal conformance.

### Candidate grammar and kinding

The grammar change is intentionally narrow:

```text
typeParameter        ::= IDENTIFIER [ "<" "_" ">" ] [ ":" contractType
                         { "+" contractType } ]
typeArgument         ::= type | "_"
typeArgumentsBody    ::= typeArgument { "," typeArgument }
hktContractMethod    ::= memberName [ typeParameters ]
                         "(" parameters ")" ":" type ";"
receiverParameter   ::= "this" ":" type
constructorWitness   ::= "witness" [ typeParameters ] contractUse
                         "for" constructorPattern "{"
                         { witnessMethod } "}"
constructorPattern  ::= qualifiedName "<" typeArgument
                         { "," typeArgument } ">"
constructorImplementation ::= "implementation" contractUse "{"
                               { witnessMethod } "}"
witnessMethod       ::= "fn" memberName [ typeParameters ]
                         "(" parameters ")" ":" type
                         ( "=" expression ";" | block )
```

Within an HKT contract method or its witness/implementation, `this:` is permitted only on the first
parameter. It marks that operation for receiver-call syntax; it does not create an implicit receiver
or change its static evidence signature. Non-HKT methods cannot use this marker.

`typeArgument` holes are accepted only when the surrounding context expects a constructor; `_` is
not a new ordinary type. A type parameter written `F<_>` has kind `* -> *`; `F<A>` is then a type
of kind `*`. A constructor pattern has kind `* -> *` only when exactly one slot is open and every
fixed slot is a well-kinded type. Thus `List<_>` and `Result<_, E>` are valid; `Pair<_, _>` is not
in the initial system. Applying `F` must supply exactly one type argument.

Kind checking applies at declarations, applications, bounds, witnesses, and inferred substitutions.
The same constructor and fixed arguments must be inferred consistently throughout a call. Calls
infer `F` from `F<A>` arguments and expected results where possible; underconstrained calls require
explicit type arguments, for example `map<List<_>, Int, String>(values, render)`. Constructor
identity includes its qualified declaration and the position and types of fixed arguments, so
`Result<_, String>` and `Result<_, IOException>` are distinct constructors.

### Semantics and evidence

- HKT contract methods are statically dispatched constructor-family operations; no `static`
  modifier is written. A first parameter marked `this: F<A>` additionally enables receiver-call
  syntax on values of type `F<A>`. The marker is syntactic call metadata: evidence dispatch remains
  static, and the receiver is still the first formal parameter. `F.operation(value, ...)` remains
  available. Operations without a receiver marker do not become instance-style calls. Mutating a
  container through an operation requires an explicit mutable reference parameter. Default
  class-side methods are deferred. A generic class
  may list an HKT conformance in its `is` clause and implement it in a matching class-body
  `implementation` block. This is distinct from ordinary instance conformance.
- HKT contracts compose through ordinary `requires` clauses. Generic functions require an explicit
  constructor bound such as `F<_>: Functor<F>`. Calling `F.map(source, f)` or `source.map(f)`
  selects that bound's evidence; neither form performs runtime lookup.
- Constructor witnesses use the existing orphan and coherence rules, generalized to constructor
  patterns. The active scope must contain exactly one applicable witness for a concrete
  constructor/contract pair. Missing or ambiguous evidence is a compile-time error. Generic
  callers forward evidence; concrete callers select it statically. A witness may be generic over
  fixed constructor arguments, as in `Result<_, E>`.
- A declaration-site HKT conformance is globally available with its class declaration. A
  constructor witness cannot also claim the same constructor/contract pair; duplicates are rejected
  rather than hidden by import scope. The implementation block is not an ordinary member scope and
  does not add same-named ordinary instance methods to the JVM class.
- `Functor.map` is expected to obey identity and composition; `Monad` additionally expects the
  usual `pure`/`flatMap` identity and associativity laws. These are documented contracts, not
  compiler-proven properties.
- Matching signatures do not promise matching operational behavior. `Stream` can remain lazy,
  `Result` can short-circuit, and `List` can enumerate eagerly. The HKT operations specify only
  their type and documented laws; concrete APIs may provide additional operations. In particular,
  the generic `FlatMap` callback returns `F<B>`, while the current `Stream.flatMap` accepts any
  `Iterable<B>`; the HKT instance can use the narrower `Stream<B>` form without removing the
  concrete API.
- `join` can be derived from `flatMap` with identity. Operation-specific `Join<Out>` contracts
  remain useful when only one input/output relationship is needed; HKT support is additive and
  does not replace them.

### Compilation strategy

The candidate keeps HKT identity at compile time and reuses static evidence passing:

1. Add kinded type-parameter and constructor-pattern descriptors. Resolution checks kinds,
   substitutes fixed and open arguments, infers constructor identity, and selects witnesses using
   the existing evidence scope and coherence rules.
2. Represent each required HKT operation as a hidden `MethodHandle` evidence parameter on generic
   function and method implementations. Receiver-marked operations retain their receiver as the
   first handle parameter; receiver syntax supplies it implicitly, while `F.operation(value, ...)`
   supplies it explicitly. Generic callers forward the handle. Direct callers resolve either the
   unique declaration-site conformance or, when none exists, the unique constructor witness and
   pass its handle. No dictionary object or runtime `Class` token is created.
3. Constructor witness bodies compile to static helpers. Declaration-site implementation helpers
   are emitted as synthetic static methods in the implementing class, allowing their bodies to use
   private class members while keeping HKT dispatch static. HKT applications such as `F<A>` erase
   to `Object` inside a generic implementation, as
   other type-variable-dependent types do. The helper's erased descriptor uses `Object` for
   constructor-applied values and the ordinary erased function-shape descriptor for callbacks. A
   helper casts to its known concrete constructor representation, performs or forwards the
   operation, and returns the erased result; callers apply the normal result casts. Applied types
   remain available to resolution but are not reified.
4. Extend the versioned library index to encode kinded parameters, constructor applications with
   holes, receiver markers on HKT requirements and witness methods, declaration-site constructor
   conformances, constructor witness patterns, and helper metadata. This is a binary schema change and requires advancing the
   API-index schema version. Existing source and runtime descriptors that do not use HKT syntax
   remain unchanged; old indexes are rejected by the existing schema-version check.

This is an implementation overview, not a commitment to this ABI. The erased helper descriptor
must be validated during implementation, especially for callbacks whose element types are primitive
or nested generic types.

## Compatibility and impact

The candidate is additive to applied contracts, witnesses, bounds, and extensions, but replaces
contract constructor requirements. Existing contract constructors must be migrated: generic
constructor-family operations become HKT static capabilities, while factories for kind-`*` targets
are passed as explicit function or factory-object values. The compiler must not silently preserve
constructor evidence as an alternate dispatch path. HKT declarations add new source forms and
compile-time descriptors; constructor witnesses add new API-index metadata and therefore require a
schema-version change. They do not require runtime generic type reification. A consumer must use a
compiler and library index that agree on the new schema, while non-HKT source and generated runtime
APIs retain their existing behavior.

HKT support need not imply runtime reification: compile-time constructor identity and contract
evidence are separate from runtime identity of applied generic types, as discussed in
[ZEP-0015](./ZEP-0015.md).

## Alternatives

- **Keep only the current tools** — avoids additional type-system complexity and remains sufficient
  for concrete methods and operation-specific relations such as `join`; it does not provide a
  reusable abstraction over arbitrary `F<A>` and `F<B>`.
- **Add associated type constructors** — can express a type family through a contract implementation
  without passing `F` explicitly; projections and their interaction with generic inference and
  evidence still require design.
- **Add HKTs** — gives generic APIs a direct way to abstract over constructors and compose
  constructor-polymorphic operations; it adds kind checking, constructor-level implementation and
  witness rules, and metadata requirements.
- **Replace all ordinary applied contracts and witnesses with HKTs** — would conflate operations
  on values with operations on constructor families and make anonymous-object behavior awkward. This
  proposal retains ordinary behavioral contracts and witnesses.

## Implementation and validation

Prototype the grammar and type descriptors before lowering. A minimal implementation probe should
cover `List<_>`, `Option<_>`, `Stream<_>`, and `Result<_, E>`, including the existing
`Result.map`/`andThen` shape. Test constructor inference and explicit arguments, fixed-argument
substitution, generic method calls, missing and overlapping constructor witnesses, witness imports,
orphan checks, erased signatures, callback shape casts, and separately compiled consumers. Compare
the implementation cost with the `Join<Out>` operation-specific approach and an associated-family
alternative. No implementation schedule is implied by this exploration.

## Open questions

None blocking acceptance of this design direction. The initial implementation is limited to
first-order constructors with one open slot, including fixed remaining arguments; both
`F.map(value, ...)` and receiver syntax `value.map(...)` are supported for receiver-marked
operations; declaration-site implementations use class-body `implementation` blocks; witnesses
remain available for non-nominal families but may not duplicate a declaration; and laws are
documented rather than compiler-verified. The Java ABI is not promised for HKT
evidence-bearing generic entry points; ordinary source declarations keep their existing descriptors.
The helper ABI and schema encoding must be validated during implementation.

## Decision

Accepted 2026-10-18. Adopt additive first-order HKT abstractions for statically dispatched
constructor-family operations, with one open type slot, fixed remaining arguments, and optional
receiver-marked operations permitted. Keep ordinary
behavioral contracts and witnesses, but remove contract constructor requirements: use HKT factory
capabilities for generic families and explicit factory values for kind-`*` targets. Support both
declaration-site implementation blocks and non-duplicating constructor witnesses. The design does
not replace ordinary contracts or require runtime type reification.
