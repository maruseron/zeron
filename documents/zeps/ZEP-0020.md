## Abstract

This proposal explores how Zeron can avoid recompiling unchanged source when building a project.
It will define the compilation units and dependency information that can be cached, the conditions
that invalidate cached results, and how incremental output remains equivalent to a clean build.

## Motivation

Project compilation currently processes a configured source set and emits generated classes and
library metadata. As projects grow, repeating all compiler phases after a small source change may
make command-line builds and future editor feedback unnecessarily slow. Reusing prior results is
only safe if the compiler detects every relevant source, dependency, configuration, compiler, and
library change; stale generated classes or API metadata must never be mistaken for current output.

## Goals

- Identify a useful initial incremental boundary, such as source units or dependency-connected
  groups, and compare it with finer-grained declaration caching.
- Define cache keys and dependency tracking for source text, compiler version, build configuration,
  classpaths, standard-library inputs, and relevant library metadata.
- Specify invalidation and removal behavior for changed, deleted, renamed, and newly discovered
  sources and generated artifacts.
- Preserve deterministic output and the observable correctness of clean builds.
- Decide whether caches are process-local, persistent in the project, or stored outside the output
  directory.

## Non-goals

- Changing source-language semantics, project dependency resolution, or the public library-index
  format solely to improve build speed.
- Distributed or remote build execution, content-addressed artifact sharing across machines, or
  general-purpose build scripting.
- Promising incremental semantic analysis at declaration granularity before its correctness and
  cost are understood.
- Making the compiler depend on generated files in `dist/` as its source of truth.

## Proposal

Compare a conservative source-unit cache with finer-grained approaches. For each candidate, identify
the inputs that determine parsing, resolution, compilation, and emitted artifacts. Dependencies
may include imported source declarations, generic witness metadata, generated function-shape
interfaces, standard-library sources or compiled APIs, Java classpaths, the entry source, and
project settings.

Define how changes to a public signature invalidate dependent units, while private implementation
changes may permit narrower recompilation where safe. Include cycles, mutually dependent source
units, top-level initializer dependencies, and compiler-generated helpers in the model. A cache hit
must not bypass diagnostics that depend on current project state.

Specify an atomic output strategy so interrupted builds cannot leave a mixture that appears valid.
Determine how stale outputs are removed after source deletion, package or source-path changes, and
renames. Distinguish incremental compilation from build caching: reuse within one project need not
imply portable or cross-project artifact reuse.

The proposal should compare incremental results with a clean build as the correctness oracle, and
state which artifacts must be byte-for-byte deterministic versus semantically equivalent.

## Compatibility and impact

The source and library artifact formats need not change if cache data remains internal. Persistent
cache keys must account for compiler and API-index compatibility so old results cannot silently
survive an incompatible compiler change. Build output layout, failure recovery, command-line
behavior, and the compiler service API may be affected. The design should preserve existing clean
build behavior and provide a way to force a clean rebuild.

## Alternatives

- **Always compile the complete source set** — simple and reliable, but scales poorly as the project
  grows.
- **Cache only parsing or scanning** — lower implementation risk, but may not materially reduce
  compile time when resolution and bytecode emission dominate.
- **Cache complete source-unit results** — a conservative starting point with clear invalidation
  boundaries, though changes to shared declarations can trigger broad recompilation.
- **Cache individual declarations or phases** — may reduce work further, but requires precise
  dependency tracking across resolver and compiler state and risks stale or inconsistent output.

## Implementation and validation

Measure representative project builds before choosing the cache boundary. Prototype cache keys and
dependency invalidation on projects with imported types, generic bounds and witnesses, top-level
initializers, generated function shapes, standard-library inputs, and Java classpaths.

For each change scenario, compare an incremental build against a clean build for diagnostics,
library-index contents, generated class behavior, and stale-file cleanup. Cover interrupted builds,
cache corruption, compiler-version changes, configuration changes, and explicit clean rebuilds.
No implementation schedule is implied.

## Open questions

- Is source-unit granularity sufficient for the expected project sizes, or is phase/declaration
  caching needed?
- Which dependency changes require invalidating consumers: any source change, public API changes,
  or a more precise semantic fingerprint?
- Should cache data be committed, ignored, or placed in a tool-managed user cache?
- How should concurrent builds, cancellation, and interrupted output publication be handled?
- What cache invalidation or inspection controls should the CLI expose?
- Can future editor analysis safely share caches with command-line compilation, or should those
  caches remain separate?
