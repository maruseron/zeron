## Abstract

This proposal adds persistent, project-local caching of per-source emitted classes. Every build still
scans, parses, resolves, and plans the complete current project; cached emission is reused only when
the source and conservative semantic fingerprints match. Complete output is staged and published
only after a successful build.

## Motivation

Project compilation currently processes a configured source set and emits generated classes and
library metadata. As projects grow, repeating all compiler phases after a small source change may
make command-line builds and future editor feedback unnecessarily slow. Reusing prior results is
only safe if the compiler detects every relevant source, dependency, configuration, compiler, and
library change; stale generated classes or API metadata must never be mistaken for current output.

## Goals

- Reuse per-source emitted classes while rerunning all current-project front-end and semantic
  phases.
- Key cached entries by source content, compilation configuration, compiler identity, classpath and
  library inputs, and the resolved project API/witness surface.
- Rebuild shared generated artifacts and library metadata from the current full-project analysis.
- Ensure changed, deleted, renamed, and newly discovered sources cannot leave stale output.
- Preserve clean-build output and failure behavior through staged publication.

## Non-goals

- Changing source-language semantics, project dependency resolution, or the public library-index
  format solely to improve build speed.
- Distributed or remote build execution, content-addressed artifact sharing across machines, or
  general-purpose build scripting.
- Incremental scanning, parsing, name resolution, type/effect resolution, or initialization
  planning.
- Declaration-level caching, cross-project or remote cache sharing, and LSP cache sharing.
- Making the compiler depend on generated files in `dist/` as its source of truth.

## Proposal

### Cache boundary

The cache operates after scanning, parsing, full-project resolution, validation, and initialization
planning succeed. These phases always run against the complete current source set and current
dependencies, so cache hits cannot suppress diagnostics or rely on stale semantic state. The cache
stores only the emitted class files owned by each source compilation unit. Shared generated support
classes, function-shape interfaces, initialization gateways/plans, and the library API index are
rebuilt from the current compilation context.

This is deliberately not incremental semantic analysis. It avoids repeated per-unit bytecode
emission, while retaining full semantic checking as the correctness boundary. Declaration/phase
reuse may be considered separately after measurements justify its dependency-tracking cost.

### Cache identity and invalidation

The persistent cache is project-local, ignored by version control, and stored separately from the
published output directory. A unit entry is reusable only when its source-content digest and the
following build identity match:

- compiler build/version, class-file target, API-index schema, and standard-library API version;
- normalized project and CLI configuration, entry/root selection, and output-affecting options;
- selected standard-library mode and the bundled standard-library source/API fingerprint;
- compiled-library API-index fingerprints and Java class-directory/JAR content fingerprints; and
- a canonical fingerprint of the complete resolved project public API, extension surface, contract
  witnesses, and other exported metadata relevant to generated call sites.

A source body change invalidates that source unit. Any change to the project-wide public
API/witness fingerprint conservatively invalidates all unit emission entries. A change to compiler,
configuration, library, standard-library, or Java-classpath identity also invalidates all affected
entries (the initial implementation may conservatively invalidate the whole cache). No timestamp
alone is sufficient to establish a hit. The current source-file set is recorded in the output
manifest so additions are compiled and deleted or renamed units are omitted from the staged output;
membership changes alone do not invalidate unrelated unit entries.

Cache entries are content-checked before use. A corrupt or incompatible entry is reported and
treated as a miss; it must never be partially trusted. A force-clean/no-cache CLI option bypasses
cached entries and performs fresh emission.

### Output publication and stale artifacts

Every build constructs a complete staged output tree from current cache hits, newly emitted unit
classes, and freshly generated shared artifacts. The compiler publishes that tree only after
compilation and packaging succeed; failed or interrupted builds leave the previous successful
output intact. Reconstructing the complete tree from the current source set removes artifacts for
deleted or renamed sources and packages without relying on ad hoc stale-file deletion.

Same-project writers are serialized with a process-safe project lock. Temporary staging and cache
records are not considered valid until their manifests and content digests are complete. A process
exit releases the lock; abandoned temporary entries are ignored and can be cleaned on a later
build.

The emitted artifact tree must be byte-for-byte equivalent to a clean build for the same inputs.
Cache presence must not affect diagnostics, generated behavior, API-index contents, or deterministic
class/interface bytes.

## Compatibility and impact

The source and library artifact formats do not change; cache records are internal and versioned
independently. Build output is staged, so publication and recovery behavior must preserve the last
successful output on failure. The feature applies to CLI and project builds only. LSP analysis keeps
its server-owned caches separate. A CLI bypass option provides a clean-emission path for diagnosis
and equivalence testing.

## Alternatives

- **Always compile the complete source set** — simple and reliable, but scales poorly as the project
  grows.
- **Cache only parsing or scanning** — excluded from this scope because parsing is not the target
  reuse boundary and current semantic phases still run in full.
- **Cache complete source-unit results including resolution** — may reduce more work, but requires
  serializing semantic state and tracking resolver dependencies; deferred.
- **Cache individual declarations or phases** — may reduce work further, but requires precise
  dependency tracking across resolver/compiler state and risks stale or inconsistent output.

## Implementation and validation

Measure representative clean builds and warm-cache builds; report where emission reuse saves time
and avoid claiming gains in semantic analysis. Compare incremental output byte-for-byte with a clean
build across source-body changes, public API and witness changes, additions, deletion/rename,
top-level initializers, generated function shapes, library and Java-classpath changes, and project
configuration changes. Confirm diagnostics are identical. Test corrupt entries, compiler-version
changes, force-clean builds, interrupted staging, publication failures, and concurrent same-project
builds. LSP cache sharing is explicitly outside this validation scope.

## Open questions

None blocking acceptance of the initial scope. Measurements may show that per-source emission
reuse is not valuable enough; in that case the implementation should be deferred rather than
silently expanding into incremental semantic analysis.

## Decision

Accepted 2026-10-18. The first implementation scope caches per-source emitted classes after complete
current-project semantic analysis, stores entries in a persistent ignored project-local cache,
invalidates conservatively using source and global API/dependency fingerprints, rebuilds shared
artifacts, and publishes a staged complete output tree only on success. CLI/project builds only;
LSP sharing and incremental semantic analysis are out of scope.

Deferred 2026-10-19 after reviewing build measurements: current performance does not establish a
compelling need for the implementation cost and cache-maintenance risk. Keep this proposal as a
design record, but do not target a release until future project-scale measurements show that
per-source emission is a material build-time cost.
