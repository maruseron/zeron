# ZEP-0022: Relaxing Visibility Requirements for Methods and Properties

## Abstract

This proposal allows omitted visibility modifiers on class and effect methods and properties,
defaulting them to private while keeping public API exposure explicit.

## Motivation

Class and effect methods and properties currently require an explicit `public` or `private`
modifier. This makes the access decision visible at each declaration, but can add repetitive syntax,
especially when many members share the same visibility. Relaxing the rule could make declarations
more concise, but an implicit default might expose implementation details or hide members in ways
that are easy to miss.

The design must also keep member visibility consistent across source analysis, contract
implementations, library metadata, and future member-discovery and editor tooling.

## Goals

- Reduce repetitive `private` annotations without making public API exposure implicit.
- Apply one visibility rule consistently to methods and properties, including accessors.
- Preserve current visibility behavior for other declaration categories.

## Non-goals

- Changing package-level visibility, import rules, or the meaning of existing `public` and `private`
  modifiers.
- Redesigning constructor visibility, contract requirement visibility, extension visibility, or
  top-level visibility unless a consistent proposal requires considering them explicitly.
- Adding protected, internal, friend, or module-level access.
- Changing runtime dispatch or granting extensions access to private members.

## Proposal

Allow visibility to be omitted from class and effect methods and properties; omission means
`private`. A public member must continue to be marked `public` explicitly. Apply one visibility to
a property and its accessors. Do not add visibility sections or alter visibility syntax for
constructors, contract members, extension methods, top-level declarations, or other declarations.
Contract implementations that satisfy a public contract requirement must remain publicly
accessible under existing conformance rules; omission does not make a private member satisfy a
public requirement.

## Compatibility and impact

Existing declarations with explicit modifiers should retain their current meaning. Allowing omitted
modifiers is additive syntax, but the chosen default affects the accessibility of newly written
members and may change generated API metadata. Visibility groups would add grammar and parser
state. Any option must preserve package boundaries, private-member checks, and the ability to
distinguish exported members from implementation details in compiled libraries and discovery
results.

## Alternatives

- **Default omitted visibility to public** — reduces annotations for library-facing types, but risks
  unintentionally exporting members.
- **Use visibility sections** — reduces repeated modifiers while keeping intent visible at a group
  boundary, but introduces scope and override rules.
- **Keep explicit modifiers on every member** — maximizes local clarity but requires repetitive
  `private` annotations.

## Implementation and validation

Inventory current grammar and visibility checks for class/effect methods and properties, then
prototype candidate syntax against mixed-access declarations, property accessors, contract
implementations, extensions, and compiled-library consumers. Verify that source and library
discovery expose exactly the same members under each candidate rule and that private access remains
rejected across packages and from extensions.

## Open questions

None for the accepted scope. Public visibility remains explicit; contract, extension, constructor,
and top-level visibility rules are unchanged.

## Decision

Accepted 2026-10-18. Omitted visibility means private for class and effect methods and properties.
Public members remain explicitly marked `public`; properties have one visibility for the property
and its accessors. Do not add visibility sections or alter other declaration categories.

## Implementation status

Implemented in the parser and resolver. The authoritative grammar and class/contract design
documentation reflect the optional modifier and private default. Resolver tests cover omitted
visibility and continued rejection of inaccessible members; existing explicit modifiers retain
their behavior.
