## Abstract

This proposal explores whether Zeron should remove required semicolon (`;`) terminators from
statements and declarations. It will compare newline-sensitive termination, automatic terminator
insertion, and other delimiter rules, while accounting for the grammar's current use of semicolons.

## Motivation

Zeron currently uses semicolons to terminate many declarations and statements, including
expressions, bindings, package and import declarations, and type declarations. Removing required
semicolons could make common code less punctuated, but source newlines currently are not a general
statement-termination rule in the grammar. A replacement must distinguish a completed expression
from a continued or multiline one without making parsing surprising or diagnostics fragile.

The change also needs to decide whether semicolons disappear entirely or remain accepted as
optional separators for compatibility and for code that places multiple declarations on one line.

## Goals

- Inventory all grammar positions where `;` is currently required and decide which are terminators
  versus separators.
- Compare newline-sensitive statement termination, automatic semicolon insertion, and explicit
  delimiter-based alternatives.
- Define behavior for multiline expressions, comments, chained calls, operators at line boundaries,
  blocks, and multiple statements on one line.
- Preserve predictable parsing, useful diagnostics, and formatter behavior.

## Non-goals

- Changing expression precedence, block structure, or declaration semantics for reasons unrelated to
  statement termination.
- Removing commas, braces, or other delimiters.
- Requiring one formatting style or introducing a formatter as a prerequisite.
- Accepting ambiguous source by guessing intent without a defined parsing rule.

## Proposal

Compare candidate rules using representative code:

```zeron
let answer = compute(
    first,
    second
)
print(answer)
```

and cases where a line break may either continue or terminate an expression:

```zeron
let value = receiver
    .transform()
```

Evaluate at least:

1. **Newline-sensitive termination:** line breaks separate declarations and statements except
   where the grammar explicitly continues an expression.
2. **Automatic semicolon insertion:** the parser or scanner inserts virtual terminators according
   to a specified token/context rule, similar to explicit semicolons but allowing them to be omitted.
3. **Optional semicolons with structural boundaries:** permit omission only where braces, declaration
   forms, or other unambiguous grammar boundaries determine the end.

For each option, define whether explicit semicolons remain legal, whether multiple statements on one
line are supported, and how comments and blank lines affect termination. Account for package and
import declarations, top-level declarations, contract requirements, fields, properties and
accessors, expression statements, control-flow statements, and `for` headers. The proposal should
state how the scanner represents line breaks if they become syntactically relevant and how parser
recovery identifies the next declaration after an error.

## Compatibility and impact

Allowing omission while continuing to accept existing semicolons could be source-compatible, but
newline-sensitive rules can change how existing multiline expressions are parsed if line breaks
gain meaning. Removing semicolon acceptance would be a source-breaking change. The grammar,
scanner/parser, syntax diagnostics, formatter or code-generation tools, and examples would be
affected. Compiled artifacts and the library-index schema need not change unless source provenance
or tooling contracts change.

## Alternatives

- **Keep required semicolons** — retains a simple explicit grammar and unambiguous statement
  boundaries, at the cost of punctuation in source.
- **Make semicolons optional at safe boundaries only** — limits ambiguity, but may produce
  inconsistent rules and leave common forms requiring terminators.
- **Use newline-sensitive termination** — familiar and visually concise, but requires precise
  continuation and multiline rules.
- **Use automatic semicolon insertion** — can preserve a semicolon-oriented grammar internally,
  but insertion rules can create surprising edge cases unless specified narrowly.

## Implementation and validation

Inventory semicolon use in the authoritative grammar and parser before choosing a rule. Build
positive and negative examples for every affected grammar position, especially multiline calls,
operators and member access at line boundaries, comments, adjacent declarations, and same-line
statements. Validate parser recovery and diagnostics, and compare any formatter output with the
chosen canonical style. Keep the old syntax covered if explicit semicolons remain accepted.

## Open questions

- Should newlines terminate statements, or should semicolons simply become optional?
- Which token patterns continue an expression across a line break?
- Should explicit semicolons remain accepted indefinitely?
- Are multiple statements on one line a supported language feature?
- Do package and import declarations need terminators if ordinary statements do not?
- How should comments, blank lines, and parser error recovery interact with virtual terminators?
- Is the goal to remove semicolons from all grammar positions or only executable statements?

## Decision

Rejected 2026-10-18. Keep required semicolon terminators in the current language. The proposal
would make line breaks syntactically significant across declarations and statements, requiring
substantial continuation, comment, and parser-recovery rules without a demonstrated need that
outweighs the existing explicit and predictable boundaries. Revisit only with concrete usability
evidence and a tested grammar alternative.
