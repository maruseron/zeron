## Abstract

This proposal explores a discoverable `zeron.math` module for common operations over Zeron's
built-in numeric types, with explicit behavior for overflow, rounding, floating-point special
values, and domain errors.

## Motivation

Zeron provides `Int` and `Float` plus basic operators, but does not yet define a dedicated math
library. A standard module can provide common functions without requiring applications to rely on
host-specific Java APIs. The public contract must specify numeric edge cases rather than merely
wrapping platform functions.

## Goals

- Identify a small, useful set of mathematical functions for `Int` and `Float`.
- Define overflow, rounding, precision, special-value, and domain-error behavior.
- Keep runtime math functions distinct from generic numeric admissibility and operator constraints.

## Non-goals

- Arbitrary-precision arithmetic, complex numbers, units, or generic numeric operators.
- A `Char` primitive or networking API; these are explored separately.
- Promising cross-platform bit-for-bit floating-point results unless explicitly specified.

## Proposal

Inventory common operations and group them into a `zeron.math` API only when their semantics can
be stated precisely. Determine which operations are functions and which remain built-in operators.
Specify integer overflow behavior, floating-point rounding and special values, and how invalid
domains or non-finite results are represented. Do not introduce a closed-set `Numeric` constraint
or operation-bearing numeric contracts as an incidental part of this library proposal; those
questions remain in ZEP-0010.

## Compatibility and impact

This adds standard-library functions and compiled-library metadata. It should not change existing
operator semantics or generic well-formedness. Platform-backed implementations must preserve the
documented source-level behavior.

## Alternatives

- Use Java interop or external libraries — avoids standardizing an API, but reduces portability and
  discoverability.
- Add only a minimal set of built-ins — may be smaller, but risks scattering mathematical
  operations across the language rather than a coherent module.
- Defer a dedicated module — avoids premature semantics until concrete application needs arise.

## Implementation and validation

Compare candidate APIs against representative application needs. Test boundary integers,
overflow, rounding, infinities, NaN, signed zero, and invalid domains. Verify compiled-library
metadata and behavior on each supported JVM platform.

## Open questions

- Which operations are sufficiently common to include in the first module?
- Which results require exact cross-platform semantics, and which may follow JVM floating-point
  behavior?
- Should domain failures be returned as values, raised as typed effects, or follow IEEE-754 results?
- Which integer operations should detect overflow rather than use existing wraparound semantics?
