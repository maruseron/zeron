## Abstract

This proposal explores whether Zeron should add a primitive `Char` value and how it would interact
with strings, Unicode, indexing, iteration, conversion, and Java interop.

## Motivation

String operations can search, measure, and slice text, but Zeron has no character value type. A
character API needs a clear semantic unit: Unicode scalar values, UTF-16 code units, or another
representation. That decision affects observable indexing and iteration behavior and cannot be
made solely by adopting the JVM's internal string representation.

## Goals

- Decide whether a primitive `Char` is useful in the language.
- Define its value domain and conversion to and from `String`.
- Establish consistent string iteration, indexing, slicing, equality, and malformed-surrogate
  behavior if `Char` is adopted.
- Specify compiler, runtime, library-index, and Java interop impact.

## Non-goals

- Grapheme-cluster segmentation, locale-aware text operations, or full Unicode normalization.
- Changing existing string indexing or length semantics without an explicit compatibility decision.
- Math or networking APIs; these are separate proposals.

## Proposal

Compare a Unicode scalar-value `Char` with a UTF-16 code-unit `Char` and with retaining `String`
operations without a primitive character. Define whether lone surrogates can exist as characters,
how malformed input is handled, and how iteration and slicing relate to the chosen unit. State
whether existing `String.length`, search, and substring operations keep their current semantics or
change under a migration plan.

## Compatibility and impact

A primitive affects source syntax, type descriptors, compiler lowering, standard-library APIs,
compiled-library metadata, and Java interop. Changing existing string index or length behavior may
break source expectations even if JVM representation is unchanged. The design must document these
effects before implementation.

## Alternatives

- Keep strings as the only text value and provide carefully named scalar/code-unit operations —
  avoids a new primitive but may make character-oriented APIs awkward.
- Use UTF-16 code units — maps naturally to JVM indexing but exposes surrogate halves as characters.
- Use Unicode scalar values — models Unicode characters more naturally but requires explicit
  behavior for malformed surrogate data and differs from JVM indexing.

## Implementation and validation

Prototype candidate semantics against supplementary-plane characters, combining marks, lone
surrogates, conversion boundaries, Java strings, and existing substring/index operations. Verify
that compiler descriptors and library metadata preserve the chosen source-level identity.

## Open questions

- Is a primitive `Char` needed, or are string operations sufficient?
- Does `Char` represent a Unicode scalar value or a UTF-16 code unit?
- How should malformed surrogate data and conversion failures behave?
- Should indexing and length count code units, scalar values, or another unit?
- What compatibility path applies if current string operations adopt different semantics?
