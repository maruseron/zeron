# ZEP-0025: Character Type and String Interoperation

## Abstract

This proposal adds a primitive `Char` representing one Unicode scalar value and specifies its
interaction with strings, indexing, iteration, conversion, and Java interop. Existing String
operations retain their UTF-16 code-unit semantics; new scalar-aware operations use explicit names.

## Motivation

String operations can search, measure, and slice text, but Zeron has no character value type. A
scalar-value `Char` makes character-oriented APIs and Unicode scalar processing possible without
changing the behavior of existing JVM-backed String operations. It intentionally does not represent
grapheme clusters, which may contain multiple scalar values.

## Goals

- Define a primitive `Char` as exactly one Unicode scalar value.
- Preserve established UTF-16 String APIs and add explicitly named scalar-aware operations.
- Specify conversion, scalar indexing, iteration, and malformed-surrogate behavior.
- Specify compiler, runtime, library-index, and Java interop impact.

## Non-goals

- Grapheme-cluster segmentation, locale-aware text operations, or full Unicode normalization.
- Changing existing string indexing or length semantics without an explicit compatibility decision.
- Math or networking APIs; these are separate proposals.

## Proposal

### Character values and literals

`Char` is a primitive whose values are Unicode scalar values: integers from U+0000 through U+10FFFF,
excluding U+D800 through U+DFFF. It is not a UTF-16 code unit and cannot contain a lone surrogate.
A character literal contains exactly one scalar value. The candidate syntax is a single-quoted
literal with the standard single-character escapes and a braced scalar escape:

```text
characterLiteral ::= "'" ( unicodeScalar | characterEscape ) "'"
characterEscape  ::= "\\" | "\'" | "\n" | "\r" | "\t"
                   | "\u{" hexDigit { hexDigit } "}"
```

The scanner rejects literals containing zero or multiple scalar values, malformed escapes,
surrogate values, or values above U+10FFFF. The final escape set should follow the existing String
escape conventions rather than create an unrelated one.

### String API and units

Existing `String.length`, `indexOf`, `lastIndexOf`, and `substring(start, end)` keep their current
UTF-16 code-unit semantics and signatures. This preserves compatibility and remains useful for
Java interoperation and low-level text processing.

Add an explicitly scalar-oriented API under `zeron.lang.String`:

- `codePointLength(): Int` counts Unicode scalar positions. A lone surrogate in the backing Java
  String counts as one malformed position.
- `codePointAt(index: Int): Option<Char>` uses a zero-based scalar index and returns `None` when
  out of range.
- `substringByCodePoints(start: Int, end: Int): Option<String>` uses a half-open scalar-index range;
  invalid bounds return `None`, matching the checked shape of the existing substring API.
- `indexOfCodePoint(value: Char): Int` searches by scalar value and returns a zero-based scalar
  index, or `-1` if absent.
- `codePoints(): Stream<Char>` iterates scalar positions in order.
- Strict variants return `Result<..., UnicodeError>` rather than replacing malformed UTF-16.
  `UnicodeError` identifies the UTF-16 code-unit offset of the first malformed surrogate sequence.
  Strict `codePoints` validates the complete String before returning its stream, so iteration cannot
  discover a deferred decoding error.
- `Char.toString(): String` encodes the scalar as a one-scalar String. `Char.toInt(): Int` returns
  its scalar value; `Int.toChar(): Option<Char>` succeeds only for a valid scalar.
- `String.singleChar(): Option<Char>` succeeds only when the string contains exactly one scalar
  position; empty and multi-scalar strings return `None`.

Scalar-aware traversal, indexing, slicing, and `singleChar` conversion replace every lone surrogate
encountered in a Java String with U+FFFD. They continue processing after the malformed code unit.
Scalar slicing therefore returns well-formed scalar text for malformed input. This policy allows
Zeron to interoperate with arbitrary Java Strings while ensuring every produced `Char` remains a
Unicode scalar. Existing UTF-16 APIs preserve lone surrogates as ordinary code units.

This initial API does not promise grapheme-cluster segmentation, normalization, locale-aware
operations, Unicode category predicates, or a Char range/ordering API.

## Compatibility and impact

`Char` uses an integer JVM representation (`int`) so every scalar value is representable; it does not
use Java `char`, which is a UTF-16 code unit and cannot represent supplementary scalars. Java
`char` parameters and results therefore require explicit conversion through UTF-16-aware APIs;
there is no implicit `char`/`Char` interop conversion. `Char` must be added to type descriptors,
literal scanning, constant handling, compiler lowering, formatting, and library-index type encoding.
The API-index schema and standard-library API version must be reviewed and advanced as required.

The existing String ABI and semantics do not change. New methods are standard-library extensions,
backed by Java String code-point operations or small curated helpers, and are exported through the
normal compiled-library index.

## Alternatives

- Keep strings as the only text value and provide carefully named scalar/code-unit operations —
  avoids a new primitive but makes character-oriented APIs awkward and does not give APIs a precise
  scalar parameter type.
- Use UTF-16 code units — maps naturally to JVM indexing but exposes surrogate halves as characters.
- Change existing String operations to scalar indices — presents one text model, but silently
  changes established index meanings and Java interoperation expectations.

## Implementation and validation

Implement scanner tests for literals and escapes, including supplementary scalars and rejected
surrogates. Test scalar APIs with BMP and supplementary characters, combining sequences, empty and
multi-scalar strings, lone high and low surrogates, range boundaries, and Java-created Strings.
Confirm that existing UTF-16 String tests remain unchanged. Verify the integer JVM descriptor,
checked Int conversions, overload rejection for Java `char`, API-index round trips, and separately
compiled consumers.

## Future considerations

- Should explicit Java `char`/UTF-16 code-unit conversion helpers be considered in a later release?

## Implementation

Strict methods use the suffix `Strict`: `codePointLengthStrict`, `codePointAtStrict`,
`substringByCodePointsStrict`, `indexOfCodePointStrict`, `codePointsStrict`, and
`singleCharStrict`. Each returns `Result<value, UnicodeError>`, where
`UnicodeError.MalformedSurrogate(utf16Offset)` reports the first malformed UTF-16 code-unit offset.
The API-index schema and standard-library API versions are both version 5. `Char` uses JVM `int`;
Java `char` interoperation remains unsupported.

## Decision

Accepted 2026-10-18; implemented 2026-10-19. `Char` is a Unicode scalar value; character literals use
single quotes, standard escapes, and braced `\\u{...}` escapes; existing String operations retain
UTF-16 code-unit semantics; scalar-aware operations replace lone surrogates with U+FFFD and also
offer strict variants; String-to-Char conversion returns `Option<Char>` and succeeds only for
exactly one scalar position; the API includes scalar length, access, iteration, slicing, search, and
conversions; `indexOfCodePoint` returns a scalar index; Java `char` interop remains unsupported.
