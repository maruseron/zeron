## Abstract

This proposal explores a portable `zeron.net` API for network sockets and/or a synchronous HTTP
client, including resource ownership, timeouts, failures, protocol behavior, and transport security.

## Motivation

Applications may need networking without depending directly on Java-specific APIs or third-party
libraries. A standard API could compose with Zeron's synchronous I/O and resource model, but sockets
and HTTP have distinct portability, security, and compatibility requirements.

## Goals

- Establish concrete use cases for low-level sockets, high-level HTTP, or both.
- Define protocol, resource lifetime, timeout, and failure semantics.
- Reuse the synchronous I/O and disposal conventions in ZEP-0011 where appropriate.
- Make TLS certificate validation the secure default if HTTPS is included.
- Define portable behavior and explicitly identify platform-dependent limits.

## Non-goals

- Asynchronous networking, cancellation, event loops, or a general web server framework.
- Raw operating-system calls or implicit insecure transport.
- Math or character APIs; these are separate proposals.

## Proposal

Determine independently whether the initial API should include TCP sockets, UDP datagrams, an HTTP
client, or a smaller subset. For sockets, define roles, connection behavior, timeouts, ownership,
and how byte readers/writers compose with ZEP-0011. For HTTP, specify supported protocol versions,
request/response and body streaming, redirects, connection lifetime, timeout policy, and failure
effects.

HTTPS must validate certificates by default; any insecure override must be explicit, narrowly
scoped, and conspicuous. Do not commit to exposing low-level transport primitives unless a concrete
use case requires them.

## Compatibility and impact

Networking adds public standard-library APIs and compiled-library metadata. Behavior depends on
host networking and may vary across operating systems. Resource and effect signatures must remain
clear at source level while Java-backed implementations remain behind the existing external-facade
boundary.

## Alternatives

- Use Java interop or external networking libraries — avoids standardizing network semantics but
  reduces portability and discoverability.
- Provide only HTTP — smaller and application-oriented, but does not support non-HTTP protocols.
- Provide only sockets — lower-level and flexible, but requires consumers to define protocol logic.
- Defer networking — avoids security and portability commitments until concrete needs arise.

## Implementation and validation

Use deterministic local test servers and clients. Validate connection failures, timeouts, disposal,
partial I/O, HTTP status and headers, body streaming, redirects, TLS certificate validation, and
failure propagation. Test on supported operating systems and verify compiled-library metadata.

## Open questions

- Which use cases require sockets versus an HTTP client?
- Should the first scope include TCP, UDP, both, or neither?
- Which HTTP versions, redirect behavior, timeouts, and streaming guarantees are required?
- Which typed effects represent DNS, connection, protocol, and TLS failures?
- How should pooled connections and cancellation be treated if excluded from the initial scope?
