## Abstract

This proposal defines the initial direction for a portable `zeron.net` synchronous HTTP client.
The initial scope excludes raw sockets and servers, and specifies streaming responses, bounded
timeouts, explicit redirect handling, and secure TLS defaults.

## Motivation

Applications need a portable way to make HTTP requests without depending directly on Java-specific
APIs or third-party libraries. A synchronous client can build on Zeron's byte I/O, typed effects,
and disposable-resource model. Beginning with HTTP provides a concrete application-facing API
without committing the standard library to low-level transport abstractions before there is a
demonstrated need.

## Goals

- Provide a synchronous HTTP client with portable request and response semantics.
- Stream response bodies through the existing byte-reader and disposal contracts.
- Define protocol, redirect, timeout, failure, and resource-lifetime behavior.
- Validate TLS certificates by default and avoid insecure transport fallbacks.
- Keep platform-specific transport details behind the standard-library API.

## Non-goals

- Raw TCP/UDP sockets, listening servers, and general web-server frameworks.
- Asynchronous networking, cancellation, and event loops.
- Streaming request bodies in the initial API.
- Automatic retries, cookie persistence, caching, proxy configuration, or custom trust stores in
  the initial API.
- Math or character APIs; these are separate proposals.

## Proposal

The first API is a synchronous HTTP client. It accepts an HTTP request with a method, URI, headers,
and an optional buffered `ByteArray` body, then returns a response containing the status code,
headers, and a streaming byte body. Request bodies are buffered in this initial scope; a future
proposal or revision may add streaming uploads if a concrete use case requires them.

The response body follows the existing `Reader` and `Disposable` conventions. The response is
disposable and owns its body stream, so disposing the response closes the body and releases
associated resources. Reading the body can raise `IoFailure`, consistent with other byte readers.
An HTTP status, including 3xx, 4xx, or 5xx, is a normal response value and is not itself an effect.

The client sends requests synchronously. It supports HTTP/1.1 and may negotiate HTTP/2 when the
peer and transport support it; the response exposes the protocol version actually used. HTTP/3 is
outside the initial scope. The implementation manages connection reuse within a client instance;
clients are reusable and disposable, and disposing a client releases its owned resources.

Redirects are not followed automatically. A 3xx response, including its `Location` header, is
returned to the caller, who can decide whether and how to issue another request. This avoids
implicit cross-origin credential forwarding and protocol downgrades.

HTTPS uses the platform's normal certificate and hostname validation. The initial API has no
certificate-validation bypass, custom trust store, or implicit HTTPS-to-HTTP fallback. Plain HTTP
may be used when explicitly requested by the URI.

Transport failures are represented by a typed `HttpFailure` effect, with enough structured
information to distinguish resolution/connection, TLS, timeout, and protocol failures while
preserving an underlying cause where available. Failures while reading an established response
body use the `Reader` I/O failure contract. No automatic request retries are performed.

Timeouts are finite and configurable at the client level, with request-level overrides. The initial
defaults are a 10-second connection timeout, a 30-second deadline for sending a request and
receiving response headers, and a 30-second idle timeout for each blocking response-body read.
The body-read timeout resets after each successful read; it is not a total body-download deadline.

## Initial API

The initial source API is in `zeron.net.http`. `HttpUri.parse` and `HttpMethod.parse` return
`Result` values; `HttpHeaders.add` validates caller-supplied fields; and `HttpRequest` provides
immutable builders for headers, a buffered body, and response/body-idle timeout overrides.
`HttpClientConfig.standard()` supplies the defaults, while `withTimeouts` validates custom finite
values. `HttpClient.send` returns response status, headers, negotiated version, and a streaming
`Reader`; transport failures raise `HttpFailure`, and body-read failures use `IoFailure`.

The current implementation uses the JDK HTTP client behind compiler-registered bindings. Redirects
are disabled in the transport, and compiler output includes the helper and its nested runtime
classes so generated programs do not need the compiler on their runtime classpath.

## Compatibility and impact

Networking adds public standard-library APIs and compiled-library metadata. Behavior depends on
host networking and may vary across operating systems. Request/response types, typed failures,
stream ownership, and timeout behavior must remain clear at source level while Java-backed
implementations remain behind the existing external-facade boundary.

## Alternatives

- Add TCP/UDP sockets alongside HTTP — supports more protocols, but expands the API and resource
  semantics without an identified need for low-level transport.
- Provide only sockets — flexible, but requires every consumer to implement HTTP and other common
  protocols independently.
- Use Java interop or third-party networking libraries — avoids standardizing network semantics,
  but reduces portability and discoverability and exposes implementation-specific APIs.
- Defer networking — avoids security and portability commitments, but leaves common application
  networking without a standard API.

## Implementation and validation

Automated tests cover URI/method/header validation, a loopback buffered request, response status and
headers, streamed body reads and disposal, manual redirect handling, body-idle timeouts, external
binding resolution, and runtime-helper packaging. The bundled standard-library build succeeds, and
the full Maven test suite passes. The broader transport matrix—especially TLS rejection,
DNS/connection failures, HTTP/2 negotiation, and connection reuse—remains outstanding.

## Resolved design decisions

- The initial scope is a synchronous HTTP client only; raw sockets, UDP, and server APIs are
  excluded.
- Requests have optional buffered `ByteArray` bodies. Response bodies stream through the existing
  `Reader`/`Disposable` model; streaming uploads are deferred.
- HTTP/1.1 is required, HTTP/2 may be negotiated, and HTTP/3 is excluded initially.
- Every received status is returned as response data. Transport failures use typed effects;
  response-body read failures follow the reader I/O contract.
- Redirects and retries are never automatic.
- HTTPS certificate and hostname validation use the platform defaults, with no insecure bypass in
  the initial API.
- Connection, response-header, and response-body idle timeouts have finite configurable defaults
  of 10 seconds, 30 seconds, and 30 seconds respectively. The response-body timeout is an idle
  timeout, not a total download deadline.
- A client is reusable and disposable, owns its managed connection resources, and a response owns
  its disposable body stream.

These decisions define the implemented initial networking scope.
