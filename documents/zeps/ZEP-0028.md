## Abstract

Add a built-in `zeron fmt` command that applies a deterministic canonical layout to Zeron source
files in a project. The command should also provide a non-mutating `--check` mode for CI and preserve
comments and source meaning.

## Motivation

Projects benefit from a consistent source layout that can be applied locally and verified in
automation. A built-in formatter can use the language's own syntax and project boundaries without
requiring each project to select and configure an external formatter. A check mode lets teams enforce
the canonical layout without modifying files during CI.

The formatter must not discard comments or rewrite malformed source into a success-shaped result.
This is important because a parser-driven formatter may otherwise lose trivia that is not represented
in the AST.

## Goals

- Provide a project-level command for formatting Zeron source files.
- Provide a `--check` mode that reports files needing formatting and exits unsuccessfully without
  writing changes.
- Produce deterministic, idempotent output while preserving comments and program meaning.
- Report parse and I/O errors explicitly and leave affected source files unchanged.
- Keep initial behavior simple, with one canonical style and no user-defined style configuration.

## Non-goals

- Formatting Java sources or generated compiler output.
- Changing Zeron syntax, semantics, or compiler diagnostics.
- Supporting multiple configurable styles or a general-purpose text-rewriting framework.
- Automatically formatting files through the language server or editor integration in the initial
  implementation.

## Proposal

Add `zeron fmt` to the CLI.

- With no explicit paths, discover Zeron source files belonging to the current project using its
  project configuration and source roots.
- Accept file and directory paths to limit formatting to selected `.zn` sources.
- Accept explicitly named `.zn` files outside the current project; project-wide discovery remains
  scoped to the project.
- Exclude generated output, compiled artifacts, and dependency sources from project-wide discovery.
- Format files in place by default. With `--check`, do not write any files; report each file whose
  contents differ from canonical output and return a nonzero exit code if any file needs formatting.
- If a selected file cannot be parsed or read, report the error and leave that file unchanged.
- Use one documented canonical layout. Reformatting already formatted source must produce no further
  changes.
- Preserve each file's existing line-ending convention rather than normalizing all files to one
  platform-specific convention.
- Preserve comments and other source content not represented in the semantic AST. The implementation
  validates syntax with the parser and formats the ranged scanner token stream; comments must remain
  in source order and must not be silently dropped. When sorting imports would move comments between
  declarations, preserve the existing import order instead.
- Do not follow directory symlinks during recursive discovery. Deduplicate selected files by their
  normalized real path where available.
- Write each formatted file through a temporary sibling and replace the original only after
  formatting succeeds. If replacement fails, report the error and leave the original unchanged.
- Continue processing other selected files when one file fails. A parse, read, or write failure
  leaves that file unchanged and contributes to a nonzero command exit status.
- In `--check` mode, do not write files; report files whose contents differ and return nonzero if any
  file differs or any selected file fails to parse or read.
- Use the canonical, versioned style in `src/main/resources/style.toml`; it is not a project-level
  configurable style in the initial implementation.
- Preserve each file's detected line-ending convention. For mixed line endings, use the first
  encountered newline convention for formatted output; use LF for a file with no existing newline.
- Preserve explicitly written syntax, including constructor declarations. Formatting must not remove
  syntax based on assumed semantic equivalence.

Formatting is a source-only operation: it should not perform name resolution, type checking, or code
generation. Formatting errors should use the existing diagnostic conventions where applicable.

The initial canonical style uses four-space indentation, a 100-column preferred width, one blank
line between declarations, and import groups separated by one blank line when the first package
component changes. Sum-type cases are vertically aligned. Function layout prefers a break after `=`
before breaking the parameter list; parameters wrap only when the function header exceeds the width.

## Compatibility and impact

Formatting does not change language semantics or compiled artifacts. Running the command may produce
source diffs; `--check` provides a safe way to identify those diffs before adopting the formatter in
CI. The CLI documentation should describe path discovery, exit behavior, and the canonical style.

## Alternatives

- **Require an external formatter** — avoids maintaining formatter logic, but fragments style and
  project discovery across tools and makes language-specific syntax support less cohesive.
- **Format only explicitly named files** — simpler discovery, but does not provide the requested
  project-level workflow.
- **Allow configurable styles immediately** — offers flexibility but adds policy and compatibility
  surface before a canonical layout has been established.
- **Print directly from the AST without retaining trivia** — simple to implement, but risks losing
  comments and other source text; this is not acceptable unless trivia preservation is added.

## Implementation and validation

1. Define and document canonical formatting rules for declarations, statements, expressions,
   indentation, blank lines, and line endings.
2. Implement project and explicit-path discovery with exclusions for generated and dependency
   outputs.
3. Implement formatting while preserving comments and source meaning; keep parse and I/O failures
   explicit and avoid writing malformed files.
4. Add tests for deterministic output, idempotence, comment preservation, parse-error behavior,
   project discovery, explicit paths, exclusions, and `--check` exit behavior.
5. Verify that formatted files parse and resolve identically to their original source.

## Implementation notes

The initial implementation adds `zeron fmt` and `--check`, project source-root discovery, explicit
file/directory selection, parser-validated token formatting, comment retention, line-ending
preservation, and temporary-sibling replacement. Canonical layout includes import sorting and package-root grouping where comments, wildcard imports,
or colliding local names do not make reordering unsafe; declaration spacing, aligned sum cases, and
function-body/parameter-list wrapping are also implemented. Focused tests cover CLI parsing, comments,
invalid input, line endings, idempotence, and representative project sources.

## Decision

Accepted 2026-10-18; implementation decisions completed 2026-10-19. The command preserves each
file's detected line-ending convention, allows explicitly named `.zn` files outside the current
project, and keeps project-wide discovery scoped to configured project roots. Recursive discovery
does not follow directory symlinks. The formatter uses parser structure with scanner trivia, writes
files via temporary siblings, preserves failed files, and continues processing other selected files.
`--check` is non-mutating and fails when files differ or errors occur. The initial implementation
uses the versioned canonical style in `src/main/resources/style.toml` without style configuration.
