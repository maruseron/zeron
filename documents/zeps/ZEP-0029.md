## Abstract

Add a runnable, multi-package query-engine sample under `sample_programs` that exercises a
representative cross-section of Zeron's existing language and library features. The sample also
provides a more realistic project-build workload than the existing two-source example.

## Motivation

Small isolated programs are useful for feature examples but provide weak evidence about how Zeron
behaves on a project with multiple source units and package dependencies. A query engine naturally
combines domain types, recursive syntax trees, generic behavior, extensions, and a backend, while
remaining small enough to understand and build quickly.

The sample is intended to support learning and repeatable compiler measurements. It is not evidence
by itself that incremental compilation is worthwhile; that decision requires clean and warm-build
measurements and output-equivalence checks.

## Goals

- Provide a runnable, multi-package Zeron project with realistic cross-unit dependencies.
- Demonstrate nominal IDs, a dynamic value sum, a recursive query plan, generic codec evidence,
  extension-based query builders, and an in-memory executor.
- Provide a repeatable project workload for future clean-build and incremental-build measurements.

## Non-goals

- Implementing a production database, SQL parser, optimizer, storage engine, or network protocol.
- Reifying arbitrary lambdas into query expressions.
- Introducing new language syntax or standard-library APIs solely for this example.
- Treating the sample's build time as a release gate without controlled comparative measurements.

## Proposal

Add the project at [`sample_programs/query_engine`](../../sample_programs/query_engine), with
separate packages for values and IDs, errors, codecs, rows, query expressions and plans, the fluent
builder API, the in-memory backend, execution, and a runnable demo.

The demo constructs an AST explicitly, joins sample users and orders, filters rows using an
expression, projects selected columns, orders the results, and prints them. `Codec<T>` witnesses
convert supported values into the dynamic `Value` sum. The in-memory backend returns typed errors
for unknown tables and invalid query operations.

The project is a compilation workload, not a claim that ordinary closures are query quotations.
Its DSL therefore builds `Expr` values directly rather than interpreting lambda bodies as data.

## Compatibility and impact

The sample does not change language semantics, compiler output formats, or standard-library APIs.
It adds source files and project documentation only. The sample should continue to build and run
with the supported compiler and bundled standard-library mode.

## Alternatives

- **Generate many trivial source files** — would increase unit count but would not represent
  meaningful dependency structure or language use.
- **Use only the existing `list_monad` sample** — remains useful as a compact example, but its two
  source files are too small to represent a multi-package project workload.
- **Build a real database engine** — would add substantial scope and external concerns without
  improving the compiler workload proportionally.

## Implementation and validation

Implemented in `sample_programs/query_engine`. Validation builds and runs the manifest project and
checks the demo's joined, filtered, projected, ordered output. The project currently contains 14
Zeron source units. Benchmarking should separately compare cold clean builds, repeat builds, and
representative source changes; compiler phase measurements are needed to estimate the portion
incremental emission could save.
