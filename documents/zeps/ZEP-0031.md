# ZEP-0031: Declarative Annotations and Declaration Metadata

## Abstract

This proposal introduces typed declarative annotations, written with `@Name`, for attaching
validated metadata to declarations, members, and parameters. Annotations provide a uniform way for
libraries and compiler-supported declaration features to describe properties such as persistence
mapping, serialization behavior, validation constraints, and code-generation hints.

The initial design is intentionally metadata-oriented. It does not introduce general-purpose
macros, arbitrary compile-time execution, or unrestricted AST transformation.

## Motivation

Libraries often need information about declarations that is not naturally part of a type's runtime
behavior. An ORM may need to identify a primary key, a serializer may need an external field name,
and a validation library may need to associate constraints with a property.

Without a common annotation mechanism, libraries tend to rely on naming conventions, manually
maintained metadata, or specialized syntax for each use case. A small declarative mechanism would
let these concerns share a consistent representation while preserving Zeron's preference for
explicit, statically checked capabilities.

## Goals

- Provide syntax for attaching metadata to supported declarations, members, and parameters.
- Validate annotation placement and arguments during compilation.
- Preserve public annotation information for compiler features and library tooling.
- Define predictable behavior across source compilation and compiled-library boundaries.
- Keep ordinary declarations and runtime behavior unchanged unless a consumer explicitly interprets
  the metadata.

## Non-goals

- General-purpose compile-time execution or macro expansion.
- Arbitrary mutation of compiler ASTs by libraries.
- A universal annotation-processing framework with unrestricted compiler hooks.
- Defining the semantics of individual annotations such as `@PrimaryKey`; those belong to the
  feature or library that owns them.
- Specifying runtime reflection; see [ZEP-0032](./ZEP-0032.md).

## Proposal

### Syntax

Applications precede the declaration or member they annotate. Parameters may also be annotated
immediately before their name. An application may use positional or named arguments; omitted
arguments use declared defaults.

```zeron
import zeron.data.Entity;
import zeron.data.PrimaryKey;
import zeron.data.Generated;
import zeron.data.OneToMany;

@Entity
public data class User(
    @PrimaryKey @Generated(strategy = "identity") id: Int,
    name: String
) {
    @OneToMany(mappedBy = "user")
    orders: Array<Order>;
}
```

An annotation is not repeatable in the initial design: a declaration may have at most one
application of a given annotation identity. Distinct annotations may be combined, and their source
order is preserved in source metadata.

### Annotation declarations and identity

Annotations are declared with a dedicated declaration form. Its typed parameters define the
application's argument shape, and its target list limits where it may be applied:

```zeron
public annotation Entity on CLASS;
public annotation PrimaryKey on FIELD, PROPERTY, DATA_COMPONENT;
public annotation Generated(strategy: String = "default") on FIELD, PROPERTY, DATA_COMPONENT;
public annotation OneToMany(mappedBy: String) on FIELD, PROPERTY, DATA_COMPONENT;
public annotation ManyToOne on FIELD, PROPERTY, DATA_COMPONENT;
public annotation CodeModel on PARAMETER;
```

Annotation identity is nominal and follows ordinary package and import rules. An application must
resolve to a declared annotation; unresolved names are errors, including misspellings of
tooling-only annotations. Annotation declarations are non-generic. Parameter and argument names,
types, defaults, and targets are part of the annotation's public contract.

The initial targets are `CLASS`, `CONTRACT`, `FUNCTION`, `METHOD`, `CONSTRUCTOR`, `FIELD`,
`PROPERTY`, `DATA_COMPONENT`, and `PARAMETER`. `CLASS` includes regular and data classes.
`DATA_COMPONENT` denotes a declared data-class component, distinct from an ordinary parameter or
stored field. The `FUNCTION` target covers top-level functions; `METHOD` covers class, contract, and
extension methods. `CONSTRUCTOR` covers constructors and named constructors.

## Metadata model

The compiler records annotation identity and validated arguments in declaration metadata. Consumers
should receive a stable, read-only representation rather than direct access to mutable compiler AST
nodes. Annotation arguments are stored as typed values, not source snippets. Source-mode analysis
may retain locations for diagnostics and IDE features; source paths and offsets are not part of
compiled-library annotation metadata.

The representation should distinguish:

- the annotated declaration;
- the annotation's resolved identity;
- its validated arguments;
- source location information where useful for diagnostics.

Metadata should not implicitly add members, change dispatch, or alter runtime representation. An
annotation has no effect unless a compiler feature or external tooling explicitly interprets it.
This proposal does not provide general compiler plugins or declaration transformation.

### Annotation arguments

Arguments must be compile-time constants checked against the declared parameter types. The initial
constant forms are string, Boolean, and built-in numeric literals, `null` for nullable parameters,
unary `+` and `-` applied to numeric constants, and one-dimensional arrays of supported constants.
Numeric values are range-checked and must be representable by the declared built-in numeric type.
Array elements must conform to the array's element type. Arbitrary expressions, calls, variable
references, captures, and compile-time execution are not supported. Type/class literals and nested
annotation values are also deferred; relationships can initially use the annotated property's
declared type and scalar options such as `mappedBy`.

Positional and named arguments follow the annotation declaration's parameter order and names.
Duplicate, unknown, missing-required, and ill-typed arguments are compile-time errors.

### Targets, tooling, and compiler semantics

The compiler validates that each annotation target is permitted and that arguments satisfy the
annotation's declared shape. Tooling-only annotations are supported: they must be declared and
validated, but need not have compiler-defined behavior. Applications are compile-time metadata and
have no runtime reflection representation in this proposal. A compiler-recognized annotation may
affect compile-time validation or lowering only as separately specified.

`@CodeModel` is declared as `zeron.compiler.CodeModel` for the `PARAMETER` target. The compiler
recognizes that canonical identity and implements its parameter behavior as specified by ZEP-0080.
Other annotations remain inert unless a separately specified compiler feature or external tool
interprets them. Knowing an annotation declaration does not grant arbitrary compiler-phase hooks.

### Library and tooling consumption

Annotation definitions and applications on exported public declarations, members, data components,
and parameters are serialized in the versioned Zeron API index. Applications on private declarations
remain available to source-mode analysis but are not exported. An annotation used on an exported
public API must itself be public, so separate-compilation consumers can resolve its identity and
schema.

The API index exposes annotation metadata through a stable, read-only compiler/tooling API.
Ordinary Zeron runtime code and libraries do not reflect over annotations; runtime reflection is
outside this proposal. Annotation metadata is not a compiler plugin interface.

## Compatibility, evolution, and impact

The syntax is additive, but it affects parsing, name resolution, declaration metadata,
compiled-library indexes, and diagnostics. The serialized metadata format must be versioned or
otherwise governed by the existing library artifact compatibility policy.

Changes to the API-index wire representation use `API_INDEX_SCHEMA_VERSION`, independently of the
standard-library API version and artifact version. Required wire changes are consolidated and the
schema is incremented according to the existing release-cycle policy.

An annotation's qualified identity and public argument schema are part of the library metadata
contract. Adding an optional parameter with a default or broadening its target set is compatible.
Removing or narrowing targets, changing parameter names or types, adding a required parameter, or
changing established interpretation incompatibly requires a new annotation identity or an
incompatible library release. Annotation metadata does not by itself change a declaration's JVM
ABI.

## Alternatives

- Ad hoc syntax for every metadata use case — rejected as the default direction because it
  duplicates syntax and compiler support across unrelated libraries.
- General-purpose macros — deferred; unrestricted transformation is substantially broader and
  harder to validate than declarative metadata.
- Runtime reflection only — insufficient for compile-time validation and may impose runtime
  metadata and performance costs.

## Implementation and validation

A likely implementation sequence is:

1. Parse annotation declarations and applications, then resolve annotation identity through normal
  imports and visibility.
2. Validate target applicability, argument names, defaults, constant forms, and types.
3. Preserve typed metadata on supported declarations, members, and parameters.
4. Serialize public annotation definitions and applications in the versioned API index.
5. Expose metadata through a read-only compiler/tooling API; reserve compiler behavior for explicitly
  recognized annotations such as `zeron.compiler.CodeModel`.
6. Test diagnostics, source analysis, separate compilation, library compatibility, and metadata
  stability.

Validation should verify that tooling-only annotations remain inert, metadata survives library
compilation and consumption, and ordinary runtime behavior remains unchanged.

## Implementation status

Implemented 2026-11-01. The compiler parses and validates annotation declarations, applications,
targets, arguments, and supported constants. Public definitions and applications on exported API
are preserved in API-index schema 9 and restored for separately compiled consumers. Annotation
metadata remains compile-time/tooling data and does not add runtime reflection.

## Decision

Accepted 2026-11-01. Use prefix `@Name` applications on declarations, members, data components, and
parameters; define annotations with typed `annotation Name(parameters...) on TARGET, ...;`
declarations; begin with the target set specified above; allow only the specified compile-time
constant forms; require all annotations to resolve while allowing declared tooling-only annotations;
and expose public annotation metadata through the versioned read-only API index, without runtime
reflection. `zeron.compiler.CodeModel` is the compiler-recognized annotation for ZEP-0080.

The annotation wire representation follows the API-index schema version, while annotation
definitions and interpretations follow library compatibility rules. Release candidacy remains
separate from proposal status and is tracked only in [ZEP.md](./ZEP.md); no release bundle is
selected here.
