## Abstract

This proposal introduces declarative annotations, written with `@Name`, for attaching validated
metadata to declarations and declaration members. Annotations provide a uniform way for libraries
and compiler-supported declaration features to describe properties such as persistence mapping,
serialization behavior, validation constraints, and code-generation hints.

The initial design is intentionally metadata-oriented. It does not introduce general-purpose
macros, arbitrary compile-time execution, or unrestricted AST transformation.

## Motivation

Libraries often need information about declarations that is not naturally part of a type's runtime
behavior. An ORM may need to identify a primary key, a serializer may need an external field name,
and a validation library may need to associate constraints with a property.

Without a common annotation mechanism, libraries tend to rely on naming conventions, manually
maintained metadata, or specialized syntax for each use case. A small declarative mechanism would
let these concerns share a consistent representation while preserving Zeron's preference for
explicit, statically checked capabilities.

## Goals

- Provide syntax for attaching named metadata to supported declarations and declaration members.
- Validate annotation placement and arguments during compilation.
- Preserve annotation information in a form that compiler features and authorized library tooling can
  consume.
- Define predictable behavior across source compilation and compiled-library boundaries.
- Keep ordinary declarations and runtime behavior unchanged unless a consumer explicitly interprets
  the metadata.

## Non-goals

- General-purpose compile-time execution or macro expansion.
- Arbitrary mutation of compiler ASTs by libraries.
- A universal annotation-processing framework with unrestricted compiler hooks.
- Defining the semantics of individual annotations such as `@PrimaryKey`; those belong to the
  feature or library that owns them.
- Specifying runtime reflection; see [ZEP-0032](./ZEP-0032.md).

## Proposal

### Syntax

The proposed syntax is:

```zeron
@Entity
class User derives Codec<User> {
    @Column("display_name")
    name: String;
}
```

An annotation may optionally receive arguments. The exact permitted argument forms should be
restricted to expressions that can be evaluated or recorded deterministically during compilation.
The initial implementation should prefer literals and other simple constant forms.

The language should define which declaration kinds accept annotations. A reasonable initial set is
classes, contracts, functions, constructors, properties, and parameters, subject to implementation
feasibility. Including annotations for top level values, effects and effect handlers remains up
for consideration.

## Annotation declarations and identity

An annotation name must resolve to a declared annotation definition or to a compiler-recognized
annotation. Annotation identity is nominal and follows ordinary package and import rules.

This proposal does not settle whether annotation definitions are declared using a dedicated
annotation declaration, a restricted contract-like declaration, or a compiler/library registry.
That choice is an open question and should be resolved before implementation.

## Metadata model

The compiler records annotation identity and validated arguments in declaration metadata. Consumers
should receive a stable, read-only representation rather than direct access to mutable compiler AST
nodes.

The representation should distinguish:

- the annotated declaration;
- the annotation's resolved identity;
- its validated arguments;
- source location information where useful for diagnostics.

Metadata should not implicitly add members, change dispatch, or alter runtime representation. A
feature that uses metadata to generate declarations must specify that elaboration separately.

## Validation and consumption

The compiler validates that an annotation is applicable to the target declaration and that its
arguments satisfy the annotation's declared shape.

A consumer may interpret annotations only through an explicitly supported mechanism. The language
should not imply that every annotation is meaningful to every compiler phase or library.

Unknown annotations should produce a clear diagnostic when they are used in a context requiring
resolution; whether tooling-only annotations may be preserved without a compiler definition remains
open.

## Compatibility and impact

The syntax is additive, but it affects parsing, name resolution, declaration metadata,
compiled-library indexes, and diagnostics. The serialized metadata format must be versioned or
otherwise governed by the existing library artifact compatibility policy.

Annotations should not change runtime behavior by themselves. If a later proposal defines
annotation-driven code generation, that proposal must describe the generated API and compatibility
implications.

## Alternatives

- Ad hoc syntax for every metadata use case — rejected as the default direction because it
  duplicates syntax and compiler support across unrelated libraries.
- General-purpose macros — deferred; unrestricted transformation is substantially broader and
  harder to validate than declarative metadata.
- Runtime reflection only — insufficient for compile-time validation and may impose runtime
  metadata and performance costs.

## Implementation and validation

A likely implementation sequence is:

1. Define annotation declaration identity and permitted targets.
2. Parse annotation applications and resolve their names.
3. Validate argument forms and target applicability.
4. Preserve metadata in compilation artifacts.
5. Expose a read-only metadata API to compiler-supported consumers.
6. Add tests for invalid targets, invalid arguments, imports, separate compilation, and artifact
  compatibility.

Validation should verify that annotations have no effect unless a defined consumer interprets them, and that metadata survives library compilation and consumption.

## Open questions

- What declaration form defines an annotation?
- Which declaration targets are supported in the first slice?
- Which compile-time constant expressions may appear as annotation arguments?
- Are annotations required to resolve in all compilation modes, or may tooling-only annotations
  be preserved?
- Which metadata is exposed to libraries, and through what stable API?
- How should annotation metadata evolve across compiled-library versions?
