## Abstract

Explore whether Zeron should support user-defined decorators or another declaration-annotation
mechanism, and identify a useful, constrained role for such a feature without committing to syntax
or compile-time execution.

## Motivation

As the language gains libraries and tooling, users may want to attach reusable behavior or
machine-readable metadata to declarations. Possible use cases include deriving boilerplate,
registration, validation, serialization metadata, and tooling hints. These use cases differ
substantially: some need only metadata, while others transform declarations or generate code.

Calling all of these “decorators” risks conflating passive annotations with macros or arbitrary
compile-time programs. An exploration should establish concrete use cases and semantic boundaries
before Zeron adopts a feature.

## Goals

- Inventory demonstrated use cases that annotations, derivation, generated code, or compiler
  intrinsics do not already serve adequately.
- Compare passive declaration metadata, compiler-recognized annotations, and user-defined
  declaration transformations.
- Evaluate typing, visibility, generic declarations, diagnostics, composition order, and library
  metadata requirements.
- Identify whether a deliberately limited first scope would be valuable.

## Non-goals

- Adding decorator syntax or implementation as part of this exploration.
- Committing to macros, compile-time evaluation, arbitrary code execution, or declaration rewriting.
- Replacing existing contract witnesses, explicit derivation, compiler intrinsics, or external
  bindings.
- Specifying runtime reflection; see [ZEP-0032](./ZEP-0032.md).

## Proposal

Study a spectrum of possible mechanisms:

1. **Passive metadata** attached to declarations and consumed by compiler tooling or libraries.
2. **Compiler-recognized annotations** that enable a small, fixed set of checked behaviors.
3. **User-defined decorators** that transform declarations or generate additional declarations.

For each category, record concrete use cases, whether the behavior is compile-time or runtime,
how errors point to source, how multiple annotations compose, how generated declarations interact
with visibility and API indexes, and how separately compiled libraries preserve metadata.
Prefer the least powerful mechanism that addresses the validated use cases. A declaration
transformation model must explain hygiene, termination, reproducibility, incremental-build
identity, and how generated names avoid collisions before it can be considered.

This ZEP is an open-ended design exploration, not a proposal to implement one of these mechanisms.

## Compatibility and impact

Any eventual feature could affect declaration syntax, compilation phases, diagnostics, generated
APIs, and compiled-library metadata. Runtime-retained metadata could also affect artifact size and
interoperability. These impacts must be compared for each candidate model; no compatibility policy
is selected here.

## Alternatives

- **Use ordinary functions and explicit derivation** — simple and statically checked, but may not
  cover declaration metadata or repetitive generated structures.
- **Add passive metadata only** — limits semantic and compiler complexity, but cannot generate or
  validate behavior by itself.
- **Adopt a general macro system immediately** — maximally expressive, but creates major questions
  around staging, hygiene, type checking, tooling, reproducibility, and build invalidation before
  sufficient use cases are established.
- **Keep using compiler intrinsics for every case** — maintains control but can make reusable
  library-level behavior unavailable to users.

## Implementation and validation

Collect and rank concrete use cases, then prototype representative examples against the three
mechanism categories without committing to production syntax. Estimate compiler and API-index
impact and test whether the desired tooling can inspect source locations and generated declarations.
Any implementation should receive a separate accepted scope or a revised ZEP.

## Open questions

- Which current or planned use cases require declaration-level metadata or transformation?
- Should annotations be visible at runtime, available only in compiler metadata, or both?
- Is any user-defined transformation power justified over a closed set of compiler-recognized
  annotations?
- What hygiene and failure model would be acceptable if declarations can be generated?
