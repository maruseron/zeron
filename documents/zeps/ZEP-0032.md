## Abstract

Explore whether Zeron needs user-visible runtime reflection, which metadata and operations it would
require, and how a bounded design could coexist with JVM erasure, compiled libraries, and the
existing compile-time member-discovery API.

## Motivation

Runtime reflection can support serializers, dependency injection, diagnostics, dynamic adapters,
and plugin systems. It can also require metadata retention, expand public ABI commitments, weaken
static guarantees when combined with dynamic invocation, and impose costs on generated artifacts.

Zeron already has a compile-time public member-discovery API. Separately, ZEP-0015 explores runtime
reification of generic type identity for a specific semantic need. Neither implies that programs
should receive general runtime access to declarations or members. This exploration should determine
whether concrete runtime use cases justify that additional surface.

## Goals

- Distinguish runtime type identity, declaration metadata, public member discovery, and dynamic
  invocation as separate possible capabilities.
- Identify concrete use cases that cannot be served by static APIs, generated adapters, explicit
  registries, or narrowly scoped runtime descriptors.
- Evaluate visibility, generic types, separate compilation, Java interoperation, code size,
  runtime overhead, and optimization impact.
- Establish whether a restricted reflection model is sufficient or whether no runtime reflection
  should be added.

## Non-goals

- Implementing reflection or selecting a source API in this proposal.
- Treating JVM reflection as automatically equivalent to source-level Zeron reflection.
- Replacing compile-time public member discovery.
- Conflating contract evidence with runtime type identity or metadata.
- Broadening [ZEP-0015](./ZEP-0015.md) from generic type reification into general reflection.

## Proposal

Explore a graduated set of capabilities, keeping them independently assessable:

1. **Runtime type descriptors** for a defined set of source types, with no member enumeration.
2. **Runtime declaration metadata** for selected public types and members, without invocation.
3. **Dynamic member lookup or invocation**, with explicit rules for visibility, overloads,
   mutability, effects, and Java boundaries.

For each level, specify which source distinctions are observable, what data must be emitted and
serialized in library artifacts, how erased generic applications are represented, and whether users
can inspect only public declarations. Compare runtime descriptors with ZEP-0015's type-identity
requirements and with ZEP-0009's static catalog; avoid duplicating either service without a
demonstrated need.

Prefer generated, explicit metadata or closed capabilities if they satisfy the identified use
cases. General reflective invocation should require a separate scope decision because it affects
static checking, accessibility, runtime errors, and ABI stability.

## Compatibility and impact

Runtime metadata and invocation could affect generated class size, compilation and startup time,
optimization, library-index or artifact formats, and compatibility guarantees for public
declarations. Dynamic operations may move errors from compile time to runtime. This exploration
selects no retention policy, metadata format, or invocation contract.

## Alternatives

- **Keep introspection compile-time only** — preserves the current static model and is sufficient
  for editor features, but does not directly serve runtime serializers or plugin discovery.
- **Use JVM reflection directly** — reuses existing platform facilities, but may expose erased
  implementation details and does not define Zeron source visibility or generic identity.
- **Generate explicit registries or adapters** — keeps runtime behavior typed and bounded, but
  requires explicit participation and may duplicate metadata for different use cases.
- **Use runtime type reification only where required** — addresses applied type identity without
  implying member reflection, but does not support arbitrary declaration discovery.

## Implementation and validation

First gather concrete runtime use cases and determine which capability level each needs. Prototype
artifact and runtime costs for representative generic types and separately compiled libraries.
Validate visibility boundaries, generic identity, deterministic metadata, Java interoperability,
and behavior under optimization. Implementation, if justified, should follow a separately accepted
scope.

## Open questions

- Which runtime use cases are compelling enough to justify metadata in ordinary builds?
- Should metadata describe source declarations, generated JVM members, or a stable source-level
  projection?
- Is reflection limited to public members sufficient, and how should dynamic invocation handle
  overloads, effects, and mutability?
- Can explicit registries or generated adapters meet the same needs at lower cost?
