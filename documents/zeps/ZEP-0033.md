# ZEP-0033: Soft `get` and `set` Accessor Keywords

## Abstract

Treat `get` and `set` as ordinary identifiers except in property accessor positions, where the
parser recognizes them contextually as soft keywords.

## Motivation

`get` and `set` describe property accessors, but reserving them lexically prevents their use as
ordinary identifiers. In particular, `set` is a natural variable name for a `Set` value, and both
words are useful as method, parameter, and local names. Accessor blocks already provide a narrow,
unambiguous grammatical context for the special meaning.

## Goals

- Permit `get` and `set` wherever ordinary identifiers are accepted.
- Preserve existing property accessor syntax and semantics.
- Keep accessor interpretation local to a property's accessor block.
- Keep scanner, parser, diagnostics, syntax highlighting, and completion behavior consistent.

## Non-goals

- Changing property mutability, getter/setter behavior, or accessor evaluation.
- Making other hard keywords soft.
- Adding getter or setter shorthand or changing property syntax.

## Proposal

The scanner emits `get` and `set` as `IDENTIFIER` tokens. The parser recognizes either spelling
only in the corresponding property accessor position:

```zeron
class Example {
    backing: Int;

    public mut property value: Int {
        get = this.backing;
        set(next) {
            this.backing = next;
        }
    }

    public get(): Int = this.backing;
}

fn use(): Int {
    let set = Set<Int>.empty();
    let get = Example.new(0);
    return get.get();
}
```

Outside the accessor block, the words follow ordinary identifier rules. Member names therefore
need no special-case grammar alternative. In the accessor block, only `get` and `set` introduce
accessors; duplicate and malformed accessors retain their existing diagnostics.

## Compatibility and impact

This is a source-compatible relaxation: programs that previously failed because `get` or `set`
was reserved become valid. Existing accessor blocks retain their meaning. The scanner token model,
parser, grammar reference, terminal syntax highlighter, VS Code grammar, and LSP keyword completion
must stop treating these words as globally reserved.

## Alternatives

- **Keep both words reserved** — preserves the current token model but unnecessarily restricts
  ordinary names such as `set`.
- **Make only `get` soft** — leaves the same restriction for `set` and treats the accessor pair
  inconsistently.
- **Remove accessor words or change accessor syntax** — would solve the naming conflict but cause
  avoidable source churn.

## Implementation and validation

Remove the dedicated scanner token kinds and keyword mappings, use contextual spelling checks in
property accessor parsing, and update grammar and editor highlighting/completion. Test tokenization
and resolution of `get`/`set` as variables and methods, as well as property getter/setter parsing
and existing accessor semantics.

## Decision

Accepted 2026-10-18. Both words become soft keywords together, recognized only in property
accessor blocks; elsewhere they are ordinary identifiers.
