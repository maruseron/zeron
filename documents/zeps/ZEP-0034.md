# ZEP-0034: Namespace-Scoped Wildcard Imports

## Abstract

Allow wildcard imports to select all public members of a namespace, including extensions declared
in that namespace, so callers can intentionally activate an extension group without importing
extensions for the same receiver from unrelated packages.

## Motivation

Importing extensions by receiver identity makes wildcard scope global to a compilation: a target
such as `model.Box.*` can activate every public `Box` extension regardless of its declaring
package. This is surprising when multiple libraries provide competing extensions for one receiver.
Declaration namespaces already provide an explicit ownership boundary and are a natural unit for
loading a group of related extensions.

## Goals

- Interpret a namespace wildcard as importing its public functions, immutable values, and
  extensions.
- Make extension activation depend on the declaring namespace, not receiver identity.
- Preserve package wildcard imports as a separate way to activate public declarations and
  extensions across a package.
- Keep duplicate and ambiguous extension behavior deterministic.

## Non-goals

- Importing all extensions for a receiver across packages.
- Re-exporting declarations through wildcard imports.
- Changing explicit extension imports, receiver applicability, or extension precedence.

## Proposal

```zeron
package model;

public class Box { }
namespace Box {
    public fn empty(): Box = Box.new();
}
```

```zeron
package extras;

import model.Box;
public extension Box {
    public fn label(): String = "extra";
}
```

`import model.Box.*;` selects members in the `model.Box` namespace. If a type and namespace share
the qualified name, the namespace is selected for wildcard import purposes. This imports the
namespace's public ordinary functions and immutable values by their unqualified names, and
activates its public extensions for receiver syntax. It does not activate extensions declared in
`extras.Box`; those are selected with `import extras.Box.*;` (or an explicit extension import).

Package wildcards such as `import extras.*;` retain their package-wide meaning. If a wildcard target
matches both a namespace and a package, it is rejected as ambiguous. An extension wildcard and
explicit extension imports participate in the same lookup tier; importing the same declaration by
both routes does not duplicate it, while distinct applicable declarations with colliding names
remain ambiguous.

## Compatibility and impact

This changes the meaning of wildcard imports that previously resolved to a receiver type: receiver
family activation is removed. Existing package wildcard behavior and explicit imports remain.
Resolver, top-level value dependency planning, compiled-library lookup, LSP completion, and import
documentation must all apply the same namespace ownership and visibility rules.

## Alternatives

- **Receiver-family wildcard** — concise, but loads extensions across package boundaries and can
  create surprising collisions.
- **Package wildcard only** — predictable at package scope, but may activate unrelated extension
  groups from that package.
- **Explicit member imports only** — maximally selective, but unnecessarily repetitive when using
  a namespace's public API broadly.

## Implementation and validation

Implemented namespace recognition and wildcard activation in import resolution, ordinary function
and value lookup, extension lookup, dependency ordering, and LSP completion. Regression coverage
checks same-named type/namespace resolution, extension isolation across packages, public visibility,
package wildcard compatibility, ambiguity, and library metadata.
