# ZEP-0035: Standard Library Source in Release Bundle

## Abstract

Ship the Zeron standard-library source tree in the release distribution and let the language server
map compiler references to those files, enabling users to navigate to standard-library definitions.

## Motivation

The compiler already bundles standard-library source resources for source-mode resolution, but the
language server's workspace snapshot maps compiler source paths only to project files. As a result,
definition requests targeting standard-library declarations cannot produce a navigable file URI.
Release installations should provide stable filesystem paths to those source files.

## Goals

- Include the complete standard-library source tree in the portable release archive.
- Make the installed launcher identify its distribution root to the compiler/LSP.
- Map bundled standard-library compiler paths to their installed source files in LSP snapshots.
- Preserve source-checkout LSP navigation and compiled-library configuration behavior.

## Non-goals

- Changing standard-library semantics or compiled API metadata.
- Adding standard-library source files to compiled standard-library JARs.
- Providing source navigation for arbitrary third-party compiled libraries.

## Proposal

Package standard-library `.zn` files under `share/zeron/stdlib`, preserving paths relative to the
standard-library root. Both launchers provide the installation root using the `zeron.home` system
property. In source mode, the LSP maps canonical `/stdlib/...` compiler paths to these files and
includes their contents in the analysis snapshot so definition locations can be returned as normal
filesystem URIs. Development environments may resolve the source resources directly from the
compiler classpath or source checkout.

## Compatibility and impact

The release archive grows by the size of the standard-library source tree. The language server's
definition responses gain locations for standard-library declarations; compilation and runtime
behavior are unchanged.

## Alternatives

- **Use opaque JAR resource URIs** — avoids copying files but editor navigation support is not
  reliable for those URIs.
- **Embed source in compiled-library API metadata** — duplicates data in a generated API artifact
  and does not provide direct source files to editor clients.
- **Require users to install a source checkout** — makes navigation unavailable to ordinary
  distribution users.

## Implementation and validation

Implemented source-tree staging and archive verification in the release script, installation-root
discovery in both launchers, source-path mapping in LSP workspace snapshots, and definition
navigation regression coverage.
