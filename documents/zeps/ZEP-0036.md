# ZEP-0036: Operator Overloading Through Algebraic Contracts

## Abstract

This proposal introduces operator overloading through explicit, operation-specific contracts.
Addition and multiplication require monoid-like contracts, while subtraction and multiplicative
division require stronger group-like contracts. The compiler checks contract conformance and
dispatches through its evidence model, but does not prove that implementations obey algebraic laws.

## Motivation

Built-in operators are convenient for arithmetic and other algebraic operations, but allowing any
type to define an arbitrary binary method as an operator risks obscuring behavior. A closed set of
compiler-recognized numeric types avoids that ambiguity but excludes useful user-defined types and
does not express the behavior generic algorithms need.

Operation-specific contracts offer a middle ground. Requiring an identity for `+` or `*` makes
operator syntax a deliberate capability: types with only a useful binary combination can retain a
named method without acquiring the operator. Stronger contracts can add inverses for types whose
operations support subtraction or division.

## Goals

- Enable generic and user-defined operator behavior through explicit contract requirements.
- Require identity-bearing algebraic capabilities for `+` and `*`.
- Express subtraction and division through inverse operations on stronger contracts.
- Preserve static dispatch and the existing contract-evidence model.
- Leave algebraic laws as documented semantic expectations rather than compiler-proven guarantees.

## Non-goals

- Proving associativity, identity, inverse, commutativity, or other algebraic laws.
- Defining every arithmetic, comparison, equality, logical, or type-test operator.
- Introducing runtime reflection, first-class types, or a closed-set `numeric` constraint.
- Replacing the existing semantics of built-in numeric operators or string concatenation.
- Requiring types with useful binary operations but no identity to expose operator syntax.

## Proposal

### Algebraic contract hierarchy

Define operation-specific contracts for the two initial algebraic structures:

- `Add<T>` supplies an associative binary operation and its identity.
- `Addition<T>` requires `Add<T>` and supplies an inverse for each value.
- `Mult<T>` supplies an associative binary operation and its identity.
- `Multiplication<T>` requires `Mult<T>` and supplies an inverse for each value.

The member names are operation-specific so a type can implement both structures without colliding
on a shared identity method:

- `Add<T>` provides `add` and its additive identity `zero`.
- `Addition<T>` requires `Add<T>` and provides `negate`.
- `Mult<T>` provides `multiply` and its multiplicative identity `one`.
- `Multiplication<T>` requires `Mult<T>` and provides `reciprocal`.

These contracts describe distinct operations and identities. Neither requires commutativity.

`Addition` and `Multiplication` require an inverse operation for every value in their carrier.
Thus ordinary integer multiplication can conform to `Mult<Int>` but not `Multiplication<Int>`,
because zero has no multiplicative inverse. The compiler checks required members and types; it
does not prove that an inverse cancels a value or that the operations obey group laws.

### Operator mapping

The initial operator mapping is:

| Operator | Required contract | Meaning |
| -------- | ----------------- | ------- |
| `+` | `Add<T>` | Apply the additive binary operation. |
| `*` | `Mult<T>` | Apply the multiplicative binary operation. |
| unary `-` | `Addition<T>` | Apply `negate`. |
| binary `-` | `Addition<T>` | Add the negation of the right operand to the left operand. |

The initial operator slice is limited to `+`, `*`, unary `-`, and binary `-`. Division remains
deferred; `Multiplication<T>` provides `reciprocal`, but `/` syntax and behavior are not introduced
by this proposal. Each binary operator initially requires both operands and the result to have the
same type; mixed-type promotion is not inferred.

Operator use in a generic function requires the corresponding contract bound to be declared
explicitly. The compiler does not infer hidden bounds from an operator expression. Generic calls
dispatch through the existing static contract-evidence model, with evidence forwarded through
bounded calls. The bundled standard library provides built-in numeric witnesses for the supported
operations, while concrete built-in arithmetic retains its current intrinsic behavior and
precedence.

The initial built-in evidence matrix is deliberately explicit:

| Type | `Add<T>` | `Addition<T>` | `Mult<T>` | `Multiplication<T>` |
| ---- | -------- | ------------- | --------- | ------------------- |
| `Int` | Yes | Yes | Yes | No |
| `Long` | Yes | Yes | Yes | No |
| `Float` | Yes | Yes | Yes | Yes |

`Int` and `Long` do not implement `Multiplication<T>` because zero has no multiplicative inverse.
`Float` implements it using IEEE floating-point reciprocal; the compiler does not promise inverse
laws for zero, infinities, or NaN.
Runtime type inspection is not introduced.

The existing `String + T` behavior requiring `Display<T>` also remains intrinsic and takes
precedence over additive evidence when the left operand is `String`. Operator contracts cannot
replace or make that behavior ambiguous. Equality and relational operators remain outside this
proposal and retain their existing evidence and built-in rules.

### Laws and API expectations

The contract names describe intended capabilities, not verified algebraic laws. Conformance makes
no guarantee of associativity, identity, inverse cancellation, or commutativity, and the compiler
does not test those properties. In particular, callers must not infer lawfulness solely from
contract conformance.

The contracts deliberately require identities for operator capability. A type that has an
associative combination but no useful identity may expose a named method instead of implementing
`Add<T>` or `Mult<T>`. There is no general `Semigroup<T>` contract that grants `+` in this proposal.

## Compatibility and impact

This is additive source-language behavior for user-defined and generic operators and adds the four
public algebraic contracts to the standard library API. Existing built-in operator behavior must
not change. Existing generic functions gain no inferred requirements, and new generic functions
using these operators must declare explicit bounds.

Operator expressions use synthesized contract calls and the existing compiled-library witness
metadata; generic call sites forward the relevant evidence. The built-in evidence matrix is
recorded above, including the `Float` reciprocal behavior. Conformance promises required operation
signatures, not algebraic lawfulness. String concatenation and primitive arithmetic retain
precedence over contract lookup.

## Alternatives

- **Allow any contract to provide an operator-shaped method** — flexible, but allows arbitrary
  operations to claim familiar syntax without a meaningful semantic commitment.
- **Map operators to a generic `Semigroup<T>`** — permits combination without an identity, contrary
  to the deliberate identity requirement for operator capability.
- **Use one generic `Monoid<T>` for both `+` and `*`** — obscures which operation and identity an
  operator uses when a type supports both.
- **Use a closed-set `numeric` constraint** — can restrict admissible types but neither exposes
  operations nor supports user-defined algebraic types.
- **Leave all operators compiler-recognized and built-in-only** — preserves current simplicity but
  does not support generic algorithms over user-defined types.

## Implementation and validation

Implemented the public contracts and built-in witnesses in the standard library. Concrete
`Int`/`Long`/`Float` arithmetic remains intrinsic; generic calls use static contract evidence.
The standard-library API version advanced from 6 to 7 for the added public contracts.

Tests cover nominal conformance, non-nominal witnesses, explicit generic bounds and evidence
forwarding, the built-in matrix, existing string concatenation and arithmetic, negative cases for
missing or wrong contract evidence, and a separately compiled client using a library witness.
The full preview-enabled Maven suite passes (487 tests). No test asserts algebraic laws.

## Open questions

None for the initial scope. Division, mixed-type arithmetic, and any guarantee or verification of
algebraic laws require separate design decisions.

## Decision

Accepted and implemented 2026-10-19. Use `Add`/`Mult` for identity-bearing additive and
multiplicative capabilities, with `Addition`/`Multiplication` adding `negate`/`reciprocal`. The
initial operators are `+`, `*`, unary `-`, and binary `-`; division and mixed-type promotion are
deferred. Built-in operations and `String + T` retain precedence, and contract conformance does
not guarantee algebraic laws. Shipped in 0.5.0.
