# ZEP-0037: Null Tests with the `is` Operator

## Abstract

This proposal adds `value is null` and `value is not null` as readable null-test forms alongside
Zeron's existing type-test syntax. They are built-in forms of `is`, not overloadable contract
operations. They require neither first-class type values nor runtime reflection and participate in
the existing flow-refinement model.

## Motivation

Zeron already supports nullable types, null checks, flow refinement, and `is Type` tests. A null
check written as an equality or identity comparison is valid, but `value is null` and
`value is not null` express the question more directly to readers. The existing `is` syntax also
provides a natural place for these forms without treating types as runtime values.

Null testing is not an algebraic operation. Modeling it as a contract overload would conflate a
language-defined type/null predicate with user-defined operations, and an operation shaped like
`is<V, T>(value: V, type: T): Boolean` would require types to be values. Neither contract-based
overloading nor first-class type values are needed for this feature.

## Goals

- Support `value is null` and `value is not null` using the existing `is` syntax family.
- Reuse the existing null-check flow facts and stable-binding restrictions.
- Preserve current `is Type` and `is not Type` behavior.
- Keep null tests built-in and independent of contract evidence and runtime reflection.

## Non-goals

- Making types first-class values or introducing reflection.
- Allowing user-defined overloads of `is`.
- Replacing or changing the semantics of `==`, `!=`, or `===`.
- Expanding flow refinement to unstable expressions, mutable globals, properties, or array slots.
- Changing existing nullability or type-test rules beyond supporting the new syntax.

## Proposal

Extend the existing type-test syntax with a dedicated null-test target:

```text
typeTest ::= comparison [ "is" [ "not" ] (Type | nullTestTarget) ]
nullTestTarget ::= "null"
```

The parser represents `null` as a special test target, not as a source type or a runtime type
value.

The forms have these meanings:

- `value is null` evaluates to `true` exactly when `value` is null.
- `value is not null` evaluates to the complementary result.
- `value is T` and `value is not T` retain their existing type-test semantics.

Null tests are built-in language operations. They do not resolve a contract member or witness, and
they do not turn the `null` token or a type into a runtime value. Implementations may lower a null
test using the same underlying comparison as an existing null check, while preserving the `is`
syntax and its flow-analysis behavior.

When the tested expression is a stable local or parameter read, the true and false paths establish
the corresponding null/non-null facts. For a nullable `T?`, `value is not null` refines the
non-null path to `T`; `value is null` refines the null path accordingly. Refinements obey the
existing control-flow joins, short-circuit rules, and invalidation on assignment. Non-stable
expressions may be tested but do not gain a refinement for a later reevaluation.

Testing a statically non-null expression with `is null` is valid and evaluates to `false`;
`is not null` evaluates to `true`. These cases do not produce diagnostics. They add no refinement
beyond the expression's already non-null static type and do not require a new unreachable-code
diagnostic.

`===` remains reference identity, and equality operators retain their existing equality semantics.
This proposal adds readable null-test syntax rather than redefining those operators.

## Compatibility and impact

This is additive source syntax. Existing type tests, null comparisons, equality, and reference
identity retain their current behavior. The parser and resolver should reuse the existing null-test
and flow-fact machinery so the new spelling does not create a second set of nullability rules.
No runtime representation, contract API, compiled-library metadata, or ABI change is expected.

## Alternatives

- **Use only `== null` or `=== null`** — already expresses null checks, but is less direct as a
  predicate and does not provide the requested `is` spelling.
- **Overload `is` through contracts** — would make a language-level type/null test depend on
  user-defined evidence and would not naturally express a type as a compile-time target.
- **Make types first-class values and define `is(value, type)`** — a much broader reflection and
  runtime type-identity feature than required for null checks.
- **Introduce a separate null-test keyword** — possible, but duplicates the predicate role already
  served by `is` and its existing type-test syntax.

## Implementation and validation

Extend parsing and resolution of `is` tests to accept the `null` token while retaining `is Type` and
`is not Type`. Verify both forms in conditions, `if` expressions, short-circuit `and`/`or`/`not`,
and guard clauses. Test true/false branch refinement for nullable stable locals and parameters,
fact invalidation after assignment, and the absence of refinement for properties, array slots, and
call results. Confirm existing equality, identity, and type-test behavior is unchanged.

## Decision

Accepted 2026-10-19. Add `is null` and `is not null` as built-in forms with a dedicated null-test
target, reuse existing stable-binding flow refinement, and treat tests of statically non-null
expressions as valid constant Boolean results without diagnostics.

Implemented 2026-10-19 with parser, resolver, and bytecode support. Tests cover runtime behavior,
nullable flow refinement, non-null static operands, and preservation of existing type-test behavior.
