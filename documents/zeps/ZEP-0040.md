## Abstract

This proposal adds conventional binary, octal, and hexadecimal prefixes for integer literals while
evaluating whether Zeron should support only these common radices or arbitrary bases.

## Motivation

Non-decimal literals make bit masks, protocol fields, flags, and low-level constants easier to read
and write. These use cases fit existing fixed-width integer types and do not require changing
arithmetic semantics.

## Goals

- Evaluate standard prefixed binary, octal, and hexadecimal integer literals.
- Define invalid-digit and overflow diagnostics consistently with decimal literals.
- Decide whether the source language needs arbitrary-base literal syntax.

## Non-goals

- Adding floating-point literals in non-decimal radices.
- Changing the types or arithmetic behavior of integer literals.
- Replacing decimal literals or adding legacy leading-zero octal syntax.

## Proposal

Support fixed conventional, case-insensitive prefixes:

```text
0b1010
0o755
0xFF
```

The prefix identifies the radix; digits are validated against it. Lowercase is the canonical
spelling, but uppercase prefix letters are accepted. An optional integer suffix such as the
existing `L` applies after the digit sequence. The leading sign remains a unary operator, not part
of the literal token.

Without a suffix, a radix-prefixed integer has the same `Int` type and signed range as an unsuffixed
decimal integer. With `L`, it has the same `Long` type and signed range as a decimal `L` literal.
Contextual types do not silently widen or reinterpret an out-of-range literal. Invalid digits and
overflow produce diagnostics. Leading-zero decimal values remain decimal; legacy leading-zero octal
syntax is not supported.

Only binary, octal, and hexadecimal prefixes are included. Arbitrary-radix source forms such as
`base#digits` are excluded; callers needing another radix can use a parsing API. Radix-prefixed
floating-point literals are also excluded. Underscore separators compose with the prefix and digit
rules as specified by [ZEP-0039](./ZEP-0039.md).

## Compatibility and impact

This adds integer literal syntax. Existing decimal literals and their types remain unchanged.
Leading-zero values must not silently change interpretation. Scanner, parser, formatter, grammar
documentation, and syntax highlighting need consistent rules.

## Alternatives

- **Support only binary, octal, and hexadecimal** — recognizable and covers common programming
  needs, but does not support specialized radices directly in source.
- **Support arbitrary radix prefixes** — more expressive, but adds uncommon syntax and additional
  lexer/parser edge cases; library parsing may serve this need.
- **Use only a parsing API** — avoids new literal syntax but is less convenient for constants and
  compile-time numeric expressions.

## Implementation and validation

The scanner supports the specified prefixes and existing `Int`/`Long` ranges. Tests cover
case-insensitive prefixes, digit boundaries, optional suffixes, invalid digits and prefixes, decimal
leading zeroes, formatter preservation, editor grammar, and compiled runtime values.

## Open questions

None for the accepted scope. Type selection and range checking match existing decimal integer
literals; arbitrary radices and floating-point radix forms are excluded.

## Decision

Accepted 2026-10-19. Add case-insensitive `0b`, `0o`, and `0x` integer prefixes, with unsuffixed
literals using the existing `Int` rules and `L` literals using the existing `Long` rules. Do not
add arbitrary-radix or radix-prefixed floating-point syntax.

Implemented 2026-10-19.
