## Abstract

This proposal evaluates unsigned fixed-width integer types, including an unsigned 64-bit type,
alongside Zeron's existing signed `Byte`, `Int`, and `Long` types. It focuses on useful ranges,
arithmetic semantics, conversions, and host interoperability.

## Motivation

Unsigned values naturally represent bit fields, byte-oriented protocols, sizes, and nonnegative
domains that use the full width of a machine word. The existing signed integer types cannot express
the full unsigned 32-bit or 64-bit range without custom wrappers or conversions.

## Goals

- Assess a coherent family of unsigned fixed-width integer types, including unsigned 32-bit and
  64-bit values.
- Specify arithmetic, comparison, bitwise, shift, overflow, and conversion behavior.
- Preserve explicit distinctions between signed and unsigned types.
- Account for Java interoperation and the compiler's JVM representation.

## Non-goals

- Replacing or changing the signed semantics of existing `Byte`, `Int`, or `Long`.
- Introducing arbitrary-precision integer types.
- Assuming unsigned values are appropriate for every quantity that is nonnegative.

## Proposal

Evaluate unsigned types matching a consistent fixed-width family, with `UInt` and `ULong` as the
minimum useful candidates and `UByte`/`UShort` as possible additional members. The design should
choose widths deliberately rather than adding isolated aliases. Existing signed types keep their
current ranges, operators, and source names; conversions between signed and unsigned types are
explicit and define behavior when the value is out of range.

The ZEP should settle:

- whether ordinary addition, subtraction, and multiplication wrap modulo \(2^n\), trap, or provide
  checked alternatives;
- whether division, remainder, comparison, and shifts use unsigned interpretation;
- how literals identify or infer an unsigned type and how radix literals interoperate with those
  rules;
- how unsigned values map to Java primitives, boxed values, arrays, and external method signatures;
- how generic code and operator contracts distinguish signed from unsigned arithmetic.

Unsigned fixed-width arithmetic has modular behavior, unlike unbounded integer arithmetic.
Operator-contract conformance must describe that behavior honestly and avoid implying that the
operation is ordinary integer arithmetic over the mathematical integers.

## Compatibility and impact

This adds source types and requires compiler, resolver, bytecode, API-index, Java-interop, standard-
library, and diagnostic support. JVM primitives have no unsigned source types, so descriptors and
operation lowering must preserve the distinction even when storage uses the same bit patterns as
signed primitives. Existing signed APIs and generated descriptors must remain unchanged.

## Alternatives

- **Use signed types and masks/conversions only** — keeps the type system smaller, but makes range
  and comparison intent less explicit and complicates common interoperation.
- **Add only `UInt` and `ULong`** — covers word-sized use cases with less surface area, but leaves
  byte-oriented and 16-bit values without corresponding unsigned types.
- **Provide unsigned wrappers in a library** — avoids adding primitive numeric types, but may incur
  allocation or complicate operator and Java interoperation behavior.
- **Treat unsigned values as an interpretation of signed values** — preserves storage but does not
  provide type safety against accidental signed operations.

## Implementation and validation

Validate boundary values at every width, signed/unsigned comparisons, arithmetic overflow,
division/remainder, shifts, explicit conversions, boxing, arrays, and Java interop. Include compile-
time diagnostics for mixed signed/unsigned operations and library-index round trips. Test operator
contracts only after their semantics are settled with [ZEP-0036](./ZEP-0036.md).

## Open questions

- Which widths should be included initially?
- Should arithmetic wrap by default, with checked operations provided separately?
- How should negative literals, literal suffixes, contextual typing, and radix prefixes select an
  unsigned type?
- Which Java interop mappings can be supported without losing the unsigned interpretation?
