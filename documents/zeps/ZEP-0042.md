## Abstract

This draft evaluated arbitrary-precision numeric support and compared separate integer and
floating-point types with a unified `BigNum`. The initial Zeron implementation choice for exact
integers and fractions is now specified by [ZEP-0071](./ZEP-0071.md): `Integer` and `Rational` are
separate exact types, while binary floating point remains `Float`.

## Motivation

Fixed-width integers cannot represent every exact integer, and binary64 floating point cannot
provide arbitrary precision for decimal or scientific calculations. Users may need exact large
integer arithmetic, predictable decimal calculations, or precision that can be selected for
numerical algorithms. The language should identify which needs justify built-in types and which are
better served by libraries.

## Goals

- Evaluate arbitrary-precision integer support.
- Compare arbitrary-precision decimal and binary floating-point semantics.
- Decide whether integer and floating values should have distinct types or share a unified `BigNum`.
- Define literal selection, mixed arithmetic, rounding, conversions, and operator behavior for any
  selected design.
- Keep arbitrary precision distinct from fixed-width unsigned support.

## Non-goals

- Committing to a particular implementation library or runtime representation.
- Changing the behavior or representation of existing `Int`, `Long`, or `Float`.
- Treating decimal floating point and arbitrary-precision binary floating point as equivalent.
- Guaranteeing constant-time arithmetic or bounded resource use for arbitrarily large values.

## Proposal

Compare at least these alternatives:

1. **Separate types:** provide an arbitrary-precision integer such as `BigInt` and, if justified,
   a distinct decimal or binary arbitrary-precision floating type. Each type has clear exactness,
   rounding, and conversion rules.
2. **Unified `BigNum`:** provide one numeric type capable of representing both integral and
   fractional values. Specify whether it uses a tagged integer/decimal representation, a single
   decimal representation, or another model; define when operations preserve exact integers and
   when they round.
3. **Integer-only initial support:** add `BigInt` first and defer arbitrary-precision floating point
   until a concrete use case and rounding model are established.
4. **Library-only support:** leave the language core unchanged and expose arbitrary-precision
   facilities through a standard or external library.

The evaluation must distinguish:

- arbitrary-precision integers, which can represent every integer exactly;
- arbitrary-precision decimal arithmetic, which can represent finite decimal fractions exactly
  but needs a precision/rounding policy for operations such as non-terminating division; and
- arbitrary-precision binary floating point, which needs a precision and rounding model for
  binary floating operations and transcendental functions.

### Initial proof-of-concept scope

The standard library now provides `zeron.numeric.Integer` and `zeron.numeric.Rational`; `Integer` uses the
general custom `n` suffix from [ZEP-0043](./ZEP-0043.md). Their exact arithmetic and contextual
literal conversions are specified by [ZEP-0071](./ZEP-0071.md). That proposal also removes the
Zeron `BigDecimal` wrapper and replaces the legacy operator model from
[ZEP-0036](./ZEP-0036.md), including its `zeron.algebra` package.

A unified `BigNum` must not leave integer-versus-fractional promotion implicit. It should specify
whether its value representation records an exact integer case, how division behaves, and whether
precision is global, per value, per operation, or supplied through a context. Separate types should
likewise define whether mixed operations are rejected or explicitly converted.

Literal syntax should be evaluated separately from the type choice. Options include explicit
suffixes, contextual typing, constructors/parsing APIs, or preserving the current default literal
types while requiring an explicit spelling for arbitrary-precision values. Large literals should be
parsed exactly before range/type validation. Digit separators and radix prefixes, if adopted, are
specified independently in [ZEP-0039](./ZEP-0039.md) and [ZEP-0040](./ZEP-0040.md).

## Compatibility and impact

Any built-in arbitrary-precision type adds compiler, runtime, standard-library, generic-bound,
operator, and compiled-library considerations. JVM object representations differ from primitive
numeric descriptors and may affect boxing, arrays, Java interoperation, and performance. Existing
fixed-width types and literal defaults must not change implicitly.

Operator behavior should align with [ZEP-0036](./ZEP-0036.md) without claiming that floating-point
operations obey exact algebraic laws. Resource use for extremely large values also needs clear
documentation; arbitrary precision is not unlimited practical capacity.

## Alternatives

- **Separate `BigInt` and floating type** — precise and explicit, but exposes multiple APIs and
  requires deliberate conversions.
- **One `BigNum` type** — offers one broad interface, but risks hiding representation, rounding,
  promotion, and performance differences between integers and fractions.
- **Only `BigInt`** — addresses exact integer overflow with comparatively simple semantics while
  deferring rounding-sensitive floating-point design.
- **Library-only implementation** — avoids new core types and compiler support, but may make common
  exact arithmetic awkward and inconsistent.
- **Rely on `Float`** — insufficient for arbitrary precision because the existing type is fixed
  binary64.

## Implementation and validation

First select motivating numeric use cases and an exactness model. For any selected type, validate
large positive and negative values, arithmetic across representation boundaries, division and
rounding behavior, conversions, literal inference, overflow/resource behavior, generic bounds,
operator dispatch, and separately compiled libraries. For floating types, include decimal
round-tripping and operations with non-terminating results; do not test an unspecified rounding
policy as though it were settled.

## Open questions

- Is arbitrary-precision integer support independently valuable enough to implement first?
- Is the floating-point need decimal arithmetic, arbitrary-precision binary floating point, or both?
- Would one `BigNum` have a well-defined and unsurprising representation and promotion model, or
  should exact integers and floating-point values remain separate types?
- How are precision and rounding selected and propagated?
- Should arbitrary-precision types be compiler-known primitives, bundled library types, or
  user-provided library types?
- What literal suffix or contextual-typing rules distinguish arbitrary-precision values?

## Decision

Draft created 2026-10-19 to compare built-in arbitrary-precision numeric designs, including
separate integer/floating types, a unified `BigNum`, integer-only support, and library-only
support. The initial proof-of-concept direction is `BigInteger` only, with `BigDecimal` and unified
`BigNum` left for later evaluation. The type model beyond that initial scope, floating-point
semantics, and literal rules remain open.
