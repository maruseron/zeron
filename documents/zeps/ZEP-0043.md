## Abstract

This proposal adds library-defined numeric literal suffixes that construct typed values from
numeric literals, such as `20i` for an `Imaginary` value. Suffixes resolve statically through
declared and imported APIs; they are not arbitrary source macros.

## Motivation

Some numeric domains have natural literal notation that is more readable than explicit constructor
calls. An imaginary-number library could offer `20i`, and a domain library could offer a typed value
such as `20m`. Supporting such notation through ordinary static library declarations would make
domain-specific literals available without hardcoding each type into the compiler.

## Goals

- Allow libraries to define custom suffixes for supported numeric literal forms.
- Construct a statically typed value without changing the meaning of unsuffixed literals.
- Make suffix lookup deterministic, import-aware, and suitable for separately compiled libraries.
- Preserve exact literal information until its target representation and range are checked.

## Non-goals

- Arbitrary compile-time execution, textual macro expansion, or user-defined lexer plugins.
- Implicit multiplication between adjacent expressions.
- Defining physical-unit dimensions, prefixes, or conversions; those are explored separately in
  [ZEP-0044](./ZEP-0044.md).
- Replacing built-in literal suffixes such as the existing `L`.

## Proposal

Treat an identifier immediately adjacent to a numeric literal as a candidate suffix. For example:

```text
20i
3.5m
```

The adjacency is significant: `20m` may be a suffixed literal, while `20 m` is not. A suffixed
literal is a single expression that invokes the constructor associated with that suffix; it is
conceptually similar to applying a statically resolved `i` or `m` constructor to the literal value.
It does not introduce general juxtaposition multiplication.

A library declares a suffix and associates it with typed construction behavior. The declaration is
owned by its class, and its suffix name is an unquoted identifier. The association must be exported
through the library API metadata and selected through normal static name resolution. Each suffix
declaration is a separately importable symbol; only an explicit named suffix import makes it
available in a source unit:

```zeron
import suffix zeron.units.Meter.m as mm;
```

The alias, when present, is the spelling recognized in that source unit. Importing the owning type,
wildcard imports, and automatic imports do not activate its suffixes. Unknown suffixes and
conflicting explicitly imported suffix definitions produce diagnostics; there is no global
registry or runtime suffix lookup.

The registration mechanism must associate each supported numeric-literal category with an
ordinary, statically callable factory. For example, a `Meter` class might expose separate integer
and decimal constructors:

```zeron
public class Meter {
    value: Float;

    public constructor ofInt(value: Int) = Meter.new(value.toFloat());
    public constructor ofFloat(value: Float) = Meter.new(value);
}
```

The declaration makes it explicit which factory handles each literal category. The keyword is
`suffix`, used contextually in a suffix-declaration position rather than reserved as a keyword
everywhere. Outside that position, `suffix` remains an ordinary identifier. Labels such as
`integer`, `decimal`, and `string` are likewise context-sensitive when used in suffix-declaration
syntax: they are recognized as keywords only in that declaration context and remain ordinary
identifiers elsewhere. `integer` identifies decimal and radix-prefixed integer literal forms;
`decimal` identifies decimal-point forms. `string` selects a lossless textual factory input: the
factory receives the exact numeric token spelling, excluding the suffix and preserving radix
prefixes and digit separators. It is an input representation, not a string-literal category, and
does not by itself make additional numeric categories valid. Each declaration explicitly lists
which numeric categories it accepts, with at most one factory per category. A category entry may
use the `string` input marker to request the exact spelling instead of a converted numeric argument.
Factories are public unary named constructors. Without `string`, integer factories accept `Int` or
`Long`, while decimal factories accept `Float`; with `string`, either category accepts `String`.
Suffix declarations on generic classes are not supported. For example, the integer-only
`BigInteger` suffix can use:

```zeron
public class BigInteger {
    suffix n {
        integer: string fromLiteralText;
    }
}
```

The class-owned form for a type that accepts converted numeric arguments is:

```zeron
public class Meter {
    // constructors and members
    suffix m {
        integer: ofInt;
        decimal: ofFloat;
    }
}
```

Explicit syntax can be inspected directly by compiler phases and validated with ordinary syntax
and type rules. Suffix identifiers are case-sensitive, matching ordinary Zeron identifiers.

Ordinary contract conformance alone does not register a compile-time suffix. An instance property
such as `suffix: String` is available only after constructing a value, which is too late for
resolving the literal. A contract-based approach would need a new static associated constant or
other compile-time metadata facility; evaluating arbitrary methods or properties during
compilation is outside this proposal.

The compiler preserves the literal's numeric category, radix, and exact magnitude while resolving
the suffix. For the `string` input representation, it also preserves the exact token spelling.
Range checking occurs before conversion to a bounded input type; the compiler must not silently
round or wrap a literal to make it fit. A leading sign remains a unary operator, so it is not part
of the literal text supplied to a factory. Exponent notation is outside this proposal's initial
scope; its use with unit literals is explored in [ZEP-0044](./ZEP-0044.md).

Built-in suffixes retain precedence and cannot be shadowed by a library declaration. In
particular, the existing `L` suffix remains built in; custom suffixes apply only to otherwise
unsuffixed numeric tokens and cannot be composed with built-in suffixes. Integer suffix categories
compose with radix prefixes and digit separators according to [ZEP-0039](./ZEP-0039.md) and
[ZEP-0040](./ZEP-0040.md). A contiguous identifier after a number is treated as a suffix
candidate; if it is not an available suffix, the compiler reports an unknown or unavailable suffix
diagnostic. Whitespace prevents suffix attachment, so `20 m` is not a suffixed literal. Any
resulting call follows ordinary static dispatch; constant folding is an optimization, not a
semantic requirement.

### Initial proof-of-concept scope

The first end-to-end consumer should be the ordinary `BigInteger` standard-library type from
[ZEP-0042](./ZEP-0042.md), using a library-declared suffix that the client explicitly imports. The
suffix mechanism must remain general: the compiler should resolve a visible declaration and invoke
its typed factory without special-casing `BigInteger` or the suffix's chosen spelling. An
integer-only first slice is sufficient to validate exact large-value construction; support for
decimal literal categories can be designed separately.

The initial consumer supports integer literal forms only. Its suffix declaration uses the
`string` input representation so the factory receives the exact source spelling and constructs the
`BigInteger` without an intermediate `Int` or `Long` range check. Decimal literal support and
additional consumers can follow separately.

## Compatibility and impact

This adds expression syntax and library metadata for suffix declarations. Existing unsuffixed
numeric literals and built-in suffixes retain their current meanings. Scanner, parser, resolver,
formatter, the authoritative grammar document, the VS Code TextMate grammar, the ANSI syntax
highlighter, and library-index validation must share consistent adjacency and resolution rules.
Because `suffix` is context-sensitive, the parser and both syntax highlighters must recognize its
declaration position, and `integer`, `decimal`, and `string` must be recognized only as labels
within the declaration; ordinary uses of these words remain identifiers. The import parser and
library index must support explicit imports of class-owned suffixes and optional aliases.
Conflicting named suffix imports are diagnosed. Importing an ordinary type or namespace must not
silently change which numeric suffixes are recognized.

## Alternatives

- **Use explicit constructors such as `i(20)`** — simple and unambiguous, but less compact for
  conventional numeric notation.
- **Hardcode a fixed set of suffixes** — straightforward for built-in types, but does not serve
  third-party domains without compiler changes.
- **Use arbitrary source macros** — very flexible, but adds compile-time execution, hygiene, and
  separate-compilation complexity beyond literal construction.
- **Interpret any adjacent identifier as multiplication** — concise, but makes ordinary name
  adjacency ambiguous and would introduce implicit multiplication.
- **Activate suffixes through ordinary type, wildcard, or automatic imports** — convenient, but
  makes numeric syntax less visible and gives less control over suffix collisions.
- **Register suffixes only through a `Suffixed` instance contract** — appears to reuse the contract
  system, but a runtime instance value cannot supply compile-time registration metadata. An
  associated-constant or compile-time-evaluation model would be additional language machinery.

## Implementation and validation

Update the scanner, parser, resolver, formatter, authoritative grammar document, VS Code TextMate
grammar, ANSI syntax highlighter, and library index to support class-owned suffix declarations,
explicit named suffix imports, and aliases. Test that `suffix` and the `integer`, `decimal`, and
`string` labels are recognized contextually and remain ordinary identifiers elsewhere. Test that
only explicit suffix imports activate declarations; importing the owning type, a namespace
wildcard, or relying on automatic imports must not. Also test category selection, exact text
preservation, import visibility, aliases, collisions, built-in suffix precedence, adjacency,
unknown suffix diagnostics, digit separators, and radix literals. Verify compiled-library
round-tripping and ensure custom suffixes do not alter unsuffixed literal typing or expression
evaluation order. The `BigInteger` proof of concept must cover values beyond `Long` without
premature range rejection.

## Resolved design decisions

- Declarations are class-owned and use an unquoted, case-sensitive identifier as the suffix name.
- Each suffix is enabled only by an explicit named import of the form
  `import suffix package.Type.name [as alias];`. The alias is the spelling accepted at use sites.
- `integer` covers decimal and radix-prefixed integer tokens; `decimal` covers decimal-point
  tokens. A category entry marked `string` passes the exact source spelling, excluding the
  suffix, as the factory input.
- Each category maps to one public unary named constructor with a category-compatible parameter;
  generic owner classes cannot declare suffixes.
- Built-in `L` remains reserved and cannot be shadowed or composed with a custom suffix. Exponent
  notation is deferred by this proposal; unit-literal support is explored in ZEP-0044. A contiguous
  unknown suffix gets a dedicated diagnostic; whitespace prevents suffix attachment.
- Suffix construction and operator capabilities are separate concerns. Heterogeneous operator
  results remain in [ZEP-0045](./ZEP-0045.md).

## Decision

Accepted and implemented 2026-10-19. The mechanism supports class-owned suffix declarations,
explicit named imports and aliases, category-specific public constructor factories, and lossless
string input without special-casing a type name or suffix spelling. The bundled
`zeron.math.BigInteger` proof of concept parses large decimal and radix-prefixed values through its
ordinary `integer: string` factory and implements `Addition` and `Mult`. `suffix`, `integer`,
`decimal`, and `string` are context-sensitive in their declaration positions. Shipped in 0.5.0.
