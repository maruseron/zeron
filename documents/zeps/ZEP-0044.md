## Abstract

This proposal evaluates typed unit literals such as `20m` and `20kg`, including declarative unit
scales and dimensional behavior. It explores whether scaled units can be expressed as exact
transformations such as `20kg` corresponding to `20 * 1000 * g`, without using arbitrary source
macro expansion.

## Motivation

Physical quantities are easier to read when values carry units at their point of construction.
Typed unit literals can prevent accidental mixing of dimensions and allow third-party libraries to
define domain-specific units. Scaled units such as kilograms and grams also need predictable
conversion behavior without silently losing precision or overflowing an intermediate value.

## Goals

- Evaluate unit suffixes built on the custom literal-suffix mechanism in [ZEP-0043](./ZEP-0043.md).
- Evaluate decimal scientific notation and exponent forms for unit literals.
- Represent a quantity together with its dimension and unit or scale.
- Define how scaled units and conversions preserve exactness and report range or precision loss.
- Keep unit declarations and suffixes available to third-party libraries.

## Non-goals

- Adding built-in physical quantities or selecting a mandatory standard unit package.
- Executing arbitrary user-defined compile-time code or rewriting source text.
- Promising that every unit conversion is exact or representable in every numeric type.
- Defining affine units such as temperature offsets in the initial design.

## Proposal

Evaluate a statically typed quantity model in which a numeric literal suffix constructs a quantity
associated with a unit and dimension:

```text
20m
20kg
```

### Scientific and exponent notation

The proposal also evaluates decimal scientific notation, particularly when a unit suffix follows
the exponent:

```text
1e3m
1.25e-3s
6.022E23mol
```

These forms represent a base-10 significand multiplied by ten raised to a signed integer exponent.
The exponent marker and exponent belong to the numeric literal; the unit suffix follows them.
Thus, `1.25e-3s` constructs a time quantity from the value represented by `1.25 × 10^-3`, while
`-1.25e-3s` applies unary negation to that suffixed literal. Exponent forms should be treated as
decimal forms for suffix dispatch even when their mathematical value is integral.

The notation must not force early conversion through binary floating point when that would lose
precision before applying a unit scale. The implementation should preserve the significand and
exponent, or an equivalent exact decimal representation, until a target numeric representation
requires conversion. The proposal focuses on decimal exponents; non-decimal floating-point forms
remain excluded by [ZEP-0040](./ZEP-0040.md). Whether scientific notation is available to all
decimal literals or only in contexts such as suffixed unit literals remains to be decided.

For example, a library could define `g` as a mass unit and `kg` as a scaled unit whose exact ratio
to `g` is 1000. Semantically, `20kg` then represents the same quantity as `20 * 1000 * g`.
This equivalence should be implemented as unit-aware construction or conversion, not as textual
macro expansion. The implementation may retain the original magnitude and scale instead of
eagerly multiplying, avoiding accidental overflow or rounding before a conversion is needed.

The design should compare declarative unit definitions with explicit suffix aliases. A declarative
scaled unit may specify an exact rational scale relative to another unit, while suffix aliases map
directly to a constructor. If metric prefixes are supported, their composition with unit symbols
must be explicit and deterministic; the compiler must not guess that arbitrary identifier prefixes
are unit multipliers.

The quantity representation and operation rules remain to be settled. Candidate models include a
quantity carrying a numeric representation and unit scale, or a type indexed by a dimension with a
canonical representation. The design must address:

- whether addition and comparison allow different units of the same dimension by converting them;
- how multiplication and division combine dimensions;
- what result representation and display unit are chosen after arithmetic;
- whether exact rational scales are preserved until an explicit conversion;
- how conversion behaves when the target numeric representation cannot express the result.

The model should support library-defined dimensions and units without requiring compiler knowledge
of each unit name. Suffix visibility and ambiguity follow the static import and resolution rules
specified by ZEP-0043.

## Compatibility and impact

This adds library-level types and literal-suffix metadata, with possible compiler support for
declaring and validating scaled-unit relationships, as well as decimal exponent syntax. Separate
compilation must preserve dimension and scale information required to type-check client
expressions. Numeric conversions, operator resolution, and display may interact with
[ZEP-0036](./ZEP-0036.md), but unit arithmetic must not silently change existing primitive
arithmetic. Scanner, parser, formatter, grammar documentation, and syntax highlighting must agree
on exponent boundaries, suffix adjacency, and invalid forms.

## Alternatives

- **Represent units only with explicit constructors and conversion functions** — avoids new literal
  or compiler support, but is more verbose and may leave dimensional correctness to runtime APIs.
- **Expand unit literals to source expressions** — appears simple, but risks intermediate overflow,
  rounding, capture/name-resolution problems, and dependence on arbitrary compile-time expansion.
- **Store only a canonical base-unit value** — simplifies comparisons and arithmetic, but may force
  rounding or overflow at construction and lose the user's chosen unit for display.
- **Keep magnitude and scale as a quantity** — can preserve exact conversions and original units,
  but requires defined arithmetic and normalization behavior.

## Implementation and validation

First specify unit declaration metadata, dimension identity, scale representation, and quantity
arithmetic. Test equivalent values expressed in different units, exact and inexact conversions,
overflow boundaries, mixed-unit addition and comparison, compound dimensions, suffix visibility
and ambiguity, compiled-library round trips, and display stability. Include scientific notation
with positive and negative exponents, exponent/suffix adjacency, malformed and out-of-range
exponents, separator placement in significands and exponents, and exactness when applying unit
scales. Include a case where eager scale multiplication would overflow although the represented
quantity itself is valid.

## Open questions

- Should a scaled unit be declared as an explicit suffix alias or as a rational multiple of another
  unit, or should both be available?
- Should decimal scientific notation be available for all decimal literals or only in suffixed
  contexts such as unit literals?
- What exact exponent grammar is supported, including `e`/`E`, an optional exponent sign, decimal
  point forms, and digit separators?
- Which numeric category and suffix rules apply to exponent forms, and what exponent range or
  resource limits are required?
- Should exponent forms preserve an exact decimal significand and scale until conversion, or use
  the language's binary floating-point representation?
- Should metric prefixes compose automatically, or should each accepted prefixed unit be declared
  explicitly?
- What type-level dimension representation can be expressed and compiled efficiently?
- When should quantities normalize to a base unit, and how is the preferred display unit retained?
- Which conversions should be exact, checked, or rounding, and how is rounding requested?
- Should the initial scope support only multiplicative scale conversions, leaving offset units for
  a later design?
