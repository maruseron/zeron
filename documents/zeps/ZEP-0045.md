# ZEP-0045: Heterogeneous Operator Signatures

## Abstract

Explore extending contract-based operator overloading to support different left operand, right
operand, and result types. This would allow operations such as adding a `Duration` to an `Instant`
or subtracting one `Instant` from another without requiring mixed-type promotion or weakening the
type guarantees of the existing operator contracts. This proposal records a possible future
direction; it does not add operators to any standard-library types.

## Motivation

[ZEP-0036](./ZEP-0036.md) deliberately limits its binary operators to operands and results of the
same type. Its `Add<T>` and `Mult<T>` contracts model operations within one carrier type, and
subtraction is expressed by negating a same-typed right operand before addition.

Useful operations do not always have that shape. Temporal arithmetic commonly has signatures such
as:

```text
Instant + Duration -> Instant
Instant - Duration -> Instant
Instant - Instant  -> Duration
```

The current contract signatures cannot express these relationships. The standard library
therefore uses named methods for temporal arithmetic. This is a reasonable API in its own right,
but future operator support could make these operations more natural while retaining explicit
static evidence and precise result types.

## Goals

- Explore a contract-based model for operators whose operand and result types may differ.
- Preserve static type checking, explicit generic requirements, and static contract-evidence
  dispatch.
- Define how overload selection, inference, diagnostics, and existing intrinsic operators interact.
- Consider real standard-library use cases, especially temporal arithmetic, without committing to
  add operators to those types.

## Non-goals

- Changing the same-type operator behavior established by ZEP-0036.
- Adding operator overloads to `Instant`, `Duration`, collections, or other types as part of this
  proposal.
- Introducing implicit numeric conversions, mixed-type promotion, or runtime overload dispatch.
- Deciding overflow behavior for `Duration` or other arithmetic APIs.

## Proposal

Investigate a contract shape in which the left operand's evidence declares the right operand and
result types. For example, a future contract family could conceptually express:

```text
Add<Right, Result> {
    add(other: Right): Result;
}
```

Under such a model, `Instant` could provide evidence for adding a `Duration` and returning an
`Instant`; subtraction could have separate evidence for `Instant - Duration` and `Instant -
Instant`, with the latter returning `Duration`. These are illustrative signatures, not settled
contract names or syntax.

Operator expressions should continue to resolve from the static types of their operands and
explicitly available contract evidence. Generic functions should declare the required evidence in
their bounds; the compiler should not silently infer hidden operator requirements. The model should
not introduce implicit conversions, and ambiguity should be diagnosed statically.

The design should account for the existing intrinsic and special cases. Built-in numeric
operations must retain their current behavior and precedence. `String + T` must retain its
`Display<T>` behavior. Existing same-type contracts and generic code must remain valid, with any
migration or compatibility requirements identified before implementation.

Temporal arithmetic is a motivating example, not a prescribed semantic decision. In particular,
`Duration` currently returns `Option<Duration>` from checked addition, subtraction, negation, and
scalar multiplication to represent overflow. Heterogeneous signatures can describe different
operand and result types, but do not by themselves settle whether an operator returns an `Option`,
uses another checked-operation contract, or has different overflow semantics.

## Compatibility and impact

An implementation would affect operator resolution, contract bounds and evidence, expression
typing, and compiler emission. The public standard-library API index may also change when new
contracts or witnesses are added. Existing intrinsic operators, string concatenation, and
same-type contract-based operators must remain source-compatible unless a separately reviewed
breaking change is explicitly approved.

This draft proposes no immediate compatibility changes and no release target.

## Alternatives

- Keep mixed-type operations as named methods — preserves clear signatures and avoids expanding
  operator resolution, but leaves no path for generic contract-based heterogeneous operators.
- Add compiler-special-cased operators for temporal types — could address a narrow use case, but
  would not provide a reusable model for user-defined types.
- Use implicit conversions or numeric promotion — can make expressions concise, but introduces
  broader questions about conversion selection, precision, and ambiguity that this proposal does
  not intend to take on.

## Implementation and validation

If the design is accepted, implementation should begin with a narrowly scoped operator-contract
prototype and compile-time tests for distinct left, right, and result types. It should cover
explicit generic bounds, evidence forwarding, missing and ambiguous evidence, interaction with
intrinsics and `String + T`, and separately compiled libraries. Standard-library temporal
operators should be considered only after the type-system and overflow questions are settled.

## Open questions

- Should the contract be declared on the left operand and parameterized by the right operand and
  result, or should it use a different evidence model?
- Should operators with the same token but different operand pairs use separate contracts, or may
  one contract provide multiple overloads?
- How should type inference determine generic right-operand and result types, and how should
  overlapping evidence be rejected or disambiguated?
- Should heterogeneous signatures apply only to binary operators, or should the design cover
  additional operator forms?
- What consistency guarantees are needed for intrinsic operators, overload precedence, and chained
  expressions?
- Which types, if any, should receive heterogeneous operators first? Temporal arithmetic is a
  candidate, but its checked-overflow behavior needs a separate decision.
