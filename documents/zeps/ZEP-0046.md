## Abstract

Define a constrained, statically checked widening mechanism for binary operator expressions. A
destination type explicitly declares accepted source types, allowing a `Complex` type to absorb a
`Float` operand so that `6.0 + 7.0i` can be evaluated without an explicit conversion. Exact operator
matches retain priority, and widening is limited to a single declared, value-preserving embedding.

## Motivation

Custom numeric types can express their own literal syntax through [ZEP-0043](./ZEP-0043.md), and
operator contracts can provide statically dispatched arithmetic. However, an expression combining
a built-in numeric value with a custom numeric value still needs a deliberate rule for the
different operand types. For complex arithmetic, converting a real value to a complex value with
zero imaginary component is mathematically natural:

```zeron
let value = 6.0 + 7.0i;
```

The left operand is a `Float`, while the suffixed right operand is hypothetically a `Complex`.
Requiring an explicit conversion may make common numeric expressions cumbersome. Silently
converting values without a bounded, predictable model, however, risks ambiguity, unexpected
precision loss, and surprising changes to overload resolution.

This problem is related to but distinct from [ZEP-0045](./ZEP-0045.md). A heterogeneous operator
could directly define `Float + Complex -> Complex`; implicit widening could instead convert the
`Float` operand to `Complex` and then use a same-type operator. The design should establish whether
these are alternatives, complementary mechanisms, or whether only one should be supported.

## Goals

- Allow destination types to declare which source types they can safely absorb in operator
  expressions.
- Preserve static type checking, deterministic overload selection, and understandable diagnostics.
- Define interactions with operator contracts, built-in numeric operations, literals, and generic
  code.
- Distinguish value-preserving widening from arbitrary implicit conversions and lossy numeric
  coercions.

## Non-goals

- Introducing unrestricted implicit conversions between arbitrary user-defined types.
- Defining the complete `Complex` API or its arithmetic semantics.
- Committing to implementation or defining the complete `Complex` API.
- Changing existing numeric literal types or conversion behavior as part of this exploration.
- Settling arbitrary-precision decimal or binary floating-point precision policies from
  [ZEP-0042](./ZEP-0042.md).

## Proposal

Use a destination-owned widening constructor to identify each accepted source type. A hypothetical
`Complex` type may mark a constructor from `Float` as widening, embedding the value with a zero
imaginary component:

```zeron
public class Complex {
    public widening constructor fromFloat(value: Float) =
        Complex.new(value, 0.0);
}
```

The widening constructor is statically available from its destination type and is exported for
separately compiled libraries. It may also be called explicitly like an ordinary constructor; the
`widening` marker additionally makes it eligible for operator resolution.

Resolve a binary operator in this order:

1. Preserve existing built-in intrinsic behavior and exact operator matches, including an exact
   heterogeneous signature if [ZEP-0045](./ZEP-0045.md) is implemented.
2. If there is no exact match, consider one-step widening only when one operand already has the
   destination type and that type declares a conversion from the other operand's type. The
   destination type must provide the applicable operator.
3. Select a unique candidate. If multiple destination types are applicable, report ambiguity;
   never select by declaration order, conversion cost, or runtime value.

Only one operand may widen in this initial model. Both operands are not converted to a third common
type. Chaining is prohibited; a type that needs to accept a source must declare a direct conversion.
Widening applies only during binary operator resolution, not to assignments, arguments, returns, or
other expression contexts. An ordinary explicit conversion remains available through the declared
factory.

For example, a hypothetical `Complex` type could accept a `Float` value:

```zeron
let value = 6.0 + 7.0i;
let reverse = 7.0i + 6.0;
```

The custom suffix resolves `7.0i` to `Complex` before operator resolution. For `Float + Complex`,
the right operand's type is the destination candidate; for `Complex + Float`, the left operand's
type is the destination candidate. No commutativity or other algebraic law is inferred.

A widening declaration must describe a total, injective, documented value-preserving embedding.
The representation may change, as with embedding a `Float` as the real component of a `Complex`,
but the conversion must not round, overflow, or fail for values of its declared source type.
Ordinary `Int` to `Float` is not a widening if it cannot preserve every `Int` value.

The initial validation scope is the hypothetical `Float`-to-`Complex` embedding for `+` in both
operand orders. It adds no built-in numeric promotions. Unsuffixed and custom-suffixed literals
keep their current typing; widening applies only after the literal has resolved to its ordinary
type. Generic function bodies gain no hidden widening requirements: generic operators remain
exact-bound only until an explicit generic-bound model is designed.

## Compatibility and impact

This adds source expressions that may resolve where they previously failed. Existing intrinsic
behavior and exact matches retain precedence. Ambiguous, missing, or invalid conversions must
produce compile-time diagnostics; the compiler must not choose a path based on runtime values.
Generic functions gain no implicit requirements, and built-in arithmetic and literal typing remain
unchanged.

This draft proposes no immediate compatibility changes and has no release target.

## Alternatives

- Keep conversions explicit — maximizes visibility and predictability, but leaves common numeric
  combinations more verbose.
- Use heterogeneous operator signatures as explored in [ZEP-0045](./ZEP-0045.md) — directly
  models mixed operands and results without converting values, but may require separate evidence
  for each operand pairing.
- Add compiler-defined numeric promotion rules — familiar from some languages, but risks embedding
  a fixed numeric hierarchy and special cases in the compiler.
- Allow arbitrary implicit conversions — flexible, but makes overload resolution, ambiguity, and
  accidental lossy conversion difficult to control.

## Implementation and validation

Begin with compile-time tests for a small numeric model containing `Float` and a hypothetical
`Complex` type. Verify `Float + Complex` and `Complex + Float`, exact-match precedence, missing and
ambiguous destination declarations, and rejection of chained widening and lossy or partial
conversions. Test that generic functions remain exact-bound only, literals retain their types,
built-in intrinsic behavior is unchanged, and widening declarations work through separately
compiled libraries.

## Open questions

No unresolved semantic questions are currently identified. The exact grammar and validation rules
for the `widening` constructor marker must be specified during implementation design.
