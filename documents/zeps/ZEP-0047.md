# ZEP-0047: Java Type and Array Mapping Semantics

## Abstract

Define a deliberate, documented mapping between JVM primitive, boxed, reference, and array types
and Zeron types. Specify conversion direction, nullability, mutability, and array ownership so
resolver and compiler behavior is predictable and usable by standard-library and application
integrations.

## Motivation

Java interop currently supports a small set of descriptors, including Java `int`, `long`, `byte`,
`double`, `boolean`, `void`, `String`, `byte[]`, `Object`, and `Object[]`. Other references receive
mutable nullable views, while several primitive and typed-array descriptors are rejected. The
details are spread across type mapping, call resolution, array adaptation, and emission. This makes
it difficult to know which Java APIs can be called safely and encourages adapter code when a value
cannot cross the boundary directly.

The mapping is not always symmetric. For example, Java `float` can be widened to Zeron `Float`
(represented as a JVM `double`), while converting a Zeron `Float` back to Java `float` loses
precision. Java `char` is a UTF-16 code unit, whereas Zeron `Char` represents a Unicode scalar.
Array conversion also needs an explicit aliasing and mutation policy.

## Goals

- Publish one authoritative mapping table for Java primitive, boxed, and reference values.
- Specify argument, result, field, constructor, and varargs conversion behavior where they differ.
- Define nullability and mutability for mapped references.
- Define supported Java array shapes and the ownership, copying, aliasing, and mutation behavior at
  each boundary.
- Require explicit diagnostics for unsupported or lossy conversions rather than guessing.
- Keep mapping semantics consistent across direct interop, external-class facades, and typed
  compiler bindings.

## Non-goals

- Supporting generic Java type signatures; that is covered by [ZEP-0048](./ZEP-0048.md).
- Defining Java checked-exception mapping to Zeron effects; that is covered by
  [ZEP-0049](./ZEP-0049.md).
- Adding arbitrary implicit conversions between unrelated Java and Zeron types.
- Changing Zeron's own array invariance or `Char` scalar semantics.

## Proposal

Create an explicit descriptor mapping and conversion policy for each supported Java type category:
primitive values, boxed primitives, `String`, `Object`, other class/interface references, and arrays.
For every supported mapping, specify whether it is valid for parameters, results, fields, constructors,
and expanded varargs, and whether conversion is exact, widening, copying, or unsupported.

Array mappings must distinguish at least primitive arrays, reference arrays, and multidimensional
arrays. The design must state when a Zeron array is copied, when Java and Zeron share storage, how
Java-side writes interact with Zeron's invariant element types, and whether callers can pass an
already-packed Java array. Unsupported descriptors must produce a stable resolution diagnostic.

The mapping table and conversion rules should be implemented in shared interop code rather than
being inferred separately by resolver and emitter modules. Existing supported signatures remain
valid unless an explicit compatibility decision says otherwise.

### Initial mapping scope

The initial mapping table preserves the existing scalar mappings and adds only the directional
Java `float` read described below. Java `void` maps to `Unit`; Java `boolean`, `byte`, `int`, `long`,
and `double` map to `Boolean`, `Byte`, `Int`, `Long`, and `Float`. Java `float` maps to Zeron
`Float` only for method results and field reads, where conversion to Zeron's JVM `double`
representation is exact. Java `float` parameters, constructor arguments, and expanded varargs are
rejected because they would narrow a Zeron `Float`. Java `short` and `char` remain unsupported.

The currently supported boxed mappings remain nullable: Java `Integer`, `Long`, `Double`, and
`Boolean` map to the corresponding nullable Zeron scalar. Other boxed wrappers, including `Byte`,
`Float`, `Short`, and `Character`, remain unsupported in this slice. Java `String` maps to nullable
`String`, `Object` to nullable `Any`, and other supported non-generic class/interface references to
nullable mutable views. Java constructors produce non-null mutable views.

Unannotated Java reference and array parameters/results map as nullable; constructors are
non-null. An external-class facade may state a stronger non-null contract, but a non-null Java
result must be checked at runtime before it is exposed as non-null in Zeron.

Array conversion should copy the array container across the Java/Zeron boundary rather than promise
shared identity or aliasing. This preserves Zeron's invariant array guarantees when Java code
mutates an argument. The policy does not imply deep-copying objects stored in reference arrays.
The first implementation slice should preserve Java `byte[]` / Zeron `ByteArray` as the direct
representation, especially for I/O buffers. At Java reference boundaries, `byte[]` maps to
nullable `ByteArray`. Provide explicit, copying conversions between non-null `ByteArray` and
non-null `Array<Byte>` for APIs that prefer a general array. The standard library exposes these as
`zeron.io.byteArrayToArray` and `zeron.io.arrayToByteArray`. Nullable `Array<Byte?>` elements cannot
be represented by Java's primitive `byte[]` and are rejected.

The slice should add one-dimensional `int[]`, `long[]`, `double[]`, and `boolean[]` mappings to the
corresponding nullable Zeron arrays (`Array<Int>?`, `Array<Long>?`, `Array<Float>?`, and
`Array<Boolean>?`). These are copied on both arguments and results. The existing `Object[]` mapping
to nullable `Array<Any?>` also copies the container in both directions; its elements remain shared.
The mappings apply to method and constructor calls and expanded varargs, but not to Java array
fields. Passing an already-packed array to a Java varargs method remains unsupported.

Java `float[]`, `short[]`, `char[]`, typed reference arrays other than `Object[]`, and
multidimensional arrays remain unsupported in this slice. Typed reference-array covariance and
runtime element checks are deferred with those array shapes.

## Compatibility and impact

Clarifying or expanding mappings may make previously rejected Java calls available. Any change to
nullability, mutability, numeric precision, array copying, or aliasing can affect source typing and
runtime behavior. The proposal therefore requires behavior tests at each interop entry point and
explicit compatibility notes for any existing mapping whose semantics change.

## Alternatives

- Keep mappings implicit and add descriptors only when needed — minimizes upfront design but
  continues to produce inconsistent edge cases and adapter-heavy library APIs.
- Map every Java type directly to a superficially similar Zeron type — simpler to describe, but can
  lose precision or confuse Java UTF-16 code units with Unicode scalar values.
- Expose all Java arrays as opaque handles — preserves identity but weakens ordinary Zeron array
  usability and requires separate operations for common collection behavior.

## Implementation and validation

1. Inventory the current mappings and every conversion site in resolution, compilation, and facade
   validation.
2. Agree on the mapping table and array ownership rules before enabling new descriptors.
3. Implement the listed scalar and one-dimensional array mappings in shared conversion helpers,
   including runtime checks for explicitly non-null facade results and copying conversions between
   `ByteArray` and non-null `Array<Byte>`.
4. Test parameters and results, copying and mutation isolation, null handling where applicable,
   varargs interactions, rejected conversions, and separately compiled libraries.
5. Keep existing standard-library integrations passing, especially the networking API from
   [ZEP-0026](./ZEP-0026.md).

## Deferred scope

- Boxed `Byte`, `Float`, `Short`, and `Character` mappings.
- Java `float` parameters and all narrowing conversions.
- Java array fields, already-packed varargs arrays, typed reference arrays, and multidimensional
  arrays.
- Reference-array covariance and runtime element-check policy; decide these when typed reference
  arrays are proposed.

## Decision

Accepted on 2026-10-20. The mapping, conversion direction, nullability, and first-slice boundaries
are approved for implementation; deferred array and wrapper cases remain outside this scope.

## Implementation status

Implemented. Java `float` results widen to Zeron `Float`; Java primitive arrays and `Object[]` are
copied at method, constructor, expanded-varargs, and registered-binding boundaries. `ByteArray`
remains the direct `byte[]` representation, with explicit copying conversions in `zeron.io`.
Non-null reference results declared by external facades are checked at runtime.
