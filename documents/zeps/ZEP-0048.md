## Abstract

Define how Java generic classes, methods, bounds, and generic results can participate in Zeron
interop while preserving compile-time type safety and predictable JVM erasure behavior.

## Motivation

Java generic interoperability is implemented for supported class, method, and constructor
signatures. Explicitly imported generic classes and interfaces support class-level signatures and
wildcard projections; generic methods and constructors use inferred or explicit type arguments and
emit calls with erased JVM descriptors. Raw types, generic arrays, unsupported bounds/signatures,
and generic `throws` type variables remain unsupported.

## Goals

- Complete and document class-level generic signature behavior, including supported type-variable
  bounds and nested parameterized member types.
- Specify Java method- and constructor-level type parameters and their interaction with class-level
  parameters.
- Reuse Zeron's existing generic-call inference and explicit type-argument rules for Java generic
  callables.
- Define how erasure, bridge methods, wildcards, and raw types affect validation and invocation.
- Reuse the mapping and array rules from [ZEP-0047](./ZEP-0047.md).

## Non-goals

- Changing Zeron's generic type system independently of Java interop.
- Providing runtime reification where Java exposes only erased types.
- Supporting raw Java generic types or generic arrays in this proposal; raw types are rejected, and
  generic arrays are deferred to follow-up work under [ZEP-0047](./ZEP-0047.md).
- Supporting reflection or annotation processing as a substitute for class-file metadata.
- Enabling callbacks or SAM conversion; these remain in [ZEP-0050](./ZEP-0050.md).

## Proposal

Read class-file generic signatures as source-level type information for validation, never as a
replacement for the erased JVM descriptor. The class-level owner and member-signature foundation
implemented with ZEP-0052 remains the first layer: substitute the imported owner's type arguments,
then resolve member and method-level types. Extend that model to method- and constructor-level
type parameters on both generic and non-generic owners.

For Java generic methods and constructors, use the existing Zeron generic-call model. Seed
substitutions from explicit type arguments when present, infer remaining variables from the
receiver and actual arguments, and resolve callback arguments using the existing expected-function
type rules. Check every inferred or explicit argument against supported bounds. Do not infer a type
parameter solely from the expected result type; if a parameter remains unresolved, require an
explicit type argument using the existing generic-call syntax, such as `receiver.method<T>(...)`.
When the owner is generic, substitute its class parameters before solving method parameters.

Generic applicability is determined from the supported signatures and inferred substitutions before
the existing overload-selection rules choose a member. Ambiguous candidates remain errors. The
selected declaration retains its exact erased descriptor for invocation; the erased descriptor alone
must not be used as the source-level result type. Generic results erased to `Object` are adapted to
their resolved static result type after invocation.

Support exact and projected generic arguments recursively in nested parameterized class and interface
types, using the wildcard mapping settled by ZEP-0052: `? extends U` maps to `out U`, `? super L`
maps to `in L`, and unbounded `?` maps to `out Any?`. Treat Java `Object` as the unbounded top
bound. Accept other type-variable bounds only when they can be represented and checked by Zeron's
existing bound model; reject unsupported class or intersection bounds and other unrepresentable
signature forms with a diagnostic rather than erasing them to `Any?`.

Raw Java generic types remain unsupported and are rejected; no implicit unchecked/raw view is
introduced. Generic arrays, including arrays whose component type is parameterized or a type
variable, are deferred to follow-up work under ZEP-0047. This does not change the ordinary Java
array mappings already defined there.

Bridge methods are compiler-generated implementation details, not additional source overloads.
When a non-bridge generic declaration is available, use its generic signature for source checking and
its exact erased descriptor for invocation; do not expose its bridge as a separate candidate.
Unsupported or inconsistent signature metadata must be rejected rather than guessed from erased
descriptors.

## Compatibility and impact

Previously rejected generic Java declarations may become callable. Incorrectly mapping erased types
to precise Zeron types could permit unsafe casts, so generic metadata must be checked during
resolution and must not depend on runtime guessing. Existing non-generic overload selection should
remain unchanged, and ZEP-0052's already-implemented class-level projection behavior must remain
compatible.

## Alternatives

- Keep generic owners and methods unsupported — safest and simplest, but leaves common libraries
  impractical to use without wrappers.
- Erase every type parameter to `Any?` — broadens reach but discards useful guarantees and can
  create unsafe results.
- Require handwritten compiler bindings for every generic API — precise but scales poorly and
  preserves the adapter burden.

## Implementation and validation

The supported class-level generic owner and member-signature foundation is already implemented with
ZEP-0052. Extend it with method and constructor type parameters, reusing the Zeron generic-call
inference and explicit-argument behavior. Test nested generic signatures, supported and unsupported
bounds, wildcards, explicit and inferred calls, ambiguous overloads, bridge filtering, and erased
bytecode descriptors. Test separately compiled Zeron callers against directory and JAR dependencies.

## Settled design decisions

The design questions are resolved as follows:

- Build on the class-level owner/member signature support already implemented with ZEP-0052, then
  add Java generic methods and constructors on both generic and non-generic owners.
- Mirror Zeron generic-call behavior: infer from the receiver and arguments, allow explicit method
  type arguments, require explicit arguments when inference leaves a parameter unresolved, and do
  not infer from the expected result type alone.
- Reject raw Java generic types rather than silently treating them as `Any?` or adding an unchecked
  view.
- Defer generic arrays to follow-up work under ZEP-0047.
- Recursively support nested parameterized class/interface signatures and ZEP-0052 wildcard forms
  when the bounds are representable in Zeron; reject unsupported bounds or signature forms.
- Treat bridge methods as implementation details, not independent source-call candidates; preserve
  the selected declaration's erased invocation descriptor.

## Decision

Implemented. Java generic method and constructor signatures are parsed and checked using inferred
or explicit type arguments and supported bounds. Calls retain erased JVM descriptors, adapt generic
arguments and results, and reject unresolved type parameters, raw types, and unsupported signatures.
Shipped in 0.5.0.
