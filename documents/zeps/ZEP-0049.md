# ZEP-0049: Java Exceptions and Typed Effects

## Abstract

Define how exceptions declared or thrown by Java interop calls map to Zeron's typed raised effects,
including declaration syntax, propagation, catch behavior, and preservation of exception causes.

## Motivation

Java methods communicate failures through checked and unchecked exceptions, while Zeron APIs can
declare typed raised effects. The current boundary handles these cases unevenly: direct Java calls
that declare checked exceptions are rejected, external-class facades can declare mappings to
effects, and compiler bindings may translate selected exceptions in handwritten runtime helpers.
Library authors need one predictable model rather than custom translation at each boundary.

## Goals

- Define how Java checked exceptions are associated with Zeron raised-effect types.
- Specify which declarations are permitted to translate, propagate, or wrap Java exceptions.
- Preserve the original cause and avoid silently swallowing exceptions.
- Define behavior for exception inheritance, multiple declared exception types, unchecked
  exceptions, and Java `Error`s.
- Apply consistently to constructors, methods, external functions, and compiler-provided bindings
  where appropriate.

## Non-goals

- Replacing Zeron's typed-effect model or introducing resumable effects.
- Catching every unchecked exception or `Error` automatically.
- Defining Java generic exception types; see [ZEP-0048](./ZEP-0048.md).
- Requiring all Java exceptions to be converted into Zeron effects.

## Proposal

Specify an explicit checked-exception mapping at the Java interop boundary. A declaration that maps
a Java exception to a Zeron effect must expose that effect in its resolved raised-effect signature.
Calls then participate in ordinary Zeron effect checking, handling, and propagation.

The design must distinguish Java exceptions that are declared by the member from unchecked
exceptions that may still arise at runtime. It should define whether a declaration may map multiple
Java exception classes to one effect, how subclass relationships affect completeness, and how the
original Java exception is made available as a cause. Unmapped checked exceptions should fail
resolution or declaration validation; unchecked exceptions and `Error`s should retain an explicit,
documented policy.

Use one checked-exception mapping model for external-class methods and constructors, external
function declarations backed by compiler-configured bindings, and those bindings where class-file
metadata is available. A direct Java call with declared checked exceptions remains invalid unless
it resolves through one of these explicitly mapped declarations; do not add call-site mapping
syntax.

Every declared checked exception must be covered by a compatible mapping. A mapped exception type
must correspond to a declared checked exception or a subtype of one, and every declared checked
exception must be covered by an equal or broader mapped type. Choose the most-specific applicable
mapping and reject duplicate mappings for one Java exception type on a callable. Distinct Java
exception types may map to the same Zeron effect through constructors that retain the respective
exception types.

Pass the original Java exception object as the mapped effect payload. This preserves its identity,
stack trace, and cause without introducing a generic wrapper. `RuntimeException` descendants and
`Error`s continue to propagate unchanged, including when a broad mapping names `Exception` or
`Throwable`. Only the Java invocation is translated; receiver and argument evaluation remain
outside the mapping boundary. Reject generic Java throws signatures that use a type variable rather
than guessing from the erased exception bound.

## Compatibility and impact

Calls that are currently rejected may become valid when their declared failures are mapped.
Changing an existing call's raised-effect signature is source-visible and may require callers to
handle or propagate a new effect. Java exception objects crossing into Zeron must retain an
appropriate reference/cause representation without weakening effect checking.

## Alternatives

- Continue rejecting all checked-exception Java calls — keeps the boundary simple, but prevents
  direct use of many standard and third-party APIs.
- Wrap every checked exception in one generic host exception effect — easy to implement but loses
  useful failure distinctions.
- Translate exceptions only in compiler-written helpers — preserves local control but perpetuates
  repetitive bindings and inconsistent semantics.
- Allow all Java exceptions to escape without effect checking — maximizes access but breaks the
  declared-effect guarantees of Zeron APIs.

## Implementation and validation

The implementation extends checked-exception mappings to external-class constructors and external
functions backed by configured Java bindings. Callable raised-effect signatures remain in compiled
API metadata, and external-class constructor mappings are serialized for separately compiled
clients. Tests cover declared-exception completeness, subtype matching, shared effects,
original-payload identity, generic-throws rejection, and pass-through behavior for unchecked
exceptions and `Error`s.

## Settled design decisions

- Reuse one mapping model across external-class methods and constructors, external function
  declarations backed by configured bindings, and compiler bindings where Java metadata is
  available. Direct calls without an explicit mapped declaration continue to reject checked
  exceptions.
- Require complete compatible coverage of declared checked exceptions, reject duplicate mappings
  for one Java exception type per callable, and select the most-specific applicable mapping.
- Preserve the original exception object as the effect payload. Distinct exception types may map to
  one effect through appropriately typed constructors; one exception type has one mapping per
  callable.
- Let unchecked exceptions and `Error`s pass through unchanged, even under broad mappings.
- Reject generic `throws E` signatures for now; do not infer exception mappings from erased generic
  bounds.
- Translate only the Java invocation, never failures from receiver or argument evaluation.

## Decision

Implemented. Checked Java exceptions can be mapped explicitly at supported interop boundaries and
then participate in Zeron's ordinary raised-effect checking, handling, propagation, and library
metadata.
