## Abstract

Settle how direct Java host access relates to Zeron's typed raised effects. Curated `external class`
and `external fn` declarations remain the trusted, reusable interop surface. Direct Java invocations,
constructor calls, and field access become an explicit `unsafe` boundary: they are allowed only
through an `unsafe` expression, which acknowledges that unchecked host failures and observable side
effects are outside the typed effect signature. `raises` continues to describe typed control-flow
effects, not purity.

## Motivation

The current Java interop implementation supports direct metadata lookup, public constructors and
methods, selected fields, overloads, and expanded varargs, but still excludes capabilities used by
many Java libraries. It also sits in an awkward place with respect to Zeron's effect system.

Java has no purity guarantee. A Java method that declares no exception can still mutate shared
state, read the environment, perform I/O, throw an unchecked exception, or fail with an `Error`.
At the same time, Zeron's `raises` clause is a typed control-flow channel: it records effects that
may escape and be handled, not whether an operation is pure. Zeron code can already mutate through
`&T`, write output, and read the environment without a purity effect. Treating every Java call as
`IO` would therefore require a language-wide purity or IO effect, not just an interop rule, and would
not compose cleanly with `handle`.

The PureScript approach avoids the problem by making every boundary declaration a reviewed FFI
binding. That is accurate and auditable, but it taxes every Java API, including trivial and
frequently used members. The Flix approach is the opposite: all Java is importable, every call is
implicitly effectful, and `unsafe` is a local escape hatch. Zeron already has a middle tier in its
curated facades, but direct Java access currently behaves as if it were trusted even when no facade
declares the effects.

The missing piece is an explicit trust boundary for direct host access. It should not silently claim
purity that the compiler cannot verify, and it should not force every Java API through a handwritten
facade. Passing Zeron behavior into Java is a separate concern, proposed in
[ZEP-0148](./ZEP-0148.md); the remaining interop inventory is proposed in [ZEP-0149](./ZEP-0149.md).

## Goals

- Make every Java host access an explicit choice: a compiler-validated facade declaration or an
  `unsafe` expression.
- Keep curated `external class` and `external fn` declarations as the preferred, reusable,
  compiler-checked boundary.
- Keep checked-exception mapping complete and typed for facades, while allowing `unsafe` to opt out
  of mapping for one-off direct access.
- Preserve the documented pass-through behavior for unchecked exceptions and `Error`s.
- Keep `handle` as the only typed control-flow form; do not add `try`/`catch`.
- Keep `raises` as a typed control-flow channel rather than a purity effect.
- Define the principle for adding capabilities: explicit, descriptor-checked, and covered by
  compile-time and runtime tests.

## Non-goals

- Inferring the purity or side-effect behavior of Java methods.
- Adding an implicit `IO` effect or a general purity effect. If Zeron wants purity tracking, it is a
  language-wide design and belongs in a separate proposal.
- Automatically converting unchecked exceptions or `Error`s into typed Zeron effects.
- Introducing statement-level `try`/`catch`, or making `handle` catch host exceptions.
- Repeating or broadening the type/array, generic, or checked-exception semantics owned by
  [ZEP-0047](./ZEP-0047.md), [ZEP-0048](./ZEP-0048.md), and [ZEP-0049](./ZEP-0049.md).
- Converting Zeron lambdas or function references to Java functional interfaces; that is
  [ZEP-0148](./ZEP-0148.md).
- General inherited/interface member lookup, JPMS configuration, or user-extensible external
  bindings; those are [ZEP-0149](./ZEP-0149.md).
- Promising complete JVM language interoperability.
- Enabling arbitrary reflection, package scanning, implicit imports, or unrestricted access to
  non-public members.

## Proposal

Zeron has two interop tiers.

1. **Declared facade — trusted and reusable.** An `external class` or `external fn` declaration names
   the exact Java owner and member, is descriptor-checked against class-file metadata, and declares
   the callable's Zeron effects, including checked-exception mappings. Its `raises` set is the
   authoritative Zeron contract. Calls through the facade need no `unsafe` marker. The facade author
   is responsible for the untyped remainder: unchecked failures, `Error`s, side effects, and any
   behavior the Java class-file metadata does not express. Review a facade like an FFI boundary.
2. **Direct Java access — unsafe and local.** A direct Java invocation, constructor call, or field
   access is permitted only inside an `unsafe` expression. `unsafe` is a local, compile-time
   permission marker. It allows the host access and accepts that unchecked host failures and
   observable side effects are outside the Zeron effect signature. It does not establish purity and
   does not add a typed effect.

```zeron
let text = unsafe (java.nio.file.Files.readString(path));
```

Under `unsafe`, a direct Java member that declares checked exceptions may be called without a
mapping. Those exceptions propagate as host exceptions; the call does not acquire a Zeron raised
effect. A facade for the same member still requires a complete mapping and declares the mapped
effects as one would today. `unsafe` does not bypass descriptor support, visibility, module exports,
overload checking, or generic-signature validation. It changes only the trust classification of the
member access and the checked-exception policy for that access.

`unsafe` is not transitive in a way that hides Zeron effects. A Zeron effect raised inside the
operand has no Java origin, still escapes the `unsafe` expression, and must be handled or declared
by the enclosing function. `unsafe` is not a general escape from effect rows; it is a statement
about the host access at that boundary. A public `static final` field with a class-file
`ConstantValue` attribute is a compile-time constant and may be read without `unsafe`; other direct
fields require it.

Bare direct Java access without `unsafe` is rejected. This is a source break for direct interop, but
facades, external functions, and the standard library keep their current signatures and semantics;
any bundled source that calls Java directly migrates to a facade or an explicit `unsafe` expression.

`unsafe` takes one expression. With the value-producing block expressions of
[ZEP-0146](./ZEP-0146.md), an `unsafe { ... }` block can scope several host calls; while that form is
unavailable, nested or sequential `unsafe` expressions are the equivalent. `unsafe` is deliberately
not a purity cast; it acknowledges an unchecked host boundary and remains a suitable place to
discharge a future purity effect if one is adopted.

## Compatibility and impact

The trust boundary is the source-language change in this proposal. Existing bare direct Java access
becomes an error or migration warning; calls through facades, external functions, and the standard
library keep their current behavior. `unsafe` becomes a reserved keyword, so an existing identifier
with that name must be renamed. `unsafe` is compile-time only: it adds no runtime wrapper, generated
descriptor, or API-index field. Checked-exception mappings and their derived raised-effect
signatures remain unchanged for facades. Unchecked exceptions and `Error`s retain their current
pass-through behavior, so a call under `unsafe` can still throw a host exception that does not appear
in a Zeron effect row.

The change touches the scanner, parser, formatter, highlighter, language-server surfaces, resolver
diagnostics, and the Java-interoperability and raised-effect guides. It does not change the Java
type/array mappings, generic interop, intrinsic bindings, or the Zeron library artifact format, and
it does not change `raise` or `handle` typing.

## Alternatives

- **Require a facade for every Java access (PureScript-style).** This is the safest and most
  auditable model, but it taxes every Java API and makes broad library use impractical. Rejected as
  the default; facades remain the preferred tier and the only reusable one.
- **Tag every Java call with an implicit `IO` effect and use `unsafe` to discharge it (Flix-style).**
  This is conservative for purity, but Zeron does not currently track purity for its own operations,
  and its `raises` channel is abortive control flow rather than a monadic IO capability. Copying the
  model only at the Java boundary would be inconsistent; copying it language-wide is a separate
  design. Rejected for this proposal.
- **Annotate nothing and add unchecked-exception handling primitives.** This reintroduces a
  statement-level `try`/`catch` that overlaps `handle`, gives host exceptions a second control-flow
  path, and still does not address unchecked failures from ordinary calls. Rejected.
- **Keep the current permissive direct-access behavior.** This is the least disruptive option, but
  it silently presents unvalidated host access as if it had a complete Zeron effect signature.
  Rejected.
- **Make every raw Java call raise a `HostFailure` effect by default.** This gives unchecked failures
  a typed channel, but introduces a host marker with no natural handler, forces runtime translation
  or a non-handleable pseudo-effect, and infects signatures with a broad effect that is not useful
  at call sites. Deferred unless a concrete need appears; `unsafe` plus facade mappings is the
  lighter model.

## Implementation and validation

1. Add `unsafe` expression syntax and the corresponding scanner, parser, formatter, highlighter,
   language-server keyword completion, and TextMate grammar surfaces.
2. Gate direct Java invocations, constructors, and field accesses on `unsafe` while leaving facade
   calls and external functions unchanged. Exempt `static final` `ConstantValue` reads.
3. Keep checked-exception completeness and mapping rules for facades. Under `unsafe`, allow checked
   exceptions to escape without a mapping and without contributing a raised effect.
4. Preserve Zeron raised effects raised inside an `unsafe` operand as ordinary Zeron effects.
5. Add diagnostic entries and explanation resources for bare host access, misplaced `unsafe`, and
   unsupported or ambiguous forms.
6. Add focused tests for facade calls, `unsafe` calls, checked exceptions under `unsafe`, unchecked
   exceptions and `Error` pass-through, nested `unsafe` scopes, non-host operands, effect
   preservation inside an `unsafe` operand, formatter and language-server behavior, and
   `static final` constant reads.
7. Update the Java-interoperability and raised-effect guides and the editor documentation.

The remaining interop areas are staged in [ZEP-0149](./ZEP-0149.md), and Java callback conversion is
staged in [ZEP-0148](./ZEP-0148.md). Keep unrelated features in separate proposals or revisions when
their design decisions are independent.

Implementation notes: `unsafe` is a hard keyword parsed as a unary prefix expression, so
`unsafe (assignment)` is the form for a direct field write. The standard library uses explicit
`unsafe` expressions for its remaining direct JDK calls, and ZR2027 reports bare direct host access.
The implementation adds no runtime wrapper or descriptor and leaves facade exception mappings and
API-index output unchanged.

## Open questions

- Should `unsafe` accept only a primary expression, or a full expression including assignment? The
  initial slice should choose the narrower form unless a concrete need appears.
- Should facade mappings be extended to selected unchecked exception types, or should a Java
  adapter remain the supported way to type an unchecked failure?
- Should the migration produce a hard error immediately or a deprecation warning for one release
  cycle? The source break is intended, but the migration window needs a decision.
- Should `unsafe` be a hard keyword or a contextual keyword? A hard keyword is simpler and matches
  the acknowledged source break; a contextual form would preserve existing identifiers.

## Decision

Implemented 2026-11-18 and accepted 2026-11-17 as a `0.8.0` candidate. Curated facades remain the trusted, typed tier; direct
Java invocation, construction, and field access require an explicit `unsafe` expression; checked
exceptions still require mappings for facades; unchecked exceptions and `Error`s continue to
propagate as host exceptions; and `raises` remains a typed control-flow channel rather than a purity
effect. No statement-level `try`/`catch` and no implicit `IO` effect are introduced.

The original umbrella also covered Java callback conversion and the remaining interop inventory.
Those areas were split into [ZEP-0148](./ZEP-0148.md) and [ZEP-0149](./ZEP-0149.md) so each can be
implemented and reviewed independently; this proposal now owns only the trust boundary.
