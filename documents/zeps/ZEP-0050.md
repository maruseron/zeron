## Abstract

Inventory and define the remaining Java interoperability features that are not covered by type and
array mappings, generics, or exception/effect integration. The proposal groups related follow-on
work without treating every possible JVM feature as a commitment.

## Motivation

The current Java interop implementation supports direct metadata lookup, public constructors and
methods, selected fields, overloads, and expanded varargs, but still excludes capabilities used by
many Java libraries. After the foundational type, generic, and exception boundaries are addressed,
the project needs a deliberate way to prioritize remaining features without expanding Java access
implicitly.

## Goals

- Maintain an explicit inventory of remaining interop gaps and their dependencies.
- Define the principle for adding capabilities: explicit, descriptor-checked, and covered by
  compile-time and runtime tests.
- Evaluate callback/SAM conversion, inherited/interface members, Java module configuration, and
  user-extensible external bindings as separate feature areas.
- Preserve explicit imports, classpath roots, and facade allowlists unless a separate design
  approves a broader discovery model.

## Non-goals

- Repeating or broadening the type/array, generic, or exception semantics owned by
  [ZEP-0047](./ZEP-0047.md), [ZEP-0048](./ZEP-0048.md), and [ZEP-0049](./ZEP-0049.md).
- Promising complete JVM language interoperability.
- Enabling arbitrary reflection, package scanning, implicit imports, or unrestricted access to
  non-public members.

## Proposal

Track and design the following remaining areas independently, selecting implementation only when
there is a concrete standard-library or application use case:

- **Callbacks and SAM conversion:** adapt Zeron functions/lambdas to Java functional interfaces,
  including exception propagation, captures, and lifetime behavior.
- **Inherited and interface members:** define lookup through superclasses and interfaces, default
  methods, ambiguity, access, and overload precedence.
- **JPMS configuration:** decide whether projects may declare module-path entries, readability, and
  qualified exports in addition to current classpath and exported-JDK lookup.
- **External-binding extensibility:** assess how users or library authors can declare checked,
  descriptor-validated host bindings without changing compiler-owned registries or weakening the
  explicit facade model.
- **Interop conformance and diagnostics:** maintain a capability matrix and focused tests covering
  supported descriptors, overloads, JAR/class-directory lookup, runtime classpaths, and failure
  diagnostics.

The work remains opt-in and explicit. New capabilities must not silently introduce package scans,
implicit imports, runtime dependencies, or unvalidated conversions.

## Compatibility and impact

These features can affect overload resolution, runtime classpath requirements, and the safety of
host callbacks. Each should have its own compatibility review and tests. This umbrella proposal
does not alter existing source behavior or define a release bundle.

## Alternatives

- Stop after the three foundational interop proposals — keeps the boundary small but leaves
  common callback- and module-based APIs inaccessible.
- Attempt broad JVM compatibility in one change — offers a larger surface quickly but couples
  unrelated semantics and makes validation difficult.
- Add features only as compiler-internal adapters — solves individual use cases but perpetuates
  the current manual-binding burden.

## Implementation and validation

Use the capability inventory to identify the next concrete use case after the foundational
proposals. For each selected feature, define its source syntax, descriptor checks, resolution
behavior, runtime requirements, diagnostics, and focused tests before implementation. Keep unrelated
features in separate proposals or revisions when their design decisions are independent.

## Open questions

- Which remaining area should follow type/array mappings, generics, and exception/effect integration?
- Should user-extensible host bindings be source declarations, project configuration, library
  metadata, or a combination?
- What callback lifetime and threading guarantees should Zeron make when Java retains a callback?
- Is JPMS module-path support needed for the first host-library consumers?
