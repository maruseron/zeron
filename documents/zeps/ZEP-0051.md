## Abstract

Add explicit, checked declaration-site covariance for generic Zeron classes and contracts, while
keeping unannotated parameters invariant. Record use-site projections as an area of interest for
Java interoperability, not as part of this proposal's language scope.

## Motivation

Zeron generic classes and contracts are currently invariant. As a result, even a type that only
produces values of `T` cannot be used through a type instantiated with a supertype of `T`. This
limits substitutability for read-only abstractions and complicates modeling Java APIs such as
`List<? extends T>`.

Java wildcards are a concrete interop use case, but use-site projections and declaration-site
variance are distinct mechanisms. Defining Zeron's variance model independently will keep
Java-specific rules from silently setting the language's general subtyping semantics.

## Goals

- Add declaration-site covariance using an explicit `out T` annotation on generic classes and
  contracts.
- Keep soundness statically enforced through variance-position checking.
- Allow safe assignment conversions between applications of the same covariant nominal type.
- Preserve existing invariance for arrays, mutable references, and exact generic effect identity.
- Record use-site projections as a separate interop design interest for ZEP-0048.

## Non-goals

- Changing Java array covariance or the array mappings accepted by [ZEP-0047](./ZEP-0047.md).
- Reifying generic arguments at runtime.
- Making mutable generic abstractions covariant merely because they are read through a particular
  reference.
- Adding declaration-site contravariance, use-site projections, or wildcard capture.
- Adding variance annotations to functions, function types, sums, or type aliases.
- Deciding Java wildcard semantics in place of [ZEP-0048](./ZEP-0048.md).
- Changing generic effect identity; effect arguments remain exact and invariant.

### Cross-language observations

- Producer-only APIs can often be covariant; consumer-only APIs can often be contravariant. APIs that both consume and produce a type parameter generally need invariance or a restricted view.
- Declaration-site annotations centralize the generic declaration's contract. Use-site projections let callers request a restricted view without changing the declaration.
- Mutability is a soundness boundary. Mutable references, writable properties, and methods that accept `T` can invalidate covariance; checking only whether `T` occurs in a result type is insufficient.
- Array covariance is a distinct, historically common exception and may require runtime checks. It should not be inferred from generic covariance.

## Settled design

### Declarations and syntax

Generic classes and contracts may mark a type parameter covariant with `out`, for example:

```zeron
public contract Producer<out T> {
    get(): T;
}
```

Unannotated parameters remain invariant. This proposal covers covariance only; contravariance
(`in T`) is deferred to a later design. Annotations are part of the generic declaration's public
contract and are checked by the compiler rather than treated as unchecked promises.

### Variance checking

An `out T` parameter may occur only in covariant (positive) value positions. The checker examines
all declarations, including private implementation details, so private visibility does not bypass
the rule.

- Method and function results and read-only property results are positive positions.
- Method and function parameters are negative positions. Function-type parameters reverse polarity;
  function-type results preserve it.
- Nullable wrappers preserve polarity.
- Mutable references, writable properties, mutable fields, `Array<T>`, and any invariant generic
  application make the contained occurrence invariant. An invariant occurrence is not permitted
  for `out T`.
- Nested applications of a covariant class or contract preserve the occurrence's polarity. If a
  nested generic parameter is invariant or its variance is unknown, the occurrence is invariant.
- Constructor inputs are not treated as member input positions: a constructor creates a value at
  the exact type application and cannot be invoked through an already widened instance. Any stored
  field or property is still checked according to its own mutability and access rules.
- Bounds remain compile-time constraints under the existing bound rules; they do not grant
  unchecked value-level occurrences of `T`.

These rules reject an ordinary method that accepts `T` or a writable `T` property on a covariant
declaration, but permit producing `T` and safe nested positive uses. The same checking applies to
contract requirements and to implementations.

### Subtyping and inference

If `S` is assignable to `T` under Zeron's existing type-compatibility rules, then `C<S>` is
assignable to `C<T>` for the same nominal generic class or contract `C` when the corresponding
parameter is declared `out`. Invariant parameters must remain exactly equal. The rule composes
through nested generic applications according to each declaration's variance; it does not create
class inheritance or any new subtype relation between unrelated nominal declarations.

Variance conversions do not change nullability or reference capability. In particular, they cannot
turn a read-only view into a mutable reference or make mutable references with different type
arguments interchangeable. `Array<T>` remains invariant. Generic effect arguments remain exact
and invariant because they participate in applied-effect identity.

This proposal adds no common-supertype inference or variance-driven inference. Existing generic
inference continues to infer from its current structural constraints; callers may need explicit
type arguments where variance alone would otherwise be needed to infer a wider type. Once types
are resolved, ordinary assignment and argument compatibility apply the variance conversion.

### Runtime and metadata

Variance is a compile-time assignability rule. It does not reify generic arguments or change JVM
erasure. The versioned Zeron API index must preserve each generic parameter's variance so separately
compiled consumers apply the same rules. Update the API-index schema version when the metadata
format changes, and retain the existing explicit compatibility behavior for unsupported schema
versions.

Use-site projections such as Java's `? extends T` and `? super T` remain outside this proposal.
Their general language semantics are explored in [ZEP-0052](./ZEP-0052.md); [ZEP-0048](./ZEP-0048.md)
decides how supported Java wildcard signatures map to those projections.

`Array<T>` and other mutable generic abstractions remain invariant unless a separate, sound
read-only view is part of the type. The JVM representation may remain erased; covariance is a
compile-time assignability rule and does not require runtime type-argument reification.

Use-site projections and wildcard capture are separate from declaration-site variance and are
explored in ZEP-0052, with Java signature mapping retained in ZEP-0048.

## Compatibility and impact

Adding variance changes source-level assignability and generic conformance. It may allow new calls
but can also make previously accepted declarations invalid if their type parameters occur in
unsafe positions. The resolver, type compatibility, contract implementation checking, and
compiled-library metadata must agree on variance. Existing declarations without annotations retain
invariant behavior.

Serialized library metadata is required so variance is consistent across compiled-library
boundaries. JVM erasure itself need not change, but generated bridge methods and invocation
descriptors must remain valid.

## Alternatives

- Keep all Zeron generic types invariant and add only Java-specific wildcard adapters — smaller
  language change, but leaves producer APIs less substitutable and duplicates variance concepts at
  the interop boundary.
- Infer variance from member use — reduces annotations but makes the public contract less explicit
  and complicates APIs whose representation is hidden.
- Allow unchecked covariance for mutable types — convenient but can permit writes that violate the
  statically promised type.

## Implementation and validation

Implement declaration metadata and position checking, then add resolver tests for valid and invalid
declarations, assignments, nested types, nullable/reference wrappers, contract conformance, and
compiled-library round trips. Verify that mutable arrays remain invariant and erased JVM
descriptors and bridge methods remain valid. Java wildcard projections remain in ZEP-0048.

## Decision

Accepted on 2026-10-20. The initial scope is explicit checked declaration-site covariance on
generic classes and contracts, with invariant defaults. Contravariance and use-site projections are
outside this proposal; use-site projections remain a stated design interest for Java interop.
