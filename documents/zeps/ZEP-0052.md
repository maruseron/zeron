## Abstract

Define bounded use-site variance for generic type applications, using `out T` and `in T` in type
argument lists. The feature should provide safe producer and consumer views of invariant generic
types and a principled mapping for Java wildcards, without confusing per-use projections with
declaration-site variance.

## Motivation

[ZEP-0051](./ZEP-0051.md) adds checked declaration-site covariance to Zeron classes and contracts.
That rule lets a declaration promise that one of its parameters is only produced. It cannot,
however, make an arbitrary invariant Java type covariant: Java APIs express flexible views at each
use site with wildcards such as `List<? extends Number>` and `List<? super Integer>`.

Use-site projections can also be useful for Zeron APIs that must expose a restricted view of an
invariant type without changing the declaration. To be sound, a projection must restrict which
members can be called and how their generic arguments and results are typed. It cannot be treated
as an unchecked spelling for ordinary `C<T>`.

## Goals

- Use only `out T` and `in T` as the new projection markers in generic type-argument lists.
- Define producer and consumer capabilities, projection assignability, and composition with
  declaration-site variance.
- Apply a shared projection model to Zeron generic classes and contracts and to imported Java
  generic types.
- Define implicit, call-scoped capture sufficient for safe member access without adding explicit
  existential or capture syntax.
- Map Java wildcard signatures to projections while preserving erased invocation descriptors.

## Non-goals

- Replacing or changing the declaration-site `out T` semantics in ZEP-0051.
- Inferring declaration-site variance from member use.
- Projecting generic sums, products, or intrinsic arrays in the initial scope.
- Reifying generic arguments at runtime.
- Supporting raw Java types or Java generic arrays in the initial scope.
- Changing the copying, nullability, or primitive-array mappings in ZEP-0047.
- Enabling Java callbacks or SAM conversion, which remain in ZEP-0050.
- Requiring support for every wildcard, raw type, or generic signature accepted by Java.

## Influence-language inventory

This inventory focuses on use-site variance or closely related bounded type-argument forms in the
languages listed as Zeron influences. Declaration-site annotations alone are not counted as
use-site projections.

### Contrasts

C# and F# provide declaration-site variance for selected interfaces and delegates, but do not use
wildcard arguments such as `C<? extends T>` at each use. TypeScript variance annotations describe
structural relationships rather than adding bounded projection syntax to a generic application.
These models help distinguish variance conversion from a captured, per-use type argument.

### Cross-language observations

- An `out` projection is useful only when the view prevents unsafe consumption of the hidden type;
  an `in` projection is useful only when reads are widened to a safe upper bound.
- A projection denotes an unknown argument satisfying bounds, not a concrete argument that can
  always be substituted independently at each member access.
- Capture or an equivalent existential representation is needed when an operation must preserve
  the identity of an unknown argument across multiple positions.
- Java wildcards are erased at runtime, but generic signatures still matter to static checking.
  Zeron should not add wrapper allocation solely to represent a projection unless a separately
  justified boundary conversion requires it.
- Declaration-site variance and use-site projections solve related but different problems:
  the former validates a declaration once; the latter restricts an individual view.

## Proposal

### Syntax direction

Use the existing words `out` and `in` as contextual markers at the start of a generic type
argument:

```zeron
contract Source<T> {
    get(): T;
}

contract Sink<T> {
    accept(value: T): Unit;
}

fn read(source: Source<out Animal>): Animal = source.get();
fn feed(sink: Sink<in Dog>, value: Dog): Unit = sink.accept(value);
```

Here `Source<out Animal>` asks for a producer view whose hidden argument is bounded above by
`Animal`; `Sink<in Dog>` asks for a consumer view whose hidden argument can accept `Dog`. The
markers apply to individual type arguments, not to the generic declaration. They are distinct from
the already-supported declaration form `contract Source<out T>`.

The intended syntax does not use Java's `? extends` / `? super`, Scala's `forSome`, or a new
punctuation form. An unbounded projection, if supported, should be expressible using the existing
top type and `out`, such as `Source<out Any?>`, rather than introducing a third marker.

### Settled scope and semantic direction

Projections are part of the general Zeron type system, not syntax restricted to Java calls. In the
initial scope they may be used on applications of Zeron generic classes and contracts and on
imported Java generic classes and interfaces. They may appear in local types, parameters, results,
and public Zeron API signatures. Generic sums, products, and intrinsic arrays are not projectable
in this slice.

For an invariant generic declaration `C<T>`, `C<out U>` denotes a view of `C<X>` for an unknown
`X` assignable to `U`; `C<in L>` denotes a view of `C<X>` where `L` is assignable to `X`, subject
to the declaration's upper bounds. These are existential views, not new concrete instantiations.

- An `out U` view exposes produced values as `U`. Operations requiring a value of the hidden `X`
  are unavailable unless the supplied argument is independently safe for every permitted `X`.
- An `in L` view permits consumers to receive `L`. Values produced as `X` are exposed using the
  declaration's upper bound when it has one representable as a single Zeron type; otherwise they
  are exposed as `Any?`.
- For an invariant `C`, `C<S>` is assignable to `C<out U>` when `S` is assignable to `U`, and to
  `C<in L>` when `L` is assignable to `S`. Assigning a projected `C` to an unprojected invariant
  `C<T>` is not allowed unless the hidden argument is proven to be exactly `T`.
- `C<out S>` is assignable to `C<out U>` when `S` is assignable to `U`. `C<in S>` is assignable
  to `C<in L>` when `L` is assignable to `S`. Opposite-direction projections are incompatible.
- Use-site and declaration-site variance must agree. A declaration-site covariant parameter may
  be used unprojected or with a compatible `out` projection; an opposing `in` projection is
  rejected. A same-direction projection is allowed even when it is redundant. An invariant
  declaration parameter may use either projection.
- Nested generic applications compose by the declared and projected polarities. An invariant or
  mutable position does not become covariant merely because an outer type is projected.

The resolver creates capture variables implicitly for a projected receiver or argument while
resolving its member/method call. A capture is scoped to that call, is shared only among the
positions participating in that call, and cannot escape as a named or inferred result type; results
are widened to the projection's visible bound. No explicit capture or existential-binder syntax is
added. This is not a promise of general existential-type inference across independent expressions
or calls.

### Java signature mapping and compilation candidates

Java `C<? extends U>` maps to `C<out U>`, `C<? super L>` maps to `C<in L>`, and unbounded `C<?>`
maps to `C<out Any?>`. Raw Java types are rejected rather than treated as projected or erased
`Any?` types. Java generic arrays and Zeron intrinsic arrays remain outside this proposal's initial
scope and follow ZEP-0047.

The Java mapping depends on ZEP-0048's support for generic class and member signatures. ZEP-0052
defines the projection model; it does not independently settle Java generic-method inference or
overload selection. Unsupported wildcard bounds and signatures are rejected rather than silently
replaced with `Any?`.

Projections and captures are compile-time only. The resolver retains the generic signature,
substitutes owner and method parameters, checks calls against the projected view, and emits the
selected erased JVM descriptor. No runtime projection wrapper is introduced. Projections in public
Zeron signatures are preserved by API-index schema 8.

### Excluded initial forms

Use-site projection does not apply to generic sums, products, intrinsic arrays, Java arrays, or raw
Java types in this slice. In particular, `Array<out T>` is not a read-only view in this proposal;
array covariance and runtime/copying behavior remain governed by ZEP-0047. These exclusions do not
change the invariant behavior of unprojected type applications.

## Compatibility and impact

Projections add source-level types and assignments but do not change generic declaration metadata
or JVM erasure. The parser, resolver, member lookup, inference, diagnostics, language server,
formatter, and Java signature reader must agree on projection bounds and capabilities. Unannotated
type arguments retain current invariant behavior.

Projection information crossing a compiled-library or Java classpath boundary must not be lost.
Public Zeron API-index signatures may contain projections; the implementation must preserve them
and version the schema if needed. Java class-file generic signatures remain metadata for checking,
not replacements for erased invocation descriptors.

## Alternatives

- Rely only on declaration-site variance from ZEP-0051 — simpler, but cannot express a restricted
  view of an invariant declaration or faithfully represent Java wildcard uses.
- Adopt Java's `? extends T` / `? super T` syntax — directly recognizable at the Java boundary,
  but adds punctuation-heavy syntax and diverges from Zeron's existing `out T` vocabulary.
- Use explicit existential quantification — expressive, but would require additional syntax and
  expose capture details to callers.
- Generate adapters for each generic Java API — can be precise for curated libraries, but scales
  poorly and does not solve general generic type checking.

## Implementation and validation

1. Add parser and type-descriptor support for `out` / `in` type arguments on Zeron generic classes
   and contracts and imported Java generic types; verify formatting,
   diagnostics, and language-server display.
2. Implement projection-aware member substitution and call-scoped capture;
   test nested, nullable, bounded, invariant, and mutable positions.
3. Parse Java generic signatures and map supported wildcard forms without changing the selected
   erased invocation descriptor.
4. Test generic owner and member calls, Java generic-method interaction as scoped by ZEP-0048,
   overloads, explicit and inferred type arguments, rejected raw/unsupported forms, and separately
   compiled library boundaries.
5. Keep array projection and Java generic-array behavior deferred to ZEP-0047; verify that the
   exclusions do not weaken existing array copying, nullability, or mutability guarantees.

## Decision

Implemented. Use-site projections use `out T` / `in T` in generic type arguments. The implemented
scope covers Zeron generic classes and contracts plus imported Java generic types; captures are
implicit and call-scoped, and arrays and raw Java types remain excluded. The release state remains
Shipped in 0.5.0.
