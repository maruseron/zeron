## Abstract

Loosen the current ban on parameterized generic targets in `is` and `as?` when static type
relationships prove that a raw JVM class test is sufficient to justify the applied target type.
Generic arguments remain static-only: the compiler does not inspect or reify them at runtime.

## Motivation

The current compiler rejects all parameterized runtime type-test targets, even when the source's
static type and a declared generic conformance establish the target application's arguments. For
example, if `Implementation<T>` conforms to `Contract<T>`, a value statically typed as
`Contract<Int>` can be narrowed to `Implementation<Int>` by testing the raw `Implementation` class.
The declared conformance supplies the relationship between the source and target arguments; the
runtime test need only determine whether the value is an `Implementation`.

This must not become a general unchecked generic cast. JVM erasure cannot distinguish
`Implementation<Int>` from `Implementation<String>`. A broader source such as `Contract<Any>` may
contain either application, so testing only the raw class cannot safely narrow it to one concrete
application.

## Goals

- Permit `is` and `as?` with applied generic targets only when the static source type, target
  declaration, and declared generic conformances prove the target application.
- Keep runtime tests erased to the raw class or contract; do not add runtime generic identity.
- Allow safe projected target views when the source can be viewed through the projection, without
  exposing or claiming the hidden concrete type argument.
- Apply one static admissibility rule to `is` and `as?`, including the flow refinement and result
  types they produce.
- Preserve diagnostics for generic targets whose arguments cannot be justified statically.

## Non-goals

- Reifying generic arguments, adding runtime type descriptors, or distinguishing applied generic
  types with JVM class tests. General reification remains separate in [ZEP-0015](./ZEP-0015.md).
- Adding parameterized array or function-shape runtime tests.
- Adding an unchecked cast operator such as `as!`. Any intentionally unsafe cast requires a
  separate proposal with explicit unsafe semantics.
- Extending generic targets to checked `as`; this proposal changes only `is` and `as?`.
- Establishing generic relationships for Java external types; the initial implementation is limited
  to Zeron-declared classes and contracts, including declarations loaded from Zeron library indexes.

## Proposal

`is` and `as?` may accept an applied generic target when the compiler can establish that a successful
raw-class test implies a value with the requested source-level application.

The proof is based on static type relationships, not merely on whether the source and target might
overlap. The compiler must account for the target's generic parameters and its declared applied
contract conformances. For example:

```zeron
contract Contract<out T> { }

class Implementation<T> is Contract<T> {
    public constructor new;
}

fn narrow(value: Contract<Int>): Boolean =
    value is Implementation<Int>;
```

Here, if the runtime class test succeeds, the declared `Implementation<T> is Contract<T>`
conformance and the source type `Contract<Int>` establish `T` as `Int`. The generated test checks
only `Implementation`; the compiler uses the established relationship to refine the source-level
type on the true branch.

By contrast, the following narrowing is invalid:

```zeron
fn unsound(value: Contract<Any>): Implementation<Int>? =
    value as? Implementation<Int>;
```

Because `Contract` is covariant, `Contract<Any>` may hold an `Implementation<String>` as well as an
`Implementation<Int>`. A raw `instanceof Implementation` cannot distinguish them. The compiler must
reject the cast rather than return an incorrectly typed value.

An explicitly projected view may be tested when it is a safe view of the source value:

```zeron
fn view(value: Any): Box<out Any?>? =
    value as? Box<out Any?>;
```

The runtime check establishes only that the value is a `Box`. The result retains the projection, and
member operations remain restricted by the use-site projection rules. This does not establish the
concrete argument stored in the `Box`.

The same admissibility proof applies to `is` and `as?`. A successful `is` may refine a stable
binding to the applied target type. `as?` returns the applied target type made nullable and returns
null when the raw runtime test fails. Neither operator may use generic arguments as runtime
discriminators. A projected target is accepted only when the compiler can prove that the source can
safely be viewed through that projection.

The proof must reject targets where the source merely admits some values of the target application
but does not guarantee the application conditional on the target's raw runtime class. In
particular, covariance does not justify narrowing a broad view to a more specific argument.

## Compatibility and impact

This proposal accepts some programs that currently fail target validation; it does not change
runtime representations or require generic reification. Existing `is` and `as?` behavior for
non-generic classes, contracts, built-ins, and generated sum cases remains unchanged.

The static guarantee relies on declared Zeron types and versioned Zeron library metadata. Java
external generic relationship proofs are outside the initial scope.

## Alternatives

- Continue rejecting every applied generic target — simple and safe, but rejects downcasts whose
  arguments are already determined by the source type and declared conformance.
- Test only the raw class and accept the requested generic target — convenient, but unsound when
  the source view allows multiple applications of that raw class.
- Reify generic arguments — could support dynamic discrimination, but adds runtime identity,
  propagation, ABI, and separate-compilation requirements outside this proposal.
- Add an unchecked cast escape hatch — can express unsafe interop assumptions but deliberately
  weakens type safety and should be designed separately.

## Implementation and validation

Update runtime-target validation to admit only generic targets with a proof of application
compatibility. Share the proof between `is` and `as?`, and ensure flow narrowing uses only the
validated target. Keep bytecode tests focused on raw class/interface checks; no emitted code should
claim to test generic arguments. Checked `as` retains its existing rejection of generic targets.

Validation should cover:

- a generic implementation whose declared contract application determines its type argument, such
  as `Contract<Int>` to `Implementation<Int>`;
- rejection when a covariant source application permits multiple target arguments, such as
  `Contract<Any>` to `Implementation<Int>`;
- invariant and covariant contracts, nested generic arguments, and target conformances whose
  applied arguments are fixed versus derived from type parameters;
- safe projected targets from `Any` and other compatible sources, preserving the projected type
  for flow facts and safe-cast results;
- matching behavior for `is` and `as?`, including nullability, stable-binding flow refinement, and
  separately compiled library declarations;
- generated bytecode containing only the raw class/interface runtime test, with source-level casts
  and results checked against the proven target type.

## Accepted scope and entailment rule

- Generic targets are supported for `is` and `as?`; checked `as` retains its current generic-target
  rejection.
- Generic entailment uses Zeron-declared class and contract relationships, including transitive
  applied contract composition from source declarations and library indexes. Java external generic
  class-file relationships are deferred.
- A generic class target is accepted only when the target's declared applied contracts and the
  source's applied contract views determine every target type parameter and the same generic
  arguments exactly. A class parameter absent from the matching conformance does not become known
  merely because the conformance itself is fixed. Nested generic
  arguments and projections are supported when their complete applied shapes match. A covariant
  source contract argument must itself be statically final; a wider contract view such as
  `Tagged<Parent>` cannot determine `Implementation<Parent>` when `Implementation<Child>` may also
  satisfy it. Broad variance, conflicting or multiple applications, and unresolved mappings are
  rejected.
- A generic contract target is accepted when the source is already safely assignable to that applied
  target. From `Any` or `Any?`, a raw-class test may produce only a Zeron generic view whose every
  argument is `out Any?`; the resulting binding retains that projection.
- A failed proof uses the existing invalid runtime type-test/cast diagnostic and explains that the
  generic arguments are not statically determined.

## Discussion direction

The initial design discussion selected static-only generic arguments and rejected concrete
application narrowing from an unknown source. It also selected allowing an explicit safe projected
view, such as `Box<out Any?>`, as a raw-class test when the resulting binding preserves that
projection. The accepted scope excludes checked `as` and Java generic relationships.
