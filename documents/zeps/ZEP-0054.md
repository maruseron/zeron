# ZEP-0054: Nominal Effect Payload Types

## Abstract

Bring effect payload declarations closer to ordinary nominal classes by allowing them to declare
methods and conform to ordinary contracts. Preserve the effect marker that distinguishes raisable
payloads from regular classes, and keep raised-effect sets and handler matching exact.

## Motivation

Effects are already represented as nominal, class-backed payloads, but the resolver treats them as a
separate restricted declaration category. They cannot declare methods or implement contracts, which
prevents effect payloads from using the same reusable APIs as other nominal values. This restriction
does not follow from their runtime representation: a raised effect carries an ordinary generated
class instance.

Unifying the payload's nominal capabilities need not change the control-flow role of effects.
Ordinary contract conformance can describe payload APIs without implicitly making a contract a
raised-effect supertype or changing which handler cases match.

## Goals

- Allow an effect payload to use ordinary class members and conform to ordinary contracts.
- Retain an explicit effect marker; ordinary classes do not become raisable by implementing a
  contract.
- Preserve exact effect identity in `raises` declarations and handler cases.
- Preserve the current carrier-based runtime behavior unless a separate proposal changes it.
- Preserve effect and nominal API information across compiled-library boundaries.

## Non-goals

- Effect subtyping or a denotable top `Effect` type; see [ZEP-0013](./ZEP-0013.md).
- Effect-kinded generic parameters; see [ZEP-0055](./ZEP-0055.md).
- Generic effect declarations or applied generic effect identity; see [ZEP-0005](./ZEP-0005.md).
- Effect rows, resumable effects, first-class handlers, or automatic conversion to `Result`.

## Proposal

Keep the `effect` declaration form and its effect-kind marker, while applying ordinary nominal class
rules to its payload members and contract conformances. For example:

```zeron
public contract Retryable {
    retryDelay(): Duration;
}

public effect FileFailure is Retryable {
    public property path: String;

    public retryDelay(): Duration = Duration.fromNanoseconds(1000000000L);
}
```

The exact surface syntax remains subject to parser compatibility review; the example illustrates
that effect payloads can expose an ordinary contract API.

An effect may be raised, listed in `raises`, or named by a concrete handler case because it has the
effect marker, not because it conforms to a contract. Contract conformance supports ordinary
member access and generic bounds only. A handler for `Retryable`, for example, does not match every
effect that implements it under this proposal; effect subtyping remains separately specified.

Effect methods follow the callable rules for ordinary class methods, including visibility,
mutability, and raised-effect checking. Effect construction continues to use the existing class
construction rules. Effect classes remain final, as are other classes in the current language.

## Compatibility and impact

This is additive for source programs that use existing effects. Existing effects retain their
nominal identity, raised signatures, handler behavior, and runtime payload representation.

The compiled-library index already records effect markers. It must also preserve any effect member
and contract metadata not already represented by the ordinary exported-class format. A schema
change is required only if the current index cannot round-trip that information.

## Alternatives

- Keep effect payloads property-only and isolated — preserves the smallest model, but prevents
  ordinary contracts and methods from being reused.
- Treat every contract conformance as effect subtyping — rejected here because API capability and
  raised-effect inclusion have different handler and coverage consequences; see ZEP-0013.
- Make effects ordinary classes with no effect marker — rejected because any ordinary class could
  then be raised, losing the static distinction between values and control-flow effects.

## Implementation and validation

Align effect declaration registration with ordinary class member and conformance resolution while
retaining the effect-kind marker in the declaration registry and API index. Validate:

- effect methods, properties, constructors, and ordinary contract conformance;
- rejection of ordinary non-effect classes in `raise`, `raises`, and handler cases;
- exact `raises` compatibility and handler behavior despite contract conformance;
- effect payload use through separately compiled libraries and the versioned API index;
- unchanged exception-carrier behavior and Java checked-exception mappings.

## Open questions

- Should effect payloads support the full ordinary class member and mutability model, or should
  selected restrictions remain to encourage immutable, data-oriented payloads?
- Does the current compiled-library index fully preserve effect members and contract conformances,
  or is a schema revision needed?

open.
