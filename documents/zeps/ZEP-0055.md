## Abstract

Add the `effect` admissibility marker for generic type parameters, allowing generic declarations to
accept and propagate effect types while enforcing effect-kind membership at erased generic raise
sites.

## Motivation

Only concrete effect declarations can currently appear in `raise`, `raises`, and handler cases.
This prevents generic code from forwarding an effect supplied by its caller, even when it does not
inspect or handle that effect. A dedicated effect-kind constraint would let generic code state that
a type parameter is an effect and preserve that exact effect through callable signatures.

This is distinct from a generic effect declaration such as `Failure<T>`. A type parameter may stand
for an existing effect class without making effect applications generic or requiring the runtime to
distinguish erased effect arguments.

## Goals

- Add an effect-kind constraint, written `E: effect`, to every generic declaration that supports
  bounds, using the existing generic-bound syntax.
- Permit effect-kinded type parameters in `raise` expressions and `raises` lists.
- Propagate abstract effect identities through generic calls and function types by ordinary type
  substitution.
- Preserve exact effect-set identity and require callers to handle or declare unresolved effects.
- Keep handler cases concrete; the marker does not make unresolved generic effect identities
  available for runtime case matching.

## Non-goals

- Generic effect declarations or effect payload applications such as `Failure<T>`; see
  [ZEP-0005](./ZEP-0005.md).
- Effect-row polymorphism or implicit effect-set variables.
- Handler cases that test an unresolved effect type parameter.
- A denotable top `Effect` type, which is explored separately in [ZEP-0013](./ZEP-0013.md).
- Resumable effects, first-class handlers, or automatic Java-exception conversion.

## Proposal

A type parameter with the effect-kind constraint may only be instantiated with a non-null effect
type:

```zeron
fn relay<E: effect>(failure: E) raises E {
    raise failure;
}
```

The raised effect is the exact type argument substituted for `E`. Callers must handle that effect
or declare it in their own `raises` set. If the caller's type argument is not statically known, the
abstract effect remains in the escaping set.

The constraint is available wherever generic bounds are supported, including functions, methods,
classes, contracts, and extension methods. It composes with ordinary contract bounds using the
existing `+` syntax so effect payload APIs remain usable under their declared contracts.

Handler cases continue to name concrete effect declarations. A generic body cannot use `case E` to
test an unresolved type parameter: the kind constraint proves that `E` is an effect but does not
provide the concrete identity needed for case dispatch. A generic caller may specialize the callable
and handle the resulting concrete effect at a scope where that identity is known.

The effect-kind constraint is inherently non-null and cannot be combined with the `nullable`
admissibility marker. A nullable occurrence such as `E?` is still available and must be proven
non-null before it is raised. The effect-kind constraint is separate from ordinary contract
conformance. Implementing a normal
contract does not satisfy `E: effect`, and a non-effect class cannot be raised even if it implements
contracts also implemented by effects. If ZEP-0013 introduces the denotable top `Effect` type, it
satisfies the effect kind because it denotes only effect values; this does not accept the rest of
ZEP-0013. Instantiating `E` with `Effect` declares the broad top effect in the callable's
raised-effect set.

Generated effect payload classes carry a compiler-owned runtime effect marker. If introduced,
denotable `Effect` uses the same marker. A generic `raise` whose operand has an effect-kinded type
parameter checks that marker before raising the value. If an unchecked Java/raw-generic boundary
supplies an ordinary value, the check fails with `ClassCastException`. This check enforces
effect-kind membership without reifying generic arguments and does not enable `case E`.

## Compatibility and impact

This is additive for non-generic effect code. Generic function and function-type signatures may
carry type parameters in their raised-effect lists, so substitution, effect-set compatibility, and
compiled-library metadata must preserve the effect-kind constraint. The general non-null generic
default and explicit nullable opt-in are specified in ZEP-0010. The library-index schema may need a
version change if generic parameter metadata cannot currently encode these constraints.

The runtime carrier need not inspect the abstract effect type for propagation. Runtime enforcement
is localized to generic raise sites, where it prevents a non-effect value introduced through an
unchecked boundary from being raised.

## Implementation

Generated effect classes implement `zeron.runtime.EffectValue`. Generic `raise` sites call
`zeron.runtime.EffectSupport.requireEffect`; an invalid unchecked value fails with
`ClassCastException`. Both classes are included in generated outputs, and effect-kind metadata
round-trips through API-index schema version 10.

## Alternatives

- Restrict raising and `raises` to concrete effect declarations — simpler, but prevents generic
  forwarding APIs.
- Use an ordinary contract bound as the effect constraint — rejected because any ordinary class
  could implement that contract and become raisable.
- Permit generic handler cases immediately — rejected until the compiler has a sound runtime
  identity mechanism for unresolved effect types.
- Add generic effect declarations in the same proposal — rejected as separate scope because
  `Failure<Int>` and `Failure<String>` require applied-effect runtime identity.

## Implementation and validation

Represent the effect kind in generic declaration metadata and preserve it through type-parameter
substitution, raised-effect signatures, and library-index export/import. Validate:

- valid and invalid effect-kind substitutions across all generic declaration forms;
- generic `raise` and `raises E` propagation through direct calls, function values, and nested
  generic calls;
- effect-set inclusion after specialization and diagnostics when an effect escapes undeclared;
- rejection of handler cases on unresolved effect parameters;
- compiled-library round trips and Java/raw-generic boundary enforcement.

## Decision

Accepted and implemented 2026-10-20. `E: effect` permits exact generic effect propagation, rejects invalid values
at erased generic raise sites using a runtime marker check, composes with contract bounds using
existing syntax, admits the proposed top `Effect` type if introduced by ZEP-0013, and does not
permit handler cases on unresolved `E`.
