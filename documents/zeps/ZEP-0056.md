## Abstract

Add named, reusable declarations for stateless handlers of existing abortive typed effects. A
declaration contains effect cases and can be applied to a protected expression by name, while
preserving exact effect identity and allowing uncovered effects to propagate.

## Motivation

The current handler syntax embeds every case list at the expression being handled. Repeated handling
logic must therefore be copied or placed in ordinary functions that combine the operation and its
handling policy. Named handler declarations would allow a policy to be reused independently of the
operation without yet requiring a general structural handler type or anonymous handler expressions.

This is an intentionally smaller step than making handlers first-class values. The compiler can
know a named declaration's cases at each use site, while the type needed to store, pass, or abstract
over arbitrary handlers is deferred to [ZEP-0057](./ZEP-0057.md).

## Goals

- Declare named handlers with statically checked cases for existing concrete effect types.
- Apply a named handler to one expression with an explicit `handle` expression.
- Preserve abortive handling, exact nominal matching, and the protected expression's normal result
  type.
- Permit partial handling and propagate effects not completely handled by the declaration.
- Reuse the coverage and case-order rules of existing inline handlers.

## Non-goals

- First-class structural handler types, handler parameters, or anonymous handler expressions; see
  [ZEP-0057](./ZEP-0057.md).
- Effect subtyping or broad matching through `Effect`; see [ZEP-0013](./ZEP-0013.md).
- Generic effect payloads, abstract effect parameters, effect rows, or unresolved-effect matching.
- Continuation capture, resumption, implicit ambient handler scopes, or asynchronous handlers.
- A handler-composition operator.

## Proposal

Introduce a named handler declaration using `handler`. Handler declarations follow ordinary
declaration visibility and import rules. Cases are private implementation details of the handler;
the declaration exposes its statically determined handler shape, not its individual case functions.

```zeron
public handler EmptyString {
    case IoFailure(_): String = "";
}

handle (readFile(file)) with EmptyString;
```

Each `case` must name an existing, concrete effect declaration. The resolver validates the effect
identity and payload pattern, and rejects ordinary classes, contracts, type parameters, and other
non-effect types in that position. Cases use exact nominal identity; contract conformance and
effect subtyping do not broaden a case. Multiple cases for one effect are allowed and tried in
source order, matching inline-handler behavior.

All cases in a handler produce the same normal result type. At an application site, that type must
match the protected expression's normal result type, as with existing expression handlers. Effects
raised while evaluating a handler case escape outward and are not caught again by that handler.
An unmatched payload, failed refutable pattern, or failed guard propagates the original raised
effect outward.

Let `E` be the effects that may escape from the protected expression, `H` be the effects for which
the handler has complete, statically guaranteed coverage, and `G` be the
effects raised by handler cases. The application may raise `(E \ H) ∪ G`. An effect type with an
extra case not present in `E` is permitted and simply unused. An effect is in `H` only if at least
one case for it has an unguarded, irrefutable pattern; guarded or refutable cases do not prove
complete coverage, and separate refutable cases are not combined to infer exhaustiveness. These
rules are the same as for inline handlers.

Named handler declarations are stateless and cannot capture local values. A handler can be applied
directly by name with `handle (expression) with HandlerName;`. First-class values, including
anonymous handlers and handlers passed as parameters, are specified separately by
[ZEP-0057](./ZEP-0057.md). Handler composition is outside this proposal; nested applications remain
ordinary expression-scoped handling.

## Compatibility and impact

This is additive. Existing inline `handle` expressions retain their behavior. Public named
declarations require handler metadata in the versioned compiled-library index so consumers can
validate their cases, result type, handled effects, and handler-raised effects. A schema change is
needed only if the current index cannot represent that information.

## Alternatives

- Keep all handlers inline — avoids new syntax but leaves case logic coupled to the operation.
- Combine named declarations and first-class handler values in one initial feature — avoids a staged
  design, but expands the first implementation to include structural type identity and value
  lowering; the accepted scope separates that work into ZEP-0057.
- Declare a handler as an ordinary function over an effect payload — loses typed case coverage and
  propagation unless handler semantics are recreated separately.

## Implementation and validation

Implemented named handlers as immutable top-level or namespace values, with case signatures and
handler shapes preserved in compiled-library metadata. Applications use the same exact effect
matching and coverage analysis as inline handlers and lower to scoped dispatch over the existing
raised-effect carrier.

End-to-end tests cover separately compiled library imports, reuse, exact shape checking, residual
effect propagation, case-raised effects, guard failure propagation, and preservation of the original
raised-effect carrier when no case matches. First-class values and anonymous handlers are specified
and implemented by [ZEP-0057](./ZEP-0057.md).

## Open questions

None blocking acceptance. The declaration keyword is `handler`; visibility follows ordinary
declaration rules; cases preserve inline source ordering and coverage semantics; and composition is
deferred.

## Decision

Accepted on 2026-10-21. Named handlers use exact concrete effect matching and the current inline
handler coverage rules. They are stateless declarations applied by name; first-class handler values
are the separate scope of ZEP-0057, and composition is deferred.
