## Abstract

Add structural types for first-class abortive effect handlers. A handler type records the protected
computation's normal result type, the exact effects the handler completely handles, and the effects
raised by its cases. Named and anonymous handlers share this shape and can be passed through
statically typed APIs.

## Motivation

Named handler declarations can be applied where their declarations are visible, but they do not by
themselves provide a safe type for storing or passing arbitrary handler implementations. A generic
constraint such as `H: handler` is insufficient unless it also exposes the effects handled and
raised by `H`. A shaped type can make those capabilities explicit and can provide a path to
anonymous handler expressions.

The notation `R ~> {E1, E2} [raises {G1}]` denotes this shape. It intentionally differs from `->`:
`R` is the protected computation's normal result type; the first set lists effects the handler
completely handles, and the optional `raises` set lists effects its cases may raise. Omitting that
clause means the handler cases raise no effects; the explicit `raises {}` spelling is equivalent.

## Goals

- Define a first-class handler type that preserves handler capabilities during assignment and
  parameter passing.
- Record a common result type for handler cases and the exact effect identities they handle.
- Record effects raised by handler cases so they remain in the enclosing effect set.
- Make named and anonymous handlers values of the same structural type.
- Permit storing and passing handlers without losing their handled-effect guarantees.
- Preserve abortive semantics and explicit propagation of unhandled effects.

## Non-goals

- Resumable continuations or algebraic operation resumption; see [ZEP-0007](./ZEP-0007.md).
- Generic effect payloads, handler cases on unresolved effect parameters, or effect-row
  polymorphism.
- Effect subtyping or top-type matching unless separately accepted in [ZEP-0013](./ZEP-0013.md).
- Implicit ambient scopes, asynchronous handlers, or handler composition.

## Proposal

Define a structural handler descriptor with three semantic components:

1. the protected computation's normal result type `R`;
2. the finite set `H` of exact effect identities completely handled by the handler; and
3. the effect set `G` that may escape from evaluating handler cases.

Use `R ~> {E1, E2} [raises {G1}]` for a handler that preserves computations with normal result type
`R`, guarantees complete coverage for exact effects `E1` and `E2`, and may raise `G1` while handling.
Omitting `raises {G1}` means the handler cases raise no effects; writing `raises {}` explicitly is
equivalent. Effect names in either set must be concrete effect types. Each set is finite,
duplicate-free, and normalized by effect identity. The notation is domain-specific; `->` continues
to denote ordinary function types.

For example, an anonymous handler might be written:

```zeron
let h: String ~> {IoFailure, FileNotFound} raises {AuditFailure} = handler {
    case IoFailure(_) -> "";
    case FileNotFound(_) -> "";
};
```

An anonymous handler may capture immutable locals by value under the existing lambda capture rules.
Named handlers from [ZEP-0056](./ZEP-0056.md) have the same structural type but cannot capture local
values. Each handler case has the common result type `R`.

Applying a handler to a computation with normal result type `R` and possible raised-effect set `E`
preserves the normal result type and yields the escaping set:

```text
(E \ H) ∪ G
```

Only effects with complete, statically guaranteed case coverage belong to `H`, using the existing
inline-handler rule: an unguarded, irrefutable case is required. Additional handler cases outside
`E` are harmless. Handler-case code remains outside its own handling scope.

The protected expression's normal result type must exactly match `R` in the initial version.

The descriptor is structural: named and anonymous handlers with the same normalized result type and
effect sets have the same type regardless of declaration name. In the initial version, structural
compatibility requires an exact match of all three components; variance and subtype-based handler
assignability are deferred. Generic functions may accept a handler only when its concrete shape is
expressible in the parameter type. No handler-set or effect-row polymorphism is introduced.

Apply a handler value with the existing expression-scoped syntax, placing the handler value after
`with`: `handle (computation) with h;`. Handler composition is not part of this design. Programs may
use nested handler applications, each with ordinary scope and propagation semantics.

## Compatibility and impact

Handler shapes affect type compatibility and compiled-library metadata. The compiler may generate
a canonical JVM interface or dispatch adapter per handler shape, but the shape's identity must be
stable across separately compiled libraries. The source-level shape identity must remain independent
of generated JVM names. Adding this structural type and anonymous expressions may require a
library-index schema update.

## Alternatives

- Keep named handler declarations only — a smaller first step, but does not permit handlers to flow
  through typed APIs.
- Use a nominal base handler type — simple to name, but too weak to encode which effects are handled
  and therefore cannot safely calculate residual effects.
- Add only a `handler H` generic kind — limits admissible arguments without exposing the handler's
  handled-effect set, result type, or raised effects.
- Represent handlers as ordinary single-function values — cannot directly describe a heterogeneous
  set of effect-specific payload cases without an additional dispatch abstraction.

## Implementation and validation

Implemented structural handler types with exact compatibility across result type, completely
handled effects, and handler-case raised effects. Handler shapes are retained in the compiled-library
index, while JVM lowering reuses function-shape interfaces and lambda support. Named and anonymous
handlers share the same structural type; anonymous handlers use the existing lambda capture rules.

End-to-end tests cover assignment and argument passing, mismatched shapes, residual and
case-raised effect propagation, guarded-case rethrowing, immutable captures, and importing and
invoking named handlers across a compiled-library boundary.

## Open questions

None blocking acceptance. Generic effect-set abstraction, variance, effect-subtyping integration,
and composition are deferred.

## Decision

Accepted on 2026-10-21. First-class abortive handlers use exact structural shapes containing the
protected result type, complete handled-effect set, and handler-case raised-effect set. Named and
anonymous handlers share the shape; anonymous handlers may capture immutable locals by value.
Compatibility is exact, effect sets contain concrete effects only, and composition, variance,
effect subtyping, and effect-row polymorphism are deferred.
