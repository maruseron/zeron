# ZEP-0058: Clause-Based For-Expressions and Lazy Yield

## Abstract

This proposal evolves Zeron's ordered for-expression pipelines into a clause-based comprehension
syntax. It introduces explicit generators, local bindings, guards, and a final result clause. A
`yield` result clause produces a lazy `Stream<T>`, while collection remains an eager operation. The
syntax is intended to express nested traversal and intermediate computation without requiring users
to encode every step as one of a fixed set of pipeline operators.

## Motivation

Current for-expressions support an ordered set of `map`, `flatMap`, `filter`, `drop`, `take`,
`dropWhile`, and `takeWhile` stages, optionally ending in `collect`. This is concise for linear
transformations, but it is a closed pipeline vocabulary. Naming an intermediate value or expressing
another generator requires encoding the work inside a stage callback, particularly `flatMap`.

List-comprehension syntax can be concise but often has restricted composition rules, while more
general enumerator forms can make intermediate bindings feel like a specialized language within the
language. Zeron should make traversal, local computation, and filtering visible in source order using
familiar constructs, and retain a clear distinction between a lazy result and eager collection.

## Goals

- Express nested iteration, local bindings, and filtering in one ordered for-expression.
- Make the result projection explicit.
- Define lazy stream production separately from eager collection.
- Preserve left-to-right evaluation, lazy traversal, and short-circuit behavior.
- Permit straightforward lowering to existing stream operations initially, without promising stream
  fusion.

## Non-goals

- Guaranteeing stream fusion or eliminating intermediate iterators and callbacks.
- Replacing statement-form `for` loops.
- Defining general generator, coroutine, or resumable `yield` semantics.
- Adding a standard-library API reference or changing collection contracts as part of this proposal.
- Adding arbitrary control flow, such as `break` or `continue`, inside comprehension clauses.

## Proposal

Evolve for-expressions toward an ordered sequence of clauses. The core syntax is:

```zeron
for item in source
    let key = normalize(item)
    if isValid(key)
    for child in children(key)
    yield render(item, child)
```

An eager form uses the same clauses but names both the projected value and the sink:

```zeron
for item in source
    let key = normalize(item)
    if isValid(key)
    for child in children(key)
    collect render(item, child) into List<String>.empty()
```

The clauses have the following intended roles:

- `for name in expression` introduces a generator. Its iterable is traversed in order; a later
  generator is nested within the bindings established by earlier clauses.
- `let name = expression` evaluates a local value for each traversal path reaching that clause. The
  name is visible to subsequent clauses and the result clause.
- `if condition` is a guard. A false condition skips the remainder of the current path; a guard after
  a nested generator applies to each value produced by that generator.
- `yield expression` is the final lazy result clause. It defines each output element and makes the
  for-expression evaluate to a lazy `Stream<T>`. It does not consume the stream.
- `collect expression into sink` is the final eager result clause. It evaluates the sink once,
  evaluates the projected expression for each traversal path that reaches the clause, adds each
  result to the sink, and returns that sink. The Boolean result of `Sink<T>.add(T)` is ignored.

Exactly one result clause is required, and it must be last. `yield` and `collect` are alternatives:
there is no form that first yields a stream and then collects it within the same comprehension.
Collection does not require an intermediate `Stream<T>`; an implementation may traverse and add
directly.

Clause ordering is semantically significant. In the example, `normalize(item)` is evaluated once for
each source item that reaches the `let`; `children(key)` is evaluated only after the guard passes;
and `render` is evaluated as traversal demands output elements. Nested generators must be traversed
before advancing the preceding generator. A traversal that yields no values contributes no output.

The resulting stream is lazy: constructing the expression evaluates the outermost source expression
once but does not traverse it or execute per-element clause expressions. Each traversal requests
iterators from its sources as needed; later generator expressions are evaluated for each path that
reaches them. The language does not promise that those sources are replayable or produce the same
values on repeated traversal. Expressions outside the clauses that are captured by the comprehension
are evaluated at construction, consistent with the existing lazy for-expression model.

An eager `collect` evaluates the outermost source expression and sink expression once, in that
order, before traversal. Clause expressions then execute in lexical, depth-first order. Each projected
value is added immediately before traversal proceeds. If source, clause, projection, or sink addition
raises an effect or fails, evaluation stops at that point; already-performed effects and sink
mutations are not rolled back.

The clause markers are contextual keywords and do not become globally reserved identifiers.
Expressions in a clause end at the next clause marker at the same syntactic level or at the result
clause; nested expressions retain their ordinary grouping rules.

Replace the current operator-stage for-expression syntax rather than retaining it as a compatibility
form. The existing `Stream<T>` methods remain ordinary library operations, including `map`, `flatMap`,
`filter`, `drop`, `take`, `dropWhile`, and `takeWhile`; these are not additional comprehension clauses.
In particular, slicing and while-predicate behavior can be composed by calling stream methods on a
yielding comprehension. The surface syntax may change incompatibly because the language is pre-1.0;
the migration is a direct expression of the old transformations in clauses followed by `yield` or
`collect`.

## Compatibility and impact

This changes the source-language grammar and requires coordinated parser, AST, resolver, compiler,
diagnostic, formatter, syntax-highlighting, and documentation work. Existing operator-stage
for-expressions are intentionally not source-compatible; migration examples and diagnostics should
help users translate them. No runtime or standard-library change is required for a lazy form returning
the existing `Stream<T>` abstraction or for the eager form using the existing `Sink<T>` contract.

Normalize clauses into the existing internal `map`, `filter`, and `flatMap` pipeline representation
where practical: generators correspond to nested `flatMap`, guards to `filter`, and local bindings to
scoped mapping state. The implementation may add a small internal representation for lexical
environments rather than forcing source clauses into an unsuitable AST shape. The eager form may
continue to lower directly to iteration and sink additions.

A future fused lowering could represent clauses as a single iterator/state machine, but must preserve
clause order, laziness, short-circuiting, repeated-traversal behavior, captures, and exception/effect
behavior. Fusion is an implementation optimization, not a semantic guarantee of this proposal.

## Alternatives

- **Keep the current fixed stage pipeline** — concise for transformations and supports lazy/eager
  forms, but intermediate values and nested traversal remain callback-encoded; rejected in favor of
  explicit lexical clauses.
- **Adopt list-comprehension-only syntax** — compact for simple filters and mappings, but risks a more
  limited or surprising composition model.
- **Use conventional Scala-style enumerators** — expressive, but the design goal is to make
  intermediate computation read as ordinary `let`, guard, and generator clauses rather than
  introducing specialized binding vocabulary.
- **Make every for-expression eager** — simpler result ownership, but loses the existing lazy stream
  composition capability.

## Implementation and validation

Implemented on 2026-10-21. The parser represents ordered generator, local-binding, guard, and result
clauses explicitly. Resolution lowers them to existing stream operations, while eager collection
projects through the complete lazy pipeline before folding into the sink. The removed operator-stage
syntax is rejected; current tests and guide examples use the clause form.

Validation passed:

- `mvn -DargLine=--enable-preview test`
- VS Code editor tests (`npm test` from `editors/vscode`)

The implementation does not add generator functions, asynchronous sequences, fibers, or stream
fusion.

## Decision

Accepted on 2026-10-20. The project will replace the current operator-stage for-expression syntax
with the clause-based form. `yield` is the lazy result projection; a future generator function may
also use `yield` to suspend a producer while preserving its state, with the surrounding construct
distinguishing those related sequence-production contexts. Eager collection uses
`collect expression into sink`. General generator functions, asynchronous sequences, fibers, and
stream fusion are outside this proposal.
