# ZEP-0059: Removing Contract Constructor Requirements

## Abstract

Remove named constructor requirements from contracts and their associated conformance and witness
rules. Contracts describe behavior of existing values; construction is expressed through an HKT
factory capability for a type family or passed explicitly as a factory value for a particular type.

## Motivation

Contract constructors describe class-side factories, not behavior available on a conforming value.
They therefore make ordinary contract conformance depend on a class-level declaration that an
anonymous object cannot provide. Their generic use is also narrow: they provide convenient
construction through a bound, while HKT contracts can describe factories over a reusable type
constructor.

Separating value behavior from construction removes this friction without removing class constructors
or ordinary named factories. It also follows the separation already established by
[ZEP-0019](./ZEP-0019.md), which specifies HKT factory capabilities and explicit factory values in
place of contract constructor requirements.

## Goals

- Make ordinary contracts describe instance methods and properties only.
- Allow anonymous objects and witnesses to satisfy behavioral contracts without class-side factories.
- Use HKT capabilities for factories that operate over a generic type family.
- Keep non-generic factories explicit in function signatures.
- Remove constructor-requirement evidence and metadata rather than retaining a parallel mechanism.

## Non-goals

- Removing named constructors from classes or changing their direct static-call behavior.
- Requiring every factory to be represented as an HKT.
- Adding associated types, static abstract class members, or implicit factory discovery.
- Changing the instance behavior of unrelated ordinary contracts.

## Proposal

Remove constructor declarations from contract bodies. A contract may require instance methods,
properties, and other instance-level behavior, but it cannot require a named class-side factory.
Conformance checks no longer require a class to provide a matching constructor, and a witness no
longer maps a contract constructor requirement to a class constructor.

Class named constructors remain available as ordinary class-side factories. Keep `Sink<T>` as an
ordinary behavioral contract for adding to an existing sink, without a constructor requirement.
Generic collection families that provide both empty construction and insertion use a distinct HKT
capability:

```zeron
public contract Sink<T: nullable> {
    mut add(value: T): Boolean;
}

public contract Collector<C<_>> {
    empty<A: nullable>(): &C<A>;

    mut add<A: nullable>(this: C<A>, value: A): Boolean;
}
```

`Collector<C<_>>` is a constructor-family capability; it does not replace the per-value `Sink<T>`
contract. Its `add` operation is intentionally repeated so a generic API that creates an empty
collection and populates it can use one family bound, for example `C<_>: Collector<C>`. An API that
only mutates an existing value continues to require `Sink<T>` and does not need construction
evidence. Families whose element operations do not impose additional unexpressed bounds can provide
both ordinary `Sink<T>` behavior and the HKT `Collector<C<_>>` capability; `List<_>` is the initial
standard-library implementation. A factory for a particular, non-generic target continues to be
passed explicitly rather than turned into an HKT.

### Member-call and evidence selection

Both behavioral contracts and HKT contracts may declare receiver operations. Receiver lookup uses
these precedence tiers:

1. A concrete nominal instance method has precedence over contract evidence.
2. If one or more ordinary behavioral contract bounds provide the receiver method's name, that
   tier wins. A unique requirement is selected; independent conflicting requirements are ambiguous.
   A type, arity, or mutability error in this tier does not fall through to an HKT operation of the
   same name.
3. Only when no ordinary contract bound provides that name are HKT receiver operations considered.
   A unique operation is selected; multiple independent HKT providers are ambiguous.

Collision is determined by member name before argument applicability, so a contract method cannot
silently redirect to an HKT operation because its signature does not fit a particular call. A
requirement reached repeatedly through contract composition is one provider. Bound source order
does not select between independent providers. Explicit constructor calls such as `C.add(sink,
value)` always select HKT evidence directly and bypass receiver lookup precedence.

This proposal does not introduce requirements between ordinary contracts and HKT contracts in
either direction. `Collector<C<_>>` declares both operations directly; a future proposal may define
one-way cross-kinded requirements and their evidence propagation if needed.

A factory for a particular, non-generic target is passed explicitly, for example as `() -> C`, or
through a factory object. The API should express whether it needs to create a value rather than
assuming construction is implied by the value's behavioral contract.

For example, a `TokenFactory` contract that only requires `constructor from(value: Int)` becomes an
explicit factory parameter or a value-level factory object. A class can still expose
`Token.from(value)` for direct callers; that named constructor simply does not become a requirement
of every `Token` implementation.

## Compatibility and impact

This is an intentional source incompatibility for contract declarations, conformance, witnesses,
and generic calls that rely on contract constructor evidence. It also clarifies receiver lookup when
ordinary and HKT contract evidence overlap. Zeron is pre-1.0, so the migration is direct rather than
retaining a compatibility form.

The standard library's `Sink<T>.empty()` constructor requirement moves to `Collector<C<_>>`.
`Sink<T>` remains the behavior contract for existing sink values, while collection-family
implementations provide the `Collector<C<_>>` operations for generic construction and insertion.
Generic APIs migrate to the capability they actually need: an applied HKT constructor bound such as
`C<_>: Collector<C>` when creating and populating a collection, or `Sink<T>` when only adding to an
existing value. Concrete class constructors and direct calls remain unchanged.

The compiled-library index must no longer export contract constructor requirements or witness
factory mappings. Advance its schema version if removing this metadata changes the encoded format;
indexes with the previous schema must be rejected rather than interpreted under the new rules.
HKT implementation metadata for `Collector<C<_>>` must continue to round-trip across
compiled-library boundaries.

## Alternatives

- **Keep contract constructors and forbid anonymous conformance to those contracts** — preserves
  existing behavior but retains the mismatch between instance behavior and class-side creation.
- **Allow anonymous objects to invent constructor behavior** — rejected because an object value has
  no class-side constructor or type-family identity.
- **Use HKT factories for every factory** — rejected for non-generic targets, which do not form a
  constructor family and are more directly represented by an explicit function or factory object.
- **Use an HKT factory-only contract alongside `Sink<T>`** — viable, but rejected here because
  generic collection-building APIs would need separate factory and insertion evidence despite
  always using them together.
- **Split HKT sink creation and insertion into separate contracts** — rejected for this migration:
  collection-family construction and population form one capability for APIs that need both.

## Implementation and validation

Remove contract-constructor parsing, conformance validation, witness remapping, evidence selection,
and API-index export/import support. Retain `Sink<T>` as the ordinary behavioral contract and move
its constructor requirement into the HKT `Collector<C<_>>` in `zeron.collections`. Migrate generic
APIs to use ordinary sink evidence or collector-family evidence according to whether they construct
a value. Use a targeted diagnostic for contract constructor declarations and obsolete witness
constructor mappings so migration failures identify the removed feature directly.

Validate that:

- classes and anonymous objects can satisfy behavioral contracts without constructor obligations;
- ordinary methods, properties, defaults, and transitive contract requirements remain unchanged;
- HKT `Collector<C<_>>` implementations provide `empty` and mutable `add` for the expected applied
  types and work across compiled-library boundaries;
- `Sink<T>` receiver calls and `Collector<C<_>>` explicit calls select their intended evidence when
  both bounds are available;
- conflicting methods from independent contract bounds report ambiguity instead of depending on
  bound order;
- mutating `Sink<T>` methods are callable through a generic bound only in a mutable receiver
  context, following the same mutability rules as other instance methods;
- generic APIs can mutate an existing `Sink<T>` without requiring a family constructor;
- generic APIs can construct and populate a collection family through one applied HKT bound;
- a non-generic factory can be passed explicitly and is not inferred from the target contract;
- class named constructors remain callable directly;
- old contract-constructor declarations and witness mappings receive the targeted migration
  diagnostic;
- library indexes round-trip under the new schema and reject incompatible prior schemas.

## Resolved design decisions

- The standard library's HKT `Collector<C<_>>` belongs in `zeron.collections`; it is a collection
  capability rather than a general-purpose factory abstraction.
- Constructor declarations removed by this proposal receive a targeted migration diagnostic rather
  than the parser's general unsupported-syntax diagnostic.
- `Sink<T>` remains the ordinary value-level behavior contract. `Collector<C<_>>` is the HKT family
  capability that combines creation and insertion; its `add` operation is intentionally present in
  both abstractions for their different use cases.
- Receiver syntax supports both behavioral and HKT operations. Behavioral contract bounds win name
  collisions; HKT receiver lookup is the fallback, with explicit constructor-qualified calls
  available to select HKT evidence directly. Member lookup is source-order independent and reports
  ambiguous independent providers.
- Cross-kinded contract requirements are not part of this proposal.

## Decision

Implemented: contract constructor requirements and witness factory mappings are removed; ordinary
`Sink<T>` behavior remains, and the combined HKT `Collector<C<_>>` capability supports generic
collection construction and insertion. `Collector.empty` returns a mutable reference, and receiver
dispatch follows the precedence rules above.
