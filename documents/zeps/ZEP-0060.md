# ZEP-0060: Treating Arrays as Iterable Values

## Abstract

Allow a non-null `Array<T>` to be used wherever `Iterable<T>` is expected, including ordinary
function arguments, results, assignments, and generic contract bounds. Preserve the existing
intrinsic array iteration path while providing an adapter when an array must be represented as an
`Iterable<T>` value.

## Motivation

Zeron already permits arrays in `for` loops through intrinsic compiler support. That special-case
iteration does not make `Array<T>` compatible with the nominal `Iterable<T>` contract, so an array
cannot currently be passed to a reusable API such as:

```zeron
fn first<T: nullable>(values: Iterable<T>): T = ...
```

This forces callers to copy or wrap arrays even when an API only needs to iterate them. The
standard library already has `ArrayIterator<T>`, but an `iterator()` extension alone does not
establish contract compatibility or provide a value implementing `Iterable<T>`.

## Goals

- Let `Array<T>` satisfy `Iterable<T>` in all ordinary type positions, not only in loop syntax.
- Support passing arrays to contract-typed parameters and discharging concrete generic bounds
  requiring `Iterable<T>`.
- Preserve element type identity and array invariance.
- Avoid copying array elements when adapting an array to an `Iterable<T>` value.
- Preserve the existing direct, intrinsic lowering of array iteration.

## Non-goals

- General structural typing for contracts based on method names.
- Making arrays general witness targets or changing witness coherence rules.
- Making arrays covariant or allowing an `Array<A>` to satisfy `Iterable<B>` through variance.
- Adding resize, collection, or mutation operations to `Array<T>`.
- Changing iteration semantics for integer ranges or other `Iterable<T>` implementations.

## Proposal

Treat each non-null `Array<T>` as having a built-in conformance to `zeron.collections.Iterable<T>`.
The conformance is intrinsic to the compiler-known array type; it is not declared with a source
`witness`, because arrays are represented by a dedicated intrinsic descriptor rather than a
nominal Zeron type.

The conformance applies wherever normal type compatibility or generic-bound evidence is checked.
For example, an array can be passed directly to an `Iterable<T>` parameter:

```zeron
fn sum(values: Iterable<Int>): Int = ...

fn fromArray(values: Array<Int>): Int = sum(values);
```

It also supplies concrete evidence for a generic bound:

```zeron
fn consume<T: Iterable<Int>>(values: T): Unit = ...

fn fromArray(values: Array<Int>): Unit = consume(values);
```

The element argument must match exactly in the initial version. Since `Array<T>` is invariant,
this proposal does not make `Array<Subtype>` usable as `Iterable<Supertype>` through covariance.
Nullable element types remain supported when they satisfy the existing `Iterable<T>` bound;
nullable array references do not satisfy a non-null `Iterable<T>` requirement without explicit
null handling.

When an array is used in a context that requires an `Iterable<T>` JVM value, provide a lightweight
adapter implementing `Iterable<T>`. The adapter holds the original array and delegates
`iterator()` to `ArrayIterator.from`; it does not copy elements. Thus, writes through another
mutable alias remain visible when the iterable is consumed. An adapter is needed at a type boundary
because a JVM array cannot itself implement Zeron's generated contract interface.

Array iteration in a `for` statement or a clause-based for-expression remains on the current
intrinsic path and does not need to allocate the adapter. The existing public array `iterator()`
extension may remain as a direct API; it is not itself the conformance mechanism.

## Compatibility and impact

This is an additive source-level compatibility rule. Existing array types, mutability rules, loop
behavior, and JVM array representation remain unchanged. Calls or assignments that previously
rejected an array where `Iterable<T>` was expected will become valid.

The compiler must insert the adapter at boundaries that require the contract representation,
including function arguments, returns, assignments, and generic-bound evidence. The adapter must
preserve the original array reference and use the ordinary `Iterable<T>` contract dispatch for
default and required methods. No public API-index schema change is expected unless the selected
representation requires new serialized metadata.

## Alternatives

- Require a manual wrapper at each call site — works with current nominal contracts but leaves
  routine array-to-iterable adaptation to users.
- Add overloads for arrays to every iterable API — avoids a conversion but duplicates APIs and does
  not help user-defined generic functions.
- Treat any type with an `iterator()` method as `Iterable<T>` — would introduce structural
  conformance beyond arrays and change contract semantics globally.
- Permit `Array<T>` as a general witness target — conflicts with the intrinsic array type model and
  would require a broader extension to witness representation and runtime dispatch.

## Implementation and validation

Implement intrinsic conformance and adapter lowering for `Array<T>` to `Iterable<T>`, including
generic-bound evidence. Validate:

- passing arrays to `Iterable<T>` parameters, returning them, and assigning them to iterable values;
- use of arrays to satisfy concrete generic bounds and calls through both required and default
  contract methods;
- nullable elements, exact element-type matching, and rejection of nullable array references where
  a non-null iterable is required;
- preservation of mutable-alias visibility and absence of element copying;
- unchanged intrinsic array iteration in loops and for-expressions;
- separately compiled libraries consuming iterable values produced from arrays.

## Open questions

- Should the adapter be allocated per conversion or be reused where the compiler can prove that
  doing so preserves object identity and observable behavior?
- Should source-level `Array<T>` conformance be exposed in member-discovery metadata, or remain an
  intrinsic compiler rule only?
