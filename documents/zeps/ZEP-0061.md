## Abstract

Provide language-server hover, completion, and go-to-definition support for Java types and
external bindings. Editor results should describe the same Java members and external declarations
that the compiler can resolve, and should navigate to Java source when available or to the
corresponding Zeron binding otherwise.

## Motivation

Zeron's Java interop is explicit and compiler-resolved, but editor support does not yet consistently
expose that information. A qualified Java type can be valid in a signature without useful
completion or navigation, and an external class or function binding may not provide enough context
to understand which Java symbol it represents. This makes interop declarations harder to author
and use, particularly when the Java API is surfaced through curated external facades.

The language server should make the existing interop boundary visible without suggesting Java
members that the compiler would reject.

## Goals

- Show useful hover information for qualified Java types, external classes, external functions,
  and external-class members.
- Offer completion for Java and external members supported by the active interop resolver and
  visible external facade declarations.
- Navigate from Java type and member references to Java source when source is available.
- Navigate from Java references and calls to the matching Zeron external declaration when Java
  source is unavailable or the reference is provided through an external facade.
- Navigate from Zeron uses of external functions and facade members to their Zeron declarations.
- Keep editor visibility, access checks, overload selection, and supported signatures consistent
  with compiler resolution.

## Non-goals

- Expanding the Java signatures, members, conversions, or type mappings accepted by the compiler.
- Providing general Java reflection, package scanning, implicit imports, or unrestricted
  completion from every classpath entry.
- Requiring Java source attachments or adding a Java build-system importer.
- Replacing curated external-class facades with automatic facade generation.
- Implementing Java-aware refactorings or semantic diagnostics beyond what hover, completion, and
  navigation require.

## Proposal

Use compiler interop metadata as the authoritative source for editor features. Java type lookup
should use the same explicit qualified names, configured classpath roots, exported JDK packages,
and supported type subset as compilation. Completion should list only accessible constructors,
methods, and fields accepted by the resolver, including the methods intentionally exposed through
an external-class facade. Results must respect imports, aliases, visibility, static-versus-instance
context, and overload resolution.

Hover should identify the Java binary type or member and show its supported signature. For external
declarations it should also identify the external binding, for example the Java class name behind an
external class or the resolved Java target of an external function. Raised effects and mapped Java
exceptions should be shown where the declaration carries that information.

Go-to-definition should choose the most useful available source target:

1. Navigate to Java source for a resolved Java type or member when an appropriate source attachment
   can be located.
2. Otherwise, navigate to the Zeron external-class or external-function declaration that exposes
   the resolved Java symbol, when such a declaration exists.
3. If neither source is available, return no definition rather than a misleading location.

For a Zeron call through an external binding or facade, navigation should prefer its Zeron
declaration when that declaration is the API the user is invoking. For a direct Java call,
navigation should prefer the Java declaration when source is available. Exact precedence for
overlapping facade and Java targets remains an open question.

The language server may expose completion and hover for Java symbols that do not have a Zeron
facade, but only when those symbols are discoverable through the compiler's existing explicit
interop resolution. It must not imply that an incomplete or unsupported Java signature is callable.

## Compatibility and impact

This proposal changes editor behavior only; it does not change source compatibility, generated
bytecode, Java interop semantics, or runtime behavior. It may require exposing Java classpath and
member metadata from analysis to the language server and retaining source locations for external
bindings. Java source navigation may require support for source attachments or a bounded mechanism
for locating source archives.

Completion and navigation must remain responsive for large classpaths. Any indexing or source
lookup should be bounded, cancellable where practical, and avoid scanning packages not explicitly
referenced or imported.

## Alternatives

- **Support only Zeron external declarations** — simpler and deterministic, but leaves qualified
  Java types and direct interop calls without useful editor support.
- **Use a separate Java language server for all Java symbols** — can provide richer Java navigation
  when configured, but does not by itself connect Zeron references to the interop resolver or
  external facade declarations.
- **Reflect over all classes and packages on the classpath** — could produce broad completion, but
  would conflict with explicit lookup, be expensive, and suggest members unsupported by Zeron.

## Implementation and validation

Implement in stages:

1. Represent resolved external and Java symbols, their supported signatures, binding targets, and
   source locations in an editor-facing model without duplicating compiler resolution rules.
2. Add hover and go-to-definition for source-level external declarations and resolved Java types.
3. Add completion and navigation for supported Java constructors, methods, and fields, preserving
   visibility and overload behavior.
4. Add Java source navigation when source is available, with external-declaration fallback and
   explicit behavior when no source is available.

Validate Java types resolved from JDK modules and configured classpath roots; aliased and qualified
imports; external class and external function declarations; static and instance members;
overloads, varargs, access restrictions, and unsupported signatures; mapped checked exceptions;
source-present and source-absent navigation; and completion behavior for unsupported or unresolved
qualified names. Verify that editor suggestions never claim a call is valid when compiler
resolution rejects it.

## Open questions

- Should Java source navigation initially support attached source archives only, or also source
  trees discoverable from project configuration?
- When a Java call is exposed through an external facade, should go-to-definition prefer the
  facade declaration, Java source, or depend on whether the reference is written in a facade body?
- Which Java symbols should be offered by completion: only symbols reached through existing type
  resolution, or also members of explicitly imported Java classes?
- How should the language server present Java symbols for which the compiler has metadata but no
  source location or external Zeron declaration?
- Should external-function binding targets be displayed in hover using source-level binding
  syntax, resolved Java owner/member names, or both?
