# ZEP-0062: Mutable-Type Admissibility for Generic Parameters

## Abstract

Add a `mut` admissibility marker for first-order generic type parameters and make mutable-reference
type arguments inadmissible by default. Generic declarations that intentionally accept and preserve
mutable-reference arguments opt in with `T: mut`. The marker controls which arguments may be
substituted; it does not grant generic code permission to perform mutations.

## Motivation

Zeron's `&T` is a mutable-capability view, while plain `T` is read-only. Generic type parameters
currently accept mutable-reference arguments without an explicit declaration of that capability.
As a result, generic APIs can transport mutable authority even when their declarations do not
indicate that they intend to accept it.

For example, a comparison contract does not mutate its argument, but declaring
`Comparable<&Duration>` makes its `compareTo` parameter mutable-capability. Such uses should be
expressed with a read-only type argument. More generally, generic declarations that do need to
preserve mutable-reference arguments should make that intent visible, just as nullable arguments
and effect types use explicit admissibility markers.

## Goals

- Make mutable-reference type arguments inadmissible for ordinary first-order type parameters by
  default.
- Provide an explicit `mut` marker to opt a type parameter into accepting mutable-reference
  arguments.
- Preserve the existing distinction between argument admissibility and operations available in a
  generic body.
- Apply the rule consistently to generic functions, methods, classes, contracts, and witnesses.
- Keep mutability as a compile-time capability with no new JVM runtime representation.

## Non-goals

- Adding ownership, borrowing, uniqueness, or aliasing guarantees. `&T` remains a capability, not
  proof of exclusive access.
- Allowing a marker to replace contract bounds or to grant access to methods not otherwise
  available through a bound.
- Changing mutating receiver, field, property, or array rules.
- Applying `mut` admissibility to higher-kinded constructor parameters such as `F<_>` in this
  proposal.
- Redesigning variance or allowing mutable references in covariant positions.

## Proposal

Use the existing generic-bound syntax to declare mutable-reference admissibility:

```zeron
fn identity<T: mut>(value: T): T = value;
```

Without the marker, a type parameter accepts read-only type arguments but rejects a mutable
reference view:

```zeron
fn read<T>(value: T): T = value;

let item: &Widget = ...;
read(item); // rejected: T does not admit mutable-reference arguments
identity(item); // accepted: T: mut explicitly admits them
```

The `mut` marker permits, but does not require, a mutable-reference argument. It is an
admissibility rule, not a promise that every substitution is mutable. Existing mutable-to-read-only
projection remains available where it is already type-safe; no conversion may create mutable
capability from a read-only view.

The check applies to the type argument at the current generic parameter boundary. It does not
recursively scan the argument's entire type structure for mutable references. Each nested generic
application enforces the admissibility declared by its own type parameters. Thus, whether a type
such as `Array<&Widget>` is valid is determined by `Array`'s parameter policy; an outer parameter
accepting that `Array` type does not repeat the nested check.

Admissibility is independent of contract bounds. A declaration may combine `mut` with ordinary
bounds, for example `T: mut + Inspect<T>`. The marker only permits mutable-reference type arguments;
it does not make a mutating operation available on `T`. Such operations remain governed by the
existing member and contract rules.

`mut` and `nullable` describe independent properties and should be combinable. For example,
`T: nullable + mut` admits nullable type arguments and mutable-reference arguments; each property
is still checked independently. The `effect` marker cannot be combined with `nullable` or `mut`:
effect-kinded parameters continue to represent exact effect identities, not mutable-reference views
of those effects. When an effect value arrives through a mutable reference, the effect-kind boundary
normalizes it to the nominal effect identity rather than propagating the reference capability.

The admissibility check applies consistently to explicit type arguments and inferred substitutions,
including constructor and expected-type inference. The resolver must retain a mutable-reference
argument when `T: mut` is used rather than erase or silently weaken its capability. Generic
substitution and type identity continue to preserve the existing reference/view qualifier.

Mutable-reference types remain invariant under the existing variance rules. This marker does not
make mutable arguments safe in covariant positions or change use-site projection behavior.

This proposal applies to first-order type parameters declared by Zeron. Higher-kinded constructor
parameters remain outside its scope. Imported Java generic parameters retain their existing
interoperability behavior; they do not acquire the new default or the `mut` marker through this
proposal.

## Compatibility and impact

This is source-incompatible for generic applications that currently infer or explicitly supply a
mutable-reference type argument to an unmarked parameter. Those declarations must opt in with
`T: mut` when accepting and preserving such arguments is intended, or use a read-only type when
mutation capability is unnecessary. The standard library, examples, and tests need an audit to
distinguish those cases.

Type-parameter admissibility is preserved in compiled library metadata. The API index encodes and
round-trips the new property; its schema version is coordinated with the other API-index changes in
the current release cycle. No runtime class or descriptor change is required.

Java generic declarations are not governed by this marker. Java interop behavior, including how
Java type parameters admit arguments, continues to follow the existing mapping rules.

## Alternatives

- Continue admitting mutable-reference arguments by default — avoids source migration, but leaves
  capability flow implicit at generic boundaries.
- Make every generic parameter read-only and provide no opt-in — gives a stricter default but
  prevents reusable generic containers and functions from deliberately carrying mutable views.
- Treat `mut` as a requirement that every argument be mutable — rejected for this proposal because
  it would not express the intended opt-in to capability-carrying generic APIs and would make
  ordinary arguments unusable with the marked parameter.
- Rely only on contract bounds — rejected because a bound describes available operations, not
  whether the type argument itself may carry a mutable-reference capability.

## Implementation and validation

Implementation:

- Added and preserved mutable admissibility through type substitution, function signatures,
  conformance, public member metadata, and API-index serialization.
- Enforced the boundary rule for explicit and inferred arguments across supported generic
  declarations while retaining existing Java generic behavior.
- Audited and migrated standard-library generic APIs that intentionally carry mutable references.
- Verified that admissibility does not authorize mutating member calls without the corresponding
  mutable receiver or contract bound.
- Tested nullable-plus-mutable combinations, generic bounds and inference, formatter output,
  parser rejection of invalid marker combinations, and compiled-library round trips.

## Decision

Accepted 2026-10-21; implemented 2026-10-21. Generic mutability is explicit:
mutable-reference arguments are rejected by default, and `T: mut` admits them while retaining
ordinary arguments. Admissibility is checked at each generic parameter boundary, applies to
first-order Zeron-declared parameters, and does not change imported Java generic behavior. `mut`
cannot be combined with the `effect` marker.
