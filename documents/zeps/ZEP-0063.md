## Abstract

This proposal explores a `zeron.test` package for writing, discovering, and running automated
tests for Zeron projects. It aims to provide a small standard test API and a clear command-line
workflow without requiring every project to adopt a separate test framework.

## Motivation

Projects need a consistent way to express test cases, report failures, and run tests during
development and automation. A standard package can make tests discoverable to new users and give
the compiler and CLI a stable integration point.

## Goals

- Provide a small API for assertions and test failure reporting.
- Define how test cases are declared, discovered, executed, and summarized.
- Integrate test execution with project source roots and command-line workflows.
- Keep test-only APIs separate from ordinary application dependencies and runtime behavior.

## Non-goals

- Mocking, code coverage, benchmarking, or property-based testing in the initial scope.
- Replacing external test runners or preventing projects from using them.
- Specifying a general build automation or continuous-integration system.

## Proposal

Add a `zeron.test` package with assertion helpers and a runner for project test cases. Test
execution should report each failure with enough context to identify the test and assertion, return
a non-zero process status when any test fails, and produce deterministic summaries suitable for
human and automated use.

The package should support isolated tests that do not require application entry-point behavior.
The exact declaration or registration mechanism, test source layout, and relationship to ordinary
project source roots remain open. The design should avoid silently including test declarations in
normal application builds or shipping test-runner implementation details as application runtime
dependencies.

## Compatibility and impact

The package adds public standard-library API. If test discovery requires compiler or CLI support,
that support must be designed to coexist with the existing `build` and `run` workflows. The
implementation should specify whether tests compile with production sources, against a separately
compiled library, or through another explicit project configuration.

## Alternatives

- Use third-party test frameworks only — avoids standardizing a framework, but leaves the language
  without a consistent entry-level testing workflow.
- Add only assertion functions — simple, but does not define discovery, execution, or reporting.
- Integrate tests into ordinary program entry points — reuses `run`, but mixes application and test
  behavior and complicates automation.

## Implementation and validation

Validate assertion behavior, test discovery and ordering, failure isolation, output and exit status,
project configuration, and behavior when no tests are found. Include tests for compiled-library
consumers and verify that normal application builds do not acquire test-runner dependencies.

## Open questions

- How should a test case be declared: a naming convention, annotation/attribute, explicit registry,
  or generated test entry point?
- Should the CLI expose a dedicated `zeron test` command, and how should test sources be configured?
- Which output formats are required initially beyond a concise text summary?
- Should setup/teardown or fixtures be included in the first API?
