## Abstract

This proposal defines a standard testing surface for Zeron projects. Tests are ordinary top-level
functions marked with `@Test`; a small `zeron.test` package provides assertions that raise a typed
`TestFailure` effect; the compiler discovers tests at compile time and generates a runner; and the
`zeron test` command builds and runs test targets declared through the project manifest. The design
builds on the shipped declarative target model from [ZEP-0117](./ZEP-0117.md) and keeps test code
out of application builds and runtime artifacts.

## Motivation

Projects need a consistent way to declare test cases, report failures, and run tests during
development and automation. Today every project that wants tests must either adopt an external
framework with its own conventions or write ad hoc entry points. Neither option gives the compiler
and CLI a stable integration point, and both make test discovery and reporting project-specific.

A standard testing surface makes tests discoverable to new users, lets the compiler validate test
declarations and generate a deterministic runner, and gives the CLI one command with predictable
exit status. It also keeps test-only APIs separate from ordinary application dependencies: the test
runner is generated only for test targets and never ships as part of an application build.

## Goals

- Declare tests with the existing declarative annotation model rather than a new declaration form.
- Provide a small assertion API whose failures are typed values, not host exceptions.
- Discover tests at compile time, with no runtime reflection or manual registration.
- Generate a deterministic runner for a test target and report per-test results plus a summary.
- Add a dedicated `zeron test` command with project-manifest configuration.
- Keep test sources out of application builds and out of shipped runtime dependencies.
- Reuse the project target, source-root, warning, and generated-documentation machinery from
  ZEP-0117.

## Non-goals

- Mocking, dependency injection, code coverage, benchmarking, or property-based testing.
- Compatibility with JUnit, TestNG, or another host test framework's annotations or lifecycle.
- General runtime reflection or an annotation query API; discovery is compile-time only, following
  [ZEP-0091](./ZEP-0091.md).
- Process-per-test isolation, parallel execution, timeouts, or resource sandboxing in the first
  version.
- Machine-readable result formats, test filtering, fixtures, setup/teardown hooks, or parameterized
  tests in the first version. The design leaves room for them as compatible additions.
- A general build system, task graph, or arbitrary command runner.

## Proposal

### Test declarations

`zeron.test` declares two annotations using the existing annotation syntax from
[ZEP-0031](./ZEP-0031.md):

```zeron
package zeron.test;

public annotation Test on FUNCTION;
public annotation Ignore(reason: String = "") on FUNCTION;
```

The canonical identities are `zeron.test.Test` and `zeron.test.Ignore`. A user-declared annotation
with the same simple name but a different package is not a test annotation. The compiler recognizes
only these canonical identities, in the compile-time direction permitted by ZEP-0091.

A test is a top-level function, optionally declared inside a namespace, that satisfies all of the
following:

- it is annotated with `@Test`;
- it is `public`;
- it declares no type parameters, no parameters, and no variadic parameter;
- it returns `Unit`;
- it may declare any raised-effect set.

Extension methods, contract methods, constructors, class members, and external functions are not
test declarations even when annotated. `@Test` and `@Ignore` are rejected outside a test root.

`@Ignore` may appear only on a function that also has `@Test`. Its optional `reason` argument is
reported with the skipped test. An ignored test is still validated for the signature rules above.

A minimal test unit looks like this:

```zeron
package app;

import zeron.test.Test;
import zeron.test.assertEquals;

@Test
public fn additionAddsOperands(): Unit raises TestFailure {
    assertEquals(4, 2 + 2);
}
```

### Assertion API

`zeron.test` provides a typed failure effect and a small set of assertions:

```zeron
public effect TestFailure {
    property message: String;
}

public fn fail(message: String): Unit raises TestFailure;

public fn assertTrue(condition: Boolean,
                     message: String = "expected condition to be true"): Unit raises TestFailure;

public fn assertFalse(condition: Boolean,
                      message: String = "expected condition to be false"): Unit raises TestFailure;

public fn assertEquals<T: Eq<T> + Display>(expected: T, actual: T,
                                           message: String = ""): Unit raises TestFailure;

public fn assertNotEquals<T: Eq<T> + Display>(unexpected: T, actual: T,
                                              message: String = ""): Unit raises TestFailure;

public fn assertNull<T: nullable>(value: T?,
                                  message: String = "expected a null value"): Unit raises TestFailure;

public fn assertNotNull<T: nullable>(value: T?,
                                     message: String = "expected a non-null value"): Unit raises TestFailure;

public fn assertApproximatelyEquals(expected: Float, actual: Float, tolerance: Float,
                                    message: String = ""): Unit raises TestFailure;
```

Assertions raise `TestFailure` instead of returning a result or throwing a host exception. This keeps
failures inside the language's typed-effect model: a test that calls an assertion declares
`raises TestFailure`, and the generated runner handles that effect. `assertEquals` and
`assertNotEquals` require `Display` so the default message can render both values; types without a
`Display` witness can use `assertTrue` with an explicit predicate and message.

The failure message is the only payload in the first version. Per-assertion source locations,
structured expected/actual values, and host exception capture are follow-ups; a test can already
convert a host exception explicitly through `Effect.fromException` if it needs to assert on one.

### Discovery

Discovery runs during project compilation for a test target, over the project's test roots:

1. Every parsed test unit is checked for `@Test` and `@Ignore`.
2. Each annotated function is validated against the signature rules.
3. Ignored tests are collected as skipped; all others are collected as runnable.
4. Runnable and skipped tests are ordered lexicographically by fully qualified name, where the name
   includes the package, optional namespace, and function name.

The order is deterministic across builds and platforms. It is not source order, and tests must not
depend on it. Duplicate fully qualified names are already rejected by normal declaration rules.

Test functions must be `public` so the generated runner can invoke them from its synthetic holder.
Package-private or private test functions are rejected with a diagnostic rather than silently
skipped.

### Generated runner

For a test target, the compiler generates a synthetic runner entry unit after resolution. The runner
is not written to a source root and is not part of the standard-library or compiled-library API
index. Its observable behavior is fixed by this proposal; whether the compiler represents it as an
internal AST or as generated Zeron source is an implementation detail.

The runner:

- invokes each runnable test in discovery order;
- invokes each test inside a handler that catches `TestFailure` before the general `Effect` case,
  so an assertion failure is reported as a failure and any other raised effect as an error;
- records skipped tests without invoking them;
- prints one line per test and a final summary;
- returns exit status `0` when every runnable test passes and `1` when any test fails or errors;
- treats a run with no discovered tests as a successful run with a `no tests discovered` line.

A representative report is:

```text
running 3 tests in target 'unit'
test app.CalculatorTest.additionAddsOperands ... ok
test app.CalculatorTest.divisionTruncates ... FAILED: expected 3, got 2
test app.CalculatorTest.pendingWork ... skipped: not ready
1 passed, 1 failed, 1 skipped
```

Host exceptions are not effects. An uncaught host exception from generated JVM code aborts the run,
consistent with the language's effect model; tests that need to assert on host failures must convert
them explicitly. Tests share one JVM process and any process-wide state. The runner is sequential and
does not provide per-test isolation, ordering guarantees beyond the deterministic order above, or
parallel execution.

The generated runner references `zeron.test` only in test-target output. Application targets neither
compile test roots nor emit the runner, so a shipped application does not acquire a test dependency.

### Manifest integration

The manifest additions extend ZEP-0117 without changing its existing keys:

```toml
[project]
source-roots = ["src"]
test-roots = ["tests"]
output = "dist"
default-target = "app"

[targets.app]
entry = "src/main.zn"
output = "dist/app"

[targets.unit]
kind = "test"
output = "dist/test"
deny-warnings = true
```

`[project]` gains one optional key:

| Key | Type | Default | Meaning |
| --- | ---- | ------- | ------- |
| `test-roots` | array of strings | `["tests"]` | Project-wide roots containing test sources. Must be non-empty when present and must not overlap a source root. |

`[targets.<name>]` gains one optional key:

| Key | Type | Default | Meaning |
| --- | ---- | ------- | ------- |
| `kind` | string | `"application"` | `"application"` for a runnable program; `"test"` for a generated test runner. |

The accepted `kind` values are `"application"` and `"test"`; any other value is rejected. A
`kind = "application"` target keeps ZEP-0117's `entry` rules. A `kind = "test"` target forbids
`entry`, may omit it even when `[project].entry` is absent, and requires at least one configured
test root. Test roots are resolved relative to the manifest, normalized, and validated like source
roots.

A test target compiles the union of the project source roots and test roots so tests can reference
production code. Application targets compile only the source roots. Both target kinds share the
project's standard-library mode, Zeron libraries, Java classpath roots, and warning policy. Each
target keeps its own output directory under ZEP-0117's uniqueness rule.

When no `[targets]` table exists, `zeron test` synthesizes an implicit test target with output
`<project.output>/test`, the `[build].deny-warnings` policy, and the project's source and test roots.
The implicit target is never selected by `zeron build` or `zeron run`.

### Command-line behavior

The command surface becomes:

```text
zeron test [<target>] [--manifest <file>] [--debug]
           [--deny-warnings | --no-deny-warnings]
```

- `zeron test` selects a test target, builds it, launches the generated runner, and exits with the
  runner's status. Build and resolution failures keep the existing CLI exit codes.
- With a positional target, the target must exist and have `kind = "test"`; selecting an application
  target is an invalid invocation.
- With no positional target, `zeron test` uses `[project].default-target` when it is a test target,
  otherwise the only test target when exactly one exists, otherwise the implicit test target when no
  test targets exist. If several test targets exist and none is selected, the command reports the
  available test target names.
- `zeron build` may build a test target, including the generated runner, for CI artifacts.
  `zeron run` rejects a test target and directs the user to `zeron test`.
- `zeron lsp` and `zeron fmt` continue to operate on the project's analysis universe. Test roots are
  included so tests receive diagnostics, completion, and formatting, but they remain excluded from
  application target compilation.
- `--manifest`, `--debug`, `--deny-warnings`, and `--no-deny-warnings` keep their existing
  meanings. Supplying both warning options is an error.

The command, option, and manifest-schema additions are recorded in the shared metadata described by
ZEP-0117. `zeron help`, `guide/39-command-reference.md`, and `guide/40-manifest-reference.md` are
regenerated from that metadata, and the staleness checks extend to the new keys and command.

### Diagnostics

Implementation introduces diagnostics for:

- `@Test` or `@Ignore` outside a test root;
- `@Ignore` on a function that is not `@Test`;
- a test function that is not `public`, has parameters or type parameters, or does not return
  `Unit`;
- a `kind = "test"` target that declares `entry` or has no test root;
- an unknown target `kind`;
- overlapping source and test roots;
- a selected target that is not a test target for `zeron test`, or a test target passed to
  `zeron run`.

Exact diagnostic codes are assigned during implementation following the diagnostics guide; this
proposal fixes the conditions that must be diagnosed.

## Compatibility and impact

- This adds public standard-library API (`zeron.test`), so the standard-library API version must be
  bumped once for the `0.8.0` cycle, consolidated with the other additions before release.
- It adds manifest keys and a CLI command. Older compilers reject them as unknown, which is the
  intended forward-compatibility behavior for additive manifest and command surfaces.
- Application builds are unchanged: test roots are excluded, the runner is not generated, and
  `zeron.test` is not referenced unless a production source imports it.
- Compiled-library consumers can use `zeron.test` from the standard-library artifact. The generated
  runner lives in the test target's output and does not change the API index.
- Test declarations and assertions are ordinary Zeron code, so they follow the language's effect,
  visibility, and generic-evidence rules. No runtime reflection, annotation retention, or host
  exception bridge is added.

## Alternatives

- **Naming convention instead of annotations.** A `test` prefix or a reserved directory avoids an
  annotation dependency but cannot express ignore reasons, metadata, or future options, and it makes
  accidental discovery more likely. Annotations reuse the shipped declaration-metadata model.
- **Manual registration in a suite object.** This needs a hand-written list and either reflection or
  boilerplate, and it gives the compiler nothing to validate. Compile-time discovery removes both.
- **Runtime reflection over compiled classes.** Zeron has no runtime reflection, and adding it for
  tests would be a much larger change with its own compatibility cost.
- **External test framework only.** This avoids standard-library policy but leaves the language
  without a consistent entry-level workflow, project configuration, or exit-status contract.
- **Returning a `Result` from assertions instead of raising.** Results compose well but force every
  assertion to be threaded manually and make early failure awkward. A typed effect matches the
  language's abortive control flow and lets the runner handle failures uniformly.
- **Process-per-test isolation.** Stronger isolation, but high startup cost and a much larger
  runner contract. It remains a possible follow-up rather than a first-version requirement.
- **Generating a JUnit-compatible runner.** This would couple the standard workflow to a host
  framework and its lifecycle, which the effect-based design does not need.

## Implementation stages

1. **Standard-library API.** Add `zeron.test` annotations, `TestFailure`, and the assertion
   functions in standard-library source, with API-index coverage and focused tests.
2. **Discovery and validation.** Recognize `zeron.test.Test` and `zeron.test.Ignore` at compile time,
   validate test signatures and placement, and produce deterministic discovery results.
3. **Runner generation.** Generate the synthetic runner for test targets, including per-test effect
   handling, skipped tests, reporting, and the exit-status contract.
4. **Project and CLI integration.** Add `test-roots`, target `kind`, `zeron test`, target selection,
   and manifest/CLI validation. Regenerate the command and manifest references from metadata.
5. **Documentation and release bookkeeping.** Update the configuration and command guides,
   `CHANGELOG.md`, the ZEP tracker, and any testing guidance. Keep `zeron build`/`run` behavior
   unchanged.

## Validation

- Unit-test assertion messages, `TestFailure` payloads, and the default text for each assertion.
- Compiler-test discovery order, ignore handling, invalid signatures, `@Test` outside a test root,
  and test-root/source-root overlap.
- CLI-test `zeron test` target selection, unknown and application targets, `zeron run` rejection,
  exit statuses, warning policy, and the no-tests case.
- Integration-test a project whose tests call production code, a project using
  `stdlib = "compiled"`, and a project with several test targets.
- Assert that application targets emit no test classes or runner and that test targets emit the
  production, test, and runner classes into their own output directory.
- Keep the full `zeron build`/`run` and formatting/language-server suites green to prove the
  additions are isolated.

## Open questions

- Should assertions capture a source location automatically, and if so, through compiler intrinsics
  or an explicit location parameter?
- Should `zeron test` gain filtering, listing, and machine-readable output (for example JSON or TAP)
  in the same release or a follow-up?
- Should the first version include fixtures, setup/teardown, or shared context, or leave them to a
  later proposal?
- Should tests support expected-failure, timeout, or retry metadata on `@Test`?
- Should `@Test` also cover extension methods or contract-provided test cases once method-level
  discovery is available?

## Decision

Accepted for `0.8.0` on 2026-11-19 as the standard-library and tooling companion to
[ZEP-0064](./ZEP-0064.md) and [ZEP-0117](./ZEP-0117.md). The committed surface is the
`zeron.test.Test`/`zeron.test.Ignore` annotation identity, the `TestFailure` effect and assertion
API, project `test-roots`, target `kind`, the generated runner contract, and the `zeron test`
command. Filtering, machine-readable output, fixtures, parallel execution, and process isolation are
explicitly deferred and may be added compatibly.
