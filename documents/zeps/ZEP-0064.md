## Abstract

This proposal explores a `zeron.log` package for application logging with levels, structured
context, and configurable output. It seeks to provide a portable API that does not expose a
particular host logging implementation as the language's public contract.

## Motivation

Applications commonly need diagnostics that are more controllable and structured than direct
printing. A standard logging API can give libraries a shared way to emit messages while allowing
applications to configure filtering and output centrally.

## Goals

- Define a small, stable logging API for libraries and applications.
- Support severity filtering and useful structured context.
- Make output and configuration behavior explicit and testable.
- Keep host-specific logging implementations behind the standard-library boundary.

## Non-goals

- A full observability suite, metrics, tracing, or telemetry export protocol.
- Mandating a particular logging backend or remote service.
- Replacing simple console output for small programs.

## Proposal

Add a `zeron.log` package with a logger abstraction, a bounded set of severity levels, and a
configuration path for selecting a minimum enabled level and one or more output destinations.
Libraries should be able to obtain a logger without taking ownership of process-wide configuration.
Applications should have an explicit point at which they can configure logging.

The API should support structured fields in addition to a message so callers do not need to encode
all context into strings. It should define how fields are represented and rendered, how messages are
filtered before expensive formatting, and how failures in a destination are surfaced. The initial
implementation may use synchronous output, but must document ordering and concurrency behavior.

Default configuration, logger naming, output format, and the relationship to `zeron.io` are not
settled by this draft.

## Compatibility and impact

This adds public standard-library APIs. Logging must not change the behavior of existing `print`
and `println` functions. Configuration and output choices should remain stable across platforms,
and library logging should not unexpectedly reconfigure an embedding application.

## Alternatives

- Use direct `print`/`println` calls — adequate for simple programs, but lacks levels and centralized
  filtering.
- Depend on Java logging APIs — immediately interoperable on the JVM, but exposes host-specific
  semantics and reduces portability.
- Leave logging entirely to third-party packages — avoids standard-library policy, but gives
  libraries no common logging boundary.

## Implementation and validation

Test level filtering, structured field preservation, output formatting, destination failures,
multiple logger instances, configuration boundaries, and concurrent calls if concurrency is
supported. Verify that disabled messages avoid evaluating deferred formatting work if the API
provides lazy message construction.

## Open questions

- Which severity levels and logger naming model should be standardized?
- Should configuration be process-global, explicitly passed, or based on a scoped context?
- Which output destinations and formats belong in the initial release?
- Should logging calls be synchronous, and what guarantees should concurrent callers receive?
- How should destination failures be reported without recursively logging them?
