## Abstract

This proposal defines a `zeron.serialization.json` package for parsing and writing JSON with specified
syntax, value, and error semantics. It is intended to support common data interchange without
committing the language to implicit serialization of arbitrary user-defined types.

## Motivation

JSON is widely used for configuration, APIs, and persisted data, but applications should not need
to rely directly on host-specific parser libraries. A standard package can provide predictable
behavior and a foundation for higher-level conversion APIs.

## Goals

- Parse JSON text into a documented representation with precise error locations.
- Define JSON value and number semantics without silent precision loss.
- Provide a clear path for producing valid JSON output.
- Integrate typed conversion through the canonical serialization contracts in ZEP-0068.
- Avoid implicit reflection or a format-specific typed-mapping system.

## Non-goals

- Automatically serializing arbitrary Zeron classes or products.
- Defining network transport or HTTP-specific JSON behavior.
- Requiring a streaming API in the first implementation.

## Proposal

Add a `zeron.serialization.json` package with parsing from text and a documented JSON value model for
null, Boolean, number, string, array, and object values. Parsing should reject malformed input with a
typed error that identifies the failure and, where practical, its source location. The package
should represent objects with a dedicated string-keyed type that preserves insertion order.
Duplicate object keys are rejected with a parse error. A JSON number retains its exact validated
source lexeme; conversions to integer or decimal types are explicit and checked so that precision
is never silently lost. Parsing must also define Unicode escape handling and limits for deeply
nested or excessively large input.

The package should provide serialization of values produced by the JSON API, with escaping and
number formatting specified well enough to guarantee valid output. Object serialization preserves
the value's insertion order, and a retained number lexeme is emitted without changing its value.
Typed encoding and decoding helpers use the `Encode` and `Decode` capabilities defined by ZEP-0068;
this proposal does not define a separate schema or typed-mapping system. It does not enable
implicit reflection over arbitrary user-defined types.

The initial parser and writer APIs operate on complete text and JSON values; streaming parser and
writer APIs are deferred. The design should remain compatible with later integration with byte
readers and the existing I/O and resource model, without introducing implicit resource ownership.
Typed helpers should adapt the canonical protocol directly rather than require a universal
intermediate data tree.

The initial public API exposes package-level `parse`, `number`, and `stringify` functions, plus
JSON value, array, and object types and factories. The settled representation for a tagged
alternative is a single-member JSON object whose key is the case tag; a payload-less case uses JSON
null. Input is limited to 1 MiB of UTF-16 code units and nesting depth 256. Unpaired UTF-16
surrogates are rejected both in raw text and in Unicode escapes.

## Compatibility and impact

This adds public standard-library APIs and a format-specific value model. Changing object-key
semantics, number representation, or serialization output after release may be incompatible.
Implementations must follow JSON's applicable specification and must not silently turn invalid input
into a successful value.

## Alternatives

- Depend on a host JSON implementation — reduces implementation effort, but can expose platform
  differences and host-specific types.
- Map JSON directly into arbitrary Zeron objects — convenient, but requires a separate schema,
  conversion, and evolution design.
- Support parsing only — smaller, but leaves callers without a standard way to produce JSON.

## Implementation and validation

The parser, value model, and writer are implemented. Tests cover valid and invalid syntax, escapes
and Unicode, numeric boundary and precision cases, duplicate keys, nesting limits, exact error
locations, and serialization round trips. Typed codec integration remains pending the
type-directed operations in ZEP-0068; the JSON value API does not define a separate typed-mapping
system.

Accepted 2026-10-22. The `zeron.serialization.json` package, JSON value model, duplicate-key and
