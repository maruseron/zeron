## Abstract

This proposal explores a `zeron.parsers.toml` package for reading and optionally writing TOML
documents. It aims to support configuration use cases with explicit value, date/time, and diagnostic
semantics.

## Motivation

TOML is already familiar to Zeron users through the project manifest and is a common human-edited
configuration format. A standard parser would let programs consume TOML without depending on host
libraries or confusing project-manifest parsing with a general application API.

## Goals

- Parse TOML documents into a documented representation of tables, arrays, and scalar values.
- Specify TOML version conformance and useful source diagnostics.
- Preserve the distinction between compiler project configuration and the public parser API.
- Decide whether editing and serialization are part of the supported use case.

## Non-goals

- Replacing the compiler's project-manifest implementation as an incidental implementation detail.
- Implicitly mapping TOML documents to arbitrary Zeron classes.
- Supporting multiple incompatible TOML dialects without an explicit compatibility policy.

## Proposal

Add a `zeron.parsers.toml` package for parsing TOML text into an explicit value model. The model
must represent TOML tables, arrays, strings, Booleans, integers, floating-point values, and local
date/time values without silently discarding distinctions required by the format. Parse failures
should report a typed error with source location and a useful explanation.

The proposal targets a clearly named TOML specification version; the initial draft recommends TOML
1.0.0 unless implementation constraints or ecosystem needs justify another choice. The API should
decide whether it is read-only or also supports serialization. If writing is included, the policy
for preserving comments, key ordering, and original formatting must be explicit; a semantic-value
writer need not promise source-preserving edits.

Project manifests remain a compiler-owned configuration format even if the compiler later reuses
the package internally. The public parser's types and failure behavior should not become coupled to
internal manifest structures.

## Compatibility and impact

This adds public standard-library APIs. TOML specification version, numeric representation, and
local date/time types affect the stable public model. The design must also make explicit how values
interoperate with other parser packages, if a shared representation is desired.

## Alternatives

- Parse only the subset used by project manifests — simpler, but misleading as a general TOML
  package and inadequate for application configuration.
- Depend on a host TOML library — expedient, but may limit portability and make API behavior depend
  on the JVM dependency.
- Provide parsing and source-preserving editing immediately — useful for formatters, but increases
  complexity beyond ordinary configuration loading.

## Implementation and validation

Test the selected specification's valid and invalid examples, numeric boundaries, date/time values,
table and array rules, duplicate/conflicting definitions, source diagnostics, and serialization if
included. Verify the project's own manifest behavior remains unchanged when implementation code is
shared.

## Open questions

- Should the package target TOML 1.0.0 or a later specification?
- What Zeron types should represent local date, time, and date-time values?
- Is serialization required, and must it preserve comments or formatting?
- Should TOML values share a common representation with JSON, or remain format-specific?
- Should typed conversion helpers be provided, and where should they live?
