## Abstract

This proposal explores a `zeron.parsers.xml` package for safely parsing XML with explicit namespace,
document-model, and resource-handling semantics. It aims to support common XML interchange without
making unsafe external resource resolution implicit.

## Motivation

XML remains common in configuration and data interchange, but its namespace and entity rules and
the behavior of host parsers can make applications difficult to secure and portable. A standard
package should make safe defaults and supported XML behavior clear at the API boundary.

## Goals

- Define a safe XML parsing API with precise, typed diagnostics.
- Specify XML version, namespace, and document model behavior.
- Make entity, DTD, and external-resource handling explicit.
- Allow future streaming support without hiding resource ownership.

## Non-goals

- An XML schema language, XSLT engine, or general document-transformation framework.
- Unrestricted DTD processing or implicit network access during parsing.
- Implicit binding of XML documents to arbitrary Zeron classes.

## Proposal

Add a `zeron.parsers.xml` package for parsing XML text or an explicit input source into a documented
tree or event representation. The design must specify supported XML version and encoding behavior,
namespace handling, comments and processing instructions, mixed content, and how source locations
appear in errors.

Parsing must use safe defaults: external entities and external DTD/resource resolution are disabled
unless a future explicit API defines a constrained, auditable opt-in. Entity expansion and document
size/depth limits must prevent unbounded resource consumption. A parser must report malformed or
disallowed input rather than silently omit content.

The initial design should choose between a tree API, a streaming event API, or a staged combination.
Any streaming reader must follow the existing resource ownership and disposal rules. XML output,
canonicalization, schema validation, and typed object mapping require explicit scope decisions and
are not implied by parsing support.

## Compatibility and impact

This adds public standard-library APIs. XML security defaults are part of the public behavior and
must not be weakened silently. The choice between tree and streaming APIs, namespace identifiers,
and text/mixed-content representation affects library compatibility.

## Alternatives

- Expose the platform's XML parser directly — reduces implementation effort, but risks exposing
  unsafe defaults and host-specific behavior.
- Provide only a streaming API — limits memory use, but makes simple document access more complex.
- Provide only a tree API — convenient for small documents, but requires limits and may not suit
  large inputs.
- Defer XML support — avoids a broad compatibility and security surface until concrete use cases
  establish priorities.

## Implementation and validation

Test namespaces, encodings, mixed content, malformed documents, source diagnostics, and document
limits. Include security tests proving external entities and DTDs do not access local files or
network resources by default, as well as tests for any explicitly supported opt-in policy. Test
resource disposal for streaming APIs.

## Open questions

- Should the initial API expose a document tree, streaming events, or both?
- Which XML version and encodings are required?
- Should DTDs be rejected entirely or accepted with external access disabled?
- Which node types, comments, and processing instructions must be preserved?
- Should XML writing, schema validation, or typed conversion be separate future proposals?
