## Abstract

This proposal defines the need and direction for a serialization contract in Zeron: a principled,
explicit way to encode values and decode them back from data representations. It is intended as a
foundation for mature JSON, TOML, and XML libraries and, eventually, schema-oriented and custom
binary formats such as Avro, Protocol Buffers, Thrift, and Fury.

## Motivation

Parsing a format into a generic syntax tree is not enough for applications that need stable,
typed data interchange. Each format library otherwise has to invent its own mapping between Zeron
types and encoded data, including field naming, missing and nullable values, sum cases, errors, and
schema evolution. Duplicated conventions make it harder to use multiple formats consistently and
make it difficult to add generated or schema-driven binary encodings.

A shared contract can give format libraries and user-defined types a common interoperability
boundary, while allowing each format to retain its own data model and wire-format rules.

## Goals

- Define explicit, bidirectional serialization capabilities for Zeron values.
- Define a canonical logical data model and explicit encoding/decoding contracts with
  format-specific adapters.
- Cover primitive values and the language's supported product, sum, generic, and collection forms.
- Make field/case identity, optionality, nullability, and unknown or missing data behavior explicit.
- Support explicit custom implementations and safe, opt-in derivation for declared data aggregates.
- Enable JSON, TOML, and XML adapters to share type-level mappings where their semantics align.
- Keep the foundation extensible to schema-aware and binary codecs with explicit compatibility and
  evolution policies.

## Non-goals

- Mandating one wire format, document model, or byte encoding for every serializer.
- Treating arbitrary reflection as the default serialization mechanism.
- Requiring every codec operation to materialize a universal in-memory tree.
- Promising that one mapping can preserve every distinction in JSON, TOML, and XML identically.
- Defining Avro, Protocol Buffers, Thrift, or Fury wire compatibility in this proposal.
- Making implicit serialization part of ordinary function calls or object construction.
- Defining a universal canonical byte encoding or byte-for-byte output across formats.

## Proposal

### Canonical model and format adapters

Establish a canonical, format-independent logical model and explicit encoding/decoding contracts.
The model describes Zeron data shapes; it is not a wire format, a universal document AST, or a
canonical byte representation. JSON, TOML, XML, and future binary libraries own their native
syntax and value models, and provide adapters between those models and the canonical contract when
the mapping is faithful.

The canonical logical model covers null, Boolean, string, exact integer and decimal values,
explicit floating-point values, byte sequences, ordered records with named fields, tagged
alternatives, sequences, and maps. Missing record fields are distinct from fields explicitly
containing null. Field ordering is preserved where supplied, but the model does not impose a
universal map-ordering or byte-output guarantee.

Format-specific distinctions that do not fit this common model use explicit format-specific
extensions or remain in a format-native API. This includes at least TOML local date/time values,
XML namespaces and mixed content, and JSON number lexemes when lexical spelling matters. An
adapter must preserve a distinction, require an explicit conversion, or report that the mapping is
unsupported; it must not silently narrow or discard information.

The primary codec contract is protocol-based and must allow streaming without first materializing a
complete canonical value tree. A format-independent in-memory tree may be provided as an optional
convenience layer over that protocol, but codecs are not required to allocate it. Adapters may also
expose native parse trees or event streams suited to their formats.

### Encoding and decoding capabilities

Encoding and decoding are independently usable capabilities; a combined codec is a convenience for
types supporting both directions. Implementations are selected explicitly and statically through
Zeron's contract and witness mechanisms, and generic bounds can require the needed capability.
Hand-written implementations remain supported.

Format syntax, data-shape, and conversion failures are returned as typed decoder/encoder errors with
structured context where available, such as a field or case path and source position. Resource or
other declared operational effects remain raised effects. When decoding constructs a data aggregate,
effects from its canonical initializer propagate through the decoder operation; they are not
converted into format errors. This follows the construction rule in
[ZEP-0069](./ZEP-0069.md).

### Aggregate mapping and derivation

The model supports primitive values, records, tagged alternatives, generic aggregates, arrays and
collections, nullable values, and maps. Derivation is available only for explicitly declared data
aggregates with known canonical shapes: native products, native sums, and transparent data classes.
It is opt-in for each direction. A type with a codec only for one direction need not implement the
other. Derived mappings use the declared shape and supported component codecs; they do not inspect
runtime objects.

Ordinary classes are not serializable through field, property, or method reflection. A domain class
may explicitly map to a data aggregate or provide a hand-written codec, but the compiler does not
claim to prove that such a mapping is total, invertible, or invariant-preserving.

Record fields use their source component names as the default logical names. A declaration may
override a logical field name and provide accepted legacy aliases. Renaming a field without an
explicit stable name or alias changes its logical identity. Sum cases follow the same rule for case
tags. Binary formats that require numeric field identifiers define those identifiers in their
format-specific schema or adapter; this proposal does not derive durable binary IDs from source
order or names.

A missing required field is a decoding error; null is decoded only when the field's declared type
and codec accept null. This proposal does not infer a decoding default from a constructor or field
initializer. Unknown record fields are ignored by default for forward compatibility, with an
adapter option for strict rejection. Unknown sum cases are errors unless the target aggregate
explicitly declares a representation for them.

### Scope boundaries

Adapters must not claim that a common logical mapping automatically provides a format's schema
evolution guarantees. Binary formats may add schema descriptions, numeric field IDs, version
negotiation, and reader/writer compatibility checks. JSON/TOML/XML proposals specify their own
native parser, writer, security, and format-specific semantics, and may expose native data models
even when a value cannot be mapped to the canonical model.

## Compatibility and impact

The contract and any derived metadata become public standard-library and compiled-library API.
Changes to field identity, case tagging, null/missing semantics, defaults, or generated mappings can
break persisted data even when source signatures remain unchanged. The design must distinguish
source compatibility from wire compatibility and provide stable explicit identifiers or versioning
hooks before promising durable data compatibility.

This proposal guides [ZEP-0065](./ZEP-0065.md), [ZEP-0066](./ZEP-0066.md), and
[ZEP-0067](./ZEP-0067.md). Those packages may first expose format-native data models and then
provide adapters to the canonical model where representable. Typed conversion for products, sums,
and data classes uses explicit derivation and contracts, not arbitrary object serialization.

## Alternatives

- Let every format library define unrelated type mappings — simpler initially, but duplicates
  semantics and makes cross-format use inconsistent.
- Serialize arbitrary values through runtime reflection — convenient, but weakens static
  guarantees and makes naming, visibility, and schema evolution implicit.
- Require every codec to pass through a universal in-memory tree — easy to inspect and test, but
  may allocate heavily and impede streaming or preserve format-native distinctions poorly.
- Define a separate schema system for each format — preserves each format's full capability, but
  does not provide reusable Zeron type mappings across libraries.
- Defer a shared contract — avoids early coupling, but risks JSON, TOML, and XML APIs independently
  hardening incompatible conversion conventions.

## Implementation and validation

The first core slice defines the canonical value and error types, streaming `Encoder` and `Decoder`
contracts, and `Encode<T>`, `Decode<T>`, and combined `Codec<T>` capability contracts in
`zeron.serialization`. Products, sums, and transparent data classes can request codec evidence
through derivation; `Codec` requests both directions, and component evidence is checked. This is
compile-time capability evidence only: generated streaming encode/decode operations are not yet
implemented, so these contracts do not yet provide value round-trips.

The current implementation scope intentionally defers concrete adapters to their respective format
proposals. Remaining core work includes type-directed `decoder.decode<T>()` dispatch, generated
streaming mappings for products, sums, and data classes, aliases and stable field/case identifiers,
unknown-field/case policies, structured nested error propagation, custom mappings, and library
index round-tripping for codec metadata. Before this proposal is marked implemented, tests must
exercise those behaviors, verify that streaming paths do not require a complete intermediate tree,
and cover separate compilation of derived and hand-written codecs. Adapter prototypes for two
distinct text formats are deferred with the format proposals, as requested.

For each adopted text format, test round-trip semantics without assuming byte-for-byte
canonicalization unless that format explicitly guarantees it. For any future binary codec, test
schema evolution and old-reader/new-writer compatibility as part of that codec's own proposal.

## Open questions

The core source names and low-level streaming operations are established in the standard library.
Type-directed decoder dispatch and stable-name/alias metadata still need implementation. Binary
schema languages and compatibility algorithms belong in separate format proposals.

## Decision

Accepted 2026-10-22. Adopt a streaming-capable canonical logical model with optional tree
conveniences, separate encoding and decoding capabilities, and format-specific adapters that
preserve native distinctions. Restrict derivation to declared data aggregates, keep format errors
distinct from raised effects, and leave binary schema-evolution guarantees to format-specific
proposals. The core is partially implemented; adapters remain deferred to their format proposals.
Release state: candidate for 0.6.0, as recorded in the ZEP tracker.
