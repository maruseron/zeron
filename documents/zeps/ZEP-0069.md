## Abstract

This proposal defines a restricted nominal `data class` declaration whose canonical data
representation is an explicitly declared set of immutable components. Data classes may also have
behavior and auxiliary state, but only their canonical components participate in derived equality
and serialization.

## Motivation

Native products and sums have explicit data shapes and can receive structural operations, but they
cannot currently carry the methods and contract conformances available to ordinary classes.
Ordinary classes can have behavior and implement contracts, but their fields, properties, and
methods do not in general reveal a complete, stable representation suitable for serialization.

A restricted data class could bridge this gap: it would remain a nominal class usable in ordinary
APIs, while its declaration promises that its named components are the complete data representation.
This gives serialization a sound derivation boundary without reflecting over arbitrary objects or
trying to prove serialization laws from general-purpose pattern matching.

## Goals

- Introduce an explicit nominal aggregate form whose declared components are its complete canonical
  data representation.
- Allow data classes to define methods and computed properties and to implement ordinary contracts
  without including those behaviors in the serialized shape.
- Permit explicitly initialized auxiliary fields while keeping them separate from canonical
  components.
- Define initialization order for components, direct field initializers, and initializer blocks.
- Permit effect-free function calls in direct field initializers while requiring initializer-block
  effects to be declared on construction.
- Support stable structural equality over declared components.
- Make eligible data classes usable with the canonical serialization model in [ZEP-0068](./ZEP-0068.md).
- Provide conditional structural equality from canonical components.
- Keep automatic display out of scope and make hashing an explicit opt-in.

## Non-goals

- Making ordinary classes serializable by inspecting fields, properties, or methods.
- Inferring that arbitrary pattern matches are total, invertible, non-mutating, or
  invariant-preserving.
- Adding class inheritance or open data-class hierarchies.
- Adding component defaults, alternate named constructors, or data-class destructuring patterns.
- Deriving `Display` or defining a structural debug-formatting capability.
- Defining a universal wire format or binary schema evolution policy.
- Guaranteeing object identity, alias preservation, or cyclic graph reconstruction.

## Proposal

Add a restricted final nominal class form, provisionally named `data class`. Its declaration
explicitly lists immutable canonical components in a tuple-like header:

```zeron
public data class Point(x: Int, y: Int) {
    magnitudeFromOrigin: Float = Math.sqrt(
        x.toFloat() * x.toFloat() + y.toFloat() * y.toFloat());

    public squaredDistanceFromOrigin(): Int = this.x * this.x + this.y * this.y;
}
```

The class remains nominal: another data class with identical component types is not assignment-
compatible. Component parameters are immutable, are available as read-only component properties,
and are initialized before any class-body state. The canonical constructor takes every component;
component defaults are not supported. Data classes have no alternate named constructors. Ordinary
top-level or namespace functions may provide convenient factories, but they do not replace the
canonical constructor. Each component has a read-only property whose visibility matches the data
class declaration; individual component visibility modifiers are not supported.

The transparency promise applies to the declared components, not to inferred JVM layout or all
observable members:

- Methods and computed properties may be declared, but they are behavior and do not add serialized
  components.
- Contract conformance is permitted; required or default contract methods do not affect the data
  representation.
- Additional stored fields may be declared as auxiliary state, including mutable fields. They are
  not canonical components and are excluded from derived equality and serialization. Their
  initialization cannot assign to or replace canonical components. Auxiliary state may affect
  methods and computed properties, but is not preserved by equality or serialization; a
  serialize/deserialize round trip promises equivalent canonical component values, not equivalent
  auxiliary state or behavior that depends on it.
- Serialization derivation uses only declared components and the stable field identifiers defined
  by the canonical model. It does not inspect private storage or infer a schema from properties.
- Component types may include mutable references. Component bindings themselves remain immutable,
  but immutability is shallow: referenced objects may change through mutable aliases. Such changes
  can change component-based equality and serialized output.

Initialization has a defined order: first assign all canonical components from the constructor
arguments; next evaluate direct field initializers in declaration order; finally execute
initializer blocks in source order. Components are in scope for body initialization, and each
initializer block can use fields initialized earlier in this sequence. An auxiliary field initialized
by a block must not also have a direct initializer, and every auxiliary field must be initialized
before construction completes. Initializer blocks may assign auxiliary fields but cannot mutate
canonical components.

Direct field initializers may call functions whose declared raised-effect set is empty; they cannot
raise or propagate declared effects. This relaxes the current restriction on function calls in
ordinary class field initializers while keeping those initializers effect-free. Initializer blocks
are data-class-only in this proposal and may perform effectful work. A block declares its effects
with constructor-style syntax such as `Point raises MagnitudeFailure { ... }`; multiple effects use
the ordinary comma-separated `raises` list. The generated canonical constructor exposes the union
of the effects declared by all initializer blocks, and construction requires the caller to handle or
propagate those effects. If initialization raises, construction does not produce a data-class value.
Initializer blocks may not define additional construction paths or constructors.

For example, a block could initialize an auxiliary field using an effectful operation:

```zeron
public data class Point(x: Int, y: Int) {
    magnitudeFromOrigin: Float;

    Point raises MagnitudeFailure {
        magnitudeFromOrigin = calculateMagnitude(x, y);
    }
}
```

This initializer block is distinct from a named constructor: it runs as part of canonical
construction, and its declared effects contribute to the effects of constructing `Point`.

Every data class has compiler-provided structural `Eq` evidence when all canonical components have
applicable `Eq` evidence. It compares only canonical components, in declaration order, and cannot
be overridden; if a component lacks `Eq`, the data class remains usable but equality is unavailable.
Automatic `Display` is not provided: a debug representation may be useful, but user-facing display
has different compatibility and information-disclosure expectations. `Hashable` is available only
through explicit derivation when component evidence permits it. As with other hashable values,
callers must not mutate equality- or hash-relevant state while a value is used as a hash key;
mutable references in components make this obligation particularly important.

Data classes may opt into encoding and decoding through the explicit capabilities from ZEP-0068.
The standard library now exposes those capability contracts and derivation checks, but generated
streaming operations are still in progress. Once available, the mapping must use ordinary
construction and report decoding failures rather than bypassing invariants. Thus decoding invokes
the canonical constructor and its initializer blocks; any declared initialization effects propagate
through the decoder contract to its caller. Format parse and representation failures remain decoder
errors rather than being converted into constructor effects. Domain classes that are not transparent
data aggregates can explicitly map to a data class or provide hand-written codecs, but are not
automatically serialized.

The data-class contract is a language-level promise about its canonical component representation,
not a promise to preserve heap identity, object sharing, auxiliary state, caches, or cycles.
Equality and round-trip expectations are value-based and apply to declared components. Auxiliary
state can affect other observable behavior, but such behavior is outside the equality and
serialization guarantee.

## Compatibility and impact

This adds source syntax, nominal type metadata, construction and member-resolution behavior,
initializer-block semantics, and potential derived `Eq` and serialization evidence. Component
order, names, types, and stable serialization identifiers can become compatibility-sensitive. The
language must distinguish source-level component renames from wire-level identifier changes.

Existing classes and their current `deriving Eq` behavior must remain distinct unless a separate
migration is designed. In particular, the current class derivation rules inspect stored fields and
initialized properties; a data class has intrinsic conditional equality and defines its
serialization shape solely through its declared components. Effects from initializer blocks become
part of the canonical constructor type and must be preserved through compiled-library metadata.

## Alternatives

- Continue using nominal products and sums only — simple and explicit, but they cannot provide
  ordinary class methods and contract conformance.
- Derive serialization for ordinary classes from stored fields or properties — convenient, but
  makes implementation details and incomplete state part of the wire contract.
- Use pattern matching to extract and rebuild arbitrary classes — expressive, but the compiler
  cannot establish the required reconstruction and invariant-preservation laws for arbitrary
  patterns.
- Require hand-written serializers for every class — explicit, but duplicates routine mappings and
  gives no language-level distinction between data carriers and behavioral objects.

## Implementation and validation

Implemented source syntax, immutable components, auxiliary fields, methods and computed properties,
direct initializer ordering, effectful initializer blocks, conditional component-based `Eq`,
explicit `Hashable` derivation, and compiled-library metadata including canonical constructor
effects. Focused tests cover component-only equality, generic data classes, initialization order,
effect propagation and handling, auxiliary-field initialization, and separately compiled
construction, effects, and equality. Ordinary class derivation remains unchanged.

The `Encode`/`Decode`/`Codec` capability contracts and streaming protocol from ZEP-0068 are present,
and data classes can derive compile-time capability evidence. Generated value operations,
constructor-based decoding, stable field identifiers, and round-trip behavior are not yet available.

## Open questions

The source-level initialization rules and restrictions are settled. A required auxiliary field that
is not initialized, or is initialized more than once in a block, reports `ZR2017` (Invalid
initializer). Wire-level field identifiers, aliases, and schema evolution follow the canonical
serialization design in [ZEP-0068](./ZEP-0068.md); they must be implemented there before derived
serializers are treated as stable for persisted data.

## Decision

Accepted 2026-10-22. The declared immutable components define a clear canonical data shape without
making arbitrary class state implicitly serializable. Auxiliary state, construction effects,
shallow mutability, and explicit hashing behavior are specified separately from that canonical
representation. The tracker records this proposal as a 0.6.0 candidate.
