## Abstract

This proposal explores extending newtypes beyond concrete built-in scalar representations. It
considers generic newtypes and newtypes backed by nominal Zeron or Java types while preserving a
distinct source-level identity. Such wrappers could give one representation multiple explicit
semantic views, including higher-kinded algebraic wrappers such as `Sum<A>`.

## Motivation

The current newtype feature supports only non-generic `Int`, `Float`, `Boolean`, and `String`
representations. This is sufficient for simple domain labels, but prevents a newtype from wrapping a
type parameter or a nominal value such as a class, product, sum, or Java class.

Generic wrappers are useful when the same underlying type needs several explicit interpretations.
For example, `Sum<A>` and `Product<A>` can distinguish additive and multiplicative structures over
the same `A`, and can be used as higher-kinded constructors in separate witnesses. Nominal
representations also allow domain wrappers around existing classes without defining a forwarding
class and manually storing or exposing each operation.

These capabilities raise representation and safety questions. A wrapper around a generic or
nominal reference may require a JVM object, and a guarded invariant may be invalidated if the
representation is mutable or can be mutated through another alias. The proposal therefore makes
runtime representation and invariant preservation explicit design topics.

## Goals

- Permit generic type parameters in newtype declarations.
- Consider nominal Zeron and Java types as backing representations.
- Preserve newtypes as distinct nominal source types with explicit construction and extraction.
- Define how generic newtypes participate in higher-kinded bounds and constructor-pattern witnesses.
- Specify runtime representation, boxing, library metadata, and compatibility expectations.

## Non-goals

- Changing operator syntax or the algebraic hierarchy in ZEP-0036.
- Implicit conversion to or from the representation type.
- Automatically forwarding the representation's methods or contract evidence.
- Generalizing newtypes into arbitrary multi-field wrappers or transparent data classes.
- Promising allocation-free or unboxed representation for generic newtypes.
- Defining serialization or Java interoperation that bypasses newtype construction and validation.

## Proposal

### Generic and nominal representations

Allow a newtype to bind type parameters and use a permitted type expression as its single
representation:

```zeron
public newtype Sum<A> = A;
public newtype UserKey = UUID;
```

The first declaration defines a unary type constructor `Sum<_>` suitable for higher-kinded
contracts. The second illustrates a wrapper over an existing nominal type. Exact representation
admissibility rules remain to be settled. Candidate nominal representations include Zeron classes,
products, sums, other newtypes, and explicitly declared Java external classes. Applied generic
representations such as `Box<A>` may be allowed when their type arguments satisfy the target type's
bounds.

Generic parameters follow the language's generic admissibility and variance rules. Newtypes remain
nominal and invariant unless a separate, checked variance design is accepted. Representation types
must be fully resolved and statically known; arbitrary structural or dynamically selected
representations are not introduced.

### Identity and construction

A newtype remains a distinct type even when its representation is identical to another type.
Construction and extraction are explicit. There is no implicit widening, narrowing, method
forwarding, or automatic inheritance of `Eq`, `Hashable`, or other contract evidence from the
representation. Existing `.new`, `.tryNew`, and `.value` semantics remain the starting point,
subject to resolution of generic and nominal validator safety.

An implementation may define explicit witnesses or extensions for the newtype. A generic newtype
constructor can be used as an HKT target, for example:

```zeron
contract Semigroup<F<_>> {
    associate<A>(this: F<A>, other: F<A>): F<A>;
}

contract Monoid<F<_>> {
    zero<A>(): F<A>;
}

witness Semigroup<Sum<_>> for Sum<_> {
    // The implementation delegates to the selected additive evidence for A.
}
```

This is schematic: it illustrates the constructor-shaped witness target, not complete compilable
syntax. It does not settle HKT contract design, required bounds on `A`, or numeric operator
availability. The witness target should denote the newtype constructor, not only its erased or
underlying representation. Operator overloading changes are explicitly outside this proposal.

### Runtime representation

The current implementation uses nominal JVM wrapper classes. The conservative default is to retain
that representation for generic and nominal newtypes unless a separate representation rule is
approved. Generic operations may box primitive arguments at erased JVM boundaries. This cost applies
only where a value is represented or passed through the wrapper/erased abstraction; it does not
change ordinary primitive `Int` operations globally.

Direct-carrier lowering or specialization may be considered separately. Any such optimization must
preserve nominal type checks, generic dispatch, nullability, mutable-reference capability, method
handles, separate compilation, and stable library ABI. It must not be described as zero-cost unless
those guarantees are verified at all relevant boundaries.

### Guarded newtypes and mutable representations

The existing `where` validator establishes a construction-time invariant. Extending it to
representations that can mutate creates a soundness question: a valid value might become invalid
after construction, through the wrapper's `.value`, a mutable receiver, or another alias.

The design must either restrict guarded newtypes to representations whose invariant cannot be
invalidated, prevent mutable access that could invalidate it, or define guarded construction as a
one-time check that does not promise a lasting invariant. The compiler must not imply a stronger
guarantee than the chosen rule provides.

### Compiled-library metadata

Library metadata must record generic parameters, representation types, guards, visibility, and
derivations needed by consumers. Separate compilation must preserve newtype identity and
constructor/extraction rules without inferring source semantics from generated JVM wrapper classes.
Any schema change must follow the project's release-cycle schema-version policy.

## Compatibility and impact

Generic and nominal representations expand the accepted source syntax and public library metadata.
They may affect generated class layouts and method descriptors, especially if later representation
optimizations are introduced. The initial extension should prefer a conservative wrapper ABI;
unboxing or specialization should be a separately versioned compatibility decision.

The feature must not make existing scalar newtypes implicitly interchangeable with their
representations. Existing validators must retain their current construction behavior. Any change to
the validity guarantees of guarded newtypes requires explicit documentation.

## Alternatives

- **Keep scalar-only newtypes** — preserves the simple implementation and current invariants, but
  prevents generic wrappers and nominal domain wrappers.
- **Use ordinary classes for every wrapper** — supports arbitrary backing values and behavior, but
  requires boilerplate and does not provide a reusable type-constructor representation.
- **Make newtypes transparent aliases** — avoids wrapper construction, but loses the nominal
  distinction that prevents accidental interchange.
- **Promise direct-carrier lowering immediately** — may reduce allocations, but complicates generic,
  nullable, mutable, interop, and ABI boundaries before their semantics are established.

## Implementation and validation

Implementation should begin only after representation admissibility, mutability, and validator
semantics are settled. Tests should cover generic construction and extraction, nominal
representations, nested and applied generic representations, generic bounds, HKT witness selection
and dispatch, guarded construction, nullable and mutable views, and ordinary primitive behavior.
Separate-compilation tests must round-trip newtype metadata and compile consumer code against it.
Bytecode tests should measure wrapper allocation and primitive boxing at concrete and erased
boundaries without assuming direct-carrier lowering.

## Open questions

- Which nominal representations are admissible: all nominal source types, Java external classes,
  applied generic types, or a narrower subset?
- May a representation be nullable, mutable, or itself a mutable reference?
- What lasting invariant, if any, does a guarded generic or nominal newtype promise?
- Is `.value` always exposed, and if so, what reference capability does it return?
- Are newtypes generic over a type variable allowed to derive equality or hashing conditionally?
- Is a wrapper JVM class the required initial representation, or may concrete non-generic cases
  retain scalar lowering?
- What bounds and witness syntax are needed for reusable `Sum<A>`/`Product<A>` witnesses?
