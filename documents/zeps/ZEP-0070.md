## Abstract

This proposal extends newtypes beyond concrete built-in scalar representations. Generic newtypes
and newtypes backed by nominal Zeron or Java types preserve a distinct source-level identity. A
newtype is a nominal view over a directly represented value rather than a JVM wrapper object: the
representation is the runtime carrier, the single `.value` field is removed, and `this` inside the
newtype's extensions and witnesses is the representation. This gives one representation multiple
explicit semantic views, including higher-kinded algebraic wrappers such as `Sum<A>`, and provides a
nominal single-value shape without legalizing unary products.

## Motivation

The current newtype feature supports only non-generic `Int`, `Float`, `Boolean`, and `String`
representations. This is sufficient for simple domain labels, but prevents a newtype from wrapping a
type parameter or a nominal value such as a class, product, sum, or Java class.

Generic newtypes are useful when the same underlying type needs several explicit interpretations.
For example, `Sum<A>` and `Product<A>` can distinguish additive and multiplicative structures over
the same `A`, and can be used as higher-kinded constructors in separate witnesses. Nominal
representations also allow domain views over existing classes without defining a forwarding class
and manually storing or exposing each operation.

These capabilities raise representation and safety questions. A newtype over a generic or nominal
reference may use a reference carrier, and a guarded invariant may be invalidated if the
representation is mutable or can be mutated through another alias. The proposal therefore makes
runtime representation and invariant preservation explicit design topics.

## Goals

- Permit generic type parameters in newtype declarations.
- Consider nominal Zeron and Java types as backing representations.
- Preserve newtypes as distinct nominal source types with explicit construction.
- Lower a newtype directly to its representation, with no generated `value` field or wrapper object.
- Make `this` inside a newtype's extensions and witnesses the representation, so operations use the
  representation directly instead of dereferencing `.value`.
- Define how generic newtypes participate in higher-kinded bounds and constructor-pattern witnesses.
- Specify boxing, library metadata, and compatibility expectations at erased and generic boundaries.

## Non-goals

- Changing operator syntax or the algebraic hierarchy in ZEP-0036.
- Implicit conversion to or from the representation outside a newtype-owned extension or witness
  body.
- Automatically forwarding the representation's methods or contract evidence.
- Generalizing newtypes into arbitrary multi-field wrappers or transparent data classes.
- Promising an unboxed representation at every generic, nullable, array, or erased boundary; those
  positions may box according to the existing representation rules.
- Giving a newtype a distinct runtime class or a runtime type-test identity separate from its
  representation.
- Defining serialization or Java interoperation that bypasses newtype construction and validation.

## Proposal

### Generic and nominal representations

Allow a newtype to bind type parameters and use a permitted type expression as its single
representation:

```zeron
public newtype Sum<A> = A;
public newtype UserKey = UUID;
```

The first declaration defines a unary type constructor `Sum<_>` suitable for higher-kinded
contracts. The second illustrates a newtype over an existing nominal type. The initial admissible
representations are all statically known, well-formed Zeron type expressions: built-in scalar and
`String` types, type parameters, Zeron classes, products, sums, data classes, other newtypes,
function types, and explicitly declared Java external classes. Applied generic representations
such as `Box<A>` are allowed when their arguments satisfy the target type's bounds. A reference
representation may itself be nullable; the newtype value is still non-null. Unary products are
not an admissible substitute for a newtype; [ZEP-0129](./ZEP-0129.md) records that decision.

Generic parameters follow the language's generic admissibility and variance rules. Newtypes remain
nominal and invariant unless a separate, checked variance design is accepted. Representation types
must be fully resolved and statically known; arbitrary structural or dynamically selected
representations are not introduced.

### Identity and construction

A newtype remains a distinct type even when its representation is identical to another type.
Construction is explicit through `.new` or `.tryNew`. A newtype has no generated `value` field and
no `.value` property. There is no implicit widening, narrowing, method forwarding, or automatic
inheritance of `Eq`, `Hashable`, or other contract evidence from the representation.

### Representation context in extensions and witnesses

The body of an extension or witness whose target is a newtype is a **representation context** for
that newtype. Inside the body, `this` has the representation type, and a parameter or local declared
with the newtype type is also represented by that same representation:

```zeron
public newtype Meters = Float;

public extension Meters {
    public fn plus(other: Meters): Meters = Meters.new(this + other);
    public fn toFloat(): Float = this;
}
```

`this` and `other` are `Float` values in the two bodies. `Meters.new` re-establishes the nominal
type at the boundary; returning a raw representation does not implicitly convert it to `Meters`.

A witness uses the same rule:

```zeron
public witness DisplayMeters: Display for Meters {
    fn toString(): String = this.toString();
}
```

There is no `.value` read in either body. Outside newtype-owned bodies, a `Meters` value remains
opaque and does not implicitly convert to `Float`; a newtype that needs to expose its representation
does so through an explicit extension such as `toFloat`. The `where` validator keeps its immutable
candidate binding named `value`; that binding is a constructor argument, not a member.

An implementation may define explicit witnesses or extensions for the newtype. A generic newtype
constructor can be used as an HKT target, for example:

```zeron
contract Semigroup<F<_>> {
    associate<A>(this: F<A>, other: F<A>): F<A>;
}

contract Monoid<F<_>> {
    zero<A>(): F<A>;
}

witness Semigroup<Sum<_>> for Sum<_> {
    // The implementation delegates to the selected additive evidence for A.
}
```

This is schematic: it illustrates the constructor-shaped witness target, not complete compilable
syntax. It does not settle HKT contract design, required bounds on `A`, or numeric operator
availability. The witness target should denote the newtype constructor, not only its erased or
underlying representation. Operator overloading changes are explicitly outside this proposal.

### Runtime representation

A newtype lowers directly to its representation. A concrete field, local, parameter, or return of
`newtype N = Int` uses the `Int` carrier; a `newtype N = String` uses the `String` carrier; a
function-shaped newtype uses the function value. No wrapper class, `value` field, or accessor is
generated for the newtype.

Generic, `Any`, nullable, array, and other erased positions may box or erase according to the
existing representation rules. For example, an `Array<N>` or a value passed through a generic `T`
uses whatever carrier that position requires; the newtype does not promise primitive storage at
every boundary. Direct representation is a lowering rule, not a claim that every use is unboxed.

Because the newtype has no distinct runtime class, runtime type tests and casts that target a
newtype are not supported. `value is N`, `value as N`, and `value as? N` cannot distinguish `N` from
its representation and are diagnosed. Compile-time nominal checking still prevents implicit
interchange outside newtype-owned bodies.

Direct representation changes generated JVM descriptors for newtype-typed fields, parameters, and
returns. Any later optimization or carrier change must preserve nominal source checks, validator
behavior, nullability, mutable-reference capability, method handles, separate compilation, and
stable library metadata.

### Guarded newtypes and mutable representations

The existing `where` validator establishes a construction-time invariant. Extending it to
representations that can mutate creates a soundness question: a valid value might become invalid
after construction through a mutable receiver or another alias.

For this bundle, guarded newtypes remain restricted to the existing immutable built-in scalar and
`String` representations. Generic and nominal representations are unguarded: they expose `.new`,
not `.tryNew`, and make no lasting invariant promise. Guarded reference newtypes require a later
design that either stores an immutable carrier, prevents invalidating access, or explicitly defines
a one-time check. The compiler must not imply a stronger guarantee than the chosen rule provides.

### Compiled-library metadata

Library metadata must record generic parameters, representation types, guards, visibility, and
derivations needed by consumers. It must also identify the representation context for public
extensions and witnesses so separately compiled bodies are checked against the same carrier.
Separate compilation must preserve newtype identity and construction rules without inferring source
semantics from generated JVM classes. Any schema change must follow the project's release-cycle
schema-version policy.

## Compatibility and impact

Generic and nominal representations expand the accepted source syntax and public library metadata.
Direct representation is a breaking runtime ABI change: generated fields, parameters, returns, and
method descriptors use the representation instead of a wrapper class, and the `.value` property is
removed. Existing source that reads `.value` must migrate to an explicit newtype extension or to
operations defined by the newtype. This is a pre-1.0 change and must be called out in the release
notes and guides.

The feature must not make existing scalar newtypes implicitly interchangeable with their
representations outside newtype-owned bodies. Existing validators must retain their current
construction behavior. Runtime tests or casts that previously observed the wrapper class no longer
have a newtype-specific target and must be rewritten against the source-level type. Any change to
the validity guarantees of guarded newtypes requires explicit documentation.

## Alternatives

- **Keep scalar-only newtypes** — preserves the simple implementation and current invariants, but
  prevents generic and nominal domain wrappers.
- **Use ordinary classes for every wrapper** — supports arbitrary backing values and behavior, but
  requires boilerplate, retains a wrapper object, and does not provide a reusable type-constructor
  representation.
- **Keep the wrapper and `.value` accessor** — preserves the current ABI, but duplicates the
  representation and keeps extension/witness bodies indirect. Rejected in favor of direct
  representation.
- **Make newtypes transparent aliases** — avoids representation work, but loses the nominal
  distinction that prevents accidental interchange.
- **Use direct representation only inside extensions and witnesses** — keeps the wrapper for ordinary
  values, which still allocates and still exposes a field. Rejected; the carrier should be direct at
  the value boundary too.
- **Allow implicit conversion everywhere to avoid migration** — removes the `.value` cost but also
  removes the nominal boundary. Rejected; representation context is limited to newtype-owned
  bodies.

## Implementation and validation

Implementation should begin only after representation admissibility, mutability, and validator
semantics are settled. It must remove wrapper generation, generate direct carriers for newtype
fields, parameters, and returns, and create representation contexts for extension and witness
bodies. Tests should cover generic construction, nominal representations, nested and applied
generic representations, generic bounds, HKT witness selection and dispatch, guarded construction,
nullable and mutable views, and ordinary primitive behavior. Separate-compilation tests must
round-trip newtype metadata and compile consumer code against it. Bytecode tests should verify
direct carriers at concrete boundaries and expected boxing at erased boundaries; they must not
assume a wrapper class that no longer exists.

## Open questions

- Should a newtype be able to expose its representation through a generated standard extension, or
  should every representation exposure be hand-written?
- Should a migration diagnostic for `.value` and newtype runtime tests be paired with a mechanical
  rewrite, or is a release-note migration guide sufficient?
- Should runtime type tests on newtypes be rejected permanently, or could a future reified newtype
  opt into a distinct descriptor?
- How should direct representation interact with mutable-reference carriers and nullable carriers at
  Java interop boundaries?
- Should generic newtypes eventually permit conditional equality or hashing derivation?
- Should guarded reference newtypes be supported, and if so, how is their invariant preserved?
- What serialization or host-interop rules prevent construction from bypassing the newtype API?

## Decision

Accepted on 2026-11-14 and marked `Candidate` for the `0.8.0` normalization bundle, together with
[ZEP-0129](./ZEP-0129.md).

The settled design is:

- newtypes may bind type parameters and use any statically known, well-formed Zeron type
  expression, including function types and explicitly declared Java external classes;
- a newtype lowers directly to its representation; no wrapper class, `value` field, or `.value`
  accessor is generated;
- construction is explicit through `.new` or `.tryNew`; the body of a newtype-owned extension or
  witness is a representation context where `this` and newtype-typed parameters use the carrier
  directly;
- outside those bodies there is no implicit conversion, method forwarding, or inherited evidence;
  exposing the representation requires an explicit extension such as `toFloat`;
- guarded newtypes remain limited to immutable built-in scalar and `String` representations;
  generic and nominal newtypes are unguarded in this release;
- runtime type tests and casts targeting a newtype are rejected because the newtype has no distinct
  runtime identity;
- generic newtype constructors may serve as higher-kinded targets, but do not synthesize or forward
  contract evidence;
- compiled-library metadata records type parameters, representation types, guards, visibility, and
  representation contexts, with the schema-version change required by the release policy.

Unary products are not introduced; a one-value nominal view is a newtype. ZEP-0129 records the
comparison and the decision.
