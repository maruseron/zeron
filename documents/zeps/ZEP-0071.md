## Abstract

Replace algebraic-identity requirements for arithmetic operators with a numeric hierarchy named
`Numeric`, `Fractional`, and `Floating`. Unsuffixed numeric literals use their expected type's
numeric evidence and convert from exact integer or rational values, while retaining today's
unconstrained defaults. Exact rational arithmetic is represented by `Rational`, based on
`Ratio<Integer>`.

## Motivation

[ZEP-0036](./ZEP-0036.md) makes `+` and `*` depend on identity-bearing algebraic contracts. That
couples familiar numeric syntax to general algebraic structures: a type with a valid numeric
addition operation must also provide an identity to use `+`, while general higher-kinded
combination and identity abstractions risk being mistaken for numeric capabilities.

A numeric hierarchy separates these concerns. Numeric types explicitly opt into arithmetic and
literal conversion; general abstractions such as semigroups and monoids remain useful for
combinatorial code without granting arithmetic operators. Exact rational literal conversion and a
`Rational` type also avoid making decimal rounding policy a prerequisite for fractional arithmetic.

## Goals

- Define numeric capabilities through a first-order `Numeric` → `Fractional` → `Floating`
  hierarchy, with `Integral` as an integer-specific subtype of `Numeric`.
- Restrict arithmetic operators to the corresponding numeric capabilities, not general HKT
  combination or identity contracts.
- Allow unsuffixed literals to be converted using the expected type's numeric evidence.
- Convert literal values exactly, without an intermediate `Float`.
- Preserve existing defaults for unconstrained integer and fractional literals.
- Provide an arbitrary-precision integer type named `Integer` and an exact rational type based on
  `Ratio<Integer>`.

## Non-goals

- Defining general higher-kinded `Semigroup` or `Monoid` APIs, or making them grant operators.
- Introducing implicit numeric widening, mixed-type operator resolution, or a new complex-number
  API; see [ZEP-0045](./ZEP-0045.md) for heterogeneous operator questions.
- Replacing or generalizing the explicit, imported suffix-factory mechanism in
  [ZEP-0043](./ZEP-0043.md).
- Proving that numeric implementations satisfy algebraic laws.
- Maintaining a Zeron `BigDecimal` wrapper as part of the standard math library.
- Renaming Java's `java.math.BigInteger` type; it remains available through Java interoperation.

## Proposal

### Numeric capability hierarchy

Provide first-order numeric contracts with the following semantic responsibilities:

- `Numeric<T>` supplies addition, subtraction, multiplication, negation, absolute value, signum,
  and conversion from an exact `Integer` value.
- `Integral<T>` extends `Numeric<T>` with exact conversion to `Integer`, truncating quotient and
  remainder (`quot` and `rem`), and floor quotient and remainder (`div` and `mod`).
- `Fractional<T>` extends `Numeric<T>` with division, reciprocal, and conversion from an exact
  rational value.
- `Floating<T>` extends `Fractional<T>` with the standard transcendental and floating-point
  operations listed below.

The conversion members are evidence-dispatched static contract members with these semantic
signatures. `Integral<T>.toInteger` is an instance operation.

```zeron
Numeric<T>.fromInteger(value: Integer): T
Integral<T>.toInteger(this: T): Integer
Fractional<T>.fromRational(value: Rational): T
```

The exact declaration syntax follows Zeron's contract conventions. The operators `+`, binary and
unary `-`, and `*` require `Numeric<T>` evidence; `/` requires `Fractional<T>` evidence.
`Floating<T>` does not add an operator mapping by itself. Initial operator signatures remain
same-type; this proposal does not infer promotions or mixed operand types.

`Floating<T>` provides `sqrt`, `pow`, `exp`, `ln`, `log10`, `sin`, `cos`, `tan`, `asin`, `acos`,
`atan`, and `atan2`, matching the current floating-point math API. Constants such as `PI`, `TAU`,
and `E`, along with rounding functions such as `floor`, `ceil`, `trunc`, and `round`, remain
ordinary standard-library declarations rather than contract members.

The public arbitrary-precision integer type is named `Integer`; its implementation may wrap or
delegate to Java's `java.math.BigInteger`, which remains accessible by its fully qualified Java
name or an explicit import alias. Zeron's `Integer` is distinct from `java.lang.Integer`.

`Integer` and `Rational` are the canonical exact literal carriers. The compiler parses literal
tokens into those exact values directly; constructing a carrier does not call that carrier's own
numeric conversion member. `Numeric<T>.fromInteger` receives an `Integer`, and
`Fractional<T>.fromRational` receives a `Rational`. The corresponding conversions on `Integer`
and `Rational` are identity conversions; `Rational.fromInteger` constructs the exact integral
ratio. This avoids a conversion cycle and avoids exposing an inexact intermediate representation.

Conversion to `Int` or `Long` is range-checked and never wraps. An out-of-range literal is a
compile-time diagnostic; an out-of-range value passed to a conversion member dynamically raises the
host `ArithmeticException`. Conversion from `Rational` to `Float` rounds to the nearest representable
binary64 value, ties to even, according to IEEE 754.

Generic functions using these operations declare the relevant numeric bound explicitly. The
compiler does not infer numeric requirements from an operator expression. Algebraic contracts,
including any `Semigroup` or `Monoid` abstractions, remain independent: conforming to one does not
grant `+`, `*`, or any other arithmetic operator. A numeric newtype may explicitly implement both
numeric and general algebraic capabilities.

### Exact, context-directed numeric literals

When an unsuffixed literal has an expected type, the compiler selects that type's numeric evidence
and converts the literal's mathematical value:

- Integer literals convert from an exact, arbitrary-precision integer value.
- Fractional literals convert from an exact rational value. A decimal such as `0.125` therefore
  denotes `125/1000` (canonically `1/8`) before conversion to the target type.

The conversion must not first parse or round through `Float`. Radix prefixes, digit separators,
and other spelling details do not change the mathematical value used by numeric evidence. Existing
unconstrained defaults remain: integer literals default to `Int`, and fractional literals default
to `Float`. A context that requires numeric conversion but has no applicable evidence produces a
type error rather than silently selecting another type.

The implementation must define how exact literal values are represented and passed to conversion
evidence. That mechanism must not require constructing the target type recursively in order to
construct its own literal value.

### Exact rational arithmetic

Provide a standard-library nominal `Rational` class based on `Ratio<Integer>`:

```zeron
class Rational is Ratio<Integer>;
```

This is an ordinary class over the generic ratio representation and does not require generic
newtype support from [ZEP-0070](./ZEP-0070.md). Its representation must maintain a positive,
nonzero denominator and a reduced fraction; zero is represented with denominator one. Rational
addition, subtraction, multiplication, division by a nonzero value, and conversion from a rational
literal are exact.

Division by zero does not return a `Result` or silently round. Rational division raises the host
`ArithmeticException`, and the exception propagates unchanged. Floating types retain IEEE
floating-point behavior, including infinities and NaN where applicable.

`Int`, `Long`, and `Integer` implement `Integral` (and therefore `Numeric`). `Float` implements
`Numeric`, `Fractional`, and `Floating`; `Rational` implements `Numeric` and `Fractional`, but not
`Integral`. The current Zeron `BigInteger` class is renamed to `Integer`; its `n` suffix spelling
is retained, with the suffix now owned by `Integer`. The current Zeron `BigDecimal` wrapper and its
`D` suffix are removed from the standard library. Java's `java.math.BigDecimal` remains accessible
through ordinary Java interoperation; a separately maintained wrapper is outside this proposal.

`quot` truncates the quotient toward zero and `rem` has the sign of the dividend. `div` rounds the
quotient toward negative infinity and `mod` has the sign of the divisor. Both pairs satisfy
`x = q * y + r`; all four operations propagate the host division-by-zero exception unchanged.
They are available only through an `Integral<T>` bound; `/` remains the `Fractional<T>` operator.

### Custom suffixes remain independent

Custom numeric suffixes remain explicitly imported factories under [ZEP-0043](./ZEP-0043.md).
They continue to receive their declared converted argument or exact source spelling, and do not
require `Numeric` or `Fractional` conformance. A suffixed literal uses its suffix factory rather than
context-directed numeric conversion. Unsuffixed literals use numeric evidence as described above.
Existing built-in suffixes retain their current precedence and behavior.

## Compatibility and impact

This proposal supersedes the operator-to-contract mapping introduced by ZEP-0036 without changing
that accepted proposal's historical record. Existing primitive arithmetic behavior and precedence
must remain unchanged. `Add<T>`, `Addition<T>`, `Mult<T>`, and `Multiplication<T>` remain public
ordinary contracts, but cease to provide compiler-recognized operator evidence. User-defined and
generic code relying on those contracts for operator syntax must migrate to `Numeric<T>` or
`Fractional<T>` and update its explicit bounds. Generic code using integer quotient/remainder
declares `Integral<T>`. The public arbitrary-precision type rename is a source-breaking change;
the `n` suffix spelling is unchanged, though its owning type's import path changes. There is no
transitional release retaining both operator mappings or the old `BigInteger` type name; the
compiler reports missing numeric bounds or unresolved names as appropriate.

The standard-library numeric contracts, witnesses, `Rational` API, literal conversion, and removal
of the `BigDecimal` wrapper affect compiled-library metadata and public API versioning. The
implementation must preserve explicit suffix imports and separately compiled library behavior.
The breaking change ships in one versioned release under the project's pre-1.0 compatibility
policy; no separate deprecation cycle is required.

## Alternatives

- **Keep arithmetic tied to monoid-like contracts** — reuses the shipped design, but makes numeric
  operator availability depend on identities and conflates numeric and general algebraic
  capabilities.
- **Let any combination contract grant `+`** — more permissive, but would make familiar arithmetic
  syntax available to non-numeric structures.
- **Use compiler-recognized built-in numeric types only** — simple for primitive arithmetic, but
  does not support user-defined or generic numeric code through explicit evidence.
- **Retain `BigDecimal` as the standard fractional type** — finite decimal values are exact, but
  general division needs a rounding or failure policy; `Rational` provides exact division without
  that policy.
- **Convert fractional literals through `Float`** — straightforward for the current default, but
  irreversibly loses precision before conversion to exact numeric types.

## Implementation and validation

The numeric contracts and standard-library witnesses are implemented, and arithmetic operator
resolution now requires `Numeric<T>` or `Fractional<T>` evidence for user-defined types. Exact
integer and rational literal conversion is implemented alongside the existing `Int` and `Float`
defaults, and `Integer`/`Rational` provide arbitrary-precision numeric types. General algebraic
contracts remain available but no longer grant arithmetic operators. Generated applications
include the numeric runtime helpers they need.

Validation covers:

- `Numeric`, `Integral`, `Fractional`, and `Floating` conformance, required bounds, and generic
  evidence forwarding;
- integer and fractional literals under expected types, including large integers and fractions not
  exactly representable by `Float`;
- unchanged `Int` and `Float` defaults when literals are unconstrained;
- rejection when the expected type lacks the required numeric evidence;
- exact `Rational` normalization and arithmetic, range checks, and unchanged host exception
  propagation on division by zero;
- unchanged floating-point division behavior and custom suffix factory resolution;
- absence of operator eligibility from general semigroup/monoid evidence; and
- separately compiled libraries, public API metadata including static witness methods, primitive
  intrinsic precedence, standalone application launch, and string concatenation behavior.

## Open questions

None. The conversion carriers and signatures, `Floating` operation set, `BigDecimal` disposition,
and migration path are specified above.

## Decision

Accepted 2026-10-22. The proposal specifies numeric-only operator capabilities, exact
context-directed literal conversion with existing unconstrained defaults, independent explicit
suffix factories, and exact rational arithmetic through `Rational` backed by `Ratio<Integer>`.
Division-by-zero exceptions propagate unchanged to the host. The Zeron `BigDecimal` wrapper and
`zeron.algebra` package are removed, and arbitrary-precision `Integer` and `Rational` live in
`zeron.numeric`. Existing source must migrate in the release that implements this change. This
implementation is included in the 0.6.0 candidate.
