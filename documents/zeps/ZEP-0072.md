# ZEP-0072: Class-Scoped Static Functions as Companion Namespace Members

## Abstract

Allow ordinary Zeron classes to declare `static fn` members. A class-scoped static function is
source-level syntax sugar for a function in a namespace sharing the class's name. It is called
through the class name, has no receiver, and does not introduce JVM-style static dispatch semantics.

## Motivation

Factories and other functions associated with a type are currently declared separately from the
class, in a namespace. This separates related APIs and makes the source less direct. Static
contract requirements solve a different problem: they dispatch through contract evidence, rather
than being ordinary functions associated with a particular class.

Companion namespace syntax would let a class group its ordinary type-related functions with its
instance API while preserving the existing namespace function model. It would also keep the
distinction between class-associated functions and evidence-dispatched contract methods explicit.

## Goals

- Allow ordinary classes to declare static functions callable as `ClassName.function(...)`.
- Define those declarations as namespace functions in the namespace sharing the class name.
- Keep static functions receiver-free and independent of class type parameters.
- Permit a static function to declare and use its own generic type parameters.
- Reject static/instance member name collisions, including collisions with applicable extension
  member names, so lookup remains unambiguous.

## Non-goals

- Static properties or fields.
- JVM-style static member representation or dispatch guarantees.
- Changing static requirements on contracts or static witness implementations.
- Changing namespace functions, extension resolution, or constructor syntax beyond the collision
  rules needed for this feature.

## Proposal

Permit the `static` modifier on a function declared in an ordinary class:

```zeron
public class Box<T: mut> {
    public constructor new(value: T);

    public static fn from<U: mut>(value: U): Box<U> = Box<U>.new(value);
}
```

The declaration is equivalent to a namespace function in the companion namespace:

```zeron
namespace Box {
    public fn from<U: mut>(value: U): Box<U> = Box<U>.new(value);
}
```

Both forms expose the function as `Box.from(...)`. It has no implicit `this`, cannot access
instance state, and does not capture the class's type parameters. In the example, `U` is declared
on the function and is available to its signature and body; the class parameter `T` is not.

Static functions are namespace functions for lookup, overload resolution, and separate compilation.
They must follow the companion namespace's visibility and API-index rules. They do not create
instance methods or JVM static methods as part of the language contract.

Static and instance declarations share a member-name space for collision checking. A class cannot
declare an instance method and a static function with the same name, even when their parameter
types differ. A static declaration also cannot conflict with an applicable extension member name.
This prevents class-associated functions from creating a second interpretation of member syntax
and keeps extension lookup predictable. Ordinary namespace overload rules continue to govern
functions within the companion namespace.

This feature does not alter `static` on contract requirements. A static contract method remains a
requirement implemented by witness evidence; it is not desugared into a namespace function.

## Compatibility and impact

The feature is additive for programs that do not introduce a new static declaration. Code that
introduces a static function whose name conflicts with an instance or applicable extension member
will be rejected and must rename one of the declarations. Existing namespace functions remain
valid.

The compiler and library metadata must represent class-scoped declarations as companion namespace
functions consistently for source lookup, API discovery, and separately compiled clients. Generated
JVM details are implementation-specific and must not expose a new static-dispatch guarantee.

## Alternatives

- **Require namespace functions only** — preserves current behavior but leaves related factories and
  utilities visually separate from their class.
- **Emit JVM static methods on the class** — rejected because the desired feature is syntactic
  grouping within Zeron's namespace model, not a new runtime dispatch mechanism or Java ABI promise.
- **Allow same-named static and instance members** — rejected because it creates competing member
  names and interacts poorly with extension lookup.

## Implementation and validation

Implementation should:

- parse static functions in ordinary class declarations and lower them to companion namespace
  functions;
- reject static declarations that use instance state or implicitly capture class type parameters;
- allow function-local generic parameters;
- enforce the static/instance and extension-member collision rules;
- preserve visibility, diagnostics, member discovery, API-index serialization, and separate
  compilation behavior; and
- verify that contract static requirements and Java external-class static members remain unchanged.

Tests should cover class-name calls, visibility, generic static functions on generic classes,
rejection of instance-state access and class-type-parameter capture, static/instance and extension
collisions, namespace coexistence, and compiled-library clients.
