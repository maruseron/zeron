## Abstract

Extend library-defined numeric suffixes to newtypes, so a library can construct a distinct
newtype value directly from a suffixed integer or decimal literal. This would allow domain-specific
types, including nominal newtypes backed by `Rational`, to have explicit literal spellings without
making them implicitly interchangeable with their representation.

## Motivation

[ZEP-0043](./ZEP-0043.md) introduced statically resolved, library-defined numeric suffixes whose
factories are associated with classes. Newtypes provide a more direct way to express a distinct
semantic view of an existing representation, but the current suffix mechanism does not associate
suffix factories with newtypes.

For example, coordinate components may both be represented by `Rational` while remaining
different source types:

```zeron
newtype XCoordinate = Rational;
newtype YCoordinate = Rational;

let position = Vector.new(1x, 2y);
```

The suffixes could construct `XCoordinate` and `YCoordinate` values directly. The example is
illustrative; it does not prescribe newtype or vector syntax, or the suffix declaration grammar.
This capability depends on defining nominal newtypes over `Rational`, as explored in
[ZEP-0070](./ZEP-0070.md).

## Goals

- Allow a numeric literal suffix to construct a declared newtype value.
- Preserve the newtype's distinct source-level identity and explicit construction semantics.
- Retain static suffix imports, deterministic resolution, and separately compiled library support
  from ZEP-0043.
- Preserve exact literal information until the selected newtype construction path validates or
  converts it.

## Non-goals

- Replacing or duplicating the general suffix mechanism in ZEP-0043.
- Making a newtype implicitly convertible to or from its representation.
- Automatically forwarding numeric contracts or other evidence from a representation to a
  newtype.
- Defining physical units, dimensional arithmetic, or a vector type.
- Defining a general contextual numeric literal model; that is explored separately in
  [ZEP-0075](./ZEP-0075.md).
- Changing unsuffixed numeric literal defaults or the numeric hierarchy from ZEP-0071.

## Proposal

Extend suffix declaration and resolution so a newtype may explicitly associate one or more
supported numeric literal categories with a statically known construction path that produces that
newtype. The exact declaration form, accepted factory shapes, and whether the suffix belongs to the
newtype declaration or a separate declaration remain open.

A suffix must select a newtype deliberately. It must not infer the newtype from its underlying
representation or cause an unsuffixed literal to become that newtype. A value constructed with a
suffix remains nominally distinct and participates in operations only through explicitly declared
members, extensions, or witnesses.

The design should preserve the guarantees of ZEP-0043: suffixes are explicitly imported, aliases
are source-local, suffix matching is deterministic, and library metadata contains the information
needed to resolve and invoke the factory without the library source. Integer and decimal categories
must have defined exact-input behavior; a bounded factory input must not silently wrap or round the
literal.

The implementation should support scalar newtypes already expressible by the language independently
where possible. Newtypes backed by nominal types such as `Rational` require the representation and
construction semantics selected by ZEP-0070. Generic newtypes should not be required unless their
literal construction and metadata rules can be specified without making suffix resolution depend
on arbitrary type inference.

## Compatibility and impact

This adds source syntax or declaration forms, parser and resolver behavior, newtype metadata, and
possibly API-index schema fields. Existing class-owned suffixes and imports remain unchanged.
Existing unsuffixed literal typing and newtype identity remain unchanged.

Separate compilation must preserve suffix ownership and factory signatures for newtypes. Any
schema change must follow the release-cycle policy. The proposal's scope must stay coordinated with
ZEP-0070 so newtype suffix construction cannot bypass its representation, validator, or runtime
identity rules.

## Alternatives

- **Use explicit constructors** — requires no language extension and remains fully explicit, but is
  more verbose at each literal and does not provide suffix notation.
- **Keep suffixes class-only** — preserves the current mechanism, but requires wrapper classes where
  a nominal newtype would otherwise express the domain distinction.
- **Infer a newtype from its representation or expected type** — rejected as the suffix's primary
  meaning because it hides which nominal type is being constructed and makes literal resolution
  context-dependent.

## Implementation and validation

Specify syntax, factory input categories, exactness, and resolution before implementation. Tests
should cover integer and decimal forms, negative literals, imports and aliases, unavailable and
ambiguous suffixes, invalid factory signatures, newtype identity, representation range failures,
guarded construction, and compiled-library round trips. Where the backing representation is
generic or nominal, test the selected ZEP-0070 runtime and metadata behavior.

## Open questions

- Which newtypes may declare suffixes: existing scalar newtypes only, all nominal newtypes, or
  generic newtypes as well?
- Should a suffix factory receive the exact token text, an exact integer/rational value, or a
  category-specific converted value?
- How should suffix declarations be represented and exported for a newtype?
- Can multiple suffixes construct the same newtype, and how are conflicts diagnosed?
- How do newtype validators participate in suffix construction, especially when the representation
  is mutable or nominal?
- Should suffix construction support only direct newtype construction, or may it call an ordinary
  named factory that returns the newtype?
