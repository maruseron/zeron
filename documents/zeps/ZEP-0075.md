## Abstract

Define a general, compositional model for resolving unsuffixed numeric literals from their expected
type. The model should build on the exact, contract-directed literal conversions implemented by
[ZEP-0071](./ZEP-0071.md), while making expected-type propagation explicit and extensible to
future literal forms rather than adding one-off compiler behavior for each syntax.

## Motivation

ZEP-0071 allows an expected numeric type to direct integer and decimal literal conversion through
numeric contracts. It also propagates an expected type through selected numeric expression trees;
for example, `1 / 3` can be resolved as exact `Rational` division when the expression is expected to
have type `Rational`.

This is useful but does not yet define a general model for contextual literal construction. As
additional numeric types and literal forms are introduced, separate hard-coded resolver rules could
make context propagation inconsistent or unpredictable. A compositional model could also guide
future aggregate literals: for example, an expected `Vector2<Rational>` might provide the type
context for each component of a vector literal.

## Goals

- Specify how an expected type can direct the construction of an unsuffixed numeric literal.
- Preserve exact integer and decimal source values until the target conversion is selected.
- Define how context propagates through numeric expression forms such as grouping, unary operators,
  and arithmetic expressions.
- Provide a principled extension point for future library-defined numeric types and composite
  literal forms.
- Preserve existing unconstrained literal defaults and avoid implicit conversions between
  established numeric types.

## Non-goals

- Replacing the numeric hierarchy or exact `Integer` and `Rational` semantics in ZEP-0071.
- Changing the existing default types for uncontextualized integer and decimal literals.
- Treating arbitrary expressions as compile-time values or adding compile-time execution.
- Defining a vector type, vector syntax, physical units, or dimensional arithmetic.
- Replacing explicitly imported suffixes from ZEP-0043 or the proposed newtype suffixes in
  ZEP-0074.
- Adding implicit promotion between `Int`, `Long`, `Float`, `Integer`, `Rational`, or user-defined
  numeric types.

## Proposal

Define a deterministic contextual-construction process for unsuffixed numeric literals. The
expected type supplies a target type; the compiler preserves the literal's exact mathematical
value and resolves an explicitly available conversion capability for that target. If no usable
context exists, existing literal defaults apply. If a target conversion cannot represent the value,
the language must report the specified conversion failure rather than silently rounding or wrapping.

The model should distinguish:

- **Literal syntax and exact value**, including integer and decimal categories, radix and separator
  information where applicable.
- **Target selection**, from an explicit expected type or the existing defaulting rules.
- **Conversion capability**, which states how a target type accepts an exact integer or rational
  value.
- **Context propagation**, which defines which enclosing expression forms pass their expected
  type to contained numeric expressions and which forms establish an independent type context.

The existing numeric contracts are one possible conversion-capability mechanism and should remain
the initial implementation basis unless the design identifies a concrete limitation. The proposal
should evaluate whether separate integer and rational conversion capabilities are sufficient or
whether a shared literal-construction contract is warranted. Whatever mechanism is selected must
remain statically resolvable and available through separately compiled libraries.

Context propagation must be bounded and predictable. It should explain cases such as:

```zeron
let third: Rational = 1 / 3;
let exactSum: Rational = 0.1 + 0.2;
```

It should also consider future aggregate syntax without committing to a particular form:

```zeron
let position: Vector2<Rational> = vector(1 / 3, 0.5);
```

The latter example is illustrative. The design should decide whether a composite literal provides
component contexts, how component types are selected when they differ, and when nested expressions
must instead be explicitly annotated. It must not infer arbitrary type relationships from a
container's representation.

Explicit suffixes remain a separate selection mechanism: a suffix chooses a declared construction
path, while contextual typing directs an unsuffixed literal from its expected type. If both appear
in one expression, their precedence and interaction must be specified rather than left to resolver
accident.

## Compatibility and impact

This proposal primarily clarifies and generalizes static type-resolution behavior, but may require
changes to the AST's literal representation, resolver phases, diagnostics, and compiled-library
contract metadata. Existing ZEP-0071 behavior and exactness guarantees should be preserved unless a
deliberate compatibility change is accepted.

The model must not alter primitive arithmetic, literal defaults, or overload selection for
unrelated expressions. Compiled libraries must expose any conversion evidence needed by consumers.
If a new contract or API-index representation is introduced, its schema version must follow the
release-cycle policy.

## Alternatives

- **Keep the current specialized rules** — avoids additional design and implementation work, but
  risks inconsistent behavior as more literal forms are added.
- **Require explicit constructors or suffixes everywhere** — makes construction visible, but gives
  up concise context-directed literals and duplicates target information already present in a type
  annotation.
- **Use one global conversion table in the compiler** — can be simple for built-in types, but
  prevents ordinary libraries from defining conversions and expands compiler-specific knowledge.
- **Evaluate arbitrary user functions at compile time** — rejected because it introduces general
  compile-time execution, with substantial determinism, safety, and tooling implications.

## Implementation and validation

First document the contextual-construction rules and compare them against the behavior implemented
by ZEP-0071. Tests should cover exact positive and negative integer and decimal values, explicit
expected types, defaults without context, generic target types, contract evidence from compiled
libraries, failed or out-of-range conversions, and the specified propagation through grouping,
unary operations, and arithmetic.

If aggregate literal forms are included in the design, validate each component's independent
expected type, heterogeneous components, inference failures, nested numeric expressions, and
interactions with explicit suffixes. Tests should demonstrate that ordinary function calls and
unrelated expressions do not receive surprising context propagation.

## Open questions

- Are the current `Numeric<T>.fromInteger` and `Fractional<T>.fromRational` capabilities sufficient,
  or should literal construction have dedicated contracts?
- Which enclosing expression forms propagate an expected numeric type?
- How should expected types flow through arithmetic when operand and result types can differ in
  future designs?
- How are contextual conversions selected when several compatible witnesses or conversion paths
  exist?
- Should composite literal forms receive per-component contexts, and how are heterogeneous
  component types represented?
- How do explicitly suffixed literals interact with expected types and contextual conversion?
- Which literal categories, exact representations, and resource limits are included initially?
