## Abstract

Allow an HKT implementation block to opt into forwarding compatible operations to methods declared
on its containing class, instead of spelling out trivial forwarding bodies.

## Motivation

Classes often already expose the operation required by a higher-kinded contract. Their
`implementation` blocks nevertheless repeat receiver forwarding, such as `this.map(transform)`.
This is the same duplication addressed for witnesses, but HKT implementation blocks carry an
explicit operation receiver and live inside the conforming class.

## Goals

- Add an explicit, declaration-level opt-in using `delegating implementation`.
- Forward compatible receiver-based operations to methods declared directly on the containing class.
- Preserve explicit implementation methods as authoritative, including invalid explicit methods.
- Preserve existing behavior for contract defaults and receiverless operations.
- Support mutating operations only when the HKT receiver and target method are compatible.

## Non-goals

- Inferring HKT conformance or implementation blocks from class methods.
- Delegating static or receiverless operations.
- Delegating to extensions, Java members, properties, or methods on another receiver.
- Changing class-header conformance or HKT evidence selection.

## Proposal

Write `delegating` immediately before the class's HKT `implementation` block:

```zeron
class Box<T: mut> is Mapper<Box<_>> {
    public map<R: mut>(transform: (T) -> R): Box<R> =
        Box<R>.new(transform(this.value));

    delegating implementation Mapper<Box<_>> {}
}
```

For each non-default operation with an explicit receiver that is not already implemented in the
block, the compiler compares the operation after applying the HKT constructor pattern with public
instance methods declared directly on the containing class. Matching substitutes the containing
class's type parameters from the operation receiver, then applies the existing signature
compatibility rules, including method type parameters, effects, variadics, receiver mutability, and
return assignability. A compatible method receives a synthesized static implementation helper that
calls it on the operation receiver.

An explicit block method takes precedence, even when invalid; its normal diagnostics are retained
rather than falling back to delegation. Contract defaults and operations without a receiver retain
their existing behavior. Static and unmatched operations are not delegated. Mutating operations
may be delegated when both the HKT receiver and target class method permit mutation.

Delegation does not add a class member or change the class's explicit HKT conformance. The generated
helper uses the existing HKT implementation and bridge representation.

## Compatibility and impact

The contextual `delegating` modifier adds syntax only before `implementation` within a class.
Existing implementation blocks retain their meaning. No runtime or compiled-library metadata
format change is required because generated helpers are recorded as ordinary HKT implementation
methods.

## Alternatives

- Require explicit forwarding methods — rejected because this retains the duplication.
- Infer implementation methods from class methods without an opt-in — rejected because unrelated
  same-named methods must not silently change HKT behavior.
- Permit private methods as candidates — rejected for consistency with delegating witnesses and to
  avoid making private method names part of the automatic matching surface.

## Implementation and validation

- Parse and retain `delegating implementation` on HKT implementation blocks.
- Synthesize helpers before class implementation methods are resolved.
- Exercise generic class parameter substitution, generic operation parameters, mutating receivers,
  explicit overrides, receiverless operations, and HKT dispatch.

## Open questions

None.

## Decision

Accepted on 2026-10-22 and implemented on 2026-10-22. Delegation remains opt-in and uses public
class methods only. HKT implementation blocks preserve their receiver-aware and mutability-aware
semantics.
