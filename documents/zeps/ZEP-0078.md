# ZEP-0078: Default Method Implementations in Higher-Kinded Contracts

## Abstract

Allow higher-kinded contracts to provide default implementations for operations, so common
operations can be derived from the contract's required operations rather than repeated in every
HKT implementation or witness.

## Motivation

Higher-kinded contracts often define operations that can be expressed in terms of other operations
already required by the contract or its parents. For example, `Applicative.map2` can be derived
from `Functor.map` and `Applicative.ap`, and `Foldable.count` or `isEmpty` can be derived from
`foldLeft`. Requiring every HKT implementation to repeat these bodies adds boilerplate and makes
the contracts harder to use.

The parser currently rejects default bodies in HKT contracts, even though regular contracts
already support defaults and HKT evidence can provide the operations used by a derived body.

## Goals

- Permit default bodies on HKT contract operations.
- Type-check each body against the contract's type parameters and required-contract operations.
- Use a default when an HKT implementation or witness does not explicitly provide that operation.
- Preserve explicit implementations as authoritative.
- Make defaults usable when a contract is consumed from a compiled library.
- Keep defaults within the existing contract conformance and evidence model.

## Non-goals

- Inferring HKT conformance or creating new evidence providers from defaults.
- Changing how HKT witnesses or implementation blocks are selected.
- Adding state or changing the runtime representation of HKT evidence.
- Allowing static default operations in the initial feature.

## Proposal

An HKT contract may declare a default body using the existing `default` syntax:

```zeron
public contract Applicative<F<_>> requires Functor<F> {
    ap<A: mut, B: mut>(this: F<A>, transform: F<(A) -> B>): F<B>;

    default map2<A: mut, B: mut, C: mut>(
        first: F<A>,
        second: F<B>,
        combine: (A, B) -> C
    ): F<C> =
        first.map((a) -> (b) -> combine(a, b)).ap(second);
}
```

The body is resolved in the declaring contract's generic scope. It may use the contract's
abstract operations and operations supplied by its transitively required contracts, after applying
the same type substitutions and bounds used for ordinary HKT operation resolution. A default does
not gain access to ambient witnesses that are not part of that required-contract graph.

An operation with a default remains a contract requirement, but an HKT implementation or witness
may omit its body. The compiler supplies the default through the same selected HKT evidence as the
other operations. An explicit implementation takes precedence over a default. Defaults do not
create additional evidence providers.

Default selection follows existing contract rules: a more-specific declaration may override an
inherited default; if multiple unrelated inherited defaults apply to the same operation, an
explicit implementation is required to resolve the conflict. An invalid explicit implementation
continues to receive its ordinary diagnostic and does not silently fall back to a default.

Receiver-based and receiverless HKT operations may have defaults. Their source signatures,
receiver capabilities, effects, and generic bounds retain their existing meanings. A `static`
default is excluded initially because it does not have the evidence-backed operation dispatch
semantics of an HKT contract operation.

The compiler must make a default body callable from HKT evidence generated both in the current
compilation and when consuming a compiled library. The generated contract artifact should expose a
stable callable helper for each HKT default; the library index continues to identify default
operations, while the compiled artifact carries the executable body.

## Compatibility and impact

This adds source syntax previously rejected by the parser. Existing HKT contracts and evidence
remain unchanged. Generated contract artifacts gain callable helpers for HKT defaults; helper
names and descriptors must avoid collisions and preserve generic evidence parameters.

The existing library index already records whether a contract operation has a default. If the
implementation requires additional index metadata, its schema version must be updated in
accordance with the release policy. No default body may be silently unavailable to downstream
compilation of a compiled library.

## Alternatives

- Require each HKT implementation or witness to repeat derived operations — rejected because it
  preserves the boilerplate this feature is intended to remove.
- Permit defaults only when compiling the same source unit — rejected because HKT contracts are
  intended to work across compiled-library boundaries.
- Treat HKT defaults as additional evidence providers — rejected because this would make evidence
  selection ambiguous and change conformance semantics.

## Implementation and validation

- HKT default bodies are parsed and resolved in their declaring contract context, with operations
  available from the transitive required-contract graph.
- Omitted HKT operations use selected defaults for witnesses and class implementation blocks;
  explicit implementations retain precedence, and unrelated inherited defaults diagnose conflicts.
- Compiled contract artifacts expose callable default helpers for separately compiled consumers.
- Runtime and library tests cover receiver-based and receiverless defaults, required-operation
  composition, inherited conflicts, and compiled-library consumption.
- Enabled the standard-library defaults for `map2`, `count`, `isEmpty`, and `sequence`.

## Resolved design choices

- Receiver-based and receiverless non-static HKT defaults are supported; static defaults remain
  excluded.
- Explicit implementations take precedence. Multiple unrelated inherited defaults require an
  explicit implementation to resolve the conflict.
- Default bodies may call operations from their own contract and its transitive `requires` graph,
  but not ambient witnesses.
- HKT defaults are emitted as stable static helpers on the compiled contract artifact so they
  remain callable from separately compiled clients.

## Decision

Accepted and implemented. Receiver-based and receiverless defaults use the same evidence selection
as other HKT operations, explicit implementations remain authoritative, and unrelated inherited
defaults require an explicit implementation. The standard library now uses defaults for
`Applicative.map2`, `Foldable.count`, `Foldable.isEmpty`, and `Traversable.sequence`.
