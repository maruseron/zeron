## Abstract

This proposal introduces a `schema` declaration for describing how a nominal domain type maps to an
external data representation, initially with relational persistence as the motivating use case.

A schema declaration is elaborated by the compiler into ordinary nominal declarations and metadata
that implement defined contracts. The proposal aims to make schema declarations concise while
keeping domain types independent of storage-specific concerns.

## Motivation

ORM APIs frequently force users to choose between concise declarations with weak guarantees and
highly expressive declarations whose type machinery and syntax are difficult to understand. Placing
persistence details directly on domain classes also couples domain models to a particular storage
representation.

A dedicated `schema` declaration can describe table and field mapping without making the domain
type itself a database-specific object. If elaborated into ordinary Zeron declarations, the result
can participate in existing static dispatch, contracts, imports, and type checking.

## Goals

- Introduce a concise declaration for mapping a nominal type to a schema.
- Keep domain types independent of storage-specific mapping details.
- Validate mapped properties and their declared types statically.
- Elaborate schema declarations into ordinary nominal types, contracts, and metadata.
- Permit multiple schemas for one domain type where appropriate.

## Non-goals

- Defining a complete ORM or database client.
- Defining SQL query syntax or query execution.
- Requiring automatic CRUD generation in the initial design.
- Making persistence an inherent property of every domain class.
- Defining database migrations, transaction semantics, or dialect behavior.

## Proposal

### Illustrative syntax

```zeron
class User {
    id: UserId;
    name: String;
    email: String;
    age: Int;
}

schema UserSchema for User {
    table "users";

    id    -> "id"    primaryKey generated;
    name  -> "name"  required;
    email -> "email" unique;
    age   -> "age";
}
```

This syntax is illustrative. The exact grammar and constraint vocabulary remain open.

The schema names a domain type and describes its external representation. Field mappings refer to
declared properties of that type. The compiler validates that referenced properties exist and that
mapping declarations are internally consistent.

### Elaboration

A schema declaration should elaborate into an ordinary nominal descriptor type and associated
metadata. Conceptually, the example could produce an API resembling:

```zeron
class UserSchema is EntitySchema<User> {
    // Table identity and typed column descriptors
}
```

This is a semantic illustration, not a commitment to this exact generated source shape.

Generated declarations should be visible to ordinary type checking and should not require a special
runtime type system. The generated schema type may expose typed column descriptors, table identity,
and other metadata required by libraries.

The elaboration rules must specify generated names, visibility, collisions, and how generated
declarations appear in diagnostics and IDE navigation.

### Domain and schema separation

`User` describes the domain value. `UserSchema` describes one mapping of that value. This
separation permits different mappings for different databases or storage systems without changing
the domain declaration.

The design should distinguish at least:

- a domain type, such as `User`;
- a schema descriptor, such as `UserSchema`;
- a persistence capability or entity contract, if required by a library.

Entity\<T> and EntitySchema\<T> should not be conflated by default: one may describe a domain
capability, while the other describes mapping metadata.

### Annotations and constraints

Schema declarations may use a constrained vocabulary for primary keys, generated values,
uniqueness, nullability, and relationships. Where practical, these should share the
annotation/metadata mechanism proposed by ZEP-0031 rather than introduce unrelated metadata
infrastructure.

The schema feature owns the validation and meaning of schema clauses. It should not assume that
every annotation or constraint is universally meaningful.

### Relationships

A future or expanded form may describe references to other schemas:

```zeron
schema PostSchema for Post {
    table "posts";
    author -> UserSchema.id onDelete Cascade;
}
```

Relationship syntax and semantics are not required for the initial slice.

## Compatibilty and impact

This is an additive source-language declaration and therefore affects parsing, name resolution,
semantic analysis, code generation or declaration elaboration, diagnostics, and library indexes.

Generated declarations become part of the observable source-level API. Their naming and visibility
rules must be stable enough for separate compilation and IDE tooling. Changes to schema elaboration
may therefore have source and compiled-library compatibility implications.

The initial design should avoid silently changing the runtime representation of the domain type.
Schema metadata should be associated with the generated descriptor, not injected into every domain
instance unless a later design explicitly requires it.

## Alternatives

- Persistence annotations directly on domain classes — useful for simple cases, but couples domain
  declarations to persistence and makes multiple mappings harder.
- Ordinary builder APIs only — avoids new syntax, but can make declarative mappings verbose and
  defer errors that could be caught during compilation.
- A fully general code-generation macro system — broader than necessary for a constrained schema
  declaration and harder to validate.

## Implementation and validation

A possible implementation sequence is:

1. Specify the minimum schema grammar and its name-resolution rules.
2. Resolve the target nominal type and validate property references.
3. Elaborate the declaration into generated nominal declarations and metadata.
4. Make generated declarations available to ordinary type checking and library indexing.
5. Add tests for invalid properties, incompatible mappings, duplicate declarations, generated-name collisions, and separate compilation.
6. Build a small example library that consumes the generated schema without requiring ORM-specific compiler support.

The first implementation should target a deliberately small relational mapping surface and defer relationships, migrations, and automatic CRUD generation.

## Open questions

- Is schema a top-level declaration only, or may it be nested in a namespace?
- What is the exact syntax for field mappings and constraints?
- Which contracts must every generated schema implement?
- How are generated declarations named, imported, and exposed in compiled-library metadata?
- Can multiple schemas target the same domain type, and how are they selected?
- Should schema declarations support non-relational storage models from the beginning?
- Which constraints belong in the language grammar and which should be annotations?
