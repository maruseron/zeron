## Abstract

This proposal introduces `model` declarations for describing how a nominal Zeron type maps to an
external representation. A model names an ordinary contract that describes the capabilities
exposed to a consumer, then maps properties of the target type to external field names.

The compiler validates the Zeron side: the target type, the referenced properties, and the
consumer contract. It does not understand the external format. A model is an opt-in singleton
whose descriptor is emitted statically; it provides no introspection of types that were not
mapped.

## Motivation

Libraries that interact with external representations need a way to describe mappings without
coupling domain types to one format. An ORM maps properties to columns; another library may map
them to keys of a document.

Putting those concerns on the domain type makes multiple representations awkward. Builder APIs
avoid that coupling and, with property references ([ZEP-0090](./ZEP-0090.md)), can refer to
properties in a typed way, but they still check little beyond each individual reference:
duplicate mappings, accessibility, and consumer-contract conformance are all checked late, and
the mapping is not available to tools as a declaration. Model declarations provide a concise
declarative mapping with those checks done at compile time.

The scope relative to `deriving Codec` is deliberate. `deriving Codec` gives a type one canonical
serialization. Models serve **additional representations of the same type without modifying
it**, and **consumers that need structure rather than a stream** (persistence, schemas).
Serialization of a type's canonical form is not a motivating case for this proposal.

## Goals

- Map a nominal Zeron type to one or more external representations.
- Keep the mapped type's declaration and runtime representation independent of those mappings.
- Express consumer capabilities through ordinary contracts.
- Validate mapped property references statically using typed property references.
- Permit multiple models for one target type.
- Avoid any dependence on runtime reflection or on type descriptors.

## Non-goals

- An ORM, serializer, database client, query language, or external data format.
- Defining the semantics of mapping annotations or constraints.
- User-defined syntax, arbitrary code generation, or macros.
- Constructing instances of the target type from a model, migrations, or automatic CRUD.
- Introspection of types for which no model was declared.
- Implicit, type-directed resolution of models.
- Changing the layout or behavior of the mapped type.

## Proposal

### Illustrative syntax

```zeron
public model UserSql is SqlModel<User> {
    tableName = "users";

    id   -> "id";
    name -> "name";
}
```

The syntax is illustrative. A model body contains two kinds of clause, distinguished by their
operator:

- `property -> "external"`: a **field mapping**. The identifier on the left is resolved against
  the target type exactly as `User::property` would be, with the same accessibility rule
  ([ZEP-0090](./ZEP-0090.md)): it must name a property with a getter accessible at the model's
  declaration site. The right side is a string literal naming the external field.
- `property = value`: an **assignment to a property of the model's parent contract** (such as
  `tableName = "users"`), type-checked against that property.

The two operators keep the namespaces apart even if the target type has a property named
`tableName`, and keep the body grammar closed. Initializers on the right of `=` are constants:
literals or property references. A model therefore has no initialization-order effects.

### Models are singletons

A `model` declares a named singleton, in the same way a named effect handler declaration does. It
has no constructor and no state, and its name denotes a single value. This is what lets APIs
accept a model as a value:

```zeron
database.from(UserSql).where(user -> user.age >= 18);   // ZEP-0081
```

Rules:

- A model has its own nominal identity and satisfies its declared contract for `T`. It does not
  wrap `T`, add members to `T`, or change `T`'s representation.
- Consumers should accept the contract (`SqlModel<User>`), not the concrete model, and there is no
  implicit resolution of a model from a type. The model is always passed explicitly, so there are
  no coherence or orphan-model problems.
- An anonymous `object : SqlModel<User> { ... }` may satisfy the contract by hand, but it is not a
  model: the mapping syntax, validation, and compiler-generated descriptor belong to `model`.
- **A model name is a first-class value**, like a named handler. It can be bound, stored, and
  passed wherever a value of one of its contracts is expected:

  ```zeron
  let m: SqlModel<User> = UserSql;
  ```

  Following the precedent of named handlers, where the name denotes a value and its type is stated
  through its capability rather than through the name, the model's name is not additionally a
  type. Declaring a model but forbidding it from being used as a value would create an asymmetry
  with handlers for no benefit.

### Core contracts and classes

```zeron
// illustrative
public contract Model<T: nullable + mut> {
    property fields: Array<AnyField<T>>;
    field<V: nullable + mut>(source: PropertyRef<T, V>): Option<Field<T, V>>;
    fieldOf(id: PropertyId): Option<AnyField<T>>;
}

// erased view of a mapping; independent of Field (no inheritance between them)
public class AnyField<T: nullable + mut> {
    public property externalName: String;
    public property sourceId: PropertyId;
}

// typed view of a mapping; independent of AnyField (no inheritance between them)
public class Field<T: nullable + mut, V: nullable + mut> {
    public property externalName: String;
    public property sourceId: PropertyId;               // equals source.id
    public property source: PropertyRef<T, V>;
    public property writer: Option<(&T, V) -> Unit>;   // present if a setter is accessible
}

public contract SqlModel<T: nullable + mut> requires Model<T> {
    property tableName: String;
}
```

- **Mappings are emitted as read-only metadata.** For each `model` the compiler generates the
  singleton implementing `Model<T>`; it does not synthesize arbitrary contract methods from
  clauses. `Model<T>` is therefore close to an ordinary contract, and compiler support is limited
  to generating the descriptor and validating references.
- **`PropertyRef<T, V>` identifies the property** (see [ZEP-0090](./ZEP-0090.md)).
  `model.field(User::name)` returns a `Field<User, String>`; the source type reaches the caller
  without any runtime type information, and the compiler guarantees the correspondence. Lookup
  uses reference identity, so `Named::name` (a contract property) does not find a mapping for
  `User::name`, because they are different declarations.
- **`PropertyId` relates mappings to expressions** ([ZEP-0093](./ZEP-0093.md)). Every field
  exposes the `PropertyId` of its source property, and `fieldOf(id)` finds a mapping from an
  identity alone, for example the identity of a property named in a code model
  ([ZEP-0080](./ZEP-0080.md)). A consumer therefore does not need to construct a `PropertyRef` to
  look up a mapping. The result is the erased `AnyField<T>`, because an identity carries no value
  type; typed access remains `field(PropertyRef)`. For a `Field<T, V>`, `sourceId` equals
  `source.id`.
- **`fields` enumerates** the mapped fields through `AnyField<T>`, which erases `V`.
  Zeron erases generics at runtime, so a consumer cannot recover `V` by pattern matching. It
  obtains typed access through `field(...)`, or through behavior the compiler generates (see
  Future extensions). The proposal intentionally does not add a `TypeDescriptor`.
- **`AnyField<T>` and `Field<T, V>` are separate classes.** Both are final and neither extends the
  other. `AnyField<T>` is the erased view, returned by `fields` and `fieldOf`; `Field<T, V>` is
  the typed view, returned by `field`. Both carry `externalName` and `sourceId`. There is no
  downcast from one to the other: a consumer that holds an `AnyField<T>` and needs typed access
  obtains it with `field(PropertyRef)`. Because they are final, user code cannot implement
  either, and changing their members later would be a compatibility decision.
- **`field` returns `Option`.** An unmapped property is the ordinary absent case.

### Static validation

The compiler must:

- require that the target type is nominal and resolve it;
- reject unknown properties and properties without an accessible getter at the declaration site;
- fill `writer` when an accessible setter exists;
- **reject duplicate mappings of the same source property**;
- check parent-contract property assignments against their types and require all required
  properties;
- require parent-contract initializers to be constants.

A mapped property is a getter/setter pair, so a "stored" versus "computed" distinction does not
exist; accessibility decides what can be mapped. Duplicate **external names** are not checked by
the compiler, because it does not know what they mean; a consumer may reject them.

The compiler guarantees that a property exists, that its type is represented faithfully in
`Field<T, V>`, and that the typed lookup is coherent. It does not guarantee that `V` suits any
external format; that is the consumer's responsibility.

### Target types

- The target may be declared in another library, subject to the same public-getter limitation as
  property references.
- A generic target must be fully instantiated: `model IntBoxSql is SqlModel<Box<Int>>` is valid.
  Because [ZEP-0090](./ZEP-0090.md) preserves applied owner arguments, mapped properties have
  their instantiated types.
- A generic model (`model BoxSql<T> ...`) is not supported, since a singleton cannot be generic.
- Models are declared at package level, like other types. They cannot be nested.

### Partial mappings

In the first version, models are partial: a model may map a subset of the target type's
properties. Because a model never constructs the target type, this is always well-formed. The
compiler cannot be asked to check totality, and a consumer has no way to verify it without
introspection of the target type, so v1 provides no totality guarantee. A compiler-checked
`total` modifier, with an explicit way to omit properties, is future work.

### Evidence and the consumer's contract

`Model<T>` imposes no capability on mapped property types. Whether a field's value type must be
serializable (`Encode`, `Decode`, `Codec`) is a requirement of the consumer, because the
requirement differs per consumer (a read-only export needs only `Encode`). Where a consumer asks
for a typed field, it can state this as a bound on `V` in its own API. Requiring evidence for
every field of an enumerated model needs compiler-generated behavior and is deferred to
[ZEP-0092](./ZEP-0092.md).

### Field metadata and annotations

Annotations require explicit targets, and [ZEP-0031](./ZEP-0031.md) defines none that covers a
mapping clause. This proposal therefore does **not** accept annotations on clauses in the first
version, and does not define how annotations are read ([ZEP-0091](./ZEP-0091.md) addresses
consumption). [ZEP-0097](./ZEP-0097.md) proposes a `MAPPING` target for field-mapping clauses;
once it is accepted, annotations on clauses can be introduced additively. `Field.annotations` is
reserved. A model does not expose the annotations of the mapped property on the target type:
those stay with the target's declaration, so that the target remains independent of any one
representation.

Until then, consumers can capture metadata that is singular and structural as typed properties of
their own contracts, including property references, for example:

```zeron
// illustrative: a consumer contract, not part of this proposal
public contract SqlModel<T: nullable + mut, K: nullable + mut> requires Model<T> {
    property tableName: String;
    property primaryKey: PropertyRef<T, K>;
}
```

Such a reference is typed against the target type, but nothing makes the compiler check that the
referenced property is also mapped in the model. That cross-check is not provided by this
proposal. Per-field flags (for example, generated values) wait for annotation consumption.

The model feature does not define a vocabulary of format-specific keywords.

### Relationship to `deriving Codec`

The two mechanisms are separate. Names and aliases used by `deriving Codec` for a type's canonical
serialization come from that type's derivation; names in a model apply to that model's
representation only. Overlap in renaming is acknowledged as a known cost, and may be revisited
once annotations can be consumed. A model may later be accepted as a source of identifiers for a
derivation, but this proposal does not specify it.

### Future extensions

None of the following is part of the first version.

- **Generated serialization operations.** When [ZEP-0092](./ZEP-0092.md) provides generated encode
  and decode entry points, a model could expose per-field operations, for example
  `encode(owner, encoder)` implemented as `encode<V>(source.get(owner), encoder)` with evidence
  resolved where the model is declared. Writing into existing mutable properties (`decodeInto`)
  could use `writer`. A static `shape: ValueKind` could be exposed for schema-oriented consumers.
  [ZEP-0092](./ZEP-0092.md) leaves an opt-in consumer contract for per-field operations to a
  follow-up, so models are unaffected until one exists.
- **Annotations on clauses**, through the `MAPPING` target of [ZEP-0097](./ZEP-0097.md), once
  [ZEP-0091](./ZEP-0091.md) defines their consumption.
- **Total models**, checked by the compiler, together with the placement of modifiers on a model
  declaration. Both are left to a separate proposal.
- **Compiler-checked cross-references** between consumer-contract properties and mapped fields.

## Compatibility and impact

This additive declaration affects parsing, name resolution, type checking, diagnostics, and the
library index. A `model` is a new kind of declaration, so the library index needs an entry for it
and `API_INDEX_SCHEMA_VERSION` is expected to change. The entry records the ordinary singleton
declaration, a marker that it originates from a `model`, the target type, the parent contract
assignments, and, per field, the property identity (as defined by
[ZEP-0090](./ZEP-0090.md): `declaringQualifiedName#propertyName`) and the external name. The
property identity also gives later work an anchor for attaching metadata. No separate artifact
format is defined for models.

Models may be public and used across compilations, so visibility, imports, and identity follow
ordinary library rules. Changing a model's external names changes the behavior of the API that
exposes it and is versioned like any other API change; no versioning mechanism specific to models
is defined. Changes to a model must not silently change the target type.

## Alternatives

- **Mapping annotations on domain properties** — concise for one representation, couples the
  type, and complicates multiple mappings. Also cannot be consumed today.
- **Builder APIs with property references** — avoid new syntax and now give typed references.
  They cannot reject duplicates, check consumer-contract conformance, or expose a declaration to
  tools without additional machinery. This is the closest alternative, and the gap it leaves is
  the case this proposal must justify.
- **`deriving Codec` plus annotations on the type** — suitable for one canonical representation.
  Does not support several representations without touching the type.
- **Format-specific compiler declarations** — duplicate compiler features and require knowledge
  of each format.
- **Runtime type descriptors** — would provide format-neutral type information but introduce a
  runtime type system that resembles reflection; rejected for the first version.
- **Macros or user-defined syntax** — much broader than required.

## Implementation and validation

1. Property references ([ZEP-0090](./ZEP-0090.md)) are implemented; `PropertyId`
   ([ZEP-0093](./ZEP-0093.md)) is required.
2. Define the `model` grammar, target resolution, visibility, and singleton identity.
3. Generate the model singleton implementing `Model<T>`, including `fields`, `field`, and `writer`.
4. Validate mapped properties, duplicates, accessibility, and parent-contract assignments.
5. Add the model declaration to the library index and preserve it across separate compilation.
6. Test unknown properties, duplicate mappings, inaccessible getters, writer presence, invalid
   contract conformance, non-constant initializers, partial mappings, instantiated generic
   targets, foreign targets, and diagnostics.
7. Test that `field(...)` returns the typed field for a mapped property and `None` for an
   unmapped one, and that a contract-owned reference does not find a class property's mapping.
   Test that `fieldOf(id)` finds the mapping for the `PropertyId` of a property named in a code
   model, returns `None` for an unmapped property, and agrees with `field(...)` on `sourceId`.
8. Test that a function taking `SqlModel<User>` infers `T = User` from a model passed as a value,
   as in the example of [ZEP-0081](./ZEP-0081.md), and that a model name can be bound to a
   binding typed with its contract.
9. Build independent consumer examples (a persistence-style and a document-style consumer) to
   verify the compiler remains agnostic about each format.

The first implementation uses a deliberately small mapping surface and excludes relationship
traversal, migrations, automatic CRUD, annotations on clauses, and user-defined syntax.

### Implementation notes (2026-11-08)

Validation against the declared scope is complete. `ModelCompilationTest` covers the full
acceptance surface: typed and `fieldOf` lookups, agreement of `sourceId` with a reference's `id`,
field order, empty and partial models, contract-versus-class identity, instantiated generic
targets, foreign targets across three compilations, writers including custom setters, models passed
as `Model<T>` directly and through an intermediate contract, the library-index record, contract
typed access, and rejection of duplicate, unknown, inaccessible, and type-mismatched mappings and
assignments. `DslCompositionTest` supplies the composed consumer of [ZEP-0081](./ZEP-0081.md).

Two documentation corrections belong to this validation. `guide/34-model-declarations.md` no longer
claims that mappings are read-only; it documents that an accessible setter yields a writer.
`AnyField` and `Field` keep public constructors because the generated model implementation lives in
the consumer's package and `Model.field` constructs the typed view in `zeron.lang`; the standard
library comment now says a model creates the instances it exposes instead of implying exclusive
construction.

### Implementation notes (2026-11-07)

A model value can be passed where `Model<T>` is expected, whether the model declares `Model<T>`
directly or through an intermediate contract such as `SqlModel<User>`. Generic inference now
projects a class's contract uses to the expected generic contract, substituting the class's type
arguments, instead of requiring the argument's type to be that contract already. This is what makes
`jsonModel(UserWire, user)` and `acceptsAnyModel<T>(model: Model<T>)` accept a model. A model also
binds directly to a parent contract (`let model: Model<User> = UserDoc`). `ModelCompilationTest`
covers a generic `Model<T>` consumer for both consumer contracts, a direct parent-contract binding,
and the same inference across separate compilation. The generated singleton's constructor is public
in bytecode because the compiled top-level value initializer lives in another class; the class name
is unlexable and its library-index export hides the constructor, so this is not a source-level
construction API.

### Implementation notes (2026-11-06)

Writer tracking is implemented. `PropertyReferenceResolver` synthesizes an assignment lambda for a
mapped property that is mutable and accessible and resolves it against `(&T, V) -> Unit`;
`PropertyRef.writer` carries it as an `Option`, `Model.field` forwards it to `Field.writer`, and the
synthesized property-reference factory and `BytecodeEmitter` pass the extra argument. A read-only
mapped property has no writer.

`ModelCompilationTest` covers writing and reading back a mutable mapped property, the absence of a
writer for a read-only property, writer use across separate compilation, and two independent
consumers over one type: the SQL-style `SqlModel` and a document-style `DocumentModel`.
Annotations on clauses, a compiler-checked `total` modifier, and per-field serialization operations
remain deferred.

### Implementation notes (2026-11-04)

The declaration, its validation, the generated descriptor, and the library-index entry are
implemented; `writer` tracking and the consumer examples of step 9 are not.

- `model` is a contextual keyword. A declaration parses to `Expr.ModelLiteral` and behaves like a
  named handler declaration: `Stmt.Var` with an immutable value type. Resolution resolves the
  parent contract, takes `T` from the applied `zeron.lang.Model<T>` in its composition closure,
  and synthesizes one package-private class per model implementing the parent contract. The class
  is named `<model name>$model`, so the model's name stays a value and a member call on it is never
  read as a static call on a class.
- The synthesized class stores the parent contract's assigned properties as canonical constructor
  parameters and implements `fields` through a generated getter that builds one `AnyField<T>` per
  mapping. Clauses are validated by the property-reference resolver, so unknown and inaccessible
  properties report the same diagnostics as `T::p`; duplicate identities, duplicate assignments,
  non-constant assignments, and missing contract property assignments are rejected.
- `zeron.lang.Model`, `AnyField`, and `Field` live in `zeron.lang.model`. `Model.field` and
  `Model.fieldOf` are contract default methods rather than methods generated per model, so a model
  supplies `fields` plus its parent contract's properties and nothing else. `Field.get` reads
  through the `PropertyRef`, and no runtime type information is introduced.
- Mappings record only the property's `PropertyId` (as `AnyField.sourceId`); the compiler emits the
  identity directly, because a descriptor has no use for a `PropertyRef` reader.
- Deviation from the original draft: `AnyField<T>` and `Field<T, V>` are independent final
  classes, not a sealed contract with `Field` as its variant. Sealed permits require the same
  type-parameter arity, so `Field<T, V>` cannot be a permitted implementation of `AnyField<T>`
  in the current language.
- A public model is exported as `ModelExport`: the target type, the parent contract, each
  mapping's property identity and external name, and the contract property assignments, next to the
  ordinary `ValueExport` for the model's name and a `ClassExport` for its implementation class.
  The record extends the unreleased schema 9 instead of bumping `API_INDEX_SCHEMA_VERSION`, because
  the release cycle already bumped it. Consumers materialize the value and the class, so `field`,
  `fieldOf`, `fields`, and contract-typed use work across separate compilations; lookup remains
  identity-based, so a consumer's `(User::name).id` matches the ids the library recorded.
- Deferred at the time (writer support was added on 2026-11-06, below): `Field.writer` and setter
  tracking; annotations on clauses; and a compiler-checked `total` modifier.
- Validation: `ModelCompilationTest` compiles a model, reads mappings through `field`, `fieldOf`,
  and `fields`, passes the model where `SqlModel<User>` is expected, binds it to a contract-typed
  value, and rejects duplicate mappings, unknown properties, missing and non-constant contract
  property assignments, and a contract that does not require `Model<T>`. It also compiles a library
  whose public model is exported, checks the index record and the implementation-class export, and
  compiles a consumer that imports the model and reads it across the library boundary.

## Open questions

None. The exact placement of modifiers on a model declaration, and the syntax of a future `total`
modifier, are deferred to a separate proposal.

Per-field evidence and the `path` of errors raised through a model are addressed by
[ZEP-0092](./ZEP-0092.md): `Model<T>` itself requires no evidence, and errors raised through a
model use the clause's external name in their `path`.

## Decision

Accepted and implemented on 2026-11-06. The declaration, validation, generated descriptor, and
library-index entry are implemented, and mappings record an optional writer for properties with an
accessible setter. Annotations on clauses, a compiler-checked `total` modifier, and generated
per-field serialization operations remain outside the first version, as recorded above.
