## Abstract

This proposal introduces `model` declarations for describing how a nominal Zeron type maps to an
external representation. A model names an ordinary contract that describes the capabilities
exposed to a consumer, then maps properties of the target type to external field names.

The compiler validates the Zeron side: the target type, the referenced properties, and the
consumer contract. It does not understand the external format. Models are opt-in, closed, and
statically emitted descriptors; they provide no introspection of types that were not mapped.

## Motivation

Libraries that interact with external representations need a way to describe mappings without
coupling domain types to one format. An ORM maps properties to columns; another library may map
them to keys of a document.

Putting those concerns on the domain type makes multiple representations awkward. Builder APIs
avoid that coupling and, with property references, can refer to properties in a typed way, but
they still check little beyond each individual reference: duplicate mappings, accessibility,
consumer-contract conformance, and mapping metadata are all checked late, and the mapping is
not available to tools as a declaration. Model declarations provide a concise declarative
mapping with those checks done at compile time.

The scope relative to `derive Codec` is deliberate. `derive Codec` gives a type one canonical
serialization. Models serve **additional representations of the same type without modifying
it**, and **consumers that need structure rather than a stream** (persistence, schemas).
Serialization of a type's canonical form is not a motivating case for this proposal.

## Goals

- Map a nominal Zeron type to one or more external representations.
- Keep the mapped type's declaration and runtime representation independent of those mappings.
- Express consumer capabilities through ordinary contracts.
- Validate mapped property references statically using typed property references.
- Permit multiple models for one target type.
- Avoid any dependence on runtime reflection or on type descriptors.

## Non-goals

- An ORM, serializer, database client, query language, or external data format.
- Defining the semantics of mapping annotations or constraints.
- User-defined syntax, arbitrary code generation, or macros.
- Constructing instances of the target type from a model, migrations, or automatic CRUD.
- Introspection of types for which no model was declared.
- Changing the layout or behavior of the mapped type.

## Proposal

### Illustrative syntax

```zeron
public model UserSql is SqlModel<User> {
    tableName "users";

    id   -> "id";
    name -> "name";
}
```

The syntax is illustrative. Two kinds of clause exist, distinguished syntactically:

- `property -> "external"`: a **field mapping**. The identifier must resolve to a property of the
  target type.
- `property value`: an **assignment to a property of the model's parent contract** (such as
  `tableName "users"`), type-checked against that property.

This keeps the two namespaces apart even if the target type has a property named `tableName`,
and keeps the body grammar closed.

### Core contracts and classes

```zeron
// illustrative
public contract Model<T> {
    property fields: Array<AnyField<T>>;
    field<V>(source: PropertyRef<T, V>): Option<Field<T, V>>;
}

public sealed contract AnyField<T> {
    property externalName: String;
}

public class Field<T, V> is AnyField<T> {
    public property source: PropertyRef<T, V>;
    public property writer: Option<(&T, V) -> Unit>;   // present if a setter is accessible
}

public contract SqlModel<T> requires Model<T> {
    property tableName: String;
}
```

- **Mappings are emitted as read-only metadata.** The compiler generates a final class for each
  `model` implementing `Model<T>`; it does not synthesize arbitrary contract methods from
  clauses. `Model<T>` is therefore close to an ordinary contract, and compiler support is limited
  to generating the descriptor and validating references.
- **`PropertyRef<T, V>` identifies the property** (see [ZEP-0090](./ZEP-0090.md)). `model.field(User::name)`
  returns a `Field<User, String>`; the source type reaches the caller without any runtime type
  information, and the compiler guarantees the correspondence.
- **`fields` enumerates** the mapped fields through the sealed `AnyField<T>`, which erases `V`.
  Zeron erases generics at runtime, so a consumer cannot recover `V` by pattern matching. It
  obtains typed access through `field(...)`, or through behavior the compiler generates (see
  Future extensions). The proposal intentionally does not add a `TypeDescriptor`.
- **`AnyField<T>` is sealed with a single variant today.** This is intentional: it erases `V`
  for enumeration and leaves room for further variants without breaking exhaustive consumers.
- **Identity.** A model has its own nominal identity and satisfies its contract for `T`. It does
  not wrap `T`, add members to `T`, or change `T`'s representation.

### Static validation

The compiler must:

- resolve the target type and reject unknown properties;
- require an accessible getter for each mapped property at the model's declaration site;
- fill `writer` when an accessible setter exists;
- **reject duplicate mappings of the same source property**;
- check parent-contract property assignments against their types and require all required
  properties;
- validate annotations written on clauses for identity, applicability, and argument shape.

A mapped property is a getter/setter pair, so a "stored" versus "computed" distinction does not
exist; accessibility decides what can be mapped. Duplicate **external names** are not checked by
the compiler, because it does not know what they mean; a consumer may reject them.

The compiler guarantees that a property exists, that its type is represented faithfully in
`Field<T, V>`, and that the typed lookup is coherent. It does not guarantee that `V` suits any
external format; that is the consumer's responsibility.

### Partial mappings

A model may map a subset of the target type's properties. Because a model never constructs the
target type, this is always well-formed. A consumer that requires complete mappings states so
in its own contract documentation, and may later be backed by a compiler-checked totality
requirement.

### Evidence and the consumer's contract

`Model<T>` imposes no capability on mapped property types. Whether a field's value type must be
serializable (`Encode`, `Decode`, `Codec`) is a requirement of the consumer, because the
requirement differs per consumer (a read-only export needs only `Encode`). How a consumer
contract expresses a per-field requirement is an open question.

### Field metadata and annotations

A mapping clause may carry annotations declared under ZEP-0031, and the compiler validates them
and records them in the library index. **This proposal does not define how annotations are read**:
ZEP-0031 provides no consumption API and a separate proposal ([ZEP-0091](./ZEP-0091.md)) will address it.
`AnnotatedField` access is therefore reserved and not part of the first version. Until then,
consumers express metadata through typed properties of their own contracts, for example a per-field
contract with `primaryKey: Boolean`.

The model feature does not define a vocabulary of format-specific keywords.

### Relationship to `derive Codec`

The two mechanisms are separate. Names and aliases used by `derive Codec` for a type's canonical
serialization come from that type's derivation; names in a model apply to that model's
representation only. Overlap in renaming is acknowledged as a known cost, and may be revisited
once annotations can be consumed. A model may later be accepted as a source of identifiers for a
derivation, but this proposal does not specify it.

### Future extensions

When [ZEP-0092](./ZEP-0092.md) provides generated encode and decode entry points, a model could expose
per-field operations, for example `encode(owner, encoder)` implemented as
`encode<V>(source.get(owner), encoder)` with evidence resolved where the model is declared. Writing
into existing mutable properties (`decodeInto`) could use `writer`. A static `shape: ValueKind` could
be exposed for schema-oriented consumers. None of these is part of the first version.

## Compatibility and impact

This additive declaration affects parsing, name resolution, type checking, diagnostics, and the
library index. Each model records, per field, the stable identity of the property (shared with
property references), the external name, and any annotations as declared, using the index
mechanism already used for annotations. No separate artifact format is defined for models.

Models may be public and used across compilations, so visibility, imports, and identity follow
ordinary library rules. Changes to a model must not silently change the target type.

## Alternatives

- **Mapping annotations on domain properties** — concise for one representation, couples the
  type, and complicates multiple mappings. Also cannot be consumed today.
- **Builder APIs with property references** — avoid new syntax and now give typed references.
  They cannot reject duplicates, check consumer-contract conformance, or expose a declaration to
  tools without additional machinery. This is the closest alternative, and the gap it leaves is
  the case this proposal must justify.
- **`derive Codec` plus annotations on the type** — suitable for one canonical representation.
  Does not support several representations without touching the type.
- **Format-specific compiler declarations** — duplicate compiler features and require knowledge
  of each format.
- **Runtime type descriptors** — would provide format-neutral type information but introduce a
  runtime type system that resembles reflection; rejected for the first version.
- **Macros or user-defined syntax** — much broader than required.

## Implementation and validation

1. Specify and implement property references ([ZEP-0090](./ZEP-0090.md), implemented).
2. Define the `model` grammar, target resolution, visibility, and nominal identity.
3. Generate the model descriptor implementing `Model<T>`, including `fields`, `field`, and `writer`.
4. Validate mapped properties, duplicates, accessibility, and parent-contract assignments.
5. Accept annotations on clauses and record them in the index without a consumption API.
6. Preserve model information across separate compilation.
7. Test unknown properties, duplicate mappings, inaccessible getters, writer presence, invalid
   contract conformance, partial mappings, annotation validation, diagnostics, and library use.
8. Build independent consumer examples (a persistence-style and a document-style consumer) to
   verify the compiler remains agnostic about each format.

The first implementation uses a deliberately small mapping surface and excludes relationship
traversal, migrations, automatic CRUD, and user-defined syntax.

## Open questions

- Exact grammar for models, clauses, and the placement of annotations.
- How does a consumer contract state a per-field requirement (such as `Encode` evidence)?
- How are `Model<T>`'s generic method and sealed `AnyField<T>` presented in diagnostics and
  tooling?
- Should `field` return `Option<Field<T, V>>` or a sealed mapping result (`Mapped`/`Unmapped`)
  to allow further states such as `Excluded`?
- Should a model be able to require total mappings?
- Is a model permitted for a generic target type, or for a type from another library?
- Top-level only, or nested within namespaces?
- How are models named, imported, indexed, and versioned across separate compilation?
- What is the canonical behavior of `path` in encode and decode errors when produced via a model?
  They should use the external name; this must align with [ZEP-0092](./ZEP-0092.md).
