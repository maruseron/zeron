## Abstract

This proposal introduces an opt-in `@CodeModel` parameter annotation that allows a function to
receive a typed, inspectable representation of a caller-supplied expression instead of receiving
only an executable function value.

The initial model is produced from expressions that the compiler has already resolved and
type-checked. It is a stable, read-only representation intended for libraries that translate or
analyze expressions, such as query builders, validators, and serializers.

## Motivation

Some APIs need to interpret the structure of a lambda rather than execute it. A query builder, for
example, needs to translate `user -> user.age >= 18` into a query predicate. Receiving an ordinary
function value does not provide a portable or reliable way to recover the source-level expression.

Exposing the compiler's internal AST directly would couple libraries to parser and resolver
implementation details. Re-parsing source text or inspecting JVM bytecode would be unreliable and
would discard useful source-level type information.

A typed code model provides a narrow boundary: the compiler guarantees that the expression is
resolved and well-typed, while the consuming library defines what the represented operations mean
in its own domain.

## Goals

- Allow selected parameters to request a typed model of a caller-supplied expression.
- Build the model only after normal name resolution and type checking.
- Preserve source-level type information needed by consumers.
- Keep the public representation independent of the compiler's internal AST.
- Make unsupported constructs diagnosable at compile time.
- Support non-ORM consumers such as validators, serializers, and authorization libraries.

## Non-goals

- General reflection over runtime values, stack frames, local variables, or arbitrary program state.
- Exposing mutable compiler AST nodes.
- General-purpose macros or compile-time execution.
- Guaranteeing that every valid Zeron expression can be represented.
- Defining SQL, validation, serialization, or authorization semantics in the language.

## Proposal

### Parameter annotation

The proposed API shape is:

`CodeModel` is the declared `zeron.compiler.CodeModel` annotation with the `PARAMETER` target,
defined by [ZEP-0031](./ZEP-0031.md). The compiler recognizes this canonical annotation identity;
other declared annotations do not acquire compiler behavior merely by being present.

The annotated parameter has an explicit `CodeModel<F>` wrapper type, where `F` is the function
type of the supplied expression:

```zeron
import zeron.compiler.CodeModel;

class Query<T: Entity> {
    public where(
        @CodeModel predicate: CodeModel<(T) -> Boolean>
    ): Query<T> { ... }
}
```

The wrapper is an immutable runtime value and is not an executable callback. The call supplies an
inline lambda expression in the ordinary function shape, for example
`query.where(user -> user.age >= minimumAge)`. The compiler resolves and type-checks that lambda
against the wrapped function type, then supplies its model. A pre-existing function value or
function reference has no recoverable source expression and is not accepted for an initial
`@CodeModel` parameter.

### Typed semantic representation

The model represents resolved semantic constructs, not raw source text. A simple predicate might be
represented conceptually as:

```text
Lambda
  Parameter(user: User)
  GreaterThanOrEqual
    PropertyAccess(user, User.age: Int)
    Literal(18: Int)
```

The public model API should be defined independently of internal compiler AST classes. It should
expose an immutable `CodeModel<F>` root and a structural `CodeType` representation for source-level
types. Resolved properties and other declaration references use stable qualified source identities
and resolved signatures, not JVM implementation names or compiler-internal numeric IDs. Lambda
parameters are identified by stable positions within the lambda; source names may be retained for
display and diagnostics.

The model should retain:

- resolved parameter identities;
- expression node kinds;
- source-level types of nodes;
- resolved property and callable identities;
- literal values;
- source locations where useful for diagnostics.

It should not expose compiler-internal mutable objects or depend on JVM bytecode layout.

### Initial expression subset

The first slice should support a deliberately small expression language suitable for common
predicates:

- lambda parameters and references to them;
- typed string, Boolean, numeric, and null literals;
- property access;
- comparisons (`==`, `!=`, `<`, `<=`, `>`, and `>=`);
- Boolean conjunction, disjunction, and negation;
- null tests;
- immutable captured values, represented as bindable capture slots.

Arithmetic expressions, method/function calls, statements, mutation, effects, arbitrary control
flow, and function references are outside the initial subset. Parentheses do not add semantic nodes.
The compiler rejects any unsupported construct with a diagnostic; it never falls back to executing
the lambda.

### Captured values

Captured values should be represented separately from expression structure. For example:

```zeron
let minimumAge = 18;
query.where(user -> user.age >= minimumAge);
```

The model identifies a stable capture slot, while the corresponding value is supplied separately
as a bindable capture. Each captured immutable binding is evaluated once, eagerly, when the
annotated argument is evaluated at the call site; repeated references to that binding use the same
slot. Each call creates a model carrying that call's capture values. Consumers may reuse a
translation plan for the expression structure while binding the current model's capture values.
Captures are values, not live variable references; mutation through an aliased object is not
deep-copied or otherwise given special semantics.

### Consumer interpretation

A consumer traverses the typed model and interprets supported nodes. For example, an SQL backend
may translate property access to a column reference and a comparison to a parameterized predicate.
Captured values are supplied as parameters, never interpolated into generated SQL text. The model
does not generate or compile Zeron source, and third-party translation runs as ordinary runtime
library code, not as a compiler plugin or compile-time expansion.

The language does not guarantee that every consumer supports every node. Consumers must be able to
reject unsupported nodes with meaningful diagnostics or errors.

If a function needs both an inspectable model and an executable callback, it declares separate
parameters: an annotated `CodeModel<F>` parameter and an ordinary `F` parameter. The call supplies
each argument explicitly; the compiler does not implicitly create both views from one lambda.

### SQL null semantics

This proposal does not define SQL semantics. However, an ORM consumer must not assume that a Zeron
Boolean predicate and SQL's three-valued predicate logic are interchangeable. A query API may use a
dedicated predicate type or define an explicit translation policy.

## Compatibility and impact

The feature affects parameter annotations, call resolution, lambda typing, semantic-model
construction, runtime model construction, diagnostics, and compiled-library metadata.

The annotated parameter type and annotation identity are carried through the existing versioned
API index, so call sites can recognize `@CodeModel` across separate compilation. Runtime model
objects are not serialized or persisted. The public model API evolves under the standard-library
API compatibility policy and its API version; no separate model-format version is introduced.

Ordinary function parameters and calls remain unchanged. Only explicitly annotated parameters
request model production.

## Alternatives

- Execute the function against proxy objects — can support some query APIs, but is difficult to
  make reliable for arbitrary operators, control flow, and side effects.
- Inspect JVM bytecode — loses source-level intent, is backend-dependent, and complicates reliable
  type-aware translation.
- Expose the compiler's internal AST — rejected because it couples library APIs to compiler
  implementation details and risks exposing mutable internal state.
- Parse source strings — rejected because it bypasses ordinary name resolution and type checking
  and produces fragile diagnostics.

## Implementation and validation

A possible implementation sequence is:

1. Define a public typed expression-model API independent of internal AST classes.
2. Define the initial predicate node set, structural type representation, and rejection rules.
3. Add `@CodeModel` parameter recognition and call-site validation, including separate-compilation
   metadata.
4. Build immutable runtime models after name resolution and type checking.
5. Define capture slots and eager call-site capture evaluation.
6. Test generic lambdas, overload resolution, captures, unsupported constructs, separate
  compilation, and model stability.
7. Build a small consumer that translates predicates into parameterized SQL and verifies binding.

## Open questions

None for the initial scope. SQL null semantics remain the responsibility of each consumer and its
documented translation policy.

## Decision

Accepted 2026-11-01. `@CodeModel` requires an explicit `CodeModel<F>` parameter and produces an
immutable runtime model of an inline lambda after resolution and type checking. The initial subset
includes lambda parameters, typed literals, property access, comparisons, Boolean operators, null
tests, and immutable captures evaluated eagerly by value at the call site. The API exposes
structural source types and stable resolved declaration identities. Consumers interpret the model;
the feature does not perform compile-time expansion or generate Zeron code. APIs needing both an
executable callback and a model declare separate parameters. The model API follows standard-library
API versioning; models are not a persisted format.
