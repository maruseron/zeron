## Abstract

This proposal establishes a direction for building type-safe embedded domain-specific languages
(DSLs) in Zeron using ordinary language constructs and a small set of compiler-supported
capabilities.

The proposal treats DSL support as a composition of independently useful mechanisms: nominal types
and contracts, static extensions, property references, model declarations, declarative metadata,
typed code models, receiver lambdas, and trailing-lambda calls. It does not propose a
general-purpose macro system or library-defined grammars.

## Motivation

Libraries often need concise, expressive APIs for domains such as persistence, validation,
serialization, authorization, and build configuration. Existing fluent APIs can become verbose,
while highly specialized DSL machinery can introduce complex type-level encodings or weakly typed
escape hatches.

Zeron already emphasizes static dispatch, explicit contracts, nominal types, and fluent interfaces.
A coherent embedded-DSL model should build on those strengths rather than introduce a parallel
language inside each library.

The individual mechanisms are specified by their own ZEPs. This proposal records how they are meant
to compose, so that features such as `model` declarations, typed code models, property references, and
receiver lambdas fit together predictably, and identifies which mechanism is responsible for which
concern.

## Goals

- Make embedded DSLs expressible primarily through ordinary Zeron libraries.
- Preserve static type checking for names, receivers, operations, and expression results.
- Keep compiler support generic and independent of any particular DSL domain.
- Reuse static extensions and contracts as the ordinary API composition mechanism.
- Provide controlled ways to attach declaration metadata and inspect selected expressions.
- Keep the model understandable and incrementally adoptable.

## Non-goals

- User-defined grammars or arbitrary syntax extensions.
- General-purpose macro expansion or unrestricted compile-time execution.
- Encoding every legal state of a DSL in a large collection of generic type parameters.
- Requiring every DSL to use receiver lambdas, typed code models, or models.
- Defining a standard ORM, SQL dialect, validation framework, or serialization library.

## Proposal

### Architectural model

A type-safe embedded DSL is built from separable concerns. Each has one primary mechanism, and no
mechanism subsumes another:

| Concern | Primary mechanism |
| --- | --- |
| Operations available on a value | Contracts and static extensions |
| Identity of a property, and a value that denotes it | `PropertyId` ([ZEP-0093](./ZEP-0093.md)) and property references ([ZEP-0090](./ZEP-0090.md)) |
| Mapping a nominal type to an external representation | Model declarations ([ZEP-0079](./ZEP-0079.md)) |
| Optional metadata on declarations | Declarative annotations ([ZEP-0031](./ZEP-0031.md)); consumption by [ZEP-0091](./ZEP-0091.md) |
| Structured interpretation of a selected expression | Typed code models ([ZEP-0080](./ZEP-0080.md)) |
| A typed implicit receiver for a block of operations | Receiver function types and lambdas ([ZEP-0082](./ZEP-0082.md)) |
| Concise call-site syntax for a final function argument | Trailing-lambda calls ([ZEP-0083](./ZEP-0083.md)) |

A DSL may use any subset of these. They should not be fused into a single compiler feature.

### Choosing the mechanism

The mechanisms differ in what they give a library, and a DSL API should use the narrowest one that
carries the information it needs:

- **A function value** is enough when the library only needs to *run* the operation.
- **A property reference** is a runtime *value* that denotes a property: it can be invoked, stored,
  used as a key, and used for typed access to a model field. Use it when the library needs the
  value.
- **A code model** carries the *structure* of an expression. Use it for predicates and other
  expressions the library translates, within the supported expression subset. It also serves
  selectors: a `CodeModel<(T) -> V>` parameter accepts both `user -> user.name` and the literal `User::name`,
  and the library recovers the selected property's identity ([ZEP-0093](./ZEP-0093.md)).
- **A property identity** (`PropertyId`) is shared by all of these. It is what a library uses to
  relate a property named in an expression to a model's mapping.
- **A model declaration** carries a *mapping* between a type's properties and an external
  representation, declared once and passed explicitly to the library.

### Ordinary APIs first

The baseline should remain expressible through ordinary functions, contracts, extension methods, and
lambdas. For example, a query builder may begin with:

```zeron
database
    .from(UserSql)
    .where(user -> user.age >= 18)
    .orderBy(User::name)
    .fetch();
```

Here `UserSql` is a model passed as a value; `where` takes a `CodeModel<(T) -> Boolean>` parameter
so the library receives the structure of the predicate; and `orderBy` takes a
`CodeModel<(T) -> V>` selector, so
`User::name` and `user -> user.name` are interchangeable and the library receives the same
`PropertyId` for both.

A receiver lambda provides a typed scope. The type parameter of the scope must be fixed by the
function's signature, not by statements inside the block, so the model is an argument of the
enclosing call:

```zeron
// illustrative
class Database {
    public query<T: nullable + mut>(
        model: SqlModel<T>,
        body: &QueryScope<T>.() -> Unit
    ): QueryResult<T>;
}

class QueryScope<T: nullable + mut> {
    public where(predicate: CodeModel<(T) -> Boolean>): Unit;
    public orderBy<V: nullable + mut>(selector: CodeModel<(T) -> V>): Unit;
}

database.query(UserSql, () -> {
    where(user -> user.age >= 18);
    orderBy(User::name);
});
```

Trailing-lambda syntax ([ZEP-0083](./ZEP-0083.md)) can shorten the call to
`database.query(UserSql) { ... }`. That syntax is independent of receiver function types and does
not introduce a separate runtime model.

### Static guarantees

A DSL should retain ordinary compiler guarantees wherever possible:

- names resolve to declared properties, methods, or extensions, and receiver lookup is static;
- generic constraints and contract evidence are checked statically;
- expression types are checked before interpretation;
- model mappings are validated against the target type and exposed through stable contracts or
  metadata;
- a code model is built only from an inline lambda after resolution and type checking, and
  unsupported constructs produce diagnostics rather than falling back to executing the lambda;
- a property reference is constructed only by the compiler, so its value type matches the declared
  property type.

A DSL library remains responsible for domain-specific semantics. For example, a query library must
define SQL null behavior and parameter binding; the compiler need not understand SQL. A consumer
that translates a code model must also decide how the properties named in the expression relate to
the fields of a model; both use the same `PropertyId` ([ZEP-0093](./ZEP-0093.md)), so the match is a
lookup and not a convention.

### Type-level complexity

The proposal recommends avoiding APIs that encode every query state in a long generic type such as:

```zeron
Query<Source, Projection, Joins, Grouping, Ordering, Limit, ...>
```

Such encodings may be appropriate for narrow guarantees, but should not be the default
architecture. A typed expression model and a runtime or compile-time query representation can
preserve important safety properties without making every operation alter many type parameters.

This is guidance, not a prohibition on generic state modeling.

### Adoption

The mechanisms are independent, and a DSL can adopt them in any order. A reasonable progression is:

1. Build the DSL using ordinary APIs and extensions.
2. Use property identities and references where the library needs to name a property.
3. Add model declarations where mappings justify them.
4. Add typed code models for APIs that must inspect expressions.
5. Add receiver function types and lambdas where an implicit typed receiver benefits the API.
6. Use trailing-lambda calls for concise call sites.

Broader syntax extensibility should be reconsidered only if real use cases demonstrate that these
mechanisms are insufficient.

## Compatibility and impact

This proposal is architectural guidance and requires no runtime or compiler change of its own. Each
mechanism carries its own compatibility impact in its own ZEP: receiver function shapes are
distinct function shapes ([ZEP-0082](./ZEP-0082.md)); the code-model API follows standard-library
API versioning and models are not persisted ([ZEP-0080](./ZEP-0080.md)); property reference
identity derives from names already present in the library index ([ZEP-0090](./ZEP-0090.md)); and
model declarations add an index entry ([ZEP-0079](./ZEP-0079.md)).

## Alternatives

- General-purpose macros and user-defined syntax — deferred because they greatly expand the
  language and compiler trust boundary.
- A dedicated DSL facility for each domain — rejected as the default because it duplicates compiler
  features and fragments the language.
- Ordinary fluent APIs only — remains the baseline, but may not adequately address expression
  interpretation, property identity, or repetitive declaration metadata.
- Large generic state machines for all DSLs — not prohibited, but discouraged as a universal
  approach because of complexity and inference costs.

## Implementation and validation

This proposal is validated through small independent examples and one composed example, not a
monolithic DSL implementation. The mechanism ZEPs for code models, receiver lambdas, trailing
lambdas, property references, and model declarations are implemented. Validation consists of:

1. A model declaration that exposes a typed mapping through an ordinary contract
   ([ZEP-0079](./ZEP-0079.md) tests).
2. A query predicate represented through a `CodeModel<F>` parameter, translated to a
   parameterized predicate ([ZEP-0080](./ZEP-0080.md)).
3. A receiver lambda that resolves names through a typed receiver, including mutable and read-only
   receiver views ([ZEP-0082](./ZEP-0082.md)).
4. A selector written as `User::name` and as `user -> user.name`, accepted by one `CodeModel<F>`
   parameter and yielding the same `PropertyId` ([ZEP-0093](./ZEP-0093.md)).
5. A consumer library that composes these mechanisms, with no compiler knowledge of its domain,
   along the lines of the `database.query(UserSql) { ... }` example above. It must verify that:
   the type parameter of the receiver is inferred from the model; a predicate's property nodes are
   matched to model fields through `PropertyId`; and an unmapped property is reported by the
   consumer.

Step 5 depends on [ZEP-0079](./ZEP-0079.md) and [ZEP-0093](./ZEP-0093.md), both implemented.
`DslCompositionTest` validates step 5: it composes a model, a generic receiver scope, predicate and
selector code models, and `PropertyId`-based field lookup, and reports an unmapped property without
compiler knowledge of the consumer's domain.

The project should measure compiler complexity, diagnostic quality, IDE support, and API
ergonomics before expanding the feature set. The minimum IDE support is the one required by
[ZEP-0082](./ZEP-0082.md): completion, hover, navigation, and diagnostics for receiver members and
receiver function values.

## Decision

Accepted and implemented 2026-11-08. The architectural mapping and its guidance are the accepted
direction; the resolutions below are the accepted positions:

- **This proposal remains a separate architectural document.** Its content is the mapping from
  concerns to mechanisms, the guidance on choosing among them, and the composed validation example;
  none of this belongs in any single mechanism ZEP.
- **Mandatory static guarantees for receiver-based builders** are those of
  [ZEP-0082](./ZEP-0082.md): the receiver's type and capability are part of the function type,
  lookup is static, and there is no dynamic scope or implicit conversion.
- **Expression models use the compiler-defined API** of [ZEP-0080](./ZEP-0080.md), as revised by [ZEP-0093](./ZEP-0093.md), provided by the
  standard library and versioned with it. No separate standard interface for expression models is
  proposed.
- **Minimum IDE support** is the receiver-member completion, hover, navigation, and diagnostics
  specified in [ZEP-0082](./ZEP-0082.md).
