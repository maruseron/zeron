## Abstract

This proposal establishes a direction for building type-safe embedded domain-specific languages
(DSLs) in Zeron using ordinary language constructs and a small set of compiler-supported
capabilities.

The proposal treats DSL support as a composition of independently useful mechanisms: nominal types
and contracts, static extensions, declarative metadata, typed code models, and contextual blocks.
It does not propose a general-purpose macro system or library-defined grammars.

## Motivation

Libraries often need concise, expressive APIs for domains such as persistence, validation,
serialization, authorization, and build configuration. Existing fluent APIs can become verbose,
while highly specialized DSL machinery can introduce complex type-level encodings or weakly typed
escape hatches.

Zeron already emphasizes static dispatch, explicit contracts, nominal types, and fluent interfaces.
A coherent embedded-DSL model should build on those strengths rather than introduce a parallel
language inside each library.

The project needs a clear architectural direction so that individual features such as `schema`, `@CodeModel`, and contextual blocks compose predictably.

## Goals

- Make embedded DSLs expressible primarily through ordinary Zeron libraries.
- Preserve static type checking for names, receivers, operations, and expression results.
- Keep compiler support generic and independent of any particular DSL domain.
- Reuse static extensions and contracts as the ordinary API composition mechanism.
- Provide controlled ways to attach declaration metadata and inspect selected expressions.
- Keep the initial model understandable and incrementally implementable.

## Non-goals

- User-defined grammars or arbitrary syntax extensions.
- General-purpose macro expansion or unrestricted compile-time execution.
- Encoding every legal state of a DSL in a large collection of generic type parameters.
- Requiring every DSL to use contextual blocks or code models.
- Defining a standard ORM, SQL dialect, validation framework, or serialization library.

## Proposal

### Architectural model

A type-safe embedded DSL should be built from four separable concerns:

| Concern | Primary mechanism |
| --- | --- |
| Operations available on a value | Contracts and static extensions |
| Metadata attached to declarations | Declarative annotations |
| Structured interpretation of selected expressions | Typed code models |
| Concise name resolution within a scoped API | Contextual blocks |

A DSL may use any subset of these mechanisms. They should not be fused into a single compiler feature.

### Ordinary APIs first

The baseline should remain expressible through ordinary functions, contracts, extension methods, and lambdas. For example, a query builder may begin with:

```zeron
database
    .from(UserSchema)
    .where(user -> user.age >= 18)
    .orderBy(user -> user.name)
    .fetch();
```

A contextual-block form may later provide a more concise spelling:

```zeron
database.query {
    from(UserSchema);
    where { age >= 18 };
    orderBy { name };
}
```

The latter should elaborate into ordinary calls and typed lambdas rather than introduce a separate
runtime model.

### Static guarantees

A DSL should retain ordinary compiler guarantees wherever possible:

- names resolve to declared properties, methods, or extensions;
- generic constraints and contract evidence are checked statically;
- expression types are checked before interpretation;
- generated declarations are visible to ordinary type checking;
- unsupported code-model constructs produce diagnostics rather than silently changing execution
  behavior.

A DSL library remains responsible for domain-specific semantics. For example, a query library must
define SQL null behavior and parameter binding; the compiler need not understand SQL.

### Type-level complexity

The proposal recommends avoiding APIs that encode every query state in a long generic type such as:

```zeron
Query<Source, Projection, Joins, Grouping, Ordering, Limit, ...>
```

Such encodings may be appropriate for narrow guarantees, but should not be the default
architecture. A typed expression model and a runtime or compile-time query representation can
preserve important safety properties without making every operation alter many type parameters.

This is guidance, not a prohibition on generic state modeling.

### Layered evolution

The expected progression is:

1. Build DSLs using ordinary APIs and extensions.
1. Add declarative metadata and schema elaboration where repetitive declarations justify them.
1. Add typed code models for APIs that need to inspect expressions.
1. Add contextual blocks as syntax over typed receiver lambdas.
1. Reconsider broader syntax extensibility only if real use cases demonstrate that these mechanisms are insufficient.

## Compatibility and impact

This proposal is primarily architectural guidance. Its individual mechanisms are specified by
related ZEPs and carry their own compatibility impacts.

The key compatibility requirement is that contextual blocks and generated declarations should
elaborate to ordinary typed constructs with stable semantics. Typed code models need a stable
public representation and artifact-versioning policy. This ZEP itself does not require a runtime
change.

## Alternatives

- General-purpose macros and user-defined syntax — deferred because they greatly expand the
  language and compiler trust boundary.
- A dedicated DSL facility for each domain — rejected as the default because it duplicates compiler
  features and fragments the language.
- Ordinary fluent APIs only — remains the baseline, but may not adequately address expression
  interpretation or repetitive declaration metadata.
- Large generic state machines for all DSLs — not prohibited, but discouraged as a universal
  approach because of complexity and inference costs.

## Implementation and validation

This proposal should be validated through small independent examples rather than a monolithic DSL
implementation:

1. A schema declaration that elaborates to a nominal descriptor.
1. A query predicate represented through @CodeModel.
1. A contextual block that resolves names through a typed receiver.
1. A consumer library that composes these mechanisms without compiler knowledge of its domain.

The implementation order should follow the dependencies of the individual ZEPs. The project should
measure compiler complexity, diagnostic quality, IDE support, and API ergonomics before expanding
the feature set.

## Open questions

- Is this architectural proposal sufficiently distinct from the individual mechanism ZEPs, or
  should it remain design guidance in a parent document?
- Which static guarantees should be mandatory for all contextual DSLs?
- Should the language provide standard interfaces for expression models, or only a compiler-defined
  model API?
- What minimum IDE support is required for contextual name resolution?
- What evidence would justify considering user-defined syntax in the future?
