## Abstract

This proposal introduces contextual blocks: a concise syntax for supplying a lambda whose body is
resolved with an explicit receiver context. The feature is intended to support type-safe embedded
DSLs and fluent APIs without introducing library-defined grammars or a new runtime object model.

The initial direction is to treat contextual blocks as syntax that elaborates to ordinary lambdas
with an explicit context parameter. The exact syntax and scope-resolution rules remain open for
discussion.

## Motivation

Fluent APIs can become noisy when every operation requires an explicitly named receiver or when
nested lambdas require repeated parameter names. Kotlin-style type-safe builders demonstrate that
receiver lambdas can provide concise DSL syntax while retaining static typing.

Zeron's static extensions and contracts already allow libraries to add operations to types without
modifying their declarations. Contextual blocks could complement that model by making a typed
receiver available implicitly within a bounded expression.

The feature should preserve ordinary name resolution and static checking rather than create a
separate language for each DSL.

## Goals

- Provide concise syntax for lambdas with an implicit, statically known receiver context.
- Elaborate contextual blocks into ordinary function/lambda calls.
- Reuse existing type checking, contracts, and static extension resolution.
- Support nested contexts with deterministic and diagnosable name resolution.
- Keep the feature independent of any particular DSL domain.

## Non-goals

- User-defined syntax or grammars.
- Dynamic scoping or runtime lookup of contextual names.
- Implicit conversion of arbitrary values into contexts.
- Replacing ordinary lambdas or explicit receiver qualification.
- Defining the semantics of individual DSL operations.

## Proposal

### Illustrative syntax

A library might expose an API conceptually resembling:

```zeron
database.query {
    from(UserSchema);

    where {
        age >= 18;
    }

    orderBy {
        name;
    }
}
```

The query operation supplies a context type for its block. Within the block, members and extensions
available on that context can be referenced without explicitly naming the receiver.

The exact syntax for declaring a contextual-block parameter is open. One possible conceptual
signature is:

```zeron
class Database {
    fn query<R>(block: &QueryScope<R>.() -> Unit): R {
        let scope = QueryScope.new<R>();
        scope.block();
        return scope.fetch();
    }
}
```

Here `&QueryScope\<R>.() -> Unit` denotes a function whose body is resolved against QueryScope;
it is not intended to assert that this exact function-type syntax already exists.

### Elaboration

The preferred initial model is syntactic elaboration to an ordinary lambda with an explicit
parameter:

```zeron
database.query {
    from(UserSchema)
}
```

Conceptually becomes:

```zeron
database.query(scope -> {
    scope.from(UserSchema)
});
```

The contextual block shold not introduce a new runtime value category. Its receiver is an ordinary
value with an ordinary nominal type.

This keeps runtime behavior and dispatch aligned with existing function and extension semantics.

### Name resolution

Within a contextual block, unqualified member references are resolved against the declared context type, using ordinary member and extension lookup rules as far as possible.

The design must define:

- whether local declarations shadow contextual members;
- how imported extensions participate;
- how multiple active contexts are represented;
- how ambiguity is diagnosed;
- whether explicit receiver qualification is always available.

The initial implementation should favor a single context per block. Multiple implicit receivers should be deferred unless a compelling use case establishes clear rules.

### Nested contextual blocks

Nested blocks are important for builders, but they can make unqualified names ambiguous. For
example:

```zeron
database.query {
    from(UserSchema);

    where {
        exists {
            from(OrderSchema);
            total > 100;
        }
    }
}
```

The language must specify whether an inner context replaces, shadows, or coexists with outer
contexts. The initial slice should avoid silently selecting among equally valid candidates.
Ambiguous references should produce compile-time diagnostics, and explicit qualification should
remain an escape hatch.

A future design may introduce a declaration-level marker that controls which contextual receivers
remain visible through nested DSL scopes. This proposal does not commit to a particular marker
syntax or semantics.

### Interaction with extesnsions

Contextual blocks should reuse static extension resolution. A context type makes a receiver
available; extensions imported in the relevant lexical scope add operations to that receiver
according to the existing extension rules.

The feature should not make extension dispatch dynamic or allow contextual blocks to access private
members.

### Interaction with `@CodeModel`

A contextual block may be passed to a parameter annotated with `@CodeModel`. In that case, the
compiler should first resolve and type-check the block against its context, then produce the typed
expression model according to the rules of the corresponding code-model proposal.

The two features remain independent: contextual blocks provide a receiver-oriented syntax, while
`@CodeModel` requests an inspectable representation.

## Compatibility and impact

This is an additive syntax feature affecting parsing, lambda contextual typing, name resolution,
diagnostics, and IDE tooling. If blocks elaborate entirely to existing function values, no new
runtime representation should be required.

The compiler must preserve source locations through elaboration so diagnostics refer to the user's
block rather than only generated lambda syntax. Compiled-library APIs should use ordinary function
types or another stable representation, not compiler-private contextual-block types.

## Alternatives

- Explicit lambda parameters only — simplest and fully supported by ordinary APIs, but can be
  verbose in deeply nested builders.
- Dynamic scopes or implicit runtime environments — rejected because they weaken static reasoning
  and make name resolution depend on runtime behavior.
- User-defined syntax extensions — deferred because they require a much broader parser and compiler
  extension model.
- A distinct runtime receiver-lambda type — not preferred for the initial design because
  elaboration to ordinary lambdas appears sufficient.

## Implementation and validation

A possible implementation sequence is:

1. Define a minimal contextual-block syntax and its parameter declaration form.
1. Elaborate a block into an ordinary lambda with an explicit receiver parameter.
1. Reuse ordinary type checking and extension lookup for the body.
1. Add diagnostics for unresolved and ambiguous contextual names.
1. Preserve source mappings for IDE navigation and diagnostics.
1. Test nested blocks, local shadowing, imported extensions, generic contexts, and separate
  compilation.
1. Test composition with @CodeModel after that feature has a defined model API.

The first slice should support one receiver context per block and avoid advanced receiver stacking
or DSL-specific markers.

## Open questions

- What exact syntax declares a contextual-block parameter?
- Should contextual blocks be a special lambda spelling or a general receiver-function type?
- Which names are implicitly visible: only members, or also selected extensions and top-level
  declarations?
- What are the precise shadowing and ambiguity rules?
- Should nested blocks replace the outer context by default?
- Is a DSL-scope marker needed, and should it be part of the first implementation?
- How should the language server expose contextual members in completion and navigation?
