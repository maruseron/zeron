## Abstract

This proposal introduces receiver function types and receiver lambdas. The current syntactic
candidate for a receiver function type is:

```text
ReceiverType.(ParameterList) -> ReturnType
```

A receiver function is an ordinary statically typed function value whose body is checked with a
declared receiver available for member and extension lookup. This supports type-safe builders for
embedded DSLs, configuration, execution contexts, transactions, validation, resource management,
and document construction.

Optional trailing-lambda call syntax is specified separately in [ZEP-0083](./ZEP-0083.md). It is
not what makes a function a receiver lambda. Receiver lambdas work with ordinary parenthesized
arguments; trailing-lambda syntax is an additional call-site form when the receiver-function
parameter is final.

## Motivation

Some APIs apply a group of operations to a particular value or scope. Requiring every operation to
repeat that value can make configuration and builder APIs noisy. A receiver function gives the
library a statically typed way to make that value available as the lambda's implicit receiver,
while keeping the body an ordinary expression- and statement-checked function.

This pattern is useful beyond DSLs. Libraries may use receiver lambdas to configure an object,
scope operations to a transaction or execution context, validate a value with a validator receiver,
manage a resource scope, or construct a document. The common capability is a typed receiver, not a
special-purpose DSL block.

Zeron separates mutable and read-only views. A receiver function must preserve the receiver's
capability rather than silently widening or upgrading it. A general `Self` type could help fluent
builders return their exact nominal type and view, but is not required for receiver functions and
is outside this proposal.

## Goals

- Add receiver function types using the candidate syntax
  `ReceiverType.(ParameterList) -> ReturnType`.
- Make receiver lambdas usable as ordinary function values: parameters, return values, and
  arguments to functions.
- Contextually type existing lambda literals from an expected receiver function type, including
  when the function value is stored or returned.
- Resolve receiver members and statically imported extensions using the receiver's declared type.
- Preserve the receiver's mutability projection through type checking and function-shape identity.
- Keep receiver function types distinct from ordinary function types with the receiver as an
  explicit first parameter.
- Support type-safe builders across multiple library domains without compiler knowledge of those
  domains.

## Non-goals

- Introducing a separate “contextual block” value category or dynamic scope.
- Adding user-defined syntax, library-defined grammars, or a general macro system.
- Defining the semantics of configuration, transactions, validation, resource management, or other
  builder domains.
- Defining optional trailing-lambda call syntax; see [ZEP-0083](./ZEP-0083.md).
- Defining a general-purpose `Self` type or guaranteeing fluent APIs can return their exact
  receiver type.

## Proposal

### Receiver function types

The proposed type form places the receiver type before the explicit parameter list:

```zeron
Configuration.() -> Unit
Transaction.(Request) -> Result
Validator<T>.(T) -> Validation<T>
```

The receiver is distinct from the explicit parameters. It is supplied when the function value is
invoked as argument zero, and its type provides the context for resolving unqualified receiver
members in the body. The function's explicit parameters and result retain their ordinary static
types. A receiver function is a distinct source-level function type and function shape; it is not
implicitly interchangeable with an ordinary function whose first parameter has the receiver type.

The receiver type includes its reference capability. In Zeron, `&T` is a mutable-capability view
and plain `T` is a read-only view. Therefore these are distinct receiver function types:

```zeron
Configuration.() -> Unit
&Configuration.() -> Unit
```

The second type may call operations requiring a mutable receiver; the first may not. A
receiver-function assignment must follow existing assignability rules and must not upgrade a
read-only receiver or erase a mutable view when that would change the operations available to the
body.

Receiver lambdas reuse existing lambda-literal syntax. An expected receiver function type supplies
the receiver context, and a receiver lambda without such an expected type is not inferred as a
receiver lambda:

```zeron
fn configure(body: Configuration.() -> Unit): Unit = ...;

configure(() -> {
    host = "localhost";
});
```

The same lambda can be supplied as a trailing lambda when the receiver-function parameter is the
call's final function-valued parameter:

```zeron
configure {
    host = "localhost";
};
```

Both spellings have the same contextual typing and function value. No receiver-specific lambda
literal marker or new block syntax is introduced.

### Receiver lookup and scope

Within a receiver lambda, unqualified member references are resolved against the statically known
receiver using ordinary member lookup. Statically imported extensions participate according to the
existing extension rules. The receiver adds no dynamic lookup, visibility bypass, or implicit
conversion.

Lexical parameters and local declarations shadow implicit receiver members. The innermost receiver
is used for unqualified receiver-member lookup; member and statically imported extension lookup
otherwise follow the existing rules, including ambiguity diagnostics.

Inside a receiver lambda, `this` denotes its receiver. An enclosing receiver can be selected with
`EnclosingType.this`, which denotes the nearest enclosing receiver scope whose declared receiver
type matches that type:

```zeron
outer.withConfiguration(() -> {
    // Unqualified members and `this` use the Configuration receiver.
    Outer.this.name;
});
```

If no enclosing receiver of the requested type exists, the qualified reference is an error. When
nested receiver scopes have the same type, the nearest matching scope is selected.

### Type-safe builders

Receiver function types let ordinary library APIs declare the scope and result of a builder:

```zeron
class Database {
    public fn transaction<R>(body: Transaction.() -> R): R;
}

class Application {
    public fn configure(body: Configuration.() -> Unit): Unit;
}
```

The function type, rather than a special block construct, determines which receiver members are
available and what result the caller must produce. The same mechanism can support:

| Use case | Example receiver function type |
| --- | --- |
| Configuration setup | `Configuration.() -> Unit` |
| Execution context | `ExecutionContext.(Request) -> Result` |
| Transaction | `Transaction.() -> Result` |
| Validation | `Validator<T>.(T) -> Validation<T>` |
| Resource scope | `ResourceScope.() -> Result` |
| Document construction | `DocumentBuilder.() -> Document` |

These are library patterns. The compiler checks the receiver and function types but does not define
their domain-specific behavior.

### Receiver-function invocation

A receiver function value is invoked through receiver-call syntax. The receiver appears before the
function value's name, followed by the function's ordinary explicit arguments:

```zeron
fn invoke<R>(transaction: Transaction, body: Transaction.() -> R): R {
    return transaction.body();
}
```

For `receiver.callback(arguments)`, if `callback` resolves to an in-scope receiver-function value
whose receiver type accepts `receiver`, that value is invoked with `receiver` as its receiver.
Otherwise, ordinary member and extension resolution applies. An in-scope receiver-function value
therefore takes precedence over a same-named member or extension when its receiver type is
compatible. Ordinary function calls and ordinary member calls retain their current behavior.

The receiver is passed as the first runtime argument, before the explicit arguments. This is the
lowering convention, not a source-level conversion to an ordinary function type.

### Fluent APIs and `Self`

This proposal does not add `Self`. Receiver function types preserve the declared receiver type and
capability, but do not change the return types of methods called on that receiver. APIs can return
an independently declared result type. A future proposal may define a general `Self` type if a
concrete need justifies its effects on classes, contracts, method typing, and mutability views.
Until then, this proposal makes no guarantee that a fluent operation can return its exact receiver
type or view.

### Interaction with typed code models

A receiver lambda may be passed to a parameter annotated with `@CodeModel`. The compiler should
first contextually type and resolve the lambda, including its receiver references, before
constructing the code model. The model contains the same resolved semantic constructs as for other
supported expressions; it does not introduce a receiver-specific model node. Unsupported constructs
remain subject to the code-model diagnostics. Receiver function types and model representation are
separate concerns; neither feature requires DSL-specific compiler behavior.

## Compatibility and impact

Receiver function types affect function-type parsing, lambda contextual typing, member resolution,
function-shape identity, diagnostics, and IDE support. The receiver and its capability projection
must be represented consistently in source-level types and compiled-library metadata. Function
type serialization and the canonical function-shape key include a receiver marker and receiver
type, so receiver function shapes remain distinct even when their invocation descriptors otherwise
match ordinary function shapes.

At runtime, a receiver function is an ordinary callable function with the receiver supplied as its
first argument, not a captured dynamic scope or a new runtime context. Its generated callable shape
remains distinct from the corresponding ordinary function shape. Compiled-library metadata must
preserve the receiver type and follow the project's artifact compatibility and versioning policy.
The public representation must not expose unstable compiler-private types.

## Alternatives

- Explicit receiver parameters only — fully expressible with ordinary lambdas, but repeats the
  receiver name in every operation and does not provide receiver-oriented member lookup.
- Contextual blocks as a distinct feature — unnecessary if receiver functions provide the typed
  receiver and ordinary lambda semantics.
- Dynamic scopes or implicit runtime environments — rejected because name resolution would depend
  on runtime behavior rather than static types.
- User-defined syntax extensions — deferred because they require a much broader parser and compiler
  extension model.

## Implementation and validation

A possible implementation sequence is:

1. Add a receiver component to function types, type formatting, substitution, assignability, and
   serialized library metadata.
2. Include the receiver marker and type in canonical function-shape identity; lower invocation with
   the receiver as argument zero while keeping receiver and ordinary shapes distinct.
3. Use expected receiver function types to contextually type existing lambda literals, and resolve
   their bodies with ordinary parameter, return, member, extension, and capture rules.
4. Implement receiver-call resolution and `EnclosingType.this` qualification, including lexical
   shadowing, nested receivers, and source-accurate diagnostics.
5. Integrate with trailing-lambda calls and ensure `@CodeModel` processing follows contextual
   typing and resolution.
6. Validate public APIs, separate compilation, and IDE completion, hover, navigation, and
   diagnostics for receiver function values.
7. Test generic receiver types, overload resolution, imported extensions, captures, nested receiver
   scopes, receiver mutability, and distinct function-shape identity across compiled-library
   boundaries.

Receiver lambdas do not depend on `Self`; fluent APIs requiring a self type are outside this
proposal's validation scope.

## Open questions

None for the proposed initial scope. A general `Self` type is explicitly out of scope and may be
proposed separately if future requirements justify it.

## Decision

The design choices in this draft are resolved as described above: receiver lambdas reuse contextual
ordinary lambda syntax; `this` denotes the innermost receiver and `EnclosingType.this` selects the
nearest enclosing receiver of that type; receiver types are distinct function shapes lowered with
the receiver as argument zero; receiver-call lookup prioritizes a compatible in-scope receiver
function; and existing receiver assignability rules apply without implicit conversion to ordinary
function types. `Self` is excluded and is not required for this feature.

The design is accepted for implementation. Release candidacy remains separate from proposal status
and is tracked only in [ZEP.md](./ZEP.md); no release bundle is selected here.
