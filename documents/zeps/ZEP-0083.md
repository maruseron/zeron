## Abstract

This proposal groups three additive syntax improvements for lambdas and function-valued APIs:

1. Allow lambda parameters to declare their types explicitly.
2. Allow unary function types to omit parentheses around their single input type.
3. Allow a final function-valued call argument to be written as a trailing lambda.

The first two improve the ability to write and understand lambda and function types. Trailing-lambda
calls are a separate call-site convenience, included here because they compose with the same APIs
and can be implemented independently. These changes do not depend on implementations from
ZEP-0079 through ZEP-0082; trailing-lambda calls can first support ordinary function parameters
and later compose with receiver function parameters.

## Motivation

Lambda parameter types are usually inferred from an expected function type. When a lambda appears
where that context is unavailable or not propagated, the compiler may be unable to resolve its
parameters. For example, an explicitly typed lambda can make its function shape clear at a return
site or when a lambda is stored without an expected type.

Function types currently parenthesize their input list, including a single input. This makes
curried function types visually repetitive:

```zeron
(Int) -> (Int) -> Int
```

An unparenthesized unary form can express the same type more directly, provided associativity and
the distinction between curried and multi-parameter functions are explicit.

Finally, passing a lambda as the last argument can make builder and callback calls noisy. A trailing
form can improve those calls without changing lambda typing or requiring a receiver function.

## Goals

- Permit explicit types on lambda parameters using the existing `name: Type` parameter notation.
- Retain expected-type inference for lambda parameters that do not need explicit annotations.
- Add `A -> B` as an alternative spelling for the unary function type `(A) -> B`.
- Specify right-associative function-type arrows and preserve clear syntax for zero- and
  multi-parameter function types.
- Add optional trailing-lambda call syntax for a final function-valued parameter.
- Allow an arrowless trailing lambda with a unary expected type to refer to its input as `it`.
- Preserve the existing parenthesized function types, lambda syntax, and ordinary call syntax.
- Keep all three changes additive and independently implementable.

## Non-goals

- Guaranteeing complete type inference for every lambda or expression.
- Changing function-type identity, runtime representation, or lambda capture semantics.
- Replacing expected-type inference with mandatory lambda parameter annotations.
- Adding receiver-function semantics; see [ZEP-0082](./ZEP-0082.md).
- Adding multiple trailing lambda arguments, arbitrary trailing blocks, or user-defined syntax.
- Requiring trailing-lambda syntax for APIs that accept function values.

## Proposal

### Explicit lambda parameter types

Allow a lambda parameter to include an optional type annotation in the existing parameter-list
position:

```zeron
let add: (Int, Int) -> Int =
    (left: Int, right: Int) -> left + right;

fn makeIncrementer(): (Int) -> Int {
    return (value: Int) -> value + 1;
}
```

The same form should work with expression and block bodies:

```zeron
let describe: (User) -> String = (user: User) -> {
    return user.name;
};
```

An explicit parameter type constrains that parameter; it does not override an incompatible
expected function type. If an expected type is available, unannotated parameters continue to be
inferred from it. Without an expected type, every parameter whose type cannot otherwise be
determined must be annotated, and unresolved parameters should produce a direct diagnostic.

Explicit parameter types are an inference aid, not a substitute for expected-type propagation. In
particular, when a function has a declared function-valued result type, the compiler should use
that type to check a returned lambda where possible. This proposal does not claim that explicit
parameter annotations fix unrelated inference gaps in nested lambdas, overload resolution, or
generic constraints.

The initial scope need not add a separate lambda return-type annotation. The lambda result should
continue to be checked or inferred using existing body and expected-type rules; whether a result
annotation is needed for additional context-free cases remains open.

### Unary function-type shorthand

Permit an unparenthesized input type for a unary function:

```zeron
Int -> Int
```

This is exactly equivalent to the existing spelling:

```zeron
(Int) -> Int
```

Arrows should associate to the right. Thus:

```zeron
Int -> Int -> Int
```

means:

```zeron
Int -> (Int -> Int)
```

It does not mean a two-parameter function. The existing multi-parameter form remains distinct:

```zeron
(Int, Int) -> Int
```

Parentheses remain available when a function type is itself an input:

```zeron
(Int -> Int) -> Boolean
```

The zero-parameter spelling `() -> Result` remains unchanged. Existing parenthesized unary
function types remain valid, so this is a source-compatible shorthand rather than a replacement.
The formatter and documentation should choose one canonical spelling for unary function types.

This shorthand applies to ordinary function types. Receiver function types retain their explicit
receiver separator and parameter-list form from ZEP-0082, such as
`Transaction.(Request) -> Result`.

### Trailing-lambda call syntax

Allow a call's final function-valued argument to be supplied after the ordinary argument list:

```zeron
items.map(value -> value + 1);
items.map { value -> value + 1 };
```

The trailing form is equivalent to passing the lambda as the final argument. It may also be used
when the function-valued argument is the only argument:

```zeron
database.transaction { performWork(); };
```

The call's expected function type determines the lambda's parameter and result types just as it
does when the lambda appears inside parentheses. The trailing form is call syntax, not a new block
or function-value category. It can apply to ordinary function parameters and, when supported, to
receiver function parameters; receiver lookup itself remains governed by ZEP-0082.

When a trailing lambda omits its parameter list, a unary expected function type supplies an
implicit parameter named `it`:

```zeron
items.map { it + 1 };
```

The expected arity preserves existing zero-parameter trailing blocks. An arrowless lambda expected
to take more than one parameter must name its parameters explicitly. In a unary trailing lambda,
`it` is the lambda parameter and shadows an outer binding with the same name.

The initial design should support one trailing lambda for the final function-valued parameter.
Calls with multiple function-valued parameters can continue to use ordinary parenthesized
arguments. The feature should not make arbitrary blocks valid after any expression.

The exact grammar must define how trailing syntax interacts with overload resolution, default
arguments, named arguments, and nested calls. Resolution should be equivalent to resolving the
same lambda in the corresponding final argument position of an ordinary call.

### Relationship among the changes

Explicit lambda parameter types and unary function-type shorthand improve the expressiveness and
readability of function types and lambda expressions. Trailing-lambda syntax improves the call
site. They are grouped here as additive function/lambda syntax improvements, but no one part should
be a prerequisite for implementing or using the others.

## Compatibility and impact

Explicit lambda parameter annotations and unary function-type shorthand are additive source syntax.
The shorthand denotes the same function type as the existing parenthesized form and must not alter
function-shape identity or compiled-library metadata.

Trailing-lambda syntax changes call parsing and overload-resolution inputs but should lower to an
ordinary call with a final function argument. It must preserve the same overload selection,
expected-type checking, effects, and diagnostics as the equivalent parenthesized call. No new
runtime representation is intended.

The formatter, language server, diagnostics, and documentation should recognize both existing and
new spellings. Existing source remains valid.

## Alternatives

- Keep all lambda parameter types context-inferred — simple, but leaves no local annotation for
  otherwise unresolved lambda inputs.
- Replace `(A) -> B` with `A -> B` — rejected because existing source should remain valid and the
  parenthesized spelling remains useful for consistency.
- Require parentheses around every function input — unambiguous, but retains visual repetition in
  unary and curried types.
- Keep lambdas inside call parentheses — fully expressive, but makes final callback and builder
  arguments less readable.
- Require every trailing lambda to name its parameters — unambiguous, but less concise for common
  unary callbacks.
- Make trailing syntax specific to receiver lambdas — rejected because it is useful for ordinary
  function parameters too and should not depend on receiver semantics.

## Implementation and validation

The three parts can be implemented separately:

1. Extend lambda parameter parsing and type checking to accept explicit parameter annotations.
2. Extend function-type parsing to accept unary `A -> B`, define right associativity, and retain
   the existing zero- and multi-parameter forms.
3. Add trailing-lambda call parsing and lower it to an ordinary final function argument.
4. Update formatter behavior, IDE completion, and diagnostics for the new forms.
5. Test explicit and inferred lambda parameters, returned lambdas, nested and curried function
   types, overload resolution, effects, default and named arguments, and separate compilation.
6. Test implicit `it` for unary trailing lambdas, preserve zero-parameter blocks, and require
   explicit names for multi-parameter trailing lambdas.
7. Test trailing lambdas with ordinary and receiver function parameters, including nested calls and
   ambiguous overloads.

Validation should verify that old and new spellings produce the same function types and call
behavior, and that type errors are reported at the user's lambda rather than at generated or
desugared syntax.

## Open questions

- When no expected function type exists, which lambda body forms can determine the result type
  without an explicit result annotation?

## Decision

Implement individually typed lambda parameters, right-associative unary function-type arrows, and
one trailing lambda for the final function-valued argument. An arrowless trailing lambda receives
the implicit name `it` when its expected type is unary; zero-parameter trailing blocks retain their
existing behavior. The formatter retains its existing parenthesized unary function-type output.
The trailing lambda is resolved as the ordinary final argument and does not introduce new
receiver-lambda semantics.
