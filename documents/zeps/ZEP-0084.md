# ZEP-0084: 64-Bit Hashes for Zeron Values

## Abstract

This proposal changes Zeron's standard hashing capability from a 32-bit `Int` result to a 64-bit
`Long` result. `Hashable<T>.hash()` becomes the default Zeron hash operation for built-in,
user-defined, nullable, and derived hashable values.

The change preserves the equality/hash law and existing equality semantics while allowing hashing
and hash-based collections to use the full 64-bit result. Java's `Object.hashCode(): Int` remains a
separate interoperability contract and is not changed by this proposal.

## Motivation

Zeron's `Hashable<T>` currently returns `Int`. This limits custom and derived hashes to 32 bits,
even for values such as `Long` whose domain is 64 bits. The current `Long.hash()` delegates to
Java's `Long.hashCode`, which folds a `long` into an `int` by XOR-ing its high and low halves;
distinct values can therefore share the same full hash before a collection even selects a bucket.
For example, two `Long` values whose high and low 32-bit halves are swapped (`0x0000_0001_0000_0002`
and `0x0000_0002_0000_0001`) produce the same hash.

Moving the Zeron hash result to `Long` provides a wider hash domain for user-defined and structural
hashing. It also gives collection implementations the option to use high as well as low hash bits
when selecting buckets, and lets them compare the complete cached hash before falling back to
value equality. The change should be made consistently across the public contract,
compiler-provided evidence, derived implementations, and standard hash-based collections.

## Goals

- Change `Hashable<T>.hash()` to return `Long`.
- Use 64-bit hash results for built-in and compiler-derived `Hashable` evidence.
- Preserve the law that equal values must produce equal hashes.
- Ensure hash-based collections use information from the full 64-bit hash when selecting buckets.
- Keep hash results non-cryptographic and make no new cross-process stability guarantee.
- Keep Java `Object.hashCode(): Int` distinct from Zeron's `Hashable<T>.hash(): Long`.

## Non-goals

- Defining cryptographic, collision-resistant, or adversarial-input hashing.
- Making hash values stable serialized identifiers or a persistence format.
- Changing `Eq<T>`, `==`, `!=`, or the equality/hash relationship.
- Automatically deriving `Hashable` for types that do not currently qualify.
- Bridging Zeron `Hashable` implementations to Java `Object.hashCode`.
- Preserving the old 32-bit `Hashable` method as a parallel default API.
- Changing the size or index type of collections (`Int` to `Long`). Collection sizes and bucket
  indexes remain `Int`-sized. Moving to larger collections would require segmented storage and
  would affect `List`, `Array`, `String`, iterators, and Java interoperability, so it needs its own
  proposal. This ZEP neither requires nor prevents that work (see "Hash-based collections").

## Proposal

### Hashable contract

Change the standard contract method's result type:

```zeron
public contract Hashable<T: nullable + mut> requires Eq<T> {
    hash(): Long;
}
```

The hash contract remains:

> For values `a` and `b` of the same type `T`, if `a == b`, then `a.hash() == b.hash()`.

Unequal values may have the same hash. A hash result must remain consistent while the
equality-relevant state of the value remains unchanged.

Hash results are deterministic within a given compiler and standard-library version, but the
language does not promise that they remain stable across program executions or releases. In
particular, a future release may introduce per-process seeding (for example, as a defense against
hash flooding) without it being a breaking change. Programs and tests must not depend on concrete
hash values, nor on the iteration order of hash-based collections.

User-written `Hashable<T>` implementations must return `Long`. The method name remains `hash`;
this is a return-type migration, not a second hash operation alongside the old `Int` method.

### Distribution quality

Distribution quality is the responsibility of the collection's bucket mixer (see "Hash-based
collections"), not of the hash of each primitive type. Individual `Hashable` implementations are
required to satisfy the equality/hash law and to avoid discarding information needlessly; they are
not required to produce well-distributed bits on their own. This is what justifies simple
primitive hashes such as the sign-extended `Int` hash below.

### Built-in and nullable hashing

Compiler-provided evidence for the existing built-in hashable types must return `Long` and remain
consistent with their `Eq` semantics. In particular:

- `Int` hashes are the `Int` value sign-extended to `Long`. This preserves the previous numeric
  hash value of every `Int` and is deterministic and trivial to specify.
- `Long` hashing must use the full 64-bit value rather than first folding it to 32 bits.
- `Float` hashing must continue to treat all NaN values as equal and distinguish positive from
  negative zero, matching Zeron's equality rules.
- `String` hashing must be a 64-bit algorithm over the same units that `Eq<String>` compares
  (UTF-16 code units or code points, whichever equality uses). It must not simply widen Java's
  `String.hashCode()`, which would inherit the weakness this proposal addresses. It must include a
  final avalanche step.
- Boolean, Unit, and any other existing built-in hashable types must use 64-bit results
  consistent with their equality behavior.
- Nullable lifting continues to use a fixed `0L` hash for null and delegates non-null values to
  their underlying `Hashable<T>` evidence.

The concrete algorithms for built-in hashing are an implementation choice. They must satisfy the
properties above and be tested as 64-bit algorithms. The language does not promise their numeric
results as stable identifiers.

### Derived and structural hashes

Explicit `Hashable` derivation for products, sums, ordinary classes, and newtypes continues to
require the same equality and component evidence as today. The generated implementation must
combine `Long` component hashes without narrowing them to `Int`.

The combining algorithm is an implementation choice, but it must have all of the following
properties:

- **Equality-preserving:** it preserves the equality/hash law.
- **Full-width:** it uses all 64 bits of every component hash.
- **Order-sensitive:** it combines components positionally, so that, for example, `(a, b)` and
  `(b, a)` do not collide systematically.
- **Case-seeded for sums:** the declared case identity is mixed in as the initial seed of the
  accumulator rather than as one more component, so that cases such as `A(0)` and `B(0)` do not
  collide systematically.
- **Finalized:** a final avalanche step is applied once to the accumulated value.

A multiply-rotate accumulation followed by a single `fmix64`/`splitmix64`-style finalizer satisfies
these properties and is the suggested starting point. The combiner must be shared by all relevant
compiler-generated implementations and validated against representative values.

### Hash-based collections

`HashTable`, `HashMap`, `IdentityHashMap` and `HashSet` continue to require `Hashable` keys or
elements. Standard hash table implementations must carry the wider result throughout their hash
path: the hash function, the cached entry hash, and the bucket-index calculation must accept `Long`.

Bucket arrays and their indexes remain `Int`-sized. Before reducing a `Long` hash to a bucket
index, the collection must mix the hash so that all bits, high and low, can influence bucket
selection. Merely applying a power-of-two mask to the low bits of a `Long` would not use the wider
result effectively.

The standard reduction is multiplicative (Fibonacci) hashing:

```zeron
index = (h * 0x9E3779B97F4A7C15) >>> (64 - log2(bucketCount))
```

(with the single-bucket case handled separately). This keeps the cost to one multiplication and one
shift, and it distributes well even when the user's hash has patterns in its low bits, such as small
integers or sign-extended values.

The mixer must be implemented as a single shared function used by all standard hash-based
collections, and it must live in the collection layer rather than in derived or primitive hashes.
Keeping it in one place keeps distribution guarantees in one place and allows a future collection
with a larger index type to reuse the same mixing step.

Hash equality checks within a bucket must compare the complete cached `Long` hash before value
equality. Collisions remain valid and must still be resolved using `Eq<T>`.

### Java interoperability

Java's `Object.hashCode()` remains an `Int`-returning method. Java declarations such as
`Path.hashCode(): Int` continue to describe the Java API and must not be changed to `Long`.
Zeron's `Hashable<T>` contract is not an implicit implementation of Java's `equals` or
`hashCode`, and this proposal does not add such a bridge.

## Compatibility and impact

Changing the public `Hashable<T>.hash()` return type is source- and binary-incompatible for
implementations and compiled libraries that use the current `Int` signature. User implementations,
generic functions that expose the result as `Int`, generated evidence, and the public
`Map.withOperations` hash-function parameter must migrate to `Long`.

**Observable behavior.** Because hash values and the bucket reduction change, the iteration order
of `HashMap`, `HashSet`, and related collections will change. Iteration order is not guaranteed by
the language, but programs that accidentally depend on it will observe the difference.

**Affected public surface.** The implementation must produce an inventory of every public API whose
signature exposes a hash value, starting with `Hashable.hash` and `Map.withOperations`, and
include it in the migration notes. Collection sizes, capacities, and indexes are unchanged.

**Release strategy.** Zeron is pre-1.0, and this change should ship before 1.0, when
incompatible changes are still absorbed within the pre-1.0 policy of ZEP-0012 rather than
requiring a new major series.

- The compiler and standard library change together in a single release, with no compatibility
  window and no dual `Int`/`Long` contract. Maintaining two default hash APIs would fragment
  implementations and collections.
- The API index version and the compiled-library format version must be incremented, so that a
  library compiled against `hash(): Int` is rejected with a clear error rather than failing
  obscurely at link time.
- When the compiler encounters a `Hashable` implementation declaring `hash(): Int`, it should
  report a dedicated diagnostic stating that `Hashable.hash` now returns `Long`, with a suggested
  fix.

No runtime representation change is required for Zeron values. Hash results and intermediate
collection values use the existing `Long` representation. The cached hash per collection entry
grows from 4 to 8 bytes. Java `Object.hashCode()` signatures and behavior remain unchanged.

## Alternatives

- Keep `Int` hashes — simplest and compatible, but retains the 32-bit limit for Zeron hashing.
- Add a separate 64-bit method while retaining `hash(): Int` — permits gradual migration but
  creates two competing hash contracts and requires collections to choose between them.
- Keep `Hashable.hash(): Int` and widen only inside collections — does not let user or derived
  implementations provide additional hash information and obscures the actual contract.
- Mechanically widen existing 32-bit hash outputs to `Long` — changes the signature but preserves
  the old collision behavior, including folding `Long` values to 32 bits before widening.
- Mask-and-fold the bucket index in the style of `java.util.HashMap` (`h ^ (h >>> 32)` followed by
  a mask) — acceptable, but depends more on the quality of the incoming hash than multiplicative
  mixing does.

## Implementation and validation

1. Change `Hashable<T>.hash()` and all standard-library implementations to return `Long`.
2. Update compiler-provided built-in evidence and nullable lifting without changing equality
   behavior. `Int` hashes are sign-extended; `String` uses a 64-bit algorithm with a final
   avalanche step.
3. Update derived product, sum, class, and newtype hashing to use `Long` component hashes and the
   shared, order-sensitive, case-seeded, finalized 64-bit combiner.
4. Update `Map`'s hash function, cached entry hash, constructors, and corresponding `Set`
   behavior, and introduce the single shared bucket mixer.
5. Update generic bounds, tests, documentation, the affected-API inventory, and compiled-library
   and API-index version handling, including the migration diagnostic.
6. Validate built-in and derived equality/hash consistency, including NaN, signed zero, null,
   negative values, and `Long` values that differ only in high bits.
7. Validate combiner properties with representative values rather than frozen numeric results:
   order sensitivity, distinct sum cases with equal payloads, absence of systematic collisions on
   small structured sets, and approximate avalanche behavior.
8. Test map lookup, replacement, removal, and resizing with collisions and with keys that share
   low 32 bits but differ in high 32 bits, and with small sequential and negative `Int` keys to
   confirm the bucket mixer distributes sign-extended hashes well.
9. Test custom `Hashable` implementations and consumers across separate compilation, verify that
   an old compiled library is rejected with a clear error, and verify that Java `hashCode(): Int`
   interop is unchanged.
10. Benchmark insertion, lookup, and memory per entry against the current implementation to
    quantify the cost of 64-bit mixing and 8-byte cached hashes.

## Affected public API

- `Hashable.hash(): Long` (previously `Int`), including built-in, nullable, and derived evidence.
- `Integer.hash(): Long` and `Rational.hash(): Long`.
- `HashMap.withOperations` hash function `(K) -> Long`; `HashTable` stores `Long` cached hashes.
- Generated derived hash helpers return `Long`; `HashSupport` provides the shared combiner and
  finalized built-in operations.
- API index and standard-library API versions are 11 under ZEP-0012. Compiled libraries that expose
  the old `hash(): Int` signature are rejected rather than silently linked.

## Open questions

Resolved: the change ships in the 0.5.0 pre-1.0 line. The API index and standard-library API
versions increment to 11; there is no separate compiled-library format version.
