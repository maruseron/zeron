# ZEP-0085: Explicit Mutable Projections for Inferred Bindings

## Abstract

This proposal makes inferred value bindings default to read-only reference projections and adds a
prefix `mut` expression operator for explicitly retaining an existing mutable projection.

If an initializer has mutable view type `&T`, an unannotated binding infers the read-only view
`T`. Writing `mut expression` preserves `&T` when the expression already has that mutable view.
The operator cannot recover mutability from an expression whose type is already `T`.

The feature distinguishes reference mutation capability from binding reassignment: `let mut`
continues to control whether a name can be rebound, while `&T` continues to control whether the
referenced value can be mutated through that view.

## Motivation

Zeron separates whether a binding can be reassigned from whether a reference permits mutation.
However, an inferred binding initialized by a mutable reference can retain the mutable projection
without making that choice visible at the binding site. Defaulting inferred bindings to a
read-only view makes the safer capability the ordinary choice.

Callers still need a concise way to retain mutability when it is intentional. Repeating the full
type annotation, such as `let config: &Configuration = Configuration.new();`, is explicit but
duplicates a type that the initializer already determines. A prefix projection operator lets the
caller request the capability while preserving inference:

```zeron
let config = Configuration.new();       // Configuration
let mutableConfig = mut Configuration.new(); // &Configuration
```

The operator is an explicit request to preserve a capability already present in the expression. It
does not manufacture mutable access or act as a general cast.

## Goals

- Infer read-only `T` for an unannotated value binding whose initializer has mutable view type
  `&T`.
- Add `mut expression` as an explicit way to preserve an existing `&T` projection.
- Reject `mut expression` when the expression's static type is already read-only `T`.
- Preserve explicit type annotations and ordinary mutable-to-read-only projection.
- Keep binding reassignment (`let mut`) independent from reference mutation capability (`&T`).
- Erase the projection operator at runtime; it changes static typing, not object behavior.

## Non-goals

- Adding ownership, borrowing, uniqueness, or alias-control guarantees.
- Restricting `mut` to factories or promising that it creates a fresh reference.
- Allowing a read-only reference to be upgraded or dynamically tested for mutability.
- Making every inferred expression read-only; the default projection applies at inferred binding
  declarations.
- Changing `let mut` into a request for mutable reference capability.
- Changing the declared types of function parameters or function return types.
- Changing the runtime representation of mutable and read-only views.

## Proposal

The design has two separate rules: inference narrows a mutable initializer by default at an
unannotated binding, while the `mut` expression explicitly preserves a mutable projection. The
operator is not limited to factory calls and does not imply that a reference is fresh or uniquely
owned.

### Default projection for inferred bindings

When an inferred binding initializer has a mutable view type `&T`, the binding's inferred type is
the corresponding read-only view `T`, unless the initializer is explicitly marked with `mut`.
The initializer expression itself retains its `&T` type; only the inferred binding type is
narrowed.

The resulting behavior is:

| Declaration | Inferred or declared binding type |
| --- | --- |
| `let x = create()` where `create(): &T` | `T` |
| `let x = mut create()` where `create(): &T` | `&T` |
| `let x: &T = create()` | `&T` |
| `let x: T = create()` | `T` |
| `let x: T = mut create()` | `T` |

The same default applies to `let` and `let mut` bindings. Explicit annotations continue to state
the binding's exact view subject to the existing safe mutable-to-read-only projection.

The rule applies consistently to all inferred value bindings, including local and top-level
bindings. It does not apply to parameters or function return types, which retain their declared or
otherwise existing inference rules. Public top-level inferred types therefore follow the same
default as local bindings, with the compatibility impact described below.

### Mutable-projection operator

In expression position, the prefix form `mut expression` requires the expression to have mutable
view type `&T` and yields that same `&T` type:

```zeron
let item = mut factory.create();
let other = mut existingReference;
```

If `existingReference` has type `T`, the second form is an error. In particular, once an inferred
binding has narrowed `&T` to `T`, applying `mut` to that binding cannot recover the lost
projection:

```zeron
let config = Configuration.new(); // Configuration
let mutableConfig = mut config;   // error: config is read-only
```

The operator is idempotent on an already mutable view. When it is the initializer of an
unannotated binding, it suppresses that binding's default read-only narrowing; its static result
remains `&T`. In other contexts, it is simply an expression with type `&T`, subject to ordinary
assignability and mutable-to-read-only projection.

The operator does not mutate the referenced value, change the binding's reassignment policy, or
inspect a runtime object for hidden mutability. It records a static capability requirement that the
type checker must verify. It is valid for any expression whose static type is `&T`, not just a
constructor or factory call. Neither a factory's name nor the `mut` operator guarantees that the
reference is fresh or uniquely owned; aliases remain permitted.

The operator may be used on any expression, not only a local variable initializer. A conditional
expression can preserve mutability when its branches have a compatible mutable view:

```zeron
let result = mut (if (condition) then first else second);
```

Every completing branch must provide a compatible `&T`; a read-only branch cannot be upgraded to
make the conditional mutable. Parentheses make clear that `mut` applies to the result of the
conditional.

### Binding reassignment remains independent

`let mut` continues to make the binding reassignable; it does not request a mutable reference
projection. The two choices can be combined independently:

```zeron
let config = mut Configuration.new();            // immutable binding, &Configuration view
let mut configAgain = mut Configuration.new();   // reassignable binding, &Configuration view
let mut readOnlyConfig = Configuration.new();    // reassignable binding, Configuration view
```

This preserves the existing distinction between changing which value a name refers to and
mutating the value through a reference.

## Compatibility and impact

Defaulting inferred bindings to read-only changes the static type of bindings whose initializer
produces `&T`. Code that currently calls a `mut` method, writes through a mutable view, or passes
such a binding to a parameter requiring `&T` must opt in with `mut initializer` or an explicit
`&T` annotation. Code using only read operations continues to work through `T`.

The feature affects expression parsing, type inference, assignability, diagnostics, IDE type
display, and exported inferred types for public top-level values. The read-only default applies to
those exported inferred values as well, so callers may need to add `mut` at the declaration or use
an explicit `&T` annotation to retain the mutable view. The `mut` operator itself requires no
runtime operation or new JVM representation. Compiled-library metadata must preserve the inferred
projection of public values.

The compiler must report a clear error for attempted upgrades, including `mut` applied after a
read-only inferred binding has already discarded the mutable projection.

## Alternatives

- Require explicit `&T` annotations everywhere — maximally explicit, but repeats types that are
  already known from initializers.
- Keep inferring `&T` by default — convenient, but makes mutable capability the implicit choice
  at every inferred binding.
- Treat `let mut` as requesting `&T` — rejected because rebinding and mutation-through-reference
  are independent permissions.
- Allow `mut` to upgrade `T` when the runtime object happens to be mutable — rejected because
  runtime identity cannot soundly restore a static capability that the type no longer carries.

## Implementation and validation

1. Define the inferred-binding rule for mutable view types and apply it consistently to local and
   top-level value declarations.
2. Add the prefix `mut` expression form and type-check it as a preserving projection from `&T` to
   `&T`, rejecting read-only operands. Ensure a direct `mut` initializer is not narrowed again by
   inferred-binding defaulting.
3. Ensure explicit annotations, expected types, conditional expressions, generic calls, and
   ordinary mutable-to-read-only assignments continue to follow existing projection rules.
4. Update inferred-type diagnostics and IDE type display to show `T` or `&T` accurately.
5. Test inferred immutable and reassignable bindings, explicit mutable and read-only annotations,
   factory and method results, existing mutable references, conditional branches, and attempted
   re-projection after narrowing.
6. Test public inferred values and consumers across separate compilation, and verify that no
   runtime representation or binding-reassignment behavior changes.

Validation should specifically prove that `let mut` alone does not retain `&T`, that `mut`
preserves but never creates mutable capability, and that projection behavior is consistent for
branches and generic return expressions.

## Open questions

- Should the unparenthesized form `mut if (condition) then first else second` be accepted as applying
  to the whole conditional, or should conditional operands require parentheses?
- Should the default narrowing rule also apply to pattern bindings, loop bindings, and other
  inferred binding forms?
- How should `mut` interact with expressions whose type is generic or whose branches have distinct
  but compatible mutable views?
- Should diagnostics distinguish an invalid mutable projection from a value that was previously
  narrowed at a binding?
