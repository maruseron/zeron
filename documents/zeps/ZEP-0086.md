## Abstract

This proposal adds polymorphic effect rows so generic callables can accept and propagate functions
with different raised-effect sets, including the empty set. A pure lambda can therefore satisfy a
generic callback API without inventing a nominal effect type.

## Motivation

The `list_monad` sample defines a generic `map` whose callback is written as
`(T) -> R raises E`, with `E: effect`. Its `main` invokes `map` with the pure lambda
`i -> i * 2`. The lambda raises no effect, so inference has an empty effect set but cannot infer a
value for `E`: the implemented `effect` bound denotes one nominal effect type, not a set of effects.

This limits higher-order APIs that should work uniformly with pure and effectful callbacks. The
solution is to let generic signatures quantify over effect sets, with the empty set as the valid
bottom row, rather than changing the meaning of the existing effect-type parameter.

## Goals

- Represent finite effect rows, including the empty row `{}`.
- Allow generic callables and function types to quantify over and propagate effect rows.
- Infer a callback's row from its effects, inferring `{}` for a non-raising lambda.
- Preserve effect-set inclusion checks for function assignability and escaping effects.
- Keep row variables distinct from generic parameters that represent one nominal effect type, while
  letting a single effect be used wherever a row is expected.

## Non-goals

- Changing the meaning of `E: effect` from [ZEP-0055](./ZEP-0055.md).
- Generic effect payloads, which remain separately scoped in [ZEP-0005](./ZEP-0005.md).
- Effect subtyping or the top `Effect` type, which remain separately scoped in
  [ZEP-0013](./ZEP-0013.md).
- Handler cases that inspect the members of an unresolved row variable.
- Resumable effects or continuations.
- Row quantifiers inside function types (higher-rank row polymorphism). Row variables are
  quantified only on declarations, so a parameter cannot itself be row-polymorphic and be used at
  several rows inside the callee. This needs first-class polymorphic function types, which Zeron
  does not have; the declaration-level quantification covers the motivating cases.

## Proposal

An effect row is a compile-time finite set of effect types, optionally containing a row variable.
The empty row `{}` represents a computation that raises no effects. Row variables have a new kind,
spelled `effect...`, distinct from the existing `effect` kind:

- `E: effect` denotes one nominal effect type and contributes that effect to a `raises` set.
- `E: effect...` denotes a single effect row, which may be empty or contain multiple effects. It is
  one generic parameter whose value is a set; the spelling does not introduce several parameters.

A `raises` list expands each name according to its declared kind: a name of kind `effect`
contributes that one effect, and a name of kind `effect...` contributes all members of its row. No
extra marker is needed at the use site. The generic callback example is written as:

```zeron
public fn map<T, R, E: effect...>(
    list: List<T>,
    transform: (T) -> R raises E
): List<R> raises E = ...
```

Here `raises E` expands the row variable, because `E` has kind `effect...`. At a call with `i -> i * 2`, inference binds `E` to
`{}`. If the callback may raise `NotFound`, inference binds `E` to `{NotFound}`, and `map`
propagates that row to its caller.

### Fixed labels and row variables

A `raises` list may mix fixed effect labels with at most one row variable:

```zeron
fn lookup<E: effect...>(
    f: () -> Int raises NotFound, E
): Int raises NotFound, E = ...
```

The same spelling `raises NotFound, E` therefore means two single effects when `E: effect` and one
fixed effect plus a row when `E: effect...`. The meaning is determined by the declared kind of
`E`, which is always in scope at the use site, so no ambiguity arises. Expansion is a property of
the kind and applies wherever a row is expected, including type-argument positions.

At most one row variable may appear in a single `raises` list. A union of two row variables
(`E1, E2`) would not have a unique minimal solution when both are inferred from one observed set,
so a signature that needs two independent rows uses two separate positions (for example two
callback parameters). Concrete effect declarations and existing `E: effect` signatures retain
their current meaning.

### Relationship between `effect` and `effect...`

The kinds are related by one-way subkinding, `effect <: effect...`:

- An `E: effect` may be used where a row is expected, as the singleton row `{E}`. This is already
  how a single effect contributes to a `raises` set, so no new semantics are introduced and
  [ZEP-0055](./ZEP-0055.md) code can call row-polymorphic APIs without migration.
- A row may **not** instantiate an `effect` parameter, because that bound requires exactly one
  nominal effect. This preserves the guarantee that `E: effect` denotes exactly one effect type.
- An explicit type argument for a row parameter is written as a set (`{}`, `{NotFound}`). A single
  effect type is also accepted and is read as a singleton.

### Row composition and inclusion

Rows compose by set union during effect propagation. Function assignability continues to require
that every effect the implementation may raise is permitted by the expected function type. Row
inference must preserve that inclusion rule rather than treating an inferred row as an unchecked
effect declaration.

As a consequence of inclusion, a function of type `() -> T raises {}` is assignable to
`() -> T raises E` for any row `E`, and `() -> T raises NotFound` is assignable to
`() -> T raises NotFound, E`.

### Row inference

Row inference uses **inclusion constraints with a minimal solution**; row equality is not a
primitive constraint.

- Each covariant use of a row variable `E` contributes a **lower bound**, for example
  `effects(callback) ⊆ E`. When fixed labels appear alongside the variable, as in
  `{A, E}`, the observed effects must be covered by `{A} ∪ E`, so the lower bound on `E` is the
  observed set minus the fixed labels. Observing `{A, B}` against `{A, E}` yields `E ⊇ {B}`.
- The solution for `E` is the **union of its lower bounds**. It always exists and is unique. `{}`
  is the solution if and only if `E` has no lower bounds.
- If the context already fixes `E` (an expected type, an annotation, or a row variable of the
  enclosing signature), the row is not solved but **checked**: every lower bound must be included
  in the fixed row, otherwise the compiler reports a diagnostic naming the effect that does not fit.
- Contravariant uses (for example a callback that itself receives a callback) contribute **upper
  bounds**, which are verified against the minimal solution.
- A row variable that appears invariantly is constrained by inclusion in both directions
  (`E₁ ⊆ E₂` and `E₂ ⊆ E₁`); no separate equality mechanism is needed.

The only inference error is therefore a lower bound that does not fit within an upper bound or a
fixed row. The compiler must not silently replace an unresolved row obligation with `{}` merely
because inference failed: an unresolved row must remain polymorphic where permitted, or produce a
diagnostic. When multiple arguments constrain one row variable, the solution is the union of all
their lower bounds, subject to the same upper-bound checks.

### Handlers and unresolved rows

A generic body may propagate an unresolved row in its callable signature, but it may not inspect
the row's members or write a handler case for the row variable.

For a computation whose escaping set is partially known, `{L₁, …, Lₙ, E}`, a handler case for a
fixed label `Lᵢ` removes that label from the fixed part only. The **residual keeps `E`
in full**, because `E` may itself contain `Lᵢ`. For example, handling `NotFound` in a body that
raises `NotFound, E` leaves `E` escaping, not `E` minus `NotFound`. Specific handler cases
therefore cannot discharge unknown row members.

If ZEP-0013's top `Effect` case is available, its unguarded, irrefutable catch-all may cover the
unresolved row; otherwise unknown members remain in the escaping row.

### Interfaces and inherited contracts

A method that implements an interface method or overrides an inherited one may not widen the
contract's effect row. After substituting the contract's type arguments, the implementation's row
must be included in the contract's row:

- If the contract declares a fixed row, the implementation may raise any subset of it, including
  `{}`.
- If the contract wants to leave the row open, it uses generics: either a row parameter on the
  interface (`interface Source<E: effect...>`, instantiated by the implementor, for example
  `Source<{NotFound}>`) or a row parameter on the method. In the second case the implementation
  repeats the same parameter, as with any generic method override, and may not introduce a row
  parameter of its own.
- Inside such an implementation, the effects that can escape are the contract's fixed labels plus
  the members reachable through `E`, for example by calling a callback parameter whose type
  mentions `E`. Any other effect is diagnosed.

This keeps the row of a contract a property of the contract, and reuses the same inclusion rule
as function assignability.

### Runtime model

Row parameters are **erased at compile time** and have no runtime representation. Typed raised
effects already share a single runtime `RaisedEffect` class whose `Object` payload is
disambiguated by type matches. A raised effect carries its concrete effect value, so a row
variable needs no runtime witness: a `raises E` signature compiles to the same raise and
propagation code as any other `raises` list. Handler cases on fixed labels keep using the existing
type matches; the rules above guarantee that no handler case is ever generated for a row variable.
Rows therefore affect only static checking and compiled-library metadata.

## Compatibility and impact

This extends generic bounds, function-type effect signatures, inference, effect-set operations,
and compiled-library metadata. The API index must distinguish a row parameter from an
effect-kinded type parameter and preserve row expressions, including fixed labels and row
variables, through separately compiled consumers, following the existing library-index
guidelines. Existing non-generic effect declarations and `E: effect` code remain unchanged:
because `effect <: effect...`, such code may also call row-polymorphic APIs directly, with each
effect treated as a singleton row.

The spelling `effect...` does not conflict with the grammar: the only other use of `...` is the
packed-array variadic parameter (`options: T...`), and Zeron has no variadic generics. Uses of row
variables in `raises` lists need no new syntax.

Effect subtyping, if adopted through [ZEP-0013](./ZEP-0013.md), changes how effect labels satisfy
row inclusion and handler coverage but does not change the distinction between an effect type and
an effect row.

## Alternatives

- Keep exact effect-kinded parameters only — preserves the current model but cannot represent a
  pure callback's empty effect set.
- Treat `{}` as a special nominal effect type — rejected because the empty set is not an effect
  payload and would conflate row identity with nominal effect identity.
- Default every unresolved effect parameter to `{}` — rejected because it could hide a genuine
  unresolved effect obligation.
- Rows with repeatable labels, scoped labels, or absence constraints (as in Koka or Rémy-style
  rows) — rejected because effects are not resumable (see Non-goals) and rows are plain sets of
  nominal effects, so inclusion constraints with a minimal solution are sufficient.
- Spell the row kind `effects` — rejected because it differs from `effect` by a single letter and
  is easy to misread or mistype. `effect...` is visually distinct and reads as "zero or more
  effects".
- An explicit spread marker at the use site (`raises NotFound, ...E`) — rejected in favor of
  kind-directed expansion. The declared kind of every name is in scope where it is used, so the
  marker adds noise without removing a real ambiguity.

## Implementation status and validation

The compiler implements effect-row parameters, explicit row expressions, minimal inclusion-based
inference, function compatibility, handler residuals, contract checking, and compiled-library
metadata. Rows are erased at runtime and use the existing raised-effect carrier.

Validation covers:

- the pure `map` callback in `sample_programs/list_monad/src/main.zn`;
- effectful callbacks and propagation through nested generic calls;
- callbacks whose effects are a subset of a declared row;
- multiple parameters constraining one row variable, with the solution equal to the union of lower
  bounds;
- row composition with fixed effect labels, including the lower bound computed as observed effects
  minus fixed labels;
- unresolved rows in generic bodies and handler coverage, including that handling a fixed label
  leaves the full row variable as the residual;
- passing an `E: effect` where a row is expected, and rejecting a row where an `effect` parameter
  is expected;
- function-type assignment, including `raises {}` assignable to `raises E` for a row `E`;
- API-index round trips and separately compiled libraries;
- regressions proving `E: effect` still denotes exactly one effect type;
- runtime behavior: a row-polymorphic call raises and propagates the same `RaisedEffect` values as
  the monomorphic equivalent, and fixed-label handlers still match by type;
- recursive row-polymorphic functions resolved through the existing fixed-point generic resolution;
- nested callbacks with a row variable under one, two, and three parameter positions, checking
  that lower bounds are collected for even depth and upper bounds for odd depth, and that a lower
  bound exceeding an upper bound reached only through nesting is diagnosed with the offending
  effect named;
- interface and inheritance cases: an implementation with a subset of the contract's row is
  accepted, one that raises an effect outside it is rejected, a method-level row parameter must
  be repeated rather than introduced, and an interface-level row parameter is instantiated by the
  implementor;
- negative tests: an effect that escapes a fixed row is diagnosed, a lower bound that violates an
  upper bound is diagnosed, and an unresolved row is never silently defaulted to `{}`.

## Decision

Implemented. Generic effect rows, including the empty row, use the following decisions:

- Row variables use the kind `effect...` and are expanded in `raises` lists by their declared
  kind, with no extra marker; at most one row variable per list. `E: effect` keeps its current
  meaning of exactly one nominal effect.
- `effect <: effect...`: a single effect may be used as a singleton row, but not the reverse.
- Row inference uses inclusion constraints and picks the minimal solution, the union of lower
  bounds; `{}` is produced only when there are none.
- Handler cases on a partially known row remove only fixed labels; the row variable stays in the
  escaping set in full.
- Row parameters are erased at compile time and reuse the existing single `RaisedEffect` runtime
  class; no runtime representation is added.

Recursive inference relies on Zeron's existing fixed-point generic resolution. Higher-rank row
quantification is a non-goal. Implementations of a contract may not widen its row, and a contract
that wants an open row uses generics.
