# ZEP-0087: Negative Flow Refinement for Closed Sum Types

## Abstract

Refine stable values on the negative path of a case test over a closed sum type. If a test
establishes that a value is not one case, flow typing should exclude that case from the value's
remaining alternatives.

## Motivation

Flow typing already narrows a value when a sum case test succeeds. However, the opposite path does
not consistently use the closed set of alternatives. For a two-case `Option<T>`, after
`value matches Option.None()` is false, the value must be `Option.Some<T>`. Recognizing that fact
lets code safely access the `Some` payload without an assertion or an unwrap helper:

```zeron
if (new matches Option.None()) {
    remove(key);
    return new;
}

put(key, new.value);
return new;
```

The compiler knows the complete alternatives of an algebraic sum, so this is a sound static
refinement, not an unchecked assumption. The same information is useful for other closed sums and
early-return guard patterns.

## Goals

- Carry the complement of a successful case test onto its false control-flow path.
- Refine a stable sum-typed binding when the remaining alternatives identify a more specific case.
- Preserve existing payload-binding scope: `matches` payload names are available only on the
  successful path.
- Interact correctly with branch joins, early exits, Boolean negation, and binding reassignment.

## Non-goals

- Adding a general source-level union type or changing sum declarations.
- Inferring complements for open class hierarchies, arbitrary predicates, or unsupported tests.
- Adding unchecked casts or runtime checks.
- Replacing `match` when code needs to handle many alternatives or bind payloads across branches.

## Proposal

For a stable expression whose static type has a compiler-known finite set of sum alternatives, a
case test partitions that set. On the true path, retain the tested alternatives as today; on the
false path, remove the alternatives proven to match. For a single-case test, this excludes that
case. If only one alternative remains, the binding may be refined to that case and its declared
payload properties become available.

The refinement applies through a direct branch and to subsequent code when the other branch cannot
complete normally:

```zeron
if (option matches Option.None()) {
    return fallback;
}
use(option.value);
```

Payload bindings introduced by `matches` remain scoped to its successful path. The negative path
does not create payload bindings for excluded cases. Existing branch joins retain only facts valid
on every normally completing path. Any assignment or mutation that could change the tested binding
invalidates the affected case fact.

The initial scope is direct `matches` case tests on closed algebraic sums, including their generated
case types. Parentheses may group the test, and unary `not` swaps its true and false outcomes.
Payload bindings remain available only on the outcome where the underlying case pattern succeeds,
including the false branch of a negated test. This version does not infer complements for `is`
tests or compose `matches` with `and` or `or`. Other closed sealed roots and compound Boolean
conditions require separately specified semantics.

## Compatibility and impact

This is an additive static-analysis improvement: programs previously rejected for accessing a
payload on a provably refined path become valid. It does not change runtime behavior or generated
representations. Flow facts must remain local to the relevant control-flow paths and respect
existing generic argument and mutation rules.

## Alternatives

- Require `match` or an unwrap helper — safe, but verbose when one branch exits and the remaining
  case is evident.
- Require a checked cast — adds a redundant runtime operation after a test that already proves the
  case.
- Add `as!` — would weaken type safety and is unnecessary for a statically exhaustive sum.

## Implementation and validation

Extend flow facts for closed sum values to track possible alternatives on both outcomes of a case
test. Integrate the facts with branch joins, early returns, payload access, and invalidation on
reassignment.

Tests cover positive and negative case refinement, two- and multi-case sums, early-return
continuations, grouped and negated tests, generic sums, payload access and scope, and the boundaries
around `is` tests, nullable values, and compound conditions.
