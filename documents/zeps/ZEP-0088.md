# ZEP-0088: Non-Null Assertion Operator

## Abstract

Add a postfix non-null assertion operator that converts a nullable expression to its non-null
static type, performing a runtime check and failing if the value is null.

## Motivation

Flow checks and `Option`-style APIs are appropriate when absence is expected and should be handled.
At Java interop boundaries, however, an API may return a nullable reference even when the caller
knows that a particular result is present. If there is no convenient facade and the value cannot be
narrowed through existing control flow, the caller currently has no concise way to assert that
expectation before using the value.

For example, a nullable Java return value may need to be used immediately:

```zeron
ThreadLocalRandom.current()!!.nextInt()
```

An explicit runtime-checked assertion is more direct than an external facade and safer than
pretending the nullable value was non-null without a check.

## Goals

- Provide an explicit postfix assertion from `T?` to `T`.
- Fail deterministically at runtime if the asserted value is null.
- Evaluate the operand exactly once.
- Support ordinary member access after the assertion, including `nullableValue!!.field`.

## Non-goals

- Replacing flow checks, safe calls, `Option`, or effects for expected absence.
- Refining the original binding after asserting a separate expression.
- Introducing unchecked type casts or generic runtime reification.
- Making Java APIs non-null by default or changing external nullability declarations.

## Proposal

Add postfix `!!` with the following behavior:

- Its operand must have nullable type `T?`; its result has non-null type `T`.
- At runtime, evaluate the operand once. If it is non-null, return that value unchanged; if it is
  null, fail with a specified non-null assertion error.
- The result may be used directly for member access:

```zeron
let random = ThreadLocalRandom.current()!!;
let number = ThreadLocalRandom.current()!!.nextInt();
let field = nullableRecord!!.field;
```

The operator is an explicit checked assertion, not a proof that null is impossible. It does not
change the declared type or flow facts of the source binding outside the asserted expression.
Whether the runtime failure uses a dedicated Zeron exception or a standard null-pointer exception
must be settled before implementation; the failure must not silently return a default value.

## Compatibility and impact

This adds expression syntax and a runtime failure path but does not change the representation of
nullable values or Java interop. The parser must distinguish postfix `!!` from logical negation and
preserve the existing precedence and chaining rules. Existing code remains unchanged unless it uses
the new token sequence.

## Alternatives

- Add a local non-null check — fully safe and provides a flow fact, but requires branching when an
  immediate assertion is intended.
- Wrap the Java API in a non-null facade — works per API but adds boilerplate and obscures the
  nullability contract at each call site.
- Use an unchecked cast — inappropriate because nullness can be checked directly at runtime.

## Implementation and validation

Add postfix parsing and resolution, lower the assertion to a single operand evaluation and null
check, and define the runtime exception behavior. Validate non-null and null inputs, primitive and
reference representations where applicable, chained member access, Java external calls, operand
evaluation count, and diagnostics for already-non-null or unsupported types.

## Decision

The initial implementation accepts `!!` on already non-null expressions as a no-op. A null
assertion failure throws `NullPointerException` with the stable message
`Non-null assertion failed.` The operator applies to nullable references and nullable boxed
primitives; nullable primitives are unboxed after the check. It does not update flow facts for the
original binding.
