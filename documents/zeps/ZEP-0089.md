# ZEP-0089: Explicit Unchecked Casts

## Abstract

Explore an explicit unchecked cast operator, provisionally spelled `as!`, for narrowly scoped
interop or migration cases where a programmer intentionally assumes a target type that the
compiler cannot prove.

## Motivation

Checked casts reject statically unjustified conversions, while `as?` provides a safe nullable
result. Some foreign APIs or legacy boundaries may carry stronger runtime guarantees than their
declared types express. A deliberately unsafe operator could let callers state that assumption
without weakening ordinary casts.

This convenience has a significant cost: the compiler can no longer guarantee the result's target
type. The operator therefore needs explicit semantics, diagnostics, and documentation rather than
being treated as another spelling of a checked cast.

## Goals

- Keep ordinary `as` and `as?` checked and safe.
- Make any bypass of static cast admissibility explicit at the cast site.
- Specify runtime behavior accurately for JVM raw types and erased generic arguments.
- Ensure diagnostics and documentation communicate that later operations may fail.

## Non-goals

- Reifying generic arguments or making erased runtime type tests sound.
- Replacing checked or safe casts in ordinary application code.
- Adding a general unsafe block or unchecked access to arbitrary memory.
- Using unchecked casts to work around missing flow refinement for closed sums.

## Proposal

Reserve `as! T` as the candidate syntax for an unchecked cast. The exact boundary of the bypass
remains an open design question: it could bypass static source-target compatibility while retaining
any runtime raw-class check the JVM requires, or it could be restricted to cases where the runtime
representation cannot perform that check.

The proposal must not imply that a raw JVM check validates an applied generic target. For example,
a runtime check can distinguish `List` from an unrelated raw class but cannot distinguish
`List<String>` from `List<Int>`. Any accepted design must state when failure occurs—at the cast,
at a later generated check, or at an operation that consumes the value—and must not claim generic
type safety that the runtime cannot enforce.

The operator should be considered only for explicit trust boundaries such as Java interop or
migration. It must not be required for a soundly provable case refinement, and it must not alter
the semantics of existing `as` or `as?`.

## Compatibility and impact

This adds syntax and an intentional escape from static type guarantees. It may affect parser
precedence, diagnostics, IDE highlighting, and generated bytecode. Because erased generic
arguments cannot be verified, accepting a target may defer failures or allow unsound values to
reach generated code; this risk is part of the feature, not an implementation detail.

## Alternatives

- Keep checked `as` and `as?` as the only casts — maximizes static guarantees, but cannot express
  some deliberate foreign-boundary assumptions.
- Add a facade or explicit validation function — preserves checked call sites and keeps the trust
  assumption localized to an adapter.
- Reify generic arguments — could enable stronger runtime checks, but requires a separate runtime
  identity design.

## Implementation and validation

Before implementation, define the operator's admissibility rules, raw-class runtime behavior,
generic erasure behavior, failure timing, diagnostics, and Java interop restrictions. If accepted,
test checked and unchecked target cases separately, including erased generic applications,
separately compiled libraries, and failures at both the cast and later use sites.

## Open questions

- Is `as!` the right syntax and precedence, given the existing checked `as` and safe `as?` forms?
- Which statically impossible conversions may it express?
- Should raw JVM class checks still be emitted, or should the operator bypass only static checks?
- How should unchecked generic claims be represented in source types, metadata, and diagnostics?
- Should the feature be restricted to explicit Java/external interop boundaries?
