## Abstract

This proposal introduces property references: statically resolved values that denote a property
of a nominal type, such as `User::name`. A property reference has identity, carries the property's
source name, can invoke the property's getter, and converts implicitly to an ordinary function
`T -> V`.

The feature is deliberately small. It adds no reflection, no lookup of properties by string, and
no new callable abstraction.

## Motivation

Selectors are everywhere: sorting (`sortBy(User::name)`), typed queries, validation, change
observation, and external mappings. A lambda `{ u -> u.name }` works as a selector but is opaque:
two equivalent lambdas cannot be compared, and tools cannot recover which property was meant.

APIs that need to know *which* property was selected, not only how to read it, currently have two
options: accept a `String` (loses type safety and defers errors) or accept a lambda and give up
identity. Property references provide both a callable and an identity, checked at compile time.

## Goals

- Denote a property of a nominal type with a statically checked, typed value.
- Give each reference a stable identity usable as a key and comparable across compilations.
- Be usable wherever a `T -> V` function is expected.
- Introduce no runtime introspection beyond the references the program itself writes.

## Non-goals

- Reflection, or discovering the properties of a type.
- Resolving properties by name at runtime.
- A general `Callable` contract for nominal invocables with state (see Alternatives).
- References to methods, constructors, or local variables.
- Bound references (`user::name` capturing a receiver) in the first version.

## Proposal

### Illustrative syntax

```zeron
let byName: PropertyRef<User, String> = User::name;
let selector: User -> String = User::name;       // implicit conversion
users.sortBy(User::name);                        // selector position
model.field(User::name);                         // identity position
```

The syntax is illustrative.

### The `PropertyRef` type

```zeron
public class PropertyRef<T: nullable + mut, V: nullable + mut>
        is Eq<PropertyRef<T, V>> {
    private property reader: (T) -> V;
    public property name: String;      // source name, for diagnostics and tooling
    public property identity: String;  // stable declaration identity

    private constructor new(reader: (T) -> V, name: String, identity: String);

    public get(owner: T): V = this.reader(owner);
    public eq(other: PropertyRef<T, V>): Boolean = this.identity == other.identity;
}
```

`PropertyRef` is a class constructed only by the compiler. Users cannot create instances,
which is what lets the compiler guarantee that `V` is the property's declared type. The canonical
constructor is private and the compiler emits references through a synthesized static factory whose
name contains a character that Zeron source cannot spell, so no source program can fabricate a
reference.

### Semantics

- **`get` invokes the getter.** A property in Zeron is a getter and/or setter pair, not a field.
  `get` may therefore be costly or have effects, exactly as `owner.name` does.
- **Capability and visibility.** `T::p` requires a getter for `p` that is accessible at the
  reference site. A property that is only writable cannot be referenced.
- **Identity.** Two references are equal if and only if they denote the same property of the same
  declaring symbol. Identity is based on the declaration's stable identifier, so it is preserved
  across separate compilation.
- **Conversion to function.** `PropertyRef<T, V>` converts implicitly to `T -> V`. The conversion
  reuses the existing lambda adapter and is **one-way and loses identity**: a `T -> V` obtained
  this way cannot be turned back into a reference. APIs that need identity must request
  `PropertyRef` explicitly.
- **Operand is a type.** The left side of `::` names a type, never an expression. A reference may
  name a class property or a property required by a contract; the owner type in that case is the
  contract and the getter call is virtual.
- **Erasure.** Generics are erased at runtime. `V` exists at compile time only; the compiler
  guarantees that the static type of a reference matches the property's declared type, and use-site
  adapters handle generic positions as they do for lambdas. Identity does not include type
  arguments.

### Identity format

`identity` is the declaring type's qualified name, `#`, and the property's source name, for
example `com.maruseron.example.User#name`. It depends only on names that already appear in the
library index for the declaring type and its properties, so no index schema change and no
`API_INDEX_SCHEMA_VERSION` bump are required. A contract property and a class property of the same
name have different identities because their declaring symbols differ.

Equality is value equality (`==`) on `identity`, provided by the declared `Eq<PropertyRef<T, V>>`
conformance. `===` remains object identity of the wrapper and is not the reference identity.

### Mutability

The first version provides read access only. Write access to mutable properties is expressed by
consumers through ordinary `(T, V) -> Unit` functions that the compiler may generate (for example,
the `writer` of a model field in ZEP-0079). Whether a dedicated `MutPropertyRef` is warranted is
left open.

## Compatibility and impact

This is an additive feature affecting parsing (`::`), name resolution, type checking, and
diagnostics. `::` already qualifies static members: followed by `<` it is the existing
function-specialization form, and followed by an identifier it is a property reference, so no new
token is introduced.

Reference identity is derived from the declaring type's qualified name and the property's name.
Both are already present in the library index, so references keep their identity under separate
compilation without a new serialized field. Renaming a property changes the identity of its
references; that is a source-breaking change like any rename.

## Alternatives

- **Plain lambdas** — no new feature, but no identity or name.
- **String property names** — simple, but errors surface at runtime and types are lost.
- **A general `Callable` contract** — would let nominal types with state be invoked like
  functions. Zeron's lambdas are structural (`T -> V`), so a nominal `Callable` would require
  bridging nominal contracts and structural types, which is a much larger design than this
  proposal needs. It is better treated as a separate future proposal; property references only
  need a conversion, not an implementation relationship.
- **Reflection-based lookup** — rejected; contradicts the language's no-reflection stance.

## Implementation and validation

1. Parse `T::p` in expression position, including applied generic and qualified owners, and keep
   `f::<T>` function specialization unchanged.
2. Resolve the owner type and the property declaration, check getter accessibility, and compute the
   applied property type.
3. Build the reader lambda with the existing lambda machinery, emit the `PropertyRef` instance
   through the synthesized factory, and delete the wrapper when the expected type is a function.
4. Test identity equality, the implicit conversion, inaccessible and unknown properties, contract
   owners, generic owners, and diagnostics.

All four steps are implemented. The parser produces `Expr.PropertyReference`;
`PropertyReferenceResolver` checks the owner type and the property declaration and builds the
reader; `BytecodeEmitter` creates the instance through the synthesized `$zeron$propertyRef`
factory, adapting the concrete reader to the erased `(Object) -> Object` shape stored by the
class. The standard library class lives in `zeron.lang.propertyref` and
`PropertyReferenceTest` covers identity, equality, reading, conversion, annotation use, contract
and generic owners, inaccessible and unknown properties, bound-reference diagnostics, and identity
stability across separate compilation.

For [ZEP-0079](./ZEP-0079.md) model mappings (2026-11-06), a reference also carries an optional
`writer: Option<(&T, V) -> Unit>` when the property has an accessible setter, so a model field can
write the property it maps. This is not the first-class assignment target described under future
work: there is no `set` on the reference and no `MutPropertyRef` type.

A reference converts wherever a function value is expected, including generic selector parameters
such as `Option.map`'s `(T) -> R`. Those arguments are resolved after the call's other arguments so
the reference sees the instantiated parameter type, and inference takes the reader's fixed
parameter type only for type parameters that are still unknown, so a bare owner type does not
conflict with a mutable projection inferred from another argument.

## Open questions

None. The decisions are recorded under [Decision](#decision).

## Future work

The first version is deliberately limited to unbound references to readable properties. These
extensions are recorded here and are not part of this proposal:

- **Bound references** (`value::property`) that capture a receiver, giving a zero-argument reader.
  They would need a second kind of identity and would compete with ordinary lambdas for the same
  use, so they are deferred until a consumer needs them.
- **Method and constructor references** (`Type::method`, `Type.new`), which extend the same syntax
  and identity scheme to callables that are not property getters. This needs a design for callable
  identity, receiver shapes, and parameterized references.
- **Writable references** (`MutPropertyRef<T, V>` with `set`, or a `set` on the reference), which
  would replace the generated `(T, V) -> Unit` writers where a consumer needs a first-class
  assignment target and its identity.
- **References to inherited and statically dispatched members** and references used as witness or
  evidence arguments, which would broaden the conversion rules beyond ordinary function values.
- **Selector-based collection APIs.** Sorting and grouping currently accept comparators such as
  `sortBy(compare: (T, T) -> Ordering)`, so a property reference cannot be used directly. Adding a
  selector-based API, for example `sortedBy<T, R: Comparable<R>>(selector: (T) -> R)` under a
  distinct name, is a standard-library API change rather than a language change, and is deferred
  with the extensions above.

## Decision

Accepted for implementation on 2026-11-02. Resolutions of the former open questions:

- **Syntax is `T::p`.** `::` already means “statically qualified member” for effect constructors
  and function specialization, so no new token or keyword is added. After `::`, `<` continues the
  existing specialization form and an identifier starts a property reference. The left operand is
  parsed as a type, so qualified names and applied generic owners such as `Box<Int>::value` work.
- **Contract properties may be referenced and are distinct from class properties.** Identity is the
  declaration, and a conforming class declares its own property; `Named::name` and `User::name`
  therefore have different identities even when `User` conforms to `Named`. The owner of a
  contract reference is the contract type, so the getter call is virtual.
- **Bound references do not exist.** The left side of `::` must name a type. A closure over a
  receiver is already expressible as an ordinary lambda, and a bound value would add state and a
  second kind of identity without serving the first consumer.
- **No `MutPropertyRef` and no `set` in the first version.** References are read-only. Writes are
  expressed by `(T, V) -> Unit` writers, which models generate (ZEP-0079). A writable reference is
  reconsidered only if a consumer cannot be served that way.
- **Generic owners keep their applied arguments.** Diagnostics and tooling format the reference
  type with `TypeFormatter`, so a reference to `Box<Int>::value` keeps the applied owner
  (`PropertyRef<…Box<Int>, Int>`, with the usual qualified type names). Errors about a missing
  property name the declaring type and the property.
- **Identity is `declaringQualifiedName#propertyName`**, compared with `==` through the declared
  `Eq<PropertyRef<T, V>>` conformance. It is derived from indexed names, so the library index and
  its schema version are unchanged.
- **`PropertyRef` is constructed only by the compiler.** Its canonical constructor is private and
  the compiler emits a synthesized static factory whose name cannot be spelled in Zeron source.
