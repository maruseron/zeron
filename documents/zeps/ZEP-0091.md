## Abstract

[ZEP-0031](./ZEP-0031.md) introduced annotation declarations and the ability to annotate symbols. Annotation
metadata is recorded in the library index, but nothing can read it: there is no API, and the
compiler offers no way to ask for it. This proposal defines how annotation metadata may be
consumed, with a bounded, opt-in model rather than a general query facility.

## Motivation

Annotations that nobody can read are inert. Several pending proposals need to attach metadata to
declarations and have libraries act on it:

- [ZEP-0079](./ZEP-0079.md) models want per-field markers (primary key, generated value) that a persistence library
  interprets.
- The serialization work needs aliases, stable field and case identifiers, and unknown-field
  policies, all of which are naturally metadata.

Zeron has no runtime reflection, so the answer cannot be "ask any symbol for its annotations".
Consumption must be explicit, closed, and tied to declarations that opted in.

## Goals

- Let a library obtain annotation values as typed data, not as strings or untyped bags.
- Keep access bounded: only declarations that opted in expose their annotations, only through a
  contract the consumer defined.
- Preserve annotation arguments across separate compilation as structured constant values.
- Avoid introducing general-purpose reflection.

## Non-goals

- Changing annotation declaration or application rules from ZEP-0031.
- A runtime query such as "give me the annotations of this symbol".
- Defining any particular annotation or its domain meaning.
- Annotation processors or arbitrary compile-time code execution.
- Defining new annotation targets; those belong to their own proposals (see
  [ZEP-0097](./ZEP-0097.md) for mapping clauses).

## Proposal

Consumption has two directions, delivered in stages. Direction B comes first because it is small
and the serialization work needs it; Direction A follows. Direction C is rejected.

### Direction B: compile-time access (first stage)

Annotations are readable by compile-time validation and generation steps (for example, derivation
of `Codec`), and never at runtime. ZEP-0031 already allows a compiler-recognized annotation to
affect compile-time validation or lowering "as separately specified", so this stage needs no new
reading mechanism for compiler features. What it requires is that each such feature specify:

- the canonical identity of the annotation it recognizes (for example, the serialization alias
  annotation specified by [ZEP-0092](./ZEP-0092.md));
- the targets on which the annotation is valid;
- how its arguments affect the feature.

Annotation arguments are available to the feature as the typed constants ZEP-0031 already
records. Nothing is exposed to user code.

### Direction A: contract-directed exposure (second stage)

A contract declares which annotations on a conforming declaration become values exposed through
one of its properties. The consumer receives typed values; no global lookup exists.

```zeron
// illustrative
public annotation PrimaryKey on FIELD, PROPERTY, DATA_COMPONENT;
public annotation Column(name: String) on FIELD, PROPERTY, DATA_COMPONENT;

public contract SqlColumn {
    // populated by the compiler from annotations on the conforming declaration
    property primaryKey: Boolean from PrimaryKey;
    property columnName: Option<String> from Column.name;
}
```

The compiler validates that the annotation exists, is applicable to the declaration kind, and
that the property type matches the annotation's argument type. Declarations that do not conform
to the contract expose nothing.

Binding rules:

- **Presence and arguments.** A marker annotation (no parameters) binds to a `Boolean` property:
  `true` if the annotation is present, `false` otherwise. An annotation argument binds to an
  `Option<A>` property, where `A` is the argument's type: `None` if the annotation is absent, and
  `Some(value)` if it is present, where `value` is the declared default when the application
  omits the argument. Other property types are not supported in the first version.
- **One annotation per property.** A property binds to exactly one annotation or one argument of
  one annotation. A consumer that needs to combine several does so in its own code. Allowing
  several bindings later is additive.
- **Argument types.** Exactly the constant forms of ZEP-0031: string, Boolean, built-in numeric,
  `null` for nullable parameters, and one-dimensional arrays of those. The property type must
  match the argument type.
- **No repetition.** ZEP-0031 forbids repeating an annotation on one declaration, so a property
  always receives at most one value. Presentation of repeated annotations only needs revisiting
  if ZEP-0031 allows repetition in the future.

### Binding syntax and diagnostics

A binding is written after the property type as `from Annotation` (marker) or
`from Annotation.argument`, as illustrated above. It is validated when the contract is compiled
and again at each conforming declaration:

- an unknown annotation, an unknown argument, or a property type that does not match the
  argument type is reported at the binding, naming the contract property and the annotation;
- an annotation that cannot be applied to the kind of a conforming declaration is reported at
  that declaration, naming the contract.

### Direction C: general runtime query (rejected)

A function returning the annotations of an arbitrary symbol would be reflection under another
name and contradicts the language's design.

### Representation and retention

- Annotation arguments must be compile-time constants and are stored in the library index as
  structured typed values, not text, so they survive separate compilation. ZEP-0031 already
  specifies this for exported declarations (API-index schema 9).
- **Retention is a property of the binding, not of the annotation declaration**, so ZEP-0031's
  declaration syntax is unchanged. By default an annotation is index-only (compile-time
  consumption). A value is emitted at runtime only when a contract binds it to a property, and
  only for declarations that conform to that contract.

### Declarations that are not the conformer

A contract binding reads the annotations of the declaration that conforms to the contract. Two
related cases are handled differently:

- **The mapped property of a model clause.** A [ZEP-0079](./ZEP-0079.md) model is the conformer;
  the property it maps belongs to the target type. This proposal does **not** read annotations
  of the target's property through the model, because that would couple the target to a
  particular representation, which models exist to avoid. Metadata about a mapping belongs on
  the mapping clause, which [ZEP-0097](./ZEP-0097.md) makes annotatable through a `MAPPING`
  target.
- **Consuming clause annotations** is out of scope for this proposal. A follow-up proposal
  extends Direction A with bindings on a per-field contract, anchored on the `PropertyId` of the
  mapped property within its model ([ZEP-0093](./ZEP-0093.md)), after
  [ZEP-0097](./ZEP-0097.md) is implemented. Until then, models use typed properties of the
  consumer's own contract (for example, a `primaryKey` property reference), as
  [ZEP-0079](./ZEP-0079.md) describes.

## Compatibility and impact

[ZEP-0031](./ZEP-0031.md) is implemented and finalized; this proposal must not change it. The
index already records annotation arguments as structured typed values, so Direction B needs no
index change. Direction A may extend the index to record contract bindings and emitted values,
which falls under the project's artifact compatibility policy.

## Alternatives

- **Do nothing**: consumers express metadata with typed properties in their own contracts (for
  example a per-field `primaryKey: Boolean`). This works today and is more verbose, but it
  duplicates what annotations exist for.
- **Format-specific keywords in each feature**: rejected; produces a growing, fixed vocabulary.
- **Retention on the annotation declaration**: rejected; it would change the declaration syntax
  fixed by ZEP-0031 and is redundant with the binding.
- **Read the target property's annotations through a model**: rejected; couples the target type
  to one representation.

## Implementation and validation

1. Verify that the index preserves annotation arguments as structured values, including `null`
   and arrays, across separate compilation. ZEP-0031 states it does; this step confirms the
   edge cases.
2. Direction B: specify the recognized-annotation contract for compiler features and use it for
   the first consumer ([ZEP-0092](./ZEP-0092.md) aliases).
3. Direction A: define the binding syntax and its validation rules, including type matching and
   `Boolean` / `Option<A>` presence semantics.
4. Emit annotation values for conforming declarations and test across separate compilation.
5. Test that declarations that do not conform expose nothing, and that no API reads annotations
   of an arbitrary symbol.
6. Per-field bindings for model clauses are specified separately and are not part of this
   implementation.

## Open questions

None for this proposal's scope. Consumption of annotations on model mapping clauses is a
follow-up proposal, not an open question of this one.

## Decision

Accepted 2026-11-05. Consume annotations only through two bounded mechanisms, never through a
runtime query: compile-time access by compiler features that recognize specific annotations
(Direction B, delivered first), and contract-directed exposure of annotation values through
`from` bindings on contract properties (Direction A, delivered second). Bind one annotation or
one annotation argument per property, as `Boolean` for markers and `Option<A>` for arguments,
limited to the constant forms of ZEP-0031. Retention is determined by the binding rather than by
the annotation declaration. Do not read the annotations of a model's mapped target property
through the model; consumption of model clause annotations is left to a follow-up proposal
anchored on ZEP-0097 and ZEP-0093. ZEP-0031 is unchanged.

Release candidacy remains separate from proposal status and is tracked only in
[ZEP.md](./ZEP.md); no release bundle is selected here.
