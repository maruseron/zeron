## Abstract

The core serialization slice defines the canonical value and error types, the streaming `Encoder`
and `Decoder` contracts, and the `Encode<T>`, `Decode<T>`, and `Codec<T>` capability contracts.
Derivation currently provides compile-time evidence only: no encode or decode operation is
generated, so nothing can round-trip a value. This proposal specifies the generated streaming
operations and the entry points that apply them.

## Motivation

`Codec<T>` evidence is useful for checking that a type may be serialized, but no program can yet
serialize anything. Format libraries, and consumers such as ZEP-0079 models, need a defined way
to apply a codec to an `Encoder` or `Decoder` without a complete intermediate tree and without
runtime reflection.

## Goals

- Generate streaming encode and decode operations for products, sums, and transparent data classes
  that derive `Encode`, `Decode`, or `Codec`.
- Define entry points to apply evidence: encoding a value and type-directed decoding.
- Keep streaming paths free of a required intermediate `CanonicalValue` tree.
- Preserve source-level type safety under erasure.
- Define how hand-written codecs participate.

## Non-goals

- Concrete format adapters (JSON and others belong to their own proposals).
- Schema languages, migrations, or schema evolution policy for binary formats.
- Introspection of types that did not opt in through derivation.

## Proposal

### Entry points

```zeron
// illustrative
public fn encode<T: nullable + mut + Encode>(
    value: T, encoder: &Encoder): Result<Unit, EncodeError>;

public fn decode<T: nullable + mut + Decode>(
    decoder: &Decoder): Result<T, DecodeError>;     // also as decoder.decode<T>()
```

Generics are erased at runtime, so dispatch is resolved at the use site. The compiler passes the
generated operation for `T` as evidence, the same way use-site adapters work for generic lambdas.
Generic functions constrained by `T: Encode` receive the evidence from their caller.

### Generated mappings

- **Products** encode as records: `beginRecord`, one `writeField` per component, `endRecord`.
  Decoding reads fields with `nextField` and applies the unknown-field policy.
- **Sums** encode as alternatives: `beginAlternative(tag)`, the payload, `endAlternative`.
- **Transparent data classes** encode as the wrapped type.
- **Component evidence** is checked at derivation; a component without evidence is a compile error
  that names the component.

### Identifiers, aliases, and policies

Field and case identifiers default to source names and may be given stable aliases. Policies for
unknown fields and unknown cases are declared per derivation. How aliases are specified depends on
a mechanism to read annotations (ZEP-0091, annotation consumption). Until that exists, aliases
should be expressed in the derivation declaration, or deferred.

### Errors

Errors from nested values propagate with a structured `path`. The path uses the stable identifier
(alias if present) of each component, so path segments match what appears in the external format.

### Static shape (optional)

Some consumers (schema generation, DDL) need the kind of a value before they have one. The
evidence may expose a static `shape: ValueKind` and `nullable: Boolean`, determined at derivation
(`RecordKind` for products, `AlternativeKind` for sums, the wrapped type's kind for transparent
data classes). Hand-written codecs must declare their shape explicitly or opt out.

### Hand-written codecs

A hand-written codec implements the generated operation's shape: a function applying an `Encoder`
or `Decoder`. The proposal must define how it is registered as evidence for a type and how it
composes with derived codecs for components.

### Per-component operations for models

ZEP-0079 models enumerate fields whose value types are erased. A model-level `encode` per field
is just `encode<V>(source.get(owner), encoder)` with evidence for `V` resolved where the model is
declared. This requires only the entry point above; whether a model must guarantee evidence for
every mapped field is decided by the consumer's contract, not by `Model<T>`.

## Compatibility and impact

Generated operations and any evidence metadata must be recorded in the library index and
round-trip across separate compilation, for derived and hand-written codecs alike.

## Alternatives

- **Build a `CanonicalValue` tree first** — simpler, but violates the streaming requirement.
- **Reflection-based serializers** — rejected.
- **Methods added to every derived type** — pollutes the type's public surface; evidence-based entry
  points keep the declaration untouched.

## Implementation and validation

1. Specify and generate encode and decode for products, sums, and data classes.
2. Implement `encode`, `decode`, and `decoder.decode<T>()` dispatch via use-site evidence.
3. Implement identifiers, aliases, and unknown-field and unknown-case policies.
4. Implement structured nested error propagation.
5. Specify hand-written codecs and evidence round-tripping through the library index.
6. Verify that streaming paths need no complete intermediate tree.
7. Test separate compilation of derived and hand-written codecs, and (per format) round-trip
   semantics without assuming byte-for-byte canonicalization.

## Open questions

- Is the entry point a free function, a method on `Encoder` and `Decoder`, or both?
- How is evidence represented and passed through erased generic code?
- Is `shape` part of the evidence, and what happens for hand-written codecs?
- Where do aliases live before annotations can be consumed?
- Should `Encode` and `Decode` evidence be requestable independently per component (an encode-only
  type inside a `Codec` derivation)?
- How is custom mapping of a single component expressed?
