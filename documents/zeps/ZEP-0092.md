## Abstract

[ZEP-0068](./ZEP-0068.md) defines the canonical value and error types, the streaming `Encoder`
and `Decoder` contracts, and the `Encode<T>`, `Decode<T>`, and `Codec<T>` capability contracts.
Derivation currently provides compile-time evidence only: no encode or decode operation is
generated, so nothing can round-trip a value. This proposal specifies the generated streaming
operations and the entry points that apply them, following the derivation model of
[ZEP-0008](./ZEP-0008.md) and the decisions already taken in ZEP-0068 and
[ZEP-0069](./ZEP-0069.md).

## Motivation

`Codec<T>` evidence is useful for checking that a type may be serialized, but no program can yet
serialize anything. Format libraries, and consumers such as ZEP-0079 models, need a defined way
to apply a codec to an `Encoder` or `Decoder` without a complete intermediate tree and without
runtime reflection.

## Goals

- Generate streaming encode and decode operations for native products, native sums, and
  transparent data classes that derive `Encode`, `Decode`, or `Codec`.
- Define entry points to apply evidence: encoding a value and type-directed decoding.
- Keep streaming paths free of a required intermediate `CanonicalValue` tree.
- Preserve source-level type safety under erasure.
- Define how hand-written codecs participate.
- Reuse the existing derivation and witness mechanisms rather than introducing parallel ones.

## Non-goals

- Concrete format adapters (JSON and others belong to their own proposals).
- Schema languages, migrations, or schema evolution policy for binary formats.
- Introspection of types that did not opt in through derivation.
- Serializing ordinary classes by inspecting fields, properties, or methods (ZEP-0068). Ordinary
  classes use a hand-written codec or an explicit mapping to a data aggregate.
- Derivation for newtypes in this version. ZEP-0068 limits derivation to native products, native
  sums, and transparent data classes; a newtype uses a hand-written codec.

## Proposal

### Derivation model

Serialization derivation follows [ZEP-0008](./ZEP-0008.md):

- **Request.** Derivation is requested in the declaration-site `deriving` clause, as in
  `deriving Encode`, `deriving Decode`, or `deriving Codec`. The clause remains a plain list of
  contracts with no parameters. Policies and names are expressed through annotations (see below),
  not through clause arguments.
- **Targets.** Native products, native sums, and transparent data classes (ZEP-0069). Derivation
  is opt-in for each direction (ZEP-0068).
- **Codec.** `deriving Codec` is equivalent to `deriving Encode, Decode`. Listing `Codec` together
  with `Encode` or `Decode` is rejected as redundant, in the spirit of ZEP-0008's rejection of
  redundant `Eq`.
- **Components.** Derivation uses only declared shape. For products these are the declared
  components, and for sums the declared cases. For a data class, only the canonical components, in
  declaration order. Auxiliary fields, methods, and computed properties do not participate, and
  private storage is never inspected (ZEP-0069). This differs deliberately from ZEP-0008's
  derivation for ordinary classes, which covers all stored state.
- **No silent override.** Deriving a capability for a type that also has explicit evidence for it
  is an error.
- **Recursion.** Direct self-recursion is supported. Mutually recursive declaration groups are
  deferred. No runtime object-cycle detection is promised, so encoding a cyclic object graph is
  not supported.
- **Nullable components.** They follow the existing evidence-lifting rules.
- **Asymmetry.** A type may derive one direction and hand-write the other. Unlike ZEP-0008's
  `Hashable`/`Eq` pairing, no law relating the directions can be checked by the compiler, so
  derivation promises no round trip when the other direction is hand-written.
- **Derivable set.** This proposal extends the set of derivable contracts beyond `Eq` and
  `Hashable` with `Encode`, `Decode`, `Codec`, and `Shape`. ZEP-0008 is not changed, and each
  derivable contract carries its own rules.

### Entry points

The free functions are the canonical entry points:

```zeron
// illustrative
public contract Encode<T: nullable + mut, E: effect...> {
    encode(value: T, encoder: &Encoder): Result<Unit, EncodeError> raises E;
}

public contract Decode<T: nullable + mut, E: effect...> {
    decode(decoder: &Decoder): Result<T, DecodeError> raises E;
}

public fn encode<T: nullable + mut + Encode<E>, E: effect...>(
    value: T, encoder: &Encoder): Result<Unit, EncodeError> raises E;

public fn decode<T: nullable + mut + Decode<E>, E: effect...>(
    decoder: &Decoder): Result<T, DecodeError> raises E;
```

`T: Encode<E>` bounds `T` by `Encode<T, E>`. The effect row `E` is row-polymorphic and defaults to
the empty row, so `Encode<T>` and `Decode<T>` keep their current meaning (see Effects).

`decoder.decode<T>()` and `encoder.encode(value)` are provided as extension methods. They are
syntactic sugar over the free functions and have no semantics of their own. No method is added to
derived types, so the declaration of a type is never touched by serialization.

### Evidence

Evidence is the type-class witness mechanism that ZEP-0008 and ZEP-0068 already use: selected
explicitly and statically through contracts and witnesses, with generic bounds requiring the
capability. This proposal introduces no second representation.

- **Derived evidence** is compiler-generated witness evidence. Generic prerequisites are recorded
  as opaque contract/target-type pairs in the library index, and private component names and
  declarations are not exported.
- **Use sites.** Dispatch is resolved at the use site, so erased generic code receives the
  evidence from its caller. A function constrained by `T: Encode` or `T: Decode` receives the
  witness the same way any other bounded function does.
- **Generic derived types.** Witnesses for generic derived types are derived under erasure by the
  existing mechanism, with the component witnesses supplied by the caller.

### Generated mappings

- **Products** encode as records: `beginRecord`, one `writeField` per component, `endRecord`.
  Decoding reads fields with `nextField`.
- **Sums** encode as alternatives: `beginAlternative(tag)`, the payload, `endAlternative`.
- **Transparent data classes** encode as records of their canonical components, in declaration
  order, exactly like products. Auxiliary state is neither written nor read. Decoding reads the
  components and then invokes the canonical constructor, so initializer blocks run and invariants
  are not bypassed (ZEP-0068, ZEP-0069).
- **Missing and null.** A missing required field is a decoding error. Null is accepted only when
  the component's declared type and codec accept null. Nothing is inferred from constructor or
  initializer defaults (ZEP-0068; data classes have no component defaults).
- **Component evidence** is checked at derivation; a component without evidence is a compile error
  that names the component.

### Effects

Encoding and decoding are effect-aware. `Encode<T, E>` and `Decode<T, E>` take a row-polymorphic
effect parameter `E: effect...`, and their operations raise exactly `E`. Format, shape, and
conversion failures remain `EncodeError` and `DecodeError` values, and raised effects remain
effects: neither is converted into the other (ZEP-0068).

Rows of derived evidence:

- **Encode.** The union of the rows of the component `Encode` evidence. Reading canonical
  components adds no effect.
- **Decode for products and sums.** The union of the rows of the component `Decode` evidence.
- **Decode for data classes.** The effects declared by the initializer blocks, which form the
  effects of the canonical constructor (ZEP-0069), joined with the rows of the component
  evidence, and nothing more.
- **Generic types.** Evidence for `Box<T>` requires evidence for `T` with its row, and its own row
  joins that row with the effects of the type itself. Nullable lifting preserves the row. Direct
  self-recursion contributes nothing beyond the type's own effects.
- **Hand-written codecs** declare their row in their witness.
- **`Shape<T>`** is effect-free.

Use sites:

- The entry points and their extension sugar propagate `E`. At a concrete call site the compiler
  infers `E` from the resolved witness, and the caller handles or propagates it, as for
  construction (ZEP-0069).
- Generic code abstracts over the row (`E: effect...`) to accept any witness. A bound that names
  no row means the empty row and accepts only effect-free evidence.
- After a raised effect, as after an error, the position of the `Encoder` or `Decoder` is
  unspecified.
- The row of each witness, including its composition for generic witnesses, is recorded in the
  witness metadata of the library index, as ZEP-0069 does for constructor effects.

### Identifiers, aliases, and policies

Record field names default to source component names, and sum case tags to case names (ZEP-0068).
Renaming without an explicit stable name or alias changes the logical identity.

Names and legacy aliases are expressed with a compiler-recognized annotation,
`zeron.serialization.SerialName(name: String, aliases: Array<String> = [])`, declared
`on DATA_COMPONENT, PRODUCT_COMPONENT, SUM_CASE`. `name` is the logical name written by encoding,
and `aliases` are legacy names also accepted when decoding. It is consumed by derivation through
the compile-time access of [ZEP-0091](./ZEP-0091.md) Direction B. Numeric identifiers for binary
formats belong to the format's own schema and are not derived here (ZEP-0068).

Availability follows the targets. `DATA_COMPONENT` exists today, so data-class names and aliases
depend only on ZEP-0091 Direction B. `PRODUCT_COMPONENT` and `SUM_CASE` are introduced by
[ZEP-0098](./ZEP-0098.md), because ZEP-0031 defines no targets for native products, native sums,
or newtypes. Until each target exists, derivation uses source names for the affected fields and
case tags, and no temporary alias syntax is placed in the `deriving` clause.

Policies follow ZEP-0068 and are not declared in the derivation:

- **Unknown record fields** are ignored by default, with a strict-rejection option owned by the
  adapter (a `Decoder` configuration), not by the type.
- **Unknown sum cases** are errors, which is ZEP-0068's default. A mechanism by which a sum
  declares a representation for them is not specified here and is left to a follow-up once
  ZEP-0098's targets exist, so unknown cases are always errors until then.

### Errors

Errors from nested values propagate with a structured `path`. The path uses the stable identifier
(alias if present) of each component, so path segments match what appears in the external format.
For values reached through a [ZEP-0079](./ZEP-0079.md) model, a segment is the **external name of
the model's mapping clause**, because the model is what defines the identifiers of that
representation.

### Static shape (optional)

Some consumers (schema generation, DDL) need the kind of a value before they have one. Shape is a
separate static capability, `Shape<T>`, rather than part of `Encode`, `Decode`, or `Codec`
evidence:

- It exposes `shape: ValueKind` and `nullable: Boolean`.
- It is derivable explicitly, with `deriving Shape`, consistent with ZEP-0008's rule that derived
  behavior is requested at the declaration. `deriving Codec` does not imply it. Its kinds are
  `RecordKind` for products and data classes, and `AlternativeKind` for sums.
- A hand-written codec may provide `Shape<T>` independently.
- A consumer that needs shape states it as a bound (`T: Shape`), so a missing shape is a compile
  error at the use site and no "opt out" state exists.

### Hand-written codecs

A hand-written codec implements the generated operation's shape: a function applying an `Encoder`
or `Decoder`.

- **Form and registration.** It is an explicit witness for the capability contract (`Encode<T>`,
  `Decode<T>`, or `Codec<T>`), declared the way explicit witnesses are declared today, and not
  through a serialization-specific mechanism.
- **Coherence.** The existing coherence rules for witnesses apply. This proposal adds no new
  orphan or uniqueness rule.
- **Composition.** Derived codecs resolve component evidence the same way whether it is derived
  or hand-written, so a hand-written codec for a component type is used automatically. A
  hand-written codec that needs evidence for its own components receives it through `T: Encode`
  and `T: Decode` bounds, like any generic function.
- **Effects.** A hand-written codec states the row `E` of its operation. It is not inferred from
  the codec's body.

**Custom mapping of a single component.** In the first version, a component with a different
representation is wrapped in a data class or newtype whose hand-written codec delegates to the
component's evidence and writes whatever representation is wanted. A per-component annotation
naming a codec is deferred, because ZEP-0031 does not yet allow type or class literals as
annotation arguments.

### Per-component operations for models

ZEP-0079 models enumerate fields whose value types are erased, so `Model<T>` itself requires no
evidence for mapped fields. Requirements differ per consumer (a read-only export needs only
`Encode`).

- **First version.** A consumer asks for a typed field with a bound in its own API, such as
  `field<V: Encode<E>, E: effect...>(ref)`, and evidence arrives through the entry points above. A model-level
  encode of a field is `encode<V>(source.get(owner), encoder)` with evidence for `V`.
- **Not part of this proposal.** An opt-in consumer contract (for example `EncodableModel<T>
  requires Model<T>`) that has the compiler generate per-field operations in a model's
  singleton is a possible follow-up, once models are in use and consumers show the need.
- **Writing into existing values (`decodeInto`)** depends on `Field.writer`, which ZEP-0079
  defers. It is out of scope until `writer` exists.

## Compatibility and impact

Generated operations and any evidence metadata must be recorded in the library index and
round-trip across separate compilation, for derived and hand-written codecs alike, using the
existing witness metadata. This includes `Shape` evidence.

For serialization, derived behavior is part of the data format. Component names and order (and
case tags), and any `SerialName` value, define the logical identity of the data, so adding,
removing, renaming, or reordering components is a format-breaking change even when source
signatures are unchanged. ZEP-0008 already treats changes to participating components as a public
API compatibility concern; this proposal makes the consequence explicit. Schema evolution policy
itself remains outside this proposal (ZEP-0068).

The core contracts gain a row parameter that defaults to the empty row, so existing uses of
`Encode<T>` and `Decode<T>` are unchanged. If the language cannot default an effect parameter,
the core contracts are migrated explicitly, and derived evidence is regenerated. The effects of
a derived `Decode` follow the data class's initializer blocks, so adding, removing, or changing
those effects changes the effects every caller of `decode` must handle. This is a public API
compatibility concern, like any change to a canonical constructor's effects (ZEP-0069).

## Alternatives

- **Build a `CanonicalValue` tree first** — simpler, but violates the streaming requirement.
- **Reflection-based serializers** — rejected.
- **Methods added to every derived type** — pollutes the type's public surface; evidence-based entry
  points keep the declaration untouched.
- **A serialization-specific evidence representation** (generated singletons, factories, hidden
  parameters) — rejected: it would duplicate the witness mechanism that ZEP-0008 and ZEP-0068
  already rely on.
- **Shape generated automatically for every derived type** — rejected: it makes generated public
  behavior depend on a request the author did not make.
- **Independent `Encode` and `Decode` per component inside a `Codec` derivation** — multiplies the
  cases for little benefit; asymmetry is handled by deriving the capabilities separately.
- **Alias syntax or policies inside the `deriving` clause** — would add parameters to a clause
  that ZEP-0008 keeps as a plain list, and duplicate what annotations express.
- **Deriving for ordinary classes** — excluded by ZEP-0068, since fields, properties, and methods
  do not reveal a complete, stable representation.
- **Converting constructor effects into `DecodeError`** — rejected by ZEP-0068, which keeps format
  errors and raised effects distinct.
- **Effect-free `Decode<T>` only** — would force types with effectful initializer blocks onto
  hand-written codecs, contradicting ZEP-0068 and ZEP-0069.

## Implementation and validation

1. Specify and generate encode and decode for products, sums, and data classes, including
   canonical-constructor decoding for data classes.
2. Implement `encode`, `decode`, and the extension sugar, with evidence resolved through the
   existing witness mechanism, and verify its fit under erasure.
3. Implement effect-aware `Encode<T, E>` and `Decode<T, E>`, the row rules for derived evidence, and
   effect propagation through the entry points.
4. Implement unknown-field handling as an adapter option, and unknown-case errors.
5. Implement structured nested error propagation, including the model external-name rule.
6. Implement `deriving Shape`.
7. Implement `SerialName` names and aliases for data-class components once
   [ZEP-0091](./ZEP-0091.md) Direction B exists, and for product components and sum cases once
   [ZEP-0098](./ZEP-0098.md) is implemented.
8. Implement hand-written codecs through explicit witnesses, and evidence round-tripping through
   the library index.
9. Verify that streaming paths need no complete intermediate tree.
10. Test separate compilation of derived and hand-written codecs, redundant and conflicting
    derivations, direct recursion, nullable components, data-class auxiliary state exclusion,
    initializer-block effects during decoding, effect-row inference through generic and
    nullable-lifted witnesses, and (per format) round-trip semantics without
    assuming byte-for-byte canonicalization.

## Decision

Accepted 2026-11-05. Provide free `encode` and `decode` functions with extension-method sugar
and no methods on derived types. Make `Encode<T, E>` and `Decode<T, E>` effect-aware, with a
row-polymorphic parameter `E: effect...` that defaults to the empty row, so that initializer-block
effects propagate through decoding without becoming format errors. Resolve evidence through the
existing witness mechanism, with rows recorded in witness metadata. Request derivation with
`deriving Encode`, `Decode`, `Codec`, and `Shape` as in ZEP-0008, for native products, native sums,
and transparent data classes. Treat `Codec` as `Encode` plus `Decode`, encode data classes as
records of their canonical components, and decode them through the canonical constructor. Express
names and aliases with `zeron.serialization.SerialName`, available as the annotation targets and
ZEP-0091 Direction B exist, and treat unknown sum cases as errors until a representation mechanism
is specified. Build error paths from stable identifiers, using the external name of the clause
for values reached through a model. Leave per-field model operations to a follow-up.

Release candidacy remains separate from proposal status and is tracked only in
[ZEP.md](./ZEP.md); no release bundle is selected here.
