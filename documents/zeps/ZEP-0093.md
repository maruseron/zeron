## Abstract

This proposal does two related things.

1. It introduces `PropertyId`, a prelude type that identifies a property declaration, and uses it
   to unify the identity that property references ([ZEP-0090](./ZEP-0090.md)), typed code models
   ([ZEP-0080](./ZEP-0080.md)), and model declarations ([ZEP-0079](./ZEP-0079.md)) each use to name
   a property.
2. It replaces the public `zeron.compiler` code-model API with a typed one: sealed node and type
   representations instead of strings, typed literals and capture values instead of `Any?`, source
   locations on every node, and structural equality.

The language-level behavior defined by [ZEP-0080](./ZEP-0080.md) is unchanged: the same
expression subset, the same rejection of unsupported constructs, and the same capture semantics.
Only the representation that libraries consume changes. The API is low-level and has no consumers
yet, so the change is made now, before one appears.

It also lets a selector be written either as `User::name` or as `user -> user.name`, with the same
resulting model.

## Motivation

[ZEP-0090](./ZEP-0090.md) gives each property reference an identity,
`declaringQualifiedName#propertyName`, held in a `String`. [ZEP-0080](./ZEP-0080.md) represents
property accesses as `CodeNode`s that expose an optional `String` identity and make no statement
about its relation to a property reference's identity. This produces three problems:

1. **A consumer cannot connect the two.** A library that translates `user.age >= 18` receives a
   node naming a property. To find that property's mapping in a model, it needs a value that model
   lookup understands. `PropertyRef` is constructible only by the compiler, so the consumer cannot
   build one from a node.
2. **An API author must choose between redundant mechanisms.** A selector such as an ordering key
   can take a `PropertyRef` (accepts `User::name`, not `user -> user.name`) or a `@CodeModel`
   parameter (accepts the lambda but, today, not `User::name`). The caller expresses the same
   intent in both cases.
3. **Identity is an untyped string.**

The current code-model API has further weaknesses that the same consumers hit:

4. **String typing.** `CodeNode.kind()` and `CodeType.kind()` return strings. Consumers match on
   undocumented text, a misspelling is silent, and the compiler cannot check that a consumer
   handles every node.
5. **Optional fields that mean different things per kind.** `identity()`, `literal()`, and
   `slot()` are meaningful only for some nodes and return `null` or a meaningless value for the
   rest.
6. **Untyped values.** `literal()` and `CodeCapture.value()` return `Any?`. Nothing says which
   runtime representation corresponds to which source type, and `null` is ambiguous between "not a
   literal" and "the null literal".
7. **No source locations.** [ZEP-0080](./ZEP-0080.md) says the model should retain locations where
   useful for diagnostics, but the API exposes none, so a consumer rejecting an unsupported node
   cannot say where it is.
8. **No structural equality.** [ZEP-0080](./ZEP-0080.md) expects consumers to reuse a translation
   plan across calls, but there is nothing to key a cache on.

The mechanisms themselves are not redundant: a property reference is a cheap runtime value usable
as a function and a key, while a code model carries the structure of an expression. What overlaps
is the identity of a property and the selector use case.

## Goals

- One type that identifies a property declaration, shared by property references, code models, and
  model mappings.
- Let a selector be written in either spelling and interpreted identically.
- Make the code-model API closed and checkable: sealed nodes, sealed types, typed literals and
  captured values.
- Give every node a source location, and give models structural equality.
- Keep the behavior specified by [ZEP-0080](./ZEP-0080.md) unchanged.
- Introduce no reflection, and no lookup of properties by string.

## Non-goals

- Replacing `PropertyRef` or `CodeModel`; both keep their roles.
- Extending the expression subset; the node set stays that of [ZEP-0080](./ZEP-0080.md).
- Supporting nested property paths as selectors (see Future work).
- Restricting `@CodeModel` parameters to selector-shaped lambdas at compile time.
- Defining query, mapping, or validation semantics.
- Serializing or persisting code models.

## Proposal

### `PropertyId`

```zeron
// illustrative
public class PropertyId is Eq<PropertyId>, Hashable<PropertyId> {
    public property owner: String;     // qualified name of the declaring type
    public property name: String;      // property source name

    private constructor new(owner: String, name: String);

    public text(): String = this.owner + "#" + this.name;
}
```

- `PropertyId` lives in `zeron.lang`, next to `PropertyRef`.
- It is a plain data type, **not generic** in the owner or value type, so it survives erasure and
  needs no existential types. Equality compares `owner` and `name`.
- It identifies the **declaring symbol**, as in [ZEP-0090](./ZEP-0090.md): `Named.name` (a
  contract property) and `User.name` (a class property) are different identities even if `User`
  conforms to `Named`. Type arguments are not part of the identity.
- `text()` returns the same string as `PropertyRef.identity`.
- Its constructor is private, and instances are synthesized by the compiler through a factory whose
  name cannot be spelled in Zeron source, as for `PropertyRef`, so no source program can fabricate
  one. Opening the API to library-constructed identities is left to a future proposal.

`PropertyRef<T, V>` gains a read-only `id: PropertyId`, so `reference.id.text() ==
reference.identity`. Equality of references is unchanged.

### The revised code-model API

The API is declared with the language's own sum types, in `zeron.compiler`. The listing is
illustrative; names and syntax are to be confirmed against the implementation.

```zeron
public type SourceLocation =
    (file: String, startLine: Int, startColumn: Int, endLine: Int, endColumn: Int);

public type CodeType =
      NominalType(name: String, arguments: Array<CodeType>)
    | NullableType(inner: CodeType)
    | FunctionType(parameters: Array<CodeType>, result: CodeType);

public type CodeLiteral =
      NullLiteral
    | BooleanLiteral(value: Boolean)
    | StringLiteral(value: String)
    | IntegerLiteral(decimalText: String)
    | DecimalLiteral(decimalText: String)
    | FloatLiteral(value: Float);

public type ComparisonOperator =
      Equal | NotEqual | LessThan | LessThanOrEqual | GreaterThan | GreaterThanOrEqual;

public type CodeShape =
      ParameterNode(position: Int)
    | CaptureNode(slot: Int)
    | LiteralNode(value: CodeLiteral)
    | PropertyAccessNode(receiver: CodeNode, prop: PropertyId)
    | ComparisonNode(operator: ComparisonOperator, left: CodeNode, right: CodeNode)
    | AndNode(left: CodeNode, right: CodeNode)
    | OrNode(left: CodeNode, right: CodeNode)
    | NotNode(operand: CodeNode)
    | NullTestNode(operand: CodeNode, isNull: Boolean);

public class CodeNode is Eq<CodeNode>, Hashable<CodeNode> {
    public property shape: CodeShape;
    public property sourceType: CodeType;
    public property location: SourceLocation;
    public children(): Array<CodeNode>;
}

public type CodeParameter = (position: Int, name: String, sourceType: CodeType);

public type CaptureValue =
      LiteralCapture(value: CodeLiteral)
    | OpaqueCapture(value: Any);

public type CodeCapture =
    (slot: Int, name: String, sourceType: CodeType, value: CaptureValue);

public class CodeModel<F> is Eq<CodeModel<F>>, Hashable<CodeModel<F>> {
    public property parameters: Array<CodeParameter>;
    public property body: CodeNode;
    public property captures: Array<CodeCapture>;
    public property location: SourceLocation;
}
```

Nodes and models are immutable and constructed only by the compiler.

**Node shapes.** `CodeShape` carries exactly the constructs of the [ZEP-0080](./ZEP-0080.md)
subset. Each variant holds only the fields that are meaningful for it, so there are no optional
fields: a property access has a `PropertyId`, a literal has a `CodeLiteral`, a capture reference
has a slot. The generic `identity()`, `literal()`, `slot()`, `childCount()`, and `child()` are
removed; consumers match on `shape`, and `children()` supports generic traversals.

**The root.** The model exposes `parameters` and `body` rather than a root lambda node. In the
current subset a lambda appears only at the root, so representing it as a node would allow
meaningless trees (a lambda inside the body). If a later extension allows nested lambdas, a lambda
variant is added to `CodeShape` at that time.

**Parameters.** `ParameterNode(position)` refers to a lambda parameter by its stable position, as
in [ZEP-0080](./ZEP-0080.md). Parameter names are retained for display and diagnostics and take no
part in equality.

**Types.** `CodeType` is sealed. A source-level type is a nominal type with arguments, a nullable
type, or a function type. The variants must cover every type the implementation can produce for
a node, including any treatment of mutable views and type parameters (see Open questions).

**Literals.** Each literal is tagged by its kind, and the tag is determined by the node's source
type: `BooleanLiteral` for `Boolean`, `StringLiteral` for `String`, `IntegerLiteral` for integer
types, `DecimalLiteral` for decimals, `FloatLiteral` for floats, and `NullLiteral` for the `null`
literal. Numeric text is the decimal text of the value, consistent with the canonical value type of
the serialization API, so the exact numeric type is given by the node's `sourceType` and no value
is lost. The compiler guarantees that the tag matches the type. `null` is a distinct literal and no
longer conflated with "not a literal".

**Captured values.** A capture's value is a `CaptureValue`. A value of one of the literal kinds,
including `null`, is a `LiteralCapture`, which is the common case for query parameters and is
fully typed. Any other immutable value is an `OpaqueCapture`, which is non-null by construction;
its meaning is given by the capture's `sourceType`, and a consumer that cannot interpret that type
rejects it. Capture semantics (eager evaluation at the call site, by value, one slot per binding)
are unchanged.

**Locations.** Every node, parameter list, and model has a `SourceLocation`: a file, and start and
end line and column. Paths are relative to the compilation's source root, as in diagnostics.
Nodes the compiler synthesizes, such as those of the lambda equivalent to a property-reference
literal, carry the location of the source expression that gave rise to them. A consumer reporting
an unsupported node can therefore point at the user's code.

**Structural equality.** `CodeNode` and `CodeModel` have `==` defined structurally:

- equal if their `shape`s are equal and their `sourceType`s are equal;
- locations are ignored;
- parameter names and capture names are ignored, so `x -> x.age >= 18` equals
  `u -> u.age >= 18`;
- capture *values* are ignored; captures compare by slot and `sourceType`, because the structure
  of an expression is separate from the values it is evaluated with.

Equal models can share a translation plan, and each call binds its own capture values. Both types implement
`Hashable`, consistent with this equality. This is stated on the types, and it is deliberately not full value
equality: two equal models may carry different capture values.

### Evolution of the node set

`CodeShape` is sealed, so adding a variant (for example calls or arithmetic) makes every
exhaustive `match` on it stop compiling until the consumer decides how to handle the new node. This
is intended: it turns a silent gap into a compile error, and the API is versioned with the standard
library. Because [ZEP-0080](./ZEP-0080.md) rejects unsupported constructs at the call site, a
model never contains a node the current compiler does not define, so a consumer only has to handle
new variants when it is recompiled against a newer API.

### Migration from the current API

| Current API | Revised API |
| --- | --- |
| `CodeNode.kind(): String` | `CodeNode.shape: CodeShape` |
| `CodeNode.sourceType()` | `CodeNode.sourceType`, now a sealed `CodeType` |
| `CodeNode.identity(): String?` | Removed; `PropertyAccessNode.property: PropertyId` |
| `CodeNode.literal(): Any?` | `LiteralNode.value: CodeLiteral` |
| `CodeNode.slot()` | `CaptureNode.slot` and `ParameterNode.position` |
| `childCount()`, `child(i)` | `children()`, and the fields of each variant |
| `CodeType.kind()`, `name()`, `argument(i)` | Variants of the sealed `CodeType` |
| `CodeCapture.value(): Any?` | `CodeCapture.value: CaptureValue` |
| `CodeModel.root()` | `CodeModel.parameters` and `CodeModel.body` |
| *(none)* | `location` on nodes and models; structural `==` and hash |

### Property-reference literals as `@CodeModel` arguments

[ZEP-0080](./ZEP-0080.md) accepts only an inline lambda for a `@CodeModel` parameter and rejects
function values and function references, because they have no recoverable source expression. A
**property-reference literal** does have one. This proposal accepts it:

```zeron
users.orderBy(User::name);              // @CodeModel parameter, literal reference
users.orderBy(user -> user.name);       // equivalent
```

For an expected type `CodeModel<(T) -> V>`, the literal `T::p` is resolved and type-checked as the
lambda `(x: T) -> x.p`, and produces the same model, including a `PropertyAccessNode` whose
`PropertyId` is that of `p`. Only a literal is accepted. A value of type `PropertyRef`, or a stored
function, has no source expression at the call site and remains rejected for a `@CodeModel`
parameter. The accessibility rule of [ZEP-0090](./ZEP-0090.md) applies.

### Recovering the selected property

The model exposes enough structure to define a selector helper over the public API:

```zeron
// illustrative
public fn selectedProperty<F>(model: CodeModel<F>): PropertyId?;
```

It returns the `PropertyId` when the model has exactly one parameter and its body is a
`PropertyAccessNode` whose receiver is `ParameterNode(0)`, and `null` otherwise. It requires no
member beyond those listed above.

### Model lookup

[ZEP-0079](./ZEP-0079.md) exposes the `PropertyId` of each mapped field and a lookup by
`PropertyId`. A translator that holds the `PropertyId` of a `PropertyAccessNode` finds the mapping
without constructing a `PropertyRef`.

### Roles after this proposal

| Mechanism | Role |
| --- | --- |
| `PropertyId` | Identity of a property declaration |
| `PropertyRef<T, V>` | A runtime value: getter, map key, typed access to a model field, writer lookup |
| `CodeModel<F>` | The structure of an expression, including the degenerate selector case |
| `Model<T>` | A mapping, indexed by `PropertyId` and, for typed access, by `PropertyRef` |

### Choosing a selector parameter

Zeron does not allow name collisions, so an API declares **one** parameter type for a selector:

- **`@CodeModel selector: CodeModel<(T) -> V>`**, when the library only needs the property's
  identity or the expression's structure and wants to accept both spellings.
- **`selector: PropertyRef<T, V>`**, when the library needs a value: to store it, use it as a key,
  or call `model.field(selector)` for typed access.

## Compatibility and impact

The `PropertyId`, `PropertyRef.id`, selector-literal, and helper additions are source-compatible.

The revised code-model API is a **breaking change** to `zeron.compiler`. It is made deliberately:
the API is low-level and has no consumers. It follows the standard-library API versioning policy
of [ZEP-0080](./ZEP-0080.md), and code models are runtime values that are not persisted, so no
artifact format is affected. The behavior specified by [ZEP-0080](./ZEP-0080.md) (the subset,
rejection, and capture semantics) is unchanged; this proposal replaces only the shape of the
public API, and is the amendment of record for the part of [ZEP-0080](./ZEP-0080.md) that
describes it.

Accepting a property-reference literal for a `@CodeModel` parameter turns a previously rejected
program into a valid one and does not alter any accepted program.

## Alternatives

- **Keep string kinds and document constants.** Retains evolution without breakage, but leaves
  consumers unchecked and misspellings silent.
- **Class hierarchy with a visitor.** Closed variants without sum types, with more ceremony and no
  pattern matching. Zeron favors sealed types.
- **Keep `Any?` for literals and captures.** Cheapest, but leaves consumers guessing which runtime
  type to expect.
- **Locations in a side table.** Keeps nodes smaller but makes every consumer carry the table.
- **Make `CodeNode.identity()` use `PropertyId` text.** Rejected: typed nodes carry a `PropertyId`
  directly.
- **Retire `PropertyRef` and use only `CodeModel`.** Loses the cheap runtime value and the typed
  access used by models.
- **Retire `@CodeModel` selectors and use only `PropertyRef`.** Does not address predicates.
- **An erased contract such as `AnyPropertyRef`.** Needs a decision about variance for contract
  properties, which a plain data type avoids.

## Implementation and validation

1. Add `PropertyId` to `zeron.lang` and give `PropertyRef` an `id` equal to its existing identity.
2. Replace the code-model API with the types above, and have the model builder produce them,
   including locations and the tag-to-type correspondence for literals.
3. Define structural equality and hashing on `CodeNode` and `CodeModel`.
4. Accept a property-reference literal for a `@CodeModel` parameter and build the model of the
   equivalent lambda.
5. Add the selected-property helper.
6. Test: every node variant is produced for a corresponding construct; unsupported constructs are
   still rejected with a diagnostic at the call site; `x -> x.age >= 18` and `u -> u.age >= 18`
   are equal and hash equally; models differing only in locations or capture values are equal,
   and models differing in capture slots or types are not; each literal tag matches its source
   type and `null` is `NullLiteral`; captures of literal kinds are `LiteralCapture` and others
   `OpaqueCapture`; locations of ordinary and synthesized nodes point to the user's source;
   `User::name` and `user -> user.name` yield equal `PropertyId`s and equal models;
   `Named::name` and `User::name` are distinct; a `PropertyRef` value is rejected for a
   `@CodeModel` parameter; generic owners keep the same identity across type arguments.
7. Verify with [ZEP-0079](./ZEP-0079.md) that a model lookup by `PropertyId` finds the mapping for
   a property named in a code model, including across separate compilation.

## Open questions

- Which `CodeType` variants does the implementation need? In particular, how do mutable views
  (`&T`), type parameters of an enclosing generic function, and receiver function types appear?
- Should `x == null` be canonicalized to `NullTestNode`, or remain a `ComparisonNode` with
  `NullLiteral`? The choice affects structural equality, and the model builder should pick one.
- Should locations record the file path relative to the source root, or an opaque source id, to
  avoid leaking build paths into runtime values?
- Should `CodeShape` gain a lambda variant now, in anticipation of nested lambdas?
- Should an `OpaqueCapture` of a type with serialization evidence offer a canonical value?

## Future work

- **Public construction of `PropertyId`**, which would allow hand-written models and tests to name
  properties, at the cost of a second way to obtain an identity.
- **Property paths.** A selector such as `user -> user.address.city` already yields a chain of
  `PropertyAccessNode`s; a helper could return it as an ordered sequence of `PropertyId`s.
- **Further nodes** such as calls and arithmetic, with their own identity types.
- **Method and constructor identities**, if [ZEP-0090](./ZEP-0090.md) extends references to them.

## Decision

Accepted for implementation and implemented on 2026-11-03. Resolutions of the open questions:

- **`CodeType` has three variants.** `NominalType`, `NullableType`, and `FunctionType`. A mutable
  view `&T` is `NominalType("&", [T])`, `Array<T>` is `NominalType("Array", [T])`, and a type
  parameter of an enclosing generic function appears as a `NominalType` carrying the parameter's
  name. A receiver function appears as a `FunctionType` over its invocation parameters.
- **`x == null` stays a comparison.** It is a `ComparisonNode` whose right operand is
  `LiteralNode(NullLiteral)`; only `x is null` produces `NullTestNode`. The grammar has no
  `is not null` form, so `isNull` is currently always `true`, and negation is a `NotNode`.
- **Locations record the source path.** `SourceLocation.file` is the unit's source path as given to
  the compiler, relative to the source root as in diagnostics; lines and columns are one-based, and
  a missing column is recorded as `0`. Synthesized nodes, such as those of the lambda equivalent to
  a property-reference literal, carry the location of the source expression that produced them.
- **`CodeShape` has no lambda variant.** The model exposes `parameters` and `body`, and a lambda
  occurs only at the root, so a variant would admit meaningless trees.
- **`OpaqueCapture` offers no canonical value.** It holds the captured value and its meaning comes
  from the capture's `sourceType`. Literal extraction is defined only for the literal kinds, so
  there is no second representation to keep synchronized.
- **Literal kinds are `String`, `Boolean`, the integer types, `Float`, and `null`, including
  nullable variants.** `DecimalLiteral` exists for completeness but is not reachable from the
  subset today, because a decimal literal requires a user-declared literal type. `Char` and
  reference values are `OpaqueCapture`.
- **The compiler constructs `PropertyId` through a factory.** `PropertyId` and its factory are
  compiler-only, as specified. `PropertyRef` gains `id`, whose `text()` equals `identity`, and
  reference equality is unchanged.
- **Structural equality is defined by hand.** `CodeType` is compared and hashed by the standard
  library's own `typeEq`/`typeHash` helpers rather than through synthesized evidence, because
  `Array<CodeType>` has no `Eq` or `Hashable` witness. `CodeNode` and `CodeModel` expose `eq` and
  `hash` over `shape`, `sourceType`, parameter positions and types, and capture slots and types,
  ignoring locations, names, and capture values.
