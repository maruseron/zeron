## Abstract

This proposal turns `List`, `Map`, and `Set` from classes into contracts and renames the existing
classes `ArrayList`, `HashMap`, and `HashSet`, so alternative implementations can be written against
the contracts and passed to any API that takes them. Each contract is a small bundle of capability
contracts (`Iterable`, `Sized`, `Reversible`).

It also moves the terminal operations of `Stream` onto `Iterable` as effect-row-polymorphic default
methods, splits mutation into small capability contracts instead of a mutable bundle, and states how
effect rows apply to lazy sequences. `Stream` stays a final class.

The motivation, the options considered, and the experiments are in
[the design document](../design_documents/design-document-20_collection-contracts-v4.md).

## Motivation

`List`, `Map`, `Set`, and `Stream` are final classes with a single implementation each. A persistent
list, a linked list, a sorted map, or an identity-keyed map cannot be passed to an API that takes a
`List` or a `Map`, and a read-only API must name an array-backed or hash-backed class. The standard
library already splits behavior into capability contracts (`Sink`, `RandomAccess`, `Foldable`,
`Collector`), but there is no short name for an ordered or an associative collection, and several
capabilities are bound to the class (`Reversible<List<_>>`, `Foldable<List<_>>`,
`Collector<List<_>>`).

Two language constraints shape the design. Capability contracts over type constructors
(`Foldable<F<_>>`) cannot bound their constructor parameter, and `requires` cannot relate them to
ordinary contracts such as `Iterable<T>`, so an instance cannot be written once for a contract. And
effect rows ([ZEP-0086](./ZEP-0086.md)) allow precise effect types for higher-order collection
operations, which current signatures do not use.

## Goals and non-goals

Goals:

- Let `List`, `Map`, and `Set` have more than one implementation behind one name, with a small
  mandatory surface.
- Express mutation as capabilities named for operations, not as a contract named for a state.
- Make strict higher-order and terminal operations effect-polymorphic.
- Keep `Stream` a final class, with `Iterable` as the contract that lazy sequences implement.

Non-goals:

- Shipping a complete family of alternative implementations. The standard library includes baseline
  `LinkedList`, `ArrayDeque`, `ConsList`, and `IdentityHashMap` implementations as validation targets;
  richer structures such as `TreeMap` belong to their own proposals. `MapBackedSet` is the exception:
  it generalizes the wrapper the current `Set` class already is.
- `==` on contract-typed collections, which is a language proposal of its own.
- Effect-tracking lazy streams or effectful iteration sources, beyond the policy stated below.
- Changing `Functor`, `Monad`, or other type-class contracts.
- A language feature for an optional mutable face of a contract.

## Proposal

### Naming

| Current | After this proposal |
| --- | --- |
| `List<T>` (class) | `List<T>` (contract); the class is `ArrayList<T>` |
| `Map<K, V>` (class) | `Map<K, V>` (contract); the class is `HashMap<K, V>` |
| `Set<T>` (class) | `Set<T>` (contract); the class is `HashSet<T>` |

The plain names denote the contracts. Constructors (`of`, `empty`, `fromArray`, `withMap`,
`withOperations`) stay on the classes: classes cannot declare static members and named constructors
cannot declare type parameters, and neither is needed, since generic code builds collections through
`Collector`'s generic `empty<A>`. A contract may declare `static` members, so `List.of` is possible,
but API design must be careful with it.

### Contracts

```zeron
// illustrative
/// A finite, ordered sequence. Iteration starts at the sequence's initial end.
public contract List<T: mut> requires Iterable<T> + Sized + Reversible<List<_>> { }

public contract Set<T: mut> requires Iterable<T> {
    contains(value: T): Boolean;
}

public contract Map<K, V: mut> requires Iterable<Pair<K, V>> {
    containsKey(key: K): Boolean;
    get(key: K): Option<V>;
    keyIterator(): &Iterator<K>;
}
```

**`List`.**

- `List` means a **finite, ordered sequence**. `Iterable` promises repeatable traversal and nothing
  about order or extent: `Set` and `Map` iterate in unspecified order, and an `Iterable` may be
  unbounded. Finiteness is anchored in the signature through `Sized`, since `size(): Int` can only be
  answered by a finite collection; the compiler cannot prove it, so a conformer that reports a size
  it does not have violates the contract. Order is a documented law: `iterator()` visits the
  elements in sequence order, starting at the sequence's initial end, on every call.
- `List` does not require `RandomAccess`, since a linked or cons list cannot offer `O(1)` indexing.
  Code that indexes writes `<L: List<T> + RandomAccess<T>>`.
- `List` does not require `Sequenced`. `first()` and `last()` do not express order, and singly linked
  or fold-based representations cannot offer `last()` in constant time. Access to the ends is
  expressed through independent capabilities: `Head<T>` for `first()`, and a last-element capability
  whose name is left to the API review (`Tail` is avoided, since it conventionally names the
  remainder of a sequence).
- `List` requires `Reversible<List<_>>`, so every list offers a reversed copy. A contract cannot
  declare a witness, so the requirement only propagates the capability's abstract member, `reversed`,
  to each implementer, which provides it and returns a `List<T>`. Reversal by copy is `O(n)` in any
  representation and needs no access to the ends. `InPlaceReversible` is not required, since a
  persistent list cannot support it; a mutable class may declare it. A lazy `O(1)` reversed view
  would need backward traversal, which `Iterator` does not offer, and is outside this proposal.

**`Set` and `Map`.**

- `Set` guarantees that no two stored elements are equivalent under that set's membership relation,
  and `contains` and insertion use the same relation. `Map` contains at most one entry per
  key-equivalence class, `get` and `containsKey` use the same relation, and inserting an equivalent
  key updates the existing mapping. The contracts do not prescribe how equivalence is implemented: a
  hash set may use `Hashable`, an identity set reference identity, an ordered set its ordering.
- `Map` carries **no bound on `K`**. Each implementation states its own: `HashMap` keeps
  `K: Hashable<K>` as a class bound, an identity-keyed map has none, and a sorted map requires an
  ordering.
- `Set` and `Map` expose iteration, membership, and lookup only; key and value views are not part of
  the contracts. Map iteration yields one `Pair<K, V>` per mapping, which allocates and is in
  unspecified order unless an implementation documents otherwise; `keyIterator` is the
  allocation-free path for hot loops. It is read-only, since `Iterator` exposes only `next`; removal
  goes through `KeyedSink.remove`.

### Size

Two different questions need two different answers:

| Question | Answer |
| -------- | ------ |
| How many elements does this collection hold? | `count()`, an `Iterable` default that traverses |
| How many elements does it hold in constant time? | `Sized.size(): Int`, a capability |

`List` requires `Sized`; `Set` and `Map` do not, so a sorted map may answer `count()` by traversal and
still be a `Map`. Code that relies on constant-time size on a `Set` or `Map` declares
`<C: Iterable<T> + Sized>`, and `ArrayList`, `HashMap`, and `HashSet` conform. `count()` and
`isEmpty()` are `Iterable` defaults and therefore traversals unless overridden: every `List`
conformer overrides them from `size`, so `count()` and `size` agree, and any other implementation
with a constant-time size does the same and conforms to `Sized`.

A cons or persistent list conforms by caching its length in each node or in a header wrapper. A
sequence whose length needs a traversal, such as a pure Church encoding whose only primitive is a
fold, is an `Iterable` and not a `List`.

### Equality and hashing

Conditional conformance exists for nominal targets only, a witness whose target is a contract is
rejected, and `Eq` is receiver-shaped (`eq(other: T): Boolean`), so a contract-wide instance is not a
library-level change. Therefore:

- cross-implementation equality for `List` is expressed as generic functions with element
  evidence, `sameElements<T: mut + Eq<T>>(left: List<T>, right: List<T>): Boolean` and
  `elementsHash<T: mut + Hashable<T>>(values: List<T>): Int`, with the hash algorithm documented on
  `List` so that equal lists hash equally in any representation;
- `Eq` and `Hashable` may additionally be derived on `ArrayList`, conditional on its element type,
  for code that names the concrete class; contract-typed values deliberately have no `==`;
- for `Set` and `Map`, cross-implementation equality is not well defined because key equivalence is
  per instance, so equality is per implementation. Contract witnesses would also need an overlap rule
  against class witnesses.

### Related implementations

- **`MapBackedSet<T>`** is an implementation class, not a contract, constructed from `&Map<T, Unit>`
  by a named constructor, with `HashSet` as its `HashMap` specialization and the default. The
  injected map owns `containsKey` and `put`, so `contains` and insertion necessarily use the same
  relation; a set over a sorted map is a `MapBackedSet` over that map. The `Set` contract stays
  storage-neutral.
- **Ordered maps** are outside this proposal. When added, `SortedMap<K, V>` requires `Map<K, V>` and
  states its ordering through capabilities rather than a bound on `K`, and `TreeMap` is its single
  implementation, documented as a red-black tree with the tree class internal. A public
  `RedBlackMap` is rejected: two names for one structure, with the balancing algorithm frozen into
  the API. Later structures (B-tree, skip list) become further `SortedMap` implementations.

### Mutation as capabilities

There is no `MutableList` or similar bundle. Under Zeron's view model such a contract would offer no
method through a read-only view that `List` does not offer, and `&MutableList<T>` would repeat the
mutability that `&` already states. The standard library already names mutation by operation
(`Sink.add`, `InPlaceReversible.reverse`, `InPlaceSortable.sort`), and this proposal continues that
pattern:

| Capability | Operations | Conformers |
| --- | --- | --- |
| `Sink<T>` (existing) | `mut add(value): Boolean` | `ArrayList`, `HashSet`, `LinkedList`, `ArrayDeque` |
| `Deque<T>` | `mut addFirst(value): Unit`, `mut addLast(value): Unit`, `mut removeFirst(): Option<T>`, `mut removeLast(): Option<T>` | `LinkedList`, `ArrayDeque` |
| `PositionalEditor<T>` | `mut insert(index, value): Boolean`, `mut removeAt(index): Option<T>`, `mut replaceAt(index, value): Option<T>` | `ArrayList` |
| `Removable<T>` | `mut remove(value): Boolean` | `HashSet` |
| `KeyedSink<K, V>` | `mut put`, `mut putIfAbsent`, `mut compute`, `mut computeIfAbsent`, `mut remove(key)` | `HashMap`, `IdentityHashMap` |
| `Clearable` | `mut clear(): Unit` | `ArrayList`, `HashSet`, `HashMap`, `LinkedList`, `ArrayDeque`, `IdentityHashMap` |

Code that edits a list declares what it needs and takes a mutable view, using intersection bounds:

```zeron
// illustrative
fn drain<T: mut, L: List<T> + Sink<T> + PositionalEditor<T> + Clearable>(list: &L): Unit { ... }
```

A persistent implementation conforms to `List` and none of the mutation capabilities, which is why
mutation is not part of the contract. If naming a combination of bounds proves worth it, the existing
pattern for a bundle with no members of its own applies (`requires A + B {}`, as in `MonadPlus`), at
the price of nominal conformance.

- `PositionalEditor` is not called `Cursor`: it addresses elements by index and exposes no movable
  position handle. A true cursor, supporting efficient relative edits on linked structures, is a
  different capability outside this proposal. `insert` returns `Boolean` to report an invalid index;
  `removeAt` and `replaceAt` return `Option` to report the element they removed or replaced. The
  asymmetry is deliberate.
- `KeyedSink.compute` and `computeIfAbsent` invoke their callbacks immediately, so they are
  effect-row-polymorphic like the `Iterable` terminal methods and the callback's row propagates to
  the caller. Overloads and return behavior follow the existing `Map` API; only the effect typing
  changes:

  ```zeron
  mut compute<E: effect...>(
      key: K,
      transform: (K, Option<V>) -> Option<V> raises E
  ): Option<V> raises E;

  mut computeIfAbsent<E: effect...>(
      key: K,
      transform: (K) -> V raises E
  ): V raises E;
  ```

- Copying and in-place operations are separate capabilities: `Reversible<C<_>>` has `reversed` and
  `InPlaceReversible<C<_>>` has `mut reverse`; `Sortable<C<_>>` has `sortedBy`/`sorted` and
  `InPlaceSortable<C<_>>` has `sortBy`/`sort`. Persistent collections provide the copying side
  without claiming mutation, and a mutable class may provide both. Only `Reversible<List<_>>` is
  required by a contract, and only of `List`.

### `Iterable` defaults and effect rows

The terminal operations currently on `Stream` become default methods on `Iterable`, so any collection
can use them without `.stream()`. This is necessary rather than convenient: `Foldable` cannot be
instantiated for the `Iterable` contract, so a value typed `List<T>` or `Iterable<T>` obtains
operations only from methods of ordinary contracts. Each is polymorphic in the effect row of its
callback, because the callback runs during the call:

```zeron
// illustrative
public contract Iterable<T: mut> {
    /// Returns an iterator positioned before the first element.
    ///
    /// Every call returns an independent iterator, so a value that can be traversed twice yields
    /// the same elements each time. A one-shot source is not an `Iterable`.
    iterator(): &Iterator<T>;

    default forEach<E: effect...>(consumer: (T) -> Unit raises E): Unit raises E {
        for (let element in this) consumer(element);
    }

    default fold<R: mut, E: effect...>(
        initial: R,
        accumulator: (R, T) -> R raises E
    ): R raises E {
        let mut result = initial;
        for (let item in this) result = accumulator(result, item);
        return result;
    }

    default any<E: effect...>(predicate: (T) -> Boolean raises E): Boolean raises E { ... }
    default all<E: effect...>(predicate: (T) -> Boolean raises E): Boolean raises E { ... }
    default count(): Int = this.fold(0, (n, _) -> n + 1);
    // Stops after the first element; an unbounded `Iterable` must not be traversed to answer it.
    default isEmpty(): Boolean { ... }

    default stream(): Stream<T> = Stream.from(this);
}
```

An implementation that overrides one of these repeats the method's row parameter and may not widen
it, as [ZEP-0086](./ZEP-0086.md) requires. A call with a pure callback infers the empty row, so
existing code is unaffected.

### Effect policy for lazy sequences

- **Iteration has the empty row.** `Iterator.next` and `Iterable.iterator` declare no row, so an
  implementation cannot raise. An effectful source, such as one that reads a file, reports failures
  as data, for example by yielding `Result` values. A row parameter on `Iterator` and `Iterable` is
  rejected: it would change the arity of the two most-implemented contracts, make every `for` loop
  row-polymorphic in its enclosing function, and let an effect raised during `next()` run under the
  consumer's handler scope instead of the scope that created the sequence. If effectful iteration is
  wanted, it is a separate abstraction (`EffectfulIterator<T, E>` with row-polymorphic terminal
  operations), not a change to `Iterable`.
- **Lazy transformations take pure callbacks.** The callbacks of `Stream.map`, `filter`, `flatMap`,
  `takeWhile`, and similar operators run when the stream is consumed, not when the operator is
  called, so declaring the call as `raises E` would let the effect escape the handler scope that
  enclosed it. These operators keep a function type with the empty row, and the compiler rejects an
  effectful callback by the existing inclusion rule.
- **Terminal operations are row-polymorphic.** `fold`, `forEach`, `any`, and `all` run the traversal
  during the call, so a callback's row propagates to the caller. `count` and `isEmpty` have no
  callback and remain pure.
- **`Functor` stays pure-only.** Its instances include `Stream`, whose `map` is lazy; a row on `map`
  would be inherited by `Stream` while the effect happens at consumption, so the signature would
  misstate where the effect occurs. Effect-polymorphic strict mapping, if wanted, belongs on
  `Iterable` as a default method, which also keeps `Monad`, `Applicative`, and `Traversable`
  consistent.
- **Collection syntax is distinct.** `collect expression into sink` is eager accumulation into a
  sink, not an `Iterable.collect` method. Building a collection from a stream through the library
  API remains the job of `Stream.collect` and `Collector`.
- **The row is discharged where the effect happens.** Every effect is raised by code that runs under
  a handler scope the caller can see: a terminal operation or a callback it invokes. Nothing here
  lets an effect escape the scope that encloses the call which created the sequence.

An effect-tracking stream would need a row parameter on the stream type (`Stream<T, E: effect...>`)
and, for each operator, the union of the upstream row and the callback's row in a type argument. That
is not expressible today: the one-row-variable rule applies to `raises` lists, effect sets are parsed
only there, and a type argument is an ordinary type, though a single row variable may be passed as
one. It would also not suffice on its own, since the effect is performed inside `Iterator.next()`,
whose signature is pure. Such a proposal must decide where the row is discharged. The policy above
adds no type parameters and can be extended later without breaking it.

### `Stream` and building collections

`Stream` stays a final class over an `Iterable` source, with the lazy operators and its
`Monad<Stream<_>>` and `Foldable<Stream<_>>` instances. `Stream.toList()` remains and is generalized
through `Collector` with a method-level constructor bound:

```zeron
// illustrative
public collect<C<_>: Collector<C>>(): &C<T> { ... }
```

`toList()` returns the concrete default `ArrayList<T>`, which is a `List<T>`; callers keep the
concrete-only capabilities, such as constant-time indexing.

A fold-based (Church) sequence is an `Iterable` and is not unified with `Stream` under a new
contract. Both share `Iterable`; `Stream` adds laziness, possible infinity, and the effect policy,
none of which a finite strict encoding needs. Its `iterator()` must materialize the sequence, since a
fold is internal iteration and `Iterable` is external. A contract for internal iteration with early
termination can be introduced when a second conformer justifies it.

### Capability instances

Instances over type constructors are declared for each concrete class, not for the contract:
`Foldable<ArrayList<_>>` and `Collector<ArrayList<_>>`, using `delegating implementation` where the
class already provides the methods. The mutable array-backed class also implements
`InPlaceReversible` and `InPlaceSortable` where applicable. Generic code over any collection is
written with a method-level constructor bound, as `Traversable` does (`<C<_>: Foldable<C>, A>`), and
applies to concrete classes; such functions must retain the concrete constructor in their type
parameter.

A type that is both `Iterable` and `Foldable` must keep the two consistent, because both offer
`count` and `isEmpty`. On a value bounded by both, `x.count()` resolves to `Iterable.count`; on a
value bounded only by `Foldable`, as in `<C<_>: Foldable<C>, A>`, `c.count()` resolves to the
`Foldable` default; and `X.count(x)` always names the `Foldable` one. Resolution prioritizes
contracts over type-constructor capabilities but does not segregate them, so the same expression can
have different costs under different bounds. Therefore:

- a `Foldable` instance of an `Iterable` type delegates `count` and `isEmpty` to the type's
  `Iterable` versions (`delegating implementation`), so both paths agree in result and, where
  `Sized` applies, in cost, and `isEmpty` stops after the first element on both;
- `foldLeft` traverses in the same order as `iterator()`;
- the `count` and `isEmpty` defaults of `Foldable` are linear, and instances override them whenever
  they can do better. `foldLeft` cannot stop early, so for a `Foldable` that is not `Iterable`, such
  as a tree, `isEmpty` stays linear: a limit of the `Foldable` signature, not of this proposal.

A contract cannot declare witnesses, so a contract that names a type-constructor capability among its
requirements, as `List` does with `Reversible<List<_>>`, only propagates that capability's abstract
members to its implementers. A value typed with a contract uses the `Iterable` defaults and does not
acquire `Foldable<ArrayList<_>>` or any other implementation-specific instance.

### Serialization

Encoding works for any implementation through iteration. Decoding needs a concrete construction
strategy. A contract-typed field may use a default implementation only when it is valid for the
field's type arguments and required capabilities: `Map<K, V>` does not imply `Hashable<K>`, so
`HashMap<K, V>` is not a valid decoder for every `Map<K, V>`, and the same applies to any `Set<T>`
implementation with bounds `Set<T>` lacks.

Generated decoding must not add implementation-specific bounds to a contract or assume every contract
has one compatible default. It uses an explicit concrete type, a compatible construction witness
supplied by the serialization context, or an explicit codec; a `Map<K, V>` field cannot be decoded
through `HashMap` unless `Hashable<K>` and `Eq<K>` evidence is available for its actual arguments. If
none is available, decoding is a compile-time error. Concrete-typed fields decode into that class.
This interacts with [ZEP-0092](./ZEP-0092.md) and must be validated with it.

## Compatibility and impact

This is a source-breaking change to the standard library, accepted deliberately:

1. **Construction.** `List.of`, `Map.empty`, and similar name a concrete class.
2. **Mutation through the plain names.** Code that mutates through `List<T>` takes `&L` with
   capability bounds.
3. **Capability instances.** `Foldable` and `Collector` instances move to the concrete classes, and
   contract-typed values use the `Iterable` defaults. `Reversible` becomes a requirement of `List`.
4. **Indexed access.** Code that calls `at` on a `List` requires `RandomAccess` or names `ArrayList`.
5. **Inference.** Unannotated bindings infer a concrete class.
6. **Serialization.** Contract-typed fields require a compatible construction strategy or codec.
7. **Collection semantics.** Implementations must honor the ordering, uniqueness, key-equivalence,
   and iteration guarantees of the contracts, and every `List` must provide a constant-time `size`.

The change follows the standard-library API versioning policy. Effect rows added to `Iterable`
defaults are source compatible for pure callbacks, and the library index records the new row
parameters as described in [ZEP-0086](./ZEP-0086.md). The additive capabilities (`Sized`,
`PositionalEditor`, `Removable`, `KeyedSink`, `Clearable`) and the `sameElements`/`elementsHash`
helpers break no existing program: a class gains a capability by declaring it, and generic code opts
in by naming the bound.

## Alternatives

- **Keep the classes and write against capabilities.** No breakage, but no short name for an ordered
  or associative collection, and a persistent list is never a `List`.
- **New names for the contracts, plain names kept on the classes.** No breakage, but `ConstructList`
  would be a list that is not a `List`.
- **`List` without `Sized`.** The smallest surface, and it would admit a pure Church encoding, but the
  contract would have no members and its finiteness no anchor in any signature. Requiring `Sized`
  makes finiteness visible in the type at the price of one cached length per implementation.
- **`List` requiring `Sequenced`.** `first()` and `last()` do not express order, and `last()` is not
  constant-time for singly linked or fold-based representations.
- **`List` requiring `InPlaceReversible`.** A persistent list cannot reverse in place.
- **A `MutableList` bundle.** One name, but it repeats the mutability that `&` states, and a parameter
  typed with it and without `&` cannot mutate.
- **An optional mutable face for a contract** (mutable members required only of implementations that
  opt in). It removes the redundancy but changes the language and needs a rule for which members
  belong to the mutable face.
- **A single `Set` class over any `Map`.** Simpler, but excludes sets that are not map-backed;
  generalized instead as `MapBackedSet`.
- **`Stream` as a contract.** What varies between lazy sequences is the source, which `Iterable`
  already expresses, and the operators are a fixed set.
- **`Foldable<Iterable<_>>`.** Not expressible: a constructor parameter cannot be bounded and
  `requires` cannot relate the two kinds of contract.
- **Effect-tracking streams now, a row on `Iterator`/`Iterable`, or a row on `Functor.map`.** See
  [Effect policy](#effect-policy-for-lazy-sequences).
- **`Eq<List<T>>` as a witness over the contract.** See [Equality and hashing](#equality-and-hashing).

## Implementation and validation

1. Introduce the capability contracts (`Sized`, `PositionalEditor`, `Removable`, `KeyedSink`,
   `Clearable`) and split copying from in-place `Reversible` and `Sortable` capabilities.
2. Introduce the `List`, `Set`, and `Map` contracts, specify their guarantees, and rename the
   classes; generalize the map-backed `Set` into `MapBackedSet<T>` over any `Map<T, Unit>`.
3. Re-home capability instances on the concrete classes and re-implement the iterators over them.
4. Add the `Iterable` defaults with row parameters and have `Stream` use them; make `isEmpty` stop
   after the first element, document the re-traversal invariant on `iterator()`, and generalize
   collection construction through `Collector`.
5. Widen read-only parameters in the standard library to the contracts, auditing every public
   signature that takes or returns a collection (read-only parameter, mutating parameter, return).
6. Benchmark `at` and `count()` on concrete and contract-typed lists, and `count()` on a `Set` or
   `Map` where it is linear, comparing monomorphic, bimorphic, and megamorphic call sites after JVM
   warmup, with primitive and object element types.
7. Test in the standard library test suite:
   - **Conformance:** a persistent list and a cons list that cache their length and conform to `List`
     with a small mandatory surface; a Church-encoded sequence that conforms to `Iterable` only,
     materializes in `iterator()`, and is rejected where a `List` is required; a sorted map and an
     identity-keyed map conforming to `Map` with consistent `get`/`containsKey` and key replacement;
     sets with structural and identity membership, including duplicate rejection; generic code over
     `ArrayList` and the alternative implementations alike.
   - **Capabilities:** intersection bounds; `PositionalEditor` success and failure cases;
     copying-only and in-place reversible/sortable implementations, including that every prototype
     `List` provides `reversed` with a matching `size` and that a persistent list does not declare
     `InPlaceReversible`; `Sized` required of every `List` and elsewhere only where needed, with
     `count()` correct for a linear `Set` or `Map` and equal to `size` on every `List`.
   - **Effects:** `forEach`, `fold`, `any`, `all`, `KeyedSink.compute`, and `computeIfAbsent` with
     pure and effectful callbacks, including propagation of the row and rejection of an uncovered
     row; an effectful callback to `Stream.map` rejected and a pure one accepted; a handler
     enclosing a terminal operation handling its callback's effect.
   - **`Iterable` and `Foldable`:** a type with both gives the same `count`, `isEmpty`, and
     traversal order through `x.count()` and `X.count(x)`; a function bounded only by `Foldable`
     calls `isEmpty()` on `ArrayList` without a full traversal, and `count()` in constant time.
   - **Iteration:** `isEmpty()` returns after the first element of an unbounded `Iterable`; a
     one-shot source is rejected as an `Iterable`; a re-traversed `Iterable` yields the same
     elements.
   - **Equality and serialization:** `sameElements` and `elementsHash` agree across `ArrayList` and
     a prototype list; derived codecs over contract-typed and concrete-typed fields, including
     rejection when no compatible default or construction witness exists, and separate compilation
     of contracts, instances, and defaults.

## Implementation notes

Landed on 2026-11-04:

- `zeron.collections` now declares the `List<T>`, `Map<K, V>`, and `Set<T>` contracts. The concrete
  classes are `ArrayList<T>`, `HashMap<K, V>`, and `HashSet<T>`, and each declares the contract it
  implements. `List` requires `Sized`, so every list offers a constant-time `size`; `Map` and `Set`
  expose membership and lookup only.
- The capability contracts live beside the collection contracts: `Sized`, `PositionalEditor`,
  `Removable`, `KeyedSink`, and `Clearable` are new, `Reversible` and `Sortable` are split into
  copying and in-place variants (`InPlaceReversible`, `InPlaceSortable`), and the concrete classes
  declare the capabilities they support. `KeyedSink.compute` and `KeyedSink.computeIfAbsent` are
  effect-row-polymorphic, and `HashMap` implements them as such.
- `ArrayList.insert` returns `Boolean` to report an out-of-range index, as this proposal requires.
- Every standard-library signature that named the classes is updated; read-only parameters may now
  name the contracts, and `Stream.toList` returns an `ArrayList<T>`.
- `Iterable` carries the terminal operations as defaults: `forEach`, `fold`, `any`, and `all` are
  effect-row-polymorphic and propagate the callback's row to the caller, while `count` traverses
  and `isEmpty` stops after the first element. `Stream` repeats the row parameters on its
  overrides, as [ZEP-0086](./ZEP-0086.md) requires, and `ArrayList`, `HashSet`, and `HashMap`
  override `count` and `isEmpty` from their constant-time size. The internal `count` fields were
  renamed to `elementCount` so the name is free.

Baseline alternative implementations landed with the contracts as validation targets:

- `LinkedList<T>` is a mutable doubly linked list and `ArrayDeque<T>` is a mutable circular-array
  deque; both implement `List`, `Sequenced`, the new `Deque<T>` capability, `Sink`, `Clearable`,
  `Reversible`, `InPlaceReversible`, `Foldable`, and `Collector`.
- `ConsList<T>` is a persistent singly linked list. It implements `List`, `Sequenced`,
  `Reversible`, and `Foldable`, but no mutation capability, which exercises the split between
  copying and in-place reversal.
- `IdentityHashMap<K, V>` implements `Map` with reference identity: keys are bucketed with the new
  `System.identityHashCode` and compared with `===`, so `K` needs neither `Eq` nor `Hashable`.
- `HashMap` and `IdentityHashMap` share the package-private `HashTable` bucket structure, so the
  map contract has two implementations over one representation.
- `Deque<T> requires List<T> + Sequenced<T>` adds `addFirst`, `addLast`, `removeFirst`, and
  `removeLast`, and is the first capability contract validated by more than one class.

Supporting the array-backed `Iterable` witness required an emitter fix: the generated array adapter
now registers function-shape interfaces for every function-typed parameter and return of the
iterable contract, rather than only for `forEach`, so members such as `fold` link at run time.

Landing the row-polymorphic defaults required a compiler fix: a generic call previously re-unified
each resolved argument against the formal parameter invariantly, which rejected a broadly accepting
callback such as `(Any?) -> Unit` where `(Int) -> Unit` was expected. Argument inference now binds
only the callee's type parameters (`TypeUnifier.unifyForInference`) and leaves variance and effect
inclusion to assignability.

Deferred, with the reason:
- `MapBackedSet`, the `sameElements`/`elementsHash` helpers, conditional `Eq`/`Hashable` derivation
  on `ArrayList`, `Collector`-based construction in `Stream.toList`, and decoding contract-typed
  fields in generated serialization, all of which depend on either a second conformer or a
  language feature this slice does not need.

## Decision

Accepted on 2026-11-03 after review of the design document and of the language constraints the
proposal relies on, and amended the same day before implementation. The direction: `List`, `Map`, and
`Set` become contracts and the existing classes are renamed; `List` requires
`Iterable<T> + Sized + Reversible<List<_>>`; mutation stays in capability contracts; `Iterable` gains
row-polymorphic terminal defaults; `Stream` remains a final class with lazy operators over pure
callbacks. Iteration stays pure with failures as data, `Functor` stays pure-only, list equality is
expressed by generic functions rather than a contract-wide `Eq`, and map-backed sets and ordered maps
are implementation classes (`MapBackedSet` in scope; `SortedMap` with a single `TreeMap` out of
scope).

Acceptance approves the design direction; implementation remains subject to release planning, and
the release state in the [ZEP tracker](./ZEP.md) is unchanged.
