## Abstract

This proposal turns `List`, `Map`, and `Set` from classes into contracts, and renames the existing
classes `ArrayList`, `HashMap`, and `HashSet`. The contracts are bundles of the capability contracts
the standard library already uses (`Iterable`, `Sequenced`, `RandomAccess`, `Sink`), so alternative
implementations can be written against them and passed to any API that takes the contract.

It also moves the terminal operations of `Stream` onto `Iterable` as default methods, makes
higher-order operations on `Iterable` polymorphic in their effect row, splits mutation into small
capability contracts instead of a mutable bundle, and states how effect rows apply to lazy
sequences. `Stream` itself stays a final class.

The motivation, the options considered, and the experiments are in
[the design document](../design_documents/design-document-20_collection-contracts-v4.md).

## Motivation

`List`, `Map`, `Set`, and `Stream` are final classes with a single implementation each. A persistent
list, a linked list, a sorted map, or an identity-keyed map cannot be passed to an API that takes a
`List` or a `Map`, and an API that only reads a collection must name an array-backed or hash-backed
class. The standard library already splits behavior into capability contracts (`Sink`,
`RandomAccess`, `Sequenced`, `Foldable`, `Collector`), but there is no short name for an ordered
collection or an associative one, and several capabilities are bound to the class
(`Reversible<List<_>>`, `Foldable<List<_>>`, `Collector<List<_>>`).

Two language constraints shape the design. Capability contracts over type constructors
(`Foldable<F<_>>`) cannot bound their constructor parameter, and `requires` cannot relate them to
ordinary contracts such as `Iterable<T>`, so an instance cannot be written once for a contract.
And effect rows ([ZEP-0086](./ZEP-0086.md)) make it possible to give higher-order collection
operations precise effect types, which the current signatures do not use.

## Goals

- Let `List`, `Map`, and `Set` have more than one implementation behind one name.
- Keep the contracts small: a bundle of existing capabilities, so a new implementation has a small
  mandatory surface.
- Express mutation as capabilities named for operations, without a contract named for a state.
- Make strict higher-order operations and terminal operations effect-polymorphic.
- Keep `Stream` a final class, with `Iterable` as the contract that lazy sequences implement.

## Non-goals

- Shipping alternative implementations (`ConstructList`, `DoublyLinkedList`, `TreeMap`,
  `IdentityHashMap`, and others). They are used here as validation targets, and each belongs to its
  own proposal; the resolutions below fix their names and relationships, not their schedule.
  `MapBackedSet` is the exception, because it is the generalization of the wrapper the current `Set`
  class already is.
- Equality and hashing for collections. They are absent today and are a follow-up.
- Effect-tracking lazy streams, or effectful iteration sources, beyond the policy stated below.
- Changing `Functor`, `Monad`, or other type-class contracts.
- A language feature for an optional mutable face of a contract.

## Proposal

### Naming

| Current | After this proposal |
| --- | --- |
| `List<T>` (class) | `List<T>` (contract); the class is `ArrayList<T>` |
| `Map<K, V>` (class) | `Map<K, V>` (contract); the class is `HashMap<K, V>` |
| `Set<T>` (class) | `Set<T>` (contract); the class is `HashSet<T>` |

The plain names denote the contracts. Constructors (`of`, `empty`, `fromArray`, `withMap`,
`withOperations`) stay on the classes. A contract may declare `static` members, but one is resolved
through an implementing type and a bare contract name has none, so there is no `List.of`. Generic code
builds collections through `Collector`.

### Contracts

```zeron
// illustrative
public contract List<T: mut> requires Iterable<T> + Sequenced<T> { }

public contract Set<T: mut> requires Iterable<T> {
    contains(value: T): Boolean;
}

public contract Map<K, V: mut> requires Iterable<Pair<K, V>> {
    containsKey(key: K): Boolean;
    get(key: K): Option<V>;
    keyIterator(): &Iterator<K>;
}
```

- `List` means a **finite, ordered sequence**. It does not require `RandomAccess`, since a linked or
  cons list cannot offer `O(1)` indexing. `at` is a separate capability: code that indexes writes
  `<L: List<T> + RandomAccess<T>>`. Finiteness is part of the `List` contract; `Iterable` itself may
  describe an unbounded source.
- A `Map` contract carries **no bound on `K`**. Each implementation states its own: `HashMap` keeps
  `K: Hashable<K>` as a class bound, an identity-keyed map would have none, and a sorted map would
  require an ordering. The `Hashable` bound therefore leaves the contract and is not moved to a
  constructor.
- `Set` guarantees that no two stored elements are equivalent under that set's membership relation.
  `contains` and insertion use the same relation. The contract does not prescribe structural equality
  or hashing: a hash set may use `Hashable`, an identity set may use reference identity, and an
  ordered set may use its ordering equivalence.
- `Map` contains at most one entry for each key-equivalence class. `get` and `containsKey` use the
  same key-equivalence relation; inserting an equivalent key updates the existing mapping rather than
  creating a second entry. The contract does not prescribe how equivalence is implemented.
- `Set` and `Map` expose iteration, membership, and lookup only. Key and value views are not part of
  the contracts: iteration through `Iterator` is the existing choice and is kept. Map iteration
  yields one `Pair<K, V>` per mapping; its order is unspecified unless an implementation documents
  otherwise.
- `size` stays a property of the concrete classes, so no conformer is forced to be sized. Constant
  time size remains available on contract-typed values through the `Sized` capability. The contracts
  expose `count()` and `isEmpty()` through `Iterable` defaults; those are traversals, and an
  implementation with a constant-time size overrides `isEmpty` and conforms to `Sized`.

### Size

Two different questions need two different answers, so size is not folded into the contracts:

| Question | Answer |
| -------- | ------ |
| How many elements does this collection hold? | `count()`, an `Iterable` default that traverses |
| How many elements does it hold in constant time? | `Sized.size(): Int`, a capability |

`List`, `Set`, and `Map` do not require `Sized`: a cons list or a sorted map may answer `count()` by
traversal and still be a `List` or a `Map`. Code that relies on constant-time size declares
`<C: Iterable<T> + Sized>`, and `ArrayList`, `HashMap`, and `HashSet` conform. This keeps `count()`
honest across implementations: it is linear unless the implementation overrides it.

### Mutation as capabilities

There is no `MutableList` or similar bundle. Under Zeron's view model such a contract would offer no
method through a read-only view that `List` does not offer, and `&MutableList<T>` would repeat the
mutability that `&` already states. The standard library already names mutation by operation
(`Sink.add`, `InPlaceReversible.reverse`, `InPlaceSortable.sort`), and this proposal continues that pattern:

| Capability | Operations | Conformers |
| --- | --- | --- |
| `Sink<T>` (existing) | `mut add(value): Boolean` | `ArrayList`, `HashSet` |
| `PositionalEditor<T>` | `mut insert(index, value): Boolean`, `mut removeAt(index): Option<T>`, `mut replaceAt(index, value): Option<T>` | `ArrayList` |
| `Removable<T>` | `mut remove(value): Boolean` | `HashSet` |
| `KeyedSink<K, V>` | `mut put`, `mut putIfAbsent`, `mut compute`, `mut computeIfAbsent`, `mut remove(key)` | `HashMap` |
| `Clearable` | `mut clear(): Unit` | `ArrayList`, `HashSet`, `HashMap` |

Code that edits a list declares what it needs and takes a mutable view. Intersection bounds are valid:

```zeron
// illustrative
fn drain<T: mut, L: List<T> + Sink<T> + PositionalEditor<T> + Clearable>(list: &L): Unit { ... }
```

`PositionalEditor` is deliberately not called `Cursor`: its operations address elements by index
and do not expose a movable position handle. A true cursor abstraction would represent a position
within a sequence and could support efficient relative edits on linked structures; that is a
different capability and is not part of this proposal. `insert` returns `Boolean` so an invalid
index can be reported instead of silently ignored; `removeAt` and `replaceAt` use `Option` to report
whether an element existed.

`KeyedSink.compute` and `computeIfAbsent` invoke their callbacks immediately, so their signatures are
effect-row-polymorphic just like the `Iterable` terminal methods. The callback's row must propagate
to the caller rather than being erased. Schematically:

```zeron
mut compute<E: effect...>(
    key: K,
    transform: (K, Option<V>) -> Option<V> raises E
): Option<V> raises E;

mut computeIfAbsent<E: effect...>(
    key: K,
    transform: (K) -> V raises E
): V raises E;
```

The exact overloads and return behavior follow the existing `Map` API; this proposal changes their
effect typing, not their mapping semantics.

A persistent implementation conforms to `List` and none of the mutation capabilities, which is the
reason mutation is not part of the contract. If naming a combination of bounds proves worth it, the
existing pattern for a bundle with no members of its own applies (`requires A + B {}`, as in
`MonadPlus`), at the price of nominal conformance.

Copying and in-place operations are separate capabilities. `Reversible<C<_>>` contains `reversed`,
while `InPlaceReversible<C<_>>` contains `mut reverse`. Likewise, `Sortable<C<_>>` contains
`sortedBy`/`sorted`, while `InPlaceSortable<C<_>>` contains `sortBy`/`sort`. Persistent collections
can therefore provide copying operations without claiming to support mutation. A mutable concrete
implementation may conform to both sides.

### `Iterable` defaults and effect rows

The terminal operations currently on `Stream` become default methods on `Iterable`, so any collection
can use them without `.stream()`. This is necessary rather than convenient: `Foldable` cannot be
instantiated for the `Iterable` contract, so a value typed `List<T>` or `Iterable<T>` obtains
operations only from methods of ordinary contracts. Each is polymorphic in the effect row of its
callback, because the callback runs during the call:

```zeron
// illustrative
public contract Iterable<T: mut> {
    /// Returns an iterator positioned before the first element.
    ///
    /// Every call returns an independent iterator, so a value that can be traversed twice yields
    /// the same elements each time. A one-shot source is not an `Iterable`.
    iterator(): &Iterator<T>;

    default forEach<E: effect...>(consumer: (T) -> Unit raises E): Unit raises E {
        for (let element in this) consumer(element);
    }

    default fold<R: mut, E: effect...>(
        initial: R,
        accumulator: (R, T) -> R raises E
    ): R raises E {
        let mut result = initial;
        for (let item in this) result = accumulator(result, item);
        return result;
    }

    default any<E: effect...>(predicate: (T) -> Boolean raises E): Boolean raises E { ... }
    default all<E: effect...>(predicate: (T) -> Boolean raises E): Boolean raises E { ... }
    default count(): Int = this.fold(0, (n, _) -> n + 1);
    // Stops after the first element; an unbounded `Iterable` must not be traversed to answer it.
    default isEmpty(): Boolean { ... }

    default stream(): Stream<T> = Stream.from(this);
}
```

An implementation that overrides one of these repeats the method's row parameter and may not widen
the row, as [ZEP-0086](./ZEP-0086.md) requires. A call with a pure callback infers the empty row, so
existing code is unaffected.

### Effect policy for lazy sequences

- **Iteration has the empty row.** `Iterator.next` and `Iterable.iterator` declare no row, so an
  implementation cannot raise. An effectful source, such as one that reads a file, reports failures as
  data, for example by yielding `Result` values.
- **Lazy transformations take pure callbacks.** The callbacks passed to `Stream.map`, `filter`,
  `flatMap`, `takeWhile`, and similar operators run when the stream is consumed, not when the
  operator is called. Declaring the call as `raises E` would let the effect escape the handler scope
  that enclosed the call. These operators therefore keep a function type with the empty row, and the
  compiler rejects an effectful callback by the existing inclusion rule.
- **Terminal operations are row-polymorphic.** `fold`, `forEach`, `any`, and `all` run the
  traversal during the call, so a callback's row propagates to the caller. `count` and `isEmpty`
  have no callback and remain pure.
- **Collection syntax is distinct from a terminal method.** The language's
  `collect expression into sink` form is eager accumulation into a sink; it is not a new
  `Iterable.collect` method and does not belong in the list of effect-polymorphic callback methods.
  Building a collection from a stream through the library API remains the responsibility of
  `Stream.collect` and `Collector`.
- **The row is discharged where the effect happens.** Every effect is raised by code that runs under
  a handler scope the caller can see: a terminal operation, or a callback that operation invokes.
  Nothing in this design lets an effect escape the scope that encloses the call which created the
  sequence.

A stream that tracks the effects of its pipeline would need a row parameter on the stream type
(`Stream<T, E: effect...>`) and, for each operator, the union of the upstream row and the callback's
row in a type argument. That is not expressible today (see [Review resolutions](#review-resolutions)),
and it would not be sufficient on its own: the effect is performed inside `Iterator.next()`, which
declares the empty row, so the row would also have to be carried by the operation that performs it.
This policy is sound, adds no type parameters, and can be extended later without breaking it.

### `Stream` and building collections

`Stream` stays a final class over an `Iterable` source. It keeps the lazy operators and its
`Monad<Stream<_>>` and `Foldable<Stream<_>>` instances. `Stream.toList()` remains and is generalized
through `Collector` with a method-level constructor bound:

```zeron
// illustrative
public collect<C<_>: Collector<C>>(): &C<T> { ... }
```

`toList()` returns a `List<T>` backed by the default `ArrayList<T>` implementation. Its public
return type is the contract, so callers that need concrete-only capabilities may choose an explicit
concrete construction API instead.

### Capability instances

Instances over type constructors are declared for each concrete class and not for the contract:
`Reversible<ArrayList<_>>`, `Foldable<ArrayList<_>>`, and `Collector<ArrayList<_>>`, using
`delegating implementation` where the class already provides the methods. The mutable array-backed
class also implements `InPlaceReversible` and `InPlaceSortable` where applicable. Generic code over
any collection is written with a method-level constructor bound, as `Traversable` does
(`<C<_>: Foldable<C>, A>`), and applies to concrete classes. A value typed with the contract uses
`Iterable` defaults; it does not thereby acquire `Foldable<ArrayList<_>>` or another
implementation-specific HKT instance. Generic functions that require such an instance must retain
the concrete constructor in their type parameter.

### Serialization

Encoding works for any implementation through iteration. Decoding needs a concrete construction
strategy. A contract-typed field may use a default implementation only when that implementation is
valid for the field's type arguments and required capabilities. In particular, `Map<K, V>` does not
imply `Hashable<K>`, so `HashMap<K, V>` is not a universally valid decoder for every `Map<K, V>`;
the same issue applies if a `Set<T>` implementation requires bounds not present on `Set<T>`.

Generated decoding must not silently add implementation-specific bounds to a contract or assume that
every contract has one compatible default. It uses an explicit concrete type, a compatible
construction witness supplied by the serialization context, or an explicit codec. A `Map<K, V>`-typed
field, for example, cannot be decoded through `HashMap` unless `Hashable<K>` and `Eq<K>` evidence is
available for that field's actual arguments. If no compatible construction strategy is available,
decoding is a compile-time error. Concrete-typed fields decode into that concrete class. This
interacts with [ZEP-0092](./ZEP-0092.md) and must be validated with it.

## Compatibility and impact

This is a source-breaking change to the standard library, accepted deliberately. The breakage is:

1. **Construction.** `List.of`, `Map.empty`, and similar name a concrete class.
2. **Mutation through the plain names.** Code that mutates through `List<T>` takes `&L` with capability
   bounds.
3. **Capability instances.** `Reversible`, `Foldable`, and `Collector` instances move to the concrete
   classes, and contract-typed values use the `Iterable` defaults.
4. **Indexed access.** Code that calls `at` on a `List` requires `RandomAccess` or names `ArrayList`.
5. **Inference.** Unannotated bindings infer a concrete class.
6. **Serialization.** Contract-typed fields require a compatible default construction strategy,
   factory witness, or explicit codec; the decoder cannot assume that every contract can be
   implemented by the hash-based default.
7. **Collection semantics.** Implementations must honor the ordering, uniqueness, key-equivalence,
   and iteration guarantees stated by the contracts.

The change follows the standard-library API versioning policy. Effect rows added to `Iterable` defaults
are source compatible for pure callbacks, and the library index records the new row parameters as
described in [ZEP-0086](./ZEP-0086.md). The additive capability contracts (`Sized`, `PositionalEditor`,
`Removable`, `KeyedSink`, `Clearable`) and the `sameElements`/`elementsHash` helpers break no existing
program: a class gains a capability by declaring it, and generic code opts in by naming the bound.

## Alternatives

- **Keep the classes and write against capabilities.** No breakage, but no short name for an ordered
  or associative collection, and a persistent list is never a `List`.
- **New names for the contracts, plain names kept on the classes.** No breakage, but `ConstructList`
  would be a list that is not a `List`.
- **A `MutableList` bundle.** One name, but it repeats the mutability that `&` states, and a parameter
  typed with it and without `&` cannot mutate.
- **An optional mutable face for a contract** (the mutable members required only of implementations
  that opt in, so `&List<T>` means a mutable list). It removes the redundancy completely but changes
  the language and needs a rule for which members belong to the mutable face.
- **A single `Set` class over any `Map` implementation.** Simpler, but excludes sets that are not
  map-backed. Generalizing the current wrapper is now part of this proposal, as
  `MapBackedSet`.
- **`Stream` as a contract.** What varies between lazy sequences is the source, which `Iterable`
  already expresses, and the operators are a fixed set. A second implementation would duplicate code.
- **`Foldable<Iterable<_>>`.** Not expressible: a constructor parameter cannot be bounded and
  `requires` cannot relate the two kinds of contract.
- **Effect-tracking streams now.** Needs a row parameter on `Stream` and a union of rows in type
  arguments, which [ZEP-0086](./ZEP-0086.md) does not state to be admissible, and a pure
  `Iterator.next` to carry the row it performs.
- **A row parameter on `Iterator` and `Iterable`.** It would change the arity of the two
  most-implemented contracts and make every `for` loop row-polymorphic in its enclosing function, for
  a case that failure-as-data values already cover.
- **A row parameter on `Functor.map`.** A lazy instance such as `Stream` cannot honor it, because the
  callback runs at consumption, so the signature would misstate where the effect happens.
- **`Eq<List<T>>` as a witness over the contract.** Witnesses target nominal types only, and
  contract targets would need an overlap rule against class witnesses; for `Set` and `Map`
  cross-implementation equality is not even well defined.
- **A public `RedBlackMap` beside `TreeMap`.** Two names for one structure, with the balancing
  algorithm frozen into the public API.
- **Generic parameters on class constructors or static members.** Neither exists, and `Collector`'s
  generic `empty<A>` already covers generic construction.

## Implementation and validation

1. Introduce the capability contracts (`Sized`, `PositionalEditor`, `Removable`, `KeyedSink`,
   `Clearable`) and split copying from in-place `Reversible` and `Sortable` capabilities.
2. Introduce the `List`, `Set`, and `Map` contracts, specify their semantic guarantees, and rename
   the existing classes; generalize the current map-backed `Set` into `MapBackedSet<T>` over any
   `Map<T, Unit>`, with `HashSet` as its `HashMap` specialization.
3. Re-home capability instances on the concrete classes and re-implement the iterators over them.
4. Add the `Iterable` defaults with row parameters, and have `Stream` use them; make `isEmpty` stop
   after the first element, document the re-traversal invariant on `iterator()`, and generalize
   collection construction through `Collector`.
5. Widen read-only parameters in the standard library to the contracts.
6. Test, in the standard library test suite:
   - a prototype persistent list and a Church-encoded list (not shipped) that conform to `List` with a
     small mandatory surface;
   - a prototype sorted map and an identity-keyed map that conform to `Map`, including key
     replacement and consistent `get`/`containsKey` equivalence;
   - set implementations with structural and identity membership, including duplicate rejection;
   - generic code written with constructor bounds on `ArrayList` and on the prototype lists alike;
   - `forEach`, `fold`, `any`, and `all` with pure and effectful callbacks, including propagation of
     the callback's row to the caller and rejection of a row that is not covered;
   - `KeyedSink.compute` and `computeIfAbsent` with pure and effectful callbacks;
   - `PositionalEditor.insert` success and failure cases, plus `removeAt` and `replaceAt`;
   - copying-only and in-place reversible/sortable implementations;
   - an effectful callback passed to `Stream.map` is rejected, and a pure one is accepted;
   - a handler enclosing a terminal operation handles an effect raised by its callback;
   - intersection bounds over the capability contracts;
   - `sameElements` and `elementsHash` agree across `ArrayList` and a prototype list, and equal
     lists hash equally in both representations;
   - `Sized` is required only where constant-time size is needed, and `count()` stays correct for a
     collection whose `count()` is linear;
   - `isEmpty()` returns after the first element of an unbounded `Iterable` instead of traversing it;
   - a one-shot source is rejected as an `Iterable`, and a re-traversed `Iterable` yields the same
     elements;
   - derived codecs over contract-typed and concrete-typed fields, including rejection when no
     compatible default implementation or construction witness exists;
   - separate compilation of contracts, instances, and defaults.
7. Benchmark both `at` and `count()` on concrete and contract-typed lists, including a collection
   whose `count()` is linear, and compare monomorphic, bimorphic, and megamorphic call sites after
   JVM warmup. Include primitive and object element types.
8. Audit every public standard-library signature that takes or returns a collection and classify it as
   a read-only parameter, a mutating parameter, or a return.

## Review resolutions

The design document's direction is settled: `List`, `Map`, and `Set` become contracts and the classes
take qualifying names. The questions this proposal left open are resolved below. Statements about what
the language allows today were checked against the implementation, not assumed.

**Rows in type-argument position.** The one-row-variable rule is a rule about `raises` lists, and
effect sets are parsed only there; a type argument is an ordinary type, so a union of rows has no
syntax in type-argument position today. A single row variable may be passed as a type argument,
because a declaration may quantify `E: effect...`. Nothing here depends on rows in type arguments, so
the restriction stays where it is, and any row-union design belongs to the proposal that would
introduce an effect-tracking stream. Such a proposal must also decide where the row is discharged,
since the effect is performed inside `Iterator.next()`, whose signature is pure.

**A row parameter on `Iterator` and `Iterable`.** Rejected; iteration keeps the empty row and
effectful sources report failures as data. The row would change the arity of the two
most-implemented contracts, and `for (x in xs)` would have to become row-polymorphic in the enclosing
function, so every loop over an effectful source would infect its caller's effect row. It would also
reintroduce the escape this proposal avoids for lazy operators: an effect raised during `next()` runs
under the consumer's handler scope, not the scope that created the sequence. If effectful iteration
is wanted later, it is a separate abstraction (`EffectfulIterator<T, E>` with a matching contract and
row-polymorphic terminal operations), not a change to `Iterable` or `Iterator`.

**`Functor` purity.** `Functor` stays pure-only, and the reason is recorded on the contract. It is
keyed by constructor, and its instances include `Stream`, whose `map` is lazy; a row parameter on
`map` would be inherited by `Stream` while the effect actually happens at consumption, so the
signature would misstate where the effect occurs. Effect-polymorphic strict mapping, if it is wanted,
belongs on `Iterable` as a default method rather than in `Functor`, which also keeps `Monad`,
`Applicative`, and `Traversable` consistent with it.

**Generic parameters on constructors and static class members.** Neither exists today: classes
cannot declare static members, and a named constructor cannot declare its own type parameters.
Neither is needed. Generic construction already has a home in `Collector`'s generic `empty<A>`, and
concrete factories are named constructors that use the class's own type parameters
(`ArrayList.of(items: Array<T>)`). The question is dropped. If generic constructors are ever wanted,
adding type parameters to named constructors is cheaper than class statics, because a constructor
call is already a static call and needs no receiver-based dispatch rule.

**Map-backed sets.** Worth having, but as an implementation class rather than a contract:
`MapBackedSet<T>`, constructed from `&Map<T, Unit>` by a named constructor, with `HashSet` remaining
the default. Naming the storage is the point, because it states where key equivalence comes from: the
injected map owns `containsKey` and `put`, so `contains` and insertion necessarily use the same
relation. The `Set` contract stays storage-neutral, and a set over a sorted map is then a
`MapBackedSet` over that map, ordered because its storage is.

**Ordered maps.** When an ordered map is added, it is one contract and one implementation:
`SortedMap<K, V>` requires `Map<K, V>` and states its ordering through capabilities rather than a
bound on `K`, which `Map` does not carry, and `TreeMap` is its single implementation, documented as a
red-black tree with the tree class internal. A public `RedBlackMap` is rejected: two names for one
structure, and the balancing algorithm frozen into the API. A later structure (B-tree, skip list, AVL)
becomes another `SortedMap` implementation. Shipping an ordered map remains outside this proposal.

**Equality and hashing.** Conditional conformance exists for nominal targets only. A generic witness
may target a class, sum, or product and export element requirements
(`witness<T: mut + Eq<T>> Eq<Box<T>> for Box<T>`), and `deriving` on a generic class exports the same
requirements for separate compilation. A witness whose target is a contract is rejected. `Eq` is
itself receiver-shaped, `eq(other: T): Boolean`, so a contract-wide instance is not a library-level
change. Therefore:

- cross-implementation equality for `List` is expressed as generic functions with element evidence —
  `sameElements<T: mut + Eq<T>>(left: List<T>, right: List<T>): Boolean` and
  `elementsHash<T: mut + Hashable<T>>(values: List<T>): Int` — with the hash algorithm documented on
  `List` so that equal lists hash equally in any representation;
- `Eq` and `Hashable` may additionally be derived on `ArrayList` itself, conditional on its element
  type, for code that names the concrete class; contract-typed values deliberately have no `==`;
- witnesses targeting a contract are not added for this. Coherence would need an overlap rule against
  class witnesses, and for `Set` and `Map` cross-implementation equality is not well defined because
  key equivalence is per instance. `==` on `List<T>` is a language proposal of its own; this
  proposal's split — cross-implementation for `List`, per implementation for `Set` and `Map` — matches
  what the language can express.

### Additional changes from review

- **`Sized`.** Added as described under [Size](#size), so contract-typed values retain constant-time
  size without forcing every conformer to be sized.
- **`isEmpty()`.** The default stops after the first element rather than deriving from `count()`, so an
  unbounded `Iterable` is never traversed to answer it; implementations with constant-time size
  override it.
- **Map iteration.** Yields one `Pair` per mapping, which allocates; that cost is documented, and
  `keyIterator` is the allocation-free path for hot loops.
- **`keyIterator` is read-only.** `Iterator` exposes only `next`, so removing through a key iterator is
  not part of the contract; removal goes through `KeyedSink.remove`.
- **`PositionalEditor` return shapes.** `insert` reports whether the index was a valid insertion point
  with `Boolean`, while `removeAt` and `replaceAt` report the element they removed or replaced with
  `Option<T>`. The asymmetry is deliberate and is documented on the capability.
- **Decoding.** Stated as "a compatible construction witness or an explicit codec", including the
  `Hashable`/`Eq` evidence a `Map`-typed field needs before `HashMap` can be its default.
- **Re-traversal.** The invariant is documented on `Iterable.iterator()`: each call returns an
  independent iterator, and a one-shot source is not an `Iterable`.

## Decision

Accepted on 2026-11-03, after review of the design document and of the language constraints the
proposal relies on. The direction is unchanged: `List`, `Map`, and `Set` become contracts, the
existing classes are renamed, mutation stays in capability contracts, `Iterable` gains
row-polymorphic terminal defaults, and `Stream` remains a final class with lazy operators over pure
callbacks.

The resolutions of the former open questions are recorded under
[Review resolutions](#review-resolutions). In summary: iteration stays pure with failures as data;
`Functor` stays pure-only; rows in type-argument position are out of scope and cannot carry an
effect-tracking stream on their own; no generic parameters are added to constructors or class statics;
map-backed sets and ordered maps are implementation classes (`MapBackedSet`; `SortedMap` with a
single `TreeMap`) rather than contracts, with only `MapBackedSet` in this proposal's scope; and list
equality is expressed by generic functions with element evidence
rather than by a contract-wide `Eq`. The review also added the `Sized` capability and settled the
smaller points listed under [Additional changes from review](#additional-changes-from-review).

Acceptance approves the design direction; implementation remains subject to release planning, and the
release state in the [ZEP tracker](./ZEP.md) is unchanged.
