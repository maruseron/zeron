## Abstract

This proposal defines a compiler-wide bytecode quality program for Zeron. It reduces generated
class count, class size, allocation, and dispatch overhead without changing Zeron source semantics.
The initial scope covers `Unit` lowering, direct-carrier lowering for existing newtypes,
lambda and function-shape emission, inlining of statically known contract evidence, direct
equality and hashing codegen, top-level value initialization, and selected local peepholes.

The proposal is deliberately separate from [ZEP-0096](./ZEP-0096.md). This ZEP improves emission
without introducing primitive-specialized representations or specialized entry points; the changes
that do affect class descriptors are called out individually. ZEP-0096 introduces
primitive-specialized representations and entry points, which are ABI-changing by nature.

## Motivation

The class-file quality inventory measured a small program at 320 emitted class files and about
381 KB, with 84% of the bytes coming from the standard library. Selecting the compiled standard
library by default and emitting runtime support on demand reduced the per-program output
substantially, but the remaining generated code still contains avoidable indirection:

- `Unit`-returning methods return a reference to a singleton, and call sites load it and `pop` it.
- Newtypes allocate a wrapper object for every construction and call a getter for every
  extraction, even when the value never escapes.
- Every non-`Object` function shape receives an `Object`-shaped super-interface and a boxing bridge.
- Lambda bodies are hoisted into the application entry holder, which forces synthetic public access
  bridges and couples library bytecode to the application class.
- Generic contract calls with statically known type arguments still box arguments and results and
  dispatch through `MethodHandle.invoke`.
- Derived equality and hashing use `MethodHandle.invoke` per component.
- Top-level values perform an initialization check on every read.
- Several local patterns emit redundant bounds checks, casts, string-concatenation call sites, and
  `Object[]` carriers.

These costs are individually small but pervasive. They affect startup, code size, stack traces, and
the ability of the JIT to inline hot paths. Some fixes are local peepholes; others change class
descriptors, generated interfaces, or compiled-library contracts. The latter need a recorded design
so that separate compilation, versioning, and Java interop remain well defined.

## Goals

- Establish a repeatable bytecode quality baseline and measurable acceptance gates.
- Remove avoidable `Unit` reference traffic at returns and expression statements.
- Lower existing newtypes to their carriers when the wrapper is not observable.
- Emit lambda bodies in their owning unit and stop generating unnecessary shapes and adapters.
- Inline contract evidence when the concrete witness is statically known.
- Generate direct equality and hashing code for statically known component types.
- Remove redundant top-level initialization checks and selected local inefficiencies.
- Preserve source behavior, nullability, effects, contract resolution, and separate compilation.
- Define which changes require a class-file ABI or library-index version boundary.

## Non-goals

- Primitive-specialized arrays, monomorphized generic entry points, or primitive-backed standard
  library collections; these are owned by [ZEP-0096](./ZEP-0096.md).
- Generic or nominal newtype representations and guarded-newtype semantics from
  [ZEP-0070](./ZEP-0070.md).
- Adding, removing, or changing source syntax, contracts, effects, or nullability rules.
- Changing Java type mappings, Java generic interop, or host-binding discovery.
- Replacing the compiled-standard-library default or the on-demand runtime-support policy.
- Guaranteeing a particular JIT outcome, instruction count, or class-file size for every program.
- Removing debug metadata, source maps, or useful stack-trace information.
- General stream fusion, generator functions, or a new iterator protocol. Those change the
  standard-library protocol and deserve their own proposal.

## Proposal

### 1. Quality baseline and gates

Define a small, versioned bytecode corpus that exercises:

- a minimal program;
- generic numeric code using `Numeric`, `Integral`, and `Comparable` bounds;
- hash-based and list-based collections instantiated with primitives and references;
- data classes with derived `Eq` and `Hashable`;
- lambdas, trailing lambdas, and callbacks crossing erased boundaries;
- newtypes, top-level values, arrays, `for` expressions, and resource management.

For each program, record class count, total bytes, method count, and selected instruction counts:
`Integer.valueOf`, `Long.valueOf`, `Double.valueOf`, `MethodHandle.invoke`, `checkcast`,
`Objects.checkIndex`, `pop`, and `getstatic Unit.INSTANCE`.

Quality gates:

- all existing tests continue to pass with identical observable behavior;
- no corpus program regresses beyond an agreed threshold in bytes or class count;
- the direct-evidence path contains no boxing or `MethodHandle.invoke` for statically known
  witnesses;
- emitted output is deterministic for identical inputs and compiler versions.

Thresholds are recorded with the harness rather than hard-coded in this proposal. They may be
tightened as stages land.

### 2. `Unit` at JVM boundaries

`Unit` should not force a reference value through every return and statement boundary.

- A declaration whose result type is `Unit` emits a `void`-returning method where the value cannot
  be observed.
- A `Unit`-valued expression in statement position emits no result and no `pop`.
- The `Unit` singleton remains only where the type survives erasure: generic type arguments,
  `Array<Unit>`, `Unit?`, evidence positions, host interop that expects an object, and any
  reflective or serialized position that requires a material value.
- Function shapes distinguish "returns no value" from "returns `Object`". A shape that returns
  `Unit` uses a `void` return rather than a reference to the singleton.
- Adapters bridge `Unit` and `void` at boundaries where one side expects the other. Adapter
  selection is part of the shape identity, not a runtime convention.

The library index and API schema must distinguish a `void` result from a `Unit` result. If the
current index cannot represent the difference, this change requires an
`API_INDEX_SCHEMA_VERSION` and `STANDARD_LIBRARY_API_VERSION` review under
[ZEP-0012](./ZEP-0012.md).

### 3. Direct-carrier newtypes

Existing newtypes over the currently supported representations (`Int`, `Float`, `Boolean`, and
`String`) may lower directly to their carrier type when the wrapper is not observable. Additional
representations admitted by [ZEP-0070](./ZEP-0070.md) are outside this proposal's direct-carrier
guarantee.

- `.new`, `.tryNew`, and `.value` become no-ops at the carrier boundary. A `where` validator still
  runs at construction; it is not skipped by the optimization.
- The wrapper class, allocation, field, and getter are omitted when no boundary requires an object.
- A wrapper remains when the value crosses a generic type argument, an `Array<T>` boundary, a
  nullable reference position, contract evidence, host interop, or any position where the runtime
  class is part of the contract.
- Nominal identity remains a compile-time property. Diagnostics, overload resolution, and
  assignability continue to distinguish the newtype from its carrier.
- Library metadata records whether a newtype is represented by its carrier or by a wrapper, so
  consumers do not infer representation from generated class files.
- Generic and nominal newtypes remain governed by [ZEP-0070](./ZEP-0070.md); this proposal does not
  promise direct-carrier lowering for them.

The change must not silently make a newtype interchangeable with its carrier in Java interop or
reflection. If a newtype class is no longer emitted in some cases, that is a documented
representation rule, not a reflection guarantee.

### 4. Lambdas, adapters, and function shapes

- Emit each lambda body in the unit or class where it is written, rather than in the application
  entry holder. This removes the cross-package synthetic access bridges and stops `main.class` from
  absorbing standard-library lambda bodies.
- Emit `Object`-shaped super-interfaces and boxing bridges only when a value actually flows through
  an `Object`-typed callback position. A typed shape does not receive an `Object` shape by default.
- Canonicalize adapters by `(sourceShape, targetShape)` and reuse an existing adapter when an
  equivalent erased conversion is available. Consider moving canonical adapters and common shapes
  into a shared runtime artifact so separate compilations do not each generate them.
- Shorten shape interface names. A 16-hex prefix of the existing content digest is sufficient for
  practical collision resistance, or a stable numeric identifier with a manifest may be used.
  Collision detection and deterministic naming remain required.
- Keep shape identity stable across compilations. Changing a shape name is a class-file ABI change
  for compiled libraries and must be versioned accordingly.

### 5. Evidence inlining

When the resolver knows the concrete type arguments at a call site, the compiler should call the
selected witness directly instead of routing through the erased generic path.

- A concrete `Int` call to a witness method emits the primitive witness signature directly:
  no `Integer.valueOf`, no `MethodHandle.invoke`, and no `checkcast Integer`.
- The erased generic entry point remains available for callers whose type arguments are not
  statically known, including separately compiled libraries.
- Direct inlining does not change the erased signature or the source-level contract rules. This is
  the part of evidence optimization that [ZEP-0096](./ZEP-0096.md) does not own.
- When a generic method has an erased stub that throws `UnsupportedOperationException` and the
  resolver can prove the stub is unreachable, omit it. Otherwise keep it and mark it clearly.
- Derived `Eq` and `Hashable` helpers emit direct comparisons and hash operations for statically
  known component types: primitive comparison, `Float.compare`/`Double.compare`, `Objects.equals`,
  and direct hash helpers. `MethodHandle` remains only for unresolved type parameters.

The optimization must not change evaluation order, exceptions, null checks, or contract selection.

### 6. Top-level values and local peepholes

- Mark immutable top-level values `static final` where possible. Emit a `ConstantValue` attribute
  for compile-time constants and read the constant directly or inline it at use sites.
- Remove the empty `$zeron$initialize` call and the per-read initialized boolean for values whose
  initialization is guaranteed by class initialization. Use an initialization-on-demand holder or
  a single checked initialization for genuinely lazy values.
- Initialize only top-level values reachable from the program rather than every standard-library
  global in the entry `<clinit>`.
- Remove redundant array bounds checks when the following `aaload`/`aastore` already performs the
  check, unless Zeron's error type or message requires the explicit call.
- Flatten a left-associative string `+` chain into one `StringConcatFactory` call site and one
  recipe.
- Skip `checkcast` and `Objects.requireNonNull` when the static source type already guarantees the
  target.
- Replace legacy extractor `Object[]` results with a typed carrier, out-parameters, or direct
  getters.
- Keep resources in locals or a generated holder for a statically known `using` count instead of
  allocating a resource array.
- Review property compound-assignment lowering for single `dup_x1`/`dup2_x1` sequences.

## Compatibility and impact

Source compatibility is preserved. Observable behavior, including exceptions, null handling,
evaluation order, and contract selection, must not change.

Class-file compatibility changes in several places:

- `Unit`-returning methods and function shapes may change descriptors.
- Newtypes may no longer emit a wrapper class.
- Function-shape names and adapter names may change.
- Top-level fields may become `final` and may carry `ConstantValue`.
- Evidence call sites may switch from `MethodHandle.invoke` to direct witness calls.

These changes require a coordinated library-index and standard-library API version review under
[ZEP-0012](./ZEP-0012.md). Compiled libraries built before the change either continue to work through
adapters and erased entry points or must be rebuilt; the chosen rule must be stated in the release
notes. Stack traces and class names may change. Zeron does not currently promise a reflection
contract over generated class names, and this proposal does not add one.

Serialization formats and hash values are unaffected. Java interop keeps its existing mappings and
gains explicit `Unit`/`void` and newtype/carrier adapters where needed.

## Alternatives

- **Leave these costs to the JIT** — avoids compiler complexity, but the JIT cannot remove
  `MethodHandle` dispatch, wrapper allocations that escape, or unnecessary class generation.
- **Land only local peepholes** — low risk, but leaves the largest costs in shape generation,
  evidence dispatch, and newtype allocation.
- **Create one ZEP per item** — gives precise decisions, but fragments a single quality program and
  makes it hard to reason about the combined ABI impact.
- **Put all representation changes in ZEP-0096** — mixes two different compatibility questions:
  specialized representations versus ordinary emission quality.
- **Keep the `Unit` singleton everywhere** — simple and already correct, but preserves pervasive
  reference traffic and prevents direct `void` interop.

## Implementation and validation

Implement in independently shippable stages:

1. Local peepholes, top-level initialization cleanup, and direct derived equality/hashing.
2. Evidence inlining for statically known witnesses without changing erased signatures.
3. Lambda placement, demand-driven `Object` shapes, canonical adapters, and shortened shape names.
4. `Unit` as `void` at boundaries, with adapters and index support.
5. Direct-carrier newtypes, with library metadata and interop adapters.

Each stage must include:

- unit and integration tests for source-level behavior;
- `javap` assertions that selected boxing, `MethodHandle.invoke`, `pop`, and `checkcast` sequences
  are absent where expected;
- cross-library tests that compile a consumer against a separately built provider;
- determinism tests that compile the same input twice and compare output;
- corpus measurements recorded in the quality harness.

## Open questions

- How far should `Unit`-as-`void` extend across compiled-library boundaries: adapters only, or a
  new library ABI in which `void` is the canonical representation?
- Should newtype direct-carrier lowering be the default, or opt-in for a release while
  compiled libraries and tooling catch up?
- Should a direct-carrier newtype emit any class file for diagnostics, reflection, or tooling?
- Is a 16-hex shape prefix acceptable, or should shape identity use a stable numeric identifier and
  manifest?
- Should any stage be guarded by a compiler flag or a project setting during migration?
- Which quality thresholds should become release gates rather than advisory measurements?
