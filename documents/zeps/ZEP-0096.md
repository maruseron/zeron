## Abstract

This proposal introduces primitive specialization for Zeron generic code. It covers
primitive-specialized arrays, specialized entry points for generic functions instantiated with
primitive type arguments, primitive-backed storage for hot standard-library collections, and a
compact representation for contract evidence.

The goal is to remove per-element and per-call boxing and `MethodHandle` dispatch from generic code
whose type arguments are known to be primitives, while preserving erasure, separate compilation,
and source-level semantics. The ordinary erased entry points remain available for callers that
cannot use a specialized form.

## Motivation

Zeron represents `Int`, `Long`, `Float`, `Byte`, `Boolean`, and `Char` with JVM primitives. Direct
arithmetic and direct witness calls are already primitive. The cost appears when a value crosses a
generic boundary:

- `Array<Int>` erases to `Object[]`, so array literals box every element, reads unbox and cast every
  element, and writes box every value.
- A generic function such as `addGeneric<T: Numeric<T>>(a: T, b: T): T` erases its arguments and
  result to `Object`. Each call boxes `Int`, passes several `MethodHandle` constants, invokes
  through a signature-polymorphic call site, casts the result, and unboxes it.
- `Integral<T>` currently expands to a large evidence list because it requires `Numeric`,
  `Hashable`, and `Comparable`, and those requirements pull in further evidence.
- `HashMap<Int, V>` boxes every key on `put` and `get` and dispatches hashing and equality through
  evidence.
- `ArrayList<Int>`, `Stream<Int>`, and `Step<Int>` box at element boundaries.

The cost is not limited to numeric helpers. The standard library is written generically, so
collection, sorting, and hashing code inherits it. The class-file quality inventory measured the
boxing and evidence signatures directly.

[ZEP-0095](./ZEP-0095.md) removes boxing when the compiler can inline a statically known witness
without changing the erased generic ABI. This proposal goes further: it defines specialized
representations and entry points, which are ABI changes and need an explicit design.

## Goals

- Give intrinsic arrays a primitive representation when their element type has a primitive JVM
  carrier.
- Emit specialized entry points for generic functions called with primitive type arguments, while
  retaining the erased entry point.
- Use primitive-backed storage for the hottest standard-library collection specializations.
- Replace the long evidence parameter lists with a compact, well-defined protocol.
- Preserve source semantics, contract resolution, nullability, mutability, and effect behavior.
- Define code-size, compilation-time, and ABI rules for specialization.
- Keep separate compilation and compiled libraries working across the change.

## Non-goals

- General reified generics or removing JVM erasure for all types.
- Specializing every contract, function, or type-argument combination.
- Changing the numeric hierarchy, newtype semantics, or Java array mapping.
- Guaranteeing that no value is ever boxed at any boundary, including dynamic dispatch and host
  interop.
- Replacing `Array<T>` with a distinct source-level family of primitive array types.
- Changing the JVM, the JIT, or the invocation mechanism outside generated code.
- Adding source syntax for specialization.
- General value-type support in the style of Project Valhalla.

## Proposal

### 1. Specialization domain

The primitive carriers are the existing types with JVM primitive representations:

| Zeron type | JVM carrier |
| --- | --- |
| `Int` | `int` |
| `Long` | `long` |
| `Float` | `double` |
| `Byte` | `byte` |
| `Boolean` | `boolean` |
| `Char` | `int` |

Only exact primitive type arguments are specialized. Nullable primitives such as `Int?` remain
reference values. Reference types, newtypes, and nominal types are not specialized by this
proposal.

`Int` and `Char` share the JVM `int` carrier. The design must either distinguish them with a
wrapper at boundaries where runtime identity matters or accept erased identity and state that
limitation explicitly. This is an open question below.

### 2. Primitive-specialized arrays

`Array<T>` uses a primitive array representation when `T` is a primitive carrier:

- `Array<Int>` uses `int[]`.
- `Array<Long>` uses `long[]`.
- `Array<Float>` uses `double[]`.
- `Array<Byte>` uses `byte[]`.
- `Array<Boolean>` uses `boolean[]`.
- `Array<Char>` uses `int[]`, subject to the `Int`/`Char` identity question.

Rules:

- Array literals emit primitive stores without `valueOf`.
- Reads emit primitive loads without `checkcast` or unboxing.
- Writes emit primitive stores without boxing.
- `for` loops over primitive arrays keep the element in a primitive local.
- `size`, indexing, slicing, and copying use the primitive representation directly.
- Nullable elements and reference elements keep the erased `Object[]` representation.
- Runtime type checks and casts distinguish array element kinds through the array descriptor.
- Java interop maps specialized arrays to the corresponding JVM primitive array where the host
  signature expects one. `ByteArray` remains the direct `byte[]` representation.
- Generic code that manipulates `Array<T>` through an unresolved type parameter continues to use
  the erased representation unless a specialized entry point is selected.

This changes array descriptors and therefore the class-file and library ABI. It does not change the
source spelling `Array<T>`.

### 3. Specialized generic entry points

For a generic function or method `f<T>(...)`, the compiler may emit a specialized entry point for a
primitive instantiation, for example:

```text
f$Int(int, ...)int
f$Long(long, ...)long
f$Float(double, ...)double
```

Rules:

- The erased entry point remains available for dynamic callers and for compiled libraries that do
  not request specialization.
- Specialization is driven by calls whose type arguments are statically known primitive types.
  Unresolved type parameters do not produce a specialized variant.
- A specialized variant uses primitive parameter and result descriptors and direct witness calls.
  It does not box arguments or results merely to enter the function.
- Variant names are stable, collision-free, and recorded in the library index so consumers can
  discover and call them.
- A consumer compiling against a library may call a specialized entry point when the index
  advertises it. Otherwise it uses the erased entry point. Correctness must not depend on the
  specialized form being present.
- Specialization is applied only to reachable calls, subject to a code-size policy. Nested generic
  instantiations must not cause unbounded variant explosion. Identical instantiations are
  deduplicated.
- Specialized variants preserve evaluation order, exceptions, null checks, and contract selection
  exactly as the erased entry point does.

The proposal deliberately leaves open whether specialization clones a function body per
instantiation, emits a template that is instantiated at link time, or uses a hybrid. The observable
requirements are primitive signatures, direct evidence, and a working erased fallback.

### 4. Compact evidence protocol

Erased generic entry points currently pass one `MethodHandle` per required operation, which can
reach sixteen parameters for contracts such as `Integral<T>`. The proposal replaces that shape with
one of:

- a single evidence dictionary object holding the required operations;
- a bootstrapped `invokedynamic` call site that resolves the operations once per call site; or
- a hybrid that uses a dictionary for cross-library calls and direct calls for specialized code.

Requirements:

- Evidence selection remains static and follows the existing coherence and orphan rules. No
  runtime type lookup or dynamic contract search is introduced.
- A concrete witness is still selected at compile time. The protocol changes how it is passed, not
  how it is chosen.
- Specialized variants call witness methods directly where possible; the compact protocol is for
  erased and cross-library paths.
- Descriptor size, constant-pool size, and initialization cost are measured. A dictionary object
  must not simply trade many `MethodHandle` parameters for a per-call allocation.

This section is the ABI-changing complement to the statically known evidence inlining in
[ZEP-0095](./ZEP-0095.md).

### 5. Standard-library specialization

The hottest standard-library abstractions should use primitive-backed storage where the public
contract allows it:

- `ArrayList<Int>`, `ArrayList<Long>`, and other primitive element instantiations.
- `HashMap<Int, V>`, `HashMap<Long, V>`, and primitive keys, using direct hashing and equality.
- `Stream<Int>` and `Step<Int>` element boundaries.
- Other collections identified by measurement, subject to the collection contracts in
  [ZEP-0094](./ZEP-0094.md).

Rules:

- Public source APIs remain unchanged. `ArrayList<Int>` is still the same source-level type.
- The implementation may select a specialized internal representation based on the type argument,
  or use a hidden specialized class behind the public contract.
- Iteration order, equality, hashing, ordering, and mutation semantics are unchanged.
- Hashing uses the 64-bit result if [ZEP-0084](./ZEP-0084.md) is accepted.
- A non-specialized instantiation keeps the erased representation. A specialized instantiation
  must not change behavior when it falls back to the erased path.

### 6. Code-size and compilation policy

Primitive specialization can grow output and compilation time. The compiler applies:

- reachability-based specialization rather than specializing every declaration;
- a per-declaration variant budget, with a documented default and a way to disable specialization
  for a build;
- deduplication of identical primitive instantiations;
- deterministic naming and ordering, so output remains reproducible;
- measurement of class count, bytes, and compile time in the quality harness from
  [ZEP-0095](./ZEP-0095.md).

The exact budget is an implementation policy, not a source-language guarantee.

## Compatibility and impact

Source compatibility is preserved. Observable behavior, including exceptions, null handling,
evaluation order, and contract selection, must not change.

Class-file and library impact:

- `Array<Int>` and other primitive arrays have new descriptors.
- Specialized entry points add methods and library-index records.
- The evidence protocol changes erased generic descriptors.
- Java interop sees primitive arrays and primitive descriptors where the host signature permits it.
- Compiled libraries must be rebuilt for the new representation, or consumers must fall back to
  the erased entry points. The release notes must state which compatibility rule applies.

Versioning follows [ZEP-0012](./ZEP-0012.md). A change to the library index, array descriptors, or
evidence encoding requires an `API_INDEX_SCHEMA_VERSION` and `STANDARD_LIBRARY_API_VERSION` review.
Because both values may be bumped only once per release cycle, all required schema changes should be
consolidated before the release.

Determinism and reproducible builds remain requirements. Specialization must not depend on hash-map
iteration order, call discovery order, or wall-clock state.

## Alternatives

- **Rely on JIT escape analysis and boxing elimination** — avoids compiler work, but cannot remove
  boxed values that escape into arrays, collections, or compiled-library boundaries, and does not
  remove `MethodHandle` dispatch.
- **Only specialize primitive arrays** — removes the largest per-element cost, but leaves generic
  calls and collections boxed.
- **Only inline statically known evidence (ZEP-0095)** — removes many concrete-call costs without
  an ABI change, but does not help generic library code or primitive array storage.
- **Only specialize the standard library** — improves common cases, but leaves user generic code
  boxed and introduces an uneven optimization boundary.
- **Adopt JVM value types or reified generics** — potentially cleaner, but depends on platform
  features and a much larger language and ABI change.
- **Generate a fully monomorphized program** — removes erasure costs, but conflicts with separate
  compilation and code-size goals.

## Implementation and validation

Implement in stages:

1. **Primitive arrays.** Add primitive array descriptors, lowering, runtime checks, Java interop,
   and library-index encoding. Validate `Array<Int>`, `Array<Long>`, `Array<Float>`, `Array<Byte>`,
   `Array<Boolean>`, and `Array<Char>`, plus nullable and reference elements.
2. **Specialized entry points.** Emit primitive variants for reachable calls, retain erased
   fallbacks, and encode availability in the library index. Validate separate compilation in both
   directions.
3. **Standard-library storage.** Specialize the measured collection and stream instantiations.
   Validate behavior against the erased implementations.
4. **Evidence protocol.** Introduce the compact representation, migrate erased entry points, and
   measure descriptor, constant-pool, and allocation effects.

Validation must include:

- source-level behavior tests for every specialized type and collection;
- `javap` assertions that specialized paths contain no `Integer.valueOf`, `Long.valueOf`,
  `Double.valueOf`, `checkcast` to a wrapper, or `MethodHandle.invoke`;
- cross-library tests in which a provider is compiled with specialization and a consumer uses both
  the specialized and erased paths;
- runtime type-test and cast tests for primitive arrays;
- Java interop tests for primitive array parameters, results, and fields;
- code-size and compilation-time measurements against the ZEP-0095 corpus;
- determinism tests for repeated builds.

## Open questions

- Should `Array<Int>` and `Array<Char>` be distinguishable at runtime, or is sharing `int[]`
  acceptable if source-level type checking keeps them apart?
- Should specialized entry points be emitted for declarations or generated at call sites, and how
  does that interact with separate compilation and inlining?
- What is the per-declaration variant budget, and should projects be able to tune or disable it?
- Should the compact evidence protocol use a dictionary object, `invokedynamic`, or both?
- Which standard-library collections are specialized first, and is specialization selected by the
  type argument or by an explicit implementation detail?
- Does a primitive-specialized array participate in generic-aware runtime type tests from
  [ZEP-0053](./ZEP-0053.md), and with what exact identity?
- Should the compiler expose specialized descriptors to Java callers, or keep them behind an
  adapter boundary?
- How should specialization interact with newtype direct-carrier lowering from
  [ZEP-0095](./ZEP-0095.md) and generic newtypes from [ZEP-0070](./ZEP-0070.md)?

## Decision

Draft created 2026-11-05. The proposal defines primitive arrays, specialized entry points,
primitive-backed standard-library storage, and a compact evidence protocol. The specialization
trigger, variant budget, array identity for `Int`/`Char`, and evidence encoding remain open.
