## Abstract

[ZEP-0031](./ZEP-0031.md) defines a closed set of annotation targets, none of which covers a
field-mapping clause of a [ZEP-0079](./ZEP-0079.md) `model` declaration. This proposal adds one
target, `MAPPING`, so that metadata about how a property maps to an external representation can be
attached to the mapping itself rather than to the mapped type.

This proposal defines only the target: where `MAPPING` annotations may be written, how they are
validated, and how they are recorded. It does not define how they are read; that belongs to
[ZEP-0091](./ZEP-0091.md).

## Motivation

A model maps properties of a type to external fields without modifying the type. Some of the
metadata a consumer needs is specific to that mapping and not to the type: a primary key in one
persistence model may be an ordinary column in another, and a generated value in one representation
is irrelevant to another.

ZEP-0079 therefore does not accept annotations on clauses in its first version, and consumers
capture singular, structural metadata as typed properties of their own contracts (for example a
`primaryKey: PropertyRef<T, K>`). That works, but it cannot express per-field flags (such as a
generated value) without a parallel, hand-maintained vocabulary, and nothing checks that a
referenced property is also mapped.

The existing targets do not fit. `FIELD`, `PROPERTY`, and `DATA_COMPONENT` denote declarations of
the mapped type. Applying annotations written for those targets to a model's clause would
conflate the type's declaration with one representation of it, and would invite reading the type's
annotations through the model, which would reintroduce the coupling models exist to avoid.

## Goals

- Allow annotations on field-mapping clauses of a `model` declaration, through an explicit target.
- Keep applicability explicit: an annotation is valid on a clause only if its declaration lists
  `MAPPING`.
- Record clause annotations in the library index as structured values, so they survive separate
  compilation.
- Keep the change additive with respect to ZEP-0031 and ZEP-0079.

## Non-goals

- Defining how clause annotations are read or exposed to consumers
  ([ZEP-0091](./ZEP-0091.md)).
- Defining any particular annotation or its meaning (primary key, generated value, and so on).
- Annotations on parent-contract assignment clauses (`property = value`).
- Changing annotation declaration or application rules of ZEP-0031 other than adding the target.
- Annotations on the model declaration itself; the `CLASS` and related targets are not changed.
- Reading the annotations of the mapped property of the target type through a model.

## Proposal

### The `MAPPING` target

`MAPPING` is added to the target list that annotation declarations may use. It denotes a
**field-mapping clause** (`property -> "external"`) in a `model` declaration.

```zeron
// illustrative
public annotation PrimaryKey on FIELD, PROPERTY, DATA_COMPONENT, MAPPING;
public annotation Generated(strategy: String = "default")
    on FIELD, PROPERTY, DATA_COMPONENT, MAPPING;
public annotation Column(nullable: Boolean = true) on MAPPING;
```

An annotation declared before this proposal does not gain `MAPPING` implicitly. Its author adds
the target explicitly; broadening a target set is a compatible change under ZEP-0031.

### Application

An application precedes the clause it annotates, using the same `@Name` syntax and argument rules
as ZEP-0031:

```zeron
// illustrative
public model UserSql is SqlModel<User> {
    tableName = "users";

    @PrimaryKey @Generated(strategy = "identity")
    id -> "id";

    @Column(nullable = false)
    name -> "name";
}
```

Rules:

- A clause may carry any number of annotations with distinct identities. An annotation is not
  repeatable (ZEP-0031): two applications of the same annotation on one clause are an error.
  Source order is preserved in source metadata.
- Annotations are valid only on field-mapping clauses. An annotation on an assignment clause
  (`tableName = "users"`) is an error.
- The annotation must resolve and must list `MAPPING` among its targets. Applying an annotation
  that does not list it is an error naming the annotation and the clause.
- Arguments are the compile-time constants of ZEP-0031, validated against the annotation's
  declared parameters.
- Tooling-only annotations are allowed, and remain inert unless a compiler feature or external
  tool interprets them.

### Visibility of annotations

Any public annotation that lists `MAPPING` may be applied on a clause, regardless of the library
that declares it. A public model may use only public annotations, so separately compiled
consumers can resolve them (ZEP-0031).

### Diagnostics

A rejected application is reported at the annotation's source location, naming the annotation,
the model, and the mapped property as written in the clause. The external name is not required.

### Annotated element identity

The annotated element is identified by the model declaration together with the `PropertyId` of the
mapped property ([ZEP-0093](./ZEP-0093.md)). That pair is unique, because ZEP-0079 rejects
duplicate mappings of the same source property. It is the anchor used in diagnostics, in the
library index, and by consumption mechanisms such as ZEP-0091.

### Interaction with ZEP-0079

- Annotations on a clause do not change the clause's meaning, the generated `Model<T>` descriptor,
  `fields`, `field`, or `fieldOf`. They are metadata only.
- `Field.annotations`, reserved by ZEP-0079, may be defined once ZEP-0091 specifies consumption;
  this proposal does not define it.
- A model does not expose the annotations of the mapped property on the target type. Those remain
  with the target's declaration.

- A future `total` modifier ([ZEP-0079](./ZEP-0079.md)) defines for itself any target it needs
  for declaring omitted properties; none is reserved here.

### Library index

Public models are exported with their mappings (ZEP-0079). Each exported mapping additionally
records its clause annotations as annotation identity plus structured, typed arguments, following
the representation ZEP-0031 uses for other declarations. Applications on non-public models remain
available to source-mode analysis and are not exported. An annotation used on a public model must
itself be public, so separately compiled consumers can resolve its identity and schema.

## Compatibility and impact

The change is additive: no existing declaration or application changes meaning. It touches
parsing of model bodies, annotation target validation, declaration metadata for model clauses, and
the library index.

The target set of an annotation declaration is part of its serialized metadata. Adding a target
value and per-mapping annotation records changes the API-index representation, so it is governed
by `API_INDEX_SCHEMA_VERSION` and the artifact compatibility policy. The change follows the existing consolidation policy: it joins the current schema revision if
that revision is unreleased when this proposal is implemented, and otherwise takes the next
revision. No separate versioning is defined, and the implementation notes record which applies.

ZEP-0031 is implemented and finalized and is not edited by this proposal; `MAPPING` extends its
target list by a separate, additive decision.

## Alternatives

- **Reuse `FIELD`, `PROPERTY`, or `DATA_COMPONENT` for clauses.** Rejected: a clause is not a
  declaration of the target type, and conflating them blurs which metadata belongs to the type and
  which to a representation.
- **Annotate the mapped property on the target type and read it through the model.** Rejected: it
  couples the type to one representation and breaks multiple models for one type.
- **Typed properties on the consumer's contract only** (the ZEP-0079 pattern). Works today, but
  needs a hand-maintained vocabulary for each flag and cannot be checked against the mapped
  properties.
- **A dedicated clause syntax for metadata** (for example `id -> "id" with { ... }`). Rejected:
  duplicates the annotation system and its validation.

## Implementation and validation

1. Add `MAPPING` to the target enumeration and to annotation-declaration parsing.
2. Parse annotation applications before field-mapping clauses in model bodies; reject them on
   assignment clauses.
3. Validate target applicability, argument constants, and duplicate identities per clause,
   reusing the ZEP-0031 machinery.
4. Preserve clause annotations in declaration metadata, keyed by model and `PropertyId`.
5. Serialize them in the library index for public models and restore them for separately
   compiled consumers.
6. Test: valid application; annotation missing the `MAPPING` target; application on an assignment
   clause; duplicate application on one clause; private model not exported; public model
   annotation must be public; metadata survives separate compilation; the generated `Model<T>`
   behavior is unchanged with and without annotations; a tooling-only annotation stays inert.

## Decision

Accepted 2026-11-05. Add `MAPPING` as an annotation target denoting a field-mapping clause of a
`model` declaration. Require annotation declarations to list it explicitly, and allow it only on
field-mapping clauses, not on assignment clauses or the model itself. Allow any public annotation
that lists the target. Treat clause annotations as metadata that does not alter the generated
`Model<T>` descriptor. Identify the annotated element by the model and the `PropertyId` of the
mapped property, and export clause annotations in the library index for public models under the
existing schema-version policy. How clause annotations are read is left to a follow-up to
ZEP-0091. ZEP-0031 is not edited.

Release candidacy remains separate from proposal status and is tracked only in
[ZEP.md](./ZEP.md); no release bundle is selected here.
