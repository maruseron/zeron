## Abstract

[ZEP-0031](./ZEP-0031.md) defines annotation targets for classes (including data classes and
their components), contracts, functions, methods, constructors, fields, properties, and
parameters. It defines none for native products, native sums, or newtypes, so these declarations,
their components, and their cases cannot carry annotations.

This proposal adds targets for them: the declarations themselves (`PRODUCT`, `SUM`, `NEWTYPE`),
the components of a product (`PRODUCT_COMPONENT`), and the cases of a sum (`SUM_CASE`). It defines
where these annotations may be written, how they are validated, and how they are recorded. It does
not define how they are read ([ZEP-0091](./ZEP-0091.md)) or any particular annotation.

## Motivation

[ZEP-0068](./ZEP-0068.md) requires that record fields and sum cases can have stable logical names
and legacy aliases, and that a sum can declare a representation for unknown cases.
[ZEP-0092](./ZEP-0092.md) expresses names and aliases as an annotation. That annotation can be
applied today only to the components of transparent data classes, through `DATA_COMPONENT`.
Derived products and sums, which are native declarations and not classes, have no place to carry
it, so ZEP-0068's requirements are unmet for them.

The gap is not specific to serialization. Any library or compiler feature that interprets
metadata on these declarations (validation, persistence, schemas) hits the same limit, and
ZEP-0031's existing targets cannot be stretched to cover them without blurring what they denote:
`CLASS` is for classes, and `DATA_COMPONENT` is for data-class components.

## Goals

- Allow annotations on declarations of native products, native sums, and newtypes.
- Allow annotations on the components of a native product and the cases of a native sum.
- Keep applicability explicit: an annotation is valid on one of these elements only if its
  declaration lists the corresponding target.
- Record these annotations in the library index as structured values, so they survive separate
  compilation.
- Keep the change additive with respect to ZEP-0031 and ZEP-0008.

## Non-goals

- Defining how these annotations are read or exposed to consumers
  ([ZEP-0091](./ZEP-0091.md)).
- Defining any particular annotation or its meaning (for example `SerialName`).
- Changing annotation declaration or application rules of ZEP-0031 other than adding targets.
- Changing the `deriving` clause of ZEP-0008. Annotations are not parameters of the clause, and an
  annotation does not request derivation.
- Changing the targets of classes and data classes (`CLASS`, `DATA_COMPONENT`).
- Annotating the underlying type of a newtype or type arguments.

## Proposal

### New targets

| Target | Denotes |
| ------ | ------- |
| `PRODUCT` | the declaration of a native product type |
| `PRODUCT_COMPONENT` | a declared component of a native product |
| `SUM` | the declaration of a native sum type |
| `SUM_CASE` | a declared case of a native sum |
| `NEWTYPE` | the declaration of a newtype |

These are added to the initial target list of ZEP-0031. The names follow its convention of
distinguishing a declaration kind (`CLASS`) from its members (`DATA_COMPONENT`).

```zeron
// illustrative
public annotation SerialName(name: String, aliases: Array<String> = [])
    on DATA_COMPONENT, PRODUCT_COMPONENT, SUM_CASE;
public annotation Versioned(version: Int) on PRODUCT, SUM, NEWTYPE;
```

An annotation declared before this proposal does not gain the new targets implicitly. Its author
adds them explicitly; broadening a target set is a compatible change under ZEP-0031.

### Application

An application precedes the element it annotates, using the same `@Name` syntax, argument rules,
and non-repetition rule as ZEP-0031. For components and cases, it precedes the name, as ZEP-0031
does for parameters. The concrete placement follows the declaration grammar of products, sums,
and newtypes (design document 14).

Rules:

- An annotation is valid on an element only if its declaration lists the corresponding target.
  Applying one that does not list it is an error naming the annotation and the element.
- An annotation is not repeatable: at most one application of a given annotation identity per
  element. Distinct annotations may be combined, and their source order is preserved in source
  metadata.
- Arguments are the compile-time constants of ZEP-0031.
- Tooling-only annotations are allowed and remain inert unless a compiler feature or external
  tool interprets them.
- Annotations on these elements do not change their meaning, structural `Eq` and `Hashable`
  evidence, derivation, or representation. A compiler feature that recognizes a specific
  annotation (such as serialization recognizing `SerialName`) interprets it as separately
  specified.

### Interaction with derivation

The `deriving` clause of ZEP-0008 remains a plain list of contracts. Metadata that influences a
derived behavior is expressed with annotations on the targets above and read by the deriving
feature through compile-time access ([ZEP-0091](./ZEP-0091.md) Direction B). This is the mechanism
[ZEP-0092](./ZEP-0092.md) uses for names and aliases of product components and sum cases.

### Library index

Public declarations of these kinds are exported with their annotation applications, in the same
way ZEP-0031 exports annotations on other public declarations. This includes the applications on
their components and cases. Applications on non-public declarations remain available to
source-mode analysis and are not exported. An annotation used on a public declaration must itself
be public.

### Annotated element identity

Each element is identified by its declaration's qualified name together with its component or
case name, which are part of the declared public shape. Renaming a component or case changes the
element's identity for annotation purposes, as it does for any other consumer of the shape.

## Compatibility and impact

The change is additive: no existing declaration or application changes meaning. It touches
parsing of product, sum, and newtype declarations, annotation target validation, declaration
metadata, and the library index.

The target set of an annotation declaration is part of its serialized metadata. Adding target
values and per-element annotation records changes the API-index representation, so it is governed
by `API_INDEX_SCHEMA_VERSION` and the artifact compatibility policy. It joins the current schema
revision if that revision is unreleased when this proposal is implemented, and otherwise takes the
next revision. No separate versioning is defined, and the implementation notes record which
applies.

ZEP-0031 is implemented and finalized and is not edited by this proposal; the new targets extend
its target list by a separate, additive decision.

## Alternatives

- **Reuse `CLASS` for products, sums, and newtypes.** Rejected: they are not classes, and
  conflating them with classes would blur what annotations written for `CLASS` mean.
- **Reuse `DATA_COMPONENT` for product components.** Rejected: ZEP-0031 defines it as a
  data-class component, and reinterpreting it would change an accepted definition. Distinct
  targets keep applicability explicit, and an annotation that applies to both lists both.
- **Express names and aliases inside the `deriving` clause.** Rejected: ZEP-0008 keeps the clause
  a plain list of contracts, and parameters would duplicate the annotation system.
- **Declaration targets only, without components and cases.** Rejected: the motivating use cases
  (field names, case tags, aliases) are on components and cases.

## Implementation and validation

1. Add the five targets to the target enumeration and to annotation-declaration parsing.
2. Parse annotation applications on product, sum, and newtype declarations, on product components,
   and on sum cases.
3. Validate target applicability, argument constants, and duplicate identities per element,
   reusing the ZEP-0031 machinery.
4. Preserve these annotations in declaration metadata, keyed by declaration and member name.
5. Serialize them in the library index for public declarations and restore them for separately
   compiled consumers.
6. Test: valid application on each target; annotation missing the target; duplicate application on
   one element; private declaration not exported; public declaration requires a public annotation;
   metadata survives separate compilation; `Eq`, `Hashable`, and derivation behavior are unchanged
   with and without annotations; a tooling-only annotation stays inert; classes and data classes
   keep their existing targets.

## Open questions

- Do the payload components of a sum case, if the language gives them names, need a target of
  their own, or are they covered by `SUM_CASE`? This depends on the declaration grammar for sum
  cases and is resolved when step 2 is specified against design document 14.
- How should diagnostics identify a rejected application on a component or case: by declaration
  and member name, with the source location of the application? This is expected to follow
  [ZEP-0097](./ZEP-0097.md) unless the grammar requires otherwise.
