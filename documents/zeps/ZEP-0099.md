## Abstract

Derivation registers a witness with a closed contract type, so a derived capability's effect row is
a constant chosen when the witness is created. Evidence selection then compares contract types
syntactically, requiring the rows to be equal. This proposal makes a derived witness able to declare
its own effect-row parameter — `Decode<Foo, E>` rather than `Decode<Foo, {ConstructorEffects}>` — and
replaces row equality with row **inclusion** during evidence selection, so the row of an operation
propagates through derivation instead of being fixed at each level.

## Motivation

[ZEP-0092](./ZEP-0092.md) derives streaming encode and decode operations for products, sums, and
transparent data classes. Its rows are honest for a single level — a data class whose canonical
constructor raises `InitializationFailure` derives `Decode<Foo, {InitializationFailure}>` — but the
composed case does not work:

- A component requirement must name a row when the witness is registered, and a component decoder's
  row is only discoverable by evidence selection, which itself needs that row. The loop has no
  entry point, so components are required at the empty row.
- Consequently a type whose component has an effectful decoder cannot derive `Decode` at all. A
  nested data class `Bar` containing `Foo` fails even though `Decode<Bar, {InitializationFailure}>`
  is a perfectly good type: `Bar`'s requirement asks for `Decode<Foo, {}>`.
- The compiled-library witness export cannot see the declaration, so it writes `Decode<Foo, {}>`
  where the in-memory witness is `Decode<Foo, {InitializationFailure}>`. Separate compilation can
  therefore disagree with source derivation about which capability a type has.

The same pressure appears on the writing side as soon as a format can fail on output: a hand-written
component `Encode<Component, {IoFailure}>` cannot be used from a derived encoder that declares `{}`
unless someone writes the whole encoder by hand.

The capability shape itself is not the problem. `Codec<T, E> requires Encode<T, {E}> + Decode<T, {E}>`
already composes at a shared row. What is missing is a derivation and selection model that can leave
that row open.

## Goals

- Let a derived witness declare its own effect-row parameter and use it in its contract type, so a
  derived capability is row-polymorphic rather than monomorphic.
- Require component capabilities at that same row parameter, so a component's effects are part of the
  derived operation's row.
- Match effect rows by inclusion during evidence selection: a witness whose row is included in the
  required row satisfies the requirement. Keep equality for all non-row arguments.
- Enforce a data class constructor's effects as a lower bound on the row at selection time, without
  new surface syntax.
- Preserve derived rows through the compiled-library witness export, so separate compilation and
  source derivation agree.

## Non-goals

- New syntax for row lower bounds, such as `witness ... requires E ⊇ {Init}`. Selection-time
  enforcement is enough for this proposal; a declarative form can follow if diagnostics need it.
- Computed or associated rows ("the row of decoding `T`") as a type-level function.
- Inferring a row from whichever witnesses happen to be available. Rows remain visible in types.
- Splitting decoding from construction, or any change to the streaming code generation, the
  `CanonicalValue` model, or the runtime representation of evidence.
- Changing `Eq`, `Hashable`, `Display`, or other row-free contract selection.

## Proposal

### Row-polymorphic derived witnesses

A derived witness may carry its own row parameter. Registration synthesizes it and uses it in the
contract type and in every component requirement:

```zeron
// derived for:  public data class Foo(value: Int) raises Initialization { ... }
witness Decode<Foo, E> for Foo
    requires Decode<Int, E>
```

Equivalently, in the compiler's terms, `registerDerived` adds an effect-row type parameter to the
witness it registers and passes it, instead of the empty row, to each component requirement. The
technique already exists in the standard library: `Codec<T, E> requires Encode<T, {E}> + Decode<T, {E}>`
propagates a row to its prerequisites the same way.

Encoding follows the same rule, so `Encode<Foo, E>` requires `Encode<Component, E>`. Today every
built-in and derived encoder is effect-free, so the parameter is instantiated at `{}`; it becomes
useful when a hand-written encoder raises.

A derived witness declares a row parameter only when the contract has one. `Shape<T>` and the
row-free contracts keep their current registration.

### Inclusion matching for rows

`witnessEntails` currently compares the witness contract with the required contract using
`matchPattern`, which is equality modulo references. For row arguments that comparison becomes
inclusion: the witness row must be included in the required row, using the existing
`EffectRows.includedIn`. Every other argument keeps structural equality, so nominal matching,
references, nullability, and generic substitutions behave exactly as they do now.

The direction follows from what the row means: a decoder that may raise `{Initialization}` is
usable wherever `{Initialization, IoFailure}` is allowed, and a decoder whose row is a parameter
instantiated at `{}` is usable where `{}` is required. The reverse is not permitted.

Inclusion is applied to the *required* row, so it does not change how a call site chooses its own
row: `decode<E, T>(decoder)` still binds `E` from the expected type, and the evidence must fit that
binding.

### Constructor effects as a lower bound

A data class's canonical constructor effects are declared statically on the class, so they can be
read during derivation and checked during selection. A derived `Decode` witness for a data class
with constructor row `C` is selectable only when the required row includes `C`. No row-lower-bound
syntax is needed:

```zeron
data class Foo(value: Int) raises Initialization { ... }   // derives Decode<Foo, E> with E ⊇ {Initialization}

fn usePure(decoder: &Decoder): Result<Foo, DecodeError> raises Initialization =
    decode<{Initialization}, Foo>(decoder);          // accepted

fn useEmpty(decoder: &Decoder): Result<Foo, DecodeError> = decode<{}, Foo>(decoder);
                                                     // rejected: row misses Initialization
```

The rejection reports the unmet requirement (`Decode<Foo, {}>`), and the diagnostic names the
constructor row so the caller knows which row to declare.

### Prerequisites and diagnostics

Prerequisite resolution passes the caller's required row down unchanged, so a nested type's
component requirements are asked at the same row. When a prerequisite cannot be satisfied, the
existing "no method witness satisfies bound" diagnostic is raised for the component contract,
rather than a derived witness being silently registered with a row the consumer cannot use.

Selection also keeps the rule that a derived `Codec` witness is not considered when the required
contract is `Encode` or `Decode`, so closure entailment stays unambiguous under inclusion.

### Compiled-library index

The witness export gains the derived row parameter and the concrete decode row read from the
declaration's constructor effects, so a loaded library registers `Decode<Foo, E>` with the same
constructor lower bound as source derivation. If the export format needs a new field for the
synthesized parameter, bump `API_INDEX_SCHEMA_VERSION` once for the change, following
[ZEP-0012](./ZEP-0012.md).

### Example

```zeron
public data class Foo(value: Int) raises Initialization {
    check(value) { if (value < 0) raise Initialization.new(); };
}

public data class Bar(foo: Foo, count: Int) {}

// Derives Decode<Bar, E> requiring Decode<Foo, E> and Decode<Int, E>,
// and is selectable only when E includes {Initialization}.
fn readBar(decoder: &Decoder): Result<Bar, DecodeError> raises Initialization =
    decode<{Initialization}, Bar>(decoder);
```

## Compatibility and impact

- Source compatible: existing derivations keep resolving. Some source that previously failed now
  resolves (nested effectful components); some source that previously resolved against an
  incorrectly exported library witness now reports a missing capability, which is a correction.
- The library index changes in what it records for derived serialization witnesses; bump the schema
  version only if a field is added.
- No runtime change: evidence is still a method handle of the same shape, and raised effects are
  still values; only resolution changes.
- Documentation: ZEP-0092's row limitations move here as the active work item, and the serialization
  guide notes that effects propagate through derived codecs.

## Alternatives

- **Keep the empty-row components and require hand-written codecs for effectful nesting** — the
  status quo of ZEP-0092. Cheap, but it makes derivation all-or-nothing per type and forces users to
  hand-write encoders for ordinary compositions.
- **Give every derived witness a concrete computed row** (empty or the constructor row, as now) and
  keep equality matching — cannot express a component's row, because it is unknown at registration.
- **Computed rows / associated effects**: infer "the row of decoding `T`" as a type-level function.
  Much larger mechanism, and it makes evidence selection depend on inference instead of the other
  way round.
- **Split decoding from construction** so `Decode` is effect-free — changes what the capability means
  for every type, needs an unobservable "pending instance" type, and does not help encoding or
  hand-written decoders that raise.
- **Add row-lower-bound syntax on witnesses** — a declarative alternative to selection-time
  enforcement. Rejected for now because the constructor row is statically known and the check is
  local; the syntax can be added later without changing this design.

## Implementation and validation

Stages, each independently testable:

1. Synthesize the row parameter on derived serialization witnesses and use it in component
   requirements; verify that a nested data class with an effect-free constructor derives at `{}`.
2. Match row arguments by inclusion in `witnessEntails` and `hasEvidence`; verify that a witness
   instantiated at a smaller row satisfies a larger required row, and that the reverse fails.
3. Enforce the constructor lower bound during selection; verify that `decode<{}, Foo>` is rejected
   for an effectful constructor and that the diagnostic names the constructor row.
4. Preserve rows through the library index and add a two-unit separate-compilation test.

Validation: derivation tests for products, sums, data classes, and generic components; an
end-to-end compilation test that derives and runs a nested codec through recording codecs; a
negative test for the constructor-row rejection; a separate-compilation round-trip test; the
existing `Eq`/`Hashable`/`Display` selection tests unchanged; `mvn test` and a compile of
`src/main/resources/test.zn` for bytecode identity.

## Open questions

- Should inclusion also apply to explicit (non-derived) witnesses, so a hand-written
  `Decode<Foo, {}>` satisfies `Decode<Foo, {IoFailure}>`? It is sound by the same argument, but it
  changes error messages for hand-written code and should be decided deliberately.
- Does inclusion need refinement in ambiguity counting, or is one witness per contract type still
  guaranteed under row inclusion?
- Should the constructor lower bound become declarative (`requires E ⊇ {Init}`) once diagnostics or
  library authors need to state it outside the class declaration?
- How should a diagnostic suggest the row to use when several effects are missing from it?
