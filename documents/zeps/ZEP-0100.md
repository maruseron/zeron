## Abstract

[ZEP-0090](./ZEP-0090.md) introduced statically resolved property references: values that denote a
property declaration, carry its identity, and convert to a getter function. This proposal extends
the same idea to callables that are not property getters:

- instance and contract method references;
- constructor references, for `Type::new` and named constructors;
- static function references, without a receiver.

It also settles the policy for “method-looking” declarations that are not ordinary members:
namespace functions, extension members, witness methods, and static contract requirements. Bound
references (`value::member`) remain out of scope and are explicitly rejected for the first version.

The feature is deliberately not a general callable abstraction. It adds typed, identity-bearing
references to statically known declarations, with no reflection and no runtime member lookup.

## Motivation

Property references showed that typed selectors are more useful when they carry an identity.
Callables have the same need: an adapter or dependency-injection API wants to store “the
constructor of `User`” or “the method that normalizes an address,” not an opaque lambda. A
consumer that receives `User::normalize` can validate it, compare it, record it, and call it,
without a string or a reflective lookup.

Models are a concrete consumer. [ZEP-0079](./ZEP-0079.md) deliberately does not let a model
construct its target, and its consumer contracts can only name properties. A construction
reference lets a consumer contract state how a value is built without changing the model
declaration itself or reopening the model's “no construction” non-goal:

```zeron
public contract SqlModel<T: nullable + mut> requires Model<T> {
    property tableName: String;
    property construction: ConstructorRef<(String, Int) -> &T>;
}
```

Code models are another consumer. [ZEP-0093](./ZEP-0093.md) records a `CallNode` as future work;
a call node needs an identity for the called member, which this proposal can supply.

The existing `::` syntax already gives a property reference, and the left side already denotes a
type. Extending the resolved member kind is therefore smaller than a new reference syntax.

## Goals

- Denote an instance or contract method with a statically checked, typed value.
- Denote constructors and static functions, with a receiver rule appropriate to each.
- Give every reference a stable identity, owned by the declaring symbol, that survives separate
  compilation.
- Let a reference convert implicitly to an ordinary function type.
- Define explicitly which non-member callables may be referenced.
- Introduce no reflection and no lookup by string.

## Non-goals

- Bound references (`value::member`) that capture a receiver.
- Writable or mutable callable references.
- References to extension members, witness methods, or static contract requirements.
- Namespace function references in the first version (see Open questions).
- General higher-rank or polymorphic callable values.
- Method overloading. Zeron has none, and none of this proposal's use cases require adding it.
- Constructor currying, partial application, or argument reordering.
- Adding a `construction` member to `zeron.lang.Model<T>`.
- Call nodes or callable literals in typed code models; [ZEP-0093](./ZEP-0093.md) records that as
  separate future work.
- Reflection, dynamic invocation, or member discovery.

## Proposal

### Syntax and resolution

The existing form is extended by resolving the identifier after `::` as a callable declaration
when a property is not selected:

```zeron
let rename: (&User, String) -> Unit = User::rename;       // mutating instance method
let label: (User) -> String = User::label;                // non-mutating instance method
let make: (String, Int) -> &User = User::new;             // constructor
let parse: (String) -> Int = User::parse;                 // static function, when ZEP-0072 lands
```

Rules:

- The left operand continues to name a type. `value::member` remains invalid and keeps its current
  diagnostic; bound references are not part of this proposal.
- `::` followed by `<` remains the existing function-specialization form.
- A name is resolved as a property first, preserving every program accepted by
  [ZEP-0090](./ZEP-0090.md). If no property matches, it is resolved as a method, constructor, or
  static function, in that order. Zeron has no overloading, so resolution never chooses among
  multiple declarations with the same name and kind.
- Accessibility follows [ZEP-0090](./ZEP-0090.md): a reference must be usable at its site, and a
  public reference cannot expose a private declaration.
- A reference to a contract method or property uses the contract as its declaring symbol and
  dispatches virtually. A reference to a class member uses the class declaration.

### Reference types

The first version adds three non-generic-in-identity classes next to `PropertyRef`:

```zeron
// illustrative
public class MethodRef<F> is Eq<MethodRef<F>> {
    public property name: String;
    public property identity: String;
    public property id: CallableId;
    public property callable: F;

    private constructor new;
}

public class StaticMethodRef<F> is Eq<StaticMethodRef<F>> {
    public property name: String;
    public property identity: String;
    public property id: CallableId;
    public property callable: F;

    private constructor new;
}

public class ConstructorRef<F> is Eq<ConstructorRef<F>> {
    public property name: String;
    public property identity: String;
    public property id: CallableId;
    public property callable: F;

    private constructor new;
}
```

- `F` is an ordinary function type. For an instance method it includes the receiver as its first
  invocation parameter, so `MethodRef<(&User, String) -> Unit>` is the type of `User::rename`.
  A mutating method requires a mutable receiver; a non-mutating method uses the read-only receiver
  form its declaration permits. The exact receiver descriptor is an Open question.
- A `StaticMethodRef<F>` has no receiver parameter. Its declaring type appears only in the identity.
- A `ConstructorRef<F>` has no receiver parameter either; its result is `&T`, because construction
  in Zeron produces a mutable reference. `Type::new` and named constructors use the same type.
- The reference stores the callable as an ordinary function value. `callable` is the invocation
  surface; an implicit conversion to `F` is also provided, matching the property-reference
  conversion. The conversion is one-way and loses identity.
- References are constructed only by the compiler, using the same unspellable synthesized factory
  pattern as `PropertyRef`. No source program can fabricate one.

### Identity

Identity is a new non-generic `CallableId`:

```zeron
public class CallableId is Eq<CallableId>, Hashable<CallableId> {
    public property owner: String;          // declaring type's qualified name
    public property kind: CallableKind;     // Method, Static, or Constructor
    public property name: String;           // method or constructor name

    public text(): String;
}
```

`CallableKind` is a small closed type with `Method`, `Static`, and `Constructor` alternatives.
Because `CallableKind` has no assumed `Eq` or `Hashable` witness here, `CallableId` defines
equality and hashing over its canonical `text()`, following the approach
[ZEP-0093](./ZEP-0093.md) uses for code models.

- The identity is the declaring type's qualified name, the kind, and the name, following
  `PropertyId`'s owner-plus-name shape. A contract method is distinct from a class method with the
  same name, as in [ZEP-0090](./ZEP-0090.md) and [ZEP-0093](./ZEP-0093.md).
- Zeron has no overloading, so one owner and kind cannot have two callables with the same name.
  Adding overloading later would require extending this identity; this proposal does not assume
  it.
- Type arguments are not part of the identity, consistent with `PropertyId`. A reference to a
  generic method is identified by its declaration, not by an application.
- `==` compares identities. `===` remains object identity of the wrapper.
- Identity is derived from names already present in the library index, so references survive
  separate compilation without a new serialized field.

### Generic methods and assignability

- A reference names a unique declaration by owner, kind, and name. The expected function type
  does not participate in resolving it, because Zeron has no overloading.
- A reference to a generic method is a rank-1 callable, not a polymorphic value. It may be
  specialized from a fully constraining expected function type or by explicit type arguments in
  the reference. General polymorphic callable values remain out of scope, consistent with the
  generic-function boundary in design document 19.
- A method reference used where a function type is expected is checked with the same assignability
  rules as a lambda, including receiver capability and parameter variance.

### Member kinds and policy

| Declaration kind | Reference form | First version |
| ---------------- | -------------- | ------------- |
| Instance/class method | `T::m` → `MethodRef<F>` | Supported |
| Contract method or property | `C::m` → `MethodRef<F>` / `PropertyRef<T,V>` | Supported; virtual dispatch |
| Constructor (`new`, named) | `T::new` / `T::from` → `ConstructorRef<F>` | Supported |
| Static class function | `T::f` → `StaticMethodRef<F>` | Supported when [ZEP-0072](./ZEP-0072.md) exists |
| Namespace function | not `T::f` | Deferred; see Open questions |
| Extension method or property | `T::f` | Rejected |
| Witness method | `T::f` | Rejected |
| Static contract requirement | `T::f` | Rejected |
| Inherited member | `T::m` | Supported; identity is the declaring symbol |

**Extensions are rejected.** Extensions are statically dispatched and activated by imports. Making
`T::f` mean “some applicable extension” would make a reference's identity depend on the import set
at the reference site, and would change meaning when imports change. A consumer that needs a
callable extension writes a lambda, or a future explicit extension reference qualified by the
extension's declaring symbol.

**Witness methods and static contract requirements are rejected.** Their behavior is selected by
evidence, and the evidence is not part of the declaration reference. A value that denotes a
witness method would have to carry the selected witness. That is a reasonable future feature if
witnesses become first-class values, but it is not a type-qualified reference.

**Bound references are rejected.** A bound reference captures a receiver value. Its equality then
has no good definition: comparing only declarations makes two refs on different receivers equal
but behaviorally different; comparing receivers makes it a value identity rather than a
declaration identity. An ordinary lambda already captures a receiver, and a consumer that needs
both behavior and declaration identity can pair a lambda with a `PropertyId` or `CallableId`.
This preserves the decision recorded by [ZEP-0090](./ZEP-0090.md).

### Construction and models

A `construction` member is not added to `zeron.lang.Model<T>`. A model maps properties, and a
constructor's parameters need not correspond to them. The consumer contract owns the construction
shape, as in the `SqlModel` example above. The model body assigns it like any other parent-contract
property:

```zeron
public model UserSql is SqlModel<User> {
    tableName = "users";
    construction = User::new;

    id   -> "id";
    name -> "name";
}
```

The model still does not construct anything; the consumer uses `construction` when it decides to.
Assigning a callable reference must be accepted as a constant, in the same way a property
reference is.

Aligning constructor parameters with mapped fields for decoding is not part of this proposal. That
is a decode-path concern of [ZEP-0092](./ZEP-0092.md), especially for ordinary classes whose
constructor arguments are not properties.

### Typed code models

A method-reference literal could be accepted as a `CodeModel<F>` argument only if `CodeShape` gains a
call node. [ZEP-0093](./ZEP-0093.md) records further nodes as future work. This proposal supplies
the identity (`CallableId`) that such a node would carry but does not add the node.

## Compatibility and impact

The change is additive for programs without a name collision between a property and a method.
`T::p` continues to resolve as a property first. A class that declares a property and a method with
the same name resolves a reference to the property; whether the language should instead reject that
collision at declaration time is recorded as an Open question.

The new reference classes are standard-library API additions. Identity is derived from names
already present in the library index, so no `API_INDEX_SCHEMA_VERSION` bump is required for
references themselves. Adding a call node to `CodeShape` later is a breaking change for
exhaustive matches and is versioned separately.

Renaming a method changes the identity of its references, as renaming a property does. Zeron has
no overloading, so adding a method with an existing name is already a declaration error and cannot
silently change the meaning of a reference.

## Alternatives

- **A single `MethodRef<T, R>` with no parameter list** — cannot express the callable's parameter
  types, and cannot convert to a function. Rejected.
- **Bound references in the first version** — useful for per-instance selectors, but equality and
  identity are ill-defined, and lambdas already cover the behavior. Deferred.
- **Extension and witness references** — import-sensitive or evidence-dependent, with no stable
  declaration identity. Rejected for the first version.
- **Add `construction` to `Model<T>`** — imposes a constructor shape on every model and reopens
  the model's construction non-goal. Rejected in favor of consumer-contract properties.
- **Keep lambdas and strings** — no identity and no compile-time declaration check. Rejected as the
  only mechanism; lambdas remain the right choice when identity is not needed.
- **Static methods as `MethodRef<T, F>`** — makes the owner a phantom type parameter that cannot be
  inferred from `F`. Rejected in favor of `StaticMethodRef<F>`.

## Implementation and validation

1. Extend parsing and the reference AST to distinguish property, method, constructor, and static
   reference forms, while preserving `::<` specialization.
2. Resolve the unique member by name and kind, check accessibility and receiver capability, and
   build the function type from the declaration.
3. Add `CallableId`, `MethodRef<F>`, `StaticMethodRef<F>`, and `ConstructorRef<F>` to the standard
   library, constructed through compiler-only factories.
4. Emit the callable function value and the identity, reusing the existing lambda and function
   adaptation machinery.
5. Accept a callable reference as a constant parent-contract assignment in a model body.
6. Test: instance, contract, constructor, and static references; property-first resolution;
   accessibility; mutating receiver capability; conversion to a function; identity equality and
   stability across separate compilation; rejection of bound, extension, witness, and static
   requirement references; model assignment of a constructor reference; diagnostics.

This proposal is a design record only. ZEP-0079's initial model surface is implemented but is still
being validated; implementation of the model-construction use case should wait until that surface
is stabilized and its conformance tests are in place. The callable-reference feature itself does
not change models, and can proceed independently when scheduled.

## Open questions

- What exact receiver descriptor should `F` carry for a non-mutating method: the read-only `T`, the
  mutable `&T`, or both through an explicit conversion? The declaration's receiver capability and
  the existing projection rules should decide this.
- Should a class be allowed to declare a property and a method with the same name, or should that
  be rejected at declaration time?
- Are generic method references expressible by expected-type specialization alone, or is an
  explicit type-argument form needed? Which syntax avoids the existing `::<` specialization form?
- Should namespace functions get a `FunctionRef<F>` in a later proposal, and how should the
  companion-namespace name sharing of [ZEP-0072](./ZEP-0072.md) be kept unambiguous?
- If witnesses become first-class values, should a witness method be reachable as a bound method
  reference on the witness value rather than as `T::method`?
