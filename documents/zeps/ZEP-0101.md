## Abstract

A model maps a property to an external field name, but the property's type is not always the type
of the external representation. A timestamp property may be stored as epoch milliseconds, an
identifier newtype may be written as a string, and a money value may be written as a decimal
string.

This proposal introduces a general, format-neutral **representation adapter**:

```zeron
public contract Converter<V: nullable + mut, W: nullable + mut> {
    convert(value: V): W;
}

public contract InvertibleConverter<V: nullable + mut, W: nullable + mut>
        requires Converter<V, W> {
    revert(value: W): V;
}
```

and an optional `via` clause in a model mapping:

```zeron
createdAt -> "created" via InstantAsLong;
```

The model records that the external type is `W` and that reading the external representation goes
through the converter. The mapped type itself is unchanged.

The adapter is deliberately **not** a model-only feature. Serialization derivation has the same
need, and [ZEP-0092](./ZEP-0092.md) already defers per-component representation changes to wrapper
types and hand-written codecs. A single general adapter avoids a second, incompatible mechanism.

## Motivation

Without an adapter, the only way to change a field's external representation is to wrap the value:

- introduce a newtype or data class for the external form, or
- change the mapped type's property to the external type.

Both are invasive. Wrapping produces a type whose only purpose is one model's representation;
changing the property couples the domain type to that representation, which models exist to avoid.
[ZEP-0092](./ZEP-0092.md) records the wrapper workaround explicitly for components whose
representation differs.

A converter is smaller and reusable. It is also the natural composition point between a model and
a format adapter: a field's external value is obtained by applying `convert`, then encoded by the
format's `Encode<W>` evidence. The model does not need to know the format, and the converter does
not need to know the stream.

## Goals

- Define a general, total, format-neutral value adapter in the standard library.
- Allow a field mapping to name an adapter and an external type.
- Check the adapter against the mapped property's type at compile time.
- Keep the mapped type, its declaration, and its runtime representation unchanged.
- Preserve typed property lookup and writer rules.
- Record the adapter and external type in model metadata for separately compiled consumers.
- Reuse the adapter in serialization derivation once annotation consumption permits it.

## Non-goals

- Format-specific encoders or decoders; those remain [ZEP-0092](./ZEP-0092.md).
- Fallible or effectful converters in the first version.
- Arbitrary expression-bodied field mappings.
- Changing `deriving Codec` or per-component annotations in this proposal.
- Replacing newtypes or wrapper types; both remain valid.
- Schema evolution or migration policy.
- A general public API for constructing or modifying model descriptors.
- Runtime reflection or type descriptors.

## Proposal

### Converter contracts

```zeron
// illustrative
public contract Converter<V: nullable + mut, W: nullable + mut> {
    convert(value: V): W;
}

public contract InvertibleConverter<V: nullable + mut, W: nullable + mut>
        requires Converter<V, W> {
    revert(value: W): V;
}
```

- Both parameters admit nullable arguments so a nullable property can be adapted without a wrapper.
  A converter for a nullable `V` is responsible for handling `null`; the compiler does not insert
  a null check or a null branch.
- `Converter` is **total**. A conversion that can fail is expressed today with a wrapper type and a
  hand-written codec, as [ZEP-0092](./ZEP-0092.md) already recommends. Fallible adapters are
  future work because a model descriptor has no error channel and no effect row of its own.
- `InvertibleConverter` is the read-write form. A field gets a writer only when the mapped property
  has an accessible setter **and** the named adapter conforms to `InvertibleConverter<V, W>`.
  A one-way `Converter` yields a read-only field, mirroring the existing writer rule.
- The contracts are ordinary library contracts. A model value, a top-level immutable value, or a
  witness can provide an adapter; no compiler-specific instantiation mechanism is introduced.

### The `via` clause

A field mapping gains an optional `via` clause:

```zeron
public model UserRow is SqlModel<User> {
    tableName = "users";

    id        -> "id";
    name      -> "name";
    createdAt -> "created" via InstantAsLong;
}
```

Rules:

- `via` is valid only on a field-mapping clause, not on a parent-contract assignment.
- The expression after `via` denotes a value, not a type. It must be a constant: a top-level
  immutable value, a model value, or a property reference. This is the same constant rule the model
  body already applies to parent-contract assignments, extended to accept a named immutable value.
- The compiler checks that the value's static type conforms to `Converter<V, W>`, where `V` is the
  mapped property's declared type. `W` becomes the field's **external type**.
- If the adapter value is typed only as `Converter<V, W>`, the field is read-only even if the
  adapter's runtime value happens to be invertible. A consumer that needs a writer declares the
  adapter with the `InvertibleConverter` type.
- A property is mapped at most once, and a field clause carries at most one `via`. Combining `via`
  with a future per-clause adapter annotation is rejected as a duplicate representation.
- The external name remains a distinct string. `via` changes the value's representation, not the
  field's name.

### Typed access and the descriptor

The first version keeps the existing typed access surface:

- `Model.field(ref)` continues to return `Field<T, V>`, where `V` is the **property** type.
  `source.get(owner)` reads the property without conversion.
- `Model.fields` continues to expose `AnyField<T>` with `externalName` and `sourceId`.
- Conversion is applied by generated field operations, not by changing `Field`'s type parameters.
  For example, an encode operation for the field performs `convert(source.get(owner))` and then
  applies the format's `Encode<W>` evidence.
- The descriptor records the adapter value and the external type `W` as metadata. Schema-oriented
  consumers obtain `W` through the `Shape`/`CodeType` metadata of [ZEP-0092](./ZEP-0092.md), not
  through an erased `AnyField`.

This avoids a third type parameter on `Field` and avoids a second lookup API. A later proposal may
add a `MappedField<T, V, W>` view if a consumer needs typed external access without generated
operations. The model's public behavior in this proposal does not depend on that addition.

### Errors and effects

Because converters are total, they introduce no new error or effect. Encoding and decoding still
fail through the format adapter's existing `EncodeError`/`DecodeError` and the effect row of
[ZEP-0092](./ZEP-0092.md). If fallible adapters are added later, a conversion failure must be
reported as a format error whose `path` segment is the clause's external name, matching
[ZEP-0092](./ZEP-0092.md).

### General use outside models

The adapter is format-neutral and should be usable by serialization derivation. Once
[ZEP-0091](./ZEP-0091.md) Direction B can consume annotation values, a data class or product
component can name a converter value with an annotation, and the derived codec applies it in the
same way. That integration is not specified here; it is the reason the adapter is defined in the
serialization layer rather than in the model grammar.

Models remain a consumer of the adapter, not its owner.

### Library index

Public models are exported with their mappings ([ZEP-0079](./ZEP-0079.md)). Each exported mapping
additionally records:

- the adapter value reference, which must itself be exported and resolvable to separately
  compiled consumers;
- the external type `W` in source-level form, for diagnostics and schema consumers.

This changes the model export record and therefore the API-index representation, governed by
`API_INDEX_SCHEMA_VERSION`. It joins the current unreleased revision if one exists when this is
implemented, and otherwise takes the next revision.

The adapter is part of the external representation. Changing it changes the data format, so it is
an API compatibility concern like changing an external name.

## Compatibility and impact

The change is additive: a model without `via` behaves exactly as before, and `Field<T, V>` keeps
its current meaning. It touches model-body parsing, constant validation, type checking, generated
field operations, metadata, and the library index.

The standard library gains two public contracts, so `STANDARD_LIBRARY_API_VERSION` changes under
the normal policy. A public model's adapter must be public and exported, or the model cannot be
used from a separately compiled consumer.

## Alternatives

- **A model-only converter syntax** — duplicates the serialization layer's representation concept
  and creates a second mechanism. Rejected.
- **An annotation naming a type literal** — blocked today because annotations cannot carry type
  literals, and [ZEP-0091](./ZEP-0091.md) would still need to define consumption. A value reference
  avoids that dependency.
- **Wrapper newtypes or data classes** — the existing workaround. They remain valid, but they
  create a type per representation and are too heavy for a single field.
- **Fallible converters in the first version** — the model descriptor has no error channel, and
  effects belong to the consumer's encode/decode path. Deferred.
- **Change `Field<T, V>` to `Field<T, V, W>`** — forces every model consumer and every unmapped
  field to carry an external type parameter. Rejected for the first version.
- **Make the converter apply automatically to every mapping** — changes existing models and
  removes the opt-in distinction between a faithful property mapping and a representation change.

## Implementation and validation

1. Add `Converter` and `InvertibleConverter` to the serialization standard library.
2. Parse `via` on field-mapping clauses and extend constant validation to a named immutable value.
3. Resolve the adapter, instantiate `Converter<V, W>`, check the mapped property type, and record
   `W` and the adapter reference.
4. Generate field operations that apply the adapter, and set the writer only for an invertible
   adapter with an accessible setter.
5. Export the adapter reference and external type in the library index, and restore them for
   separately compiled consumers.
6. Test: total conversion, invertible conversion and writer presence, one-way conversion and
   writer absence, nullable property types, inaccessible adapter, non-converter value, duplicate
   `via`, `via` on an assignment clause, adapter across separate compilation, schema metadata, and
   a model whose field type and external type differ.

This proposal is a design record only. The initial [ZEP-0079](./ZEP-0079.md) model surface is
implemented but is still being validated. Implementation should wait until that surface is
stabilized, and should follow the per-field operations of [ZEP-0092](./ZEP-0092.md) and the
annotation-consumption work of [ZEP-0091](./ZEP-0091.md). The dependency is sequencing, not a
change to this design.

## Open questions

- Should the first version define a `MappedField<T, V, W>` typed view, or is generated encode/decode
  enough? The answer determines whether external types are observable in ordinary code.
- Should a fallible adapter be a separate contract with a `Result`, or should a failing conversion
  be expressed as an effect row on the adapter operation? Either way, the model descriptor cannot
  carry the failure alone.
- Should `via` accept a model-factory application ([ZEP-0102](./ZEP-0102.md)) as a constant, or
  only a top-level immutable value and a model value?
- Does the external type `W` need to be part of the mapping's identity, or is the property identity
  plus the adapter enough?
- How should a nullable external type interact with a non-nullable property: does `convert`
  produce `null`, or does the format adapter handle nullability? The converter contract admits
  nullable parameters, but the mapping's null policy must be stated.
