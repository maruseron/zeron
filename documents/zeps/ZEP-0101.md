## Abstract

A model maps a property to an external field name, but the property's type is not always the type
of the external representation. A timestamp property may be stored as epoch milliseconds, an
identifier newtype may be written as a string, and a money value may be written as a decimal
string.

This proposal introduces a general, format-neutral **representation adapter**:

```zeron
public contract Converter<V admits nullable + mutable, W admits nullable + mutable> {
    convert(value: V): W;
}

public contract InvertibleConverter<V admits nullable + mutable, W admits nullable + mutable>
        requires Converter<V, W> {
    revert(value: W): V;
}
```

and an optional `via` clause in a model mapping:

```zeron
createdAt -> "created" via InstantAsLong;
```

The model's exported mapping records that the external type is `W` and that reading the external
representation goes through the converter. The mapped type itself is unchanged.

The adapter is deliberately **not** a model-only feature. Serialization derivation has the same
need, and [ZEP-0092](./ZEP-0092.md) already defers per-component representation changes to wrapper
types and hand-written codecs. A single general adapter avoids a second, incompatible mechanism.

The first version also defines the opt-in model consumer contract that [ZEP-0092](./ZEP-0092.md)
left to a follow-up. A model that requires it gets compiler-generated per-field encode and decode
operations for adapted mappings, so the external type stays a compile-time fact and no erased
adapter enters the model descriptor.

## Motivation

Without an adapter, the only way to change a field's external representation is to wrap the value:

- introduce a newtype or data class for the external form, or
- change the mapped type's property to the external type.

Both are invasive. Wrapping produces a type whose only purpose is one model's representation;
changing the property couples the domain type to that representation, which models exist to avoid.
[ZEP-0092](./ZEP-0092.md) records the wrapper workaround explicitly for components whose
representation differs.

A converter is smaller and reusable. It is also the natural composition point between a model and
a format adapter: a field's external value is obtained by applying `convert`, then encoded by the
format's `Encode<W>` evidence. The model does not need to know the format, and the converter does
not need to know the stream.

## Goals

- Define a general, total, format-neutral value adapter in the standard library.
- Allow a field mapping to name an adapter, with the external type inferred from the adapter.
- Check the adapter against the mapped property's type at compile time.
- Generate per-field adapted encode and decode operations through an opt-in model consumer
  contract.
- Keep the mapped type, its declaration, and its runtime representation unchanged.
- Preserve typed property lookup and writer rules.
- Record the adapter and external type in model metadata for separately compiled consumers.
- Keep the external type a compile-time fact; do not add it to the erased descriptor.
- Reuse the adapter in serialization derivation once annotation consumption permits it.

## Non-goals

- Format-specific encoders or decoders; those remain [ZEP-0092](./ZEP-0092.md).
- Fallible or effectful converters in the first version. The direction is fixed as a
  `Result`-returning contract in future work, not as effects.
- Arbitrary expression-bodied field mappings. `via` names a constant value and never accepts an
  application.
- A `MappedField<T, V, W>` typed view, or any new type parameter on `Field`.
- Runtime storage of the adapter or the external type in the model descriptor.
- Changing `deriving Codec` or per-component annotations in this proposal.
- Replacing newtypes or wrapper types; both remain valid.
- Schema evolution or migration policy.
- A general public API for constructing or modifying model descriptors.
- Runtime reflection or type descriptors.

## Proposal

### Converter contracts

```zeron
// illustrative
public contract Converter<V admits nullable + mutable, W admits nullable + mutable> {
    convert(value: V): W;
}

public contract InvertibleConverter<V admits nullable + mutable, W admits nullable + mutable>
        requires Converter<V, W> {
    revert(value: W): V;
}
```

- Both parameters admit nullable arguments so a nullable property can be adapted without a wrapper.
  A converter for a nullable `V` is responsible for handling `null`; the compiler does not insert
  a null check or a null branch.
- Both parameters admit mutable-reference arguments so a property of type `&Widget` can be adapted.
  Admissibility permits such an argument without granting the generic body mutation operations,
  so an adapter cannot mutate the mapped value through `V`.
- `Converter` is **total**. A conversion that can fail is expressed today with a wrapper type and a
  hand-written codec, as [ZEP-0092](./ZEP-0092.md) already recommends. Fallible adapters are
  future work because a model descriptor has no error channel and no effect row of its own.
- `InvertibleConverter` is the read-write form. A field gets a writer only when the mapped property
  has an accessible setter **and** the named adapter conforms to `InvertibleConverter<V, W>`.
  A one-way `Converter` yields a read-only field, mirroring the existing writer rule.
- The contracts are ordinary library contracts. A model value, a top-level immutable value, or a
  witness can provide an adapter; no compiler-specific instantiation mechanism is introduced.

### Fallible adapters (future work)

The first version excludes fallible adapters, but the direction is fixed so a later version does
not need a second adapter concept:

```zeron
// illustrative
public contract TryConverter<V admits nullable + mutable, W admits nullable + mutable> {
    convert(value: V): Result<W, ConversionError>;
}

public contract TryInvertibleConverter<V admits nullable + mutable, W admits nullable + mutable>
        requires TryConverter<V, W> {
    revert(value: W): Result<V, ConversionError>;
}
```

`ConversionError` is a small serialization-layer error carrying a message. A failing conversion is
data, not control flow:

- A generated operation maps `ConversionError` into the surrounding `EncodeError` or
  `DecodeError`, with the clause's external name appended to `path`, reusing the existing
  `encodeErrorAt` and `decodeErrorAt` helpers of [ZEP-0092](./ZEP-0092.md).
- An effect row on the adapter operation is rejected for the eventual design. A model descriptor
  has no row of its own, a per-field row would have to leak into every consumer of the mapping, and
  effects would let a representation adapter perform arbitrary effects. A conversion failure is a
  value.
- No new `via` syntax is needed: a later version can accept an adapter conforming to
  `TryConverter` where it now requires `Converter`, and the generated operation reports the
  failure.

### The `via` clause

A field mapping gains an optional `via` clause:

```zeron
public model UserRow is SqlModel<User> {
    tableName = "users";

    id        -> "id";
    name      -> "name";
    createdAt -> "created" via InstantAsLong;
}
```

Rules:

- `via` is valid only on a field-mapping clause, not on a parent-contract assignment.
- The expression after `via` is a **value name**, not an arbitrary expression. It must resolve to
  one of:
  - a public top-level immutable value;
  - a parameter of the enclosing model factory
    ([ZEP-0102](./ZEP-0102.md)), when model factories are implemented;
  - a model value whose contract supplies `Converter`.
  No literal, no property reference, and no call or application expression is accepted.
- The value name is what the library index exports. A name maps to a `ValueExport`, which already
  restores across separate compilation; an application would have to be stored and re-evaluated
  when the index is loaded, and the language has no serializable constant form for it.
- The compiler checks that the value's static type conforms to `Converter<V, W>`, where `V` is the
  mapped property's declared type. `W` becomes the field's **external type**. The model does not
  spell `W`; the adapter's type fixes both arguments.
- If the adapter value is typed only as `Converter<V, W>`, the field is read-only even if the
  adapter's runtime value happens to be invertible. A consumer that needs a writer declares the
  adapter with the `InvertibleConverter` type.
- A property is mapped at most once, and a field clause carries at most one `via`. Combining `via`
  with a future per-clause adapter annotation is rejected as a duplicate representation.
- The external name remains a distinct string. `via` changes the value's representation, not the
  field's name.
- If the model is public, the adapter value must be public and exported, or the model cannot be
  used from a separately compiled consumer.

### Generated adapted-field operations

[ZEP-0092](./ZEP-0092.md) deferred an opt-in consumer contract for generated per-field model
operations. This proposal defines it for adapted fields, because a `via` mapping otherwise has no
observable behavior: `Field<T, V>` is typed in the property type, and the erased descriptor cannot
carry the adapter or `W`.

```zeron
// illustrative
public contract AdaptedModel<T admits nullable + mutable> requires Model<T> {
    /// Encodes one adapted field of `owner`; `None` when `source` is unmapped or has no adapter.
    encodeField<V admits nullable + mutable>(
        source: PropertyRef<T, V>, owner: T, encoder: &Encoder
    ): Option<Result<Unit, EncodeError>>;

    /// Reads and converts one adapted field; `None` when `source` is unmapped or has no adapter.
    decodeField<V admits nullable + mutable>(
        source: PropertyRef<T, V>, decoder: &Decoder
    ): Option<Result<V, DecodeError>>;
}
```

- The contract is opt-in per model. The compiler generates the operations in the model singleton
  only when the model's consumer contract requires `AdaptedModel<T>`. A model may declare `via`
  without requiring the contract; the mapping is then metadata only.
- Both operations return `None` for an unmapped field and for a mapped field without a `via`
  adapter. Non-adapted fields continue to use the ordinary `Encode` and `Decode` entry points.
- `encodeField` requires `Encode<W>` evidence. `decodeField` requires `Decode<W>` evidence and an
  `InvertibleConverter`; a one-way `Converter` returns `None` from `decodeField`, because there is
  no `revert` operation.
- Decoding returns the property value rather than writing into an owner. Writing remains the
  consumer's policy, because [ZEP-0092](./ZEP-0092.md) leaves `decodeInto` out of scope; a consumer
  with `Field.writer` can store the result itself. An accessible setter is not required for
  `decodeField`, and an invertible adapter without a setter still decodes to a value.
- The generated operation closes over the adapter and the `Encode<W>` / `Decode<W>` evidence
  resolved at the model declaration. The external type and its codec evidence must therefore be
  fixed there. A model that requires `AdaptedModel<T>` and has an adapted field whose external
  evidence cannot be resolved at the declaration is rejected with a diagnostic naming the field.
- The first version requires effect-free `Encode<W>` / `Decode<W>` evidence for an adapted field.
  A field whose external codec performs effects is encoded and decoded by the consumer directly;
  this keeps a per-field effect row out of the contract's signature.
- The operation identifies the field by `source.id`, applies `convert` or `revert`, and prefixes a
  format failure with the clause's external name. The internal casts are compiler-generated and
  guarded by the identity comparison.
- A `MappedField<T, V, W>` view is not defined. If a consumer later needs typed external access
  without generated operations, it is additive.

### Typed access and the descriptor

The first version keeps the existing typed access surface:

- `Model.field(ref)` continues to return `Field<T, V>`, where `V` is the **property** type.
  `source.get(owner)` reads the property without conversion.
- `Model.fields` continues to expose `AnyField<T>` with `externalName` and `sourceId`. Its layout
  is unchanged; no adapter value and no external type are added.
- Conversion is applied by generated adapted-field operations, not by changing `Field`'s type
  parameters. An adapted encode performs `convert(source.get(owner))` and then applies the
  format's `Encode<W>` evidence.
- The descriptor keeps no runtime adapter and no external type. Schema-oriented consumers obtain
  `W` from the model's exported mapping, and the external type's own shape through the `Shape`
  evidence of [ZEP-0092](./ZEP-0092.md), not an erased `AnyField`.

This avoids a third type parameter on `Field`, a second lookup API, and an erased adapter value in
`AnyField`. The model's public behavior in this proposal does not depend on a typed external view.

### Errors, effects, and nullability

Because converters are total, they introduce no new error or effect. Encoding and decoding still
fail through the format adapter's existing `EncodeError`/`DecodeError` and the effect row of
[ZEP-0092](./ZEP-0092.md).

Nullability is owned by the converter, and the compiler inserts no null check or null branch. The
pipeline is always:

```text
read V -> convert -> encode W
decode W -> revert -> store V
```

The type arguments state the whole policy:

- `V` is the mapped property's type and `W` the external type, both fixed by the adapter's
  instantiation. Neither is widened or narrowed by the mapping.
- If `V` and `W` are both non-null, neither `convert` nor `revert` can produce `null`; the
  language rejects `null` in a non-null position.
- If `V` is nullable, `convert` receives the property value, including `null`, and owns the
  policy. A nullable property with a non-null `W` maps `null` to a value chosen by the adapter,
  such as a sentinel.
- If `W` is nullable, the format adapter writes `null` for a null `W` through `Encode<W?>` and can
  produce `null` when decoding. `revert` therefore receives `null` for an externally null value
  and must return a `V`; when `V` is non-null, the adapter must choose the value for that input,
  because the first version has no failure channel.
- The format adapter never sees `V`, so it cannot be responsible for the property's nullability.
- A converter that returns `null` for a non-null `V` or `W` is a type error, not a runtime check.

If fallible adapters are added later, a conversion failure must be reported as a format error whose
`path` segment is the clause's external name, matching [ZEP-0092](./ZEP-0092.md).

### General use outside models

The adapter is format-neutral and should be usable by serialization derivation. Once
[ZEP-0091](./ZEP-0091.md) Direction B can consume annotation values, a data class or product
component can name a converter value with an annotation, and the derived codec applies it in the
same way. That integration is not specified here; it is the reason the adapter is defined in the
serialization layer rather than in the model grammar.

Models remain a consumer of the adapter, not its owner.

### Library index

Public models are exported with their mappings ([ZEP-0079](./ZEP-0079.md)). Each exported mapping
additionally records:

- the adapter value reference, which must itself be exported and resolvable to separately
  compiled consumers;
- the external type `W` in source-level form, for diagnostics and schema consumers.

The adapter reference is the qualified name of the exported value, not an inline expression.
`W` is redundant with the adapter's exported type, because the adapter's type arguments determine
it; recording it explicitly is a convenience for diagnostics and schema tools, and consumers must
not treat it as an independent key.

Identity is unchanged. A mapping is identified by the model and the mapped property's identity
([ZEP-0093](./ZEP-0093.md)); the adapter and `W` are representation metadata, like the external
name. Changing the adapter or `W` changes the data format and is an API compatibility concern, but
it does not change the mapping's identity.

This changes the model export record and therefore the API-index representation, governed by
`API_INDEX_SCHEMA_VERSION`. It joins the current unreleased revision if one exists when this is
implemented, and otherwise takes the next revision.

## Compatibility and impact

The change is additive: a model without `via` behaves exactly as before, and `Field<T, V>` and
`AnyField<T>` keep their current meaning and layout. It touches model-body parsing, constant
validation, type checking, generated model operations, metadata, and the library index.

The standard library gains `Converter`, `InvertibleConverter`, and `AdaptedModel`, so
`STANDARD_LIBRARY_API_VERSION` changes under the normal policy. A public model's adapter must be
public and exported, or the model cannot be used from a separately compiled consumer.

## Alternatives

- **A model-only converter syntax** — duplicates the serialization layer's representation concept
  and creates a second mechanism. Rejected.
- **An annotation naming a type literal** — blocked today because annotations cannot carry type
  literals, and [ZEP-0091](./ZEP-0091.md) would still need to define consumption. A value reference
  avoids that dependency.
- **Wrapper newtypes or data classes** — the existing workaround. They remain valid, but they
  create a type per representation and are too heavy for a single field.
- **Fallible converters in the first version** — the model descriptor has no error channel, and
  the fallible surface is better fixed as a `Result`-returning contract. Deferred.
- **Fallible converters as effects** — a descriptor has no row, a per-field row would leak into
  consumers, and effects would allow arbitrary effects in a representation adapter. Rejected; the
  direction is a `Result`.
- **Change `Field<T, V>` to `Field<T, V, W>`** — forces every model consumer and every unmapped
  field to carry an external type parameter. Rejected for the first version.
- **A `MappedField<T, V, W>` view in the first version** — needs the erased descriptor to carry
  the external type or runtime type information; generated adapted-field operations cover the
  need without it. Deferred.
- **Put the adapter and external type in `AnyField`** — forces an erased adapter or runtime type
  descriptors into the descriptor, which this design rejects. Rejected.
- **An application or arbitrary expression after `via`** — cannot be restored from the library
  index without storing and re-evaluating an expression. A value name is already exportable.
  Rejected.
- **Make the converter apply automatically to every mapping** — changes existing models and
  removes the opt-in distinction between a faithful property mapping and a representation change.

## Implementation and validation

1. Add `Converter`, `InvertibleConverter`, and `AdaptedModel` to the serialization standard
   library.
2. Parse `via` on field-mapping clauses and extend constant validation to a named immutable value
   and, when factories exist, an enclosing factory parameter. Reject literals, property references,
   and applications.
3. Resolve the adapter by value name, instantiate `Converter<V, W>`, check the mapped property
   type, and record `W` and the adapter reference.
4. Generate the adapted-field operations in the model singleton when the consumer contract
   requires `AdaptedModel<T>`, resolving `Encode<W>`/`Decode<W>` evidence and requiring it to be
   effect-free. Set the writer only for an invertible adapter with an accessible setter.
5. Export the adapter reference and external type in the library index, and restore them for
   separately compiled consumers.
6. Test: total conversion, invertible conversion and writer presence, one-way conversion and
   writer absence, nullable property types, each nullability combination above, inaccessible
   adapter, non-converter value, duplicate `via`, `via` on an assignment clause, an application
   after `via`, a literal after `via`, adapted operations through `AdaptedModel`, absence of
   adapted operations for plain fields, unresolved external evidence, effectful external evidence,
   adapter across separate compilation, and a model whose field type and external type differ.

Sequencing is settled: [ZEP-0079](./ZEP-0079.md) and [ZEP-0092](./ZEP-0092.md) are implemented and
shipped in `0.6.0`, and this proposal extends them rather than waiting on them. It supplies the
model consumer contract that [ZEP-0092](./ZEP-0092.md) left to a follow-up.
[ZEP-0091](./ZEP-0091.md) is not required for the core: `via` names a value, and reusing the
adapter in serialization derivation is a later, separate integration. Factory parameters become
valid `via` names when [ZEP-0102](./ZEP-0102.md) is implemented, with no syntax change here.

## Resolved questions

| Question | Decision |
| --- | --- |
| Should the first version define a `MappedField<T, V, W>` view? | No. Generated adapted-field operations through `AdaptedModel` cover the need; `Field` keeps two type parameters and the descriptor stays erased. |
| Should a fallible adapter return a `Result`, or raise an effect? | `Result`, through `TryConverter` / `TryInvertibleConverter`; effects are rejected. This is future work. |
| Should `via` accept a model-factory application as a constant? | No. `via` accepts a value name only: a public top-level immutable value, an enclosing factory parameter, or a model value supplying `Converter`. No applications, literals, or property references. |
| Does the external type `W` belong to mapping identity? | No. Identity is the model plus the property identity; adapter and `W` are representation metadata and compatibility concerns. |
| How should a nullable external type interact with a non-nullable property? | The converter owns nullability; `V` and `W` express it; the compiler inserts no branch; the format sees only `W` and handles null only when `W` is nullable. |

## Decision

The design questions raised in earlier drafts are resolved as recorded above, and this is the
implementation scope. This proposal is Accepted. It extends the shipped [ZEP-0079](./ZEP-0079.md)
and [ZEP-0092](./ZEP-0092.md) surfaces; the core does not depend on [ZEP-0091](./ZEP-0091.md), and
factory parameters become available with [ZEP-0102](./ZEP-0102.md).
