## Abstract

[ZEP-0079](./ZEP-0079.md) models are singletons, so a model cannot be generic. A generic target must
be fully instantiated, and a generic model declaration is explicitly unsupported. That leaves
generic containers without a model when their representation is not the canonical serialization
covered by `deriving Codec`.

This proposal introduces **model factories**: parameterized model declarations that take type
parameters and model-value parameters and return an ordinary model value.

```zeron
model PageJson<T>(item: JsonModel<T>) is JsonModel<Page<T>> {
    items -> "items";
    total -> "total";
}
```

used as `PageJson(UserJson)`. A factory is a generic function from models to models, not a generic
singleton. The result is a model value for `Page<User>`, with the same descriptor, identity, and
lookup rules as any other model.

The proposal is deliberately conservative. It does not add generic singletons, monomorphization,
implicit resolution, or model construction. It is recorded as a Draft because the benefit is
narrower than the effort until a concrete consumer needs generic model composition.

## Motivation

Generic containers are common: API envelopes, pagination results, event wrappers, and typed rows.
When the container's canonical representation is sufficient, `deriving Codec`
([ZEP-0092](./ZEP-0092.md)) already covers it. A generic model is needed when:

- the representation is not the canonical one (a custom envelope or a persistence row shape), and
- the element representation is supplied by the caller rather than known at the container's
  declaration.

Today the only workarounds are:

- write a separate model for each instantiation (`PageJsonUser`, `PageJsonOrder`, …), which does not
  scale;
- use a hand-written consumer that builds the descriptor, which requires public descriptor
  construction that [ZEP-0079](./ZEP-0079.md) deliberately rejected; or
- give up on the model and use a canonical codec.

Model composition is also a prerequisite for generic sums: a case such as `Some(value: T)` needs a
model of the case payload parameterized by `T`. [ZEP-0103](./ZEP-0103.md) defers generic sums until
this question is settled.

## Goals

- Allow a model declaration to take type parameters and model-value parameters.
- Make the declaration denote a generic function value from models to models.
- Infer type arguments from model arguments and the expected consumer contract.
- Keep typed field lookup working for the instantiated target.
- Export the factory and its mappings for separate compilation.
- Preserve the rule that a model name is a first-class value and is never implicitly resolved.

## Non-goals

- Generic singleton models, where one model name denotes one polymorphic value.
- Monomorphization of models per instantiation.
- Implicit, type-directed model resolution.
- Model construction, decoding, or automatic CRUD.
- A public model-builder API that lets arbitrary code fabricate descriptors.
- Generic sums in this proposal; [ZEP-0103](./ZEP-0103.md) builds on this.
- Changing `zeron.lang.Model<T>` or its lookup semantics.

## Proposal

### Declaration form

```zeron
// illustrative
public model PageJson<T>(item: JsonModel<T>) is JsonModel<Page<T>> {
    items -> "items";
    total -> "total";
}
```

- `T` is an ordinary type parameter of the declaration.
- `item` is a model-value parameter. Its type is a model contract applied to `T`.
- The target is a fully applied generic type built from `T` and the enclosing declaration's
  parameters. `Page<T>` is valid; a partially applied or raw `Page` is not.
- The body maps properties of the target exactly as a non-generic model does. A property whose type
  mentions `T` has that type under the declaration's type parameter; `Page<T>::items` has type
  `Array<T>`, and its field is `Field<Page<T>, Array<T>>`.
- Parent-contract assignments may use factory parameters and constants. Assigning the element model
  to a contract property is allowed:

  ```zeron
  public contract JsonModel<T: nullable + mut> requires Model<T> {
      property itemModel: Option<JsonModel<T>>;
  }

  public model PageJson<T>(item: JsonModel<T>) is JsonModel<Page<T>> {
      itemModel = item;
      items -> "items";
  }
  ```

### Semantics

- The factory name denotes a **generic function value**, not a model singleton. Its type is
  `(JsonModel<T>) -> JsonModel<Page<T>>`, generic in `T`.
- Each application returns a new model value implementing `Model<Page<T>>` (or the declared
  consumer contract). The value's field identities are the same `PropertyId`s a direct model would
  record, because identity is the property declaration, not the model instance.
- Applying the factory twice with the same arguments produces two equal-behaving model values but
  not the same object. Models have no declared equality, so this is not observable through a model
  contract; it is observable through reference identity (`===`), which consumers must not use to
  identify a mapping.
- `field(ref)` and `fields` work unchanged. The descriptor is built from the factory's mappings and
  the model arguments.
- No implicit resolution is introduced. The factory is always applied explicitly, preserving
  [ZEP-0079](./ZEP-0079.md)'s coherence and orphan-model properties.
- A factory may be stored, passed, and returned as an ordinary function value, subject to the
  existing rank-1 generic-function rules.

### Inference and application

```zeron
database.from(PageJson(UserJson)).where(...);
```

- `T` is inferred from the model-value argument and, when present, the expected consumer contract.
  If the arguments and context do not determine every type parameter, the call is an error and
  requires explicit type arguments.
- A factory call may use explicit type arguments when the language's generic-call syntax permits
  it. This is the escape hatch for an unconstrained `T`.
- Model arguments are ordinary values; they are not implicitly derived or looked up globally.

### Identity and export

- The factory declaration has its own identity, analogous to a generic function: qualified name
  plus type-parameter arity. It is exported as a generic declaration, not as a `ValueExport` for a
  singleton.
- Each mapping still records the `PropertyId` of the target property and the external name, as in
  [ZEP-0079](./ZEP-0079.md). No new per-field identity is introduced.
- The factory's model parameters and their contracts are part of the export, so a separately
  compiled consumer can type-check an application and construct the descriptor.
- The mapping metadata is attached to the factory, not to a runtime model instance. A consumer that
  applies the factory gets a descriptor built from that metadata at runtime.

This requires a new export record (a model factory) and therefore an `API_INDEX_SCHEMA_VERSION`
change. It is a larger index change than a non-generic model, which is one reason the proposal is
not scheduled.

### Restrictions

- A factory cannot be a singleton; there is no `PageJson` value without a model argument unless the
  declaration has no model parameters, in which case it is just a model.
- A factory cannot partially apply its model parameters in the first version. All model parameters
  are supplied at once, and type arguments may be explicit or inferred.
- A factory's target type must be fully applied with its type parameters; `Page<T>` is valid,
  `Page` is not.
- The factory body may not construct the target, use reflection, or inspect the element model
  beyond its contract.
- A model factory is not a type. It denotes a function value; the model value it returns is the
  model.

### Generic sums

[ZEP-0103](./ZEP-0103.md) maps sum cases with `via`, and a case such as `Some(value: T)` needs a
model for its payload. A factory application is the natural `via` expression:

```zeron
model OptionJson<T>(item: JsonModel<T>) is JsonSumModel<Option<T>> {
    discriminator = "kind";
    Some -> "some" via SomeJson(item);
    None -> "none";
}
```

This proposal does not define the sum grammar or case identity; it only requires that a factory
application be accepted as a constant model value when that proposal is implemented.

## Compatibility and impact

The declaration form is additive. Existing models and consumers are unchanged. The new export
record and the runtime construction of descriptors change the library index and are governed by
`API_INDEX_SCHEMA_VERSION`.

A factory's type parameters and model parameters are part of its public signature. Changing them,
or changing a mapping or external name, changes the representation and is a public API change.
Unlike a singleton model, the factory has no single exported value; its descriptor is built when
applied.

Tooling impact is significant: member discovery, the language server, and documentation need to
describe a factory as a generic model declaration, not as a value. That is a second reason to defer
implementation until a consumer justifies it.

## Alternatives

- **Generic singleton models** — one name denotes a polymorphic model value. Zeron has no general
  polymorphic values, and per-instantiation identity would be ambiguous. Rejected.
- **Monomorphized model instances** — generate a singleton per instantiation. Avoids runtime
  descriptor construction but multiplies artifacts and requires cross-library instantiation.
  Rejected for the first version.
- **A public model-builder API** — lets libraries construct descriptors for generic containers
  without new syntax. Rejected because it undermines the “models are declarations” tooling story
  and reopens compiler-only descriptor construction.
- **Separate models per instantiation** — works today but does not scale and duplicates mappings.
  This is the workaround the proposal is meant to replace.
- **No generic models** — viable. `deriving Codec` covers canonical generic containers, and custom
  generic representations remain in consumer code. This is the fallback if the effort is not
  justified.

## Implementation and validation

1. Extend the model grammar with type parameters and model-value parameters, and distinguish the
   factory declaration from a singleton model.
2. Resolve the target as a fully applied generic type and check that each mapped property's type is
   well formed under the factory's type parameters.
3. Lower the factory to a generic function value that constructs the descriptor from its mapping
   metadata and model arguments.
4. Infer type arguments from model arguments and the expected contract; diagnose unresolved
   parameters.
5. Add the model-factory export record and restore it for separately compiled consumers.
6. Test: generic target, element-model composition, inference and explicit arguments, ambiguous
   inference, storage and passing of the factory, field lookup on the produced model, separate
   compilation, and a generic factory used as a `via` model in a sum model.

This proposal is a design record only. The initial [ZEP-0079](./ZEP-0079.md) model surface is
implemented but is still being validated. Implementation should wait until that surface is
stabilized, and should follow [ZEP-0101](./ZEP-0101.md) and [ZEP-0103](./ZEP-0103.md) if those
proposals are accepted first. The recommendation is to **defer** this work until a concrete
consumer requires generic model composition.

## Open questions

- Should the declaration use `model PageJson<T>(item: ...)` or a separate `model factory` keyword?
  The former reuses `model`; the latter keeps the singleton meaning unambiguous.
- Does a factory application need a stable identity for caching or diagnostics, or is the factory
  declaration plus arguments enough?
- Can a factory be partially applied, or must all model parameters be supplied at once?
- How should a factory application be used as a `via` target in a sum model without making the sum
  model's export depend on a runtime call?
- Should a factory's produced model be comparable by structural equality? [ZEP-0079](./ZEP-0079.md)
  defines no model equality, so this is currently unobservable.
- Is the model-factory export worth the index complexity, or should generic containers stay with
  canonical codecs and consumer code?
