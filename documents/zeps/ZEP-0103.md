## Abstract

[ZEP-0079](./ZEP-0079.md) models describe how a **nominal type's properties** map to an external
representation. A closed sum type has no properties; it has cases. Its external representation is
therefore a tagged alternative, not a record.

This proposal adds sum models: a separate model contract whose descriptor names a discriminator
and maps each declared case to an external tag, optionally delegating the case payload's
representation to another model:

```zeron
public model ShapeJson is JsonSumModel<Shape> {
    discriminator = "type";

    Circle -> "circle" via CircleJson;
    Square -> "square" via SquareJson;
    Empty  -> "empty";
}
```

Sum models are total over the closed set of cases. They introduce case identity (`CaseId` and
`CaseRef`), an erased `AnyCase<T>`, a typed `Case<T, C>`, and a `SumModel<T>` contract parallel to
`Model<T>`.

## Motivation

Sum types are nominal, closed, and exhaustively matchable. Their canonical serialization is defined
by [ZEP-0092](./ZEP-0092.md) as `beginAlternative(tag)` with the case's own representation. Models
exist for **additional** representations: a document schema that uses a different discriminator
name, a persistence format that flattens a case, or a consumer that needs the case structure rather
than a stream.

A property-based model cannot express this. A sum has no properties to map, and `Model<T>`'s
`fields` array is the wrong shape. Trying to reuse it would either produce an empty descriptor or
force case information into a property-shaped API, both of which misrepresent the type.

The design also has a natural composition story: a case payload is a generated case class, which
is nominal and has properties, so a `Model<Circle>` can describe it. The sum model only needs to
name the case and its tag, and delegate the payload to that model.

## Goals

- Define a model contract for closed sum types, separate from `Model<T>`.
- Give each case a stable identity and a typed reference.
- Map each case to an external tag and optionally to a payload model.
- Require the mapping to be total over the sum's declared cases.
- Record the descriptor and nested models in the library index for separate compilation.
- Keep the sum declaration, its case classes, and its runtime representation unchanged.

## Non-goals

- Sealed contracts or open class hierarchies. They are considered separately below.
- Generic sums in this proposal; `Option<T>` needs [ZEP-0102](./ZEP-0102.md) for its case models.
- A representation for unknown cases. [ZEP-0092](./ZEP-0092.md) leaves that to the format adapter.
- Construction, decoding, or automatic CRUD.
- Changing `deriving Codec` or the canonical sum serialization.
- Defining annotation values; case metadata uses the `SUM_CASE` target of
  [ZEP-0098](./ZEP-0098.md) when needed.
- Reflection or runtime discovery of cases.

## Proposal

### Declaration form

```zeron
public model ShapeJson is JsonSumModel<Shape> {
    discriminator = "type";

    Circle -> "circle" via CircleJson;
    Square -> "square" via SquareJson;
    Empty  -> "empty";
}
```

- `discriminator = "value"` is an ordinary parent-contract assignment, using the existing constant
  rules. The contract declares the property.
- `Case -> "tag"` maps a declared sum case to its external tag. The left side is a case name, not a
  property reference.
- `via ModelExpr` is optional. It delegates the case payload's representation to a model value. It
  is required for a case with a payload and is omitted for a nullary case.
- The target `Shape` is the sum declaration itself, not a generated case class. Each case has its
  own model when delegation is used.

`JsonSumModel<T>` is an illustrative consumer contract that requires `SumModel<T>`, in the same way
`JsonModel<T>` requires `Model<T>` ([ZEP-0079](./ZEP-0079.md)). The compiler knows nothing about
JSON; a consumer contract supplies the discriminator property and any format-specific metadata.

### Contracts

```zeron
// illustrative
public contract SumModel<T: nullable + mut> {
    property discriminator: String;
    property cases: Array<AnyCase<T>>;

    default caseOf(id: CaseId): Option<AnyCase<T>>;
    default case<C: nullable + mut>(ref: CaseRef<T, C>): Option<Case<T, C>>;
}

public class AnyCase<T: nullable + mut> {
    public property tag: String;
    public property sourceId: CaseId;
}

public class Case<T: nullable + mut, C: nullable + mut> {
    public property tag: String;
    public property sourceId: CaseId;
    public property source: CaseRef<T, C>;
    public property representation: Option<Model<C>>;
}
```

- `SumModel<T>` is parallel to `Model<T>` and is not a supertype or subtype of it. A consumer that
  accepts both kinds should use separate contracts or a common marker with two sub-contracts.
  A contract cannot conditionally require `Model<T>` or `SumModel<T>`.
- `AnyCase<T>` is the erased view used by `cases`. It carries the external tag and the case
  identity, but not the payload type.
- `Case<T, C>` is the typed view. `C` is the generated case class type. `representation` is the
  nested model when `via` is present; a nullary case has `None`.
- `CaseRef<T, C>` is a compiler-constructed, statically resolved reference to a case, analogous to
  `PropertyRef`. It exposes `get(value: T): Option<C>` and the case identity. A consumer obtains one
  by writing `Shape::Circle` (see below), and lookup uses identity.

### Case identity

A new non-generic `CaseId` identifies a case declaration:

```zeron
public class CaseId is Eq<CaseId>, Hashable<CaseId> {
    public property owner: String;   // the sum's qualified name
    public property name: String;    // the case name

    public text(): String = this.owner + "#" + this.name;
}
```

- Identity is the declaring sum plus the case name. Type arguments are not part of it, consistent
  with `PropertyId`.
- `CaseRef<T, C>.id` is a `CaseId`; `AnyCase.sourceId` and `Case.sourceId` carry it.
- Equality is identity equality. The compiler constructs instances through an unspellable factory,
  as for `PropertyId` and `PropertyRef`.
- A property of a case class still has its own `PropertyId`; the case identity is a distinct
  concept. This avoids overloading `PropertyId` with a member it does not describe.

### Syntax for `CaseRef`

The reference form is `Sum::Case`:

```zeron
let circle: CaseRef<Shape, Circle> = Shape::Circle;
```

This reuses `::` and resolves a case name on a sum type. It does not collide with property
references because a sum is not a class or contract and has no properties. If
[ZEP-0100](./ZEP-0100.md) is accepted, the resolver must distinguish case names from callables on
the same owner; a sum owner has cases only, so the rule is unambiguous.

### Totality, duplicates, and tags

- **Every declared case must be mapped exactly once.** The compiler knows the closed set of cases.
  An omitted case or a duplicate case is an error. This differs from class models, which are
  partial, and is justified by the closed set: an unmapped case has no discriminator value, so a
  partial sum model cannot describe the type.
- **Tags must be distinct.** Duplicate external tags are rejected. For a discriminator-based
  representation, the tag is the dispatch key; duplicates are meaningless. This is stricter than
  class models, where duplicate external field names are left to the consumer.
- A nullary case may omit `via`; a payload-bearing case must supply it. A payload-bearing case with
  `via` omitted is an error, because the tag alone does not describe the payload.
- An unknown case name, a case from another sum, or a case listed under the wrong owner is an
  error naming the sum and the case.

### Payload delegation

- `via` expects a model value whose contract is `Model<C>` (or a consumer contract that requires
  it), where `C` is the case's generated class type.
- The case class exposes the payload fields as properties, so the nested model is an ordinary
  property model:

  ```zeron
  public model CircleJson is JsonModel<Circle> {
      radius -> "r";
      center -> "c";
  }
  ```

- The nested model is a constant: a model name, a model value, or a model-factory application
  ([ZEP-0102](./ZEP-0102.md)). It is recorded in the sum model's export and must be resolvable by
  separately compiled consumers.
- The nested model's contract is checked against the case class. A model for the wrong case is an
  error.
- A nested model may itself be a sum model if the case payload is a sum. This composes without
  special handling.

### Recursive sums

A recursive sum such as an expression tree has cases whose payloads contain the sum. A case model
may need to refer back to the sum model:

```zeron
public model ExprJson is JsonSumModel<Expr> {
    discriminator = "kind";
    Literal -> "literal" via LiteralJson;
    Add     -> "add" via AddJson;   // AddJson may refer to ExprJson
}
```

Direct recursion is expected to be expressible through a model reference, as with recursive
derived codecs in [ZEP-0092](./ZEP-0092.md). Mutual recursion between models needs a forward
reference or a declaration group; whether the first version supports it is an Open question.

### Sealed contracts

Sealed contracts are **not** part of the first version. They are closed for matching but their
implementors may be declared across libraries. A sum model would need a recorded, closed implementor
list, and adding an implementor in another library would silently change the model's totality. That
is a compatibility hazard that the native sum declaration avoids.

If sealed-contract models are pursued later, they should require a closed-world opt-in recorded in
the library index, and adding an implementor must be a breaking change for the model.

### Errors and paths

A nested model's errors keep their own external names. When a failure occurs inside a case payload,
the case tag is the path segment that identifies the alternative, following the sum error-path rule
of [ZEP-0092](./ZEP-0092.md). The sum model does not invent a second error vocabulary.

### Annotations

Per-case metadata such as aliases or legacy tags can be attached with a `SUM_CASE` annotation
([ZEP-0098](./ZEP-0098.md)) once annotation consumption ([ZEP-0091](./ZEP-0091.md)) defines how it
is read. This proposal uses the clause grammar for the primary tag and does not define annotation
values.

## Compatibility and impact

The change is additive: `Model<T>`, existing models, and derived sum serialization are unchanged.
It adds standard-library contracts and classes (`SumModel`, `AnyCase`, `Case`, `CaseId`,
`CaseRef`), so `STANDARD_LIBRARY_API_VERSION` changes.

The library index gains a sum-model export record, including the discriminator, case tags, case
identities, and nested model references. This changes the API-index representation and is governed
by `API_INDEX_SCHEMA_VERSION`.

Adding a case to a public sum is a source-breaking change for every sum model of that sum, because
totality is required. This is the correct consequence of a closed representation and should be
documented as an API compatibility rule. Changing a tag or a nested model changes the external
representation and is likewise a compatibility concern.

## Alternatives

- **Extend `Model<T>` with sum cases** — forces a property-shaped API onto a non-property type and
  gives class models a meaningless case array. Rejected.
- **Rely on `deriving Codec` for sums** — covers only the canonical representation, with
  derivation-owned tags and no per-case model structure. Rejected as the only mechanism; it remains
  the canonical path.
- **Annotations only, no case clauses** — cannot express per-case delegation to a model, which is
  the main new capability. Rejected.
- **Sealed-contract models in the first version** — open-world closure and library-index
  compatibility hazards. Deferred.
- **Allow partial sum models** — an unmapped case has no tag, so the descriptor would silently
  misrepresent the type. Rejected in favor of totality.
- **Reuse `PropertyId` for cases** — a case is not a property of the sum, and a case payload's
  properties already have their own identities. Rejected in favor of `CaseId`.

## Implementation and validation

1. Parse the sum-model form: discriminator assignment, case clauses, optional `via`, and case
   references on a sum type.
2. Resolve the target as a native sum, the case set, each nested model, and the parent-contract
   properties. Reject unknown, duplicate, and missing cases.
3. Add `SumModel<T>`, `AnyCase<T>`, `Case<T, C>`, `CaseId`, and `CaseRef<T, C>` to the standard
   library, with compiler-only construction for identities and references.
4. Generate the sum-model singleton: `discriminator`, `cases`, `caseOf`, and `case`, with the
   typed case view and nested model values.
5. Export the sum-model record and restore it for separately compiled consumers, including nested
   model references.
6. Test: every case kind, nullary and payload cases, duplicate and missing cases, duplicate tags,
   wrong nested model, nested sum, recursive sum, separate compilation, case lookup by identity,
   error paths, and a consumer contract parallel to `Model<T>`.

This proposal is a design record only. The initial [ZEP-0079](./ZEP-0079.md) model surface is
implemented but is still being validated. Implementation should wait until that surface is
stabilized, and should follow [ZEP-0098](./ZEP-0098.md) for case annotations and
[ZEP-0102](./ZEP-0102.md) for generic sums.

## Open questions

- Should `SumModel<T>` be a subtype of a shared marker contract with `Model<T>`, or remain entirely
  separate? A marker would let a consumer accept “some model” without knowing the shape, but would
  also invite field/case confusion.
- Should a nullary case's `representation` be `None` or a trivial empty model? `None` avoids
  requiring an empty model declaration but makes the typed view optional.
- Can a sum model be recursive directly, and what forward-reference rule is needed for mutually
  recursive sums?
- Should an unknown-case policy be expressible on the sum model, or must it remain a format-adapter
  option as [ZEP-0092](./ZEP-0092.md) currently says?
- How should generic sums be expressed: a generic sum model, a case model factory, or both? This
  depends on [ZEP-0102](./ZEP-0102.md).
- Should sealed-contract models be supported at all, and if so what closed-world index rule makes
  adding an implementor safe?
