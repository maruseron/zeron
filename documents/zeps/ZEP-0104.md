## Abstract

This exploration asks whether Zeron should support **bounded existential types**: types that hide a
type argument behind a name and a set of capabilities, so values of different argument types can be
stored together and used through those capabilities.

```zeron
// illustrative
let fields: Array<exists V: Encode. Field<Page, V>> = ...;
for (field in fields) {
    open (typed, evidence) = field;
    encodeField(typed, evidence, encoder);
}
```

Existentials are the dual of universal quantification. Zeron already has generic methods, bounded
rank-1 generic function values, and use-site projections that behave like limited existential views.
What it does not have is a general type former for “a value of some unknown type that provides
these capabilities.”

The immediate motivation is model field iteration. `AnyField<T>` erases a mapped property's value
type, so a generic consumer cannot read or encode a field without knowing the property. A bounded
existential would let a model expose `Array<exists V: Encode. Field<T, V>>` and let a consumer open
each element, with the evidence carried alongside the value.

No implementation is proposed here. This is a research record, like
[ZEP-0032](./ZEP-0032.md), and it should not block any other work.

## Motivation

Zeron erases generic arguments at runtime. Static types preserve the correspondence between a
property and its value, but a runtime collection cannot. The existing workarounds are manual
existentials:

- `AnyField<T>` stores `externalName` and `sourceId` but not the value type or its reader.
- A visitor can recover `V` only if the model dispatches and supplies the evidence, and then only
  for a specific capability contract.
- A consumer can use `fieldOf(id)` to find a mapping, but the typed lookup `field(ref)` requires the
  consumer to know the property and therefore `V`.

These workarounds are adequate for today's models, but they do not generalize. The same shape
appears whenever a program needs a heterogeneous collection of values with a shared capability:

- a UI tree of widgets with different state types, all renderable;
- a plugin or extension registry of handlers with different payload types, all processable;
- an erased handle whose type parameter is irrelevant to the code that stores it;
- a model field collection whose elements have different value types but shared serialization
  evidence.

Existentials are also the principled explanation of why `AnyField` exists and what a more general
replacement would look like. That makes the exploration useful even if the conclusion is “do not
add them.”

## Goals

- Decide whether Zeron needs general existential types, and for which concrete programs.
- Define a candidate syntax and semantics for bounded existentials.
- Specify packing and opening, including the escape rule for the fresh type variable.
- Decide how evidence for the bound is represented and carried.
- Evaluate erasure, runtime cost, variance, effects, pattern matching, and separate compilation.
- Compare existentials with projections, reification, visitors, and manual erased wrappers.
- Identify which use cases are served by simpler generated APIs and which are not.

## Non-goals

- Implementing existential types in this proposal.
- General runtime reflection or dynamic member access ([ZEP-0032](./ZEP-0032.md)).
- Runtime reification of generic type arguments ([ZEP-0015](./ZEP-0015.md)).
- Dynamic plugin loading, discovery, or a registry protocol.
- Higher-rank polymorphism in general; the proposal is about existential quantification.
- Changing `AnyField`, `Model`, or property references as part of the exploration.
- Replacing the existing use-site projections of [ZEP-0052](./ZEP-0052.md).

## Proposal

### Candidate syntax

Two families are worth comparing:

1. **Prefix quantification**:

   ```zeron
   exists V: Encode. Field<Page, V>
   ```

2. **Trailing quantification**:

   ```zeron
   Field<Page, V> forSome { V: Encode }
   ```

Prefix form is easier to read and nests more predictably. It does introduce a new keyword;
`exists` is not currently reserved, so using it as a hard keyword would break existing identifiers.
A soft or contextual keyword, or a symbol-led form, avoids that source break. The choice is left
open.

Multiple bounds and nullability/mutability markers should follow generic-parameter syntax:

```zeron
exists V: nullable + mut + Encode. Field<Page, V>
```

### Packing

Packing introduces an existential value from a concrete value:

```zeron
let concrete: Field<Page, Instant> = pageField;
let packed: exists V: Encode. Field<Page, V> = pack(concrete);
```

Packing must supply the bound's evidence. If the concrete type's evidence is available at the
packing site, the compiler can build the dictionary; otherwise packing is an error. Implicit
packing (assigning a concrete value where an existential is expected) is ergonomic but hides the
evidence requirement and the runtime dictionary. The exploration should compare explicit and
implicit packing.

### Opening and the escape rule

Opening eliminates an existential:

```zeron
open (value, evidence) = packed;
// value: Field<Page, V#>, where V# is a fresh rigid type
// evidence: Encode<V#>
use(value, evidence);
```

The fresh type variable:

- is abstract: only the bound's operations are available;
- cannot escape the opening scope, including into the result type, a mutable binding, a closure
  that outlives the scope, or a stored field;
- is distinct for each opening, even for two values packed from the same concrete type.

The escape rule is the central soundness condition. It is also the main usability constraint: a
function cannot return the opened value, only a result computed from it. That is enough for
rendering, encoding, and folding, but not for returning a heterogeneous value.

### Evidence and runtime representation

A bounded existential value carries:

- the value, erased to the bound's erased type (or `Object` if unbounded);
- one evidence dictionary per bound, describing the operations available for the hidden type.

For `exists V: Encode. Field<T, V>`, the runtime value is a pair of an erased `Field` and an
`Encode` witness. This is not free: packing allocates or reuses a dictionary, and opening passes it
to the consumer. Unbounded existentials carry no evidence and are therefore nearly useless in
Zeron, where an unknown type offers no operations and there is no safe cast. The exploration should
treat bounded existentials as the primary design.

If the bound is a reference type, erasure to the bound means no additional wrapper is needed for
the value itself. A JVM implementation can represent the pair as a small generated holder or as a
tuple-like runtime object. The design must state whether packing is observable through reference
identity.

### Variance and projections

- Existential types are invariant in the hidden variable. `exists V. F<V>` is not interchangeable
  with `F<Int>` or with `F<String>`.
- `Array<F<Int>>` is not an `Array<exists V. F<V>>` unless the array type and the existential's
  subtyping rules say so. Arrays are invariant in Zeron, which makes the safe rule simple.
- [ZEP-0052](./ZEP-0052.md) already provides `out T` and `in T` projections, described there as
  existential views. This exploration must explain the relationship: projections are a restricted,
  declaration-directed view of an unknown argument; general existentials add explicit packing and
  opening. The proposal should not introduce a second, incompatible notion of “unknown type.”
- If `F` is covariant, `exists V: Bound. F<V>` may have a subtyping relationship with
  `exists V: Bound. G<V>` when `F` and `G` relate pointwise. This is likely too complex for a first
  version and should be explicitly deferred.

### Pattern matching and reification

An opened variable is opaque. Zeron cannot test whether it is `Int` without runtime type
information, and generic arguments are erased. Therefore:

- an existential can be matched only against its bound's operations, not against its hidden type;
- “type-bound pattern matching” on an existential requires reified type arguments
  ([ZEP-0015](./ZEP-0015.md)) and is not provided by existentials alone;
- a `match` on an existential is either rejected or treated as a binding of the opened value with
  the bound's capabilities.

This boundary should be stated clearly so that existentials are not oversold as a replacement for
reification.

### Use cases

| Use case | Fit | Notes |
| -------- | --- | ----- |
| Heterogeneous collections of capability-bearing values | Strong | `Array<exists V: Render. Widget<V>>`; open and render each element. |
| Model field iteration | Strong with a bound | `Array<exists V: Encode. Field<T, V>>`; the model must supply the evidence for every field. |
| Erased handles | Plausible | A handle whose type parameter is irrelevant to storage, with operations through the bound. |
| Plugin registries | Necessary but not sufficient | Existentials store heterogeneous plugins; discovery, loading, and lifecycle need a registry and possibly reflection. |
| Type-bound pattern matching | Requires reification | Erasure prevents testing the hidden type; see [ZEP-0015](./ZEP-0015.md). |
| Ad-hoc “any value” containers | Weak | Without a bound or reflection, an unknown value supports no operations. |

The model case is the most concrete near-term motivation. It should be prototyped against a real
model field collection before deciding that the language feature is justified.

### Relationship to `AnyField` and the model field gap

`AnyField<T>` is a manual existential with no bound: it hides `V` and offers only name and identity.
`Field<T, V>` recovers `V` but only through a typed lookup that the consumer must already know.

A general existential would allow a model to expose a stronger collection:

```zeron
public contract EncodeModel<T: nullable + mut> requires Model<T> {
    property encodableFields: Array<exists V: Encode. Field<T, V>>;
}
```

The model singleton would pack each field's typed view with its evidence. A consumer would open
each element and call `encode`. This is the elegant version of the visitor discussed in the model
extension analysis.

It does not remove the evidence requirement. The model must still guarantee `Encode<V>` for every
mapped field, either by declaration-site evidence or by a failed conformance. `AnyField` would
remain useful for name/identity-only iteration, where no value is read.

## Compatibility and impact

If adopted, existential types affect:

- parsing and type syntax, including keyword reservation and type formatting;
- the type system: quantification, packing, opening, the escape rule, variance, and inference;
- erasure and bytecode: evidence dictionaries and their ABI;
- library metadata: existential types in public signatures, bounds, and evidence;
- diagnostics: escape errors, missing evidence, and ambiguous packing;
- interaction with generics, nullability, mutability, effects, and projections.

The feature is large. It should be evaluated against concrete programs and a prototype before any
source syntax is accepted. Runtime and artifact costs must be measured, not assumed.

The exploration does not change existing code. If it concludes that existentials are not
justified, the manual wrappers (`AnyField`, visitor-like APIs, generated per-field operations)
remain the supported answer.

## Alternatives

- **Manual erased wrappers** — `AnyField` and similar types. Works today, but each wrapper is
  bespoke and loses the ability to apply a bound generically.
- **Visitor or double dispatch** — recovers the type at a dispatch site, but requires the dispatcher
  to know the capabilities in advance, and one visitor per capability. Less general, but much
  smaller.
- **`Any` plus casts** — requires runtime checks and a cast system; conflicts with Zeron's
  no-reflection direction and is unsafe.
- **Use-site projections** — [ZEP-0052](./ZEP-0052.md) provides restricted unknown-argument views
  but not general packing/opening of arbitrary values.
- **Runtime reflection** — [ZEP-0032](./ZEP-0032.md) would answer different needs (discovery and
  dynamic invocation) and carries metadata and ABI costs.
- **No existentials** — keep generated per-field operations and manual wrappers. This is a viable
  outcome and should be compared honestly against the cost of a new type former.

## Implementation and validation

Exploration stages, not an implementation commitment:

1. Write the motivating programs in current Zeron and record where they fail: a heterogeneous
   renderer, a model field encoder, and an erased handle.
2. Specify the candidate type former, packing, opening, and the escape rule on paper; check
   soundness by hand for closures, mutable bindings, arrays, and effects.
3. Prototype the runtime representation and evidence dictionaries for one or two examples; inspect
   generated bytecode and measure allocation and call overhead.
4. Test the interaction with projections, nullability, mutability, generic bounds, and separate
   compilation.
5. Decide whether the model field case alone justifies the feature, or whether generated per-field
   operations are sufficient.
6. If the answer is yes, write a separate accepted-scope ZEP with concrete syntax, semantics, ABI,
   and index rules.

## Open questions

- What syntax avoids reserving a common identifier while remaining readable?
- Is packing explicit, implicit, or both? How is evidence supplied at the packing site?
- Does opening bind a value and evidence as a pair, or introduce a limited scope with operations?
- How is the escape rule enforced for closures, mutable bindings, arrays, and effect handlers?
- How are multiple bounds and their evidence dictionaries represented?
- Do existentials need variance or pointwise subtyping in the first version, or can they be
  invariant and non-subtyping?
- How do existential types appear in public signatures and the library index?
- Is the runtime evidence dictionary cached, allocated per pack, or shared through the witness
  mechanism?
- Does the model field case justify the feature, or is a generated per-field operation enough?
- If reification ([ZEP-0015](./ZEP-0015.md)) lands first, does it change the design?
