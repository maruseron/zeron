## Abstract

This proposal records the work left after the initial existential slice in
[ZEP-0104](./ZEP-0104.md). Its primary feature is **pattern-scoped opening**:

```zeron
if (box is Box<let T>) {
    // box has type Box<T> here; T is a fresh rigid type variable
}
```

`C<let T>` opens the hidden argument of an applied type for the true branch. It does not recover a
runtime type identity. It introduces a fresh type variable for the branch, inheriting only the
bounds, markers, descriptors, and evidence that the source type already carries.

This is not a general skolemized `let`. There is no `let T` in arbitrary type position and no
source-level binding of a skolem type outside a branch. The branch supplies the scope and the
escape boundary.

Rank-2 `use` from [ZEP-0109](./ZEP-0109.md) remains a useful library alternative, but it is not a
dependency of this opening form. Stored existentials are separate in
[ZEP-0106](./ZEP-0106.md). Result positions, escape approximation, variance, and projection sharing
remain later work in this proposal.

**Implementation status (2026-11-10).** None of the opening, result-position, or variance rules
below are implemented. Current Zeron has no star or anonymous existential type arguments, no
pattern-scoped type binder, no rank-2 function type, and only the constrained rank-1 lambda schemes
described in [ZEP-0003](./ZEP-0003.md). The code forms in this draft are illustrative design
sketches, not accepted syntax.

## Revision note

The 2026-11-09 draft assumed a named binder in type position (`<let T: Bound> T`) and a scoped
`open ... as <let T>` form. ZEP-0104 (revised) drops the type-position binder. This revision makes
the pattern-scoped binder the primary opening form and removes the dependency on rank-2 `use`:

- `C<let T>` in a direct `if` or `while` condition opens the applied type's hidden argument for the
  branch.
- The binder inherits the source type's bounds, markers, descriptor, and evidence. It does not
  perform a runtime type test or invent evidence.
- The form is total when the source type is already the applied type; it performs only a raw class
  test when the source type is `Any` or `Any?`.
- `use` over rank-2 is demoted to a library alternative for combinators and higher-order APIs.
- The general skolemized `let` and the earlier `open ... as <let T>` form are not part of this
  revision.
- The `? extends Bound`, `? : markers`, and `F<?>` spellings are obsolete; ZEP-0104 now uses
  `F<*>` and `F<: B + C>`.

## Motivation

ZEP-0104 gives three static tools:

- `F<*>` for reading an unknown argument as `Any?`;
- `F<: B + C>` for an anonymous bounded existential;
- `F<: reified>` for an anonymous existential with a runtime descriptor.

Exact pattern tests can distinguish closed applied types, but they do not give a multi-statement
body a name for an unknown argument. A function such as:

```zeron
fn count(box: Box<*>): Int {
    // What is box.get()?
}
```

can read `box.get()` as `Any?`, but cannot use the unknown argument in a generic operation without
a helper or a rank-2 callback. The opening pattern solves that locally:

```zeron
fn count(box: Box<*>): Int {
    if (box is Box<let T>) {
        return countGeneric(box); // box has type Box<T>
    }
    return 0;
}
```

No runtime type descriptor is needed because `T` is not being recovered; it is a fresh name for the
type argument already present in the static view. This is the same idea as existential elimination:
the branch may use the hidden type abstractly, but the type cannot escape.

The pattern is also the natural way to open an anonymous bounded existential:

```zeron
fn describe(box: Box<: Render>): String {
    if (box is Box<let T>) {
        let value: T = box.get();
        return value.render();
    }
    return "none";
}
```

Here `T` inherits the `Render` bound and its evidence from `Box<: Render>`.

## Goals

- Define `C<let T1, let T2>` as a branch-scoped opening pattern.
- Define binder inheritance from star views, anonymous existentials, projections, concrete
  applications, and `Any`.
- Define branch scoping, flow refinement, and escape rules.
- Keep the form independent of reification and rank-2 polymorphism.
- Define result-position and escape-approximation work separately.
- Preserve projections and stored-existential boundaries.
- Specify effects, nullability, mutability, and patterns with multiple binders.

## Non-goals

- General skolemized `let` in arbitrary type position.
- `open ... as <let T>` blocks.
- Ranking or quantifying an opening across a function value; see [ZEP-0109](./ZEP-0109.md).
- Stored existentials and holder ABI; see [ZEP-0106](./ZEP-0106.md).
- Exact type-bound matching semantics; see [ZEP-0104](./ZEP-0104.md).
- Contract-bound runtime tests; see [ZEP-0108](./ZEP-0108.md).
- Reflection or dynamic type extraction from a descriptor.
- Mixed exact/open patterns and nested opening patterns in the first version.
- An `any Contract` type: contract → conformant subtyping already makes a contract a type for a
  whole value.

## Proposal

### Surface form

The opening pattern is a type-test target in which every type argument is a `let` binder:

```zeron
if (value is Box<let T>) { ... }
if (value is Map<let K, let V>) { ... }
while (queue is Queue<let T>) { ... }
```

Rules:

- The pattern must be the direct condition of an `if` or `while`. It is not supported nested inside
  `&&`, `||`, `!`, or a general expression in the first version.
- Every type argument of the target must be a binder in the first version. Mixed exact/open
  arguments such as `Map<Int, let V>` are deferred because they combine an exact descriptor test
  with opening.
- A binder must name a fresh type variable. Duplicate names in one pattern are an error, and
  shadowing an enclosing type parameter is rejected.
- A binder cannot carry its own bounds or markers in the first version. `Box<let T: Render>` is
  rejected; the source type carries the bound, for example `Box<: Render>`.
- The target must be an applied class or contract type with type parameters. A non-generic type
  cannot use `let`.
- Nested opening patterns such as `Box<Box<let T>>` are deferred.
- `C<let T>` is a pattern-only form. It is not a type that can appear in a variable annotation,
  result, field, or function signature.

### Binder inheritance

The binder is not a runtime reification. It is a fresh rigid type variable whose facts come from
the source type:

| Source type | Binder `T` | Descriptor/evidence |
|---|---|---|
| `Box<*>` | fresh `T` with the star view's upper approximation (`Any?` or the class's declared bounds) | none |
| `Box<: B + C>` | fresh `T` satisfying `B` and `C` | evidence inherited; descriptor if `reified` |
| `Box<: reified>` | fresh `T` with the anonymous existential's bounds | descriptor inherited |
| `Box<out B>` | fresh `T` with upper bound `B` | none |
| `Box<Int>` | `T = Int` | none |
| `Any` / `Any?` | raw class test; fresh `T` with the class's declared bounds and `Any?` as needed | no descriptor or evidence invented |
| `Box<in B>` | rejected in the first version | no lower-bound representation |

More precisely:

- The binder inherits only facts and hidden slots already present in the source type.
- A star view exposes a universal read-only approximation and no descriptor or evidence.
- An anonymous existential with a contract bound has already selected its witness at packing; the
  binder inherits that evidence.
- An anonymous existential marked `reified` has already received its hidden descriptor; the binder
  inherits that descriptor and can use it for exact tests on values of type `T`.
- A raw class test from `Any` proves only the erased class. It does not synthesize a descriptor or
  evidence for the type argument. Class-declaration bounds remain static type facts, but operations
  that need a witness remain unavailable unless the source type carried that witness.
- Opening a concrete application such as `Box<Int>` substitutes the known argument, so no fresh
  runtime variable is needed. The binder is still useful as a local name.

### Branch scope and totality

When the source type is already the applied type, the opening pattern is **total**:

```zeron
fn count(box: Box<*>): Int {
    if (box is Box<let T>) {
        return countGeneric(box); // always taken
    }
    return 0;                     // unreachable
}
```

The compiler can omit the runtime class check and mark the false branch unreachable. When the source
type is `Any` or another supertype, the pattern performs the existing raw class test:

```zeron
fn describe(value: Any): String {
    if (value is Box<let T>) {
        // value has type Box<T>
        return "box";
    }
    return "other"; // reachable
}
```

`T` is in scope only in the true branch. It is available in:

- local variable annotations;
- generic calls;
- local function and lambda bodies that do not escape the branch;
- further type tests that are valid for `T` (for example, exact tests when `T` is reified).

It is not available in the false branch, after the `if` or `while`, or in the condition itself after
the pattern.

### Flow refinement

On the true path, the tested expression is refined to the applied type with the fresh binders
substituted:

```zeron
if (box is Box<let T>) {
    // box : Box<T>
    let value: T = box.get();
}
```

For a direct variable, this uses the existing flow-refinement mechanism. The refinement is
branch-local and is discarded on the false path. If the test is total, the false path is
unreachable.

For `while`, the binder is scoped to the loop body and is not visible after the loop. The existing
while-condition flow rules apply.

### Escape rules

A binder is rigid and branch-scoped. No type mentioning `T` may appear outside the true branch.

Error cases include:

- returning a value of type `T`, `Box<T>`, or any type containing `T` from the enclosing function;
- assigning such a type to an outer binding;
- using `T` in a raised effect that escapes the branch;
- capturing `T` in a closure or function value that escapes the branch;
- storing a value whose type mentions `T` in an outer container or field.

These are allowed:

- local bindings and local containers inside the branch;
- passing values of type `T` to generic calls whose results remain inside the branch;
- calling a generic function that consumes `T` and returns an unrelated type;
- using a branch-local closure that captures `T`, provided the closure does not escape.

The diagnostic should name the pattern binder, for example “type `T` from the opening pattern at
line N escapes the branch through the result type.”

An escaping return is rejected even when the declared result erases the binder:

```zeron
fn leak(box: Box<*>): Box<*> {
    if (box is Box<let T>) {
        return box; // error: Box<T> escapes; re-packing is deferred
    }
    return box;
}
```

Re-packing a branch-local `Box<T>` as `Box<*>` may become legal later, but the first version keeps
the escape rule conservative.

### Relation to reification and exact tests

Opening does not require `reified`. It does not inspect the hidden argument’s runtime identity.
It only gives the branch a name for the static approximation.

If the source type inherited a descriptor, the binder can be used where a reified type is required:

```zeron
fn inspect(box: Box<: reified>): String {
    if (box is Box<let T>) {
        return inspectGeneric(box); // passes T's inherited descriptor
    }
    return "none";
}
```

If the source is `Box<*>`, the binder has no descriptor and cannot be passed to a call requiring a
reified type:

```zeron
fn inspect(box: Box<*>): String {
    if (box is Box<let T>) {
        return inspectGeneric(box); // error: T is not reified
    }
    return "none";
}
```

Exact tests remain ZEP-0104's mechanism. Opening a `Box<: reified>` and then testing values of type
`T` is possible only because `T` inherited the descriptor; opening alone never invents one.

### Examples

Opening a star view and using the unknown type generically:

```zeron
fn size(box: Box<*>): Int {
    if (box is Box<let T>) {
        return sizeGeneric(box);
    }
    return 0;
}

fn sizeGeneric<T>(box: Box<T>): Int = 1;
```

Opening a bounded anonymous existential:

```zeron
fn describe(box: Box<: Render>): String {
    if (box is Box<let T>) {
        let value: T = box.get();
        return value.render();
    }
    return "none";
}
```

Opening multiple arguments:

```zeron
fn describeMap(map: Map<*, *>): String {
    if (map is Map<let K, let V>) {
        let key: K = firstKey(map);
        let value: V = map.get(key);
        return "some";
    }
    return "empty";
}
```

Opening an arbitrary value after a raw class check:

```zeron
fn classify(value: Any): String {
    if (value is Box<let T>) {
        return "box";
    }
    if (value is String) {
        return "string";
    }
    return "other";
}
```

Opening a type that is already known:

```zeron
fn useKnown(box: Box<Int>): Int {
    if (box is Box<let T>) { // T = Int
        let value: T = box.get();
        return value;
    }
    return 0;
}
```

### Opening versus `use`

The branch-scoped pattern is the primary opening form because it needs no rank-2 function type and
has a natural lexical escape boundary.

Rank-2 `use` remains useful for reusable combinators:

```zeron
public extension<T> Box<T> {
    public fn use<R>(f: <U> (Box<U>) -> R): R = f(this);
}
```

This is a sketch using the proposed rank-2 function type from
[ZEP-0109](./ZEP-0109.md); it is not current syntax. `use` is better when the opening operation is a
library API or a higher-order control-flow construct. The pattern is better for local,
multi-statement work and does not require [ZEP-0109](./ZEP-0109.md) to ship.

### Result positions

Result-position anonymous existentials remain a separate question. Opening a value gives `T` only
inside the branch; returning `T` or `Box<T>` is an escape error. Returning an anonymous existential
such as `fn make(): Box<: Render>` would require a holder or carrier for the hidden argument and is
deferred.

Descriptor carriage decides the cost:

- A **non-`reified`** anonymous existential result is erased and needs no new representation.
- A **`reified`** anonymous existential result needs a carrier for the hidden argument's descriptor,
  which is the holder ABI of [ZEP-0106](./ZEP-0106.md).

Result-position anonymous existentials are not required for the opening slice. Whether they are
needed at all remains open.

### Escape: error or approximation

For pattern-scoped opening, the first version uses **error**, not approximation. Java-style
approximation of an escaping variable by its upper bound is a possible later extension:

- **Error** (this proposal): simple, branch-local only; a generic function returning `T` cannot be
  called with an opened value whose result would escape.
- **Approximate by bound**: the result mentions the bound, or an anonymous existential when the
  variable sits in an applied type. Requires existential types in result and local positions.

Approximation is deferred because it interacts with reification and holders. ZEP-0106 would need to
carry the descriptor for an approximated reified variable.

### Anonymous existentials and projections

ZEP-0104 accepts `F<*>` as the unbounded `F<out Any?>` projection and `F<: B + C>` as an anonymous
existential binder. Projections `F<out B>` and `F<in B>` are declaration-directed bounded views,
while `F<: B>` introduces a hidden exact argument that can be reified, captured, and forwarded.
They are distinct even with one bound. A lower bound is expressed only as `in B`; `F<: ...>` carries
upper bounds and markers.

Opening a projection:

- `F<out B>` contributes an upper bound `B` and no descriptor or evidence.
- `F<in B>` is rejected for opening until the type system represents lower bounds.

### Variance and pointwise subtyping

Anonymous existentials hide an invariant argument in ZEP-0104. Star views are already projections.
Opening does not change variance. Later work may allow:

- `F<: B>` to relate to `G<: B>` when `F` and `G` are pointwise related;
- covariant `F` to preserve a wider bound;
- projections to be explained as a restricted existential view.

Pointwise subtyping is likely too complex for the near term and should stay deferred unless a
concrete use case requires it.

### Capture and projections

Pattern opening and ZEP-0052 projections both describe unknown arguments. They should share the
same internal captured-type representation:

- star views are projections and approximate the hidden argument by `Any?`;
- anonymous existentials add implicit packing and capture at generic call sites;
- pattern opening introduces a branch-scoped rigid name for the already-captured argument;
- descriptors and evidence are inherited, never synthesized by opening.

### Effects and markers

An escape error applies to raised effects as well as result types. A pattern binder may not appear
in a `raises` clause that escapes the branch. Nullability and mutability markers remain part of the
hidden type's identity and bound, not separate evidence.

If the source type is `Box<: nullable>`, the binder `T` is nullable-admitting and values of type
`T` require the existing null-check flow before non-null use. If the source is `Box<: mut>`, the
binder inherits the mutable-admissibility marker.

## Compatibility and impact

This expands source syntax and type-system rules for patterns. It should not change the ABI
established by ZEP-0104 for parameter-position anonymous existentials. Pattern binders are local
and are not serialized in the library index. Any descriptor or holder change for result positions
must extend the same schema revision or introduce a coordinated one.

## Alternatives

- **General skolemized `let`** — not needed for this use case. It would introduce a source-level
  binder outside branches and a broader escape problem.
- **Rank-2 `use` as the primary opening form** — useful for libraries and higher-order APIs, but
  requires ZEP-0109 and does not cover simple local multi-statement work. Demoted to an alternative.
- **Keep only implicit capture and helpers** — avoids new syntax, but forces every local opening
  into a named generic helper.
- **Scoped `open ... as <let T>` block** (2026-11-09 draft) — dropped: the `is` branch already
  supplies the scope, so a separate block form adds syntax without new capability.
- **Implicit binder without `let`** — rejected: `Box<T>` in a type test reads as an exact type, not
  a binder. `let` makes the opening explicit.
- **Mixed exact/open patterns** — deferred; they combine reified exact tests with opening and need
  a careful evidence rule.
- **Add full variance immediately** — likely exceeds demonstrated need and complicates evidence.
- **Merge with stored existentials** — conflates branch escape semantics with holder ABI; keep
  separate.

## Implementation and validation

1. Extend the parser for `let` binders in the type-test target in a direct `if` or `while`
   condition.
2. Add branch-scoped type variables and name resolution for the true branch.
3. Infer binder facts from the source type: star approximation, anonymous bounds/markers,
   projection bounds, concrete arguments, and raw-class checks.
4. Refine the tested variable to the applied type with binders substituted; mark total patterns
   unreachable on the false path where appropriate.
5. Implement escape checking for results, outer bindings, raised effects, and escaping closures.
6. Add diagnostics for mixed exact/open patterns, nested opening, duplicate binders, `in`
   projections, non-generic targets, and binders used outside the branch.
7. Test star views, bounded and reified anonymous existentials, `Any` raw checks, multiple binders,
   nullable/mut markers, total patterns, `while`, escape errors, local closures, and interaction
   with exact tests.
8. Ensure the opening pattern remains local-only and adds no library-index ABI.

## Open questions

- Should the opening pattern be allowed in `if` only, or also `while`, `else if`, and composed
  conditions?
- Should mixed exact/open patterns such as `Map<Int, let V>` be supported later, and what descriptor
  rule would they use?
- Should nested opening patterns be supported after the first version?
- How should class-declaration bounds interact with a raw `Any` test when no witness is available?
- Should `C<in B>` opening be rejected permanently or supported once lower bounds exist?
- Should a binder be allowed to shadow an enclosing type parameter, and how should that be
  diagnosed?
- How much escape checking can be shared with ordinary generic calls and projections?
- Are result-position anonymous existentials needed at all, and are `reified` results gated on
  ZEP-0106?
- Does rank-2 `use` remain necessary for library APIs after this pattern exists?
- Is any anonymous existential variance sound and useful, or should invariance remain permanent?
