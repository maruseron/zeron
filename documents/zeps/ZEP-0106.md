## Abstract

This proposal covers anonymous existentials that can be stored: existential types in fields,
locals, collection and array element types, and nested type arguments. It defines when a holder is
needed, the holder representation, evidence layout, equality, nullability, and library-index
metadata needed to make stored existentials stable across separately compiled libraries.

It is the proposal that would make heterogeneous capability-bearing collections and the model-field
use case expressible. [ZEP-0104](./ZEP-0104.md) deliberately excludes storage. This proposal keeps
parameter-position anonymous existentials on their existing hidden-parameter ABI; a holder is used
only where a value has to preserve a hidden argument after the parameter has been left behind.

**Implementation status (2026-11-12).** The holder slice and collection-element storage are
implemented: stored anonymous existentials in fields, locals, array elements, collection elements,
and nested type arguments, conditional erased versus holder-backed storage, `Exists1`–`Exists3` and
`ExistsN`, descriptor and evidence packing, stored reads that restore evidence tokens, `===` payload
identity, and API-index schema 14 metadata. `ArrayList` construction, mutation, reads, iteration,
nested collections, and separately compiled collection fields retain independent per-element
holders. A separately compiled holder field also round-trips through the index and restores its
descriptor and evidence.

The array-backed model-field prototype now stores one evidence group per element and executes its
per-field operation. The 2026-11-13 cost pass records 24 B/field and sub-nanosecond traversal
overhead. The [ZEP-0109](./ZEP-0109.md) rank-2 callback comparison is also recorded: 4.17–5.09
ns/field for the model-shaped `Unit` callback and 15.5 B/field, against 0.54–0.99 ns/field holder
traversal. It does not gate this proposal, which is implemented. No `AnyField`, `Model`, or
property-reference API changes in this proposal. Current type arguments otherwise
use `_` as an erased/HKT placeholder and `out`/`in` projections; the `<: ...>` forms in stored
positions are the implemented spellings.

## Revision note

The 2026-11-09 draft was written against the `<let V: Bound> F<V>` binder of the earlier ZEP-0104.
That binder no longer exists. This revision:

- rewrites stored existentials as anonymous existentials in storing positions:
  `Array<Widget<: Render>>`;
- treats `Widget<*>` as the existing `Widget<out Any?>` projection, which stores no hidden identity
  and needs no holder;
- makes the holder conditional: an anonymous existential that needs neither a descriptor nor
  evidence is erased and needs no holder;
- defines holder slots by `reified` markers and evidence-bearing bounds instead of one descriptor
  plus evidence per binder;
- takes over the carrier for reified anonymous existential locals and stored values, while leaving
  result-position syntax unsupported; [ZEP-0116](./ZEP-0116.md) explicitly excludes it;
- keeps the rank-2 callback of [ZEP-0109](./ZEP-0109.md) as the comparison baseline for the
  model-field case.

### Settled decisions (2026-11-12)

| Question | Decision |
|---|---|
| When is a holder needed? | Only when at least one hidden slot must survive storage: a `reified` descriptor or evidence for a bound. Erased and marker-only existentials keep the payload. |
| Holder shape | One standard-library family with typed slots: `Exists1` through `Exists3`, plus `ExistsN` with an array of slots for four or more. The compiler chooses the smallest arity. |
| Descriptor and evidence families | One family, not separate families. Each slot has a slot kind and a statically known type. |
| Holder ownership | Standard-library source types in `zeron.lang.existential`, not per-site compiler-generated classes. Their constructors and slot accessors are reserved compiler ABI, not supported application API. |
| Slot order | Left-to-right by anonymous existential occurrence in the stored type; within one existential, descriptor first (when present), then evidence ordered by canonical qualified bound name. Equivalent bounds are deduplicated. |
| Equality | Holders do not synthesize `==`. `===` compares the underlying payloads; `==` requires opening the value or an explicit witness. Descriptors and evidence never participate in equality. |
| Stored positions | Fields, locals, collection/array element types, and nested type arguments. Result positions, receivers, lambdas, and function-type parameters remain excluded. |
| Result positions | Not part of this proposal, ZEP-0105, or ZEP-0116. A future proposal can reuse this holder ABI if it accepts result-position existentials. |
| Library versioning | Holder metadata requires `API_INDEX_SCHEMA_VERSION` 14. The ZEP-0015 descriptor encoding itself is unchanged. |
| Model-field case | The holder ABI is accepted independently. Migrating `AnyField`, `Model`, or property references is not part of this proposal; the model case is a validation target against the rank-2 callback. |

## Motivation

The strongest existential use cases are collections:

```zeron
Array<Widget<: Render>>
Array<Field<T, : Encode>>
```

Each element hides its own type argument. Depending on the markers and bounds, an element must
contain:

- the erased payload;
- the hidden argument's runtime descriptor, for type-bound tests, only if marked `reified`;
- evidence for each bound that needs it, for operations.

The parameter-position slice forwards those pieces as hidden parameters. Storage needs a stable
holder object and a serialized slot order.

The model case is concrete: `AnyField<T>` currently hides a field's value type and evidence. A
stored existential could expose a stronger collection while preserving per-field encoding. It must
be compared honestly with a visitor, a rank-2 callback, or generated per-field operations before
any model API changes.

## Goals

- Define when a stored anonymous existential needs a holder and when it is erased.
- Define holder classes, slot kinds, and canonical slot order.
- Define equality, identity, nullability, and mutability for stored existentials.
- Preserve hidden-argument descriptors for stored `reified` anonymous existentials.
- Support separately compiled libraries and duplicate holder definitions.
- Provide the carrier for reified anonymous existential locals and stored values.
- Evaluate the model-field use case against simpler alternatives without changing model APIs in
  this proposal.

## Non-goals

- Parameter-position anonymous existentials and exact matching; see [ZEP-0104](./ZEP-0104.md).
- Star views; `Widget<*>` is an existing projection, not a stored existential.
- Result-position syntax, escape approximation, and variance; these remain unsupported by
  [ZEP-0105](./ZEP-0105.md) and [ZEP-0116](./ZEP-0116.md). This proposal only supplies the holder
  carrier that result positions would reuse if a future proposal accepts them.
- Contract-bound runtime tests; see [ZEP-0108](./ZEP-0108.md).
- General reflection or dynamic member access.
- Changing `AnyField`, `Model`, or property references in this proposal.
- Lambda/function-type parameters and rank-2 existential quantification; see
  [ZEP-0109](./ZEP-0109.md).
- Dynamic plugin loading or registry protocols.

## Proposal

### Stored positions

A stored anonymous existential is accepted in a type position where the value can outlive the
callable that introduced it:

- a class or contract field type;
- a local variable annotation;
- a collection element type, including `List<Widget<: Render>>`;
- an array element type, including `Array<Widget<: Render>>`;
- a nested type argument in one of the above.

The existing parameter-position form remains unchanged: a direct parameter `Widget<: Render>`
forwards hidden parameters and uses no holder. A parameter position with a nested stored existential,
such as `List<Widget<: Render>>`, uses holders inside the collection; it does not add hidden outer
parameters for the elements. ZEP-0104 remains the parameter-position slice and remains implemented;
this accepted proposal is the later extension for the stored positions it deliberately rejected.

The following remain rejected in this proposal:

- result types;
- receiver types;
- lambda and function-type parameter types;
- `Array<*>` and other direct star projections, which are not existential storage;
- any attempt to use an existence's hidden binder outside its declaration or opening branch.

Stored positions are introduced by ZEP-0106 only when a holder is needed. A field or local whose
existential is marker-only and has no evidence or descriptor keeps the erased payload type, as
described below.

### When a holder is needed

An anonymous existential's runtime needs are fixed by its markers and bounds, as in ZEP-0104:

| Form | Runtime need | Representation |
|------|--------------|----------------|
| `Box<*>` | none; it is `Box<out Any?>` | erased; `List<Box<*>>` is a `List<Box>` at runtime |
| `Box<: nullable>` | none beyond the payload's nullability marker | erased payload with the hidden argument's nullability |
| `Box<: Render>` with an evidence-bearing bound | evidence | holder |
| `Box<: reified>` | one descriptor | holder |
| `Box<: reified + Render>` | descriptor and evidence | holder |
| `Map<: KeyBound, : ValueBound>` | evidence for each binder, in binder order | holder with one slot group per binder |

Erased anonymous existentials need no new ABI. A holder is needed only when the existential carries
something to recover later. This keeps unbounded star storage and marker-only storage free.

A bound participates in the holder only when its operations require evidence. Marker-only bounds
do not consume a slot. If a declaration has both a descriptor and evidence, the descriptor is the
first slot in that binder's group.

### Holder representation

First release uses one standard-library holder family, keyed by the number of carried slots:

```text
Exists1<P, S1>
Exists2<P, S1, S2>
Exists3<P, S1, S2, S3>
ExistsN<P>          // slots: Array<Object>
```

The compiler selects the smallest holder that fits. More than three slots use `ExistsN` with an
array in canonical slot order. A holder contains:

- the erased payload `P`, which is the whole value of the applied type (for example the `Widget`);
- the slots, in canonical order.

A slot is either a hidden-argument descriptor from [ZEP-0015](./ZEP-0015.md) or one evidence value.
The descriptor identifies the applied source type; evidence provides operations. Neither is derived
from the other.

`Exists1` through `Exists3` have typed slot parameters. `ExistsN` stores slots as erased `Object`
values and is used only when the slot count exceeds three; the compiler inserts checked conversions
using each slot's recorded static type. There are no separate descriptor-only and evidence-only
holder families.

Holder classes live in `zeron.lang.existential`. Their constructors and reserved slot accessors are
compiler ABI. They are not intended to be constructed, pattern-matched, or inspected directly by
application source, and documentation identifies them as support types rather than user-facing data
structures.

### Slot order and schema

Slots are ordered by anonymous existential occurrence, left to right in the stored source type.
Within one anonymous existential, the descriptor (if `reified`) comes first, followed by evidence
ordered by the bound's canonical qualified name. The order is recorded in the library index and must
be stable across compilers and separate compilation. Duplicate or equivalent bounds are deduplicated
before ordering.

For nested positions, each holder belongs to the type argument that introduces it. For example,
`List<Box<: B>>` stores one holder per element, with slots only for `Box`'s hidden binder; the
`List` itself has no additional slots.

Holder classes, slot kinds, slot counts, and slot order are public ABI. The library index records:

- every stored existential position and its markers and bounds;
- the holder family and arity;
- canonical slot kinds and order;
- the descriptor schema version used by the slots.

`API_INDEX_SCHEMA_VERSION` becomes 14 when this proposal is implemented. The ZEP-0015 descriptor
wire format is unchanged. Two copies of a library must produce equal slot ordering for the same
declaration. Incompatible versions fail at the library boundary rather than silently reordering
slots.

### Packing, storing, unpacking, and opening

An anonymous-existential value has three forms:

- in a parameter (ZEP-0104): the payload plus hidden parameters for each slot;
- in a stored position: the payload inside a holder;
- in a star projection: an erased payload with no slots.

Packing is implicit when a concrete value meets a stored anonymous existential type. The pack site
resolves evidence, composes descriptors from ZEP-0015 for `reified` existentials, and fills the
canonical slots. Packing never invents evidence: a concrete type must satisfy every bound, and a
missing bound is a compile error at the pack site.

Passing a stored value as a parameter unpacks the slots into hidden parameters. Assigning one stored
existential to another stored existential reuses the same holder when the payload type and slot
order are identical; otherwise it unpacks and repacks. A star projection may be taken from a stored
value only by discarding the hidden identity, which is an ordinary projection operation and does not
recover slots later.

Opening uses the pattern-scoped form from ZEP-0105, `if (value is C<let T>)`. At the opening
boundary the compiler unpacks the holder's payload, descriptor, and evidence into the branch-scoped
binder. A captured variable receives the holder's descriptor and evidence. Type-bound tests refine
the payload; bound operations use the evidence. The holder itself is not visible as a first-class
destructurable value.

Opening is explicit. Storing a value does not implicitly open it, and a stored existential may be
passed around or placed in a collection without exposing the hidden binder. Escape of an opened
binder remains governed by ZEP-0105; this proposal adds no second escape rule.

### Equality, identity, nullability, and mutability

- The holder is not observable as a distinct value identity: `===` compares the underlying payloads.
- Holders do not synthesize `==`. A user compares stored values by opening them and using the
  available equality evidence, or by providing an explicit witness. This avoids defining equality
  when one bound supplies `Eq` and another does not.
- Descriptors and evidence never participate in equality.
- A nullable star view (`Widget<*>?`) and an anonymous existential over a nullable argument
  (`Widget<: nullable>`) are distinct types. The nullability of the hidden argument lives in its
  markers; the outer `?` makes the holder itself nullable.
- A mutable reference argument remains a reference in the payload and in the holder; the holder does
  not add mutability or copy the referenced value.
- No implicit structural equality or hashing is derived for holder values.

### Model-field case

A candidate consumer contract:

```zeron
public contract EncodeModel<T: nullable + mut> requires Model<T> {
    property encodableFields: Array<Field<T, : Encode>>;
}
```

The model must guarantee evidence of `Encode` for every mapped field, either by declaration-site
evidence or by failed conformance. This relies on `: Encode` being accepted as a contract-bounded
anonymous existential in a stored element position. The proposal compares this shape with:

- a visitor with `visit<V: Encode>(field: Field<T, V>)`;
- a rank-2 callback, which needs no stored existential:

  ```zeron
  contract EncodableFields<T> {
      forEachEncodable(f: <V: Encode> (Field<T, V>) -> Unit);
  }
  ```

  The method signature is illustrative rank-2 syntax from [ZEP-0109](./ZEP-0109.md); the contract
  declaration itself follows the current `contract Name { member(...): Result; }` shape.

- generated per-field operations;
- the existing `AnyField<T>` plus typed lookup.

The rank-2 callback covers iteration. Storage is justified only if the collection must be held,
filtered, sorted, or passed around as a value. This proposal accepts the holder ABI so that such a
collection is expressible; it does not accept a change to `AnyField`, `Model`, or property
references. The model-field prototype is a validation target, not an API commitment.

The 2026-11-12 validation spike used an array-backed `Column<T, : Show>` element and stored one
evidence group per column, then invoked `show()` through the recovered evidence. It compiles,
executes, and survives the ordinary array-element path. The spike deliberately does not synthesize
typed model fields or change the model API.

The 2026-11-13 cost pass measured the holder path against two representations of the same
one-evidence-per-field shape: parallel payload/evidence arrays and a direct payload-only array.
The benchmark stored 4,096 fields, traversed each field 96 times per round, and reported the median
of 31 rounds over three process runs on JDK 26 (Windows, OpenJDK, process-level timing rather than
JMH):

| Representation | Pack cost | Allocation | Traversal |
| --- | ---: | ---: | ---: |
| `Exists1` holder per field | 1.92–1.96 ns/field | 24 B/field | 0.54–0.99 ns/field |
| Parallel payload/evidence arrays | 1.50–1.78 ns/field | 0 B/field | 0.30 ns/field |
| Direct payload array | 0.05 ns/field* | 0 B/field | 0.23 ns/field |

\* The direct row uses `System.arraycopy`, so its pack number is a lower bound rather than a
realistic per-field operation. The parallel arrays approximate the storage-free traversal shape a
rank-2 callback can use. The 2026-11-13 ZEP-0109 rank-2 benchmark now measures that callback:
4.17–5.09 ns/field for the model-shaped `Unit` callback and 3.63–3.81 ns/field for an `Int`
result, both allocating 15.5 B/field, against 0.54–0.99 ns/field holder traversal in the model run.
The callback avoids stored holders but is not cheaper for the already-stored traversal.

Within this microbenchmark, a holder adds one 24-byte object per field and roughly 0.24–0.69 ns of
traversal over parallel arrays. A 100-field model therefore pays about 2.4 KB and 0.2 µs of packing,
with traversal still below 100 ns. That overhead is small enough not to block the accepted holder
ABI, but it does not by itself justify changing `Model`. The existing `AnyField` plus typed lookup
still covers consumers that only need names and property identity, and a traversal-only consumer
can use a rank-2 callback without storing anything. A typed field array becomes worthwhile only
when a consumer must hold, filter, sort, or pass the typed fields around as a value; that should be
an additive model proposal, not a change made here. The measured rank-2 callback costs more per
field than holder traversal in the recorded shape, so it does not justify replacing the holder ABI
or changing `Model`; it remains the storage-free alternative.

## Compatibility and impact

This adds standard-library holder types and a public ABI for slot layout. It affects the library
index, serialization of anonymous existential signatures, and generated packing/unpacking code.
Erased existentials add no ABI. Existing programs without stored existentials are unaffected.

The holder family is additive: parameter-position anonymous existentials keep the ZEP-0104 hidden
parameter ABI, and `F<*>` remains the existing projection. The library-index schema moves to 14
when holder metadata is emitted; clients and libraries with incompatible versions fail at the
library boundary.

## Alternatives

- **No stored existentials** — keep `AnyField`, visitors, rank-2 callbacks, and generated per-field
  operations. A valid outcome if the model case does not justify the feature; the holder ABI then
  remains unimplemented.
- **Always box existential values** — uniform but allocates for erased existentials that need
  nothing. Rejected in favor of conditional holders.
- **One erased holder per bound contract** — narrower, but duplicates holder machinery and does not
  compose multiple bounds cleanly. Rejected in favor of typed slots in one family.
- **Compiler-generated holder per site** — avoids exposing support types, but duplicates ABI across
  libraries and complicates separate compilation. Rejected for the first release; the standard
  library family is the stable ABI.
- **Reflection-based holder** — rejected; it conflicts with Zeron's no-reflection direction.
- **Store only descriptors, resolve evidence dynamically** — rejected; evidence must be fixed at
  packing time and available without runtime search.
- **Return-position and local result existentials in this proposal** — rejected as scope creep;
  result positions remain unsupported by ZEP-0105 and ZEP-0116 and can reuse the holder ABI later.

## Implementation and validation

1. Add stored positions for fields, locals, collection/array elements, and nested type arguments;
   keep result, receiver, lambda, and function-type positions rejected.
2. Classify each stored existential as erased or holder-backed from its bounds and markers.
3. Add `Exists1` through `Exists3` and `ExistsN` to `zeron.lang.existential` with reserved
   compiler accessors and typed slot order.
4. Implement packing, holder reuse/repacking, parameter-position unpacking, and branch-scoped
   opening through ZEP-0105's binder form.
5. Encode stored existential positions, holder arity, slot kinds, and slot order in API-index schema
   14; reject incompatible ordering at library boundaries.
6. Test erased anonymous existentials allocate no holder, reified and bounded storage preserve
   descriptors and evidence, nested collection elements are independent, nullability and mutability
   survive packing, and opening cannot leak a hidden binder.
7. Test separately compiled libraries, duplicate libraries, holder arity boundaries at three and
   four slots, and multiple bounds with deterministic deduplication.
8. Prototype the model-field shape against the visitor and rank-2 callback. The array-backed
   prototype, holder allocation/access measurements, and the 2026-11-13 rank-2 callback comparison
   are recorded above. Do not change `AnyField` or `Model` unless the stored collection is
   materially clearer and a consumer needs to hold it.
9. Record the resulting costs and library-version decision in the ZEP-0015 validation matrix and the
   release notes. The recorded holder cost does not justify weakening the ABI or changing `Model`.

## Decision

Accepted 2026-11-12 as the stored-existential and holder-ABI design. The first slice adds
conditional holders for reified descriptors and evidence-bearing bounds in fields, locals,
collection/array elements, and nested type arguments. It uses one standard-library `Exists1` through
`Exists3` family plus `ExistsN` for larger slot counts, with canonical slot order and API-index
schema 14. Erased existentials allocate no holder; parameter-position anonymous existentials keep
their existing ABI; result-position syntax is excluded by ZEP-0116.

The design deliberately does not settle model API migration. The model-field shape is a validation
target, and `AnyField`, `Model`, and property references remain unchanged unless the prototype shows
that storage is materially better than a rank-2 callback. Separate-compilation validation is
complete for holder fields and collection fields. Holder allocation and access are measured, and
the ZEP-0109 rank-2 callback comparison is recorded: it is slower per field than holder traversal
for the already-stored shape and still allocates a callback boundary. The proposal is implemented
for `0.7.0`; the cost measurements do not justify changing `Model`, and `AnyField`, `Model`, and
property references remain unchanged.
