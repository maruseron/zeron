## Abstract

This proposal extends the shared runtime descriptor from [ZEP-0015](./ZEP-0015.md) with ancestor
information so generic effects can participate in subtyping and handler dispatch can match a
generic effect through `under`.

Applied type identity remains exact. Ancestry is separate metadata used for subtype queries; it
must not change descriptor equality, hashing, or the identity of an applied type.

**Scope.** Effects are the only consumer specified here. Ancestor-aware matching of ordinary
(non-effect) types, which [ZEP-0104](./ZEP-0104.md) excludes by matching exactly, is not covered and
has no owning proposal yet; see Open questions.

**Implementation status (2026-11-10).** Effects are currently non-generic and match nominal effect
identities, using the nominal `under` relation from [ZEP-0013](./ZEP-0013.md). Generic effect
declarations are specified by [ZEP-0005](./ZEP-0005.md), which is `Accepted` with a closed
applied-effect scope and no release target; applied-effect descriptors and applied ancestry are not
implemented. The
`T: effect + reified` marker combination parses, but handlers do not yet consume applied
descriptors or applied ancestor metadata.

## Motivation

ZEP-0005 proposes starting with exact matching. It defers:

- handler cases over effect variables such as `T: effect + reified`;
- generic effects under an `under` edge;
- most-specific selection when an applied child effect is raised and a parent case could match.

ZEP-0013 adds nominal `under` edges and most-specific handler selection. Generic effects need a
runtime representation that can answer “is this applied child under that applied parent?” without
conflating subtype membership with identity.

## Goals

- Define ancestor metadata for applied types.
- Keep exact descriptor equality independent of ancestry.
- Support handler matching on reified effect variables.
- Support generic effects under `under`.
- Preserve most-specific matching and runtime ambiguity behavior from ZEP-0013.
- Define library-index and separate-compilation rules for applied ancestry.

## Non-goals

- Changing exact applied-effect identity or argument invariance.
- Contract-bound runtime tests; see [ZEP-0108](./ZEP-0108.md).
- General reflection or subtype inspection outside effects.
- Function types as effect arguments.
- Stored existentials or holder ABI.
- Subtype or ancestor tests on non-effect types (for example a reified `T` against
  `Collection<Int>`); exact tests are ZEP-0104.

## Proposal

### Identity and ancestry are separate

A descriptor remains:

```text
owner + type arguments + nullability + mutability + array shape
```

Equality and hashing use only those identity components. Ancestry is a separate, queryable
relation.

Two representations are candidates:

1. **Descriptor-associated ancestry:** an immutable ancestor view attached to a descriptor after
   construction but excluded from equality/hash.
2. **Companion metadata:** a static table keyed by the effect owner and applied arguments, loaded
   from the library index, consulted by handler dispatch.

The companion-table approach keeps descriptors small and makes ancestry a property of the effect
hierarchy rather than the type identity. It also avoids duplicating ancestor sets on every payload.
The design should prototype both before choosing.

### Applied ancestry

An `under` edge between nominal effects is declared statically. Generic effects add substitution:

```zeron
E<Int> under F<Int>
```

requires that `E` is under `F` and that the arguments are compatible under the declared relation.
For the first version, arguments remain invariant: only identical applied arguments participate in
a generic `under` relation unless a later design explicitly adds variance.

Ancestry may be transitive. The runtime relation must avoid cycles and ambiguous multiple parents;
ZEP-0013’s ambiguity rules apply.

### Handler matching

- A handler case for a concrete applied effect `E<Int>` matches exactly that applied identity, as
  proposed in ZEP-0005.
- A case over a reified effect variable `T: effect + reified` may match any applied effect whose
  ancestry includes `T`’s descriptor.
- A case for a concrete parent `F<Int>` may match a raised `E<Int>` when `E<Int> under F<Int>`.
- Most-specific matching follows ZEP-0013. Incomparable visible cases remain a compile-time error
  when statically detectable and a runtime ambiguity when a later library introduces one.

Ancestor lookup must not turn non-matching applied types into matches. In particular, `E<String>`
must not match `F<Int>` merely because `E under F` nominally.

### `T: effect + reified`

`T: effect + reified` supplies a descriptor but not an ancestor set until this proposal. With
ancestry, the descriptor identifies the raised applied effect, and the companion metadata answers
whether it is under the case’s constraint.

The case still cannot treat an arbitrary descriptor as a subtype of `T` without an explicit
ancestry query. This keeps identity and subtyping separate.

### Library index

The index already records nominal `under` edges from ZEP-0013. This proposal adds:

- applied ancestry queries or enough metadata to derive them;
- generic effect declaration parameters;
- the descriptor schema version from ZEP-0015.

One coordinated schema revision is preferred. Older compilers must reject newer indexes rather than
guess at applied ancestry.

### Runtime cost

Ancestry lookup should not allocate per raise. Candidates:

- precompute immutable applied ancestor sets for monomorphic sites;
- cache lookups by descriptor;
- keep the common exact-match path free of table scans.

The benchmark matrix from ZEP-0015 extends with generic `under`, nested applied parents, and
most-specific selection.

## Compatibility and impact

This changes handler behavior for generic effects and effect variables. Exact-match programs keep
their behavior. The library index must preserve applied ancestry; runtime dispatch must remain
deterministic across separate compilation and duplicate library copies.

## Alternatives

- **Keep exact matching forever** — simpler, but generic effects cannot participate in `under` and
  effect variables cannot be handled.
- **Put ancestors into descriptor equality** — makes two values of the same applied type compare
  differently depending on hierarchy metadata. Rejected.
- **Dynamic runtime search of all handlers** — conflicts with most-specific dispatch and introduces
  ambiguity/performance problems.
- **Only nominal ancestry, no applied arguments** — would make `E<String>` match `F<Int>` when
  `E under F`; unsound for invariant generic effects.

## Implementation and validation

1. Choose descriptor-associated ancestry or companion metadata after a prototype.
2. Extend the library index with applied ancestry metadata.
3. Implement handler matching for concrete parents and reified effect variables.
4. Test transitive, ambiguous, and separate-compilation cases.
5. Verify exact-match fast paths do not consult ancestry.
6. Measure lookup and allocation overhead.

## Open questions

- Descriptor-associated ancestry or companion metadata?
- How is applied ancestry canonicalized for nested generic effects?
- Does any argument variance participate, or is invariance permanent for `under`?
- How are runtime ambiguities introduced by later libraries reported and recovered?
- Can ancestry be shared with non-effect types later, or should it remain effect-specific? This
  decides whether non-effect subtype matching extends this proposal or gets its own.
- Should a handler case accept a wildcard applied effect (`E<?>`, `E<? : reified>`) matching any
  argument, in addition to reified effect variables? ZEP-0104 defines wildcards only in parameter
  positions.

Draft for later work. Not scheduled. Depends on the implemented ZEP-0015 descriptor, the accepted

ancestry to this proposal, including any notion of "all applications of a generic effect".
