## Abstract

This proposal explores runtime tests for **contract bounds**: deciding at runtime whether a hidden
or reified type satisfies a contract and, if so, obtaining the evidence needed to use its
operations.

It is deliberately separate from type-bound matching. A runtime type descriptor identifies an
applied source type; it does not provide contract operations. A contract-bound test is an evidence
query, not a type-identity query.

**Implementation status (2026-11-10).** No contract-bound runtime test over captured evidence is
implemented. Contract conformance is checked statically for known types, and an ordinary `is` test
can consult the runtime class/interface; `reified` supplies a type descriptor rather than evidence.
The `supports`, `case Bound(...)`, and `using ... as Bound` spellings below are candidate surface
forms only; none is current Zeron syntax.

## Motivation

Wildcard existentials and reified type variables make it possible to carry a value whose concrete
type is known only at runtime. Some programs need to branch on capabilities rather than exact types:

```zeron
if (value supports Display) {   // candidate syntax; not implemented
    return value.display();
}
return fallback();
```

This is different from:

```zeron
if (value is Box<Int>) {
    return consumeInt(value);
}
```

The second form is also proposed applied-type matching from [ZEP-0104](./ZEP-0104.md), not current
exact applied-type behavior.

The first asks whether evidence for `Display` is available. The second asks whether the applied
type is exactly `Box<Int>`. Conflating them would make effect identity carry contract dictionaries
and would make type tests depend on imports or witness search.

## Goals

- Define what it means for a value to satisfy a contract bound at runtime.
- Define where the evidence comes from and when it is fixed.
- Preserve the distinction between type identity and contract evidence.
- Support capability branching for existential values.
- Define diagnostics for missing, ambiguous, or unavailable evidence.
- Specify library-index metadata and separate-compilation behavior.

## Non-goals

- Exact type-bound matching; see [ZEP-0104](./ZEP-0104.md).
- Runtime type identity and descriptors; see [ZEP-0015](./ZEP-0015.md).
- Dynamic plugin loading, discovery, or import activation.
- General reflection or dynamic member invocation without evidence.
- Changing existing compile-time witness selection rules.
- Effect ancestry; see [ZEP-0107](./ZEP-0107.md).

## Proposal

### Test semantics

A contract-bound test asks whether a value’s captured evidence includes a requested bound.

Candidate surface syntax is deliberately unspecified:

- `value supports Bound` as a boolean condition;
- a pattern `case Bound(value) -> ...` that binds the evidence;
- a scoped `using value as Bound { ... }`.

The design must choose one primary form and ensure it composes with existing flow typing and
pattern matching. It must not look like a type test if it is actually an evidence test.

### Evidence source

Evidence is fixed at packing or capture time, following ZEP-0104’s rules:

1. Concrete packing site resolves witnesses under normal imports and ambiguity rules.
2. A type variable forwards its captured evidence.
3. An already-captured existential forwards its captured evidence.
4. Later witness availability cannot change the answer.

There is no runtime search, dynamic import activation, or global witness registry. A failed test
means “this value was not packed with that evidence,” not “no implementation exists anywhere in the
program.”

This keeps tests deterministic and separate-compilation-safe. It also means a value packed without
`Display` cannot later be tested into `Display`, even if the concrete type has an implementation
elsewhere.

### Closed evidence sets and subtyping

Two points limit what this test can observe under the model of ZEP-0104 (revised):

1. **Evidence sets are closed at packing.** An anonymous existential or type parameter carries
   evidence for
   exactly its declared bounds and what they entail. A test for a declared bound is statically
   known to succeed, and a test for any other bound fails. Non-trivial capability branching needs
   evidence that is not fully declared, for example an optional bound or a holder with an open
   evidence set. The latter approaches the registry or dynamic search this proposal rejects. A
   concrete use that does not reduce to a statically known answer must be shown before this
   proposal proceeds.
2. **Nominal conformance already has a static answer.** Contract → conformant subtyping decides
   nominal conformance when the class is known. A runtime `is Contract` test, where available,
   asks about the value's runtime class rather than captured evidence. The test here must say how
   it relates: cover only evidence-based (external witness) satisfaction and leave nominal
   conformance to the existing relation, or subsume both. Two tests that can give different answers
   for the same pair are to be avoided.

### Evidence and entailment

`Bound` may be a supercontract of a captured bound. The test uses the same entailment rules as
compile-time witnesses:

- exact evidence;
- supercontract evidence;
- composed or delegated evidence where ZEP-0008/ZEP-0076/ZEP-0078 allow it.

A successful test returns or binds the evidence needed to call the bound’s operations. The
underlying type descriptor is not necessary for the test, though it may be used to specialize
branches.

### Relationship to reification

Reification is neither necessary nor sufficient for contract-bound tests:

- a reified type variable supplies a descriptor, not evidence;
- an existential may carry evidence without needing a type-bound match;
- a program can use both: test the exact type, then use the evidence already attached.

This separation prevents descriptors from becoming evidence dictionaries and keeps effect payloads
small.

### Ambiguity and failure

- Missing evidence at packing is an error, as in ZEP-0104.
- Ambiguous evidence at packing is an error with the same diagnostics as ordinary witness
  resolution.
- A runtime test over unavailable evidence returns false or fails a non-optional `using` form with
  a clear message.
- A test may not trigger a new witness search. Dynamic search is explicitly rejected.

### Library index

The index records contract identities, evidence compatibility, and the same anonymous existential,
bound-order,
and slot-layout metadata as ZEP-0106 for stored existentials. Contract and witness IDs must be stable across
separate compilation. A coordinated schema revision with ZEP-0015/0104/0106 is preferred.

## Compatibility and impact

This changes existential capability branching and adds runtime evidence queries. Existing
compile-time witness dispatch is unchanged. The design affects the library index, holder layout for
stored existentials, and diagnostics, but must not add runtime lookup to ordinary generic calls.

## Alternatives

- **Compile-time-only witnesses** — keep evidence entirely static; capability branching remains
  impossible. A valid outcome if the use cases are weak.
- **Treat contract bounds as type identity** — would require descriptors to carry dictionaries and
  would conflate `value is Box<Int>` with `value supports Display`. Rejected.
- **Dynamic witness search** — allows late availability but breaks determinism and separate
  compilation. Rejected.
- **Reflection-based capability discovery** — out of scope and contrary to Zeron’s direction.

## Implementation and validation

1. Choose the source form for a bound test.
2. Specify captured-evidence layout and entailment.
3. Prototype capability branching for a parameter-position existential.
4. Extend to stored existentials if ZEP-0106 is accepted.
5. Test missing, ambiguous, supercontract, and separately compiled evidence.
6. Verify no runtime search or per-call evidence allocation on the common path.

## Open questions

- Is the primary form a boolean test, a pattern, or a scoped `using` block?
- Should a failed non-optional test throw, return false, or be a compile-time error in some forms?
- How is evidence represented so that a supercontract test is O(1) without scanning?
- Does a successful test refine the value’s static type, or only expose bound operations?
- Which concrete capability test is non-trivial under closed evidence sets (see above)?
- Does `supports` overlap `is Contract` for nominal conformance, and which owns which case?
- Is this feature justified independently of stored existentials?
