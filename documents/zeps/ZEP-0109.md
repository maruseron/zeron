## Abstract

Zeron supports rank-1 polymorphism: type parameters are declared on functions, methods, and types,
and each call instantiates them. A constrained rank-1 scheme also exists for supported immutable
`let`-bound lambdas. This proposal adds **polymorphic function types** (`<T: Bound> (T) -> R`) and
**generic lambdas** so that a universally quantified function can be passed as an argument and
instantiated at several types by its receiver.

The proposal adds no existential type former. It provides the universal quantifier that scoped
opening of existentials ([ZEP-0105](./ZEP-0105.md)) needs in order to be expressed in a library
with escape safety derived from ordinary scoping.

## Current baseline and implementation status

Implemented:

- named generic functions and methods are rank-1 schemes; each call instantiates them;
- generic function values are obtained by explicit specialization (`f::<T>`) or from a fully
  constraining expected function type;
- immutable `let`-bound identity and constant-result lambdas, including the constrained
  member-use extension from [ZEP-0003](./ZEP-0003.md), generalize to a rank-1 scheme;
- polymorphic function types use a leading binder list (`<T: Bound> (T) -> R`), generic lambdas
  infer binders from annotated parameters, and polymorphic types compare up to alpha-renaming;
- bounded and `reified` values use a distinct `FunctionShapeKey` with hidden evidence and
  descriptor slots supplied at each application; unbounded values keep the erased shape;
- [ZEP-0015](./ZEP-0015.md) evidence and descriptor threading is preserved through the library API
  index and separate compilation.

Remaining out of scope:

- nested or rank-3 schemes and impredicative instantiation;
- effect-kinded binders and binder-dependent effect rows;
- generic SAM implementations;
- result-position existential syntax.

## Motivation

Rank-1 polymorphism cannot express a callback that must work for *every* type:

```zeron
fn describeBoth(f: <T> (T) -> String, a: Int, b: String): String =
    f(a) + f(b);
```

Today `f` would have to be monomorphic, so `f(a)` and `f(b)` cannot both type-check. The same
limitation blocks:

- natural transformations (`<T> (List<T>) -> Option<T>`);
- scoped resource and context helpers whose continuation is polymorphic in a hidden type;
- generic callbacks with `reified` or contract-bounded parameters (`<T: Render> (T) -> String`);
- a library-level encoding of existential opening (see below).

The workaround available today is a contract with a generic method. It works, but it needs a named
declaration at every use and cannot be implemented by a lambda.

### Relationship to existentials

An existential is a rank-2 value in continuation-passing form:

```text
∃T. B(T) ∧ T   ≅   ∀R. (∀T. B(T) ⇒ T → R) → R
```

With polymorphic function types, "open this anonymous-existential-typed value and run a block over
its hidden type" can be packaged as an ordinary library function. ZEP-0105's pattern-scoped
opening covers local multi-statement work without rank-2; this is the reusable library alternative:

```zeron
public extension<T> Box<T> {
    public fn use<R>(f: <U> (Box<U>) -> R): R = f(this);
}
```

`R` is bound outside `U`'s scope, so it cannot mention `U`. The escape rule that
[ZEP-0104](./ZEP-0104.md) states for captured variables then follows from scoping for this form.
The receiver and quantified function type are proposed syntax, not current Zeron syntax. The
extension declaration itself follows the implemented `public extension<T> Receiver<T> { ... }`
shape.

This remains the main motivation for rank-2 support, independent of ZEP-0105's local
pattern-scoped opening.

### Note on an earlier justification

ZEP-0104 (2026-11-09 text) claimed that a `let`-binder lambda parameter gives "rank-2 polymorphism
cheaply". That is inaccurate. An existential in *parameter* position is equivalent to a rank-1
universal; rank-2 requires a `∀` nested inside the type of a parameter. This proposal supplies it.

## Goals

- Add polymorphic function types with bounds and `reified` markers.
- Add generic lambdas as the introduction form, checked against polymorphic types.
- Keep inference bidirectional and predictable: annotations only where signatures already carry them.
- Support eta-expansion of generic named functions to polymorphic function types.
- Define the runtime representation using hidden descriptor and evidence parameters.
- Keep escape safety a consequence of scoping.
- Preserve the existing rank-1 lambda and function-value behavior.

## Non-goals

- Star views, anonymous existentials, and capture; see [ZEP-0104](./ZEP-0104.md) and
  [ZEP-0105](./ZEP-0105.md).
- Impredicative instantiation (`List<<T> (T) -> T>`, or inferring a type variable as a polymorphic
  type).
- Rank-N inference without annotations.
- Higher-kinded polymorphism changes (`F<_>` is unchanged).
- Polymorphic lambdas as implementations of contracts with generic methods (see Open questions).
- Changing monomorphic function-type syntax or semantics.

## Proposal

### Polymorphic function types

```zeron
<T: Bound, U> (T, U) -> R
```

Binders use the existing generic-bound grammar (`nullable`, `mut`, contracts, `reified`, and
`effect` where applicable, joined with `+`). Binders scope over the parameter and result types. A
polymorphic function type may appear anywhere a type may appear, subject to predicativity below.

This is a candidate spelling. The current parser has no binder list before a function type.

### Generic lambdas

```zeron
let show = <T: Render> (value: T) -> value.render();   // <T: Render> (T) -> String
let identity = <T> (value: T) -> value;
```

- **Checking mode:** when the expected type is polymorphic, the expected binders become rigid
  (skolem) variables in the lambda body. A lambda with its own binder list is matched to the
  expected binders by position, up to renaming; bounds must be equal in the first version.
- **Inference mode:** a lambda with an explicit binder list and annotated parameters has the
  polymorphic type its annotations describe. A lambda without a binder list keeps today's rules.

The current lambda grammar accepts `(value: T) -> expression`; only the leading `<T>` binder is new.
A generic lambda is an immutable `let` initializer or an inline contextual argument. Mutable
bindings, fields, and arbitrary expression results remain monomorphic unless a later proposal
extends the value restriction.

### Instantiation

Applying a value of polymorphic type instantiates its binders by ordinary inference, exactly as
for a generic named function, and resolves bound evidence and `reified` descriptors at the call
site under existing witness rules. A polymorphic function value may also be used where a monomorphic
function type is expected by instantiation at the use site; this is a one-step coercion, not a
subtyping lattice.

Explicit instantiation uses the existing specialization spelling (`f::<Int>(value)`), unless the
parser adopts a different call-site form for rank-2 values.

### Bidirectional inference and predicativity

- A parameter whose type is polymorphic must be annotated; it is never inferred. This costs nothing
  new: function parameters are already annotated.
- Polymorphic types are propagated inward (checking) and are not inferred as the result of an
  arbitrary expression.
- Type arguments and inferred type variables are monotypes. A polymorphic function type may not
  instantiate a type variable.

### Equivalence and variance

Polymorphic function types are equal up to alpha-renaming of binders and identical bounds. Beyond
that they are invariant in the first version. Relaxing bounds (accepting a function that works for
a wider set of types) and reordering binders are deferred.

### Eta-expansion

A generic named function or method reference may be supplied where a polymorphic function type is
expected, if its signature matches the expected type after skolemizing the expected binders:

```zeron
fn identity<T>(value: T): T = value;
let polymorphic: <T> (T) -> T = identity;
```

The bare `identity` reference is accepted only because the expected type is fully
constraining and rank-2. A generic callable without either an expected type or explicit
specialization remains an error, as it is today. `::identity` is not current syntax.

### Reification and evidence

A binder marked `reified` makes each application pass a ZEP-0015 descriptor; a binder with a bound
that requires evidence makes it pass that evidence. Descriptors and evidence follow the existing
hidden-parameter convention in ZEP-0015 and are supplied at each application, not fixed when the
function value is created.

This is the key difference from a rank-1 function value. Specializing `identity::<Int>` today can
bake the `Int` descriptor into the specialized function value. A rank-2 value such as
`<T: reified> (T) -> T` must be usable at several types, so its hidden slots belong to the
application boundary.

### Escape

Binders are rigid inside a lambda body and are out of scope outside it. No separate escape rule is
needed: a type mentioning a binder cannot appear in an outer binding or a result type that was
fixed outside the binder's scope.

### Runtime representation

The first version should represent a polymorphic function value as an instance of a synthesized
functional interface whose invocation method includes the hidden evidence and descriptor slots after
the erased source parameters, evidence first and descriptors second, matching the existing
[ZEP-0015](./ZEP-0015.md) hidden-parameter convention. The interface is keyed by the full invocation
shape: source arity, erased parameter and result types, and the number and kinds of hidden slots.

`FunctionShapeKey` encodes the hidden counts in a distinct
`zeron-function-shape-v2-e<evidence>-d<descriptors>;` key, so polymorphic adapter shapes cannot
collide with ordinary SAM shapes; `FunctionShapeNames` and the generated Java class descriptor
inherit the distinction.

`LambdaMetafactory` creation works for the polymorphic ABI: the implementation helper exposes
captures, erased source parameters, evidence `MethodHandle`s, then reified descriptors, matching the
generated interface method and `samMethodType`. A synthesized adapter class was not required. The
runtime still performs no witness search.

### Library index

Public signatures may contain polymorphic function types. The index encodes the binder list, bound
order, `reified` markers, and the hidden-slot shape needed to invoke the value. This must extend the
versioned API index in coordination with the anonymous existential signatures of
[ZEP-0104](./ZEP-0104.md) and generic effects of [ZEP-0005](./ZEP-0005.md). Older compilers reject
newer indexes by schema version.

## Compatibility and impact

This is an additive source feature. It affects parsing (a leading `<` in expression position),
type formatting, bidirectional checking, lambda lowering, function-shape identity, library
metadata, and diagnostics. Programs that do not use polymorphic function types or binder-prefixed
lambdas are unaffected.

Runtime cost is limited to polymorphic function values: each application passes the hidden
descriptors and evidence of its binders. Monomorphic functions and lambdas are unchanged.

## Alternatives

- **Remain rank-1.** Viable, but leaves scoped existential opening to a special compiler rule and
  keeps natural transformations and generic callbacks inexpressible.
- **Contracts with generic methods only.** Works today, needs a named declaration per shape, and
  cannot be implemented by a lambda. It remains available and is the closest fallback
  representation.
- **Existential binder in type position (`<let T> T`).** Rejected in
  [ZEP-0104](./ZEP-0104.md): it is a rank-1 universal in disguise for parameters and is not rank-2.
- **Arbitrary-rank inference without annotations.** Undecidable in general; the annotation-driven
  bidirectional approach is the practical choice.
- **Impredicative polymorphism.** Substantial complexity for little demonstrated need.

## Implementation and validation

1. Extend the grammar for polymorphic function types and binder-prefixed lambdas; resolve the
   parsing ambiguity with `<` in expressions.
2. Add bidirectional checking with skolemization and one-step instantiation.
3. Implement eta-expansion for generic named functions and supported method references.
4. Define and test a full function-shape key that distinguishes hidden descriptor/evidence slots.
5. Lower polymorphic function values to synthesized functional interfaces with hidden parameters;
   prototype the lambda-creation path and fall back to an adapter class if needed.
6. Thread ZEP-0015 descriptors and bound evidence through each application.
7. Test: `describeBoth`, bounded and `reified` binders, nested generics, escape errors,
   eta-expansion, separate compilation, and the `use` encoding from the Motivation.
8. Measure the cost of polymorphic application against monomorphic application. The 2026-11-13
   process-level benchmark (`Rank2ApplicationBenchmark`) uses 4,096 fields, 512 rounds, 12 warmup
   rounds, and the median of 31 measured rounds over three JDK 26 runs. A bounded rank-2 callback
   returning `Int` costs 3.63–3.81 ns/field and allocates 15.5 B/field; the model-shaped callback
   returning `Unit` costs 4.17–5.09 ns/field and also allocates 15.5 B/field. The direct
   monomorphic traversal costs 0.52–0.72 ns/field. The callback is therefore roughly 5–10× the
   monomorphic call cost in this un-JIT-specialized shape, with the `Unit` form paying the extra
   generic boundary cost.
9. Compare ZEP-0106's array-backed stored model fields with a rank-2 `forEachEncodable` callback
   once the syntax exists. Record allocation/access cost and the model API recommendation without
   changing `AnyField`, `Model`, or property references here. The 2026-11-13 cost pass records the
   stored side at 24 B/field, 1.92–1.96 ns/field to pack, and 0.54–0.99 ns/field to traverse,
   versus 0 B and 0.30 ns/field for a parallel-array traversal shape. The rank-2 callback is now
   measured at 4.17–5.09 ns/field for the model-shaped `Unit` callback (3.63–3.81 ns/field for an
   `Int` result), with 15.5 B/field allocation, against 0.54–0.99 ns/field holder traversal in the
   2026-11-13 model run. The callback avoids storing holders but is not cheaper for this traversal;
   it remains the storage-free alternative, while the holder path is faster once the collection is
   already stored. Neither result justifies changing `AnyField`, `Model`, or property references,
   so the model API stays unchanged. The comparison is recorded in the
   [ZEP-0015 validation matrix](./ZEP-0015.md) and is a model-API follow-up, not a gate for
   ZEP-0106, which is implemented.

## Resolved design questions

Accepted 2026-11-13.

- **Surface syntax:** use a leading binder list, `<T: Bound, U> (T, U) -> R` for types and
  `<T: Bound> (value: T) -> expression` for lambdas. A leading `<` is only accepted at the start of
  a type or expression, where it cannot be a comparison. Require parentheses around a polymorphic
  function type used as a type argument, as in `List<(<T> (T) -> T)>`, to avoid nested-angle and
  `>>` ambiguity. Do not add a `forall` keyword.
- **Hidden slots:** use a separate polymorphic adapter shape keyed by the full invocation shape:
  source arity, erased parameter and result types, and the number, order, and kinds of hidden
  evidence/descriptor slots. Do not change every rank-1 synthesized function interface. Hidden
  slots follow the existing convention: after the erased source parameters, evidence first and
  descriptors second.
- **LambdaMetafactory:** prototype it, but permit a generated adapter class as the fallback. The
  language ABI must not be shaped around a bootstrap implementation detail.
- **Generic SAM implementation:** do not allow a generic lambda to implement a contract whose
  single abstract method is generic in this version. Require a named generic method or an explicit
  wrapper; revisit only with a concrete use case and a dictionary-passing design.
- **`raises`:** allow a fixed `raises` clause on a polymorphic function type, but do not allow a
  rank-2 binder to occur in the effect row in this version. Binder-dependent effect rows need a
  separate design combining rank-2 binders with effect applications.
- **Bounds:** keep functions invariant up to alpha-renaming and identical bounds. Contravariant
  bound subtyping is deferred; it is not needed for the initial use cases.
- **Overload resolution:** add no special rules for generic lambda arguments. A generic lambda
  requires a fully known expected polymorphic type; multiple candidate expected types are an
  ambiguity error and require an annotation.
- **`use` helpers:** ZEP-0105 owns existential-opening helpers. This proposal supplies the
  quantifier; a standard-library `use` combinator can follow once the rank-2 core works.
- **Call boundaries and escape:** share the hidden-slot ABI and lowering with anonymous existential
  capture where practical, but keep escape checking separate. Rank-2 escape follows binder scoping;
  existential capture has its own result and field-escape restrictions.
- **Value restriction:** generic lambdas remain immutable `let` initializers or inline contextual
  arguments. Do not extend them to fields, mutable bindings, or arbitrary expression results in
  this version.

## Decision

Accepted 2026-11-13. Implementation is independent of ZEP-0104's initial slice and of ZEP-0105's
pattern-scoped opening, and may proceed in parallel. Only the optional library `use` combinator
depends on it. Begin with syntax, bidirectional checking, alpha-equivalence, eta-expansion, and
diagnostics; the hidden-slot runtime ABI and `LambdaMetafactory`/adapter choice form the second
slice. No polymorphic function values are needed for existing rank-1 programs.

## Implementation status (2026-11-13)

Both slices are implemented:

- leading binder syntax parses in type and expression position, including parenthesized
  polymorphic function types in type arguments;
- generic lambdas check against expected polymorphic types, with positional binder matching up to
  alpha-renaming and identical bound/marker checks;
- generic lambdas infer a polymorphic type from annotated parameters when used as immutable `let`
  initializers;
- polymorphic function types are alpha-equivalent for assignment and calls instantiate the value's
  binders at each application;
- bare generic named function references eta-expand to full polymorphic expected types;
- monomorphic use of a generic lambda, mutable polymorphic bindings, and binder mismatches report
  resolution diagnostics;
- bounded and `reified` binders lower through a polymorphic hidden-slot adapter whose shape key
  includes the hidden evidence/descriptor counts, with slots supplied at each application;
- lambdas, eta-expanded generic function references, and binding calls share that ABI;
- polymorphic callback signatures retain their binder lists, bounds, and `reified` markers through
  the library API index, including bounded and `reified` applications across separate compilation;
- nested generic callback applications and the `use`-style continuation shape resolve.

Unbounded, non-reified polymorphic values lower through the existing erased function shape. Bounded
and `reified` values append evidence `MethodHandle`s and `AppliedTypeDescriptor`s after the erased
source parameters, evidence first. Generic SAM implementations and binder-dependent effect rows
remain explicit non-goals; effect-kinded binders stay rejected. The 2026-11-13 rank-2 application
benchmark records 3.63–3.81 ns/field for an `Int`-returning bounded callback and 4.17–5.09 ns/field
for the model-shaped `Unit` callback, both at 15.5 B/field, against 0.52–0.72 ns/field for a direct
monomorphic traversal. The proposal is `Planned` for `0.7.0`; its release state is recorded in the
[ZEP tracker](./ZEP.md).
