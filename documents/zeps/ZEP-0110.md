## Abstract

A `handle` expression currently protects exactly one expression, so an effectful *sequence* of
statements can only be handled by extracting it into a separate function or lambda and calling it.
This proposal adds a block form, `handle { … } with handlers`, that protects a statement block,
without changing abortive handler semantics, effect rows, or runtime representation.

## Motivation

Handlers are expressions, not statement-level `try`/`catch` constructs, and the guide states this
directly. A multi-step operation is the normal case for the effects Zeron has:

```zeron
fn promote(id: Int): User raises NotFound, DbError {
    let record = db.find(id);
    let account = repo.account(record.owner);
    return account.user;
}
```

Handling both effects at one boundary today requires moving the body out of line, which changes
capture rules, name scoping, and the natural reading order:

```zeron
fn promote(id: Int): User =
    handle (loadParticipant(id)) with {
        case NotFound as missing -> guest(missing.id);
        case DbError as failure -> guest(0);
    };
```

with `loadParticipant` defined purely to be the protected expression. The alternative — nesting
one `handle` per statement — degrades as soon as two statements raise the same effect set and the
policy should apply once, and it forces each intermediate result into its own wrapper or local.

The gap is purely in the protected-expression position. It needs no new handler semantics, no
resumption, and no monadic lowering; it is the ergonomic half of the "one handler around an
effectful region" request that motivates [ZEP-0007](./ZEP-0007.md) and
[ZEP-0111](./ZEP-0111.md), and it is useful independently of both.

## Goals

- Allow a `handle` expression to protect a statement block instead of a single expression.
- Keep the existing handler model exactly: abortive cases, most-specific-first selection, guards,
  refutable cases, `with suppressed` cleanup bindings, and the current coverage rules.
- Keep the effect bookkeeping identical: the block's escaping row is the union of its statements'
  rows, the handler removes what it fully covers, and the remainder is the expression's row.
- Preserve direct-style compilation: no monadic wrapper type, no per-statement closure, no change to
  the `RaisedEffect` carrier or to Java interoperability.
- Allow the existing single-expression form to remain valid and unchanged.

## Non-goals

- Resumption, continuation capture, or any suspending semantics; see [ZEP-0119](./ZEP-0119.md)
  (one-shot) and [ZEP-0121](./ZEP-0121.md) (multi-shot).
- Monadic or `do`-notation lowering; see [ZEP-0111](./ZEP-0111.md).
- General expression-valued blocks outside `handle` (for example `if`/`loop` bodies whose value is
  their final expression). This proposal introduces no new block-value rule beyond the one chosen
  in its "Block value" section.
- Handler composition, catch-all changes, or wildcard handler syntax. `case Effect` already exists
  through [ZEP-0013](./ZEP-0013.md) and is unchanged.
- Statement-level `try`/`catch`/`finally` forms, and `break`/`continue` that cross the handler
  boundary.

## Proposal

### Syntax

```zeron
fn promote(id: Int): User =
    handle {
        let record = db.find(id);
        let account = repo.account(record.owner);
        return account.user;
    } with {
        case NotFound as missing -> guest(missing.id);
        case DbError as failure -> guest(0);
    };
```

The protected region is a brace-delimited statement block in the position where the existing form
takes a parenthesized expression. Everything after `with` keeps today's forms: an inline case list,
a named handler (`with MissingUserText`), or a handler value expression (`with policy`).

The existing form is unchanged:

```zeron
handle (findUser(id)) with MissingUserText;
```

`handle` is already a keyword, so `{` in this position is unambiguous: the current grammar requires
`(` after `handle`.

### Block value

Two rules are possible for what the block produces:

- **A — `return`-based (recommended).** The block behaves like a function body: `return expr`
  produces the protected result, and falling off the end is an error unless the block's result type
  is `Unit`. This reuses the existing block and `return` rules verbatim and needs no new value
  semantics.
- **B — final-expression value.** The block's value is its final expression statement, which would
  make this the first expression-valued block in the language and require reconciling value rules
  with `if`, `loop`, `using`, and `match` bodies later.

Rule A is recommended because it is the smaller change and keeps `return` meaning one thing inside
a block. Rule B is recorded as an alternative in case the ergonomics review prefers it; the design
below assumes A. Under A, a one-expression block is written `handle { return expr } with …` and is
a convenience form only, not a replacement for `handle (expr) with …`.

`return` inside the block is block-local: it terminates the protected block and yields its value to
the handler boundary. A `return` inside a lambda written *inside* the block continues to return from
that lambda.

### Typing and effect bookkeeping

- The block's escaping row is the union of the rows of its statements and of the returned
  expression, computed with the existing row union and inclusion rules from
  [ZEP-0086](./ZEP-0086.md), including any row variable in scope.
- Applying the handler removes the labels it *fully* covers, exactly as for the current
  single-expression form: an unguarded, irrefutable case for effect `L` removes `L`; a guarded or
  refutable case does not; a fixed label handled out of a partially known row leaves the row
  variable intact in full.
- Effects raised by handler arms propagate unless they are handled further out or declared by the
  enclosing callable.
- The normal value and every handler arm must have compatible types, as today.
- `using` scopes inside the block behave as they do in any other block, including the existing
  rule that a primary raised effect stays primary and disposal failures are attached as suppressed
  outcomes. `with suppressed` bindings are available to handler arms exactly as they are today.

### Scoping and control flow

- Locals declared in the block are visible only inside it. Nothing declared in the block is visible
  in handler arms, and handler arms see only their own pattern binding, the enclosing function's
  locals captured by the handler value, and immutable locals of the enclosing block.
- `break`/`continue` whose target loop lies outside the protected block are rejected, matching the
  existing rule that a handler is an expression boundary. If the language later allows non-local
  exit, it must decide the interaction with effect coverage first.
- `raise` inside the block is caught by the handler when covered, otherwise it propagates normally.

### Desugaring

There is no semantic desugaring. The block is lowered as an inline protected region so that
existing handler emission is reused:

1. Parse `handle {`, collect statements with the ordinary block parser, and record a protected
   block node in the existing handle expression.
2. Resolve and type-check the block in a nested scope, computing the union row, then apply the
   handler's coverage to obtain the expression's row.
3. Emit the try region with the block's statements inlined, not wrapped in a lambda. Inlining is
   required for parity: a lambda wrapper would change capture requirements for mutable locals and
   could change the row, since mutable capture rules are stricter inside lambdas.

The single-expression form keeps its current path.

## Compatibility and impact

Source-compatible addition: no existing program changes meaning. The grammar gains one production
for the protected position after `handle`. The AST gains one protected-region node or reuses the
block statement in that position. No runtime, descriptor, library-index, or ABI change is needed,
because the row is compile-time only and lowering reuses the existing carrier.

Documentation impact: the raised-effects guide's statement that handlers are expressions rather than
statement-level forms stays true in the sense that matters (no `try`/`catch`, no statement
construct); the guide needs one section describing the block form and the block-value rule.

## Alternatives

- **Keep the single-expression form only.** Simplest, but forces out-of-line extraction for every
  multi-statement effectful region, which is the common case.
- **Introduce general expression-valued blocks.** More uniform in the long run, but touches every
  statement position and interacts with lambda capture, `if`, and `loop` value rules; too large for
  the ergonomic problem being solved.
- **Desugar to an immediately-invoked lambda.** Minimal compiler work, but changes mutable-capture
  rules and allocates, and would make the protected block a lambda body for the purposes of
  [ZEP-0002](./ZEP-0002.md) capture checking.
- **Add a `try`/`catch` statement form.** Rejected: it duplicates `handle` with different coverage
  and effects rules, and contradicts the language's expression-oriented effect model.
- **Ask users to nest one `handle` per statement.** No language change, but duplicates the policy
  and cannot let later statements contribute to one handler's coverage decisions.

## Implementation and validation

Stages:

1. Parser and AST: accept a block after `handle`; keep the existing form; formatter support for the
   new shape.
2. Resolver and effect analysis: nested scope for block locals, union row, existing coverage
   computation, rejection of escaping `break`/`continue`.
3. Emitter: inline protected block in the existing try region; verify no added allocation and no
   change to handler dispatch.
4. Documentation: raised-effects guide and a sample.

Validation:

- a two-effect block handled at one boundary, with both cases selected and the remainder empty;
- a block whose handler covers only one of two raised effects, leaving the other in the callable's
  row, and a variant that omits the declaration and fails;
- a guarded/refutable case that leaves the effect escaping;
- a block containing a `using` scope whose disposal fails while the primary effect is raised, with
  `with suppressed` inspected in the arm;
- a row-polymorphic body whose protected block raises a fixed effect plus a row variable, checking
  that handling the fixed effect leaves the row variable intact;
- scoping negatives: a block local used in a handler arm, and `break`/`continue` escaping the block;
- `return` inside a lambda inside the block returning from that lambda only;
- bytecode comparison against the extracted-function form, checking one protected region, unchanged
  descriptor, and no new closure;
- regression: the existing single-expression form, named handlers, anonymous handler values, and
  `case Effect` behavior are unchanged.

## Open questions

- Block value rule A (`return`) versus B (final expression). A is recommended; B should be revisited
  only together with a general expression-valued block design.
- Whether a block with a `Unit` result type may omit `return` entirely (recommended: yes, matching
  function bodies).
- Whether `handle { … } with …` should permit a trailing empty case list as an explicit
  "no coverage, row unchanged" form (current preference: no, it has no use).
