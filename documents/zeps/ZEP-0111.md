## Abstract

`for … yield` and `for … collect … into` already desugar into `map`, `flatMap`, and `fold` calls, but
the lowerer emits ordinary member calls that resolve against `Stream` only. This proposal adds a
`do` expression whose binds dispatch through the `Monad<M<_>>` witness already present in
`zeron.control`, so the same source shape works for `Option`, `Result<_, E>`, `Stream`, and
library-defined constructors.

The proposal is strictly a library-level notation change. It does not alter `raise`, `handle`, effect
rows, or the handler model, and it does not turn raised effects into a monad.

The 2026-11-10 revision settles the design and narrows the first slice: binds require at least one
monadic step, `yield` lowers to `map`/`flatMap` only, there is no `pure` call in the lowering, no
guard clause, and no default constructor. All former open questions are resolved in "Settled design
decisions".

## Revision note

The initial draft left the binding token, constructor inference, guards, and the `Unit` rule open,
and it proposed a lowering that emitted `pure` for the result clause. Settling the design against
the shipped witness machinery changed three things:

- the target constructor is inferred from the first bind (or an expected type, or an explicit
  `do<…>`), so a block never needs a default;
- `yield` lowers to a final `map`, whose receiver is already typed, so the lowering uses only
  receiver-marked operations and never names `pure`;
- a `do` block requires at least one bind, which removes the zero-bind `pure` case entirely.

## Motivation

Zeron ships first-order higher-kinded contracts and a comprehension form:

```zeron
let doubled = for (item in items) yield item * 2;
let lookup: Map<Int, String> = for (item in items) collect item.name into Map<Int, String>();
```

Those clauses lower to `map`, `flatMap`, `filter`, and `fold` member calls. Because the target is
fixed, a chain over `Option` or `Result` cannot use the shape and must be written as nested
`match`es:

```zeron
fn load(id: Int): Result<User, LookupError> =
    match (repo.findId(id)) {
        case Result.Ok(existing) -> match (db.load(existing)) {
            case Result.Ok(record) -> Result.Ok(record.toUser());
            case Result.Err(error) -> Result.Err(error);
        };
        case Result.Err(error) -> Result.Err(error);
    };
```

The `Monad` contract, its `Applicative`/`Functor` prerequisites, witness dispatch, and default
members are implemented, so the missing piece is notation, not abstraction.

**Scale of the existing pain (2026-11-10 measurement).** The bundled standard library contains 57
`match (` expressions, 12 of them nested inside an arm across 6 files, and essentially no hand-
written `.flatMap`/`.map` chains. The observed nestings are mostly two levels and frequently mix
constructors (`Result` then `Option`), branch on a discriminant, or decorate errors per step, which
this notation does not remove. The design is therefore deliberately minimal: it adds the chain shape
for dependent binds over one constructor, and nothing else. Acceptance records a design direction,
not a priority claim; the evidence gate for implementation is in "Implementation and validation".

## Goals

- Provide a `do` expression with binds and a result clause that dispatches through a
  `Monad<M<_>>` witness rather than a fixed receiver type.
- Support at least `Option`, `Result<_, E>` with fixed `E`, and `Stream`, plus library-defined
  constructors that implement `Monad`.
- Determine the target constructor without a default, from an expected type, an explicit
  `do<…>`, or the first bind.
- Reuse the shape of the existing comprehension lowering (clauses → `flatMap`/`map`) so both forms
  share analysis and tests.
- Keep evaluation order, laziness for `Stream`, and short-circuiting for `Option`/`Result`
  unchanged from the equivalent hand-written chain.
- Add no runtime type, descriptor, ABI, or effect-system change.

## Non-goals

- Changing `raise`/`handle` semantics, effect rows, or handler coverage. A `do` block's raised
  effects are the union of its clauses and are handled by ordinary handlers.
- Monadic lowering of raised effects, resumption, or async/await; see
  [ZEP-0119](./ZEP-0119.md) for one-shot resumption, [ZEP-0121](./ZEP-0121.md) for multi-shot, and
  [ZEP-0120](./ZEP-0120.md) for the async surface.
- Row-polymorphic monads. The constructor must be a closed application; `Result<_, E>` is supported
  with a fixed `E`, but a monad whose index is itself an effect row is out of scope, because a
  row-changing bind needs two open slots and a type-level row join, neither of which
  [ZEP-0019](./ZEP-0019.md) provides.
- Guard clauses, `filter` stages, and `MonadPlus` evidence in the language. A predicate is an
  ordinary bind against a library helper or a value-level `if` expression.
- Replacing `for … yield` / `collect`. `collect … into` remains eager and `Stream`-oriented; `do`
  has no `collect` clause.
- Applicative-only or arrow-style notation. `do` requires `Monad` evidence.
- Multi-shot or reversed evaluation orders, and any automatic lifting between nested blocks.
- Unifying `for` and `do` in this proposal; see "Relationship to `for`".

## Proposal

### Surface syntax and clause set

`do` is a soft keyword, recognized in expression position when followed by `{` or by a type
argument and then `{`. `<-` is a new single token and does not currently appear in the grammar.

```zeron
fn load(id: Int): Result<User, LookupError> = do {
    let existing <- repo.findId(id);
    let record <- db.load(existing);
    yield record.toUser();
};
```

A block contains, in order:

- **Bind clauses:** `let name <- expression`. `expression` must have the target constructor applied
  to an element type; the binder introduces the element. Binders are sequential and lexical.
- **Plain binding clauses:** `let name = expression`. Ordinary value binding, no monadic
  destructuring, sequential scope. This mirrors `for`'s local binding clause and avoids recomputing
  a subexpression across steps.
- **Result clause:** `yield expression`, exactly once, last in the block. Its value is `M<R>`.

No other statement forms are admitted: conditionals, loops, and `collect` clauses are not part of
the grammar of a `do` block. A block must contain **at least one bind clause**; a zero-bind block is
a diagnostic, because lifting a single value is already spelled with the constructor's own
operations.

```zeron
let known = do<Option<_>> {
    let name <- names.get(id);
    yield name.length;
};
```

### Constructor selection and inference

The target constructor is determined in this order, and every source that is present must agree:

1. **Expected type**, when the surrounding context fixes one. A fully applied expected type
   `M<A>` decomposes into the constructor and the element type `A`.
2. **Explicit constructor**, written `do<Option<_>>` or `do<Result<_, LookupError>>`. The placeholder
   spells the open slot, exactly as witness declarations already spell `Monad<Option<_>>` and
   `Monad<Result<_, E>>`. A concrete type in the slot (`do<Result<Int, LookupError>>`) is a
   diagnostic, and so is a constructor written without its open slot (`do<Option>`), because a
   `Monad` constructor takes exactly one open slot.
3. **First bind**, when neither of the above fixes a constructor: the type of the first bind's
   expression supplies it, and its element type is inferred by ordinary inference.

Rules that follow:

- Every later bind must use the same constructor; its element type is unified normally. A mismatch
  is reported at that clause, naming the constructor expected from the first bind or the declared
  one.
- A bind whose expression is not an application of the target constructor is a diagnostic ("a `do`
  bind requires a `M<…>` value"), not an implicit lift.
- If the chosen constructor has no `Monad<M<_>>` witness, the existing missing-implementation
  diagnostic names the contract and the constructor. It is reported at the `do` keyword, not at a
  generated call.
- There is **no default constructor**. A block whose constructor cannot be determined from any of
  the three sources is an inference error. Defaulting to `Stream` would hide the choice;
  defaulting to `Option` would be arbitrary.
- Ordinary `let` clauses do not participate in constructor selection.
- `do` blocks nest independently; no implicit lifting or flattening occurs between them.

### Desugaring

Clauses are lowered right-associated, reusing the existing comprehension pipeline walk:

```zeron
do { let x <- a; let y <- b; let z = g(x); yield f(x, y, z); }
```

becomes

```zeron
a.flatMap { x -> b.map { y -> { let z = g(x); return f(x, y, z); } } }
```

with these rules:

- The final `yield e` lowers to `map` over the last bind; with a single bind it is
  `a.map { x -> e }`.
- Each preceding bind lowers to `flatMap` with the rest of the block as the continuation.
- Plain `let` clauses become locals inside the continuation lambda and are evaluated at their
  position, left to right.
- Both `flatMap` and `map` are receiver-marked contract operations, so they resolve through the
  witness for the receiver's concrete type using the existing dispatch. **The lowering never names
  `pure`**: with at least one bind, every path ends in `map`, which the lowered AST reaches from an
  already-typed receiver. This keeps the emitted code independent of any new static-call spelling
  and reuses the same resolution the comprehension lowerer relies on today.
- The desugaring must be visible in the AST dump, and a type error in a clause must name the clause
  rather than the generated call.

### Scoping, order, and laziness

- Binder scope is lexical and sequential: each binder is visible in subsequent clauses and in the
  `yield`; a plain `let` behaves the same way.
- Evaluation order is left to right, matching the nested `flatMap`/`map` shape. For `Stream` this
  preserves laziness and element order; for `Option`/`Result` it preserves short-circuiting, since
  later clauses are not evaluated when an earlier value is empty or `Err`.
- No binder escapes the block. A `yield` that references an out-of-scope name is an ordinary
  resolution error.

### Interaction with effects

`do` is ordinary expression syntax. A clause expression may raise effects; the union row becomes the
block's row and follows existing propagation, handler coverage, and declared `raises` rules. Handler
arms inside a clause are normal handler expressions. Nothing about `handle` changes, and no effect is
implicitly converted into a monadic value. A `do` block inside a `handle` body behaves like any
other expression.

### Predicates without a guard clause

There is no `if` clause. A short-circuiting predicate is written as a bind against a value-level
`if` expression, which needs no new syntax:

```zeron
let user <- if (record.active) Option.Some(record) else Option.None();
```

A generic `guard` helper over `MonadPlus`/`Alternative` is a possible library addition later; it is
not part of this design, and it would be an ordinary function call rather than clauseware.

### Relationship to `for`

`for` keeps its current meaning and lowering: generators over iterables, lazy `Stream` yield, eager
`collect … into`, and its pipeline representation. `do` is the form that names or infers a
constructor through `Monad`, and it admits `Stream` as one constructor among others because
`Stream` already has a `Monad<Stream<_>>` implementation; `do<Stream<_>>` therefore produces a lazy
stream by construction, with no special rule.

The two forms overlap for streams and stay separate otherwise. A later proposal may unify them by
making `for` dispatch on a witness when its source is not a `Stream`, but that is not part of this
scope, and no behavior of existing `for` code changes here.

## Compatibility and impact

Source-compatible addition. `do` is a soft keyword: it remains a valid identifier everywhere except
in expression position followed by `{` or `<…>{`, matching the existing soft-keyword precedents
(`handler`, `model`, `with`, `suppressed`, `collect`, `into`, `yield`). `<-` becomes a single token;
old code that wrote `a < -b` keeps its meaning as long as the space is retained, exactly as `->`
already requires. The grammar document and formatter need updating, and the formatter must handle
the clause shape deterministically.

No runtime, descriptor, library-index, or ABI change: the lowering produces ordinary
witness-dispatched receiver calls that already exist in compiled code paths. Library-index impact is
limited to syntax metadata needed for source round-tripping; the contracts themselves are already
exported.

Cost profile: one closure per bind plus one `map` result per success path, all through the existing
witness dispatch and subject to the evidence-inlining direction in [ZEP-0095](./ZEP-0095.md). No
speedup is claimed; implementation must measure against hand-written chains.

## Alternatives

- **Keep `Stream`-only comprehensions.** No change, but leaves `Option`/`Result` chains verbose
  despite the `Monad` contracts being implemented and shipped.
- **Extend `for` itself to dispatch on witnesses.** Avoids a second form, but changes inference and
  documentation for existing `for` code and mixes eager collection with monadic binds. A separate
  `do` form is the smaller increment; unification remains possible later.
- **Use `for`-style `let x = expr` for binds.** Reuses existing punctuation but collides with plain
  binding at the same nesting depth and makes a monadic extraction invisible; `<-` keeps the
  distinction explicit while both clause kinds stay available.
- **Default the constructor to `Stream`.** Hides the choice and makes `Option`/`Result` blocks read
  as streams.
- **Lower `yield` through `pure`.** Requires naming a static contract operation inside lowered code
  and admits zero-bind blocks whose only operation is a lift. Requiring one bind removes both costs.
- **Applicative-only notation (`let x <- a; let y <- b;` without dependency).** Cheaper and permits
  parallelism later, but cannot express dependent steps; not a substitute for `flatMap`.
- **A `?`-style propagation operator instead.** Would address some stdlib nesting (per-step error
  decoration, mixed constructors) more directly than `do`, but it is a distinct feature that needs
  its own semantics next to `raise`. Not part of this proposal; the measurement above is recorded so
  that decision can be taken separately.
- **A library macro or builder DSL.** Zeron has typed embedded DSL support and receiver lambdas, but
  a builder cannot give short-circuiting binds without a control abstraction, and the existing
  comprehension machinery already provides the lowering shape.

## Implementation and validation

Stages:

1. Scanner, grammar, and formatter: `<-` token, soft keyword `do`, optional `<…>` constructor,
   clause block, idempotent formatting.
2. AST and resolution: bind/plain-let/yield clause nodes sharing the existing clause representation
   where practical; sequential scoping; at least one bind; no other statement forms.
3. Lowering: reuse the comprehension lowerer's right-associated walk, emitting receiver `flatMap`
   and `map` calls for the selected constructor, with plain `let`s placed in the continuation
   lambda.
4. Inference: the three-source constructor rule, element unification, closed-application check,
   witness diagnostics, clause-local error reporting.
5. Documentation: for-expressions guide cross-reference and a `do` section with `Option`, `Result`,
   and `Stream` examples.

Validation:

- `Option` chain that short-circuits at the second bind, checking that the third clause is not
  evaluated and the result is the first empty value;
- `Result<_, E>` chain with a fixed `E`; a step whose expression has a different `E` is a
  diagnostic; a mismatch in element type is reported at the clause;
- `Stream` chain with `yield` preserving laziness and element order, compared against the equivalent
  `for … yield`;
- constructor selection from an expected type, from `do<Option<_>>`, from
  `do<Result<_, EncodeError>>`, and from the first bind; conflicting sources are diagnostics; a
  block with no determinable constructor is an inference error;
- negative cases: zero binds, `yield` missing, `yield` not last, non-monadic bind expression,
  `collect` clause, `do<Result<Int, E>>` with a concrete slot, missing `Monad` witness;
- plain `let` clauses interleaved with binds, checking scope and left-to-right evaluation;
- nested `do` blocks with distinct constructors, checking no implicit lifting;
- library-defined constructor with a user `Monad` implementation, including a separate compilation
  round trip;
- raised effects inside clauses: union row, handler coverage, and declared-row propagation, with a
  negative case that omits the declaration;
- bytecode/descriptor comparison against the hand-written chain, verifying the same dispatch path
  and no extra wrapper types;
- a smoke refactor of a real chain site (for example the serialization `encodeNamed` shape) as a
  readability check, recorded with the before/after text rather than asserted;
- formatter idempotence on `do` blocks with wrapping.

Evidence gate before implementation is scheduled: at least one hand-written `flatMap` chain longer
than two steps exists in shipped code, or a sample program demonstrates the shape. With the current
stdlib measurement (0 real chains, 12 nested matches, mostly two levels and frequently
non-monadic), implementation is not justified yet even though the design is accepted.

## Open questions

None. The former open questions are resolved in "Settled design decisions"; anything still
undecided is a library or follow-up matter listed under Non-goals.

## Settled design decisions (2026-11-10)

- **Binding punctuation.** `let name <- expression` for binds and `let name = expression` for plain
  locals; `<-` is one token, never split across lines, and does not exist in the grammar today.
- **`do` is a soft keyword**, recognized in expression position before `{` or `<…>{`; it stays a
  valid identifier elsewhere.
- **Constructor selection.** Expected type, then explicit `do<…>`, then the first bind; all present
  sources must agree; no default; failure is an inference error.
- **Explicit constructor spelling** uses the existing open-slot form, `do<Option<_>>` and
  `do<Result<_, E>>`; a concrete type in the slot is a diagnostic.
- **At least one bind is required**, so no zero-bind `pure` case exists.
- **`yield` lowers to `map`**, and each bind to `flatMap`; the lowering names only receiver-marked
  operations and never `pure`.
- **No guard clause and no `collect`.** Predicates are binds against value-level `if` expressions;
  a `MonadPlus` `guard` helper is an optional library addition.
- **No `Unit` elision.** Every block ends in an explicit `yield`, including `yield ()`.
- **`Stream` is included** as an ordinary `Monad` constructor; `for` keeps its own lowering and
  meaning, and unification is out of scope.
- **Same constructor, same fixed arguments.** `Result<_, E>` binds require one `E`; adaptation is a
  `.mapError(...)` on the individual expression, not a notation feature.
- **Nesting does not lift.** Each `do` block resolves its own constructor.
- **No ABI change.** Lowered code is ordinary witness-dispatched receiver calls; no new runtime
  type, descriptor, or index record.

## Implementation status (2026-11-11)

The evidence gate was waived by the author: nested `match` expressions for two or three fallible
steps compose poorly and are limited to single expressions, and the notation is meant to keep them
from becoming the idiomatic shape. The slice below shipped with that decision recorded.

Shipped in the compiler:

- `TokenType.LEFT_ARROW` and a scanner rule for `<-`, which exists only in `do` clauses;
- `do` as a soft keyword in expression position, before `{` or `<…>{`, so it stays a valid name
  elsewhere;
- `Expr.Do`, which holds the keyword, the optional declared constructor, and the lowered chain;
- parser lowering: each bind becomes a `flatMap` receiver call and the final `yield` becomes `map`,
  with lambdas carrying plain-`let` local statements and the returned expression; both calls are
  marked witness-dispatched, so they resolve through the receiver's contract witness instead of an
  instance method that happens to share the name;
- `ExpressionFlowResolver.resolveDo`, which resolves the lowered chain and checks a declared
  constructor against the inferred one by simple name;
- `MemberInteropResolver.resolveWitnessDispatchedCall`, which routes a marked call through
  `resolveWitnessMethodCall` for concrete receivers and `resolveBoundedMemberCall` for `F<A>`
  receivers bounded by `Monad<F>`; receiver-based calls to HKT contract methods that declare
  `this` now subtract the receiver from arity and argument positions, so `value.map(...)` on a
  bounded constructor no longer reports an argument-count mismatch;
- `BytecodeEmitter` and the lambda walkers delegate to the lowered chain, so dispatch, captures,
  and evidence use the ordinary member-call paths and no ABI changes;
- `DoNotationTest` (8 tests): an `Option` chain that short-circuits and projects `yield`, a
  `Result<_, E>` chain that stops at the first `Err`, plain-`let` locals between binds, a `Stream`
  chain through the explicit `do<Stream<_>>` constructor, a nested `Stream` cartesian product that
  would select the wrong instance `flatMap` without witness dispatch, a chain over a constructor
  parameter bounded by `Monad<F>`, a constructor mismatch, and parse diagnostics for zero binds, a
  missing `yield`, a local before the first bind, a concrete constructor slot, and a non-monadic
  bind.

Implementation limits, recorded rather than deferred silently:

- **No expected-type constructor selection.** Zeron has no general mechanism that fixes a
  constructor from a surrounding expected type, so the constructor always comes from the first
  bind's receiver. An explicit `do<…>` is validated after resolution instead of steering
  inference, so it reports a mismatch but cannot repair an otherwise ambiguous chain.
- **Plain `let` clauses follow the first bind only.** Lowering evaluates each local inside the
  previous bind's continuation; a local before the first bind would need an immediately invoked
  lambda or a reordering, so it is a parse diagnostic instead.
- **Bindings must agree.** `Result` binds share one `E`; adapting an individual expression with
  `mapError` is the supported workaround, exactly as settled.
- **A witness is required.** Because steps dispatch through `Monad`, a constructor that only
  declares instance `map`/`flatMap` methods and no `Monad` implementation is rejected even if the
  instance signatures would happen to fit. This is the intended meaning of the notation, but it is
  stricter than an instance-call lowering and worth knowing when a library adds `do` support.
- **Not separately asserted:** raised-effect propagation through clauses, formatter idempotence,
  and bytecode comparison against a hand-written chain. Effects travel through the ordinary
  `flatMap`/`map` rows, and the emitter emits the lowered chain directly, but no test pins those
  two claims yet.

## Decision

Accepted 2026-11-10 as a notation-only design. Fixed points:

- `do` with `let x <- e` binds, plain `let x = e` locals, and a mandatory final `yield`;
- at least one bind, no `pure` in the lowering, no guards, no `collect`, no `Unit` elision;
- constructor from expected type, explicit `do<Option<_>>` / `do<Result<_, E>>`, or the first bind,
  with no default;
- `Stream` included through its existing `Monad` witness, `for` unchanged;
- witness-dispatched receiver calls only, so no runtime, descriptor, or ABI change.

The proposal is accepted, implemented on 2026-11-11, and unscheduled; the tracker records it as
`Implemented` with no release target. The evidence gate in "Implementation and validation" was
waived by the author on the grounds recorded in "Implementation status", which also lists the
limits of the shipped slice.
