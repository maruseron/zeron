## Abstract

Zeron targets JDK 25, where blocking a virtual thread is cheap. This proposal defines the
standard-library structured-concurrency primitive: `Scope`, `Task<T>`, scoped lifetimes, cooperative
cancellation, timeouts, and the rule for how raised effects cross a task boundary. Blocking on
virtual threads is the suspension mechanism; this proposal adds no suspension syntax, no wrapper
return type, and no compiler transform.

The optional effect-level async surface (`Await`, `Future`, `spawn`, `await`) is
[ZEP-0120](./ZEP-0120.md), built on these primitives. This proposal does not require it, and it does
not capture continuations.

## Motivation

A fetch-then-load operation has two different kinds of effect:

```zeron
fn promote(id: Int): User raises NotFound, DbError {
    let record = db.find(id);
    let account = repo.account(record.owner);
    return account.user;
}
```

`NotFound` and `DbError` are *abortive*: when raised, the rest of the body does not run, and an
abortive handler at a boundary is sufficient. Nothing about them needs sequencing machinery.

A network read is different in kind: `db.find` may need to wait, then continue with a value. In a
thread-per-request runtime this is just a call. On a JVM without cheap blocking it would force a
different calling convention, which is exactly the coloring that async/await syntax encodes in the
type system: every caller in the chain has to become `Task`-shaped and the wrapper becomes part of
the signature.

Two mechanisms are available, and they are not equivalent:

- **Direct-style blocking on virtual threads.** The call looks like any other call, blocks the
  virtual thread, and lets the carrier run something else. The signature is unchanged; nothing in the
  language or ABI changes.
- **A monadic or CPS encoding of the suspension.** The operation returns a suspended computation and
  the caller chains it; resumption is explicit. This imposes a wrapper on every participating
  signature. The mechanism analysis is recorded in [ZEP-0007](./ZEP-0007.md); this proposal does not
  adopt it.

Zeron targets JDK 25 and already has Java interoperability, so blocking calls are the natural shape.
What the standard library lacks is a way to *start*, *bound*, *cancel*, and *join* concurrent work
without exposing raw threads, and a rule for what happens to raised effects inside such work. That is
this proposal's scope. The language-level async effect surface is layered on top in
[ZEP-0120](./ZEP-0120.md); this proposal is the runtime primitive it uses.

## Goals

- Provide structured concurrency: create a scope, start tasks in it, join all of them, cancel on
  failure, and propagate cancellation to children.
- Use virtual-thread blocking as the suspension mechanism, with no `async`/`await` keyword, no
  wrapper return type, and no compiler transform in this proposal.
- Define how raised effects interact with task boundaries: capture at the boundary, re-raise at the
  join point, never implicitly cross a thread.
- Define failure and cleanup precedence, reusing the existing `using` and suppressed-failure rules.
- Keep the implementation portable across supported JVMs, without depending on preview APIs.

## Non-goals

- Continuation capture, resumption, or anything that would turn virtual threads into algebraic-effect
  handlers. [ZEP-0007](./ZEP-0007.md) explicitly warns against assuming that equivalence, and this
  proposal does not.
- The effect-level async surface (`Await`, `Future`, `spawn`, `await`). That is
  [ZEP-0120](./ZEP-0120.md), built on this proposal's `Scope` and `Task`.
- `async`/`await` keywords, monadic task types in signatures, or compiler CPS transformation.
- Deterministic single-threaded interleaving, cooperative scheduling of user code, multi-shot
  continuations, or generators. Those need a different runtime; see
  [ZEP-0119](./ZEP-0119.md), [ZEP-0121](./ZEP-0121.md), and [ZEP-0111](./ZEP-0111.md).
- Parallel collections, reactive streams, or a scheduler abstraction with pluggable policies beyond
  a single injected executor for tests.
- Changing `raise`/`handle` coverage, `using`, or Java exception translation.

## Proposal

### Surface

`do`-notation and block handlers from [ZEP-0111](./ZEP-0111.md) and
[ZEP-0110](./ZEP-0110.md) are independent of this proposal. Here the surface is library-level:

```zeron
fn loadAll(ids: Array<Int>): Array<User> raises DbError {
    using (scope = Scope.open()) {
        let first = scope.start(() -> repo.user(ids[0]));
        let second = scope.start(() -> repo.user(ids[1]));
        join(scope);
        return [first.value(), second.value()];
    }
}
```

- `Scope.open()` starts a scope bound to the enclosing `using` block; closing it joins or cancels
  outstanding tasks and never leaves one running.
- `scope.start(block)` runs the block on a virtual thread and returns a `Task<T>` handle. The block's
  raised effects do not escape the task implicitly.
- `Task<T>.value()` blocks the caller (suspending its virtual thread) until the task completes and
  returns its result, re-raising a captured effect at the call site so ordinary handlers apply there.
- `Scope.cancel()` cancels the scope's tasks cooperatively; structured shutdown is the default, and
  a scope does not outlive its `using` block.
- Timeouts are expressed as `Scope.deadline` or a `withTimeout` library helper; no language syntax is
  added.

Whether the surface is spelled `Scope`/`Task` or follows another naming scheme is a library decision
recorded during implementation, not part of this proposal's design direction.

### Effect and exception rules

- **Capture at the boundary.** A raised effect inside a task body is captured as the task's outcome,
  not thrown across threads. Stack unwinding stops at the task boundary.
- **Re-raise at the join.** `value()` re-raises the captured effect in the joining thread, where
  existing handlers and declared rows apply. The joining function's row must therefore cover every
  effect its tasks may raise; a task body that exceeds that row is a compile-time diagnostic, not a
  runtime surprise.
- **`using` inside a task.** Cleanup obligations run inside the task that owns them, with the
  existing primary-effect/suppressed-failure precedence. A task that is cancelled during cleanup
  follows the same rules for interruptions that the resource guide defines for interruption of a
  `using` body.
- **Java exceptions.** No automatic translation is introduced. A Java method that declares a checked
  exception still maps to an effect only through the existing explicit interop mapping
  ([ZEP-0049](./ZEP-0049.md)); an unmapped exception fails the task and surfaces as a host failure at
  the join point.
- **No implicit sharing of mutable state.** Lambdas passed to `start` follow the existing capture
  rules from [ZEP-0002](./ZEP-0002.md): mutable captures are explicit, and cross-task mutation is
  never implied by the API.

### Runtime requirements

- Virtual threads are the execution mechanism; the standard library must not require a preview API.
  Where a platform structured-concurrency API exists and is final, it may be used internally behind
  the Zeron surface; otherwise the scope is implemented over an `ExecutorService` of virtual threads
  with an explicit join/cancel/shutdown protocol.
- The carrier pool must not be pinned by library code. Blocking on `Task.value()` inside a virtual
  thread parks rather than blocks a carrier. Implementation must verify pinning behavior on the
  supported JDK and document any library operation that still pins.
- Scope-local context, if needed for tracing or deadlines, must not rely on inheritable thread
  locals in a way that surprises virtual-thread migration; if a context mechanism is required, it is
  a separate proposal.
- A single-process, injected executor must be available so tests are deterministic in ordering of
  joins and cancellation, without asserting wall-clock timing.

### Relationship to ZEP-0120

[ZEP-0120](./ZEP-0120.md) defines `Await`, `Future`, `spawn`, and `await` as an optional effect
surface. It does not add a second runtime:

- `spawn(scope, body)` wraps `scope.start`;
- `Future.join()` wraps `Task.value()`;
- `await` is a tail-resumptive handler that calls `join` and resumes with its result.

The blocking suspension, cancellation, effect-capture, and cleanup semantics are this proposal's.
ZEP-0118 (response types) and ZEP-0119 (continuation capture) are not prerequisites for using
`Scope`/`Task` directly, and a user may ignore the effect surface entirely.

### Why not a task monad

A `Task<T>` free monad with an interpreter would also solve suspension, and it composes with the
do-notation of [ZEP-0111](./ZEP-0111.md). It is rejected as the *default* strategy because it
reintroduces coloring at the library boundary: every function participating in a task becomes
`Task`-returning, and interop with blocking Java APIs requires adapters at each boundary. It remains
a reasonable later library addition for deterministic composition, and nothing here prevents it.

## Compatibility and impact

- No language or ABI change. Signatures keep their current shape; a function that blocks on I/O is an
  ordinary function with an ordinary `raises` row.
- Standard-library addition only: new public contracts and functions, with the usual library-index
  encoding and separate-compilation round trip.
- Behavior change: none for existing code, since no existing library API becomes implicitly
  concurrent. Concurrency is always entered explicitly through a scope.
- Documentation: resource-management guide gains scoped-task cleanup rules; I/O and networking guides
  gain a "blocking is cheap" note; the raised-effects guide gains the capture-at-boundary/re-raise-at-
  join rule.

## Alternatives

- **`async`/`await` syntax with a compiler transform.** Familiar, but colors every participating
  signature, requires the CPS/state-machine machinery in [ZEP-0119](./ZEP-0119.md) and
  [ZEP-0121](./ZEP-0121.md), changes method descriptors, and has no good answer for foreign Java
  frames.
- **A monadic `Task` library with explicit binds.** Keeps the compiler unchanged but moves coloring
  into the library and requires adapters for blocking interop; viable as an addition, not as the
  default.
- **Raw `Thread`/`ExecutorService` through Java interop.** Works today, but has no structured shutdown,
  no effect-capture rule, and no cancellation contract; users would reimplement the scope in every
  project.
- **CPS-transform only the suspending library functions.** Splits the world into transformed and
  untransformed callees, which is coloring by another name and breaks at the Java boundary.
- **Do nothing until a resumption proposal is accepted.** Leaves the concurrency primitive
  unexamined; ZEP-0119 and ZEP-0121 are about resumption, not about I/O concurrency, and neither
  supplies scopes, tasks, or structured shutdown.

## Implementation and validation

Stages:

1. Spike: a `Scope` over virtual threads with join, cancel, deadline, and a `Task<T>` handle; measure
   carrier pinning, task startup cost, and cancellation latency with a representative blocking
   workload.
2. Contracts and semantics: effect capture at the boundary, re-raise at join, cleanup precedence,
   capture-rule checks for task lambdas.
3. Library integration: I/O and networking entry points documented as blocking; a sample program that
   fans out several requests and joins.
4. Documentation and migration notes.

Validation:

- fan-out/join over a blocking I/O workload with bounded concurrency, checking that thread count stays
  proportional to tasks in flight rather than to platform threads;
- a task that raises a declared effect: capture at the boundary, re-raise at `value()` inside a
  handler, and the negative case where the joining row omits it;
- cancellation: a scope cancelled while a task blocks, verifying cooperative interruption, no leaked
  task after scope close, and suppressed cleanup failures;
- `using` inside a task and around a scope, checking precedence when both the body and disposal fail;
- a Java method that throws an unmapped exception, checking it surfaces as a host failure at the join
  point and not as a Zeron effect;
- an injected single-threaded executor to make join order and cancellation paths deterministic without
  wall-clock assertions;
- pinning measurement on the supported JDK for every library blocking operation, recorded with the
  measured numbers rather than assumed.

## Open questions

- Whether the scope belongs in `using` only, or whether a `withScope` helper should also exist for
  expression positions.
- Whether effect re-raising at the join point should aggregate multiple task failures (a suppressed
  list, like cleanup failures) or surface the first failure and cancel the rest. The first is
  proposed; aggregation needs a payload shape that does not exist yet.
- Whether deadlines belong on the scope, the task, or both.
- Whether task-local context is needed at all, and if so, whether it can be expressed as an explicit
  parameter rather than a runtime context mechanism.
- Whether a `Task<T>` free-monad library should be specified as a companion for deterministic
  composition, or deferred until a use case requires it.
