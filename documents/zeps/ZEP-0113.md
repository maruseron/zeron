# ZEP-0113: Declaration-Site Covariance for Sum and Product Types

## Abstract

Extend Zeron's explicit, checked declaration-site covariance (`out`) from generic classes and
contracts to nominal sum and product type declarations. Read-only sums and products then admit the
same safe widening conversions as read-only classes, and the standard-library `Option`, `Result`,
and `Pair` adopt covariant parameters.

## Motivation

Sum and product types are Zeron's primary immutable data carriers. `Option<T>`, `Result<T, E>`, and
`Pair<A, B>` expose their components for reading but do not permit callers to write through them.
Today `Option<Dog>` is not usable where `Option<Animal>` is expected, even though every operation
that reads the payload is safe under that widening. Callers must map every value, duplicate helpers
for supertypes, or lose precision at API boundaries.

[ZEP-0051](./ZEP-0051.md) introduced checked `out` parameters for generic classes and contracts but
explicitly excluded sums and products. Most of the supporting machinery is already present:

- `TypeCompatibility` applies declaration variance for classes and contracts.
- A sum is compiled as a compiler-synthesized sealed contract plus case classes; a product is
  compiled as a generated class with read-only properties.
- The versioned library index already records variance for sum and product type parameters.

Two gaps remain. The parser rejects `out` on a `type` declaration, and the variance-position checker
treats synthesized sum payload fields as invariant because it cannot tell them apart from ordinary
mutable class fields. This proposal closes those gaps without introducing a new runtime
representation or a new variance form.

## Goals

- Allow `out` on generic sum and product declarations in the same positions as on generic classes
  and contracts.
- Enforce the existing variance-position rules against sum payloads, product components, generated
  members, nested applications, and derived contracts.
- Make `S<A>` safely assignable to `S<B>` for covariant parameters, using the existing nominal
  subtyping and inference model.
- Preserve invariance for ordinary mutable fields, writable properties, mutable references,
  arrays, and generic effects.
- Adopt covariance for `Option`, `Result`, and `Pair` in the standard library.
- Preserve erased JVM descriptors and existing generated class names.

## Non-goals

- Declaration-site contravariance (`in`).
- Inferring variance from payload or component use.
- Covariance for newtypes, type aliases, functions, or function types.
- New existential type formers, stored existentials, or general existential inference; see
  [ZEP-0104](./ZEP-0104.md), [ZEP-0105](./ZEP-0105.md), and [ZEP-0106](./ZEP-0106.md).
- Writable covariant payloads or components.
- ADT-specific generic bounds beyond the existing bounds and admissibility markers.
- Extending use-site projections (including star views) to sum and product applications; that
  remains excluded by [ZEP-0052](./ZEP-0052.md).
- Changing structural equality, hashing, generic effect identity, or HKT constructor identity.
- Reifying generic arguments or adding runtime variance checks.
- Changing Java wildcard mapping or array covariance.

## Proposal

### Surface syntax

A sum or product declaration may mark a type parameter `out`:

```zeron
public type Option<out T: nullable + mut> =
      Some(value: T)
    | None;

public type Result<out T: nullable + mut, out E: nullable + mut> =
      Ok(value: T)
    | Err(error: E);

public type Pair<out A: nullable + mut, out B: nullable + mut> = (fst: A, snd: B);
```

`out` is accepted on a generic sum or product declaration exactly where it is accepted on a generic
class or contract. Unannotated parameters remain invariant. `in` remains rejected, and `out`
remains rejected on function, extension, and witness type parameters. No other syntax changes.

### Read-only payloads and components

A sum case payload is read by pattern matching, and the synthesized case-class field is assigned
only by the constructor; it is not writable from source. A product component becomes a read-only
property. These are positive positions, analogous to a non-mutating property on a covariant class.

Ordinary private class fields remain invariant. This proposal narrows the checker only for
compiler-synthesized, read-only sum payload fields and product components. If a future construct
permits writing such a component, that occurrence remains invariant and the corresponding `out`
declaration must be rejected.

### Variance checking

The rules from [ZEP-0051](./ZEP-0051.md) apply unchanged:

- Method and function results, read-only properties, pattern outputs, and covariant nested
  applications are positive positions.
- Method and function parameters are negative positions; function-type parameters reverse polarity
  and function-type results preserve it.
- Nullable wrappers preserve polarity.
- Mutable references, writable properties, mutable fields, arrays, invariant generic applications,
  and raised effects make an occurrence invariant.
- An `out` parameter may occur only in covariant positions. Bounds do not grant unchecked
  value-level occurrences.

For a sum declaration, every payload type is checked at positive polarity. The generated sealed
contract and case classes inherit the sum's variance. The case class's use of the sealed contract is
a covariant occurrence, and constructor inputs are not treated as member input positions. For a
product declaration, every component type is checked at positive polarity; its generated read-only
properties are positive and its constructor inputs are not member input positions.

Derived contracts are checked as contract uses under the derived contract's declared variance. A
covariant sum or product that would pass `T` into an invariant or consuming position of a derived
contract is rejected. In particular, deriving an invariant equality contract that consumes `T` is
not automatically permitted merely because the payload is read-only.

Extensions and witnesses remain separate declarations with their own invariant type parameters.
Covariance of the target type does not make an extension or witness type parameter covariant. An
extension whose receiver is `Option<T>` still instantiates its own `T` at each call, and declaration
covariance permits a wider receiver instantiation where ordinary assignability allows it.

An implementation may either validate the source `SumDecl`/`ProductDecl` and its derived contracts
directly, or classify the compiler-synthesized payload fields as read-only for the existing checker.
Ordinary `Stmt.Field` occurrences must not be reclassified.

### Subtyping and inference

If `S` is a nominal sum or product with corresponding `out` parameters, then `S<A1, ..., An>` is
assignable to `S<B1, ..., Bn>` when each `Ai` is assignable to the corresponding `Bi` for a
covariant parameter and exactly equal for an invariant parameter. The same nominal declaration is
required; variance does not create inheritance between unrelated declarations.

Variance conversions preserve nullability and reference capability. They compose through nested
applications according to each declaration's variance, so `Option<Result<Dog, E>>` is assignable to
`Option<Result<Animal, E>>` when `Result`'s first parameter is covariant. `Array<T>`, mutable
references, and generic effect arguments remain invariant.

This proposal adds no common-supertype inference or variance-driven inference. Existing structural
inference continues to work as it does today; callers may need an explicit expected type where
variance alone would otherwise have to infer a wider type. Once types are resolved, ordinary
assignment, argument, and result compatibility apply the variance conversion.

HKT constructor identity is unchanged. `Option<_>` remains the same type constructor when passed to
an HKT contract; variance applies when an applied source type is checked, not when a constructor is
used as a higher-kinded argument.

### Standard library adoption

`Option`, `Result`, and `Pair` adopt the annotations shown above. Their extensions and witnesses do
not need new variance annotations: those declarations have their own invariant parameters, and a
widened receiver is handled by ordinary assignability. For example, after `Option<Dog>` is widened
to `Option<Animal>`, `getOrElse(animal)` is an ordinary call on `Option<Animal>`.

Structural equality, hashing, and generated `Eq` behavior are unchanged. A covariant ADT that
derives a contract consuming `T` is rejected by the variance check rather than silently weakening
equality.

### Projected ADT applications

[ZEP-0052](./ZEP-0052.md) excludes generic sum and product applications from use-site projections.
This proposal does not lift that exclusion. `Option<out Animal>` and `Option<*>` over a Zeron sum or
product remain unsupported in this slice. The implementation should reject those applications with a
clear diagnostic instead of accepting a partially working view.

Extension or witness dispatch over a projected or captured ADT receiver is therefore outside this
proposal. Any later proposal that adds projections over ADTs must reuse the projection/capture model
already used for classes and contracts, rather than binding extension type parameters directly to a
projection descriptor.

### Compilation and metadata

Variance remains a compile-time assignability rule. It does not reify generic arguments or change
JVM erasure, and the generated sealed-contract and case-class names remain unchanged. The library
index already serializes type-parameter variance for `SumExport` and `ProductExport`; the
implementation must verify that this metadata round-trips and that separately compiled consumers
apply the same rules. No API-index schema change is expected. Invalidating or versioning the
standard-library index is required because its public signatures change: bump
`STANDARD_LIBRARY_API_VERSION` once per release cycle when the updated standard library ships.

## Compatibility and impact

This is an additive source feature. Declarations without `out` remain invariant, so existing
programs keep their current semantics. Source that currently writes `out` on a sum or product is
rejected today and begins to compile.

The new subtype relation can affect overload selection, inference, and assignability in existing
code that already uses the affected generic ADTs. The change is monotonic for valid programs, but
new conversions can make an overload set ambiguous or allow a call that previously required an
explicit mapping. Regression tests should cover inference and overload behavior, not only direct
assignments.

Public standard-library signatures change from invariant to covariant. Consumers compiled against
the old standard-library index must be rebuilt or use the versioned index invalidation rules.
Separately compiled user libraries keep whatever variance their own declarations recorded; an
unannotated declaration remains invariant even if a newer compiler could prove it read-only.

## Alternatives

- Keep sums and products invariant and require callers to map values — simple, but leaves the most
  common read-only containers without the substitutability already provided for classes.
- Infer variance automatically from payload and component use — avoids annotations, but makes the
  public contract depend on hidden representation and conflicts with ZEP-0051's explicit model.
- Treat every ADT payload as covariant without an `out` marker — convenient, but removes the
  declaration's ability to promise a narrower contract and would become unsound if writable
  payloads are added.
- Extend use-site projections over ADTs at the same time — broader and requires the capture work
  that ZEP-0052 deferred; declaration-site covariance already covers the main widening need.

## Implementation and validation

1. Allow `out` on generic `type` declarations for sums and products; keep `in` and variance on
   other declaration forms rejected.
2. Propagate variance to the synthesized sealed contract, case classes, and product class. Mark
   synthesized sum payload fields and product components as read-only for variance checking without
   relaxing ordinary class fields.
3. Validate payloads, components, generated members, derived contracts, nested applications,
   nullable/reference wrappers, arrays, and effects with the existing polarity rules. Diagnostics
   should name the unsafe payload or component.
4. Verify `TypeCompatibility` applies variance for sum contracts and product classes, and that the
   library index round-trips variance across separately compiled libraries.
5. Annotate `Option`, `Result`, and `Pair`, update standard-library documentation, and bump
   `STANDARD_LIBRARY_API_VERSION` when the change ships.
6. Reject use-site projections over ADT applications with a clear diagnostic while keeping
   `Array<*>` rejected.
7. Add resolver tests for valid and invalid declarations; assignments, arguments, and results;
   nested and nullable applications; matching; extensions and witnesses after widening; derived
   contracts; generic bounds; and inference/overload regressions.
8. Add separate-compilation tests that build a library with a covariant sum and product and consume
   it through the API index. Use `javap -classpath dist` to confirm that generated class names and
   method descriptors are unchanged.
9. Remove `dist/` before compiling Zeron sources, run focused tests during development, and run the
   full `mvn test` suite sparingly.

## Open questions

- Should `out` eventually be permitted on newtypes and type aliases, or should the explicit
  covariance surface remain limited to classes, contracts, sums, and products?
- Are ADT use-site projections a desirable follow-up, or does declaration-site covariance make
  projections over sums and products unnecessary?
- How should the `mut` admissibility marker interact with covariance in diagnostics and in
  documentation, given that it never makes a stored position writable?
- Should generated case classes expose their inherited variance in public API documentation, or only
  the source sum declaration?
