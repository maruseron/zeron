# ZEP-0115: Warning-Severity Compiler Diagnostics

| Field | Value |
| ----- | ----- |
| Status | Implemented |
| Author | Marcelo Rodríguez |

| Updated | 2026-11-11 |

## Abstract

Give the compiler a first-class warning channel. A diagnostic may be declared with warning severity,
reported without aborting the current stage, collected alongside errors, and printed with the same
formatting and source spans. Warnings do not change the exit code by default; an explicit
`--deny-warnings` option turns them into a build failure. Errors keep their current behavior,
including throwing through the resolver.

## Motivation

`Severity` already distinguishes `ERROR`, `WARNING`, and `INFO`, and the LSP maps all three to editor
severities, but nothing produces a warning. Every catalog entry is created with the default error
severity, every resolver diagnostic is thrown as a `ResolutionError`, and the CLI derives its exit
code from `hadResolutionError`. The result is a compiler that can only accept or reject a program.

That gap now blocks work the project has already accepted:

- [ZEP-0114](./ZEP-0114.md) deprecates anonymous witness declarations; without warnings the
  deprecation is either silent or a hard error before the removal release.
- Routine but suspicious code such as an unused import, an unreachable branch, a shadowed binding,
  or a redundant visibility marker cannot be flagged without rejecting the program.
- Library authors have no way to signal a deprecated API while keeping consumers building.
- Tooling cannot distinguish "this must be fixed" from "this deserves attention", even though the
  editor already has the severity to display it.

A warning channel also gives deprecations a migration path: ship a warning, let code keep building,
then remove the construct in a later release.

## Goals

- Allow a catalog entry to be declared with warning severity, with a stable code and explanation.
- Add a reporting API that emits a warning, records it in the current result, and never throws.
- Report warnings through the existing diagnostic formatter, ordering, and source-span machinery.
- Keep builds succeeding when only warnings are present, and give users an explicit way to deny
  warnings.
- Expose warnings separately from errors in compiler results so tests and tools can assert on them.
- Publish warnings to the language server with warning severity.
- Use the channel for the ZEP-0114 anonymous-witness deprecation.

## Non-goals

- A suppression mechanism, `@Suppress`-style attributes, or per-code configuration files. This
  proposal defines the channel; suppression can be a later proposal.
- Turning existing diagnostics into warnings by default, or reclassifying current errors.
- Auto-fixes or code actions attached to warnings.
- A new code namespace for warnings. Warning entries share the existing `ZRxxxx` catalog and carry
  severity in the entry rather than in the number.
- Changing how errors abort a stage. Errors keep throwing; warnings are additive.
- Making `INFO` a user-facing category. It remains reserved for tooling and notes.

## Proposal

### Catalog entries

`DiagnosticCatalog.Entry` already stores a severity. It gains a warning constructor:

```java
public static final Entry ANONYMOUS_WITNESS_DEPRECATED = warning(
        "ZR3010", "Anonymous witness declarations are deprecated");
```

Entries keep one code space. The number says which diagnostic fired; the severity says whether it
blocks the build. A warning may later be promoted to an error by changing one catalog entry, without
renumbering tooling configuration.

### Reporting

```java
public static void warning(final Token token, final Entry entry, final String message) {
    reportWarningDiagnostic(Diagnostic.atToken(entry, token, token.span().sourcePath(), message));
}

public static void reportWarningDiagnostic(final Diagnostic diagnostic) {
    reportStageDiagnostic(diagnostic);
    // no hadError / hadResolutionError flag
}
```

A warning is reported immediately, in source order relative to other diagnostics of the same stage.
It never throws, so the stage continues and can report more warnings. Warnings and errors share the
renderer, so labels, notes, and helps behave identically; only the prefix and the exit status differ.

Duplicate suppression is stage-local: identical code, span, and message emitted twice by the same
stage is reported once. Warnings from separate stages are not deduplicated.

### Results and exit status

`ResolutionResult` and `CompilationResult` gain `warnings()` alongside `errors()`. `errors()` returns
only error-severity diagnostics, so existing callers keep their meaning. A build with warnings and no
errors compiles, writes its output, and exits successfully.

An opt-in option makes warnings fatal:

```text
zeron build --deny-warnings
zeron run --deny-warnings
```

With `--deny-warnings`, warnings are still reported as warnings, but the invocation exits with the
existing resolution or compilation failure code after the stage completes. The option does not change
diagnostic text or promote entries in the catalog.

### Language server

The LSP already maps `Severity.WARNING`; warnings are published as diagnostics with warning severity
and do not affect whether a document compiles. No protocol change is needed.

### First use

[ZEP-0114](./ZEP-0114.md) declares anonymous witnesses deprecated at introduction. Once this proposal
lands, the parser reports `ANONYMOUS_WITNESS_DEPRECATED` at each anonymous `witness` declaration with a
help naming the replacement form. The declaration keeps working for the migration release, and the
following release rejects it as an error.

## Compatibility and impact

No source syntax changes. Programs that compile today keep compiling, and programs that fail keep
failing with the same errors. The visible changes are new advisory output and new result accessors.

Tooling that treats any diagnostic as failure must filter by severity; the compiler's own exit code
already ignores warnings unless `--deny-warnings` is passed. Snapshot tests that compare full
diagnostic output may need to account for warnings, but only for programs that trigger them.

The catalog, formatter, and LSP already support severity, so no runtime or library-index change is
involved. The API-index schema is unaffected.

## Alternatives

- Report deprecations as errors and remove the construct in the same release — simplest, but breaks
  working code with no migration window, which is why ZEP-0114 separates introduction from removal.
- Emit warnings through `System.err` without a diagnostic object — cheap, but loses spans, codes,
  formatting, LSP delivery, and testability.
- Promote all existing soft diagnostics to warnings — tempting, but requires auditing every catalog
  entry; this proposal adds the channel and lets future proposals reclassify entries deliberately.
- Add a suppression mechanism in the same proposal — useful, but it expands the design into
  configuration and annotation semantics; the channel should land first.

## Implementation and validation

1. Add a warning-severity constructor to `DiagnosticCatalog.Entry` and keep existing entries as
   errors.
2. Add `Zeron.warning(...)` and `Zeron.reportWarningDiagnostic(...)` that report without setting the
   error flags, plus stage-local duplicate suppression.
3. Split `errors()` and `warnings()` in `ResolutionResult` and `CompilationResult`, preserving the
   current meaning of `errors()` and `successful()`.
4. Add `--deny-warnings` to the CLI options and apply it at the end of resolution and compilation,
   without changing how errors abort a stage.
5. Report warnings through the LSP with warning severity.
6. Use the channel for ZEP-0114's anonymous-witness deprecation.
7. Tests: a warning is reported and the program compiles; `errors()` excludes it and `warnings()`
   contains it; exit code stays zero; `--deny-warnings` exits nonzero after reporting; errors still
   abort with their existing code; duplicate warnings are collapsed; warnings from two stages are
   both reported; the formatter renders warning severity; the LSP publishes warning severity.
8. Remove `dist/` before compiling Zeron sources, run focused tests during development, and run the
   full `mvn test` suite sparingly.

## Implementation status (2026-11-11)

Implemented in this slice:

- A warning-severity catalog constructor and `Zeron.warning` reporting that never sets an error
  flag, uses the existing formatter and source spans, and suppresses identical stage-local repeats.
- `ResolutionResult.warnings()` and split `CompilationResult.errors()`/`warnings()`, with
  `successful()` and `errors()` keeping their error-only meaning.
- `--deny-warnings` for project builds, runs, and direct compilation.
- `--no-warnings` for the same commands, which hides warning output without suppressing collection
  or changing the exit status; it composes with `--deny-warnings`.
- Warning delivery through the language server, which already maps warning severity.
- The ZEP-0114 anonymous-witness deprecation (`ZR3010`) and an initial warning set: unused local
  variables (`ZR3011`), imports (`ZR3012`), and private functions (`ZR3013`), unreachable
  statements (`ZR3014`), unnecessary mutable projections (`ZR3015`), `while (true)` loops
  (`ZR3016`), and shadowed locals (`ZR3017`).

Not implemented: source- or manifest-level warning suppression, per-code denial, attached fixes,
and warning emission from bytecode generation. `--no-warnings` is display filtering, not a
suppression mechanism.

## Open questions


- Should suppression be a source annotation, a manifest setting, or a CLI code filter, and should it
  be per file or per project?
- Should CI configurations be able to deny specific warning codes rather than all warnings?
- Should a warning ever be emitted from code generation, or is the channel limited to scanning,
  parsing, resolution, and compilation?
- Should duplicate suppression be keyed on code and span only, or also on message text?
- Should `--deny-warnings` be an alias for promoting entries, or remain an invocation-level gate as
  proposed?
- Do generated documentation and `zeron explain` need a separate warning section, or is the entry's
  severity enough?

## Decision

Accepted 2026-11-11 and implemented. Warnings are non-fatal by default, share the error catalog and
formatter, are exposed separately in compiler results, and can fail an invocation with
`--deny-warnings`. The initial warning set is advisory and does not reclassify existing errors.
