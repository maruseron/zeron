## Abstract

This proposal collects the work deferred from [ZEP-0105](./ZEP-0105.md) after its direct
`if`/`while` opening slice shipped. It covers:

- composed, mixed, nested, and binder-annotated opening patterns;
- the remaining escape contexts and escape approximation;
- result-position anonymous existentials;
- opening `in` projections once lower bounds exist;
- variance and pointwise subtyping for existential views;
- raw-`Any` bound/evidence rules and shared capture representation.

The implemented `C<let T>` form remains specified by ZEP-0105. This proposal does not reopen that
slice.

## Motivation

ZEP-0105 gives a local name to an otherwise hidden type argument:

```zeron
if (box is Box<let T>) {
    let value: T = box.value;
}
```

That covers the common branch-local case, but several useful cases still fail:

- a pattern that mixes a known argument with an opened one, such as `Map<Int, let V>`;
- a nested pattern such as `Box<Box<let T>>`;
- opening as one clause of a larger condition or after an `else if`;
- returning or storing an opened value through an explicit approximation;
- returning an anonymous existential from a function;
- using an `in` projection after lower bounds are available;
- proving that every escape path out of a branch is closed.

Without a defined continuation, users must fall back to hand-written helpers or unsafe casts. This
proposal is the design home for those continuations.

## Goals

- Define additional opening-pattern shapes without weakening ZEP-0105's branch scoping.
- Complete escape analysis for raised effects, closures, fields, containers, and aliases.
- Decide whether escaping opened values are errors, bound approximations, or explicit re-packings.
- Decide when result-position anonymous existentials are useful and how reified results are
  carried.
- Define `in` projection opening if lower bounds are introduced.
- Define variance and pointwise-subtyping rules for existential views.
- Specify how raw `Any` tests interact with class-declared bounds and available evidence.
- Share the capture representation with ZEP-0052 projections.
- Add validation for nullable and mutable binders, branch-local closures, and exact tests.

## Non-goals

- Re-specifying the implemented direct `if`/`while` opening form; see [ZEP-0105](./ZEP-0105.md).
- Stored existentials and holder ABI; see [ZEP-0106](./ZEP-0106.md).
- Rank-2 polymorphism and library `use`; see [ZEP-0109](./ZEP-0109.md).
- Contract-bound runtime tests; see [ZEP-0108](./ZEP-0108.md).
- General skolemized `let` in arbitrary type position.
- Reflection or dynamic type extraction from a descriptor.
- An `any Contract` type.

## Proposal

### Composed and conditional forms

ZEP-0105 requires the opening test to be the direct condition. This proposal may allow:

- an opening test as one clause of `and`/`or`, provided the binder's scope and short-circuit path
  are defined;
- an opening test in an `else if` chain;
- an opening test that is guarded by a preceding null or class check;
- opening in a value-producing `if` expression, with the binder scoped to its true result branch.

Each extension must preserve the rule that a binder is introduced only on the path where the test
succeeds. A composed condition cannot make the binder visible before its test succeeds, and an
opening test that is negated cannot introduce a binder. The design must also state whether a
binder can be used in the remainder of a short-circuit expression after the test.

### Mixed exact/open patterns

A mixed pattern such as:

```zeron
if (pair is Pair<Int, let V>) {
    let value: V = pair.second;
}
```

combines an exact argument test with an open binder. The proposal must define:

- when the exact argument is checked statically, by an erased class test, or through an inherited
  descriptor;
- whether the exact argument must be statically determined before the pattern is accepted;
- how a failed exact argument interacts with the open binder's scope;
- which argument positions may be open when the target has covariant or projected parameters.

The preferred direction is to reuse ZEP-0104's static-proof boundary: exact arguments are accepted
only when their applied identity is statically justified, and mixed patterns do not invent runtime
descriptors.

### Nested opening

A nested pattern such as:

```zeron
if (box is Box<Box<let T>>) {
    // T names the inner hidden argument
}
```

requires more than one raw class test and a nested binder-scope rule. The design must define:

- whether the outer and inner classes must be runtime-testable;
- how a failure at either level maps to the true and false paths;
- whether an outer binder can be opened at the same time;
- how nested binders interact with totality and unreachable branches.

The first implementation may require every level to be statically known or raw-class testable and
may reject nested opening when a level needs an unavailable descriptor.

### Binder-declared bounds and markers

ZEP-0105 rejects `Box<let T: Render>` because the source type carries the bound. A later form could
allow an explicit binder bound:

```zeron
if (box is Box<let T: Render>) {
    box.value.render();
}
```

The design must define whether this is:

- an intersection with the source bounds;
- a stronger requirement that narrows the accepted source view;
- or unsupported because the source is the only authority for inherited evidence.

Binder-owned markers such as `nullable` and `mut` need the same treatment. The implementation must
not synthesize evidence that the source did not carry.

### Complete escape checking

ZEP-0105 rejects returns and assignments to non-branch-local bindings. This proposal completes the
escape boundary for:

- raised effects whose type mentions an opened binder;
- closures and function values that capture a binder and escape the branch;
- storing a binder-typed value in a field or outer container;
- assigning through a reference or alias to storage that outlives the branch;
- returning a value from a nested lambda that outlives the branch;
- loop bodies and `break`/`continue` paths that would leak a binder;
- separate-compilation or library boundaries that would serialize a binder.

The diagnostic should identify the binder, the escape path, and the branch that owns it.

### Escape approximation and re-packing

Instead of rejecting every escape, a later version may approximate an escaping type by its upper
bound or by an anonymous existential:

```zeron
fn leak(box: Box<*>): Box<*> {
    if (box is Box<let T>) {
        return box as Box<*>; // possible future re-packing
    }
    return box;
}
```

The design must choose between:

- **error only**, as in ZEP-0105;
- **approximate by bound**, returning `Render` or `Box<: Render>`;
- **explicit re-packing**, requiring a visible projection or existential construction.

Approximation interacts with reification: an approximated reified binder needs a descriptor
carrier. That carrier belongs to [ZEP-0106](./ZEP-0106.md) or a coordinated ABI extension.

### Result-position anonymous existentials

ZEP-0105 allows opening a value but rejects returning `T` or `Box<T>`. This proposal decides
whether a function may return an anonymous existential:

```zeron
fn make(): Box<: Render>;
```

A non-reified result is erased and may need no new runtime representation. A reified result needs a
carrier for the hidden argument's descriptor and the holder ABI from
[ZEP-0106](./ZEP-0106.md). The design must define packing at the return site and opening at the
call site, including how the caller can test or forward the hidden argument.

### `in` projections and lower bounds

ZEP-0105 rejects opening `C<in B>` because the type system has no lower-bound representation.
This proposal may add:

- a lower-bound fact on the opened binder;
- a conversion from the opened value to the lower bound;
- rules for combining a lower bound with an upper bound or a class-declared bound.

If lower bounds remain unsupported, the rejection should become permanent and documented as a
type-system boundary rather than a temporary limitation.

### Variance and pointwise subtyping

Anonymous existentials hide an invariant argument in ZEP-0104. Star views are projections. Opening
does not change variance today. Later work may allow:

- `F<: B>` to relate to `G<: B>` when `F` and `G` are pointwise related;
- covariant `F` to preserve a wider bound;
- projections to be explained as a restricted existential view;
- an opened binder to be used where a covariant supertype is expected.

Pointwise subtyping is likely too complex for the near term. It should remain deferred unless a
concrete API requires it.

### Raw `Any` and inherited class bounds

A raw test from `Any` proves only the erased class. Class-declaration bounds remain static type
facts, but ZEP-0105 does not synthesize the evidence needed to call bound operations. This proposal
must decide whether a later version can:

- use a class-declared bound only when compatible evidence is already in scope;
- report a targeted diagnostic distinguishing “bound known” from “evidence available”;
- reject the raw-class form entirely for classes whose bounds require unavailable evidence.

Opening must never invent a witness or descriptor from a raw class test.

### Shared capture and projection model

Pattern opening and ZEP-0052 projections both describe unknown arguments. They should share the
same internal captured-type representation:

- star views approximate the hidden argument by `Any?`;
- anonymous existentials add implicit packing and capture at generic call sites;
- pattern opening introduces a branch-scoped rigid name for the already-captured argument;
- mixed and nested patterns preserve the same captured argument identities;
- descriptors and evidence are inherited, never synthesized by opening.

### Relationship to rank-2 and stored proposals

Rank-2 `use` remains a library alternative in [ZEP-0109](./ZEP-0109.md). Stored and result-position
existentials remain coordinated with [ZEP-0106](./ZEP-0106.md). This proposal does not make opening
depend on rank-2 polymorphism, and it does not move holder representation into the branch-scoped
form.

### Validation gaps

Focused coverage must include:

- nullable and mutable binder markers;
- branch-local closures that do and do not escape;
- raised effects that mention a binder;
- assignments through aliases, fields, and outer containers;
- mixed and nested patterns with exact, raw, and reified arguments;
- total and partial patterns at each nesting level;
- exact tests through inherited descriptors;
- separately compiled library callers;
- the interaction of opening with `Codec`, `Encode`, and `Decode` bounds where applicable.

## Compatibility and impact

Branch-local extensions should preserve the ZEP-0105 ABI: no descriptor slot, evidence slot, or
library-index field is added for a binder that stays inside its branch.

Result-position existentials and escape approximation may require a carrier or descriptor metadata.
Those changes must be coordinated with [ZEP-0106](./ZEP-0106.md) and the API-index schema revision
policy in [ZEP-0012](./ZEP-0012.md). Source compatibility must be considered before accepting a
previously rejected pattern shape.

## Alternatives

- **Keep every escape an error** — simplest and sound, but blocks useful APIs that return or store
  anonymously typed values.
- **Approximate every escape by its upper bound** — expressive, but loses binder identity and can
  require descriptor carriers for reified values.
- **Support only direct patterns permanently** — avoids nested and composed interactions, but
  leaves common map, container, and guard cases to hand-written helpers.
- **Reject mixed patterns permanently** — keeps descriptor rules simple, but prevents opening one
  argument while testing another.
- **Add full variance immediately** — likely exceeds demonstrated need and complicates evidence.
- **Move result positions into ZEP-0106** — keeps holder ABI together, but separates packing and
  opening semantics; coordination is preferable to a silent split.

## Implementation and validation

1. Extend the parser and branch-scope machinery for the accepted composed, mixed, nested, and
   binder-annotated forms.
2. Extend binder fact inference to preserve exact arguments, nested captures, lower bounds, and
   projections.
3. Implement the complete escape analysis and decide whether each escape is an error or an
   approximation.
4. Add result-position packing and any carrier required for reified results.
5. Add diagnostics that distinguish unsupported shape, missing evidence, unavailable descriptor,
   and genuine escape.
6. Add positive and negative tests for every accepted extension and every remaining rejection.
7. Verify that no extension changes the ZEP-0105 branch-local ABI unless the proposal explicitly
   requires it.

This section is a design outline, not an implementation commitment or schedule. No part of this
proposal is implemented yet beyond what ZEP-0105 already ships.

## Open questions

- Should opening be allowed in composed conditions, `else if`, and value-producing `if`
  expressions?
- What exact descriptor rule should mixed patterns use for exact arguments?
- Should nested opening be supported, and if so, can multiple levels be opened at once?
- Can a binder declare bounds or markers that intersect with the source's facts?
- How should raw `Any` tests expose class-declared bounds when the evidence is unavailable?
- Should `C<in B>` opening be rejected permanently or supported once lower bounds exist?
- Which escape contexts should remain errors, and which should approximate or re-pack?
- Should result-position anonymous existentials be supported, and are reified results gated on
  ZEP-0106?
- Is any anonymous existential variance sound and useful, or should invariance remain permanent?
- Does rank-2 `use` remain necessary for library APIs after this pattern family exists?
