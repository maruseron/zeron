## Abstract

Extend `zeron.toml` with optional declarative build settings and named project targets. A target
bundles a runnable entry point with its own output directory and build-policy overrides. `zeron build`
and `zeron run` gain an optional positional target name; omitting it preserves today's behavior by
selecting the project's default target. The manifest remains a declarative description of compilation
inputs, not a shell-script or arbitrary-command facility.

The same change makes CLI and manifest documentation generated artifacts. Command, option, and
manifest-schema metadata become the single source of truth for parsing, `zeron help`, and the
command/manifest reference chapters, with tests that fail when the checked-in documentation is stale.

## Motivation

`zeron build` and `zeron run` currently address exactly one implicit target: `[project].entry`. That
is sufficient for a simple application but not for projects that ship several runnable programs, such
as an application plus benchmarks, examples, or tooling entry points. Users must either maintain
separate manifests, duplicate project setup, or compile individual files outside the project model,
which bypasses configured dependencies and standard-library selection.

The manifest also has no way to express project-wide compiler policy. `--deny-warnings` already
exists as an invocation option, but a project cannot declare that warnings are errors for its normal
build while still allowing an explicit command-line override. Adding unrestricted flag arguments to
the manifest would create a second, undocumented CLI with ambiguous precedence and would expose
options such as `--manifest` and `--build-stdlib` that have no meaning as project settings.

Documentation is a second, related gap. `CliHelp` contains useful focused topics, but the guide has no
complete command or flag reference. The manifest reference is prose with one example and omits defaults,
validation rules, precedence, and several configuration details. The overview also omits options such
as `--stdio` and `--check` even though focused topics exist. Because CLI parsing, help text, and
manifest key validation are maintained separately, documentation drifts as options are added. This
proposal addresses both gaps together: targets need documented selection and precedence rules, and
the project should generate those pages from the same metadata that drives behavior.

## Goals

- Support multiple named runnable targets in one project manifest without duplicating source roots or
  dependencies.
- Keep `zeron build` and `zeron run` with no target argument fully backward compatible.
- Add a small, typed project build-policy table for settings that apply to every target by default.
- Define deterministic inheritance and command-line precedence, including boolean negation.
- Validate target names, entries, outputs, and `default-target` references before compilation.
- Prevent targets from overwriting each other's output directories by default.
- Keep the language server and formatter operating on one project-wide source set.
- Make command, option, and manifest-schema metadata the single source of truth for runtime help and
  generated reference documentation.
- Add automated checks that every supported command, option, and manifest key is documented and that
  the checked-in generated pages are current.

## Non-goals

- Arbitrary shell commands, build hooks, plugins, or task graphs. Targets are declarative compiler
  invocations, not general-purpose scripts.
- Per-target source roots, standard-library modes, or dependency lists in the first version. All
  targets share the project's source roots, standard library, and dependency configuration so the
  language server has one coherent analysis universe.
- A generic `flags = ["--..."]` passthrough for compiler options.
- Target-specific runtime arguments stored in the manifest, or general argument forwarding to the
  launched program. These may be considered separately.
- Automatic dependency fetching, lockfiles, or incremental builds.
- Adding `--debug` to the manifest. Compiler traces remain an invocation concern.
- Versioning the manifest schema itself. New tables are additive, and older compilers reject them as
  unknown keys.
- Changing language semantics, the standard-library API, or the compiled-library API index.

## Proposal

### Manifest additions

The manifest keeps its current top-level tables and adds two optional tables:

```toml
[project]
entry = "src/main.zn"
source-roots = ["src"]
output = "dist"
default-target = "app"

[build]
deny-warnings = false

[targets.app]
entry = "src/main.zn"
output = "dist/app"

[targets.bench]
entry = "src/bench.zn"
output = "dist/bench"
deny-warnings = true
```

The accepted top-level keys become `project`, `platform`, `dependencies`, `build`, and `targets`.
Unknown keys continue to be rejected with the existing context-specific error.

#### `[project]`

Existing keys keep their meaning and defaults. `entry` remains required when no `default-target` is
configured. The new optional `default-target` key names the target selected by `zeron build` and
`zeron run` when no positional target is supplied. It must name an existing `[targets.<name>]` entry.

For compatibility, omitting both `default-target` and `[targets]` selects the implicit project target
described by `[project].entry` and `[project].output`. When `default-target` is present,
`[project].entry` may be omitted if that target declares an entry; otherwise it remains required.

#### `[build]`

`[build]` holds typed compiler policy that applies to project compilation by default. Its initial
key is:

| Key | Type | Default | Meaning |
| --- | ---- | ------- | ------- |
| `deny-warnings` | boolean | `false` | Treat reported warnings as a failed build after the stage completes. |

Future compiler settings may be added to this table by a later proposal. They must be typed keys, not
raw command-line strings. `--debug` remains CLI-only.

#### `[targets.<name>]`

Each target name is case-sensitive and must match `[A-Za-z][A-Za-z0-9_-]*`. A target supports:

| Key | Type | Default | Meaning |
| --- | ---- | ------- | ------- |
| `entry` | string | `[project].entry` | Entry source whose `main` is compiled and launched. |
| `output` | string | `<project.output>/<name>` | Generated-program directory for this target. |
| `deny-warnings` | boolean | `[build].deny-warnings` | Per-target override of the build policy. |

Manifest paths continue to resolve relative to the manifest file. Each target entry must exist, have a
`.zn` extension, and reside under one of the project source roots. Normalized output directories must
be distinct across the project's effective targets so building one target cannot overwrite another.

The implicit project target uses `[project].output` exactly, preserving existing behavior. Named
targets default to a per-target subdirectory; a target that intentionally shares a directory with the
project target must set `output = "dist"` explicitly.

### Command-line behavior

```text
zeron build [<target>] [--manifest <file>] [--debug]
            [--deny-warnings | --no-deny-warnings]
zeron run   [<target>] [--manifest <file>] [--debug]
            [--deny-warnings | --no-deny-warnings]
```

- With no positional target, the command selects `[project].default-target`, or the implicit project
  target when no default is configured.
- With a positional target, the command selects that target. An unknown name is an invalid invocation
  and reports the available target names.
- `--deny-warnings` sets the effective policy to `true`; `--no-deny-warnings` sets it to `false`.
  Supplying both is an error. Supplying either option more than once remains an error.
- `--debug` and `--manifest` are unchanged and remain CLI-only.
- `zeron build` and `zeron run` continue to accept no source-file positionals; introducing the target
  position does not collide with the existing CLI grammar.
- `zeron lsp` and `zeron fmt` do not take a target. They continue to analyze and format the project's
  source roots, which include every validated target entry.
- `zeron init` continues to emit the existing minimal manifest; it may include commented examples of
  `[build]` and `[targets]`, but those omissions must not change generated reference documentation.

### Inheritance and precedence

Effective settings resolve in this order, lowest to highest:

1. built-in defaults;
2. `[project]` facts and `[build]` policy;
3. the selected `[targets.<name>]` overrides;
4. explicit command-line options.

The resolved values are computed before path validation and compilation. The same resolution is used
for `build` and `run`, so a target cannot build differently from how it runs.

### Compilation behavior

The selected target supplies the effective entry and output directory passed to project compilation and
launch. Source roots, standard-library mode, Zeron libraries, and Java classpath roots remain
project-wide. The generated main class is launched from the selected output directory, so two targets
cannot accidentally load each other's classes.

All target entries are validated and included in the project source universe. Warning analysis remains
project-wide, and diagnostics are attributed to the file that produced them. The language server and
formatter therefore see the same sources regardless of which target was last built.

### Generated documentation

Command, option, and manifest-schema metadata become shared runtime data:

- a command specification records the command name, synopsis, summary, supported options, and
  examples;
- an option specification records long and short names, value arity, applicable commands, summary,
  detailed help, and manifest-key mapping, if any;
- a manifest schema specification records each table and key, TOML type, required/default status,
  constraints, description, and applicable version notes.

`CliParser` uses the option specifications for validation where practical, and `CliHelp` renders the
overview and focused topics from them instead of maintaining a parallel text map. `ProjectManifest`
derives its accepted-key sets from the manifest schema specification so parsing, validation errors,
help, and documentation cannot list different keys. The help system also gains a `manifest` topic that
summarizes the manifest tables and points at the generated reference.

Two reference chapters become generated, checked-in artifacts:

- `guide/39-command-reference.md` — every command, full synopsis, every option, applicability,
  defaults, precedence, exit behavior, and examples;
- `guide/40-manifest-reference.md` — every top-level table, every key, type, requirement, default,
  path-resolution rule, validation rule, and precedence rule, including `[build]` and `[targets]`.

Generated pages carry a "generated from ...; do not edit manually" notice. `guide/25-configuration-releases-and-roadmap.md`
remains the conceptual overview and links to both references. Hand-written explanations, tutorials,
and language guides are not generated.

A generator entry point renders both pages from the metadata. Regeneration is available as a single
documented command, and a test regenerates the pages in memory and compares them with the committed
files, failing with an instruction to regenerate when they differ. Additional tests assert that every
command and option has a help topic, every manifest key has a reference row, no help topic refers to an
unknown command or option, and `zeron help` output is derived from the same metadata.

## Compatibility and impact

Existing manifests remain valid and `zeron build` / `zeron run` with no positional target continue to
compile and launch the `[project].entry` target into `[project].output`. The new manifest keys are
optional. Older compilers reject `[build]` and `[targets]` as unknown keys, so documentation identifies
the first release that supports them.

The only CLI incompatibility is intentional: `zeron build <name>` and `zeron run <name>` previously
failed as unknown options/arguments and now succeed when `<name>` is a declared target. Unknown names
still fail with the normal invalid-argument status. `--deny-warnings` keeps its meaning, and
`--no-deny-warnings` is additive.

No language, runtime, standard-library, compiled-library, or API-index compatibility changes are
expected. `API_INDEX_SCHEMA_VERSION` and `STANDARD_LIBRARY_API_VERSION` do not change. `zeron help`
text and the guide gain content, so help/output snapshots and any documentation checks must be updated
with the implementation.

The LSP and formatter keep their current project semantics. If a future proposal allows per-target
source roots or dependencies, the LSP will need an explicit selection or union rule; this proposal
avoids that ambiguity.

## Alternatives

- **Manifest-wide raw flag passthrough (`flags = ["--deny-warnings"]`)** — rejected. It creates a
  duplicate, weakly typed CLI with unclear precedence, makes many invocation-only options meaningless,
  and complicates documentation and quoting.
- **Only add flags to the manifest, with no targets** — rejected. It does not address multiple entry
  points, which is the primary motivation, and still needs a policy/CLI distinction.
- **Only use a `--target` option, with no manifest table** — rejected. Target definitions need a
  persistent home for entry, output, and policy; repeating them on the command line is error-prone.
- **`zeron run path/to/file.zn`** — rejected. It would bypass project source roots, dependencies,
  standard-library mode, and target-specific output, and would bypass the language server's project
  model.
- **Arbitrary shell scripts or task hooks** — rejected for this scope. They are platform-dependent,
  introduce trust and quoting problems, and do not help the compiler understand project structure.
- **A separate scripts or workspace file** — rejected. Splitting project configuration across files
  makes discovery, validation, and editor integration harder; `zeron.toml` already owns project data.
- **Hand-written reference pages plus separate help text** — rejected. The current drift is the
  motivation for generation; a single metadata source is cheaper to keep correct.
- **Require explicit output directories for every target** — safer but more verbose. This proposal
  defaults named targets to `dist/<name>` while requiring distinct effective outputs.
- **`--target <name>` instead of a positional name** — acceptable, but more verbose. `build` and `run`
  have no competing positionals, so a positional target is unambiguous and remains backward
  compatible.

## Implementation and validation

Likely implementation stages:

1. Extract command, option, and manifest-schema metadata; make `CliHelp`, `ProjectManifest` key checks,
   and documentation rendering consume it without changing behavior. Add generated reference pages
   and the staleness test.
2. Add `[build]`, `[targets]`, `default-target`, inheritance, and validation to `ProjectManifest`.
   Expose an effective-target resolution API for CLI dispatch.
3. Extend `CliParser` and `Zeron.runProjectCommand` to select a target, resolve policy, pass the target
   entry/output to compilation, and launch from the target output directory.
4. Update `guide/25`, the generated command and manifest references, `README.md` where appropriate,
   `zeron init` examples, and `CHANGELOG.md`. Confirm the LSP and formatter still use the project-wide
   source set.
5. Run focused parser/manifest tests, then the LSP and formatting suites, and finally the broader test
   suite for configuration changes.

Validation should cover:

- backward compatibility: a manifest without new tables builds and runs exactly as before;
- default selection: no target, configured default target, and implicit project target;
- explicit target selection, unknown target errors, and target-name syntax;
- inheritance and precedence for `deny-warnings`, including both negation forms and conflicting flags;
- manifest validation: missing `default-target`, invalid target entries, paths outside source roots,
  duplicate normalized outputs, and unknown keys in each table;
- integration: two targets with different entries and outputs run the correct `main` without
  cross-loading classes;
- documentation: generated pages match metadata, every command/option/manifest key is covered, and
  regeneration is the only way to update them;
- language server and formatter regression tests confirming project-wide analysis is unchanged.

This was the implementation sketch; the first version landed on 2026-11-14 without changing the
language, runtime, standard library, or API index.

## Open questions

- Is `[targets]` the preferred name, or should the project adopt `[scripts]` or `[[bin]]`? This
  proposal uses `targets` because "script" already means a `.zn` source file and because these are
  declarative compiler invocations.
- Should named targets default to `<project.output>/<name>` as proposed, or require an explicit
  `output` for every target?
- Should `zeron build` eventually gain `--all-targets`, or should CI invoke each target explicitly?
- Should `zeron run <target> -- <program arguments>` be added in the same proposal, a follow-up, or
  omitted entirely?
- Are per-target source roots or dependency lists ever desirable, and if so, how should the language
  server choose what to analyze?

## Decision

Accepted 2026-11-13 for the `0.8.0` bundle. The direction is retained: optional declarative
`[targets]` and `[build]` tables, a positional target for `zeron build` and `zeron run`, and
generated command and manifest reference pages driven by shared metadata. The proposal's recommended
defaults stand unless implementation reveals a concrete conflict: the table name `targets`,
per-target output defaulting to `<project.output>/<name>`, and command-line options taking
precedence over manifest policy. Open questions about `--all-targets`, forwarded program arguments,
and per-target source roots or dependencies remain implementation follow-ups rather than blockers;
the first version keeps project-wide source roots, dependencies, and standard-library selection.

Implemented 2026-11-14 in the `0.8.0` bundle. `ProjectManifest` now resolves `[build]`,
`[targets.<name>]`, and `default-target`, including inheritance, target-name and output validation,
and effective entry/output selection. `zeron build [<target>]` and `zeron run [<target>]` share that
resolution, apply `--deny-warnings` / `--no-deny-warnings` overrides, and launch from the selected
target output. `CliMetadata` drives `zeron help` and the generated
`guide/39-command-reference.md` and `guide/40-manifest-reference.md`, with a staleness test. Open
questions about `--all-targets`, forwarded program arguments, and per-target source roots or
dependencies remain follow-ups.
