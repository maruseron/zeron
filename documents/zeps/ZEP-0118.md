## Abstract

Add a response type to effect declarations and make `raise` an expression whose value is supplied by
a handler. Effects without a response keep today's abortive behavior and type `Never`.

The proposal also defines the three levels of handler explicitly:

1. **abortive** — the case does not resume; already implemented;
2. **tail-resumptive** — the case resumes exactly once, in tail position; compiled to a direct
   handler call with no stack capture;
3. **general resumable** — the case stores the continuation and resumes it later; specified
   separately by [ZEP-0119](./ZEP-0119.md).

This proposal implements levels 1 and 2. It introduces the library effects `Yield<T>`, `Ask<T>`, and
`Log`, and the push direction of generators. It does not capture continuations.

## Motivation

Raised effects currently only abort. That is sufficient for failures, but several useful effects are
requests that the handler must answer:

```zeron
fn greet(name: String): Unit raises Ask<String> {
    let answer = raise Ask<String>.new();
    println("Hello, " + answer + " (" + name + ")");
}
```

`Ask` needs to return a value at the raise site. `Yield` needs to hand a value to a consumer and
continue. `Log` needs to observe a message and continue. Today each must be encoded as a callback,
a collector, or an ordinary function parameter, which loses the uniform row and forces different
call shapes for pure, failing, and request-like code.

The missing type-level piece is the **response type**: the raise site must know what the handler will
supply when it continues. Carrying that type on the effect declaration is enough for tail-resumptive
handlers, because they return the response value directly to the raise site. No continuation object
needs to exist and no stack needs to be captured.

## Goals

- Let an effect declaration state the type its handler returns at the raise site.
- Make `raise` an expression of that response type, with `Never` for abortive effects.
- Preserve every existing abortive effect, handler, and row rule.
- Define a conservative, syntactic criterion for tail-resumptive handlers.
- Lower tail-resumptive handlers to a direct call or loop, not to continuation capture.
- Add `Yield<T>`, `Ask<T>`, and `Log` as standard-library effects.
- Support push-style generators: a producer raises `Yield`, a handler consumes each value and
  resumes immediately.
- Keep handler types `T ~> {...}` and existing `handle` typing.
- Record response metadata in compiled-library API indexes.

## Non-goals

- Storing a continuation, resuming it later, or resuming it from a callback.
- A first-class `Cont<R, T>` that can be stored, passed, or resumed later; `cancel`.
- Multi-shot continuations or backtracking.
- `Async`, `Future`, scheduling, or concurrency. Those are [ZEP-0120](./ZEP-0120.md).
- Pull-style generators. Converting push to pull requires saving a continuation between elements
  and is [ZEP-0119](./ZEP-0119.md).
- Rewriting `for ... collect` on top of `Yield` in this proposal.
- Allowing arbitrary classes or Java-library types to declare a response.
- Changing `raise`/`handle` coverage, `using`, or Java exception translation.
- Linear or affine enforcement of "resume exactly once".

## Proposal

### Response declarations

An effect may declare a response type with `responds`:

```zeron
public effect NotFound {}                         // responds Never; abortive

public effect Ask<T> responds T {}                // handler supplies a T

public effect Yield<T> responds Unit {
    public property value: T;
}

public effect Log responds Unit {
    public property message: String;
}
```

`responds R` is part of the effect declaration, not an ordinary contract a user can implement on an
unrelated type. The compiler synthesizes a built-in marker contract, `Responds<R>`, for handler
dispatch:

```zeron
case e: Responds<Unit> as request -> ...
```

`Responds<R>` has no members, cannot be implemented explicitly by a class or by a foreign type, and
is invariant in `R`. An effect declares at most one response type; two declarations are an error.
The compiler may expose `Responds<R>` as an ordinary contract name for patterns and generic bounds,
but conformance is derived from `responds`, not written by hand.

The alternative surface `effect Ask<T> is Responds<T> {}` is rejected for this proposal because it
makes a library contract part of the declaration mechanism and invites accidental or fictitious
conformance. The design document follows `responds`; the final syntax is owned here.

### `raise` as an expression

For an effect `E` with response `R`, a `raise` of an `E` value has type `R`:

```zeron
let answer: String = raise Ask<String>.new();
```

For an effect without `responds`, `raise` keeps type `Never`. `Never` is bottom, so existing code
that assigns, returns, or passes the result of an abortive `raise` continues to type-check.

This changes control-flow analysis:

- a `raise` of an abortive effect is divergent and makes the rest of the block unreachable;
- a `raise` of a responding effect is a normal expression that may return, so subsequent statements
  are reachable;
- a `match` arm that ends in a responding `raise` has the response type, while an abortive `raise`
  keeps the arm bottom-typed.

The row still records the carrier. Handling removes it exactly as today. The response type is not a
second effect and does not appear in the row.

### Handler typing

Handler types and the `handle` typing rule are unchanged. A responding case gains a `resume` binder in
addition to the carrier pattern.

```text
e : T raises (E1 + E2 + F)
h : T ~> { E1, E2 }
--------------------------------
handle (e) with h : T raises (F + G)
```

At level 2 the binder is a restricted token, not a first-class `Cont`: only `k.resume(v)` in tail
position is allowed, and the token cannot be stored, passed, or cancelled. The case can be understood
as returning the response to the raise site. The full `Cont<R, T>` value appears only in
[ZEP-0119](./ZEP-0119.md).

A case that does not resume aborts, exactly as today. A case that stores the continuation, uses it
under a lambda, resumes it more than once, or resumes it after other work is not tail-resumptive and
is rejected until ZEP-0119 is accepted.

### Tail-resumptive handlers

A case is tail-resumptive when all of the following hold:

- it refers to the resume binder exactly once;
- that reference is `k.resume(v)` in tail position of the case;
- it is not inside a lambda, loop, nested handler, or conditional branch that can skip it;
- it does not store, return, or otherwise capture `k`;
- no work follows the `resume`.

The criterion is deliberately conservative and syntactic. A helper call that eventually resumes is
not detected; it is treated as general resumable and rejected until ZEP-0119 exists. This is a
limitation, not a soundness claim: a stored continuation can always defeat a local check, which is
why the general level requires a runtime state machine.

Lowering does not allocate a continuation. For a case that matches a single carrier, the compiled
method returns the response value; the raise site calls the nearest handler and continues with the
result. For a case that matches several carriers through one contract with a common response `R`, the
same method dispatches on the reified carrier type and returns an `Object` that the raise site casts
to `R`. Separate arms for carriers with different responses lower to separate methods.

Handler lookup is an implementation detail. A synchronous thread-local handler frame is sufficient
because a tail-resumptive handler always returns before the raise site continues; an explicit
evidence parameter is the alternative if it composes better with separate compilation. The observable
model is a direct call: no continuation escapes and no stack is captured.

`cancel` is not available at level 2; it is part of ZEP-0119.

### Standard-library effects

```zeron
public effect Yield<T> responds Unit {
    public property value: T;
}

public effect Ask<T> responds T {}

public effect Log responds Unit {
    public property message: String;
}
```

`Yield` is the push half of iteration. A producer raises a value; a handler consumes it and resumes:

```zeron
fn numbers(): Unit raises Yield<Int> {
    for i in 0..3 {
        raise Yield.new(i);
    }
}

fn printNumbers(): Unit =
    handle (numbers()) with {
        case Yield(value), k -> {
            println(value);
            k.resume(unit);
        }
    };
```

The pull direction — an external iterator whose `next()` resumes a stored continuation — is a
generator and requires ZEP-0119. The two directions are duals; this proposal only implements the
one that needs no capture.

`Ask` and `Log` are ordinary tail-resumptive effects. `Ask` covers dependency injection and
read-only context; `Log` covers observation. Neither needs a new runtime mechanism.

### Interaction with `for ... collect`

`for source collect into collector<T>` already has the push shape: the source produces values and
the collector decides what to do with them. It is structurally close to `Yield`, but a collector has
`init`, `accumulate`, and `finish` and may change the result type, while a handler is `T` to `T`.

This proposal leaves `for ... collect` unchanged and does not rewrite it on top of `Yield`. A later
proposal may unify them once the handler/collector difference is resolved. Existing collector code
and performance stay as they are.

### Generic response bounds

A `raise` on a row variable has no known response type:

```zeron
fn forward<E: effect...>(f: () -> Unit raises E): Unit raises E = f();  // fine
fn synthesize<E: effect...>(): Never raises E = raise ???;               // no response type
```

A function that quantifies over a **single** effect and raises into it can name the response with a
bound:

```zeron
fn withAnswer<E: effect + Responds<R>, R>(
    body: () -> Unit raises E,
    answer: R
): Unit raises E = ...
```

A row variable is a set of carriers, so `E: effect... + Responds<R>` would claim that every carrier
in the row has the same response. That is not the intended meaning. A row-level constraint, if it is
desirable, needs a different form (for example, a distinguished response parameter). Until it is
settled, generic code can call and forward effectful functions but cannot itself perform a responding
`raise` through a row variable. This limitation should be documented rather than hidden, because the
uniformity argument for rows is weaker without it.

## Compatibility and impact

Existing effect declarations have no `responds`, so their `raise` remains `Never` and their
behavior is unchanged. Existing handler cases that abort are unchanged. Existing `handle` typing is
unchanged.

The only source-level change for existing code is that `raise` is no longer unconditionally bottom-
typed; for abortive effects it still is, so the change is source-compatible in practice. Flow
analysis and reachability must be updated, and that can change warnings.

Compiled effect metadata gains the response type. An old API index without the field must be read as
`Never`, so the reader remains compatible with existing libraries. Writing the field requires an
`API_INDEX_SCHEMA_VERSION` addition; per project policy it is bumped once for the release cycle that
ships the feature, not per patch.

Adding `Yield`, `Ask`, and `Log` to the standard library changes `STANDARD_LIBRARY_API_VERSION` once
for the release cycle; `Responds<R>` is compiler-provided and does not itself add a library API. The abortive lowering does not change
descriptors, so separate compilation of existing effectful functions is unaffected.

No Java interop change is required. A Java method cannot declare a Zeron response, and an effect
from a Java library remains abortive.

## Alternatives

- **`effect E is Responds<R> {}` with a user-implementable contract** — rejected. It makes a library
  contract part of the declaration mechanism, allows accidental conformance, and complicates the
  rule that only Zeron effect declarations can be resumable.
- **Make every handler resumable through `Cont`, even tail-resumptive ones** — rejected. It pays
  for stack capture on the common case and makes `Yield`/`Ask`/`Log` depend on ZEP-0119.
- **Encode requests as callbacks or function parameters** — rejected. It loses the uniform row and
  produces a different call shape for each effect.
- **Require `await`/`yield` keywords** — rejected. It reintroduces function coloring.
- **Rewrite `for ... collect` on `Yield` now** — deferred. The collector has state and a return
  clause; unifying before the handler model is stable would couple two changes.
- **Use `never` instead of `Never`** — rejected for consistency with the existing `Never` type.

## Implementation and validation

Likely stages:

1. Parse `responds`, store it in the effect declaration, and reject more than one response or a
   response on a non-effect.
2. Resolve response types for concrete carriers and expose the synthesized `Responds<R>` view for
   handler patterns.
3. Update `raise` typing, divergence/reachability analysis, and handler case checking.
4. Implement tail-resumptive analysis and direct-call lowering; reject non-tail cases with a
   diagnostic that points at ZEP-0119.
5. Add response metadata to the compiled-library API index and preserve backward reading.
6. Add `Yield`, `Ask`, and `Log` to the standard library, expose the compiler-provided
   `Responds<R>` marker, and document both.
7. Add focused tests, then run the resolver, API-index, and standard-library suites.

Validation should cover:

- abortive effects: existing `raise`, `handle`, `using`, and `Result` tests unchanged;
- response typing: `raise` produces `R`, abortive `raise` produces `Never`, wrong response is an
  error;
- reachability: statements after an abortive `raise` are unreachable, statements after a responding
  `raise` are reachable;
- tail-resumptive `Yield`, `Ask`, and `Log` at runtime, including nested handlers;
- rejection of stored, lambda-captured, conditional, and double `resume`;
- bytecode inspection showing no continuation allocation or stack capture for level 2;
- generic forwarding of a row and the current diagnostic for generic responding `raise`;
- API-index round-trip for response metadata and backward reading of old indexes;
- `for ... collect` regression to prove it was not rewritten;
- separate compilation of a library declaring a responding effect.

## Open questions

- Is `responds R` the final syntax, or should `Responds<R>` remain a writable contract? This proposal
  chooses `responds` and a synthesized marker.
- Is `case C(payload), k -> ...` the right way to bind the resume token, or should it be a named
  parameter, a pattern annotation, or an implicit name?
- How is a response bound written on a single effect or on a row variable, and does it require a new
  kind or constraint form?
- Does `case e: Responds<Unit>` work with applied generic contract identity in the current evidence
  model?
- Should the primary user-facing form be `raise Ask<String>.new()` or a wrapper such as `ask<String>()`?
- Is a thread-local handler frame acceptable, or should handlers be passed as explicit evidence?
- Are `Ask` and `Log` standard-library effects or documented examples?
- Should `for ... collect` eventually be re-expressed through `Yield`, and what happens to collector
  return clauses?
- Does a responding `raise` inside a `using` block need a lint even when resumption is immediate?
  This proposal assumes it does not, because level 2 never suspends.
