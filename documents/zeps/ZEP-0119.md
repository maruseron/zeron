## Abstract

Define the semantics of general resumable effects: a handler case may store a continuation and resume
it later. The proposal introduces `Cont<R, T>` with `resume` and `cancel`, dynamic one-shot
enforcement, deep-handler semantics for resumed computations, automatic cancellation when a `handle`
exits, and an internal cancellation signal outside the effect row.

Acceptance is gated on prototype evidence. This proposal does **not** commit to a shipping backend,
does not authorize production use of `jdk.internal.vm.Continuation`, and does not gate reified
generics on its ABI. [ZEP-0118](./ZEP-0118.md) is a prerequisite; [ZEP-0120](./ZEP-0120.md) owns the
async/task surface.

## Motivation

[ZEP-0118](./ZEP-0118.md) covers effects whose handler resumes immediately in tail position. That is
enough for `Yield`, `Ask`, and `Log`, but not for:

- a scheduler that stores a continuation and resumes it when an operation completes;
- a pull-style generator whose `next()` resumes a stored continuation;
- an `await` implementation that does not block the current virtual thread;
- any handler that needs to do work between receiving a request and answering it.

These need a first-class continuation value. The current runtime has none: `raise` throws a carrier
and unwinds the JVM stack to a handler. Adding resumption changes the compiler/runtime model, so the
design must state the continuation contract, handler depth, resource behavior, cancellation, and
threading before implementation. [ZEP-0007](./ZEP-0007.md) recorded that exploration and deferred it;
this proposal is the scoped design that follows from it.

## Goals

- Define `Cont<R, T>` and the `resume`/`cancel` operations.
- Enforce one-shot use dynamically with a defined state machine.
- Specify deep-handler semantics for resumed computations.
- Scope continuation lifetime to the owning `handle`.
- Define automatic cancellation of pending continuations when the `handle` exits.
- Define an internal cancellation signal that carriers and generic handlers cannot intercept.
- Specify cleanup and suppressed-failure behavior across suspension and cancellation.
- Specify thread-confinement and handoff rules for continuations.
- Define a prototype and explicit falsification criteria for the JVM backend.
- Preserve the abortive and tail-resumptive behavior defined by ZEP-0118.
- Give handler and closure representations an extension point for a continuation parameter without
  making reified generics depend on it.

## Non-goals

- Multi-shot continuations, backtracking, or replaying a computation
  ([ZEP-0121](./ZEP-0121.md)).
- Linear or affine types; one-shot is a dynamic guarantee.
- Shipping on an internal JDK API.
- Suspending across native frames, an unaware Java callback, or `Disposable.dispose`.
- Defining `Async`, `Future`, `spawn`, `await`, or a scheduler. Those are ZEP-0120.
- Rewriting `for ... collect`.
- Changing abortive `raise`/`handle`, `using`, or Java exception translation.
- Gating reified generics, existentials, or the handler ABI on this proposal.
- A general `NoSuspend` capability kind in this proposal; the boundary rules below are the input to
  that later decision.

## Proposal

### `Cont<R, T>`

A case over a carrier with response type `R` receives a continuation whose result type is the
handled expression's type `T`:

```zeron
public handler scheduler {
    case Await(f), k -> {                 // k: Cont<T, Unit>
        f.onComplete { value -> k.resume(value) };
    }
}
```

```text
Cont<R, T>
    resume(value: R): T
    cancel(): Unit
    isDone(): Boolean
```

`resume` supplies the response value and runs the rest of the handled computation. It returns the
handled expression's result when that computation finishes. `cancel` abandons the computation after
running its cleanup. `Cont` is a runtime value; it is not a carrier and does not appear in a
`raises` row.

The handler's `case` still returns `T`. A case may abort (never touch `k`), resume once, or cancel.
A case that resumes and then continues working must eventually return a `T`; the value returned by
`resume` is available for that work.

### One-shot state machine

The dynamic state is:

```text
suspended -> running -> done
    |           |
    |           +-> failed
    +-> cancelled
```

- `suspended` is the initial state. `resume` and `cancel` are legal.
- `resume` moves to `running`, then to `done` or `failed` when the computation returns or raises.
- `cancel` moves a suspended continuation to `cancelled` after unwinding.
- `cancel` on `running` records a cancellation request; the computation observes it at the next
  suspension point or `using` boundary.
- `cancel` on `done`, `failed`, or `cancelled` is idempotent.
- `resume` on anything other than `suspended` is a program error and panics. It is not a carrier,
  because making it one would contaminate every row.
- `isDone` is true for `done`, `failed`, and `cancelled`.

The compiler may warn when two `resume` calls are visible on the same path, but the guarantee is
dynamic. A continuation stored in a field, captured by a lambda, or passed to another function cannot
be checked locally, and no interprocedural completeness is claimed.

Multi-shot resumption is excluded. Resuming a computation twice while it holds an open `Disposable`
would require duplicating or replaying resource acquisition; that is a consequence of the choice, not
its justification. The justification is that one-shot is what a single-stack runtime can provide and
what pull generators, non-blocking schedulers, and non-blocking `await` need. Multi-shot monads remain
the domain of `do`-notation and [ZEP-0111](./ZEP-0111.md).

### Deep handlers

Resuming a continuation re-enters the handled computation **inside** the same `handle`. Effects
raised after resumption are caught by the same handler. This is required for a scheduler: after
resuming, the body may `await` again, and the same scheduler must see it.

The `case` body itself stays outside the handler, as it is today. If a case raises, that effect
escapes the `handle` unless an outer handler catches it. The precise rule:

- the resumed computation is inside the `handle`;
- the `case` body is outside the `handle`;
- nested `handle`s inside the resumed computation still take precedence for their own carriers.

Deep semantics make a handler with captured continuations a per-`handle` state machine. Its state
must survive across suspension. A named singleton handler that captures `k` is therefore not
stateless; either the runtime materializes a per-`handle` instance, or the handler must be written
as a factory. This proposal requires per-`handle` state for any handler that stores a continuation.

### Thread confinement

A `Cont` belongs to the `handle` instance that created it and is confined to that handle's thread.
`resume` from a different thread is a runtime error in the first version. A scheduler that completes
work on another thread must dispatch the resumption back to the handle's thread, for example through
an event loop or an explicit `resumeOn(executor, value)` operation added later.

This restriction exists because handler state, the handler stack, and any thread-local context do not
travel with a captured stack automatically. Allowing cross-thread resumption without transferring
that state would produce silently wrong behavior. A future proposal may add explicit migration with a
defined transfer of handler state; it is not part of this one.

### Cancellation

Without linearity, nothing forces a handler to resume or cancel a continuation. The hard case is the
abandoned continuation: nobody closes its open `Disposable` resources, and abandoning a captured
stack does not run `finally` blocks.

Two rules replace linearity:

1. **`k.cancel()`** resumes the computation with an internal cancellation signal that unwinds the
   stack and runs the `dispose` of open `using` blocks in LIFO order. It uses the same unwinding as
   an abortive effect, with a different cause.
2. **`handle` cancellation scope.** When the `handle` exits — by normal completion, by an aborting
   case, by a case that returns without resuming, or by an effect escaping from a case — every
   pending continuation owned by that `handle` is cancelled. A continuation that is still suspended
   after its `handle` has exited is invalid; `resume` on it panics.

A scheduler that intentionally outlives its `handle` must opt in through a later, explicit mechanism.
The default is structured: continuations do not outlive the handler that owns them.

### The cancellation signal is not a carrier

If cancellation were an ordinary carrier, `catchAll<T, E>` and `case Effect` would intercept and
swallow it, which is the known `CancellationException` problem in Kotlin. Cancellation is therefore
an internal object:

- it is outside every row and every carrier type test;
- a `case` cannot handle it;
- only `using`/`dispose` and the runtime observe it;
- user code that wants to react uses `Disposable`, not a handler case.

At the JVM level the signal should be a private `Throwable` subtype with an unforgeable token, so
that Java `finally` blocks run. The trade-off is that Java code with `catch (Throwable)` can observe
or swallow it. The runtime must document this boundary and may wrap the token so a swallowed signal
is detected when control returns. A non-`Throwable` signal would avoid interception but would not run
Java cleanup; that is worse for interop.

### Resources and suppression

| Situation | Behavior |
| --- | --- |
| Abortive `raise` on the live stack | `using` blocks between the raise and the `handle` unwind before the case runs; suppressions are available through `with suppressed as s`. |
| Pending continuations when the `handle` exits | They are cancelled after the case has produced its result or escaping effect; cleanup failures leave through the `handle`'s row as `DisposeFailure` (the first, with the rest suppressed). |
| Case has suspended the computation | The computation stays suspended with its resources open. Nothing is unwound. |
| Case aborts and a `dispose` also fails | The aborting result or effect wins; cleanup failures accumulate as suppressed. |
| `cancel` while suspended | `cancel` unwinds, runs `dispose` LIFO, and returns; failures are collected by the canceller. |

A `Disposable.dispose` cannot contain a **general** resumable effect (level 3). Its row may contain
`DisposeFailure`, abortive effects, and tail-resumptive level-2 effects such as `Ask` or `Log`, but no
carrier whose handler can suspend the computation. This keeps cancellation synchronous:
`k.cancel()` unwinds and returns without a scheduler in between.

A `using` block may stay open across a resumable `raise`. The compiler should lint this because the
resource remains open while the computation is suspended. The lint is not an error: holding a
resource across suspension is legitimate, but it must be deliberate.

Because a `handle` that captures continuations may cancel them and observe cleanup failures, its
result row can gain `DisposeFailure`. This proposal takes the predictable rule: **a `handle` whose
cases statically capture a continuation includes `DisposeFailure` in its result row.** A
tail-resumptive or purely abortive handler does not. This is a typing cost and is listed as an open
question; the alternative is to report cleanup failures through an explicit hook or a
`CancellationReport` value.

### Backend options

**A. Loom delimited continuations.** `jdk.internal.vm.Continuation` is a one-shot continuation, but
it is not implicit delimited control. Suspending requires an explicit `yield(scope)` with the right
`ContinuationScope`; the raise site must resolve which handler scope owns the carrier. That means a
handler stack or evidence-passing mechanism still exists. `run()` executes on the calling thread, so
the thread-confinement rule above is mandatory.

Direct use has serious costs:

- it is an internal, encapsulated API requiring `--add-exports java.base/jdk.internal.vm=ALL-UNNAMED`;
- its behavior and availability can change on any JDK, including Java 25 updates;
- every launch path, including user programs started outside `zeron run`, must carry the export;
- native frames are a hard barrier, and suspension across an unaware Java frame is a semantic hazard
  even when the frame is technically capturable;
- JEP 491 changed monitor pinning for **blocking** virtual threads. It did not establish that direct
  `Continuation.yield` has the same monitor semantics; that must be tested, not assumed.

**B. Compiler-managed transformation.** A CPS or state-machine transform is portable and does not
depend on an internal API. It changes descriptors for functions that may suspend, breaks tail calls
in the naive encoding, and degrades stack traces. It is the likely shipping fallback unless a public
continuation API appears.

**Recommendation.** Use A only as a **prototype to falsify the semantics**, not as the production
backend. Use B, or a public API if one exists, for any shipping decision. The source language and
the `Cont` contract must be identical under both, so the backend remains an implementation choice.

The prototype must answer:

1. Can the raise site resolve the correct handler scope without changing the ABI of every function?
2. Can handler state be preserved when a continuation is resumed from a callback thread, or does the
   thread-confinement rule force an event loop?
3. Does cancellation run `using` cleanup and Java `finally` blocks correctly?
4. What happens to stack traces, debugger stepping, and `using` suppressions across suspension?
5. Does yielding across a frame that holds a monitor, a native frame, or an unaware Java callback
   fail safely or silently corrupt state?

If any answer requires an ABI change, the "Loom avoids the ABI problem" claim is false and the
proposal proceeds with B or is deferred.

### ABI and generics sequencing

Do not make reified generics depend on this proposal. The handler and closure representations should
reserve an extension point for a continuation parameter, but generics, existentials, and the current
handler ABI may ship without it.

If B ships, every function that may suspend changes its descriptor and the API index needs a schema
change. If A ships, the descriptor does not change but the runtime depends on the internal API. The
backend decision, and therefore the ABI decision, is deferred until the prototype reports.

### Suspension boundaries

Suspension is forbidden across:

- native frames and JNI calls;
- an unaware Java callback that may hold locks or thread-local state;
- `Disposable.dispose`, because cancellation must be synchronous;
- any frame whose row is not known to be free of general resumable (level-3) carriers.

A later `NoSuspend` capability or an abortive-and-tail-resumptive row kind may express this. For now,
the rule is a boundary check: a generic function with an open row cannot be used at a suspension
boundary unless the row is closed and contains no level-3 carriers. Tail-resumptive level-2 effects
are synchronous and remain allowed. This is stricter than a lint and is an input to the later
capability design.

## Compatibility and impact

This proposal is additive and does not change abortive or tail-resumptive behavior. It depends on
ZEP-0118's `responds` and `raise` expression. `Cont`, `resume`, and `cancel` are new surface.

The cancellation signal is internal, so it adds no row or carrier. `DisposeFailure` may appear in
the result row of a `handle` that captures continuations; that is a source-level typing change for
new code, not for existing abortive code.

If the backend is a compiler-managed transform, functions that may suspend change descriptors and the
compiled-library API index requires a schema addition. If the backend is Loom, descriptors are
unchanged but the distribution and every launch path inherit the module export. Neither change is
authorized until the prototype is evaluated.

No standard-library API version change is required by this proposal alone; the `Cont` type and
runtime support are compiler/runtime surface. ZEP-0120 owns `Future` and `Await`, which do change the
standard library.

## Alternatives

- **Monadic lowering of a handled block** — recorded and rejected in [ZEP-0007](./ZEP-0007.md) for
  the abortive case; it needs a two-slot row-changing bind, residual-row handlers, and descriptor
  changes. A library-level version remains possible for suspending effects but is not this design.
- **Loom-only, shipped as the backend** — rejected. The API is internal, the scope-resolution problem
  remains, and thread handoff is unresolved.
- **No continuation capture** — insufficient for pull generators and non-blocking schedulers; it is
  the ZEP-0118 baseline.
- **Multi-shot continuations** — deferred. They require replaying resource acquisition and a
  different runtime; `do`-notation covers the monadic use cases.
- **Linear types to enforce one-shot** — rejected for this proposal. A dynamic state machine is
  cheaper and matches the existing lack of linearity.
- **A separate `resumable effect` declaration kind** — considered. ZEP-0118's `responds` already
  distinguishes abortive from responding carriers; adding a second kind would duplicate it.
- **Report cancellation cleanup through the row as `DisposeFailure`** — proposed, but the ergonomic
  cost is real; an explicit `onCancel` hook or `CancellationReport` is the main alternative.

## Implementation and validation

This is a staged prototype, not a schedule.

1. Land ZEP-0118 (response types and tail-resumptive handlers).
2. Implement the `Cont` state machine and the cancellation token in the runtime, with a test-only
   driver that resumes a continuation synchronously. This validates lifecycle and cleanup without a
   compiler transform.
3. Build a minimal Loom spike that suspends at a `raise` and resumes from a handler. Measure scope
   resolution, thread handoff, cleanup, stack traces, and monitor/native boundaries.
4. Build a minimal compiler-managed transform for the same toy program and compare descriptors,
   debugging, and performance.
5. Decide whether to proceed, defer, or reject based on the prototype report. Do not merge a
   backend before that decision.

Validation should cover:

- `resume` once, twice, after `cancel`, after `done`, and after the `handle` exits;
- `cancel` while suspended, while running, and after completion;
- nested handlers and deep re-entry: a resumed body raises the same carrier again;
- handler state across suspension, including two continuations from one handler;
- `using` cleanup and suppressed `DisposeFailure` in every row of the resource table;
- cancellation from a callback thread under the thread-confinement rule;
- cancellation across a Java frame and across a native frame (must fail safely);
- FFI and `dispose` boundary diagnostics;
- bytecode/descriptor inspection under both backends;
- a full regression run of the abortive and ZEP-0118 tail-resumptive suites.

## Open questions

- Is thread confinement acceptable, or must the first version support `resumeOn(executor, value)`?
- What does `cancel` on a running continuation guarantee, and is that state reachable under thread
  confinement?
- Should a `handle` that captures continuations gain `DisposeFailure` in its result row, or should
  cleanup failures go to an explicit hook?
- Can `Cont` escape its `handle`, or should there be a static scope token that makes escape a type
  error?
- Is `jdk.internal.vm.Continuation` viable on Java 25 at all, and what is the falsification result?
- Can the raise site resolve the handler scope without an ABI change?
- How is handler state represented and transferred if cross-thread resumption is ever allowed?
- Are Java frames capturable in practice, and which interop patterns must be forbidden?
- Does the cancellation `Throwable` remain safe when Java code catches `Throwable`?
- Should multi-shot ever be reconsidered, or is `do`-notation the permanent answer?
- Exactly which functions change descriptors under the compiler-managed backend, and when is the API
  index schema bumped?
- How does this interact with ZEP-0120's blocking `await`, and can the same source switch backends
  without recompilation of callers?
