## Abstract

Define the level-3 handler model: a handler case may store a one-shot continuation and resume it
later. The missing capability is **not** a non-blocking `await`. Blocking a virtual thread is the
accepted default, and [ZEP-0112](./ZEP-0112.md), [ZEP-0164](./ZEP-0164.md), and
[ZEP-0165](./ZEP-0165.md) make the blocking policy cheap, typed, and ergonomic. The capability that
does not exist today is **pull generators** and **general effect handlers** whose case does work while
the body stays suspended: a consumer-driven `next()`, a stateful interpreter, or a handler that waits
for an external event before resuming. In v1 that wait may park the owning thread; multiplexing many
suspended bodies on one thread is not part of the first version.

The proposal introduces `Cont<R, T>` with `resume` and `cancel`, dynamic one-shot enforcement,
deep-handler resumption, automatic cancellation when a `handle` exits, and a cancellation signal
unified with ZEP-0112's task interruption. Its first consumer is a standard-library `generator`
function taking a trailing `() -> Unit performs Yield<T>` lambda; it adds no generator declaration
kind and no new generator syntax. v1 is owner-thread confined: a cross-thread callback wakes
the owner, which calls `resume`; there is no public gate or `resumeOn`. Acceptance is gated on
prototype evidence from three backends: Loom's internal continuations (A), a compiler-managed
transform (B), and a public-API virtual-thread/park backend (C). This proposal does **not** commit to
a shipping backend, does not authorize production use of `jdk.internal.vm.Continuation`, and does not
gate reified generics on its ABI.

## Motivation

[ZEP-0118](./ZEP-0118.md) covers effects whose handler resumes immediately in tail position. That is
enough for `Yield`, `Ask`, `Log`, and the blocking `Await` handler in
[ZEP-0164](./ZEP-0164.md), which waits on a `Completion` and resumes in tail position. Level 2 needs
no stack capture, and it is the right default for async code on virtual threads.

Level 3 is a different capability, not a faster spelling of the same one. It is required when the
handler must keep the body suspended while control returns somewhere else:

- **Pull generators.** A consumer calls `next()`; the producer body is suspended at `Yield` between
  calls. The push direction in ZEP-0118 cannot express this, because its handler resumes immediately.
- **General effect handlers.** A stateful interpreter, protocol driver, or scheduler receives a
  request, does work between the request and the response, and resumes later. The case cannot answer
  in tail position because the answer is not available yet.
- **Waiting for an external event.** A handler may need to wait for I/O or a protocol reply, apply
  a policy, and then resume the body. In v1 the owning thread may block while it waits, so this is a
  suspended body with a parked owner, not a multiplexing scheduler. Interleaving several bodies
  without parking an owner thread needs a future step/control result; it is not a v1 capability.

A non-blocking `await` is one client of this capability, not its justification. The blocking `await`
remains the default and is not deprecated. The real question is what a handler can express when the
body must stay suspended; that is why the continuation contract, handler depth, resource behavior,
cancellation, and threading must be specified before implementation.
[ZEP-0007](./ZEP-0007.md) recorded the exploration and deferred it; this proposal is the scoped
design that follows from it.

## Goals

- Define `Cont<R, T>` and the `resume`/`cancel` operations.
- Enforce one-shot use dynamically with a defined state machine.
- Specify deep-handler semantics for resumed computations, including what `resume` returns when the
  body suspends again.
- State the case-result rule: abort, resume, or cancel, and what a case may return in each shape.
- Scope continuation lifetime to the owning `handle`.
- Define automatic cancellation of pending continuations when the `handle` exits.
- Unify the continuation cancellation signal with ZEP-0112's task interruption and
  `CancellationException`.
- Specify implicit versus explicit cleanup-failure reporting.
- Specify owner-thread confinement and the rule that cross-thread callbacks wake the owner rather
  than resuming it directly.
- Ship a standard-library `generator` function taking a trailing `() -> Unit performs Yield<T>`
  lambda, plus the `Generator`/`GeneratorSource` contracts and cleanup on abandonment.
- Settle the `resume` re-suspension and tail-transfer rules that determine generator stack behavior.
- Add a public-API virtual-thread/park backend (C) to the prototype and compare it with A and B.
- Forbid `Await` in `dispose`, including through a blocking handler, and make that prohibition
  enforceable despite row erasure.
- Preserve the abortive and tail-resumptive behavior defined by ZEP-0118.
- Give handler and closure representations an extension point for a continuation parameter without
  making reified generics depend on it.

## Non-goals

- Multi-shot continuations, backtracking, or replaying a computation
  ([ZEP-0121](./ZEP-0121.md)).
- Linear or affine types; one-shot is a dynamic guarantee.
- Shipping on an internal JDK API.
- Suspending across native frames, an unaware Java callback, or `Disposable.dispose`.
- Changing the blocking `await` policy or the `Task`/`Completion` surface owned by
  [ZEP-0164](./ZEP-0164.md) and [ZEP-0165](./ZEP-0165.md).
- A multiplexing scheduler, `resumeOn`, or a public cross-thread gate in the first version. The
  thread-confinement section defines the supported owner-thread handoff and why a fire-and-forget
  `resumeOn` cannot replace it.
- A general generator combinator library beyond `generator` and its cursors. There is no `yield
  from`, generator method, multi-shot generator, or implicit generator-to-`Stream` fusion.
- A new generator declaration kind or a `generator` block grammar. The surface is an ordinary
  standard-library call with a trailing lambda, so generator-producing functions have no separate
  color.
- Making a one-shot `Generator<T>` conform to `Iterable<T>`. `Iterable` is replayable; a generator
  cursor is not. The `generator` function returns a separate `GeneratorSource<T>` when a replayable
  factory type is needed.
- Allowing any `Await` perform or level-3 suspension inside `Disposable.dispose`. A blocking
  `await` still performs `Await`; direct `task.value()` is a separate blocking library call and is
  covered by the cleanup rules below.
- Rewriting `for ... collect`.
- Changing abortive `raise`/`handle`, `using`, or Java exception translation.
- Gating reified generics, existentials, or the handler ABI on this proposal.
- A general `NoSuspend` capability kind in this proposal; the boundary rules below are the input to
  that later decision.

## Proposal

### `Cont<R, T>`

A case over a carrier with response type `R` receives a continuation whose result type is the
handled expression's type `T`:

```text
Cont<R, T>
    resume(value: R): T
    cancel(): Unit performs DisposeFailure
    isDone(): Boolean
```

`resume` supplies the response value and runs the rest of the handled computation. It is synchronous:
it returns the handled expression's result only when that computation finishes, and it is legal only
on the continuation's owning thread. `cancel` abandons a suspended computation after running its
cleanup; it performs `DisposeFailure` because the caller explicitly asked to observe the cleanup
outcome. `Cont` is a runtime value; it is not a carrier and does not appear in a `raises` row.

The handler's `case` still returns `T`. The valid case shapes are:

- **Abort.** The case never calls `resume`. It returns a `T` it computed itself. The `handle` exits
  and cancels any pending continuations implicitly.
- **Resume.** The case calls `resume(v)` on the owning thread and returns the resulting `T`,
  optionally transformed after the body finishes. `resume` does not return while the body is still
  suspended. Calling it from another thread is a confinement error; a case cannot hand `k` to a
  spawned task and keep the handle alive.
- **Cancel.** The case calls `cancel()` on a suspended continuation, handles the `DisposeFailure` if
  any, and returns a `T` it computed itself.

A case that has not yet produced a `T` cannot return one. This is why a k-guarding case cannot
simply store `k`, return a placeholder, and let the body continue: returning is an abort. The
`handle` exits, and the continuation is cancelled. `Unit` is not a placeholder exception: a case
with `T = Unit` that stores `k` and returns `unit` aborts exactly like any other returning case. The
blocking scheduler below is valid because it waits and returns `k.resume(unit)`; it does not return
while the body is suspended. v1 has no case shape that stores `k`, returns, and keeps the body alive.

#### Blocking scheduler with the `Await` carrier

[ZEP-0164](./ZEP-0164.md)'s carrier responds `Unit` and carries a `Completion`, so the case never
reads the task value:

```zeron
public handler scheduler {
    case Await as awaited, k -> {          // k: Cont<Unit, Unit>
        awaited.pending.awaitDone();       // wait on the owning virtual thread
        return k.resume(unit);             // tail resume; a later Await re-enters this case
    }
}
```

This is the blocking policy and is valid in v1. It does not call `resume` from a completion thread.
The wait happens on the owning virtual thread. v1 has no public cross-thread handoff primitive, so a
handler whose event arrives on another thread must arrange for the owning thread to wake and call
`resume` itself; the callback must never call `resume`. Multiplexing several suspended bodies without
a parked owner thread is future work.

#### Pull generator

The capability that level 2 cannot express is the pull direction. The producer body stays suspended
between calls; the consumer drives it. The source surface is an ordinary standard-library function
with a trailing lambda:

```zeron
public fn generator<T admits nullable + mutable>(
    body: () -> Unit performs Yield<T>
): GeneratorSource<T>

let numbers = generator {
    raise Yield.new(0);
    raise Yield.new(1);
    raise Yield.new(2);
};

for (let n in numbers) {
    println(n);
}
```

This adds no generator declaration kind and no new generator keyword. Any function can call
`generator { ... }`, so there is no generator function color and no separate generator variant. The
existing `Yield<T>` effect is the suspension point; the body is an ordinary lambda with the row
`performs Yield<T>`. `raise`/`perform` spelling follows ZEP-0147; the effect is unchanged.

The body may leave only `Yield<T>` unhandled. Other effects must be handled inside the lambda, because
`GeneratorSource<T>` must remain an `Iterable<T>` and `Iterator.next(): Step<T>` is effect-free.
An effectful generator channel is future work. Normal lambda capture rules apply: the body captures
immutable bindings by value and cannot implicitly capture a reassignable local; shared mutable state
must be reached through a captured object or reference. Two iterators may invoke the same lambda
value concurrently, so shared captures are not implicitly synchronized.

`generator` returns a replayable `GeneratorSource<T>`, which is an `Iterable<T>`. Each call to
`iterator()` invokes the lambda again, so `for`, `Stream`, `forEach`, and repeated traversal work with
the normal `Iterable` contract. The iterator returned by that call is a one-shot `Generator<T>`; it
is not an `Iterable` and must not be reused after it is done. Replayability is structural: each
traversal runs a fresh body with the same captured values. External side effects follow ordinary
function-call semantics, just as they do for a hand-written `Iterable`.

#### `Generator` and `GeneratorSource`

`Iterable<T>` is deliberately replayable: every `iterator()` call returns a fresh cursor. A
continuation-backed generator cursor is one-shot. Making the cursor an `Iterable` would violate that
contract and would make `stream()`, `forEach`, and a second `for` traversal silently reuse exhausted
state. The two roles are therefore separate:

```zeron
public contract Generator<T admits nullable + mutable> requires Iterator<T> {
    /// Stops the body and runs its cleanup. Explicit failure reporting.
    mut cancel(): Unit performs DisposeFailure;
    /// True after Done or cancel.
    isDone(): Boolean;
}

public contract GeneratorSource<T admits nullable + mutable> requires Iterable<T> {
    /// Starts a fresh generator body for this traversal.
    iterator(): &Generator<T>;
}
```

`Generator<T>` is a refinement of `Iterator<T>`: one-shot pull, plus explicit cancellation. It is
never an `Iterable<T>`. `GeneratorSource<T>` is the replayable factory: it is an `Iterable<T>` whose
iterator type is `Generator<T>`. The `generator` function returns `GeneratorSource<T>`; a value can
also be used where an `Iterable<T>` is expected.

Each started body begins on the first `next()` call. Closing or cancelling before the first `next()`
marks the cursor done without invoking the lambda; closing after a partial pull cancels the suspended
body and runs its cleanup. `isDone` is true after `Step.Done`, `close`, or `cancel`.

`Iterator<T>` gains an idempotent `mut close(): Unit` with a default no-op. `for` and the `Stream`
adapters close the cursor they own on normal exhaustion, `break`, `return`, and exceptional exit.
For a generator cursor, `close` cancels the body and sends cleanup failures to the runtime diagnostic
log. This keeps ordinary `for` rows free of `DisposeFailure`. Explicit `cursor.cancel()` is the
reporting path: it performs `DisposeFailure` at the call site. `Stream` adapters must propagate
`close` to their upstream iterator; this is part of the generator surface, not optional cleanup.

A hand-written `Generator` or `GeneratorSource` is allowed, but the compiler cannot verify its
one-shot state or its close behavior. The standard-library `generator` function is the preferred
authoring form: it takes the `() -> Unit performs Yield<T>` lambda and supplies the source and cursor
implementation. The effect row and `Yield<T>` value type do the checking that a dedicated generator
declaration would otherwise duplicate.

#### Runtime shape of a generator

The standard-library implementation uses the same runtime machinery as the raw pull example:

```zeron
// Internal shape of the library implementation; the handler runs on the owning thread.
handle (body()) with {
    case Yield(value), k -> {              // k: Cont<Unit, Unit>
        handOff(value);                    // publish, then park the owning handler thread
        return k.resume(unit);             // tail resume; the next Yield re-enters this case
    }
}
```

`handOff` is a runtime rendezvous with the consumer's `next()`. It publishes the value and parks the
owning handler thread; after the consumer takes the value, that same owning thread calls `resume`.
Under backend C the body runs on a separate virtual thread, but the case and the `resume` call stay
on the owning thread. The body thread is never used to call `resume`, so confinement is preserved.

Because this case is `return k.resume(unit)` in syntactic tail position, the runtime uses the
tail-transfer path defined below. A generator whose case does work after `resume`, or resumes through
a helper call, may retain one case frame per element; the constant-stack guarantee is limited to the
tail-transfer shape. The `generator` library function's case has the tail shape.

### One-shot state machine

The dynamic state is:

```text
suspended --resume()--> running --> done
    |                       |    \--> failed
    |                       \--> cancelled   (runtime request delivered)
    \--cancel()------------> cancelled
```

- `suspended` is the initial state. `resume` and `cancel()` are legal there.
- `resume` is legal only from `suspended`. It moves to `running`, then to `done` or `failed` when the
  computation returns or raises.
- `cancel()` on `suspended` unwinds the continuation, runs `using` cleanup in LIFO order, performs
  any `DisposeFailure` at the call site, and moves to `cancelled`.
- `cancel()` on `done`, `failed`, or `cancelled` is idempotent and performs no cleanup; it is the
  only terminal-state call that is allowed.
- There is no `Cont` operation for cancelling a `running` computation. The runtime may record a
  cancellation request for a running computation and deliver it at the next suspension point or
  `using` boundary. That request is internal, returns no `DisposeFailure`, and surfaces at the task
  boundary if it is task cancellation.
- `resume` on anything other than `suspended` is a program error and panics. It is not a carrier,
  because making it one would contaminate every row.
- `resume` or `cancel()` from a thread other than the owning handler thread is a confinement error.
- `isDone` is true for `done`, `failed`, and `cancelled`.

The compiler may warn when two `resume` calls are visible on the same path, but the guarantee is
dynamic. A continuation stored in a field, captured by a lambda, or passed to another function cannot
be checked locally, and no interprocedural completeness is claimed.

Multi-shot resumption is excluded. Resuming a computation twice while it holds an open `Disposable`
would require duplicating or replaying resource acquisition; that is a consequence of the choice, not
its justification. The justification is that one-shot is what the supported backends can provide and
what pull generators and general handlers need. Multi-shot monads remain the domain of `do`-notation
and [ZEP-0111](./ZEP-0111.md).

### Deep handlers

Resuming a continuation re-enters the handled computation **inside** the same `handle`. Effects
raised after resumption are caught by the same handler. This is required for a generator: after
`resume`, the body may `Yield` again, and the same case must see it.

The `case` body itself stays outside the handler, as it is today. If a case raises, that effect
escapes the `handle` unless an outer handler catches it. The precise rule:

- the resumed computation is inside the `handle`;
- the `case` body is outside the `handle`;
- nested `handle`s inside the resumed computation still take precedence for their own carriers.

#### What `resume` returns

`resume(v)` runs the rest of the handled body under the same handler and returns the final `T`:

1. If the body finishes, `resume` returns its `T`.
2. If the body suspends again on a carrier this handler handles, the matching case runs on the
   owning thread before `resume` returns. The nested case's eventual result becomes the result of
   the original `resume`, and therefore of the outer case if the outer case returns it. The same
   handler sees every subsequent suspension; there is no "suspended" return value and no step token.
3. If the body raises an effect this handler does not handle, that effect escapes from `resume` with
   its row; the case cannot catch it unless it handles it explicitly.
4. If the body is cancelled, the cancellation signal unwinds through `resume` to the `handle`
   boundary. It is not a carrier and cannot be caught by a case.
5. If a nested case aborts or cancels the body, the whole `handle` terminates. Its `T` becomes the
   handle result, and enclosing `resume` calls do not return normally; their post-`resume` code does
   not run.

#### Tail transfer and stack behavior

A case that does work after `resume` keeps its frame and observes the final `T`. A case whose last
operation is `return k.resume(v)` in syntactic tail position, with no work after the resume, may be
lowered to a **tail-resume transfer** instead of an ordinary call. Work before the resume, such as a
handoff or a completion wait, does not prevent the transfer. The compiler emits a transfer marker;
the runtime discards the case frame at the resume point, before running the body and invoking the
next case. This is a handler-specific trampoline, not general tail-call elimination: Zeron does not
optimize ordinary tail calls, and a `resume` reached through a helper call is not detected.

The tail-transfer shape is what makes a pull generator constant-stack. A non-tail case, or a case
that reaches `resume` through a helper, uses the ordinary synchronous call and may retain one frame
per re-suspension. No constant-stack guarantee is made for those shapes; the prototype measures them
and reports the difference. The nested-case rule above is semantic: the tail-transfer implementation
satisfies it with a runtime loop rather than a Java call, so the observable result is unchanged.

A case that returns without resuming aborts. Returning a placeholder `T` does not keep the body
alive, and `T = Unit` is not special; the `handle` exits and cancels the continuation. The scheduler
example above therefore waits on the owning thread and tail-resumes; it does not store `k` and
return.

Deep semantics make a handler with captured continuations a per-`handle` state machine. Its state
must survive across suspension. A named singleton handler that captures `k` is therefore not
stateless. v1 resolves this by having the runtime materialize a fresh handler instance per `handle`
for any handler whose cases may capture `k`; a handler with only abortive or tail-resumptive cases
keeps the singleton representation. A case that stores `k`, or stores state derived from `k`, writes
to the per-`handle` instance, never to a process-global field.

### Thread confinement

A `Cont` belongs to the `handle` instance that created it and is confined to that handle's thread.
`resume` and `cancel` from a different thread are runtime errors in the first version. The rule is
about the **handler state**, not about where the body's stack happens to live: under backend C the
body runs on a separate virtual thread, but that thread is driven only by the runtime, and user code
still calls `resume` on the handle's thread.

A completion callback on another thread must not call `resume` or `cancel()`. It may signal a
synchronization object owned by the handler, obtained from a library or host interop, but v1 does
not provide a public gate, latch, or queue API. The supported v1 shape is for the owning thread to
wait for the event (for example, on `Completion.awaitDone()`) and then call `resume` itself. A handler
that needs to multiplex several bodies without parking an owner thread needs a future step/control
result or a public handoff design; a callback-driven scheduler is not a v1 source pattern.

The prototype's pull-generator runtime may use a private rendezvous, but that is not exposed as
source API and does not change the confinement rule. One parked owning thread per suspended handled
computation is the v1 resource model.

`resumeOn(executor, value)` is **not** in v1, for two reasons:

- A fire-and-forget `resumeOn` cannot produce the case's `T`. The case would still have to wait for
  the body, and if the executor is the same thread that is waiting, the posted resume cannot run.
- A synchronous `resumeOn` that returns `T` is not a convenience. It either blocks the caller until
  the owner finishes, which is a handoff rather than migration, or transfers handler state to
  another thread, which needs separate ownership, cleanup, and cancellation rules.

The v1 rule is therefore "wake the owning thread, resume there." A multiplexing scheduler that wants
to park no thread per continuation needs a shallow/step handler or a control-type result, not just
`resumeOn`; that is future work.

The restriction exists because handler state, the handler stack, and any thread-local context do not
travel with a captured stack automatically. Allowing cross-thread resumption without transferring
that state would produce silently wrong behavior. A future proposal may add explicit migration with a
defined transfer of handler state; it is not part of this one.

A `Cont` may escape its `handle` as an ordinary value. The runtime carries a per-`handle` generation
token; `resume` or `cancel()` after that handle has exited is a runtime error. A static scope token
that makes escape a type error is future work, not a v1 requirement.

### Cancellation

Without linearity, nothing forces a handler to resume or cancel a continuation. The hard case is the
abandoned continuation: nobody closes its open `Disposable` resources, and abandoning a captured
stack does not run `finally` blocks.

Two rules replace linearity:

1. **Explicit `k.cancel()`.** It is legal only on a suspended continuation. It unwinds the suspended
   computation, runs the `dispose` of open `using` blocks in LIFO order, and performs any
   `DisposeFailure` at the call site. It is the only cancellation path that may add
   `DisposeFailure` to the case's row when the failure is unhandled.
2. **`handle` cancellation scope.** When the `handle` exits — by normal completion, by an aborting
   case, by a case that returns without resuming, or by an effect escaping from a case — every
   pending continuation owned by that `handle` is cancelled implicitly. A continuation that is still
   suspended after its `handle` has exited is invalid; `resume` on it panics.

A scheduler that intentionally outlives its `handle` must opt in through a later, explicit mechanism.
The default is structured: continuations do not outlive the handler that owns them.

#### Relationship to ZEP-0112

[ZEP-0112](./ZEP-0112.md) cancels a task by interrupting its virtual thread. The task's
`CancellationException` is the public outcome at `Task.value()`; cleanup failures are suppressed on
it. This proposal does not add a second, unrelated cancellation mechanism. The continuation signal
is the same cancellation event at a finer grain:

- The runtime has one private cancellation token, outside rows and carrier tests. It is a
  `Throwable` subtype so Java `finally` blocks run.
- The token is a private `java.util.concurrent.CancellationException` subclass with an unforgeable
  marker. The task boundary checks the marker before generic failure handling and converts the token
  to a public `CancellationException` with cleanup failures suppressed when the task's cancellation
  state is set. A token that reaches a task boundary without that state is a runtime error, not a
  user cancellation. A user-thrown `CancellationException` is not mistaken for task cancellation
  because it lacks the marker.
- `k.cancel()` is a local, explicit cancellation of one suspended continuation. It does not set the
  task's cancellation state; it unwinds that continuation and reports cleanup failures to the
  caller.
- `Task.cancel()` and `Scope.cancel()` are the structured, implicit path. They set the task state,
  interrupt the task's virtual thread, and deliver cancellation to any continuation the body is
  suspended in. Cancelling a running continuation is an internal request, not a `Cont.cancel()`
  call.

#### Cancelling a task suspended in a continuation

1. The task's cancellation state is set and its virtual thread is interrupted.
2. If the body is suspended, the park is interruptible. The task's cancellation record identifies
   the active continuation, its body thread, and its owning thread. Under backend C the runtime
   interrupts the body thread and wakes the owning thread; on a single-thread backend both roles are
   the same thread.
3. The token unwinds the continuation, runs `using` cleanup in LIFO order, and marks the
   continuation `cancelled`. A case cannot catch the token; only `using`/`dispose` and the runtime
   observe it.
4. The task ends cancelled. `Task.value()` raises `CancellationException` with any cleanup failures
   suppressed. No continuation remains resumable.
5. Under backend C, the body thread and the owning thread must both be woken, and neither remains
   parked. The owning thread returns the cancellation through the handle; the body thread unwinds.

If the continuation is running when cancellation arrives, the internal request is recorded, the
body thread is interrupted when it is distinct from the owning thread, and the request is observed at
the next suspension point or `using` boundary, as in the state machine above. There is no public
`Cont.cancel()` call on a running continuation.

### The cancellation signal is not a carrier

If cancellation were an ordinary carrier, `catchAll<T, E>` and `case Effect` would intercept and
swallow it, which is the known `CancellationException` problem in Kotlin. Cancellation is therefore
an internal object:

- it is outside every row and every carrier type test;
- a `case` cannot handle it;
- only `using`/`dispose` and the runtime observe it;
- user code that wants to react uses `Disposable`, not a handler case.

At the JVM level the signal is a private `Throwable` subtype with an unforgeable token, so Java
`finally` blocks run. The trade-off is that Java code with `catch (Throwable)` or
`catch (CancellationException)` can observe or swallow it. The runtime documents this boundary and
detects a swallowed token when control returns to a suspension or task boundary. A non-`Throwable`
signal would avoid interception but would not run Java cleanup; that is worse for interop.

### Resources and suppression

| Situation | Behavior |
| --- | --- |
| Abortive `raise` on the live stack | `using` blocks between the raise and the `handle` unwind before the case runs; suppressions are available through `with suppressed as s`. |
| Pending continuations when the `handle` exits | They are cancelled implicitly after the case produces its result or escaping effect. If the handle exits by an escaping effect, cleanup failures are suppressed onto that effect and are available to an outer `with suppressed`. If it exits by a normal `T`, the result and the handle's row are unchanged; the first failure and its suppressed failures go to the runtime cancellation diagnostic log. The `handle` row does **not** gain `DisposeFailure`. |
| Case has suspended the computation | The computation stays suspended with its resources open. Nothing is unwound. |
| Case aborts and a `dispose` also fails | The aborting result or effect wins; cleanup failures accumulate as suppressed. |
| Explicit `k.cancel()` while suspended | `cancel` unwinds, runs `dispose` LIFO, and performs any `DisposeFailure` at the call site. If the case does not handle it, the case's row includes `DisposeFailure`. |
| Task or scope cancellation | The task is interrupted; the continuation unwinds; cleanup failures are suppressed on the `CancellationException` raised by `Task.value()`. |

**No static-capture inference.** The earlier draft made a `handle`'s result row depend on whether its
cases "statically capture" a continuation. That rule is withdrawn: passing `k` to a helper, storing it
in a lambda, or returning it through a function would all change the row in ways that are hard to
define and easy to break. The new rule is local and explicit:

- **Implicit cancellation never changes the normal path or the result row.** Cleanup failures are
  suppressed onto the escaping effect when there is one. A normal `T` cannot carry suppressions, so
  the first failure and its suppressed failures go to a runtime diagnostic log (test-visible, not a
  source API). The log is best-effort and never throws into the handle. The `handle` still returns
  its `T`.
- **Only an explicit `k.cancel()` performs `DisposeFailure`.** The call site sees the failures, and
  the case's row includes them as ordinary effect typing. This is the path a handler uses when it
  wants to observe cleanup.

A `Disposable.dispose` may not **suspend**. Its row may contain `DisposeFailure`, abortive effects,
and tail-resumptive level-2 effects such as `Ask` or `Log`. An unhandled level-3-capable carrier in
the row is a compile error. This keeps cancellation synchronous: `k.cancel()` unwinds and returns
without a scheduler in between.

**`Await` in `dispose` is forbidden, including through a blocking handler.** `Await` is
level-3-capable by declaration, so an unhandled `Await` in a `dispose` row is rejected at compile
time. Handling it does not legalize it: `blocking(() -> await(task))`, an inline tail-resumptive
handler, and a helper that hides either all perform `Await` while cleanup is running. The runtime
marks the `dispose` boundary and rejects any `Await` perform while the marker is active, even if the
handler would resume synchronously, and also rejects any level-3 suspension attempt from another
carrier. The marker is a runtime `dispose` depth on the current thread, set around every `dispose`
call and checked by the `Await` perform path and the suspension path. This is what makes the
prohibition enforceable despite row erasure. The static check gives the useful compile-time
diagnostic; the marker catches the hidden cases.

An inline `handle` in `dispose` whose case captures `k` is also rejected as a level-3 handler. A
direct `task.value()` does not perform `Await`; it is a blocking library call and is allowed only
when the task's `E` is empty, and it is discouraged because it can deadlock during scope shutdown.
Forbidding `Await` even in its blocking form keeps all cleanup waiting policy out of the synchronous
LIFO unwind; a `dispose` that needs to wait must be redesigned to do so outside cleanup.

A `using` block may stay open across a resumable `raise`. The compiler should lint this because the
resource remains open while the computation is suspended. The lint is not an error: holding a
resource across suspension is legitimate, but it must be deliberate.

### Backend options

**A. Loom delimited continuations.** `jdk.internal.vm.Continuation` is a one-shot continuation, but
it is not implicit delimited control. Suspending requires an explicit `yield(scope)` with the right
`ContinuationScope`; the raise site must resolve which handler scope owns the carrier. That means a
handler stack or evidence-passing mechanism still exists. `run()` executes on the calling thread, so
the thread-confinement rule above is mandatory.

Direct use has serious costs:

- it is an internal, encapsulated API requiring `--add-exports java.base/jdk.internal.vm=ALL-UNNAMED`;
- its behavior and availability can change on any JDK, including Java 25 updates;
- every launch path, including user programs started outside `zeron run`, must carry the export;
- native frames are a hard barrier, and suspension across an unaware Java frame is a semantic hazard
  even when the frame is technically capturable;
- JEP 491 changed monitor pinning for **blocking** virtual threads. It did not establish that direct
  `Continuation.yield` has the same monitor semantics; that must be tested, not assumed.

**B. Compiler-managed transformation.** A CPS or state-machine transform is portable and does not
depend on an internal API. It changes descriptors for functions that may suspend, breaks tail calls
in the naive encoding, and degrades stack traces. It is the likely shipping fallback unless a public
continuation API appears.

**C. Virtual thread plus park/unpark.** Run the handled body on its own virtual thread. At a level-3
raise, the body publishes the carrier and parks; the owning handler thread runs the case. `resume`
delivers the response, unparks the body, and waits for the next suspension or completion. `cancel`
delivers the cancellation token and unparks. One-shot is natural: the body thread runs once, the
state machine prevents a second resume, and a terminal state retires the thread. Tail transfer is
implemented by discarding the case frame before the next case runs; the body thread remains the only
place where the body executes.

This backend uses only public API (`Thread.ofVirtual`, `LockSupport.park/unpark`, an
`ExecutorService`) and reuses [ZEP-0112](./ZEP-0112.md)'s virtual-thread and cancellation
infrastructure. It needs no internal JDK API and no descriptor or API-index change. It is the
cheapest way to validate the source semantics, the `Cont` contract, deep resumption, and cleanup.

Its costs are real:

- one extra body virtual thread per suspended handled computation, plus the owning thread's parked
  case stack;
- a context switch between the body and handle threads at every effect, not just at blocking calls;
- stack traces, debugger views, and profiling are fragmented across two threads;
- thread-local state and handler state do not travel automatically;
- a body that blocks on a monitor or a native frame can delay or pin; cancellation must wake both
  threads and must not leave either parked;
- per-effect latency and memory are higher than A or B.

C is not a semantic compromise: the same `Cont` contract, one-shot rule, deep-handler rule, and
cleanup rules apply. It is a different implementation of the same source model. It may be the first
shipping backend if its measured costs are acceptable for generators and handlers, and it is the
baseline against which A and B are judged.

**Recommendation.** Prototype **C first**, because it is public-API-only and exercises the semantics
without an ABI commitment. Use A as a semantic probe for stack capture and scope resolution, and B as
the portable fallback if C's per-effect cost or stack fragmentation is unacceptable. Do not commit to
A or B before the prototype report. The source language and the `Cont` contract must be identical
under A, B, and C, so the backend remains an implementation choice.

The prototype must answer:

1. Can the raise site resolve the correct handler scope without changing the ABI of every function?
2. Can the owning handler thread always be woken without requiring user-visible `resumeOn`, and does
   the runtime keep thread-confined resume reliable under backend C?
3. Does cancellation run `using` cleanup and Java `finally` blocks correctly, including waking both
   the body thread and the owning thread under C?
4. What happens to stack traces, debugger stepping, and `using` suppressions across suspension?
5. Does yielding across a frame that holds a monitor, a native frame, or an unaware Java callback
   fail safely or silently corrupt state?
6. Under C, what are the measured context-switch, memory-per-suspended-computation, and cancellation
   latencies for a pull generator and for a blocking external-event wait?
7. Under C, are stack traces and thread-local state understandable enough for diagnostics, and can a
   parked body and its owning thread always be woken on cancellation?
8. Does the tail-transfer path keep stack depth bounded for a long tail-resuming generator, and what
   is the depth growth for a non-tail case?

If any answer requires an ABI change, the "Loom avoids the ABI problem" claim is false and the
proposal proceeds with B or is deferred. If C meets the targets, it can ship first without waiting
for A or B.

### ABI and generics sequencing

Do not make reified generics depend on this proposal. The handler and closure representations should
reserve an extension point for a continuation parameter, but generics, existentials, and the current
handler ABI may ship without it.

If B ships, every function that may suspend changes its descriptor and the API index needs a schema
change. If A ships, the descriptor does not change but the runtime depends on the internal API. If C
ships, neither the descriptor nor the API index changes, and the runtime uses one virtual thread per
suspended handled computation. The backend decision, and therefore the ABI decision, is deferred
until the prototype reports.

### Suspension and cleanup boundaries

Suspension is forbidden across:

- native frames and JNI calls;
- an unaware Java callback that may hold locks or thread-local state;
- `Disposable.dispose`, because cancellation must be synchronous;
- any frame whose row is not known to be free of general resumable (level-3) carriers.

`Await` is level-3-capable by declaration, so an **unhandled** `Await` in a `dispose` row is
forbidden. A handled `Await` is also forbidden in cleanup: the runtime `dispose` marker rejects any
`Await` perform while cleanup runs, including a blocking handler that would resume synchronously,
and rejects any level-3 suspension attempt from another carrier. This keeps all cleanup waiting
policy and suspension out of the synchronous LIFO unwind. A direct `task.value()` is a blocking
library call, not `Await`, and is allowed only when the task's `E` is empty; it is discouraged
because it can deadlock during scope shutdown.

A later `NoSuspend` capability or an abortive-and-tail-resumptive row kind may express this. For now,
the rule is a boundary check: a generic function with an open row cannot be used at a suspension
boundary unless the row is closed and contains no level-3 carriers. Tail-resumptive level-2 effects
are synchronous and remain allowed. This is stricter than a lint and is an input to the later
capability design.

## Compatibility and impact

This proposal is additive and does not change abortive or tail-resumptive behavior. It depends on
ZEP-0118's `responds` and `raise` expression. `Cont`, `resume`, `cancel`, `Generator`,
`GeneratorSource`, `Iterator.close`, and the standard-library `generator` function are new surface.

The cancellation signal is internal, so it adds no row or carrier. **Implicit cancellation does not
add `DisposeFailure` to a `handle`'s result row.** The earlier static-capture rule is withdrawn;
`DisposeFailure` appears only when a case explicitly calls `k.cancel()`, which is ordinary effect
typing at that call site. A `handle` that captures continuations and cancels them implicitly keeps
its normal `T` and row.

`Await` in `dispose` changes as follows: an unhandled `Await` in the cleanup row is a compile-time
error, an inline handler that captures `k` is a compile-time error, and **any** `Await` perform or
level-3 suspension while the runtime `dispose` marker is active panics, including one reached
through `blocking` or a helper. A direct `task.value()` is a separate blocking call, allowed only
when `E` is empty and discouraged.
`await` remains available everywhere outside cleanup.

If the backend is a compiler-managed transform, functions that may suspend change descriptors and the
compiled-library API index requires a schema addition. If the backend is Loom, descriptors are
unchanged but the distribution and every launch path inherit the module export. If the backend is C,
descriptors and the API index are unchanged, and the cost is the extra virtual thread per suspended
computation. None of these changes is authorized until the prototype is evaluated.

This proposal now adds standard-library surface: `Generator`, `GeneratorSource`, `Iterator.close`,
and the `generator` function. `Cont` and its runtime support remain compiler/runtime surface,
and v1 adds no public gate or cross-thread handoff API. The standard-library API version is bumped
once for these additions under the existing consolidation rule. The [ZEP-0164](./ZEP-0164.md) and
[ZEP-0165](./ZEP-0165.md) surfaces own `Task`, `Completion`, `Await`, and the blocking `await`
policy.

## Alternatives

- **Monadic lowering of a handled block** — recorded and rejected in [ZEP-0007](./ZEP-0007.md) for
  the abortive case; it needs a two-slot row-changing bind, residual-row handlers, and descriptor
  changes. A library-level version remains possible for suspending effects but is not this design.
- **Loom-only, shipped as the backend** — rejected. The API is internal, the scope-resolution problem
  remains, and thread handoff is unresolved.
- **Backend C only, without A or B** — not rejected. C is public-API-only and may ship first if its
  measured costs are acceptable. It is still a prototype decision, not an a-priori commitment.
- **No continuation capture** — insufficient for pull generators and general handlers; it is the
  ZEP-0118 baseline.
- **Multi-shot continuations** — deferred. They require replaying resource acquisition and a
  different runtime; `do`-notation covers the monadic use cases.
- **Linear types to enforce one-shot** — rejected for this proposal. A dynamic state machine is
  cheaper and matches the existing lack of linearity.
- **A separate `resumable effect` declaration kind** — considered. ZEP-0118's `responds` already
  distinguishes abortive from responding carriers; adding a second kind would duplicate it.
- **Static-capture `DisposeFailure` on the `handle` row** — withdrawn. It made typing depend on an
  undefined notion of capture and changed the normal path. Implicit cancellation now uses
  suppression; explicit `k.cancel()` performs `DisposeFailure`.
- **`CancellationReport` returned by `k.cancel()`** — a viable alternative to `cancel()` performing
  `DisposeFailure`. It keeps the row unchanged and lets the caller inspect failures, but it adds a
  value type and a second reporting convention next to `DisposeFailure`.
- **`resumeOn` in v1** — deferred. A fire-and-forget form cannot produce the case's `T`; a
  synchronous form is either a blocking handoff or a thread migration of handler state. v1 wakes the
  owning thread, which calls `resume`.
- **A public gate/latch in v1** — deferred. A gate would make callback-driven handlers usable
  without changing `Cont`, but it is a new public synchronization API and a stdlib version change.
  The prototype uses a private rendezvous for its generator; user code gets no gate in this
  proposal.
- **Allowing handled blocking `Await` in `dispose`** — rejected. A blocking handler is synchronous,
  but it can still deadlock during cleanup, and row erasure means the obvious check cannot forbid it.
  The settled rule forbids every `Await` perform under the runtime `dispose` marker; a `dispose` that
  must wait is redesigned to wait outside cleanup.
- **Shallow handlers or a control-type result for multiplexing schedulers** — future work. The
  current `case : T` model requires the case to remain alive until the body produces `T`, so a
  single-threaded multiplexing scheduler is not expressible in v1.
- **A second, continuation-specific cancellation token** — rejected. It would duplicate ZEP-0112's
  interruption and `CancellationException`; the token is the same cancellation event, normalized at
  the task boundary.

## Implementation and validation

This is a staged prototype, not a schedule.

1. Land ZEP-0118 (response types and tail-resumptive handlers).
2. Implement the `Cont` state machine, the cancellation token, and the runtime `dispose` marker in
   the runtime, with a test-only driver that resumes a continuation synchronously. This validates
   lifecycle, the explicit-vs-running cancellation split, token normalization, the `Await`-perform
   rejection in cleanup, and cleanup without a compiler transform.
3. Build the **backend C** prototype: a runtime-supported pull generator, a blocking external-event
   wait, deep re-entry, tail transfer, cancellation of a suspended body, and cleanup. Measure
   per-effect context switches, memory per suspended computation, cancellation latency, stack depth
   for tail and non-tail cases, and stack-trace quality.
4. Add `Generator`/`GeneratorSource`, `Iterator.close`, the standard-library `generator` function,
   and `for`/Stream close propagation. This is the shipping generator surface; it depends on the
   runtime state machine and the tail-transfer path, not on the backend choice. No parser or
   formatter change is required.
5. Build a minimal Loom spike (A) that suspends at a `raise` and resumes from a handler. Measure scope
   resolution, thread handoff, cleanup, stack traces, and monitor/native boundaries.
6. Build a minimal compiler-managed transform (B) for the same toy program and compare descriptors,
   debugging, and performance.
7. Compare A, B, and C against the same source program and decide whether to proceed, defer, or
   reject. Do not merge a backend before that decision; C may ship first if it meets the targets.

Validation should cover:

- `resume` once, twice, after `cancel`, after `done`, and after the `handle` exits;
- `cancel()` while suspended and after completion; no public `cancel()` on a running continuation;
  the internal request is delivered at the next suspension or `using` boundary;
- nested handlers and deep re-entry: a resumed body raises the same carrier again, and `resume`
  returns the final `T` after the nested case;
- a case that returns without resuming aborts and cancels the continuation, including a `Unit` case
  that stores `k` and returns `unit`; a cross-thread `resume` panics under the confinement rule;
- handler state across suspension and re-entry, including a cached continuation that is resumed after the handler instance has observed another suspension;
- `generator { ... }` is an ordinary trailing-lambda call usable inside any function, with no
  parser, formatter, or declaration-kind change; the lambda is not invoked until the first `next()`;
- a generator source traversed twice yields two independent bodies; its cursor is rejected where an
  `Iterable` is required and cannot be reused after `Done`;
- a generator body that leaves an effect other than `Yield<T>` unhandled is rejected, and a body that
  tries to capture a reassignable local follows the ordinary lambda capture diagnostic;
- `for` over a generator closes the cursor on normal exhaustion, `break`, `return`, and an escaping
  effect; `using` cleanup runs, and implicit cleanup failures reach the diagnostic log;
- `Stream` adapters over a generator propagate `close` upstream, including early termination;
- explicit `Generator.cancel()` after a partial pull reports `DisposeFailure`; `isDone` is true after
  `Done` and after cancel;
- a pull generator with many elements, checking that the syntactic tail-transfer case keeps bounded
  stack under A and C, and measuring the growth of a non-tail case;
- a blocking external-event wait: the owning thread waits and calls `resume`; a direct `resume` from
  the callback thread panics, and v1 exposes no public gate;
- cancellation of a task whose body is suspended in a continuation: interrupt, unwind, `using`
  cleanup, and `CancellationException` at `value()` with suppressed failures; the marker is
  normalized even when the task's cancelled flag was set by another path;
- explicit `k.cancel()` performing `DisposeFailure`, and implicit cancellation leaving the normal
  `T` and the `handle` row unchanged;
- `using` cleanup and suppressed failures in every row of the resource table;
- unhandled `Await` and capturing handlers in `dispose` rejected; `Ask` and `Log` allowed; any
  `Await` perform, including a blocking `await` hidden in a helper, and any other level-3 suspension
  panics at the runtime dispose marker; direct `task.value()` warned when `E` is empty;
- cancellation across a Java frame and across a native frame (must fail safely);
- FFI and `dispose` boundary diagnostics;
- bytecode/descriptor inspection under A and B, and descriptor/API-index equality under C;
- a full regression run of the abortive and ZEP-0118 tail-resumptive suites.

## Future work and prototype questions

These questions do not change the v1 source contract. They decide the backend and later extensions;
implementation may proceed against the semantics above while the prototype answers them.

- Should a future step/control result replace the synchronous `resume: T` shape so one thread can
  multiplex several suspended bodies? v1 keeps the synchronous shape and owner-thread confinement.
- Is `resumeOn` worth adding later, and what owns handler state after a cross-thread handoff? A
  fire-and-forget form cannot produce `T`; a synchronous form needs explicit handoff or migration.
- Should v1 eventually expose the private gate used by the generator runtime as a public handoff
  API, and what is its close/cancellation protocol?
- Should a future static scope token make `Cont` escape a type error? v1 permits escape and detects
  use after handle exit at runtime.
- Is backend C viable as the first shipping backend, and what are its measured context-switch,
  memory, and cancellation costs?
- Is `jdk.internal.vm.Continuation` viable on Java 25 at all, and what is the falsification result?
- Can the raise site resolve the handler scope without an ABI change?
- How is handler state represented and transferred if cross-thread resumption is ever allowed?
- Are Java frames capturable in practice, and which interop patterns must be forbidden?
- Does the cancellation `Throwable` remain safe when Java code catches `Throwable` or
  `CancellationException`, and how is a swallowed token detected in practice?
- Should multi-shot ever be reconsidered, or is `do`-notation the permanent answer?
- Exactly which functions change descriptors under the compiler-managed backend, and when is the API
  index schema bumped?
- Can a future `NoSuspend` capability replace the runtime `dispose` marker? The current rule rejects
  every `Await` perform in cleanup and does not depend on a handler-level annotation.
- Can the same source switch between A, B, and C without recompiling callers, and how does that
  interact with [ZEP-0164](./ZEP-0164.md) and [ZEP-0165](./ZEP-0165.md)?

## Decision

Draft. No backend or shipping direction is approved. The revised design:

- foregrounds pull generators and general effect handlers, not non-blocking `await`;
- ships the standard-library `generator` function plus `GeneratorSource`/`Generator`; the source
  is a replayable `Iterable`, while the cursor is a one-shot `Iterator` and never an `Iterable`;
- adds `Iterator.close` and requires `for`/`Stream` to close generator cursors, with implicit
  cleanup failures logged and explicit `Generator.cancel()` reporting `DisposeFailure`;
- keeps the blocking `await` of [ZEP-0164](./ZEP-0164.md) and
  [ZEP-0165](./ZEP-0165.md) as the default;
- defines the case-result rule, including the rule that `Unit` is not a placeholder and a returning
  case aborts;
- defines the deep `resume` result, including re-suspension, nested abort/cancel, and the
  syntactic tail-transfer path that keeps a tail-resuming generator's stack bounded;
- keeps v1 owner-thread confined; cross-thread callbacks must wake the owner, and v1 adds no public
  gate or `resumeOn`;
- unifies continuation cancellation with ZEP-0112's interruption and `CancellationException`, with
  explicit `Cont.cancel()` only on suspended continuations and an internal request for running
  continuations;
- removes the static-capture `DisposeFailure` rule: implicit cancellation suppresses or logs,
  explicit `k.cancel()` performs `DisposeFailure`;
- forbids `Await` in `dispose` even through a blocking handler: unhandled `Await` and capturing
  handlers are compile-time errors, and any `Await` perform under the runtime `dispose` marker
  panics; direct `task.value()` is allowed only when `E` is empty and is discouraged;
- adds backend C to the prototype and recommends prototyping it first.

Acceptance is gated on the prototype and the future/prototype questions above; until then this
proposal must not be treated as authorization to use an internal JDK API or to change the handler
ABI. The source semantics above are the settled v1 contract for an implementation; the prototype
chooses the backend and measures it.
