> `Task`, changes `spawn` to return `&Task<T, {E}>`, and changes `await` to accept `Task<T, E>`.

## Abstract

Add a direct-style async surface over [ZEP-0112](./ZEP-0112.md)'s structured concurrency.
`Future<T, E>` is a value that represents a task in flight, `spawn(scope, body)` starts a task and
returns a future, and `await(future)` blocks the current virtual thread and returns its value.

`await` is an ordinary generic library function whose body is `future.join()`. Source therefore
needs no `async`/`await` keyword, no suspend modifier, and no wrapper return type. The task body's
effects stay in the future's `E` row and are re-raised at the await site, so the caller's
`performs` clause is checked exactly as it is for `Task.value()`.

This is the blocking library layer. A responding `Await` carrier and an automatic entry-point
handler are deliberately not part of this design; they are specified separately in
[ZEP-0164](./ZEP-0164.md) so that the blocking surface does not depend on new effect-application or
handler machinery.

## Motivation

[ZEP-0112](./ZEP-0112.md) gives Zeron direct-style blocking suspension, scopes, cancellation, and
structured concurrency, but its surface is library-shaped: `ConcurrentScope`, `Task`, `start`, and `value`.
That is sufficient for concurrency, but it is more syntax than a simple fan-out needs:

- a `Task` handle exposes the primitive name `value()` rather than the async vocabulary;
- users must thread `Task<T, {E}>` through signatures when they only need a handle;
- `Scope.start` returns a read-only task view, so a handle cannot be cancelled without cancelling
  the whole scope.

A future is the value users actually name at the call site. It starts work immediately, records the
result and effect row, and blocks on `join`. Because blocking a virtual thread is cheap, this does
not need a scheduler, continuation capture, or a state machine: `await` is a direct call to `join`.

The proposal also gives the eventual effect layer a stable user-facing surface. `spawn` and `await`
are source-compatible with adding a carrier later: the rows already mention `E`, and the calls do
not change shape.

## Goals

- Define `Future<T, E>` as a handle to a task started with `spawn`.
- Give `spawn(scope, body)` and `await(future)` a direct-style surface with no keyword, suspend
  modifier, or wrapper in the caller's return type.
- Propagate a task's raised effects to the await site with the caller's row checked.
- Map task and scope cancellation onto ZEP-0112's structured-concurrency rules.
- Implement the surface on ZEP-0112's virtual-thread primitives with no continuation capture.
- Preserve `ConcurrentScope` and `Task` as the primitive library surface.
- Keep the source compatible with a later carrier and non-blocking backend.

## Non-goals

- A responding `Await` carrier, an automatic top-level handler, or named resuming handlers. These
  are [ZEP-0164](./ZEP-0164.md).
- Non-blocking `await`; that is [ZEP-0119](./ZEP-0119.md).
- `async`/`await` keywords, a `suspend` modifier, or a wrapper return type.
- Effect-row runtime representation, open applied effect applications, or wildcard effect cases.
- Reified type parameters on classes.
- Deterministic single-threaded interleaving, cooperative scheduling of user code, or multi-shot
  continuations ([ZEP-0121](./ZEP-0121.md)).
- A pluggable scheduler abstraction beyond a single injected executor for tests.
- Replacing `ConcurrentScope`, `Task`, or ZEP-0112's effect-capture rules.
- Program argument forwarding, thread pools, reactive streams, or parallel collections.
- A monadic `map`/`flatMap` surface on `Future`.

## Proposal

### `Future<T, E>`

A `Future<T, E>` is a handle to a task that returns `T`, may raise effects in row `E`, or may be
cancelled. It is a value, not a computation in a monad; it is only needed when work is actually
concurrent.

```zeron
public contract Future<T admits nullable + mutable, E admits effect...> {
    join(): T performs E;        // blocks the current virtual thread
    isDone(): Boolean;
    isCancelled(): Boolean;
    mut cancel(): Unit;
}
```

The task's outcome is one of:

- `Ok(value)` — `join` returns `value`;
- `Raised(effect)` — `join` re-raises the captured effect;
- `Cancelled` — `join` raises the internal cancellation signal.

`join` is the only join point. `isDone` and `isCancelled` are ordinary observations and do not
perform the task's effects.

### `spawn`

```zeron
public fn spawn<T admits nullable + mutable, E admits effect...>(
    scope: &ConcurrentScope,
    body: () -> T performs E
): &Future<T, {E}>
```

`spawn` starts `body` in `scope` with `scope.start` and wraps the task handle. Starting a task does
not itself perform `E`: the body's effects are captured as the task outcome and re-raised at
`join`. A failure to start, such as a closed scope, is a programming error reported by the scope.

The returned mutable view lets a caller keep the handle and cancel that one task:

```zeron
using (let scope = ConcurrentScope.open()) {
    let first = spawn(scope, () -> load(1));
    let second = spawn(scope, () -> load(2));
    let value = await(first) + await(second);
    ...
}
```

`ConcurrentScope` still owns cancellation, joining, deadlines, and the lifetime of every task. `spawn` is a
typed convenience over `scope.start`, not a second concurrency model.

### `await`

```zeron
public fn await<T admits nullable + mutable, E admits effect...>(
    future: Future<T, E>
): T performs E =
    future.join();
```

`await` is an ordinary function. It adds no row label of its own: the only escaping effects are the
task's `E`, which `future.join()` re-raises. A function that awaits therefore declares exactly the
effects its awaited tasks may raise, and no additional async marker.

This is why there is no carrier in this proposal. `await` does not need to suspend, capture a
continuation, or transfer control to a handler. It blocks the current virtual thread until the task
finishes, then returns or re-raises.

### The `Scope.start` reference capability

`Scope.start` now returns `&Task<T, {E}>` instead of `Task<T, {E}>`. The mutable view is required so
a `Future` can delegate `mut cancel`. A `&Task` projects to the read-only `Task` view, so existing
reads and `value()` calls keep working, and a task can still be used without a future. This is the
only signature change to a ZEP-0112 API.

### Failure, cancellation, and scope exit

- **Failure.** A task body that raises `E` captures the carrier. `Future.join` re-raises it at the
  await site; existing handlers and the caller's row apply there, exactly as ZEP-0112 specifies for
  `Task.value()`.
- **Cancellation.** `Future.cancel()` requests cooperative cancellation of that task.
  `ConcurrentScope.cancel()` cancels the scope's tasks. A task that observes cancellation unwinds through its
  `using` blocks and ends `Cancelled`. Awaiting a cancelled task raises the internal cancellation
  signal; it does not return a `Cancelled` value into user code.
- **Scope exit.** Leaving the `using` scope joins or cancels outstanding tasks and never leaves one
  running. A `Future` that outlives its scope is invalid; using it after scope exit is a programming
  error.
- **No implicit failure propagation between tasks.** A task failure does not cancel its siblings;
  `await` observes one outcome at a time, and `scope.cancel()` stops the rest.

### Relationship to ZEP-0112

ZEP-0112 is the runtime primitive: virtual threads, `ConcurrentScope`, `Task`, effect capture at the task
boundary, re-raise at the join point, structured shutdown, and cooperative cancellation. This
proposal is the direct-style convenience layer:

- `spawn` wraps `scope.start`;
- `Future.join` wraps `Task.value`;
- `await` is `Future.join` under an async-facing name;
- failure, cancellation, and scope lifetime are ZEP-0112's semantics, not new ones.

A user may keep using `ConcurrentScope` and `Task` directly. This proposal does not deprecate them.

### Relationship to the deferred carrier

An earlier revision of this proposal described `Await<T, E>` as a responding effect with a blocking
handler and an automatic top-level runtime. That design is not representable in the current
language: effect applications must be closed, a type parameter or an effect row cannot appear in an
applied effect, and a handler case cannot cover every application of a generic effect. It also made
`main` depend on handler installation for the simplest async program.

[ZEP-0164](./ZEP-0164.md) records the follow-up design: a non-generic, identity-erased `Await`
carrier, `await` as a performing function with a runtime-checked response, and a blocking handler
installed at the program entry point in the same change. Until that design is accepted, `await`
remains the plain blocking function specified here.

## Compatibility and impact

The proposal is additive. It adds `Future`, `spawn`, and `await` to `zeron.concurrent` and bumps
`STANDARD_LIBRARY_API_VERSION` once for the release cycle (to 21). The only signature change to an
existing API is `Scope.start` returning the mutable `&Task<T, {E}>` view; the read-only `Task` view
and `value()` are unchanged.

There is no descriptor or ABI change: `Future` is an ordinary contract, `spawn` an ordinary generic
function, and `await` an ordinary call to `join`. The only runtime cost is the virtual-thread
blocking already provided by ZEP-0112.

A later carrier from ZEP-0164 changes `await`'s row by adding `Await`. That is a source-visible
change and must ship with its own release note and entry-point handling; this proposal does not
pretend the two are interchangeable.

## Alternatives

- **A responding carrier in this proposal** — deferred to ZEP-0164. The generic `Await<T, E>`
  form would need open effect applications, effect-row identity or erasure, a handler covering all
  applications, and entry-point installation. ZEP-0164 instead proposes a non-generic, erased
  carrier, which avoids the first two. None of it is required for the blocking surface.
- **Library-level `Task` only (ZEP-0112)** — rejected as the whole surface. It is usable but lacks
  the async-facing names and a cancellable handle that does not require the scope.
- **`async`/`await` keywords** — rejected. They colour the call chain and duplicate `map`/`filter`.
- **A `Future<T>` with no error parameter** — rejected. It would erase the task's row and force
  `await` to raise `Effect` or lose checked propagation.
- **A monadic `Future`** — rejected as the primary surface. `map`/`flatMap` reintroduce a wrapper
  and a second calling convention; a future here is a handle to running work, not a lazy
  computation.
- **Non-blocking first** — rejected for this slice. It needs ZEP-0119's unproven runtime; blocking
  on virtual threads is portable and already available.
- **Source-level `main` wrapper** — rejected. Requiring `main` to call a `blocking(...)` helper is
  worse ergonomics than a plain `join` and would make the simplest async program depend on handler
  plumbing.

## Implementation and validation

Implemented in 0.9.0:

1. Added `Future<T, E>` and its implementation over ZEP-0112's `Task`.
2. Added `spawn(scope, body)` as a typed wrapper over `scope.start`.
3. Added `await(future)` as an ordinary `future.join()` call.
4. Changed `Scope.start` to return `&Task<T, {E}>` so the future can delegate `mut cancel`.
5. Documented the surface and its relationship to `ConcurrentScope`/`Task` in the structured-concurrency
   guide.

Validation covers:

- no wrapper type and no `async` keyword or suspend modifier in source or compiled signatures;
  `await` resolves as an ordinary library function;
- `spawn` plus `await` returns the task value on a virtual thread;
- a task failure re-raises at the await site and is handled by an ordinary `handle`;
- the caller's row is checked: an unhandled task effect is a compile-time diagnostic;
- cancellation through `Future.cancel` and `ConcurrentScope.cancel`, including `using` cleanup;
- a cancelled task raises `java.util.concurrent.CancellationException` at `await`;
- the ZEP-0112 scope/task regression suite still passes with the reference-capability change.

`AsyncFutureTest` is the focused regression. The full suite passes with 1044 tests.

## Open questions

- Should `spawn` accept a name or label for diagnostics, and does that belong in the manifest or
  source?
- Does a `Future` outliving its `ConcurrentScope` deserve a static scope token rather than a runtime check?
- Should `await` eventually become interceptable? That question belongs to ZEP-0164 and ZEP-0119,
  not to this surface.
- Are row aliases or a super-effect worth adding if async rows become verbose once ZEP-0164 adds an
  `Await` label to non-entry functions?

## Decision

Implemented on 2026-11-21. The accepted direction is the blocking direct-style surface:
`Future<T, E>`, `spawn(scope, body)`, and `await(future)` on top of ZEP-0112's `ConcurrentScope`/`Task`, with
no keyword, suspend modifier, wrapper return type, or carrier.

The earlier async-as-an-effect design was split out rather than reimplemented partially:
[ZEP-0164](./ZEP-0164.md) owns the `Await` carrier, its runtime identity, and the blocking handler
at the program entry point. It must ship the entry handler with the carrier so that `await` stays
ergonomic in `main`.

Superseded on 2026-11-22 by [ZEP-0165](./ZEP-0165.md). `Future` duplicated `Task` as a transparent
forwarding wrapper; the only differences were the `join`/`value` method names and the
`spawn`/`Scope.start` factory. ZEP-0165 keeps `Task` as the single eager handle and retains this
proposal's blocking direct-style policy. The `Await` carrier and entry handler remain ZEP-0164,
with `Task` as the payload type.
