## Abstract

Define a direct-style async surface without `async`/`await` keywords and without a wrapper in every
signature. `Await<T, E>` is a responding effect; `Future<T, E>` is a value that represents a task in
flight. `spawn` starts a task in a [ZEP-0112](./ZEP-0112.md) scope, and `await` raises `Await`.

The first implementation is **blocking on virtual threads**, using ZEP-0112's `Scope` and `Task`.
`await` is a tail-resumptive handler, so it needs no continuation capture. A non-blocking handler
that stores the continuation is opt-in and gated on [ZEP-0119](./ZEP-0119.md); the source language
does not change when the backend changes.

## Motivation

[ZEP-0112](./ZEP-0112.md) gives Zeron direct-style blocking suspension, scopes, cancellation, and
structured concurrency, but its surface is library-shaped: `Scope`, `Task`, `start`, `value`. That
is sufficient for concurrency, but it does not give the uniformity that motivates the effect model:
`map`, `filter`, and `retry` should accept pure, failing, and asynchronous functions with the same
row-polymorphic shape.

[Design document 21](../design_documents/design-document-21_suspendable-effects-and-one-shot-continuations.md)
proposes `Async` as an effect and `Future` as a value, with `spawn` and `await`. This proposal makes
that surface concrete and reconciles it with ZEP-0112 so the project does not end up with two
competing concurrency models.

The key observation is that a **blocking** `await` is tail-resumptive: the handler calls
`future.join()`, gets the value, and resumes immediately. It needs ZEP-0118, not ZEP-0119. Only a
non-blocking scheduler that stores the continuation needs capture.

## Goals

- Define `Await<T, E>` as a responding effect and `Future<T, E>` as its value.
- Give `spawn(scope, body)` and `await(future)` a direct-style surface with no wrapper in the
  caller's return type.
- Propagate a task's raised effects to the `await` site with the caller's row checked.
- Map task and scope cancellation onto the existing structured-concurrency rules.
- Provide a runtime top-level handler for `main`.
- Implement the first version on ZEP-0112's virtual-thread primitives, with no continuation capture.
- Keep the source compatible with a later non-blocking handler from ZEP-0119.
- Preserve `Scope`/`Task` as the primitive library surface.

## Non-goals

- `async`/`await` keywords, a `suspend` modifier, or a wrapper return type.
- Non-blocking `await` in the first implementation; that is ZEP-0119.
- Deterministic single-threaded interleaving, cooperative scheduling of user code, or multi-shot
  continuations ([ZEP-0121](./ZEP-0121.md)).
- A pluggable scheduler abstraction beyond a single injected executor for tests.
- Replacing `Scope`, `Task`, or ZEP-0112's effect-capture rules.
- Program argument forwarding, thread pools, reactive streams, or parallel collections.
- Defining `Async` as a new primitive keyword.
- Changing `using`, `Disposable`, or abortive `raise`/`handle`.

## Proposal

### `Future<T, E>`

A `Future<T, E>` is a handle to a task that returns `T`, may raise effects in row `E`, or may be
cancelled. It is a value, not a computation in a monad; it is only needed when work is actually
concurrent.

```zeron
public class Future<T, E: effect...> {
    public fn isDone(): Boolean;
    public fn isCancelled(): Boolean;
    public fn cancel(): Unit;
    public fn join(): T raises E;        // blocks the current virtual thread
}
```

The task's outcome is one of:

- `Ok(value)` — `join` returns `value`;
- `Raised(effect)` — `join` re-raises the captured effect;
- `Cancelled` — `join` raises the internal cancellation signal.

The `E` row parameter is necessary for soundness: if `Future` erased it, `await` could not prove
that the caller handles the effects the task may raise. Whether effect declarations accept a row
parameter this way is an open question; the fallback is a closed `E` or a single-effect parameter.

### `Await<T, E>` and `await`

```zeron
public effect Await<T, E: effect...> responds T {
    public property future: Future<T, E>;
}

public fn await<T, E: effect...>(future: Future<T, E>): T
        raises Await<T, E> + E =
    raise Await.new(future);
```

`Await` responds `T`; the handler supplies the task's value when it resumes. The `+ E` in `await`'s
row covers the handler's possible re-raise of a task failure. The carrier does not invent a new
error channel.

### `spawn`

```zeron
public fn spawn<T, E: effect...>(
    scope: Scope,
    body: () -> T raises E
): Future<T, E>
```

`spawn` starts `body` in `scope` using ZEP-0112's `scope.start`, and wraps the task handle. Starting
a task does not itself raise `E`: the body's effects are captured as the task outcome and re-raised
at `await`. A failure to start (for example, a closed scope) is a programming error reported by the
scope, not a carrier.

The primitive remains:

```zeron
using (scope = Scope.open()) {
    let f = spawn(scope, () -> load(id));
    let value = await(f);
    ...
}
```

`Scope` owns cancellation and joining. `spawn` is sugar that returns a typed `Future` instead of a
raw `Task`.

### The blocking handler

The first implementation installs this handler:

```zeron
public handler blockingAsync<E: effect...> {
    case Await(future), k -> k.resume(future.join());
}
```

This is tail-resumptive: `join()` returns the value (or re-raises `E`), and `k.resume` is in tail
position. It uses `Future.join`, which blocks the current virtual thread and lets the carrier run
other tasks. No stack capture is involved.

The handler's row includes `E` because `join` may re-raise a task failure; that matches `await`'s
declared `+ E`. If the task was cancelled, `join` raises the internal cancellation signal defined by
ZEP-0119.

A non-blocking handler is a separate implementation:

```zeron
public handler resumableAsync<E: effect...> {
    case Await(future), k -> {
        future.onComplete { outcome -> k.resume(outcome.value()) };
    }
}
```

That handler stores `k` and is general resumable (level 3, ZEP-0119). It is opt-in. The source
program, its signatures, and its rows are identical.

### The top-level runtime

`main` may declare the async carriers it raises:

```zeron
fn main(): Unit raises Await<Int, {}> {
    ...
}
```

The runtime installs `blockingAsync` around `main` and reports any carrier that remains unhandled.
This proposal does **not** require a nominal `Async` effect. Design document 21's `raises Async` is
read as shorthand for "the row contains async carriers." A nominal `Async` super-effect could be
introduced later with `under` or a contract, but it is not assumed here:

- `raises Async` would need contract-typed rows or a new row kind;
- an `Async` super-effect with `case Async` loses the concrete operation needed to join or schedule;
- declaring the concrete carriers, or using `raises Effect` at the top level, works today.

If experience shows that the concrete row is too verbose, a later proposal can add a row alias or a
super-effect.

### Failure and cancellation

- **Failure.** A task body that raises `E` captures the carrier. `Future.join` re-raises it at the
  `await` site; existing handlers and the caller's row apply there, exactly as ZEP-0112 specifies
  for `Task.value()`.
- **Cancellation.** `Future.cancel()` requests cooperative cancellation of that task.
  `Scope.cancel()` cancels the scope's tasks. A task that observes cancellation unwinds through its
  `using` blocks and ends `Cancelled`. `await` on a cancelled task raises the internal cancellation
  signal; it does not return a `Cancelled` value into user code and does not expose a catchable
  carrier.
- **Scope exit.** Leaving the `using (scope = Scope.open())` block joins or cancels outstanding tasks
  and never leaves one running. A `Future` that outlives its scope is invalid; `join` after scope
  exit is a programming error.
- **Task cancellation vs continuation cancellation.** `Future.cancel()` cancels a task at its
  suspension points; `Cont.cancel()` from ZEP-0119 cancels a suspended handler continuation. They
  are different operations and must not be conflated in documentation.

### Relationship to ZEP-0112

ZEP-0112 is the runtime primitive: virtual threads, `Scope`, `Task`, effect capture at the task
boundary, re-raise at the join point, structured shutdown, and cooperative cancellation. This
proposal is the effect-surface layer:

- `spawn` wraps `scope.start`;
- `Future.join` wraps `Task.value`;
- `await` is an effect whose blocking handler calls `join`;
- the semantics of failure, cancellation, and scope lifetime are ZEP-0112's, not new ones.

A user may keep using `Scope`/`Task` directly. This proposal does not deprecate them.

## Compatibility and impact

The proposal is additive. It adds `Future`, `Await`, `spawn`, and `await` to the standard library and
changes `STANDARD_LIBRARY_API_VERSION` once for the release cycle. It does not change existing
`Scope`/`Task` behavior.

With the blocking handler, there is no descriptor or ABI change: `Await` is an ordinary effect
carrier and `await` is an ordinary function. The only runtime cost is the virtual-thread blocking
already provided by ZEP-0112.

A non-blocking handler from ZEP-0119 is a backend swap. If the source is unchanged, callers may need
to recompile only if ZEP-0119's backend changes descriptors; that decision belongs to ZEP-0119.

The proposal relies on ZEP-0118's `responds` and on tail-resumptive handlers. Without ZEP-0118,
`await` cannot return a value at the raise site and this surface is not expressible.

## Alternatives

- **`Future<T>` plus `do`-notation** — rejected as the primary surface. It works for any monad but
  reintroduces a mandatory wrapper and a second calling convention; it remains available for
  multi-shot monads.
- **Library-level `Task` only (ZEP-0112)** — acceptable fallback. It is simpler but does not give the
  uniform row-polymorphic API that motivates async as an effect.
- **`async`/`await` keywords** — rejected. They color the call chain and duplicate `map`/`filter`.
- **A nominal `Async` effect** — deferred. It needs contract-typed rows or a super-effect whose
  handler can still recover the concrete operation. Concrete carriers work without it.
- **Non-blocking first** — rejected for the first version. It needs ZEP-0119's unproven runtime;
  blocking on virtual threads is portable and already available.
- **`Future` with no error parameter** — rejected. It would erase the task's row and force `await`
  to raise `Effect` or lose checked propagation.

## Implementation and validation

Likely stages:

1. Add `Future<T, E>` and the task outcome representation on top of ZEP-0112's `Task`.
2. Add the `Await<T, E>` effect and `await` as `raise Await.new(future)`.
3. Add `spawn(scope, body)` as a typed wrapper over `scope.start`.
4. Implement and install the blocking handler; wire the runtime top-level handler for `main`.
5. Document the surface and the relationship to `Scope`/`Task`.
6. Optionally add the non-blocking handler from ZEP-0119 behind the same source surface.

Validation should cover:

- no wrapper type and no `async` keyword or suspend modifier in source or compiled signatures;
  `await` is an ordinary library function, not a keyword;
- `spawn` + `await` returns the task value on a virtual thread;
- a task failure re-raises at the `await` site and is handled by an ordinary `handle`;
- the caller's row is checked: an unhandled task effect is a compile-time diagnostic;
- cancellation through `Future.cancel` and `Scope.cancel`, including `using` cleanup;
- a `Future` used after its scope exits fails safely;
- nested scopes and nested `await`;
- `main` with an async row runs under the runtime handler;
- Java interop from a task body;
- source compatibility when swapping the blocking handler for the resumable one;
- a regression run of ZEP-0112's scope/task tests.

## Open questions

- Is `Future<T, E>` with a row parameter representable in an effect declaration and its runtime
  identity, or must `E` be closed or single-effect?
- Is a nominal `Async` marker or super-effect worth adding later, and how would its handler recover
  the concrete operation?
- Should `await`'s default be blocking, with resumable opt-in, or should the backend be a project or
  runtime setting?
- Does `Future.cancel` need a distinct `Cancelled` carrier for inspection, or is the internal signal
  plus `isCancelled` enough?
- Who owns the executor/scheduler: `Scope`, the runtime, or an injected test hook?
- Can `main` declare an open async row, or does it need a row alias or `raises Effect`?
- Should `spawn` accept a name/label for diagnostics, and does that belong in the manifest or source?
- How does this surface interact with `do`-notation and ZEP-0111's witness dispatch?
- Does a `Future` outliving its `Scope` deserve a static scope token rather than a runtime check?
