## Abstract

Record the only resumption scope not covered by the one-shot design: **multi-shot continuations**, in
which a handler resumes the same captured continuation more than once. Multi-shot resumption is the
mechanism behind backtracking, nondeterministic search, and replay-based testing, but it conflicts
with resource acquisition, mutable state, and the single-stack runtime that
[ZEP-0119](./ZEP-0119.md) assumes.

This proposal is deliberately `Deferred`. It states the problem, the obstacles, and the conditions
under which the question should be reopened. It does not propose syntax, runtime support, or an
implementation schedule.

## Motivation

[ZEP-0118](./ZEP-0118.md) makes a `raise` return a handler-supplied value, and
[ZEP-0119](./ZEP-0119.md) lets a handler store that continuation and resume it once. Together they
cover `Yield`, `Ask`, `Log`, blocking and non-blocking `await`, pull generators, and schedulers.
[ZEP-0120](./ZEP-0120.md) defines the async surface on top.

One control pattern remains outside that design. A search or parser may want to explore several
alternatives from the same suspended point:

```text
handler chooses:
    resume(k, firstAlternative)
    ... later, if that fails ...
    resume(k, secondAlternative)
```

The same saved state is entered twice, with different responses, and the computation branches. This
is not a loop over the original function, because the work already performed before the `raise` must
not be repeated blindly. That is multi-shot resumption.

[ZEP-0007](./ZEP-0007.md) listed this as an open question and deferred it. Its design direction is now
split into 0118 (response types and tail-resumptive handlers), 0119 (one-shot capture and
cancellation), and 0120 (async surface). This proposal carries the remaining piece so that the split
leaves no resumption scope unrecorded.

## Goals

- State precisely what multi-shot resumption would mean in Zeron.
- Identify why it is incompatible with the one-shot state machine in ZEP-0119.
- Record the resource and mutation problems it creates.
- Compare it with the multi-shot monads already expressible through `do`-notation.
- Define the evidence that would justify reopening the question.
- Keep the one-shot design unblocked: nothing here changes ZEP-0118, ZEP-0119, or ZEP-0120.

## Non-goals

- Implementing multi-shot continuations or scheduling any work.
- Proposing syntax such as a cloneable `Cont`, `resumeMany`, or `fork`.
- Changing the one-shot `Cont<R, T>` contract from ZEP-0119.
- Redefining the `Monad` contracts from ZEP-0019 or the `do` surface from ZEP-0111.
- Duplicating the mechanism comparison already recorded in ZEP-0007.
- Promising replay on the JVM, copyable stacks, or continuation equality.
- Changing abortive `raise`/`handle`, `using`, or Java interop.

## Background: what is already settled

The split proposals answer most of ZEP-0007's questions:

| Question from ZEP-0007 | Current answer |
| --- | --- |
| One-shot or multi-shot? | One-shot; enforced dynamically by ZEP-0119. |
| Deep or shallow handlers? | Deep for resumed computations; the case body stays outside the handler. |
| What does a resumed raise receive? | The response type declared on the carrier (ZEP-0118). |
| Cleanup across suspension? | `using`/`dispose` rules, automatic cancellation, and possible `DisposeFailure` on the `handle` row (ZEP-0119). |
| Foreign frames? | Continuation barriers; suspension is forbidden across them (ZEP-0119). |
| Monadic lowering as the semantics of `raise`? | Rejected in ZEP-0007 and not proposed by 0118–0120. |
| Multi-shot? | This proposal. |

The mechanism comparison in ZEP-0007 remains the historical record for why a free-monad encoding
needs a two-slot constructor, a type-level row join, and residual-row handler types.

## Why multi-shot is a different problem

### The runtime assumes one stack

ZEP-0119 resumes a suspended computation by re-entering its captured stack once. A second entry
either requires a second copy of that stack or re-execution from the beginning. The JVM offers no
copyable stack, and `jdk.internal.vm.Continuation` is one-shot. A multi-shot design therefore needs
one of:

- **Replay:** re-run the computation from the start and skip or repeat already observed effects
  until the new branch is reached. Side effects are repeated unless the program records and
  replays their results.
- **A continuation tree:** represent the suspended computation as immutable data that can be
  entered more than once, which is the free-monad encoding analyzed in ZEP-0007.
- **A copyable stack:** not available on the JVM and not proposed here.

None of these is a small extension of ZEP-0119. Each changes the runtime contract, and replay changes
observable behavior, not only performance.

### Resources are acquired once

A suspended computation may hold open `using` blocks. Resuming it twice would either:

- run the same `dispose` twice, which most resources do not tolerate;
- share one live resource between branches, which makes disposal ordering depend on which branch
  finishes last; or
- re-acquire the resource for the second branch, which duplicates external effects and may change
  the result.

ZEP-0119 avoids the question by cancelling pending continuations when the `handle` exits and by
enforcing one-shot resumption. A multi-shot proposal must choose a resource model explicitly; there
is no neutral default.

### Mutable state has to fork or be shared

A captured computation can mutate variables captured by its lambdas (ZEP-0002) and can mutate objects
reachable through references. Re-entering it twice must state whether each branch observes:

- an independent snapshot of mutable state, which requires copying or structural state;
- shared state, which makes the branches order-dependent; or
- replayed state, which repeats the mutations and may double-apply them.

"Backtracking" usually implies rolling state back, but Zeron has no general mechanism for that, and
adding one would not be a continuation feature.

### Handler state is not a value

A deep handler in ZEP-0119 is a per-`handle` state machine. With multi-shot, two branches may return
to the same handler with different histories, and the handler state must be forked, merged, or
replayed. ZEP-0119's state machine has no operation for this.

## Relationship to `do`-notation

Multi-shot monads already have library support in Zeron. `Option`, `Result<_, E>`, and `Stream`
work with `do`-notation ([ZEP-0111](./ZEP-0111.md)), and `List` has a witness-based
`map`/`bind`/`join` example ([ZEP-0019](./ZEP-0019.md)). Nondeterminism and backtracking can be
expressed as ordinary values with explicit binds; a generic `guard` helper over `MonadPlus` is a
possible library addition, not current language surface.

That encoding:

- makes branching and failure explicit in the types;
- gives the program control over which effects are replayed;
- composes with `do` syntax without a new runtime;
- does not attempt to resume a captured stack.

The trade-off is the familiar one: the monadic form colors the participating functions and requires
adapters at the boundary with direct-style code. Direct-style multi-shot effects would remove that
cost, but only by taking on the runtime questions above.

Until a use case shows that the direct-style form is materially better than `do`, the monadic form is
the supported answer. This is why the proposal is `Deferred` rather than `Draft`: there is no
accepted problem statement that `do` cannot serve.

## Requirements if the question is reopened

A future proposal would have to settle, at minimum:

1. **Semantics.** Replay, tree, or some other model, and what a second resumption observes.
2. **Resources.** Whether `using` blocks are duplicated, shared, or forbidden across a branch point.
3. **Mutation.** Snapshot, shared, or replayed state, and how it is expressed in the type system or
   documented as a runtime rule.
4. **Handler state.** Fork/merge/replay rules for deep handlers.
5. **Cancellation.** What cancelling one branch does to its siblings, and how it interacts with
   ZEP-0119's `handle` scope.
6. **Type system.** Whether a two-slot constructor with a row join and residual-row handlers is
   required, and whether ZEP-0086's declaration-level row polymorphism can be extended or must be
   replaced.
7. **Cost.** A measured comparison against the monadic encoding for a representative search.
8. **Boundaries.** Native frames, Java callbacks, and `dispose` remain continuation barriers unless
   proven otherwise.

A design that answers fewer than these is not ready to move out of `Deferred`.

## Alternatives

- **Keep one-shot only and use `do` for multi-shot** — the current decision. Simple, portable, and
  already available for the known use cases.
- **Replay the whole computation for each branch** — portable, but repeats effects and requires the
  program to be replay-safe; not a general answer.
- **Continuation tree / free monad** — expressible only with the type-system additions ZEP-0007
  identified; it is a monadic encoding by another name.
- **Copyable stacks** — not available on the JVM and not proposed.
- **Linear or affine types to force disciplined branching** — out of scope; ZEP-0119 already rejects
  linearity for one-shot enforcement.
- **Treat multi-shot as a library-only feature forever** — plausible; it would make this proposal a
  permanent record rather than a precursor.

## Compatibility and impact

None at present. The proposal authorizes no language, runtime, ABI, or standard-library change, and
the one-shot proposals do not depend on it.

If a future design is accepted, it would affect the continuation representation, the handler ABI, and
the resource rules; it should then be recorded as a new proposal rather than by changing this one,
per the ZEP process.

## Implementation and validation

Not scheduled. The only appropriate next step is a written use-case review: find a direct-style
program that `do` cannot express acceptably, then decide whether the resource and state questions can
be answered without weakening ZEP-0119.

No prototype is authorized. A spike would be justified only after a use case and a semantic model
exist, because the JVM mechanism (replay versus tree) determines what the spike can measure.

## Open questions

- Is there a concrete use case where direct-style multi-shot resumption is materially better than
  `do`-notation, not merely more convenient?
- Should a second resumption replay effects, share their results, or be forbidden when effects are
  observable?
- Are `using` blocks duplicated, shared, or a compile-time error across a branch point?
- Does backbranching require state snapshots, and if so, is that a language feature or a library
  convention?
- Can handler state be forked cheaply, or does multi-shot force handlers to be stateless?
- Does multi-shot require the two-slot row-changing constructor, or can a closed application suffice
  for the accepted use cases?
- Would multi-shot ever be compatible with ZEP-0119's automatic cancellation scope?
- Is `List`-style nondeterminism the only real use case, in which case `do` is permanent?

## Decision

Deferred 2026-11-12. This proposal carries the remaining scope of [ZEP-0007](./ZEP-0007.md) after its
split into ZEP-0118, ZEP-0119, and ZEP-0120: multi-shot resumption. Do not design or implement it
until a concrete use case demonstrates that `do`-notation and one-shot resumption cannot serve the
need. Reopening requires the semantics, resource, mutation, handler-state, cancellation, and type
system questions above to be answered together; they are not independent choices.
