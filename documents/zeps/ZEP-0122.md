## Abstract

This proposal makes an applied class pattern such as `case Box<Int>` a real runtime discriminator
when the scrutinee's applied identity is available through the implemented
[ZEP-0015](./ZEP-0015.md) descriptor:

```zeron
fn classify<T: reified>(box: Box<T>): String = match (box) {
    case Box<Int> -> "integer box";
    case Box<String> -> "string box";
    case _ -> "other box";
};
```

The compiler emits the existing erased `instanceof Box` test followed by exact descriptor equality
before casting or binding. A successful case is typed and destructured as `Box<Int>`; a mismatch
continues to the next arm. The descriptor is supplied by a closed source type or by a reified type
parameter or anonymous existential. No descriptor field is added to ordinary generic classes.

This is the ordinary-`match` companion to [ZEP-0005](./ZEP-0005.md)'s generic effect handler cases.
Both use one exact-descriptor test. ZEP-0005 applies it to payload-carried effect identity; this
proposal applies it to descriptor-backed values in `match`.

## Motivation

ZEP-0104 introduced exact applied type tests through `is` and `as?` for reified type parameters and
reified anonymous existentials. ZEP-0005 uses the same identity for generic effect handler cases.
Ordinary `match` remains erased: `case Box<Int>` compiles to an `instanceof Box` test and cannot
distinguish `Box<Int>` from `Box<String>`. A user can write an `if` chain with ZEP-0104 tests, but
cannot use the destructuring, coverage, guard, and result-expression machinery that `match` already
provides.

Leaving that gap would make the release story asymmetric:

- `handle (effect) with { case Failure<Int> -> ... }` can distinguish applied effect identities;
- `match (box) { case Box<Int> -> ... }` cannot distinguish applied class identities;
- yet both are pattern forms over the same descriptor and the same cast-and-bind operation.

The absence is not just a convenience gap. A `match` arm that appears to test `Box<Int>` but accepts
any `Box` is unsound-looking and makes the generic matching rules depend on whether the value is an
effect payload or an ordinary value. This proposal closes that gap for values whose applied identity
is already available, without introducing a second identity mechanism.

## Goals

- Make an exact applied class/product pattern in `match` a runtime descriptor test when the
  scrutinee's application is descriptor-backed.
- Reuse ZEP-0015's descriptor, constants, composition, and equality rules.
- Preserve the existing erased class test as the first part of the check.
- Cast, bind, destructure, and flow-refine only after the descriptor matches.
- Define coverage, duplicate-case, and exhaustiveness behavior for exact applied cases.
- Share one exact-descriptor test with ZEP-0005's handler dispatch.
- Add no descriptor field to ordinary generic classes and no new library-index schema.
- Keep existing static-only patterns and existing `match` roots unchanged.

## Non-goals

- Adding a runtime descriptor field to every generic class or value. That is a holder/storage ABI
  question, not this proposal; see [ZEP-0106](./ZEP-0106.md).
- Exact tests on `Any`, non-reified type parameters, star views, or erased projections. Those
  values do not have a descriptor to compare.
- Subtype, ancestor, variance, or interface matching; see [ZEP-0107](./ZEP-0107.md) and
  [ZEP-0108](./ZEP-0108.md).
- Changing generic effect handler syntax or coverage; that remains [ZEP-0005](./ZEP-0005.md).
- Changing applied arguments in sum-case patterns or sealed-contract patterns. Those remain
  statically checked destructuring patterns with their current semantics.
- Opening patterns in `match`; see [ZEP-0105](./ZEP-0105.md). ZEP-0116's accepted opening design is limited to `if`/`while` conditions.
- Nested exact applied patterns in this slice. A nested pattern uses the static type substituted by
  its parent pattern; only the top-level applied pattern selects by descriptor.
- Reflection, dynamic descriptor construction from a class name, or runtime member discovery.
- General `Any`-based type discrimination. A raw class test still proves only the erased class.

## Proposal

### Descriptor-backed roots

An exact applied pattern is a pattern whose target is a class or product type with type arguments,
such as `Box<Int>` or `Pair<String, Box<Int>>`. It performs a runtime application test only when the
scrutinee has a **descriptor source**:

| Scrutinee static type | Descriptor source |
|---|---|
| Closed application `Box<Int>` | Constant `Box<Int>` descriptor |
| `Box<T>` with `T: reified` | Composed from the hidden descriptor for `T` |
| Reified type parameter `T: reified` | The hidden descriptor for `T` |
| `Box<: reified>` | The hidden argument descriptor, composed with the known outer `Box` constructor |
| Application composed from closed arguments and reified variables | Composed recursively |
| `Any`, `Any?`, non-reified `T`, `Box<*>`, `Box<out B>`, or another erased view | None |

A `match` root becomes eligible for exact applied patterns when its static type has a descriptor
source and at least one arm uses an applied pattern. This is an additional root mode, not a change
to the existing sealed, product, literal, or concrete-root modes.

The root mode does not make `Any` a valid applied-discrimination root. For `Any`, the compiler can
test the erased class but cannot distinguish `Box<Int>` from `Box<String>`. Such a program is
rejected with a diagnostic directing the user to a reified parameter, a reified anonymous
existential, or a statically known application.

### Static total and static impossible cases

The compiler first compares the source application with the target application as source types:

- If they are statically identical, the case is **total** for that root. No descriptor test is
  emitted. This preserves patterns such as `case Box<T>` on a `Box<T>` scrutinee, including when
  `T` is not reified.
- If the source is a closed application and the target is a different closed application, the case
  is **statically impossible** and is rejected. It must not become a runtime arm that can never
  match.
- If the source is descriptor-backed but not statically identical to the target, the case is
  **refutable** and the runtime descriptor test is emitted.

A closed source and a target that differs only in nullability or mutability are different
applications and are statically impossible. Exact identity includes the full structural descriptor;
there is no variance at this step.

### Target rules

An exact target application must be fully written and closed, or statically identical to the source
application.

Accepted targets:

- closed nominal classes, primitives, arrays, nullable forms, and nested generic applications;
- a generic class or product application whose arguments are closed;
- the source's own application when it is statically identical, even if it mentions a type
  parameter.

Rejected targets:

- `Box<_>`, `Box<*>`, `Box<out Int>`, `Box<in Int>`, star projections, captures, and type
  projections;
- type parameters in a target that are not statically identical to the source application;
- function types and other descriptor forms that cannot participate in applied identity;
- unapplied generic classes where an application is required;
- nullable roots; `match` already rejects nullable scrutinees.

A target that mentions a reified variable but is not statically identical to the source is outside
this slice. The useful runtime targets are closed applications; variable targets are either static
totals or rejected. This keeps target descriptor construction deterministic and avoids making
target composition a second, implicit inference feature.

### Matching and binding

The generated test for a refutable exact case is:

1. test the erased target class with `instanceof`;
2. compare the source's descriptor with the target's constant descriptor;
3. only on equality, cast the value to the applied target type;
4. bind the alias and destructure product/sum components using the target's substituted types.

The cast is never performed before the descriptor check. A failed descriptor test continues with
the next arm and does not evaluate the arm's guard or body. Concretely:

```zeron
fn classify<T: reified>(box: Box<T>): String = match (box) {
    case Box<Int> as integer -> "integer: " + integer.value;
    case Box<String>(text) -> "string: " + text;
    case _ -> "other";
};
```

For `case Box<String>(text)`, `text` has type `String` after the descriptor match. For
`case Box<Int> as integer`, `integer` has type `Box<Int>`. The alias is not exposed before the
descriptor matches.

A guard runs after the complete pattern succeeds, as it does today. A guard-failing case continues
to the next arm but does not contribute coverage.

### Coverage and exhaustiveness

Exact applied cases are keyed by their full descriptor identity, not by the erased class name:

- `case Box<Int>` and `case Box<String>` are distinct alternatives on a descriptor-backed root.
- Two unguarded `case Box<Int>` arms are duplicates; the later arm is unreachable.
- An unguarded exact case covers only its exact application when the source type is broader than
  that application.
- Because the set of possible applications of a generic class is open-ended, a match over a
  descriptor-backed root that is not statically fixed needs an unguarded wildcard or other total
  fallback. `case Box<Int>` plus `case Box<String>` is not exhaustive over `Box<T>`.
- If the source is statically identical to the target application, the case is total and covers the
  root without a wildcard.
- A wildcard covers all remaining applications and all remaining values permitted by the root.
- A final `case Box<Int>` is not a catch-all for other applications. There is no implicit
  `Box<Any>` or `Box<*>` fallback in this proposal.

Coverage remains conservative: a guard, a refutable nested pattern, or a refutable pattern
declaration does not contribute total coverage. Existing sealed-contract, product, and literal
coverage rules are unchanged.

### Relationship to sum-case patterns

Sum-case patterns such as `case Success<Int>.extract(item)` are not changed by this proposal. They
are static destructuring patterns over a scrutinee whose applied arguments are already fixed by the
sum or sealed-contract type. The existing resolver rule that their type arguments must match the
scrutinee remains in force, and their runtime test remains the erased case-class test.

The new descriptor test applies to an ordinary class or product pattern that is being used to
distinguish applications of a broader or reified value. A sealed-contract root does not become an
applied-discrimination root merely because one of its permitted cases is generic.

### Relationship to ZEP-0005

ZEP-0005 needs the same primitive for `case Failure<Int>` in a handler: erased payload-class test,
then exact descriptor equality, then payload cast and binding. This proposal does not define effect
handler semantics, but it requires the implementation to factor one exact-descriptor test that both
paths use.

The two proposals are a release pair:

- if ZEP-0005 ships, ZEP-0122 ships in the same `0.7.0` bundle;
- if ZEP-0122 is delayed, ZEP-0005 must not ship alone;
- neither proposal changes the other's identity rules, target grammar, or coverage model.

### Runtime and library ABI

No descriptor field is added to ordinary generic classes. The descriptor is already supplied by
ZEP-0015 through hidden parameters for reified variables and anonymous existentials, or by a
constant for a closed application. The only new runtime work is the descriptor comparison and the
existing cast/bind path.

No new library-index record is required:

- `match` patterns are source-level constructs and are not exported;
- reified markers, anonymous existentials, and applied type descriptors already have their ZEP-0015
  and ZEP-0104 encodings;
- target constants are compiler-generated, not public API.

Separate compilation must still be tested because a library-defined generic class can be matched in
a client whose reified argument descriptor crosses the library boundary.

## Compatibility and impact

This is an additive source feature for descriptor-backed roots. It does not change the meaning of
existing valid `match` expressions:

- `case Box<Int>` on a scrutinee already known as `Box<Int>` remains valid and becomes statically
  total; it still matches every value of that type.
- `case Box<T>` on a `Box<T>` scrutinee remains a static total pattern, even when `T` is not
  reified.
- Sum-case and sealed-contract applied patterns remain static-only destructuring patterns.
- Existing programs that were rejected because a generic class root could not discriminate
  applications become valid only when a descriptor source exists.

The design-document-16 rule that generic arguments are static-only remains the default and
continues to govern `Any`, star views, projections, non-reified parameters, and sealed/sum case
patterns. This proposal adds an explicit descriptor-backed mode; it does not make generic arguments
generally reified.

The runtime cost is one descriptor comparison per attempted exact arm after the erased class test.
Closed targets use cached constants. No allocation is added to class construction or to unrelated
matches. The ZEP-0015 measurement matrix must record the comparison and composed-descriptor costs
for this path.

## Alternatives

- **Extend `is` only and desugar every match arm to `if` chains.** This loses `match` coverage,
  alias scoping, guards, and result-expression behavior, and duplicates the matching implementation.
  Rejected.
- **Make generic arguments runtime discriminators for all generic values.** This requires a
  descriptor field on every generic object or a holder ABI change. That is much broader than the
  shared ZEP-0015 hidden-parameter model and belongs to stored-existential work. Rejected for this
  slice.
- **Keep erased `match` patterns and tell users to use `is` first.** This preserves the current
  implementation but leaves an obvious asymmetry with generic effect handlers and cannot express
  destructuring after an exact test. Rejected.
- **Use `Box<Any>` or `Box<*>` as an implicit catch-all.** Neither is an exact application; treating
  one as a fallback would create variance or projection semantics that this proposal does not
  define. Rejected.
- **Match on `Any` by testing only the erased class.** This would accept `case Box<Int>` for any
  `Box`, which is the unsound-looking behavior this proposal exists to remove. Rejected.
- **Add a separate `case Type is Box<Int>` syntax.** The existing applied type-pattern spelling is
  already parsed and is the natural form. Rejected as unnecessary surface.

## Implementation and validation

1. Mark an ordinary class/product pattern with applied arguments as an exact applied pattern during
   resolution. Do not mark sum-case patterns or sealed-contract destructuring patterns.
2. Classify the scrutinee's descriptor source using ZEP-0015: constant closed application, reified
   variable, reified anonymous existential, or composed application. Reject exact patterns when no
   source descriptor exists.
3. Validate target arguments as closed or statically identical to the source. Reject wildcards,
   projections, functions, non-reified variables, and other non-describable targets.
4. Compare source and target statically first: mark identical applications total; reject impossible
   closed applications; otherwise mark the case as a runtime descriptor test.
5. Emit the erased class test, then descriptor equality, then the existing cast, alias binding,
   product/sum destructuring, guard, and flow-refinement path.
6. Extend match coverage to key exact applied cases by descriptor identity. Require a wildcard or
   total fallback for open-ended descriptor-backed roots, and diagnose duplicate or subsumed exact
   cases.
7. Reuse the same descriptor-test helper for ZEP-0005 handler dispatch; do not introduce a second
   test implementation.
8. Test:
   - `T: reified` roots with `Box<Int>` and `Box<String>` values, including a fallback;
   - `Box<T>` roots where `T` is a reified function type parameter;
   - `Box<: reified>` roots and composed source descriptors;
   - `case Box<Int> as box` binding and `case Box<Int>(value)` destructuring;
   - guards, multiple arms, duplicate exact cases, and non-exhaustive open roots;
   - statically total `case Box<Int>` on a `Box<Int>` root and rejection of a disjoint closed case;
   - rejection for `Any`, non-reified `T`, `Box<*>`, `Box<out Any?>`, projections, wildcards, and
     function-type arguments;
   - preservation of existing sum-case patterns, including `case Success<Int>.extract`;
   - descriptor equality across a separately compiled library-defined generic class;
   - no descriptor field on ordinary class instances and no regression for non-generic matches.
9. Record descriptor comparison, composed-descriptor construction, and cast/bind costs in the
   ZEP-0015 matrix. If the comparison cannot meet the accepted overhead bound, this feature does
   not ship in `0.7.0`.

## Implementation status (2026-11-12)

Implemented the descriptor-backed applied `match` slice for top-level class and product
patterns. A match whose scrutinee is a closed application, a `reified` type parameter, or a
reified anonymous existential now enters an `APPLIED` root mode when at least one top-level arm
writes type arguments. The resolver:

- classifies the scrutinee's descriptor source and rejects `Any`, non-reified parameters, star
  views, projections, erased targets, and nullable roots;
- treats a statically identical target as total and emits no descriptor test;
- rejects a different closed target as statically impossible before code generation;
- marks a refutable exact target and requires a wildcard or a statically total applied case for
  exhaustiveness;
- keys coverage and duplicate diagnostics by the full `GenericDescriptor`, not the erased class;
- leaves sum-case, sealed-contract, opening, and nested applied patterns in their existing static
  modes.

Code generation performs the erased class test first, then the same ZEP-0015 descriptor equality
helper used by generic effect handlers, and only then casts, binds, and destructures. Class
positional destructuring uses the target application's public properties; product destructuring
uses the substituted product components. No descriptor field is added to ordinary classes and no
library-index schema changes are required.

`AppliedTypeMatchCompilationTest` covers exact class dispatch, static totals, class positional
patterns, product destructuring, `Box<: reified>` roots, reified type-parameter roots, separate
compilation, impossible targets, erased roots, star targets, duplicate exact cases, and
non-exhaustive open roots. The focused regression set (`ProductTypeTest`, `SumTypeTest`,
`GenericEffectCompilationTest`, `ExistentialGenericsTest`, `EffectRowCompilationTest`, and
`Zep0015AcceptanceTest`) passed: 47 tests, 0 failures, 0 errors. The applied-match comparison reuses
the measured ZEP-0015 descriptor equality path; no separate match-specific benchmark was added.

Remaining out of scope: nested exact applied patterns, applied ancestry, variance, stored
descriptors on ordinary values, opening in `match`, and contract-bound tests. Sum-case and
sealed-contract applied patterns retain their previous static semantics.

## Open questions

None. The initial scope is deliberately limited to top-level exact applied patterns with a
descriptor source. Nested exact patterns, stored descriptors on ordinary class values, variance,
ancestry, and contract-bound tests have separate owners.

## Decision

Accepted and implemented 2026-11-12 as the ordinary-`match` companion to ZEP-0005. It is recorded
as a `Candidate` for the `0.7.0` bundle and is a required companion to ZEP-0005, not an optional
rider. The two
features share one exact-descriptor test; the release must not ship generic effect handler matching
without applied-type `match` patterns, or vice versa.

The design reuses ZEP-0015 without changing its descriptor ABI. It requires a descriptor source on
the scrutinee and therefore does not add descriptors to ordinary generic objects or make `Any` and
erased views runtime-discriminable. Exact applied patterns are refutable unless the source
application is already statically identical; open-ended roots require a wildcard or other total
fallback. Sum-case patterns, sealed-contract matching, opening, applied ancestry, and holder ABI
remain outside this proposal.
