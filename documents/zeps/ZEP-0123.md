## Abstract

Introduce a dedicated `admits` clause for generic admissibility markers so that “which type
arguments may be substituted” is visibly separate from “which operations are available.” Canonical
markers are `nullable`, `mutable`, and the effect markers `effect`, `effect<Never>`, `effect<R>`,
and `effect...`. A bare `effect` admits an effect of unknown response and supports forwarding but
not a generic `raise`; `effect<Never>` admits abortive effects and preserves today’s generic
`raise`; `effect<R>` admits effects whose handler supplies exactly `R`. `effect<*>` is reserved and
not accepted. `reified` is explicitly not an admissibility marker; it becomes a leading capability
modifier. This proposal supersedes the marker syntax and semantics of ZEP-0010, ZEP-0055, and
ZEP-0062, while carrying forward their underlying nullability, mutability, and effect-kind rules.

## Motivation

Generic declarations currently write admissibility markers in the same list as contract bounds:

```zeron
fn old<T: Display<T> + nullable + mut, E: effect>(value: T): T = value;
```

That makes three different questions look identical:

- Which operations does the generic body have? (`Display<T>`)
- Which type arguments may be substituted? (`nullable`, `mut`, `effect`)
- Which runtime or ABI capability does the declaration require? (`reified`)

The ambiguity is already visible in `reified`, which is not an admissibility property at all: it
adds a hidden descriptor parameter. It will get worse with response-typed effects. `effect<Unit>` is
not a contract the body can call; it says which effect types are admissible and what a generic
`raise` returns. A dedicated clause makes that boundary explicit and leaves ordinary bounds to
describe operations.

The current effect marker is also underspecified for response typing. `E: effect` today permits
`raise` because every effect is abortive. Once effects can respond, a generic `raise` on an unknown
effect has no sound response type. The marker set needs an explicit distinction between unknown,
abortive, and exactly responding effects before response typing lands.

## Goals

- Add `admits` as a distinct grammatical slot after ordinary contract bounds.
- Define the canonical marker set: `nullable`, `mutable`, `effect`, `effect<Never>`, `effect<R>`,
  and `effect...`.
- Keep safe defaults: non-null, read-only, and no effect-kind use unless explicitly admitted.
- Make bare `effect` a forwarding-only, unknown-response marker.
- Make `effect<Never>` the explicit abortive marker and the migration target for generic `raise`.
- Make `effect<R>` an exact, invariant response marker that prepares for
  [ZEP-0118](./ZEP-0118.md)’s `responds R`.
- Rename the mutable admissibility marker from `mut` to `mutable`, while leaving the `mut`
  declaration modifier unchanged.
- Move `reified` out of the marker list into a leading capability modifier.
- Use the same `admits` clause in anonymous existentials.
- Preserve compiled-library compatibility for pre-response effect markers.
- Supersede the admissibility-marker framework in ZEP-0010, ZEP-0055, and ZEP-0062.

## Non-goals

- Implementing response-typed effects, `responds R`, or tail-resumptive handlers; those remain
  [ZEP-0118](./ZEP-0118.md).
- General effect subtyping or a denotable top effect type; those remain
  [ZEP-0013](./ZEP-0013.md).
- Row-level response polymorphism or a constraint that every carrier in a row responds `R`.
- An `any` admissibility shorthand for combined `nullable + mutable`.
- Giving `effect<*>` a meaning.
- Changing nullability, mutability, effect runtime representation, or handler dispatch semantics.
- Changing variance, higher-kinded constructor admissibility, or Java interop behavior.
- Redesigning the `reified` descriptor facility; only its source spelling changes.
- Renaming the `mut` modifier on functions, receivers, fields, or mutable references.

## Proposal

### Surface syntax

`admits` is a new clause after the ordinary bound list. It is separate from `:` so that bounds and
admissibility markers cannot be confused:

```text
typeParameter = [ "out" ], [ "reified" ], IDENTIFIER, [ "<", "_", ">" ],
                [ ":", bound, { "+", bound } ],
                [ "admits", marker, { "+", marker } ] ;
bound  = type ;
marker = "nullable" | "mutable" | effectMarker ;
effectMarker = "effect", ( "..." | [ "<", type, ">" ] ) ;
```

`admits` is a contextual keyword in this position and remains an ordinary identifier elsewhere. An
`admits` clause must contain at least one marker. Markers are order-insensitive; the formatter prints
`nullable` before `mutable` and at most one effect marker. A parameter may omit both the bound list
and the `admits` clause. `admits` is available wherever admissibility markers are currently
permitted: generic functions, methods, classes, contracts, data classes, extensions, and witnesses,
subject to the existing reification and higher-kinded restrictions.

Examples:

```zeron
fn doSomething<
    T: A<*> admits nullable + mutable,
    E: B + C admits effect<Unit>,
    Row admits effect...
>(...): ... { ... }

fn identity<T admits nullable>(value: T): T = value;

fn forwardRef<T admits mutable>(value: T): T = value;

fn render<T: Display<T> admits nullable>(value: T): T = value;
```

The `:` list remains ordinary contract and type bounds. The `admits` list never provides operations,
and a contract bound never grants admissibility.

### Bounds, capabilities, and admissibility

Three concepts are now written separately:

| Concept | Position | Example | Meaning |
| --- | --- | --- | --- |
| Contract or type bound | after `:` | `T: Display<T> + Inspect<T>` | Operations and conformance available in the body |
| Admissibility marker | after `admits` | `T admits nullable + mutable` | Which type arguments may be substituted |
| Capability modifier | leading | `reified T` | Additional hidden ABI input, such as a runtime descriptor |

`reified` is not an admissibility marker. It states that the callee receives a runtime applied-type
descriptor and is restricted to callable type parameters by ZEP-0015. It composes with `admits`:

```zeron
fn describe<reified T: Render admits nullable>(value: T): String { ... }
```

`out` remains a class/contract variance annotation. `out` and `reified` do not combine, because
variance applies to class/contract parameters while reification applies to callable parameters.

Higher-kinded constructor parameters such as `F<_>` do not take `admits` in this proposal;
first-order admissibility does not describe a constructor’s own argument policy. Effect-row
parameters are first-order and use `admits effect...`.

The old bound-position spellings are rejected with a migration diagnostic: `T: nullable`, `T: mut`,
and `T: reified` must be rewritten as `T admits nullable`, `T admits mutable`, and `reified T`
respectively. `T: effect` becomes `T admits effect`, `effect<Never>`, or `effect...` according to
its use. The marker names `null`, `mut`, and `any` are not accepted in `admits`.

### Marker semantics

#### `nullable`

`T admits nullable` permits both nullable and non-null type arguments. Without it, a parameter
admits only non-null arguments. This is an admissibility property, not a type transformation:

- `T` is not itself nullable merely because it admits nullable arguments.
- A nullable occurrence such as `T?` remains nullable.
- Inside the generic body, a value of type `T` is possibly null when `T admits nullable`, so a null
  check must refine it before member access, bound operations, operators, iteration, indexing, or
  passing it to a non-null parameter.
- Inference must reject a nullable argument inferred for a parameter that does not admit nullable
  arguments rather than silently removing nullability.

`nullable` replaces the old `T: nullable` spelling. The marker `null` is rejected because `null`
names a value, not an admissibility property.

#### `mutable`

`T admits mutable` permits mutable-reference type arguments as well as read-only ones. Without it, a
parameter admits only read-only arguments. The marker permits but does not require a mutable
argument, and it does not grant mutation operations to the generic body:

```zeron
fn inspect<T admits mutable>(value: T): T = value;
```

The check applies at the current generic parameter boundary. Whether a nested type such as
`Array<&Widget>` is valid is determined by `Array`’s own parameter policy; an outer parameter does
not recursively scan the argument’s structure. `mutable` does not change variance or make mutable
references safe in covariant positions.

`mutable` replaces the old `mut` marker. The `mut` modifier on declarations and mutable references
is unrelated and unchanged. The project prefers `mutable` for the admissibility marker because
`mut` already appears as a modifier and would read as a capability of the declaration rather than a
property of admissible arguments.

#### Composition and defaults

- `nullable` and `mutable` are independent and may be combined: `T admits nullable + mutable`.
- Without an `admits` clause, a parameter admits non-null, read-only arguments and does not grant
  effect-kind use in `raise` or `raises`.
- An effect marker is exclusive with `nullable` and `mutable`. A nullable occurrence such as `E?`
  can still be written and must be proven non-null before it is raised. A mutable view of an effect
  value normalizes to the nominal effect identity rather than propagating the reference capability.
- At most one effect marker may appear. Duplicate markers and contradictory combinations are
  compile-time errors.
- Admissibility is checked for explicit and inferred arguments, including constructor and
  expected-type inference. No check silently widens an argument.

### Effect markers and responses

ZEP-0118 gives an effect declaration an optional `responds R`. An effect without `responds` is
abortive and responds `Never`. The response is a single exact type and is invariant. The `raises`
row continues to record effect carriers, not responses. This proposal gives that response a place
in generic admissibility.

| Marker | Admits | Generic `raise e` type | Generic `raise` allowed |
| --- | --- | --- | --- |
| `effect` | any non-null effect type | unknown | No |
| `effect<Never>` | abortive effects responding `Never` | `Never` | Yes |
| `effect<R>` | effects responding exactly `R` | `R` | Yes |
| `effect...` | an effect row | no single response | No |
| `effect<*>` | reserved; not accepted | — | No |

#### Bare `effect`

`E admits effect` admits any non-null effect type, regardless of response. It is the general
forwarding marker. It can be used in `raises E`, pass effect values, call functions that raise `E`,
and let a concrete caller instantiate and handle the effect.

A generic body cannot `raise` an `E` value with bare `effect`, because the raise expression would
need a response type and `E` does not provide one. It also cannot use `case E`; that restriction
already exists because the concrete identity is unknown. Bare `effect` therefore supports
forwarding and concrete handling, but not generic raising.

#### `effect<Never>`

`E admits effect<Never>` admits only effects whose response is exactly `Never`, meaning abortive
effects. A raise has type `Never` and is divergent, so statements after it are unreachable. This is
the direct replacement for generic raise code that currently writes `E: effect`:

```zeron
fn relay<E admits effect<Never>>(failure: E) raises E {
    raise failure;
}
```

Before ZEP-0118 lands, every effect is abortive, so `effect<Never>` is enforceable immediately. It
is the migration target for existing generic `raise` sites. If ZEP-0013’s top `Effect` type can
include responding effects later, it is not admitted by `effect<Never>`; it belongs to bare
`effect` unless a future top-effect response rule says otherwise.

#### `effect<R>`

`E admits effect<R>` admits only effects whose response is exactly `R`. A raise has type `R` and may
return, so subsequent statements are reachable. The response is an ordinary value type; it is not
another effect marker or an effect row. It may be `Unit`, a nullable type, or another type
parameter. For example, `effect<Unit>` is the preparation for a handler that resumes with unit, such
as `Yield` or `Log`; `effect<String>` describes an `Ask`-style request.

`effect<R>` is invariant in `R`: `effect<Unit>` does not admit an effect responding `Any`, `Unit?`,
or a supertype of `Unit`. Any conversion happens at the handler or at the raise site, not by
widening the admissibility marker. An abortive effect has response `Never`, not an arbitrary `R`;
it must be admitted with `effect<Never>`, not silently treated as responding with `R`.

This proposal does not introduce a new effect kind. `effect<R>` lowers to the existing effect-kind
membership plus the compiler-owned `Responds<R>` requirement from ZEP-0118. It remains one marker
in the `admits` clause for readability. If ZEP-0118 changes the internal response-bound
representation, the lowering follows that representation; the source meaning fixed here remains
“effect with exactly this response.”

Until ZEP-0118 supplies response metadata, only `Never` is satisfiable because all existing effects
are abortive. A non-`Never` response marker is diagnosed as requiring response-typed effects rather
than being approximated.

#### `effect...`

`effect...` is the effect-row form. It admits an effect set, expands in `raises` lists, and supports
forwarding a row:

```zeron
fn forwardRow<Row admits effect...>(body: () -> Unit raises Row): Unit raises Row = body();
```

A row has no single response type. A generic body can forward the row and handle concrete members
after instantiation, but it cannot `raise` through the row. This preserves ZEP-0118’s rule that a
row-level response bound is not the same as every carrier responding `R`. The row marker is exactly
`effect...`; `effect`, `effect<Never>`, and `effect<R>` describe a single effect parameter, not a
row. A future row response form is a separate design.

#### `effect<*>` and `effect<_>`

`effect<*>` is reserved and rejected. `*` already means a star projection in type arguments;
reusing it for responses would conflate an unknown response with a wildcard and invite covariance.
Bare `effect` already denotes an unknown response, so `effect<*>` has no additive meaning. A
wildcard response such as `effect<_>` is likewise not accepted: a response must be a type or a type
parameter.

#### Runtime and compatibility

Generic raise sites keep the ZEP-0055 runtime effect-kind check: the operand must implement the
compiler-owned effect runtime marker, otherwise an unchecked Java or raw-generic boundary fails
with `ClassCastException`. Response checking is compile-time. No runtime response token is added,
and handler dispatch remains as ZEP-0118 defines it. An unchecked boundary that lies about the
effect identity already escapes the type system and gains no new guarantee here.

An API index written before response metadata has no response field. A bare `effect` marker in such
an index is conservatively read as `effect<Never>` for compatibility, because every effect in that
library is abortive and the legacy marker permitted generic raise. New source written against this proposal
uses bare `effect` for unknown response and must say `effect<Never>` to raise. This keeps old
compiled libraries usable without silently changing their raise behavior or allowing a new
responding effect to be passed to old abortive-only code.

### Anonymous existentials

Anonymous existential arguments use the same separation. The bounds remain before `admits`, and
`reified` is a leading binder capability rather than an admissibility marker:

```text
anonymousExistential = [ "reified" ], ":", [ bound, { "+", bound } ],
                       [ "admits", marker, { "+", marker } ] ;
```

```zeron
Box<: Render admits nullable>
Box<reified: Render admits nullable + mutable>
Box<reified:>
```

`Box<: Render admits nullable>` hides a type that satisfies `Render` and admits nullable arguments.
The `admits` clause describes the hidden argument, not the outer `Box`. A postfix `?` after the
closing `>` continues to mean a nullable outer type. Reification is orthogonal: `Box<reified: ...>`
carries a descriptor exactly as `Box<: ... + reified>` does today.

Migration examples:

| Previous spelling | New spelling |
| --- | --- |
| `Box<: Render + reified>` | `Box<reified: Render>` |
| `Box<: reified>` | `Box<reified:>` |
| `Box<: nullable + reified>` | `Box<reified: admits nullable>` |
| `Box<: Render + nullable + mut>` | `Box<: Render admits nullable + mutable>` |

### Migration

The syntax change is source-incompatible. The canonical rewrites are:

| Previous spelling | New spelling |
| --- | --- |
| `T: nullable` | `T admits nullable` |
| `T: mut` | `T admits mutable` |
| `T: nullable + mut` | `T admits nullable + mutable` |
| `T: B + nullable` | `T: B admits nullable` |
| `T: effect` used only for forwarding | `T admits effect` |
| `T: effect` used in a generic `raise` | `T admits effect<Never>` |
| `T: effect...` | `T admits effect...` |
| `T: reified` | `reified T` |
| `T: B + reified` | `reified T: B` |
| `T: nullable + reified` | `reified T admits nullable` |
| `T: effect + reified` | `reified T admits effect<Never>` or `effect<R>` |
| `Box<: Render + reified>` | `Box<reified: Render>` |

The resolver should diagnose the old spellings with the replacement rather than treating marker
names as ordinary types. The formatter prints the canonical clause order, and the standard library,
examples, tests, and guides need the same audit as the old nullability and mutability migrations.

## Compatibility and impact

This is a source-level breaking change for declarations that use any admissibility marker. The
compiler can provide migration diagnostics and a mechanical formatter; a source-compatible alias is
not planned at this time, and a temporary `mut` alias remains an open question. The `mut`
declaration modifier, `&T` mutable references, and nullability rules are unchanged.

Compiled-library metadata must distinguish ordinary bounds from admissibility markers and must
carry the effect response marker separately from the effect kind. This requires an
`API_INDEX_SCHEMA_VERSION` change for the release cycle that implements the proposal. Old indexes
with a bare `effect` marker are read as `effect<Never>` as described above; old indexes with
`nullable`, `mut`, or `reified` markers keep their historical meaning. New compilers should reject
an old index that cannot express a required response marker rather than guessing.

`STANDARD_LIBRARY_API_VERSION` changes only if public signatures or response metadata change for
the release that ships the feature; the syntax rewrite alone does not change binary descriptors.
No JVM runtime change is required for nullable or mutable admissibility. `effect<Never>` and
`effect<R>` reuse the existing effect-kind runtime marker check and add no runtime response token.
`Responds<R>` remains compiler-provided, has no members, and is not user-implementable under
ZEP-0118.

Java generic declarations keep their current nullable- and mutable-admitting behavior because Java
metadata does not provide reliable Zeron admissibility information. Java methods cannot declare a
Zeron response; imported effects remain abortive unless they are mapped through a Zeron effect.

The response-indexed part is coupled to ZEP-0118 and belongs with the effect-control work.
The syntax-only migration could ship independently if response typing is delayed, but the tracker
does not schedule that split.

## Alternatives

- **Keep markers in the bound list and add `effect<R>` in place** — no new syntax, but preserves
  the exact ambiguity this proposal removes and keeps `reified` looking like an admissibility
  property. Rejected.
- **Use a `where` clause for admissibility** — separates the concepts, but introduces a second
  constraint syntax and a larger grammar change than a single `admits` clause. Rejected for now.
- **Use `null` instead of `nullable`** — shorter, but reads like the null literal and does not
  describe a property of admissible arguments. Rejected.
- **Keep `mut` instead of `mutable`** — concise, but `mut` already modifies declarations and
  receivers, so the marker would read as a capability rather than an argument policy. `mutable` is
  accepted; `mut` remains the declaration modifier.
- **Add an `any` marker for `nullable + mutable`** — defers boilerplate, but collides with `Any`
  and `Any?`, and would need a rule for future markers. Deferred until real boilerplate pressure
  appears; do not auto-expand it.
- **Fold `reified` into `admits`** — treats an ABI capability as an admissibility property.
  Rejected; `reified` becomes a leading modifier.
- **Let bare `effect` keep generic `raise` permission** — preserves old code, but is unsound once
  effects can respond because the raise has no response type. Rejected; bare `effect` is
  forwarding-only and `effect<Never>` is the explicit abortive form.
- **Use `effect<*>` for an unknown response** — conflates a response wildcard with star
  projections and invites covariance. Rejected and reserved.
- **Treat `Never` as satisfying any `effect<R>`** — sound for divergence, but blurs the difference
  between abortive and responding effects and makes handler response selection less explicit.
  Rejected; `effect<R>` is exact.
- **Make effect responses covariant** — would require subtyping and a top response type not
  designed here. Rejected; responses are invariant.

## Implementation and validation

Likely stages:

1. Parse `admits` on type parameters and anonymous existentials; add `mutable`, the leading
   `reified` modifier, and the `effect<R>`/`effect...` marker forms. Update the AST and formatter.
2. Resolve markers as a separate constraint category, enforce exclusivity and defaults, and add
   migration diagnostics for the old bound-position spellings.
3. Implement `effect<Never>` generic raise behavior and reject generic `raise` through bare
   `effect` and `effect...`. Add `effect<R>` response checking when ZEP-0118 supplies response
   metadata.
4. Encode bounds, markers, effect response, and reification separately in the API index; read old
   bare `effect` indexes as `effect<Never>`.
5. Migrate the standard library, examples, tests, guides, and grammar reference.

Validation should cover:

- parsing and formatting of all marker combinations, including `admits` without bounds and
  anonymous existentials;
- rejection of empty `admits`, duplicate markers, `effect<*>`, `effect<_>`, and effect markers
  combined with `nullable` or `mutable`;
- non-null and read-only defaults, nullable and mutable inference, and rejection of silently
  weakened arguments;
- generic `raise` through `effect<Never>` and `effect<R>`, rejection through bare `effect` and
  `effect...`, and exact response substitution;
- `effect<Unit>`/`effect<String>` handler behavior once ZEP-0118 is implemented;
- `reified` leading syntax, including `reified T: B admits nullable`, and unchanged descriptor
  behavior;
- anonymous existential bounds, markers, reification, and postfix `?`;
- API-index round trips, old-index reading, and separate compilation;
- unchanged Java interop and unchanged `mut` declaration behavior;
- migration of the standard library and all existing marker tests.

## Open questions

- Is `effect<Never>` the final abortive spelling, or should it be `effect<!>` or another concise
  form?
- Should `effect<R>` be available as soon as ZEP-0118’s response metadata lands, or should the
  syntax ship first and stay diagnosed until handlers are implemented?
- Is `mutable` acceptable in length, or is a `mut` alias needed during migration?
- Should `admits` eventually support an `any` shorthand for `nullable + mutable`? This proposal
  deliberately leaves it out.
- Does `Box<reified:>` read well enough for an unbounded reified existential, or should the
  unbounded form use a different spelling?
- Should a future row response marker be spelled `effect<Row, R>` or remain a separate constraint?
- Does ZEP-0013’s top `Effect` type remain abortive, or does it need a separate unknown-response
  admissibility rule once responding effects exist?
- Should bare `effect` ever become an alias for `effect<Never>`, or remain permanently
  forwarding-only?

## Decision

Draft. No disposition recorded. This proposal is the replacement home for admissibility-marker
syntax: it supersedes [ZEP-0010](./ZEP-0010.md), [ZEP-0055](./ZEP-0055.md), and
[ZEP-0062](./ZEP-0062.md) on their marker surfaces, and proposes a syntax amendment to
[ZEP-0015](./ZEP-0015.md), [ZEP-0104](./ZEP-0104.md), and [ZEP-0105](./ZEP-0105.md). Acceptance and
implementation remain pending.
