# ZEP-0123: Admissibility Clauses and Leading Reification

## Abstract

Introduce a dedicated `admits` clause for generic admissibility markers so that “which type
arguments may be substituted” is visibly separate from “which operations are available.” Canonical
markers are `nullable`, `mutable`, `effect`, and `effect...`. A bare `effect` admits any non-null
effect type; it does not imply a response. Response constraints are not admissibility markers and
remain [ZEP-0118](./ZEP-0118.md)’s compiler-provided `Responds<R>` bound.

Move `reified` out of the marker list and make it a leading capability modifier: `reified T` on a
type parameter and `reified _` on an anonymous existential. On acceptance, this proposal supersedes
the marker syntax and semantics of ZEP-0010, ZEP-0055, and ZEP-0062 on their marker surfaces, while
carrying forward their underlying nullability, mutability, effect-kind, and runtime-check rules.

## Motivation

Generic declarations currently write admissibility markers in the same list as contract bounds:

```zeron
fn old<T: Display<T> + nullable + mut, E: effect>(value: T): E = ...;
```

That makes three different questions look identical:

- Which operations does the generic body have? (`Display<T>`)
- Which type arguments may be substituted? (`nullable`, `mut`, `effect`)
- Which runtime or ABI capability does the declaration require? (`reified`)

The ambiguity is clearest in `reified`, which is not an admissibility property at all: it adds a
hidden descriptor parameter. A dedicated clause makes that boundary explicit and leaves ordinary
bounds to describe operations.

Response typing does not need to join the marker list. ZEP-0118 already gives an effect declaration
an optional `responds R` and defines the compiler-provided `Responds<R>` bound. That bound describes
what a handler must return; it is not a property of which type arguments a parameter accepts. Keeping
`Responds<R>` in the bound list avoids two spellings for one concept and avoids overloading
`effect<...>` with a meaning that is not an effect type application.

The mutable marker also reads better as `mutable`. `mut` already modifies declarations and
receivers, so `T: mut` looks like a capability of `T` rather than a statement that the parameter
admits mutable-reference arguments.

## Goals

- Add `admits` as a distinct grammatical slot after ordinary contract bounds.
- Define the canonical marker set: `nullable`, `mutable`, `effect`, and `effect...`.
- Keep safe defaults: non-null, read-only, and no effect-kind use unless explicitly admitted.
- Keep `effect` as an effect-kind marker with no implied response.
- Keep response constraints in `Responds<R>`; do not add response-indexed effect markers.
- Rename the mutable admissibility marker from `mut` to `mutable`, while leaving the `mut`
  declaration modifier unchanged.
- Move `reified` out of the marker list into a leading capability modifier.
- Give reified anonymous existentials a readable binder form.
- Preserve compiled-library compatibility for existing admissibility markers.
- Supersede the admissibility-marker framework in ZEP-0010, ZEP-0055, and ZEP-0062 on acceptance.

## Non-goals

- Adding `effect<Never>`, `effect<R>`, `effect<*>`, or any other response-indexed marker.
- Implementing or changing `responds R`, `Responds<R>`, generic responding `perform`, or response
  inference; those remain ZEP-0118 and follow-up response-typing work.
- General effect subtyping or a denotable top effect type; those remain
  [ZEP-0013](./ZEP-0013.md).
- Row-level response polymorphism or a constraint that every carrier in a row responds `R`.
- An `any` admissibility shorthand for combined `nullable + mutable`.
- Changing nullability, mutability, effect runtime representation, or handler dispatch semantics.
- Changing variance, higher-kinded constructor admissibility, or Java interop behavior.
- Redesigning the `reified` descriptor facility; only its source spelling changes.
- Renaming the `mut` modifier on functions, receivers, fields, or mutable references.
- Named existential binders. The reified form uses `_` and remains anonymous.

## Proposal

### Surface syntax

`admits` is a new clause after the ordinary bound list. It is separate from `:` so that bounds and
admissibility markers cannot be confused:

```text
typeParameter = [ "out" ], [ "reified" ], IDENTIFIER, [ "<", "_", ">" ],
                [ ":", bound, { "+", bound } ],
                [ "admits", marker, { "+", marker } ] ;
bound  = type ;
marker = "nullable" | "mutable" | effectMarker ;
effectMarker = "effect", [ "..." ] ;

anonymousExistential = [ "reified", "_" ], ":",
                       [ bound, { "+", bound } ],
                       [ "admits", marker, { "+", marker } ] ;
```

`admits` is a contextual keyword in this position and remains an ordinary identifier elsewhere. An
`admits` clause must contain at least one marker. Markers are order-insensitive; the formatter prints
`nullable` before `mutable` and at most one effect marker. A parameter may omit both the bound list
and the `admits` clause. `admits` is available wherever admissibility markers are currently
permitted: generic functions, methods, classes, contracts, data classes, extensions, and witnesses,
subject to the existing reification and higher-kinded restrictions.

Examples:

```zeron
fn doSomething<
    T: A<*> admits nullable + mutable,
    E: B + C admits effect,
    Row admits effect...
>(...): ... { ... }

fn identity<T admits nullable>(value: T): T = value;

fn forwardRef<T admits mutable>(value: T): T = value;

fn render<T: Display<T> admits nullable>(value: T): T = value;
```

The `:` list remains the constraint slot for ordinary contract/type bounds and ZEP-0118’s
`Responds<R>` response bound. The `admits` list never provides operations, and a contract bound
never grants admissibility.

### Bounds, capabilities, and admissibility

Four concepts are now written separately:

| Concept | Position | Example | Meaning |
| --- | --- | --- | --- |
| Contract or type bound | after `:` | `T: Display<T> + Inspect<T>` | Operations and conformance available in the body |
| Response bound | after `:` | `E: Responds<R>` | The handler response required by ZEP-0118 |
| Admissibility marker | after `admits` | `T admits nullable + mutable` | Which type arguments may be substituted |
| Capability modifier | leading | `reified T` | Additional hidden ABI input, such as a runtime descriptor |

`reified` is not an admissibility marker. It states that the callee receives a runtime applied-type
descriptor and is restricted to callable type parameters by ZEP-0015. It composes with `admits`:

```zeron
fn describe<reified T: Render admits nullable>(value: T): String { ... }
```

`out` remains a class/contract variance annotation. `out` and `reified` do not combine, because
variance applies to class/contract parameters while reification applies to callable parameters.

Higher-kinded constructor parameters such as `F<_>` do not take `admits` in this proposal;
first-order admissibility does not describe a constructor’s own argument policy. Effect-row
parameters are first-order and use `admits effect...`.

The old bound-position spellings are rejected with a migration diagnostic: `T: nullable`, `T: mut`,
and `T: reified` must be rewritten as `T admits nullable`, `T admits mutable`, and `reified T`
respectively. `T: effect` becomes `T admits effect`, or `T admits effect...` when it denotes a row.
A generic `perform` through a single effect parameter also needs the response bound described below.
The marker names `null`, `mut`, and `any` are not accepted in `admits`.

### Marker semantics

#### `nullable`

`T admits nullable` permits both nullable and non-null type arguments. Without it, a parameter
admits only non-null arguments. This is an admissibility property, not a type transformation:

- `T` is not itself nullable merely because it admits nullable arguments.
- A nullable occurrence such as `T?` remains nullable.
- Inside the generic body, a value of type `T` is possibly null when `T admits nullable`, so a null
  check must refine it before member access, bound operations, operators, iteration, indexing, or
  passing it to a non-null parameter.
- Inference must reject a nullable argument inferred for a parameter that does not admit nullable
  arguments rather than silently removing nullability.

`nullable` replaces the old `T: nullable` spelling. The marker `null` is rejected because `null`
names a value, not an admissibility property.

#### `mutable`

`T admits mutable` permits mutable-reference type arguments as well as read-only ones. Without it, a
parameter admits only read-only arguments. The marker permits but does not require a mutable
argument, and it does not grant mutation operations to the generic body:

```zeron
fn inspect<T admits mutable>(value: T): T = value;
```

The check applies at the current generic parameter boundary. Whether a nested type such as
`Array<&Widget>` is valid is determined by `Array`’s own parameter policy; an outer parameter does
not recursively scan the argument’s structure. `mutable` does not change variance or make mutable
references safe in covariant positions.

`mutable` replaces the old `mut` marker. The `mut` modifier on declarations and mutable references
is unrelated and unchanged. The project prefers `mutable` for the admissibility marker because
`mut` already appears as a modifier and would read as a capability of the declaration rather than a
property of admissible arguments.

#### Composition and defaults

- `nullable` and `mutable` are independent and may be combined: `T admits nullable + mutable`.
- Without an `admits` clause, a parameter admits non-null, read-only arguments and does not grant
  effect-kind use in `perform` or `performs`.
- An effect marker is exclusive with `nullable` and `mutable`. A nullable occurrence such as `E?`
  can still be written and must be proven non-null before it is raised. A mutable view of an effect
  value normalizes to the nominal effect identity rather than propagating the reference capability.
- At most one effect marker may appear. Duplicate markers and contradictory combinations are
  compile-time errors.
- Admissibility is checked for explicit and inferred arguments, including constructor and
  expected-type inference. No check silently widens an argument.

### Effect markers and responses

ZEP-0118 gives an effect declaration an optional `responds R`. An effect without `responds` is
abortive and responds `Never`. The response is a single exact type and is invariant. The
`performs` row continues to record effect carriers, not responses.

This proposal separates the effect kind from the response constraint:

| Marker | Admits | Generic `perform e` type | Response bound required |
| --- | --- | --- | --- |
| `effect` | any non-null effect type | no response implied | Yes, for a generic `perform` |
| `effect...` | an effect row | no single response | Row `perform` remains unsupported |

Bare `effect` is the effect-kind marker. It can be used in `performs E`, pass effect values, call
functions that perform `E`, and let a concrete caller instantiate and handle the effect. It says
nothing about what a handler returns.

A generic body that performs a single effect parameter must also bound its response with ZEP-0118’s
compiler-provided `Responds<R>`:

```zeron
fn relay<E: Responds<Never> admits effect>(failure: E) performs E {
    perform failure;
}
```

`Responds<Never>` is the abortive case. A responding effect substitutes the ordinary response type:

```zeron
fn withAnswer<R, E: Responds<R> admits effect>(
    body: () -> Unit performs E,
    answer: R
): Unit performs E = ...;
```

`Responds<R>` stays in the `:` list because it is a response constraint, not a type-argument
admissibility rule. It is invariant in `R`, has no members, cannot be implemented explicitly, and
is derived from the effect’s `responds` declaration. The response type must be in scope before the
parameter that names it, so `R` precedes `E` in the example.

A row has no single response type. A generic body can forward `effect...` and handle concrete
members after instantiation, but it cannot `perform` through the row. A row-level response bound is a
separate design.

### Anonymous existentials and reified binders

Reified anonymous existentials use an explicit anonymous binder, `_`, so that the capability is
visibly attached to a binder rather than to the hidden type’s bound list:

```zeron
Box<: Render admits nullable>
Box<: admits nullable>
Box<reified _: Render admits nullable>
Box<reified _:>
```

- `Box<: Render admits nullable>` hides a type that satisfies `Render` and admits nullable
  arguments. No descriptor is carried.
- `Box<reified _: Render admits nullable>` hides a type that satisfies `Render`, admits nullable
  arguments, and carries a runtime descriptor.
- `Box<reified _:>` is the descriptor-only form with no bounds or markers.
- `_` is an anonymous binder placeholder, not a type argument or a referable name. It follows the
  same “unnamed binder” convention as `case _` and `Foo(_, value)`, and mirrors the position of a
  type-parameter name in `reified T`. The HKT `F<_>` remains a distinct arity-slot use, not a
  binder; the preceding `reified` and following `:` select the existential binder production.
- The `admits` clause still describes the hidden argument, not the outer `Box`.
- A postfix `?` after the closing `>` continues to mean a nullable outer type.
- `Box<reified: Render>` and `Box<reified:>` are rejected. `reified` is not a naked prefix before
  the existential colon; it introduces the anonymous binder `_`.

Reification is orthogonal to admissibility and bounds. `Box<reified _: ...>` carries a descriptor
exactly as `Box<: ... + reified>` does today. The descriptor representation, lifetime, and hidden
parameter behavior do not change.

Migration examples:

| Previous spelling | New spelling |
| --- | --- |
| `Box<: Render + reified>` | `Box<reified _: Render>` |
| `Box<: reified>` | `Box<reified _:>` |
| `Box<: nullable + reified>` | `Box<reified _: admits nullable>` |
| `Box<: Render + nullable + mut>` | `Box<: Render admits nullable + mutable>` |
| `Box<: Render + reified + nullable>` | `Box<reified _: Render admits nullable>` |

### Migration

The syntax change is source-incompatible. The canonical rewrites are:

| Previous spelling | New spelling |
| --- | --- |
| `T: nullable` | `T admits nullable` |
| `T: mut` | `T admits mutable` |
| `T: nullable + mut` | `T admits nullable + mutable` |
| `T: B + nullable` | `T: B admits nullable` |
| `T: effect` used only for forwarding | `T admits effect` |
| `T: effect` used in a generic `raise` | `T: Responds<Never> admits effect` |
| `T: effect + Responds<R>` | `T: Responds<R> admits effect` |
| `T: effect...` | `T admits effect...` |
| `T: reified` | `reified T` |
| `T: B + reified` | `reified T: B` |
| `T: nullable + reified` | `reified T admits nullable` |
| `T: effect + reified` used only for forwarding | `reified T admits effect` |
| `T: effect + reified` used in a generic `raise` | `reified T: Responds<Never> admits effect` |
| `Box<: Render + reified>` | `Box<reified _: Render>` |
| `Box<: reified>` | `Box<reified _:>` |
| `Box<: nullable + reified>` | `Box<reified _: admits nullable>` |
| `Box<: Render + nullable + mut>` | `Box<: Render admits nullable + mutable>` |

The resolver should diagnose the old spellings with the replacement rather than treating marker
names as ordinary types. The formatter prints the canonical clause order, and the standard library,
examples, tests, and guides need the same audit as the old nullability and mutability migrations.

## Compatibility and impact

This is a source-level breaking change for declarations that use any admissibility marker. The
compiler can provide migration diagnostics and a mechanical formatter; a source-compatible alias is
not planned at this time. The `mut` declaration modifier, `&T` mutable references, and nullability
rules are unchanged.

The syntax-only change does not require an `API_INDEX_SCHEMA_VERSION` bump. The current index
already stores ordinary bounds separately from the nullable, effect-kind, effect-row, mutable, and
reified flags. Moving where those markers are parsed does not change the wire metadata. A temporary
implementation that stores markers in a new AST field only needs to preserve that serialization.

Response constraints are unchanged. `Responds<R>` remains a bound and is serialized as one, so this
proposal adds no response field and no response-indexed marker. The response metadata added by
ZEP-0118 for effect declarations is separate and untouched. Migrating a generic `perform` site to
`T: Responds<Never>` or `T: Responds<R>` assumes that `Responds<R>` is available as a writable
bound. If it is not yet implemented, the marker and reification syntax can land first while those
perform sites keep their current spelling until the response-bound work lands; the syntax change does
not implement that bound itself.

`STANDARD_LIBRARY_API_VERSION` does not change solely because of the syntax rewrite: public
signatures and binary descriptors keep the same meaning. The standard library source still needs
migration, but its exported API does not change.

No JVM runtime change is required for nullable or mutable admissibility. Generic perform sites keep
the ZEP-0055 runtime effect-kind check. Response checking remains compile-time and is not part of
this proposal.

Java generic declarations keep their current nullable- and mutable-admitting behavior because Java
metadata does not provide reliable Zeron admissibility information. Java methods cannot declare a
Zeron response; imported effects remain abortive unless they are mapped through a Zeron effect.

## Alternatives

- **Keep markers in the bound list and add only `reified T`** — fixes the worst confusion with
  minimal churn, but leaves admissibility markers looking like contract bounds and does not give
  future markers such as `scoped` a clean home. Rejected as the long-term shape.
- **Use a `where` clause for admissibility** — separates the concepts, but introduces a second
  constraint syntax and a larger grammar change than a single `admits` clause. Rejected for now.
- **Use `null` instead of `nullable`** — shorter, but reads like the null literal and does not
  describe a property of admissible arguments. Rejected.
- **Keep `mut` instead of `mutable`** — concise, but `mut` already modifies declarations and
  receivers, so the marker would read as a capability rather than an argument policy. `mutable` is
  accepted; `mut` remains the declaration modifier.
- **Add an `any` marker for `nullable + mutable`** — defers boilerplate, but collides with `Any`
  and `Any?`, and would need a rule for future markers. Deferred until real boilerplate pressure
  appears; do not auto-expand it.
- **Add `effect<Never>` / `effect<R>` response markers** — rejected. They overload effect-type
  application with a response meaning, duplicate ZEP-0118’s `Responds<R>`, and would require
  generic response bounds and inference that are not part of this syntax change. `Responds<R>` is
  the single response spelling.
- **Keep `reified` in the existential bound list** — preserves `Box<: Render + reified>` but leaves
  an ABI capability looking like an admissibility or contract property. The `reified _:` binder
  form is clearer and mirrors `reified T`.
- **Use `Box<reified: Render>`** — compact, but `reified:` reads as a unit and `Box<reified:>` is
  too cryptic. Rejected in favor of an explicit anonymous binder.
- **Allow a named existential binder such as `Box<reified T: Render>`** — closer to declarations,
  but names a hidden type that the source cannot reference and expands the existential surface.
  Deferred; `_` is the only binder placeholder in this proposal.

## Implementation and validation

Likely stages:

1. Parse `admits` on type parameters and anonymous existentials; add `mutable`, the leading
   `reified` modifier, and the `reified _:` anonymous binder. Update the AST and formatter.
2. Resolve markers as a separate constraint category, enforce exclusivity and defaults, and add
   migration diagnostics for the old bound-position spellings.
3. Keep `Responds<R>` in the ordinary bound list. Do not add response-indexed markers or change
   generic response typing here.
4. Preserve the existing API-index encoding; verify that bounds and marker flags still round-trip
   without a schema bump.
5. Migrate the standard library, examples, tests, guides, grammar reference, highlighter, and LSP
   surfaces.

Validation should cover:

- parsing and formatting of all marker combinations, including `admits` without bounds, multiple
  parameters, and anonymous existentials;
- rejection of empty `admits`, duplicate markers, and effect markers combined with `nullable` or
  `mutable`;
- non-null and read-only defaults, nullable and mutable inference, and rejection of silently
  weakened arguments;
- leading `reified` with and without bounds and markers, and rejection of `out` plus `reified`;
- `Box<reified _: ...>` and `Box<reified _:>` parsing, descriptor behavior, and rejection of
  `Box<reified: ...>`;
- `effect` forwarding and generic `perform` with `Responds<Never>`/`Responds<R>`, without adding an
  effect response marker;
- API-index round trips and separate compilation with no schema change;
- unchanged Java interop and unchanged `mut` declaration behavior;
- migration of the standard library and all existing marker tests.

## Open questions

- Is `Box<reified _: Render>` the right existential spelling, or should the anonymous binder be
  omitted in favor of a different qualifier position?
- Should a non-reified anonymous existential with only markers be written `Box<: admits nullable>`,
  or should `admits` be allowed without the existential colon when there are no bounds?
- Is `mutable` acceptable in length, or is a temporary `mut` alias needed during migration?
- Should `admits` be reserved, or remain contextual as proposed?
- Should `Responds<R>` ever become an `admits` marker, or remain an ordinary bound permanently?
- Should a future row response marker be a separate constraint, rather than a form of `admits`?

## Decision

Implemented for `0.9.0`. This proposal is the replacement home for admissibility-marker syntax: it
supersedes [ZEP-0010](./ZEP-0010.md), [ZEP-0055](./ZEP-0055.md), and [ZEP-0062](./ZEP-0062.md) on
their marker surfaces, and amends [ZEP-0015](./ZEP-0015.md), [ZEP-0104](./ZEP-0104.md), and
[ZEP-0105](./ZEP-0105.md). Legacy marker spellings now produce migration diagnostics. Response
constraints remain ZEP-0118’s `Responds<R>` and are not part of this proposal. Release state is
tracked in [ZEP.md](./ZEP.md).
