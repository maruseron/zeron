## Abstract

Allow a class that names a contract in its `is` clause to satisfy that contract's `static`
requirements nominally. A public class-scoped `static fn` can implement a static requirement
directly; a `static fn` entry in a matching `implementation` block can do so when the requirement
depends on the class's own type parameters or should not become an ordinary companion function. The
current rule that contracts with static requirements are witness-only is removed. Witnesses remain
the implementation path for non-nominal targets and for types whose declarations cannot be changed.

## Motivation

Zeron contracts currently occupy a middle ground between interfaces and type classes. First-order
contracts can declare polymorphic `static` methods, which are type-position operations: they are
dispatched through evidence and are not associated with a value receiver. This is useful for
conversion, construction, and other operations that logically belong to the type rather than an
instance, as in `Numeric<T>.fromInteger`.

The implementation path is asymmetric, however. A class can satisfy instance requirements with
ordinary members, but a contract with any static requirement, including one inherited through
`requires`, cannot be claimed with `is` at all. It must be implemented by a witness:

```zeron
contract Numeric<T> {
    static fromInteger(value: Integer): T;
    plus(this: T, other: T): T;
}

class Vector is Numeric<Vector> {
    public constructor new;
    public plus(other: Vector): Vector = ...;
}

witness Numeric<Vector> for Vector {
    static fn fromInteger(value: Integer): Vector = ...;
}
```

This splits one conformance across two declarations. The class header supplies instance behavior and
the witness supplies type behavior. It also changes how the conformance is discovered: nominal
conformance travels with the class, while the witness is import-scoped. The split is especially
awkward when the class and contract are owned by the same program and the only reason for the
witness is the presence of a static requirement.

That restriction is historical. Classes originally had no static-member form, so a class had nowhere
to put a static implementation. [ZEP-0072](./ZEP-0072.md) added class-scoped `static fn` declarations,
and [ZEP-0076](./ZEP-0076.md) explicitly deferred "delegating static requirements through companion
types" because that surface did not exist yet. This proposal revisits the rule now that it does.

A second gap remains even with companion functions. A class `static fn` cannot capture the class's
type parameters, because it is a namespace function on the type name. A generic class can still
conform to a contract whose static requirement mentions those parameters:

```zeron
class Vector2<T: Numeric<T>> is Numeric<Vector2<T>> {
    public constructor new;
    public plus(other: Vector2<T>): Vector2<T> = ...;
}
```

Here `Numeric<Vector2<T>>.fromInteger` returns `Vector2<T>`, so an implementation must be able to
name `T`. A companion function cannot, but a class-local implementation block can. Extending
`implementation` blocks to first-order contracts supplies that missing surface without making class
static functions more magical.

## Goals

- Permit `is` conformance for contracts with static requirements, including requirements inherited
  through `requires`.
- Satisfy static requirements with public class-scoped `static fn` declarations when their signatures
  are expressible without capturing class type parameters.
- Extend class `implementation` blocks to first-order contracts, initially for `static fn` entries
  that need class type parameters or explicit placement.
- Preserve contract static defaults, including static defaults inherited through contract composition.
- Keep nominal conformance authoritative: one declaration supplies the contract's evidence, and a
  witness cannot replace or override it.
- Keep witnesses for non-nominal targets, external types, intrinsic evidence, and canonical defaults.
- Produce per-requirement diagnostics and quick fixes instead of the blanket witness-only error.

## Non-goals

- Making HKT implementation blocks optional; that is [ZEP-0125](./ZEP-0125.md).
- Changing the declaration or dispatch semantics of static contract methods.
- Adding static properties, static fields, or a general JVM static-member model.
- Using Java static methods or other external static members as nominal evidence.
- Generalizing `implementation` blocks to instance requirements, mutating requirements, or arbitrary
  forwarding. First-order blocks in this proposal carry static entries only.
- Letting a named constructor implicitly satisfy a same-named static requirement.
- Conditional conformances or refined class conformance based on additional bounds.
- Inferring conformance from the presence of matching class members. The `is` clause remains the
  explicit claim.

## Proposal

### Two requirement positions

A contract requirement has a position determined by whether it has a receiver:

| Position | Requirement forms | Nominal implementation surface |
| --- | --- | --- |
| value | instance method, property, receiver-marked HKT operation | public instance member |
| type | `static` contract method, receiverless HKT operation | public class `static fn`, or an `implementation` static entry |

This proposal concerns type-position requirements on first-order contracts. The instance half of a
contract keeps its current nominal rules: public instance members satisfy the requirements, and
defaults are used where no member overrides them.

### Class static functions as evidence

A public class-scoped `static fn` declared directly on the conforming class can satisfy a static
requirement. The requirement is substituted with the applied contract arguments and matched against
the companion function by name and signature using the existing method-compatibility rules,
including method type parameters up to renaming, parameter types, variadic shape, effects, and
covariant returns.

```zeron
contract Numeric<T> {
    static fromInteger(value: Integer): T;
    plus(this: T, other: T): T;
}

class Vector is Numeric<Vector> {
    public constructor new;

    public static fn fromInteger(value: Integer): Vector =
        Vector.new(...);

    public plus(other: Vector): Vector = ...;
}
```

`Vector.fromInteger` remains an ordinary companion namespace function. It can be called directly as
before, and it also supplies static evidence for `Numeric<Vector>`. The two uses do not create a new
runtime entry point or a JVM static-dispatch guarantee.

Only public static functions are candidates. Private companion functions remain ordinary helpers and
do not become contract evidence. A static requirement cannot be satisfied by an instance method, and
an instance requirement cannot be satisfied by a static function.

### Generic classes and implementation blocks

A class static function cannot refer to the class's type parameters. If a substituted static
requirement mentions one, the class needs an `implementation` block:

```zeron
class Vector2<T: Numeric<T>> is Numeric<Vector2<T>> {
    public constructor new;

    public plus(other: Vector2<T>): Vector2<T> = ...;

    implementation Numeric<Vector2<T>> {
        static fn fromInteger(value: Integer): Vector2<T> =
            Vector2<T>.new(...);
    }
}
```

The block must correspond to a direct header conformance. Like an HKT block, it may implement
requirements inherited by that contract through `requires`; the block's contract name identifies the
conformance claim, not the declaring contract of every entry. It is evaluated in the class's scope,
so its static entries may name the class's type parameters and may use the class's constructors,
static functions, and other accessible members. It is not an ordinary member scope: the entry does
not add a second instance method or a declarative static function to the class name. It lowers to a
static helper inside the implementing class, like an HKT implementation entry.

The initial grammar generalizes the existing implementation production to distinguish static entries:

```text
implementationDecl = [ "delegating" ], "implementation", contractUse, "{",
                     { implementationMethod }, "}" ;
implementationMethod = [ "static" ] "fn", memberName, [ typeParameters ],
                       "(", methodParameters, ")", ":", type, [ raisesClause ],
                       ( "=", expression, ";" | block ) ;
```

For an HKT contract, entries remain `fn` operations with an optional explicit receiver, as today.
For a first-order contract, entries are `static fn`; instance requirements continue to be satisfied
by ordinary public class members. `delegating` retains its HKT meaning in this proposal and has no
additional effect on a first-order block.

An explicit static entry takes precedence over a class static function and over a contract default.
Duplicate entries for the same requirement are declaration errors. An explicit entry is validated
even when invalid; the compiler reports its error rather than silently falling back to another
surface.

### Defaults and composition

If neither an explicit block entry nor a class static function supplies a static requirement, the
contract's static default is used. This applies to defaults declared directly on the contract and to
defaults inherited through `requires`. An explicit implementation always overrides a compatible
default.

Static requirements inherited through `requires` are validated transitively. A class may satisfy an
inherited static requirement with its own static function or block entry; it may also rely on an
inherited static default. The blanket prohibition is removed for the whole transitive surface, not
only for directly declared members.

### Evidence selection and runtime

Static requirement evidence is a `MethodHandle` to the companion function or block helper. Evidence
selection must handle a static requirement before the nominal interface-projection path: instance
requirements continue to use interface dispatch, while static requirements use static evidence.
There is no new runtime representation, dictionary object, or vtable entry.

Calling `T.fromInteger(...)` through a contract bound continues to dispatch through the hidden
evidence slot. Calling `Vector.fromInteger(...)` directly continues to use ordinary companion
namespace lookup. Both resolve to the same implementation without making static contract methods
ordinary namespace functions.

### Coherence and conformance authority

A class header conformance remains the single source of the class's contract evidence, including its
static requirements. A witness cannot claim the same applied contract for the same target type, and
a witness cannot override or supplement a nominally conforming class's static requirements. This is
the same authority rule that already applies to instance requirements.

Each applied contract may appear once in the class header; each implementation block must match one
header conformance; an implementation block without a matching header conformance remains an error.
Existing class static-function collision rules continue to apply: a static function cannot share a
name with an instance member or an applicable extension member. If a contract requires both a static
and an instance member with the same name, a block entry supplies the static half while the instance
member supplies the value half.

### Diagnostics

The current blanket diagnostic is replaced with requirement-specific errors:

- missing static implementation for `Contract.method` with a fix to add `static fn` or an
  `implementation` block;
- static requirement depends on class type parameter `T` and cannot be supplied by a companion
  function; use an implementation block;
- implementation block does not match a class-header conformance;
- duplicate implementation entry for a requirement;
- explicit entry has the wrong static/instance shape or an incompatible signature;
- witness attempts to claim a contract already implemented nominally.

## Compatibility and impact

Programs that keep static-requiring contracts witness-only continue to work. Programs that previously
received the blanket "must be implemented through a witness" error for `is` become valid when a
matching companion function or block entry is present. The change is source-compatible in the
additive direction, but it deliberately removes an error, so compiler tests and documentation that
assert the old diagnostic must change.

There is no runtime ABI change for existing code. Class static functions already lower to companion
namespace functions and are already exported for separately compiled clients. Block static helpers
need owner-attached implementation metadata analogous to HKT implementation helpers. Consumers can
either re-run the deterministic static matching from the exported class and contract declarations, or
read a resolved implementation mapping if the API index is extended. That choice determines whether
an API-index schema bump is needed; it should be settled during implementation rather than by
assuming a schema change.

Documentation changes are user-facing: [guide/20-generic-bounds-and-witnesses.md](../../guide/20-generic-bounds-and-witnesses.md)
must describe nominal static implementation and narrow the witness-only rule to non-nominal targets.
The contracts and higher-kinded guides should cross-reference the two implementation surfaces.

## Alternatives

- **Keep static requirements witness-only.** This preserves one simple rule but leaves the split
  conformance, import-scope asymmetry, and unnecessary witness boilerplate. Rejected because the
  historical reason no longer applies.
- **Allow only class static functions, with no first-order implementation blocks.** This covers
  non-generic classes and requirements that do not mention class type parameters, but cannot express
  generic-class statics. Rejected as incomplete.
- **Allow only implementation blocks, with no companion-function matching.** This is uniform with
  HKT blocks but makes the common non-generic case noisier than necessary and ignores the natural
  companion surface created by ZEP-0072.
- **Allow a class-scoped `witness` instead.** This would preserve witness semantics and placement but
  does not make the conformance nominal, still splits evidence authority, and duplicates the block
  mechanism that already exists.
- **Treat named constructors as static evidence.** This is convenient for numeric newtypes but
  conflates construction with arbitrary type-level operations and adds an implicit matching rule.
  Deferred.
- **Generalize implementation blocks to all instance requirements now.** This would create a second
  place to declare ordinary instance behavior and interacts with mutability, properties, and
  delegation. Out of scope; the block is introduced for type-position requirements first.
- **Allow a more general generic static function to be instantiated for class type parameters.**
  This could remove some blocks but makes conformance matching depend on polymorphic instantiation
  and class bounds. Deferred as an open question.

## Implementation and validation

Likely implementation stages:

1. Remove the blanket `is` rejection for contracts with static requirements.
2. Add static-requirement matching against public class static functions after contract substitution.
3. Generalize implementation blocks to first-order contracts and parse `static fn` entries.
4. Validate blocks, defaults, composition, duplicate entries, and visibility; lower block entries to
   static helpers.
5. Select static evidence before nominal interface projection and preserve instance behavior.
6. Export block static metadata for separate compilation, or document the deterministic re-match path.
7. Add diagnostics and LSP quick fixes for missing or mis-shaped static implementations.

Validation should cover:

- non-generic nominal statics through class static functions;
- generic-class statics through `implementation` blocks, including class type-parameter references;
- static defaults and statics inherited through `requires`;
- contracts with both static and instance requirements;
- duplicate, misplaced, private, instance-shaped, and incompatible entries;
- witness rejection for a nominally conforming contract/type pair;
- separate-compilation clients and API-index round trips;
- formatter, highlighter, hover, and quick-fix behavior for the generalized block and `static fn`
  entries.

Run focused resolver, emitter, and API-index tests during development and the full `mvn test` suite
before completion. Remove `dist/` before compiling generated Zeron programs so stale classes do not
mask changes.

## Open questions

- Should a generic class static function that is more polymorphic than the requirement be allowed to
  instantiate its method type parameters to the class's type parameters, or should that case always
  require a block? This proposal takes the conservative position: use a block.
- Should separately compiled consumers re-run static matching, or should the API index export a
  resolved static implementation mapping? The latter is simpler for consumers but may require a
  schema bump.
- Should a static-only witness be permitted alongside a nominal instance conformance? This proposal
  says no: one declaration supplies the whole contract's evidence, including static requirements.
- Should non-public class static functions be candidates when the class itself is not public? The
  initial rule is no; all contract requirements are public by definition.
