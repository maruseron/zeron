# ZEP-0125: Optional Higher-Kinded Implementation Blocks

## Abstract

Make a class's higher-kinded `implementation` block optional. A class header such as
`class Box<T> is Mapper<Box<_>>` declares conformance by itself; when no block is present, the
compiler satisfies receiver-marked operations with public instance methods and receiverless
operations with public class-scoped static functions. An explicit block remains available as an
override and as the implementation surface for operations that should not become ordinary members.
This makes HKT conformance share the same "header declares conformance, members supply
implementation" model that first-order nominal conformance already uses.

## Motivation

HKT conformance currently requires two declarations even when the class already has everything the
contract needs:

```zeron
class Box<T: mut> is Mapper<Box<_>> {
    value: T;
    public constructor new;

    public map<R: mut>(transform: (T) -> R): Box<R> =
        Box<R>.new(transform(this.value));

    delegating implementation Mapper<Box<_>> {}
}
```

The block exists only to say "use the method I already wrote." [ZEP-0077](./ZEP-0077.md) softened the
duplication by letting `delegating implementation` forward to class members, but still requires the
empty block. The result is clunky and inconsistent with first-order conformance, where an `is`
clause plus matching public members is sufficient:

```zeron
class IntList is Sink<Int> {
    public constructor new;
    public mut add(value: Int): Unit { }
}
```

The mandatory block reflects an implementation boundary from the original HKT design: an
implementation block is deliberately not an ordinary member scope, so HKT helpers do not become
additional virtual methods. That boundary is still valuable for explicit implementations and for
operations that need private state or a different shape. It is not valuable when the block is empty
and the class members already express exactly the required operations.

The current rule also forces authors to choose between two equivalent implementation spellings—write
a block with forwarding bodies or write `delegating implementation ... {}`—or else leave the
conformance undeclared. Removing the mandatory block leaves one obvious default and keeps the block
for the cases where it earns its keep.

## Goals

- Permit an HKT conformance with no implementation block.
- Satisfy receiver-marked operations with public instance methods on the conforming class using the
  existing delegation matching rules.
- Satisfy receiverless operations with public class-scoped static functions after constructor
  substitution.
- Use HKT contract defaults when neither an explicit block entry nor a member supplies an operation.
- Preserve explicit block methods as authoritative, including their normal diagnostics when invalid.
- Preserve HKT evidence selection, canonical activation, coherence, and dispatch semantics.
- Keep `delegating implementation` working; treat it as the explicit spelling of the default
  forwarding behavior.
- Report missing operations individually and offer fixes that add a member or an implementation
  block.

## Non-goals

- Removing implementation blocks. Explicit blocks remain the override and escape-hatch surface.
- Inferring conformance from class members. The `is` clause remains the explicit claim.
- Changing HKT kinding, constructor patterns, evidence dispatch, or constructor-witness rules.
- Supporting multi-slot constructors, type lambdas, or constructor composition.
- Generalizing blocks to first-order instance requirements; that is [ZEP-0124](./ZEP-0124.md)'s
  static-only slice, and broader block generalization is not proposed here.
- Changing witness activation, import scope, or the orphan rules.
- Changing the meaning of an explicit block entry that is present but invalid.
- Making `delegating` imply conformance by itself.

## Proposal

### Conformance and implementation are separate questions

A class header `is Contract<C<_>>` declares constructor-level conformance. The block answers a
different question: how are the operations implemented? When a block is present, its explicit
entries take precedence and unmatched operations may delegate as described by
[ZEP-0077](./ZEP-0077.md). When no block is present, the class itself is the implementation surface.

| Required HKT operation | Surface when no block is present |
| --- | --- |
| receiver-marked (`this: C<A>`) | public instance method on the class, with receiver substitution |
| receiverless | public class-scoped `static fn`, with constructor substitution |
| contract default | default body from the contract, if no member overrides it |

### Receiver-marked operations

For an operation such as `map<A, B>(this: Box<A>, transform: (A) -> B): Box<B>`, the compiler
matches the operation's receiver pattern against the class constructor, substitutes the class type
parameters, and then applies the existing HKT delegation rules. Those rules already cover method
type parameters, bounds, variadic shape, effects, receiver mutability, and covariant return
assignability.

```zeron
class Box<T: mut> is Mapper<Box<_>> {
    value: T;
    public constructor new;

    public map<R: mut>(transform: (T) -> R): Box<R> =
        Box<R>.new(transform(this.value));
}
```

`Box.map` remains an ordinary public method. It is also the implementation of `Mapper.map` for the
`Box` constructor. No block is needed.

If a compatible method is absent, the conformance is missing that operation. The compiler reports
the specific operation and can offer a fix that inserts an implementation block with the required
signature.

### Receiverless operations

A receiverless operation has no `this` parameter:

```zeron
contract Pure<F<_>> {
    pure<A>(value: A): F<A>;
}
```

A public class static function can satisfy it after constructor substitution:

```zeron
class Box<T: mut> is Pure<Box<_>> {
    value: T;
    public constructor new;

    public static fn pure<U: mut>(value: U): Box<U> = Box<U>.new(value);
}
```

The static function is already a companion namespace function. The conformance adds an evidence use
of the same function; it does not add a JVM static method or change direct `Box.pure(...)` lookup.
Static matching follows the rules proposed by [ZEP-0124](./ZEP-0124.md). If the receiverless
operation mentions a fixed constructor argument that a class static function cannot capture, an
explicit block entry supplies it.

### Explicit blocks still win

When a block is present, its explicit entries remain authoritative in the sense established by
[ZEP-0077](./ZEP-0077.md): an explicit method takes precedence even when invalid, and the compiler
reports its normal error rather than silently falling back to a class member. Operations not present
in a `delegating` block may still forward to compatible class members.

The block remains necessary when:

- the operation belongs to a helper type rather than the conforming class;
- the implementation needs private class state that should not be exposed through a public method;
- the operation's name would collide with an existing member or with another contract's operation;
- the implementation needs the block's class-scoped type-parameter environment;
- the author wants the HKT operation to remain visibly separate from the ordinary instance API.

### `delegating implementation` after the change

`delegating implementation Contract<...> { ... }` remains valid. Its explicit entries keep their
meaning, and operations not listed are forwarded to compatible public class members. With optional
blocks, an empty `delegating` block is equivalent to omitting the block:

```zeron
class Box<T: mut> is Mapper<Box<_>> {
    public map<R: mut>(transform: (T) -> R): Box<R> = ...;

    // Equivalent to omitting the block.
    delegating implementation Mapper<Box<_>> {}
}
```

A non-empty `delegating` block remains useful as a way to combine explicit overrides with forwarding
for the remaining operations. This proposal does not remove or change that form. A future proposal
may deprecate the empty block once the optional form is established; that is not part of this
proposal.

### Defaults

HKT contract defaults from [ZEP-0078](./ZEP-0078.md) participate in the same selection order:

1. an explicit block entry;
2. a compatible public class member (instance method or static function);
3. a unique applicable contract default;
4. a missing-implementation diagnostic.

An explicit member or block entry overrides a compatible default. Multiple applicable defaults are
an ambiguity and require an explicit implementation, as with first-order contract defaults.

### Coherence and declaration authority

The header conformance remains canonical owner-scoped evidence. A constructor witness cannot also
claim the same constructor/contract pair. If a block is present, it must match a header conformance;
a block without one remains an error. The absence of a block does not weaken conformance or create a
second evidence declaration: it only changes where the implementation is found.

Structural matching is enabled only by the explicit `is` claim. A class that merely happens to have
a `map` method does not conform to `Mapper`. This preserves the explicit nature of conformance while
removing the redundant implementation declaration.

### Dispatch and runtime

HKT operations remain statically dispatched. Delegated and explicit implementations both lower to
static helpers inside the implementing class; the ABI does not distinguish an omitted block from an
empty delegating block. Evidence selection and hidden-slot passing are unchanged. This proposal does
not add runtime dispatch, runtime witness lookup, or a new JVM interface.

### Diagnostics

The current "A class HKT conformance requires an implementation block" error is replaced with
operation-specific diagnostics:

- missing HKT implementation for `Contract.operation` with a fix to add a compatible member or an
  implementation block;
- receiverless operation requires a public class static function;
- operation invoked through a receiver but no compatible public instance method exists;
- ambiguous or multiple applicable HKT defaults require an explicit implementation;
- explicit block entry is invalid and does not fall back;
- implementation block does not match a header conformance.

Quick fixes should insert either the missing method signature in the class body or an
`implementation` block, matching the shape of the existing missing-witness and missing-HKT-operation
fixes.

## Compatibility and impact

Existing programs are unaffected: an explicit block keeps its current meaning, and a
`delegating implementation` block keeps its current forwarding behavior. Programs that previously
could not express an HKT conformance without a block become valid. The removed "requires an
implementation block" diagnostic must be replaced in tests and documentation.

The semantic change is deliberate but bounded: a class that explicitly claims an HKT conformance may
now satisfy operations with same-named public members. This is the same rule first-order conformance
already uses. Because conformance is never inferred, the class author has opted into the contract.
If a stricter opt-in is preferred, the alternative is `is delegating Contract<C<_>>`, discussed
below.

Separate compilation must preserve the ability to resolve the same implementation. Header
conformance, class methods, class static functions, and explicit blocks are all exported today.
Consumers can re-run deterministic matching when no block is present. If the API index instead
records resolved HKT implementations, omitted-block conformance needs a resolved mapping and may
require a schema bump. The implementation should choose one path explicitly rather than making
separate compilation depend on source order or import order.

## Alternatives

- **Keep the mandatory block.** This preserves the current explicit boundary but retains the clunky
  empty or delegating block and keeps HKT conformance inconsistent with first-order conformance.
  Rejected as the default ergonomics.
- **Require `is delegating Contract<C<_>>`.** This preserves an explicit opt-in for structural
  forwarding without a block, but adds a new modifier position to the `is` clause. The `is` clause is
  already an explicit conformance claim, so this proposal treats it as sufficient. The stricter form
  remains available if experience shows accidental matching is a problem.
- **Remove implementation blocks entirely.** This gives one member scope and the fewest concepts, but
  breaks the guarantee that HKT helpers are not ordinary members, complicates name lookup and
  tooling, and risks adding same-named virtual methods. Too large for the problem being solved.
- **Infer HKT conformance from class methods.** This would remove the `is` clause as well, but
  silently changes evidence based on unrelated same-named methods. Rejected; only implementation
  lookup is inferred, never conformance.
- **Synthesize an empty delegating block internally but keep the source requirement.** This changes
  the implementation without changing the user-facing rule and leaves the clunkiness in place.
- **Restrict optional blocks to `delegating` only.** This is effectively the `is delegating`
  alternative with a different spelling and does not remove the syntactic cost.

## Implementation and validation

Likely implementation stages:

1. Change header validation so an HKT conformance without a block is accepted.
2. Synthesize an empty delegating implementation internally, or run the existing delegation matcher
   directly for header conformances without a block.
3. Extend delegation matching to receiverless operations and class static functions.
4. Register the resulting helpers as the canonical owner-scoped HKT evidence, preserving explicit
   block precedence.
5. Add per-operation missing-implementation diagnostics and LSP fixes.
6. Verify separate compilation with omitted blocks, explicit blocks, defaults, and `delegating`
   blocks.

Validation should cover:

- receiver-marked delegation with generic class parameters, method parameters, bounds, effects,
  variadics, mutability, and return covariance;
- receiverless operations through class static functions;
- explicit block override precedence, including invalid explicit entries;
- HKT defaults and ambiguity;
- missing operations and quick fixes;
- empty and non-empty `delegating` blocks;
- canonical evidence activation, witness duplicate rejection, and separate-compilation round trips;
- formatter, highlighter, and hover behavior for a header conformance without a block.

Run focused `HigherKindedAbstractionTest`, `ClassContractTest`, API-index, and LSP tests during
development, then the full `mvn test` suite before completion. Remove `dist/` before compiling
generated Zeron programs.

## Open questions

- Should omission be the default, or should structural satisfaction require an explicit
  `is delegating` marker? This proposal recommends omission; the explicit form remains a fallback if
  accidental same-name matching proves confusing.
- Should empty `delegating` blocks be deprecated after the optional form ships? Not now.
- Should receiverless HKT matching live in this proposal or be shared with
  [ZEP-0124](./ZEP-0124.md)'s static matching? The behavior is the same; implementation should share
  the matcher even if the proposals are decided separately.
- Should the API index store resolved HKT implementations, or should separately compiled consumers
  re-run structural matching? The latter avoids a schema change but makes the matching rules part of
  the stable consumer contract.
- ZEP-0124 and this proposal are independently decidable. If ZEP-0124 is not accepted first, this
  proposal must carry its own receiverless class-static matching rules; the shared matcher should not
  become a hidden dependency.
