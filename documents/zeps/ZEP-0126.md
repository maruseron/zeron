## Abstract

Define a compiler-owned `Main<A>` contract that describes how to execute the value produced by an
entry unit's `main` function. The existing `main(): Unit` and `main(args: Array<String>): Unit` forms
become the `A = Unit` case. A `main` may now return any closed type `A` for which `Main<A>` evidence
is available; the compiler synthesizes the host launcher that evaluates `main` and then calls
`Main<A>.run` on the result.

The contract is the single compiler-recognized entry boundary. Standard-library witnesses give
`Unit`, `Int`, and `Result<Unit, E>` their natural entry behavior. Monadic types such as a future
`IO<Unit>` can supply their own witnesses without adding compiler special cases.

## Motivation

The current entry point is defined by a narrow emitter check rather than by a language-level
contract. In the entry source unit, a zero-argument `main` or an `Array<String>`-taking `main` is
launchable only when it returns `Unit`; the compiler then synthesizes the Java `main` method. A
`main` with another return type is accepted by the resolver and emitted as an ordinary function, but
it never becomes the program entry point. The failure therefore appears late, as a missing host
entry method, instead of as a clear source diagnostic.

That restriction is now limiting:

- A program that can fail naturally produces a `Result<Unit, E>` but must unwrap it in `main`,
  print the failure, and call `process.exit` by hand.
- A program that returns an exit status cannot express that directly; it must call `process.exit`
  inside otherwise ordinary `Unit` code.
- A monadic program produces an `IO<Unit>` or another action value, but the runtime has no standard
  way to interpret it.
- Effectful programs can declare `raises` on `main`, but there is no contract that describes how an
  entry *value* is interpreted or how an interpreter's own effects escape.
- Project targets from [ZEP-0117](./ZEP-0117.md) give each target its own entry unit. A single
  standard executable shape keeps target selection, compilation, and launch aligned.

A compiler-owned contract turns these cases into ordinary evidence selection. The compiler keeps
one entry rule, and libraries extend the set of launchable programs without adding another special
case for `Result`, `Int`, actions, or future container types.

## Goals

- Introduce one canonical, compiler-recognized `Main<A>` contract for entry values.
- Preserve the existing `main(): Unit` and `main(args: Array<String>): Unit` programs unchanged.
- Allow `main` to return a closed type `A` when exactly one `Main<A>` witness is active in the
  entry unit.
- Synthesize the host launcher so users do not call `Main.run` themselves.
- Provide standard entry behavior for `Unit`, explicit `Int` exit statuses, and
  `Result<Unit, E>` failures.
- Define how effects raised while producing the entry value and while interpreting it cross the
  host boundary.
- Report missing, ambiguous, or invalid entry evidence as ordinary source diagnostics.
- Keep entry selection scoped to the configured entry unit, including every ZEP-0117 project
  target.
- Keep the public contract, built-in witnesses, and user-defined witnesses visible to the API index
  and separate compilation.

## Non-goals

- Multiple launchable functions per target, alternative entry names, or entry-point discovery in
  arbitrary packages.
- Program arguments beyond `Array<String>`, environment injection, or configuration injection at
  the entry boundary.
- Asynchronous entry points, event loops, automatic task scheduling, or cancellation.
- Installing an implicit top-level effect handler, printing unhandled effects, or converting them
  to exit codes.
- Changing how `main` declares or propagates effects.
- Generic or overloaded `main` functions beyond the supported parameter shapes.
- General function-value entry points such as `fn entry(): A -> Unit`.
- Replacing [ZEP-0117](./ZEP-0117.md) target configuration or the project manifest model.
- Changing the JVM launcher contract beyond the existing generated `public static void main`.

## Proposal

### The contract

The canonical declaration lives in `zeron.lang`:

```zeron
package zeron.lang;

/// Executes the value produced by an entry point.
public contract Main<A> {
    /// Consumes the entry value and ends the program normally or by exiting.
    static fn run(value: A): Unit raises Effect;
}
```

`A` is the entry value type. Because `A` has no `nullable` or `mut` markers, an entry value is a
non-null, non-mutable-reference value; `Unit`, `Int`, `Result<Unit, E>`, and ordinary class values
all qualify. Types that need a mutable or nullable entry value can wrap it in an ordinary class.

`Main` is compiler-owned in the same sense as the other foundational `zeron.lang` declarations:

- the canonical `zeron.lang.Main` identity is the only contract the compiler recognizes for entry
  selection;
- `zeron.lang` is already implicitly star-imported, so the contract and its standard evidence are
  available in every entry unit without an import;
- a user declaration named `Main` in another package is an ordinary contract and does not affect
  entry selection;
- users implement the contract for their own types with a witness, as with any other static
  requirement.

The static requirement means the current witness-only rule applies until
[ZEP-0124](./ZEP-0124.md) ships. After that, a class may also satisfy `Main<A>` nominally through a
public `static fn` or an implementation-block entry. This proposal does not require that extension;
its entry rule is "the applicable `Main<A>` evidence", regardless of how the evidence was declared.

`run` is declared with `raises Effect` because the entry point is the host boundary and because an
interpreter may need to raise while executing the value. A pure implementation is still valid: a
subset effect row satisfies the requirement. The generated launcher does not install a handler, so
an effect raised by `run` escapes the host boundary exactly as an unhandled effect raised by today's
`main` does. A witness can handle its own effects before returning.

### Entry function shape

The compiler recognizes a launchable `main` in the configured entry unit of the selected project
target. The rules are:

- `main` is a top-level function declaration named `main` in that entry unit.
- It has no type parameters.
- It has either no parameters or exactly one parameter of type `Array<String>`.
- Its return type is `Unit`, or a closed type `A` with exactly one applicable `Main<A>` witness.
- It may declare `raises`; that clause keeps its current meaning and does not participate in entry
  witness selection.
- Declaration visibility does not change selection. The compiler emits the host launcher and the
  user function as it does today.
- At most one `main` declaration is allowed for each supported parameter shape. If both a
  zero-argument and an `Array<String>` form are present, the argument-taking form is selected,
  preserving current behavior. If the two forms would select different entry value types, the
  entry is ambiguous and is diagnosed.

The ordinary cases therefore become:

```zeron
fn main() = println("hello");

fn main(args: Array<String>): Unit = println("arguments: " + args.size);

fn main(): Int = 0;

fn main(): Result<Unit, IoFailure> = runProgram();

fn main(): IO<Unit> = IO.println("hello");
```

The last form is illustrative; an `IO` module is not part of this proposal. Its `Main<IO<Unit>>`
witness would be declared beside `IO`, so importing `IO` activates the entry evidence through the
normal default-witness rule.

A non-`Unit` `main` without `Main<A>` evidence is a compiler error at the declaration, not a class
that silently fails to launch.

### Launcher behavior

The generated entry class keeps one JVM entry method:

```text
public static void main(String[] args)
```

Its behavior is conceptually:

```text
value = main() or main(args)
Main<A>.run(value)
```

The compiler selects the witness statically from the entry unit's active evidence and emits a direct
call to the witness helper. No runtime witness lookup or new entry metadata is required. For
`A = Unit`, the compiler uses the `Main<Unit>` default witness, whose call it may elide as a no-op.

Effects and exceptions raised while evaluating `main` escape before `run` is reached. Effects raised
by `run` escape after the entry value has been produced. Neither path installs a handler or changes
the current host-boundary behavior.

### Standard witnesses

The following entry behavior is part of the initial library surface:

| Entry type | Behavior |
| --- | --- |
| `Unit` | The identity witness declared in `zeron.lang`; ends normally. |
| `Int` | `0` ends normally; any other value terminates the program with that status. |
| `Result<Unit, E>` where `E: Display` | `Ok` ends normally; `Err` reports the displayed failure and terminates with a failure status. |

All three are ordinary `default` witnesses declared in `zeron.lang`; none requires a new
intrinsic-kind marker. `Int` already carries a default witness on an intrinsic target in that package
(`default witness Integral<Int> for Int` in `zeron.lang`), and `Unit` is the generated
`zeron.lang.Unit` singleton, so both are intrinsic targets whose canonical owner package is
`zeron.lang`. The `Result` witness sits beside `Result` itself:

```zeron
// zeron/lang/main.zn
default witness Main<Unit> for Unit {
    static fn run(value: Unit): Unit {}
}

default witness Main<Int> for Int {
    static fn run(value: Int): Unit {
        if (value != 0) System.exit(value);
    }
}

// zeron/lang/result.zn, beside the Result declaration
default witness<E: Display + nullable + mut>
Main<Result<Unit, E>> for Result<Unit, E> {
    static fn run(value: Result<Unit, E>): Unit = ...;
}
```

Declaring the standard evidence as source-level defaults keeps one rule: the compiler resolves entry
evidence exactly as it resolves any other bound, and missing or duplicate evidence is reported by the
same solver diagnostics. The only compiler-specific step is that entry resolution runs at the top
level of the entry unit after `main` returns. `Main<Unit>` is still inert at run time, so the
generated launcher may elide its call without changing behavior.

The exact failure-reporting stream, message format, and exit status are library policy recorded
below; the compiler only sees that the `Main` evidence exists. A user can replace the Result policy
only by making the default ambiguous, which is an error, or by wrapping the result in a type with its
own witness.

Reporting a `Result` failure to standard error needs a `System.err` binding, which the current
`java.lang.System` declaration does not provide (it declares `out` only). The implementation must add
that external property binding and the corresponding `zeron.io` helper, or report the failure through
the existing output path. The `Main` contract does not depend on which choice is made.

The standard witnesses are ordinary canonical evidence. They travel with `Unit`, `Int`, and
`Result` through the existing default-witness activation rules, including separate compilation.
The compiler does not import `Result` or `Int` specially for entry selection; their normal scope and
default activation rules apply.

### User-defined entry values

A user type can opt into being an entry value with an ordinary witness:

```zeron
class Job {
    public constructor new(script: String);
    public fn start(): Unit = ...;
}

witness JobMain: Main<Job> for Job {
    static fn run(value: Job): Unit = value.start();
}

fn main(): Job = Job.new("nightly");
```

When [ZEP-0124](./ZEP-0124.md) is available, a class can instead declare nominal conformance and
supply a public static function, if its `run` signature can be expressed without class type
parameters. Block entries cover generic-class cases. The entry rule remains the same: exactly one
applicable `Main<A>` evidence.

### Effectful entry points

There are two effect boundaries:

1. **Producing the entry value.** `main` may declare effects. If it raises while computing `A`, the
   effect escapes before `run` is reached, exactly as a `Unit` entry does today.
2. **Interpreting the entry value.** `Main<A>.run` may declare a subset of `Effect`. An interpreter
   that needs to raise declares those effects on its witness method; a pure witness declares none.
   Unhandled effects escape the host boundary.

This distinction lets a future `IO<Unit>` run its actions with an explicit effect row while keeping
`main` itself an ordinary value producer. It also keeps response-typed effects from
[ZEP-0118](./ZEP-0118.md) orthogonal: a `main` can use `raise` expressions internally, and its
result is still interpreted by `Main<A>`.

No implicit top-level handler, automatic error report, or exit-code conversion is added for
unhandled effects. Programs that need a formatted failure should return `Result<Unit, E>` with an
appropriate `E`, handle their effects before returning, or install their own handler.

### Diagnostics

Entry validation reports, at the declaration or entry unit:

- no top-level `main` in the selected entry unit;
- more than one launchable `main` for the same parameter shape;
- a generic `main`, an unsupported parameter type, or an unsupported parameter count;
- a non-`Unit` return type with no applicable `Main<A>` witness, with help naming `Main`;
- more than one applicable `Main<A>` witness, with the usual ambiguity help;
- a `Main` witness whose `run` shape is incompatible with the contract;
- an entry unit that belongs to a target but has no valid launchable `main` during project
  validation.

The diagnostic should name the canonical `zeron.lang.Main` contract even if the user shadowed the
unqualified name with a local declaration. A missing-evidence fix should suggest a witness
declaration for the returned type, not a `main` wrapper.

### Project targets

ZEP-0117 gives each named target its own entry and output directory. `Main` applies independently
to each target's entry unit:

- `zeron build` and `zeron run` with no target use the default target and its entry unit;
- an explicit target uses that target's entry unit;
- source roots, dependencies, and standard-library selection remain project-wide;
- the language server and formatter continue to analyze all source roots;
- project validation reports an invalid entry for every declared target, not only the default.

The contract does not add target-specific evidence, manifest keys, or a second launcher. It only
standardizes how the selected entry unit produces and interprets its value.

## Compatibility and impact

Existing `Unit` entry points are source- and behavior-compatible. `zeron init` can continue to emit
the current `fn main() { }` starter. The generated entry class keeps the same JVM `main` signature
and launcher role.

The only source-visible behavior change is for a non-`Unit` `main` that previously compiled but was
never launchable. With this proposal it either becomes launchable when matching `Main` evidence is
active or is diagnosed as an invalid entry. That is a deliberate improvement over a late host
failure, but existing tests and examples that treat such a function as an ordinary function must be
checked. A non-`Unit`, non-entry function named `main` outside the entry unit remains an ordinary
function and is unaffected.

New public standard-library surface is the `Main` contract and its standard evidence. The change
should bump `STANDARD_LIBRARY_API_VERSION`. No `API_INDEX_SCHEMA_VERSION` change is expected:
contracts, static requirements, default witnesses, and witness metadata are already indexed. Because
`Main<Unit>` and `Main<Int>` are ordinary source-level defaults over existing intrinsic targets, they
need no new intrinsic kind and no schema change.

Separate compilation needs no new mechanism. User libraries export their `Main` witnesses as
ordinary witness metadata; consumers activate them through imports or defaults and resolve the entry
evidence in the entry unit. The compiler must not depend on source order or on which target is being
built when it resolves a library witness.

Documentation changes are user-facing:

- `guide/02-your-first-program.md` should describe `main` as returning a value with `Main` evidence
  and keep the simple `Unit` case first.
- `guide/20-generic-bounds-and-witnesses.md` should show `Main` as a static-requirement witness.
- `guide/22-raised-effects.md` should distinguish effects raised while producing the entry value
  from effects raised while interpreting it.
- `guide/25-configuration-releases-and-roadmap.md` and the ZEP-0117 target reference should explain
  per-target entry selection.
- `guide/30-higher-kinded-abstractions.md` can mention the `IO`-style witness as an example once
  such a module exists.

## Alternatives

- **Keep the hard-coded `Unit` entry and special-case `Result`, `Int`, and `IO`.** This adds one
  compiler rule per return type and still leaves user types without a standard entry surface.
  Rejected in favor of one contract.
- **Require `main` to call `Main<A>.run` itself.** This makes the entry rule explicit but forces
  boilerplate in every program, duplicates the launch path, and makes `main` values less useful as
  ordinary functions. Rejected.
- **Declare `Main.run` pure.** This is simpler, but an interpreter such as `IO` may need to raise
  while executing. A pure `main` entry can still satisfy an effectful requirement, so the effectful
  contract covers both cases. Rejected as too limiting.
- **Parameterize the contract by an effect row (`Main<A, E: effect...>`).** This would give each
  entry an exact escaping row, but it complicates entry inference and source syntax for little
  benefit at the host boundary. Deferred; `raises Effect` is the initial top-effect boundary.
- **Use a dedicated `entry` declaration or a `main` attribute.** This avoids overloading `main`,
  but adds syntax and migration cost without changing the value being interpreted. Rejected.
- **Treat every non-`Unit` `main` as an exit code.** This handles `Int` but not `Result`, monadic
  actions, or user types, and it makes ordinary `fn main(): String` silently invalid.
- **Infer entry evidence structurally from a `run` member.** This would infer conformance, which
  the language deliberately does not do. The explicit `Main<A>` evidence is the opt-in.
- **Make `main` itself a witness declaration.** This would remove the value-producing function but
  loses `main` as an ordinary callable and complicates arguments, effects, and testing.

## Implementation and validation

Likely implementation stages:

1. Add the canonical `Main` declaration and the `Main<Unit>` and `Main<Int>` default witnesses in
   `zeron.lang`.
2. Factor entry discovery into a resolution step that records the selected `main`, its parameter
   shape, and its return type instead of only a boolean emitter check.
3. Resolve `Main<A>` evidence for non-`Unit` returns and emit the launcher call after the user
   `main` call. Keep the existing argument passing and the existing unhandled-effect behavior.
4. Add the generic `Result<Unit, E>` default witness and the standard failure policy.
5. Add declaration and project diagnostics, LSP hover/diagnostic coverage for `Main`, and
   quick-fix suggestions for missing evidence.
6. Update the guide, generated command/manifest reference where it mentions entry points, and
   `CHANGELOG.md`.
7. Validate API-index export and separate compilation for a library that exports a `Main` witness.

Validation should cover:

- zero-argument and `Array<String>` `Unit` entry points, including the current precedence when both
  exist;
- non-`Unit` entry points for `Int`, `Result<Unit, E>`, a user class witness, and a generic witness;
- missing, ambiguous, and invalid `Main` evidence, including a local contract named `Main`;
- `main` with type parameters, unsupported parameters, or an unsupported return shape;
- effects raised while producing the entry value, effects raised by `run`, and a witness that
  handles its own effects;
- `Result` `Ok` and `Err` exit behavior and the chosen reporting stream;
- ZEP-0117 target selection with two entries and their output directories;
- LSP diagnostics, hover, and quick fixes for entry values;
- API-index round trips and separately compiled user witnesses;
- `zeron init` compatibility and the existing project/run tests.

Run focused entry, resolver, emitter, API-index, and LSP tests during development, then the full
`mvn test` suite before completion. Remove `dist/` before compiling generated Zeron programs so
stale entry classes do not mask a changed launcher.

## Open questions

- Should `Main.run` stay declared with `raises Effect`, or should the contract be pure and leave
  interpreter effects to a separate entry contract? This proposal chooses `raises Effect`.
- For `Result<Unit, E>`, should `Err` always exit with status `1`, or should a future `ExitStatus`
  contract carry per-error codes? This proposal keeps the first version to a single failure status
  and direct `Int` returns for custom codes.
- Should the standard failure report use standard error, and what exact text should it print? The
  standard library has no `System.err` binding today; adding one is part of the implementation, but
  the exact message text remains open.
- Should `Main<Int>` treat `0` as a normal return and every other value as an exit, or should it
  always terminate through `process.exit`? This proposal uses the former, which preserves normal
  cleanup on success.
- Should `main` be required to be public as well as top-level? Current selection is
  name- and location-based, so this proposal preserves it.
- Should a non-`Unit` `main` without evidence be an error or a warning plus a non-launchable class?
  This proposal treats it as an error because the program has no valid entry.
- Should a future async entry point be `Main<Task<Unit>>`, or a separate effect-aware contract?
  That work depends on ZEP-0112 and ZEP-0120 and is outside this proposal.
- Should response-typed effects from ZEP-0118 allow a handler to answer at the entry boundary, or
  does the host boundary always remain abortive for entry values? This needs a separate decision.

## Decision

Accepted on 2026-11-13 and marked `Candidate` for the `0.8.0` normalization bundle.

The settled design is:

- a single compiler-recognized `zeron.lang.Main<A>` contract whose `run` is a `static` requirement
  declared `raises Effect`;
- the launcher evaluates `main` and then calls `Main<A>.run`, with `Main<Unit>` behaving as a no-op;
- `Unit`, `Int`, and `Result<Unit, E>` entry behavior supplied as ordinary `default` witnesses in
  `zeron.lang`, with no new intrinsic kind;
- `Int` treats `0` as a normal return and any other value as an exit status;
- `Result` `Err` reports the displayed failure and exits with a single non-zero status in the first
  release;
- a non-`Unit` `main` without `Main<A>` evidence is a source error, not a silently unlaunchable class.

The open questions above are recorded as implementation-time detail: they refine the failure report,
the public visibility of `main`, and future async and response-typed entry behavior without changing
the entry rule. Acceptance does not commit the bundle to a specific failure message or to per-error
exit codes.
