## Abstract

Make a data class's canonical components readable as part of its structural surface, regardless of
whether the data class itself is declared `public`. Also allow positional destructuring patterns
over data classes at the match root and in nested positions, using only the canonical components,
with optional type-argument inference for generic data classes.

The proposal fixes two user-visible defects without adding a package-visible member tier or a new
runtime representation:

- a non-public data class currently makes its own components private to outside code, even though
  the synthesized constructor and accessors are already public;
- data classes currently have no positional destructuring syntax, even though their canonical
  component order is their primary structural contract.

## Motivation

A data class is defined by an ordered canonical component list. That list determines the canonical
constructor, structural equality, and the generated read-only accessors. Two current behaviors
contradict that purpose.

First, a non-public data class hides its components from the surrounding file or package:

```zeron
data class Point(x: Int, y: Int)

fn lengthSquared(point: Point): Int = point.x * point.x + point.y * point.y;
```

The access to `point.x` reports `ZR2004: Property is private.` Adding `public` to `Point` makes the
same code compile. The class's own visibility is being conflated with the visibility of the
structural members that define it. The generated JVM accessors are already public, so the current
rule is resolver metadata that disagrees with the emitted ABI rather than an intentional
encapsulation boundary.

Second, data classes cannot be destructured positionally:

```zeron
match (point) {
    case Point(0, 0) -> "origin";
    case Point(x, y) -> "other point";
}
```

The root pattern is rejected because a data class is not currently recognized as a positional
pattern root. A nested form such as `Some(Point(x, y))` is rejected as well. For generic data
classes, the current applied-class path requires an explicit type application and counts every
property rather than only the canonical components:

```zeron
public data class Box<A: mut>(value: A) {
    public property doubled: A {
        get = value;
    }
}
```

`case Box<Int>(x)` currently reports an arity error because `doubled` is counted as a second
component. A refutable applied case followed by another case with the same applied identity is also
rejected as unreachable, even when the first case is only a literal test such as `Box<Int>(0)`.

These restrictions make data classes less useful precisely where their structure should be most
valuable: reading fields from nearby code and pattern matching on the canonical shape.

## Goals

- Make data-class components readable by any declaration that can name the data class, without
  requiring the data class itself to be `public`.
- Preserve the existing two-tier member visibility model; do not introduce package-visible members.
- Add positional data-class patterns at the match root and recursively in nested positions.
- Match only canonical components, in declaration order, and exclude auxiliary state and computed
  properties.
- Allow type arguments to be omitted and inferred from the scrutinee for generic data classes.
- Use the same irrefutability and coverage rules as product destructuring.
- Fix the false-unreachable diagnosis for refutable applied cases that share an identity.
- Keep named patterns and ordinary class patterns on their existing resolution paths.
- Add no new JVM ABI, standard-library API, or API-index schema change.

## Non-goals

- A general package-visible or file-visible member tier.
- Changing access rules for ordinary class fields or properties.
- Making data classes extensible, non-final, or inheritance-capable.
- Including auxiliary, mutable, computed, or custom-accessor properties in positional patterns.
- Defaults, rest patterns, named arguments, or partial positional patterns.
- Synthesizing a named pattern for every data class.
- Changing the canonical constructor, structural equality, or component storage.
- Introducing a new runtime descriptor or changing the existing applied-identity descriptor.
- General pattern-matching extensions unrelated to data-class destructuring.

## Proposal

### Component readability

Data-class components become part of the class's readable structural surface. Their generated
read-only accessors are public even when the data class declaration itself is not `public`:

```zeron
data class Point(x: Int, y: Int)

fn lengthSquared(point: Point): Int = point.x * point.x + point.y * point.y;
```

The data class's own visibility continues to govern who can name `Point`. A declaration that cannot
name the type still cannot construct it, declare a variable of that type, or call its members. A
declaration that can name the type can read its components. This preserves the useful boundary: the
type is private to its file or package, while its structural contents are available to the code that
is allowed to work with the type.

This is not a package-visible member tier. [ZEP-0022](./ZEP-0022.md) deliberately keeps member
visibility at public/private, and this proposal does not reopen that decision. It recognizes that
canonical data-class components are the type's structural contract, not incidental implementation
state.

The synthesized canonical constructor is already public, and the emitter already generates public
component accessors. The implementation should align the parser/resolver metadata with that existing
ABI rather than adding a second access path. Auxiliary fields, mutable state, methods, and computed
properties keep their declared visibility and are not affected.

### Positional data-class patterns

A data class may be matched positionally by naming the type and supplying one pattern per canonical
component, in declaration order:

```zeron
data class Point(x: Int, y: Int)

fn describe(point: Point): String = match (point) {
    case Point(0, 0) -> "origin";
    case Point(0, y) -> "on the y axis at " + y;
    case Point(x, 0) -> "on the x axis at " + x;
    case Point(x, y) -> "at " + x + ", " + y;
};
```

Each argument may be a binding, `_`, a literal, or another supported nested pattern. Component
accessors are evaluated left to right, and a failed nested component pattern proceeds to the next
arm. The pattern is statically checked against the canonical component types.

Positional data-class patterns are available recursively in the places where product and class
patterns are already allowed, including sum payloads and nested data-class components:

```zeron
match (result) {
    case Some(Point(x, y)) -> x + y;
    case None -> 0;
}
```

They are not limited to a `match` root and do not require an auxiliary opt-in.

### Canonical components only

The positional arity is the number of canonical components, not the number of all declared
properties. Auxiliary state is not part of the structural pattern:

```zeron
public data class Box<A: mut>(value: A) {
    public property doubled: A {
        get = value;
    }
}

match (box) {
    case Box<Int>(x) -> x; // binds value only; doubled is not a component
}
```

A data class with one canonical component takes one positional argument; a data class with three
takes three. A mismatch is an ordinary arity diagnostic that names the expected component count.
There are no defaults, rest patterns, or skipped components. To inspect auxiliary state, use a
normal property access or a named pattern; positional destructuring remains the canonical structural
view.

### Generic data classes and type arguments

A generic data-class pattern may spell the complete applied type or omit the type arguments:

```zeron
public data class Box<A>(value: A)

match (box) {
    case Box<Int>(x) -> "int " + x;
    case Box(x) -> "other " + x;
}
```

Omission adopts the scrutinee's applied type. Partial type-argument lists, wildcards, and inferred
mixtures such as `Box<Int, _>` are not accepted. An explicit application must agree with the
scrutinee's applied type. When that application is not statically implied by the scrutinee, the
existing descriptor-backed applied-pattern rules apply; this proposal adds no new runtime identity
test and no new reification requirement. A type argument that cannot be established under those
rules is diagnosed at the pattern.

For a non-generic data class, no type arguments are accepted. A type-argument list on a non-generic
data class is diagnosed as an invalid application rather than silently ignored.

### Irrefutability and coverage

A data-class pattern is a product pattern over a final type. Its coverage rule is therefore:

- the type must match the data class (using the existing static or descriptor-backed applied rule
  for generic applications);
- every component subpattern must be total for the pattern to cover the data class;
- a literal, type test, or other refutable component pattern makes the whole pattern refutable and
  contributes no root coverage;
- a total wildcard remains a valid final fallback.

The existing product rule for a final wildcard after a refutable product pattern continues to
apply. Only an unguarded, total pattern covers a data class root.

This rule also fixes the applied-class reachability defect. Refutable patterns with the same applied
identity may follow one another:

```zeron
match (box) {
    case Box<Int>(0) -> "zero";
    case Box<Int>(1) -> "one";
    case Box<Int>(n) -> "other " + n;
}
```

The first two cases are refutable because their component patterns are literals. They do not make a
later case with the same identity unreachable. A following case becomes unreachable only when an
earlier case is total for that identity. This is a general applied-class coverage fix, not a
data-class-only special case, and ordinary classes keep their existing matching semantics.

### Named patterns and ordinary classes

Named patterns keep precedence. A pattern written as `Type.name(...)` is resolved through the
class-defined named-pattern path. A bare positional pattern `Type(...)` on a data class is the
canonical component pattern described here. The two forms may coexist; the named form is not
rewritten into a positional form and positional matching does not require a named pattern to exist.

Ordinary classes keep their current access and matching rules. This proposal does not make ordinary
private fields readable, does not add positional destructuring to ordinary classes, and does not
change class-defined named-pattern resolution. The only shared change is the corrected reachability
rule for refutable applied cases.

### Diagnostics

The resolver should report, at the pattern or component:

- a data-class positional pattern with the wrong number of arguments, naming the expected canonical
  component count;
- a component pattern whose type is incompatible with the corresponding canonical component;
- an explicit type-argument list that does not match the scrutinee or the data class's arity;
- partial type arguments, wildcards, or arguments on a non-generic data class;
- a positional data-class pattern whose type cannot be resolved or is not a data class;
- an unreachable case only when an earlier case is total for the same applied identity;
- the existing ordinary-class diagnostics for unsupported roots, parameter shapes, and named
  patterns.

The current `ZR2004: Property is private` diagnostic must no longer appear for a canonical
data-class component merely because the data class declaration is not `public`.

## Compatibility and impact

Existing valid programs remain valid. Existing non-public data classes gain component access in
code that can already name the type; no new name becomes visible outside the type's existing
visibility. Public data classes already expose their components, so their source behavior is
unchanged.

The JVM representation does not change. Canonical constructors and component accessors are already
public, and positional patterns lower to those accessors. No API-index schema bump, no
standard-library API bump, and no separate-compilation metadata change is required. A non-public
data class is not part of an exported library surface, so making its component metadata public does
not add an exported declaration.

The change is observable in diagnostics and tooling:

- the formatter, highlighter, and parser already handle `Name(...)` patterns; they need to classify
  data-class positional patterns consistently;
- the language server should provide component-aware hover and type checking for positional
  arguments, and should not report a data-class component as private outside the class;
- the coverage and reachability diagnostics should follow the corrected applied-case rule.

Documentation changes are user-facing:

- the data-class guide should state that canonical components are readable and positional patterns
  use only those components;
- the pattern-matching guide should document root and nested data-class patterns, generic inference,
  and the canonical-component arity;
- the visibility guide should distinguish type visibility from the structural readability of
  data-class components.

## Alternatives

- **Keep components private and add a same-file resolver exception.** This would preserve the
  current metadata mismatch and create a second access rule. Rejected; the accessors are already
  public, so the parser metadata should match the ABI.
- **Add package-visible members.** This would give non-public data classes a natural access tier,
  but it reopens ZEP-0022's two-tier visibility model for one feature. Rejected.
- **Require data classes to be declared `public` before their components are readable.** This
  confuses type nameability with structural access and forces wider type visibility than the
  program needs. Rejected.
- **Expose only a named pattern and keep positional destructuring out.** This preserves the status
  quo but makes the common structural operation require a declaration for every data class.
  Rejected.
- **Include all properties in positional patterns.** This would make auxiliary state part of the
  structural contract and break when computed properties change. Rejected.
- **Require explicit type arguments on every generic data-class pattern.** This is simpler to
  implement but makes the common case noisy and prevents inference from an already-known scrutinee.
  Rejected; explicit applications remain available when needed.
- **Synthesize named patterns automatically for data classes.** This adds namespace surface and a
  second path with no additional expressive power. Rejected.
- **Add a new runtime descriptor for data classes.** The existing applied-identity descriptor and
  the canonical component accessors are sufficient. Rejected.

## Implementation and validation

Likely implementation stages:

1. Stop deriving canonical component visibility from the data class's own public modifier. Mark the
   synthesized component properties public while leaving the type's visibility unchanged.
2. Extend pattern parsing and classification so a bare `Type(...)` pattern can resolve to a data
   class as well as a product, at the root and in nested positions.
3. Resolve the canonical component list separately from auxiliary properties. Use that list for
   arity, component types, and emission order.
4. Support explicit and inferred generic applications under the existing applied-pattern rules.
5. Correct applied-case reachability so only a total earlier case covers the same identity.
6. Update the formatter/highlighter/LSP surfaces and the relevant guide chapters.
7. Add the user-facing change to `CHANGELOG.md` when the work is implemented.

Validation should cover:

- reading a non-public data class's components in the same file and in another declaration that can
  name the type;
- public data classes and ordinary private fields retaining their existing behavior;
- root and nested positional patterns, including literal and nested component patterns;
- generic patterns with explicit type arguments and with inference from the scrutinee;
- auxiliary and computed properties being excluded from positional arity and binding order;
- arity, component-type, and type-argument diagnostics;
- refutable same-identity applied cases, including the `Box<Int>(0)` / `Box<Int>(1)` sequence;
- named patterns keeping precedence and ordinary classes keeping their current rules;
- unchanged bytecode accessors and separate-compilation behavior;
- the full `mvn test` suite after focused parser, resolver, emitter, LSP, and coverage tests.

## Open questions

- Should a future package-visible member tier change the visibility of data-class components? This
  proposal deliberately keeps components public and lets type visibility gate nameability.
- Should data classes be allowed to declare named patterns alongside positional destructuring? That
  is compatible with this proposal but not required by it.
- Should partial generic type arguments be supported eventually? The initial rule accepts a complete
  application or none.
- Should a data class with mutable components expose a different pattern form? Mutable canonical
  components are outside this proposal.

## Decision

Accepted on 2026-11-14 and marked `Candidate` for the `0.8.0` normalization bundle.

The settled design is:

- canonical data-class components are public structural accessors, while the data class's own
  visibility still gates who can name the type;
- positional data-class patterns use only canonical components, at the match root and recursively
  in nested positions;
- generic type arguments may be written completely or inferred from the scrutinee; partial type
  arguments are not accepted;
- coverage follows the product rule, and refutable applied cases with the same identity no longer
  make one another unreachable;
- ordinary classes keep their existing access and matching rules, and the change adds no JVM ABI,
  standard-library API, or API-index schema change.
