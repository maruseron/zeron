## Abstract

Let sum type parameters declare the same marker and contract bounds as classes and contracts, and
let individual sum cases declare their own type parameters. A case-local parameter is existentially
quantified by the case: it is chosen when the case is constructed and is opaque when the case is
matched. It is not an argument of the sum type and does not add a runtime alternative.

The proposal removes the need to encode polymorphic cases as a sealed contract with one class per
case. It also makes a case such as `Bind` in an `IO` sum expressible without erasing the result type
of its continuation, and allows case construction and matching to omit the sum qualifier when the
context makes the case unambiguous.

## Motivation

Zeron sums currently support type parameters and marker bounds at the sum declaration, but not
contract bounds on those parameters and not case-local parameters. The `IO` exploration shows both
limitations at once:

```zeron
type IO<A: mut> =
      Pure(value: A)
    | Delay(action: () -> A)
    | Bind(source: IO<A>, transform: <B>(A) -> IO<B>);
```

The `Bind` case needs a `B` that is not part of `IO<A>`. The current declaration cannot introduce
that parameter, so the case either loses the result type of `transform` or the whole sum must be
rewritten as a sealed contract plus implementing classes. The sealed-contract workaround is valid,
but it turns a closed data declaration into a family of nominal classes and makes exhaustive
matching depend on the class hierarchy rather than on the sum.

Contract bounds fail for the same reason at a different level:

```zeron
type Sorted<A: Comparable<A>> =
      Empty
    | Cons(head: A, tail: Sorted<A>);
```

The declaration should be able to state that every `A` used by `Sorted<A>` is comparable. Today the
bound must be repeated on every consumer, or the sum must again be replaced by a sealed contract.
That makes reusable polymorphic data structures harder to declare and obscures the invariant at the
declaration site.

The examples also expose a separate ergonomic gap. A sum's cases are naturally read as part of the
sum, so writing `Cons(value, Empty)` inside a function that already returns `Sorted<A>` should not
require `Sorted.Cons(value, Sorted.Empty)`. Unqualified case names are already useful in patterns;
this proposal makes that behavior explicit and consistent for construction and matching.

## Goals

- Accept marker and contract bounds on sum type parameters using the existing bound syntax and
  conformance rules.
- Accept case-local type parameters in a case payload declaration.
- Allow unqualified case names in construction and pattern positions when the sum is determined by
  context or the name is unambiguous in scope.
- Treat a case-local parameter as existential in the sum type: chosen by construction, opaque by
  matching, and absent from the sum's applied type.
- Infer case-local arguments from payload arguments and the expected sum type; permit a complete
  explicit application on construction and reject partial or wildcard applications.
- Open case-local parameters in patterns through the existing existential binder form, without
  claiming that erased runtime identity can distinguish their arguments.
- Keep the closed set of cases, exhaustive coverage, and singleton identity of payload-less cases
  unchanged.
- Record bounds and case-local parameters in compiled-library metadata so separate compilation
  preserves the source rules.
- Add no new runtime descriptor or generic-argument reification.

## Non-goals

- GADT-style type equalities or case-local parameters that refine a sum type parameter.
- Per-case visibility, case-specific methods, or case inheritance.
- A global case namespace, implicit case imports, or unqualified names that bypass ordinary lexical
  shadowing and ambiguity rules.
- Contract bounds on case-local parameters in this slice. Marker bounds are supported; contract
  bounds need an evidence-storage design and remain deferred.
- Runtime inspection of case-local type arguments.
- Changing sum variance, the existing `Option<T>` representation, or the payload and constructor
  shape of non-generic cases; this proposal only makes the sum qualifier optional when resolution
  is unambiguous.
- Turning sums into open unions or permitting consumer-added cases.

## Proposal

### Bounds on sum type parameters

A sum declaration may write the same bounds as a class or contract:

```zeron
public type Sorted<A: Comparable<A>> =
      Empty
    | Cons(head: A, tail: Sorted<A>);
```

Every occurrence of `Sorted<A>` must satisfy `A: Comparable<A>`. The bound is checked at the
declaration and at each application. A generic function that manipulates a `Sorted<A>` must carry
the bound, just as it would for a class:

```zeron
fn insert<A: Comparable<A>>(value: A, sorted: Sorted<A>): Sorted<A> =
    match (sorted) {
        case Empty -> Cons(value, Empty);
        case Cons(head, tail) ->
            if (value.compareTo(head) <= 0)
                then Cons(value, sorted)
                else Cons(head, insert(value, tail));
    };
```

The bound is a static constraint on the sum application. A sum value does not need to carry a
hidden evidence field merely because its declaration has a bound: every site that can name
`Sorted<A>` already has either a concrete `A` with evidence or a matching bound in scope. Generated
case classes inherit the bound for their source signatures, but their erased JVM representation does
not gain a new runtime dictionary.

Sum-target extensions and witnesses follow the same rule. They may declare their own bounds, and a
sum application they mention must satisfy the sum's bounds. A witness for a bounded sum must prove
the bound for the target application; it cannot silently weaken it.

### Case-local type parameters

A case may declare type parameters immediately after its name:

```zeron
public type IO<A: mut> =
      Pure(value: A)
    | Delay(action: () -> A)
    | Bind<B: mut>(source: IO<A>, transform: A -> IO<B>);
```

`B` belongs to `Bind`, not to `IO`. `IO<A>` still has one type argument; `IO.Bind` is a generic case
constructor whose own parameter is chosen at construction.

Construction infers case-local arguments from the payload and the expected result:

```zeron
fn flatMap<A: mut, B: mut>(this: IO<A>, transform: A -> IO<B>): IO<B> =
    IO.Bind(this, transform);
```

Here the expected return type `IO<B>` and the `transform` argument determine the case-local `B`.
A complete explicit application is also allowed, for example `IO.Bind<B>(this, transform)`.
Partial applications, wildcards, and mixtures of explicit and inferred arguments are rejected.
A non-generic case rejects a type-argument list rather than ignoring it.

Case-local parameters may use marker bounds such as `mut` and `nullable`. Contract bounds on
case-local parameters are not part of this slice because a matched case would need to recover
evidence that is not represented in the sum value. A later proposal may add hidden evidence storage;
until then, a case-local parameter cannot require `Comparable<B>` or another contract bound.

### Unqualified case names

A case constructor or case pattern may omit the sum qualifier when the relevant sum is determined
by context or when the case name is unambiguous in the active scope:

```zeron
fn pure<A: mut>(value: A): IO<A> = Pure(value);

fn insert<A: Comparable<A>>(value: A, sorted: Sorted<A>): Sorted<A> =
    match (sorted) {
        case Empty -> Cons(value, Empty);
        case Cons(head, tail) ->
            if (value.compareTo(head) <= 0)
                then Cons(value, sorted)
                else Cons(head, insert(value, tail));
    };
```

The unqualified spelling is an alias for `Sum.Case`; it does not declare a new top-level value or
change the case's visibility. Resolution follows these rules:

1. **Patterns.** The scrutinee's static sum type fixes the case namespace. A case name that belongs
   to that sum may be written without the sum qualifier. A name that belongs to a different sum, or
   to no case of the scrutinee's sum, is an error.
2. **Expected-type construction.** If the expression has an expected sum type, that type fixes the
   case namespace. This includes a declared variable type, a parameter type, a return type, and a
   payload position with a known type.
3. **Unambiguous construction without an expected type.** If no expected type is available, an
   unqualified name may resolve only when exactly one visible sum exposes that case. If two visible
   sums expose the same case name, the expression is ambiguous and must be qualified.
4. **Ordinary value shadowing.** A local, parameter, field, or top-level value with the same name
   takes precedence over an unqualified case. Use the qualified form when the case is intended.
5. **Generic inference.** Unqualified construction uses the same payload inference and contextual
   type rules as the qualified form. A payload-less generic case still needs context or an explicit
   sum application to determine the sum's type arguments.
6. **Case-local parameters.** A case-local type argument list is written after the case name, for
   example `Bind<B>(source, transform)`. The sum qualifier remains optional under the rules above.

Qualification remains valid everywhere and is the disambiguation tool. The qualified and
unqualified forms have the same construction, identity, coverage, and evaluation behavior. Cases
are not separately imported: they are available with the sum's visibility, and unqualified lookup
only considers sums already in scope.

### Matching and existential opening

A case pattern binds the payload positions exactly as before. Case-local parameters are opaque:

```zeron
fn describe(io: IO<Int>): String =
    match (io) {
        case IO.Pure(value) -> "pure " + value;
        case IO.Delay(action) -> "delay";
        case IO.Bind(source, transform) -> "bind";
    };
```

Inside the `Bind` arm, `source` has type `IO<Int>` and `transform` has type
`Int -> IO<B>` for a fresh rigid `B`. The arm may call `transform`, pass the result to a generic
function, or return it where the surrounding context accepts the same opaque `IO<B>`, but it cannot
assume `B` is a particular type or let `B` escape the arm.

When the program needs to name the hidden parameter, it uses the existential binder form already
used for opening patterns:

```zeron
match (io) {
    case IO.Bind<let B>(source, transform) -> {
        let next: IO<B> = transform(42);
        consume(next);
    }
    case _ -> fallback();
};
```

The binder is branch-local and rigid. It may be used in local annotations and calls, but it cannot
escape through a return type, assignment, stored field, or raised effect. Its declared bounds, if
any, are available as static facts. If the binder is omitted, the parameter remains unnamed but the
payload types still refer to it consistently within the arm.

A concrete case-local argument in a pattern, such as `IO.Bind<Int>(source, transform)`, is rejected.
The runtime case test is an erased class test and cannot prove that the hidden argument is `Int`.
The `let` binder is the only way to name it; it does not assert a concrete argument.

### Coverage and identity

Case-local parameters do not change the closed set of cases. `IO.Bind` is one alternative for every
choice of `B`, so a pattern for `IO.Bind` or `Bind` covers all of them and a wildcard still covers
the remaining cases. A pattern with a binder is still total at the case level; nested payload
patterns may make it refutable.

Case identity remains the existing erased generated case class. No descriptor is added for `B`, and
two values of `IO.Bind` with different hidden arguments are indistinguishable at runtime, just as
two applications of an erased generic class are today. This is why a concrete case-local pattern is
not a runtime test.

Payload-less cases keep their singleton identity. A generic payload-less case with only case-local
parameters, if allowed by the declaration rules, has one singleton per erased case class; the
parameters are compile-time only and cannot create distinct runtime values.

### Bounds, witnesses, and separate compilation

Compiled-library metadata records:

- the sum's type parameters and their bounds;
- each case's payload names and types;
- each case's local type parameters and their marker bounds;
- whether a case is payload-less and therefore singleton-valued.

Consumer compilation uses that metadata to check bounds, infer case-local arguments, open patterns,
and compute coverage. It must not reconstruct bounds or case parameters from generated JVM
signatures, which are erased. Existing sums without bounds or case-local parameters export the same
source semantics and remain compatible.

## Compatibility and impact

The change is source-additive. Existing sums keep their meaning, and qualified case construction and
patterns remain valid. Existing code that repeats a bound on every consumer of a bounded sum can
keep doing so; the declaration-site bound is an additional constraint, not a new form of implicit
evidence. Unqualified case names become available only where resolution is unambiguous; they do not
shadow ordinary values.

The JVM representation stays the existing sealed common parent plus one final class per case.
Adding a case-local parameter changes the generated class's source-level generic signature but not
its erased runtime identity or payload field descriptors. No new runtime descriptor, cast, or
witness slot is introduced. Contract bounds on case-local parameters are deliberately excluded, so
this proposal does not add hidden evidence fields.

The API-index schema gains sum-parameter bounds and case-local parameter metadata. That requires the
usual schema revision and separate-compilation tests. The standard-library API does not change
unless a bundled sum adopts the new form; that is a separate library decision.

Tooling must classify case-local parameter declarations, show their bounds in hover, include their
binders in completion and rename, and reject concrete case-local pattern arguments consistently.
The formatter must preserve the case parameter list and binder syntax.

## Alternatives

- **Keep the sealed-contract workaround.** It is already implemented and supports per-case classes,
  but it loses the concise closed-data declaration and makes exhaustive matching depend on a class
  hierarchy. Rejected as the only way to express polymorphic cases.
- **Erase the case-local parameter.** This accepts `Bind` but makes `transform` return an unusable
  `IO<Any>` and loses the type relationship the case exists to express. Rejected.
- **Make case-local parameters ordinary sum parameters.** That would force every `IO<A>` to carry
  every possible `B`, which is not the intended type and destroys the sum's arity. Rejected.
- **Reify case-local arguments for pattern tests.** This would allow concrete case-local patterns
  but adds descriptors and runtime identity that the rest of the generic system deliberately avoids.
  Rejected for this slice.
- **Allow contract bounds on case-local parameters immediately.** This is useful, but requires a
  sound story for storing or reconstructing evidence after an existential opening. Deferred rather
  than silently weakening the bound.
- **Allow GADT-style equalities.** They are a larger type-system feature and are not needed for the
  `IO` case. Rejected for this proposal.

## Implementation and validation

Likely stages:

1. Extend the sum declaration parser and AST to accept bounds on sum parameters and parameter lists
   on cases. Preserve the existing case-payload syntax.
2. Resolve sum bounds with the same machinery used for class and contract bounds. Validate each sum
   application and generated case signature.
3. Add case-local parameters to the case constructor scope. Infer them from payload arguments and
   the expected sum type; check explicit complete applications.
4. Add existential opening for case patterns using the existing `let` binder machinery. Enforce
   rigid scope and escape rules; reject concrete case-local pattern arguments.
5. Add unqualified case resolution for construction and patterns: use the expected sum type or
   scrutinee type first, then unique-name lookup, while preserving lexical shadowing and reporting
   ambiguity.
6. Record and round-trip bounds and case parameters in compiled-library metadata.
7. Update formatter, highlighter, LSP hover/completion, and diagnostics for unqualified cases.
8. Add a user-facing change note when the feature is implemented.

Validation should cover:

- bounded sums with concrete, generic, and recursive applications;
- bounds inherited by extensions, witnesses, and generic helpers;
- `IO` construction and matching with inferred and explicit case-local arguments;
- unqualified case construction and patterns with expected-type, unique-name, shadowing, and
  ambiguity cases;
- opaque and named existential binders, including escape rejection;
- coverage of cases with case-local parameters and singleton payload-less cases;
- rejection of contract bounds on case-local parameters, concrete case-local patterns, partial
  applications, wildcards, and arguments on non-generic cases;
- separate compilation of a bounded sum and a case-local sum across a library boundary;
- unchanged erased case identity and payload layout;
- the full test suite after focused parser, resolver, metadata, emitter, and LSP tests.

## Open questions

- Should contract bounds on case-local parameters be supported later through hidden evidence fields,
  or should they remain forbidden in favor of a separate wrapper?
- Should a case-local parameter be allowed to appear in the case name for diagnostics, or is the
  declaration order sufficient?
- Should explicit case-local construction arguments be required when inference is ambiguous, or
  should ambiguity always be an error?
- Should a future GADT design allow case-local parameters to refine sum parameters? This proposal
  deliberately does not.

## Decision

Accepted on 2026-11-14 and marked `Candidate` for the `0.8.0` normalization bundle.

The settled design is:

- sum type parameters accept the same marker and contract bounds as classes and contracts;
- cases may declare case-local type parameters, which are existential in the sum type;
- construction infers case-local arguments from payloads and the expected type, or accepts one
  complete explicit application;
- case constructors and patterns may omit the sum qualifier when the expected sum or scrutinee
  determines the case, or when the case name is uniquely visible; ordinary values still shadow case
  names and ambiguity requires qualification;
- matching opens case-local parameters through a branch-local `let` binder; concrete case-local
  pattern arguments are rejected because case identity is erased;
- case-local parameters may use marker bounds but not contract bounds in this slice;
- coverage, singleton identity, and the erased case representation are unchanged;
- compiled-library metadata records both sum bounds and case-local parameters.
