# ZEP-0129: Unary Products versus Arbitrary-Valued Newtypes

## Abstract

Zeron needs a nominal way to name a single value, especially a function shape. Two possible
answers are a one-component product and a newtype whose representation is any statically known
type. This proposal chooses the second: products keep their minimum of two components, while
ZEP-0070 generalizes newtypes to arbitrary single-value representations.

The choice avoids two overlapping structural forms for the same shape. A product is a transparent
record with positional destructuring and intrinsic structural equality; a newtype is a nominal
view with explicit construction and no generated `value` member. A one-component product would
inherit the product machinery while providing no structural information that a newtype does not
already provide more intentionally.

## Motivation

A unary product is currently rejected:

```zeron
type IO<A: mut> = (action: () -> A);
```

The intent is not to expose a record with one component. It is to give a function shape a name,
construct it explicitly, and add operations to it. The same need appears whenever a domain value is
a function, a validated scalar, a host object, or another nominal value that should not be confused
with its representation.

A data class can already hold one component:

```zeron
public data class IO<A: mut>(action: () -> A) {}
```

That works, but it brings data-class semantics: a canonical constructor, structural equality over
the component, public component access, and compatibility with positional patterns. Those are useful
for records, not for an opaque nominal view. The `IO` exploration also exposes the ergonomic cost of
reading `.action()` everywhere when the newtype is meant to behave like a value.

A generalized newtype gives the intended shape directly:

```zeron
public newtype IO<A: mut> = () -> A;
```

Construction is explicit, the function value is the runtime carrier, and the newtype has a distinct
nominal identity. There is no generated `.value` property; a newtype-owned extension sees the
function through `this`, and callers use an explicit operation such as `run()` when they need the
result.

## Goals

- Keep the product rule that a product has at least two components.
- Generalize newtypes through ZEP-0070 so a single value of any admissible type can be named.
- Make function shapes, nominal values, and other single-value representations nameable without a
  data class or a sealed-contract workaround.
- Preserve explicit construction and representation access through newtype-owned operations; do not
  generate a `.value` field.
- Give the `IO` example a direct expression without a unary product.
- Keep structural products, data classes, and nominal newtypes as distinct tools.

## Non-goals

- Legalizing one-component products in this release.
- Making newtypes transparent aliases or structural records.
- Automatic forwarding of the representation's methods, contracts, or equality.
- Implicit conversion between a newtype and its representation outside newtype-owned extension and
  witness bodies.
- Changing the product ABI, product equality, or product pattern rules.
- Adding unary tuples or anonymous single-field records.
- Requiring guarded invariants for arbitrary representations; guarded newtypes remain scalar-only
  in ZEP-0070's initial scope.

## Proposal

### Products remain at least binary

A product declaration still requires two or more components:

```zeron
public type Pair<A, B> = (left: A, right: B);
```

The existing product rules continue to apply: nominal identity, ordered components, positional
destructuring, intrinsic conditional `Eq`, and no component-level visibility or mutation. A
one-component product is not added because it would be a structural record with no structural
relationship to another component, while still carrying product equality and positional-pattern
machinery.

### Newtypes carry the single-value case

A newtype may bind type parameters and use any statically known admissible representation:

```zeron
public newtype IO<A: mut> = () -> A;
public newtype UserKey = UUID;
public newtype Parser<A> = String -> Result<A, ParseError>;
```

The representation is not implicitly interchangeable with the newtype outside the newtype's own
extensions and witnesses. Construction is explicit:

```zeron
let action: IO<Int> = IO.new(() -> 42);
let value: Int = action.run();
```

`IO.new` returns the representation as a newtype value; it does not allocate a wrapper object.
`run()` is an explicit extension that calls the function carrier. There is no `.value` read and no
implicit call on `IO` itself.

The `IO` example can now be expressed without a unary product or a one-field data class:

```zeron
public newtype IO<A: mut> = () -> A;

public extension<A: mut> IO<A> {
    public fn map<B: mut>(transform: A -> B): IO<B> =
        IO.new(() -> transform(this()));

    public fn flatMap<B: mut>(transform: A -> IO<B>): IO<B> =
        IO.new(() -> transform(this())());

    public fn run(): A = this();
}
```

Inside the `IO` extension, `this` is the function carrier, so `this()` calls it directly. A
parameter typed `IO<B>` is also represented by its function carrier in that body, which is why
`transform(this())()` can call the returned `IO<B>` without `.value`. `IO.new` re-establishes the
nominal type; it does not add a wrapper field. The lambda itself may allocate, but the newtype does
not add another allocation on top of it.

### Comparison

| Property | Unary product | Arbitrary-valued newtype |
| --- | --- | --- |
| Identity | Nominal product identity | Nominal newtype identity |
| Shape | Structural record with one component | Nominal view with direct representation |
| Construction | Canonical product constructor | `.new` or `.tryNew` |
| Extraction | Generated component accessor | No `.value`; explicit newtype operation or representation context |
| Equality | Intrinsic conditional structural `Eq` | None unless explicitly provided |
| Patterns | Positional product pattern | No structural destructuring |
| Validation | Not part of the product MVP | Scalar guards remain available |
| Runtime | Product object | Representation carrier directly; boxing only at erased boundaries |
| Best use | Records with two or more related values | Naming one value or shape |

A data class with one component remains available for a record-like value that needs a named
component and data-class behavior. It is not a substitute for a newtype when the intent is opacity
or nominal distinction.

### Why not both

Supporting unary products and arbitrary-valued newtypes would give two ways to name a single value
with different equality, pattern, and construction semantics. The language would then need rules for
when a one-component record should be a product and when it should be a newtype, and users would
have to choose between nearly identical shapes with different ABI and evidence behavior. The
single-value need is better served by the feature whose entire purpose is nominal distinction.

If a future use case needs a transparent one-component tuple for structural typing, it should be
designed as a distinct proposal with its own equality and pattern rules. This ZEP does not reserve
that design space by legalizing unary products now.

## Compatibility and impact

Existing products remain unchanged. Existing newtypes remain valid at the source level, but their
runtime representation changes: ZEP-0070 removes the wrapper class and `.value` accessor in favor of
the direct carrier. Code that reads `.value` must migrate to an explicit extension such as
`toFloat()` or to operations the newtype declares. This is a pre-1.0 ABI break and must be recorded
in the release notes and guides.

Existing newtypes that only construct and pass values around keep their source shape; their fields,
parameters, and returns may change descriptors from the wrapper class to the carrier. Code that used
`.value` in an extension or witness should use `this` directly. The representation context is
limited to newtype-owned bodies; ordinary callers still cannot implicitly interchange the newtype
and its representation.

The newtype metadata records type parameters, representation types, and representation contexts. It
does not change product metadata or product bytecode. Function-shape representations use the
existing function-value carrier directly; they do not add a new JVM calling convention.

The standard-library API changes only if a bundled type adopts a generalized newtype. The first
consumer is expected to be a library or sample `IO` newtype, not a change to `Option` or another
existing nominal type.

## Alternatives

- **Legalize unary products only.** This satisfies the shape but leaves newtypes scalar-only and
  gives a single value product equality and positional patterns that are not wanted. Rejected.
- **Support both.** This maximizes local convenience but creates two overlapping single-value forms
  with different semantics and ABI. Rejected for this release.
- **Keep newtype wrappers and `.value`.** This preserves the old ABI but keeps an unnecessary field
  and makes extension/witness bodies indirect. Rejected in favor of ZEP-0070's direct
  representation.
- **Use a one-field data class.** It works today, but it exposes a canonical component, structural
  equality, and data-class pattern behavior. It remains a valid choice for record-like values, not
  for opaque nominal views.
- **Use a sealed contract with one case.** This is heavier, adds a class hierarchy for a single
  value, and does not give the concise nominal view the use case needs. Rejected.
- **Keep the status quo.** It forces users to choose between structural records and class/contract
  boilerplate for a common single-value shape. Rejected.

## Implementation and validation

ZEP-0070 carries the implementation of generic and nominal newtype representations, including direct
carriers and the representation context for extensions and witnesses. This proposal adds no separate
implementation beyond keeping the product arity rule and updating documentation to state the
distinction.

Validation should cover:

- a function-shaped newtype with construction, `run()` extraction, and extension methods;
- no generated wrapper class, field, or `.value` accessor;
- direct carriers for primitive, `String`, function, and nominal representations;
- expected boxing at generic, `Any`, nullable, and array boundaries;
- generic and nominal representations from ZEP-0070;
- products with two or more components retaining their current behavior;
- a one-component product remaining a parse/resolve error;
- a one-component data class retaining data-class behavior;
- explicit construction and representation access with no implicit conversion outside newtype-owned
  bodies;
- separate compilation of a generic newtype and its extension methods.

## Open questions

- Should a future transparent one-component tuple be a separate type form, or should the product
  minimum eventually become configurable?
- Should a function-shaped newtype expose a standard `run()`-style operation, or should every newtype
  define its own representation accessor?
- Should the standard library provide a canonical `IO` newtype, or leave it to libraries and
  examples?

## Decision

Accepted on 2026-11-14 and marked `Candidate` for the `0.8.0` normalization bundle, together with
[ZEP-0070](./ZEP-0070.md).

The settled design is:

- products continue to require at least two components;
- unary products are not added in this release;
- arbitrary-valued newtypes from ZEP-0070 are the supported way to name a single value or shape;
- newtypes have no generated `.value` field; construction is explicit and representation access is
  through an explicit newtype operation or the representation context of an extension/witness;
- direct carriers replace wrapper objects, with boxing only at erased or generic boundaries;
- newtypes remain nominal, with no implicit conversion outside newtype-owned bodies;
- a one-field data class remains available for record-like values, not as an opaque wrapper;
- the `IO` function wrapper is expressible as a generic newtype over a function type.
