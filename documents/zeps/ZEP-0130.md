## Abstract

Intrinsic types such as `Int`, `String`, and `Array<T>` keep compiler-owned identity, literal
syntax, storage, and runtime tests. Their public operations are owned by the standard library and
declared in canonical `zeron.lang` source modules as extensions and namespaces, not by a second
class declaration in `zeron.lang` and not by ad-hoc compiler methods.

This proposal settles that ownership rule and applies it to a bounded, practical `String` inventory.
The inventory is chosen to make ordinary text programs expressible without forcing every program to
hand-roll character loops or reach through Java interop. The motivating word-count program needs at
least `charAt`, `toLowerCase`, and a delimiter-based `split`; the same gap appears for case
conversion, trimming, line splitting, literal replacement, and simple parsing.

A `class String` in `zeron.lang` is not the right mechanism because it would declare a competing
nominal type instead of extending the compiler-owned intrinsic type.

## Motivation

The standard library already declares most intrinsic operations in source. For example,
`zeron/lang/string.zn` contains:

```zeron
public extension String {
    public fn length(): Int = stringLength(this);
    public fn substring(start: Int, end: Int): Option<String> { ... }
}
```

`zeron/lang/int.zn`, `long.zn`, `float.zn`, `byte.zn`, and `char.zn` follow the same pattern, and
`zeron/lang/array.zn` extends the intrinsic array type. The compiler owns the primitive operations
and external bindings those declarations use; the standard library owns the names, signatures,
documentation, and composition.

That policy is implicit. When an operation is missing, there is no written rule saying whether to
add a new intrinsic ID, a compiler special case, an external function binding, a standard-library
extension, or a class declaration. Each choice has different consequences for API indexing,
documentation, separate compilation, and ordinary member lookup.

The practical cost is visible in the word-count exploration. Its intended shape is small:

```zeron
fn wordCount(text: String): Map<String, Int> {
    let counts = HashMap<String, Int>.empty();
    for (let word in text.toLowerCase().split(' ')) {
        counts.put(word, counts.getOrElse(word, 0) + 1);
    }
    return counts;
}
```

The current library has `length`, `contains`, and `substring`, but no `toLowerCase`, no `split`, and
no safe character access. The program falls back to a hand-written character loop and then stops
because the remaining operations are also absent. That is not a missing corner case; it is a hole
in the basic text toolkit.

A `class String` would be especially misleading. `String` already has compiler-owned identity,
literal syntax, JVM mapping, nullability, and runtime-test behavior. A source class with the same
name would either conflict with that type or create a second, unrelated nominal type. The standard
library needs ownership of operations, not ownership of the intrinsic type itself.

## Goals

- Establish one canonical owner for the public operations of each intrinsic type.
- Keep intrinsic type identity, literals, storage, boxing, casts, and runtime tests compiler-owned.
- Declare ordinary intrinsic operations as standard-library source extensions or namespace
  functions, not as new intrinsic IDs.
- Keep intrinsic IDs for syntax operations and lowering primitives that cannot be expressed in
  Zeron source.
- Add a bounded `String` inventory that makes common text processing usable without Java interop.
- Include splitting, character access, case conversion, trimming, replacement, line handling, simple
  parsing, joining, and regex splitting in that inventory.
- Preserve API-index and separate-compilation behavior for standard-library extensions.
- Avoid a parallel `class String` or other fake nominal declaration for an intrinsic type.

## Non-goals

- Turning intrinsic types into ordinary user-declarable classes.
- Allowing user code to define new intrinsic types.
- Moving all compiler-owned operations into source when they require syntax or a JVM primitive.
- Exposing arbitrary Java or JDK members through intrinsic names.
- Changing boxing, literal syntax, runtime type tests, or the intrinsic registry's identity rules.
- Replacing the platform regex engine or exposing every Java `String` method.
- Locale-sensitive case conversion, Unicode normalization, grapheme-cluster segmentation, or
  formatting.
- A full regex replacement API; `splitRegex` is the only regex operation in this slice.

## Proposal

### Ownership rule

Every intrinsic type has a canonical standard-library module in `zeron.lang`. The module may declare:

- `extension` methods that add receiver-style operations to the intrinsic type;
- `namespace` functions for operations that are naturally named by the type rather than a receiver;
- ordinary helpers, witnesses, documentation, and error types needed by those operations.

The module is source, not a type declaration. It does not declare a class, constructor, field,
inheritance relationship, or second identity for the intrinsic type. `zeron.lang.String` is the
module/namespace that owns string operations; it is not a class named `String`.

The compiler owns:

- the type's identity and source name;
- literal syntax and contextual conversion;
- storage, boxing, nullability, and JVM mapping;
- runtime type tests and casts;
- syntax operations such as indexing and array literals;
- primitive operations that cannot be expressed as ordinary Zeron bodies.

The standard library owns:

- public operation names and signatures;
- documentation and examples;
- default implementations composed from other operations;
- ordinary validation and result types;
- extension and namespace exports in the API index.

### Intrinsic IDs and external bindings

An intrinsic ID remains appropriate for a syntax operation or a lowering primitive. Adding an
ordinary method must not add a new intrinsic ID merely because the receiver is an intrinsic type. If
an operation needs a platform primitive, the standard-library declaration may call a private external
helper or a registered intrinsic binding; that binding is an implementation detail behind the public
extension.

This keeps the intrinsic registry small and prevents ordinary library growth from changing the
compiler's operation catalogue. It also keeps the public API in source, where it can be documented,
indexed, and tested like any other library declaration.

### `String` inventory

The initial inventory keeps the existing UTF-16 code-unit operations and adds the following
standard-library extension methods. The exact names are part of the API; the list is bounded so it
covers everyday text processing without becoming a mirror of `java.lang.String`.

| Area | Operation | Semantics |
| --- | --- | --- |
| Existing | `length`, `isEmpty`, `indexOf`, `lastIndexOf`, `contains`, `startsWith`, `endsWith`, `substring` | Existing UTF-16 code-unit behavior |
| Existing scalar API | `codePointLength`, `codePointAt`, `substringByCodePoints`, `indexOfCodePoint`, `codePoints`, `singleChar`, and `*Strict` variants | Existing Unicode-scalar behavior |
| Character access | `charAt(index: Int): Option<Char>` | UTF-16 code-unit index; `None` when out of range; an unpaired surrogate is normalized to U+FFFD |
| Character access | `at(index: Int): Option<Char>` | Alias of `charAt`, matching the collection-style `at` spelling |
| Splitting | `split(separator: String): Array<String>` | Literal, non-regex separator; empty fields preserved |
| Splitting | `split(separator: Char): Array<String>` | Literal character separator; the word-count case |
| Regex splitting | `splitRegex(pattern: String): Result<Array<String>, RegexError>` | Platform regex dialect; invalid patterns return `Err` |
| Case | `toLowerCase(): String`, `toUpperCase(): String` | Locale-independent Unicode case mapping |
| Trimming | `trim()`, `trimStart()`, `trimEnd()` | Remove Unicode whitespace from both ends or one end |
| Blank checks | `isBlank(): Boolean` | True when the string is empty or contains only whitespace |
| Replacement | `replace(old: String, replacement: String): String` | Literal, non-overlapping replacement of every occurrence |
| Lines | `lines(): Array<String>` | Split on `\n`, `\r\n`, or `\r`; a terminal line break does not create an extra empty line |
| Parsing | `toInt(): Option<Int>`, `toFloat(): Option<Float>` | Full-string parse; `None` for invalid or out-of-range input |
| Joining | `String.join(separator: String, values: Iterable<String>): String` | Namespace helper for joining a sequence |

`RegexError` is a standard-library sum type:

```zeron
public type RegexError = InvalidPattern(message: String);
```

It is declared in `zeron.lang` beside the string operations, not in the compiler. A regex failure is
an ordinary `Result.Err`, not an exception.

### Splitting semantics

`split` uses a literal separator, not a regular expression. For a non-empty separator, it splits at
each non-overlapping occurrence and preserves empty fields, including a trailing empty field:

```zeron
"a,b,".split(",")   // ["a", "b", ""]
"".split(",")       // [""]
```

The `Char` overload is the same operation with a one-character separator. The empty-separator rule
is deliberately explicit:

- `"abc".split("")` splits into Unicode scalar values, `["a", "b", "c"]`;
- `"".split("")` returns an empty array;
- a malformed surrogate is normalized to U+FFFD consistently with the scalar `String` API.

`splitRegex` uses the platform regex dialect and returns `Result<Array<String>, RegexError>`.
Invalid patterns produce `RegexError.InvalidPattern` with the platform message. Its empty-match
behavior is the regex engine's documented behavior; unlike literal `split`, it is not specified by
this proposal.

### Character access and `Char`

`Char` is exactly one Unicode scalar value, so `charAt` cannot return a raw UTF-16 surrogate.
`charAt` uses a UTF-16 code-unit index, matching `length` and `substring`. If the index points at
the first unit of a valid surrogate pair, the pair is returned as one scalar; if it points at the
second unit, the result is `None`. An unpaired surrogate is normalized to U+FFFD. An index outside
the string also returns `None`.

`at` is an alias for `charAt`. It exists because collection-style code commonly reads `at(index)`,
while `charAt` is the familiar text spelling. Both return the same `Option<Char>` and have the same
index and malformed-text rules.

### Case, trimming, replacement, and lines

`toLowerCase` and `toUpperCase` use locale-independent Unicode mapping, so the result does not depend
on the host locale. They do not perform normalization or grapheme-aware casing.

`trim`, `trimStart`, and `trimEnd` remove Unicode whitespace. `isBlank` is true when the string is
empty or contains only that whitespace. `replace` is literal and non-overlapping; it does not accept
a regex. `lines` recognizes `\n`, `\r\n`, and `\r`; a terminal line break does not add an extra
empty line, while an empty input produces an empty array.

### Parsing and joining

`toInt` accepts an optional leading sign followed by one or more decimal digits, with no surrounding
whitespace, and returns `None` on an invalid character or an out-of-range value. `toFloat` accepts
the ordinary decimal and exponent forms and returns `None` on an invalid or non-finite form. Neither
operation trims its input; callers use `trim()` when surrounding whitespace is acceptable.

`String.join` is a namespace function, not a receiver method:

```zeron
String.join(", ", names)
```

It accepts `Iterable<String>`, joins the elements, and inserts the separator between them, with no
prefix or suffix. It does not add implicit `toString()` conversion for arbitrary element types;
callers map to strings first.

### API index and separate compilation

Standard-library extensions and namespaces are exported through the ordinary API-index path. A
consumer resolves a string operation from the same source metadata it uses for any other library
extension. It must not reconstruct the operation from a compiler special case or from
`java.lang.String`'s class file.

Intrinsic type metadata remains compiler-owned and versioned separately. The library API version
changes when the public inventory changes; the intrinsic ID catalogue changes only when a new syntax
or lowering primitive is introduced. Separate-compilation tests must cover a consumer compiled
against a library that exports an intrinsic-type extension and then run against a compatible
runtime.

### Member lookup and conflicts

Standard-library extensions participate in ordinary extension lookup. A user extension or witness
with the same member name follows the existing precedence and ambiguity rules; the standard library
does not receive a hidden priority merely because its receiver is intrinsic. If a new operation
would make an existing common call ambiguous, the standard-library addition needs a compatibility
review rather than a compiler exception.

## Compatibility and impact

The inventory is a standard-library API addition. It is source-compatible for programs that do not
already define an ambiguous extension with the same name. It does not change the JVM representation
of `String`, intrinsic identity, literal behavior, or runtime casts.

The proposal does not add a new compiler ABI. It adds standard-library API-index entries and a
library API version bump. Existing intrinsic IDs remain stable; no ID is removed or repurposed. The
new `RegexError` type is a library type, not a compiler intrinsic.

Tooling should show standard-library extensions on intrinsic receivers through the normal extension
metadata, including hover, completion, go-to-definition, and documentation. It should not label a
`zeron.lang.String` module as a class or offer a constructor for it.

The word-count program should compile against this inventory without a hand-written character loop:

```zeron
fn wordCount(text: String): Map<String, Int> {
    let counts = HashMap<String, Int>.empty();
    for (let word in text.toLowerCase().split(' ')) {
        counts.put(word, counts.getOrElse(word, 0) + 1);
    }
    return counts;
}
```

## Alternatives

- **Declare a class in `zeron.lang.String`.** This gives a familiar namespace but conflicts with the
  intrinsic type's identity or creates a second type. Rejected; a module/namespace is sufficient.
- **Add a compiler method for every missing operation.** This makes the compiler the library owner
  and grows the intrinsic registry for ordinary API work. Rejected.
- **Use only external Java bindings.** This exposes Java's regex and platform-specific behavior and
  bypasses Zeron result and documentation conventions. Rejected as the public model.
- **Add only `split`.** This fixes the immediate word-count split but leaves case conversion,
  character access, trimming, and replacement missing. Rejected as too narrow.
- **Mirror all of `java.lang.String`.** This would expose locale-sensitive, regex-heavy, and
  encoding-specific behavior without a coherent Zeron API. Rejected.
- **Keep the current implicit policy.** It leaves each gap to an ad-hoc decision and makes API
  ownership unclear. Rejected.

## Implementation and validation

The policy is implemented by documenting the ownership rule, adding the `String` extensions to
`zeron.lang.string`, and ensuring the API index exports them as ordinary extensions. The first
delivery should include the word-count program as an integration example.

Validation should cover:

- `split` on ordinary, empty, leading-separator, trailing-separator, repeated-separator, and
  empty-separator inputs;
- `split` with `String` and `Char` separators;
- `splitRegex` success, invalid patterns, and empty matches;
- `charAt`/`at` at ASCII, supplementary-scalar, boundary, out-of-range, and unpaired-surrogate
  positions;
- locale-independent lowercase and uppercase conversion;
- trimming of Unicode whitespace, blank checks, literal replacement, and line endings;
- `toInt`/`toFloat` valid, invalid, signed, exponent, and range-boundary inputs;
- `String.join` with empty, singleton, and multi-element inputs;
- use from a separately compiled consumer through the library index;
- hover, completion, and go-to-definition on intrinsic receivers;
- no new intrinsic ID and no `class String` declaration;
- existing string operations and external helper bindings remaining unchanged;
- a user extension with the same name following the ordinary ambiguity rules;
- the standard-library API version bump and release notes;
- the word-count program compiling and running against the new inventory.

## Open questions

- Should `split` return `Array<String>` or `List<String>`? The initial inventory uses `Array` to match
  the intrinsic collection surface; a later library-wide convention may change it.
- Should `charAt` return `Option<Char>` or a direct `Char` with an array-style bounds failure? The
  safe `Option` form is chosen here because `Char` excludes lone surrogates.
- Should `at` remain an alias of `charAt`, or should one name be deprecated before the API ships?
- Which regex dialect and replacement syntax should `splitRegex` document as stable? The initial
  choice is the platform regex engine with a library-owned `RegexError`.
- Should `toInt` and `toFloat` accept leading/trailing whitespace, or should callers always trim?
- Should `String.join` accept `Iterable<String>` only, or also a transform for arbitrary elements?

## Decision

Accepted on 2026-11-14 and marked `Candidate` for the `0.8.0` normalization bundle.

The settled design is:

- intrinsic types keep compiler-owned identity, literals, storage, casts, and runtime tests;
- their public operations are declared by standard-library source in canonical `zeron.lang`
  modules as extensions and namespaces, not as a second class;
- ordinary operations do not add intrinsic IDs; IDs remain for syntax and lowering primitives;
- the initial `String` inventory includes literal `split`, `splitRegex`, `charAt`/`at`,
  locale-independent case conversion, trimming, blank checks, literal replacement, `lines`, simple
  integer/float parsing, and `String.join`;
- `split` preserves empty fields and has an explicit empty-separator rule;
- `splitRegex` returns `Result<Array<String>, RegexError>` rather than throwing;
- standard-library extensions use ordinary API-index export, member lookup, and separate
  compilation;
- the word-count program is the integration target for the inventory.
