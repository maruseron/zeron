## Abstract

Complete the flow-refinement story for conditions and remove routine `this.` noise from instance
code.

The proposal has two connected parts:

- `is` and `matches` transfer refinement through chained `and`, `or`, and `not` conditions,
  including `matches` payload bindings and stable read-only member paths;
- an unqualified field or property read inside an instance body resolves to the implicit `this`
  receiver when ordinary lexical lookup finds no closer declaration.

The first part makes guard conditions express a sequence of type tests and destructuring steps
without repeated casts. The second makes those conditions readable when the tested values are the
receiver's own fields or properties.

## Motivation

The red-black tree example exposes both problems:

```zeron
case T<A>.of(_, T<A>.of(_, T<A>.of(_, a, x, b), y, c), z, d)
    if (left is T<A>) and ((left as? T<A>).left is T<A>)
    and ((left as? T<A>).color is Color.R)
    and (((left as? T<A>).left as? T<A>).color is Color.R)
    -> ...
```

The condition knows that `left` is a `T<A>` after the first test, but the later clauses repeat
`as?` because the refinement does not carry through the chain or through the member path. That is
both noisy and dangerous: a safe cast is nullable, so every repeated cast should require a null
check, yet the code reads as if the value were already proven.

The same class body also writes `this.color`, `this.left`, and similar receiver-qualified reads
throughout methods. In a language where fields and properties are already members of the implicit
receiver, the qualification adds visual noise without adding information. The problem is worse in
guards, where the condition is already long.

`matches` has the same limitation in a different form. It can bind payloads in a direct `if` or
`while` condition, but it is not supported in a chained condition such as
`shape matches Circle(radius) and radius > 0`. Users must split the condition into nested `if`
statements or fall back to `match`.

## Goals

- Propagate `is` facts through `and`, `or`, and `not` with the existing short-circuit rules.
- Support `matches` as a condition operand in the same compositions, including payload bindings on
  the successful path.
- Refine stable read-only member paths, not only local variables and parameters.
- Make `matches` destructuring usable in chained conditions without leaking bindings onto paths
  where the match did not succeed.
- Allow unqualified reads of fields and properties on the implicit `this` receiver.
- Keep lexical locals, parameters, and pattern bindings authoritative over member names.
- Keep writes explicit: `this.x = ...` remains required.
- Add no runtime checks, descriptors, or changes to generated representations.

## Non-goals

- General-purpose pattern matching in arbitrary expression positions.
- Refining mutable fields, mutable properties, array slots, call results, or effectful getters.
- Inferring a declared union type or a general subtype lattice.
- Changing the existing precedence of locals, parameters, and pattern bindings.
- Implicit writes, implicit method declarations, or implicit constructor arguments.
- Changing `as?` semantics; the nullable-result correction is [ZEP-0132](./ZEP-0132.md).
- Refining through lambda bodies or across closure boundaries.

## Proposal

### Chained `is` and `matches`

Conditions are resolved with the existing short-circuit transfer rules, extended consistently to
`is` and `matches`:

- `A and B`: resolve `B` under the true facts of `A`; the true outcome combines both true paths.
  The false outcome joins the paths where `A` is false and where `A` is true but `B` is false.
- `A or B`: resolve `B` under the false facts of `A`; the true outcome joins the paths where `A` is
  true and where `A` is false but `B` is true. The false outcome requires both operands false.
- `not A`: swap the true and false outcomes.

This applies to `is`, `is not`, `is null`, `is not null`, and `matches` when they occur as condition
operands. The condition may appear in a statement-form `if`, an `else if`, a `while`, or a
value-producing `if`.

A successful `is T` refines a stable path to non-null `T` on the true path. A successful `matches`
refines the tested sum value to the matched case on the true path and makes its payload bindings
available to the rest of that path:

```zeron
if (shape matches Shape.Circle(radius) and radius > 0) {
    drawCircle(radius);
}
```

`radius` is in scope for the second operand and the true branch, not for the false branch or for
code after the condition. A binding introduced in the left operand of `and` is available in the
right operand and the combined true path. A binding introduced in an `or` operand follows the
existing OR-pattern rule: every alternative must bind the same names with compatible types, and the
bindings are available only on the joined true path.

For a direct `matches` test on a closed sum, the false path keeps the existing negative-complement
rule when the remaining alternatives identify a case. Chained negation and composition use the
same outcome transfer; they do not invent complements for `is` tests or for open class hierarchies.

### Stable member paths

Refinement applies to a stable path, not only to a bare local:

- the root is a local, a parameter, or `this`;
- every segment is a read-only storage-backed member: a final field or a sum payload property;
- no segment is a mutable field, a mutable property, an array slot, a call result, or a property
  with a custom accessor;
- the root binding is not reassigned between the test and the use.

A path such as `left.left.color` qualifies when `left` is a final field or sum payload and each
intermediate member is also stable. The compiler records a flow fact keyed by the path's binding
and member chain, not by source spelling alone. A reassignment of the root, or any write that could
change a segment, invalidates the fact. Because only read-only storage-backed members are refined,
ordinary method calls cannot silently replace the tested value.

A test of an effectful getter or a mutable member still returns a Boolean and still short-circuits,
but it does not refine a later read of that member. The programmer can bind the value to a local
first:

```zeron
let current = this.currentNode();
if (current is T<A> and current.left is T<A>) {
    use(current.left);
}
```

This keeps the refinement sound without requiring purity analysis for arbitrary getters.

### The tree condition

The red-black tree guard can be written without repeated casts:

```zeron
case T<A>.of(_, T<A>.of(_, T<A>.of(_, a, x, b), y, c), z, d)
    if (left is T<A>
        and left.left is T<A>
        and left.left.color is Color.R
        and left.left.left is T<A>
        and left.left.left.color is Color.R)
    -> T.new(Color.R(), T.new(Color.B(), a, x, b), y, T.new(Color.B(), c, z, d));
```

Each `is` test refines the next stable path. The compiler still inserts a runtime class test for
each `is`; it does not assume that a successful test on one path proves a different path. The
difference is that the source no longer needs a cast after a test that already established the
type.

### Implicit receiver reads

Inside a body with an instance receiver, an unqualified field or property read resolves to the
implicit `this` receiver when ordinary lexical lookup finds no closer declaration:

```zeron
class Node<A> {
    color: Color;
    left: Tree<A>;
    right: Tree<A>;

    public fn isRed(): Boolean = color is Color.R;
    public fn leftIsRed(): Boolean = left is T<A> and left.color is Color.R;
}
```

`color` and `left` are reads of `this.color` and `this.left`. A local, parameter, or pattern binding
with the same name shadows the member, exactly as it would shadow a top-level declaration today.
If ordinary lookup finds a top-level declaration, that declaration still wins; implicit receiver
lookup is a fallback for an otherwise unresolved read, not a new shadowing rule.

Only reads are implicit. Assignment and compound assignment still require an explicit receiver:

```zeron
this.left = replacement; // required
left = replacement;      // rejected or resolves to a local, never an implicit field write
```

An unqualified property read invokes the property's getter normally. Implicit receiver access does
not promise purity or make a custom getter stable; it only removes the `this.` spelling. A nullable
member keeps its normal null rules, and a member read on a nullable receiver still requires a null
check or safe navigation.

Implicit member lookup is limited to fields and properties. Method calls, nested type names, and
namespace members keep their existing resolution rules. If a class somehow exposes two members with
the same name, the read is ambiguous and diagnosed rather than selecting one.

### Scope

Implicit receiver reads apply to bodies that already have an instance receiver: class methods,
property accessors, initializers, contract defaults, and extension bodies. They do not apply to
top-level functions, static functions, or namespace functions without a receiver.

Stable-path refinement applies at condition boundaries. It does not cross a lambda boundary, a
loop backedge that may write the root, or a call that can reassign the root binding. The existing
branch-join rules retain only facts valid on every normally completing path.

## Compatibility and impact

The change is source-additive. Existing programs keep their current meaning:

- lexical lookup still wins over implicit receiver lookup;
- writes still require `this`;
- existing `as?` result types are unchanged by this proposal;
- runtime checks are still emitted for `is` and `matches`; no new descriptor or cast is introduced;
- the JVM representation, field layout, and method descriptors do not change.

Some previously rejected conditions become valid. Some previously unresolved member reads become
valid through the implicit receiver fallback. Code that deliberately used `this.x` continues to
work. There is no migration requirement.

Tooling should complete implicit members with a marker that distinguishes them from locals, show
the resolved `this` receiver in hover, and highlight stable-path facts consistently. The formatter
must not rewrite explicit `this.` reads into implicit ones or vice versa.

## Alternatives

- **Keep refinement limited to bare locals and direct conditions.** This is simpler but leaves
  common guard chains full of redundant casts and forces nested `if` statements for `matches`.
  Rejected.
- **Refine every property read, including custom getters.** This is convenient but unsound when a
  getter returns a different value on each call. Rejected; only stable storage-backed members are
  refined.
- **Refine mutable fields after a call.** A call can change the field, so the fact would not be
  stable. Rejected.
- **Require `this.` everywhere.** This preserves the current spelling but leaves the noise that
  motivated the proposal. Rejected.
- **Allow implicit writes as well as reads.** This makes assignment ambiguous and makes it harder to
  see when a mutable field or property setter is invoked. Rejected for this slice.
- **Introduce a declared union type.** Flow-only alternatives are sufficient and avoid a much
  larger type-system change. Rejected.

## Implementation and validation

Likely stages:

1. Extend condition resolution so `is` and `matches` produce and consume facts through the existing
   `and`/`or`/`not` transfer machinery.
2. Add `matches` payload-binding scopes for chained condition operands, including OR binding-set
   compatibility and branch-local cleanup.
3. Represent stable member paths in flow facts. Validate root stability, member storage, and
   invalidation on writes; exclude custom getters and call results.
4. Add implicit receiver fallback to unqualified field/property reads in instance bodies while
   preserving lexical precedence.
5. Update diagnostics for ambiguous member reads, nullable receiver access, and escapes of
   condition-bound payloads.
6. Update the language server for hover, completion, definition, and references on implicit member
   reads and chained bindings.
7. Add guide examples and a user-facing change note when the behavior lands.

Validation should cover:

- `is` chains with locals, parameters, `this` fields, and stable nested paths;
- `matches` chains with payload bindings used in later operands and the true branch;
- `or` chains with equivalent and mismatched binding sets;
- `not`, `else if`, `while`, and value-producing `if` placements;
- invalidation after assignment, mutable field writes, and calls that may change a root;
- custom getters and mutable members remaining unrefined;
- implicit reads shadowed by locals, parameters, and pattern bindings;
- implicit reads of fields, properties, nullable members, and contract defaults;
- implicit writes remaining rejected;
- unchanged runtime tests and generated bytecode for existing programs;
- the full test suite after focused flow, resolver, emitter, LSP, and formatter tests.

## Open questions

- Should a later purity or `readonly` annotation allow custom getters to participate in stable-path
  refinement?
- Should implicit method calls be included, or do method calls already have sufficient unqualified
  resolution?
- Should a local that shadows a member produce a warning, or is silent lexical precedence enough?
- Should stable paths include `this` inside extension bodies, where the receiver may be a value
  rather than a class instance?

## Decision

Accepted on 2026-11-14 and marked `Candidate` for the `0.8.0` normalization bundle.

The settled design is:

- `is` and `matches` transfer facts through `and`, `or`, and `not` with existing short-circuit
  semantics;
- `matches` payload bindings follow the successful path and OR binding-set rules;
- refinement covers stable read-only member paths rooted at locals, parameters, or `this`, and
  excludes mutable members, array slots, call results, and custom getters;
- unqualified field and property reads resolve to the implicit `this` receiver only when ordinary
  lexical lookup finds no closer declaration;
- implicit writes remain prohibited;
- no runtime representation or descriptor changes are introduced.
