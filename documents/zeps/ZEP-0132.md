# ZEP-0132: Nullable Safe-Cast Correction

| Field | Value |
| ----- | ----- |
| Status | Accepted |
| Author | Marcelo Rodríguez |

| Updated | 2026-11-14 |

## Abstract

Make `as?` consistently produce a nullable result. A safe cast of a nullable source must not behave
as a non-null cast to `T`, and a nullable target spelling `T?` must not lose its nullability.

The rule is simple: for any target type `T`, `value as? T` has type `T?`; if the target is already
`T?`, the result is still `T?`. The operator returns null when the source is null or when the
runtime test fails. It never asserts non-nullness and never refines the source binding.

This is a corrective proposal. The documented language already says `as?` returns `T?`; the defect
is that the implementation can behave as if it returned `T` for a nullable value. That is dangerous
because it lets a member access follow a cast without a null check.

## Motivation

Safe casts are used to turn an uncertain value into a nullable view:

```zeron
let node: T<A>? = value as? T<A>;
if (node != null) {
    use(node.left);
}
```

The result must be `T<A>?`. If the compiler treats it as `T<A>`, the null check is no longer
required, and a null source can reach `node.left`. The same problem appears when the target is
written with a nullable annotation:

```zeron
let node: T<A>? = value as? T<A>?;
```

A safe cast to `T?` is still a safe cast: it tests the non-null base type and returns null on
mismatch. It must not strip the target's `?` and produce a non-null `T`.

The red-black tree example uses safe casts inside repeated conditions:

```zeron
((left as? T<A>).left is T<A>)
```

If `left as? T<A>` were non-null, that expression would compile even though the source could be
null or the wrong case. The correct rule forces either a null check, safe navigation, or a better
flow refinement. ZEP-0131 removes the need for repeated casts in that example; this proposal makes
the remaining safe casts sound.

## Goals

- Define `as?` to return a nullable result for every target type.
- Preserve `T?` when the target is already nullable; do not add or remove more than one nullability
  layer.
- Return null for a null source and for a failed runtime test.
- Keep the runtime test on the erased non-null base type.
- Prevent member access on the result without a null check or safe navigation.
- Keep `as?` from refining the source binding.
- Fix the defect immediately, ahead of the broader 0.8.0 work.

## Non-goals

- Changing checked `as` or adding a new unchecked cast operator.
- Reifying generic arguments or changing ZEP-0053's static-proof rules.
- Adding a `Result`-returning cast; that remains a possible future API.
- Refining the source binding after a safe cast.
- Changing nullability syntax, nullable assignment, or safe navigation.
- Making a successful `as?` test count as a non-null flow proof for a different expression.

## Proposal

### Type rule

For a source expression of any type and a target type `T`:

```text
typeof(value as? T) = nullable(T)
```

where `nullable(T)` is `T` if `T` is already nullable and `T?` otherwise. Examples:

```zeron
let a: Int? = anyValue as? Int;       // Int?
let b: String? = maybeText as? String; // String?
let c: Node? = maybeNode as? Node?;   // Node?, not Node
```

A safe cast never has a non-null result type. The only way to use the result as a non-null value is
to prove it non-null with a null check, an `is not null` test, safe navigation, or an explicit
non-null assertion where that operator is otherwise allowed. The cast itself is not such a proof.

### Runtime behavior

`value as? T` evaluates `value` once. If the source is null, the result is null. Otherwise the
compiler tests the non-null base of `T` with the same runtime test used by `is` and checked `as`.
On success, the value is cast to that base and returned as a nullable result. On failure, the result
is null.

The operation does not throw for a failed test. It does not inspect generic arguments; applied
targets remain subject to the static proof rules in ZEP-0053. A target that cannot be tested at
runtime is rejected before emission, just as it is for `is` and checked `as`.

For a primitive target such as `Int`, the result is the boxed nullable form `Int?`; the success path
unboxes only when the surrounding context requires a primitive and the value has been proven
non-null. For `Unit`, the result is `Unit?` and a failed test returns null rather than a fabricated
unit value.

### Member access and flow

A member access on a safe-cast result follows the ordinary nullable rules. This is rejected:

```zeron
let node = value as? T<A>;
use(node.left); // nullable receiver; requires a check or safe navigation
```

These are accepted:

```zeron
let node = value as? T<A>;
if (node != null) use(node.left);

use((value as? T<A>)?.left);
```

The safe cast does not refine `value`. A later use of `value` still has its declared type and flow
facts; only the result binding carries the nullable cast type. A successful `as?` does not prove
that a second evaluation of the source would produce the same value.

### Parser and normalization

`as?` is parsed as the `as` operator followed by the `?` modifier, then a complete type. A nullable
target type is accepted and normalized:

```zeron
value as? T?   // result T?
value as? T    // result T?
```

The result has one nullable layer, never `T??` or a non-null `T`. A target that is already a
nullable type parameter or nullable reference follows the same normalization. The parser must not
attach the `?` to the expression instead of the target type.

### Immediate correction

This is a correctness fix, not a feature that waits behind the rest of the refinement work. The
implementation should:

1. Make the resolver compute the result as `nullable(target)` for every safe cast.
2. Make the emitter test the non-null base type, return null on null or mismatch, and set the
   emitted expression type to the nullable result.
3. Ensure member lookup and assignment reject a nullable safe-cast result without a proof.
4. Add regression tests for nullable sources, nullable targets, generic applied targets, primitives,
   `Unit`, classes, contracts, and null literals.

The fix should land before or alongside ZEP-0131's refinement changes so that new chained conditions
cannot accidentally rely on an unsound cast result.

## Compatibility and impact

The documented type of `as?` is already `T?`; this proposal aligns the implementation with that
contract. Programs that used `as?` as if it were non-null were relying on unsound behavior and may
need a null check or a checked `as` after a proof. That source break is intentional.

Existing checked `as`, `is`, flow refinement, generic target proofs, and runtime casting behavior
are unchanged. No JVM representation, descriptor, or library metadata changes are required. The
diagnostic for a nullable receiver already exists; the fix makes safe-cast results participate in
it consistently.

## Alternatives

- **Keep the current behavior and document `as?` as a non-null cast.** This is unsound for null or
  mismatched sources and defeats the purpose of a safe cast. Rejected.
- **Make `as?` return `T` and add a separate `as!` for nullable results.** This reverses the useful
  default and duplicates ZEP-0089's unchecked-cast space. Rejected.
- **Return a `Result<T, CastError>`.** This preserves the failure reason but is a larger API and
  does not fix the existing nullable contract. Deferred.
- **Require every `as?` to be immediately null-checked syntactically.** This is more restrictive
  than necessary; a nullable value can be stored, passed, or safely navigated. Rejected.
- **Add a non-null assertion to the cast syntax.** Zeron already has a separate non-null assertion
  path; conflating it with `as?` would make the dangerous behavior the default. Rejected.

## Implementation and validation

The change is localized to safe-cast resolution and emission, plus the nullable-receiver checks that
consume the result.

Validation should cover:

- `value as? T` from `T`, `T?`, `Any`, `Any?`, and `null` sources;
- `value as? T?` producing `T?`, not `T` or `T??`;
- a successful cast, a failed cast, and a null source returning null;
- member access on the result rejected without a null check or safe navigation;
- the same access accepted after a null check or with safe navigation;
- generic applied targets following ZEP-0053 and still yielding a nullable result;
- primitive and `Unit` targets;
- generic type parameters with nullable bounds;
- no refinement of the source binding;
- bytecode producing a null result rather than throwing on mismatch;
- the full test suite after focused resolver, emitter, nullability, and LSP tests.

## Open questions

- Should `as?` on a target that is already `Any?` be simplified to the source's nullable view, or
  remain a runtime test against `Any`?
- Should a future `Result`-returning cast distinguish null input from a type mismatch?
- Should the compiler warn when an `as?` result is immediately asserted non-null, since a checked
  `as` or flow proof may express the intent more directly?

## Decision

Accepted on 2026-11-14 and marked `Candidate` for the `0.8.0` normalization bundle.

The settled design is:

- `as?` always returns a nullable target type, including when the target is written `T?`;
- null input returns null, a failed runtime test returns null, and no `ClassCastException` is thrown;
- the runtime test uses the erased non-null base type under ZEP-0053's existing proof rules;
- the result must be null-checked or safely navigated before member access;
- the safe cast does not refine the source binding;
- the correction is an immediate implementation priority within the bundle.
