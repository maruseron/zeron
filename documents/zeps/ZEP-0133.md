## Abstract

A lambda whose parameters have no annotations and no expected function type currently cannot use an
operator such as `+` or `<` because the compiler has no type at which to resolve the operator. This
proposal extends the existing immutable `let`-bound generalization rule so that an uncontextualized
typeless lambda can infer a rank-1 scheme with numeric and comparison operator constraints from its
body.

The motivating results are:

```zeron
let add = (a, b) -> a + b;
let less = (a, b) -> a < b;
```

The inferred scheme is conceptually:

```text
<T: Numeric<T>> (T, T) -> T
<T: Comparable<T>> (T, T) -> Boolean
```

`add` is not specialized to `Int` or `Float` at its definition. Each use instantiates `T` and
resolves `Numeric<T>` independently, so `add(1, 2)` and `add(1.5, 2.5)` both work, and a user-defined
numeric type can be used when it supplies the necessary witness. Likewise, `less` uses the
`Comparable<T>` evidence for its instantiated type.

This is deliberately not a general type-class search or a full Hindley–Milner solver. It applies to
directly let-bound, uncontextualized lambdas and to operators with one unambiguous generic contract
mapping. Expected types, annotated parameters, and ordinary contextual inference continue to take
precedence. String concatenation, equality, logical and type-test operators, mixed-type promotion,
and arbitrary lambda positions remain outside the initial rule.

## Motivation

Zeron already generalizes safe immutable `let`-bound lambdas for identity and constant-result
bodies. [ZEP-0003](./ZEP-0003.md) extends that to applied-contract bounds inferred from direct
contract-member use and bounded generic callees. Operator constraints were explicitly left out of
that proposal, so a reusable arithmetic or ordering callback still needs an explicit parameter type
or a named generic function:

```zeron
let addInt = (a: Int, b: Int) -> a + b;
let addFloat = (a: Float, b: Float) -> a + b;
```

That is unnecessarily repetitive when the body itself fully determines the requirement: `+` is the
numeric addition operator, both operands and the result must have the same type, and `<` requires
ordering evidence for two operands of the same type. The natural user expectation is that
`(a, b) -> a + b` means “a function that adds two values of some numeric type” and
`(a, b) -> a < b` means “a function that orders two values of some comparable type”, not “the
compiler must choose a concrete type now.”

The current limitation is especially visible in generic APIs that accept a callback. A lambda with
an expected function type already receives contextual parameter types and works. The gap appears
when the lambda is stored first:

```zeron
let add = (a, b) -> a + b;
let combine = add;
let total = combine(1, 2);
```

Without a scheme, the compiler cannot resolve `a + b` at the `let`. The only alternatives today are
to annotate one concrete type, losing reuse, or to write a generic named function. Both are more
ceremony than the operation warrants.

The fix should not invent a default type. Choosing `Int` would make `add(1.5, 2.5)` fail for a
reason unrelated to the user's intent, and choosing `Float` would make exact integer use lossy.
Likewise, choosing a witness at definition time would prevent a later use from selecting a different
numeric or ordered type. The inferred requirement must stay generic and be resolved per use.

## Goals

- Infer fresh type variables for unannotated lambda parameters when no expected function type is
  available.
- Infer the numeric or comparison contract required by operator use in a directly let-bound lambda
  body.
- Unify the operands of same-type operators into one type variable; unify the numeric result with
  the operands, and keep comparison results `Boolean`.
- Build a rank-1 scheme with a bound such as `T: Numeric<T>` or `T: Comparable<T>` rather than a
  concrete default type.
- Instantiate the scheme independently at each use and resolve the required evidence there.
- Reuse the existing constrained-lambda template and evidence-bound closure machinery.
- Preserve explicit parameter annotations and expected-type inference; they take precedence over
  inference from the body.
- Combine operator constraints with the applied-contract constraints already inferred by
  ZEP-0003.
- Produce a direct diagnostic when a use has no available witness or when evidence is ambiguous.
- Leave runtime representation, function-shape identity, and the public API index unchanged.

## Non-goals

- Full Hindley–Milner inference, arbitrary unification, or a general-purpose constraint solver.
- Inferring constraints from call sites rather than the lambda body.
- Defaulting an unresolved numeric or ordered type to `Int`, `Float`, `String`, or any other
  concrete type.
- Inferring from every operator. String concatenation, equality, logical, and type-test operators
  keep their existing contextual rules in this slice.
- Mixed-type arithmetic, mixed-type comparison, or numeric promotion. Both operands of an inferred
  operator remain the same type; arithmetic results remain that type, and comparison results are
  `Boolean`.
- Inferring arbitrary member calls that are unrelated to a declared contract. ZEP-0003's existing
  contract-member rule remains the boundary for those.
- Generalizing mutable or reassignable bindings.
- Generalizing lambdas in arbitrary expression positions, returned lambdas, assignments, or
  library-exported values. The initial rule stays with directly initialized immutable local `let`
  bindings.
- Rank-2 or higher-rank inference, implicit binder lists, or explicit `forall`.
- Effect-polymorphic schemes or inferred raised effects.
- Runtime type inspection, dynamic witness search, or a new ABI for evidence.
- Changing the meaning of an explicitly typed lambda or an existing expected function type.

## Proposal

### Eligibility

The initial rule applies when all of the following hold:

1. The lambda is written directly as the initializer of an immutable local `let` binding.
2. There is no expected function type for that initializer.
3. At least one parameter is unannotated.
4. The body contains an operator use covered by the mapping below, or an existing ZEP-0003
   contract-member use that contributes a constraint.

A lambda with an expected function type keeps the existing contextual path. Its parameters are
checked against that type and no new scheme is inferred. A lambda with every parameter annotated
also keeps the existing path; if its body uses an operator, the annotated types must already
provide the required evidence.

If some parameters are annotated and some are not, the annotated types constrain the fresh
variables during body checking. The scheme quantifies only the variables that remain unresolved.
A parameter that is still unresolved after checking requires an annotation and is diagnosed rather
than defaulted.

The binding must be immutable. A reassignable binding or a mutable lambda value is not generalized,
because a later assignment or mutation could make different uses observe incompatible
instantiations. Captured values are fixed in the scheme exactly as in ZEP-0003; only type variables
independent of the captured environment are quantified.

### Operator mapping

For an uncontextualized lambda, operator checking uses these rules:

| Form | Inferred constraint | Type relationship |
| --- | --- | --- |
| `left + right` | `Numeric<T>` | `left`, `right`, and result are `T` |
| `left - right` | `Numeric<T>` | `left`, `right`, and result are `T` |
| `left * right` | `Numeric<T>` | `left`, `right`, and result are `T` |
| `-value` | `Numeric<T>` | operand and result are `T` |
| `left / right` | `Fractional<T>` | `left`, `right`, and result are `T` |
| `left < right` | `Comparable<T>` | `left` and `right` are `T`; result is `Boolean` |
| `left <= right` | `Comparable<T>` | `left` and `right` are `T`; result is `Boolean` |
| `left > right` | `Comparable<T>` | `left` and `right` are `T`; result is `Boolean` |
| `left >= right` | `Comparable<T>` | `left` and `right` are `T`; result is `Boolean` |

The mapping uses the existing numeric operator contract from ZEP-0071 and the relational contract
from `zeron.lang.Comparable<T>`. It does not add promotion, mixed operand types, or a second
overload for string concatenation. When both operands are unresolved, the compiler deliberately
selects the generic numeric mapping for `+` rather than leaving the lambda ambiguous; a caller that
needs string concatenation supplies an annotation or an expected type. If the operator is used on
types that are already concrete, normal existing checking applies and inference adds no hidden
requirement.

The inferred constraint is an applied contract bound on the fresh type variable. A body may
accumulate several constraints; they are combined on the same scheme. `Fractional<T>` already
requires `Numeric<T>`, so `left / right` does not also need a separate `Numeric<T>` requirement.
`Comparable<T>` is independent of `Numeric<T>` and `Eq<T>`: ordering does not imply equality, so a
body that also uses `==` or `!=` needs the corresponding `Eq<T>` constraint separately.

### Literal operands

Numeric literals use the existing context-directed literal rules. In `(a) -> a + 1`, the literal
`1` is checked against the same `T` as `a`, with the existing exact-integer conversion through
`Numeric<T>.fromInteger` rather than an eager `Int` default. The existing literal behavior for
explicitly typed and contextually typed code does not change.

If a literal cannot be represented by the inferred numeric type at a particular use, the existing
literal/conversion diagnostic applies at that use. The lambda definition does not select a concrete
carrier merely because a literal appears in its body.

### Resulting scheme

For `(a, b) -> a + b`, the inferred scheme is:

```text
<T: Numeric<T>> (T, T) -> T
```

For `(a, b) -> a / b`, it is:

```text
<T: Fractional<T>> (T, T) -> T
```

For `(a, b) -> a < b`, it is:

```text
<T: Comparable<T>> (T, T) -> Boolean
```

These are rank-1 schemes local to the binding. They are not serialized into the library API index
and do not make the lambda a top-level polymorphic value. Each use instantiates fresh variables,
selects evidence using ordinary witness selection, and specializes the closure to the selected
erased function shape. A use that resolves `T = Int` and a use that resolves `T = Float` produce
different specializations and do not mutate the stored scheme.

The existing ZEP-0003 template path already caches evidence-bound closures per function shape and
selected evidence for the lifetime of the binding. This proposal adds operator-derived bounds to
that path; it does not introduce a second generic-lambda runtime mechanism.

### Interaction with expected types and annotations

A declared function type remains authoritative:

```zeron
let add: (Int, Int) -> Int = (a, b) -> a + b;
```

Here `a` and `b` are `Int` from the expected type, `+` uses the built-in numeric behavior, and no
scheme is inferred. A lambda parameter annotation likewise fixes that parameter:

```zeron
let add = (a: Float, b: Float) -> a + b;
```

If an expected type leaves a parameter unresolved, ordinary contextual inference still tries to
resolve it from the body. This proposal only adds constraints when the lambda would otherwise have
no expected type and the binding is eligible for ZEP-0003-style generalization.

### String concatenation and other operators

`String + value` is an existing intrinsic operation with `Display` behavior and takes precedence
when the left operand is known to be `String`. It is not part of this inference rule. A typeless
lambda whose body is `(a, b) -> a + b` chooses the generic numeric operator path because both
operands are unresolved; it is not an inferred string-concatenation function. Consequently:

```zeron
let add = (a, b) -> a + b;
let joined = add("a", "b"); // error: no Numeric<String> evidence
```

The string case remains available through explicit annotation or an expected function type:

```zeron
let join = (a: String, b: String) -> a + b;
```

This boundary is deliberate. If the compiler tried to infer both `Numeric<T>` and a left-String
`Display` path from the same unresolved body, it would need an overload/union constraint and would
have to choose between incompatible schemes. The initial rule prefers the one operator mapping that
unifies both operands and the result, and leaves the built-in precedence rule undisturbed.

Equality, logical, and type-test operators remain excluded from inference in this slice. They have
separate evidence or built-in rules and need their own soundness analysis. Relational operators are
included through `Comparable<T>`; a typeless lambda that uses equality without context still
requires annotations or an expected type.

### Constraint conflicts and diagnostics

If body checking produces incompatible requirements, the definition is rejected. The compiler must
not select one constraint, silently weaken a bound, or defer the conflict to a use.

Examples of diagnostics:

- an unannotated parameter remains unresolved after body checking: require an annotation;
- an operator is applied to types that cannot share one type: report the conflict at the operator;
- a use instantiates `T` but no witness satisfies the required `Numeric<T>`, `Fractional<T>`, or
  `Comparable<T>` contract: report at the use and name the lambda binding and the contract;
- multiple applicable witnesses make evidence ambiguous: use the existing witness-ambiguity
  diagnostic and name the binding;
- a use combines numeric and comparison operators on different types: report the unification
  conflict rather than choosing one operator's type;
- a string-concatenation use is attempted against the numeric scheme: report missing
  `Numeric<String>` evidence rather than silently changing the inferred scheme.

### Scope and lowering

This is a generalization of ZEP-0003's constrained let-bound lambda path, not a change to lambda
syntax or function-type identity. The AST still stores the original lambda and its resolved
function descriptor. The scheme records quantified type variables and their applied contract
bounds. At each use, the compiler instantiates the scheme, resolves evidence, substitutes the
function shape, and emits the same closure template and evidence slots already used for constrained
lambdas.

No wrapper, box, or new runtime descriptor is introduced. The inferred binders are compile-time
only. The existing erased SAM shape, hidden-slot mechanism where applicable, and adapter rules for
generic callback boundaries remain unchanged.

## Compatibility and impact

The change is additive for programs that previously failed because a typeless arithmetic or ordering
lambda had no expected type. It does not make an existing well-typed program ill-typed, and it does not
change explicit annotations or contextual lambdas.

The main compatibility risk is diagnostic and inference-surface change: a lambda that previously
required an annotation may now infer a scheme, and a use that previously failed at the definition
may now fail at the use with a missing-evidence error. Tooling should show the inferred scheme,
including its numeric or comparison bounds, on hover and in diagnostics.

The change has no library API-index change, because schemes are local to immutable `let` bindings
and are not serialized. It has no runtime ABI change, because it reuses the existing constrained
lambda closure path. It does not change `Numeric<T>`, `Fractional<T>`, operator precedence, string
concatenation, or the explicit-bound requirement for generic functions.

## Alternatives

- **Keep the current behavior.** This preserves the existing rule but leaves the common arithmetic
  and ordering callbacks requiring annotations or named generic functions. Rejected.
- **Default unresolved numeric lambdas to `Int`.** This makes the arithmetic example work but
  prevents `Float` reuse and makes the choice depend on an arbitrary default. Rejected.
- **Default to `Float`.** This loses exact integer behavior and still prevents user-defined numeric
  types. Rejected.
- **Infer from call sites.** This could resolve a particular use, but makes the inferred scheme
  depend on visitation order and lets one use constrain another. Rejected.
- **Infer every operator, including string concatenation and equality.** This requires overload
  selection or union constraints and interacts with built-in precedence. Deferred to a separate
  design.
- **Use full Hindley–Milner inference.** This is a much larger type-system change and would
  generalize many positions beyond the safe let-bound slice. Rejected for this bundle.
- **Require an explicit generic lambda for every reusable arithmetic or ordering callback.** This
  is the status quo with more syntax; it does not address the ergonomic gap. Rejected as the only
  option.

## Implementation and validation

Implementation should extend the existing constrained-lambda inference path:

1. Detect eligible immutable local `let` lambdas with no expected function type.
2. Allocate fresh type variables for unannotated parameters and build the body's operator
   constraints.
3. Unify same-type operator operands and the appropriate results, then attach `Numeric<T>`,
   `Fractional<T>`, or `Comparable<T>`.
4. Combine operator constraints with ZEP-0003's applied-contract bounds and reject conflicts.
5. Generalize only variables independent of captures and leave the binding local-only.
6. Reuse the constrained template, evidence selection, and closure-specialization path.
7. Update hover/diagnostics to display inferred operator bounds and the originating binding.

Validation should cover:

- `(a, b) -> a + b` with `Int`, `Float`, and a user-defined `Numeric` type at different uses;
- `+`, binary `-`, `*`, and unary `-` inferring `Numeric<T>`;
- `/` inferring `Fractional<T>`;
- `<`, `<=`, `>`, and `>=` inferring `Comparable<T>` with a `Boolean` result;
- a user-defined comparable type and built-in scalar comparisons;
- a scheme combining numeric and comparison constraints;
- multiple operator constraints on one scheme;
- literal operands such as `a + 1` and per-use conversion;
- annotated and expected-type lambdas bypassing inference;
- partially annotated lambdas where the remaining variable is resolved or diagnosed;
- a parameter left unresolved with a direct annotation diagnostic;
- conflicting operator and member constraints;
- missing evidence at a use and ambiguous evidence at a use;
- string concatenation remaining contextual and the numeric scheme rejecting `String`;
- equality, logical, and type-test operators remaining outside the rule; relational operators being
  inferred through `Comparable<T>`;
- immutable versus reassignable bindings;
- captures fixed in the scheme;
- per-use instantiation with distinct evidence and closure specializations;
- no API-index change, no new function-shape key, and unchanged erased descriptors;
- the full test suite after focused lambda, operator, resolver, and code-generation tests.

## Open questions

- Should equality operators gain analogous inference through `Eq<T>` in a later proposal?
- Should `Comparable<T>` eventually require or imply `Eq<T>`, or remain a separate capability?
- Should left-String concatenation infer a `Display` constraint when the left operand is
  explicitly `String` and the right operand is unresolved?
- Should the rule eventually cover immutable top-level `let` bindings, or remain local-only because
  schemes are not serialized?
- Should an inferred scheme be displayable as source-level polymorphic function syntax, or remain
  an internal scheme shown only in hover and diagnostics?
- Should a future defaulting rule exist for otherwise-unused numeric or ordered parameters, or
  should an unresolved parameter always require an annotation?

## Decision

Accepted on 2026-11-14 and marked `Candidate` for the `0.8.0` normalization bundle.

The settled design is:

- an uncontextualized typeless lambda written directly as an immutable local `let` initializer may
  infer a rank-1 scheme from numeric or comparison operator use;
- `(a, b) -> a + b` infers `<T: Numeric<T>> (T, T) -> T`; `(a, b) -> a / b` infers
  `<T: Fractional<T>> (T, T) -> T`; `(a, b) -> a < b` infers
  `<T: Comparable<T>> (T, T) -> Boolean`;
- both operands of a same-type operator must unify; arithmetic operands and results remain `T`,
  comparison operands remain `T`, and comparison results are `Boolean`; no mixed-type promotion or
  concrete default is introduced;
- each use instantiates the scheme independently and resolves evidence there; missing or ambiguous
  evidence is reported at that use;
- explicit parameter annotations and expected function types take precedence;
- `Comparable<T>` is independent of `Eq<T>`; equality remains outside this rule, as do string
  concatenation, logical, type-test, and arbitrary member operations;
- the scheme is local-only, uses the existing constrained-lambda template, and adds no runtime ABI
  or library API-index record;
- full Hindley–Milner inference, arbitrary lambda positions, mutable bindings, and rank-2 inference
  remain outside this proposal.
