## Abstract

Allow an argument list to follow any expression whose non-null type is a function type, not only a
name or a property. This makes the direct composition of first-class function operations legal:

```zeron
makeFunction()();
makeFunction()(21);
(if (chooseAdd) then add else subtract)(21);
callbacks[0]();
```

The callee expression is evaluated exactly once, before its arguments, and the invocation uses the
same generated function-shape interface and `invoke` lowering already used for a function value
stored in a variable. No new runtime representation, public API, or function-shape identity is
introduced.

The canonical grammar already permits a call suffix after an arbitrary primary expression. The
current parser narrows that production to variables and properties, and the AST has no general
callee-expression invocation node. This proposal aligns the implementation with the language's
first-class function model and with the documented grammar.

## Motivation

Function values can already be stored, passed, returned, and invoked through a name or a property:

```zeron
let operation: (Int) -> Int = double;
operation(21);                 // works

let result = makeFunction();   // works
result();                      // works
```

The natural composition is rejected:

```zeron
makeFunction()();              // rejected by the parser today
(makeFunction())();           // also rejected
```

The parser currently permits an argument list after `Expr.Variable` and `Expr.Property` only. When
it sees another expression followed by `(`, it reports:

> Only functions and named methods can be called.

Parenthesizing the result does not help because `Expr.Grouping` is not a callable form either. The
only workaround is to introduce a temporary binding, which obscures the operation and makes
curried or factory-returned functions unnecessarily awkward:

```zeron
let temporary = makeFunction();
temporary();
```

This is a rough edge for the core first-class function feature. It is especially visible with
right-associative function types: `Int -> Int -> Int` describes a function returning a function, so
`add(2)(3)` should be the direct way to apply the result. It also affects APIs that return
callbacks, conditional selection between callbacks, and indexing collections of function values.

The canonical grammar in
[design-document-01_grammar.ebnf](../design_documents/design-document-01_grammar.ebnf) already
describes a call as a primary expression followed by zero or more call suffixes. The current
restriction is therefore narrower than the documented language, not an intentional semantic rule.

## Goals

- Allow invocation when an expression's non-null type is an ordinary function type.
- Support direct invocation of call results, parenthesized expressions, conditional expressions,
  indexed function values, and other function-valued expression positions.
- Evaluate the callee expression exactly once, before evaluating the arguments.
- Preserve left-to-right argument evaluation.
- Check arity, argument assignability, and the result type using the existing function-value rules.
- Propagate raised effects from both the callee expression and the function invocation.
- Require a null check when the callee expression has a nullable function type.
- Preserve existing named-function, member-method, constructor, generic-call, and property-function
  behavior.
- Keep the existing generated function-shape interface and `invokeinterface` lowering.
- Add no API-index schema, standard-library API, or runtime ABI change.
- Produce a source-accurate diagnostic at the callee expression when the expression is not
  callable.

## Non-goals

- A general `Callable` contract or implicit invocation of nominal objects with an `invoke` method.
- Dynamic invocation through reflection, method handles, or runtime type inspection.
- Invoking a receiver-function value without supplying a receiver.
- New safe-call syntax for function values, such as `expression?()`.
- Explicit type arguments attached directly to an arbitrary expression callee, such as
  `factory()<Int>()`.
- Partial application, automatic currying, or changes to function-type arity.
- Operator overloading for `()`.
- Changing how named functions, methods, constructors, property functions, or generic calls are
  parsed and resolved.
- Changing trailing-lambda association, except where a new outer invocation naturally receives a
  trailing lambda.
- Changing `CodeModel` acceptance. A runtime function value and an arbitrary call-expression
  result still do not provide a recoverable source model.
- Changing the runtime representation of function values or their generated interface names.

## Proposal

### Surface syntax

An argument list may follow any postfix expression whose resolved type is a non-null function type:

```zeron
makeFunction()();
makeFunction()(21);
(readFactory())();
(if (useAdd) then add else subtract)(21);
callbacks[0]();
factory()()();
```

The existing variable and property forms remain valid and keep their current AST and lowering:

```zeron
operation(21);
receiver.callback(21);
Type.factory(21);
Type<Int>.factory(21);
```

The new form does not introduce a token or keyword. It is the ordinary postfix call suffix already
described by the grammar, applied to an expression that is not a name or property.

### Callable expression types

An expression is callable when its non-null resolved type is a `FunctionDescriptor`, after applying
the same reference and erasure handling used by existing function-value calls. A nominal class is
not callable merely because it declares a method named `invoke`; user-defined invocation is outside
this proposal.

The callee expression may be:

- a call result;
- a grouped expression;
- an `if` expression;
- an array or collection element;
- a property read that produces a function value, when it is not already resolved as a member
  method or property-function call;
- a named function value produced by the existing function-value conversion rules;
- a callable or property reference converted to a function type.

A constructor or method is not itself a first-class function value with this syntax unless it has
already been converted to its documented function type. The existing `Type::new`, `Type::method`,
and generic function-reference forms continue to define those values.

### Evaluation order

For

```zeron
makeFunction()(argument);
```

evaluation is:

1. evaluate the callee expression `makeFunction()`;
2. evaluate the arguments from left to right;
3. invoke the resulting function value.

The callee expression is evaluated exactly once. This matters when it has side effects:

```zeron
let callbacks = 0;
fn next(): () -> Int {
    callbacks += 1;
    return () -> callbacks;
}

let value = next()();
// next() runs once; value is 1
```

If argument evaluation fails or raises, the already-evaluated function value is not evaluated a
second time. The lowering may keep it in a local temporary, but no source-level temporary is
introduced and no additional user-visible name exists.

### Type checking and behavior

The resolved callee must have a non-null function type. Its explicit parameters and result are
checked by the same rules used when the function value is held in a binding. The call expression's
type is the function's declared result type after the usual substitutions.

Ordinary function values retain their existing full-arity shape. Defaults and variadic declarations
are features of named declarations; a function value does not gain a new arity or default-argument
rule through this proposal.

Generic function values follow the existing application rules:

```zeron
fn makeIdentity(): <T> (T) -> T = <T> (value: T) -> value;

let value = makeIdentity()(21);
```

The argument and expected result type instantiate the value's binders exactly as they do for a
stored polymorphic function value. If the binders cannot be determined, the existing generic-call
diagnostic applies; bind the value to an immutable `let` or provide a constraining expected type.
Explicit type arguments attached to an arbitrary expression callee are not part of the initial
slice.

A nullable function-valued expression is not directly callable:

```zeron
let maybeCallback: (() -> Int)? = ...;
maybeCallback();              // error: nullable value requires handling

// Use an existing null check or the existing non-null assertion.
if (maybeCallback != null) {
    maybeCallback();
}
```

No new `?()` operator is introduced.

### Effects

The invocation's raised effects are the union of:

- effects raised while evaluating the callee expression;
- effects declared by the resolved function value's invocation signature.

This must compose with the existing effect-flow analysis for named calls. A function value returned
from an effectful factory therefore carries both the factory's effects at the callee expression and
the invoked function's effects at the call. A handler may cover either set under the existing
handler rules.

### Receiver functions

A receiver function value is distinct from an ordinary function value; its receiver is supplied
through receiver-call syntax. A bare invocation has no place to supply that receiver:

```zeron
fn makeReceiver(): Transaction.() -> Result = ...;

makeReceiver()();              // error: receiver-function value requires a receiver
```

The existing form remains available after binding the value to a name:

```zeron
let callback = makeReceiver();
transaction.callback(request);
```

A future proposal may define a syntax for applying an expression-valued receiver function
directly, but this proposal does not invent one. The same rule applies to any expression whose
resolved function type has a receiver component.

### Trailing lambdas

Existing trailing-lambda association is unchanged. A trailing lambda follows the nearest completed
call:

```zeron
makeFunction() { value -> value + 1 };       // lambda is an argument to makeFunction
makeFunction()() { value -> value + 1 };    // lambda is an argument to the outer invocation
```

To pass the lambda to the inner call and then invoke the returned function, use the existing
postfix order:

```zeron
makeFunction() { value -> value + 1 }();
```

The parser must continue allowing a call suffix after a completed call, including a call that has a
trailing lambda. No new lambda-typing rule is introduced.

### Parsing and AST

The existing `Expr.Call` node stores a callee token and is tailored to named functions, generic
functions, and constructor shorthand. `Expr.MemberCall` represents member and property-function
calls. Neither represents an arbitrary callee expression.

Add a dedicated invocation expression node, for example:

```text
Expr.Invoke(calleeExpression, arguments, resolvedFunctionDescriptor, resultType)
```

The parser creates this node when an argument list follows a postfix expression that is not a
supported named-function or member-call form. Existing `Expr.Variable` and `Expr.Property` call
paths remain unchanged so constructor, generic, default-argument, and member-call behavior does not
move through a new path unnecessarily.

The node must participate in every expression traversal that already handles calls, including:

- name and symbol resolution;
- expected-type and generic inference;
- raised-effect collection;
- lambda capture and shape planning;
- code-model rejection or diagnostic traversal;
- formatter and syntax highlighter;
- language-server hover, signature help, and type checking;
- bytecode emission and initialization planning.

The canonical grammar should make the existing general call suffix explicit and document that its
resolved callee must be a function value. No new grammar terminal is required.

### Lowering

The invocation lowers without a new runtime type:

1. emit the callee expression and leave the function object on the operand stack;
2. emit the arguments in source order with the existing conversions;
3. invoke the generated function-shape interface's `invoke` method with `invokeinterface`;
4. apply the existing result conversion.

This is the same runtime path already used for a function value held in a variable. The compiler
must ensure the function object is evaluated once and kept available while the arguments are
evaluated; an implementation may use a temporary local or an equivalent stack strategy. No wrapper
object, dynamic lookup, or additional generated interface is required.

## Compatibility and impact

The change is source-compatible in the additive direction. Programs that currently fail to parse or
resolve an expression-callee invocation become valid; existing valid programs retain their meaning.
Parenthesized calls such as `(operation)(21)` become legal as a consequence of the general rule,
although they are redundant for a simple variable.

There is no runtime ABI change: function objects, generated shape interfaces, `invoke` descriptors,
and erase/boxing behavior are unchanged. There is no public API-index schema change because no new
type or declaration is introduced. Function types are already represented in compiled-library
metadata.

The main compatibility surface is diagnostics and tooling:

- the current “Only functions and named methods can be called” diagnostic is retired for valid
  expression callees and replaced by a type-directed non-callable diagnostic where appropriate;
- the language server must report the outer call's result type and signatures consistently;
- the formatter and highlighter must treat the postfix argument list as a call suffix rather than a
  malformed expression;
- effect diagnostics must attribute callee-expression effects and invocation effects to the right
  source span.

`CodeModel<F>` is unaffected. A stored function value or an arbitrary call-expression result still
has no recoverable inline source expression, so it remains invalid where a code model requires an
inline lambda or property reference. No new model representation is added.

## Alternatives

- **Keep the restriction and improve the diagnostic.** This makes the limitation clearer but does
  not make first-class function values uniformly callable. Rejected for the proposed target.
- **Special-case only the result of another call.** This handles `makeFunction()()` but leaves
  `(if ...)(...)`, `callbacks[0]()`, and grouped expressions inconsistent. Rejected in favor of the
  general postfix rule.
- **Require parentheses around the callee.** `(makeFunction())()` is still rejected today and
  would not solve the AST problem. Requiring redundant parentheses adds no clarity.
- **Desugar in the parser to a synthetic temporary binding.** This can model evaluation once, but
  it creates hidden names, complicates diagnostics, and would not represent the expression in the
  AST faithfully. Rejected.
- **Add an `invoke` keyword or a `.call()` method.** This adds syntax or library surface without
  new capability and conflicts with the existing first-class function model.
- **Add a general `Callable` contract.** This would let nominal objects define invocation behavior,
  but it is a separate type-system and dispatch feature. Deferred.
- **Use a general fixed-arity `apply` helper.** This preserves the limitation and burdens callers
  with extra names; it also does not integrate with trailing lambdas or generic function values.
  Rejected.
- **Extend `Expr.Call` with an expression callee.** This is possible, but the existing node carries
  a required callee token and name-oriented resolution. A dedicated node keeps named and method
  call behavior stable. Either representation is acceptable if the same semantics are preserved.

## Implementation and validation

A likely implementation sequence is:

1. Add the invocation expression node and parser support for an argument-list suffix after a
   non-name, non-property postfix expression.
2. Resolve the callee expression, require a non-null function value, and reuse the existing
   function-value argument, result, generic, and effect rules.
3. Emit the callee once, then arguments, then the existing `invokeinterface` call; include the node
   in all expression walkers, lambda planning, and bytecode support.
4. Add source-accurate diagnostics for non-callable expressions, nullable function values, and
   receiver-function values.
5. Update the grammar reference, lambda/function guide, formatter, highlighter, and language-server
   behavior.
6. Add user-facing documentation and the change to `CHANGELOG.md` when implementation lands.

Validation should cover:

- `makeFunction()()`, `makeFunction()(21)`, and a three-level `factory()()()`;
- curried application such as `add(2)(3)`;
- grouped, conditional, and indexed callees;
- a function-valued property read and an already-supported member function call;
- callee evaluation exactly once, including a side-effecting factory;
- left-to-right argument evaluation;
- raised effects from the callee expression, from the invoked function, and from both;
- a non-function callee diagnostic at the callee span;
- nullable function values requiring an explicit null check;
- receiver-function values producing a receiver-call diagnostic;
- generic and rank-2 function values instantiated from arguments or an expected type;
- trailing-lambda association for both the inner and outer call;
- formatter idempotence and language-server type/signature behavior;
- no API-index or generated function-shape change;
- the full `mvn test` suite after focused parser, resolver, effect, emitter, and LSP tests.

## Open questions

- Should explicit type arguments after an arbitrary expression callee eventually be supported, for
  example `factory()<Int>()`, or is binding to a name sufficient for underconstrained generic
  values?
- Should a safe-call form such as `maybeCallback?()` exist independently, or should nullable
  function values always use the existing null-check or `!!` rules?
- Should an expression-valued receiver function eventually have direct application syntax, or
  should the existing named receiver-call form remain the only spelling?
- Should the general rule also cover a reference-to-function value (`&F`) if named function values
  currently accept that reference form, or should both paths remain restricted to the same
  existing function-value assignability rules?
- Should a future `Callable` contract provide nominal invocation, or does that belong to a separate
  object-model proposal?
