# ZEP-0135: Witness Provision, Requirement Evidence, and Owner-Directed Dispatch

## Abstract

Separate what a witness *provides* from what its contract *requires*. A witness declared for a
contract provides that contract only; every contract in its `requires` chain must be satisfied by
its own canonical provider. A `default` witness is the canonical provider for its contract and
target type, so sibling contracts such as `Monad<F>` and `Alternative<F>` can share the same
`Applicative<F>` evidence without either one becoming a second `Applicative` provider.

Operations are then dispatched by their declaring contract. `map` resolves through `Functor`,
`pure` and `ap` through `Applicative`, `flatMap` through `Monad`, and `empty`/`orElse` through
`Alternative`, even when the receiver is a concrete type that implements all four. Generic bounds
keep closure entailment: `F<_>: Monad<F>` still permits `map`, but the operation is projected from
the bound's `Applicative` and `Functor` prerequisite evidence rather than selected from a sibling
witness.

This removes the false ambiguity in the `Option` type-class hierarchy without adding a
`uses`-style provider clause, a multi-contract witness declaration, or a single-instance-per-type
coherence rule.

## Motivation

A contract such as `Applicative<F>` requires `Functor<F>`, and both `Monad<M>` and
`Alternative<F>` require `Applicative<F>`. `Option` should therefore provide all four
capabilities. The current resolver cannot express that cleanly:

- `witnessEntails` treats a witness as providing every contract in the `requires` closure of its
  declared contract.
- `hasEvidence` counts every matching witness, not every distinct provider.
- Method selection scans every active witness whose closure contains the requested contract.

As a result, `Monad<Option<_>>` and `Alternative<Option<_>>` are both counted as independent
providers of `Applicative<Option<_>>` and `Functor<Option<_>>`. Because each witness must currently
implement inherited abstract operations itself, `map`, `pure`, and `ap` also exist in both
witnesses. A call such as `Option.Some(1).map(...)`, a generic `Functor<F>` bound instantiated at
`Option`, or the operations generated for `do` notation becomes ambiguous.

The errors are not caused by a mistake in the program. They are caused by conflating two different
relations:

- **requirement:** `Monad<F>` needs `Applicative<F>` evidence;
- **provision:** a witness for `Monad<Option<_>>` is not itself a witness for `Applicative<Option<_>>`.

The same conflation appears whenever two contracts share an ancestor. Picking one witness by source
order, import order, or first match would hide a legitimate ambiguity and make dispatch depend on
environment rather than on declarations. Collapsing all witnesses for a type into one canonical
instance would break the language's deliberate support for multiple named witnesses, such as
different `Eq` or `Ord` interpretations for the same type.

The intended model is the usual dictionary model used by functional languages: one dictionary per
contract and type, with child dictionaries referring to parent dictionaries. Zeron already represents
bound evidence as method handles, so the runtime representation can remain flat; what needs to
change is which provider supplies each slot.

## Goals

- Define a single provision relation: a witness provides the contract it is declared for.
- Define requirement evidence: each `requires` contract is resolved to its own provider.
- Make `default` witnesses the canonical provider for requirement lookup.
- Keep closure entailment for generic contract bounds.
- Resolve operations by the contract that declares them, not by arbitrary witness matching.
- Allow `Monad<Option<_>>` and `Alternative<Option<_>>` to share one
  `Applicative<Option<_>>` and one `Functor<Option<_>>`.
- Preserve independent named witnesses and report ambiguity when two true providers compete.
- Allow a witness to omit inherited abstract methods; those methods belong to parent evidence.
- Keep separate compilation and the API index able to reconstruct providers and operation owners.
- Remove the four current standard-library and `do`-notation ambiguity failures as a consequence of
  the model, not through per-type exceptions.

## Non-goals

- Introducing multi-contract witness declarations such as
  `witness Monad<Option<_>> + Alternative<Option<_>>`.
- Introducing an explicit `uses` or `provides` clause on witness declarations.
- Enforcing one global witness per target type, or changing the rules for named `Eq`/`Ord`
  witnesses.
- Redesigning the standard-library contract hierarchy or removing `Alternative`'s
  `Applicative` requirement.
- Changing generic admissibility, mutability, effect rows, or contract inheritance syntax.
- Adding runtime dictionary lookup, reflection, or a new evidence ABI.
- Defining general type-class coherence beyond superclass requirements.
- Changing how operator overloading or `do` notation infers its constructor.
- Providing a migration window for existing witnesses that implement inherited methods.

## Proposal

### Terminology

For a witness `W`, contract `C`, and target type `T`:

| Relation | Meaning |
| --- | --- |
| `provides(W, C)` | `W` is declared for `C` and targets `T`. |
| `requires(C, P)` | `P` appears in the `requires` closure of `C`. |
| `entails(C, D)` | `D` appears in the closure of contract `C`. |
| `provider(C, T)` | The selected witness that provides `C` for `T`. |
| `owner(method)` | The contract that declares `method`. |

Provision is direct. Requirement evidence is resolved separately. Entailment is transitive and is
used only to decide whether a bound satisfies another bound.

### Provision

A witness declaration provides exactly its declared contract. A class `implementation` block
provides exactly the contract named by that block. A derived witness provides the derived contract.
A `default` witness provides its contract and participates in canonical provider selection.

A witness for `Monad<Option<_>>` therefore does **not** provide `Applicative<Option<_>>` or
`Functor<Option<_>>`. It requires them.

For a given contract `C` and target `T`, there must be exactly one selected provider:

1. If a `default` witness for `C` at `T` is active, it is the canonical provider.
2. Otherwise, exactly one active named witness or class implementation must provide `C` at `T`.
3. Zero providers is a missing-evidence error.
4. More than one non-default provider is an ambiguity error.

The existing special evidence rules for derived equality, serialization, built-in `Eq`/`Hashable`,
and composite `Codec` remain in force. They are alternative ways to establish a provider for a
specific contract, not additional providers of unrelated ancestors.

### Requirement evidence

When a witness `W` for contract `C` is validated, each contract `P` in `C`'s `requires` list is
resolved as `provider(P, T)`, where `T` is the witness target after substitution.

Requirement lookup prefers the canonical default provider. If no default exists, it uses the unique
active provider. If several named providers are active, the witness has ambiguous prerequisite
evidence and is diagnosed at its declaration.

This is the implicit provider edge that replaces an explicit `uses` clause:

```zeron
default witness Applicative<Option<_>> for Option<_> {
    fn pure<A>(value: A): Option<A> = Option.Some(value);
    fn ap<A, B>(this: Option<A>, function: Option<(A) -> B>): Option<B> = ...;
}
```

`Applicative` requires `Functor`, so its requirement evidence is
`provider(Functor, Option<_>)`, which resolves to the default `Functor<Option<_>>` witness.

A witness is conformant when:

- every abstract method declared directly by its contract is implemented;
- every method it declares matches a method of its contract, including defaults it explicitly
  overrides where that is permitted;
- every required contract has exactly one selected provider;
- the selected providers' type arguments match the substituted requirement.

Inherited abstract methods are no longer part of the witness's conformance obligation. A witness for
`Applicative<Option<_>>` implements `pure` and `ap`; it does not implement `map`, because `map`
belongs to `Functor<Option<_>>`.

### Bound entailment

Bound entailment remains transitive. If a type parameter is declared as:

```zeron
fn mapAll<F<_>: Monad<F>, A, B>(source: F<A>, transform: (A) -> B): F<B> =
    source.map(transform);
```

then `Monad<F>` entails `Applicative<F>` and `Functor<F>`. The call to `map` is valid. The evidence
for `map` is projected from the `Monad` bound's `Applicative` prerequisite, and from that
`Applicative` prerequisite's `Functor` prerequisite.

Entailment does not turn a concrete `Monad<Option<_>>` witness into a concrete
`Functor<Option<_>>` provider. When a concrete `Option` is passed to a function requiring
`F<_>: Functor<F>`, the compiler selects the direct `Functor<Option<_>>` provider. When a value is
inside a generic function with a `Monad` bound, the compiler projects the `Functor` capacity from
that bound's dictionary.

This distinction is the core of the proposal:

> A `Monad` bound entails `Functor`, but a `Monad` witness does not provide `Functor`.

### Owner-directed method dispatch

Every contract operation has an owner: the contract that declares it. Dispatch selects the
provider for the owner contract at the receiver type.

Examples:

| Operation | Owner | Concrete `Option` provider |
| --- | --- | --- |
| `map` | `Functor` | `Functor<Option<_>>` |
| `pure`, `ap` | `Applicative` | `Applicative<Option<_>>` |
| `flatMap` | `Monad` | `Monad<Option<_>>` |
| `empty`, `orElse` | `Alternative` | `Alternative<Option<_>>` |
| `foldLeft` | `Foldable` | `Foldable<Option<_>>` |

The algorithm is:

1. Determine the owner contract from the selected method signature.
2. If the receiver is a concrete type, select `provider(owner, receiverType)`.
3. If the receiver is a type parameter, find the bound whose closure contains the owner contract
   and project the owner's evidence slot from that bound.
4. If the owner method has a default implementation, emit or call that default with its own
   requirement evidence. Do not replace it with a same-named method from a sibling witness.
5. If no provider exists, report missing evidence for the owner contract. If more than one
   non-default provider exists, report ambiguity for the owner contract.

Method selection must not scan every witness whose contract closure contains the operation. That is
what makes the duplicate `map` implementations in sibling witnesses ambiguous today.

### Option after the change

The standard hierarchy becomes:

```zeron
default witness Functor<Option<_>> for Option<_> {
    fn map<A, B>(this: Option<A>, transform: (A) -> B): Option<B> = ...;
}

default witness Applicative<Option<_>> for Option<_> {
    fn pure<A>(value: A): Option<A> = ...;
    fn ap<A, B>(this: Option<A>, function: Option<(A) -> B>): Option<B> = ...;
}

default witness Monad<Option<_>> for Option<_> {
    fn flatMap<A, B>(this: Option<A>, transform: (A) -> Option<B>): Option<B> = ...;
}

default witness Alternative<Option<_>> for Option<_> {
    fn empty<A>(): Option<A> = ...;
    fn orElse<A>(this: Option<A>, other: Option<A>): Option<A> = ...;
}
```

Resolution is then:

```text
provider(Functor, Option)     = Functor witness
provider(Applicative, Option) = Applicative witness
provider(Monad, Option)       = Monad witness
provider(Alternative, Option) = Alternative witness

requires(Applicative) = [Functor]      -> same Functor witness
requires(Monad)       = [Applicative]  -> same Applicative witness
requires(Alternative) = [Applicative]  -> same Applicative witness
```

`Monad<Option<_>>` and `Alternative<Option<_>>` do not become competing `Applicative` providers.
They both consume the one default `Applicative<Option<_>>`.

The same pattern applies to `Result` and `Stream`. A type that deliberately provides multiple
interpretations can still declare named witnesses for the same contract; selecting one is an
ordinary witness-selection decision, not a consequence of an unrelated child witness.

### `do` notation

`do` notation already infers the constructor from its bind clauses. It should resolve each generated
operation by owner contract:

- `flatMap` through `Monad`;
- `pure` through `Applicative`;
- `map` through `Functor`;
- any `orElse`-style operation through `Alternative` when the notation grows that surface.

For a generic `S<_>: Monad<S>` block, these operations are projected from the bound's prerequisite
evidence. For a concrete `Option` block, they select the direct default providers.

This removes the current concrete-`Option` ambiguity in `DoNotationTest` and keeps generic `do`
working through the bound rather than through ambient witnesses.

### Evidence representation and separate compilation

The current implementation flattens a bound's contract closure into one evidence method handle per
slot. That representation can remain:

- a slot's owner contract is known from its `ContractComposition.MethodSlot`;
- the call site selects the provider for that owner contract;
- a parent slot points at the parent witness's helper, or at the parent contract's default helper;
- a default helper carries its own prerequisite evidence when it needs ancestor operations.

No new runtime dictionary object is required. The change is in which provider supplies each slot,
not in the shape of the evidence array.

Metadata and compiled-library indexes must preserve enough information to reconstruct:

- the contract each witness provides;
- each contract's `requires` list;
- each operation's declaring contract;
- default-witness identity and activation;
- the requirement edges used by a bound's flattened evidence.

If the existing index already records contract declarations, witness contract types, and method
slots, no schema change is needed. Any new provider/owner metadata added by implementation must be
covered by `API_INDEX_SCHEMA_VERSION`; standard-library witness layout changes should be coordinated
with `STANDARD_LIBRARY_API_VERSION` under the normal release policy.

### Diagnostics

The resolver should report, at the witness declaration or use site:

- a witness that implements a method not declared by its own contract, including an inherited
  abstract method that now belongs to parent evidence;
- a witness whose required contract has no selected provider;
- a witness whose required contract has multiple active non-default providers;
- a method call with no provider for the owner contract;
- a method call with multiple non-default providers for the owner contract;
- a bound whose prerequisite evidence cannot be projected;
- a compiled-library witness whose recorded provider or requirement edges are inconsistent with its
  contract declarations.

Messages should name the owner contract and the target type. For example:

```text
No Applicative<Option<_>> evidence is available for Monad<Option<_>>.
Implement Applicative<Option<_>> or make one witness the default provider.
```

The existing general ambiguity diagnostic remains for genuinely independent providers.

### Migration

The standard library must split its self-contained witnesses:

- `Functor<Option<_>>`, `Applicative<Option<_>>`, `Monad<Option<_>>`,
  `Alternative<Option<_>>`, and `Foldable<Option<_>>`;
- the corresponding `Result` and `Stream` chains;
- `ArrayFoldable` stays a direct `Foldable` provider;
- `Main`, `Eq`, `Ord`, serialization, and other contracts keep their existing direct witnesses.

Strict rejection applies immediately: a witness may only implement operations declared by its own
contract. An inherited implementation is a declaration error, not a redundant method to be ignored
and not a fallback provider of the ancestor contract. Standard-library, sample, and test witnesses
are migrated as part of this proposal. Silently accepting inherited implementations would recreate
the coupling this proposal removes.

Class `implementation` blocks follow the same rule. A class that wants a full chain provides one
block per contract, or uses `delegating implementation` blocks that forward to its members. A block
for `Monad` does not provide `Applicative` or `Functor`. The exact class-chain ergonomics are left as
an open question; the provision rule is not.

## Compatibility and impact

This is a source-semantics change for witnesses that rely on ancestor entailment as provision.

- Programs with one self-contained witness per type must split it into one witness per contract;
  inherited method implementations in the child witness are rejected.
- Programs with two sibling witnesses sharing an ancestor, such as `Option` with `Monad` and
  `Alternative`, become unambiguous when the ancestor has a canonical default provider.
- Programs with two genuinely independent providers for the same ancestor remain ambiguous, as they
  should.
- Programs with no direct provider for a required ancestor become errors instead of silently using a
  child witness. This is the intended strictness.
- `do` notation becomes more deterministic because it resolves through the inferred bound and owner
  contracts rather than through unqualified method lookup.

The change is likely to require a `STANDARD_LIBRARY_API_VERSION` bump because the standard library's
witness layout and exported provider structure change. It should not require a runtime ABI change if
the existing flattened evidence representation is retained. Any compiled-library metadata additions
must follow the API-index version policy and be consolidated with other changes in the release
cycle.

Documentation should explain the distinction between requirement and provision, the canonical role
of `default` witnesses, and owner-directed dispatch in the generic-bounds and higher-kinded guides.
LSP hover and diagnostics should identify the owner contract and the selected provider.

## Alternatives

- **Multi-contract witness declarations.** A single witness could implement `Monad` and
  `Alternative` together, making it one root. This resolves the diamond but adds syntax, forces
  unrelated capabilities into one declaration, and still needs a rule for separately declared
  witnesses. Rejected for the initial design; it remains a possible future ergonomic layer.
- **Explicit `uses` provider clauses.** A witness could name the witness that supplies each
  inherited capability. This is the most flexible option, but it adds graph edges, visibility rules,
  cycle handling, and metadata. Canonical `default` witnesses already express the common case
  implicitly. Deferred until cross-witness delegation is a demonstrated need.
- **Nearest-ancestor preference.** Count a direct contract witness ahead of a one-hop ancestor, and
  so on. This would resolve `Option` without splitting it, but it silently lets a `Monad` witness
  stand in for `Functor` and makes behavior depend on declaration depth. Rejected as a permanent
  rule; it may be useful only as a migration bridge.
- **One canonical witness per target type.** This is simple but breaks deliberate multiple `Eq`,
  `Ord`, and other named-witness interpretations. Rejected.
- **Implicit deduplication by method body.** Rejected because semantic equality is not decidable
  locally, and resolution would change when an implementation body changes.
- **Change the contracts instead.** Making `Alternative` not require `Applicative`, or requiring a
  combined `MonadPlus` witness only, would address `Option` but not the general diamond. It would
  also weaken generic `Alternative` code. Rejected as a general solution.
- **Keep closure provision and special-case `Option`.** This hides the modeling error and leaves the
  next shared-ancestor hierarchy broken. Rejected.

## Implementation and validation

Likely implementation stages:

1. Split the evidence relations in `TypeClassEvidence`: direct provision, prerequisite lookup, and
   closure entailment for bounds.
2. Change `hasEvidence` to count providers rather than all witnesses in the closure.
3. Make `selectMethod` owner-directed, including owner lookup for concrete receivers and evidence
   projection for type parameters.
4. Update witness conformance validation in `DeclarationResolver` and `Resolver` so inherited
   abstract methods are satisfied by prerequisites, not by the child witness.
5. Update evidence emission and flattened slots in `BytecodeEmitter` and related compilation plans so
   each slot points at its owner provider or owner default.
6. Split the standard-library `Option`, `Result`, and `Stream` chains; keep `ArrayFoldable` direct.
7. Update `do`-notation lowering to resolve operations through the inferred bound and owner
   contracts.
8. Update the guide, design-document-15, `CHANGELOG.md`, and the API-index/library tests.
9. Decide and document the migration diagnostic for redundant inherited implementations.

Validation should cover:

- concrete `Option` calls to `map`, `pure`, `ap`, `flatMap`, `empty`, and `orElse`;
- `Option` under generic `Functor`, `Applicative`, `Monad`, `Alternative`, and `MonadPlus` bounds;
- `do` notation over concrete `Option` and over a generic `Monad` bound;
- `Result` and `Stream` generic operations after their witness chains are split;
- ambiguous independent providers for the same contract;
- missing parent providers and malformed provider metadata;
- a witness that redundantly implements an inherited method;
- compiled-library round trips for split witnesses and their requirement edges;
- class `implementation` chains and `delegating implementation` forwarding;
- LSP hover and diagnostics naming the owner contract and provider;
- full `mvn test` after focused resolver, emitter, library-index, and `do`-notation tests.

## Implementation decisions

- Inherited method implementations in a child witness are rejected immediately. There is no
deprecation or acceptance window.
- Prerequisite lookup always prefers the canonical `default` provider for the required contract. A
  named provider is used only when no default exists and exactly one named provider is active for
  that scope. This keeps superclass evidence independent of ambient named-witness imports.
- A class satisfies a contract chain with one `implementation` block per contract. Each block
  provides only the contract it names. `delegating implementation` may be used at each level.
  Multi-contract class blocks are not added.
- A child witness may not override an inherited default method. Customization belongs in the
  parent contract's own witness.
- Composite evidence remains limited to the existing `Codec` rule and the other established
  special cases. Operationless contracts such as `MonadPlus` need their own direct witness when
  used; no general operationless-contract synthesis is added.
- The existing API index already records contracts, witness contract types, requirements, and
  method slots. The implementation should avoid new schema metadata; if provider/owner metadata
  proves necessary, it must be versioned with `API_INDEX_SCHEMA_VERSION` and coordinated with the
  standard-library API bump.
- The standard-library API version advances with the split witness layout, coordinated with the
  rest of the `0.8.0` release cycle.

## Decision

Accepted and implemented on 2026-11-15; marked `Candidate` for the `0.8.0` normalization bundle.

The settled design is:

- a witness provides exactly its declared contract; ancestors are requirement evidence, not
  additional providers;
- requirement lookup selects the canonical `default` provider first, otherwise the unique active
  named provider;
- generic bounds keep closure entailment and project ancestor operations from the bound's
  prerequisite evidence;
- method dispatch is owner-directed: the contract that declares the operation selects its provider;
- child witnesses must not implement inherited methods, with no migration window;
- class implementations provide one contract per block, and children do not override inherited
  defaults;
- the standard-library `Option`, `Result`, and `Stream` witnesses are split into their contract
  chains as part of the implementation.
