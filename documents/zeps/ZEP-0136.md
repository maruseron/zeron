# ZEP-0136: Witness Bundles and Coherent Prerequisite Evidence

## Abstract

Group the witnesses for one target type into a **witness bundle**: one named or `default` declaration
whose members supply a set of contracts with a recorded, coherent prerequisite closure. Bundle
members may satisfy each other's contract prerequisites, and prerequisites not supplied by a member
resolve through the normal evidence paths at the bundle declaration and are recorded as part of the
bundle.
Selecting a bundle (defined by [ZEP-0137](./ZEP-0137.md)) activates the bundle's closure atomically.

A named bundle is **selection-only**: importing its name does not activate its evidence. A `default`
bundle is ambient canonical evidence, activated with its target type. Bundles restore the
dictionary-like pairing between a contract and its prerequisites without copying inherited methods,
so owner-directed dispatch from ZEP-0135 remains intact.

## Motivation

ZEP-0135 separated what a witness *provides* from what its contract *requires*. A witness provides
exactly its declared contract, and every contract in its `requires` chain is resolved as its own
requirement. That is the right dispatch model, but it leaves multiple lawful interpretations of the
same contract and target with no way to stay paired.

The `Monoid`/`Semigroup` hierarchy is the clearest example:

```zeron
public contract Semigroup<A> {
    combine(other: A): A;
}

public contract Monoid<A> requires Semigroup<A> {
    static empty(): A;
}
```

Addition and multiplication are both lawful monoids for `Int`. Selecting "multiplication" must
select both a `Semigroup<Int>` and a `Monoid<Int>`; selecting only the `Monoid` witness would take
multiplication's identity (`1`) while `combine` still dispatched through a canonical additive
`Semigroup`. The result is not a coherent algebra.

Today the alternatives are unsatisfactory:

- Declare separate named witnesses and rely on import scoping. This is package- or file-granular,
  makes the pairing implicit, and cannot express two coordinated sets in one file.
- Add an explicit provider clause to every witness. This is more granular, but it spreads a single
  bundle decision across several declarations and makes it easy to pair the wrong providers.
- Collapse everything into one instance per type. This rejects deliberate multiple interpretations.

A bundle makes the grouping explicit, local, and atomic. It is deliberately more rigid than
per-witness provider references: one declaration names the whole intended provider set, and a
selection activates the declared closure as a unit.

ZEP-0135 rejected multi-contract witness declarations and explicit `uses`/`provides` clauses for its
initial scope. This proposal revisits that decision for a concrete need: coordinated alternate
instances, not a general superclass-linking mechanism.

## Goals

- Add `witness bundle` declarations for a single target type, with named and `default` forms.
- Let bundle members supply the contract implementations; members are not independently selectable.
- Resolve each member's contract prerequisites from the bundle first, then through nominal,
  compiler-provided, or canonical default evidence, and record the resolved dependencies.
- Make named bundles selection-only: their names are importable, but their evidence is not ambient.
- Make `default` bundles ambient canonical evidence, activated with the target type.
- Validate bundle coherence: one target, no duplicate provider pairs, compatible generic patterns,
  complete prerequisite coverage, visibility, and nominal-conformance rules.
- Preserve owner-directed dispatch and the one-provider-per-contract-and-target rule.
- Export bundle metadata across separate compilation without adding a runtime dictionary object.
- Provide the declaration mechanism that [ZEP-0137](./ZEP-0137.md) selects with `using witness`.

## Non-goals

- Adding a `uses` or `provides` clause to individual witness declarations.
- Multi-target bundles, or bundles that group implementations for unrelated target types.
- Replacing nominal class conformance for any member contract.
- Making bundles or their members first-class values, function arguments, or fields.
- Runtime bundle lookup, dynamic scope, or a new evidence ABI.
- Changing ZEP-0135 owner-directed dispatch or inherited-method rules.
- Bundling compiler-provided structural or built-in `Eq`/`Hashable` evidence, or derived
  serialization evidence.
- `delegating witness bundle` forwarding in the initial design.
- Referencing an existing named witness as a bundle member without redeclaring its methods.
- Enforcing algebraic laws; bundles provide structural coherence only.
- Changing the activation rules for standalone named witnesses.
- File-wide activation of named bundles.

## Proposal

### Terminology

For a bundle `B`, target type `T`, and contract `C`:

| Term | Meaning |
| --- | --- |
| member | A `witness Contract<...> { ... }` entry inside `B`. |
| provides | The member supplies `C` for `T`. |
| requirement | A contract `P` in `requires(C)`. |
| closure | `B`'s members plus the recorded canonical default providers for prerequisites not supplied by a member. |
| selection | A `using witness (...)` block from ZEP-0137 that activates a bundle locally. |

A bundle directly provides the contracts named by its members. Its closure additionally activates the
recorded canonical default prerequisites; nominal and compiler-provided prerequisites remain
authoritative through their normal paths and are not stored as local overrides. It does not provide
unrelated contracts, and it does not turn its members into independently named witnesses.

### Declaration syntax

A named bundle introduces a name in the witness namespace and a single target pattern; it may declare
type parameters and bounds after the name:

```zeron
public witness bundle Multiplication for Int {
    witness Semigroup<Int> {
        fn combine(other: Int): Int = this * other;
    }

    witness Monoid<Int> {
        static fn empty(): Int = 1;
    }
}
```

A `default` bundle is unnamed, cannot be marked `public`, and must appear in the compilation unit
that declares the head of its nominal target, or in the canonical package for an intrinsic target:

```zeron
package zeron.lang;

default witness bundle for Int {
    witness Semigroup<Int> {
        fn combine(other: Int): Int = this + other;
    }

    witness Monoid<Int> {
        static fn empty(): Int = 0;
    }
}
```

A bundle may be generic:

```zeron
public witness bundle ListMonoid<T> for List<T> {
    witness Semigroup<List<T>> {
        fn combine(other: List<T>): List<T> = ...;
    }

    witness Monoid<List<T>> {
        static fn empty(): List<T> = List.Nil();
    }
}
```

The `default` form accepts the same optional type parameters and bounds after `bundle`; it is
written `default witness bundle<T> for List<T>` rather than with a bundle name.

`bundle` is a soft keyword in witness-declaration position: it begins a bundle declaration when it
appears immediately after `witness` or `default witness` and is not followed by `:`. Elsewhere it
remains an ordinary identifier. A contract type literally named `bundle` must be written with a
qualified name in an anonymous witness declaration, while a named witness may still be called
`bundle` because the colon disambiguates it.

A bundle may target a constructor pattern for higher-kinded contracts:

```zeron
public witness bundle OptionInstances for Option<_> {
    witness Functor<Option<_>> {
        fn map<A, B>(this: Option<A>, transform: (A) -> B): Option<B> = ...;
    }

    witness Applicative<Option<_>> {
        fn pure<A>(value: A): Option<A> = Option.Some(value);
        fn ap<A, B>(this: Option<A>, function: Option<(A) -> B>): Option<B> = ...;
    }

    witness Monad<Option<_>> {
        fn flatMap<A, B>(this: Option<A>, transform: (A) -> Option<B>): Option<B> = ...;
    }
}
```

The same target form is valid for a `default` bundle when the target's canonical evidence is
consolidated into that bundle.

The bundle target and member contract types use existing witness-target rules. A member's contract
must apply to the bundle target, and it may use the bundle's type parameters. Method-level type
parameters and contract defaults work as they do for standalone witnesses. Member method bodies
follow the existing witness rules: `this` is read-only, only public target members are accessible,
and inherited contract methods are not implemented by the child member.

Bundle members have no source names of their own. Their identity is the bundle plus their applied
contract and target. This keeps the bundle atomic and avoids a second, independently selectable name
for each member.

### Prerequisite closure

Members are validated as a set. For every member contract `C` and every `P` in `requires(C)`:

1. If another member provides `P` for the same applied target, use that member.
2. Otherwise, if the target nominally conforms to `P`, use the nominal conformance.
3. Otherwise, if compiler-provided evidence exists for `P` at the target, use it.
4. Otherwise, if exactly one canonical default provider exists for `P` in the bundle's declaration
   scope, record it. A canonical default provider is a standalone `default` witness or a member of
   a `default` bundle.
5. Otherwise, reject the bundle.

Resolution happens at bundle declaration, not at each consumer use. The chosen canonical default
providers are recorded and exported with the bundle, so a consumer cannot silently re-pair them;
nominal and compiler-provided prerequisites are authoritative and resolve identically for consumers.
When a recorded canonical default dependency is generic, the bundle's type parameters must satisfy
that dependency's bounds; otherwise the bundle is rejected or the dependency must be supplied as a
member with the needed bounds.

Inside a member's methods, an operation declared by a prerequisite resolves through the bundle's
provider for that prerequisite, not through an unrelated ambient witness. Owner-directed dispatch
from ZEP-0135 still chooses the declaring contract; the bundle only fixes which provider supplies it.

A bundle may intentionally provide only a child contract and rely on the canonical parent:

```zeron
public witness bundle AdditionMonoidOnly for Int {
    witness Monoid<Int> {
        static fn empty(): Int = 0;
    }
}
```

Here `Monoid` requires `Semigroup`. The bundle records the canonical additive `Semigroup<Int>` and
pairs it with the additive identity. If the author wanted multiplication, the `Semigroup` member
must be included. A child-only bundle that pairs a new identity with an incompatible canonical
parent is still structurally accepted, because bundles do not enforce algebraic laws; the author is
responsible for choosing a compatible parent. The compiler does not guess intent from names or
declaration order.

If a prerequisite has no member, no nominal conformance, no compiler-provided evidence, and no
unique canonical default, the bundle declaration is invalid. The diagnostic should name the missing
contract and suggest either adding a member or providing canonical evidence.

Members may provide independent roots. A bundle for `Int` could supply `Display`, `Comparable`, and
`Semigroup` together even though those contracts are unrelated. The closure rule applies per member.

### Coherence and validation

The declaration resolver must enforce:

- one target pattern per bundle;
- no two members provide the same applied contract for that target;
- every member contract applies to the target after substitution;
- every member's generic pattern covers the bundle's full target pattern; a member such as
  `Semigroup<List<Int>>` cannot appear in a bundle for `List<T>`;
- no member introduces an unbound type parameter not declared by the bundle;
- every member's contract prerequisites resolve by the closure rule;
- no member may provide a contract that the target class implements nominally;
- no member may provide compiler-provided structural or built-in `Eq`/`Hashable`, or derived
  serialization evidence;
- every recorded canonical dependency must be valid under the bundle's own type-parameter bounds; a
  dependency that requires a bound the bundle does not declare is rejected, and the author must add
  the bound or provide the dependency as a member;
- an exported bundle (`public`, or `default` with a public target) may not expose a package-local
  type through its target, type-parameter bounds, member contracts, member method signatures, or
  recorded closure; every such type must be public, and a named bundle that needs package-local
  types must remain package-local;
- a `default` bundle follows the placement, public-contract, and uniqueness rules of default
  witnesses for every member.

Named bundles are intentionally allowed to duplicate an active default for the same contract and
target. That is the alternate-instance use case. They are not part of the ambient active scope, so
they do not create an overlap error there; conflicts among selected providers are checked when the
bundle is selected.

### Activation and visibility

**Named bundles are selection-only.** A named bundle's name is a witness-namespace name. Importing it
makes the name available for `using witness`, but it does not activate its members as ambient
evidence:

```zeron
import witness lib.Multiplication;

using witness (Multiplication) {
    // Multiplication's members are active here only.
}
```

A fully qualified public bundle name works without an import. A package-local bundle is usable only
inside its package. A named bundle declared in the current package is name-visible but still not
ambient evidence. Ordinary package star imports do not name or activate named bundles.
`import witness pkg.Name;` and `import witness pkg.*;` make the public bundle names in `pkg`
available for `using witness` without activating them; a qualified selection needs no import.

This is deliberately different from a standalone named witness, and it is an explicit exception to
ZEP-0114's active witness scope: named bundles are never ambient candidates, even when declared in
the current package or listed by a witness wildcard import. Standalone witnesses keep the
import-activation rules from ZEP-0114. Bundles exist to make alternate instance sets selectable
without creating an import-time ambiguity.

**Default bundles are ambient canonical evidence.** Each member behaves as a default witness for its
contract and target. A default bundle activates with the target type, through the current package, an
explicit type import, or a package star import; intrinsic targets are always active. A default
bundle is unnamed and cannot be imported or selected by name.

### Example: additive and multiplicative monoids

With the default additive bundle above, ordinary code keeps using addition:

```zeron
fn total(values: List<Int>): Int = fold(values, 0, (a, b) -> a + b);
```

A file that wants multiplication selects the alternate bundle locally:

```zeron
using witness (Multiplication) {
    let product = combineAll(values); // Semigroup<Int> and Monoid<Int> are multiplication
}
```

Selecting `Multiplication` activates both members. A direct `combine` call inside the block uses
multiplication's `Semigroup`, not the canonical additive one. Outside the block, the default bundle
resumes.

### Separate compilation and API index

The library index must preserve:

- the bundle's qualified name or default identity;
- its visibility and default marker;
- its type parameters and bounds;
- its target pattern;
- each member's contract type, methods, prerequisites, and helper metadata;
- the recorded canonical default dependencies for prerequisites not supplied by members; nominal and
  compiler-provided resolutions are recomputed from their authoritative paths and are not stored as
  bundle dependencies.

Named bundles are exported as bundle declarations, not as a set of independently selectable named
witnesses. Default bundle members must remain reconstructible as canonical providers for normal
evidence lookup, including for consumers that resolve them without selecting the bundle.

This requires a new bundle export record or equivalent metadata and an `API_INDEX_SCHEMA_VERSION`
bump. If another schema change ships in the same release cycle, consolidate the bump under
ZEP-0012. Older libraries without bundle metadata remain loadable. If the standard library adopts
default bundles, coordinate the change with `STANDARD_LIBRARY_API_VERSION` under ZEP-0012.

No runtime dictionary is introduced. Members still emit static witness helpers; a selected bundle
supplies the same method handles it would have supplied as separate witnesses.

### Diagnostics

Report, at the bundle declaration or selection site:

- two members providing the same applied contract for the target;
- a member contract that does not apply to the bundle target;
- a generic member pattern that is over-specialized or leaves a target parameter unbound;
- a missing prerequisite with no member, nominal conformance, compiler-provided evidence, or unique
  canonical default;
- an ambiguous prerequisite with several canonical candidates;
- a member that conflicts with nominal class conformance;
- a member that attempts to provide compiler-owned structural, built-in, or derived evidence;
- an exported bundle that exposes a package-local target, bound, contract, method, or dependency
  type;
- a named bundle selected with an incompatible or missing type argument (from ZEP-0137).

Messages should identify the bundle, member contract, target, and missing or conflicting provider.
For example:

```text
Bundle 'Multiplication' for 'Int' has no provider for prerequisite 'Semigroup<Int>'.
Add a Semigroup<Int> member or provide canonical Semigroup<Int> evidence.
```

### Migration

The syntax is additive. Existing named and default witnesses remain valid and keep their current
activation rules. A library may introduce a bundle for a coordinated set without converting
unrelated witnesses.

The standard library may later consolidate default witness chains such as `Option`'s
`Functor`/`Applicative`/`Monad` into a default bundle. That adoption is optional for this proposal
and should be handled as a separate migration with the normal standard-library version policy.

## Compatibility and impact

- New source syntax for declarations; no existing program is required to change.
- Bundle names enter the existing witness namespace; a bundle name may not collide with a standalone
  witness name in the same package.
- Named bundles do not change ambient evidence availability. Code that does not select one behaves
  as before.
- Default bundles add canonical providers; a target may have at most one default per contract and
  target, whether declared by a standalone default witness or a default bundle member.
- The API index gains bundle metadata and requires a schema bump. Runtime evidence remains hidden
  method handles with no new ABI.
- Formatter, highlighter, and LSP support must recognize bundle declarations and member blocks.
- Documentation should explain bundles, selection-only named activation, default bundle activation,
  and the prerequisite closure rule.

## Alternatives

- **Explicit provider clauses on individual witnesses.** The most granular option, but it spreads one
  bundle decision across several declarations, makes pairing errors likely, and requires graph
  handling in every witness. Bundles are the rigid, local alternative.
- **Multi-contract witness declarations.** ZEP-0135 rejected these for its initial scope. A bundle is
  the same idea with a target header, member blocks, and an explicit coherence rule; it avoids
  repeating the target on every member.
- **Implicit grouping by package or naming convention.** Rejected: it makes evidence depend on naming
  and declaration layout, which ZEP-0004 explicitly avoids.
- **Ambient named bundles.** Importing a bundle would activate all members and recreate the overlap
  error this proposal exists to avoid. Selection-only named bundles keep ambient coherence intact.
- **One instance per target type.** Rejected: it removes deliberate multiple interpretations.
- **Newtype tags only.** Tagged types are a principled way to distinguish algebras and preserve global
  coherence, but they change value types and require wrapping. Bundles are a complement for code that
  wants a local interpretation without changing the target type.
- **Bundle members that reference existing named witnesses.** Useful for reuse, but it reintroduces
  per-member provider references and complicates export and visibility. Deferred until bundles are in
  use.
- **Bundles as first-class values.** Rejected: it would make evidence a runtime object and change the
  inference and ABI model.

## Implementation and validation

Likely stages:

1. Add `witness bundle` declarations, member blocks, optional bundle type parameters, the
   default/named forms, and the contextual `bundle` keyword to the parser and AST.
2. Register bundles separately from standalone witnesses. Resolve member contracts against the
   target, validate duplicate pairs and generic coverage, and compute the prerequisite closure at
   declaration time.
3. Register default bundle members as canonical providers and named bundle members as
   selection-only metadata. Keep named bundles out of ambient witness lookup and overlap checks.
4. Export and load bundle metadata, including recorded canonical default dependencies, through the
   API index with a schema bump.
5. Reuse existing witness helper emission for members; record bundle provenance for diagnostics and
   separate compilation.
6. Wire bundle selection into the ZEP-0137 local evidence environment.
7. Update the formatter, highlighter, LSP surfaces, guide chapters, and design-document-15.

Validation should cover:

- additive and multiplicative bundles for `Int`, including direct `combine` and `empty` use;
- a child-only bundle that relies on a canonical parent;
- a child-only bundle that cannot resolve its parent and is rejected;
- generic bundles over `List<T>` and higher-kinded bundles over `Option<_>`;
- a generic bundle whose recorded dependency requires a bundle type-parameter bound, including the
  accepted and rejected cases;
- duplicate members, over-specialized members, and unbound parameters;
- exported bundles that expose a package-local target, bound, contract, method, or dependency type;
- named bundles that intentionally duplicate an active default and are selected locally;
- default bundle placement, public-contract requirements, and uniqueness;
- nominal conformance conflicts and compiler-owned structural, built-in, or derived evidence
  rejection;
- source and compiled-library round trips, including consumers that do not select the bundle;
- old library indexes without bundle metadata;
- focused resolver, emitter, index, and formatter tests, followed by the full `mvn test` suite once
  the implementation is complete.

## Open questions

- Should default bundles be allowed to depend on a named standalone provider, or only on canonical
  default, nominal, and compiler-provided evidence?
- Should a bundle member be allowed to reference an existing named witness instead of restating its
  methods? This is deferred, but it affects reuse and export design.
- Should member blocks accept optional diagnostic names, or is `Bundle.Contract` sufficient?
- Should a bundle be allowed to have multiple targets if all members are independent? The initial
  design says no, for local reasoning.
- Should `delegating witness bundle` be added, and if so, does it delegate per member or across the
  whole bundle?
- Should a `default` bundle be allowed to include a contract already provided by a standalone
  default witness for a different target pattern? The uniqueness rule should answer this per pair,
  but the diagnostic and migration story need to be explicit.

## Decision

Accepted on 2026-11-15 as the bundle-declaration mechanism for coherent prerequisite evidence.
Named bundles are selection-only, `default` bundles are ambient canonical evidence, and the
prerequisite closure is resolved at declaration time and exported as metadata. Added as a `0.8.0`
candidate; implementation follows normal project prioritization.
