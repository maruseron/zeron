## Abstract

Add a lexical witness context:

```zeron
using witness (Multiplication) {
    // Multiplication's members are the providers here.
}
```

The block selects named witness bundles, and named standalone witnesses where appropriate, for the
duration of the block. Selection is static and lexical: the compiler resolves the selected providers
at each concrete use, forwards their evidence to generic calls, and captures selected handles in
closures created inside the block. A direct function or method invocation may also carry a single-call
`with witness (...)` clause, which supplies providers to that invocation's existing hidden evidence
parameters without making evidence a value or changing the ABI. There is no runtime lookup or
dynamic scope.

A selected bundle is activated atomically within its block: its members and recorded canonical default
prerequisites are inserted as a unit rather than re-resolved piecemeal. Within the block, a selected
provider shadows an ambient default for the same applied contract and target. Outside the block,
normal import-scoped selection and ZEP-0004 coherence remain unchanged.

## Motivation

Named and default witnesses made witness identity and activation explicit, but activation is still
tied to imports, packages, or the target type rather than to a region of code. That is a poor fit
for two lawful interpretations of the same contract and target:

- `Display<Int>` may be decimal or hexadecimal;
- `Comparable<Int>` may be ascending or descending;
- `Monoid<Int>` may be addition or multiplication;
- an application may want a case-insensitive comparison for one report and ordinary comparison
  everywhere else.

Today a file can choose one interpretation by importing one witness, but it cannot use two in
different regions. Importing both makes the selection ambiguous, and ZEP-0004's eager active-scope
overlap check rejects the compilation unit even when the competing providers are only used in
disjoint regions. Splitting code into separate files or packages works, but it is coarse and pushes
an implementation detail into project structure.

ZEP-0135 rejected explicit provider clauses and multi-contract witnesses for its initial scope.
ZEP-0136 now supplies coherent bundles. What remains is a way to say, locally and unambiguously,
"use this bundle for this region" or "use it for this call." ZEP-0004 explicitly left explicit witness selection as a separate
proposal when a concrete need arose; this is that need. ZEP-0114 also anticipated future
explicit-evidence-selection syntax while keeping aliases diagnostic-only.

First-class witnesses or arbitrary evidence arguments would make witnesses value-like, complicate
inference and call syntax, and expose evidence in the ABI. A lexical context keeps witnesses
compile-time-only and reuses the existing hidden-handle model. A provider-reference-only clause on a
single invocation gets the same locality without making evidence a value, so the design includes
both a block form and a narrower call-site form.

## Goals

- Add a `using witness (Provider, ...) { ... }` block statement.
- Select named witness bundles from ZEP-0136 atomically within the selecting block.
- Select named standalone witnesses for simple contracts and backward-compatible use cases.
- Resolve selected providers lexically and statically, with no runtime dictionary or dynamic scope.
- Let a selected provider shadow an ambient default for the same applied contract and target inside
  the block.
- Forward selected evidence to generic calls with concrete type arguments.
- Capture selected evidence in closures and function references created inside the block.
- Allow a direct function or method invocation to supply providers for that call with a postfix
  `with witness (...)` clause.
- Keep call-site selection provider-reference-only: it fills existing hidden evidence parameters and
  never makes evidence an ordinary value or argument.
- Support fully qualified provider names without an import, and aliases as selection names.
- Keep ambient witness activation, overlap checking, and ZEP-0004 coherence unchanged outside the
  block.
- Diagnose conflicting selections, unknown or inaccessible providers, and unsupported selection of
  compiler-owned evidence.
- Update the grammar, formatter, highlighter, LSP surfaces, and guides.

## Non-goals

- Making witnesses or bundles first-class values, fields, parameters, or return values.
- First-class evidence values or arbitrary evidence expressions at call sites. The provider-reference
  clause defined below is a selection form, not an evidence value.
- Runtime witness lookup, thread-local evidence, or dynamic scoping.
- Changing the import activation rules for standalone named witnesses.
- Making named bundles ambient evidence; ZEP-0136 defines them as selection-only.
- Selecting a `default` witness or `default` bundle by name.
- Selecting anonymous or derived witnesses by name.
- Declaration-site selection. The call-site clause is the only expression-level selection form in
  this design.
- Supplying evidence to a call that has no hidden evidence parameters, or overriding evidence that a
  function body already selected when it was compiled.
- Changing witness overlap rules for code outside a selection block.
- Replacing compiler-owned structural or built-in `Eq`/`Hashable`, derived serialization, `Main<A>`,
  or intrinsic arithmetic lowering.
- Enforcing algebraic laws.
- Providing a warning for every unused selection in the initial design.

## Proposal

### Syntax

A witness context is a statement with one or more provider references and a block body:

```zeron
using witness (Multiplication) {
    let product = combineAll(values);
}
```

Multiple independent selections are comma-separated:

```zeron
using witness (HexDisplay, DescendingComparable) {
    let report = renderAll(values);
    let ordered = sortValues(values);
}
```

The `using witness` form is distinct from resource `using (let name = expression) { ... }`. The
`witness` keyword immediately after `using` selects the witness-context production, so the resource
form and its disposal semantics are unchanged.

A fully qualified public provider is selectable without an import:

```zeron
using witness (acme.format.HexDisplay) {
    let text = render(value);
}
```

An imported or aliased name is also usable:

```zeron
import witness acme.format.HexDisplay as Hex;

using witness (Hex) {
    let text = render(value);
}
```

At least one provider is required. The same provider listed twice by identity is a duplicate
selection. A private or otherwise inaccessible provider cannot be selected from another package.

### Call-site selection

A direct function or method invocation may carry a single-call evidence clause:

```zeron
combineAll(values) with witness (Multiplication)
```

The clause uses the same provider-reference grammar as `using witness`. It names bundles or
standalone witnesses, accepts fully qualified names without an import, and accepts imported or
aliased names. At least one provider is required, and listing the same provider twice by identity is
an error.

A call-site clause is **not** an evidence value and does not add an ordinary argument. It supplies
the providers for evidence parameters that the call already has. The callee's source signature,
JVM descriptor, and hidden-handle ABI are unchanged.

For a generic call, matching happens after ordinary type-argument inference and substitution:

```zeron
fn combineAll<A: Monoid<A>>(values: List<A>): A = ...

let product = combineAll(intValues) with witness (Multiplication);
```

Here `intValues` determines `A = Int`; `Multiplication` then supplies `Monoid<Int>` and, through the
bundle closure, its `Semigroup<Int>` prerequisite. The call emits the same hidden evidence arguments
it would emit inside a `using witness (Multiplication)` block.

Explicit evidence does not participate in type inference or overload resolution. If the call's type
arguments remain unresolved after ordinary inference, the compiler reports that explicit type
arguments are required instead of inferring them from the provider.

The clause is local to that invocation:

```zeron
using witness (Addition) {
    let additive = combineAll(values);                  // Addition
    let product = combineAll(values)
        with witness (Multiplication);                  // Multiplication for this call only
    let additiveAgain = combineAll(values);             // Addition again
}
```

A call-site clause overrides an enclosing block only for the pairs it provides. Requirements it does
not provide continue through the surrounding block and ambient evidence. It does not leak into
later calls, nested declarations, or the rest of the block.

Provider matching is by applied contract and target, not by argument position:

1. the call-site clause for this invocation;
2. the innermost surrounding selection map;
3. outer selection maps;
4. ambient default and named witness selection;
5. nominal class conformance and compiler-provided evidence, in their existing order.

A bundle is expanded at the call site exactly as it is for a block selection: its member pairs and
recorded canonical default dependencies are inserted atomically, while nominal and compiler-provided
dependencies remain authoritative. A call-site bundle must be internally coherent under the same
conflict rules as a block selection. A standalone provider follows the existing rule that selecting
a child witness does not automatically select its prerequisites; use a bundle when a coherent
prerequisite chain is required.

A call-site clause cannot override nominal class conformance, compiler-owned structural or built-in
`Eq`/`Hashable`, derived serialization evidence, intrinsic arithmetic lowering, or any other
evidence excluded by this proposal.

Initial callable forms are direct calls to free functions, instance or static methods, and named
factories that declare hidden evidence parameters. Function values, closures, class constructors,
operator invocations, and `do`-notation operations are not in the initial call-site form. Function
references and constructed instances keep the capture rules below: evidence is captured when the
reference or instance is created and cannot be re-supplied when it is later invoked.

A call-site clause on an invocation with no hidden evidence parameters is an error. This includes a
non-generic function whose body already selected concrete evidence at compilation:

```zeron
fn renderDefault(value: Int): String = "" + value;

// Error: renderDefault has no hidden evidence parameter for Display<Int>.
renderDefault(value) with witness (HexDisplay);
```

A separately compiled library function with hidden evidence parameters can be supplied evidence at
the call site. A library function that already fixed its evidence internally cannot.

A standalone provider that matches no requirement of the invocation is an error. A selected bundle
may contain independent roots that the invocation does not use, provided at least one bundle member
supplies a required pair.

### Provider kinds

A provider reference names either:

1. A named witness bundle from ZEP-0136. Selection activates the bundle's members and recorded
   canonical default dependencies; compiler-owned evidence remains subject to the exclusion rules
   below.
2. A named standalone witness. Selection activates that witness for its declared contract and target.

Default witnesses and default bundles are unnamed and cannot be selected by name. They are already
ambient when active. Selecting a provider that is already active and identical is permitted and has
no additional effect.

Named bundles are selection-only, so importing one only makes its name available; the selection is
what activates its evidence. Standalone witnesses keep their existing import activation rules, but a
standalone witness may also be named by a fully qualified reference inside a selection without being
imported. This lets a file use two standalone witnesses in different blocks without importing both
and triggering the eager overlap check.

### Local evidence environment

The resolver maintains a stack of local selection maps. Each map is keyed by an applied contract and
target pair, such as `(Monoid, Int)` or `(Functor, Option<_>)`, and stores the selected provider.

A bundle selection inserts every member pair plus the bundle's recorded canonical default
dependencies from ZEP-0136. Recorded nominal and compiler-provided dependencies are not inserted as
local overrides: nominal conformance and compiler-provided evidence are already authoritative and are
not selectable. A standalone witness selection inserts its own pair. For each pair, the innermost
block that provides a provider wins.

A selected pair with a constructor target matches every concrete use that unifies with it; a fully
applied pair matches only itself. Method-level type parameters are instantiated at the use, as they
are for an ambient witness. A selected `(Functor, Option<_>)` pair therefore applies to
`Functor<Option<Int>>`, while a selected `(Monoid, List<Int>)` pair does not apply to
`Monoid<List<String>>`.

Evidence resolution is:

1. the call-site clause for the current invocation, when present;
2. the innermost local selection map;
3. the next outer selection map;
4. ambient default and named witness selection, as today;
5. nominal class conformance and compiler-provided structural, built-in, or derived evidence,
   following their existing relative precedence.

A selected provider therefore shadows an ambient default for the same pair. It does not shadow
unrelated contracts. If a bundle does not include a prerequisite and records a canonical default
dependency, that dependency is inserted into the local map as well, so the bundle's chosen default is
preserved even when another selection would otherwise shadow it. Recorded nominal and
compiler-provided dependencies need no insertion because selection cannot replace them.

### Conflict rules

- Two selections in the same block that provide different providers for the same applied pair are an
  error.
- Two bundles that share a pair through their recorded canonical default dependencies may be
  selected together only if they agree on the provider for that pair. Identical providers are
  deduplicated.
- A standalone selection for a child contract does not automatically select its prerequisites.
  Prerequisite lookup consults the local environment first, then ambient evidence. Bundles are the
  intended way to keep a whole chain coherent.
- A nested block may intentionally select a different provider for a pair already bound by an outer
  block. The inner map shadows the outer map. This is an explicit local re-pairing: the outer
  bundle's other pairs remain visible, the compiler does not merge the two selections, and it does
  not enforce algebraic compatibility between them.
- A call-site clause may intentionally override an enclosing block for the same pair. The override
  applies only to that invocation; it is not reported as a selection conflict, and the block's other
  pairs remain available to the call.
- Selecting a provider whose contract is already implemented nominally by the target type is an
  error; nominal conformance remains authoritative.
- Selecting a provider that is not applicable to any use is allowed in a block. The block is a
  context, not a per-call annotation. A future warning may report unused block selections. A
  call-site standalone provider that matches no requirement is an error, as described above.

### Static semantics and evidence capture

Selection is a compile-time environment.

- Each call site resolves its required evidence against the local maps and passes the selected hidden
  handles, exactly as ordinary witness selection does. A call-site clause contributes the highest
  priority map for that invocation only.
- A closure, lambda, or function reference created inside the block captures the selected handles at
  creation. Invoking it later keeps that selection.
- A generic function called with concrete type arguments inside the block receives the selected
  evidence for its substituted bounds. A call-site clause supplies that evidence for its invocation
  in the same way.
- A use whose type parameter is still abstract cannot match a concrete selection. It uses evidence
  projected from its own bounds.
- An instance constructed inside the block may capture selected evidence in its hidden fields,
  exactly as it captures any other evidence at construction. That captured evidence travels with the
  instance; it is not dynamic scope.
- Code compiled outside the block is unaffected. In particular, a separately compiled library
  function with concrete operations already selected keeps its own evidence; a consumer's selection
  cannot retroactively change it. If that function takes hidden evidence parameters, the call site
  inside the block supplies the selected evidence.

No runtime lookup, dictionary object, or new ABI is introduced.

### Defaults, nominal conformance, and owner-directed dispatch

Owner-directed dispatch from ZEP-0135 is unchanged. An operation is still resolved through the
contract that declares it. Selection, whether block-scoped or call-site, only changes which provider
supplies that contract's evidence.

For a selected bundle, a child contract operation dispatches through the bundle's member for the
declaring contract. A direct `combine` call on `Int` inside a multiplication bundle uses the bundle's
`Semigroup<Int>` member, not the ambient additive default.

Nominal class conformance remains authoritative and cannot be replaced by a selection. A selected
provider for a contract the target class already implements nominally is rejected.

### Generic and higher-kinded bundles

A generic bundle is selected with explicit type arguments in the initial design:

```zeron
using witness (ListMonoid<Int>) {
    let result = combineAll(intLists);
}
```

Unapplied generic selection is deferred. A future extension may let a block hold a provider scheme
for all matching instantiations, but the initial rule keeps each selection concrete. The same
explicit-application rule applies to generic standalone witnesses; selecting one inserts its applied
contract and target pair.

A bundle with a fixed constructor target and no bundle type parameters, such as
`OptionInstances for Option<_>`, is selected by name and needs no type arguments:

```zeron
using witness (OptionInstances) {
    let combined = sequence(options);
}
```

A bundle with its own type parameters, whether ordinary type parameters or constructor parameters,
still requires explicit type arguments, like any other generic provider.

A selection with a concrete target, applied or constructor, does not affect a use under an abstract
constructor bound. The bound's own evidence is used.

### Operators, display, and `do` notation

The local environment must be consulted by every evidence path that can be resolved inside the
block, not only by direct witness-member lookup. A call-site clause applies only to its direct
invocation; operator and `do`-notation lowering continue to use block and ambient evidence.

Initial supported cases:

- ordinary contract operations, including `Comparable` and user-defined contracts;
- equality operators on nominal targets that use a user-defined `Eq` witness, so a selected `Eq` is
  observable; compiler-owned structural and built-in equality remain outside selection;
- `Display` evidence used by string concatenation and formatting, so a selected display provider is
  observable;
- `do` notation, which resolves its generated operations through the selected `Monad`,
  `Applicative`, and `Functor` providers when the constructor is concrete;
- class construction with bounded type parameters: evidence selected at the construction site is
  retained by the instance as usual.

Not selectable in the initial design:

- compiler-synthesized structural `Eq` and `Hashable` for sums and products;
- built-in `Eq` and `Hashable` for scalar types;
- derived serialization evidence and `Codec` synthesis;
- the compiler-owned `Main<A>` entry-point evidence;
- intrinsic arithmetic lowering for built-in numeric types. Selecting a different `Numeric<Int>` does
  not change `+` on `Int`; use a bundle's explicit operations or a tagged type instead.

The `Display` exception is intentional: presentation is a legitimate local choice, and alternate
display is a primary use case. Compiler-owned equality and hashing are excluded because they interact
with built-in lowering and structural derivation. A user-defined `Eq`/`Hashable` witness for a
nominal target remains selectable, but hash tables capture evidence, so this is the least settled
part of the design; see Open questions.

### Name resolution

- A qualified name resolves a public provider without requiring an import.
- An unqualified name resolves through the current package and witness imports, including aliases
  and witness wildcard imports.
- `import witness pkg.Name;` and `import witness pkg.*;` make public bundle names available for
  selection without activating the bundles. For bundle names, the two forms differ only in which
  names they introduce; neither activates a bundle.
- A package-local provider is usable only inside its package.
- A witness alias may be used as a selection name. This refines ZEP-0114's diagnostic-only alias rule
  for explicit selection; aliases still do not affect applicability or implicit activation.
- Ambiguous unqualified names use the existing import diagnostics; a qualified name disambiguates.

### Interaction with ambient coherence

Selection does not add providers to the compilation unit's ambient active scope. Therefore:

- ZEP-0004 active-scope overlap checking is unchanged.
- Two named bundles or standalone witnesses may be selected in different blocks even when they
  provide the same contract and target, provided neither is ambiently active.
- Importing overlapping standalone witnesses still triggers the existing ambiguity or overlap error.
  To use two standalone alternates in one file, reference them by qualified name inside their
  respective blocks instead of importing both.
- A selected provider that duplicates an ambient default shadows it locally; no ambiguity is
  reported between the selection and the shadowed default.

### Example: two monoids in one file

```zeron
import zeron.control.Monoid;

fn addAll(values: List<Int>): Int = combineAllWithAddition(values);

fn multiplyAll(values: List<Int>): Int {
    using witness (acme.math.Multiplication) {
        return combineAll(values);
    }
}
```

`combineAll` requires `Monoid<Int>`. Inside the block, the multiplication bundle supplies both
`Monoid<Int>` and `Semigroup<Int>`, so identity and combination agree. Outside, the canonical additive
default remains in effect. Neither bundle needs to be imported as ambient evidence.

### Example: alternate display

```zeron
using witness (acme.format.HexDisplay) {
    let text = "value = " + value; // uses HexDisplay for Int
}

let ordinary = "value = " + value; // ambient display
```

### Diagnostics

Report:

- an unknown provider name;
- an ambiguous unqualified provider name;
- an inaccessible or non-public provider;
- an attempt to select a default, anonymous, or derived provider by name;
- a duplicate selection of the same provider;
- two different providers for the same applied pair in one block;
- a bundle dependency conflict between selected bundles;
- a generic bundle selected without required type arguments;
- selection of an unsupported contract or compiler-owned evidence path;
- a selected provider that conflicts with nominal class conformance;
- a call-site provider that matches no evidence requirement of the invocation;
- a call-site clause on an invocation with no hidden evidence parameters;
- two different call-site providers for the same applied pair;
- a call-site generic provider selected without required type arguments;
- a call whose evidence requirements cannot be determined because its type arguments remain
  unresolved.

Messages should name the provider, contract, target, and block. For example:

```text
Selection conflict: 'Multiplication' provides Semigroup<Int>, but
'CustomAdditive' provides Semigroup<Int> in the same witness context.
```

### Scope form

Statement-level selection is block-only. Expression-level selection is limited to the single-call
`with witness (...)` clause; declaration-site forms are future work:

```zeron
// Future possibility, not part of this proposal:
fn renderHex(value: Int): String using witness (HexDisplay) = ...;
```

Block scope is sufficient for local algorithms, formatting, and tests, while the call-site clause
covers a single invocation without a surrounding block. The block form is a statement, not an
expression: it cannot be used directly as a `let` initializer or an expression-bodied function
result. Use a block body and an explicit `return` when the surrounding function must produce a
value. The call-site clause is a postfix on a call and does not by itself create a scope for other
expressions.

## Compatibility and impact

- The syntax is additive. `using`, `witness`, and the soft keyword `with` are already available, and
  resource `using` keeps its current grammar and disposal semantics.
- Named bundle selection depends on ZEP-0136 metadata and its API-index schema bump.
- Selection itself is source-local and needs no API-index or runtime ABI change.
- Standalone witness import and activation behavior is unchanged. A qualified selection without an
  import is a new explicit local activation path.
- Aliases become usable as selection names for selected providers. This is a deliberate refinement
  of ZEP-0114's statement that aliases are diagnostic-only; it does not change implicit activation.
- The compiler must consult the local environment in direct member lookup, generic evidence
  forwarding, `Display` and string-concatenation lowering, user-defined equality operators, and
  `do` notation. Missing one of these paths would make selection behave inconsistently.
- Call-site selection adds a postfix clause to direct calls. It changes no signature, API-index
  metadata, or runtime ABI; it supplies providers to the call's existing hidden evidence slots.
- Formatter, highlighter, and LSP hover, completion, and diagnostics need the new statement, the
  call-site clause, and provider references.
- Documentation should explain selection-only bundles, local shadowing of defaults, and the
  difference between importing a provider and selecting it.

## Alternatives

- **First-class evidence arguments at call sites.** More local than a block, but making evidence an
  ordinary value changes signatures and inference and exposes it in the ABI. Rejected. A
  provider-reference clause on a call is retained instead: it selects providers for existing hidden
  evidence slots without adding a value argument.
- **Declaration-site `using witness` on functions.** Makes dependencies visible to callers and avoids
  nesting, but is less flexible inside an expression and affects the function's public surface.
  Deferred as a future form.
- **Import-only selection.** The current workaround: one witness per file or package. It cannot
  express two interpretations in one file and forces project structure to carry a local choice.
  Rejected for the target problem.
- **Ranked or most-specific witness selection.** Rejected by ZEP-0004; it makes selection depend on
  declaration or import order and hides genuine ambiguity.
- **Runtime dynamic scope.** Would allow selection to cross function boundaries without evidence
  parameters, but conflicts with static selection, separate compilation, and the existing
  method-handle ABI. Rejected.
- **Newtype tags only.** Tagged types preserve global coherence and are the right choice when the
  algebra is part of a value's type, but they require wrapping and conversion. Bundles plus local
  selection are complementary.
- **Bundle-only selection.** Simpler, but standalone named witnesses with no prerequisites are also
  useful locally, and the mechanism should not force every witness into a bundle. Standalone
  selection is allowed with the coherence caveat.
- **Reusing bare `using (Name)`.** Avoids a new form but overloads resource management and makes
  `using` mean two unrelated things. The `using witness` spelling keeps the concepts separate.
- **Per-call provider-value arguments.** A middle ground between a block and first-class evidence,
  but making evidence an argument changes call signatures and inference. The provider-reference
  postfix clause above is not this alternative: it selects providers for existing hidden evidence
  slots and adds no value argument. Arbitrary per-call evidence values remain rejected; the
  provider-reference form is accepted for direct calls.

## Implementation and validation

Likely stages:

1. Add the `using witness (...)` statement, the call-site `with witness (...)` postfix, provider
   references, optional applied type arguments, and AST nodes to the parser and formatter.
2. Resolve provider names, aliases, qualified names, visibility, and generic bundle arguments.
3. Add a scoped selection stack to `ResolutionContext` and make witness lookup consult it before
   ambient providers.
4. Expand bundle selections with ZEP-0136 member and dependency metadata, match generic and
   constructor pairs against concrete uses, and enforce same-block conflict rules.
5. Thread the local environment through direct member lookup, generic evidence forwarding, `Display`
   and string-concatenation lowering, user-defined equality operators, and `do` notation.
6. Resolve call-site providers after call type-argument substitution, validate them against the
   callee's hidden evidence requirements, and consult that call-local map before the block stack.
7. Ensure closures and function references capture selected handles at creation, and that no runtime
   lookup or ABI change is introduced.
8. Update the highlighter, LSP hover/completion/diagnostics, guides, design-document-15, and the
   `using`-statement documentation.
9. Keep ambient overlap and import behavior unchanged; add regression tests proving no leakage.

Validation should cover:

- hexadecimal and ordinary `Display<Int>` in adjacent blocks;
- additive and multiplicative `Monoid<Int>` bundles in one file, including direct `combine` and
  `empty` use;
- a generic function call receiving selected evidence, and an abstract-type use that falls back to
  its bounds;
- one call annotated with a different provider while an enclosing block keeps its own selection;
- a call-site bundle supplying a coherent prerequisite chain, and a call-site standalone witness
  whose prerequisite falls back to the surrounding scope;
- a call-site clause on a function without hidden evidence parameters, rejected;
- an unused call-site standalone provider and a bundle with an unrelated root;
- call-site type inference remaining independent of the provider, with an unresolved call rejected;
- HKT and generic call-site providers, including an applied generic bundle;
- closures created inside a block and invoked outside;
- nested blocks with shadowing and conflict diagnostics;
- two bundles sharing a canonical dependency, and two bundles disagreeing on it;
- selected providers shadowing ambient defaults and resuming outside the block;
- qualified selection without import, aliases, package-local access, and inaccessible providers;
- `do` notation under a selected `Monad` bundle;
- `Display` and string concatenation inside a selection;
- user-defined equality selection on a nominal target, and rejection of compiler-owned structural
  and built-in equality;
- nominal conformance conflicts and unsupported compiler-owned evidence;
- separate compilation, including a library function with pre-selected concrete evidence;
- formatter/highlighter/LSP parsing and diagnostics;
- focused resolver, emitter, and tooling tests, followed by the full `mvn test` suite once the
  implementation is complete.

## Open questions

- Should generic bundles support unapplied selection as a provider scheme for every matching
  instantiation in the block, or remain explicitly applied?
- Should the call-site spelling be `with witness (...)` or a postfix `using witness (...)`?
- Should function-value and closure invocation support call-site selection if their types carry hidden
  evidence parameters, or remain capture-only?
- Should class construction accept a call-site clause, or remain governed by the block construction
  rules?
- Should declaration-site selection be added later with the same environment?
- Should an unused selection produce a warning, and should a selection that is never applicable be a
  warning or an error?
- Should selecting a standalone child witness warn when its prerequisites resolve to ambient default
  evidence that the author did not select?
- Should user-defined `Eq`/`Hashable` remain selectable for nominal targets, or should all
  `Eq`/`Hashable` selection be excluded initially because hash tables capture evidence? This proposal
  allows the user-defined nominal case and excludes compiler-owned structural and built-in evidence.
- Should aliases be usable for all named witnesses, or only for bundles? The proposal permits both
  for explicit selection while keeping them diagnostic-only for implicit activation.
- Should `import witness pkg.Bundle` have any effect beyond making the name available, such as
  enabling file-wide selection? The initial design says no.
- How should selection interact with compiler-owned entry points and `Main<A>` if a future form
  declares entry behavior in user code?
- Should the standard library provide canonical bundles for `Option`, `Result`, and `Stream` as part
  of a later migration, or remain separate default witnesses?

## Decision

Accepted on 2026-11-15 and extended on 2026-11-16 with call-site selection. `using witness (...)` is
a statement-level lexical context; a direct invocation may also carry a `with witness (...)` clause
that applies the same provider selection to that call's existing hidden evidence parameters. Both
forms select named bundles and named standalone witnesses, shadow ambient defaults locally, and
introduce no runtime lookup, evidence values, or dynamic scope. Added as a `0.8.0` candidate;
implementation depends on ZEP-0136 bundle metadata and follows normal project prioritization.
