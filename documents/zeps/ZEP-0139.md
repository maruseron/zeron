## Abstract

Add a `new` constructor to guarded newtypes alongside the existing option-producing `tryNew`. The
new constructor is checked:

- if the validator and argument are constant-foldable and the predicate is true, emit no runtime
  check;
- if they are constant-foldable and the predicate is false, report a compile-time error; and
- otherwise, emit a runtime validator check whose failure propagates to the host like a checked
  cast.

`tryNew` keeps its current `Option` result and remains the total, non-throwing path. Guarded newtypes
continue to have no source-accessible unchecked constructor.

## Motivation

A guarded newtype currently exposes only `tryNew`, so every construction from a literal, a constant,
or a value already proven valid forces `Option` handling:

```zeron
public newtype UserId = String where value != "";

let id = UserId.tryNew("ada"); // Option<UserId>
```

That is correct, but it makes the common case noisy and discourages small validated types. A checked
`new` gives the ergonomic path without weakening the invariant. Constant folding removes the check
for literal and constant construction; a runtime check covers dynamic values; a provably false
constant is a compile error.

The design mirrors the existing checked `as` and safe `as?` pair: `new` is the checked operation that
fails on violation, and `tryNew` is the option-producing alternative. It also avoids making `new`
available only when the optimizer happens to fold the argument.

## Goals

- Expose `new` on guarded newtypes with the same validator as `tryNew`.
- Elide the runtime check when the predicate is statically true.
- Reject provably false constant construction at compile time.
- Use a runtime check for dynamic or non-foldable predicates.
- Evaluate the argument and the validator once, with no temporary `Option`.
- Keep `tryNew` unchanged.
- Preserve the existing restriction that guarded newtypes have immutable `Int`, `Float`, `Boolean`,
  or `String` representations.
- Report the failure mode and remediation clearly.

## Non-goals

- Changing `tryNew` or removing it.
- Changing unvalidated newtypes, which already use an ordinary unchecked `new`.
- Allowing guarded newtypes over mutable or arbitrary nominal representations.
- Bypassing validated construction for deserialization or host interop.
- Compile-time evaluation of arbitrary calls or mutable reads.
- Removing the runtime check for dynamic values.
- General constructor overloading or ad-hoc validation expressions at call sites.

## Proposal

### Surface

A guarded newtype exposes both constructors:

```zeron
public newtype UserId = String where value != "";

let a = UserId.new("ada");       // UserId
let b = UserId.tryNew(input);    // Option<UserId>
```

An unvalidated newtype keeps its ordinary total constructor:

```zeron
public newtype Meters = Float;
let m = Meters.new(1.5);         // no validator, no check
```

`new` and `tryNew` share one validator and one argument type. The only difference is failure
representation.

### Static evaluation

The compiler attempts to evaluate the validator with the supplied argument using the constant
evaluator from [ZEP-0138](./ZEP-0138.md). There are three outcomes:

| Outcome | `new` behavior |
| --- | --- |
| Constant `true` | Emit the constructed value; no runtime check |
| Constant `false` | Report a compile-time error; emit no code |
| `UNKNOWN` | Emit a runtime validator check |

Once comparison and refined-type facts from [ZEP-0140](./ZEP-0140.md) are available, a stable
validator is also checked against the current fact context. Facts that entail the substituted
predicate elide the check; facts that entail its negation make the call a compile-time error. This
generalizes constant `true` and `false` to proven `true` and `false` without changing the runtime
behavior. An unstable validator still uses the runtime path, because facts do not describe the state
it observes.

The static check is an optimization and a diagnostic improvement, not a requirement. A validator
that calls a helper, reads a public immutable value not known at compile time, or uses an unsupported
operation still has a usable `new`; it simply uses the runtime path.

Compile-time rejection is limited to stable validators: those the constant evaluator can evaluate, or
those the fact context can decide. Zeron does not promise validator purity, so a validator that reads
mutable state or calls a function is never folded and never produces a static `true` or `false`; it
always takes the runtime path. This
keeps the compile-time error sound even though the language has no general purity guarantee.

A provably false constant should not suggest that `tryNew` might succeed. The diagnostic should say
that the predicate is false for the supplied value. The `tryNew` suggestion belongs to the
`UNKNOWN` case, where the value is dynamic.

### Lowering

`new` must evaluate its argument once, even when the validator mentions `value` more than once.
Source-level lowering is:

```text
let v = argument;          // one evaluation
if (validator[v/value]) return v;
fail("...");               // uncatchable runtime failure
```

The constructed newtype is its representation, so no wrapper allocation is introduced. The
runtime-failure path uses the same host-exception convention as a failed checked `as`: Zeron source
has no catch construct, and the failure propagates to the caller or host. The exact failure type and
message are an implementation decision; the observable rule is that a failed dynamic `new` does not
return a value.

The compiler may inline the validator. If inlining would duplicate an effectful argument or an
effectful validator subexpression, the compiler must bind the value first and preserve the existing
evaluation order.

### Validator semantics

`new` and `tryNew` must agree on every input. They share:

- the same argument evaluation;
- the same `value` binding;
- the same short-circuit behavior;
- the same integer overflow and string equality semantics; and
- the same treatment of a validator that raises an effect.

A validator has no declared raised effects today. If a future proposal permits effects in a
validator, `new` must not silently discard them; it should either propagate them through its own
declared effects or reject the validator. This proposal assumes the current no-effect rule.

### Diagnostics

The two failure modes are distinct:

- **Provably false**: an error at the `new` call, naming the predicate and the failing value or
  known facts. The help text explains the value is invalid, not that the compiler could not decide.
- **Not provable**: no error. The compiler emits a runtime check. If a lint mode is added, it may
  note that the check could be removed by guarding the value or using `tryNew`, but the default is a
  working program.

A declaration-level diagnostic remains for a validator that is not a `Boolean` or that uses a
representation outside the guarded set.

### Separate compilation

`new` is an ordinary exported constructor compiled into the library. A consumer calls it without
needing the validator's source, so the invariant remains enforced even when the predicate is not
exported. If the predicate is exported through the [ZEP-0138](./ZEP-0138.md) metadata, consumers can
also treat the result as a proven value and elide later checks.

A library's `new` implementation is part of its behavior. Changing the validator changes when `new`
fails; that is a behavioral library change and follows the artifact version rules in
[ZEP-0012](./ZEP-0012.md).

### Interaction with flow facts

Once comparison and refined-type facts from [ZEP-0140](./ZEP-0140.md) are available, `new` can use a
statically proven argument:

```zeron
fn make(seed: Int) {
    if (seed > 0) {
        let p = Positive.new(seed); // statically true on this path
    }
}
```

Before that proposal lands, `new` still works with constants and dynamic runtime checks. The two
proposals are independent at the source level.

## Compatibility and impact

The change is source-additive. Existing guarded newtypes gain a public `new` constructor; existing
`tryNew` calls keep their meaning. Unvalidated newtypes are unchanged.

The new constructor is a public API addition and must be recorded in the API index and public member
catalog. For a guarded newtype, `new` is checked; for an unvalidated newtype, `new` remains total.
Documentation and completion must make that distinction visible.

The runtime gains an uncatchable failure path for dynamic `new`, analogous to checked `as`. Programs
that only use `tryNew` see no behavior change. Programs that use `new` with a dynamic value accept
that failure mode explicitly.

No JVM descriptor change is required beyond the new constructor entry. No standard-library version
change is required unless the standard library adopts `new` for its own guarded newtypes.

## Alternatives

- **Make `new` compile-time-only and reject `UNKNOWN`.** This was the original roadmap shape. It
  keeps `new` purely static but makes its availability depend on optimizer strength and forces a
  rewrite to `tryNew` for ordinary dynamic input. Rejected as the default; it could be offered as a
  lint or a separate strict constructor.
- **Keep only `tryNew`.** This preserves the status quo but keeps the ergonomic problem that
  motivated the proposal. Rejected.
- **Allow an unchecked `new` on guarded newtypes.** This bypasses the invariant and contradicts the
  existing no-unchecked-constructor rule. Rejected.
- **Return `Result` or `Option` from `new`.** This duplicates `tryNew` and makes constructor calls
  inconsistent with the checked-cast precedent. Rejected.
- **Use a distinct name such as `newChecked` or `newConst`.** A distinct name would preserve the
  strict compile-time-only behavior but adds another constructor spelling. `new` is preferred because
  guarded and unguarded newtypes already share the same construction call shape, and the guard is the
  distinguishing property.

## Implementation and validation

Likely stages:

1. Extend the generated newtype namespace with `new` for guarded newtypes.
2. Add argument binding and validator inlining without duplicate evaluation.
3. Add the constant-evaluation path and the provably-false diagnostic.
4. Add the runtime-failure lowering and test the host propagation boundary.
5. Record the constructor in the API index and public member catalog.
6. Update completion, hover, signatures, and guide examples.

Validation should cover:

- literal true, literal false, and dynamic arguments;
- validators over `Int`, `Float`, `Boolean`, and `String`;
- validators that use calls or unsupported operations and therefore take the runtime path;
- argument side effects evaluated exactly once;
- agreement between `new` and `tryNew` on the same inputs;
- overflow, division by zero, NaN, and string equality in constant evaluation;
- separate compilation of a guarded newtype in a compiled library;
- public member catalog and API-index round-trips; and
- unchanged behavior for unvalidated newtypes and existing `tryNew` calls.

## Open questions

- Which host exception type and message should a failed dynamic `new` use?
- Should the compiler offer a warning when a constant `tryNew` is always `None`, or is that a lint
  outside this proposal?
- Should a strict compile-time-only constructor exist as an opt-in for safety-critical APIs?
- Should `new` be usable in constant expressions, or is that a later constant-value feature?
- How should a future effectful validator interact with `new`?
