## Abstract

Add a `new` constructor to guarded newtypes alongside the existing option-producing `tryNew`. The
new constructor is checked:

- if the validator and argument are constant-foldable and the predicate is true, or the fact
  context proves the predicate, emit no runtime check;
- if the same evaluation proves the predicate false, report a compile-time error on a reachable
  path; and
- otherwise, emit a runtime validator check whose failure propagates to the host like a checked
  cast.

`tryNew` keeps its current `Option` result for validation outcomes; a validator fault propagates
from both constructors. A failed dynamic `new` raises `zeron.runtime.ValidationException`, a
host-visible runtime exception that Zeron source cannot handle. Guarded newtypes continue to have
no source-accessible unchecked constructor.

## Motivation

A guarded newtype currently exposes only `tryNew`, so every construction from a literal, a constant,
or a value already proven valid forces `Option` handling:

```zeron
public newtype UserId = String where value != "";

let id = UserId.tryNew("ada"); // Option<UserId>
```

That is correct, but it makes the common case noisy and discourages small validated types. A checked
`new` gives the ergonomic path without weakening the invariant. Constant folding removes the check
for literal and constant construction; a runtime check covers dynamic values; a provably false
constant is a compile error.

The design mirrors the existing checked `as` and safe `as?` pair: `new` is the checked operation that
fails on violation, and `tryNew` is the option-producing alternative. It also avoids making `new`
available only when the optimizer happens to fold the argument.

## Goals

- Expose `new` on guarded newtypes with the same validator as `tryNew`.
- Elide the runtime check when the predicate is statically true.
- Reject provably false constant construction at compile time.
- Use a runtime check for dynamic or non-foldable predicates.
- Evaluate the argument and the validator once, with no temporary `Option`.
- Keep `tryNew` unchanged.
- Preserve the existing restriction that guarded newtypes have immutable `Int`, `Float`, `Boolean`,
  or `String` representations.
- Define stable validators and use them for static proof without assuming general purity.
- Use one host-visible validation failure type, shared with later parameter-precondition checks.
- Report the failure mode and remediation clearly.

## Non-goals

- Changing `tryNew` or removing it.
- Changing unvalidated newtypes, which already use an ordinary unchecked `new`.
- Allowing guarded newtypes over mutable or arbitrary nominal representations.
- Bypassing validated construction for deserialization or host interop.
- Compile-time evaluation of arbitrary calls or mutable reads.
- Removing the runtime check for dynamic values.
- General constructor overloading or ad-hoc validation expressions at call sites.

## Proposal

### Surface

A guarded newtype exposes both constructors:

```zeron
public newtype UserId = String where value != "";

let a = UserId.new("ada");       // UserId
let b = UserId.tryNew(input);    // Option<UserId>
```

An unvalidated newtype keeps its ordinary total constructor:

```zeron
public newtype Meters = Float;
let m = Meters.new(1.5);         // no validator, no check
```

`new` and `tryNew` share one validator and one argument type. The only difference is failure
representation.

### Stable validators

A validator is **stable** when its body is expressible in the scalar fact IR from
[ZEP-0138](./ZEP-0138.md) and its free names are limited to `value`, compile-time constants, and
literal-initialized public immutable scalar or `String` values. It may not call functions or
constructors, allocate, read mutable state, use type or null tests, or use `Float` terms.

Only a stable validator can be queried against the fact context. Ground constant folding is broader:
a validator whose body is constant-foldable can still be evaluated for a constant argument,
including `Float` comparisons with the documented NaN and signed-zero semantics. A validator that is
neither constant-foldable nor stable is still enforced at runtime by `new` and `tryNew`; it simply
never produces a symbolic `true` or `false`. This is a precision rule, not a purity guarantee.

### Static evaluation

The compiler attempts to evaluate the validator with the supplied argument using the constant
evaluator from [ZEP-0138](./ZEP-0138.md). There are three outcomes:

| Outcome | `new` behavior |
| --- | --- |
| Constant `true` | Emit the constructed value; no runtime check |
| Constant `false` | Report a compile-time error; emit no code |
| `UNKNOWN` | Emit a runtime validator check |

Ground constant folding is independent of symbolic term formation. A ground validator can be
evaluated exactly even when its arithmetic would be unsafe to form as a symbolic term; wrapping and
string semantics follow [ZEP-0138](./ZEP-0138.md), while division or remainder by zero yields
`UNKNOWN` and falls back to the runtime check. Facts use only formed terms, so an overflow-unsafe
expression can decide a constant call while still yielding `UNKNOWN` for a dynamic one.

Once comparison and refined-type facts from [ZEP-0140](./ZEP-0140.md) are available, a stable
validator is also checked against the current fact context. Facts that entail the substituted
predicate elide the check; facts that entail its negation make the call a compile-time error. This
generalizes constant `true` and `false` to proven `true` and `false` without changing the runtime
behavior. An unstable validator is never queried against the fact context, because facts do not
describe the state it observes; if it is constant-foldable, only ground evaluation applies.

The static check is an optimization and a diagnostic improvement, not a requirement. A validator
that calls a helper, reads a public immutable scalar or `String` value not known at compile time, or
uses an unsupported operation still has a usable `new`; it simply uses the runtime path.

Static rejection is limited to validators the constant evaluator can evaluate with a ground
argument, or those the fact context can decide with a stable validator. Zeron does not promise
validator purity, so a validator that reads mutable state or calls a function is never folded and
never produces a symbolic `true` or `false`; it always takes the runtime path. This keeps the
compile-time error sound even though the language has no general purity guarantee.

A provably false constant should not suggest that `tryNew` might succeed. The diagnostic should say
that the predicate is false for the supplied value. The `tryNew` suggestion belongs to the
`UNKNOWN` case, where the value is dynamic. A provably false call in unreachable code is not
reported, because there is no executable obligation there.

### Lowering

`new` must evaluate its argument once, even when the validator mentions `value` more than once.
Source-level lowering is:

```text
let v = argument;          // one evaluation
if (validator[v/value]) return v;
throw ValidationException; // host-visible, not a Zeron effect
```

The constructed newtype is its representation, so no wrapper allocation is introduced. A failed
dynamic `new` raises `zeron.runtime.ValidationException`, which extends
`java.lang.IllegalArgumentException`. The exception identifies the guarded declaration and explains
that the validator rejected the value; it does not include the raw value by default. It is a host
exception, not a Zeron effect: Zeron source cannot handle it, and it propagates to the caller or
host like a failed checked cast. Host code may catch it as `ValidationException` or as
`IllegalArgumentException`. [ZEP-0144](./ZEP-0144.md) uses the same type for a failed parameter
precondition at a runtime entry check.

The observable rule is that a failed dynamic `new` does not return a value. A validator that itself
faults propagates its original exception instead of being wrapped in `ValidationException`.

The compiler may inline the validator. If inlining would duplicate an effectful argument or an
effectful validator subexpression, the compiler must bind the value first and preserve the existing
evaluation order.

### Validator semantics

`new` and `tryNew` must agree on every input. They share:

- the same argument evaluation, which happens exactly once;
- the same `value` binding, which is evaluated once;
- the same short-circuit behavior;
- the same integer overflow and string equality semantics; and
- the same propagation of a validator fault.

They differ only when the validator returns `false`: `new` raises `ValidationException`, while
`tryNew` returns `None`. If the validator itself throws, both propagate the original exception.

A validator has no declared raised effects today. If a future proposal permits effects in a
validator, `new` must not silently discard them; it should either propagate them through its own
declared effects or reject the validator. This proposal assumes the current no-effect rule.

### Diagnostics

The diagnostic cases are distinct:

- **Provably false**: an error at the `new` call, naming the predicate and the failing value or
  known facts. The help text explains the value is invalid, not that the compiler could not decide.
  A provably false call in unreachable code is not reported.
- **Not provable**: no error. The compiler emits a runtime check. An optional lint may note that the
  check could be removed by guarding the value or using `tryNew`, but the default is a working
  program.
- **Constant `tryNew` always `None`**: a warning when a constant-foldable validator and a ground
  argument prove the validator false, or a stable validator and facts prove it false. `tryNew`
  remains total for validation outcomes; the warning identifies a definite `None` result.
- **Runtime fallback**: an optional warning when a stable validator's check could not be elided. It
  is advisory only; the runtime check is the designed path.

A declaration-level diagnostic remains for a validator that is not a `Boolean` or that uses a
representation outside the guarded set.

### Separate compilation

`new` is an ordinary exported constructor compiled into the library. A consumer calls it without
needing the validator's source, so the invariant remains enforced even when the predicate is not
exported. If the predicate is exported through the [ZEP-0138](./ZEP-0138.md) metadata, consumers can
also treat the result as a proven value and elide later checks.

A library's `new` implementation is part of its behavior. Changing the validator changes when `new`
fails; that is a behavioral library change and follows the artifact version rules in
[ZEP-0012](./ZEP-0012.md).

### Interaction with flow facts

Once comparison and refined-type facts from [ZEP-0140](./ZEP-0140.md) are available, `new` can use a
statically proven argument:

```zeron
fn make(seed: Int) {
    if (seed > 0) {
        let p = Positive.new(seed); // statically true on this path
    }
}
```

Before that proposal lands, `new` still works with constants and dynamic runtime checks. The two
proposals are independent at the source level.

## Compatibility and impact

The change is source-additive. Existing guarded newtypes gain a public `new` constructor; existing
`tryNew` calls keep their meaning. Unvalidated newtypes are unchanged.

The new constructor is a public API addition and must be recorded in the API index and public member
catalog. For a guarded newtype, `new` is checked; for an unvalidated newtype, `new` remains total.
Documentation and completion must make that distinction visible.

The runtime gains `ValidationException` for a failed dynamic `new`, analogous to the host failure of
checked `as` but distinct from `ClassCastException`. Programs that only use `tryNew` see no behavior
change. Programs that use `new` with a dynamic value accept that failure mode explicitly.

No JVM descriptor change is required beyond the new constructor entry. No standard-library version
change is required unless the standard library adopts `new` for its own guarded newtypes.

## Alternatives

- **Make `new` compile-time-only and reject `UNKNOWN`.** This was the original roadmap shape. It
  keeps `new` purely static but makes its availability depend on optimizer strength and forces a
  rewrite to `tryNew` for ordinary dynamic input. Rejected as the default; it could be offered as a
  lint or a separate strict constructor.
- **Keep only `tryNew`.** This preserves the status quo but keeps the ergonomic problem that
  motivated the proposal. Rejected.
- **Allow an unchecked `new` on guarded newtypes.** This bypasses the invariant and contradicts the
  existing no-unchecked-constructor rule. Rejected.
- **Return `Result` or `Option` from `new`.** This duplicates `tryNew` and makes constructor calls
  inconsistent with the checked-cast precedent. Rejected.
- **Use a distinct name such as `newChecked` or `newConst`.** A distinct name would preserve the
  strict compile-time-only behavior but adds another constructor spelling. `new` is preferred because
  guarded and unguarded newtypes already share the same construction call shape, and the guard is the
  distinguishing property.
- **Reuse `ClassCastException` for a failed `new`.** A failed validator is not a failed cast, and
  hosts could not distinguish the two. Rejected.
- **Use a bare `IllegalArgumentException` without a dedicated type.** It loses the ability to
  identify validation failures and to share one runtime contract with parameter preconditions.
  Rejected.

## Implementation and validation

Likely stages:

1. Extend the generated newtype namespace with `new` for guarded newtypes.
2. Classify stable validators against the scalar fact IR and define the runtime fallback.
3. Add argument and validator binding without duplicate evaluation.
4. Add the constant-evaluation path, the fact-context query, and the provably-false diagnostic.
5. Add `ValidationException` and the runtime-failure lowering, including host propagation.
6. Add the constant-`tryNew` warning and the optional runtime-fallback lint.
7. Record the constructor in the API index and public member catalog.
8. Update completion, hover, signatures, and guide examples.

Validation should cover:

- literal true, literal false, and dynamic arguments;
- validators over `Int`, `Float`, `Boolean`, and `String`;
- stable and unstable validators, including calls and unsupported operations;
- constant folding that is exact despite overflow-unsafe symbolic formation;
- argument and validator evaluation exactly once, in order;
- agreement between `new` and `tryNew` on the same inputs;
- a validator that faults propagating the original exception from both paths;
- `ValidationException` identity, host catchability, and message without raw values;
- separate compilation of a guarded newtype in a compiled library;
- public member catalog and API-index round-trips; and
- unchanged behavior for unvalidated newtypes and existing `tryNew` calls.

## Open questions

None remain for version 1. The runtime failure type, constant `tryNew` warning, strict-constructor
question, constant-expression use, effectful-validator rule, and stable-validator boundary are
settled in the Decision.

## Decision

Accepted 2026-11-27.

The settled design is:

- guarded newtypes gain a checked `new`; a constant-true or fact-proven validator elides the
  runtime check, a constant-false or fact-proven false one is a compile error on a reachable path,
  and `UNKNOWN` emits a runtime check;
- only a stable validator participates in fact queries; ground constant folding can evaluate a
  constant-foldable validator, including ground `Float`, without making it a flow fact; an unstable,
  non-constant validator always uses the runtime path;
- ground constant folding is independent of symbolic term formation, so exact constant results are
  available even when the expression is unsafe to form as a symbolic term;
- once ZEP-0140 facts are available, a stable validator is substituted and queried; `TRUE` elides,
  `FALSE` errors on a reachable path, and `UNKNOWN` keeps the runtime check;
- the argument is evaluated once, then the validator once; `new` and `tryNew` share argument and
  validator behavior, and differ only when the validator returns `false`;
- a false validator result raises `zeron.runtime.ValidationException`, which extends
  `java.lang.IllegalArgumentException`, identifies the declaration, omits the raw value by default,
  and is shared with ZEP-0144's parameter-precondition entry check;
- a validator fault propagates unchanged from both `new` and `tryNew`;
- `new` in unreachable code is not diagnosed as a false predicate;
- a constant-foldable or fact-proven ground-false argument warns on `tryNew`; a runtime fallback may
  produce an advisory lint, but not an error;
- no strict compile-time-only constructor and no constant-expression form are added in version 1;
- effectful validator declarations remain rejected; a future effectful-validator proposal must make
  `new` declare and propagate its effects;
- `new` is recorded in the API index and public member catalog, and changing the validator is a
  behavioral library change under [ZEP-0012](./ZEP-0012.md).
