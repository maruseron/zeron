## Abstract

Extend flow typing from nullness and runtime-type alternatives to value facts. Conditions such as
`x > 0` and `x < n` establish normalized comparison facts on the true and false paths, and a binding
whose declared type is a guarded newtype with a stable validator contributes that predicate as a
type-intrinsic fact. Facts compose with `and`, `or`, and `not`, join across branches, invalidate on
writes, and can be queried for subsumption.

This is the flow-fact core of the static-verification roadmap. It does not add interval reasoning,
predicate functions, range loop facts, or parameter declarations; those are separate proposals.

## Motivation

The current flow model tracks nullness and possible runtime types. It cannot remember that a guard
proved `index >= 0` or that `index < length` holds in the body:

```zeron
if (index >= 0 and index < values.length) {
    use(index); // the compiler forgets both relations
}
```

That leaves the most common index and bounds patterns outside static verification.

Guarded newtypes have a related gap. A value of type `Positive` is known to satisfy `value > 0` at
construction, but the flow analyzer does not expose that fact. As a result, a `Positive` cannot
discharge a later precondition, and a checked constructor cannot use an existing proof.

The comparison facts and the newtype facts are the same kind of information in two sources: a
condition proves a formula on a path, and a guarded type guarantees a formula for every value. A
shared fact context can combine them.

## Goals

- Add normalized comparison facts over stable paths.
- Transfer facts through `and`, `or`, `not`, `if`, `while`, and value-producing `if`.
- Retain false-path facts so guard clauses work.
- Make stable guarded-newtype invariants available as type-intrinsic facts.
- Combine comparison and type-intrinsic facts in one query context.
- Preserve the existing branch-join and invalidation rules.
- Support subsumption queries used by checked construction and later parameter refinements.
- Degrade gracefully when a compiled library does not export a predicate.
- Keep facts as effective-type refinements; never change a binding's declared type.

## Non-goals

- Interval or difference-bound arithmetic; see [ZEP-0142](./ZEP-0142.md).
- Predicate functions with reusable named bodies; see [ZEP-0141](./ZEP-0141.md).
- Parameter declarations with `where`; see [ZEP-0144](./ZEP-0144.md).
- `IntRange` loop facts; see [ZEP-0143](./ZEP-0143.md).
- General arithmetic reasoning, multiplication, division, or modular relations.
- Full SMT or complete predicate decidability.
- Refining mutable fields, array slots, call results, or custom getters.
- Creating declared union or refinement types.

## Proposal

### Fact vocabulary and normalization

Facts use the IR from [ZEP-0138](./ZEP-0138.md). The initial source forms are:

```zeron
x == y
x != y
x < y
x <= y
x > y
x >= y
```

with `Int`, `Long`, `Boolean`, and `String` equality. Ordered comparisons are enabled for `Int` and
`Long`; string ordering is not. `Float` comparison facts are deferred because NaN and signed zero
need an explicit model.

Comparison operands are stable paths from [ZEP-0131](./ZEP-0131.md) or immutable structural terms
from [ZEP-0138](./ZEP-0138.md). A stable path is:

- a local, parameter, or `this` root;
- read-only storage-backed member segments;
- no mutable field, mutable property, array slot, call result, or custom getter; and
- no reassignment of the root between the test and the use.

A `Length(path)` term is an immutable structural observation of a stable array or string reference.
Array elements, mutable fields, call results, and custom getters are never operands.

An arbitrary expression on either side yields no fact. A test such as `f(x) > 0` still returns a
Boolean and still short-circuits, but it establishes nothing about a later read.

Normalization rewrites `x > 0` to `0 < x`, `x >= 0` to `0 <= x`, and `x != 0` to `not (x == 0)`.
For total orders, `not (x < 0)` becomes `0 <= x`. The normalizer is deterministic and idempotent.

### Condition transfer

The existing short-circuit transfer rules extend to comparison atoms:

- `A and B`: resolve `B` under the true facts of `A`; the true outcome combines both true paths.
  The false outcome joins `A` false with `A` true and `B` false.
- `A or B`: resolve `B` under the false facts of `A`; the true outcome joins `A` true with `A` false
  and `B` true. The false outcome combines both false paths.
- `not A`: swap the true and false outcomes.

Examples:

```zeron
if (x > 0) {
    // true: 0 < x
} else {
    // false: x <= 0
}

if (x >= 0 and x < n) {
    // true: 0 <= x and x < n
}

if (x < 0 or x >= n) {
    // false: 0 <= x and x < n
}
```

A guard clause keeps the fact after the early exit:

```zeron
if (index < 0) return;
// continuation: 0 <= index
```

Equality facts are exact:

```zeron
if (x == 5) {
    // true: x == 5
} else {
    // false: x != 5, retained as a negative atom
}
```

Disequality is not representable as a convex interval. The fact context keeps it as a negative atom;
the interval backend from [ZEP-0142](./ZEP-0142.md) must not pretend it is a range.

A comparison involving a mutable local is valid at the point of the test. Assigning the local kills
every fact that mentions it. A relational fact depends on both operands, so assigning either side
kills it.

### Refined-type facts

A guarded newtype with a stable validator carries that predicate as a **type-intrinsic fact**. Every
value of the newtype was constructed through `new` or `tryNew`, so the invariant holds for the value
itself:

```zeron
public newtype Positive = Int where value > 0;

fn use(p: Positive) {
    // the invariant holds for p's representation, independently of flow stability
}
```

Type-intrinsic facts differ from flow facts:

- they are derived from the declared type at each read;
- they do not require a stable path, because the invariant belongs to every value of the type;
- assigning a new value of the same type does not invalidate them, because the new value also
  satisfies the invariant; and
- they remain available across calls.

The fact is expressed over the carrier: `Carrier(p) > 0`. Since guarded newtypes lower directly to
their carrier, the view is zero-cost.

Ordered and equality facts are currently enabled for `Int`, `Long`, `Boolean`, and `String`.
A guarded `Float` newtype therefore carries no type-intrinsic flow fact until a NaN and signed-zero
model is specified. Its invariant is still enforced by `new` and `tryNew`; it simply does not
participate in flow proofs.

A newtype with no validator contributes no fact. A newtype whose predicate is not in the IR, or
whose predicate is unavailable from a compiled library, also contributes no fact. That is a loss of
precision, not a soundness failure.

A validator that calls an ordinary function or reads mutable state is not a stable predicate. It is
still enforced by `new` and `tryNew` at construction, but it contributes no type-intrinsic fact,
because the compiler cannot re-check it at each read. Only a validator expressed over `value` and
stable immutable observations, such as compile-time constants or public immutable values, counts as
an intrinsic invariant.

The trust assumption is the one recorded in [ZEP-0138](./ZEP-0138.md): all construction boundaries,
including host interop and deserialization, enforce validated construction. A future guarded newtype
over a mutable representation needs its own stability rule.

### Constructors and option paths

`Positive.new(argument)` produces a `Positive`, so the result carries the type-intrinsic fact. If
the argument was statically proven, the fact is already known; if the call used the runtime check,
the successful return still guarantees it.

`Positive.tryNew(argument)` produces `Option<Positive>`. On the `Some(payload)` path, the payload has
type `Positive`, so the fact follows from the payload type. On the `None` path, there is no value to
refine.

This makes the fact system independent of how validation is implemented. It depends only on the
nominal type of the value.

### Fact context and invalidation

The fact context follows [ZEP-0138](./ZEP-0138.md):

- `assume(formula)` adds a normalized fact;
- `check(formula)` returns `TRUE`, `FALSE`, or `UNKNOWN`;
- `join(left, right)` retains facts valid on both paths;
- `invalidate(path)` removes every fact mentioning the path; and
- lexical scope exit discards facts for bindings declared in that scope.

Invalidation rules:

- assigning a local kills facts that mention it;
- writing a mutable field kills facts that mention the field path;
- a call may change a mutable root or a mutable field, so those facts do not survive the call;
- immutable locals and parameters retain facts across calls, because calls cannot rebind them;
- read-only stable member paths retain facts unless a write can change a segment; and
- type-intrinsic newtype facts are not invalidated by these rules.

The existing flow engine already tracks assignments, calls, loop backedges, `break`, and `continue`.
This proposal plugs comparison formulas into that engine rather than creating a second dataflow
analysis.

### Joins and loops

At a branch join, retain only facts valid on every normally completing path. A conservative
implementation intersects the normalized fact sets. A solver-backed implementation may retain a fact
that both incoming contexts entail:

```text
join(F1, F2) = { f in facts(F1) union facts(F2) | entails(F1, f) and entails(F2, f) }
```

The candidate set should be bounded to avoid quadratic growth. The existing loop fixed-point
machinery applies: assignments kill facts at the assignment point, loop headers join preheader and
backedge states, and condition facts hold in the body. Interval widening belongs to
[ZEP-0142](./ZEP-0142.md).

### Subsumption

Subsumption asks whether the current facts imply a required predicate:

```text
implies(context, required) -> TRUE | FALSE | UNKNOWN
```

Examples:

```zeron
let p: Positive = Positive.new(5);
// implies(context, Carrier(p) > 0) = TRUE by type

if (index > 0) {
    // implies(context, index > 0) = TRUE by flow
}
```

Subsumption is used by [ZEP-0139](./ZEP-0139.md) for `new` and by
[ZEP-0144](./ZEP-0144.md) for parameter preconditions. This proposal supplies the query and the
fact sources; the consuming proposals define when a `FALSE` or `UNKNOWN` result is an error.

### Diagnostics and tooling

This proposal does not need a new error for an ordinary condition. It adds no runtime checks and no
changes to generated code.

Two advisory diagnostics are possible but not required:

- a note when a fact is established but immediately invalidated before use; and
- a warning when a condition is provably false or true under the current facts.

Any warning must be sound with respect to the fact model. An `UNKNOWN` result is never reported as a
contradiction.

The language server should show the effective facts for a stable binding on hover. Inlay hints are
optional. The formatter and highlighter need no changes because the source syntax is unchanged.

### Separate compilation

Type-intrinsic facts require the newtype predicate in the API index. The encoding is defined by
[ZEP-0138](./ZEP-0138.md). If a compiled library omits it:

- the nominal type still checks;
- construction still enforces the invariant;
- the consumer loses the type-intrinsic fact; and
- a later static proof that depends on it becomes `UNKNOWN` rather than unsound.

Flow facts are local to a compilation unit and are never exported.

## Compatibility and impact

The change is source-additive. Existing programs keep their meaning; some previously rejected
refinements and constructor calls become valid when a fact discharges them. There is no runtime
representation, descriptor, or generated-code change.

The resolver and flow analysis change. The API index changes only if predicates are exported through
[ZEP-0138](./ZEP-0138.md); the schema bump is shared with the other predicate-bearing proposals.

Tooling gains fact-aware hover and diagnostics. Guide examples should show both a direct comparison
guard and a guarded-newtype value used as proof.

## Alternatives

- **Keep only null and runtime-type facts.** This leaves the common numeric guard and index patterns
  unverified. Rejected.
- **Create a declared union or refinement type for each fact.** This changes the type system far
  beyond the goal and duplicates newtypes. Rejected.
- **Use an SMT solver for all conditions.** It is heavier, less predictable, and unnecessary for the
  initial fact vocabulary. Rejected for now.
- **Refine only bare locals and not stable member paths.** This is simpler but discards the stable
  path work already accepted in [ZEP-0131](./ZEP-0131.md). Rejected.
- **Treat newtype invariants as flow facts that invalidation can kill.** That is wrong: every value
  of the type satisfies the invariant, regardless of the flow state. Rejected.

## Implementation and validation

Likely stages:

1. Add comparison atoms to the existing flow condition transfer.
2. Add normalized fact storage, assignment invalidation, and branch joins.
3. Add type-intrinsic facts for guarded newtypes in the same module.
4. Add subsumption queries and use them in checked construction.
5. Add exported-predicate loading and graceful degradation for compiled libraries.
6. Add hover and fact diagnostics.

Validation should cover:

- true and false facts for each comparison operator;
- `and`, `or`, `not`, `else if`, `while`, and value-producing `if`;
- guard-clause facts after an early return;
- equality and disequality;
- assignment and call invalidation for locals, parameters, and stable member paths;
- relational facts invalidated by either operand;
- joins with facts valid on one path only;
- guarded newtype facts for `new`, `tryNew` `Some`, and assignment of another value of the same type;
- compiled-library degradation when the predicate is absent;
- interactions with existing null and runtime-type facts; and
- unchanged generated bytecode for programs that use no new fact.

## Open questions

- Should an immutable `let n: Int = p;` inherit the type-intrinsic fact from a `Positive` source, or
  should the nominal type be required?
- Should `Boolean` equality facts be normalized further, such as `x == true` to `x`?
- How should facts interact with `Any` boxing and unboxing?
- Should the join retain facts entailed by both contexts, or only syntactically common facts, in the
  first implementation?
- Should provably true or false conditions be warnings, or should diagnostics stay silent until the
  interval backend can explain them?
- Should `Float` comparison facts be included once a NaN model is specified?
