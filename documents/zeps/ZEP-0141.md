## Abstract

Add a `predicate fn` declaration form: a named Boolean function whose body is a formula in the
shared fact IR over its parameters. `predicate` is a declaration modifier on `fn`, matching the
`extension fn` and `mut fn` modifier family, rather than a separate declaration keyword. When a call
appears in a condition, the true path establishes the predicate formula for stable argument paths,
and the false path establishes its exact negation. The body is checked structurally against the fact
language, so a predicate cannot silently promise a fact it does not implement.

This separates reusable named conditions from the inline comparison facts in
[ZEP-0140](./ZEP-0140.md). It replaces the proposed `param is Type` return-type spelling with an
explicit declaration form.

## Motivation

Inline facts cover direct conditions, but the same test is often repeated:

```zeron
if (index >= 0 and index < values.length) { ... }
```

Users need a reusable name:

```zeron
if (isInBounds(index, values.length)) { ... }
```

The current language has ordinary Boolean functions, but calling one establishes no fact. The
compiler cannot tell whether `isInBounds` means exactly `0 <= index < length`, a weaker test, or an
unrelated predicate.

A dedicated declaration gives the compiler the formula. It also gives readers and tooling a stable
place to describe the fact, and it lets separate compilation export the formula without exporting the
body.

The earlier `param is Type` return-type idea was considered. It is ambiguous with type tests and
describes only type facts, not relational facts such as `low <= value < high`. A predicate
declaration covers scalar value relations; type and null facts stay in the existing flow layer and
are not predicate bodies in version 1.

## Goals

- Add a `predicate fn` declaration form with parameters and a fact-language body.
- Make the predicate an ordinary Boolean function at runtime.
- Check the body structurally so only declared facts are transferred.
- Transfer the predicate formula to stable argument paths on the true path.
- Transfer the exact negation on the false path.
- Support multiple parameters and relational formulas.
- Reject effects, mutable reads, and unsupported expressions in a checked predicate.
- Export public predicate formulas for separate compilation.
- Define what happens for non-stable arguments and function values.

## Non-goals

- General preconditions, postconditions, or arbitrary function contracts.
- Trusting arbitrary Boolean functions to refine values.
- Effects, mutation, allocation, or calls inside a checked predicate body.
- Generic predicates or higher-kinded predicate parameters in the first version.
- Runtime reflection over predicates.
- Changing `is`, `as`, or existing Boolean functions.
- Automatic inlining guarantees.

## Proposal

### Declaration syntax

`predicate` is a soft keyword modifier placed before `fn`. A predicate declares parameters and a
single fact-language expression:

```zeron
predicate fn isPositive(value: Int) = value > 0;

predicate fn isInBounds(index: Int, length: Int) =
    index >= 0 and index < length;

predicate fn isNonEmpty(value: String) = value != "";
```

The predicate modifier precedes `fn`; `mut` and a receiver are not allowed on a predicate. The
spelling reuses the ordinary `fn` declaration shape and keeps `predicate` available as an ordinary
identifier when it is not followed by `fn` in declaration position.

The predicate has the ordinary function type `(Int) -> Boolean` (or the corresponding parameter
types). It can be called anywhere a Boolean function is allowed. No explicit return type is needed;
if one is written, it must be `Boolean`.

A predicate does not declare a raised-effect row. Its body is pure by construction. If the body
needs a call, an allocation, or mutable state, it is not a predicate; it is an ordinary function and
transfers no fact.

### Body rules

A predicate body must be an expression in the scalar fact IR from [ZEP-0138](./ZEP-0138.md):

- its free names are the predicate's own parameters, compile-time constants, and literal-initialized
  public immutable scalar or `String` values;
- it may use comparisons, Boolean `and`, `or`, and `not`, and supported arithmetic terms;
- it may call another predicate function only if that call's formula can be inlined without cycles; the
  first version may reject predicate calls entirely;
- it may not use type tests, null tests, or other type/null flow facts;
- it may not use `Float` terms in version 1; `Float` predicates wait for the documented NaN and
  signed-zero flow model;
- it may not call ordinary functions, constructors, or external functions;
- it may not read `this`, mutable locals, mutable fields, array elements, or call results; and
- it may not allocate or raise effects.

The compiler checks the body by resolving it to the fact IR after normalization. The body *is* the
fact; there is no separate declared formula that could disagree with the implementation. If the body
falls outside the subset, the declaration is rejected with guidance to use an ordinary function.

This is deliberately stricter than "trust the Boolean function." A trusted-but-arbitrary predicate
would make flow facts unsound, and the language has no purity or effect analysis that could justify
the trust.

### Call-site transfer

When a predicate call appears in a condition, the compiler substitutes the argument expressions into
the predicate formula. A fact is established only when the substituted term is a stable path, a
constant, or an immutable structural term such as `values.length`:

```zeron
if (isPositive(index)) {
    // true: 0 < index
}

if (isInBounds(index, values.length)) {
    // true: 0 <= index and index < values.length
}
```

Non-stable arguments still call the predicate and still produce the correct Boolean, but establish
no fact:

```zeron
if (isPositive(next())) {
    // no fact about a later call
}
```

For a direct comparison, the false path gets the exact negation because the predicate body is an
exact formula:

```zeron
if (isPositive(index)) {
    // true: 0 < index
} else {
    // false: index <= 0
}
```

For a compound predicate, the false path is the negation of the whole formula. The fact context may
keep it as a normalized formula even when the interval backend cannot represent it. A consumer that
cannot use the negative form simply gets `UNKNOWN`.

The existing `and`, `or`, and `not` transfer rules apply. A predicate call in the left operand makes
its fact available in the right operand:

```zeron
if (isInBounds(index, length) and values[index] > 0) {
    // both facts are available
}
```

An `or` joins the successful alternatives. Facts that hold in only one alternative do not survive
the join; facts implied by every alternative do.

### Multiple parameters and relations

A predicate may relate several parameters:

```zeron
predicate fn isRange(value: Int, low: Int, high: Int) =
    low <= value and value < high;

if (isRange(x, 0, n)) {
    // 0 <= x and x < n
}
```

This is the main advantage over a single-parameter `param is Type` annotation. Substitution is
positional and simultaneous; a parameter name is replaced by the corresponding argument term.

### Stability and invalidation

A transferred fact follows the [ZEP-0140](./ZEP-0140.md) rules. The predicate call itself is pure,
so it cannot invalidate the arguments. The resulting fact is keyed by the stable paths in the
substituted arguments:

- assigning a mentioned local kills the fact;
- writing a mentioned mutable field kills the fact;
- a call that may change a mutable root kills the fact;
- immutable locals and parameters retain the fact; and
- constants remain constant.

A predicate call on an expression that is not a stable path, constant, or immutable structural term
establishes no fact. A predicate call on a stable path that is later reassigned loses the fact at the
assignment.

### Function values and separate compilation

A predicate is an ordinary function value. Calling it through a function value does not transfer a
fact in the first version, because the compiler would need the predicate formula attached to the
value and would need to preserve it through higher-order flow. The direct call form carries the
fact.

A public predicate exports its normalized formula and parameter types through the API index. The
body need not be exported. The encoded formula uses positional parameters, `Carrier(parameter)`,
`Length(parameter)`, literal constants, and literal-initialized public immutable scalar or `String`
values encoded by value; version 1 exports no member paths. A consumer can transfer the fact from the direct call
without reading the implementation. A package-local predicate is not exported; consumers see only an
ordinary Boolean function.

The exported formula is part of the public API. Changing the body or its normalized meaning changes
what callers may prove, so it is a behavioral library change under
[ZEP-0012](./ZEP-0012.md). A library that omits the formula degrades to an ordinary function on the
consumer side.

### Runtime lowering

A predicate lowers to an ordinary static function with a Boolean return. No descriptor, allocation,
or dispatch change is required. The compiler may inline a predicate whose body is cheap, but the
first version does not require it. Because the body is pure and total for its declared parameter
types, inlining cannot change evaluation order in an observable way.

### Diagnostics

- A body outside the fact language is an error at the predicate declaration, with a note that an
  ordinary function does not transfer facts.
- A body with an effect, allocation, or mutable read is rejected for the same reason.
- A non-Boolean body is a type error.
- A recursive predicate cycle is rejected.
- A predicate call with non-stable arguments is accepted and produces no fact; it is not an error.
- A direct call through a function value is accepted but produces no fact; tooling may note the lost
  refinement.

The final `ZR####` codes are assigned at implementation time from the resolution range.

## Compatibility and impact

The change is source-additive. `predicate` remains a soft keyword, so existing identifiers named
`predicate` continue to resolve. Only the `predicate fn` declaration position is new. Existing
Boolean functions keep their behavior and transfer no facts. No runtime representation or descriptor
changes.

The API index gains a predicate record for public predicates. The schema bump is shared with
[ZEP-0138](./ZEP-0138.md) and the other predicate-bearing proposals. The standard-library API version
changes only if the standard library publishes predicates.

The formatter, highlighter, completion, hover, and signature help need to recognize the declaration.
The guide should show a reusable bounds predicate and its use in a guard.

## Alternatives

- **Use a `param is Type` return annotation.** It is ambiguous with type tests, covers only type
  facts, and does not express relations among several parameters. Rejected.
- **Trust any Boolean function used in a condition.** A function could return `true` without
  enforcing the fact, making flow analysis unsound. Rejected.
- **Require an annotation or attribute on an ordinary function.** The compiler would still need to
  check the body or trust it; a distinct declaration is clearer and easier to serialize. Rejected.
- **Inline all predicates and never export formulas.** This would limit cross-library use and lose
  the declaration as a stable API element. Rejected.
- **Support effects and mutable reads in predicates.** That would require a purity model the
  language does not have and would make fact stability depend on call effects. Rejected for now.

## Implementation and validation

Likely stages:

1. Parse `predicate fn` declarations and resolve their parameters and body.
2. Lower the body to the fact IR and check the subset.
3. Add direct-call fact transfer to condition resolution.
4. Add negation transfer for the false path.
5. Export public predicate formulas and load them from compiled libraries.
6. Add hover, completion, and declaration documentation.

Validation should cover:

- single-parameter and multi-parameter predicates;
- true and false transfer, including compound formulas;
- non-stable arguments producing no fact;
- assignment and call invalidation after a predicate fact;
- predicate calls in `and`, `or`, `not`, `else if`, `while`, and value-producing `if`;
- rejection of calls, effects, allocations, mutable reads, and recursion in a body;
- function-value calls producing no fact;
- exported and package-local predicates across separate compilation; and
- unchanged runtime behavior for ordinary Boolean functions.

## Open questions

- Is `predicate fn` the right modifier spelling, or should the declaration reuse a clause on the
  ordinary return type?
- Should the first version allow calls to other predicates, and if so, how are cycles detected?
- Should an explicitly trusted, opaque predicate be allowed for FFI or performance-critical checks?
- Should generic predicates be supported, and how would their formulas be serialized?
- Should block bodies with a single final expression be allowed, or only expression bodies?
- Should the standard library publish common predicates such as bounds and range checks?
