## Abstract

Add an integer abstract domain to the fact solver. The domain combines intervals with
difference-bound constraints of the form `x - y <= c`, so the compiler can combine facts such as
`0 <= index` and `index < length`, answer whether a refined predicate is implied, and detect
contradictory combinations. It supports observable stable terms such as `values.length` and safe
arithmetic such as `values.length - 1`, but not arbitrary calls, mutable reads, or array elements.

The domain is an internal analysis backend. It does not change the runtime and does not promise
bounds-check elimination. Its first obligation is soundness: a `TRUE` answer must hold for every
concrete execution consistent with the modeled facts.

## Motivation

[ZEP-0140](./ZEP-0140.md) gives the compiler individual comparison facts, but an individual fact set
cannot answer the questions that matter:

```zeron
if (index >= 0 and index < values.length) {
    // Is 0 <= index < values.length still known?
    // Does index satisfy a Positive precondition?
}
```

Intervals answer one-variable range questions. Difference bounds answer relations between two
stable terms, including `index < values.length` and `index <= values.length - 1`. Together they cover
the index and bounds patterns that motivate the static-verification roadmap.

The domain also gives range loops and parameter refinements a common query backend, so each feature
does not need its own arithmetic reasoning.

## Goals

- Provide a sound interval domain for `Int` and, if enabled, `Long` terms.
- Provide difference-bound relations between stable terms.
- Support stable symbolic terms such as array and string length.
- Support safe arithmetic terms when overflow is excluded.
- Combine facts across `and`, `or`, `not`, branches, and loops.
- Detect contradictory fact sets and unreachable paths.
- Answer `check` and `entails` queries for the fact IR.
- Use widening so loop analysis terminates.
- Keep the domain deterministic and bounded in cost.

## Non-goals

- `Float` intervals, NaN reasoning, or signed-zero arithmetic.
- String ordering, string length arithmetic beyond simple integer terms, or Unicode reasoning.
- Multiplication, division, modulo, or non-linear relations.
- Alias analysis, ownership analysis, or mutation tracking beyond stable paths.
- Bounds-check elimination or any optimization guarantee.
- A general SMT or linear-programming solver.
- Arbitrary function calls, constructors, array element reads, or mutable field reads.
- Proving properties of values that are not representable by stable terms.

## Proposal

### Terms

The domain accepts the term forms from [ZEP-0138](./ZEP-0138.md):

```text
Const(c)
Path(stablePath)          // Int or Long scalar
Length(path)              // Int; array or string length
Add(a, b)
Sub(a, b)
Neg(a)
```

`Path` follows the stable-path rules in [ZEP-0131](./ZEP-0131.md). `Length` is an immutable structural
observation:

- arrays are fixed-length, and `append` returns a new array;
- strings are immutable; and
- reassigning the root binding kills facts that mention `Length(root)`.

Array element reads, mutable field reads, call results, and custom getters are not terms. They
produce no interval or relational fact.

Arithmetic terms are admitted only when overflow is excluded. `Length(path) - 1` is safe because a
length is non-negative. `x + 1` is not safe for an arbitrary `Int` and is not formed. A term that
cannot be formed yields `UNKNOWN`, not an unsound approximation.

### Domain

The domain has two components:

1. **Intervals** for each tracked term: a lower and upper bound, either a constant or unbounded.
2. **Difference bounds** for pairs of tracked terms: a constraint `a - b <= c` with an integer
   constant `c`.

The difference-bound component encodes:

```text
a < b       as  a - b <= -1
a <= b      as  a - b <= 0
a == b      as  a - b <= 0 and b - a <= 0
a > b       as  b - a <= -1
a >= b      as  b - a <= 0
```

A special zero term represents constants, so `a <= 5` is `a - zero <= 5`. The domain computes the
transitive closure of the difference constraints and uses it to answer queries. A negative cycle
means the constraints are contradictory.

Disequality `a != b` is not representable as a convex difference-bound system. The solver keeps the
negative atom from [ZEP-0140](./ZEP-0140.md) and does not pretend it is a range. It may still use the
atom in structural contradiction checks.

The domain is bounded:

- cap the number of tracked terms per program point;
- drop the least useful terms when the cap is reached; and
- widen loop-header bounds after a fixed number of iterations.

The cap and widening policy are implementation details, but they must be deterministic and
documented.

### Transfer

Condition transfer uses the existing short-circuit rules:

- a true comparison adds its constraint;
- the false outcome adds the negation when it is representable;
- `and` intersects the true facts;
- `or` joins the successful alternatives; and
- `not` swaps the outcomes.

Branch joins use the interval hull and the difference-bound join. A conservative implementation
keeps only bounds and relations valid on both paths:

```text
join([0, 10], [5, 20]) = [0, 20]
join(x <= y, true)     = true
```

The join is intentionally weaker than the union. Losing precision is acceptable; claiming a relation
that holds on only one path is not.

Loops use the existing flow fixed point. The loop header joins the preheader and reachable backedges.
After a bounded number of iterations, unstable bounds widen to unbounded. `break` exits join with the
normal exit; `continue` is a backedge. Condition facts hold in the loop body.

A contradictory constraint system, detected as a negative cycle in the difference-bound closure, means
the current path is unreachable. Because the domain only records constraints that are actually true
on the path, a negative cycle is a sound impossibility result. The compiler may omit unreachable code
or report a diagnostic; it must not report a reachable path as unreachable.

### Overflow

The soundness rules are:

- A comparison between runtime `Int` or `Long` values is a fact about those values. Transitive
  closure over comparison constraints is sound and does not depend on arithmetic assumptions.
- An arithmetic term is formed only when the compiler can show that its evaluation cannot overflow
  for every value admitted by the current bounds.
- If overflow is possible, the term is not formed and any fact that depends on it becomes
  `UNKNOWN`.
- `Int.MIN_VALUE - 1` and `Int.MAX_VALUE + 1` are not silently treated as mathematical integers.
- Division and remainder are not modeled; a fact that would require them is `UNKNOWN`.

For example, with `0 <= length`, `length - 1` is safe. With an arbitrary `x`, `x + 1 > x` is not
assumed, because `x + 1` can wrap. A program that needs that fact must guard the range first.

### Queries

`check(context, formula)` and `entails(context, premise, conclusion)` use the domain as one backend
in the [ZEP-0138](./ZEP-0138.md) solver chain. The domain answers:

- whether a comparison is implied by the current bounds;
- whether a conjunction of comparisons is contradictory;
- whether a term is within a constant interval; and
- whether one interval is contained in another.

It does not answer arbitrary formulas. A query outside the domain returns `UNKNOWN`.

Refined predicates use the same query. For example, if `Positive` requires `value > 0`,
`Positive.new(index)` is accepted when the domain proves `0 < index`. The consuming proposals decide
whether `FALSE` or `UNKNOWN` is an error.

### Interaction with array lengths

`values.length` is stable for a stable array reference. Another alias may mutate the array's
elements, but not its length; arrays are fixed-length and `append` returns a new array. Therefore a
fact such as `index < values.length` remains valid after a call that mutates elements.

`values[index]` is not stable. A read of an element is a value, not a term. A fact about an element
does not survive a call or another alias's write, and the domain does not track it.

This distinction is what allows read-only array parameters to carry useful length bounds without
claiming that the array contents are frozen.

### Performance and determinism

The analysis must be bounded and must not make compilation unpredictable:

- use a deterministic term order;
- cap tracked terms and constraints;
- use a fixed widening threshold;
- cache normalized formulas and query results per program point; and
- avoid invoking the domain for formulas that structural or constant evaluation already decides.

The domain is an internal analysis. Its cost must not grow with program-wide alias complexity; only
the facts in the current flow context are considered.

## Compatibility and impact

The change is resolver-internal. It adds no runtime representation, descriptor, or generated-code
change. It does not change the meaning of existing programs. Some programs that previously failed a
refinement check may now pass because the compiler proves more.

The analysis affects compilation time and memory. The caps and widening policy should be tuned with
representative programs before release. Diagnostics must not depend on incidental precision: a
message should say the fact is not proven, not that it is false, unless the domain actually proves
the negation.

No API-index change is required by this proposal. Predicate export belongs to
[ZEP-0138](./ZEP-0138.md) and [ZEP-0141](./ZEP-0141.md).

## Alternatives

- **Constant intervals only.** This is a useful first stage but cannot express `index < length` or
  other relations. Rejected as the endpoint.
- **Full polyhedral analysis or linear programming.** It is more precise than needed and adds a large
  solver dependency. Rejected for now.
- **Symbolic execution with an external SMT solver.** It is harder to make deterministic, harder to
  ship, and unnecessary for the initial fact vocabulary. Rejected.
- **Only relational facts without intervals.** This covers comparisons but makes constant bounds and
  range questions awkward. The two components are complementary.
- **Use the array's length as a path fact rather than a term.** This loses the ability to express
  `index < values.length - 1` as a relation. Length as a term is more useful.

## Implementation and validation

Likely stages:

1. Add constant intervals for `Int` terms.
2. Add difference-bound constraints and closure.
3. Add stable `Length` terms and safe arithmetic.
4. Add branch joins, loop fixed points, and widening.
5. Integrate with the fact solver and refined-predicate queries.
6. Add overflow-safety tests and performance limits.

Validation should include:

- property tests that a `TRUE` query holds for random concrete assignments consistent with the
  context;
- contradiction and unreachable-path cases;
- bounds at `Int.MIN_VALUE` and `Int.MAX_VALUE`;
- arithmetic terms that may and may not overflow;
- ascending and descending loop bounds with widening;
- joins that lose precision without claiming false facts;
- array length stability across element mutation and calls;
- element reads producing no fact;
- cross-module range loops from [ZEP-0143](./ZEP-0143.md); and
- full-suite resolution and flow tests.

## Open questions

- Should `Long` be enabled in the first release, or should the domain start with `Int` only?
- Should disequality be represented by a finite set of intervals, or remain an opaque negative atom?
- Should a contradictory constraint set produce an unreachable-code diagnostic, or only suppress later
  analysis?
- What term cap and widening threshold keep compilation predictable on large functions?
- Is a difference-bound matrix the best implementation, or would a simpler interval-plus-relation set
  suffice for the first version?
- Should `Length` be modeled as a term or as a distinguished path fact with special rules?
- How should step sizes greater than one in ranges interact with the interval bounds? (The
  congruence part is deferred to [ZEP-0143](./ZEP-0143.md).)
