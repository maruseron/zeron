## Abstract

Make integer ranges verifiable. The proposal:

- preserves the current inclusive `..` behavior for compatibility;
- adds a half-open range form for safe index loops;
- exposes read-only `start`, `end`, `step`, and `exclusive` metadata on `IntRange`;
- recognizes `IntRange` values in `for..in` and introduces per-iteration bounds facts for the loop
  variable; and
- defines exit and mutation behavior for those facts.

The result is that a loop written as `for (let i in 0..<values.length)` carries
`0 <= i and i < values.length` into its body, where the interval backend from
[ZEP-0142](./ZEP-0142.md) can use it.

## Motivation

The common index loop is:

```zeron
for (let i in 0..values.length - 1) {
    use(values[i]);
}
```

The compiler currently knows only that `i` is an `Int`. It does not know the bounds, so it cannot
prove an index precondition or use the loop to establish later facts.

There is also a semantic footgun in the current inclusive constructor. `IntRange.closed(start, end)`
chooses its direction from `start <= end`, so `0..-1` is a two-element descending range that yields
`0` and `-1`. For an empty array, `0..values.length - 1` therefore iterates instead of doing
nothing. A half-open range has a natural empty case and is the better spelling for index loops.

The range object itself already knows its bounds internally, but the fields are not public. Exposing
them as read-only properties makes the bounds observable to users and to the compiler without
changing iteration behavior.

## Goals

- Preserve the meaning of existing inclusive ranges.
- Add a half-open range syntax and constructor with natural empty behavior.
- Expose `start`, `end`, `step`, and `exclusive` as read-only properties.
- Recognize `IntRange` in `for..in` and establish bounds facts for the loop variable.
- Handle ascending, descending, and half-open ranges.
- Invalidate facts when the loop variable is written.
- Define exit facts and `break`/`continue` joins.
- Reuse the interval and difference-bound backend rather than creating a second range analysis.
- Keep facts local to `IntRange`; do not claim facts for arbitrary `Iterable` implementations.

## Non-goals

- Changing the existing `..` inversion behavior.
- Inferring facts for arbitrary user-defined iterables or transformed ranges.
- Step-congruence facts for step sizes beyond the initial supported cases.
- `Long` ranges.
- Bounds-check elimination as a required optimization.
- Changing iterator allocation, laziness, or evaluation order.
- Making `IntRange` a special runtime representation.

## Proposal

### Range semantics

Existing behavior is retained:

```zeron
for (let i in 1..5) { ... }   // 1, 2, 3, 4, 5
for (let i in 5..1) { ... }   // 5, 4, 3, 2, 1
```

The inclusive form chooses its direction from `start <= end` and is not changed by this proposal.

Add a half-open form:

```zeron
for (let i in 0..<values.length) { ... }   // 0 <= i < values.length
```

`a..<b` is ascending and yields `a` through `b - 1` inclusive. It is empty when `a >= b`. It lowers
to a new `IntRange.halfOpen(start, end)` constructor, or to `until(start, end)` if that spelling is
preferred. A descending half-open form is not added; use `descending` when an explicit descending
range is needed.

`..<` is scanned as a single token, preferred over `..` by the longest-match rule, so `0..<n` does
not parse as `0 .. (<n)`. It keeps the same lowest precedence and right-associativity as `..`, so
`0..<n - 1` groups as `0..<(n - 1)`. The grammar production is extended with the alternative
spelling rather than a second expression level.

The standard library additions are:

```zeron
public constructor halfOpen(start: Int, end: Int) =
    IntRange.new(start, end, 1, true);

public constructor halfOpenDescending(start: Int, end: Int) =
    IntRange.new(start, end, -1, true);
```

`halfOpen` iterates only while `current < end`. `halfOpenDescending` iterates only while
`current > end`. The existing `ascending`, `descending`, and `closed` constructors keep their
current behavior and pass `false` for `exclusive`.

`IntIterator` currently stops inclusively at `end`, so it needs the matching distinction. It gains
the same `exclusive` flag, forwarded by `IntRange.iterator()`. `next()` stops when
`exclusive and current >= end` for an ascending iterator and when
`exclusive and current <= end` for a descending iterator. The public iterator constructors keep
their inclusive meaning.

Documentation should recommend `..<` for index loops and explain the difference from `..`. The
existing `0..length - 1` spelling remains valid and receives the same bounds facts, but it retains
the empty-array footgun; the half-open form avoids it.

### Exposed bounds

`IntRange` currently stores `start`, `end`, and `step` as package-private fields. Replace them with
public automatic properties of the same names:

```zeron
public property start: Int;
public property end: Int;
public property step: Int;
public property exclusive: Boolean;
```

An automatic property without `mut` acquires only a getter, so callers can read the metadata but
cannot assign it. The canonical constructor supplies `start`, `end`, `step`, and `exclusive` in
declaration order, and no custom accessor or extra storage is needed. `step` is `1` for ascending
ranges and `-1` for descending ranges. `exclusive` is `false` for `ascending`, `descending`, and
`closed`, and `true` for the two half-open constructors. Keeping exclusivity in its own value rather
than inferring it from `step` preserves the existing inclusive meaning of the public constructors.

Exposing the range metadata and constructors is a public standard-library API addition. It does not
change the iterator behavior. Whichever release cycle adopts the change must bump
`STANDARD_LIBRARY_API_VERSION` once under the consolidation rule in [ZEP-0012](./ZEP-0012.md).

### Recognition in `for..in`

The compiler recognizes a loop source whose resolved type is exactly `zeron.ranges.IntRange`:

```zeron
for (let i in 0..<values.length) { ... }
for (let i in range) { ... }          // range: IntRange
```

The range value is evaluated once, as it is today. Its `start`, `end`, `step`, and `exclusive`
observations are immutable, so they remain stable for the duration of the loop. A reassignment of a
local holding the range does not affect the already-evaluated loop source.

Recognition is by resolved nominal type, not by source spelling. A user-defined type with the same
members is not recognized. `IntRange` is a compiler-known standard-library type for this purpose,
like the existing intrinsic array and `Option` shapes. The guide should document that status.

The first version recognizes the concrete type only. A general `Bounded` contract or an intrinsic
range interface is a possible future extension.

### Loop facts

For a recognized ascending inclusive range `a..b`:

```text
a <= i <= b
```

For a recognized descending inclusive range `a..b` where `a > b`:

```text
b <= i <= a
```

For a half-open ascending range `a..<b`:

```text
a <= i < b
```

For a half-open descending range:

```text
b < i <= a
```

Constants and stable terms are substituted directly. With `values.length` as `b`, the interval
backend can use `Length(values)` as a term and prove index bounds.

The loop variable is a fresh binding for each iteration. The fact is established at the start of the
body and applies to that iteration's binding. If the loop variable is declared `let mut` and the body
assigns it, the assignment kills the fact for the remainder of that iteration; the next iteration
starts with the range fact again.

The body may use `break` and `continue`. `continue` is a backedge and does not change the range
fact for the next iteration. `break` exits the loop; the exit state joins the normal completion state
and the break states, so a fact that holds only on normal completion does not survive a join with a
break.

Normal completion of an ascending inclusive range implies `i > b`; a half-open range implies
`i >= b`. A descending range implies the symmetric lower bound. These exit facts are optional; the
first version may conservatively retain only facts valid on every exit.

### Step sizes

The standard constructors use `step` values of `1` or `-1`. The first version establishes only the
interval bounds. It does not establish congruence facts such as `i == start (mod step)`.

A future extension can add congruence reasoning for constant steps. A hypothetical stepped
constructor would carry the residue:

```text
for (let i in IntRange.stepped(0, 10, 2))   // i is even, 0 <= i <= 10
```

That requires a domain that tracks residues, which [ZEP-0142](./ZEP-0142.md) does not provide. The
proposal records the extension and leaves it out of the first release.

### Index bounds and downstream use

The primary use is to prove an index is in bounds:

```zeron
for (let i in 0..<values.length) {
    use(values[i]);                     // 0 <= i < values.length
    let p = Positive.new(i + 1);        // only when i + 1 is proven positive
}
```

The compiler is not required to eliminate a runtime bounds check. The fact is available to the
analysis and to refined predicates; any optimization is a separate decision.

The loop fact also supplies the length relation that [ZEP-0142](./ZEP-0142.md) needs for
`values.length - 1` terms. Because array length is fixed, the fact remains valid after a call that
mutates elements.

### Diagnostics and tooling

No new error is required for an unrecognized loop source. The compiler simply establishes no fact.
A note may explain why a loop did not produce bounds when the source looks range-like but resolves to
another type.

The parser, formatter, and highlighter need to recognize `..<`. The language server should show the
range fact on hover over the loop variable and complete the new constructors and properties.

## Compatibility and impact

The inclusive `..` behavior is unchanged. The half-open syntax and constructors are source-additive.
The public properties are API-additive. Existing loops keep their current generated code; loops that
become analyzable gain facts but do not change runtime behavior.

A program that relied on `0..-1` iterating descending continues to do so. The proposal documents the
footgun and offers `..<` rather than silently changing the meaning of an existing range.

## Alternatives

- **Change `..` to ascending-only with an empty result when `start > end`.** This removes the
  footgun but changes existing descending-range programs. Rejected unless a separate compatibility
  decision accepts the break.
- **Make `IntRange` an intrinsic type rather than a standard-library class.** This would make
  recognition and representation easier but would remove the ordinary class surface and library
  ownership. Rejected for now; compiler-known recognition is sufficient.
- **Use a `Bounded` or `Range` contract instead of recognizing `IntRange`.** A contract would allow
  user-defined ranges, but facts would depend on arbitrary getter implementations and would need a
  stability model. Deferred.
- **Add an `indices(length)` helper and infer facts only from it.** This is a useful convenience but
  does not cover direct ranges. It can be added later.
- **Establish facts only for literal range constructors.** This would miss a range stored in a local.
  Recognition by resolved type is more useful and still safe because the bounds are immutable.
- **Add congruence facts for arbitrary steps immediately.** This requires a richer domain and is
  outside the first release.

## Implementation and validation

Likely stages:

1. Add `..<` parsing and lowering, plus the half-open constructors.
2. Expose the read-only metadata properties and the `exclusive` flag.
3. Recognize `IntRange` loop sources in flow analysis.
4. Add per-iteration bounds facts and assignment invalidation.
5. Add exit and `break`/`continue` handling.
6. Integrate with the interval backend and add tooling.

Validation should cover:

- ascending, descending, and half-open ranges;
- empty half-open ranges;
- the existing `0..-1` behavior, documented rather than changed;
- ranges stored in locals and passed to the loop;
- stable and non-stable bounds, including `values.length`;
- loop-variable writes in `let mut` loops;
- `break`, `continue`, nested loops, and exit joins;
- index bounds proofs and refined-predicate calls in the body;
- user-defined types that look like ranges but are not recognized; and
- unchanged iteration order and generated code for existing loops.

## Open questions

- Should `..` eventually become ascending-only, or is the current inversion behavior permanent?
- Is `..<` the preferred spelling, or should the language use `until` as the only half-open form?
- Should `IntRange` be a compiler-known class, an intrinsic, or an implementation of a general
  bounded-range contract?
- Should the standard library add an `indices(length)` helper?
- Should congruence facts for constant steps be part of the next iteration of the interval domain?
- Should a descending half-open form exist, or is `descending` sufficient?
- Does exposing the metadata as automatic properties change generated field visibility or member
  descriptors, and should internal code keep reading the backing storage directly?
