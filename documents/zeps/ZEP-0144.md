## Abstract

Allow a parameter type to carry a `where` refinement:

```zeron
fn at(length: Int, index: Int where index < length): ...
```

The refinement is a **precondition**. A call site must establish the substituted predicate with
constant evaluation, flow facts, or interval facts. A provably false
predicate is an error; an unprovable predicate is an error unless the call is guarded by a check or
the function provides a runtime-checked entry. Inside the callee, the predicate is an entry fact for
the duration of the call.

Predicates may mention only observations that cannot change during the call: immutable scalar
parameters and fixed structural properties such as array and string length. A read-only view of a
mutable reference is not a snapshot, so it cannot justify a predicate over mutable contents.

## Motivation

Guarded newtypes give a reusable name to an invariant, but a function that needs a local relation
often does not want to declare a type:

```zeron
fn slice(values: Array<Int>, start: Int, end: Int): Array<Int> {
    // start <= end and end <= values.length are required
}
```

Today the function must either document the precondition and check it at runtime, or introduce a
wrapper newtype for every relation. A parameter refinement states the condition directly, lets
callers use the facts they already have, and lets the callee rely on the condition without a manual
guard:

```zeron
fn slice(
    values: Array<Int>,
    start: Int where 0 <= start,
    end: Int where start <= end and end <= values.length
): Array<Int> { ... }
```

The feature is the capstone of the static-verification roadmap because it consumes every other
piece: normalized facts, newtype invariants, intervals, and range bounds.

## Goals

- Add `name: Type where predicate` to function, method, and static-function parameters.
- Treat the predicate as a call-site obligation and a callee entry fact.
- Prove obligations from constants, comparison facts, and intervals.
- Reject provably false calls and report unprovable calls with actionable facts.
- Support predicates over earlier parameters and immutable structural observations.
- Keep the entry fact stable for the whole call by restricting what predicates may observe.
- Define the read-only-view coherence rule explicitly.
- Export predicates for separate compilation.
- Provide a runtime backstop for public and first-class functions.
- Keep JVM descriptors and runtime representations unchanged.

## Non-goals

- Return-type refinements or general postconditions.
- Full dependent types or predicates over arbitrary expressions.
- Refinements over mutable fields, array elements, call results, or custom getters.
- `this`-based parameter predicates.
- Function-type refinements, refined function values, or higher-order contract subtyping.
- Automatic runtime wrappers for every call site.
- Changes to `raise`, `handle`, or the effect system.
- Proving predicates by executing arbitrary user code at compile time.

## Proposal

### Surface

A parameter refinement is written after the type:

```zeron
fn at(values: Array<Int>,
      index: Int where 0 <= index and index < values.length): Int {
    return values[index];
}
```

The predicate uses the parameter name, not `this`. `this` is rejected in a parameter predicate:
it is the receiver, it is absent in top-level functions, and it would reintroduce the aliasing
problem this proposal is designed to avoid. A method that needs a receiver-derived bound takes it as
an explicit parameter or uses a newtype.

A predicate may reference:

- the parameter it refines;
- earlier parameters of the same declaration;
- compile-time constants and literal-initialized public immutable scalar or `String` values; and
- read-only structural observations of those parameters, such as `values.length`.

It may not reference later parameters, `this`, mutable locals, mutable fields, array elements, call
results, or custom getters. Type and null tests are not part of a parameter predicate in version 1,
and `Float` terms wait for the documented NaN and signed-zero flow model. The earlier-parameter rule
keeps the obligation acyclic and lets the caller check predicates in declaration order.

### Semantics

The predicate is a precondition:

- **Caller obligation**: the call is valid only when the substituted predicate is proven, or when
  the caller explicitly checks it. A provably false predicate is an error. An unprovable predicate
  is an error by default.
- **Callee assumption**: on entry, the predicate holds for the parameter binding. It remains valid
  for the duration of the call because the allowed observations cannot change.
- **Runtime backstop**: a public or first-class function emits an entry check. The check is elided
  only when the compiler can prove every call site and the function is not exported or used as a
  value. A failed entry check raises `zeron.runtime.ValidationException`, the same host-visible type
  as a failed checked `new` ([ZEP-0139](./ZEP-0139.md)); it names the function and parameter but does
  not include the argument value.

The runtime backstop is important for separate compilation and library upgrades. A caller compiled
against an older library version may not know about a newly added predicate. The entry check keeps
the callee's assumption true even for that caller. It also protects against compiler analysis bugs
and against a predicate that is not exported.

For a private function whose calls are all in the same compilation unit and all statically proven,
the compiler may omit the check. This is an optimization, not a semantic difference.

### Coherence and read-only views

A read-only view prevents mutation through that particular binding. It does not prevent mutation
through another alias. Zeron explicitly does not promise uniqueness or borrow checking, so a
read-only view of a mutable reference is **not** a snapshot.

Therefore, a parameter predicate may mention only observations that cannot change during the call:

| Observation | Allowed | Reason |
| --- | --- | --- |
| Immutable scalar parameter | Yes | The binding cannot be reassigned |
| Earlier immutable scalar parameter | Yes | The binding cannot be reassigned |
| Array or string length | Yes | Arrays are fixed-length; strings are immutable |
| Array element | No | Another alias may mutate it |
| Mutable field | No | Another alias may mutate it |
| Read-only field of a reference value | No | Another alias may mutate it, and there is no deep freeze |
| Custom property getter | No | It may return a different value on each call |
| Call result | No | It is not a stable observation |
| `this` or a receiver field | No | Receiver aliasing is not tracked |

A read-only view is still required for a reference-typed parameter named in a predicate, so the
callee cannot mutate it through that binding. It is a necessary hygiene rule, not a sufficiency
proof. The sufficiency comes from the observation table.

If a function needs a predicate over mutable contents, it should snapshot the value into an
immutable local at entry and refine the local:

```zeron
fn useFirst(values: Array<Int>) {
    if (values.length == 0) return;
    let first = values[0];       // snapshot
    if (first > 0) {
        consumePositive(first);
    }
}
```

The snapshot is a value, not a view. A later mutation of `values` does not change `first`.

A future deep `frozen` or `immutable` capability could allow predicates over the contents of
values that are guaranteed never to change. That requires a capability beyond the current
read-only view and is outside this proposal.

### Call-site checking

The compiler substitutes each argument term for its parameter in the predicate and asks the fact
solver to prove the result:

```zeron
fn use(index: Int where 0 <= index, values: Array<Int>) { ... }

fn caller(values: Array<Int>, i: Int) {
    if (0 <= i) {
        use(i, values);          // proven by the guard
    }

    use(5, values);              // proven by constant evaluation

    for (let j in 0..<values.length) {
        use(j, values);          // proven by the range fact
    }

    use(i, values);              // error: not provable
}
```

The three query outcomes have distinct behavior:

- `TRUE`: the call is accepted. The runtime entry check may be elided for an internal function.
- `FALSE`: the call is rejected. The diagnostic says the predicate is false for these arguments.
- `UNKNOWN`: the call is rejected by default. The diagnostic lists the facts that were available
  and suggests a guard, a stable local, or a checked entry point.

A guard is the normal escape hatch:

```zeron
if (0 <= i) {
    use(i, values);
}
```

The caller may also use a fallible or checked API. This proposal does not synthesize a wrapper
automatically; the function author can write one with an `Option` or `Result` result and a `tryNew`-
style check.

### Entry fact and invalidation

Inside the callee, the predicate is an entry fact. The allowed observations cannot change, so the
fact remains valid throughout the body:

- an immutable scalar parameter cannot be reassigned;
- array and string length cannot change for the passed reference; and
- no allowed observation is an array element, mutable field, read-only reference field, custom
  getter, or call result.

If a parameter binding is reassignable in a future language extension, assignment kills the fact.
The current proposal assumes parameters are immutable bindings. A call inside the body cannot
invalidate the fact because the underlying observations are immutable.

### Dependent ordering

A predicate may reference an earlier parameter:

```zeron
fn range(
    low: Int,
    high: Int where low <= high
): Int { ... }
```

A forward reference is rejected. This keeps the predicate acyclic and makes call-site substitution
straightforward. To express a condition where the bound comes first, reorder the parameters:

```zeron
fn range(
    high: Int,
    low: Int where low <= high
): Int { ... }
```

### Newtype interop

Newtypes are nominal: a `Positive` is not implicitly assignable to `Int`, so a refinement over `Int`
cannot accept a `Positive` argument directly. The supported direction is construction, where a
parameter fact discharges the validator:

```zeron
fn caller(index: Int where 0 < index) {
    let p = Positive.new(index); // proven by the parameter fact
}
```

[ZEP-0140](./ZEP-0140.md) still exposes the invariant internally as a `Carrier(p)` fact, and checked
construction and carrier-typed expressions use it. Crossing the nominal boundary in an ordinary call
requires an explicit representation accessor such as a `toInt()` extension. The first version does
not assume that an arbitrary accessor returns the carrier, so `p.toInt()` establishes no fact.
Recognizing an identity representation accessor, or allowing a refinement on a newtype-typed
parameter whose predicate is stated in the carrier, is a future extension.

When to use which:

- A newtype names a reusable invariant and creates a distinct nominal type.
- A parameter refinement states a local relation without introducing a type.
- A relation that crosses several parameters, such as `low <= high`, belongs in a parameter
  refinement, not in a newtype.

### Function values

In the first version, a refined function cannot be used as a first-class function value. Doing so
would either drop the precondition, allowing an unchecked call, or require refined function types
and contravariant contract subtyping. Both are larger features.

A direct call is supported. A function reference, method reference, or lambda that would call the
refined function should be rejected with a diagnostic that suggests an ordinary wrapper with an
explicit runtime check. A future proposal can add refined function types.

### Separate compilation and versioning

A public function exports its parameter predicates through the API index, using the encoding from
[ZEP-0138](./ZEP-0138.md). The encoding uses positional parameters, literal constants,
`Length(parameter)`, and literal-initialized public immutable scalar or `String` values; version 1
exports no member paths. A consumer uses the predicate to check calls and to prove obligations.
The predicate is part of the public API; changing it changes which calls are valid and is a
behavioral library change under [ZEP-0012](./ZEP-0012.md).

If a compiled library omits a predicate, or a consumer reads an older index, the consumer treats
the predicate as `UNKNOWN`. The public callee entry check still enforces it at runtime. The compiler
should report the lost static precision clearly rather than silently accepting the call.

The JVM descriptor does not change. The runtime entry check is emitted in the callee body, so stale
callers that satisfy the descriptor remain safe.

### Diagnostics

Candidate diagnostics, with final `ZR####` numbers assigned at implementation time:

- **Refinement not provable**: the call may violate the predicate, but the compiler cannot prove
  it. Show the required predicate, the substituted arguments, and the available facts.
- **Refinement is false**: the arguments provably violate the predicate. Show the failing
  comparison.
- **Missing exported refinement**: the library predicate is unavailable. Explain that the call will
  be checked at runtime but cannot be verified statically.
- **Refinement on a mutable observation**: the predicate mentions an array element, mutable field,
  custom getter, or call result. Explain the allowed observation categories and suggest a snapshot.
- **Refinement on `this`**: explain that receiver-derived bounds must be explicit parameters.
- **Refined function used as a value**: explain that refined function types are not supported.

The guide should show the guard, snapshot, `tryNew`, and range-loop patterns.

### Tooling

Signature help and hover should display parameter predicates. Completion should show which
parameters carry refinements. The language server should offer a quick fix that inserts a guard when
the missing fact is a direct comparison. Inlay hints for the callee entry facts are optional.

## Compatibility and impact

The syntax is source-additive. `where` is already a soft keyword used by guarded newtypes, so an
existing parameter named `where` is unaffected. Existing functions keep their behavior and transfer
no preconditions.

The JVM descriptor and runtime representation do not change. Public functions gain an entry check
when they have refined parameters; this is a small runtime cost and a new failure path. Private
functions may elide it when every call is proven.

The API-index schema gains parameter predicate records. The schema bump is shared with the other
predicate-bearing proposals. The standard-library API version changes only if standard-library
functions adopt refinements.

Callers of a refined function must be compiled with the predicate metadata to receive static
checking. Older compiled callers remain runtime-safe because the callee checks its own entry.

## Alternatives

- **Use only newtypes.** This works for named invariants but is heavy for local relations and cannot
  express relations among several parameters. Rejected as the only mechanism.
- **Make parameter predicates runtime-only checks.** This is simpler but does not provide static
  verification or caller diagnostics. Rejected as the primary design; the runtime check is kept as a
  backstop.
- **Trust a comment or annotation without checking call sites.** This is unsound and does not
  prevent violations. Rejected.
- **Use `this` as the refined value binder.** This conflicts with the receiver, fails in top-level
  functions, and reintroduces aliasing. Rejected; use the parameter name.
- **Allow predicates over mutable contents through a read-only view.** A read-only view is not a
  snapshot and another alias can mutate the contents. Rejected.
- **Support refined function values immediately.** This needs refined function types and contract
  variance. Deferred.
- **Use full dependent types.** The feature only needs a small fact language over earlier
  parameters. Full dependent types are unnecessary and much larger.

## Implementation and validation

Likely stages:

1. Parse `where` on parameters and resolve the predicate scope.
2. Reject forbidden observations and forward references.
3. Substitute argument terms and query the fact solver at call sites.
4. Emit the runtime entry check for public and first-class functions.
5. Add the callee entry fact and its stability rules.
6. Export predicates and load them from compiled libraries.
7. Add diagnostics, quick fixes, signature help, and guide examples.

Validation should cover:

- constants, guards, and range facts discharging a predicate;
- parameter facts discharging checked construction;
- newtype values crossing the nominal boundary only through an explicit accessor, which currently
  establishes no fact;
- provably false, unprovable, and missing-metadata cases;
- multiple parameters, earlier-parameter references, and forward-reference rejection;
- array length predicates and element predicates (the latter rejected);
- mutable fields, custom getters, call results, and `this` (all rejected);
- snapshot patterns that turn a mutable observation into an immutable value;
- private-function elision and public-function runtime backstop;
- shared `ValidationException` identity, host catchability, and message without raw arguments;
- stale compiled callers and library predicate changes;
- refined functions used as values (rejected);
- nested calls and effectful function bodies;
- unchanged descriptors and runtime representation; and
- full-suite resolution, flow, emitter, and library-index tests.

## Open questions

- Should the runtime entry check be mandatory for all public refined functions, or should a library
  build mode be able to omit it?
- Should `where` allow a block predicate with several conjuncts, or only a single expression?
- Should a refined function be callable through a function value with an exact predicate match, or
  should the first version reject all function-value uses?
- Should the language eventually add a deep `frozen`/`immutable` capability for content predicates?
- How should default arguments, if added later, interact with predicates?
- Should an explicit checked-call form be added, or is `if` plus `tryNew` sufficient?
- Should an identity representation accessor be recognized so a newtype invariant can discharge a
  carrier-typed parameter refinement, and if so, how is that accessor declared?
- Should a refinement on a newtype-typed parameter be allowed when the predicate is stated in the
  carrier?
- Should return refinements be a separate ZEP?
