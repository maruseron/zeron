## Abstract

Make the namespace the single source container for functions, immutable values, extension functions,
and extension properties. An extension becomes a namespace member declared with an `extension`
modifier and an explicit first `this` parameter:
`extension fn firstOr<T>(this: List<T>, fallback: T): T`. The existing
`extension<T> List<T> { ... }` block remains as sugar for a receiver-named namespace, so existing
source, import paths, and JVM owners continue to work.

The change does not alter dispatch: extension members remain statically dispatched receiver-first
functions. It makes the source model match the compiler's existing lowering and removes the
artificial split between two constructs that already share a namespace, a JVM owner, and an import
path.

## Motivation

The compiler already treats an extension block as a namespace:

- `Parser.extensionDeclaration` returns a `Stmt.Namespace` named after the receiver's simple name.
- `NamespaceMembers.flatten` produces the same member shape for namespace blocks and extension
  blocks.
- `CompilationMetadata` gives both the owner `pkg.$zeron$Namespace$<Name>`.
- `DeclarationRegistry` already rejects a function and an extension that share a qualified name.
- Imports already address both as `pkg.Namespace.member`.

The source language nevertheless presents them as unrelated constructs. That split has concrete
costs:

- A `namespace List` and an `extension List` in the same package are the same qualified namespace,
  but they look unrelated and collide only when member names happen to match.
- An extension block cannot be nested in a namespace, so all extensions for a receiver in a package
  are forced into the receiver-named namespace.
- Extension members are receiver-dot only, while namespace functions are callable as
  `Namespace.f(...)`, even though both lower to the same static shape.
- The receiver type parameters live on the block, so a single method cannot be read independently of
  the block's parameter list.

[ZEP-0072](./ZEP-0072.md) already uses the same idea for class-scoped statics: a class-scoped static
function is source sugar for a companion namespace member. Extensions should follow that precedent.
[ZEP-0141](./ZEP-0141.md) adds `predicate fn`, making `modifier fn` a general declaration shape;
`extension fn` fits the same family.

This is a source-container change, not a move to witness dispatch. `extension fn` remains a
statically dispatched function; it does not create a witness, dictionary, or coherence requirement.
Contract receiver projection remains the compile-time rule already documented.

## Goals

- Make namespaces the single source container for ordinary functions, immutable values, extension
  functions, and extension properties.
- Add canonical `extension fn ... (this: T, ...)` and `extension property ... (this: T)` members.
- Preserve the existing `extension<T> T { ... }` block as sugar for a receiver-named namespace.
- Preserve existing import paths and JVM owners for unsugared code.
- Let extensions be grouped by any namespace, not only by the receiver's simple name.
- Let extension methods participate in qualified calls and function-value references when their
  namespace is visible.
- Define receiver mutability through the ordinary `&T` capability.
- Keep the existing erased-signature collision checks and receiver-dot precedence rules.

## Non-goals

- Merging extensions with witnesses, contract conformance, or dictionary-based typeclass dispatch.
- Changing instance-method or contract-default precedence at the receiver dot.
- Adding `public namespace`, nested namespaces, namespace sealing, or re-exports.
- Defining receiver predicates (`extension predicate fn`) or how receiver facts transfer.
- Unifying the library-index `ExtensionExport` and `FunctionExport` records.
- Removing the existing extension block in this proposal.

## Proposal

### Unified member model

A namespace member is one of:

- an ordinary function declaration;
- an immutable value declaration;
- an `extension fn` declaration; or
- an `extension property` declaration.

The first two are today's namespace members. The last two are the extension members. A namespace
may mix them freely. The namespace remains a compile-time bag, not a runtime value; the receiver
does not become a namespace parameter.

### Canonical extension members

```zeron
package collections;

namespace Ordering {
    public extension fn firstOr<T>(this: List<T>, fallback: T): T =
        if (this.isEmpty()) fallback else this[0];

    public extension fn append<T>(this: &List<T>, value: T): Unit =
        this.add(value);

    public extension property size<T>(this: List<T>): Int {
        get = this.length;
    }

    public fn empty<T>(): List<T> = ...;
    public let defaultCapacity: Int = 16;
}
```

Rules:

- `this` must be the first parameter of an extension function or the only parameter of an extension
  property. It is a normal parameter binding in the body.
- The receiver type is the base type of the `this` parameter. A read-only extension writes
  `this: T`; a mutating extension writes `this: &T`.
- `this` cannot be variadic and cannot have a default value.
- All type parameters are ordinary method type parameters. An extension that needs a generic
  receiver writes them on the method, not on a block.
- Default arguments and variadic parameters are allowed after the receiver, with the existing
  restrictions.
- The extension body sees only public receiver members, as today.
- `extension` is a declaration modifier, not a separate declaration keyword. The canonical modifier
  order is visibility, then `extension` or `predicate`, then `fn`.

### Block sugar

The existing block form remains valid:

```zeron
public extension<T> List<T> {
    public fn firstOr(fallback: T): T = ...;
    public mut fn append(value: T): Unit = ...;
    public property size: Int { get = ...; }
}
```

At top level, it contributes members to a namespace named after the receiver's simple name:

```zeron
namespace List {
    public extension fn firstOr<T>(this: List<T>, fallback: T): T = ...;
    public extension fn append<T>(this: &List<T>, value: T): Unit = ...;
    public extension property size<T>(this: List<T>): Int { get = ...; }
}
```

The mapping is:

- block receiver type parameters are copied to each member's type-parameter list, before the
  member's own type parameters;
- `mut fn` maps to a `this: &T` receiver;
- unmarked `fn` maps to a `this: T` receiver;
- `property` maps to `extension property` with the same getter-only rules;
- the block-level `public` combines with the member-level `public`; the desugared member is public
  only when both are public.

For a generic receiver, the synthesized namespace uses the outer base type's simple name. A block
`extension<T> List<List<T>> { fn flatten(): List<T> = ...; }` contributes to `namespace List`; the
desugared member is `extension fn flatten<T>(this: List<List<T>>): List<T>`. The nested `List<T>` is
a type argument, not a second receiver or a nested namespace. The namespace is a flat grouping name
and does not encode the receiver's type arguments, so blocks for `List<T>` and `List<List<T>>` both
contribute to `namespace List` unless the author writes an explicit namespace.

A top-level `extension fn` / `extension property` is the same sugar for a single member. It is
equivalent to placing the member in `namespace <ReceiverSimpleName>`.

The block form is allowed only at top level in this proposal. Inside a namespace, use the member
form. Allowing a block inside a namespace is an open question.

### Namespaces, visibility, and reopening

- A namespace still has no visibility modifier and no runtime identity.
- Namespace members keep their ordinary declaration visibility.
- Namespace blocks with the same name in the same package continue to merge; duplicate member names
  are diagnosed.
- A namespace and a type may still share a simple name. `List<T>` in a type context is a type;
  `List.sort(...)` is a qualified namespace call.
- An extension member is a namespace member for identity, imports, documentation, and JVM ownership.

### Imports and lookup

- Explicit imports select namespace members, including extension members:
  `import collections.Ordering.firstOr;`.
- A namespace wildcard imports the namespace's public members, including extension members:
  `import collections.Ordering.*;`.
- A package star import continues to enumerate public declarations in a package, including public
  extension members.
- Receiver-dot lookup keeps the existing tiers: instance or contract-default method, then local
  extension, then explicit and namespace-wildcard imports, then package-star imports. The declaration
  namespace is now the namespace written in source, not a name synthesized from the receiver type.
- An explicit import or alias changes the name used at the receiver dot, as today.
- Importing a receiver type does not activate an extension; importing the declaration or its
  namespace does.

### Call surfaces

An extension function is callable in two forms:

```zeron
list.firstOr(fallback);           // receiver form
Ordering.firstOr(list, fallback); // qualified form
```

The qualified form is the ordinary receiver-first static call. It is available whenever the
declaration or its namespace is visible. It provides an explicit way to select an extension when an
instance method shadows it, and it lets an extension be used as a function value:

```zeron
let pick = Ordering.firstOr;
let value = pick(list, fallback);
```

The unqualified form follows ordinary import resolution:

```zeron
import collections.Ordering.firstOr;
let value = firstOr(list, fallback);
```

Rules:

- The first positional argument corresponds to `this`.
- Receiver-dot and qualified calls select the same declaration and the same instantiated signature.
- An instance or contract-default method still wins at the receiver dot. The qualified form is the
  explicit escape hatch.
- A function and an extension cannot share a qualified name in the same namespace; the existing
  declaration-collision rule remains.
- Ambiguity between declarations from different namespaces follows the existing import ambiguity
  rules.
- Extension properties remain receiver-dot only in this proposal; qualified getter calls are an open
  question.

### Mutability

Mutation is expressed through the receiver parameter type, not a second `mut` flag:

```zeron
extension fn append<T>(this: &List<T>, value: T): Unit = ...;
```

A `this: &T` extension requires a mutable receiver view at the receiver dot and a mutable argument
in the qualified form. A `this: T` extension is read-only and accepts either view. The existing
`&T` rules from [design-document-04](../design_documents/design-document-04_mutability.md) apply.

The block form keeps `mut fn` as sugar for `this: &T`. The canonical member form does not accept
`mut`; the reference type is the single spelling.

### Properties

An extension property is a namespace member with one `this` parameter and a getter:

```zeron
extension property size<T>(this: List<T>): Int {
    get = this.length;
}
```

It keeps today's rules: explicit return type, getter only, no setter, no initializer, and no
mutation. It lowers to a zero-argument getter with the receiver as the first parameter.

### Metadata and ABI

- The JVM owner remains `pkg.$zeron$Namespace$<NamespaceName>`.
- For top-level and block sugar, the synthesized namespace is the receiver's simple name, so
  existing owners and import paths do not change.
- Moving an extension to a different explicit namespace changes its qualified name and JVM owner.
  That is a library API change under [ZEP-0012](./ZEP-0012.md), like any other rename.
- The library index already has the information this model needs. `ExtensionExport` carries
  `namespaceName`, `receiverType`, the receiver-first `signature`, `mutating`, `minimumArity`,
  `variadic`, and `property`. No new export record or schema bump is required.
- `Stmt.ExtensionMethod` already stores the receiver as the first parameter and validates that its
  base type matches `receiverType`. The canonical form leaves `receiverTypeParameters` empty; the
  block sugar populates it.
- The erased-JVM-signature collision check remains keyed by the qualified namespace name.
- Extension annotations are keyed by the receiver-qualified member name today. The block and
  top-level sugar should preserve that key, and the explicit-namespace key is an open question.

### Runtime lowering

Each extension member continues to lower to a receiver-first static method in the namespace owner.
No descriptor, allocation, or dispatch change is required. The qualified call is the same
`invokestatic`; the receiver-dot call binds the receiver to the first argument.

### Diagnostics

- A missing `this` parameter in a canonical `extension fn` or `extension property` is an error.
- `this` outside the first position is an error.
- A variadic or defaulted `this` parameter is an error.
- `this: &T` on an extension property is an error.
- A `mut` modifier on a canonical `extension fn` is an error; use `this: &T`.
- A function and an extension with the same qualified name remain a duplicate declaration.
- Two extensions with the same receiver and name remain a duplicate declaration.
- Two extensions whose erased JVM signatures collide in the same namespace remain an error.
- A top-level extension whose synthesized namespace collides with an explicit namespace member name
  is diagnosed by the ordinary duplicate-member rule.

## Compatibility and impact

The syntax is source-additive. Existing `extension<T> T { ... }` blocks and top-level extensions
continue to parse as sugar, keep their import paths, and keep their JVM owners. Existing extension
annotations keep the receiver-qualified key used for the sugar.

The canonical form is new source. Moving an extension into an explicit namespace is optional and is
a normal library API change. The formatter should gain a rewrite from block to member form, but no
mass migration is required.

An explicit or wildcard import of an extension member now also makes the receiver-first unqualified
form available. Existing code that imports an extension and separately declares a same-named
callable may see a new ambiguity; an alias or the qualified form resolves it. This is the main
behavioral consequence of unifying the call surfaces.

The source model becomes more permissive in one direction: an explicit namespace can contain
extension members for several receivers. The existing collision checks still apply per qualified
name.

No runtime representation, descriptor, or API-index schema change is required. The standard-library
API version changes only if the standard library moves an extension to a different namespace.

The formatter, highlighter, completion, hover, and signature help need to recognize `extension fn`
and `extension property` as namespace members. Completion should offer applicable extension members
at the receiver dot and namespace members after a namespace qualifier.

## Alternatives

- **Keep extension blocks and namespaces separate.** The compiler already unifies them at the
  namespace, owner, and import level, so the split is only a source-level leak. Rejected.
- **Remove the block form immediately.** A clean break would simplify the model further, but it
  would break every existing extension declaration and its import path for no semantic gain.
  Rejected for this proposal; it can be a later compatibility decision.
- **Require every extension to be inside an explicit namespace.** This would remove the synthesized
  receiver namespace, but it would break existing source and add ceremony to one-off extensions.
  Rejected for this proposal; top-level sugar preserves compatibility.
- **Keep `mut` instead of `this: &T`.** `mut` makes `this` the only parameter whose type is
  implicitly wrapped in a reference. The explicit `&T` spelling uses the existing capability model.
  Rejected, but the block form keeps `mut` as sugar.
- **Use `Type.method` receiver syntax instead of a `this` parameter.** Dot is the member operator,
  and `Type.method` would be ambiguous with qualified calls and type arguments. Rejected.
- **Make extension members callable only at the receiver dot.** This preserves today's rule, but it
  leaves a namespace member that cannot be called as `Namespace.f(...)` and cannot be used as a
  function value. Rejected; qualified calls are the explicit escape hatch.

## Implementation and validation

Likely stages:

1. Accept `extension fn` and `extension property` as namespace members; parse `this` as the
   receiver parameter. `methodSignature` already recognizes a first `this` parameter.
2. Stop rejecting `parsed.receiverParameter()` in extension declarations; derive `receiverType`
   from the parameter and set `isMutating` from `&T`.
3. Desugar the top-level block and top-level member form into the receiver-named namespace.
4. Update import and lookup code to use the declaration namespace for extension members.
5. Add qualified calls and function-value references for extension members.
6. Update the formatter, highlighter, completion, hover, signature help, and the guide.

Validation should cover:

- existing block extensions and top-level extensions unchanged;
- canonical member form with read-only and `&T` receivers;
- generic receivers, default arguments, and variadic parameters after `this`;
- extension properties;
- a namespace mixing ordinary functions, values, and extensions for several receivers;
- explicit, wildcard, and package-star imports;
- receiver-dot precedence and the qualified escape hatch;
- ambiguity between same-named declarations from different namespaces;
- duplicate and erased-signature collisions in one namespace;
- annotation and documentation keys;
- separate compilation and library-index round-trips for both forms; and
- JVM owner and descriptor stability for existing extensions.

## Open questions

- Should `extension R { ... }` blocks be allowed inside a namespace and contribute to that
  namespace, or should the member form be required there?
- Should extension properties support qualified getter calls such as `Ns.size(list)`?
- Should `mut` remain an accepted alternative spelling for `this: &T` in the member form?
- Should `extension predicate fn` be supported, and how would receiver facts transfer?
- Should extension annotations key on the declaration namespace instead of the receiver-qualified
  name?
- Should a namespace gain a visibility modifier so one modifier can gate all members?
- Should nested namespaces be allowed once extensions are namespace members?
- Should the library index eventually merge `ExtensionExport` and `FunctionExport`, or keep the
  extension record as the one that carries receiver applicability?
