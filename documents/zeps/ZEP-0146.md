## Abstract

Add a brace-delimited block expression whose value is introduced by a final `yield` clause:

```zeron
let total = {
    let subtotal = price(quantity);
    yield subtotal + shipping;
};
```

A block is value-producing only in an expression position. The same braces in a statement
position remain an ordinary `Stmt.Block` and continue to have type `Unit`. Existing constructs that
consume statement blocks—`if` statement branches, `loop`/`while`/`until` bodies, `using` bodies, and
function bodies—do not become value-producing and are not migrated by this proposal.

The handler use case that motivated [ZEP-0110](./ZEP-0110.md) follows without a handler-specific
block rule: `handle { … yield value; } with …` protects an ordinary block expression. The existing
`handle (expression) with …` form is unchanged.

## Motivation

ZEP-0110 proposed a block-bodied handler with two possible value rules. The recommended rule made
`return` block-local, which would give `return` a different meaning inside a handler block than
everywhere else. The alternative—a final-expression value—would have introduced implicit value
semantics for brace blocks before the language had a general value-block design.

A final `yield` is a better marker for the block's produced value:

- `yield` already means "this is the value produced" in `for` and `do` expressions.
- `return` keeps one meaning: leave the enclosing function.
- A block expression can serve handlers, `let` initializers, arguments, and `match` arms without a
  special case for each consumer.
- The final `yield` makes the value edge explicit, so ordinary statement blocks keep their current
  `Unit` meaning and do not acquire a second, context-dependent rule.

The goal is not to make every brace block valued. It is to introduce one explicit value form for
positions that already expect an expression.

## Goals

- Add a value-producing block expression in expression positions.
- Require exactly one final `yield expression;` in a value block.
- Make the yielded expression the block's value and use the ordinary expression checker for it.
- Make `yield` target the innermost value block.
- Preserve the current `Unit` meaning of statement blocks and every construct that consumes them.
- Let `handle` protect a block expression directly, without changing handler typing or runtime
  behavior.
- Keep the lowering inline: no immediately-invoked lambda, closure, wrapper type, or runtime ABI
  change.
- Keep `yield` a soft keyword and preserve its existing `for` and `do` meanings.

## Non-goals

- Migrating `if` statement branches, `loop`/`while`/`until` bodies, `using` bodies, function bodies,
  or any other statement-block consumer to value semantics.
- An implicit final expression as the block value. A bare final expression remains a statement.
- Early `yield` from nested control flow, multiple `yield` clauses, or `yield` as a general
  non-local exit. Those are a separate control-flow proposal.
- Block-local `return`. `return` continues to return from the enclosing function.
- Value-producing `loop`, `using`, or other statement forms.
- Changing the lowering or semantics of `do` expressions or `for` expressions.
- A handler-specific value rule or a new handler typing rule. Handlers continue to use the existing
  structural result compatibility.
- Monadic lowering, resumable effects, or response-typed effects.

## Proposal

### Syntax and block selection

A value block is a primary expression:

```zeron
fn totalPrice(first: Int, second: Int): Int = {
    let subtotal = first + second;
    yield subtotal * 2;
};
```

The grammar for the new expression is:

```text
valueBlock = "{", { statement }, "yield", expression, ";", "}" ;
```

The block must contain exactly one `yield`, and it must be the last clause. A block with no
`yield`, or with a `yield` before another statement, is a parse error when parsed as an expression.
A block with `yield` in a statement position is also an error; statement blocks do not acquire the
new meaning.

A brace block in expression position is always parsed as the value form. A brace block in statement
position remains an ordinary `Stmt.Block`. This is a syntactic position distinction, not an
inference choice: the parser does not decide after the fact whether a block is valued.

Examples:

```zeron
// Expression position: value block.
let result = { yield compute(); };

// Statement position: ordinary Unit block, unchanged.
{
    compute();
    return;
}

// A function expression body may be a value block.
fn answer(): Int = { yield 42; };
```

A value block used where a `Unit` value is expected still writes `yield ();` explicitly:

```zeron
fn logBoth(): Unit = {
    println("first");
    yield ();
};
```

This follows the existing explicit-result discipline of `do` and avoids a second implicit `Unit`
rule for expression blocks.

### `yield` ownership

`yield` belongs to the innermost value block:

```zeron
let pair = {
    let inner = {
        yield 2;
    };
    yield inner + 1;
};
```

The inner block yields `2`; the outer block yields `3`. A `yield` in a nested *statement* block is
not a value clause and is rejected. Conditional values use the existing value-producing `if`
expression before the final yield:

```zeron
let label = {
    let value = if (enabled) then 1 else 0;
    yield value.toString();
};
```

Early `yield` inside an `if` statement branch, a `loop` body, or a `match` arm's statement block is
outside this proposal. `match` arms in expression position may contain value blocks; each such block
has its own final yield.

### Scoping and control flow

- A value block introduces one lexical scope. Locals declared in it are visible to later statements
  and to the final yield, and do not escape the block.
- The value block does not create a new function or lambda. Captures and mutable-access rules are the
  same as the enclosing function.
- `return` retains its existing function-level meaning. It does not yield the block value. A
  `return` inside a value block exits the enclosing function, subject to the existing unreachable
  and effect rules.
- `break` and `continue` retain their lexical loop targets. A value block inside a loop does not
  introduce a new control boundary. A value block used as a handler operand does not weaken the
  existing handler-boundary rule for `break`/`continue` that cross the handler.
- `raise`/`perform` and `handle` inside a value block behave as ordinary nested expressions.
- A `using` statement inside a value block keeps its existing disposal and suppressed-outcome
  behavior. It remains a statement and does not itself produce the block value.

### Typing and effects

The block's type is the type of its yielded expression. An expected type, when present, constrains
that expression through the ordinary expression checker; otherwise the ordinary inference rules
apply. There is no implicit final-expression type and no implicit `Unit` fallback.

The escaping effect row is the union of the rows of all statements in the block and the yielded
expression, using the existing row union and handler-coverage rules. `yield` itself adds no effect.
A handler around the block sees the same protected row it would see for the equivalent statements
and final expression.

### Handlers

The existing handler operand becomes:

```zeron
handle {
    let record = load(id);
    let account = accountFor(record.owner);
    yield account.user;
} with {
    case NotFound as missing -> guest(missing.id);
    case DbError -> guest(0);
};
```

This is equivalent to:

```zeron
handle ({
    let record = load(id);
    let account = accountFor(record.owner);
    yield account.user;
}) with {
    case NotFound as missing -> guest(missing.id);
    case DbError -> guest(0);
};
```

No handler-specific parsing, value rule, or typing rule is added. The existing single-expression
form remains unchanged:

```zeron
handle (findUser(id)) with MissingUserText;
```

A Unit-valued protected block writes `yield ();`. Handler arms continue to use the existing
structural result compatibility; the protected result is simply the block's yielded type.

### Interaction with `for` and `do`

`for` and `do` keep their current clause grammars and meanings. A `yield` at the clause level
belongs to the enclosing `for` or `do`, as it does today. A value block nested inside a clause or a
bind expression owns its own yield by the innermost-block rule.

A value block may be a `do` block's final monad-valued expression, because it is an ordinary
expression. This does not add a second result rule to `do`.

### Lowering

The compiler lowers a value block inline. It emits the block's statements in a new lexical scope and
uses the yielded expression as the expression result. It must not lower the block to an
immediately-invoked lambda: that would change mutable capture rules, add allocation, and make
`return`, `break`, and `continue` behave differently from the enclosing function.

The likely AST shape is a new `Expr.ValueBlock` containing the statements and the final yielded
expression. `Stmt.Block` remains statement-only. The existing statement resolver and emitter handle
the statements; the expression path handles the yielded value. No new runtime type, descriptor,
library-index record, or ABI is required.

### Diagnostics

- `Yield is only valid as the final clause of a value block.`
- `A value block must end with a 'yield' clause.`
- `A value block may contain only one 'yield' clause.`
- `A 'yield' clause must be the last clause of a value block.`
- Existing diagnostics for `return`, `break`, `continue`, `using`, effects, and type mismatch apply
  unchanged inside the block.

## Compatibility and impact

The new expression is source-additive. Existing statement blocks keep their current parse, type,
and lowering; existing `for` and `do` yield clauses are unchanged. `yield` remains a soft keyword
and is recognized as the value clause only in a value block's final position or in the existing
clause contexts.

Existing source that used braces in an expression position did not compile as an expression block,
so no previously valid program changes meaning. The new `handle { … } with …` spelling is additive;
`handle (expression) with …` remains valid.

No runtime representation, descriptor, library-index schema, or standard-library API version
changes. Formatter, highlighter, AST dump, completion, and parser tests need the new expression
shape. The grammar and guide sections describing block values and handler operands need updates.

Because this is a syntax and compiler-surface change, not a runtime mechanism, it can be validated
in the same release cycle as the existing syntax work. It does not depend on response-typed effects.

## Alternatives

- **Keep ZEP-0110's return-based handler block.** Rejected because it makes `return` block-local in
  one construct and does not generalize to non-handler expression positions.
- **Use a final expression without `yield`.** Rejected for this proposal because it makes every
  brace block potentially valued and hides the value edge. A final-expression form remains a
  possible later language change.
- **Allow early or multiple yields.** Deferred. Early yield is a control-flow feature: it interacts
  with `if`, `loop`, `break`, `using`, and handler boundaries, and should not be smuggled into a
  value-block syntax proposal.
- **Lower to an immediately-invoked lambda.** Rejected because it changes capture, allocation, and
  non-local control flow.
- **Rewrite every statement block into a value block.** Rejected. Only expression positions gain the
  new form; this proposal deliberately does not migrate block-statement consumers.
- **Implement this only inside `handle`.** Rejected because the same value form is useful in
  ordinary `let` initializers, arguments, return expressions, and expression arms.

## Implementation and validation

Likely stages:

1. Grammar and parser: add a value-block primary in expression position; preserve statement-block
   parsing; parse exactly one final `yield`; update diagnostics and the `handle` protected operand
   to accept a block expression directly.
2. AST: add `Expr.ValueBlock` with its statements and final yielded expression; keep
   `Stmt.Block` unchanged.
3. Resolution: nested scope, flow analysis, expected-type checking, effect-row union, and
   existing `return`/`break`/`continue` rules.
4. Emission: inline statements and yielded value; no closure or new ABI.
5. Tooling and documentation: formatter, highlighter, AST dump, LSP positions, grammar, raised
   effects guide, and handler examples.

Validation should cover:

- a value block in a `let`, argument, return, and `match` arm;
- nested value blocks and innermost-yield ownership;
- an empty value block, a missing yield, an early yield, and multiple yields;
- a Unit value block with `yield ()`;
- locals not escaping the block and shadowing in nested blocks;
- `return` inside a value block returning from the enclosing function;
- `break`/`continue` inside a loop and the existing rejection when crossing a handler;
- `using` inside a value block, including disposal effects and suppressed outcomes;
- effect union and handler coverage for statements plus the yielded expression;
- `handle { … yield … } with …` equivalent to the parenthesized block form;
- unchanged statement-block and `if`/`loop`/`using` behavior;
- formatter and highlighter round trips;
- bytecode showing inline lowering rather than an immediately-invoked lambda.

## Open questions

None blocking the initial slice. Early yield, a final-expression value rule, and value-producing
`loop`/`using` are explicitly deferred rather than left implicit.

## Decision

Accepted and implemented on 2026-11-20 for the `0.8.0` bundle.

`Expr.ValueBlock` holds the block statements, the yielded expression, and the `yield` token. A brace
block in expression position is parsed by a dedicated value-block entry point that requires the
final `yield`; a block in statement position still produces `Stmt.Block` and keeps `Unit`. The
resolver scopes the block like any other block, checks the yielded expression with the ordinary
expression checker, and the emitter writes the statements and value inline, so no closure or runtime
ABI is introduced. `yield` remains a soft keyword and keeps its `for` and `do` meanings; the
formatter recognizes the form and indents it as a block.

The deferred items above remain deferred, not implicitly decided: early `yield`, multiple `yield`
clauses, an implicit final-expression value, block-local `return`, and value-producing `loop` or
`using` are all rejected or unchanged rather than permitted. Validation covers value blocks in
`let` initializers, expression-bodied functions, `if` arms, and nested blocks through
`ValueBlockTest`; a missing or non-final `yield` is rejected by the parser with a span on the
offending token.
This proposal supersedes [ZEP-0110](./ZEP-0110.md); ZEP-0110's return-based block rule is not
carried forward.
