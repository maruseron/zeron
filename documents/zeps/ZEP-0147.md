## Abstract

Hard-drop the `raise` and `raises` keywords and replace them with `perform` and `performs`:

```zeron
fn read(path: String): String performs IoFailure =
    perform IoFailure.new("cannot read " + path);

fn applyTwice<E: effect...>(
    value: Int,
    transform: (Int) -> Int performs E
): Int performs E = transform(transform(value));
```

`perform` is the control-transfer keyword. It applies an effect value and has type `Never`.
`performs` is the effect-row clause on declarations, function types, handler types, and contracts.
There are no compatibility aliases: existing programs using `raise` or `raises` are migrated or
rejected with a targeted diagnostic.

Raising can still be expressed through a named effect constructor:

```zeron
public effect IoFailure {
    public constructor raise(message: String);
}

fn read(path: String): String performs IoFailure =
    perform IoFailure.raise("cannot read " + path);
```

Once `raise` is removed from the keyword set, `raise` is an ordinary identifier and can name an
effect constructor. The explicit `IoFailure.raise(...)` communicates both the effect and the
intent at the perform site.

## Motivation

The current vocabulary treats every effect operation as an exception-like raise. That vocabulary
fits abortive effects, but it is misleading for tail-resumptive and general resumable effects:

- A tail-resumptive operation may return a response value and continue normally; it is not
  necessarily an exceptional exit.
- A resumable operation describes a request or operation being performed, not a thrown exception.
- `raise` suggests an immediate failure and a stack-based unwind, which is only one possible
  response model.
- `raises` on a function type describes the effects the callable may perform, including effects
  whose handlers resume.

`perform` is the standard vocabulary for algebraic effects: the computation performs an operation,
and a handler decides how to respond. `performs` reads as a property of the callable and does not
presuppose stack unwinding. The rename separates the language-level effect mechanism from the
host's exception mechanism and leaves `raise` available as an ordinary constructor name when an
author wants an exception-flavored effect.

The change is deliberately a hard drop. Keeping `raise` as an alias would preserve two
vocabularies, make new documentation inconsistent with old code, and keep the exception-oriented
reading alive. Zeron is still pre-1.0, so the source break belongs in a dedicated release.

## Goals

- Replace the `raise` keyword with `perform` at every effect-operation site.
- Replace the `raises` clause keyword with `performs` in declarations, function types, handler
  types, and effect-row positions.
- Keep the existing type rules, effect-set semantics, handler dispatch, and runtime carrier
  unchanged.
- Remove the old spellings rather than accepting aliases.
- Allow ordinary effect constructors named `raise`, since `raise` is no longer a keyword.
- Give source using the removed spellings a clear migration diagnostic.
- Update the standard library, grammar, formatter, highlighter, LSP word lists, guides, and tests.

## Non-goals

- Changing abortive versus tail-resumptive versus general resumable semantics.
- Adding response types, continuation capture, or new handler behavior; those remain
  [ZEP-0118](./ZEP-0118.md) and related proposals.
- Changing effect identity, effect subtyping, effect-row inference, or handler coverage.
- Changing the generated `RaisedEffect` carrier or Java exception mappings.
- Keeping deprecated aliases for `raise` or `raises`.
- Migrating documentation prose mechanically where “raise” is being used as ordinary English
  rather than as a Zeron keyword.

## Proposal

### Surface syntax

The keyword mapping is complete:

| Old spelling | New spelling |
| --- | --- |
| `raise expression` | `perform expression` |
| `raises Effect1, Effect2` | `performs Effect1, Effect2` |
| `(A) -> B raises E` | `(A) -> B performs E` |
| `R ~> {E} raises {G}` | `R ~> {E} performs {G}` |
| `raises {}` | `performs {}` |

Examples:

```zeron
fn load(id: Int): String performs MissingUser =
    perform MissingUser.new(id);

fn loadLabel(id: Int): String performs MissingUser =
    load(id);

fn callback(transform: (Int) -> Int performs E): Int performs E =
    transform(1);
```

A handler type continues to distinguish the effects it handles from the effects its arms may
perform:

```zeron
String ~> {MissingUser} performs {IoFailure}
```

The `perform` expression resolves its operand as an effect payload, contributes that nominal effect
to the enclosing row, and has type `Never`. `performs` clauses use exactly the same parsing,
duplicate checking, subtyping, row-polymorphism, and compatibility rules as `raises` did. This is a
spelling change, not a semantics change.

### Named effect constructors

Effects already have a canonical `new` constructor and may declare named constructors. Because
`raise` is removed from the keyword set, it is available as an ordinary constructor name:

```zeron
public effect IoFailure {
    public property message: String;
    public constructor raise(message: String);
}

fn read(path: String): String performs IoFailure =
    perform IoFailure.raise("cannot read " + path);
```

`IoFailure.raise(...)` is an ordinary effect-constructor call; `perform` applies the resulting
effect value. This preserves the intent of “raising an I/O failure” without retaining `raise` as a
language keyword. A library may also use `new` or any other constructor name.

### Hard removal and migration

- `raise` and `raises` are removed from the keyword vocabulary and become ordinary identifiers.
  This is what allows a constructor to be named `raise` and called as `IoFailure.raise(...)`.
- The parser recognizes the old syntactic shapes narrowly for diagnostics, so a program using a
  bare `raise expression` or a `raises` clause reports `'raise' was removed; use 'perform'.` or
  `'raises' was removed; use 'performs'.` where the old shape is unambiguous. These recognizers
  are diagnostic-only; they never accept the old forms as aliases. A member call such as
  `IoFailure.raise(...)` is not an old operation form and remains legal.
- A source file that uses the old spellings does not compile until it is migrated.
- `perform` and `performs` are reserved keywords. Existing identifiers named `perform` or
  `performs` must be renamed; this is part of the pre-1.0 hard break.
- The formatter, highlighter, LSP keyword list, and documentation examples use only the new
  spellings after migration.
- The standard library and bundled sample programs are migrated in the same change so the
  distribution does not mix vocabularies.

### Semantics

No semantic changes accompany the rename:

- `perform` has type `Never`, like `raise`.
- `perform` contributes its effect to the enclosing row exactly as `raise` did.
- `performs` mentions the same exact effect applications and row variables as `raises`.
- Handler cases, effect subtyping, coverage, and most-specific selection are unchanged.
- The generated `RaisedEffect` carrier, Java exception mappings, and handler dispatch are
  unchanged.
- The rename works for abortive, tail-resumptive, and future resumable effects. Whether an effect
  resumes is determined by its response typing and handler model, not by the spelling of the
  operation.
- The rename does not itself add `await`, continuations, or response types. Those remain separate
  proposal work.

### Tooling and diagnostics

The scanner, parser, formatter, highlighter, LSP, and diagnostic catalog move together:

- Add `PERFORM` and `PERFORMS` tokens and remove `RAISE` and `RAISES` as accepted syntax.
- Retain removal diagnostics for the old spellings.
- Update keyword completion and syntax highlighting.
- Update formatter spacing and line-breaking rules that currently special-case `raises`.
- Update grammar documentation and error messages to say “perform” and “performs”.
- Update all standard-library declarations and tests that currently write `raises`.

## Compatibility and impact

This is an intentional source-breaking change. Every declaration, function type, handler type, and
effect operation using `raise` or `raises` must be migrated. No binary compatibility is affected:
the keyword spelling is not part of JVM descriptors, the runtime carrier, or the library-index
schema. The effect set and the generated code are identical after the rename.

The standard library API version does not need to change solely for a keyword rename; its exported
declarations retain the same names and effect metadata. The source distribution, guides, examples,
formatter output, and compiler tests do change. A release note and a concise migration table are
required. Because the project is pre-1.0, the break is scheduled for `0.9.0` under the versioning
policy in [ZEP-0012](./ZEP-0012.md).

The main risk is diagnostic quality, not semantics: once `raise` is no longer a keyword, a missing
migration could otherwise surface as an unrelated identifier or argument error. Dedicated removal
diagnostics are therefore part of the proposal, not optional polish.

## Alternatives

- **Keep `raise`/`raises` as aliases indefinitely.** Rejected: it preserves the exception-oriented
  vocabulary and creates two ways to write the same declaration.
- **Keep `raise` but rename only `raises`.** Rejected: the operation site is where the misleading
  exception reading is strongest, and the pair should remain grammatically parallel.
- **Use `perform` with `raises`.** Rejected for the same reason: a function would perform an effect
  but “raise” its row, keeping the vocabulary split.
- **Use contextual keywords instead of reserved keywords.** This would reduce identifier breakage,
  but it complicates parsing and does not remove the old vocabulary. The hard drop is intentional.
- **Use `invoke`, `signal`, `effect`, or `emit` for the operation.** `perform` is the established
  algebraic-effects term and reads naturally with an effect constructor. The alternatives either
  collide with existing concepts or suggest a particular response model.
- **Migrate with a formatter-only rewrite.** The formatter can help, but it cannot safely rewrite
  `raise` used as an ordinary identifier or a constructor name. The migration must be explicit.

## Implementation and validation

Likely stages:

1. Scanner and tokens: add `perform`/`performs`; remove `raise`/`raises` from accepted syntax; add
   removal diagnostics.
2. Parser: update operation expressions, declarations, function types, handler types, and effect
   rows.
3. Tooling: formatter, highlighter, LSP keywords, diagnostics, and grammar.
4. Migration: bundled standard library, sample programs, tests, and guides.
5. Documentation: release note, migration table, and cross-references that currently describe
   `raise`/`raises` as the language keywords.

Validation should cover:

- `perform` with `new` and with a named constructor such as `IoFailure.raise(...)`;
- `performs` on functions, methods, extensions, constructors, function types, contract methods,
  handler types, and row-polymorphic declarations;
- effect-subtype compatibility and handler coverage unchanged;
- generic effect applications and `effect...` rows unchanged;
- nested handlers, guarded cases, and suppressed outcomes unchanged;
- old-spelling diagnostics for `raise` and `raises` in each syntactic position;
- formatter idempotence and highlighter/LSP keyword behavior;
- standard-library and separate-compilation round trips after migration;
- a Java exception mapping still producing the same effect at the external boundary.

## Open questions

- Should the removal diagnostics remain permanently, or only for the first post-drop release?
  Keeping them permanently is recommended for migration clarity.
- Should the formatter offer an opt-in migration rewrite, or should the compiler only diagnose and
  leave edits to the user? A diagnostic-only first implementation is recommended.
- Should `perform` and `performs` be unconditionally reserved, or could `performs` remain contextual
  while `perform` is reserved? The hard-drop intent favors reserving both.
