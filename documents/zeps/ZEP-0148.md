## Abstract

Allow an effect-free Zeron lambda or top-level function reference to implement a Java functional
interface when the expected parameter type is explicitly a Java SAM type. The compiler discovers the
interface's single abstract method from class-file metadata, including inherited abstract methods and
classpath interfaces, infers the lambda parameters from that method, and lowers the conversion
through the existing `LambdaMetafactory` path. `raises` remains a Zeron control-flow channel; a
converted callback must have an empty effect row.

## Motivation

Zeron lambdas implement generated Zeron function-shape interfaces. That representation is efficient
for Zeron-to-Zeron calls but unusable for Java APIs that expect `java.util.function.Function`,
`Predicate`, `Comparator`, `Runnable`, `Callable`, or a classpath-defined functional interface. The
current resolver rejects the situation outright: `MemberInteropResolver.resolveJavaCall` reports
`UNSUPPORTED_JAVA_INTEROP_FEATURE` for any lambda argument to a Java member.

Today the only workaround is a hand-written Java adapter or a facade that accepts a Zeron function
and performs the adaptation in Java. That duplicates machinery Zeron already has. Zeron lowers its
own lambdas to synthetic SAM interfaces through `LambdaMetafactory`, and the class-file metadata
reader already exposes Java methods, generic signatures, and interface flags. The missing work is
target selection, functional-interface discovery, effect policy, and a small amount of lowering,
not a new calling convention.

Passing behavior into Java is distinct from the trust boundary in
[ZEP-0050](./ZEP-0050.md): the boundary decides when a host access is allowed; this proposal decides
how a Zeron lambda can satisfy an explicitly written Java SAM parameter.

## Goals

- Convert effect-free Zeron lambdas and top-level function references to Java functional interfaces
  when the expected parameter type is explicitly a Java SAM, without changing the representation of
  Zeron function values.
- Discover Java SAMs from class-file metadata, including inherited abstract methods and classpath
  interfaces, rather than requiring a hand-maintained interface table.
- Infer lambda parameter and return types from the SAM method, using the existing Java type and
  generic-signature mappings.
- Reuse `LambdaMetafactory` and add no new runtime class, generated interface, or API-index field.
- Reject a conversion whose lambda or function reference has a non-empty `raises` row.
- Select an overload deterministically, and report ambiguity rather than guessing from the lambda
  body.

## Non-goals

- Implicitly converting an already-typed Zeron function value to a Java SAM. A lambda or function
  reference at the Java call site is the supported form in this slice.
- Generic Zeron lambdas or SAM methods with their own type parameters. A Java SAM method must be
  monomorphic after the interface's type arguments are substituted.
- Java method references (`Type::method`).
- Interfaces with more than one abstract method, or classes used as functional targets.
- Mapping Zeron raised effects into Java exceptions, or permitting `zeron.runtime.RaisedEffect` to
  escape into Java frames.
- Refining a SAM's inferred parameter or return nullability through a facade.
- Guaranteeing callback lifetime, identity, serialization, reentrancy, or thread safety when Java
  retains a callback.
- Changing the representation of Zeron function values or Zeron function-shape interfaces.

## Proposal

### Functional-interface discovery

A Java functional interface is a Java interface with exactly one abstract method after excluding
`Object` methods (`equals`, `hashCode`, `toString`), static and default methods, and bridge or
synthetic methods. Inherited abstract methods count, so `UnaryOperator<T>` is a SAM because it
inherits `Function<T, T>.apply`.

The compiler discovers this shape from class-file metadata rather than from a hand-maintained table,
so the curated JDK set, `Comparator`, `Runnable`, `Callable`, and classpath interfaces all use the
same path. Discovery walks superinterfaces to find candidate abstract methods and reports an
interface with zero or multiple candidates as non-convertible. The `@FunctionalInterface` annotation
is informational and is not required. Results are cached per binary name.

Discovery may traverse superinterfaces to find the single abstract method. That is not general
inherited-member lookup, which remains [ZEP-0149](./ZEP-0149.md).

### Contextual conversion

A Zeron lambda or top-level function reference may be converted to a Java SAM when the expected
argument type is an explicitly written Java functional-interface type. The resolver substitutes the
interface's type arguments into the SAM method, converts the Java method signature to a Zeron
function type with the existing Java type and generic-signature mappings, and resolves the lambda
against that function type. Lambda parameter and return types are therefore inferred from the SAM,
exactly as they are inferred from a Zeron function parameter today.

```zeron
import java.util.function.Function;

// Illustrative facade; the same rule applies to a direct Java call under `unsafe`.
public external class Mapper = "example.Mapper" {
    public static transform(values: Array<String>, f: Function<String, String>): Array<String>;
}

let names = Mapper.transform(names, (name) -> name.trim());
```

The existing Zeron function-shape interfaces remain the default. A Java SAM target is selected only
when the parameter type is a Java functional interface; a Zeron function parameter is never
implicitly retargeted to Java. Prefer a Zeron function-typed parameter when both it and a Java SAM
would be applicable.

Java overload resolution currently resolves argument types eagerly, so it cannot choose between
candidates whose SAM targets differ. The resolver must defer lambda and function-reference
arguments, filter candidates by arity and SAM applicability, and resolve only when one candidate
remains. If several candidates remain applicable with different SAM targets, report an ambiguity
diagnostic; do not guess from the lambda body in this slice.

### Lowering

Lowering reuses the current `LambdaMetafactory` path. The `invokedynamic` return type is the Java
interface, the SAM method type is the interface method's erased descriptor, and the instantiated
method type is that descriptor with the interface type arguments substituted. The implementation
method remains the same static method that implements the Zeron lambda. The metafactory supplies the
required boxing, unboxing, reference widening, and `Unit`-to-`void` discard. Captures and generated
function-shape interfaces are unchanged, so there is no new runtime class, generated interface, or
API-index field.

### Effect and nullability rules

Two restrictions keep the callback boundary sound.

- **No Zeron raised effects may cross into Java.** A converted lambda or function reference must
  have an empty `raises` row. It may handle its effects internally. A Java callback has no Zeron
  handler boundary and may run after the originating call has returned, so allowing a
  `zeron.runtime.RaisedEffect` into Java would turn typed control flow into an untyped host failure.
  Host exceptions from `unsafe` Java calls still propagate as host exceptions and are not mapped
  into Zeron effects.
- **Java reference types keep their existing nullability mapping.** A Java callback may pass null
  where Zeron expects a non-null reference. That is the same host-trust limitation that applies to
  direct Java calls. A facade documents its callback contract, but current argument checking does
  not let a facade refine the SAM's inferred nullability; nullable-aware refinement is a follow-up.

SAM conversion does not itself require `unsafe` when the target type is explicit in a Zeron or
facade signature. A direct Java call still requires `unsafe` under
[ZEP-0050](./ZEP-0050.md), and a lambda inside that operand follows the same effect-free rule.

### Callback lifetime

A callback created this way may be retained by Java and invoked later, on another thread, or more
than once. This slice makes no lifetime, identity, serialization, or thread-safety guarantee. Values
captured by the lambda remain subject to the normal closure rules; a facade that retains a callback
must document that the captured values remain reachable and safe for the invoking thread.

### Supported forms

Inline lambdas and top-level function references are in scope. Implicitly converting a value whose
Zeron type is already a function value (for example a `let` binding) is not: write a lambda at the
Java call site or add an explicit adapter.

## Compatibility and impact

SAM conversion adds no syntax. It changes overload selection for Java calls with lambda or
function-reference arguments: a Java functional-interface parameter is now a valid target, and an
ambiguous set of SAM overloads is rejected instead of being reported as an unsupported callback. The
generated bytecode uses the Java interface directly and introduces no new runtime class, generated
interface, or API-index field.

A Zeron library that exposes a Java SAM type in its signature is unchanged; callers resolve the SAM
from the JDK or classpath and generate the implementation at the call site. The effect-free rule can
reject a lambda that a Zeron higher-order function would accept; that is intentional and is reported
at the conversion site. Existing Zeron function values and Zeron function-shape interfaces keep
their current representation, and there is no implicit conversion of a stored function value in this
slice.

The change touches resolver diagnostics, Java class-file metadata, the lambda compilation plan, the
bytecode emitter, and the Java-interoperability, raised-effect, and lambda guides. It does not change
the Java type/array mappings, generic interop, intrinsic bindings, or the Zeron library artifact
format, and it does not change `raise` or `handle` typing.

## Alternatives

- **Use only a hard-coded table of JDK functional interfaces.** This is simple and predictable, but
  it cannot serve classpath APIs and would need compiler changes for each new interface. Rejected;
  the JDK set is the required test matrix, while discovery is metadata-driven.
- **Require a hand-written Java adapter class for every callback (PureScript-style FFI).** This is
  explicit and safe, but it makes ordinary `forEach`, `map`, and `Comparator` use impractical and
  duplicates the lambda machinery Zeron already has. Rejected as the default; an adapter remains
  the escape hatch for a callback that must map Zeron effects or refine nullability.
- **Allow effectful callbacks and let `zeron.runtime.RaisedEffect` escape into Java.** This would
  preserve the lambda's effects syntactically, but Java code can catch the carrier as an ordinary
  `RuntimeException`, callbacks may run on another thread, and the effect no longer has a Zeron
  handler boundary. Rejected for this slice; effectful callbacks must handle or map their effects
  before conversion.
- **Add a `sam` cast or adapter expression.** This adds syntax and a second way to spell a
  conversion that the expected parameter type already determines. Rejected; contextual typing is
  sufficient, and an explicit adapter method remains available for the unsupported cases.
- **Convert stored function values implicitly.** This would make a Zeron function value usable
  wherever a Java SAM is expected, but it hides a representation change at an assignment boundary
  and complicates overload selection and inference. Rejected for this slice; require a lambda or
  function reference at the Java call site.
- **Model a SAM as an `external newtype` over a function type**, for example
  `external newtype Function<T, R> :: "java.util.function.Function" = T -> R`. This looks like a
  zero-cost naming of the SAM as a function type, but a direct-carrier newtype has one
  representation: either the generated Zeron shape (`T -> R`) or the Java interface, not both.
  Construction would have to run an adapter instead of merely re-labelling the carrier. Inside a
  newtype extension `this` is the carrier, so Java defaults such as `andThen` and `compose` cannot be
  invoked on the Java object, and newtypes have no static namespace for `identity`. Newtype
  parameters are invariant, which conflicts with both Zeron function variance and the interface's
  own generic contract. The effect-free and nullability rules would also have to be restated on the
  newtype, and contextual overload selection would remain. Rejected for this slice; a Java-object
  representation with call lowering and an explicit member surface would be a separate proposal, not
  a newtype amendment.

## Implementation and validation

1. Extend class-file metadata with the superinterface list and abstract/default method flags. Add
   functional-interface discovery that walks superinterfaces, ignores `Object` methods and
   static/default/bridge/synthetic methods, rejects interfaces with more than one abstract method,
   and caches the result per binary name.
2. Add a Java SAM target descriptor to lambda and function-reference resolution. Substitute the
   interface type arguments into the SAM method generic signature, convert the method to a Zeron
   function type, and record the Java interface, erased SAM descriptor, instantiated descriptor, and
   type arguments on the expression so lowering does not have to rediscover them.
3. Replace the eager `resolveJavaCall` lambda rejection with candidate-aware argument handling.
   Defer lambda and function-reference arguments, filter overloads by arity and SAM applicability,
   resolve only when one candidate remains, and report an ambiguity diagnostic otherwise. Prefer a
   Zeron function-typed parameter over a Java SAM when both are applicable.
4. Extend `LambdaCompilationPlan` and the emitter with a Java-SAM target: use the Java interface as
   the `invokedynamic` return type, the erased interface method as the SAM method type, and the
   substituted method as the instantiated type. Keep Zeron function-shape emission unchanged.
5. Enforce the empty-`raises` rule for converted lambdas and function references, with a diagnostic
   that points to `handle` or an explicit adapter. Keep host exceptions outside the Zeron effect
   row.
6. Add focused tests for the curated JDK set (`Function`, `UnaryOperator`, `Predicate`, `Consumer`,
   `Supplier`, `BiFunction`, `Comparator`, `Runnable`, `Callable`, and the primitive
   specializations), inherited SAMs such as `UnaryOperator`, classpath SAMs, captures, boxing and
   unboxing, `Unit`-to-`void`, top-level function references, effect rejection, overload ambiguity,
   separate compilation, formatter and language-server behavior, and runtime invocation from Java.
7. Update the Java-interoperability guide with the supported callback contract and its lifetime and
   nullability limitations.

The trust boundary in [ZEP-0050](./ZEP-0050.md) should land first because it defines the direct-access
gate; SAM conversion then builds on the same call-resolution path.

## Open questions

- Should a stored Zeron function value convert implicitly to a Java SAM, or should the explicit
  lambda-at-the-call-site rule remain the only form?
- Should a facade be able to refine a SAM's inferred parameter and return nullability, or is a
  nullable-aware adapter the right escape hatch?
- What callback lifetime and threading guarantees should Zeron make when Java retains a callback?
  This slice documents that none are promised; a later design may add an explicit retained-callback
  contract.
- Should a conversion be allowed when the SAM parameter is a type variable or projection that
  resolves to a functional interface, or only when the written type is directly a Java interface?

## Decision

Accepted 2026-11-17 as a `0.8.0` candidate and implemented on 2026-11-18, split from the original
accepted [ZEP-0050](./ZEP-0050.md) umbrella. An effect-free Zeron lambda or top-level function
reference can implement a Java functional interface when the expected parameter type is explicitly
that Java interface. Discovery is metadata-driven, including inherited abstract methods and classpath
interfaces; lowering reuses `LambdaMetafactory`; and no new runtime, generated-interface, or
API-index ABI is introduced. Zeron `RaisedEffect`s must not cross into Java, and the slice makes no
callback lifetime or thread-safety promise.

ZEP-0050 now owns only the host-access trust boundary. The remaining interop inventory is
[ZEP-0149](./ZEP-0149.md).
