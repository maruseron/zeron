## Abstract

Inventory the Java interoperability areas that are not covered by type and array mappings, generics,
exception/effect integration, the host-access trust boundary, or SAM conversion, and define the
conditions under which each is worth implementing. The areas are general inherited and interface
member lookup, external contracts for Java interfaces, external enums, JPMS configuration,
user-extensible external bindings, and interop conformance and diagnostics.

This proposal is an inventory, not a commitment. It carries no release target until a concrete
standard-library or application use case justifies a slice.

## Motivation

Java interop now has a settled trust boundary ([ZEP-0050](./ZEP-0050.md)) and a bounded way to pass
Zeron behavior into Java ([ZEP-0148](./ZEP-0148.md)). Several capabilities remain unavailable, and
they have different risks, dependencies, and design questions. Grouping them into one release would
force unrelated decisions—member dispatch, foreign interface conformance, enum representation,
module configuration, binding ownership, and diagnostic coverage—through a single review.

Keeping them in one inventory still has value: it records what is intentionally absent, so the
absence is not mistaken for an oversight, and it lets each area be promoted on its own evidence
rather than by expanding Java access implicitly.

## Goals

- Record the remaining interop areas and the questions each must answer before implementation.
- Define the promotion rule: an area is implemented only when a concrete use case, descriptor
  checks, diagnostics, and focused tests are identified.
- Preserve explicit imports, classpath roots, and facade allowlists unless a separate design
  approves a broader discovery model.
- Keep each area's syntax, metadata, resolution, runtime, and compatibility impact independent.

## Non-goals

- Implementing any of the areas in this proposal.
- Reopening the trust-boundary decisions in [ZEP-0050](./ZEP-0050.md) or the SAM rules in
  [ZEP-0148](./ZEP-0148.md).
- Broadening the type/array, generic, or checked-exception semantics owned by
  [ZEP-0047](./ZEP-0047.md), [ZEP-0048](./ZEP-0048.md), and [ZEP-0049](./ZEP-0049.md).
- Treating an external contract as a witness-bearing or `requires`-composing Zeron contract, or
  changing the contract model in [ZEP-0135](./ZEP-0135.md) and [ZEP-0136](./ZEP-0136.md).
- Fusing an external enum into Zeron sum lowering, or promising Java enum ABI from a Zeron sum.
- Promising complete JVM language interoperability, reflection, package scanning, or implicit
  imports.

## Proposal

Track and design the following areas independently, selecting implementation only when there is a
concrete standard-library or application use case.

### General inherited and interface members

Define lookup through superclasses and interfaces: instance and static methods, default methods,
fields, ambiguity, access, overload precedence, and interaction with the facade tier.

Open questions:

- Does a direct Java call see inherited public members by default, or only members declared on the
  named class?
- How are default methods invoked, and how is an ambiguous default resolved?
- Does a facade declaration name the declaring type or the receiver type, and how does it validate
  the owner?
- Do inherited static members participate in the same lookup and overload rules?

SAM discovery in [ZEP-0148](./ZEP-0148.md) traverses superinterfaces to find the single abstract
method. That is not general inherited-member lookup and does not settle these questions.

### SAM conversion limits carried forward

[ZEP-0148](./ZEP-0148.md) implements contextual conversion for inline lambdas and top-level function
references only. These limits remain outside that slice and belong to this inventory or a future
revision:

- only an inline lambda or a top-level function reference converts; a stored Zeron function value,
  a generic Zeron lambda, a `let`-bound callback, or a value whose type is already a function type
  requires an explicit adapter;
- Java method references (`Type::method`) and constructor references are not conversion targets;
- an interface with zero or multiple abstract methods, a class used as a functional target, an
  abstract method with its own type parameters, or a projected type argument is rejected rather than
  adapted;
- discovery distinguishes SAM shape only; it does not provide general inherited-member lookup,
  default-method dispatch, or inherited field access for ordinary Java calls;
- the SAM's inferred nullability comes from the ordinary Java reference mapping, and a facade cannot
  refine a callback parameter or result to a non-null Zeron type;
- a converted callback must have an empty `raises` row; Zeron effects are not mapped to Java
  exceptions, and `zeron.runtime.RaisedEffect` must not escape into Java;
- overload selection defers callbacks only when the unresolved argument is a lambda or a top-level
  function reference; candidates that remain tied after SAM applicability are reported as
  ambiguous;
- no callback lifetime, identity, serialization, reentrancy, or thread-safety guarantee is made, and
  Java may retain or invoke the callback later or on another thread;
- the conversion is selected from an explicitly written expected parameter type. Contextual
  conversion of an underconstrained generic parameter, or a callback hidden behind a projection or
  alias, does not become general SAM discovery;
- the emitted class-file metadata records the Java interface on the call target; no API-index record
  is added for the callback itself. Cross-library consumers rediscover the SAM from the JDK or
  classpath.

These limits do not reopen [ZEP-0050](./ZEP-0050.md)'s trust boundary. A direct Java call still
requires `unsafe`; a facade still needs its declared callback contract, and a callback that needs
nullability refinement or effect mapping remains an explicit adapter.

### External contracts for Java interfaces

Define a declaration that binds a Java interface as a Zeron nominal type whose JVM face is the
interface itself, so a Zeron class can implement it and a Zeron value can be passed back to Java:

```zeron
public external contract Comparator<T> = "java.util.Comparator" {
    public fn compare(left: T, right: T): Int;
}
```

The main use is the reverse of [ZEP-0148](./ZEP-0148.md): a named class or anonymous object
implements a multi-method foreign interface, not just a single-method callback. Using an existing
Java interface value only requires the inherited-member work above; implementing one requires a
conformance rule.

A first slice should be explicitly smaller than Zeron's contract model:

- conformance is declaration-site: `class X is ExternalContract` emits `implements` the Java
  interface, with the existing generic-contract bridge machinery satisfying erased descriptors;
- Java default methods are inherited through JVM dispatch, and a compatible Zeron class method
  overrides them;
- no `requires`, witnesses, higher-kinded bounds, or sealed `permits`; Java `extends` supplies
  composition, and a witness has no object to supply as the interface value;
- invariant type parameters, methods only, and one descriptor per member name until overloads are
  decided;
- no static methods or constants in the first slice. [ZEP-0124](./ZEP-0124.md) explicitly excludes
  static fields, a general JVM static-member model, and Java static methods as nominal evidence, so
  `Comparator.comparing` and `Function.identity` need a separate decision;
- a runtime type test checks the Java interface, consistent with today's rule that a contract test
  checks the generated JVM interface;
- an external Java class is usable as an external contract only through a metadata-driven widening
  rule over the superinterface list, or through an explicit facade until that rule exists.

The prerequisites are generic external declarations (an `external class` declaration still has no
type parameters, although an import alias can name a parameterized Java type), inherited-member
metadata and lookup, abstract/default method flags, and a decision on overloads and statics. The
declaration also needs a conflict rule with `external class` when both name the same binary name,
and an API-index record for the Java owner, descriptors, and version.

Open questions:

- Is `external contract` the right name, or should this be a distinct `external interface` form that
  does not imply witnesses and `requires`?
- Should the first slice support one descriptor per member name, or reuse the Java interop overload
  resolution inside conformance checking?
- Are Java interface statics and constants part of this declaration, a separate static-member
  mechanism, or permanently delegated to facades?
- Should a Zeron class conform to an external contract only by declaration, or may class-file
  metadata prove conformance for an `external class` value?
- Do Java default methods need the inherited-member work to be callable, or can they be invoked
  directly through the interface once the interface is bound?
- Do generic external declarations belong here, in [ZEP-0048](./ZEP-0048.md), or in a separate
  proposal?
- How does a `LambdaMetafactory` callback from [ZEP-0148](./ZEP-0148.md) relate to a generated
  single-method implementation of the same external contract? They should not produce two
  incompatible representations.

### External enums

Bind a Java enum as an external type and decide whether it also exposes a closed case set for
matching. The two goals conflict: passing a value back to Java requires the actual enum object, while
exhaustive matching without an `else` requires a constant set that a separate-compiled library can
change.

Evaluate three tiers, in order:

1. **External class plus constants.** Allow enum classes in class-file metadata (they are currently
   excluded alongside annotations and modules), expose constants as static reads, and declare
   `name`, `ordinal`, `values`, `valueOf`, and any instance members explicitly. This is
   ABI-faithful, requires no new matching semantics, and is the minimum needed to use an enum at
   all.
2. **`external enum` as a case-set view.** Cases compile to static reads of the Java constants,
   identity is preserved, and `when` compiles to identity tests. `values()` and `valueOf()` remain
   declared members rather than synthesized operations, because a newer library version can return a
   constant the declaration does not list. Exhaustiveness is not assumed by default; a closed-set
   opt-in would have to record the constant set in the API index and check it at runtime.
   Constant-specific class bodies and abstract methods implemented per constant are out of scope.
3. **Zeron sum plus adapter functions.** For application-owned sets, declare a Zeron payload-less
   sum and write explicit conversions at the Java boundary. This gives the best Zeron ergonomics and
   needs no compiler work, but it creates two types for one concept and cannot represent
   constant-specific behavior without additional mapping.

Do not fuse an external enum into Zeron sum lowering. [Design document
14](../design_documents/design-document-14_sum-product-types-and-newtypes.md) records that a
generated JVM enum is an optimization for payload-less sums, not an exposure of Java enum operations
or ABI.

Open questions:

- Is the external-class tier sufficient, or is `external enum` worth the matching surface?
- Should matching an external enum always require `else`, require an explicit closed-set opt-in, or
  fail at runtime on an unmatched constant?
- How are plain enums distinguished from enums with constant-specific bodies or per-constant
  abstract methods, and should the latter be rejected or partially mapped?
- Should `values()` be synthesized from class-file metadata, and how does the constant set interact
  with separate compilation and the API index?
- Does reading an enum constant require `unsafe` under [ZEP-0050](./ZEP-0050.md)? An enum constant is
  `static final` but has no class-file `ConstantValue` attribute, so the current constant-read
  exemption does not apply. An immutable singleton read is a reasonable extension of that exemption.
- How are `EnumSet`, `EnumMap`, `ordinal`, and serialization fidelity preserved without promising
  that a Zeron sum is the Java enum?

### JPMS configuration

Decide whether projects may declare module-path entries, readability, and qualified exports in
addition to the current classpath and exported-JDK lookup.

Open questions:

- Are module-path entries a project-manifest concern, a CLI concern, or both?
- How do readability and qualified exports interact with the existing unnamed-module generation?
- Does module metadata participate in the compiled-library API index?
- What diagnostics distinguish a missing module, a non-exported package, and a non-readable
  module?

JDK module exports are already honored for discovered classes; this area concerns project-declared
modules and the runtime classpath model.

### External-binding extensibility

Assess how users or library authors can declare checked, descriptor-validated host bindings without
changing compiler-owned registries or weakening the explicit facade model.

Open questions:

- Are bindings source declarations, project configuration, library metadata, or a combination?
- How is a user binding descriptor-checked against class-file metadata?
- How are binding identities and checked-exception mappings serialized, versioned, and validated in
  a compiled library?
- What prevents a binding from silently widening access beyond the facade allowlist?

A user-extensible binding must remain explicit and reviewable. It must not become a path for package
scanning or implicit imports.

### Interop conformance and diagnostics

Maintain a capability matrix and focused tests covering supported descriptors, overloads,
JAR/class-directory lookup, runtime classpaths, and failure diagnostics.

Open questions:

- Which capabilities need a machine-checked conformance matrix rather than prose documentation?
- How should diagnostics distinguish an unsupported descriptor, an inaccessible member, a missing
  runtime dependency, and a trust-boundary violation?
- Which conformance checks belong in the compiler test suite, and which belong in a sample or
  external integration suite?

## Compatibility and impact

This proposal changes no behavior. It records deferred areas and the promotion rule for future
work. Any implemented area will carry its own source, runtime, API-index, and migration analysis in
a separate proposal or revision.

## Alternatives

- **Fold the areas back into the trust-boundary proposal.** This keeps one interop document, but it
  couples independent decisions and makes the accepted `0.8.0` slice look larger than it is.
  Rejected; the trust boundary and SAM conversion are now separate proposals.
- **Implement all remaining areas immediately.** This maximizes interop coverage, but it expands
  metadata lookup, module configuration, and binding ownership without concrete use cases and
  without settled diagnostics. Rejected.
- **Drop the inventory and document gaps only in guides.** Guides explain current behavior, but they
  do not carry design questions or promotion criteria. Rejected; the inventory keeps ownership and
  dependencies explicit.

## Implementation and validation

Each area receives its own syntax, descriptor checks, resolution behavior, runtime requirements,
diagnostics, and focused tests when selected. Before implementation:

1. Identify the concrete standard-library or application use case.
2. Decide whether the area needs a new proposal or a revision to this one.
3. Define the diagnostic set and the class-file metadata additions.
4. Define compatibility and migration impact.
5. Add a capability-matrix row and a focused test plan.

The existing guidance remains: new capabilities must not silently introduce package scans, implicit
imports, runtime dependencies, or unvalidated conversions.

## Open questions

- Which remaining area should be promoted first, and what use case justifies it? The interface and
  enum areas need concrete host APIs before they can be promoted.
- Should external contracts precede external enums, or the reverse? External contracts depend on the
  inherited-member and descriptor work; external enums can start from the smaller external-class
  tier.
- Does `external contract` reuse the `contract` keyword, or should a distinct `external interface`
  form avoid implying witnesses, `requires`, and higher-kinded bounds?
- Does an external enum need closed-set matching, or is an external class with constant reads
  sufficient for the first consumers?
- Should external-binding extensibility precede inherited-member lookup, or the reverse?
- Is JPMS support needed for the first host-library consumers?
- Should user-extensible bindings be source declarations, project configuration, library metadata,
  or a combination?
- Does every area need its own ZEP, or may related areas share one when their design decisions are
  coupled?

## Decision

Draft. No disposition yet. The proposal is an unscheduled inventory and is not a `0.8.0`
commitment. It was split from the original [ZEP-0050](./ZEP-0050.md) umbrella when the trust
boundary and SAM conversion became independent proposals. External contracts for Java interfaces and
external enums were added on 2026-11-17 as inventory areas; neither is accepted or scheduled, and
each needs its own proposal before implementation if its design proves independent. The implemented
limits of [ZEP-0148](./ZEP-0148.md) were recorded on 2026-11-18 so the remaining inventory does not
imply support for stored function values, Java method references, generic SAM methods, effect
mapping, or callback lifetime guarantees.
