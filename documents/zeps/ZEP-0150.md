# ZEP-0150: Safe Invocation of Nullable Function Values

## Abstract

Allow a nullable function-valued expression to be invoked with the existing safe-navigation
operator followed by an argument list:

```zeron
couldBeNull?.();
callback?.(21);
factory()?.(21);
```

The callee expression is evaluated once. If it is `null`, the arguments are not evaluated and the
whole expression produces `null`. Otherwise the function value is invoked normally, and its result
is made nullable.

## Motivation

[ZEP-0134](./ZEP-0134.md) made an argument list follow any non-null function-valued expression, but
deliberately left nullable callees as an error. A nullable callback therefore still requires a
temporary binding or an explicit branch:

```zeron
if (couldBeNull != null) {
    couldBeNull(21);
} else {
    null;
}
```

The safe-navigation syntax already means “continue only when the receiver is non-null” for member
access. Applying the same spelling to an invocation keeps nullable callbacks as convenient as
nullable properties, without weakening the non-null rule for an ordinary `couldBeNull(21)` call.

## Goals

- Accept `?.` followed by an argument list after any function-valued expression.
- Evaluate the callee once and skip both argument evaluation and invocation when it is `null`.
- Produce a nullable result, even when the function's declared result is non-null.
- Preserve argument checking, generic and rank-2 instantiation, evidence and reified slots, raised
  effects, receiver-function rejection, and trailing-lambda association.
- Reuse the existing function-shape interface and `invokeinterface` lowering.
- Add no runtime, API-index, standard-library, or function-shape ABI change.
- Add editor hover and signature-help coverage for both ordinary and safe expression invocation.

## Non-goals

- Safe member-call syntax such as `receiver?.callback()`. Existing `?.` member navigation already
  produces a nullable member value; invoking it still requires its own explicit handling.
- Combining `?.` with explicit type arguments, as in `factory?.<Int>()`.
- Changing `!!`, ordinary null checks, or the nullable-value diagnostic for `couldBeNull(...)`.
- Eliding the call's result when the callee is null; the expression has a value and that value is
  `null`.
- Conditional effects that exclude the invoked function's effects on the null path. The static
  effect row remains conservative and includes everything the call may raise.
- General optional chaining beyond invocation.

## Proposal

### Syntax

A safe invocation is a postfix call suffix:

```text
safeCallSuffix = "?.", arguments ;
```

It follows the same postfix position as an ordinary argument list:

```zeron
fn run(callback: ((Int) -> Int)?): Int? = callback?.(21);
```

Concrete valid forms include:

```zeron
callback?.(21);
callback?.();
makeCallback()?.(21);
callbacks[0]?.();
(if (flag) then callback else null)?.(21);
```

Named and member calls keep their current syntax. `?.` followed by `(` is parsed as safe invocation;
`?.` followed by a member name remains safe member navigation, and `?.(` is not a method named `(`.

### Evaluation and typing

For

```zeron
callee?.(arguments);
```

evaluation is:

1. evaluate `callee` exactly once;
2. if it is `null`, skip the arguments and produce `null`;
3. otherwise evaluate the arguments left to right, invoke the function value, and produce its
   result.

The callee's non-null base must be an ordinary function descriptor. The result type is the
function's result type made nullable:

```zeron
fn maybe(flag: Boolean): (Int -> Int)? = if (flag) then (value -> value + 1) else null;

let result: Int? = maybe(true)?.(41);   // 42
let missing: Int? = maybe(false)?.(41); // null
```

Argument count and assignability use the same rules as an ordinary function-value invocation.
Generic and rank-2 function values instantiate their binders from the arguments exactly as they do
for a non-safe expression callee. Receivers are still required for receiver-function values, and
`receiver?.callback()` is only safe member navigation; it does not supply a receiver for a
receiver-function call.

A safe invocation is also accepted on a non-null function value. It behaves like an ordinary call
with an already-present callee, and its result is still nullable, so the operator's result type does
not depend on flow refinement of the callee.

### Effects

The call's raised effects are the union of the callee expression's effects and the resolved
function's declared effects. The null path does not raise the invocation's effects at runtime, but
the static row remains conservative; this matches the existing treatment of nullable branches whose
one arm never executes.

### Lowering

The existing generated function-shape interface is unchanged. The compiler emits:

1. the callee expression;
2. a duplicate and an `ifnull` branch;
3. on the non-null path, the arguments, hidden evidence and reified slots, and the existing
   `invokeinterface` call;
4. on the null path, discard the callee and push `aconst_null`;
5. apply the existing result conversion and box a primitive result for the nullable result type.

No local temporary, wrapper object, dynamic lookup, or new generated interface is introduced.

### Editor coverage

Hovering the closing parenthesis of an expression invocation or safe invocation shows the invokable
function value, such as `function value Int -> Int`. Traditional signature help is available through
`textDocument/signatureHelp`, reports the active argument, and works for named calls, expression
callees, and safe invocation. The editor capability advertises `(` and `,` as trigger characters.

## Compatibility and impact

The change is additive. With the exception of new `?.(` syntax, programs that parsed before retain
their meaning. `callback?.(...)` previously failed with a nullable-value diagnostic or a
safe-navigation parse error, so it becomes newly valid.

There is no runtime ABI change: function objects, generated interfaces, descriptors, and evidence
layout are unchanged. The API index records no new declaration shape, and the standard-library API
version does not change. The language server gains a new request handler and capability, but the
extension protocol remains backwards compatible.

## Alternatives

- **Require an explicit null check.** This preserves the current rule but keeps nullable callbacks
  awkward and duplicates behavior already expressed by `?.`.
- **Reuse `?()` without a dot.** It is visually close to a ternary or optional-type marker and does
  not reuse the established safe-navigation spelling. Rejected.
- **Return `Unit` on the null path.** This loses the distinction between a missing callback and a
  function that completed normally, and it cannot apply when the callee returns a value. Rejected.
- **Exclude the invocation's effects on the null path.** This requires path-sensitive effect rows
  for a fallback that usually does not run; conservative effects keep analysis predictable and match
  the current design. Deferred as a separate effect-analysis change.
- **Add safe member-call syntax as part of this proposal.** That would need a separate decision about
  receiver functions and member navigation. Left out.

## Implementation and validation

Implemented on 2026-11-18 as an `0.8.0` candidate:

- the parser accepts `?.` followed by an argument list and records the safe flag and callee-end token
  on `Expr.Invoke`;
- resolution unwraps the nullable function type, rejects non-functions and receiver functions, and
  makes the result nullable;
- emission tests the callee, leaves the null path without evaluating arguments, and boxes a
  primitive result on the non-null path;
- hover covers invocation-expression parentheses, and the language server implements signature help.

Validation covers non-null and null callees, safe invocation of a non-null value, generic and rank-2
values, skipped argument evaluation, rejection of non-function and receiver-function callees, LSP
hover and signature help for expression and safe calls, and the full test suite.

## Open questions

- Should `?.` support safe member calls as a separate extension?
- Should explicit type arguments be allowed after a safe expression callee, such as
  `factory?.<Int>()`?
- Should effect rows eventually become path-sensitive enough to omit invocation effects on a
  statically known null path?
