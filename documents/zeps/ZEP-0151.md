# ZEP-0151: Spread Arguments for Variadic Parameters

## Abstract

Add a prefix spread operator for variadic argument lists:

```zeron
fn total(values: Int...): Int = values.fold(0, (sum, value) -> sum + value);

let numbers = [1, 2, 3];
total(...numbers);              // 6
total(10, ...[20, 30]);         // 60
```

`...` is the call-site dual of the variadic parameter syntax `values: Int...`. It tells the
compiler that the operand already contains the variadic elements. When an array supplies the whole
variadic tail, the existing packed array is passed through without copying or repacking. For any
other `Iterable<E>`, the compiler extracts the elements with the normal iteration protocol, packs
them into the array the callee receives, and invokes the call once.

## Motivation

Variadic parameters already make direct calls concise, and their lowered form is an array:

```zeron
fn logAll(messages: String...): Unit = ...;

logAll("starting", "ready");
```

The same functions cannot consume an existing array or collection directly. A caller with a
dynamically sized `Array<String>` or `ArrayList<String>` must index it manually, build a second
array, or reshape the API. Function values do not solve the problem because an indirect call takes
one `Array<T>` argument, while a direct variadic call still expects individual elements.

Spread syntax closes that gap without changing the variadic representation. The packed array is
already the calling convention, so the array case is only a signal to the compiler; the iterable
case reuses the existing `Iterable` traversal and creates the packed array the callee already
expects.

## Goals

- Add `...expression` as a spread argument in a direct call's variadic tail.
- Accept a non-null `Array<E>` and pass its existing backing array directly.
- Accept any non-null value assignable to `Iterable<E>` and pack its elements into the variadic
  array.
- Infer a generic variadic element type from the spread operand's `Array<E>` or `Iterable<E>`
  element type.
- Preserve left-to-right evaluation and evaluate the spread operand exactly once.
- Preserve the existing variadic calling convention for functions, methods, contract methods, and
  named constructors.
- Reuse the existing intrinsic array conformance and `Iterable` evidence/protocol lookup; do not
  introduce a second iteration model.
- Keep the feature syntactically local: no new runtime representation, public API, API-index
  schema, or compiled-library metadata.
- Update the formatter, syntax highlighting, and language-server surfaces for the new argument
  form.

## Non-goals

- Multiple spreads in one call, or any argument after a spread. The first version accepts at most
  one spread, as the final argument.
- Spreading into an ordinary fixed `Array<E>` parameter. Passing that array normally already
  expresses the intent.
- Spreading into Java varargs. Direct Java calls keep their existing argument adaptation.
- Spread in array literals, collection literals, pattern positions, `for` headers, or any position
  other than a direct-call argument.
- Treating a nullable array or iterable as empty. Nullability must be handled explicitly.
- Tuple, record, or generic-pack expansion. This proposal only forwards a homogeneous sequence of
  the variadic element type.
- Changing indirect function-value calls. A function value whose variadic parameter is represented
  as `Array<T>` continues to take that array as one argument.
- Changing variadic arity, default-argument, or effect-row rules.

## Proposal

### Syntax and placement

A spread argument is an argument expression prefixed with the existing `...` token:

```text
argument       = expression | spreadArgument ;
spreadArgument = "..." expression ;
```

The grammar accepts `...` only at the start of an argument. Parentheses may be needed to spread a
compound expression:

```zeron
logAll(...messages);
total(10, ...moreNumbers);
total(...(if (useExtra) then extra else []));
```

A spread is valid only when the resolved call has a variadic parameter, and it must be the final
argument. It never fills a fixed parameter. Fixed parameters are supplied by ordinary arguments
before the spread or by their defaults. Ordinary arguments before the spread may also supply
earlier variadic elements; the spread contributes the remaining elements of the tail:

```zeron
fn tagged(prefix: String = "tag", values: Int...): String = ...;

tagged(...numbers);          // default prefix, spread values
tagged("sum", ...numbers);   // explicit prefix, spread values
total(1, ...[2, 3]);         // fixed prefix is empty; packs 1, 2, 3
total(...[1, 2], 3);         // rejected: the spread is not final
total(...[1], ...[2]);       // rejected: only one spread
```

At most one spread may appear in a call. The restriction keeps argument order explicit and avoids a
variadic tail assembled from several interleaved sources. A later proposal can relax it if a
concrete use case appears.

### Typing

Let the resolved variadic parameter have element type `E`; its lowered parameter type is
`Array<E>`. The spread operand must be non-null and satisfy one of:

- `Array<E>`, or an array view such as `&Array<E>` projected to the read-only parameter, which
  uses the direct array path;
- a type assignable to `Iterable<E>`, which uses the extraction path.

The `Iterable` check is the same conformance check used for an ordinary `Iterable<E>` argument.
Array conformance to `Iterable<E>` from [ZEP-0060](./ZEP-0060.md) applies, but an array operand is
recognized before that adaptation so it can take the direct path.

Array compatibility remains invariant. An `Array<Dog>` cannot be spread into a variadic parameter
whose element type is `Animal` merely because `Dog` is an `Animal`; an `Iterable<Animal>` view must
be produced explicitly, as with any other generic argument.

For generic calls, each spread operand contributes `Array<E>` or `Iterable<E>` evidence to
inference instead of contributing a value of type `E`:

```zeron
fn firstOf<T: nullable>(fallback: T, values: T...): T =
    if (values.length > 0) values[0] else fallback;

let numbers = [4, 5, 6];
firstOf(0, ...numbers);                 // E inferred as Int
```

A nullable spread operand is rejected at compile time. `values?` must be checked or asserted
non-null before spreading; a null value is not an empty sequence.

### Evaluation and lowering

Arguments are evaluated left to right. Ordinary arguments are evaluated first, in source order,
then the spread operand is evaluated exactly once, and finally the call is invoked. The elements of
an iterable are traversed after the operand value is produced.

#### Array path: pass the packed array through

When the operand's resolved type is an array and the spread supplies the whole variadic tail:

1. Evaluate the operand once.
2. Project a mutable `&Array<E>` view to the read-only `Array<E>` expected by the callee, when
   needed.
3. Pass the resulting `Object[]` reference as the variadic array argument.

No new array is allocated and no element is copied. This is the mechanical meaning of "the array
is already packed." The callee receives a read-only `Array<E>` view over the same backing array, so
it cannot mutate slots through the variadic parameter. Writes through another mutable alias remain
visible, matching the existing array-to-`Iterable` adapter behavior. This optimization depends on
the operand's static type: an array value already viewed as `Iterable<E>` goes through the
extraction path below.

If ordinary variadic arguments precede the spread, the packed tail is assembled from those values
and the array's contents. The compiler allocates one exactly sized `Object[]`, stores the earlier
values, and copies the array elements into the remaining slots. The array is still not traversed
through `Iterable`; only the unavoidable combination allocates.

#### Iterable path: extract and pack

When the operand is another `Iterable<E>`:

1. Evaluate the operand once and retain it in a temporary.
2. Obtain its iterator with the existing `Iterable.iterator()` protocol.
3. Repeatedly call `next()`, appending each `Step.Yield` payload to a temporary growable buffer
   until `Step.Done`.
4. Copy the buffer into an exactly sized `Object[]` and pass that array as the variadic argument.

The buffer is necessary because `Iterable` does not expose a length. The traversal is `O(n)` time
and uses `O(n)` temporary space for the packed elements. The iterator protocol is the same one used
by `for` loops, including generic `Iterable` evidence and the intrinsic array conformance when an
array is viewed through `Iterable`. A single-use `Iterable` implementation is consumed by the
spread, exactly as it would be by any other traversal.

Iteration itself is effect-free in the current `Iterable` contract; only evaluation of the spread
operand can add effects to the call. The packed array is freshly allocated on this path, so no
caller-owned collection is exposed to the callee. When ordinary variadic arguments precede the
spread, they are stored in the same buffer before the iterable elements are appended.

### Calls in scope

Spread applies to direct calls whose callee is declared with a variadic parameter, including:

- top-level functions;
- class, contract, and extension methods;
- named constructors;
- signature-only external functions declared with a Zeron variadic parameter.

Function values and indirect calls are unchanged: their variadic parameter is already a single
`Array<T>` parameter, so callers pass the array normally. Canonical `new` constructors have no
variadic parameters and are unaffected.

### Diagnostics and tooling

- A spread on a call without a variadic parameter reports an argument-shape error explaining that
  only variadic tails accept spread arguments.
- A spread used for a fixed array parameter reports the same argument-shape error and suggests
  passing the array normally.
- A non-`Iterable` operand reports an argument-type mismatch against `Iterable<E>`.
- A nullable operand reports that a nullable value cannot be spread; it does not silently become an
  empty sequence.
- A spread that is not final, or a second spread, reports a placement error at the offending
  argument.
- The formatter renders `...` attached to the following expression, the highlighter treats it as an
  operator, and signature help accepts a spread where the variadic tail begins.

## Compatibility and impact

This is an additive source-syntax change. Calls that were previously invalid become valid; no
existing valid call changes meaning. Indirect function-value calls, variadic arity, defaults,
effects, and the lowered `Array<T>` parameter are unchanged.

No runtime representation, public standard-library API, API-index schema, or compiled-library
metadata is added. Compiled libraries already export the variadic marker, so spread calls work
against library functions without a new export record. Separate compilation needs only the
consumer-side parser, resolver, and emitter changes.

The direct array path intentionally shares the caller's backing array. Because the callee's
variadic parameter is read-only, the callee cannot write through it; mutation through another
alias remains observable, consistent with existing array views and array-to-`Iterable` adaptation.
Callers that need an isolated snapshot can pass a copied array explicitly.

## Alternatives

- **Postfix `values...`.** It mirrors the parameter spelling visually but collides with the type
  suffix and reads like a range or operator applied to the value. The prefix form makes the
  argument-level operation clear.
- **A `spread(values)` library function.** It cannot be typed generically over arbitrary variadic
  element types without reflection, and it would add a call-shaped special form that is harder to
  recognize during resolution.
- **Only support arrays.** This covers the already-packed case, but callers with a list, set, or
  stream would still need to materialize an array themselves. The iterable path is the reason the
  feature is broadly useful.
- **Always copy arrays before passing them.** This avoids aliasing but discards the central
  guarantee that an existing packed array can be forwarded without work. Existing read-only array
  views already make sharing safe at the type level.
- **Allow multiple or interleaved spreads immediately.** This is a straightforward later extension,
  but it complicates ordering, arity diagnostics, and the minimal lowering. A single final spread
  covers the motivating use cases and leaves room to relax the rule.
- **Use `*values`, following Kotlin.** `*` already denotes multiplication and would be visually
  ambiguous in argument expressions; `...` already belongs to the variadic parameter syntax.

## Implementation and validation

Implementation stages:

1. Parse `...` at argument start into an explicit spread argument node or argument flag; reject it
   outside argument position. Update formatter spacing and highlighter tokens.
2. Resolve the callee first, identify the variadic tail and its element type `E`, check that the
   spread is final and unique, and type the operand as `Array<E>` or `Iterable<E>`. Feed the same
   evidence into generic inference instead of the ordinary element constraint.
3. Lower the array path by emitting the operand once and forwarding its `Object[]`. Lower the
   iterable path with the existing iterator protocol and a temporary buffer, then emit the packed
   array as the variadic argument. Keep fixed arguments and their conversions unchanged.
4. Add resolver diagnostics for non-variadic targets, fixed array parameters, nullable operands, and
   invalid placement.
5. Update the language guide, grammar reference, formatter/highlighter/LSP behavior, and changelog
   as part of the implementation change.

Validation should cover:

- direct array spread, including identity of the forwarded array and behavior under a later alias
  write;
- mutable-array-view projection to the read-only variadic parameter;
- list, set, stream, and user-defined `Iterable` extraction, including empty sources;
- mixed fixed arguments and spread, and spread after omitted defaults;
- generic inference from `Array<E>` and `Iterable<E>`;
- named-constructor and contract/extension-method calls;
- rejection of nullable operands, non-iterable operands, non-variadic targets, fixed array
  parameters, non-final spreads, and multiple spreads;
- operand evaluation exactly once, left-to-right order, and propagation of operand effects;
- separate compilation against a library-declared variadic function;
- formatter, highlighter, and signature-help coverage.

## Resolved questions

- **Multiple spreads and interleaved elements.** No. A call keeps one spread, and it must supply the
  whole variadic tail as its final argument. The restriction mirrors the `T...` calling convention,
  which carries exactly one packed array: a second spread would force an intermediate merge and
  make the evaluation order of individual elements harder to read. Interleaving fixed arguments
  after a spread is therefore impossible by construction. This decision is enforced by
  `SpreadSupport.unwrap` and can be revisited by a separate proposal if a real program needs it.
- **Dedicated diagnostic code.** No. Placement and target mismatches report
  `ARGUMENT_OR_PARAMETER_COUNT_MISMATCH` with messages specific to spreads (at most one, final
  argument, variadic target only), and a nullable operand reports
  `NULLABLE_VALUE_REQUIRES_HANDLING`. Both point at the `...` token. A dedicated code would add a
  fifth explanation page for conditions that are argument-list errors and are already named
  precisely at the call site.

## Decision

Accepted and implemented on 2026-11-20 for the `0.8.0` bundle.

`Expr.Spread` records the `...` token and its operand, and `SpreadSupport` unwraps the spread for
every call path, so functions, methods, contract methods, extensions, named constructors, and
instance calls share one implementation. An `Array<E>` operand is forwarded as the packed array the
callee already receives, and any other `Iterable<E>` operand is expanded through the existing
iteration protocol into that array; the operand is emitted once, in argument order. Generic
inference draws the variadic element type from the operand's `Array<E>` or `Iterable<E>` element
type, and the existing argument-count, variadic-target, and nullable-operand checks report at the
`...` token. Validation covers array, list, mixed-tail, omitted-default, generic, method, and
named-constructor calls through `SpreadArgumentTest`; the deferred items above remain deferred.
