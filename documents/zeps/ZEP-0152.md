## Abstract

Add a `zeron.random` module with a seedable, general-purpose pseudorandom generator. `Random` is a
mutable value that produces primitive values, bounded integers, and collection selections, and it
can shuffle a mutable sequence in place.

## Motivation

Programs have no supported source of randomness. Users either write their own generator, reach for
host APIs through `unsafe` Java interop, or misuse time values as a seed. A standard generator gives
deterministic tests, reproducible simulations, and collection selection without pinning applications
to a host API.

## Goals

- A `Random` type with explicit construction from a `Long` seed and from a host entropy source.
- `nextInt`, `nextLong`, `nextBoolean`, `nextFloat`, and `nextByte` production.
- Bounded variants that are uniform without modulo bias: `nextInt(bound)`, `nextInt(origin,
  bound)`, and `nextLong(bound)`, each returning `Option` so an empty range is explicit rather
  than undefined.
- Collection helpers: uniform `pick` over an `Iterable`, and in-place `shuffle` of an
  `ArrayList`.
- Deterministic behavior for a given seed and algorithm, within one release series.

## Non-goals

- Cryptographic randomness or any claim of unpredictability against an attacker.
- A process-wide default instance, implicit seeding, or hidden global state.
- Thread safety. A `Random` is a mutable value and callers synchronize or use separate instances.
- Stable output across `0.9.0` and later releases. Pre-1.0, an algorithm change may alter sequences.
- Random distributions beyond uniform selection from a range.

## Proposal

```zeron
import zeron.collections.ArrayList;
import zeron.random.Random;

fn main() {
    let mut random = Random.seeded(42L);
    let mut values = ArrayList<Int>.empty();
    values.add(1);
    values.add(2);
    values.add(3);
    let die = random.nextInt(1, 7); // Some(value), or None for an empty range
    random.shuffle(values);
}
```

`Random` wraps a 256-bit state and uses xoshiro256** with a SplitMix64 seed expansion, so every
`Long` seed, including `0L`, produces a usable state. The generator owns no shared state and no
lock.

Construction:

- `Random.seeded(seed: Long): Random` is the deterministic constructor.
- `Random.fromEntropy(): Random raises IoFailure` reads host entropy; it is the only constructor
  that touches the host, and it never falls back to a time-only seed.
- `Random.shared()` is not provided.

Primitive production and bounded helpers live as member functions. Bounded integers use Lemire's
multiply-and-reject method so every value in the range is equally likely, and they return `None`
instead of defining behavior for an empty range. Collection helpers use reservoir sampling for
`pick` and Fisher–Yates for `shuffle`, so `pick` does not require `Sized` or indexing. `shuffle`
uses `ArrayList`'s existing indexed access and mutation; a shared mutable-access contract can
replace that concrete parameter later without changing call sites that pass an `ArrayList`.

`pick` returns `Option<T>` and yields `None` for an empty input. `shuffle` takes `&ArrayList<T>` and
leaves elements in a uniformly random permutation; it is the only helper that mutates its argument.

## Compatibility and impact

- Additive standard-library module. No source, runtime, or ABI change to existing programs.
- Adds entries to the standard-library API index, so `STANDARD_LIBRARY_API_VERSION` is bumped once
  for the release that includes it.
- The module is ordinary Zeron code; it does not need a new intrinsic or Java binding.
- Documentation: a new guide section under the standard-library chapters, plus API reference pages.

## Alternatives

- **Expose `java.util.Random` through a curated facade.** Rejected: it pins the sequence and the
  algorithm to a host class and its seeding quirks, and it does not give a portable bounded API.
- **Use `ThreadLocalRandom` for convenience.** Rejected: implicit global state defeats deterministic
  tests and makes the seed invisible.
- **A PCG variant.** Viable, but xoshiro256** has a smaller state, simpler code, and well-known
  reference vectors; the choice is not user-visible in this proposal.

## Implementation and validation

1. Implement SplitMix64 expansion and xoshiro256** in `zeron.random`, with the state held in a
   mutable class.
2. Add bounded helpers, `pick`, and `shuffle` over the existing collection contracts.
3. Validate against published reference sequences for fixed seeds, and test that repeated seeds
   produce identical output.
4. Verify bounded uniformity with frequency checks over large samples, and test every bound edge
   (`1`, powers of two, `Int.max`).
5. Run the tests under `zeron test`, using `@Test` functions from the standard testing APIs.

## Open questions

- Should the algorithm be a constructor choice, or is one algorithm enough for `0.9.0`?
- Does `shuffle` belong on `Random` or as an extension on mutable sequences with an explicit
  generator argument?
- Should `Random.fromEntropy()` live in `zeron.random` or in a host-facing namespace, given that
  the rest of the module is pure?
- Should `shuffle` be generalized through a mutable random-access contract instead of the concrete
  `ArrayList` parameter?

## Decision

Implemented 2026-11-24 and shipped in `0.9.0`. `zeron.random.Random` uses xoshiro256** with
SplitMix64 seeding and exposes `nextLong`, `nextInt`, `nextByte`, `nextBoolean`, `nextFloat`,
`nextIntBelow`, `nextIntBetween`, `nextLongBelow`, `pick`, and `shuffle`. Methods cannot overload
by arity, so the bounded operations use the names recorded in the module instead of the shorter
names in the proposal sketch. Entropy seeding declares `IoFailure`.
