## Abstract

Add `PriorityQueue`, `SortedSet`, and `SortedMap` to `zeron.collections`. The queue is a binary
min-heap; the sorted collections are a single red–black tree implementation exposed through two
contracts. All three order elements or keys by `Comparable`, and all three are mutable and
single-threaded like the existing collections.

## Motivation

The standard collections cover hash-based and list-based storage but not ordered retrieval. Users
who need a running minimum, a nearest-key lookup, or ascending iteration currently sort a fresh copy
at every query or implement a tree by hand. These are standard, well-understood structures and
belong in the library rather than in application code.

## Goals

- `PriorityQueue<T: Comparable<T>>` with `add`, `peek`, `poll`, `size`, `clear`, and removal by
  value.
- `SortedSet<T: Comparable<T>>` implementing `Set<T>`, `Sized<T>`, and `Sequenced<T>`, with
  ascending iteration and `O(log n)` membership.
- `SortedMap<K: Comparable<K>, V>` implementing `Map<K, V>`, `Sized<Pair<K, V>>`, and
  `Sequenced<Pair<K, V>>`, with ascending key iteration, `firstKey`, and `lastKey`.
- `O(log n)` insertion, removal, and lookup for the sorted collections; `O(1)` `peek` and
  `O(log n)` `add`/`poll` for the queue.

## Non-goals

- Custom comparators or explicit `Ordering` arguments. `0.9.0` orders by `Comparable` only; a
  comparator-carrying variant is a later addition.
- Persistent or immutable trees, structural sharing, and bulk-build constructors.
- Concurrent collections, lock-free variants, and iteration that tolerates mutation.
- Priority changes after insertion, indexed access into the heap, and stable tie-breaking.
- A `SortedMap` view hierarchy (`subMap`, `headMap`, `tailMap`) in this proposal.

## Proposal

```zeron
import zeron.collections.PriorityQueue;
import zeron.collections.SortedMap;

fn main() {
    let mut queue = PriorityQueue<Int>.empty();
    queue.add(5);
    queue.add(1);
    queue.add(3);
    println(queue.peek()); // Some(1)
    println(queue.poll()); // Some(1)

    let mut ages = SortedMap<String, Int>.empty();
    ages.put("ada", 36);
    ages.put("grace", 45);
    for (let entry in ages) println(entry.first); // ascending key order
}
```

`PriorityQueue` stores its elements in an `ArrayList` laid out as a binary heap. `add` sifts up and
`poll` sifts down, so the smallest element is at index `0`. `remove(value)` locates the value
linearly and repairs the heap, so it is `O(n)`. Iteration yields the heap array order, not sorted
order, and the documentation says so.

`SortedSet` and `SortedMap` share a red–black tree. The tree stores keys in descending/ascending
order with parent, left, and right links and a color bit; insertion and deletion use the standard
rotations and rebalancing cases. `SortedSet` stores the element as the key; `SortedMap` stores a
`Pair<K, V>` and compares only the key. `SortedSet`'s `contains` and `SortedMap`'s `get` walk the
tree rather than hashing, so neither requires `Hashable`.

`SortedSet` implements `add`, `remove`, `contains`, `size`, `clear`, `first`, `last`, and iteration.
`SortedMap` implements `put`, `remove`, `get`, `containsKey`, `keyIterator`, `size`, `clear`,
`firstKey`, `lastKey`, `first`, `last`, and iteration over entries. Iteration is a snapshot-free
in-order walk; mutating during iteration is a programming error, matching the other collections.

Both sorted types require `K: Comparable<K>` (or `T: Comparable<T>`) at construction. Evidence is
resolved through the existing `Comparable` witness, so `Int`, `Long`, `Float`, `String`, and
user types with an implementation work without adapters.

## Compatibility and impact

- Additive collections and contracts. No existing signature changes.
- `PriorityQueue` is a class; `SortedSet` and `SortedMap` are contracts with one implementation
  each. The API index records the contracts, constructors, and tree implementation, so
  `STANDARD_LIBRARY_API_VERSION` is bumped once for the release.
- No intrinsic, runtime, or bytecode-shape change. The tree is ordinary Zeron classes and arrays.
- Documentation: extend the collections chapter with complexity and ordering guarantees.

## Alternatives

- **Sort an `ArrayList` on demand.** Rejected for repeated queries: every lookup becomes `O(n log
  n)`, and mutation invalidates the order.
- **A skip list.** Simpler to implement and adequate, but expected rather than worst-case bounds,
  and it needs more memory per node.
- **A treap.** Randomized balancing is deterministic only with a seeded generator, which couples
  the collections to ZEP-0152 and makes worst-case behavior less predictable.
- **Expose `java.util.TreeMap` through a facade.** Rejected: it would pin ordering and iteration
  details to the host and bypass the collection contracts.

## Implementation and validation

1. Add the `PriorityQueue` class in `zeron/collections/priority_queue.zn` with heap tests for
   duplicates, single element, and interleaved add/poll.
2. Add the red–black tree in `zeron/collections/sorted_tree.zn`, then the `SortedSet` and
   `SortedMap` contracts and implementations.
3. Validate ordering and balancing by inserting ascending, descending, and shuffled keys, then
   deleting from the root, leaves, and one-child nodes.
4. Compare behavior with a reference sorted `ArrayList` on randomized operation sequences.
5. Test contract conformance and that `contains`/`get` work without `Hashable`.

## Open questions

- Should `SortedMap` expose `firstEntry`/`lastEntry` as `Option<Pair<K, V>>` in addition to
  `firstKey`/`lastKey`?
- Do we want `subSet`/`subMap` range views in a follow-up ZEP, or keep the surface closed for now?
- Should `PriorityQueue` support `addAll` and a bulk-heapify constructor, which is cheaper than
  repeated `add`?

## Decision

Implemented 2026-11-24 and shipped in `0.9.0`. `PriorityQueue`, `SortedSet`, and `SortedMap`
are ordered by `Comparable`. The first implementation uses a binary min-heap for the queue and
sorted parallel arrays for the ordered set and map. This gives `O(log n)` lookup and `O(n)`
insertion/removal rather than the proposed red-black-tree asymptotics; the deviation is documented
on `SortedMap` and `SortedSet` and can be replaced without changing their public surface.
