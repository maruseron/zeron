## Abstract

Add a `zeron.text` package with two independent facilities: `Formatter` for placeholder-based,
locale-neutral string formatting, and `Regex` for compiling a pattern once and running matches,
searches, replacements, capture-group access, and match iteration. Regex compiles to a host
`java.util.regex.Pattern` behind the standard library's trusted interop boundary.

## Motivation

Applications assemble user-visible text and match input with hand-written concatenation and
`indexOf` loops. Both are error-prone: formatting loses width and alignment control, and ad-hoc
searching cannot express alternation, repetition, or capture groups. The standard library already
depends on host facilities for I/O and text, so a curated regex surface is a smaller step than a
new pattern engine.

## Goals

- `Formatter.format(template: String, arguments: Array<String>): Result<String, FormatError>`
  with `{}` and `{n}` placeholders, `{{`/`}}` escapes, and width/alignment options.
- Numeric formatting helpers for fixed-notation `Float` and zero-padded integers.
- `Regex.compile(pattern: String): Result<Regex, RegexError>` with a compiled, reusable value.
- `Regex.matches`, `find`, `findAll`, `replaceFirst`, `replaceAll`, and capture-group access by
  index and by name.
- A `Match` value carrying the matched text and its offsets, with iteration over all matches.

## Non-goals

- Unicode normalization (NFC/NFD/NFKC/NFKD). The tables and canonical-ordering algorithm need their
  own proposal and are not part of this surface.
- Locale-aware formatting, collation, or message pluralization. Those belong to the i18n track.
- A new regular-expression engine, a different pattern dialect, or a timeout/step budget for
  catastrophic backtracking in `0.9.0`.
- Formatting arbitrary user-defined values through `Display`. `Display` has no type parameter and
  there is no heterogeneous argument list, so values arrive as `String`.
- Streaming regex matches over an `InputStream`.

## Proposal

```zeron
import zeron.text.Formatter;
import zeron.text.Regex;

fn main() {
    let line = Formatter.format(
        "{:>8} | {:<6} | {:.2}",
        ["total", "bytes", Formatter.fixed(12.3456, 2)]
    );
    // "   total | bytes  | 12.35"

    let digits = match (Regex.compile("(\\d{3})-(\\d{4})")) {
        Ok(regex) -> regex,
        Err(error) -> {
            println(error.message);
            return;
        }
    };
    let text = "call 555-1234 or 555-9876";
    for (let found in digits.findAll(text)) {
        println(found.group(1)); // "555"
        println(found.group(2)); // "1234"
        println(found.start);
        println(found.end);
    }
}
```

### Formatter

The template language is small and closed:

- `{}` consumes the next argument; `{n}` consumes argument `n`; indices are zero-based.
- `{{` and `}}` produce literal braces.
- A field may carry `:<`, `:>`, or `:^` followed by a width, and strings may carry `:.` followed by
  a truncation length. Numeric arguments are already formatted strings, so precision for numbers is
  decided by `Formatter.fixed`.
- A missing argument, an out-of-range index, a malformed field, or leftover arguments produce a
  typed `FormatError` rather than a partially built string.
- `Formatter.fixed(value: Float, places: Int): String` renders non-localized fixed notation with
  round-half-up behavior and `places` digits after the point.
- `Formatter.zeroPadded(value: Long, width: Int): String` renders decimal digits with leading zeros.

The formatter performs no locale lookup and no implicit `toString`. Callers pass values they have
already chosen to display.

### Regex

`Regex.compile` validates the pattern once and reports `RegexError(message, offset)`. The compiled
`Regex` is immutable and reusable, and it is safe to share across threads; matching allocates only
the result values.

- `matches(text): Boolean` requires the whole input to match.
- `find(text): Option<Match>` returns the first match anywhere in the input.
- `findAll(text): Array<Match>` returns every non-overlapping match in order.
- `replaceFirst(text, replacement)` and `replaceAll(text, replacement)` substitute the match;
  replacements support `$1` and `${name}` backreferences.
- `Match.start`, `Match.end`, `Match.text`, `Match.group(index): Option<String>`,
  `Match.namedGroup(name): Option<String>`, and `Match.groupCount`.

The pattern syntax is exactly `java.util.regex.Pattern`. That is a deliberate compatibility
commitment for the `0.9.0` series: the standard library documents it, tests pin the supported
constructs, and a later release may narrow or replace the engine only with a versioned note. The
host class is referenced only from `zeron.text`; applications never import it.

## Compatibility and impact

- Additive package; no existing signature changes.
- Regex pins behavior to the host engine. This is an intentional trade: a portable engine is a much
  larger project, and a host-backed surface is honest about that cost.
- Adds API-index entries and a `STANDARD_LIBRARY_API_VERSION` bump in the release that includes it.
- The host pattern object is an implementation detail and does not appear in the public signatures.
- Documentation: a text-processing chapter covering the format grammar, regex dialect, backreference
  replacement, and catastrophic-backtracking caveat.

## Alternatives

- **Write a regex engine in Zeron.** Rejected for `0.9.0`: Unicode classes, anchors, and backtracking
  semantics are a project on their own and would delay the rest of the bundle.
- **Expose `String.format` and Java's `Pattern` directly.** Rejected: it leaks host types and
  locale-sensitive defaults into portable code.
- **A structured format builder instead of a template string.** Safer for types, but it cannot
  express a template loaded from configuration; the string grammar is the requested surface.
- **Format values through a `Display` constraint.** Currently impossible: `Display` has no type
  parameter and calls take a homogeneous argument list.

## Implementation and validation

1. Implement `Formatter` in ordinary Zeron over `String` and `ArrayList`; keep the parser small and
   report every error with the placeholder offset.
2. Implement `Regex` with `import java.util.regex.Pattern;`, converting host matcher state into
   `Match` values and never exposing `Pattern` or `Matcher`.
3. Test format cases: escapes, sequential and indexed fields, alignment and width, truncation,
   missing and extra arguments, and malformed fields.
4. Test regex cases: whole-string matching, first and repeated matches, named and positional groups,
   empty matches, backreference replacement, invalid patterns, and a Unicode character class.
5. Record the host engine version in the test notes so a future dialect change is visible.

## Open questions

- Does `{}` with automatic indices make accidental reordering too easy, or should every field be
  indexed?
- Should `replaceAll` accept a function from `Match` to `String` in addition to a template string?
- Do we want an optional step budget or timeout to bound catastrophic backtracking before 1.0?
- Should `Formatter` remain in `zeron.text`, or move next to the string API in `zeron.lang`?

## Decision

Implemented 2026-11-24 and shipped in `0.9.0`. `zeron.text.Formatter` supports `{}`, `{n}`,
`{{`/`}}`, `<`/`>`/`^` alignment, width, and `.n` truncation; numeric precision belongs to
`Formatter.fixed`. `zeron.text.Regex` wraps the documented `java.util.regex` dialect with typed
compile errors, matches, numbered and named groups, iteration, and replacement. `.n` is truncation,
not a precision specifier, because the style surface keeps numeric formatting separate.
