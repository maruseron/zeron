## Abstract

Add a curated, receiver-lambda building surface to the standard collections: `List.build { ... }`,
`Set.build { ... }`, `Map.build { ... }`, and `Stream.build { ... }`. Each call creates a builder,
runs the body with the builder as the implicit receiver, and returns the finished collection. The
existing constructors and `Collector` API are unchanged.

## Motivation

Building a small collection currently takes one of two forms: repeated `add` calls on a mutable
local, or a pipe through `Collector`. The first is noisy at the declaration site, and the second is
aimed at folding an existing stream rather than declaring a literal collection. A builder block
keeps the elements next to the binding, reads as one expression, and gives the builder a single
place to enforce its invariants.

`zeron.collections` already declares a `CollectionBuilder` contract with `empty` and `add`, and the
list and deque classes implement it. What is missing is the ergonomic entry point described here;
this proposal does not redesign that contract.

## Goals

- `List.build<T>(body: (ListBuilder<T>) -> Unit): &ArrayList<T>`.
- `Set.build<T: Hashable<T>>(body: (SetBuilder<T>) -> Unit): &HashSet<T>`.
- `Map.build<K: Hashable<K>, V>(body: (MapBuilder<K, V>) -> Unit): &HashMap<K, V>`.
- `Stream.build<T>(body: (StreamBuilder<T>) -> Unit): Stream<T>`.
- Builder methods: `add`/`put`, `addAll`/`putAll`, `size`, `isEmpty`, and `clear`.
- The body's trailing lambda uses the implicit receiver, so members are called without a qualifier.

## Non-goals

- Replacing constructors, `Collector`, or `CollectionBuilder`. All remain available.
- Builders for the sorted collections in ZEP-0154; those can follow once their constructors settle.
- A DSL for nested structures, arithmetic, or conditional element inclusion beyond ordinary `if`
  and loops in the body.
- Builders that survive the call. The builder is not returned, so a caller cannot keep and reuse it.
- Parallel or concurrent building.

## Proposal

```zeron
import zeron.collections.HashSet;
import zeron.collections.HashMap;
import zeron.collections.List;
import zeron.collections.Map;
import zeron.collections.Set;

fn main() {
    let names = List.build<String> {
        add("ada");
        add("grace");
        if (true) add("edsger");
    };

    let unique = Set.build<String> {
        add("ada");
        add("ada"); // ignored: a set holds one copy
    };

    let ages = Map.build<String, Int> {
        put("ada", 36);
        put("grace", 45);
    };

    println(names.size);  // 3
    println(unique.size); // 1
}
```

- Each `build` function is a static contract function with a default implementation: `List.build`
  returns an `ArrayList`, `Set.build` a `HashSet`, and `Map.build` a `HashMap`. `Stream.build`
  returns the existing `Stream` value. Sets and maps carry the `Hashable` bounds their concrete
  implementations already require. The defaults are the canonical choice for the contract; an
  implementation that wants a different concrete type uses the class constructor directly.
- `ListBuilder<T>` wraps an `ArrayList<T>` and forwards `add`, `addAll(values: Iterable<T>)`,
  `size`, `isEmpty`, and `clear`. `SetBuilder` wraps a `HashSet` and returns the boolean result of
  `add`, so a body can observe whether an element was new. `MapBuilder` wraps a `HashMap` and adds
  `put`, `putAll(values: Iterable<Pair<K, V>>)`, `remove`, `size`, `isEmpty`, and `clear`.
- `StreamBuilder` accumulates into an `ArrayList` and converts once at the end, because `Stream` is
  a lazy view and the block is a declaration, not a pipeline stage.
- The body runs exactly once per call, in order. The builder is a fresh value per call, so nested
  builds and recursion are safe.
- A body that raises an effect propagates the effect through `build`; the builder is abandoned and
  no partial collection escapes.

The entry points rely on the existing receiver-lambda and trailing-lambda surface: the body is
contextually typed as a function whose first parameter is the builder and whose implicit receiver
makes its members callable unqualified. If resolving a static contract default through the contract
name is not accepted by the current resolver, the implementation may declare `build` on the
concrete classes and keep `List.build` as a forwarding namespace function; that fallback is an
implementation detail and not part of the user-visible design.

## Compatibility and impact

- Additive API on existing contracts and classes; no source break.
- Adds `ListBuilder`, `SetBuilder`, `MapBuilder`, and `StreamBuilder` to the API index, so
  `STANDARD_LIBRARY_API_VERSION` is bumped once for the release.
- No new runtime representation: builders are ordinary classes, and the returned collections are
  the existing implementations.
- Documentation: extend the collections chapter with builder examples and the set/map boolean and
  replacement semantics.

## Alternatives

- **Use `Collector` for literals.** Rejected: it is designed for folding an existing stream and
  requires a terminal call, which is heavier than a block that declares its elements.
- **Keep only the mutable local plus `add`.** Rejected: it splits one expression into a declaration
  and several statements and allows the mutable binding to leak.
- **A literal syntax for collections.** Rejected for `0.9.0`: it is a parser and type-inference
  change, while the builder block works with existing lambda syntax.
- **Return the builder and require a separate `finish()`.** Rejected: it makes it possible to keep
  and reuse a builder, and it adds a terminal call to every site.

## Implementation and validation

1. Add the four builder classes in `zeron/collections` with the listed forwarding methods.
2. Add the static `build` defaults to `List`, `Set`, `Map`, and `Stream`, or the concrete-class
   fallback if contract-static default resolution is incomplete.
3. Test element order for lists, deduplication for sets, last-write-wins for maps, and laziness of
   `Stream.build` at the conversion boundary.
4. Test an effectful body, a nested build inside another block, and an empty block.
5. Confirm the trailing-lambda implicit receiver resolves builder members without a qualifier and
   that an outer name with the same spelling is not shadowed incorrectly.

## Open questions

- Should `build` live on the contracts or on concrete classes with contract-named forwarding?
- Do we want `SortedSet.build` and `SortedMap.build` in the same pass, or after ZEP-0154?
- Should `addAll` accept a variadic argument list as well as an `Iterable`?
- Should a builder expose `addIf(condition, value)` sugar, or is an ordinary `if` clearer?
