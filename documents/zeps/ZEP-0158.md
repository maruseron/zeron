## Abstract

Add an expression-valued resource block to the standard library: `File.open(path) { ... }` acquires
a resource, runs a receiver lambda with the open resource as a `scoped &File` receiver, disposes it
when the block exits, and returns the block's value. The receiver is denotable, but its scoped type
prevents it from being returned, stored, captured, or passed to an unscoped parameter. Non-escape is
enforced by [ZEP-0160](./ZEP-0160.md) and the receiver method surface of
[ZEP-0161](./ZEP-0161.md), not by hiding the name `this`. The existing `using` statement and
`Disposable` contract remain for resources that outlive a block or are managed explicitly.

## Motivation

`using` is a statement. A function that wants to return a value computed from a resource must
declare a mutable local, assign inside the block, and return afterwards. Nested resources need
nested statements, and handlers cannot wrap the body expression directly. The block form reads as
one expression and puts acquisition and release at the same syntactic level as the value it
produces.

The receiver is a capability rather than an ordinary value. A scoped receiver needs member access
and the ability to call checked helpers, but it must not outlive the block that owns the resource.
A `scoped` type expresses exactly that restriction. It also gives better diagnostics than the
earlier non-denotable receiver: the compiler can name the value, the escape path, and the block
origin instead of reporting that `this` is not a valid expression.

The current model also carries suppressed cleanup outcomes through a dedicated handler-arm clause
(`with suppressed as name`). That is a general mechanism for a case that is specific to resource
cleanup. The block form can put the same information on the disposal failure value instead.

## Goals

- `File.open(path) { ... }` as an expression of the block's result type.
- Exactly-once disposal, in reverse acquisition order for nested blocks, on normal completion and
  on an abrupt exit such as a raised effect or a failed acquisition.
- A scoped receiver of type `scoped &File`, with a denotable `this` and the ZEP-0160 escape rules.
- Helpers authored as `scoped fn` methods on the resource type, so callers can call them without
  naming the receiver and the compiler checks that the receiver does not escape.
- An inline receiver-lambda literal is required at each scoped call; a stored or passed receiver
  function value is rejected. This is the exactly-once rule, not the escape rule.
- Disposal failures carry the body failure as typed payload data instead of relying on
  `with suppressed` at the handler arm.
- Additive adoption: `using` and `Disposable` keep working unchanged.

## Non-goals

- Lifetimes, regions, ownership transfer, or a general borrow checker.
- Linear or `once` function types. The inline-literal restriction makes them unnecessary for this
  feature.
- Asynchronous or cancellation-aware cleanup. That is ZEP-0112/ZEP-0120 work.
- Removing `using` or `Disposable`. Long-lived handles still need explicit disposal.
- Preventing a resource type's own API from publishing an alias to itself or to a resource-owned
  object through an ordinary member. That remains a trusted library-authoring concern; a checked
  helper is a `scoped fn` with a scoped result.
- Allowing a scoped handle to cross the host interop boundary.
- Scoped generic containers or scoped type arguments; [ZEP-0162](./ZEP-0162.md) owns those rules.
- `scoped extension` as a declaration form. Extensions stay ordinary containers and methods carry
  the marker.

## Proposal

```zeron
import zeron.fs.File;

fn firstLine(path: String): String raises IoFailure + DisposeFailure =
    File.open(path) { readLine() };

fn totalSize(paths: Array<String>): Int raises IoFailure + DisposeFailure {
    let mut total = 0;
    for (let path in paths) {
        total = total + File.open(path) { size() };
    }
    return total;
}
```

The standard-library entry point has the shape:

```zeron
public class File {
    public static fn open<T>(path: String, body: (scoped &File).() -> T): T
        raises IoFailure + DisposeFailure;
}
```

`File.open(path)` takes the block as a trailing receiver lambda. The block's receiver type is
`scoped &File`, scoped to the block's dynamic extent. The call returns the block's value, and the
resource is disposed when the block exits normally or raises. `scoped &File` keeps the existing
mutable-reference capability, so `readLine()` and other mutating members are callable.

### Scoped receiver

Inside a scoped block:

- unqualified member access and extension calls resolve against the receiver, as with any receiver
  function;
- `this` is a valid expression with type `scoped &File`;
- `let saved: scoped &File = this` is allowed while the block is active;
- `helper(this)` is allowed when `helper` takes `scoped &File`;
- nested receiver lambdas may qualify the outer receiver as `File.this`; the result has type
  `scoped &File` and the same escape rules;
- `readLine()`, `this.readLine()`, and `File.this.readLine()` are equivalent receiver calls.

The receiver cannot escape the block:

```zeron
File.open(path) { this };                 // error: returns the scoped receiver
File.open(path) { let saved = this; ... }; // allowed only if `saved` does not escape
File.open(path) { pair(this, 1) };        // error if `pair` takes an unscoped parameter
File.open(path) { () -> this };           // error: an escaping closure captures the scoped receiver
```

The block result type `T` is unscoped. A block that returns the receiver would require a scoped type
argument for `T`, which version 1 rejects; the escape checker reports the return as an escape. A
block that returns an independent `String`, `Int`, or other unscoped value works normally.

### Scoped helpers

Helpers are ordinary methods marked `scoped fn`:

```zeron
public class File {
    public scoped fn readHeader(): Header = Header.parse(readBytes(4));
    public scoped fn checksum(): Long = ...;
    public scoped mut fn advance(bytes: Int): Unit { ... }
}
```

A `scoped fn` has a read-only receiver of type `scoped File`; a `scoped mut fn` has `scoped &File`.
The block receiver is `scoped &File`, so it can call both forms. The method bodies cannot return,
store, capture, or pass the receiver to an unscoped parameter. A helper that returns an independent
value, such as `Long`, is itself an ordinary value and can leave the block.

A helper that returns a receiver-tied view must say so:

```zeron
public class File {
    public scoped fn readerView(): scoped &Reader = this.reader;
}
```

The block cannot return that view, because its origin is the block. A helper that returns an
unscoped `&Reader` from an ordinary method remains part of the resource type's trusted surface; the
compiler cannot prove that the method did not publish an alias. Library authors should mark
receiver-derived views as `scoped`.

### Inline literal requirement

The block argument must be a receiver-lambda literal written at the call site. Passing a receiver
function value is an error:

```zeron
let work: (scoped &File).() -> Int = () -> size();
File.open(path, work); // error: a scoped block must be written inline
```

This is what guarantees exactly one invocation: the block is lowered into the acquired scope and is
never materialized as a value. The lowerer reuses the existing `using` acquisition and cleanup
machinery, including reverse-order disposal and cleanup on a raised effect.

`scoped` does not imply exactly-once. A stored `(scoped &File).() -> Int` is type-safe from an
escape perspective, but the callee could invoke it twice. The inline-literal rule supplies the
multiplicity guarantee without introducing `once`. A stored unscoped `File.() -> Int` is not
assignable to `(scoped &File).() -> Int` in the first place, because function parameters are
contravariant and `scoped &File` is not a subtype of `&File`.

### Failures

The call's effect row contains the acquisition effects, the block's effects, and `DisposeFailure`.

- If the body completes and disposal fails, `DisposeFailure` propagates.
- If disposal fails after the body raised, the cleanup failure is primary: `DisposeFailure` is
  raised, with the body failure preserved in its payload. The body's effect remains in the row
  because it is raised whenever cleanup succeeds. A handler for the body effect does not observe
  the body failure in the dual-failure case; the failure value is available through
  `DisposeFailure`.
- If the body fails and disposal succeeds, the body failure propagates unchanged.
- With nested blocks, an inner cleanup failure becomes the outer body's failure and is preserved in
  the outer disposal failure's payload when the outer cleanup also fails.

The disposal payload is extended to carry the preserved failure:

```zeron
public effect DisposeFailure {
    public property cause: Any?;
    public property bodyFailure: Any?;
    public property suppressed: Array<Any?>;
}
```

`bodyFailure` is the unhandled body value when cleanup also failed, and `suppressed` holds earlier
cleanup failures in nested cases. `cause` keeps its current meaning for host failures. This replaces
the handler-arm `with suppressed` clause for scoped blocks; `using` keeps the existing mechanism
until it is retired or aligned in a later proposal.

### Scope and nesting

Nested scoped blocks acquire left-to-right and dispose right-to-left. If an inner acquisition
fails, already acquired resources are disposed and the acquisition failure propagates. A scoped
block may contain loops and `if` statements; `break` and `continue` are allowed only when they target
a construct inside the block, matching ordinary lambda rules. A `return` is always rejected inside a
scoped block, because it would transfer control across the disposal boundary and the block origin
would end before the returned value could be used.

A scoped value declared inside the block cannot be assigned to a loop-carried local whose origin is
outside the block. A value tied to the block receiver may be used across iterations of a loop inside
the same block; a value tied to an inner block cannot leave that inner block.

## Compatibility and impact

- Depends on [ZEP-0160](./ZEP-0160.md) for the `scoped` type and escape checker and on
  [ZEP-0161](./ZEP-0161.md) for `scoped fn`. This proposal owns the block surface, acquisition,
  disposal, failure payload, and nesting rules.
- Additive source surface for resources that opt in by declaring a scoped entry point. Existing
  `using` code continues to compile and behave as before.
- New parser context for a scoped receiver block, a receiver type of `scoped &File`, and a check
  that the block is an inline literal. The earlier name-resolution rule that hides `this` is
  removed.
- The escape checker rejects returning, storing, capturing, and passing the receiver to an
  unscoped parameter. Ordinary member bodies remain trusted.
- The standard library adds scoped entry points for `File`, readers, writers, and other `Disposable`
  values. These are API-index changes, so `STANDARD_LIBRARY_API_VERSION` is bumped once for the
  release. The scoped modifier itself requires the ZEP-0160 schema bump; do not bump either version
  twice.
- `DisposeFailure` gains payload fields. Construction sites in the standard library are updated;
  callers that raise the effect themselves must supply the new values.
- No runtime representation change for resources; the lowering reuses the `using` cleanup path.
- Documentation: resource-management guide, collections of examples, and a migration note that
  recommends the block form without deprecating `using`.

## Alternatives

- **Keep only `using`.** Rejected as the end state, because it cannot produce a value and forces a
  mutable local. It remains supported for long-lived and multi-resource cases.
- **The earlier non-denotable receiver.** Superseded by ZEP-0160/ZEP-0161. Hiding `this` is a local
  name-resolution trick; it cannot describe a receiver-tied result, gives worse diagnostics, and
  would leave two escape mechanisms with the same name.
- **A denotable `this` with a `scoped` receiver type.** Selected. It is more expressive and reuses
  the general scoped projection.
- **Full lifetimes or ownership.** Rejected as disproportionate; the block form does not need
  general aliasing control.
- **Kotlin-style contracts to promise single invocation.** Rejected: contracts are trusted
  declarations, and they do not stop the receiver from escaping. Inline lowering gives the same
  invocation guarantee without a new contract form.
- **A `once` function type (Rust `FnOnce` analogue).** Unnecessary while blocks must be inline; it
  becomes relevant only if stored scoped blocks are allowed later. It is a separate axis from
  `scoped`.

## Implementation and validation

1. Land the ZEP-0160 scoped projection and the ZEP-0161 scoped method surface first.
2. Add the scoped block call form and recognize the receiver-lambda literal in the parser and
   resolver. Type the receiver as `scoped &File` with a block origin.
3. Reject escaping uses of the receiver with diagnostics that name the value, the escape path, and
   the block. Do not hide `this`.
4. Reject non-literal block arguments at the call site.
5. Lower the block to the existing acquire/body/dispose path, including cleanup on a raised effect
   and reverse-order nesting. Reject `return` and `break`/`continue` that target an enclosing
   construct.
6. Extend `DisposeFailure` and update the standard-library construction sites and handlers.
7. Test: escaping attempts (return, outer assignment, unscoped parameter, capture, nested receiver),
   a valid scoped helper call, a receiver-tied view, nested resources, an acquisition failure after
   a successful one, a body failure, a disposal failure, and a dual failure.
8. Confirm that `using` programs still compile and that the API index records the new entry points.

## Open questions

- Does rejecting `return` across the block break any desirable pattern, or should non-local return
  run disposal and transfer? The conservative rule is rejection.
- Should `using` be aligned to the same `DisposeFailure` payload in a later release, or keep its
  handler-arm suppression for compatibility?
- How does this interact with ZEP-0112's `Scope` and ZEP-0119's resumption points, where cleanup may
  happen while a continuation is suspended?
- Should the block receiver be `scoped &File` for every resource, or should read-only resources use
  `scoped File`? The draft uses `&File` because resource operations commonly mutate position.
- Should a resource block be callable on an explicit receiver, such as `file.open { ... }`, or only
  as a static entry point?
- Should a scoped helper be allowed to return a receiver-tied view from a temporary block receiver?
  The draft allows it only when the view is consumed inside the block.
- Is `scoped` the final spelling, or should the type qualifier and the method marker use a
  different name? See ZEP-0160 and ZEP-0161.
