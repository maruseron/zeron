## Abstract

Add a generated reference for the bundled standard library. One hand-written overview chapter explains
the module map and cross-cutting conventions, while the generator renders a page per package from the
public API index and the `///` documentation already attached to declarations. A generated index page
links the packages. Generation is deterministic, checks internal links, and can run in a check mode
that fails when the committed reference is stale or broken.

## Motivation

The guide explains the standard library through examples, but it has no complete, navigable reference.
A reader who wants to know every operation on `Stream`, the requirements of `Monad`, or which package
exports a type must open the bundled `.zn` sources or run `zeron dump --stdlib` and read terminal output.
Both are useful for maintainers and poor for readers.

The data needed for a reference already exists. Public declarations are exported to the API index,
`DocumentationExport` carries the markdown from `///` comments, and `ZeronLibraryIndexDump` already prints
both. What is missing is a stable rendering, package navigation, and a check that keeps the rendered
files synchronized with the API.

The reference is also a forcing function for documentation coverage. Standard-library declarations
already carry `///` prose in many places, but there is no report of which public declarations lack it.
Generating the reference makes that gap visible without turning naming and prose style into a compiler
concern.

## Goals

- One hand-written overview chapter, `guide/43-standard-library-overview.md`, covering the package map,
  imports, evidence and defaults, effects and failure, collections, I/O, and how the reference is
  organized.
- One generated page per package under `guide/reference/stdlib/`, including subpackages such as
  `zeron.io.text` and `zeron.serialization.json`.
- A generated index page, `guide/reference/stdlib/README.md`, listing packages with declaration counts
  and links.
- Page content generated from the public API index: declaration signatures, documentation markdown,
  members, requirements, effects, witness/default markers, and literal suffixes.
- Deterministic output: stable ordering, stable anchors, no timestamps or environment-dependent paths.
- Link validation for generated pages, including cross-package links and anchors.
- A check mode suitable for CI that reports stale generated files, broken links, and public declarations
  without documentation.
- No API-index schema change solely for documentation.

## Non-goals

- Replacing the existing conceptual guide chapters or duplicating their examples.
- Generating documentation for Java libraries, user projects, or arbitrary third-party Zeron libraries in
  the first version. The initial input is the bundled standard library.
- A hosted documentation site, search index, or JavaScript navigation.
- Enforcing prose style, doctests, or a minimum number of examples per declaration.
- Automatically publishing missing documentation. The generator reports coverage; authors still write it.
- Changing visibility, adding a public documentation-only API, or exporting private declarations to make
  the reference look complete.

## Proposal

### Output layout

```text
guide/
  43-standard-library-overview.md        hand-written
  reference/
    stdlib/
      README.md                          generated index
      zeron.collections.md               generated
      zeron.control.md                   generated
      zeron.io.md                        generated
      zeron.io.text.md                   generated
      ...
```

Package pages use the fully qualified package name as the file name so links are unambiguous and do not
depend on directory depth. The overview chapter is the only prose document in this track that is edited
by hand. Generated pages carry a header comment naming their source and the regeneration command, in the
same style as `guide/39-command-reference.md`.

`zeron.internal` and any package explicitly marked internal in the standard-library source are omitted.
The initial package set is every other package under `src/main/resources/stdlib/zeron/`, including
subpackages, with the list derived from the API index rather than hand-maintained.

### Page content

Each package page is assembled in a fixed order so that diffs stay small and readers can predict where
to look:

1. Package name and a link back to the reference index and the overview chapter.
2. Contracts, with type parameters, requirements, members, and documentation.
3. Classes, sums, products, and newtypes, with their public constructors, properties, and methods.
4. Witnesses and default witnesses, marked as such, with the contract and target they supply.
5. Top-level functions, values, and extensions, grouped by kind.
6. Literal suffixes and their factories, when the package declares any.

Declarations are grouped by kind and sorted by qualified name, with members sorted by name and then by
signature. Each declaration renders its source-level signature, including generic bounds, receiver and
mutability markers, effects, and parameter names. The body of a function is not rendered.

The documentation markdown follows the signature. A declaration without a `///` comment renders a fixed
placeholder and is counted in the coverage report rather than being hidden. Links written in `///`
comments are treated as page-relative and validated. Documentation that contains headings is allowed,
but generated headings are demoted or isolated so they cannot break the page outline.

The top of a package page may include a short package summary. Because the current API index does not
export package-level documentation, the first version keeps those summaries in a small
hand-maintained table beside the renderer, with one entry per top-level package; a subpackage uses
its parent's introduction when it has no entry of its own. A package with no entry shows only its
name. Adding a package-level export is a possible follow-up but is not required for this proposal.

### Source of truth

The renderer consumes a built API index, not parsed source files. This keeps the reference aligned with
what separately compiled consumers actually see, including default witnesses, canonical evidence, and
derived contracts. The existing `DocumentationExport` records provide the prose; no new serialized form
is introduced.

The generator must not depend on the repository's `dist/` directory or on classes produced by a previous
run. A clean invocation builds or receives an index for the bundled standard library, renders from it, and
writes only the generated pages.

### Invocation

Extend the existing `DocumentationGenerator` with a standard-library mode while keeping its current
command and manifest behavior:

```text
java -cp target/classes com.maruseron.zeron.DocumentationGenerator \
  --stdlib <api-index> --output guide
```

`<api-index>` accepts the same forms as `zeron dump`: a versioned `api-v<n>.bin`, a class directory, or
a standard-library JAR. The existing positional `guide` argument continues to regenerate the command and
manifest chapters, so release and documentation workflows have one entry point.

Check mode:

```text
java -cp target/classes com.maruseron.zeron.DocumentationGenerator \
  --stdlib <api-index> --output guide --check
```

Check mode renders into memory or a temporary directory and compares the result with the committed
pages. It fails when a generated file differs, is missing, or is orphaned after a package is removed. It
also fails on broken relative links or missing anchors. Missing `///` documentation produces a warning
and a coverage summary, not a failure, until the baseline is complete; whether to make it fatal later is
an open question.

The overview chapter and guide README are hand-maintained, but check mode validates their links into the
generated reference.

### Determinism and formatting

- Sort packages, declarations, and members with a locale-independent comparator.
- Render line endings as `\n`, independent of the host platform.
- Do not embed dates, absolute paths, versions, or host names in generated pages.
- Escape Markdown table cells and link labels so declaration names cannot break the layout.
- Generate anchors from a slugified qualified name plus a stable disambiguating suffix when two members
  would otherwise collide.
- Omit empty sections instead of emitting a heading with no content.

### CI and release integration

CI builds a standard-library index, runs the generator in check mode, and fails on stale output or broken
links. The release process does not rewrite the working tree; it runs the same check before packaging.
A maintainer regenerates locally with the documented command and commits the resulting pages together
with the source or documentation change that caused them.

## Compatibility and impact

- Source and runtime behavior are unchanged. No compiler or standard-library declaration changes.
- The API index schema does not change. The generator reads existing exports and documentation records.
- `DocumentationGenerator` gains optional modes but keeps its current default behavior.
- The guide gains one chapter and a generated reference directory. Existing chapter numbering is not
  renumbered; new chapters continue after `42-testing.md`.
- The release archive may include the generated reference if the documentation set is bundled, but the
  reference is not required at runtime.
- Contributors gain a regeneration step when they change a public standard-library declaration or its
  `///` documentation. CI enforces it, so a stale page cannot ship silently.

## Alternatives

- **Extend the conceptual guide with more tutorial chapters.** Rejected: tutorials cannot enumerate a
  large API without becoming unreadable, and they drift from signatures. The overview plus generated
  reference separates narrative from lookup.
- **Generate only from `.zn` source parsing.** Rejected as the primary source: it can disagree with the
  API index that separate compilation uses. The index is the public contract.
- **Publish only `zeron dump --stdlib` output.** Rejected: it is terminal-oriented, lacks navigation,
  anchors, and link checking, and is not a stable documentation format.
- **Add package documentation to the API index now.** Deferred: it may be worthwhile, but it would change
  the index schema and is not needed for a complete declaration reference. The overview supplies package
  narrative in the first version.
- **Serve a generated HTML site.** Rejected for this proposal: Markdown files in the repository match the
  existing guide, review well in diffs, and need no hosting or asset pipeline.
- **Make missing documentation a hard error immediately.** Rejected for the first version: the existing
  standard library has gaps, and a hard failure would either block unrelated work or invite placeholder
  prose. A warning plus coverage report makes progress visible.

## Implementation and validation

1. Add package grouping and deterministic ordering over `ZeronLibraryIndex` exports.
2. Add the Markdown renderer for package pages and the index page, reusing the notice and rendering style
   of `DocumentationGenerator`.
3. Add link and anchor validation, including links in the hand-written overview and guide README.
4. Add check mode and a coverage report for public declarations without documentation.
5. Write `guide/43-standard-library-overview.md` and link it from `guide/README.md` and `README.md`.
6. Generate the initial reference for every public package and fix documentation that renders incorrectly.
7. Add CI coverage for clean regeneration, stale output, a removed package, a broken link, and a missing
   anchor. Add a focused test that generates from a fixture index with no documentation and with
   overloaded members, then asserts stable ordering and anchors.
8. Document the regeneration command in the overview and in
   [`generated-artifacts-and-release.md`](../developer_guides/generated-artifacts-and-release.md).

Validation is a clean build, the focused generator tests, and a check-mode run against the bundled
standard library. The full suite is not required for documentation-only regeneration, but compiler or
index changes that affect exports do require it.

## Open questions

- Should the coverage report eventually become a hard error, or remain a warning with a release checklist
  item?
- Should package-level documentation become an API-index export in a later schema revision, replacing the
  overview's package table as the source of page summaries?
- Should the generated reference be included in the release archive, or only in the repository and the
  published documentation set?
- How should `@deprecated` or future stability annotations be rendered once annotation metadata is
  consumable by the index?
