## Abstract

Add `scoped` as a declaration attribute on a parameter: it promises that the callee will not let the
argument escape. `scoped` is not a type. It adds no subtype edge, no join, no top type, and no
runtime representation; it does not participate in type equality. Each scoped value carries an
internal origin token, and the checker rejects the positions where that value could outlive its
token. A scoped value is also sealed: only members declared `scoped` may be used on it. Version 1
covers parameters of functions, methods, lambdas, and function types, plus immutable locals derived
from scoped expressions. Scoped results exist only through [ZEP-0161](./ZEP-0161.md)'s `scoped fn`;
resource blocks are [ZEP-0158](./ZEP-0158.md); generic and container forms are
[ZEP-0162](./ZEP-0162.md).

## Motivation

[ZEP-0158](./ZEP-0158.md) needs a value that a caller can use but cannot retain. The language
already has a non-escape judgment for branch-scoped existential binders: ZEP-0105 rejects returns
and assignments that outlive a branch, and ZEP-0116 completes the rejection of raised-effect
payloads, escaping closures, fields, containers, and aliases. A resource receiver that must not
outlive its block is the same judgment with a different owner. Reusing that machinery keeps one
notion of escape.

The earlier draft expressed `scoped` as a type constructor, `Scoped(origin, base)`. That model
requires a new descriptor in every exhaustive type switch, a subtyping edge, variance, cross-origin
joins, a per-origin top, inference rules, and an API-index encoding for origins. None of that adds
safety over an attribute. The non-escape property belongs to the value the callee receives, not to
the value's type: an ordinary `File` and a scoped `&File` are the same type, and only the callee's
permission differs. Treating it as an attribute keeps the type system unchanged.

The feature also gives the existing reference axes a clear division of labor:

| Axis | Question | Surface | Modeling |
| --- | --- | --- | --- |
| `&` | What may this view do? | `&T` | Mutation capability in the type |
| `?` | May the value be absent? | `T?` | Nullability in the type |
| `scoped` | Where may this value go? | parameter/receiver modifier | Non-escape attribute on a declaration and its value flow |

`scoped` is not ownership, uniqueness, or a lifetime. Another alias to the same object may exist.
The attribute restricts what this binding may do and where this value may go; it does not prove that
every alias in the program is confined.

## Goals

- Add `scoped` as a modifier on parameters of free functions, methods, lambdas, and function types.
- Give each scoped value an internal origin token and reject uses that outlive it.
- Propagate the attribute to immutable local bindings initialized from a scoped expression.
- Seal scoped values: only `scoped` members are callable, and fields and properties are not readable.
- Reject the escape positions already covered by ZEP-0116, with diagnostics that name the value, the
  origin, and the escape path.
- Record the modifier in signature metadata for the API index and separate compilation.
- Erase at runtime: a scoped parameter has the same JVM descriptor as an unscoped one.
- Keep the type model unchanged: no new `TypeDescriptor`, no subtyping rule, no join, no top type.

## Non-goals

- `scoped` as a type constructor, `scoped T <: T`, or any subtype relation involving `scoped`.
- `scoped Any`, a per-origin top, cross-origin joins, covariance, or inference that synthesizes a
  scoped type.
- Scoped fields, properties, globals, statics, constructors, arrays, tuples, effect payloads, effect
  rows, reified types, annotations, or host signatures.
- Scoped type arguments, generic instantiations, containers, or type parameters; those are
  [ZEP-0162](./ZEP-0162.md).
- Scoped returns from free functions, lambdas, or blocks. Only a `scoped fn` may return a
  receiver-tied result ([ZEP-0161](./ZEP-0161.md)).
- Explicit `scoped` local type annotations. Locals acquire the attribute from their initializer.
- Ownership, uniqueness, linear or affine values, regions, named lifetimes, or a general borrow
  checker.
- `once` semantics. `scoped` answers where a value may go, not how many times it may be used.
- Proving that ordinary member bodies do not publish aliases of the receiver. That remains a trusted
  library-authoring boundary.
- Continuations and resumption. A single-bit non-escape rule would forbid the main use of a
  continuation; ZEP-0119's scope-token question is a different feature.

## Proposal

### Surface and canonical form

`scoped` precedes the type in a parameter declaration:

```zeron
fn inspect(file: scoped &File): Long = file.checksum();

fn open<T>(path: String, body: (scoped &File).() -> T): T;
```

The same modifier is allowed on a parameter of a lambda or a function type, where the target type
supplies it:

```zeron
let consume: (scoped &File) -> Long = file -> file.checksum();
```

On a `scoped fn` result, `scoped` may precede the result type, as in
`scoped fn view(): scoped Self`. A result position outside a `scoped fn` rejects it; receiver-tied
results are [ZEP-0161](./ZEP-0161.md)'s surface.

The canonical spelling is `scoped &T?`: `scoped` outermost, then `?`, then `&`. Nested or
misordered forms are rejected:

- `scoped scoped T`;
- `&scoped T` or `scoped T&`;
- `(scoped T)?` as a distinct type; `scoped T?` already scopes the whole nullable value.

`scoped` is contextual. It is recognized before a parameter type and before a `mut`/`fn` method
modifier. It remains an ordinary identifier in value position.

Version 1 restricts the base type:

- allowed: a non-generic nominal class or contract, optionally under `&` and/or `?`;
- allowed on a `scoped fn` result: `Self`, optionally under `&` and/or `?`;
- rejected: primitives, `Unit`, `Never`, `Any`, arrays, tuples, function types as the base, effect
  rows, host types, type parameters, and every generic instantiation.

A function type may itself contain a scoped parameter, as in `(scoped &File) -> T`; that scopes the
parameter, not the function value. `scoped ((&File) -> T)` is rejected.

`scoped` is not written in an ordinary local type annotation:

```zeron
let saved: scoped &File = file; // error: scoped is a parameter/receiver attribute
let alias = file;               // allowed if `file` is a scoped parameter
```

### Origin tokens

Each scoped value has an internal origin token. Tokens are compiler-internal; they are never written
in source, reified, or serialized. They support identity comparison only: there is no subtyping,
join, top, or variance between tokens.

| Origin | Introduced by | Ends when |
| --- | --- | --- |
| parameter | A scoped parameter at a call | The callee returns |
| local | An immutable local initialized from a scoped value | The local's scope ends |
| receiver | A `scoped fn` receiver ([ZEP-0161](./ZEP-0161.md)) | The receiver's scope ends |
| block | A resource block receiver ([ZEP-0158](./ZEP-0158.md)) | The block exits |

A scoped parameter is origin-polymorphic at the call site: the caller supplies a value, and the
callee receives a fresh abstract token for that parameter position. Two scoped parameters have
distinct tokens even when the caller passes the same value twice. The callee cannot combine them,
join them, or return either one as a receiver-tied result.

A local inherits its initializer's token. Passing a scoped value to another scoped parameter
preserves the caller's value; the nested callee gets its own token and cannot return it. A
receiver-tied result from a `scoped fn` carries the receiver's token, which is what lets a helper
return a view that stays tied to the same origin.

There is no `scoped Any` and no synthesized scoped type. A join that would need one is rejected with
the two origins named.

### Flow rules

Inside a body, a value is scoped when it is:

- a scoped parameter;
- a resource-block receiver ([ZEP-0158](./ZEP-0158.md));
- a local initialized from a scoped expression or from a restricted receiver;
- a receiver-tied result of a `scoped` method.

`this` inside a `scoped fn` is a restricted receiver rather than a scoped value: it keeps ordinary
member access for the method body, and only its escape positions are checked
([ZEP-0161](./ZEP-0161.md)). A local initialized from it is a scoped value and is sealed.

A scoped value may initialize only an immutable `let` binding. The binding inherits the token and is
itself sealed. A `var` initialized from a scoped value is rejected, and a scoped binding cannot be
reassigned; both rules avoid a flow merge between tokens. An ordinary value may always initialize an
ordinary binding.

An `if`, `when`, or `match` expression is scoped only when every branch is scoped with the same
token. A branch that produces an ordinary value cannot be joined with a scoped branch: that would
silently drop the restriction. Two scoped branches with different tokens are rejected because the
result would have no single origin.

Null tests and type tests preserve the attribute and the token. A cast to a supertype or to a
contract also preserves them; there is no cast that removes scopedness. Destructuring a sealed value
is not allowed in version 1; a type test is the only pattern form that may mention it.

### Sealing

A scoped value is sealed. It may be used only as:

- the receiver of a `scoped` method ([ZEP-0161](./ZEP-0161.md));
- an argument to a `scoped` parameter, including a scoped receiver parameter of a function value;
- the scrutinee of a null or type test, and an operand of referential equality (`===`, `!==`);
- a cast that preserves the attribute;
- the initializer of an immutable local.

Every other use is rejected:

- reading a field or property;
- indexing, iterating, spreading, or ranging over the value;
- calling an ordinary method or extension method;
- passing it to an unscoped parameter, including `println`, `toString`, an equality helper, or a
  type-class witness;
- passing it to an unscoped constructor parameter or a Java/host argument.

The reason is uniform: any ordinary member can retain its receiver, return an alias, or publish it
through a field. The compiler cannot inspect every body. Sealing is what makes the caller-side
promise meaningful, and it is why `scoped` is not merely a flow annotation.

A scoped method may return an ordinary independent value, such as `Long` or `String`. That value is
not sealed and may leave normally.

### Escape positions

A scoped value may not:

- be returned from a free function, a lambda, or a block whose result outlives the token;
- be assigned to an ordinary local, parameter, or field;
- be stored in a global, static, array, tuple, or generic container;
- be captured by a closure or stored as a function value;
- be raised as an effect payload or mentioned in an effect row;
- be used as a type argument, a reified type, an annotation value, or a host argument;
- be boxed into `Any` or `Any?`;
- be exposed through a declared unscoped result.

A cast that keeps the attribute is allowed but does not launder the value: `as Contract` still
produces a sealed value. There is no unsafe erasure, no checked cast that drops the attribute, and
no escape hatch through `Any`.

The diagnostic names the value, the origin, and the escape path:

```text
A scoped value from a parameter escapes through the return type.
A scoped value cannot be stored in field `cache`.
A scoped value cannot be passed to an unscoped parameter `value: Any?`.
Cannot join scoped values from different origins.
A scoped value can only be used through `scoped` members; `File.size` is not scoped.
```

### The receiver inside its own declaration

A `scoped fn` receiver is not a sealed `scoped T` value. Inside its own declaration, `this` keeps
ordinary member access and carries a non-escape restriction on escape positions. A local initialized
from `this` is a scoped value and is sealed. This is the one asymmetry in the model, and
[ZEP-0161](./ZEP-0161.md) explains why: a method body needs the type's own members, while a caller
holding a scoped value must not be able to reach them.

The non-escape check is therefore a check on the receiver value at the boundary of the method, not a
proof about the object graph. Calls to ordinary members of the same receiver are trusted internal
implementation. A library author can still defeat the guarantee from inside the type. This is the
same boundary ZEP-0158 records; the feature catches accidental returns, stores, captures, and
unscoped argument passing, not deliberate publication by the type's own implementation.

### Runtime and API index

The runtime representation is unchanged. `scoped &File` and `&File` have the same JVM descriptor;
no wrapper is allocated and no hidden parameter is added.

A scoped parameter or result is part of the signature for separate compilation. The API index must
record:

- the scoped flag on each parameter and result position;
- that the flag is invariant between function signatures (a stored function with an unscoped
  parameter cannot satisfy a scoped parameter requirement);
- that no runtime descriptor or origin identity is serialized.

`API_INDEX_SCHEMA_VERSION` is bumped once when the feature lands. The bump is shared with
[ZEP-0184](./ZEP-0184.md)'s self result marker and [ZEP-0161](./ZEP-0161.md)'s method flag; do not
bump the schema twice in one release cycle. `STANDARD_LIBRARY_API_VERSION` is bumped once when a
standard-library signature uses the modifier.

Scoped parameters do not cross the host boundary. An `external` declaration, Java method, Java
field, Java constructor, SAM conversion, or `unsafe` host access may not mention `scoped`. A Java
caller cannot honor the non-escape promise.

## Compatibility and impact

- Additive syntax. `scoped` is a contextual modifier in parameter position and remains an ordinary
  identifier elsewhere.
- No source break for existing code. Existing signatures are unscoped.
- The parser, formatter, highlighter, LSP, API index, and separate-compilation reader need the
  modifier. The type model does not gain a descriptor.
- The flow analyzer and escape checker reuse the ZEP-0116 contexts: returns and assignments,
  raised-effect payloads, escaping closures, fields, containers, and aliases.
- `TypeCompatibility` does not change for scopedness. Signature compatibility compares the flags
  separately, so an unscoped function value cannot satisfy a scoped parameter requirement.
- No runtime representation change. `javap` descriptors for scoped and unscoped parameters are
  identical.
- Documentation: references and mutation, lambdas and function values, resource management, and
  Java interoperability chapters need the modifier once it ships.

## Alternatives

- **The earlier `ScopedDescriptor` type wrapper.** Rejected: it requires a new descriptor in every
  exhaustive switch, a subtyping edge, variance, joins, a per-origin top, inference rules, and an
  origin encoding in the API index, while adding no safety over an attribute. The non-escape
  property is a property of the value binding, not of the type.
- **A boolean without origin tokens.** Rejected: a scoped method could return a scoped parameter
  from a different origin, and the checker could not tell it apart from a receiver-tied result.
- **`scoped T <: T` with a flow-sensitive alias checker.** More ergonomic inside a body, but it
  requires interprocedural alias tracking and a much larger checker. Rejected for version 1.
- **Type-level origins or named regions.** Rejected: that is a lifetime system under another name,
  disproportionate for resource handles and receiver views.
- **`once` or linear types.** A different axis. A scoped value may be used any number of times
  while its origin is live.
- **Type-level `scoped Any`.** There is no scoped type lattice in version 1, so there is no top.

## Implementation and validation

1. Extend the parameter grammar with the contextual `scoped` modifier and validate the base type and
   canonical `scoped &T?` form. Reject it in local type annotations and on generic instantiations,
   arrays, primitives, `Any`, and type parameters.
2. Attach the scoped flag to parameter and result signatures without adding a `TypeDescriptor`.
   Compare the flag separately in function-signature compatibility and export it to the API index.
3. Add origin tokens to the flow state for parameters, locals, receivers, and blocks. Bind a local
   only with `let`; reject scoped `var` initialization and reassignment; reject mixed or
   multi-token branch joins.
4. Extend `ExpressionFlowResolver`, `StatementResolver`, `RaisedEffectFlow`, and the compound-result
   check with the new tokens. Reject every escape position and report the origin.
5. Implement sealing in member resolution: on a sealed value, accept only `scoped` methods and the
   allowed tests; reject fields, properties, indexing, iteration, and ordinary members.
6. Record the flags in the API index and the separate-compilation reader. Reject scoped parameters
   in host signatures.
7. Update the formatter, highlighter, LSP, and completion.
8. Test: parameter passing and local flow; `let` versus `var`; same-token and cross-token joins;
   null and type tests; every escape position; sealing against each member kind; scoped-parameter
   function values and their invariant flag matching; API-index round trips; separate compilation;
   and unchanged JVM descriptors.

## Open questions

- Should explicit scoped local annotations be added later? Version 1 uses flow from an initializer so
  there is one way to acquire the attribute.
- Should a scoped value be allowed in a local `yield` or value block that stays within the same
  origin? Version 1 treats the block result as an escape and rejects it.
- How should `using` and ZEP-0112's `Scope` handles adopt scoped receivers once the block form
  lands? That is follow-up work for ZEP-0158.
- Does ZEP-0119's continuation escape question need a named scope token rather than this attribute?
  Version 1 assumes yes and does not claim to solve it.
- Should an ordinary value be explicitly convertible into a scoped local, rather than acquiring the
  attribute only from a scoped initializer? Version 1 keeps acquisition implicit at call and
  receiver boundaries.

## Decision

Accepted 2026-11-27. `scoped` is a declaration attribute with an internal, identity-only origin
token, not a type constructor. Version 1 covers parameters and immutable locals, seals scoped values
to `scoped` members, and rejects every escape position. Receiver-tied returns belong to
[ZEP-0161](./ZEP-0161.md); generic and container forms belong to
[ZEP-0162](./ZEP-0162.md). The design reuses the existing escape checker and adds no type descriptor.
