## Abstract

Introduce `scoped T` as a restriction qualifier on a value: an ordinary `T` may be viewed as a
`scoped<o> T`, but a `scoped<o> T` may not be used as its base `T` outside the origin `o`. The
qualifier is covariant, carries an origin, and is enforced by the same escape judgment that already
rejects branch-scoped existential binders. It gives resource handles, receiver-tied views, and
library callbacks a reusable non-escape capability without lifetimes, ownership, or a borrow
checker. Version 1 exposes only a narrow surface: non-generic nominal class and contract values,
their `&`/`?` wrappers, parameters, receivers, and locals. Generic containers, arrays, type
parameters, fields, effect payloads, host interop, and scoped returns from free functions are
rejected until [ZEP-0162](./ZEP-0162.md) defines their rules.

## Motivation

[ZEP-0158](./ZEP-0158.md) originally made a resource receiver non-denotable so the caller's block
could not store, return, pass, or capture the handle. That works for one call form, but it is a
name-resolution trick rather than a language capability. It gives poor diagnostics, cannot describe
a receiver-tied return, cannot be reused by builder blocks or scope handles, and does not compose
with `&` or `?`.

Zeron already has an escape judgment for branch-scoped existential binders. ZEP-0105 rejects returns
and assignments that outlive a branch, and ZEP-0116 completes the rejection of raised-effect
payloads, escaping closures, fields, containers, and aliases. A value that must not outlive a
dynamic extent is the same kind of judgment with a different owner. Reusing that vocabulary keeps
one notion of escape instead of adding a second.

The feature also makes the existing reference axes easier to explain:

| Axis | Question | Surface | Direction |
| --- | --- | --- | --- |
| `&` | What may this view do? | `&T` | Mutation permission; `&T` is a read/write view of `T` |
| `?` | May the value be absent? | `T?` | `T <: T?` |
| `scoped` | Where may this value go? | `scoped T` | `T <: scoped T`; no `scoped T <: T` |

`scoped` is not ownership, uniqueness, or a lifetime. A caller may keep another alias to the same
object. The qualifier restricts what this view may do and where it may go; it does not prove that
every alias in the program is confined.

## Goals

- Add `scoped T` as a covariant restriction qualifier with an origin.
- Define `T <: scoped<o> T`, `scoped<o> T <: scoped<o> U` when `T <: U`, and no narrowing back to
  `T`.
- Define a small origin set: a receiver origin for `scoped fn`, a caller-supplied origin for
  scoped parameters, and a block origin for resource blocks.
- Reject cross-origin joins. Give each origin its own `scoped<o> Any` top, without treating `Any`
  as a useful inference target.
- Reuse the escape contexts and diagnostic style of ZEP-0105 and ZEP-0116: returns, outer
  assignments, raised effects, escaping closures, fields, containers, and library boundaries.
- Define the version-1 appearance restriction: non-generic nominal classes and contracts, with
  optional `&` and `?`, in parameters, receivers, and locals.
- Define a canonical form and normalization so `scoped`, `&`, and `?` cannot be nested
  arbitrarily.
- Make the feature erase at runtime. `scoped &File` has the same JVM representation as `&File`.
- Record the type in the API index and separate-compilation format without reifying the origin.
- Keep host interop and generic containers out of version 1.

## Non-goals

- Named regions, lifetime parameters, ownership transfer, uniqueness, or a general borrow checker.
- `scoped T <: T`, an unchecked cast back to the base type, or an escape hatch through `Any`.
- Automatic container scoping, scoped type arguments, or `scoped Any` as a universal join; those
  are [ZEP-0162](./ZEP-0162.md).
- Scoped fields, globals, effect payloads, reified types, annotations, or host signatures.
- Scoped returns from free functions. Version 1 has only receiver-origin returns through
  [ZEP-0161](./ZEP-0161.md).
- `once` or linear/affine values. `scoped` answers “where may this go?”, not “how many times may
  this be used?”.
- Storing or resuming continuations. A single-bit non-escape qualifier would forbid the main use of
  a continuation; the scope-token question in ZEP-0119 is a different feature.
- Proving that ordinary member bodies do not publish aliases. That remains a trusted
  library-authoring boundary.
- Changing the runtime representation of classes, contracts, references, or functions.

## Proposal

### Surface and canonical form

`scoped` is a contextual modifier at the start of a type:

```zeron
fn inspect(file: scoped &File): Long = file.size;

fn open<T>(path: String, body: (scoped &File).() -> T): T;
```

The canonical spelling is `scoped &T?`, with `scoped` outermost, then `?`, then `&`. The
normalized descriptor is `Scoped(origin, Nullable(Reference(T)))`; the printer emits
`scoped &T?`. The following are rejected:

- `scoped scoped T`;
- `&scoped T`;
- `scoped T&` or any order that puts `&` outside `scoped`;
- `(scoped T)?` as a distinct type. `scoped T?` already means the whole nullable value is scoped.

An origin is not written in source in version 1. It is inferred from the declaration or expression
that introduces the value. Internal types may be written as `scoped<o> T` in this document, but the
surface is always `scoped T`.

### Origins

A scoped value is tied to one origin. Version 1 recognizes three forms:

| Origin | Introduced by | Ends when | May be returned? |
| --- | --- | --- | --- |
| `receiver` | A `scoped fn` receiver | The receiver's scope ends | Yes, as a receiver-origin result from the same method |
| `argument(i)` | A scoped parameter at a call site | The callee returns | No |
| `block` | A resource block receiver | The block exits | No |

A local scoped alias inherits the origin of a scoped initializer. Initializing a scoped local from
an unscoped value creates a new origin at the local's scope; the view is then restricted to that
local and cannot escape it. A scoped local must be initialized at its declaration. An uninitialized
scoped local is rejected because its origin would be unknown.

A scoped parameter is origin-polymorphic: the caller supplies the origin, and the callee treats it
as abstract. The callee cannot assume it outlives the call, so it cannot return the parameter.
Two scoped parameters may have different origins. The callee may pass each to another scoped
parameter, but it may not combine them into one value, container, or join.

A receiver origin belongs to the receiver expression. In version 1 the receiver of a `scoped fn`
must be a stable receiver: `this`, a parameter, a local, or an already-scoped value. Calling a
`scoped fn` on a temporary or an arbitrary expression is rejected when the result would be bound
beyond that expression's extent. This avoids inventing a lifetime for a temporary.

### Subtyping

The core rules are, for unscoped base types `T` and `U`:

```text
T                     <: scoped<o> T
scoped<o> T           <: scoped<o> U        when T <: U
scoped<o> &T          <: scoped<o> T
scoped<o> T           <: scoped<o> T?
scoped<o> T           <: scoped<o> Any
scoped<o> T           <: scoped<o> Any?
```

Nested wrappers are normalized before these rules apply; `scoped<o> scoped<o> T` is rejected rather
than treated as a second restriction.

The forbidden edges are equally important:

```text
scoped<o> T           !<: T
scoped<o> T           !<: Any
scoped<o> T           !<: scoped<o'> T    when o != o'
scoped<o> Any         !<: Any
```

`T <: scoped<o> T` is a widening into a restricted view. It says an ordinary value may be used where
a non-escaping view is expected. It does not say a scoped view may be used as the ordinary value.
`scoped<o> Any` is the top only of the types with origin `o`. It is not a universal top, and
`scoped<o1> Any` is unrelated to `scoped<o2> Any`.

`Any` remains the top of the unscoped hierarchy. Because `scoped<o> Any` is not a subtype of `Any`,
`Any` is no longer a top for every type. This is intentional. The compiler must not restore the old
behavior by boxing a scoped value into `Any`.

### Type arguments, containers, and other bases

Version 1 restricts what `scoped` may wrap:

- allowed: a non-generic class or contract type, optionally under `&` and `?`;
- allowed: `Any`, only as the formal `scoped Any` top;
- rejected: primitives, `Unit`, `Never`, arrays, tuples, function types as the scoped base, effect
  rows, host types, type parameters, and every generic instantiation.

A function type may contain a scoped parameter or receiver, as in `(scoped &File) -> T`; that scopes
the parameter, not the function value. `scoped ((&File) -> T)` is rejected.

The reason for rejecting generic instantiations is not convenience. A `scoped Box<&File>` would
still expose `get(): &File`, and a `scoped Array<&File>` would still expose its elements. The
qualifier on the whole container does not confine values read out of it. Version 1 avoids the hole
by rejecting the whole-container form. [ZEP-0162](./ZEP-0162.md) defines the propagation rules that
make containers safe.

The same restriction applies to type arguments. `Box<scoped T>`, `Option<scoped T>`, and
`Array<scoped T>` are rejected, including when inference would create them. A generic function may
take a scoped **concrete** parameter, such as `scoped &File`, and may return an unrelated unscoped
`T`; it may not infer `T` as a scoped type.

### Escape

A scoped value may be:

- read, written, and called through its ordinary members;
- passed to a scoped parameter, preserving the origin;
- passed to a `scoped fn` receiver of the same origin;
- assigned to a scoped local with the same origin, or to a new scoped local initialized from an
  unscoped value;
- compared, tested, or converted to an ordinary value by a member that returns an ordinary value;
- returned only from a `scoped fn` when the result carries the receiver origin.

A scoped value may not be:

- returned from a free function, a block, or a lambda whose result scope outlives the origin;
- assigned to an unscoped local or parameter, including `Any` and `Any?`;
- stored in a field, global, static, array, tuple, or generic container;
- passed to an unscoped parameter, including `println(value)` and other `Any?`-taking helpers;
- captured by a closure or function value that outlives the current scope;
- raised as an effect payload or used in an effect row;
- used as a type argument, reified type, annotation value, or host argument;
- cast to its base type. There is no `as` escape and no unsafe erasure.

The diagnostic names the scoped value, the escape path, and the origin. For example:

```text
A scoped value from a resource block escapes through the return type.
A scoped value cannot be passed to an unscoped parameter `value: Any?`.
Cannot join scoped values from origins `block` and `parameter(0)`.
```

### Joins and `ensureCommonParent`

The existing common-parent fallback to `Any` must not apply when a scoped value is involved.
Version 1 uses these rules:

- same origin: join the bases covariantly and wrap the result;
- different origins: reject the join, even when the bases have a common parent;
- scoped and unscoped: the unscoped value may widen into the scoped origin only when an expected
  scoped type supplies that origin; inference does not silently scope an unscoped value;
- a join whose only common base is `Any` is rejected unless the source explicitly names
  `scoped Any`. The compiler does not synthesize `scoped Any` as an inferred type.

The last rule is deliberate. `Any` is a poor program value and `scoped Any` is even less useful.
The formal top exists so the subtype relation is complete, not so inference can invent meaningless
types.

### Members, mutation, and flow

`scoped T` exposes the members of `T`. A `scoped &T` may call mutating members; a `scoped T` may
only call read-only members. `&T <: T` and covariance give `scoped &T <: scoped T`, so a mutable
scoped view can be used where a read-only scoped view is expected.

Flow typing preserves the scoped wrapper. A null test on `scoped T?` narrows to `scoped T`; a type
test narrows to a scoped subtype; no flow rule may narrow a scoped value to its unscoped base. A
cast that would remove the wrapper is rejected.

Member results follow their declared types. An ordinary method that returns `T` from a `scoped T`
receiver returns an ordinary `T`, not a scoped `T`. A method that returns a receiver-tied non-`Self`
view must declare it as `scoped` in a `scoped fn`; direct `Self`, `&Self`, and `Self?` results are
propagated automatically. See [ZEP-0161](./ZEP-0161.md). The compiler does not track aliases
reachable through ordinary members, fields, or containers. A resource type whose ordinary API
publishes an alias remains a trusted library-authoring concern. This is the same boundary that
ZEP-0158 records in its non-goals.

### Function types

A scoped receiver or parameter inside a function type follows ordinary function subtyping:

```text
(scoped<o> T) -> U          <:  (T) -> U
(T) -> U                    !<:  (scoped<o> T) -> U
(scoped<o> T) -> scoped<o> U !<:  (scoped<o> T) -> U
```

The first edge is the safe direction: a function that accepts only a scoped argument can be used
where a function accepting any `T` is expected, because `T <: scoped<o> T`. The second is the
escape: an ordinary function might store its argument, so it cannot satisfy a scoped requirement.
The third is result covariance: a scoped result cannot be used as an unscoped result, because
`scoped<o> U` is not a subtype of `U`.

These rules are load-bearing for `scoped fn` conformance and for the inline-literal rule in
ZEP-0158. A stored `File.() -> T` is not assignable to `(scoped &File).() -> T`, because that would
require `scoped &File <: &File`.

A function type whose result is scoped is rejected in version 1. A function value has no receiver
origin, and a free-function scoped return has no bindable origin either; only a `scoped fn` method
supplies one. `() -> scoped &File` is therefore not a valid type.

### Interop and runtime

Scoped types do not cross the host boundary. An `external` declaration, Java method, Java field,
Java constructor, SAM conversion, or `unsafe` host access may not mention `scoped`. A scoped value
may not be boxed into a Java collection or passed to a Java callback. The host sees the base type,
but the source boundary rejects the scoped view before it reaches the host.

The runtime representation is unchanged. `scoped &File` erases to the same descriptor as `&File`;
the origin is not reified and no wrapper is allocated. The API index records the scoped modifier
and a relative origin marker (`receiver`, `parameter`, `block`) so separate compilation can
reconstruct the signature without exposing a local identity.

### API index and separate compilation

A public `scoped` parameter, receiver, or `scoped fn` result is part of the API surface. The API
index must record:

- the scoped modifier on the type;
- whether the origin is the receiver, a parameter, or a block-relative result;
- that a scoped type is not host-visible;
- that the type has no runtime descriptor of its own.

`API_INDEX_SCHEMA_VERSION` is bumped once when the feature lands. `STANDARD_LIBRARY_API_VERSION` is
bumped once when a standard-library signature uses `scoped`. The two bumps are coordinated with
ZEP-0158 and ZEP-0161 so the release cycle does not bump either version twice.

## Compatibility and impact

- Additive syntax. `scoped` is a contextual modifier in type position and remains an ordinary
  identifier elsewhere.
- No source break for existing code. The new restriction is opt-in.
- The parser, resolver, formatter, highlighter, LSP, API index, and separate-compilation reader all
  need the modifier. The type model adds a wrapper that must participate in equality, substitution,
  canonicalization, and every exhaustive switch.
- `TypeCompatibility` must handle `scoped` before it strips `&` and `?`. The current ad-hoc
  assignability and the `Any` fallback in `ensureCommonParent` are the two places most likely to
  reopen the escape hole.
- No runtime representation change. `javap` descriptors for scoped and unscoped forms are
  identical.
- Documentation: references and mutation, lambdas and function values, resource management, and
  Java interoperability chapters need the new qualifier once it ships.

## Alternatives

- **Non-denotable receiver only.** This is ZEP-0158's original design. Rejected as the general
  feature: it is local to one call form, cannot describe a receiver-tied result, and produces worse
  diagnostics.
- **`scoped T <: T` plus a flow-sensitive escape checker.** More ergonomic inside a body, but it
  requires interprocedural alias tracking and a much larger checker. Rejected for version 1.
- **A boolean `scoped` without an origin.** Simpler, but it cannot distinguish a receiver-tied
  result from a block handle and cannot reject cross-origin joins. Rejected.
- **`scoped Any` as an ordinary top.** This would make `let x: Any = this` compile and destroy the
  guarantee. Rejected.
- **A full lifetime or region system.** Disproportionate for resource handles and receiver views.
  Named regions remain a possible later feature.
- **`once` / linear types.** A different axis. See ZEP-0158 and the open questions.

## Implementation and validation

1. Add a `ScopedDescriptor` carrying a base and a relative origin. Normalize to one canonical
   wrapper and reject nested or misordered forms.
2. Extend the type parser and resolver for the contextual `scoped` modifier. Reject it on generic
   instantiations, arrays, primitives, and type parameters, and in type arguments, fields, globals,
   effect payloads, reified types, annotations, free-function results, and host signatures.
3. Add origin inference for parameters, receivers, locals, and resource blocks. Reject
   uninitialized scoped locals and conflicting assignments.
4. Extend the escape checker with the ZEP-0116 contexts. Preserve the wrapper through flow typing,
   null tests, and type tests. Reject casts and `Any` boxing.
5. Update `TypeCompatibility`, `ensureCommonParent`, substitution, equality, formatting, the API
   index, the LSP, and the highlighter. Do not let `Any` remain a fallback for scoped values.
6. Update function-type subtyping and the conformance checks used by ZEP-0161.
7. Test: both subtype directions; covariance; `scoped &T <: scoped T`; no `scoped T <: T`; no
   `scoped T <: Any`; same-origin `scoped Any`; cross-origin join rejection; every escape position;
   valid member access and scoped-parameter passing; invalid `println(this)`, return, field store,
   capture, container, effect payload, and host call; formatter and API-index round trips;
   separate-compilation reconstruction; and unchanged JVM descriptors.

## Open questions

- Is `scoped` the best final spelling, or should the qualifier be named `borrowed`, `confined`, or
  `noescape` to avoid overloading “scope” with `using`, `Scope`, and branch scopes?
- Should version 1 allow local scoped aliases, or only parameters, receivers, and block handles?
  The draft allows locals because they are useful for `let header = readHeader()` inside a block.
- Should `scoped Any` be user-writable, or only an internal join type? The draft allows explicit
  same-origin annotations but never synthesizes it.
- Should a scoped value be allowed in a local `yield` or value block that stays within the same
  origin? The draft treats the origin, not the syntax, as the boundary.
- How should `using` and ZEP-0112's `Scope` handles adopt scoped receivers once the block form
  lands?
- Does ZEP-0119's continuation escape question need a named scope token rather than this qualifier?
  The draft assumes yes and does not claim to solve it.
