# ZEP-0161: Scoped Receiver Methods

## Abstract

Add `scoped fn` and `scoped mut fn` as per-method declaration modifiers on classes. A `scoped fn`
promises that the method will not let its receiver escape. Inside the body, `this` is the ordinary
receiver with a non-escape restriction. A receiver-tied result is written `scoped Self`,
`scoped &Self`, `scoped Self?`, or `scoped &Self?`; a plain `Self` result is an ordinary same-type
result that may be a new object. A value that is itself scoped — a scoped parameter, a scoped local,
or a resource-block receiver — is sealed and may call only `scoped` methods
([ZEP-0160](./ZEP-0160.md)). The canonical order is
`public scoped mut fn`. Version 1 excludes generic classes, properties, constructors, free-function
scoped returns, and host export. Contract requirements, contract defaults, overrides, and extension
methods are [ZEP-0185](./ZEP-0185.md).

## Motivation

[ZEP-0158](./ZEP-0158.md) needs checked helpers on a resource type. The caller holds a sealed
`&File` and must be able to read a header or a checksum, but the helper's body needs the type's own
fields and members. A `scoped` receiver marker splits those two views cleanly: the caller is
restricted, the implementation is not.

The earlier draft made the receiver a `scoped Self` value and said it exposed the ordinary members
of `T`. Those two statements cannot both hold. If a `scoped T` exposes ordinary methods, a caller
can pass the value to a method whose body stores the receiver, and the non-escape promise is gone.
The sound rule is that a scoped value exposes only `scoped` members. This proposal keeps that rule
for every scoped value a caller can hold, and it does **not** type `this` as a scoped value inside
its own declaration. The receiver is an ordinary receiver with a boundary check on escape; the
caller is the party that needs sealing, and the implementation is the party that needs member access.

`Self` ([ZEP-0184](./ZEP-0184.md)) supplies the receiver's type name, and `scoped` supplies the
receiver tie. Inside a `scoped fn`, `scoped Self` is a receiver-tied view, while plain `Self` is an
ordinary value of the same type — including a newly constructed one. That distinction lets a scoped
method return a fresh instance without pretending it is receiver-tied, and it keeps the meaning of
`Self` the same as it is in an ordinary method.

A per-method marker also composes with `mut`:

| Concern | Type surface | Declaration surface | Generic admissibility |
| --- | --- | --- | --- |
| Mutation | `&T` | `mut fn` | `T admits mutable` |
| Absence | `T?` | — | `T admits nullable` |
| Escape | scoped value attribute | `scoped fn` | `T admits scoped` ([ZEP-0162](./ZEP-0162.md)) |

A `scoped extension` would scope a container rather than a receiver and result. It would have to
answer whether every method is scoped, and it would not compose with contract requirements. It is
rejected; the extension form is [ZEP-0185](./ZEP-0185.md).

## Goals

- Add `scoped fn` to class methods.
- Add `scoped mut fn` for a mutable receiver; the canonical order is `public scoped mut fn`.
- Give `this` a non-escape restriction in the body while retaining ordinary member access.
- Make explicit `scoped Self`, `scoped &Self`, `scoped Self?`, and `scoped &Self?` results
  receiver-tied.
- Keep a plain `Self` result an ordinary same-type result, including a newly constructed value.
- Allow an explicit scoped result for a receiver-derived non-`Self` view.
- Enforce sealing: a scoped value may call only `scoped` methods.
- Require a stable receiver when a receiver-tied result is bound.
- Record the method and result flags in the API index and separate compilation.
- Keep runtime representation unchanged.

## Non-goals

- Contract requirements, contract defaults, class overrides of defaults, and extension methods.
  [ZEP-0185](./ZEP-0185.md) owns those declaration contexts.
- `scoped extension` or any container-level scoping declaration.
- Scoped constructors, fields, globals, properties, or property getters.
- Scoped methods on generic classes; [ZEP-0162](./ZEP-0162.md) owns their admissibility.
- Scoped methods on free functions, local functions, or nested functions.
- Scoped returns from free functions, including a return of a scoped parameter.
- Multiple receiver origins, named regions, lifetime parameters, or ownership transfer.
- `once`, linear values, or use-after-disposal checking.
- Host interop, Java SAM conversion, or exporting scoped methods to Java.
- Overloading a method solely by `scoped` or by receiver scope.
- Proving that ordinary member bodies do not publish aliases of the receiver.
- `Self` in contract parameters; [ZEP-0184](./ZEP-0184.md) restricts contract `Self` to results.

## Proposal

### Syntax and modifier order

`scoped` is a contextual modifier before `mut` and `fn`:

```zeron
public scoped fn checksum(): Long = ...;
public scoped mut fn readLine(): String = ...;
```

The canonical order is `public scoped mut fn`. A `scoped fn` has a read-only receiver; a
`scoped mut fn` has a mutable receiver. `static fn` cannot be scoped because it has no receiver. A
constructor cannot be scoped. A property getter or setter cannot be scoped in version 1; a
receiver-tied property is written as a `scoped fn` until property conformance is designed.

`scoped` is allowed on a class method. It is not allowed on a local or nested function declaration,
on a free function, or on an extension in this proposal.

### Receiver semantics

Inside a `scoped fn`, `this` is the ordinary receiver and carries a non-escape restriction:

```zeron
public class File {
    public scoped fn checksum(): Long = hash(readBytes(4096));
    public scoped mut fn readLine(): String = ...;
}
```

In both bodies:

- unqualified member access resolves against the receiver, as in any method;
- `this` is a valid expression and keeps ordinary member access;
- `this` may be passed to another `scoped` parameter or receiver of the same origin;
- `this` may not be returned as an unscoped value, stored in a field or container, captured by an
  escaping closure, raised as an effect payload, or passed to an unscoped parameter;
- a local initialized from `this` is a scoped value and is sealed;
- nested receiver lambdas may qualify the receiver as `File.this`; the qualified expression has the
  same restriction, and an escaping closure still cannot capture it.

The receiver is **not** a scoped value and is not typed as one; `scoped Self` is a result spelling,
not the receiver's own type. If the receiver were sealed, it would forbid `readBytes(4096)` and
every other ordinary member the body needs, and a scoped method could only call other scoped
methods. The split is deliberate: the caller holding a scoped value is sealed; the method's own body
is not.

This is the trusted-member boundary. A call to an ordinary member of the same receiver is trusted
internal implementation and may publish the receiver; the compiler does not inspect its body. The
feature catches accidental `return this`, `global = this`, `list.add(this)`, and `() -> this` in the
checked body, not deliberate publication by the type's own implementation. ZEP-0158 records the same
boundary.

### Sealed values and the call rule

A value with the scoped attribute — a scoped parameter, a scoped local, or a resource-block receiver
— is sealed by [ZEP-0160](./ZEP-0160.md). On a sealed value:

- a `scoped` method of the value's static type is callable;
- a `scoped mut fn` is callable only when the sealed value is a mutable view (`&T`);
- an ordinary method, extension method, field, or property is not callable or readable.

```zeron
fn inspect(file: scoped &File): Long =
    file.checksum() + file.readLine().size; // both must be scoped methods

File.open(path) { this }; // error: the block receiver is sealed and the result is unscoped

fn inspect(file: scoped &File): Long = file.size; // error: `size` is not scoped
```

A `scoped fn` is callable on an ordinary receiver as well as on a sealed receiver. Calling it on an
ordinary receiver creates a receiver token for the call. Calling it on a sealed receiver preserves
that value's token, so a receiver-tied result stays tied to the same origin.

A method may not be overloaded solely by `scoped` or by receiver scope. It has the same name and
parameter list as the unscoped form, so the existing duplicate-member rule applies.

### Receiver-tied results

A receiver-tied result is written with `scoped` on the result type:

```zeron
public class File {
    public scoped fn selfView(): scoped Self = this;             // receiver-tied
    public scoped mut fn mutableView(): scoped &Self = this;     // receiver-tied mutable view
    public scoped fn maybeSelf(): scoped Self? = ...;            // receiver-tied nullable view
    public scoped fn readerView(): scoped &Reader = this.reader; // receiver-tied non-Self view
    public scoped fn checksum(): Long = ...;                     // ordinary Long
}
```

`scoped` is the only marker of a receiver tie. A plain `Self` result is an ordinary same-type
result:

```zeron
public class File {
    public scoped fn copy(): Self = new File(path); // allowed: a new value of the same type
    public scoped fn leaked(): Self = this;         // error: returns the receiver as an ordinary value
}
```

Returning `this` as an ordinary result is an escape. The diagnostic should point at the `this`
expression and suggest `scoped Self` when that is the intended result:

```text
A scoped method cannot return its receiver as an ordinary result.
Write `scoped Self` for a receiver-tied view, or return an independent value.
```

`scoped` is allowed only on a result of a `scoped fn`, and only on a type version 1 can scope. It may
appear on `Self`, `&Self`, `Self?`, and `&Self?`, and on a non-`Self` view such as `scoped &Reader`.
The returned expression must be rooted at the receiver: `this`, a member of `this`, a call on
`this`, or another expression that carries the receiver token. A `null` literal is allowed for
`scoped Self?` and `scoped &Self?`; it carries no alias. A value with no receiver involvement is
rejected. The provenance is otherwise trusted: the compiler enforces the token flow and non-escape,
but cannot prove that the member is actually owned by the receiver.

A plain `Self` result that returns a receiver-derived member, such as `this.root`, is treated like
any other ordinary member result and remains part of the trusted-member boundary. The compiler does
not infer a receiver tie from the type name; an author who needs the tie writes `scoped Self`. A
future lint may warn when a plain result is visibly a member of `this` and has a reference type; it
should stay a warning, because a member may return an independent value.

`scoped Self` is the preferred spelling for a receiver-tied result of the receiver's own class;
`scoped File` is equivalent and may be used where the explicit name is clearer. Generic
instantiations such as `scoped Option<Self>` are rejected in version 1 and deferred to
[ZEP-0162](./ZEP-0162.md).

A method may itself be declared `scoped` while returning an ordinary result. The marker still
promises that the receiver did not escape; the result is an independent value such as `Long`,
`String`, or a newly constructed `Self`.

### Receiver stability

A receiver-tied result may be bound only when the receiver is stable: `this`, a parameter, a local,
or an already-scoped value. A temporary receiver has an extent that ends with the expression, so its
receiver-tied result may be consumed immediately but not bound or returned:

```zeron
let file = File.openPath(path);
let header = file.headerView();     // allowed: `file` is a local

let header = makeFile().headerView(); // rejected: binding a temporary's receiver-tied result
let n = makeFile().checksum();        // allowed: the result is an ordinary Long
use(makeFile().headerView());         // allowed: consumed within the same expression
```

A field or index expression is treated as a temporary receiver for this rule unless it is itself a
sealed value. Version 1 rejects the binding rather than inventing a lifetime extension.

### Interaction with `mut`, properties, and dispatch

- `scoped fn` receives a read-only receiver; `scoped mut fn` receives a mutable receiver.
- A sealed `&T` can call both read-only and mutating scoped methods. A sealed `T` can call only
  read-only scoped methods.
- Properties are not scoped in version 1. A receiver-tied property should be a `scoped fn`.
- `scoped` does not change visibility, dispatch, or method identity.
- A `scoped fn` may call ordinary members of its own receiver, other scoped methods, and scoped
  parameters. It may not pass `this` to an unscoped parameter.

### API index and runtime

The API index records:

- the `scoped` modifier on the method;
- the scoped flag on each parameter and on the result;
- for a scoped result, that it is receiver-tied (`receiver`), not an absolute origin identity;
- that the modifier is not host-visible.

No absolute scope identity is serialized. `API_INDEX_SCHEMA_VERSION` is bumped once when the feature
lands, shared with [ZEP-0184](./ZEP-0184.md), [ZEP-0160](./ZEP-0160.md), and
[ZEP-0185](./ZEP-0185.md); do not bump it twice. `STANDARD_LIBRARY_API_VERSION` is bumped once when a
standard-library method uses `scoped`.

The runtime representation is unchanged. A `scoped fn` is emitted as an ordinary method whose
receiver is the first argument. `scoped` adds no hidden parameter, wrapper, or descriptor.

Scoped methods are not exported to Java and do not participate in SAM conversion. A Java caller
cannot express or honor the non-escape promise.

## Compatibility and impact

- Additive declaration modifier. Existing methods are unchanged.
- `scoped` is a contextual modifier before `mut`/`fn`; it remains an ordinary identifier elsewhere.
- The parser, formatter, highlighter, LSP, API index, and separate-compilation format need the
  modifier and the result flag.
- No runtime representation change and no new method descriptor.
- Documentation: classes, lambdas and receiver functions, and resource management need the method
  form, the sealing rule, and the `scoped Self` result rule.

## Alternatives

- **Type `this` as `scoped Self`.** Rejected: a scoped value may call only scoped methods, so the
  body could not call `readBytes`, read a field, or use most of the type's API. The sound split is a
  sealed caller value and an ordinary, escape-restricted receiver in its own declaration.
- **Automatic `Self` propagation.** Rejected: it conflates “same type” with “same origin”, rejects
  a safe `scoped fn copy(): Self = new File(...)`, and makes `Self` mean different things inside and
  outside a `scoped fn`. The explicit `scoped Self` form keeps one meaning for `Self` and makes the
  receiver tie visible at the signature.
- **A boolean receiver flag without a result marker.** Rejected: the method still needs to say which
  results are receiver-tied, and `scoped Self` is that declaration.
- **A separate scoped function type for methods.** Rejected: methods already have receiver function
  types; a second representation would complicate overrides, callable references, and the API index.
- **Allow scoped returns from free functions with an inferred origin.** Rejected for version 1; the
  origin is not nameable and inference would be a lifetime system in disguise.
- **Put contract and extension forms in this proposal.** Rejected for reviewability; they are
  [ZEP-0185](./ZEP-0185.md).
- **`once` instead of `scoped`.** Rejected: `once` answers multiplicity, not place. A scoped method
  may be called any number of times.

## Implementation and validation

1. Add the `scoped` modifier to the method grammar, formatter, highlighter, and LSP. Reject it on
   `static fn`, constructors, properties, free functions, local functions, and extensions in this
   slice.
2. Give `this` a receiver token and apply the ZEP-0160 escape restrictions in the body, while
   keeping ordinary member resolution.
3. Implement explicit `scoped Self`/`scoped &Self`/`scoped Self?`/`scoped &Self?` and scoped
   non-`Self` results. Keep plain `Self` ordinary, reject `this` returned as an ordinary result with a
   `scoped Self` fix-it, and reject unrooted scoped values and scoped generic results.
4. Implement sealing in member resolution: on a sealed value, accept only `scoped` members. Reject
   ordinary fields, properties, extension methods, and calls.
5. Implement receiver stability for binding and returning a receiver-tied result.
6. Record the modifier and result flag in the API index and separate-compilation format.
7. Test: scoped and unscoped calls; sealed member rejection for each member kind; `scoped mut`
   composition; explicit `scoped Self`; plain `Self` returning a new value; `this` returned as an
   ordinary result; `null` for `scoped Self?`; explicit non-`Self` view; ordinary-result methods;
   temporary receiver binding and immediate consumption; closure capture and return rejection;
   API-index round trips; unchanged JVM descriptors; and Java export rejection.

## Open questions

- Should a `scoped` property getter be designed later, or should receiver-tied properties remain
  `scoped fn` methods permanently? Version 1 uses methods.
- Should a free function with exactly one scoped parameter be allowed to return a receiver-tied
  result? Version 1 keeps scoped returns method-only.
- Should scoped methods be allowed on generic classes once ZEP-0162 lands? Version 1 assumes yes,
  with origin propagation through admitted type parameters.
- Should extension methods and contract requirements share this receiver model exactly? Version 1
  assumes yes; [ZEP-0185](./ZEP-0185.md) owns the declaration-context rules.

## Decision

Accepted 2026-11-27. `scoped fn` / `scoped mut fn` is a per-method modifier on classes. A scoped
value a caller holds is sealed to `scoped` members; the receiver inside its own declaration is an
ordinary, escape-restricted receiver so the body can use the type's members. Receiver-tied results
are explicit `scoped Self`, `scoped &Self`, `scoped Self?`, `scoped &Self?`, or a scoped non-`Self`
view rooted at the receiver; a plain `Self` result is an ordinary same-type result. Returning `this`
as an ordinary result is an escape with a `scoped Self` fix-it. Contract requirements, defaults,
overrides, and extension methods are [ZEP-0185](./ZEP-0185.md). Generic classes, properties,
free-function scoped returns, and host export stay out of version 1.
