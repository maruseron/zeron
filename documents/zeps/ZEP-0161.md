# ZEP-0161: Scoped Receiver Methods and Contract Conformance

## Abstract

Add a `scoped` method modifier that makes the receiver a scoped value of the receiver's origin.
`scoped fn` promises that the method does not let the receiver escape, and lets `Self`, `&Self`, and
`Self?` in the result carry the receiver's origin. `scoped` composes with `mut` as `scoped mut fn`,
which receives `scoped &Self`. A scoped implementation may satisfy an unscoped contract requirement
when its result does not depend on a scoped value; an unscoped implementation may not satisfy a
scoped requirement. The declaration surface is a per-method marker, not a `scoped extension`
container. Free functions may take scoped parameters but cannot declare scoped returns in version 1.

## Motivation

ZEP-0158 needs a checked way to factor resource logic out of a block. The original proposal used
`scoped extension File { ... }`, which makes the whole declaration container scoped. That is the
wrong axis: the property the caller relies on belongs to the receiver and the result, not to every
method in a container. It also raises unnecessary questions about mixed extensions, overrides, and
contract conformance.

`mut` and `&` already separate a declaration property from a type property:

| Concern | Type surface | Declaration surface | Generic admissibility |
| --- | --- | --- | --- |
| Mutation | `&T` | `mut fn` | `T admits mutable` |
| Absence | `T?` | — | `T admits nullable` |
| Escape | `scoped T` | `scoped fn` | `T admits scoped` (ZEP-0162) |

A method marker composes per declaration, works uniformly for classes, contracts, and extensions,
and fits existing override and conformance rules. A `scoped extension` would have to answer “are
all methods scoped?” and would not compose cleanly with `mut` or contract requirements.

The receiver-tied result is the second motivation. A method such as `header()` may return a view
that depends on the receiver. Without a way to express that, the caller can store the view after
the receiver's logical scope ends. Automatically scoping direct `Self`, `&Self`, and `Self?`
results gives the common case a checked rule without a general lifetime system.

## Goals

- Add `scoped fn` to classes, contracts, extensions, and contract method requirements.
- Define `scoped fn` as a read-only receiver of type `scoped Self`, and `scoped mut fn` as a
  mutable receiver of type `scoped &Self`.
- Make `this` denotable but non-escaping inside a scoped method.
- Propagate the receiver origin through direct `Self`, `&Self`, and `Self?` results.
- Allow an explicit `scoped` result annotation for a receiver-derived non-`Self` view.
- Define contract conformance using ordinary function subtyping with the receiver first.
- Allow a scoped implementation to satisfy an unscoped requirement when its result is not scoped.
- Reject an unscoped implementation for a scoped requirement.
- Keep `mut` conformance unchanged while allowing `scoped` to compose with it.
- Allow free functions with scoped parameters, but no scoped returns in version 1.
- Reject `scoped extension` as a declaration kind.
- Record the modifier and relative origin in the API index.

## Non-goals

- `scoped extension` or any other container-level scoping declaration.
- Scoped constructors, fields, globals, properties, or property getters in version 1.
- Scoped methods on generic classes or contracts; [ZEP-0162](./ZEP-0162.md) owns their
  admissibility and origin propagation.
- Scoped returns from free functions, including returns of a scoped parameter.
- Multiple receiver origins, named regions, lifetime parameters, or ownership transfer.
- `once`, linear values, or use-after-disposal checking.
- Host interop, Java SAM conversion, or exporting scoped methods to Java.
- Changing the existing rule that a `mut` requirement needs a `mut` implementation.
- Overloading a method solely by `scoped` or by receiver scope.
- Proving that ordinary member bodies do not publish aliases of the receiver.

## Proposal

### Syntax and modifier order

`scoped` is a contextual modifier before `mut` and `fn`:

```zeron
public scoped fn checksum(): Long = ...;
public scoped mut fn readLine(): String = ...;
```

The canonical order is `public scoped mut fn`. A `scoped fn` without `mut` has a read-only receiver;
a `scoped mut fn` has a mutable receiver. `static fn` cannot be scoped because it has no receiver.
A constructor cannot be scoped in version 1.

`scoped` is allowed on a class method, a contract method requirement, a contract method default, and
an extension method. It is not allowed on a local or nested function declaration that is not a
method.

### Receiver semantics

Inside a `scoped fn`, the receiver has type `scoped Self`:

```zeron
public class File {
    public scoped fn size(): Long = ...;
    public scoped fn readHeader(): Header = Header.parse(readBytes(4));
}
```

Inside a `scoped mut fn`, the receiver has type `scoped &Self`:

```zeron
public class File {
    public scoped mut fn readLine(): String = ...;
}
```

In both bodies:

- unqualified member access resolves against the receiver, as in any method;
- `this` is a valid expression, but its type is scoped;
- `this` may be passed to another scoped parameter or receiver of the same origin;
- `this` may not be returned unless the result is a receiver-origin scoped type;
- `this` may not be stored in a field, captured by an escaping closure, placed in a generic
  container, raised as an effect payload, or passed to an unscoped parameter;
- nested receiver lambdas may qualify the receiver as `File.this`; the qualified expression has the
  same scoped type and the same escape rules.

A scoped method is callable on an unscoped receiver because `Self <: scoped<o> Self`. It is also
callable on a scoped receiver of the same origin. It is not callable on a scoped receiver from a
different origin.

### Result propagation

In a `scoped fn` result, direct occurrences of `Self` are receiver-origin scoped:

```zeron
public class File {
    public scoped fn selfView(): Self = this;          // scoped Self
    public scoped mut fn mutableView(): &Self = this;  // scoped &Self
    public scoped fn maybeSelf(): Self? = ...;         // scoped Self?
    public scoped fn checksum(): Long = ...;           // ordinary Long
}
```

The propagation rule applies only to direct `Self`, `&Self`, and `Self?`. Writing the declaring
type name instead, such as `File`, denotes an ordinary unscoped result; returning `this` as that
type is an escape. The rule does not apply to generic instantiations such as `Option<Self>`,
`Array<Self>`, or `Box<Self>`, because version 1 rejects scoped generic instantiations. Those
results must be expressed another way or deferred to ZEP-0162.

A receiver-derived non-`Self` view must be written explicitly:

```zeron
public class File {
    public scoped fn readerView(): scoped &Reader = this.reader;
}
```

An explicit `scoped` result is allowed only on a `scoped fn`, only on a type that version 1 can
scope, and only when the result can be typed as scoped. It is a trusted provenance declaration: the
compiler enforces non-escape, but it cannot prove that the returned view is actually owned by the
receiver. `Self` propagation is compiler-derived and does not require that trust.

A method that returns an ordinary `String`, `Long`, or other independent value does not need a
scoped result. The scoped marker on the method still promises that the receiver did not escape.

### Contract requirements and conformance

A contract may require a scoped method:

```zeron
public contract Readable {
    public scoped fn checksum(): Long;
    public scoped fn view(): Self;
}
```

Conformance uses ordinary function subtyping with the receiver as the first parameter. The
receiver is contravariant and the result is covariant. With `Self <: scoped<o> Self`, the important
cases are:

| Requirement | Implementation | Allowed? | Reason |
| --- | --- | --- | --- |
| `fn checksum(): Long` | `scoped fn checksum(): Long` | Yes | The implementation accepts `Self`; its result is unchanged |
| `fn view(): Self` | `scoped fn view(): Self` | No | The implementation result is `scoped Self`, which is not a `Self` |
| `scoped fn checksum(): Long` | `fn checksum(): Long` | No | The implementation receiver is `Self`, not `scoped Self` |
| `scoped fn view(): Self` | `scoped fn view(): Self` | Yes | Receiver and result origins agree |
| `scoped fn view(): Self` | `scoped fn view(): &Self` | Yes | Result covariance; `&Self <: Self` |
| `mut fn read(): String` | `scoped mut fn read(): String` | Yes | The implementation accepts `&Self`; result unchanged |
| `scoped mut fn read(): String` | `mut fn read(): String` | No | The implementation cannot accept a scoped receiver |

The first row is the useful direction: a class may strengthen an existing unscoped contract with a
scoped implementation. The second row is the cost of implicit `Self` propagation: a scoped method
that returns `Self` cannot satisfy an unscoped requirement returning `Self`, because the result is
receiver-tied. An author who needs an independent result can return the declaring type name, such as
`File`, or use an ordinary method.

`mut` conformance is unchanged. A `mut` requirement still needs a `mut` implementation. `scoped`
composes with that rule; it does not relax it. A `scoped mut fn` may satisfy an unscoped `mut`
requirement when its result is not scoped, and an unscoped `mut fn` may not satisfy a
`scoped mut` requirement.

A scoped method may not be overloaded solely by its scopedness or receiver scope. It has the same
name and parameter list as the unscoped form, so the existing duplicate-member rule applies.

### Free functions

A free function may declare scoped parameters:

```zeron
fn inspect(file: scoped &File): Long = file.size;

fn inspectBoth(first: scoped &File, second: scoped &Reader): Long =
    first.size + second.remaining;
```

Each parameter is origin-polymorphic at the call site. The callee cannot return a scoped parameter,
because its origin ends when the call returns. It may pass a parameter to another scoped parameter
or to a `scoped fn` receiver, preserving that parameter's origin. It may not join two scoped
parameters with different origins.

A free function cannot declare a scoped return type in version 1:

```zeron
fn openView(): scoped &File = ...; // error: no origin for the result
```

The receiver-origin form described above is deliberately method-only. A future proposal can add an
explicit origin annotation or a single-scoped-parameter return rule; version 1 does not guess.

### Receiver stability

The receiver of a `scoped fn` must be a stable receiver: `this`, a parameter, a local, or an
already-scoped value. This gives the result a nameable origin.

```zeron
let file = File.open(path);
let header = file.headerView();   // allowed: `file` is a local

let header = makeFile().headerView(); // rejected: the receiver is a temporary
```

A call on a temporary may be used only when the result is consumed within the same statement, such
as `makeFile().checksum()`. Binding it to a local would outlive the temporary's origin. Version 1
rejects the binding rather than inventing a lifetime extension rule.

### Trusted member bodies

A `scoped fn` body is checked for the receiver value itself. It is not a whole-program proof that
the receiver's internal graph is sealed. An ordinary method or property body still has an ordinary
`this` and may publish an alias. A field or collection reached through the receiver may contain an
alias that is not typed `scoped`.

The checked surface is therefore:

- strong for the receiver value: it cannot be returned as an unscoped value, stored, captured, or
  passed to an unscoped parameter;
- strong for direct `Self`/`&Self`/`Self?` results;
- trusted for explicit `scoped` non-`Self` results;
- shallow for ordinary member bodies and reachable aliases.

Library authors who need a checked view must declare it as `scoped fn` with a scoped result. This
is the same boundary recorded by ZEP-0158's non-goals.

### Interaction with `mut`, properties, and extensions

- `scoped fn` receives `scoped Self`; `scoped mut fn` receives `scoped &Self`.
- A `scoped &Self` can call both read-only and mutating scoped methods. A `scoped Self` can call
  only read-only scoped methods.
- Property getters are not scoped in version 1. A receiver-tied property should be a `scoped fn`
  until property conformance is designed.
- Extensions remain ordinary containers. A scoped extension method is written as `scoped fn` inside
  a normal extension. `scoped extension` is rejected. An extension has no `Self`, so a
  receiver-tied result is written explicitly, such as `scoped &File`.
- `scoped` does not change visibility, dispatch, or method identity.

### API index and runtime

The API index records `scoped` on the method and on its receiver/result types. The origin is
relative: `receiver` for a scoped method, `parameter` for a free-function parameter. No absolute
scope identity is serialized. `API_INDEX_SCHEMA_VERSION` is bumped once when the feature lands, and
`STANDARD_LIBRARY_API_VERSION` is bumped once when a standard-library method uses `scoped`.

The runtime representation is unchanged. A `scoped fn` is emitted as an ordinary method whose
receiver is the first argument. `scoped` adds no hidden parameter, wrapper, or descriptor. The
receiver's JVM type is the same as the unscoped receiver's type.

Scoped methods are not exported to Java and do not participate in Java SAM conversion. A Java
caller cannot express or honor the non-escape promise.

## Compatibility and impact

- Additive declaration modifier. Existing methods and contracts are unchanged.
- `scoped` is a contextual modifier before `mut`/`fn`; it remains an ordinary identifier
  elsewhere.
- The parser, formatter, highlighter, LSP, API index, and separate-compilation format need the
  modifier.
- Contract conformance and override checking use the new function-subtyping rules. The existing
  `mut` rule is unchanged.
- No runtime representation change and no new method descriptor.
- Documentation: extensions, contracts, lambdas and receiver functions, and resource management
  need the method form and the `Self` propagation rule.

## Alternatives

- **`scoped extension`.** Rejected: it scopes a container rather than a receiver/result, does not
  compose with `mut`, and makes contract conformance ambiguous.
- **A boolean receiver flag without result propagation.** Rejected: `Self` results need the
  receiver origin, or the method cannot return a receiver-tied view safely.
- **A separate `scoped` function type for methods.** Rejected: methods already have receiver
  function types; a second representation would complicate overrides, callable references, and
  the API index.
- **Require explicit `scoped` on every receiver-tied result.** Rejected for the common `Self`
  case; automatic propagation is checked and avoids repetitive annotations. Explicit annotations
  remain for non-`Self` views.
- **Allow scoped returns from free functions with an inferred origin.** Rejected for version 1;
  the origin is not nameable and inference would be a lifetime system in disguise.
- **Use `once` instead.** Rejected: `once` answers multiplicity, not place. A scoped method may be
  called any number of times.

## Implementation and validation

1. Add the `scoped` modifier to the method grammar, formatter, highlighter, and LSP. Reject it on
   `static fn`, constructors, fields, and properties.
2. Type the receiver as `scoped Self` or `scoped &Self` and run the ZEP-0160 escape checker in the
   body. Keep `this` denotable.
3. Implement direct `Self`/`&Self`/`Self?` result propagation and explicit scoped non-`Self`
   results. Reject scoped generic results in version 1.
4. Implement contract conformance and override checks with receiver contravariance and result
   covariance. Preserve the existing `mut` exactness rule.
5. Implement free-function scoped parameters and reject scoped free-function returns.
6. Record the modifier and relative origin in the API index and separate-compilation format.
7. Test: scoped and unscoped calls; `scoped mut` composition; `Self` propagation; explicit
   receiver-tied view; temporary receiver rejection; contract conformance in both directions;
   override strengthening; free-function parameter passing; closure capture and return rejection;
   API-index round trips; unchanged JVM descriptors; and Java export rejection.

## Open questions

- Is `public scoped mut fn` the right order, or should the formatter print `mut scoped fn`?
- Should a `scoped` contract requirement be allowed on a property getter, or are properties
  permanently out of scope?
- Should a `scoped fn` be allowed to return `scoped &Self` explicitly when `&Self` already
  propagates, or should the redundant annotation be rejected?
- Should free functions with exactly one scoped parameter be allowed to return a receiver-origin
  result, or is the method-only rule permanent?
- Should scoped methods be allowed on generic classes once ZEP-0162 lands? The draft assumes yes,
  with origin propagation through admitted type parameters.
- Does a `scoped fn` on a contract default implementation need a separate check from a class
  implementation?
- Is `scoped` the final name, given the existing uses of “scope” in `using`, `Scope`, and branch
  scopes?
