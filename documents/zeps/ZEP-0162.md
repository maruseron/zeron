## Abstract

Version 1 of the scoped value feature is a declaration attribute on parameters and receivers, not a
type constructor ([ZEP-0160](./ZEP-0160.md)). It deliberately rejects scoped type arguments, scoped
generic instantiations, arrays, type parameters, and automatic container scoping. This proposal
records that boundary and defines the future opt-in: promoting scopedness to a type-level qualifier
with an `admits scoped` admissibility marker for type parameters whose containers and generic
operations preserve a scoped origin. It also defines the future normalization rule
(`C<scoped<o> T>` becomes `scoped<o> C<T>`), origin propagation through member results, cross-origin
join rejection, and the variance and API-index consequences. Version 1 does not promise that
`Option<scoped T>`, `Array<scoped T>`, or `scoped Box<T>` works; it rejects them rather than
pretending that a qualifier on a container confines its elements.

## Motivation

Containers are where non-escape rules usually fail. A future type-level `scoped Box<&File>` is not
made safe by putting `scoped` on the box: `get()` still returns an `&File` that can escape. A
`scoped Array<&File>` still exposes its elements through indexing. The same is true for any generic
type whose members can produce a reference to a value stored inside it. The version-1 attribute
model avoids the question by rejecting every generic scoped form.

The naive fix is to say that a scoped value inside a container makes the whole container scoped.
That is the right end state, but it is not enough by itself. The container's operations must also
preserve the origin: reading an element must produce a scoped element, writing an element must
accept only a scoped value of the same origin, and joining containers from different origins must
be rejected. Those are generic admissibility and variance rules, not a local type-wrapper rule.

ZEP-0123 already separates “which operations are available” from “which type arguments may be
substituted.” `nullable` and `mutable` have both a type surface (`T?`, `&T`) and an admissibility
marker (`admits nullable`, `admits mutable`). A type-level `scoped` qualifier would need the same
treatment. Without it, a generic parameter either rejects scoped arguments accidentally or accepts
them unsoundly. The attribute model does not answer that question; this proposal owns the future
promotion.

Version 1 chooses the safe, honest boundary: no scoped type arguments and no container promises.
This proposal owns the later feature and the exact rules that make it sound.

## Goals

- Record the version-1 rejection rules and diagnostics for scoped generics and containers.
- Define `admits scoped` as an admissibility marker in the ZEP-0123 framework.
- Define when a generic declaration may accept a scoped type argument.
- Define origin propagation through generic containers and member results.
- Define the normalization `C<scoped<o> T>` to `scoped<o> C<T>`.
- Define variance: invariant by default, with covariant read-only containers only where existing
  variance rules justify it.
- Define cross-origin joins and the per-origin `scoped Any` top.
- Define the API-index and separate-compilation representation for admitted scoped parameters.
- Keep reification, effect payloads, fields, host interop, and free-function scoped returns out of
  scope.

## Non-goals

- Implementing `admits scoped` in version 1. Version 1 rejects the constructs.
- Automatic container scoping without an explicit admissibility marker.
- Scoped arrays, tuples, function values, primitives, or type parameters in version 1.
- Scoped fields, effect payloads, reified types, annotations, or host signatures.
- General region inference, named lifetimes, or ownership.
- Changing ZEP-0051 or ZEP-0052 variance rules for unscoped types.
- `once`, linear values, or use-after-disposal checking.
- Rank-2 or higher-kinded scoped parameters.
- Proving that a container's ordinary member bodies do not publish aliases.

## Proposal

### Version 1: reject the generic forms

Version 1 rejects all of the following:

```zeron
let box: Box<scoped &File> = ...;          // scoped type argument
let option: Option<scoped &File> = ...;    // scoped type argument
let array: Array<scoped &File> = ...;      // scoped element type
let scopedBox: scoped Box<&File> = ...;    // scoped generic instantiation
let scopedArray: scoped Array<&File> = ...;// scoped array
fn identity<T>(value: scoped T): T = value; // scoped type parameter
```

It also rejects:

- a scoped type inferred as a type argument, including `some(this)` where `some` returns
  `Option<T>` and `T` would become scoped;
- a scoped type in a reified argument or runtime descriptor;
- a scoped type in an effect payload, effect row, annotation value, or host signature;
- a scoped result from a free function;
- a `scoped fn` on a generic class or contract.

The diagnostic names the forbidden position and the origin, for example:

```text
A scoped type cannot be used as a type argument; `Box<scoped &File>` would expose its element.
A scoped value cannot be stored in a generic container; no admitted scoped parameter is available.
Cannot infer a common type for a scoped value and `Option<&File>`; scoped container propagation is
not enabled in this version.
```

Rejecting these forms is not a temporary parser limitation. It is the sound version-1 rule. A
container of scoped values needs the rules below.

### Version 1: what still works

- A generic function may take a scoped **concrete** parameter: `fn use<T>(file: scoped &File,
  body: (scoped &File) -> T): T`. `T` is the unscoped result, not the scoped parameter; passing a
  scoped type argument for `T` is rejected.
- A generic function may return an unrelated unscoped `T`; it may not infer `T` as scoped.
- A non-generic class or contract method may be `scoped fn`; a generic class or contract method may
  not be scoped in version 1.
- A scoped local may exist inside a generic function if its type is a concrete non-generic nominal
  type, such as `scoped &File`. It cannot be stored in a `T`, a container, or a returned generic
  value.
- A function type may have a scoped receiver or parameter, such as `(scoped &File) -> T`, because
  that is a parameter type, not a scoped type argument.

### Future: `admits scoped`

A type parameter opts in with the ZEP-0123 clause:

```zeron
contract Sink<T admits scoped> {
    fn put(value: T): Unit;
}

fn emit<T admits scoped>(sink: Sink<T>, value: T): Unit { ... }
```

`admits scoped` means the declaration may receive a scoped type argument and must preserve its
origin. A declaration without the marker rejects a scoped argument. The marker is order-insensitive
with `nullable` and `mutable`; the formatter prints `nullable`, `mutable`, then `scoped`.

The marker is not a promise that every value of `T` is scoped. It admits both scoped and unscoped
substitutions. A generic body must therefore be origin-polymorphic: it may pass a scoped `T` to
another `T admits scoped` parameter or store it in an admitted container, but it may not assume a
concrete origin, join two different origins, or return a scoped `T` from a free function in version
1.

### Future: container normalization and member results

A container of scoped values carries the origin of its elements. The canonical form moves the
qualifier outward:

```text
C<scoped<o> T>  =>  scoped<o> C<T>
```

The formatter and API index print the outer form. The type argument is still `T` inside the
container; the origin is a property of the whole container. This is the transitive scopedness rule:
if the container escapes, its elements escape with it.

Normalization alone is not enough. For an admitted container `scoped<o> C<T>`:

- a member that returns a `T` returns `scoped<o> T`;
- a member that accepts a `T` accepts only `scoped<o> T`;
- a member that returns a collection of `T` returns a scoped collection of the same origin;
- a member that returns an unrelated `String`, `Int`, or other independent value is unchanged;
- a member that returns the container itself returns `scoped<o> C<T>`;
- a member that returns a raw alias not expressible as a scoped type is rejected unless the
  declaration is outside the checked generic surface and remains a trusted library declaration.

The member-result rewrite is the part that makes containers sound. Without it, normalizing the
container type would still let `get()` return an unscoped element.

### Future: variance

Scoped containers are invariant by default. The origin is a capability, and a mutable container
must remain invariant for the same reason mutable references are invariant. A read-only container
declared covariant may be covariant in its element type only when every operation that produces an
element produces the scoped origin and every operation that consumes an element accepts the same
origin. `out` does not by itself grant scoped covariance; the declaration must also admit scoped.

Version 1 does not change ZEP-0051 or ZEP-0052. Use-site projections of scoped types are rejected
until the interaction between an existential projection and an origin is defined.

### Future: joins and `scoped Any`

Version 1 has no `scoped Any` and no type-level scoped lattice. If a future qualifier needs a top,
it must remain per-origin:

```text
scoped<o> T  <: scoped<o> Any
scoped<o> Any !<: Any
scoped<o1> Any is unrelated to scoped<o2> Any
```

Cross-origin joins are rejected. A common-parent computation that would need `scoped Any` is
rejected rather than synthesized; an explicit same-origin annotation may use it. This applies to
container joins as well: `List<scoped<o1> A>` and `List<scoped<o2> B>` do not join into a scoped
list of `Any`.

`Any` is not made into a useful universal value by this feature. It remains the top of the
unscoped hierarchy, and a future `scoped Any` would exist only to complete the subtype relation and
to support explicit same-origin widening.

### Future: reification, effects, and interop

- Origins are static and are never reified. A reified type argument cannot be scoped.
- A scoped type cannot appear in an effect row or effect payload. Raising a scoped value would let
  it escape through the handler.
- A scoped type cannot cross the host boundary, even when its base type is a Java-compatible class.
  A generic Java type cannot be instantiated with a scoped argument.
- A generic library compiled separately must record `admits scoped` and the relative origin shape.
  A consumer without the marker records a rejection, not a silent erasure.

### Future: API index and separate compilation

The API index records:

- `admits scoped` on each type parameter that accepts scoped arguments;
- scoped modifiers on parameter, receiver, and result types;
- relative origin markers (`receiver`, `parameter`, `block`) rather than local identities;
- the fact that a scoped type has no runtime descriptor.

`API_INDEX_SCHEMA_VERSION` is bumped once when the marker and its signature encoding land.
`STANDARD_LIBRARY_API_VERSION` is bumped once when a standard-library generic admits scoped. These
bumps are coordinated with ZEP-0160 and ZEP-0161 so a release cycle does not bump either version
twice.

## Compatibility and impact

- Version 1 is additive: it rejects new forms that do not exist today, so existing generic code is
  unchanged.
- The future marker is additive at declaration sites. A generic declaration that does not opt in
  continues to reject scoped arguments.
- Compiled libraries need the new admissibility bit and the relative origin encoding; a library
  compiled without it must not silently accept scoped arguments.
- The type model needs normalization and member-result rewriting. This is a larger change than a
  wrapper: it touches generic substitution, member lookup, variance, the API index, and separate
  compilation.
- No runtime representation change. Origins are not reified and containers are ordinary objects.
- Documentation: generics, variance, collections, and library-authoring chapters need the
  admissibility rule once it ships.

## Alternatives

- **Accept scoped type arguments in version 1 without admissibility.** Rejected: `Box<scoped T>`
  would expose an unscoped `T` through `get()`, and `Array<scoped T>` would expose it through
  indexing.
- **Automatically scope every container of a scoped value.** Rejected for version 1: it silently
  changes generic signatures, variance, API index, and separate compilation. It also gives no way
  for a library to opt out or for a caller to know whether an operation preserves the origin.
- **Make `scoped Any` the universal container top.** Rejected: it loses the origin and turns every
  cross-origin join into an escape.
- **Treat `scoped` as a declaration-site variance marker.** Rejected: variance answers
  substitutability, not place. A covariant container can still leak an element if its members are
  not origin-preserving.
- **Use `once` instead of containers.** Rejected: multiplicity is orthogonal. A container can hold
  a value that may be used many times but must not escape.

## Implementation and validation

Version 1:

1. Reject scoped type arguments, scoped generic instantiations, scoped arrays, scoped type
   parameters, and scoped reified/effect/host positions with targeted diagnostics.
2. Reject `scoped fn` on generic classes and contracts.
3. Reject inference that would create a scoped type argument.
4. Test all rejections, including a generic function with a concrete scoped parameter that still
   returns an unscoped `T`.

Future marker:

1. Parse `admits scoped` in the ZEP-0123 clause. Update the formatter, highlighter, LSP, and API
   index.
2. Implement admissibility: a scoped argument requires `admits scoped`; a declaration without it
   rejects the argument.
3. Implement normalization `C<scoped<o> T>` to `scoped<o> C<T>` and member-result rewriting.
4. Implement origin-preserving variance and reject cross-origin joins.
5. Encode the marker and relative origin in the API index and separate-compilation format.
6. Test: admitted and non-admitted generic calls; container reads and writes; nested containers;
   covariant and invariant containers; cross-origin joins; API-index round trips; separate
   compilation; and unchanged runtime descriptors.

## Open questions

- Is `admits scoped` the right spelling, or should the marker be `admits scope` or
  `admits noescape`?
- Does `admits scoped` need an origin parameter, such as `admits scoped<o>`, or is a relative
  origin sufficient?
- Should a read-only container ever be covariant in a scoped argument, or is invariant the only
  sound rule?
- Should `Option<scoped T>` and other pure data containers be special-cased before general
  containers?
- Should a scoped type argument be allowed in a non-generic holder class that declares no
  element-returning members?
- How do use-site projections (`out T`, `in T`) interact with origins?
- Should reified scoped types ever be allowed with an erased origin descriptor, or is static-only
  the permanent rule?
- Does a generic method on a generic class need two markers (`admits scoped` on the class and the
  method), or does one suffice?
