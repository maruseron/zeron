# ZEP-0163: Automatic Read-Only Widening for Inherited Generic Method Bounds

## Abstract

When a class implements a generic contract bound, the contract's methods are inherited through that
bound. A receiver with a mutable projection, such as `Stream<&Point>`, currently binds the inherited
method's read-only type parameter to `&Point`. That argument is rejected by default admissibility,
even though the call only needs a read-only view of each element. As a result, inherited operations
such as `map` appear not to exist for mutable-projection streams.

This proposal makes inherited generic method resolution widen a receiver-supplied mutable reference
to its read-only base when the method binder is read-only. `Stream<&Point>.map(...)` then solves the
inherited `map` binder as `Point`, and the transform receives a read-only `Point`. The widening is
local to the inherited method call: it adds no new syntax, does not make `Stream` generally
covariant, and changes no runtime representation or API-index field.

## Motivation

`Stream` declares `map` directly, but it also implements `Functor<Stream<_>>` and inherits the
contract operation. When a stream is used through that bound, or a generic helper operates through
it, the inherited operation is selected:

```zeron
public contract Functor<F<_>> {
    map<A, B>(this: F<A>, transform: A -> B): F<B>;
}
```

The inherited binder `A` is read-only because it does not declare `admits mutable`. A mutable
projection stream is a useful value, and a read-only operation should be able to consume it:

```zeron
let points: Stream<&Point> = ...;
```

Calling an inherited mapping operation on it needs to read each `Point`, not mutate it. The intended
call is therefore:

```zeron
let labels = points.map(point -> point.label);
```

The receiver supplies `Stream<&Point>` for `F<A>`, so the straightforward substitution is
`A = &Point`. Default admissibility rejects that substitution: mutable-reference arguments require
an explicit `admits mutable` binder. A direct method can keep its current substitution; the rough
edge is the inherited bound operation, which has no way to request the read-only view. Requiring
`map` to admit mutable arguments would be the wrong fix. It would make the parameter keep the
mutable capability, widen the contract surface for every implementation, and suggest that `map` may
mutate its elements.

The missing step is a read-only widening at the inherited method boundary:

```text
Stream<&Point>  --read-only method view-->  Stream<Point>
```

That view is sufficient for `map`, whose transform only receives an element. It is not a general
class-level subtype: this proposal does not make a `Stream<&Point>` value assignable to
`Stream<Point>` everywhere. It makes the inherited read-only method binder solve against the
widened receiver view.

The same rough edge can appear in other generic contracts with inherited methods, such as
`Foldable`, `Applicative`, and `Monad`, whenever a receiver carries a mutable projection but the
inherited operation only reads elements. Fixing it once at member resolution keeps those contracts
usable without adding mutable admissibility to every method that happens to accept an element.

## Terminology

This proposal uses `A: readonly` as shorthand for “a method binder that does not declare
`admits mutable`.” It does not introduce a new source-level bound. The existing admissibility rules
remain the spelling:

- `A` (no marker) is read-only; mutable-reference arguments are rejected.
- `A admits mutable` accepts both read-only and mutable-reference arguments.
- `A admits nullable` additionally accepts nullable arguments.
- `effect` binders are unaffected.

“Widening” means replacing a top-level `&T` argument with `T` for binder solving. It does not remove
a mutable capability from the receiver expression, and it does not recursively rewrite nested type
arguments.

## Goals

- Make inherited generic methods with read-only binders callable on receivers whose fixed
  type arguments are mutable references.
- Preserve the existing read-only meaning: the method body and its lambda parameters cannot mutate
  through the widened argument.
- Apply the rule only to binders fixed by the receiver, not to result binders or explicit type
  arguments.
- Preserve nullable wrappers, nested arguments, and all existing diagnostics.
- Require no new syntax, runtime descriptor, API-index field, or separate-compilation format.
- Keep the change local to inherited contract-method resolution.

## Non-goals

- General declaration-site covariance for `Stream` or any other mutable-capable class.
- Making `Stream<&Point>` assignable to `Stream<Point>` in every value position.
- Widening mutable references in direct (non-inherited) generic methods or free functions.
- Widening explicitly supplied type arguments.
- Widening result binders or changing the mutability of a returned reference.
- Recursively widening mutable references nested inside another type argument.
- Changing `admits mutable`, `admits nullable`, or `effect` admissibility.
- Changing class/contract conformance, overload selection, or runtime erasure.
- Promising the same behavior for stored generic function values or method references before their
  binder-solving rules are specified.

## Proposal

### Applicability

The rule applies when all of the following hold:

1. The selected member is an inherited operation from a generic contract bound, as opposed to a
   method declared directly on the receiver's class.
2. The method has a type parameter that is fixed by the receiver's applied type arguments.
3. That type parameter is read-only: it does not declare `admits mutable`.
4. The receiver-supplied argument for that position is a top-level mutable reference `&T`.

The binder is then solved with `T` instead of `&T`. If the argument is nullable, `&T?` widens to
`T?` and the existing nullable-admissibility check still applies. If the argument is not a top-level
reference, it is unchanged.

### Example

```zeron
public class Point {
    public property label: String;
    public constructor new;
}

fn labels(points: Stream<&Point>): Stream<String> =
    points.map(point -> point.label);
```

The inherited `Functor.map` binder is read-only. The receiver supplies `Stream<&Point>`, so the
method view is `Stream<Point>` and `A = Point`. The lambda parameter has type `Point`, and its
`label` read is allowed. The receiver expression remains a `Stream<&Point>`; only the call's method
view is widened.

By contrast, a binder that explicitly admits mutable arguments keeps its mutable view:

```zeron
contract MutatingSink<T admits mutable> {
    consume(value: T): Unit;
}
```

An inherited `consume` on a `Sink<&Point>` continues to receive `&Point`. The proposal only widens
read-only binders because it cannot preserve a capability that the binder did not admit.

### What is fixed by the receiver

Only binders that the receiver constrains participate. In an inherited method such as

```zeron
map<A, B>(this: F<A>, transform: A -> B): F<B>
```

`A` is fixed by `F<A>`, while `B` is inferred from the transform result. Only `A` is eligible for
read-only widening. The result `F<B>` keeps whatever `B` the caller's transform produces, including
a mutable reference if the transform returns one.

If a contract exposes multiple type arguments, each receiver-fixed read-only binder is treated
independently:

```text
F<&A, B>  ->  F<A, B>
```

A mutable binder in the same position is not widened.

### Explicit type arguments

Automatic widening is an inference rule, not a replacement for admissibility. If the caller writes
the binder explicitly, the existing rule applies:

```zeron
points.map<&Point, String>(...)   // rejected: &Point does not satisfy read-only A
```

The caller can write `points.map<Point, String>(...)` or let inference widen the receiver view.

### Nested arguments and nullability

Only the receiver argument at the inherited binder position is considered. Nested mutable
references remain nested and are not rewritten:

```text
Stream<Box<&Point>>  ->  no widening at the outer argument
```

`Box<&Point>` is not a top-level reference, so the inherited read-only binder still receives
`Box<&Point>` and the existing admissibility check applies. A future proposal can define recursive
widening if a use case requires it.

Nullability is preserved:

```text
Stream<&Point?>  ->  Stream<Point?>
```

The `T?` argument still requires `admits nullable` on the binder, as it does today.

### Receiver and method body

Widening changes only the call's substituted descriptor. It does not change the static type of the
receiver expression, insert a cast, or make a mutable value read-only in the caller. The inherited
method body is already checked against its declaration; it receives a read-only `A` and cannot
perform mutations through it unless the binder declares `admits mutable`.

The compiler already emits erased descriptors for generic methods. This rule changes the source
substitution used for checking and for the call's resolved descriptor, not the JVM shape. No bridge,
hidden parameter, or runtime descriptor is introduced.

### Failure behavior

If no inherited method becomes applicable after widening, the existing unknown-method or
type-mismatch diagnostic is reported. This proposal adds no new diagnostic code. In particular, it
does not silently widen a mutable argument for a binder that declares `admits mutable`; such a
binder remains satisfied by `&T` directly.

## Compatibility and impact

- Additive at call sites: an inherited call that previously failed admissibility can now resolve
  when the binder is read-only and the receiver supplies a mutable reference.
- Existing valid calls keep their current substitutions. A binder that admits mutable arguments is
  never widened, and a direct method is unaffected.
- No source syntax changes, so the formatter, grammar, highlighter, and LSP surface stay unchanged.
- No runtime, bytecode, API-index, or separate-compilation change. Resolved descriptors remain
  erased like other generic calls.
- Method selection is not overloaded, so widening cannot introduce an ambiguous overload. If a
  future overload proposal lands, it must define whether widened and non-widened candidates are
  ranked separately.
- Documentation: the generics and collections guides need a note that inherited read-only methods
  can be called on mutable-projection containers with a read-only element view.

## Alternatives

- **Require `admits mutable` on inherited read-only methods.** Rejected: it keeps the mutable view,
  widens the contract's admissibility surface, and misstates that the operation may mutate.
- **Add `out` to `Stream` and make the container generally covariant.** Rejected for this proposal:
  it changes assignability for every `Stream` position and requires a full variance audit, while
  the motivating call only needs a method-bound widening.
- **Require an explicit `Stream<Point>` cast or annotation.** Rejected as the default: it exposes a
  container implementation detail and may not be legal while `Stream` remains invariant. It can
  remain a manual workaround for callers that need a stored widened value.
- **Widen every generic method binder, including direct methods and free functions.** Rejected for
  the first slice: it changes inference far beyond inherited bounds and has no motivating use case.
- **Widen result binders too.** Rejected: if a transform returns `&Point`, erasing that capability
  from the result would lose mutation that the caller may rely on.
- **Recursively widen nested reference arguments.** Rejected for the first slice: `Box<&Point>` may
  have mutable operations of its own; rewriting its inner argument needs its own soundness rules.

## Implementation and validation

Likely implementation stages:

1. Identify inherited contract-method calls and the binders fixed by the receiver application.
2. During binder solving, widen top-level reference arguments only for read-only receiver-fixed
   binders; preserve `nullable` wrappers and leave all other arguments unchanged.
3. Use the widened binder set for the resolved descriptor and argument checking, without changing
   the receiver expression's static type.
4. Add a focused call-resolution test group and document the behavior in the generics and
   collections guides after acceptance.

Validation:

- `Stream<&Point>.map(point -> point.label)` resolves and the lambda parameter is `Point`.
- A direct read-only method on `Stream<&Point>` keeps its current behavior.
- An inherited binder declaring `admits mutable` continues to receive `&Point` and is never widened.
- Explicit `map<&Point, _>` remains rejected.
- A transform returning `&Point` produces `Stream<&Point>`; result mutability is preserved.
- `Stream<&Point?>` widens to `Stream<Point?>` only when the binder admits nullable arguments.
- `Stream<Box<&Point>>` is not recursively widened.
- Separate-compilation tests confirm the inherited method resolves from a compiled library with no
  API-index or descriptor change.
- Negative tests confirm no widening for free functions, direct generic methods, effect binders, or
  non-reference receiver arguments.

## Open questions

- Should the rule apply to inherited methods only, or also to direct generic methods whose binder is
  fixed by a read-only receiver position?
- Is `Stream`'s element position actually read-only for this purpose, or must the rule be tied to an
  explicit covariant or read-only declaration rather than inferred from the operation's shape?
- Should a future explicit marker such as `admits readonly` allow an opt-out or make the intent
  visible at the contract declaration?
- Does the same widening belong in generic function values and method references, or should those
  retain their stricter admissibility?
- Should nested containers be widened in a later proposal, and if so, which containers are known to
  be read-only at the relevant position?
- If overloads are ever introduced, should a widened candidate rank below an exact mutable binder?
- Should the compiler report an informational note when it widens, or is the call silently accepted?
