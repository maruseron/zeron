## Abstract

When a class implements a generic contract and does not declare its own method, the operation is
selected from the contract. A receiver with a mutable projection, such as `Stream<&Point>`,
supplies `&Point` for an inherited method binder such as `map<A, B>`'s `A`. Default admissibility
rejects that solution, even though the inherited method body is checked against a read-only `A`
and cannot mutate through it.

This proposal admits a mutable-reference receiver argument for a receiver-fixed read-only binder.
The binder is solved as `&Point`; no type is rewritten. An inherited `map`, `ap`, `foldLeft`,
`count`, or `filter` becomes callable through a bound on a mutable-projection receiver, and the
call's types stay accurate.

The earlier design for this proposal substituted `A = Point` at the call boundary. That is
unsound: it rewrites the whole method signature, and contracts such as `Applicative.ap` and
`Filterable.filter` place `A` in positions where the rewrite makes the call's types false. The
read-only element view it promised belongs to variance, not admissibility; that work is recorded as
future work.

## Motivation

`Functor` declares `map` with a read-only binder:

```zeron
public contract Functor<F<_>> {
    map<A, B>(this: F<A>, transform: A -> B): F<B>;
}
```

A generic helper that receives a mutable-projection container cannot call it:

```zeron
public data class Point(label: String);

fn labelAll<F<_>: Functor<F>>(points: F<&Point>): F<String> =
    points.map(point -> point.label);
```

The receiver supplies `F<&Point>` for `F<A>`, so the straightforward solution is `A = &Point`.
Default admissibility rejects that solution: a binder without `admits mutable` accepts only
read-only arguments. The same rejected solution appears for inherited default operations reached through a bound:

```zeron
fn countAll<F<_>: Foldable<F>>(values: F<&Point>): Int = values.count();
```

A direct class method is not affected. `Stream` declares `map`, `filter`, and `count` on the class
itself, so concrete calls such as `Stream<&Point>.map(...)`, `.filter(...)`, or `.count()` already
resolve with `T = &Point`; the gap is the inherited selection paths, where the binder is solved
from the receiver rather than taken from the class's own signature.

Requiring every inherited read-only method to declare `admits mutable` is the wrong fix. It widens
the contract surface for every implementation, and it says the operation may mutate when it cannot.
The missing piece is narrower: a read-only binder that the receiver itself fixes should accept the
receiver's mutable reference.

## Terminology

This proposal uses the term **read-only binder** for a method binder that does not declare
`admits mutable`. It does not introduce a new source-level bound. The existing admissibility rules
remain the spelling:

- `A` (no marker) is read-only; mutable-reference arguments are rejected by default.
- `A admits mutable` accepts both read-only and mutable-reference arguments.
- `A admits nullable` additionally accepts nullable arguments.
- `effect` binders are unaffected.

A **receiver-fixed binder** is a method type parameter whose solution is fixed by a type argument
of the receiver, such as `A` in `this: F<A>` when the receiver is `F<&Point>`. A binder inferred
only from arguments or the expected type is not receiver-fixed.

**Admission** means accepting a top-level `&T` argument for a read-only receiver-fixed binder. It
does not rewrite `&T` to `T`, and it does not change any other type argument.

## Goals

- Make contract methods callable on receivers whose fixed type arguments are mutable references
  when the corresponding binder is read-only.
- Solve the binder as `&T`; do not substitute a wider type.
- Preserve the existing read-only checking of the inherited method body: it gains no mutation
  operations through the admitted argument.
- Cover both inherited selection paths: bound-selected contract methods on a generic receiver and
  inherited default methods on a concrete receiver.
- Preserve nullability, nested arguments, explicit type arguments, and all existing diagnostics.
- Require no new syntax, runtime descriptor, API-index field, or separate-compilation format.
- Keep the change local to binding a receiver-fixed binder in an inherited method call.

## Non-goals

- Replacing an admitted `&T` with `T` for binder solving or anywhere else. This is the earlier
  read-only-widening design and is rejected as unsound.
- General declaration-site covariance for `Stream`, `Iterable`, or any other mutable-capable
  class, and any change to the variance rules of [ZEP-0051](./ZEP-0051.md).
- Making `Stream<&Point>` assignable to `Stream<Point>` in any value position.
- Changing direct (non-inherited) generic methods, direct class methods, or free functions.
- Changing explicitly supplied type arguments.
- Admitting mutable references nested inside another type argument.
- Changing result types, `admits mutable`, `admits nullable`, or `effect` admissibility.
- Changing class/contract conformance, overload selection, or runtime erasure.
- Promising the same behavior for stored generic function values or method references.
- Providing a read-only element or lambda parameter type. That requires variance and is future
  work.
- Adding an `admits readonly` marker or any other new marker.

## Proposal

### Applicability

Admission applies when all of the following hold:

1. The selected member comes from a contract declaration rather than from a method declared on the
   receiver's class. This covers a contract method selected through a generic bound, including a
   default method, and an inherited default method selected on a concrete receiver that does not
   declare its own method.
2. The method has a type parameter that is fixed by the receiver's applied type arguments.
3. That type parameter is read-only: it does not declare `admits mutable`.
4. The receiver-supplied argument for that position is a top-level mutable reference `&T`.
5. The caller does not supply that binder explicitly.

The binder is solved as `&T`. Contract bounds on the binder are checked against `&T`; admission
does not bypass them. If the receiver supplies `&T?`, the nullable part is not relaxed: the binder
must still admit nullable arguments. If the receiver supplies a non-reference argument, or a nested
`Box<&Point>`, the argument is unchanged and the existing rules apply.

### Generic helper example

```zeron
fn labelAll<F<_>: Functor<F>>(points: F<&Point>): F<String> =
    points.map(point -> point.label);
```

The inherited `Functor.map` binder `A` is receiver-fixed and read-only. The receiver supplies
`F<&Point>`, so `A` is solved as `&Point`; the lambda parameter is `&Point`, and reading `label`
is allowed. The receiver expression remains `F<&Point>`.

### Inherited default example

```zeron
fn countAll<F<_>: Foldable<F>>(values: F<&Point>): Int = values.count();

fn labelIf<F<_>: Filterable<F>>(values: F<&Point>, prefix: String): F<&Point> =
    values.filter(point -> point.label.startsWith(prefix));
```

`Foldable.count<A>` and `Filterable.filter<A>` are inherited defaults whose `A` is fixed by the
receiver. Both admit `A = &Point`. `filter` returns `F<&Point>`, not `F<Point>`.

### Direct methods and explicit arguments

A direct class method is unchanged. `Stream<&Point>.map(...)` selects the class's own `map`, whose
`T` is already `&Point`. Admission is not involved.

An explicit type argument is not receiver-fixed, so the existing admissibility rule applies:

```zeron
fn labelAll<F<_>: Functor<F>>(points: F<&Point>): F<String> =
    points.map<&Point, String>(point -> point.label);   // rejected
```

### Nullability

Nullability remains a separate property. Admission relaxes only the mutable-reference check:

```text
F<&Point>   -> A = &Point     (admitted)
F<&Point?>  -> A = &Point?    (only when A admits nullable)
F<Point>    -> A = Point      (unchanged)
F<Box<&Point>> -> A = Box<&Point> (unchanged; not top-level)
```

### Why the binder is not widened

Substituting `A = Point` was the earlier design. It is unsound because it rewrites the method
signature, not just the receiver binding:

- `Applicative.ap<A, B>(this: F<A>, transform: F<A -> B>): F<B>`. With `A = Point`, the argument
  becomes `F<(Point) -> B>`, but the actual value is `F<(&Point) -> B>`. The call could pass a
  read-only `Point` to a function that requires `&Point`.
- `Filterable.filter<A>(this: F<A>, predicate: A -> Boolean): F<A>`. With `A = Point`, the result
  is `F<Point>` from an `F<&Point>`, which asserts covariance the language does not declare.
- `map` and `foldLeft` happen to be safe because `A` does not escape, but a rule keyed only on the
  binder's marker cannot distinguish them from `ap` and `filter`.

Admission avoids all three: the binder remains `&Point`, so every position in the signature is
accurate. The inherited method body was checked against a read-only `A` and has no mutation
operations through it, so admitting a mutable reference grants it no new capability.

### Receiver and method body

Admission changes only the call's binder solution. It does not change the static type of the
receiver expression, insert a cast, or make a mutable value read-only in the caller. The inherited
method body is already checked against its declaration; it receives a read-only `A` and cannot
perform mutations through it.

The compiler already emits erased descriptors for generic methods. This rule changes the source
substitution used for checking the call, not the JVM shape. No bridge, hidden parameter, or runtime
descriptor is introduced.

### Failure behavior

If no inherited method becomes applicable after admission, the existing unknown-method or
type-mismatch diagnostic is reported. This proposal adds no new diagnostic code. In particular, a
binder that declares `admits mutable` already accepts `&T` and is unaffected, and a nullable
argument without `admits nullable` still fails.

## Compatibility and impact

- Additive at call sites: an inherited call that previously failed admissibility can now resolve
  when the binder is read-only, receiver-fixed, and supplied a mutable reference.
- Existing valid calls keep their current substitutions. No type is widened, and no result type
  changes.
- No source syntax changes, so the formatter, grammar, highlighter, and LSP surface stay unchanged.
- No runtime, bytecode, API-index, or separate-compilation change. Resolved descriptors remain
  erased like other generic calls.
- Method selection is not overloaded. Admission applies to the selected inherited method; it does
  not rank candidates. If a future overload proposal lands, it must define whether an admitted
  candidate ranks below an exact mutable binder; exact resolution should win.
- Documentation: the generics and collections guides need a note that inherited read-only methods
  can be called on mutable-projection containers, and that the element view remains mutable unless
  the receiver is projected or the container is declared covariant.

## Alternatives

- **Substitute `&T` with `T` for binder solving.** Rejected as unsound for `ap` and `filter`, and
  unnecessary for the motivating calls; the earlier draft of this proposal used it.
- **Require `admits mutable` on inherited read-only methods.** Rejected: it widens the contract
  surface for every implementation, and it states that the operation may mutate.
- **Declare `out T` on `Stream` and `Iterable` and rely on covariance.** This is the principled
  route for a read-only element view, but it is blocked today: `Iterable` and `Stream` return
  `&Iterator<T>`, and the variance rules make a mutable reference's contained type invariant, so
  `out T` is rejected. It belongs to a separate variance and collections proposal.
- **Require an explicit `Stream<out Point>` projection.** Valid for concrete containers under
  [ZEP-0052](./ZEP-0052.md), and a useful manual workaround. It is not expressible for an abstract
  `F<_>` in generic code, which is the motivating case.
- **Require an explicit cast or annotation.** Rejected as the default: it exposes a container
  implementation detail, and an invariant container still cannot be assigned to its read-only
  base.
- **Admit every generic binder, including direct methods and free functions.** Rejected for the
  first slice: it changes inference beyond inherited calls and has no motivating case.
- **Admit nested reference arguments recursively.** Rejected for the first slice: `Box<&Point>` may
  have mutable operations of its own, and rewriting its inner argument needs its own rules.
- **Add an `admits readonly` marker.** Rejected: read-only is already the default, the receiver
  position identifies the case, and the marker adds a third spelling without adding a capability.
- **Apply admission to generic function values and method references.** Deferred: they have their
  own binder-solving and a stored type that participates in the API index. A concrete use case
  should come first.

## Future work

A read-only element view for mutable-projection containers needs variance, not admissibility. The
follow-up should begin with the iterator shape:

- Decide whether `Iterable.iterator()` returns an owned iterator or a read-only iterator reference.
  The current `&Iterator<T>` makes `T` invariant under [ZEP-0051](./ZEP-0051.md), so neither
  `Iterable<out T>` nor `Stream<out T>` can be declared today.
- Audit the collection contracts for `out` positions, including nullable and mutable admissibility
  markers on the containers' parameters.
- Once `Stream<out T>` is declared, `Stream<&Point>` is assignable to `Stream<Point>` by ordinary
  covariance, and generic code can take `F<Point>`. No method-bound admission rule is needed for
  the read-only view.

Use-site projections remain available in the meantime.

## Implementation and validation

1. Identify the two inherited selection paths: bound-selected contract methods and inherited
   default methods on concrete receivers.
2. During binder solving, when a receiver-fixed binder is read-only and the receiver supplies a
   top-level `&T`, admit `&T` instead of rejecting it. Preserve the nullable check; leave every
   other argument unchanged.
3. Apply the rule only to inherited selection. Do not apply it to direct class methods, free
   functions, explicit type arguments, or non-receiver-fixed binders.
4. Add a focused call-resolution test group and document the behavior in the generics and
   collections guides.

Validation:

- A generic `Functor` helper with an `F<&Point>` receiver resolves; the transform parameter is
  `&Point`.
- A generic `Foldable` helper with an `F<&Point>` receiver resolves through `count`.
- A generic `Filterable` helper with an `F<&Point>` receiver resolves through the inherited
  default and returns `F<&Point>`.
- A generic `ap` on `F<&Point>` resolves with `F<A -> B>` solved as `F<(&Point) -> B>`.
- Concrete `Stream<&Point>` calls to `map`, `filter`, and `count` keep using the direct class
  methods and do not use admission.
- An inherited binder declaring `admits mutable` continues to receive `&Point` and is unaffected.
- An explicit `map<&Point, _>` in a generic helper remains rejected.
- `Stream<&Point?>` is admitted only when the binder admits nullable arguments.
- `Stream<Box<&Point>>` is not admitted.
- Negative tests confirm no admission for free functions, direct generic methods, explicit type
  arguments, effect binders, or non-reference receiver arguments.
- Result types never change: an inherited `filter` on `F<&Point>` produces `F<&Point>`, and no
  call produces `F<Point>`.
- Separate-compilation tests confirm the inherited method resolves from a compiled library with no
  API-index or descriptor change.

## Resolved questions

| Question | Decision |
| --- | --- |
| Inherited only, or also direct generic methods? | Inherited only: bound-selected contract methods and inherited defaults. Direct class methods already see the exact receiver arguments, and free functions are unchanged. |
| Is `Stream`'s element position read-only, or must the rule be tied to a declaration? | Neither is needed. Admission does not rewrite the element type, so no read-only-position claim is made. The read-only view is a variance follow-up. |
| Should an explicit `admits readonly` marker exist? | No. Read-only is the default, and the receiver position already identifies the case. |
| Does the rule belong in generic function values and method references? | No for the first slice; they have their own binder solving and stored type. |
| Should nested containers be admitted in a later proposal? | Not as admission. Recursive reference handling is a variance question and needs per-container read-only evidence. |
| How should an admitted candidate rank against an exact mutable binder? | Exact resolution always wins. Admission applies only to the selected inherited method, so it introduces no ranking; a future overload proposal must preserve exact-first. |
| Should the compiler report a note when it admits? | No. The behavior is documented and the inferred parameter type is visible in hover; no new diagnostic code is added. |

## Decision

Accepted. The design is settled: admission without substitution for receiver-fixed read-only
binders in inherited method calls. The earlier read-only-widening design is rejected and recorded
above. The read-only element view is deferred to a variance and iterator-ownership proposal.
