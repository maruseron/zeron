> **Revised 2026-11-22 for [ZEP-0165](./ZEP-0165.md) and redesignated the same day.** `Await` no
> longer returns the task value. It responds `Unit` and carries a non-generic `Completion` view;
> `await` waits through the handler and then reads the finished `Task`. This removes the erased
> `Any?` response, the unchecked recovery cast, and the possibility of resuming with a wrong value.
> The carrier, handler, entry-boundary, and row design were re-reviewed and accepted; entry
> integration builds on [ZEP-0126](./ZEP-0126.md).
>
> **Implementation note (2026-11-24).** Implemented. `Completion` is the non-generic
> `Task.completion()` view, `Await responds Unit` carries it, `await` performs `Await, E` and then
> reads `Task.value()`, and `blocking` installs the same handler. The compiler applies the implicit
> `Await` handler at the generated entry through `EntrySupport`; a `dispose` implementation cannot
> declare `Await` or install a continuation-capturing handler, and the runtime dispose marker
> rejects the erased paths. `AsyncTaskTest` covers entry await, inline and `blocking` handlers,
> captured-effect re-raising, the negative row diagnostic, cancellation with cleanup, and a
> child-process launch of the generated entry. `STANDARD_LIBRARY_API_VERSION` is 22.

## Abstract

[ZEP-0165](./ZEP-0165.md) specifies `await(task)` as an ordinary blocking call to `task.value()`.
That is ergonomic, but it gives the runtime no seam at which an await can be intercepted, traced, or
scheduled differently.

This proposal adds that seam without opening effect applications or changing the runtime descriptor
ABI. `Await` is a **non-generic** responding effect that responds `Unit` and carries a
`Completion`, a non-generic view of the pending task. `await<T, E>` performs `Await`, then reads the
finished typed task and returns its value. A blocking handler waits for the completion and resumes
the perform. The compiler installs that handler around the program entry point, so `main` can await
directly without declaring a row or calling a wrapper.

The proposal deliberately keeps `Await` identity erased: it is a control effect with one meaning,
not a family of effects that user code dispatches by applied type. It adds no effect-row
representation, no wildcard handler syntax, no reified class parameters, and no erased response
bridge.

## Motivation

ZEP-0165's `await` is a plain function, so the simplest async code remains ordinary blocking code:

```zeron
using (let scope = ConcurrentScope.open()) {
    let first = spawn(scope, () -> load(1));
    let second = spawn(scope, () -> load(2));
    return await(first) + await(second);
}
```

That is the right default, and it should stay the observable behavior. But two needs are not met:

1. **Interception.** A test scheduler, tracing layer, or non-blocking backend cannot replace the
   blocking policy. `await` is compiled directly to `Task.value()`, so there is no handler to
   swap.
2. **Uniform effect composition.** ZEP-0119 and the effect model want `await` to participate in the
   effect row rather than disappear into a library call. This is what lets a caller reason about
   async work as an effect and lets a later handler decide how to schedule it.

An earlier revision made `Await` a non-generic carrier with an `Any?` response, and `await` recovered
the caller's static type with a cast. That revision has three defects:

- the recovery cast is unchecked, because `T` is not reified;
- the erased join helper declares no effect even though the task's `E` escapes when the joined task
  fails, so the effect accounting is unsound; and
- a handler can resume with any unrelated value, because the response type carries no relationship
  to the task being awaited.

The value never needs to travel through the effect response. The caller still holds the typed
`Task`, so the handler only has to choose a waiting policy. This proposal separates those concerns:
the effect waits, and the typed join returns the value.

The obvious design from the original ZEP-0120 draft — `Await<T, E>` as a generic responding effect,
caught by `case Await(task), k` — remains unrepresentable for the same reasons as before: effect
applications must be closed, rows have no runtime identity, and a handler cannot cover every
application of a generic effect. The seam is worth having, but the carrier does not need applied
identity to provide it.

## Goals

- Add an `Await` effect that `await` performs, so async code has an interceptable boundary.
- Keep the effect payload non-generic and value-free: it exposes completion, not the result.
- Keep the existing observable surface: no keyword, no suspend modifier, no wrapper return type.
- Keep `main` ergonomic: awaiting in `main` requires no row and no `blocking(...)` wrapper.
- Install the blocking handler at the program entry boundary, including non-`Unit` entries.
- Preserve ZEP-0112's failure, cancellation, and scope-lifetime semantics as carried by
  [ZEP-0165](./ZEP-0165.md).
- Preserve row checking outside the entry point: non-entry code must declare or handle `Await`.
- Require no effect-row ABI, no open effect applications, no wildcard effect cases, and no reified
  class parameters.
- Keep `ConcurrentScope` and `Task` behavior unchanged; build on ZEP-0165's unified `Task` surface.

## Non-goals

- Generic `Await<T, E>` identity, `case Await<Int>` dispatch, or applied ancestry.
- Effect-row runtime descriptors, open effect applications, or wildcard/existential handler cases.
- Reified type parameters on classes.
- An erased join or any other value-returning bridge through an effect response.
- A checked-cast response helper; no value is recovered from the carrier.
- Named or first-class resuming handlers beyond the existing resuming-handler syntax.
- A non-blocking scheduler; that is [ZEP-0119](./ZEP-0119.md).
- Changing `Task.value()`, `Scope.start`, or ZEP-0165's unified `Task` surface.
- A source-level `main` wrapper requirement.
- Program arguments, thread pools, reactive streams, or parallel collections.
- Automatic conversion of host exceptions into effects.

## Proposal

### The `Await` effect

```zeron
package zeron.concurrent;

/// A non-generic view of a task's completion state.
public contract Completion {
    awaitDone(): Unit;
    isDone(): Boolean;
    isCancelled(): Boolean;
    mut cancel(): Unit;
}

public effect Await responds Unit {
    public property pending: Completion;
}
```

`Await` is a normal declared effect: it is non-generic, so it has no application descriptor and is
matched by its payload class. A handler case is therefore an ordinary nominal case:

```zeron
case Await as awaited, k -> k.resume(awaited.pending.awaitDone());
```

`Completion` deliberately erases the task's result type and effect row. A handler chooses **how to
wait**; it cannot choose **what value to return**, because it never returns a value. `awaitDone()`
waits without re-raising the outcome, so a failed or cancelled task returns normally to the handler;
the typed join reports the failure at the awaiting call site.

### `await`

```zeron
public fn await<T admits nullable + mutable, E admits effect...>(
    task: Task<T, E>
): T performs Await, E {
    perform Await.new(task.completion());
    return task.value();
}
```

The declared row has two parts, written as the comma-separated source row:

- `Await` for the control boundary;
- `E` for the task's own effects, which `task.value()` re-raises after the task is finished.

The first step only waits. A blocking handler resumes it once the task completes. The second step
does not block; it reads the typed result and re-raises `E`. The static type `T` comes from the
`Task<T, E>` argument, not from the effect response, so no cast and no bridge are involved.

`await` performs `Await`, so a non-entry caller must declare or handle it. The `E` part is checked at
the call site exactly as for `task.value()`.

### The blocking handler

The blocking policy is a normal resuming handler. A public wrapper is useful for explicit boundaries
and tests:

```zeron
public fn blocking<T admits nullable + mutable, E admits effect...>(
    body: () -> T performs Await, E
): T performs E =
    handle (body()) with {
        case Await as awaited, k -> k.resume(awaited.pending.awaitDone());
    };
```

The handler waits without reading the task. When it resumes, the `perform` expression yields
`Unit`, and the awaiting function continues to `task.value()`. The task's `E` remains on
`blocking`'s declared row and escapes from that join, exactly as it does without the wrapper.

### The entry boundary

The compiler treats `main` as having one implicit handler for `Await`. Its effects are removed from
the entry function's escaping row, so this is well-typed without a row:

```zeron
fn main(): Unit {
    using (let scope = ConcurrentScope.open()) {
        let task = spawn(scope, () -> load());
        println(await(task));
    }
}
```

The entry handler is installed around the generated launcher, not in user source. The launcher
pushes a resuming `Await` frame for the duration of:

- the call that produces a `Unit` or non-`Unit` entry value;
- the `Main<A>.run` interpretation of a non-`Unit` value.

The frame is host-side (`zeron.runtime.EntrySupport`): it recognizes an `Await` payload, waits for
its `Completion`, and resumes with `Unit`. Other carriers pass through unchanged. Because the frame
is a real handler frame, a direct `perform Await` resumes the awaiting function normally; no erased
join and no value recovery are needed at the boundary.

A captured effect raised inside a task is re-thrown at the join. A captured `Await` cannot be
resumed because the task body's continuation was already unwound; this slice does not add
continuation capture to task bodies. Awaiting outside a task is the supported direct-style path, and
ZEP-0119 owns resumable task bodies.

### Row rules

- **Entry point.** `Await` is handled implicitly. `main` may call `await` or any function whose row
  contains `Await` without declaring it. Unhandled task effects `E` still must be declared or
  handled; an unhandled `E` escapes to the host as it does today.
- **Non-entry code.** `Await` is an ordinary effect. A function that awaits, directly or through a
  callee, declares `performs Await` or handles it with `blocking`/an inline handler.
- **Task bodies.** A task body that awaits is an ordinary effectful body. Its `Await` is part of the
  task's captured row. Direct-style waiting inside a task body is deferred to ZEP-0119.
- **No implicit propagation.** Starting or spawning a task does not perform `Await`; only awaiting
  does.

This rule preserves effect checking while keeping the common `main` program free of async noise.

### Identity and runtime behavior

`Await` is a non-generic effect, so:

- it has no `AppliedTypeDescriptor` field and no descriptor comparison;
- a `case Await` matches every `Await` payload by erased class;
- the response is always `Unit`, so dispatch carries no value type.

This is intentional. `Await` is a control boundary, not a user-facing family such as `Failure<T>`.
If experience shows that user code needs `case Await<Int>`, that belongs to a future proposal that
opens effect applications and defines applied identity for control effects; this proposal does not
assume it.

The effect remains a ZEP-0118 responding effect, handled by the existing thread-local frame
machinery for direct awaits. The entry frame uses the same machinery.

### Failure and cancellation

No semantics change from ZEP-0112, as carried by ZEP-0165:

- a task failure is captured and re-raised by `Task.value()` at the boundary;
- `Task.cancel` and `ConcurrentScope.cancel` interrupt the task and unwind its `using` blocks;
- a cancelled task raises `java.util.concurrent.CancellationException` at the join;
- scope exit still joins or cancels outstanding tasks and leaves none running.

The handler does not translate cancellation or host exceptions into effects. `awaitDone()` never
reports the outcome; it only waits.

## Compatibility and impact

- **Source.** On top of ZEP-0165's `Task` surface, `await` changes from `performs E` to
  `performs Await, E`. Functions that await and are not the entry point must add `performs Await`
  or handle it. This is a source-visible change and needs a release note and a migration note in
  the structured-concurrency guide.
- **Entry point.** `main` source does not change: the implicit handler removes `Await` from its row.
  A program that previously spelled `fn main(): Unit performs Await` should drop the clause once the
  implicit handler lands.
- **Standard library.** Builds on ZEP-0165's unified `Task` surface. Adds `Completion`, the `Await`
  effect, and the `blocking` wrapper; `Task` gains `completion()`; `Task`, `ConcurrentScope`, and
  `Scope.start` behavior is otherwise unchanged.
  `STANDARD_LIBRARY_API_VERSION` is bumped once in the release cycle that includes this change,
  under the consolidation rule.
- **API index.** The new contract, effect, `completion()` member, `await` row, and public
  `blocking` wrapper are recorded. The generic effect descriptor schema is unchanged because
  `Await` is non-generic.
- **Runtime.** Non-generic effect payloads remain descriptor-free. The new runtime piece is the
  entry frame in `EntrySupport`; there is no new descriptor or class-reification layout. The
  nested `EffectSupport$Frame` class is emitted with the entry runtime support.
- **Tooling.** No grammar or formatter change. Highlighting already covers `effect`; no new keyword
  is introduced. The LSP sees a normal effect declaration and row.

## Alternatives

- **`Await` responds `Any?` with an erased join.** Rejected: the cast is unchecked, the erase
  bridge omits the task's `E`, and a handler can resume with an unrelated value.
- **Generic `Await<T, E>` with closed applications.** Rejected: a generic `await` cannot apply it,
  `E` has no runtime identity, and a handler cannot cover every application.
- **Generic `Await<T>` with reified `T`.** Rejected for this slice: it would require reification at
  every await call, still needs a wildcard/boundary handler, and buys exact identity the blocking
  policy does not use.
- **Reified type parameters on classes.** Rejected: `Await` is non-generic, and class reification is
  a broad layout and index change unrelated to the seam.
- **Effect-row ABI.** Rejected: rows are compile-time only; the handler waits on a completion and
  does not inspect the row.
- **Wildcard handler cases.** Rejected: a non-generic carrier gives the same coverage with an
  ordinary nominal case and no new syntax.
- **A source-level `main` wrapper.** Rejected: requiring `blocking(() -> ...)` in `main` defeats the
  ergonomics that motivate the carrier.
- **A thread-local frame only at the entry.** Implemented as the frame mechanism, but it handles
  direct performs only; captured task carriers are not resumable without continuation capture.
- **No carrier at all (ZEP-0165's blocking `Task` surface).** Acceptable fallback and the surface
  ZEP-0165 retains, but it leaves no interception seam for ZEP-0119 or for tests.

## Implementation and validation

Stages:

1. Add `Completion` and `Task.completion()`, the `Await` effect, `await` as a performing function,
   and the `blocking` wrapper.
2. Teach entry-point effect checking that `main` implicitly handles `Await`.
3. Install the host-side resuming frame around the generated entry launcher.
4. Update the structured-concurrency and raised-effects guides, and update the ZEP-0165 and
   ZEP-0126 cross-references.

Validation covers:

- `main` calls `await` directly and declares no `Await` row, for `Unit` entries.
- `await` inside an inline/`blocking` handler returns the task value and re-raises captured effects.
- A task failure re-raises its own effect at the join.
- Cancellation raises `CancellationException` and runs `using` cleanup.
- A non-entry function that awaits without declaring or handling `Await` gets a compile-time
  diagnostic.
- `blocking` works with a function value and as an explicit boundary.
- A separate-process launch finds the runtime support classes (`EntrySupport`,
  `EffectSupport`, and `EffectSupport$Frame`), not just the in-process test class loader.

## Open questions

Resolved on 2026-11-22:

1. **Visibility of `Await`.** Public. Asynchronous library functions need to name it in rows and
   handlers.
2. **Visibility of `blocking`.** Public. Tests can skip it, but library code needs it to propagate
   cancellation and to expose an explicit boundary.
3. **`erasedJoin`.** Removed. There is no value-returning bridge.
4. **Carrier family.** Only `Await`. No second member is being designed before ZEP-0119 ships.
5. **Entry shape.** Host-side `EntrySupport` frame installation around the generated launcher.
6. **Checked response cast.** No longer needed; the response is `Unit`.
7. **Row alias or super-effect.** Not now. Color is an important consideration for a future row
   alias, but this proposal does not add one.
8. **Effect splitting.** One `Await`. A future backend that needs to distinguish scheduling from
   joining can propose a second carrier then.

## Decision

Accepted on 2026-11-22. Revised for [ZEP-0165](./ZEP-0165.md) the same day so the payload carries
the unified `Task` handle. Redesignated on 2026-11-22: `Await` responds `Unit` and carries a
non-generic `Completion`; `await` performs the effect, then reads the finished task; `blocking` and
the entry frame only choose a waiting policy.

Acceptance approves the non-generic `Await` carrier, the `Completion` view, the
`performs Await, E` row, the public `blocking` wrapper, and the host-side entry frame. The earlier
erased `Any?` response and `erasedJoin` bridge are withdrawn. The resolved open questions above are
part of the accepted design; implementation details that do not change behavior remain ordinary
review work.
