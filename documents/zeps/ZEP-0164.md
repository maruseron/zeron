## Abstract

[ZEP-0120](./ZEP-0120.md) ships `await(future)` as an ordinary blocking call to `future.join()`.
That is ergonomic, but it gives the runtime no seam at which an await can be intercepted, traced, or
scheduled differently.

This proposal adds that seam without opening effect applications or changing the runtime descriptor
ABI. `Await` is a **non-generic** responding effect whose payload carries an erased view of a
future. `await<T, E>` performs `Await` and returns the handler's response as `T`. A blocking
handler joins the future and resumes with its value. The compiler treats the program entry point as
installing that handler, so `main` can await directly without declaring a row or calling a wrapper.
Carriers that were captured inside a task and re-raised at a join are handled at the same boundary.

The proposal deliberately keeps `Await` identity erased: it is a control effect with one meaning,
not a family of effects that user code dispatches by applied type. It adds no effect-row
representation, no wildcard handler syntax, and no reified class parameters.

## Motivation

ZEP-0120's `await` is a plain function, so a program's simplest async code already works:

```zeron
using (let scope = Scope.open()) {
    let first = spawn(scope, () -> load(1));
    let second = spawn(scope, () -> load(2));
    return await(first) + await(second);
}
```

That is the right default, and it should stay the observable behavior. But two needs are not met:

1. **Interception.** A test scheduler, tracing layer, or non-blocking backend cannot replace the
   blocking policy. `await` is compiled directly to `join`, so there is no handler to swap.
2. **Uniform effect composition.** ZEP-0119 and the effect model want `await` to participate in the
   effect row rather than disappear into a library call. This is what lets a caller reason about
   async work as an effect and lets a later handler decide how to schedule it.

The obvious design from the original ZEP-0120 draft — `Await<T, E>` as a generic responding effect,
caught by `case Await(future), k` — is not representable today:

- effect applications must be closed (`analyze/TypeResolver.validateEffectApplication`), so a
  generic `await` cannot apply `Await<T, E>`;
- `E` is a row and rows have no runtime representation, so `Await<..., E>` has no descriptor;
- a handler case cannot cover every application of a generic effect, and raw/wildcard cases are not
  part of ZEP-0005's closed-identity design;
- requiring reification of every awaited type would impose a new burden on callers and still would
  not solve handler coverage.

The seam is worth having, but the carrier does not need applied identity to provide it. This
proposal keeps the carrier nominal and erases its type arguments.

## Goals

- Add an `Await` effect that `await` performs, so async code has an interceptable boundary.
- Keep the existing observable surface: no keyword, no suspend modifier, no wrapper return type.
- Keep `main` ergonomic: awaiting in `main` requires no row and no `blocking(...)` wrapper.
- Install the blocking handler at the program entry boundary, including non-`Unit` entries.
- Handle `Await` carriers that were captured in a task and re-raised at a join.
- Preserve ZEP-0120's failure, cancellation, and scope-lifetime semantics.
- Preserve row checking outside the entry point: non-entry code must declare or handle `Await`.
- Require no effect-row ABI, no open effect applications, no wildcard effect cases, and no reified
  class parameters.
- Keep `Scope`, `Task`, and `Future` unchanged.

## Non-goals

- Generic `Await<T, E>` identity, `case Await<Int>` dispatch, or applied ancestry.
- Effect-row runtime descriptors, open effect applications, or wildcard/existential handler cases.
- Reified type parameters on classes.
- Named or first-class resuming handlers; the boundary handler is installed by the entry machinery.
- A non-blocking scheduler; that is [ZEP-0119](./ZEP-0119.md).
- Changing `Future`, `spawn`, `Scope.start`, or `Task.value` behavior.
- A source-level `main` wrapper requirement.
- Program arguments, thread pools, reactive streams, or parallel collections.
- Automatic conversion of host exceptions into effects.

## Proposal

### The `Await` effect

```zeron
package zeron.concurrent;

public effect Await responds Any? {
    public property future: Future<Any?, Effect>;
}
```

`Await` is a normal declared effect: it is non-generic, so it has no application descriptor and is
matched by its payload class. A handler case is therefore an ordinary nominal case:

```zeron
case Await as awaited, k -> k.resume(erasedJoin(awaited.future));
```

`erasedJoin` is the standard-library bridge that joins the erased future view and returns its value
as `Any?` while statically performing no effect; the task's own row is already declared at the
`await` call site. It responds with `Any?` because the response type is recovered from the `await`
call's static type, not from the effect's runtime identity. The payload holds an erased future
view; the task itself is the same ZEP-0112 task, not a copy.

`Effect` is the top effect type, so `Future<Any?, Effect>` is a closed, valid type argument. The
erased view is produced by a standard-library bridge function rather than written at every call
site.

### `await`

```zeron
public fn await<T admits nullable + mutable, E admits effect...>(
    future: Future<T, E>
): T performs Await + E =
    (perform Await.new(erased(future))) as T;
```

The declared row has two parts:

- `Await` for the control boundary;
- `E` for the task's own effects, which the handler re-raises by joining the future.

`await` performs `Await`, so a non-entry caller must declare or handle it. The response is cast to
`T`; the compiler already checks the `E` part at the call site, and the cast is correct by
construction because the handler joins the same future. A user-written `Await` handler must join
the payload's future; resuming an unrelated value is a programming error that surfaces as a normal
cast failure at the caller.

### The blocking handler

The blocking policy is a normal inline handler. A public wrapper is useful for explicit boundaries
and tests:

```zeron
public fn blocking<T admits nullable + mutable, E admits effect...>(
    body: () -> T performs Await + E
): T performs E =
    handle (body()) with {
        case Await as awaited, k ->
            k.resume(erasedJoin(awaited.future));
    };
```

`erasedJoin` returns the joined value as `Any?` while statically performing no effect. The task's
`E` still escapes at runtime and is covered by `blocking`'s declared row, exactly as `await`
declares it. The helper performs an erased view of the future, not a runtime conversion.

### The entry boundary

The compiler treats `main` as having one implicit handler for `Await`. Its effects are removed from
the entry function's escaping row, so this is well-typed without a row:

```zeron
fn main(): Unit {
    using (let scope = Scope.open()) {
        let future = spawn(scope, () -> load());
        println(await(future));
    }
}
```

The entry handler is installed around the generated launcher, not in user source. It must cover:

- the call that produces a `Unit` or non-`Unit` entry value;
- the `Main<A>.run` interpretation of a non-`Unit` value, which may itself await;
- carriers that escaped a task and are re-raised by `Task.value`/`Future.join` in the entry thread.

That last point rules out a thread-local frame push as the only mechanism. An effect raised inside a
task is captured as a `RaisedEffect` throwable and re-thrown at the join; it never re-enters
`EffectSupport.perform` on the entry thread. The boundary wrapper must therefore catch unhandled
`RaisedEffect` carriers around the whole entry and dispatch `Await` from the caught payload. Other
carriers keep propagating to the host as they do today.

Two implementation shapes satisfy this:

1. Synthesize the equivalent of `blocking(() -> entry())` around the launcher and compile it with
   the existing handler machinery.
2. Add a host-side `EntrySupport.runBlocking` that catches `RaisedEffect` at the boundary and joins
   an `Await` payload through a small bridge.

Both must install the handler only at the entry. Library code does not get an implicit handler.

### Row rules

- **Entry point.** `Await` is handled implicitly. `main` may call `await` or any function whose row
  contains `Await` without declaring it. Unhandled task effects `E` still must be declared or
  handled; an unhandled `E` escapes to the host as it does today.
- **Non-entry code.** `Await` is an ordinary effect. A function that awaits, directly or through a
  callee, declares `performs Await` or handles it with `blocking`/an inline handler.
- **Task bodies.** A task body that awaits is an ordinary effectful body. Its `Await` is captured at
  the task boundary and re-raised at the join, where the entry handler or an enclosing handler
  observes it.
- **No implicit propagation.** Starting or spawning a task does not perform `Await`; only awaiting
  does.

This rule preserves effect checking while keeping the common `main` program free of async noise.

### Identity and runtime behavior

`Await` is a non-generic effect, so:

- it has no `AppliedTypeDescriptor` field and no descriptor comparison;
- a `case Await` matches every `Await` payload by erased class;
- the response type is not part of runtime dispatch.

This is intentional. `Await` is a control boundary, not a user-facing family such as `Failure<T>`.
If experience shows that user code needs `case Await<Int>`, that belongs to a future proposal that
opens effect applications and defines applied identity for control effects; this proposal does not
assume it.

The effect remains a ZEP-0118 responding effect, handled by the existing thread-local frame
machinery for direct awaits. The entry wrapper adds the boundary catch described above.

### Failure and cancellation

No semantics change from ZEP-0120 and ZEP-0112:

- a task failure is captured and re-raised by `join` at the boundary;
- `Future.cancel` and `Scope.cancel` interrupt the task and unwind its `using` blocks;
- a cancelled task raises `java.util.concurrent.CancellationException` at the join;
- scope exit still joins or cancels outstanding tasks and leaves none running.

The handler does not translate cancellation or host exceptions into effects.

## Compatibility and impact

- **Source.** `await` changes from `performs E` to `performs Await + E`. Functions that await and
  are not the entry point must add `performs Await` or handle it. This is a source-visible change
  and needs a release note and a migration note in the structured-concurrency guide.
- **Entry point.** `main` source does not change: the implicit handler removes `Await` from its row.
  A program that previously spelled `fn main(): Unit performs Await` should drop the clause once the
  implicit handler lands.
- **Standard library.** Adds the `Await` effect and the `blocking` wrapper; `Future`, `spawn`,
  `Scope`, and `Task` are unchanged. `STANDARD_LIBRARY_API_VERSION` advances once for the change.
- **API index.** The new effect class and the new `await` row are recorded. The generic effect
  descriptor schema is unchanged because `Await` is non-generic.
- **Runtime.** Non-generic effect payloads remain descriptor-free. The only new runtime piece is the
  entry-boundary catch/dispatch; there is no new descriptor, bridge method, or class-reification
  layout.
- **Tooling.** No grammar or formatter change. Highlighting already covers `effect`; no new keyword
  is introduced. The LSP sees a normal effect declaration and row.

## Alternatives

- **Generic `Await<T, E>` with closed applications.** Rejected: a generic `await` cannot apply it,
  `E` has no runtime identity, and a handler cannot cover every application.
- **Generic `Await<T>` with reified `T`.** Rejected for this slice: it would require reification at
  every await call, still needs a wildcard/boundary handler, and buys exact identity the blocking
  policy does not use.
- **Reified type parameters on classes.** Rejected: `Await` is non-generic, and class reification is
  a broad layout and index change unrelated to the seam.
- **Effect-row ABI.** Rejected: rows are compile-time only; the handler joins a future and does not
  inspect the row.
- **Wildcard handler cases.** Rejected: a non-generic carrier gives the same coverage with an
  ordinary nominal case and no new syntax.
- **A source-level `main` wrapper.** Rejected: requiring `blocking(() -> ...)` in `main` defeats the
  ergonomics that motivate the carrier.
- **A thread-local frame only at the entry.** Rejected: it misses `Await` carriers re-raised from
  task joins, which never re-enter `perform` on the entry thread.
- **No carrier at all (ZEP-0120 status quo).** Acceptable fallback and what ships today, but it
  leaves no interception seam for ZEP-0119 or for tests.

## Implementation and validation

Stages:

1. Add the standard-library `Await` effect, the erased future bridge, `await` as a performing
   function, and the `blocking` wrapper.
2. Teach entry-point effect checking that `main` implicitly handles `Await`.
3. Install the boundary handler around the generated entry launcher and the non-`Unit` entry
   interpretation. It must catch unhandled `RaisedEffect` carriers, not just push a frame.
4. Extend the structured-concurrency guide and the raised-effects guide, and update the ZEP-0120
   cross-reference.

Validation should cover:

- `main` calls `await` directly and declares no `Await` row, for both `Unit` and non-`Unit` entries.
- `main` calls a helper whose row contains `Await`; the entry handler covers it.
- A task body awaits and the entry thread joins the task; the re-raised `Await` is handled at the
  boundary, not left as a host exception.
- A non-entry function that awaits without declaring or handling `Await` gets a compile-time
  diagnostic.
- `blocking` works as an explicit boundary and composes with nested handlers.
- A task failure still re-raises its own effect at the join, unaffected by the carrier.
- Cancellation still raises `CancellationException` and runs `using` cleanup.
- A reflection-based test that calls the user `main()` directly bypasses the launcher; tests must
  invoke the entry launcher or install the boundary explicitly.
- Separate-compilation tests confirm the non-generic effect payload and `await` row survive a
  library-index round trip with no schema change.
- The standard-library bridge can cast `Future<T, E>` to `Future<Any?, Effect>` and back without a
  new ABI. If the resolver rejects invariant contract-instantiation casts, the bridge needs an
  internal external helper rather than a source-level cast.

## Open questions

- Should `Await` be public and handleable by user code, or internal to the boundary machinery? A
  public effect is more uniform; an internal one prevents accidental wrong-value resumption.
- Should `blocking` be a public API or only an implementation detail of the entry boundary?
- Should the boundary handler eventually cover a family of async carriers, or only the concrete
  `Await` effect?
- Is a host-boundary `EntrySupport` cleaner than generating a synthetic `blocking` wrapper around
  the launcher? The generated wrapper reuses handler code; the host boundary avoids new source
  synthesis.
- Should the erased response use a checked cast helper with its own diagnostic, or is the caller's
  normal cast failure enough?
- Do non-entry async rows need a row alias or super-effect once `Await` is added everywhere?
- Does `Await` remain a single effect if a later backend needs to distinguish scheduling from
  joining, or does that split into separate carriers?
