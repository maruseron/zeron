> **Implementation note (2026-11-24).** Implemented. `zeron.concurrent` has one eager `Task<T, E>`
> handle with `spawn`, `await`, `value`, `isDone`, `isCancelled`, `cancel`, and `completion()`;
> `Future` and `FutureImpl` are gone. `AsyncTaskTest` covers virtual-thread values,
> `await(scope.start(...))`, `blocking`, captured-effect re-raising with its negative diagnostic,
> cancellation at `value()` with `using` cleanup, and a child-process entry launch. A library-index
> test records `Task`, `spawn`, and `await`, preserves the `Task<T, E>` parameter and `Await + E`
> row across separate compilation, and checks that no `Future` declaration remains. Cancellation
> also reaches a body suspended in a continuation through ZEP-0119's `CancellationSupport`.

## Abstract

Collapse `zeron.concurrent.Future` into `zeron.concurrent.Task`. `Task` becomes the single
eager handle for work started in a `ConcurrentScope`; `spawn(scope, body)` returns `&Task<T, {E}>`, and
`await(task)` accepts a `Task<T, E>` and joins it.

The blocking direct-style policy does not change. `Task` remains an in-flight handle, not a lazy
computation and not a monad. `Task.value()` remains the join method; `await(task)` is its
async-facing spelling. `Future` and `FutureImpl` are removed. This proposal supersedes the `Future`
type and the `spawn`/`await` signatures of [ZEP-0120](./ZEP-0120.md) while retaining that
proposal's blocking surface, effect capture, cancellation, and structured-scope semantics.

## Motivation

[ZEP-0120](./ZEP-0120.md) introduced `Future<T, E>` as a "direct-style convenience layer" over
[ZEP-0112](./ZEP-0112.md)'s `Task<T, E>`. The implementation is not a layer. It is a transparent
forwarding wrapper:

```zeron
class FutureImpl<T admits nullable + mutable, E admits effect...> is Future<T, {E}> {
    task: &Task<T, {E}>;

    public constructor new;

    public join(): T performs E = this.task.value();
    public isDone(): Boolean = this.task.isDone();
    public isCancelled(): Boolean = this.task.isCancelled();
    public mut cancel(): Unit = this.task.cancel();
}
```

`spawn` is `FutureImpl.new(scope.start(body))`, and `await` is `future.join()`. There is no
difference in scheduling, lifetime, effect capture, cancellation, or runtime representation. The
wrapper adds one allocation and one indirection per handle and nothing else.

The separation arguments in ZEP-0120 do not survive the implementation:

- **"`Task` exposes `value()` rather than the async vocabulary."** That is a method name. The
  async vocabulary is the free function `await(task)`; it does not require a second handle type.
- **"Users must thread `Task<T, {E}>` through signatures."** `Future<T, E>` has exactly the same
  parameters. It does not reduce what users thread; it adds a second name to choose between.
- **"`Scope.start` returns a read-only task view, so a handle cannot be cancelled without
  cancelling the whole scope."** ZEP-0120 itself fixes this by changing `Scope.start` to return
  `&Task` (`ZEP-0120.md`, "The `Scope.start` reference capability"). The mutable reference is the
  fix. `spawn` returns `&Future`; a unified `spawn` returns `&Task` with the same capability.

The split also collides with the design's own terminology. `task.zn` says monadic composition
belongs to a separate deferred abstraction, and ZEP-0112 calls that lazy abstraction `Deferred`.
`Future` conventionally names a deferred computation, so using it for an eager handle is
misleading; it would leave `Task` and `Future` as two names for one concept while `Deferred`
already owns the lazy name.

Finally, the two types are not interchangeable at API boundaries. A function taking `Task<T, E>`
cannot accept a `Future<T, E>`, there is no conversion between them, and `await` accepts only
`Future`. A user cannot write a helper over "a handle" without choosing one type. The async
surface is therefore not on the primitive handle at all: `await(scope.start(...))` does not
type-check.

`0.9.0` is unreleased, so this is a pre-release API correction rather than a shipped breaking
change. Collapsing now costs one small standard-library change; removing `Future` after the release
would require a deprecation cycle.

## Goals

- Make `Task<T, E>` the single eager handle for work started in a `ConcurrentScope`.
- Change `spawn(scope, body)` to return `&Task<T, {E}>`.
- Change `await(task)` to accept `Task<T, E>` and join it through `Task.value()`.
- Remove `Future` and `FutureImpl` from the standard library and the public API index.
- Preserve ZEP-0112's `ConcurrentScope`, `Task.value()`, `isDone()`, `isCancelled()`, `mut cancel()`,
  effect-capture, cancellation, deadline, and structured-shutdown semantics.
- Keep the blocking direct-style policy: no keyword, suspend modifier, wrapper return type, or
  monadic composition.
- Keep [ZEP-0164](./ZEP-0164.md)'s non-generic `Await` carrier compatible by giving its payload a
  clean `Completion` view of the unified `Task`.
- Keep the wrapper removal free of new runtime machinery; the companion ZEP-0164 only adds the
  `TaskSupport.waitDone` query and the `Completion` view on the existing task, with no
  library-index-schema change.
- Move only the `spawn`/`await` descriptors from `Future` to `Task`; `ScopeSupport` and the core
  `TaskSupport` protocol stay unchanged.

## Non-goals

- A monadic `map`/`flatMap`/`do` surface on `Task`.
- A lazy `Deferred` or any other deferred-computation abstraction. That remains a separate future
  design.
- Renaming `Task.value()` to `join()` in this proposal. It is a naming change to ZEP-0112's
  surface and is not required to unify the handle types.
- Adding `onComplete`, `onFailure`, `onCancel`, or other callback combinators. They need their own
  execution-context, effect, and scope-lifetime rules.
- Changing `ConcurrentScope` semantics, cancellation, deadlines, effect capture, or the runtime
  `ScopeSupport`/`TaskSupport` protocol.
- A non-blocking backend; that is [ZEP-0119](./ZEP-0119.md).
- The `Await` carrier, its handler, or the blocking entry point; those are
  [ZEP-0164](./ZEP-0164.md).
- Changing `STANDARD_LIBRARY_API_VERSION` again within the unreleased `0.9.0` cycle.

## Proposal

### The unified `Task` surface

`Task` is unchanged from ZEP-0112:

```zeron
public contract Task<T admits nullable + mutable, E admits effect...> {
    value(): T performs E;
    isDone(): Boolean;
    isCancelled(): Boolean;
    mut cancel(): Unit;
}
```

`value()` is the only join point. It blocks the current virtual thread, returns the task's value, or
re-raises the task's captured effect or cancellation. `isDone()` and `isCancelled()` are ordinary
observations and do not perform the task's effects.

### `spawn`

```zeron
public fn spawn<T admits nullable + mutable, E admits effect...>(
    scope: &ConcurrentScope,
    body: () -> T performs E
): &Task<T, {E}> =
    scope.start(body);
```

`spawn` is now a one-line forwarding function over `Scope.start`. It remains the free-function
spelling used by the async surface and by ZEP-0164's erased carrier; it is not a second concurrency
model. The returned mutable view lets a caller cancel that one task, exactly as `Scope.start`
already does.

Starting the body does not perform `E`. The body's effects are captured as the task outcome and
re-raised at `value()` or `await`.

### `await`

```zeron
public fn await<T admits nullable + mutable, E admits effect...>(
    task: Task<T, E>
): T performs E =
    task.value();
```

`await` is an ordinary blocking function. It takes the read-only `Task` view, so it accepts both a
`Task` and a `&Task` from `spawn`/`Scope.start`. It adds no row label of its own: the only escaping
effects are the task's `E`, which `value()` re-raises.

### Usage

```zeron
using (let scope = ConcurrentScope.open()) {
    let first = spawn(scope, () -> load(1));
    let second = scope.start(() -> load(2));
    return await(first) + await(second);
}
```

Both handles are `Task<T, E>`, and both are accepted by `await`. The same example can use
`first.value()` and `second.value()` without `await`; the two spellings are equivalent.

### Removed surface

`Future` and `FutureImpl` are deleted. There is no alias, subtype, or conversion. `Future.join()`
is replaced by `Task.value()` or `await(task)`. Because `0.9.0` is unreleased, no shipped program
depends on the removed type.

### Relationship to ZEP-0120

This proposal supersedes ZEP-0120's `Future<T, E>` type and its `spawn`/`await` signatures:

- `spawn` returns `&Task<T, {E}>` instead of `&Future<T, {E}>`;
- `await` accepts `Task<T, E>` instead of `Future<T, E>`;
- `Future` and `FutureImpl` are removed.

The blocking direct-style policy is retained: no `async`/`await` keyword, no suspend modifier, no
wrapper return type, no continuation capture, and no monadic surface. Failure, cancellation,
scope-lifetime, and effect-capture rules are ZEP-0112's, unchanged.

### Relationship to ZEP-0112

`Scope.start` already returns `&Task<T, {E}>`, and `Task.value()` is unchanged. This proposal
removes the wrapper that ZEP-0120 placed around those primitives; it does not change the primitive
itself. The lazy `Deferred` mentioned in ZEP-0112 remains a separate, unimplemented abstraction.

### Relationship to ZEP-0164

[ZEP-0164](./ZEP-0164.md)'s non-generic `Await` carrier is compatible with this proposal, and the
collapse makes it simpler: there is one handle type, so `Task` can expose the non-generic view
directly.

- `Await` responds `Unit` and carries `Completion`, implemented by the same `TaskImpl` that
  implements `Task`;
- `await` performs `Await`, then returns `task.value()`, so the value comes from the typed handle
  rather than an effect response;
- `Task` gains `completion(): Completion`, and no erased `Task<Any?, Effect>` view or `erasedJoin`
  bridge is needed;
- ZEP-0164's goal "Keep `ConcurrentScope`, `Task`, and `Future` unchanged" becomes "Keep `ConcurrentScope` and `Task`
  unchanged";
- ZEP-0164's validation uses ordinary `Task<T, E>` values and the `Completion` interface, with no
  variance cast between applied types.

The carrier, handler, entry-boundary, and row rules are otherwise unchanged.

### Naming

`Task` is the surviving name. It is the established primitive, the runtime is already
`TaskSupport`, and `Scope.start` already returns `&Task`. `Future` conventionally denotes a
deferred computation, `Deferred` already owns that name, and `Future` also collides with
`java.util.concurrent.Future` in Java interop.

`value()` remains the join method to keep ZEP-0112's surface stable. The async-facing spelling is
`await(task)`, not a second method. Renaming `value()` to `join()` is a possible follow-up; it is
not part of this collapse.

## Compatibility and impact

- **Source.** `spawn` changes from `&Future<T, {E}>` to `&Task<T, {E}>`; `await` changes from
  `Future<T, E>` to `Task<T, E>`; `Future` and `FutureImpl` are removed. Since `0.9.0` is
  unreleased, this is a pre-release correction. Any preview code that names `Future` should replace
  it with `Task`; `future.join()` becomes `task.value()` or `await(task)`.
- **Standard library.** The public API loses one contract, and the library loses its `FutureImpl`
  wrapper. The `spawn`/`await` signatures change. `STANDARD_LIBRARY_API_VERSION` remains 21 because
  this is the same unreleased release cycle; the API index is regenerated.
- **Runtime.** The unification itself adds no runtime machinery. The wrapper allocation and
  forwarding indirection are removed. The joint ZEP-0164 implementation adds
  `TaskSupport.waitDone` and implements `Completion` on the existing task; `ScopeSupport` is
  untouched.
- **ABI and descriptors.** `ConcurrentScope`, `ScopeSupport`, and the compiled `TaskImpl` shape keep their
  descriptors, apart from the `Completion` conformance and `completion()`/`awaitDone()` methods.
  `TaskSupport` gains `waitDone`. `spawn` and `await` change their erased `Future` descriptor to
  `Task`, and `Future`/`FutureImpl` are removed. This is a library API/ABI correction within the
  unreleased `0.9.0` cycle, not a runtime ABI change.
- **Tooling.** No grammar, formatter, or highlighter change. The LSP and API index simply expose one
  fewer contract.
- **Documentation.** The structured-concurrency guide merges its `Task` and `Future` sections. The
  `0.9.0` changelog entry is rewritten to describe the unified `Task` surface when the change is
  implemented. ZEP-0120 is marked Superseded; ZEP-0164's `Future` references are updated to `Task`.
- **ZEP-0164.** The carrier design is unaffected in substance. Its payload and `await` signature
  change mechanically to `Task`; its `Future`-specific goal and validation text are updated in its
  revised draft.

## Alternatives

- **Keep both `Task` and `Future`.** Rejected: `Future` is a transparent forwarding wrapper with
  no semantic distinction, and the two types are not interchangeable at API boundaries.
- **Keep `Future` and remove `Task`.** Rejected: it churns `Scope.start`, `TaskSupport`,
  `TaskImpl`, ZEP-0112, and the guide; `Future` conventionally denotes deferred work, `Deferred`
  already owns that name, and `Future` also collides with Java's `java.util.concurrent.Future`.
- **Rename `Task.value()` to `join()` in the same change.** Deferred: it changes ZEP-0112's
  surface and is not required to unify the handle types. It can be a separate naming proposal or a
  deprecated alias later.
- **Add `join()` as an alias while keeping `value()`.** Rejected: two names for one operation. The
  async-facing spelling is the free function `await(task)`.
- **Make `Future` a subtype or alias of `Task`.** Rejected: it still exposes two names for one
  handle. The language has no transparent type aliases, and a nominal `type` declaration would
  introduce a distinct type rather than erase the second name from signatures.
- **Make `Task` monadic or lazy.** Rejected: the accepted design is a blocking direct-style handle,
  not a deferred computation. A lazy `Deferred` is a separate abstraction.
- **Add callbacks now.** Rejected: `onComplete`/`onFailure`/`onCancel` need their own execution
  context, effect policy, registration-after-completion rule, and scope-lifetime rule. They belong
  on the one handle eventually, but in a separate proposal.

## Implementation and validation

Stages:

1. Move `spawn` and `await` from `future.zn` into `task.zn`; change their signatures to `&Task` and
   `Task`; delete `future.zn` and `FutureImpl`.
2. Update the standard-library documentation comments and the API index; confirm no `Future` entry
   remains.
3. Update the structured-concurrency guide to one `Task` section, and rewrite the `0.9.0` changelog
   entry when the implementation lands.
4. Update ZEP-0164's payload to the unified handle's `Completion` view; do not change its carrier,
   handler, or entry-boundary design here.
5. Add regression coverage for the unified surface.

Validation should cover:

- `spawn` plus `await` returns values on virtual threads, and `await(scope.start(...))` compiles and
  runs with no `spawn` wrapper.
- `await` re-raises a captured effect and checks the caller's row, including a negative diagnostic
  for an unhandled effect.
- Cancellation through `task.cancel()` and `scope.cancel()`, including `using` cleanup and
  `CancellationException` at the join.
- `Task.value()`, `isDone()`, `isCancelled()`, and `mut cancel()` are unchanged from ZEP-0112's
  regression suite.
- The public API index contains `Task`, `spawn`, and `await`, and no `Future` or `FutureImpl`.
- A separate-compilation round trip preserves the `Task`/`spawn`/`await` signatures and the `E` row.
- Runtime and `Task` ABI limited to the companion `Completion` surface: `ScopeSupport` is
  untouched, `TaskSupport` adds `waitDone`, `TaskImpl` gains `completion()`/`awaitDone()`, and
  the `spawn`/`await` descriptors plus the removed `FutureImpl` are the remaining differences.
- When ZEP-0164 is implemented, `Await` carries the same task's `Completion`, and the handler's
  `awaitDone()` plus the typed `task.value()` complete without an erased carrier or value cast.

## Open questions

- Should `Task.value()` be renamed to `join()` in a later naming proposal? The current change keeps
  `value()` to avoid touching ZEP-0112's surface.
- Should `spawn` remain a free-function spelling over `Scope.start`, or should the async surface use
  `scope.start` exclusively? Keeping `spawn` preserves the async-facing spelling and ZEP-0164's
  source compatibility.
- Should `onComplete`/`onFailure`/`onCancel` be added to `Task`? If so, they need a separate
  proposal covering execution context, effect behavior, registration after completion, and scope
  lifetime.
- Should a lazy `Deferred` be added as the separate deferred abstraction ZEP-0112 reserves? It is
  outside this proposal.

## Decision

Accepted on 2026-11-22. `Future` is a transparent forwarding wrapper around `Task`, not a separate
abstraction: the only differences are the `join`/`value` method names and the `spawn`/`Scope.start`
factory. ZEP-0120's separation arguments reduce to a method-name preference and a mutable-handle
capability that ZEP-0120 itself supplied by changing `Scope.start` to `&Task`. The two types are
also incompatible at API boundaries, and `await` is unavailable on the primitive `Task` handle.

The accepted direction is one eager handle: `Task<T, E>` keeps `value()`, `spawn` returns
`&Task<T, {E}>`, and `await` accepts `Task<T, E>`. `Future` and `FutureImpl` are removed. The
blocking direct-style policy, effect capture, cancellation, deadlines, and structured shutdown are
unchanged. The lazy `Deferred` abstraction remains separate.

This supersedes ZEP-0120's `Future` type and its `spawn`/`await` signatures while retaining the
rest of ZEP-0120's blocking surface. ZEP-0164's carrier design remains valid with `Task` as its
payload; its `Future` references and `await` signature are updated to `Task` in its revised design,
and [ZEP-0164](./ZEP-0164.md) was accepted the same day as this proposal's carrier companion.
