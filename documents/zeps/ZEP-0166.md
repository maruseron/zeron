## Abstract

Allow an applied generic effect to mention open type parameters, so a signature such as
`() -> Unit performs Yield<T>` is valid inside a generic declaration. The effect keeps its nominal
identity, and a call that substitutes `T` produces the same closed application that exists today.

## Motivation

Effect rows currently accept only closed generic applications. `TypeResolver.validateEffectApplication`
rejects any argument that is a type parameter, projection, function, row, or inference variable:

```
Effect application `zeron.lang.Yield<T>` must be closed;
`T` is not a closed type argument.
```

That restriction blocks ordinary generic composition. A generic generator cannot declare
`body: () -> Unit performs Yield<T>`, a generic forwarding helper cannot preserve a caller's row,
and a generic handler cannot state the effect it handles without repeating every instantiation. The
workaround is to erase the body to `Any` and recover the element type at runtime, which removes the
static effect check and makes the generator surface less direct:

```zeron
// Desired
public fn generator<T admits mutable>(
    body: () -> Unit performs Yield<T>
): GeneratorSource<T>

// Current workaround
public fn generator<T admits mutable>(body: Any): GeneratorSource<T>
```

This proposal addresses the type-system and API-index shape only. It does not add row
polymorphism, effect subtraction, wildcard handler cases, or generic reification.

## Goals

- Accept open applied effects in value, function, handler, and contract type positions.
- Preserve nominal effect identity and the existing closed application for monomorphic call sites.
- Define equality, substitution, and inference for applications containing type parameters.
- Record open applications in separately compiled API metadata.
- Keep runtime dispatch and effect identity unchanged.

## Non-goals

- Effect-row polymorphism, row variables in effect applications, or row subtraction.
- Wildcard or existential handler cases such as `case Yield<_>`.
- Runtime discrimination between `Yield<Int>` and `Yield<String>`.
- Reifying generic arguments, or changing `EffectValue`/payload representation.
- Making generic *external* (Java-bound) functions legal.

## Proposal

### Accepted forms

An effect application may contain any well-formed type argument, including:

```zeron
public effect Yield<T> responds Unit { public property value: T; }

public fn numbers<T admits mutable>(): Unit performs Yield<T> { ... }

public fn forward<T, E admits effect...>(body: () -> Unit performs E): Unit performs E =
    body();

public fn consume<T>(value: T): Unit performs Yield<T> = perform Yield<T>(value);
```

Nested applications remain allowed when their arguments are well-formed:
`Yield<Option<T>>`, `Yield<Box<T>>`. An effect application may not use an effect-row type in a
value-type position, and effect arguments remain limited to the effect grammar.

### Identity and equality

An open application is keyed by the effect declaration plus its ordered argument descriptors.
Arguments compare structurally. A type-parameter argument compares by its declaration identity
(owner and index), not by its lexical name, so two declarations that both spell `T` do not
accidentally share an identity.

Substitution is pointwise. At a call site, substituting `T := Int` turns `Yield<T>` into
`Yield<Int>`; after substitution the row is closed and matches existing behavior. A row containing
two applications of the same effect with different arguments remains a distinct set of effects,
not a merged or least-upper-bound effect.

### Runtime behavior

The payload class for `Yield<T>` is erased to `zeron.lang.Yield`, as it is today. Open applications
therefore create no new runtime class, descriptor, or handler identity. Dispatch still matches the
payload class; an open handler catches every instantiation it can receive.

The compiler must not emit a runtime type test for an open argument. A `case Yield<T>` that names an
open parameter is a static binding of the payload, not a check that the payload is
`Yield<Int>`. If a handler needs to distinguish instantiations, it must inspect the payload's value
or operate on a closed application.

### Inference

Generic inference unifies applied effects structurally:

- `Yield<T>` against `Yield<Int>` solves `T := Int`;
- `Yield<T>` against `Yield<Option<Int>>` solves `T := Option<Int>`;
- `Yield<T>` against `Ask<Int>` fails with the effect name in the diagnostic;
- `Yield<T>` against `Yield<U>` relates the two parameters by an equality constraint.

A lambda passed to `() -> Unit performs Yield<T>` infers its own row and unifies it with the
parameter. This is what makes the intended trailing-lambda `generator { perform Yield<Int>(0) }`
form work once the signature is expressible.

### API metadata

Separately compiled declarations must store open applications with references to their declaring
type parameters. This requires an API-index schema revision. A reader that does not understand the
new form must reject the index version rather than silently treating `Yield<T>` as `Yield<Any>` or
as an unapplied `Yield`.

Function-shape identity and witness selection must use the open form consistently: two declarations
that differ only in the identity of an argument type parameter are different shapes. The JVM
descriptors remain erased and unchanged.

## Compatibility and impact

- Source: strictly widening. Programs that compile today keep their meaning; previously rejected
  generic signatures become legal.
- Runtime: no change to payload classes, `EffectSupport`, `Level3Support`, or handler dispatch.
- API index: a schema revision is required. This is the main separately compiled compatibility cost.
- Diagnostics: the “must be closed” diagnostic is replaced by argument-well-formedness and
  inference diagnostics. Existing closed-application errors keep their codes where possible.
- Generators: the standard-library `generator` takes `body: () -> Unit performs Yield<T>`
  directly and infers `T` from the lambda.
- Handlers: no new runtime expressiveness; open cases are static descriptions of an erased carrier.

## Alternatives

- **Erase every open application to `Yield<Any>`** — rejected. It silently accepts mismatched
  yields and loses the payload type at the call site.
- **Drop the arguments and use a raw `Yield`** — rejected for the same reason; applied identity is
  the point of [ZEP-0005](./ZEP-0005.md).
- **Special-case `generator` in the compiler** — rejected. It would hide a general limitation behind
  one library function and leave every other generic effect combinator broken.
- **Wait for full row polymorphism** — rejected as a prerequisite. Open applications do not need row
  subtraction, and the generator surface is blocked on the narrower feature.
- **Reject open applications forever and keep `Any` boundaries** — rejected. It forces an unchecked
  boundary into every generic effect API, which is worse than the metadata cost.

## Implementation and validation

1. Extend the effect descriptor and equality/canonical-key code to represent open arguments.
2. Relax `validateEffectApplication` and add inference/unification for applied effects.
3. Thread substitution through call resolution, handler cases, and contract requirements.
4. Revise the API-index schema and the separately compiled reader/writer.
5. Update diagnostics and remove the `Any` workaround from `generator` once the signature compiles.

Validation should cover:

- open applications in functions, function types, handlers, contracts, and generic constraints;
- inference from a lambda row and from explicit arguments;
- substitution into monomorphic call sites and into nested applications;
- identity of two same-named type parameters from different declarations;
- an open handler case over multiple instantiations, confirming the payload class match is unchanged;
- separately compiled libraries reading and writing the new index form;
- canonical function-shape keys for declarations that differ only by type-parameter identity;
- negative tests for effect-row arguments in value positions and arity mismatches.

## Open questions

- Should `Yield<Yield<Int>>` be legal? The arguments are well-formed, but nested carriers are
  probably meaningless; this may need a diagnostic rather than a silent acceptance.
- Does an open handler case create an implicit existential that should be nameable, or is the
  payload simply typed as the unsubstituted argument with no runtime evidence?
- Should the API index store a canonical type-parameter index, or a hash of the declaration
  identity, to remain stable across recompilation of a library?
- Is a schema bump avoidable by encoding open arguments in an existing descriptor extension, or is
  a clean revision preferable?

## Decision

Implemented 2026-11-23. Open applied effects are accepted in type positions, preserved by
substitution, and unified structurally during call and lambda inference. The standard-library
`generator` takes `body: () -> Unit performs Yield<T>, DisposeFailure` directly, including its
trailing-lambda form.

The API index already represents open applications using its existing type-parameter reference
encoding, so no wire-format change or schema bump was required. Round-trip tests read the open
application back and verify that its argument is the declaring function's type parameter; a
separately compiled client then infers and uses the same signature. Runtime construction from a
non-reified generic body remains unsupported, as recorded in the open questions, and runtime
dispatch still matches only the erased effect class.
