# ZEP-0167: Capability Requirements in Generic Type Arguments

## Abstract

Separate what a generic declaration *requires* from a type argument from what instantiations it
*allows*, and check the former against the argument's guarantees. This replaces the current exact
capability matching, which rejects safe compositions such as passing an
`A admits nullable + mutable` to a parameter whose body only ever uses mutability.

## Motivation

Capability markers are currently checked as if the target parameter had to permit every capability
of the argument. Generic code therefore fails in shapes that are intuitively safe:

```
Type parameter 'T' does not admit mutable-reference type argument 'T'.
Type parameter 'T' does not admit nullable type arguments.
```

The first blocked `Yield<T>` when `T admits mutable`; the second blocked a nullable-admitting
`GeneratorSource<T>` from satisfying `Iterable<T>`. In both cases the target body does not use the
extra capability, but the checker compares declaration markers rather than body requirements.

A single `admits` clause currently carries two different meanings:

- **allowed:** the declaration may be instantiated with a type that has this capability;
- **required:** the body actually performs an operation that needs this capability.

Conflating them forces an all-or-nothing choice: either reject safe applications, or weaken every
declaration to admit everything. This proposal separates the two and derives requirements from use.

## Goals

- Define capability requirements for each type parameter from the declaration body and its
  transitive callee requirements.
- Accept an argument when its guaranteed capabilities cover the parameter's requirements.
- Keep the declaration's `admits` markers as the public set of allowed instantiations.
- Produce diagnostics that name the missing capability and where it is required.
- Record requirements in separately compiled API metadata.

## Non-goals

- Whole-program escape analysis or ownership/borrow checking.
- Effect-row bounds and `admits effect...` substitution; those remain row-kind rules.
- `admits scoped`; [ZEP-0162](./ZEP-0162.md) owns scoped admissibility.
- Changing the meaning of `admits` for classes that are used as values rather than type arguments.
- Inferring capabilities for local variables or parameters that are not type parameters.

## Proposal

### Two sets per type parameter

For a declaration `C<T admits nullable + mutable>`:

- **Allowed set** is the declared marker set. It states which instantiations the declaration accepts.
- **Required set** is inferred. It contains a capability only when the body, or a callee after
  substitution, performs an operation that needs it.

The declaration is valid when `required ⊆ allowed`. An application `C<A>` is valid when
`required(C.T) ⊆ guaranteed(A)`. Extra capabilities in `A` are irrelevant to `C`'s body.

### Inferring requirements

The initial analysis is syntactic and intra-declaration:

- `mutable` is required when the body forms `&T`, passes `T` where a mutable reference is required,
  or calls a mutable method on a value of type `T`.
- `nullable` is required when the body performs a null-sensitive operation on `T`: calling a method
  through a `T` receiver where a null receiver would fail, projecting a field, or otherwise using
  `T` in a position that assumes non-null without a prior null check. Operations that are null-safe,
  such as identity comparison, do not require it.
- If the body passes `T` to another generic declaration `D<U>`, the requirement is `D.U`'s required
  set after substituting `U := T`. Those requirements are propagated outward.

The analysis must be conservative: when an operation's null behavior is not obvious, it requires
`nullable`. Requirements are part of the declaration's public shape and must not depend on the
instantiation.

### Examples

```zeron
// Yield stores and returns T; it never inspects nullness or forms &T.
public effect Yield<T> responds Unit { public property value: T; }

// T admits mutable is accepted because Yield requires nothing of T.
public fn emit<T admits mutable>(value: T): Unit performs Yield<T> =
    perform Yield<T>(value);
```

```zeron
// Iterable's iterator protocol does not require nullable or mutability from T itself.
public fn collect<T admits mutable>(source: Iterable<T>): Array<T> { ... }

// A nullable-admitting source can be passed when Iterable requires nothing it lacks.
public fn fromNullable<T admits nullable + mutable>(source: Iterable<T>): Int { ... }
```

```zeron
// Rejected: the body forms &T, so it requires mutable from T.
class Holder<T> {
    value: T;
    public mut replace(next: T): Unit = this.value = next;
}

// Accepted: the declaration admits the capability its body uses.
class MutableHolder<T admits mutable> {
    value: T;
    public mut replace(next: T): Unit = this.value = next;
}
```

### Checking applications and forwarding

At a call site the argument's guaranteed capabilities are substituted for the parameter. The
argument must cover every requirement, including requirements reached only through forwarding. A
type parameter used as an argument is checked by its own *allowed* set at the declaration, and by
the eventual actual argument's guarantees after substitution.

This means an open application in a signature such as `Yield<T>` records no requirement on `T`,
while a signature that forwards `T` into a mutating helper records `mutable` on `T`.

### Diagnostics

Replace the current capability errors with two forms:

```
Type argument `A` does not guarantee `nullable`, which `C.T` requires at this use.
Type parameter `T` uses `mutable`, but the declaration does not admit it.
```

The first points at the application and, when possible, at the operation that requires the
capability. The second points at both the use and the declaration's markers.

### API metadata

A separately compiled declaration must record each type parameter's required set, because clients
cannot re-analyze its body. This is an API-index schema change. An older reader must reject or
conservatively treat the requirements as equal to the allowed set.

## Compatibility and impact

- Source: strictly widening for applications, but it can also reject declarations that use a
  capability without declaring it. The latter were previously accepted only because their bodies
  did not trigger the check; this is a correctness diagnostic.
- Runtime: none. Capabilities are static.
- API index: required sets must be serialized; this needs a schema revision and a documented
  fallback.
- Inference: generic inference must defer capability checking until arguments are substituted.
- Generators: with [ZEP-0166](./ZEP-0166.md), this makes
  `generator<T admits mutable>(body: () -> Unit performs Yield<T>)` legal without widening `Yield`.
- Nullability remains a property of the element type, not of the effect declaration.

## Alternatives

- **Keep exact matching** — rejected. It blocks safe generic composition and pushes erasure into
  public APIs.
- **Require every declaration to repeat all capabilities it might encounter** — rejected. It
  weakens checking and makes library signatures noisy.
- **Infer requirements only from the declaration's own body, not from callees** — rejected. It is
  unsound for forwarding and would let a body pass `T` to a helper that mutates it.
- **Allow all substitutions and check at the eventual use** — rejected as the sole rule. It moves
  errors to call sites far from the declaration and breaks separate compilation.
- **Treat `admits nullable` as the only widening** — rejected as incomplete. The same argument
  applies to mutable, and the analysis should be capability-generic.

## Implementation and validation

1. Add a capability-requirement analysis for type parameters.
2. Validate declarations (`required ⊆ allowed`) and applications (`required ⊆ guaranteed`).
3. Propagate requirements through generic calls and contract requirements.
4. Update diagnostics and the API index.
5. Enable the direct `generator<T>` signature and remove the `Any` body boundary.

Validation should cover:

- mutable-only use with a nullable+mutable argument;
- nullable use with a non-null argument (rejected), and with a nullable argument (accepted);
- null-safe operations not requiring nullable;
- forwarding through one and several generic layers, including requirements that appear only in a
  callee;
- a declaration that uses a capability without declaring it, with both diagnostic spans;
- separately compiled libraries with the new requirement metadata;
- effect arguments and scoped arguments remaining out of scope;
- the generator signature under [ZEP-0166](./ZEP-0166.md).

## Open questions

- Is `nullable` a requirement of the same kind as `mutable`, or is it only a permission? This
  proposal treats it as a requirement when the body observes nullness. That needs a precise list of
  null-observing operations.
- Should requirements be inferred per method or per type parameter across the whole declaration?
  Per-parameter is simpler and matches the current public shape, but a method that is never called
  from outside could over-require.
- How should requirements interact with contract witnesses such as `T: Eq<T>`? Witness bounds are
  already requirements; capabilities should compose with them in one constraint set.
- Should the API index store the required set verbatim, or a canonical bitset with a versioned
  mapping?
- Does this change the meaning of `admits` for existing code in a way that needs a migration note
  even though most sources keep compiling?
