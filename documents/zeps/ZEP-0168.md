## Abstract

Allow a contract that `requires` another contract to narrow the return type of a method it
redeclares. The class-side emitter already generates synthetic bridges for every contract method
whose descriptor differs from the implementation, including casts, boxing, and default-method
delegation, so this proposal needs no new bridge ABI and no API-index revision. It closes an
enforcement gap between class conformance, which already accepts the same refinement, and contract
inheritance.

The first draft of this proposal planned a default bridge in the sub-contract and an API-index
schema revision. Both are unnecessary and are recorded as rejected alternatives.

## Motivation

A class implementing `Iterable<T>` may declare `iterator(): &Generator<T>` and it compiles; the
emitter produces a bridge for `iterator(): &Iterator<T>`. The equivalent contract cannot be
written:

```zeron
public contract Generator<T admits nullable + mutable> requires Iterator<T> {
    mut cancel(): Unit performs DisposeFailure;
    isDone(): Boolean;
}

// Rejected: Incompatible inherited contract method 'iterator'.
public contract GeneratorSource<T admits mutable> requires Iterable<T> {
    iterator(): &Generator<T>;
}
```

That asymmetry is not a semantic one; it is an enforcement gap. Contracts can therefore not express
refinements such as a replayable source returning a one-shot generator cursor, and library authors
are pushed toward concrete classes. In the generator work this forced `GeneratorSource` to be a
class with an opaque `Any` body, which means users cannot write their own source at all, even though
[ZEP-0119](./ZEP-0119.md) explicitly allows hand-written sources.

## Goals

- Permit return-type refinement on a method that a contract redeclares from a required contract.
- Check the declared return against every inherited declaration of that method, not just the first.
- Reuse the existing class-side synthetic bridge without changing its ABI.
- Keep source method resolution on the refined signature for the sub-contract and the inherited
  signature for the required contract.
- Preserve separate compilation without an API-index schema revision.
- Report a diagnostic that names both the refined and inherited return types.

## Non-goals

- Parameter contravariance, overload sets, or variance annotations on type parameters.
- Property getter/setter covariance in the first slice; methods only.
- An implicit refinement among inherited declarations when the sub-contract does not redeclare the
  method. That case keeps exact matching and is deferred.
- Adding default bridges or a new bridge ABI to contract interfaces.
- Changing class conformance, which already accepts covariant returns.
- Changing runtime dispatch, reflection, or capability admissibility.
- Allowing an implementation to narrow a method it does not actually implement.
- Multiple inheritance of conflicting default bodies; existing precedence rules still apply.

## Proposal

### Admissibility rule

For a contract `S requires R`, a method `M` declared in `S` may refine an inherited method `I` of
`R` when all of the following hold:

- the names and parameter types are identical after substituting `S`'s application into `R`;
- the mutability, effect row, default-value arity, and variadic shape are identical;
- `M.returnType` is a subtype of `I.returnType` under the existing source relation.

The check runs against every inherited declaration with that name, not only the first one found in
the contract closure. If two required contracts declare the same method with returns that are not
comparable to the refined return, the redeclaration is rejected.

If `S` does not redeclare the method, the inherited declarations must be identical after
substitution. This is the current rule, made independent of closure order. No refinement is inferred
from a subtype relationship alone.

### Return subtype rules

The existing source relation is used unchanged:

- nominal conformance: `&Generator<T>` is a subtype of `&Iterator<T>` because `Generator<T>`
  conforms to `Iterator<T>`;
- nullable values: `T` is a subtype of `T?`, and the reverse is rejected;
- reference nullability: `&T` is a subtype of `&T?`.

Mutable-reference pointees stay invariant under [ZEP-0051](./ZEP-0051.md). `&Cell<Dog>` is not a
subtype of `&Cell<Animal>`, and `&(T?)` is not a subtype of `&T`; a refinement may not narrow a
pointee that another alias can mutate. Narrowing a nullable reference itself, `&T?` to `&T`, is
allowed because the implementation must return a non-null reference; it cannot affect another
alias's reference value.

Applied generics follow their declared variance: covariant `out` arguments compose, and invariant
arguments must match exactly. Nothing in this proposal changes variance.

### Bridge generation

No bridge is added to `S`. `NominalTypeEmitter` already walks the class's contract-conformance
closure and emits a public synthetic bridge for every contract method whose descriptor differs from
the selected implementation, casting and boxing results as needed. A class implementing the refined
`iterator()` therefore gets the `&Iterator<T>` descriptor for `Iterable<T>`, exactly as it does
today when the class itself redeclares a narrower return.

The synthetic bridge is not a source candidate and must not appear in completion, "find usages," or
formatter output; it is already classfile-synthetic. No emitter ABI, name, or flag changes are
planned.

An interface-level default bridge in `S` is rejected: the class-side bridge already exists, and a
default bridge cannot restore compatibility for classes compiled against an older `S`, because those
classes have only the wide method and the bridge would invoke a narrow method they do not contain.

### Source resolution

A call through a value statically typed as `S` resolves to `M` and keeps the refined return type. A
call through `R` keeps the inherited return type and dispatches through the class bridge. Generic
substitution, evidence slots, and default dispatch are unchanged; a refined method uses the same
slots and bridges as any other contract method.

### Default methods

If `M` is a default method declared in `S`, an implementing class may inherit it; existing default
precedence rules decide selection, and the class-side default bridge supplies the inherited
descriptor. If `S` inherits a default and does not declare `M`, no refinement exists and no bridge
is emitted. A default inherited from a third contract that does not return a subtype of `S`'s
declared return cannot satisfy the sub-contract; the class must declare the method.

### API metadata

No schema revision is needed. `ContractExport` already records `requiredContracts`, the contract's
methods, and their return types; both endpoint signatures of a refinement are therefore available to
a client, and the bridge is derivable from them. Separate compilation must be validated; if the
implementation shows that a needed descriptor is missing from the index, that becomes a separate,
explicitly justified schema change rather than a precondition of this design.

### Compatibility and impact

- Source: widening. Contract redeclarations that previously failed now type-check when the return
  narrows.
- Binary: adding a refined abstract method to an existing contract is a break for classes compiled
  against the older contract, because they contain only the wide descriptor. No sound interface-side
  bridge can repair that: a downcast from `&Iterator<T>` to `&Generator<T>` is not justified. Record
  the break in the release notes; the project is pre-1.0.
- API index: unchanged, subject to the separate-compilation validation above.
- Tooling: bridges remain synthetic and filtered from completion and diagnostics.
- Runtime: unchanged. The bridge is ordinary virtual dispatch with a cast.
- Capability markers: unchanged. [ZEP-0167](./ZEP-0167.md)'s inferred requirements are rejected, so
  admissibility keeps its exact application rule.

### Diagnostics

Reuse the existing contract-member diagnostic. The message names both returns:

```text
Redeclared method 'iterator' returns '&Generator<T>', which is not a subtype of inherited return
'&Iterator<T>'.
```

Parameter, effect, mutability, variadic, and default-arity mismatches keep their existing message.
No new diagnostic code is added.

## Alternatives

- **Emit a default bridge in the sub-contract.** Rejected: the class-side bridge already covers
  implementers, and an interface default cannot restore binary compatibility for older implementers.
- **Record the inherited and refined descriptors in the API index.** Rejected as unnecessary: both
  are already present through `requiredContracts` and the contract's method list.
- **Infer the most specific inherited return when the sub-contract does not redeclare.** Deferred:
  it needs an explicit rule for unrelated returns and for which signature source resolution uses.
- **Keep the class workaround.** Rejected: it makes hand-written sources impossible and leaves the
  class/contract asymmetry in the type system.
- **Add a separate accessor method instead of refining.** Rejected: it pollutes the surface and still
  does not satisfy `Iterable<T>`.
- **Allow only exact returns.** Rejected: it is the current behavior and the reason for this
  proposal.
- **Allow full covariant/contravariant method signatures.** Deferred. Parameter contravariance has
  separate soundness and overload-resolution questions.
- **Structural typing instead of contract inheritance.** Rejected as a much larger change that does
  not address default methods or witnesses.

## Implementation and validation

1. In `validateContractComposition`, separate the declared-versus-inherited check from the
   inherited-only check, and make the inherited-only comparison independent of closure order.
2. In the redeclaration check, allow a subtype return and report the targeted diagnostic. Parameter,
   effect, mutability, variadic, and default-arity checks stay exact.
3. Confirm that class-side bridge generation covers contract-method descriptor mismatches without an
   emitter change; add a `javap` assertion for the bridge, its synthetic flag, and its cast.
4. Convert `GeneratorSource` from a class to a contract once the resolver change lands, and add a
   hand-written source test.
5. Update design document 05 and the contracts guide to state that a redeclared contract method may
   narrow its return.

Validation should cover:

- a refined concrete return (`&Generator<T>` from `&Iterator<T>`);
- a refined nullable return (`T` from `T?`) and a rejected reverse refinement;
- rejected pointee narrowing (`&Cell<Dog>` from `&Cell<Animal>`, `&(T?)` from `&T`);
- a rejected parameter narrowing and a rejected effect, mutability, or arity change;
- an implementation class with the refined method, called through both contract types;
- two required contracts with comparable and incomparable returns under one redeclaration;
- an inherited-only method with differing returns, rejected independently of closure order;
- a refined default method and an unrefined inherited default;
- witness/evidence slots and generic substitution;
- separate compilation, reading the existing metadata and regenerating the bridge without a schema
  bump;
- `javap` checks that the bridge exists, is synthetic, and delegates to the refined descriptor with a
  cast;
- `for` and `Stream` over a user-defined `GeneratorSource` contract implementation.

## Resolved questions

| Question | Decision |
| --- | --- |
| Should property getters follow the same rule in the first slice? | No. Properties have separate reader/writer and bridge behavior; defer to a property-variance proposal. |
| Is `&T` covariance sound in return position? | Yes through the existing relation, which keeps mutable pointees invariant. Nominal pointee subtyping and reference nullability may narrow; `&Cell<Dog>` to `&Cell<Animal>` and `&(T?)` to `&T` may not. |
| How does a refined return interact with a default inherited from a third contract? | No new rule. Existing default precedence selects the implementation; a default that does not return a subtype cannot satisfy the sub-contract, so the class must declare the method. |
| Should the bridge be default or abstract? | Neither: no interface bridge. Reuse the class-side synthetic bridge that already handles casts, boxing, and defaults. |
| Does nullability need an explicit marker? | No. `T <: T?` is the existing relation. Identical erasure means one method and no bridge; boxing differences use the existing bridge adaptation. |
| Should two inherited declarations refine each other without a redeclaration? | Not in this slice. Exact matching stays, made order-independent; implicit most-specific selection is deferred. |
| Is an API-index schema revision required? | No on the current design: both endpoints are already recorded. A schema change is only considered if separate-compilation validation demonstrates a missing descriptor. |
| What about classes already compiled against the older contract? | Breaking: they contain only the wide method. Record it in the release notes; no sound interface bridge can avoid it. |

## Decision

Accepted 2026-11-27. Return-only covariance for methods a contract redeclares is the direction;
parameter variance, properties, interface bridges, and implicit inherited refinement stay out of
scope. The design reuses the class-side synthetic bridge and the existing API-index records, so it
introduces no new ABI and no schema revision. Implement the resolver orientation and subtype check
first, validate bridge generation with `javap` and a separate-compilation test, then convert
`GeneratorSource` back to a contract and add a hand-written source test.
