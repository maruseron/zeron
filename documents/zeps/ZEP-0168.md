# ZEP-0168: Return Covariance in Contract Inheritance

## Abstract

Allow a contract that requires another contract to narrow a method's return type to a subtype of
the inherited return type, and emit the bridge the JVM needs. This aligns contract inheritance with
class conformance, which already accepts the same refinement and emits `ACC_BRIDGE` methods.

## Motivation

A class implementing `Iterable<T>` may declare `iterator(): &Generator<T>` and it compiles; the
emitter produces a bridge for `iterator(): &Iterator<T>`. The equivalent contract cannot be
written:

```zeron
public contract Generator<T admits nullable + mutable> requires Iterator<T> {
    mut cancel(): Unit performs DisposeFailure;
    isDone(): Boolean;
}

// Rejected: Incompatible inherited contract method 'iterator'.
public contract GeneratorSource<T admits mutable> requires Iterable<T> {
    iterator(): &Generator<T>;
}
```

That asymmetry is not a semantic one; it is an enforcement gap. Contracts can therefore not express
refinements such as a replayable source returning a one-shot generator cursor, and library authors
are pushed toward concrete classes. In the generator work this forced `GeneratorSource` to be a
class, which means users cannot write their own source at all, even though
[ZEP-0119](./ZEP-0119.md) explicitly allows hand-written sources.

## Goals

- Permit return-type refinement in contract `requires` relationships.
- Define the subtype check, including reference and nullable returns.
- Emit the inherited-descriptor bridge as a default interface method.
- Keep source method resolution on the refined signature.
- Record the relationship in compiled API metadata.

## Non-goals

- Parameter contravariance, overload sets, or variance annotations on type parameters.
- Property getter/setter covariance in the first slice; methods only.
- Allowing an implementation to narrow a method it does not actually implement.
- Multiple inheritance of conflicting default bodies; existing precedence rules still apply.
- Runtime reflection-based dispatch changes.

## Proposal

### Admissibility rule

For a contract `S requires R`, a method `M` declared in `S` may refine an inherited method `I` of
`R` when all of the following hold:

- the names and parameter types are identical after substituting `S`'s application into `R`;
- the mutability, effect row, default-value arity, and variadic shape are identical;
- `M.returnType` is a subtype of `I.returnType`.

“Subtype” is the existing source-level relation, so it includes nominal contract conformance,
reference compatibility in return position, and nullability widening such as `T <: T?`. Applied
generics must match pointwise; `&Generator<T>` is a subtype of `&Iterator<T>` because the referenced
nominal type is.

Parameter types stay invariant in this slice. A parameter that names `Iterator<T>` cannot be
narrowed to `Generator<T>`; that would be contravariance and needs a separate decision.

### Bridge emission

For each refined method, emit a `public default synthetic bridge` in `S` with the inherited erased
descriptor. The bridge invokes the refined method on `this` and returns its result, adapting
nullability or boxing only when the source subtype relation requires it.

The two methods differ in their JVM descriptors (return type is part of the descriptor), so they
coexist without a name clash. The bridge must not call itself: it targets the refined descriptor,
not the inherited one.

A refinement whose types erase to the same descriptor needs no bridge. For example, `T` and `T?`
both erase to `Object`, and two applied generic returns with the same raw class erase identically.
The refined type still exists in source and metadata, but the JVM has one method. A refinement that
changes only erased generic arguments cannot be dispatched differently at runtime and is therefore
not a source-level subtype claim the JVM can enforce; it should be accepted only where the source
relation is already justified and must not produce a cast that pretends otherwise.

If `S` inherits two methods with the same name and parameters but unrelated return types, the
relationship is rejected unless one refined return is a subtype of the other. Existing witnesses and
default-method precedence are unchanged; the bridge is generated only for methods `S` actually
declares or inherits through its own conformance.

### Source resolution

A call through a value statically typed as `S` resolves to `M` and keeps the refined return type. A
call through `R` keeps the inherited return type. The synthetic bridge is not a source candidate and
must not appear in completion or diagnostics.

### Default methods

If `M` is a default method, the bridge delegates to it exactly as for an abstract method. If `S`
inherits a default implementation and does not declare `M`, no refinement exists and no bridge is
emitted. A refined default may not silently replace an inherited default with a different body
unless the existing override rules already allow it.

### Generics and API metadata

The subtype check runs after substituting the `requires` application. Requirements on type
parameters are handled by [ZEP-0167](./ZEP-0167.md); this proposal does not add new capability
inference. Compiled API metadata must record the inherited descriptor and the refined descriptor so
separate compilation can regenerate the bridge correctly. This requires an API-index schema
revision.

### Example

```zeron
public contract Generator<T admits nullable + mutable> requires Iterator<T> {
    mut cancel(): Unit performs DisposeFailure;
    isDone(): Boolean;
}

public contract GeneratorSource<T admits mutable> requires Iterable<T> {
    iterator(): &Generator<T>;
}
```

A class implementing `GeneratorSource<T>` implements `iterator(): &Generator<T>`; the sub-contract's
bridge satisfies `Iterable<T>`'s `iterator(): &Iterator<T>`.

## Compatibility and impact

- Source: widening. Previously rejected contract refinements become legal.
- Binary: sub-contract interfaces gain synthetic default bridge methods. Existing implementers do
  not need to add methods.
- API index: schema revision for the inherited/refined descriptor pair.
- Tooling: bridges should be hidden from completion, “find usages,” and formatter output; they are
  already classfile-synthetic.
- Separate compilation: the bridge is regenerated from metadata, not copied from a previous build.
- Diagnostics: the current “Incompatible inherited contract method” error remains for parameter or
  effect mismatches; return mismatches that are not subtypes get a targeted message naming both
  types.

## Alternatives

- **Keep the class workaround** — rejected. It makes hand-written sources impossible and leaves the
  class/contract asymmetry in the type system.
- **Add a separate accessor method instead of refining** — rejected. It pollutes the surface and
  still does not satisfy `Iterable<T>`.
- **Allow only exact returns** — rejected. It is the current behavior and the reason for this
  proposal.
- **Allow full covariant/contravariant method signatures** — deferred. Parameter contravariance has
  separate soundness and overload-resolution questions.
- **Structural typing instead of contract inheritance** — rejected as a much larger change that
  does not address default methods or witnesses.

## Implementation and validation

1. Change the contract `requires` compatibility check to use the subtype relation in return position.
2. Emit default bridges in the sub-contract for each refined method.
3. Thread the refined signature through call resolution and API metadata.
4. Update diagnostics and synthetic-member filtering.
5. Convert `GeneratorSource` back to a contract once the feature lands, and add a hand-written test
   source.

Validation should cover:

- a refined concrete return (`&Generator<T>` from `&Iterator<T>`);
- a refined nullable return (`T` from `T?`) and a rejected reverse refinement;
- an implementation class with the refined method, called through both contract types;
- two inherited contracts with compatible and incompatible same-name methods;
- a refined default method and an unrefined inherited default;
- witness/evidence slots and generic substitution;
- separate compilation, reading the new metadata and regenerating the bridge;
- `javap` checks that the bridge exists, is synthetic, and delegates to the refined descriptor;
- `for` and `Stream` over a user-defined `GeneratorSource` implementation.

## Open questions

- Should property getters follow the same rule in the first slice, or wait for a dedicated property
  variance proposal?
- Is `&T` covariance always sound in return position, or should mutable references require a
  separate opt-in even when nominal subtyping holds?
- How should a refined return interact with a default method inherited from a third contract that
  already provides the inherited descriptor?
- Should the bridge be `default` or abstract? A default bridge keeps existing implementers working;
  an abstract bridge gives clearer failure if a class bypasses the sub-contract.
- Does nullability widening in return position need an explicit marker, or is `T <: T?` the intended
  default?
