## Abstract

Split standard-library verification into two suites:

- a `zeron.test` suite for library behavior, which compiles the library and its tests once and runs
  them in one program;
- a smaller Java/JUnit suite for compiler diagnostics, bytecode and API-index shape, separate
  compilation, CLI behavior, distribution packaging, and process/JVM isolation.

Add `@CompileFailure` so expected compilation failures can live in the Zeron suite without making
the suite uncompilable, and improve the test runner's reporting and selection so the split is
usable.

## Motivation

The standard library is expected to grow noticeably in `0.9.0`. Today its verification is mixed
into the Java suite, where most tests compile a fixture with the bundled standard library, load the
result, and invoke methods reflectively. That has three costs:

1. Every fixture compilation recompiles the standard library, so the Java suite is dominated by
   work that is unrelated to the compiler change under test.
2. Compiler-contract tests and library-behavior tests fail together, making it hard to tell whether
   a change broke the compiler or a library implementation.
3. Library tests are written in Java against generated classes, which obscures the behavior being
   tested and makes ordinary library additions expensive to cover.

A `zeron.test` suite removes the repeated compilation and states library expectations in Zeron.
It does not remove the need for a compiler suite: expected diagnostics, classfile shape, API-index
compatibility, packaging, and child-JVM behavior cannot be asserted from inside a compiled Zeron
program.

## Goals

- Move standard-library runtime behavior into a Zeron test target.
- Keep compiler diagnostics, ABI/API-index, separate compilation, CLI, distribution, and
  process-isolation tests in Java.
- Add `@CompileFailure` with expected diagnostic assertions and fixture roots that are excluded from
  the normal test compilation.
- Make the runner report assertion messages, support filtering, and optionally emit machine-readable
  results.
- Preserve coverage parity while reducing the time to run the compiler-focused suite.

## Non-goals

- Replacing JUnit for compiler internals, classfile inspection, or process control.
- Running arbitrary compiler assertions entirely in Zeron without invoking the compiler.
- Parallel execution, per-test classloaders, or full sandboxing in this slice.
- Fixtures, setup/teardown, parameterized tests, or mocking as a general framework.
- Migrating every existing test; compiler and packaging tests remain Java by design.
- Changing library semantics as part of the migration.

## Proposal

### Two suites

**Runtime suite.** A `zeron.test` target compiles the standard-library sources and the test roots
together, then runs the generated runner. Tests call the public library API directly. A test that
merely needs a construct to compile is a positive compile test for free.

**Compiler suite.** JUnit keeps the tests that need one or more of:

- expected resolution, type, or parse diagnostics, including error codes and spans;
- generated classfile, bridge, function-shape, or API-index inspection;
- separate compilation of a library and a consumer;
- `zeron run`/`zeron build`/`zeron explain`, exit codes, or captured standard output;
- a fresh JVM, a custom launcher, `--add-exports`, or a child process;
- deliberate global or thread-local state isolation.

Tests that are runtime behavior but currently depend on a fresh `dist/` or a fresh classloader are
refactored to local state before moving, or stay in the compiler suite with a note explaining why.

### `@CompileFailure`

`@CompileFailure` marks a top-level, parameterless `Unit` function as an expected-failure test. The
runner does not call the function; it compiles a named fixture and checks the result.

```zeron
import zeron.test.CompileFailure;

@CompileFailure(fixture = "cell/read_only.zn", code = "ZR2005")
public fn cellMutationRequiresMutableReferenceView(): Unit {
}
```

The annotation carries:

- `fixture`: a path relative to a configured compile-failure root;
- `code`: an optional diagnostic code that must appear among the reported errors;
- `message`: an optional substring that must appear in that diagnostic's text.

The expected result is a failed compilation, not a crash, timeout, missing fixture, or compiler
invocation error. If `code` is empty, any resolution/compilation error satisfies the test, but the
runner still rejects an internal failure such as an unreadable project or an unrecognized option.

Fixture roots are configured on the test target and are excluded from the normal test compilation:

```toml
[targets.unit]
kind = "test"
output = "dist/test"
compile-failure-roots = ["tests/fixtures"]
```

A fixture may import the project's sources and the standard library, but it is compiled on its own.
Tests that need several independent failing units use several annotations. The value here is
separation of concerns, not process savings: moving expected failures out of the Java suite keeps
library assertions with the library and compiler assertions with the compiler, but each fixture
still costs a compilation.

### How `@CompileFailure` runs

The `zeron test` host discovers both ordinary tests and compile-failure tests. It runs the ordinary
tests through the generated Zeron runner and the compile-failure tests through a compiler
invocation, then merges their results into one report and one exit status.

The initial implementation may invoke the compiler in a child process per fixture. That keeps
diagnostic state isolated and matches the behavior a user sees from `zeron build`; the cost is
explicitly accepted for compiler-contract tests. An in-process invocation may be added later as an
optimization, but it must produce the same report and the same pass/fail judgment.

To assert diagnostics without parsing human-formatted output, add a machine-readable diagnostics
mode, for example `zeron build --diagnostics json`, carrying code, severity, message, and span. The
human output remains the default.

### Runner improvements

Before large-scale migration, the runner should:

- print the `TestFailure` message for a failed assertion;
- support `--filter <pattern>` and `--list`, matching fully qualified test names;
- support `--fail-fast`;
- print per-test timing and a distinct error count in the summary;
- optionally emit a JSON report with test name, status, assertion message, duration, and skipped
  reason.

These are small, test-only API and CLI changes. They are prerequisites because moving dozens of
tests into one target without them makes failures harder to diagnose and focused runs slower.

### Migration order

1. Inventory the Java library tests and classify each as runtime, diagnostic, ABI/API-index,
   separate compilation, CLI/packaging, or process-isolation.
2. Add the runner improvements, `@CompileFailure`, fixture roots, and the JSON diagnostics mode.
3. Move runtime tests package by package, starting with `Option`/`Result`, collections, streams,
   `Cell`, ranges, and string/numeric behavior.
4. Delete a Java test only when its Zeron replacement exists and the coverage-parity table is
   updated; keep a Java smoke test that compiles the standard library so a suite-wide compile
   failure is distinguishable from a compiler regression.
5. Re-measure both suites and adjust the split.

### Build and CI

`mvn test` becomes the compiler-focused suite. The runtime suite runs through a separate command,
for example `zeron test stdlib-runtime --manifest ...`, wired into CI and documented as a required
check. Local compiler work can run `mvn test` without recompiling the library fixtures; library work
can run the Zeron target directly.

The repository may expose both through a Maven profile, but the Zeron suite must remain runnable
without Maven for the source-mode workflow.

## Compatibility and impact

- No language or runtime semantic change.
- `zeron.test` gains annotations, possibly assertion helpers, and runner output options; this is a
  standard-library API addition and needs the corresponding API version bump.
- `zeron.toml` test targets gain `compile-failure-roots`.
- The CLI gains a machine-readable diagnostics mode.
- Test coverage moves between suites; a parity table is required so a migration does not become a
  quiet deletion.
- CI must run both suites. `mvn test` alone no longer covers library runtime behavior.
- Fixtures are not part of the normal test compilation; editor tooling may not type-check them,
  which is acceptable for deliberately invalid sources.
- The compiler suite's wall time should drop, but compile-failure fixtures still pay process and
  compilation costs. The gain comes from eliminating repeated standard-library compilation for
  runtime tests, not from making negative tests free.

## Alternatives

- **Keep everything in JUnit and cache the compiled standard library** — useful as an interim
  optimization, but it does not separate compiler-contract failures from library failures and keeps
  library tests written against generated classes.
- **Move all tests, including diagnostics and ABI, into Zeron** — rejected. A compiled Zeron program
  cannot invoke the compiler on arbitrary fixtures or inspect its own classfiles without recreating
  the Java harness inside the standard library.
- **Add `@CompileFailure` but keep runtime tests in Java** — rejected. It addresses the expected
  failure surface but not the repeated compilation that dominates runtime tests.
- **Run every test in a fresh process** — rejected for v1. It gives isolation but multiplies the
  cost the migration is meant to reduce.
- **Inline invalid source strings in annotations** — rejected for v1. Large fixtures are unreadable
  and annotation arguments are not a good editor experience; file fixtures can be formatted and
  diffed normally.
- **Parse human diagnostic output** — rejected. Diagnostic wording is not a stable API; codes and
  structured spans are.

## Implementation and validation

Validation should cover:

- discovery and execution of ordinary and compile-failure tests in one target, including mixed
  results and the merged summary;
- an expected code that is present, absent, and duplicated across diagnostics;
- a fixture that fails to parse, fails resolution, and fails compilation, each with the correct
  phase and exit status;
- a fixture that unexpectedly compiles, and a missing fixture, both reported as test errors rather
  than passes;
- `--filter`, `--list`, `--fail-fast`, assertion-message output, and JSON report shape;
- migration parity: each removed Java test maps to a Zeron test name, and the coverage table has no
  unexplained gaps;
- a runtime suite that passes against `stdlib = "source"` and a Java smoke test that still covers
  the compiled-stdlib and API-index modes;
- timing before and after for `mvn test` and the Zeron target, recorded in the ZEP when the
  migration lands.

The migration is complete when the compiler suite contains only tests that genuinely need compiler,
classfile, packaging, CLI, or process control, and the runtime suite covers the library behavior
that was removed.

## Open questions

- Should `@CompileFailure` compile fixtures in-process or in a child process by default? Resolved
  in favor of in-process execution; see the implementation update in the decision section.
- Should fixtures use `.zn` under an excluded root, or a distinct extension that tooling ignores?
- Is one expected code per annotation enough, or is a set of codes needed for tests that assert
  several diagnostics at once?
- Does the JSON report need a stable schema version, and should it be the same format for both
  suites?
- Which runtime tests genuinely need a fresh JVM, and should those be replicated in the compiler
  suite or refactored to avoid global state?
- Should `zeron.test` gain `assertThrows`/`assertFailsWith` for expected runtime effects and host
  exceptions as part of this slice, or is that a separate testing API proposal?

## Decision

Accepted 2026-11-23 for the `0.9.0` bundle as a release-support item. The direction is the
two-suite split plus `@CompileFailure`; the runner additions, the fixture-root configuration, and
the in-process versus child-process choice remain implementation decisions recorded above. The
migration must land with a coverage-parity table before any Java test is deleted.

Implementation update 2026-11-24: the library portion is in place. `zeron.test` declares
`@CompileFailure(fixture, code, message)` and adds `assertContains`, `assertNotContains`,
`assertStartsWith`, `assertEndsWith`, `assertGreaterThan`, and `assertLessThan`. The compile-failure
runner, fixture-root configuration, runner filtering/JSON reporting, and suite migration remain
the release-support work described above; the annotation is declarative until that runner lands.

Implementation update 2026-11-25: the compile-failure runner landed, so the status moves to
Implemented for the infrastructure slice.

- Test targets accept `compile-failure-roots`. A root must not overlap a project source root, and
  the key is rejected on an application target. Fixtures are excluded from the suite compilation,
  are visible to `--list`, and can be selected with `--filter`.
- After the generated runner exits, the host compiles each fixture on its own and matches the
  diagnostics against `code` and `message`. A fixture that compiles, a missing fixture, and an
  internal compiler failure are failed tests, not passes. The fixture output directory is removed
  afterwards, and fixture warnings are suppressed so an expected failure does not change the
  suite's warning state.
- The in-process question is settled in favor of in-process execution: one JVM already runs the
  whole suite, resolutions of independent fixtures do not share mutable state, and the host restores
  the warning and error flags around each fixture. The report and pass/fail judgment are the ones
  documented above.
- The generated runner prints a failed assertion's message, reports a distinct error count, and
  supports `--fail-fast`, which stops at the first failure and skips the compile-failure phase when
  the runner itself failed. `--filter` and `--list` match fully qualified names for both test kinds.

Implementation update 2026-11-25 (suite migration): the runtime suite now lives in
[`stdlib-tests/`](../../stdlib-tests/), a project whose `stdlib-runtime` target compiles the bundled
sources (`stdlib = "source"`) and the tests together. It holds 147 tests plus three
`@CompileFailure` fixtures: `Option`, `Result`, `Cell`, strings, math extensions and statistics,
`ArrayList`, sorting, collectors, builders, streams, for-expressions, hash and alternative
collections, higher-kinded operations, sorted collections, buffers and encodings, randomness,
formatting, regular expressions, generators, ranges, and a smoke test. The Java tests that covered
that behavior were deleted, and
[`stdlib-suite-parity.md`](../developer_guides/stdlib-suite-parity.md) maps each removed Java test
to its Zeron replacement and lists the assertions that deliberately remain Java. The Java suite
keeps `MathApiTest` (literal resolution, host exception behavior, and API-index publishing),
`TestCommandTest`, the generator bytecode tests, and `StandardLibraryTest`'s compiler, project, CLI,
and packaging tests. `scripts/release.ps1` runs the suite with the packaged launcher before building
the archive. The suite takes about 11 seconds on the reference machine, so `mvn test` no longer
carries the library's runtime coverage.

The remaining reporting work moved to [ZEP-0175](./ZEP-0175.md): per-test timing, the JSON report
with a stable schema, and the `--diagnostics json` compiler mode. The tracker keeps this ZEP's
`Candidate` bundle state because the bundle has not shipped; the migration work accepted for
`0.9.0` is complete.
