## Abstract

Record the intended boundary between clause-based for-expressions and `do` blocks:

- `for` is the ordered iteration and collection form;
- `do` is the constructor-generic monadic sequencing form.

Propose an advisory compiler warning when a `do` block targets the concrete `Stream` constructor,
where a for-expression can express the same collection directly.

The warning is a style and teachability aid, not a semantic restriction. `do<Stream<_>>` remains
legal, and generic code over `Monad<F>` is never warned.

## Motivation

The two forms overlap for `Stream`. These produce the same lazy stream:

```zeron
let res = for number in [1, 2]
    for result in ArrayList<Int>.of(number, number * 10)
    yield result;

let res = do {
    let number <- Stream.of(1, 2);
    let result <- Stream.of(number, number * 10);
    yield result;
};
```

The overlap is real, and it is the common case because `Stream` is both a collection and a `Monad`.
Without a stated rule, users see two ways to build a stream and documentation has to explain the
choice in passing. The current guides say to use a for-expression “when you want to collect values,”
but that is a footnote in the `Option`/`Result` chapter, not a durable language boundary.

The forms are not duplicates overall. Today only `Option`, `Result`, and `Stream` implement `Monad`,
and only `Stream` is a collection that a for-expression would iterate. `for` owns guards, multiple
generators, eager `collect … into` sinks, and iteration over any `Iterable`; `do` owns
short-circuiting `Option`/`Result` chains and code generic over `Monad<F>`. Neither can replace the
other.

The purpose of the warning is to make the canonical choice visible at the one point where the
forms collide, without removing either feature or adding a second general comprehension syntax.

## Goals

- State the semantic and stylistic boundary between `for` and `do`.
- Warn when a `do` block’s constructor resolves to concrete `Stream<_>`.
- Keep `do<Stream<_>>` valid for generic code and for deliberate monadic examples.
- Keep the warning advisory, consistent with the existing warning channel and `--deny-warnings`.
- Keep both lowerings unchanged.

## Non-goals

- Removing or deprecating either `for` or `do`.
- Forbidding `do<Stream<_>>` in all contexts.
- Adding guards, `MonadPlus` filtering, or `collect` to `do`.
- Making `for` dispatch through a `Monad` witness.
- Warning on for-expressions that could be rewritten as `do`.
- Adding automatic fixes or a new suppression mechanism in this proposal.
- Guaranteeing stream fusion or changing its status as an implementation optimization.

## Boundary

| Need | Canonical form |
| --- | --- |
| Iterate one or more `Iterable` sources | `for` |
| Filter paths with a guard | `for` |
| Produce a lazy `Stream` from generators | `for` |
| Collect eagerly into a sink | `for` with `collect … into` |
| Chain `Option` or `Result` with short-circuiting | `do` |
| Sequence through a type parameter bounded by `Monad<F>` | `do` |
| Use `Stream` as a generic `Monad` constructor | `do` only when the code is constructor-generic |

The rules that follow from the table:

1. **`for` owns ordered collection.** If the result is a `Stream` or a sink, and the sources are
   ordinary values, use a for-expression.
2. **`do` owns monadic sequencing.** If the constructor is `Option`, `Result`, or a type parameter
   bounded by `Monad`, use `do`.
3. **The overlap is `Stream` only.** A concrete `Stream` block should normally be a for-expression.
   A `do` block whose constructor is a type parameter remains the correct form even when that
   parameter is later instantiated to `Stream`.
4. **Do not close the gaps by convergence.** Adding guards or `collect` to `do` would make it
   subsume `for`; making `for` witness-dispatched would make it subsume `do`. Either change would
   weaken the reason to keep both forms.
5. **Fusion is not the justification.** Fusion for eager collection remains an implementation
   optimization, not a semantic guarantee. The boundary stands on reasoning and expressiveness, not
   on an unimplemented optimization.

## Proposed lint

### Trigger

Emit a warning for a `do` expression when all of the following hold:

- the block’s target constructor has been resolved;
- that constructor is the concrete `Stream<_>` constructor, whether written explicitly as
  `do<Stream<_>>` or inferred from the first bind;
- the block is otherwise valid enough that the warning is not cascading from an existing error.

The warning fires once per `do` expression, after constructor resolution and before lowering.

### Exclusions

Do not warn when:

- the constructor is a type parameter, such as `F<_>` bounded by `Monad<F>`, even if the enclosing
  function is later instantiated at `Stream`;
- the block targets `Option`, `Result`, or another library constructor;
- the block already has a resolution or type error that prevents a reliable constructor;
- the expression is a for-expression. The lint is one-way.

Enclosing generic parameters on the element type do not exempt a block whose constructor is still
concrete `Stream`. A block producing `Stream<A>` for a generic `A` is still expressible as a
for-expression.

### Diagnostic

Proposed warning code: the next free `ZR3xxx` entry, currently `ZR3019` at the time of writing.

Title: `do` over `Stream` duplicates a for-expression

Message shape:

```text
A 'do' block over 'Stream' is a collection comprehension; use a for-expression with 'yield'.
Use 'do' when sequencing an 'Option', a 'Result', or a type parameter bounded by 'Monad'.
```

The diagnostic points at the `do` keyword or the declared `do<Stream<_>>` constructor. It carries no
automatic fix in the first slice. Rewriting a general `do` block is not a local edit: binds may be
interleaved with plain `let` clauses, the final clause may be a monadic expression rather than
`yield`, and a bind may produce a `Stream` through a helper that a for-expression would have to
inline. A fix can be proposed later for the simple `yield`-only shape.

Severity is `WARNING`. Existing policy applies: warnings are reported by default, `--no-warnings`
hides them, and `--deny-warnings` turns them into a failed invocation after reporting. No new
suppression mechanism is introduced; source-level suppression remains the open item owned by
ZEP-0115.

### Existing uses

The shipped `DoNotationTest` uses `do<Stream<_>>` to verify witness dispatch and laziness. The test
continues to compile and is expected to emit the new warning. The test should either keep the block
and tolerate the warning, or use a focused `--no-warnings` run if the harness treats warnings as
noise. Documentation examples that show `do` over `Stream` only to demonstrate monadic dispatch
should say why the example is intentional; examples that build collections should use `for`.

## Compatibility and impact

- Source-compatible: no existing program changes meaning, and `do<Stream<_>>` remains legal.
- New warning output can break builds that use `--deny-warnings` and currently contain concrete
  `Stream` do blocks. That is the intended effect, but it is a build-policy change and must be
  called out in the changelog and migration notes.
- The diagnostic catalog needs a new warning entry and explanation resource; the language server
  surfaces it through the existing diagnostic channel.
- No scanner, parser, AST, lowering, runtime, descriptor, API-index, or ABI change.
- `guide/16-for-expressions.md`, `guide/19-option-and-result.md`,
  `guide/37-functional-abstractions.md`, and the “Relationship to `for`” section of
  [ZEP-0111](./ZEP-0111.md) should state the boundary rather than leaving it as a chapter footnote.
- The warning should not be implemented as a formatter rewrite; formatting and style diagnostics
  remain separate surfaces.

## Alternatives

- **Documentation only, no lint.** Keeps the compiler quiet but relies on readers finding the rule;
  the overlap is common enough that an advisory warning is worth the small amount of noise.
- **Make `do<Stream<_>>` an error.** Rejected. `Stream` is a legitimate `Monad`, generic code may
  instantiate to it, and the distinction is stylistic rather than semantic.
- **Suppress `Stream`’s `Monad` instance.** Rejected. It would remove valid generic monadic code and
  break the existing do-notation tests and witness surface.
- **Warn on every `do` block.** Rejected. `Option` and `Result` chains are the primary reason the
  feature exists.
- **Warn on for-expressions that could be `do`.** Rejected. The canonical direction is collection to
  `for`; a bidirectional lint would reintroduce the choice rather than settle it.
- **Add guards and `collect` to `do` instead.** Rejected for this proposal. It increases the overlap
  and makes the two forms converge.
- **Make `for` witness-dispatched and remove `do`.** Rejected. It changes inference and the
  reasoning model for existing for-expressions, and it needs a richer guard/sink abstraction than
  the language has today.
- **Add an inline suppression annotation in the same proposal.** Deferred. Warning suppression is
  already an open question in ZEP-0115 and should not be designed around one lint.

## Implementation and validation

Implementation stages:

1. Resolve the `do` constructor far enough to distinguish a concrete `Stream<_>` from a type
   parameter or another constructor, without changing the lowered AST.
2. Add the warning entry, title, explanation, and source span.
3. Emit once per block after resolution, skipping blocks with prior errors.
4. Update the guides and the ZEP-0111 relationship section.
5. Run the warning through the LSP diagnostic path and the existing warning flags.

Validation should cover:

- `do<Stream<_>>` written explicitly, and a `do` inferred from a `Stream.of(...)` bind;
- `do` over `Option` and `Result`, which must not warn;
- `do` inside `fn f<F<_>: Monad<F>>(...)`, which must not warn;
- `do` over concrete `Stream` inside a function with generic element types, which must warn;
- nested `do` blocks, each judged by its own constructor;
- a malformed `do` block, which must report its existing error without an additional lint warning;
- `--no-warnings` hiding the warning without changing status, and `--deny-warnings` failing after
  reporting it;
- an LSP publish-diagnostics check for the new code and span;
- a for-expression over the same sources, which must not warn;
- the `DoNotationTest` Stream cases, confirming the warning does not change compilation or runtime
  behavior.

## Open questions

- Should the lint generalize from concrete `Stream` to any constructor that is both `Monad` and
  `Iterable`, or stay specific until such a constructor exists?
- Is a warning on a concrete `Stream` block inside an otherwise generic function useful, or does it
  create noise in code that is already abstract enough? This proposal says warn, because the
  constructor is still concrete.
- Should a later automatic fix handle only the `yield`-only shape, or should it refuse all rewrites
  because bind shapes vary too much?
- Does the project want an inline suppression before ZEP-0115 resolves its general suppression
  question, or is `--no-warnings` sufficient for the test and documentation cases?
- Should the boundary be normative in a guide chapter as well as a ZEP, or is the ZEP plus
  cross-references enough?
