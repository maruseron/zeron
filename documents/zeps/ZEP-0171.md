## Abstract

Make fail-fast the default outcome rule for `ConcurrentScope`, and add a `concurrent { ... }`
receiver-lambda helper that removes the `using` / `DisposeFailure` / `blocking` boilerplate from
ordinary concurrent code.

`concurrent` opens a fail-fast scope, installs the blocking `Await` handler, runs the body with a
read-only scope receiver, cancels and joins any tasks still running when the body exits, and closes
the scope. The body calls `start(...)` and `await(...)` without a `scope.` prefix. Ordinary
concurrent code no longer declares `DisposeFailure`.

The first genuine task failure becomes the scope's primary failure, cancels every sibling, and
blocks new starts. The failure is raised at the failed task's join, at a sibling join when the
sibling was cancelled by the primary failure, or at scope close if no join observed it. Explicit
`cancel()` and deadline cancellation remain cancellation causes, not failures.

`ConcurrentScope.dispose` narrows to effect-free `Unit`. A fail-fast scope still reports an
unobserved failure at close; that report is a runtime safety net rather than a statically required
effect, because a task's effect row is not part of the block body's row unless the body awaits the
task. This proposal records that boundary explicitly and leaves the fully typed version to compiler
work on binder-dependent effect rows.

## Motivation

The current structured-concurrency surface is safe but noisy:

```zeron
import zeron.concurrent.ConcurrentScope;
import zeron.resource.DisposeFailure;

public fn loadBoth(): Int performs DisposeFailure {
    using (let scope = ConcurrentScope.open()) {
        let first = scope.start(() -> load(1));
        let second = scope.start(() -> load(2));
        return first.value() + second.value();
    }
}
```

The `using` block, the `scope.` prefix, and the `DisposeFailure` obligation are mechanical. Awaiting
adds another layer:

```zeron
import zeron.concurrent.ConcurrentScope;
import zeron.concurrent.await;
import zeron.concurrent.blocking;
import zeron.concurrent.spawn;
import zeron.resource.DisposeFailure;

public fn loadBoth(): Int performs DisposeFailure {
    using (let scope = ConcurrentScope.open()) {
        let first = spawn(scope, () -> load(1));
        let second = spawn(scope, () -> load(2));
        return blocking(() -> await(first) + await(second));
    }
}
```

The result is that the common fan-out/join case pays three costs that have nothing to do with the
work being expressed:

- a resource-management effect (`DisposeFailure`) for a scope whose `dispose` is an ordinary join;
- a `blocking` wrapper for the default awaiting policy;
- a named scope and a `scope.` prefix for every task operation.

The current default also leaves failure coordination to the caller. A task failure does not cancel
its siblings; the guide tells callers to invoke `scope.cancel()` when the first failure should stop
the rest. That is a poor default for in-flight work. Once `start` returns, the task is already
running; its failure is an event in the scope's lifetime, not a value the caller may choose to force
later. Waiting for the caller to notice a handle and cancel its siblings lets doomed work continue
and makes the common case easy to get wrong.

This also reconciles the primitive with [ZEP-0112](./ZEP-0112.md)'s own implementation record, which
already states that the first observed outcome wins and cancellation interrupts the rest. The
missing piece was making the scope own that rule instead of leaving it to each caller.

Fail-fast is therefore not one option in a policy matrix. It is the coherent default outcome rule
for a scope of in-flight computations:

- **Fail-fast** decides what happens when a task fails. It is the scope's outcome rule.
- **Parking** decides how a waiting task is suspended. Blocking `Await` already parks a virtual
  thread; a non-blocking backend is an execution detail.
- **First-to-completion** decides which result wins. That is a separate `race`/`first` combinator,
  not a failure rule.
- **Deadlines** are a cancellation cause and a bound, not an outcome policy.
- **Tracing** observes the scope; it does not decide its outcome.
- **Deterministic scopes** inject execution and time; they are test infrastructure.

The `0.9.0` release had not shipped, so this was the right point to correct the default and the
ergonomic surface before they shipped.

## Goals

- Add `concurrent { ... }` and `concurrentWith(executor) { ... }` as the ordinary fan-out/join
  surface.
- Make fail-fast the default for `ConcurrentScope.open()` and `ConcurrentScope.openWith(executor)`.
- Preserve the primitive `using` + `ConcurrentScope` path for custom coordination, and add
  `openManual()` / `openManualWith(executor)` for the previous behavior.
- Make the first genuine task failure the scope's primary failure, cancel siblings, and reject new
  starts.
- Raise a task failure at the failed task's join, at a sibling join when the sibling was cancelled
  by the primary failure, or at scope close when no join observed it.
- Keep explicit `cancel()` and deadline cancellation as cancellation causes, not failures.
- Narrow `ConcurrentScope.dispose` to effect-free `Unit`, so ordinary scope code no longer declares
  or handles `DisposeFailure`.
- Handle `Await` inside `concurrent`, so the body does not need `blocking`.
- Lend a read-only `ConcurrentScope` receiver to the body, so `start`, `join`, `cancel`, and
  `deadline` are unqualified and `dispose` is not callable through the receiver.
- Cancel and join tasks left running when the `concurrent` body exits, while preserving structured
  shutdown: no task outlives the block.
- Keep the `Task` surface, `Await` carrier, effect capture, and the blocking direct-style policy
  unchanged; only the outcome raised at a join changes for scope-cancelled tasks.
- Cover fail-fast cancellation, primary-failure reporting, close-time escalation, cleanup
  precedence, deadlines, manual mode, and injected-executor determinism with tests.

## Non-goals

- A `race` / `first` / `firstSuccess` combinator. It is the dual of fail-fast and belongs in a
  separate proposal.
- A typed `Timeout` effect or a `concurrentWithin` helper. `deadline` remains the primitive.
- Tracing, context propagation, or scope observers.
- A deterministic clock or scheduler. Executor injection is in scope; time injection is not.
- A non-blocking continuation backend. `concurrent` is backend-agnostic; [ZEP-0119](./ZEP-0119.md)
  owns resumable task bodies.
- Scoped receivers that statically prevent a scope or task handle from escaping the block. That is
  [ZEP-0158](./ZEP-0158.md), [ZEP-0160](./ZEP-0160.md), and [ZEP-0161](./ZEP-0161.md).
- A uniform, statically tracked effect row shared by every task in a `concurrent` block. That needs
  binder-dependent effect rows or a scoped effect-row binder in the compiler.
- Changes to the `Task<T, E>` contract shape, `Await`, `Completion`, or the entry handler.
  `Task.value()` keeps its signature and effect-capture rule; its outcome for a task cancelled by
  the scope follows this proposal's cancellation-cause rules.
- Task-local context or inheritable thread-local propagation.
- A monadic or lazy `Task` surface.

## Proposal

### The `concurrent` block

```zeron
import zeron.concurrent.await;
import zeron.concurrent.concurrent;

public fn loadBoth(): Array<User> performs DbError =
    concurrent {
        let first = start(() -> repo.user(1));
        let second = start(() -> repo.user(2));
        return [await(first), await(second)];
    };
```

No `using`, no `blocking`, no `DisposeFailure`, and no `scope.` prefix. `concurrent` opens the
scope, installs the blocking `Await` handler, runs the body with a read-only scope receiver, and
closes the scope after cancelling and joining any tasks still running.

The handler is installed around the block body, not inside task bodies. A task body that awaits is
still a captured `Await` and remains subject to [ZEP-0119](./ZEP-0119.md); `concurrent` does not add
resumable task bodies.

The primitive path remains available for code that needs custom coordination:

```zeron
using (let scope = ConcurrentScope.open()) {
    let task = scope.start(() -> load());
    scope.deadline(Duration.fromSeconds(5));
    task.value();
}
```

### Signatures

```zeron
public fn concurrent<T admits nullable + mutable, E admits effect...>(
    body: ConcurrentScope.() -> T performs Await, E
): T performs E;

public fn concurrentWith<T admits nullable + mutable, E admits effect...>(
    executor: &ExecutorService,
    body: ConcurrentScope.() -> T performs Await, E
): T performs E;
```

The receiver lambda's row has two parts:

- `Await` for the waiting policy, which `concurrent` handles;
- `E` for the body's own effects, including effects re-raised by `await` on a task.

`concurrentWith` uses an injected executor. The caller owns the executor; the block never shuts it
down. This mirrors `ConcurrentScope.openWith` and keeps deterministic tests possible without a
separate primitive path.

### Receiver surface

The body's receiver is a read-only `ConcurrentScope`. It exposes the non-`mut` operations:

| Operation | Meaning |
| --- | --- |
| `start(block)` | Starts a task and returns `&Task<T, {E}>`. |
| `join()` | Waits for every task and prevents new starts; does not raise. |
| `cancel()` | Requests cancellation of every task; first cause wins. |
| `deadline(duration)` | Schedules cancellation; a later deadline replaces an earlier one. |

`dispose` is `mut`, so the read-only receiver cannot call it. The body therefore cannot close the
scope in the middle of the block. The receiver does not yet prevent a handle or a reference to the
scope from escaping as a value; that requires the scoped receivers in
[ZEP-0158](./ZEP-0158.md), [ZEP-0160](./ZEP-0160.md), and [ZEP-0161](./ZEP-0161.md).

### Block exit

When the body exits, the helper cancels and joins every task that is still running. It does this on
both normal return and failure, so a body failure cannot hang forever on a sibling. The scope still
guarantees that no task outlives the block.

Cancel-and-join is a deliberate choice:

- `join()` before returning is available when the body needs every task to finish.
- Without an explicit `join()`, unawaited tasks are not part of the block's result; they are
  leftovers, and the block stops them.
- A body failure should not wait for unrelated work that the body no longer needs.

The helper's close path is:

1. Cancel the scope if it has no cancellation cause yet.
2. Join every task, keeping the deadline armed while joining.
3. Report the first unobserved genuine failure recorded before cancellation, if any.
4. Shut down an owned executor.

### Fail-fast semantics

1. **First genuine failure wins.** A genuine failure is a task failure on a task that was not
   cancelled. The first genuine failure becomes the scope's primary failure. The scope cancels every
   other task with cause `SCOPE_FAILURE` and rejects new starts.
2. **The failed task reports its own failure.** `Task.value()` / `await` on the failed task raises
   its captured failure, exactly as it does today.
3. **A sibling cancelled by the primary reports the primary.** A task cancelled because of the
   scope's primary failure raises the primary failure at its join, not `CancellationException`. If
   that sibling is joined and also failed during cancellation, its own failure is suppressed on the
   primary at that join. If it is never joined, its cancellation-time failure stays on the handle
   and close reports the primary if no join observed it. This prevents the common masking bug where
   awaiting a cancelled sibling hides the real error.
4. **No silent failures.** If the body returns normally and any genuine task failure has already
   occurred and was not observed, scope close raises the first unobserved genuine failure, with the
   remaining unobserved genuine failures suppressed. In the common fail-fast case that is the
   primary failure. A failure is observed when it is raised by `Task.value()` / `await`, or attached
   as suppressed to a failure that is raised. A task still running when a `concurrent` body returns
   is cancelled, not awaited, so a failure that would only happen after that cancellation never
   becomes a task failure.
5. **The body failure stays primary.** If the body throws, its failure is primary over a task
   failure reported at close. An unobserved genuine task failure is attached as suppressed by the
   existing `using` cleanup precedence.
6. **Explicit cancellation is not failure.** `cancel()` and deadline cancellation are cancellation
   causes. They cancel tasks and prevent new starts, but they do not become a primary failure. A
   task failure recorded during an explicit cancellation is a cancellation-time failure: it is not
   escalated at close. If the task was cancelled, joining it throws `CancellationException` with its
   own failure suppressed; if it was not cancelled, joining it raises its own failure. First cause
   wins.
7. **`join()` waits, it does not raise.** `join()` waits for every task and prevents new starts. It
   does not observe failures; a body that needs to observe them awaits the handles. A body that
   joins and returns without observing a failure still gets the close-time report.
8. **State transitions are serialized.** The scope records failure, cancellation, and closure under
   one lock. The first cause recorded wins. A task failure that races with block-exit cancellation
   is a cancellation outcome if the cancellation cause is recorded first. A recorded task failure is
   not overwritten by a later `task.cancel()`.

The practical rule follows from rules 4 and 6: **await or handle every task whose failure you need
to observe.** A genuine task failure is reported unless a join observes it; a task still running at
block exit is cancelled, so a failure caused by that cancellation is not escalated. Use `join()`
when the body needs the task to finish but does not need to read its handle, and `await` when the
body needs the failure at a specific site.

### Failure observation table

| Task state | `Task.value()` / `await` | Scope close |
| --- | --- | --- |
| Succeeded | Returns the value. | No failure. |
| Failed, primary | Raises its own failure; marks it observed. | No escalation once observed; otherwise reported as the first unobserved failure. |
| Failed, secondary | Raises its own failure; marks it observed. | Reported at close if still unobserved. |
| Cancelled by `SCOPE_FAILURE` | Raises the primary failure; own failure suppressed; marks the primary observed. | Reports the primary only if no join observed it. |
| Cancelled by `USER` or `DEADLINE` | Throws `CancellationException`; own failure suppressed. | Not escalated; cancellation is the outcome. |
| Cancelled by `task.cancel()` | Throws `CancellationException`; own failure suppressed. | Not escalated; cancellation is the outcome. |
| Manual-mode failure | Raises its own failure at the join. | Not escalated; manual mode has no automatic outcome rule. |

### Scope modes

`ConcurrentScope` has two modes:

- **Fail-fast** is the default for `open()` and `openWith(executor)`.
- **Manual** is opened by `openManual()` and `openManualWith(executor)`.

Manual mode preserves the behavior currently documented for `ConcurrentScope`:

- a task failure does not cancel its siblings;
- `join()` waits without raising;
- `value()` / `await` is the only failure observation point;
- `cancel()` and `deadline()` still work;
- close joins without escalating an unobserved failure.

Manual mode is not a second outcome policy. It is the absence of an automatic outcome rule for
callers that need custom coordination. The `concurrent` helper always uses fail-fast mode.

### `dispose` becomes effect-free

`ConcurrentScope.dispose` narrows from `Unit performs DisposeFailure` to effect-free `Unit`. The
`Disposable` contract still declares `performs DisposeFailure`; an implementation may narrow the
row, and `using` with a `ConcurrentScope` then no longer requires `DisposeFailure` in the caller's
row.

`dispose` still joins every task. In fail-fast mode it also reports the first unobserved genuine
failure. That report is a host-level throw of the captured failure, not a statically required
Zeron effect. If the captured failure is a `RaisedEffect`, an enclosing handler that is active at
the close site can observe it; otherwise it surfaces as a host failure. The compiler does not
require a handler for it.

This is the deliberate tradeoff that makes ordinary concurrent code free of `DisposeFailure`
boilerplate. The fully typed alternative is discussed under "Typing boundary."

### Cleanup and precedence

`using` inside a task is unchanged: the task's cleanup runs on the task's thread, and a task
failure remains primary over its own disposal failures. The scope's close path composes with the
existing `using` precedence:

- body failure primary, unobserved genuine task failure suppressed;
- body success, unobserved genuine task failure primary at close;
- explicit cancellation, cancellation-time task failures not escalated;
- deadline cancellation, same as explicit cancellation.

The `concurrent` helper uses the same `ResourceSupport` cleanup path as any other `using` block. If
the body fails and close also reports a failure, the body failure remains primary and the close
failure is suppressed. If the body succeeds and close reports a failure, the close failure is the
primary outcome.

### Typing boundary

The body's static row `E` is the union of the effects the body performs, including effects raised by
`await` on a task. Starting a task does not add the task's `E` to the body's row; that is
[ZEP-0112](./ZEP-0112.md)'s capture-at-the-boundary rule.

Consequences:

- If the body awaits every task, each task failure is checked at its await site, with the task's
  own `E` in the caller's row.
- If the body does not await a task, that task's failure is not statically in `E`. The close-time
  report is a runtime safety net.
- A sibling cancelled by the primary failure reports the primary failure even though the primary
  task's `E` may not be in the sibling's row. This is a runtime re-raise, not a statically claimed
  effect. It is what keeps the primary from being masked.

A fully typed version would require every task started in a block to share the block's effect row,
so that any task's failure is in every join's row. That needs a scoped effect-row binder or a
generic `ConcurrentScope<E>` receiver whose `start` is constrained to `E`. Neither is expressible
today: effect rows are quantified on declarations rather than inside function types, and
binder-dependent effect rows are deferred in
[design-document-19](../design_documents/design-document-19_generic-type-system.md).

This proposal does not pretend the close-time report is statically tracked. It makes the runtime
behavior explicit and keeps the ergonomic default. A future compiler proposal can close the gap by
making the block's row include every started task's effects and by typing the close-time report.

### Runtime model

The host runtime changes are internal to `ScopeSupport` and `TaskSupport`:

- `ScopeSupport` gains `failFast`, a scope cancellation cause (`USER`, `DEADLINE`,
  `SCOPE_FAILURE`), a primary failure, and per-failure observation state.
- `TaskSupport` gains a task cancellation cause and keeps its own captured failure.
  `Task.isCancelled()` / `Completion.isCancelled()` report any cancellation cause, including
  `SCOPE_FAILURE`; the task that failed is not itself cancelled.
- `TaskSupport.cancel()` records `USER` as the task's cancellation cause under the scope lock. It
  is a no-op for a task that has already failed, completed, or been cancelled, so the first task
  cause wins.
- `recordFailure(task, throwable)` runs under the scope lock. In fail-fast mode, if no cancellation
  cause is set and the task was not cancelled, it records the task as the primary failure, sets the
  scope cause to `SCOPE_FAILURE`, and cancels the other tasks. Otherwise it records the failure on
  the task handle. A failure recorded under `USER` or `DEADLINE`, or on a task that was cancelled,
  is cancellation-time; a failure on a task that was not cancelled under `SCOPE_FAILURE` is a
  genuine secondary failure. In manual mode it records the failure only on the handle and does not
  set a scope cause.
- `cancelAll(cause)` records the first scope cancellation cause and applies that cause to every
  task that has not already failed or completed. A later cause does not replace an earlier one.
  Cancellation is determined by the recorded cause, not by the exception type; a task that throws
  `CancellationException` without a cancellation request is a genuine failure. A user or failure
  cancellation leaves an armed deadline in place so it still bounds the closing join; a fired
  deadline is cleared, and `joinAll()` clears any remaining deadline after the tasks finish.
- `joinAll()` marks the scope closed, waits for every task, keeps the deadline armed while waiting,
  and shuts down an owned executor. It does not raise.
- `ScopeSupport.dispose(scope)` calls `joinAll()` and then reports the first unobserved genuine
  failure in fail-fast mode. A genuine failure is a failure on a task that was not cancelled;
  cancellation-time failures stay on their handles. `join(scope)` stays non-raising.
- `TaskSupport.await(task)` waits, then:
  - raises the task's own failure if the task was not cancelled, including manual mode;
  - raises the scope's primary failure if the task was cancelled by `SCOPE_FAILURE`;
  - throws `CancellationException` with the task's failure suppressed if the task was cancelled by
    `USER` or `DEADLINE`;
  - returns normally for success.
- `start` rejects a closed or cancelled scope with `IllegalStateException`.

`TaskSupport.await` marks the failure it raises, and any failure it attaches as suppressed, as
observed before throwing. `ScopeSupport.dispose` marks the failure it reports and the failures it
suppresses as observed before throwing, so a second close does not report them again.

### Implementation sketch

The helper is library-level; no new syntax or compiler intrinsic is needed.

```zeron
class ConcurrentBlock is Disposable {
    scope: ConcurrentScope;

    private constructor new;

    public constructor open() =
        ConcurrentBlock.new(ConcurrentScope.open());

    public constructor openWith(executor: &ExecutorService) =
        ConcurrentBlock.new(ConcurrentScope.openWith(executor));

    public run<T admits nullable + mutable, E admits effect...>(
        body: ConcurrentScope.() -> T performs Await, E
    ): T performs E =
        handle (this.scope.body()) with {
            case Await as awaited, k -> k.resume(awaited.pending.awaitDone());
        };

    public mut dispose(): Unit {
        this.scope.cancel();
        this.scope.dispose();
    }
}

public fn concurrent<T admits nullable + mutable, E admits effect...>(
    body: ConcurrentScope.() -> T performs Await, E
): T performs E {
    let result = Cell<Option<T>>.new(Option<T>.None());
    using (let block = ConcurrentBlock.open()) {
        result.set(Option.Some(block.run(body)));
    }
    return unwrapSome(result.get());
}
```

Notes:

- `using` is a statement, not an expression, so the body value travels through a `Cell`. When
  [ZEP-0158](./ZEP-0158.md)'s expression-valued resource blocks land, the cell can be removed.
- `ConcurrentBlock` is package-visible. Its `public` members are not exported because the class
  itself is not public, and it is not part of the public API index.
- The wrapper's `mut dispose` calls `scope.dispose()`; the body's read-only receiver cannot call it
  because `dispose` is `mut`.
- The helper handles `Await` directly rather than nesting `blocking`. The direct `handle` form
  avoids the current emitter's capture limitation for a receiver lambda invoked inside a
  zero-argument wrapper.
- `concurrentWith` is the same helper with `ConcurrentBlock.openWith(executor)`.

### Examples

Fail-fast fan-out:

```zeron
import zeron.concurrent.await;
import zeron.concurrent.concurrent;

public fn loadBoth(): Array<User> performs DbError =
    concurrent {
        let first = start(() -> repo.user(1));
        let second = start(() -> repo.user(2));
        return [await(first), await(second)];
    };
```

If `first` fails with `DbError`, `second` is cancelled. If the body goes on to await `second`, that
await raises the same `DbError`, not `CancellationException`; the array expression above stops at the
first failing await.

An unobserved failure is reported at close:

```zeron
public fn refresh(): Unit performs DbError =
    concurrent {
        start(() -> repo.refresh());
        join();
    };
```

`join()` waits for the task but does not read its handle. If `refresh` fails, the failure is
unobserved at close, so the block raises it. The `start` call itself does not add `DbError` to the
body's static row; the declared row documents the intended outcome. Without the `join()`, the block
cancels the task if it is still running when the body returns; a task that has already failed is
still reported.

Deadline:

```zeron
import zeron.time.Duration;

public fn loadWithBound(): User performs DbError =
    concurrent {
        deadline(Duration.fromSeconds(5));
        let task = start(() -> repo.user(1));
        return await(task)
    };
```

When the deadline fires, the task is cancelled and `await` throws `CancellationException`. The
deadline is not a failure channel.

Manual coordination:

```zeron
using (let scope = ConcurrentScope.openManual()) {
    let first = scope.start(() -> load(1));
    let second = scope.start(() -> load(2));
    scope.join();
    first.value() + second.value();
}
```

This is the previous behavior: no automatic sibling cancellation and no close-time escalation.

## Compatibility and impact

- **Source.** `ConcurrentScope.open()` and `openWith(executor)` change from caller-coordinated
  failure handling to fail-fast. Code that relied on the old default can opt into
  `openManual()` / `openManualWith(executor)`. `ConcurrentScope.dispose` no longer requires
  `DisposeFailure`; callers can drop the effect from scope-only rows. `concurrent` and
  `concurrentWith` are additive.
- **Release.** `0.9.0` had not shipped, so this was a pre-release correction rather than a shipped
  breaking change. `openManual` keeps a migration path for code that needs the old behavior.
- **Standard library.** Adds `concurrent`, `concurrentWith`, `openManual`, and `openManualWith`;
  narrows `ConcurrentScope.dispose`; adds the package-visible block helper. `Task`, `Await`,
  `Completion`, and `spawn` keep their shapes.
- **API index.** Records the new public functions and constructors and the narrowed `dispose` row.
  The descriptor schema is unchanged. `STANDARD_LIBRARY_API_VERSION` is bumped once for the
  `0.9.0` cycle that includes this change, under the consolidation rule.
- **Runtime.** `ScopeSupport` and `TaskSupport` gain fail-fast state and observation tracking. The
  runtime support classes change; no Zeron ABI or class-reification layout changes.
- **Tooling.** `concurrent` is an ordinary function, not a keyword. No grammar, formatter,
  highlighter, or LSP change is required beyond the new standard-library declarations and the
  `zeron.concurrent.concurrent` import.
- **Documentation.** `guide/43-structured-concurrency.md` gains the `concurrent` surface, the
  fail-fast default, manual mode, and the close-time report. `guide/22-raised-effects.md` gains the
  `Await`-handling and runtime-escalation boundary. `guide/26-resource-management.md` records that a
  scope's `dispose` is effect-free. `CHANGELOG.md` records the change when it lands.

## Alternatives

- **A policy matrix (`failFast`, `collect`, `firstSuccess`).** Rejected. Fail-fast is the scope's
  outcome rule. First-to-completion changes which operation wins and belongs in a `race`/`first`
  combinator. Collecting all failures means waiting for work the scope has already decided is
  doomed.
- **Keep caller-coordinated failure handling as the default.** Rejected. Tasks are in-flight; a
  failure is an event in the scope's lifetime. Requiring the caller to notice a handle and cancel
  siblings is easy to forget and lets doomed work continue.
- **Only add `concurrent`, keep `open()` unchanged.** Rejected. The helper would have to opt into a
  hidden mode, and the primitive default would remain the less safe one. Making fail-fast the
  default gives the primitive and the helper one coherent outcome rule.
- **A separate `FailFastScope` class.** Rejected. The behavior is a mode of the same scope, not a
  different lifetime or task type. Two classes would duplicate the surface and complicate the
  helper.
- **A compiler intrinsic for `concurrent`.** Rejected for this slice. The helper is expressible as
  a library receiver lambda with the current `handle` machinery. An intrinsic would add syntax and
  compiler surface without changing the semantics.
- **Join on normal return, cancel only on failure.** Rejected. Join-on-return makes unawaited tasks
  part of the block's implicit result and can hang forever on a task the body no longer needs.
  Cancel-and-join is bounded; `join()` is available when the body needs every task.
- **Aggregate all failures.** Rejected. The first failure cancels the rest; waiting for independent
  failures after the scope is doomed adds latency and produces a larger error surface. Secondary
  failures are suppressed, not promoted.
- **Report a cancelled sibling as `CancellationException`.** Rejected. It hides the primary failure
  behind a cancellation that was caused by that failure. The sibling reports the primary, with its
  own cancellation-time failure suppressed.
- **A typed close-time failure effect.** Rejected for this slice. A non-generic carrier would force
  every `concurrent` caller to handle it, reintroducing boilerplate. A generic carrier needs the
  binder-dependent effect-row support that is not available.
- **Require `blocking` around `concurrent`.** Rejected. `concurrent` installs the blocking `Await`
  handler itself; requiring a wrapper defeats the ergonomic goal.
- **Wait for ZEP-0158 expression-valued resource blocks.** Rejected as a blocker. A `Cell` carries
  the body value today; the helper can be simplified later without a semantic change.

## Implementation and validation

Stages:

1. Add fail-fast state, cancellation causes, failure observation, and close-time reporting to
   `ScopeSupport` and `TaskSupport`.
2. Add `openManual` / `openManualWith` and narrow `ConcurrentScope.dispose`.
3. Add `ConcurrentBlock`, `concurrent`, and `concurrentWith` in the standard library.
4. Update the structured-concurrency, raised-effects, and resource-management guides, and add the
   `CHANGELOG.md` entry.
5. Add Java and standard-library tests, including a compile-failure row check.

Validation covers:

- `concurrent` fan-out/join with no `DisposeFailure` in the caller's row.
- A raw `using (let scope = ConcurrentScope.open())` block compiles without `DisposeFailure`.
- First genuine task failure cancels siblings; awaiting a cancelled sibling raises the primary, not
  `CancellationException`.
- An unobserved genuine failure is reported at close; a body that catches the failure prevents the
  report.
- A body failure remains primary and suppresses an unobserved genuine task failure.
- Explicit `cancel()` and deadline cancellation produce `CancellationException` and do not escalate
  task failures recorded during cancellation.
- `join()` waits, prevents new starts, and does not raise; a later close still reports an
  unobserved failure.
- A deadline set before `concurrent` exits still bounds the closing join after block-exit
  cancellation.
- `using` cleanup inside tasks runs on cancellation and on block exit.
- Nested `concurrent` blocks: an inner failure becomes the outer task's failure and participates in
  the outer fail-fast rule.
- `concurrentWith` on a single-threaded injected executor makes ordering deterministic without
  wall-clock assertions.
- Manual mode preserves the previous behavior: no sibling cancellation and no close escalation.
- A negative effect-row check: an effect performed by the body that the enclosing function's
  declared row does not cover is a compile-time diagnostic; `Await` is handled and not in the
  caller's row.
- A close-time `RaisedEffect` is observable by an enclosing handler; without one it surfaces as a
  host failure.
- The public API index and separate-compilation round trip include the new functions and the
  narrowed `dispose` row.

## Open questions

- Should `join()` report the primary failure instead of deferring to close? This proposal keeps
  `join()` non-raising so the body can decide what to observe, and uses close as the single
  unobserved-failure report point.
- Should `concurrentWith` ship with `concurrent`, or wait for a concrete deterministic-test need?
  This proposal includes it because executor injection is already part of the primitive surface.
- Should manual mode be exposed as constructors on `ConcurrentScope`, or as a separate scope type?
  This proposal keeps one type and two modes to avoid duplicating the surface.
- Should the close-time report become a typed effect once binder-dependent effect rows are
  available? This proposal treats the typed version as future compiler work.

## Decision

Implemented 2026-11-24 and shipped in `0.9.0`. Fail-fast is the default for
`ConcurrentScope.open()` and `openWith`; `openManual` and `openManualWith` preserve caller-
coordinated failure handling. The runtime records cancellation causes and failure observation,
cancels siblings on the first genuine task failure, reports an unobserved failure at close, and
re-raises the primary failure at a sibling join. `dispose` is effect-free. `concurrent` and
`concurrentWith` install the blocking `Await` handler, lend a read-only scope receiver, and
cancel-and-join leftovers on exit. Close-time failure reporting remains a runtime safety net rather
than a typed effect, as proposed.
