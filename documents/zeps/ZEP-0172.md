## Abstract

Specify a portable continuation backend for [ZEP-0119](./ZEP-0119.md)'s one-shot continuations and
deep handlers without relying on `jdk.internal.vm.Continuation`. A compiler-managed CPS or
state-machine transform rewrites every function that may suspend, with a resume/state parameter in
its descriptor.

This work was previously sketched as "backend B, the fallback" inside ZEP-0119. It is split out
because it has its own descriptor, API-index, stack-trace, and cleanup design, and because ZEP-0119
now ships a single backend: Loom behind the provider boundary, failing with a launcher hint when the
module export is absent. Nothing here changes ZEP-0119's source semantics; this proposal only decides
how a portable implementation could realize them.

ZEP-0172 is not part of the `0.9.0` release bundle. It becomes actionable only if the Loom backend
fails its isolation or launcher gate, if a supported JDK changes the internal shape without a
replacement, or if a distribution cannot carry the module export.

## Motivation

ZEP-0119's shipping provider compiles against `jdk.internal.vm.Continuation` and requires
`--add-exports java.base/jdk.internal.vm=ALL-UNNAMED` on every launch path. That is a real packaging
cost: a plain `java -jar`, an IDE run configuration, a test runner, and any external packager must
repeat the export, and a JDK update may change the internal shape. A portable transform removes both
dependencies at the cost of rewriting descriptors and degrading stack traces.

Keeping this design inside ZEP-0119 forced every backend question to be answered twice and made the
proposal's release decision ambiguous. The split lets ZEP-0119 settle its source contract and its
shipping backend, and lets this proposal carry the portable backend's costs explicitly.

## Scope

In scope:

- the transform strategy for functions that may suspend;
- the descriptor and state-object shape, including the resume/state parameter;
- cleanup, cancellation, and non-tail re-suspension states;
- the API-index schema addition and its versioning;
- the performance and memory gate;
- stack-trace, debugger, and interop boundaries.

Out of scope:

- changing ZEP-0119's `Cont`, `Generator`, `GeneratorSource`, or cleanup semantics;
- multi-shot continuations ([ZEP-0121](./ZEP-0121.md) is deferred);
- cross-thread resumption or `resumeOn`;
- a public gate or multiplexing scheduler;
- making this backend the default in `0.9.0`.

## Design

### Transform shape

A function whose row contains a general resumable carrier, or that is called from such a context, is
compiled into a state machine. The naive CPS encoding is rejected: it breaks tail calls, changes every
call site including non-suspending callees, and produces unusable stack traces. The state-machine
encoding keeps ordinary calls ordinary:

- the suspending function gains one hidden parameter carrying a small state object (a resume value
  plus a program counter), or returns a state record through a reserved slot;
- each suspension point stores the live locals it needs, writes the program counter, and returns a
  suspension record to the driver;
- the driver is the same `Level3Support` loop ZEP-0119 already owns; it resumes by calling the
  function again with the response in the state object;
- cleanup is a normal Java `finally` in the transformed function, so `using` unwinding runs exactly
  as it does under Loom.

The transform must handle non-tail re-suspension (a case resumes, the body yields again, and the
nested case resumes too) and deep re-entry through the same handler. It must also preserve one-shot
state: a resumed state cannot be executed twice.

### Descriptor and API-index consequences

Every function that may suspend changes its descriptor. That is the central cost and the reason the
API index schema cannot be reused:

- the hidden state/resume parameter changes the method descriptor on the JVM and in
  `ZeronLibraryIndex`;
- a separately compiled caller must know whether a callee may suspend, so the API index must record
  the capability or the descriptor already encodes it;
- a schema addition is required only if this backend is adopted. Per [ZEP-0012](./ZEP-0012.md), bump
  `API_INDEX_SCHEMA_VERSION` at most once per release cycle and only after the design is accepted.

Do not bump the schema in advance. The Loom path preserves descriptors and needs no schema change;
the portable path must not make reified generics depend on it. The state parameter should reserve an
extension point that generics and existentials can ignore.

### Cancellation and cleanup states

The transform must reproduce ZEP-0119's cancellation behavior:

- explicit `k.cancel()` unwinds the state machine, runs `using` cleanup in LIFO order, and reports
  `DisposeFailure` at the call site;
- implicit cancellation when a `handle` exits cancels pending states, logging cleanup failures on a
  normal `T` and suppressing them on an escaping effect;
- task cancellation sets the private token, marks the state cancelled, and unwinds at the next
  resumption or `using` boundary;
- a canceled or completed state cannot be resumed, and a second resume is a program error.

The state machine needs explicit terminal states (`done`, `failed`, `cancelled`) so a stale state
object cannot be re-entered after cleanup has run.

### Stack traces and interop

- Stack traces lose the original call shape across a suspension; each resume shows the driver and the
  transformed function, not the user's nested calls. This is accepted but must be documented.
- Debugger stepping across a suspension is worse than Loom's real stack and must be checked, not
  assumed.
- Native frames, JNI, and unaware Java callbacks remain boundaries: no suspension may cross them
  unless the runtime can prove the frame is safe. The same boundary rule applies as in ZEP-0119.
- Java `finally` blocks run, because the signal is a `Throwable`; this matches the Loom backend.

### Performance and memory gate

The prototype's state-machine proxy measured 3.1–3.6 ns per pull, 22.6–29.3 ns per cancel, and about
36 bytes of retained heap per suspended body on JDK 26.0.1. That proxy is hand-written, has no
handler, no stack capture, and no cleanup, so it is a lower bound, not evidence that a general
transform is equally cheap.

A real transform must meet, on the ZEP-0119 integer pull-generator workload and the project target
(Java 25):

- at most 1 µs per pull;
- at most 1 KB of suspended heap per body;
- constant stack for the tail-resuming pull loop;
- exactly one cleanup block on cancellation, with correct suppression.

## Relationship to ZEP-0119

- ZEP-0119 ships backend A only. Its provider boundary remains the extension point.
- `-Dzeron.continuation.backend=auto` currently selects A when the export is present and otherwise a
  placeholder provider, which fails at the first suspension with a message naming the export and the
  `zeron` launcher. This proposal owns that placeholder and any real replacement.
- If this backend is adopted, callers recompile against the new descriptors and the API index moves
  to the new schema. The source contract does not change.
- The reverse is not true: adopting this backend must not require ZEP-0119 to reopen its source
  semantics.

## Validation

- Descriptor inspection and API-index round trip for a separately compiled client.
- One-shot resume, double resume, cancel while suspended, cancel after done, and use after handle
  exit.
- Deep re-entry and non-tail re-suspension through the same handler.
- `using` cleanup on normal completion, abort, explicit cancel, and task cancellation, with failures
  suppressed on the right outcome.
- Tail-resuming generator of at least one million elements without stack growth.
- The 1 µs pull and 1 KB suspended-heap gate, measured on Java 25.
- Stack-trace and debugger behavior recorded, including the loss of intermediate frames.
- A plain `java -jar` launch with no module export, proving the portable path needs none.

## Alternatives

- **Keep B in ZEP-0119 as a fallback** — rejected by the split. A release decision that silently
  changes descriptor and API-index shape is not a fallback; it is a second implementation with its
  own gates.
- **CPS encoding** — rejected for tail-call and stack-trace costs.
- **Virtual-thread backend (C)** — rejected in ZEP-0119 for per-element generator yields; its
  measured pull cost is 19–59× the Loom backend.
- **Wait for a public continuation API** — possible, but it would make the portable path unnecessary
  rather than replace its design.

## Open questions

- Exact state-object layout and whether the resume value travels in the parameter or a reserved
  return slot.
- Which functions the transform must rewrite: only direct suspenders, or every callee with an open
  row?
- How the API index records the capability, and whether a caller can remain descriptor-compatible.
- Whether the transform can preserve any user-visible stack frames across a suspension.
- Whether the portable path can reuse the Loom provider's `Session` interface unchanged.

## Decision

Draft, unscheduled. This proposal records the portable backend split out of ZEP-0119. It is not part
of the `0.9.0` bundle and does not change ZEP-0119's shipping decision: backend A ships behind the
provider boundary, and an unavailable A fails with the launcher hint. The transform, descriptor
change, API-index schema addition, cleanup states, and the 1 µs/1 KB gate must all be designed and
validated here before this backend can be selected.
