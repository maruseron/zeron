## Abstract

Give generated Zeron classes the standard Java debug attributes so a JVM debugger can map bytecode
back to Zeron source. The compiler currently emits no `SourceFile`, `LineNumberTable`, or
`LocalVariableTable`, so breakpoints, line stepping, local inspection, and source lines in
exception traces cannot work in an IDE even though the language and runtime behave correctly. This
proposal adds source/line metadata, local-variable metadata, stable names for generated members, and
the frame filtering needed to step across effect handlers and continuation suspensions. It changes
debug output only; language semantics, the runtime provider ABI, and the API-index schema are
unchanged.

## Motivation

[ZEP-0119](./ZEP-0119.md) landed pull generators, deep handlers, one-shot continuations, and
cancellation, and its runtime/provider work is implemented. Its manual IDE check could not pass
because generated classes carry no source or line information. That is not a continuation defect:
every Zeron program is affected, and the same metadata also improves ordinary stack traces and JFR
attribution.

Without this work:

- an IDE cannot place a source breakpoint in a `.zn` file;
- step over, step into, and step out land on synthetic methods or are unavailable;
- parameters and locals have no names, so debugger variable views are empty or numerical;
- exception traces show generated method names but no Zeron file or line;
- stepping across `Continuation.yield` is untested in a real debugger;
- provider frames such as `Level3Support` and `SessionDelegate` appear in the user's stepping path.

The last two points are the ZEP-0119 follow-up. The rest are general compiler quality.

## Goals

- Emit a `SourceFile` attribute naming the originating `.zn` file for every generated class.
- Emit `LineNumberTable` entries that map executable bytecode to Zeron source lines, including
  expression-level constructs and effect operations.
- Emit `LocalVariableTable` entries for source parameters and locals, plus `MethodParameters` for
  method and constructor parameters.
- Give generated methods, lambdas, anonymous handler classes, and shape interfaces stable,
  source-related names or an equivalent source map so a debugger presents a readable frame.
- Define how generated helper frames are stepped through or hidden, especially `Level3Support`,
  `SessionDelegate`, the continuation provider, and synthetic lambda adapters.
- Verify breakpoints, stepping, local inspection, and exception line attribution in a real IDE,
  including a suspension inside a generator body and a level-3 handler resume.

## Non-goals

- Changing Zeron semantics, effect-handler lowering, lambda shape identity, or continuation
  behavior.
- Changing the API-index schema or any published standard-library signature.
- A new debugger UI, Debug Adapter Protocol server, or language-server extension. This proposal
  produces the bytecode metadata those tools consume; a future ZEP can own an editor-side debugger
  integration.
- Source-level debugging of Java library internals or of the bundled standard-library sources when
  the compiler inlines or bundles them; attribution rules for bundled code are addressed only as far
  as the generated class's own `SourceFile`.
- Changing JFR event definitions; only line attribution in existing events is in scope.
- Preserving debug metadata through minification or other post-processing that is not part of the
  compiler.

## Proposal

### Source and line attributes

Every class emitted for a Zeron compilation unit gets a `SourceFile` attribute. For a source unit
`src/query/engine/expressionevaluator.zn`, the attribute names the source file, not the generated
class. A compilation unit that produces several classes, including nested handler and lambda shape
classes, uses the same `SourceFile` unless a class is wholly synthetic and has no source
correspondence; in that case the nearest owning source file is used.

`LineNumberTable` entries are emitted for every method with source-derived code. Each entry maps a
bytecode offset to the source line of the construct that produced it. The emitter already visits
AST nodes with source spans, so the implementation attaches the current span to instruction
emission rather than reconstructing lines from class names.

Rules:

- A statement or expression that emits several instructions marks the first instruction at its
  source line and may mark later instructions only when they correspond to a distinct source
  construct, such as a nested call or a branch arm.
- Generated prologue, stack-map, and cleanup instructions do not invent source lines; they inherit
  the line of the surrounding construct or remain unmarked.
- A lowered construct that crosses source lines, such as a multiline call, maps each argument's
  instructions to that argument's line where practical.
- Effect operations (`perform`) map to the `perform` expression's line, not the handler's.

### Local variables

Parameters and locals that have a source name and a stable JVM slot receive a `LocalVariableTable`
range covering the source scope in which they are visible. Compiler temporaries, lowered
destructuring slots, and captured-value plumbing are omitted unless they correspond to a named
source binding.

`MethodParameters` records source parameter names on methods and constructors. Lowered trailing
lambdas, receiver parameters, and synthetic adapters use the source name when one exists; otherwise
they are marked synthetic and excluded from the user-visible variable view.

### Names and source mapping

Generated members keep their stable identity where the ABI requires it, but user-facing frames gain
a readable form. The proposal prefers, in order:

1. source-derived names for methods and classes that correspond one-to-one with a declaration;
2. a `SourceDebugExtension` or equivalent source map when a single generated class mixes multiple
   source forms and readable names alone cannot identify the origin;
3. synthetic names with a documented prefix when neither applies.

Changing a name must not change a shape interface's canonical identity or the API index. Shape
identity remains governed by the existing canonical-key rules.

### Stepping through runtime support

The debugger should not require the user to step through ZEP-0119's support frames. The proposal
does not require hiding them at the JVM level, which is not portable. Instead:

- the compiler marks purely synthetic bridge methods so a debugger can filter them;
- the runtime support classes carry their own `SourceFile` pointing at their Java source, so a
  step into support code lands in readable Java rather than an unnamed class;
- the ZEP-0119 provider frames remain visible when the user deliberately steps into runtime code,
  but the documented step-over path treats a `resume` or generator pull as one source-level call;
- a suspension across `Continuation.yield` must preserve the Zeron source frame for the suspended
  body and report the suspension point's line.

The exact IDE presentation depends on the debugger; the compiler's obligation is correct metadata
and stable names, not a specific stepping policy.

### Validation

- `javap -v` shows `SourceFile`, `LineNumberTable`, and `LocalVariableTable` on a compiled program
  with functions, classes, lambdas, and a generator.
- A JVM debugger places a breakpoint on a Zeron statement, steps over statements, steps into a
  Zeron function, and reads a parameter and a local by source name.
- An exception thrown at a known source line reports that `.zn` file and line in its stack trace.
- A breakpoint inside a generator body is hit on each pull, and stepping across a suspension keeps
  the body's source frame.
- A breakpoint in a level-3 handler case and in the resumed body maps to the correct Zeron lines,
  and the support frames are identifiable as runtime rather than user code.
- JFR events that carry stack traces report Zeron file and line where the JVM uses the line table.
- Debug metadata does not change generated bytecode behavior; the full suite and bytecode/API-index
  identity checks pass unchanged.

## Compatibility and impact

Class files grow by the size of the new attributes, which is normally small but measurable for
lambda-heavy programs. No source, runtime, standard-library, or API-index compatibility is affected;
the metadata is ignorable by the JVM when no debugger is attached. Deterministic-output checks and
any golden bytecode inspections must be updated to account for the new attributes. Tooling that
parses generated class files should tolerate the additional attributes.

## Alternatives

- **Emit metadata only under a debug build flag.** This keeps release classes smaller, but produces
  two bytecode shapes to test and makes production traces less useful. It remains a fallback if the
  size cost proves material.
- **Use a sidecar source map.** IDEs and JFR consume JVM attributes, not a compiler-private file; a
  sidecar would require a custom debugger or agent and would not fix stack traces.
- **Rely on a Java agent to reconstruct lines.** The agent would still need the source map and would
  not help source breakpoints before the agent transforms classes.
- **Change the continuation backend to improve stepping.** The debugger gap is metadata, not
  continuation plumbing; changing backends would not give Zeron lines or locals.

## Implementation and validation

This is not an implementation commitment or schedule. A staged path:

1. Attach source spans to emitted instructions and emit `SourceFile` plus `LineNumberTable` for
   ordinary functions and methods.
2. Extend line mapping to expression forms, branches, pattern matching, lambdas, and effect
   operations, including `perform` and handler cases.
3. Emit `LocalVariableTable` and `MethodParameters` for source parameters and locals, excluding
   compiler temporaries.
4. Add readable names or a source map for generated classes and members without changing shape
   identity or the API index.
5. Validate the ZEP-0119 cases: generator pulls, suspension, level-3 resume, and cancellation
   unwinding, using a real IDE debugger and JFR.
6. Update generated-artifact expectations, `javap` checks, and the debugging documentation.

## Open questions

- Should debug attributes be always on, or controlled by a project setting with release defaults?
- How should a class that mixes bundled standard-library code with user code attribute its
  `SourceFile` when the compiler inlines across units?
- Can generated lambda and handler names become readable without affecting shape identity or
  deterministic output?
- Which support frames should the documented step-over policy treat as transparent, and does that
  differ between provider A and the portable backend in [ZEP-0172](./ZEP-0172.md)?
- Is a source map necessary once lambda and handler classes carry their owning source file, or do
  mixed-source classes still need one?
