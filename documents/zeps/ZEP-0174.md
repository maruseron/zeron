# ZEP-0174: `if` Guards in Do-Notation through `Filterable`

## Abstract

Add `if` guard clauses to `do` blocks. A guard keeps only the paths for which its Boolean condition
is true:

```zeron
do {
    let user <- findUser(id);
    if (user.active);
    yield user;
}
```

Each guard lowers to a witness-dispatched `filter` call from the existing `Filterable<F<_>>`
contract in `zeron.control`. A `do` block still sequences through `Monad<F>`; a block that contains
a guard additionally requires `Filterable<F>` evidence for its constructor. This proposal adds
natural `Filterable` implementations for `Option` and `Stream`; `Result<_, E>` has no natural
implementation because filtering out an `Ok` has no error value to return. The change is parser,
resolution, library, and documentation work only, with no runtime or ABI change.

## Motivation

Do-notation removes nested `match` expressions from fallible chains, but it has no compact way to
discard a path after a value has been bound. A predicate currently becomes another bind against a
value-level `if`:

```zeron
let user <- findUser(id);
let active <- if (user.active) Option.Some(user) else Option<Int>.None();
```

That is noisy, repeats the source value, and is specific to the constructor's surface operations.
The problem becomes worse when several predicates apply to the same step.

For-expressions already have `if condition` guards, so users reasonably expect the same clause in
`do`. The two forms serve different scopes: a for-expression filters an `Iterable` and produces a
stream, while `do` sequences arbitrary monadic constructors. A guard in `do` should therefore be
expressed through the smallest contract that describes "keep or discard elements" without requiring
an empty constructor.

`Filterable` is that contract. Its `mapFilter` primitive transforms and drops elements, and `filter`
is derived from it:

```zeron
public contract Filterable<F<_>> requires Functor<F> {
    mapFilter<A, B>(this: F<A>, transform: A -> Option<B>): F<B>;
    default filter<A>(this: F<A>, predicate: A -> Boolean): F<A>;
}
```

Its documentation already names `if` guards in do-notation as the intended use. This proposal turns
that relationship into source syntax.

## Goals

- Add an `if (condition);` guard clause to `do` blocks.
- Lower guards to witness-dispatched `filter` calls through `Filterable<F<_>>`.
- Require `Filterable<F>` only for blocks that contain a guard; existing bind-only blocks keep
  their `Monad<F>` requirement.
- Preserve left-to-right evaluation, short-circuiting, and stream laziness: a false guard skips the
  remainder of that path, and later clauses are not evaluated for it.
- Provide standard `Filterable` implementations for `Option` and `Stream`.
- Keep guard predicates pure and statically checked as `Boolean`.
- Add no runtime type, descriptor, or generated-code shape beyond ordinary witness calls.

## Non-goals

- Replacing `Filterable` with `Alternative`/`MonadPlus` and an `empty`-based `guard` helper.
- A default `Filterable<Result<_, E>>`, or choosing a synthetic error for a failed predicate.
- Guards in bind-free `do<C<_>>` blocks. The initial version requires a preceding bind.
- Guards after a plain `let` local that belongs to the same bind group. See "Placement and local
  bindings" for the rationale and the initial restriction.
- Effectful guard predicates. `Filterable.filter` accepts a pure `A -> Boolean`.
- Adding `collect` to `do`, unifying `for` and `do`, or changing for-expression guards.
- Changing the existing `map`, `flatMap`, constructor-inference, or last-clause rules of
  [ZEP-0111](./ZEP-0111.md).

## Proposal

### Syntax

A guard clause is written in clause position after a bind:

```zeron
do {
    let value <- source;
    if (value > 0);
    yield value;
};
```

The grammar adds one clause form:

```ebnf
doClause = "let", IDENTIFIER, "<-", expression, ";"
         | "let", IDENTIFIER, "=", expression, ";"
         | "if", "(", expression, ")", ";" ;
```

Parentheses are required, matching the existing value-level `if (condition) then ... else ...`
form. `if` is already a keyword, so no new reserved word is introduced.

The value-level conditional keeps its meaning in final-expression position because it always
continues with `then` after the closing parenthesis. A `do` parser can distinguish the two forms
after parsing the parenthesized condition: `;` makes it a guard, while `then` makes it an ordinary
conditional expression. A block with a guard still needs a `yield` or a final monadic expression;
the guard itself does not supply the block's value.

A block may contain several guards:

```zeron
do {
    let value <- source;
    if (value > 0);
    if (value < 100);
    yield value;
};
```

Consecutive guards are evaluated left to right.

### Placement and local bindings

A guard belongs to the nearest preceding bind. Between that bind and the guard, only other guards
may appear. Plain `let name = expression` clauses may follow the guards:

```zeron
do {
    let user <- findUser(id);
    if (user.active);
    if (user.verified);
    let label = user.name;
    let account <- findAccount(label);
    if (account.balance >= 0);
    yield account;
}
```

The following placement is rejected in the initial design:

```zeron
do {
    let user <- findUser(id);
    let label = user.name;
    if (label != ""); // error: a guard must precede the bind group's plain locals
    yield user;
}
```

Filtering the preceding generator is what gives a guard its short-circuit meaning. A plain local
between the bind and the guard may depend on the bound value, so pushing the predicate onto the
source without re-evaluating the local would require carrying the local environment through the
filter operation. This version deliberately keeps the simple, allocation-free lowering and reports
a diagnostic. The predicate can usually be moved before the local, or the computed value can be
introduced as a monadic bind. Lifting this restriction is recorded as an open question.

A guard before the first bind is also rejected. Leading plain `let` clauses may still precede the
first bind, because they are evaluated before the monadic chain and are visible to a guard attached
to that bind.

### Semantics

- A guard is evaluated for each value produced by the bind's source, after the source value is
  available and after any earlier guards on the same bind have passed.
- If the condition is `false`, the rest of the current path is skipped: no later bind, local, guard,
  or `yield` expression is evaluated for that value.
- If the condition is `true`, the bound name and all already-visible locals remain in scope for the
  rest of the block.
- For `Option`, a false guard produces `None` and a true guard leaves the value unchanged; the
  predicate is not called for an existing `None`.
- For `Stream`, filtering is lazy and order-preserving. The predicate runs per element when the
  stream is traversed, not when the block is constructed.
- For any other `F`, the result is the constructor's `Filterable` behavior: elements may be removed,
  but are never reordered or duplicated.
- The guard condition must have type `Boolean` and must be effect-free. A condition that may raise
  an effect is reported as an ordinary type error; the effect must be performed before the block or
  as an explicit bind.
- Guards do not introduce new flow-opening binders into subsequent clauses. Existing flow typing
  still applies to the condition expression itself.

### Constructor and evidence requirements

The constructor of a `do` block is selected exactly as it is today: from an explicit
`do<C<_>>`, otherwise from the first bind. A block with at least one guard must satisfy both:

- `Monad<F>` for the binds and the final result; and
- `Filterable<F>` for the lowered `filter` calls.

The requirement is per block, not per `do` syntax. Existing blocks without guards continue to work
with `Monad<F>` alone. Generic code that adds a guard must add the corresponding bound:

```zeron
fn active<S<_>: Monad<S> + Filterable<S>, A>(source: S<A>, predicate: A -> Boolean): S<A> = do {
    let value <- source;
    if (predicate(value));
    yield value;
};
```

`Option` and `Stream` receive standard implementations. `Result<_, E>` does not: a false predicate
on an `Ok` would have to produce an `E`, and no canonical error value exists. A guard in a
`Result<_, E>` block is a type error unless the program supplies its own `Filterable` witness; the
standard library does not choose one. A project that does supply one is responsible for defining
what a filtered-out success becomes.

### Desugaring

The parser continues to lower a `do` block to witness-dispatched receiver calls before an
`Expr.Do` is built. For a bind with guards, the bind source becomes the receiver of `filter` before
its normal `map` or `flatMap`:

```zeron
do {
    let value <- source;
    if (value > 0);
    if (value < 100);
    let scaled = value * 2;
    let next <- following(scaled);
    yield next;
}
```

lowers approximately to:

```zeron
source
    .filter(value -> value > 0)
    .filter(value -> value < 100)
    .flatMap(value -> {
        let scaled = value * 2;
        following(scaled).map(next -> next);
    });
```

The final bind still chooses `map` for a `yield` and `flatMap` for a final monadic expression. Each
`filter` call is marked witness-dispatched, like the existing `map` and `flatMap` calls, so it
resolves through the constructor's `Filterable` evidence rather than through an instance method
that happens to share the name. `Stream.filter` is such an instance method; the lowering must not
depend on it.

`filter` is a default member of `Filterable`, derived from `mapFilter`. The lowered source names
`filter` only. Implementations may combine consecutive guards into one predicate when doing so
preserves left-to-right evaluation, or emit a chain of `filter` calls; this is an implementation
choice, not an observable semantic difference for pure predicates.

## Compatibility and impact

This is a source-compatible addition. `if (condition);` in a `do` block is not valid today: a
value-level `if` requires `then`, and a non-`let`/`yield` clause is only accepted as the final
monadic expression. Existing final `if (condition) then ... else ...;` expressions keep their
meaning. No existing `do` block changes behavior or evidence requirements.

No runtime, generated-class, descriptor, or API-index schema change is required. Lowered calls use
the existing witness-dispatch path. The standard-library surface gains `Filterable` implementations
for `Option` and `Stream`; that is public library API and follows [ZEP-0012](./ZEP-0012.md)'s
versioning rules. `STANDARD_LIBRARY_API_VERSION` should be incremented at most once for the release
cycle, together with any other library API changes.

The proposal depends on the `Filterable` contract already defined in `zeron.control`, including its
`mapFilter` primitive and derived `filter` and `compact` members. It does not add the contract
itself.

Implementation touches the grammar and parser, resolver and witness dispatch, AST diagnostics, the
standard library, and the existing do-notation tests. The formatter and syntax highlighter already
recognize `if`; they need clause-shape and idempotence checks rather than a new keyword. The language
server should offer the guard clause in the same syntax surfaces as the other `do` clauses. After
implementation, [guide chapter 19](../guide/19-option-and-result.md) must remove its statement that
there are no `do` guards, and [ZEP-0111](./ZEP-0111.md)'s "no guard clause" decision and
[ZEP-0170](./ZEP-0170.md)'s non-goal against guards must be revised or annotated to point at this
proposal.

## Alternatives

- **`MonadPlus`/`Alternative` with an `empty`-based `guard` helper.** This supports guards in any
  position and has a familiar library shape, but it requires an empty structure, which `Option`
  has and `Result<_, E>` does not, and it does not use the `Filterable` capability the standard
  library is introducing. Rejected for this version.
- **Keep the value-level `if` bind workaround.** It is source-compatible and needs no compiler
  change, but it is verbose, repeats the value, and does not scale to several predicates. It remains
  available and is not deprecated.
- **Use only for-expressions.** For-expressions already have guards, but they only iterate
  `Iterable` values and always produce a `Stream` or a sink; they cannot sequence arbitrary monads.
  Rejected as a replacement for the `do` use case.
- **Introduce `when` or `guard` instead of `if`.** A new clause keyword would remove the
  conditional-expression ambiguity, but the syntax already distinguishes `if (condition);` from
  `if (condition) then ...`, and `if` is the established for-expression guard vocabulary. A second
  spelling would add vocabulary without adding expressiveness.
- **Filter the block's final monadic result.** This is a much smaller change, but it evaluates later
  binds and the `yield` expression before discarding the path, violating short-circuiting and stream
  laziness. Rejected.
- **Require `Filterable` for every `do` block.** This would make guard lowering unconditional but
  would reject existing `Result` blocks and narrow the notation for no benefit. Rejected; the
  requirement is per block.

## Implementation and validation

This is a proposed design, not an implementation commitment or schedule. A staged path:

1. Add the guard clause to the grammar and parser. Reuse the ordinary expression parser for the
   condition, distinguish `if (condition);` from `if (condition) then ... else ...;`, attach guards
   to the nearest preceding bind, and report placement errors before lowering.
2. Lower each guarded bind source through witness-dispatched `filter` calls, then reuse the existing
   `map`/`flatMap` lowering for the bind, locals, and final result.
3. Add resolution and diagnostics: guard condition must be `Boolean`; the block's constructor must
   have `Filterable` evidence when any guard exists; missing evidence names the constructor and
   points at the guard; `Result<_, E>` reports that no default implementation exists.
4. Add `Filterable<Option<_>>` and `Filterable<Stream<_>>` implementations in the standard library,
   using the existing `mapFilter` primitive. Keep their witness behavior consistent with the
   existing `Option.filter` and `Stream.filter` instance methods; a witness may override `filter`
   to delegate to the instance operation. Keep `Result` without a default witness.
5. Update the grammar document, formatter and highlighter checks, LSP syntax surfaces, guide
   chapter 19, the ZEP-0111/ZEP-0170 cross-references, and `CHANGELOG.md` when the implementation
   lands.
6. Validate with focused compiler tests and the full suite.

Test cases should cover:

- `Option`: a passing guard, a failing guard, multiple guards, a guard after the last bind, and a
  later bind or `yield` expression that must not run after a failed guard.
- `Stream`: guard filtering before `flatMap`, laziness before traversal, element order, repeated
  traversal, and no evaluation of a later bind for a filtered element.
- Generic code: a function bounded by `Monad<F> + Filterable<F>` compiles with a guard; the same
  function without `Filterable<F>` fails with a targeted diagnostic.
- `Result<_, E>`: a guard is rejected because no default `Filterable` witness exists.
- Placement and syntax diagnostics: guard before the first bind, guard after a bind-group local,
  guard in a bind-free block, non-Boolean condition, and effectful condition.
- Regression: ordinary `if (condition) then ... else ...;` as the final expression still parses and
  lowers as before; existing `DoNotationTest` cases pass unchanged.
- Formatter idempotence and parser spans for guard clauses.

## Decision

Accepted 2026-11-25 and implemented in the `0.9.0` cycle. The implemented slice is the one
specified above: `if (condition);` guard clauses in `do`, lowered to witness-dispatched `filter`
calls on the preceding generator before its `map`/`flatMap`; per-block `Filterable<F>` evidence in
addition to `Monad<F>`; default `Filterable` witnesses for `Option` and `Stream`, with lazy
order-preserving `Stream.mapFilter`; and no default `Result<_, E>` witness. Placement diagnostics
reject a guard before the first bind, a guard in a bind-free block, and a guard that follows the
bind group's plain locals. A non-`Boolean` condition and missing `Filterable` evidence surface as
ordinary resolution errors from the lowered `filter` call.

Implementation notes:

- Guard clauses are parsed in `Parser.doExpression` and lowered in the parser, so no AST node,
  descriptor, or generated-code shape is added. `looksLikeDoGuardClause` distinguishes
  `if (condition);` from a value-level conditional by the token after the closing parenthesis.
- Higher-kinded parameters now keep one descriptor whose bounds are published after parsing
  (`TypeParameterDescriptor.initializeBounds`). Bounds such as `S<_>: Monad<S> + Filterable<S>`
  previously referred to a placeholder without bounds, which made a derived receiver such as the
  result of `filter` unresolvable. `TypeResolver.resolveTypeNames` visits parameter bounds once to
  tolerate the resulting self-reference.
- `zeron.control.Filterable` was already declared with `mapFilter`, a default `filter`, and a
  default `compact`. This proposal adds the `Option` and `Stream` implementations and makes
  `Stream` list `Filterable<Stream<_>>` in its class-header conformance list.
- The public library additions belong to the same `0.9.0` standard-library API cycle, whose
  `STANDARD_LIBRARY_API_VERSION` was already raised once for the bundle's library work.

## Open questions

- Should a later revision allow guards after bind-group plain locals? Doing so without duplicate
  evaluation needs an environment-carrying lowering or a different guard primitive; the initial
  design intentionally restricts placement instead.
- Should bind-free `do<C<_>>` blocks allow guards by filtering a synthetic `pure(unit)`? This version
  rejects them so a guard always has a real bind source.
- Should a guard condition be able to open type-test binders whose scope extends to later clauses?
  That would couple guard lowering to flow-refinement scope rules and is outside this proposal.
- Should the standard library offer an explicit `Result` guard combinator that takes a failure value,
  separate from `Filterable`? That would preserve short-circuiting without inventing a default
  error.
- If [ZEP-0170](./ZEP-0170.md) proceeds, should its for/do boundary and advisory `Stream` warning
  account for guarded `do` blocks, or continue to prefer `for` for concrete stream construction?
