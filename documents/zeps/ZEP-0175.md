# ZEP-0175: Structured Test Reports and JSON Diagnostics

## Abstract

Add opt-in machine-readable output to Zeron's test and compiler commands:

- per-test timing in the human test output and a versioned JSON test report covering both ordinary
  tests and `@CompileFailure` fixtures;
- a `--diagnostics json` mode that emits compiler diagnostics with code, severity, message, and
  source span.

The default human output, exit status, filtering, and test semantics do not change. These items
were left open by [ZEP-0169](./ZEP-0169.md); this proposal takes over that follow-up scope.

## Motivation

ZEP-0169 moved standard-library runtime coverage into `zeron.test` and added `@CompileFailure`,
filtering, `--list`, `--fail-fast`, assertion messages, and a distinct error count. It did not add
per-test timing, a machine-readable test report, or structured diagnostics.

Human output is intentionally readable rather than stable, so CI jobs and editor extensions must
either scrape it or reimplement discovery. Scraping couples those consumers to wording and layout.
Per-test timing is likewise unavailable, which makes slow tests and suite regressions hard to
identify. Compile-failure fixtures are especially opaque: their results are merged into the runner
summary but have no structured record.

The compiler has the same gap. Diagnostic codes and messages are stable enough for assertions, but
the only command-line representation is formatted prose with ANSI styling. A consumer that needs
the diagnostic span currently has to parse the rendering or invoke compiler internals.

A small, versioned JSON surface solves both problems without making JSON the default or turning
the human output into an API.

## Goals

- Report a wall-clock duration for every ordinary and compile-failure test in both human and JSON
  output.
- Emit one versioned JSON test report with a summary and one record per test, including status,
  duration, assertion message, and skip reason where applicable.
- Add `--diagnostics json` to commands that compile, with a versioned document carrying diagnostic
  code, severity, message, and span.
- Preserve human output and exit status when the new options are absent.
- Treat both JSON documents as versioned contracts with documented compatibility rules.
- Cover the new surfaces with golden-shape tests and keep the existing runner behavior intact.

## Non-goals

- JUnit XML, TAP, or a vendor-specific CI report format. JSON is the canonical machine format.
- Parallel test execution, test discovery changes, new assertions, fixtures, setup/teardown, or
  parameterized tests.
- Changing diagnostic wording, severity, ordering, or suppression rules.
- Making JSON the default output, or promising stability for the human-readable format.
- Source maps, debug metadata, IDE stepping, or language-server diagnostics.
- Precise benchmarking. Test durations are observations, not a performance guarantee.
- A general structured-logging or tracing framework for compiler phases.

## Proposal

### Command-line surface

`zeron test` gains an optional report destination:

```text
zeron test [target] --report <path>
```

- `<path>` receives one JSON document for the run, replacing an existing file.
- `--report -` writes the document to standard output. In that mode the human progress lines move
  to standard error so standard output contains only JSON.
- Without `--report`, output is unchanged.
- The report contains both ordinary tests and compile-failure fixtures, in the same order the
  runner executes them.

Per-test timing is always shown in the human output:

```text
test lang.optionMapsValues ... ok (2 ms)
compile-failure test cell.readOnlyMutation ... ok (118 ms)
147 passed, 0 failed, 0 errors, 0 skipped
```

The exact human layout remains presentation detail, not part of this contract.

Commands that compile accept `--diagnostics json`:

```text
zeron build --diagnostics json
zeron run --diagnostics json
zeron test --diagnostics json
```

The mode emits one JSON document to standard error and suppresses human-formatted diagnostics.
Standard output remains available for the command's normal output, including a program's output
under `zeron run`. Exit status is unchanged: diagnostics do not turn a successful command into a
failure, and `--deny-warnings` retains its existing effect. For `zeron test`, expected diagnostics
from `@CompileFailure` fixtures remain test results in the test report; the diagnostics document
carries only diagnostics produced while compiling the suite itself.

### Test report schema

The initial schema is:

```json
{
  "schemaVersion": 1,
  "target": "stdlib-runtime",
  "durationMillis": 11642,
  "summary": {
    "total": 150,
    "passed": 147,
    "failed": 0,
    "errors": 0,
    "skipped": 0
  },
  "tests": [
    {
      "name": "lang.optionMapsValues",
      "kind": "test",
      "status": "passed",
      "durationMillis": 2
    },
    {
      "name": "cell.readOnlyMutation",
      "kind": "compile-failure",
      "status": "passed",
      "durationMillis": 118,
      "fixture": "cell/read_only.zn"
    }
  ]
}
```

- `schemaVersion`, `target`, `summary`, and `tests` are required. `durationMillis` at the document
  level measures the test phase and excludes suite compilation.
- `name` is the fully qualified test name. `kind` is `"test"` or `"compile-failure"`.
- `status` is `"passed"`, `"failed"`, `"error"`, or `"skipped"`. `failed` means an assertion or
  expected-diagnostic mismatch; `error` means the runner, fixture compiler, or report producer
  failed internally.
- `durationMillis` is a non-negative integer for every executed test. A skipped test may report
  `0`.
- `message` is present for `failed` and `error` records and carries the assertion or diagnostic
  mismatch message.
- `skipReason` is present for `skipped` records.
- A compile-failure record includes `fixture`; when the annotation declares expectations, the
  record also carries `expectedCode` and `expectedMessage`.
- Summary counts must equal the records by status, and `total` must equal the number of records.

Durations are measured with a monotonic clock. Ordinary tests are timed by the generated runner;
compile-failure fixtures are timed by the host around compilation and comparison. Timing excludes
report serialization.

### Diagnostics schema

The initial diagnostics document is:

```json
{
  "schemaVersion": 1,
  "command": "build",
  "diagnostics": [
    {
      "code": "ZR2014",
      "severity": "error",
      "message": "Type mismatch",
      "path": "src/Main.zn",
      "range": {
        "start": { "offset": 42, "line": 2, "column": 4 },
        "end": { "offset": 49, "line": 2, "column": 11 }
      }
    }
  ]
}
```

- `schemaVersion`, `command`, and `diagnostics` are required. The array is empty on a clean
  compilation.
- `code` is the diagnostic code, without the explanation suffix. `severity` is `"error"` or
  `"warning"`. `message` is the compact diagnostic text without ANSI styling.
- `path` is normalized to forward slashes and is project-relative when the source is inside the
  project; otherwise it is the compiler's source path.
- `range` is optional when a diagnostic has no source location. Its line and column are zero-based
  and use UTF-16 code units, matching the language server's coordinates; `offset` is the UTF-16
  code-unit offset from the start of the file.
- Diagnostics appear in compiler emission order. The document is emitted on normal completion,
  including when the array is empty; an internal crash may terminate without a document and is
  reported through the exit status.

### Schema stability

Each document has its own integer `schemaVersion`, starting at `1`. The versions advance
independently because test reports and diagnostics have different producers and consumers.

Within a version:

- adding an optional field or a new enum value that consumers can ignore is allowed;
- changing field meaning, removing a field, changing a type, or changing coordinate semantics
  requires a new version;
- unknown fields must be ignored by consumers;
- the compiler and test runner emit only the fields documented for their version.

The schemas are documented in the command-reference and testing guides. Golden fixtures pin the
version-1 shapes, and compatibility tests assert that optional additions do not change existing
required fields.

### Relationship to ZEP-0169

ZEP-0169 remains `Implemented`; its accepted suite split and migration shipped in `0.9.0`. This
proposal owns the reporting work that ZEP-0169 listed as still open: per-test timing, the JSON
report and its schema decision, and the `--diagnostics json` compiler mode. This proposal does not
reopen the `0.9.0` bundle.

## Compatibility and impact

- No language or runtime semantic change.
- No API-index schema change and no standard-library API addition are expected. Timing uses the
  existing monotonic clock, and report serialization stays in the host runner.
- The CLI gains `--report` for `zeron test` and `--diagnostics json` for compiling commands.
- The generated test runner and the host's compile-failure phase must exchange per-test records.
  The transport is internal and does not become a public API.
- Scripts that parse human output are unaffected unless they opt into a new flag. Consumers of the
  new documents must follow the schema versions.
- `scripts/release.ps1` and CI can continue to run the suite as before; adopting the report is
  optional.
- Report writing must not corrupt a previous report on failure. Writing to a temporary file and
  replacing the destination on success is preferred.
- Messages may contain arbitrary Unicode, quotes, and control characters and must be escaped by
  the JSON writer; tests should cover this.

## Alternatives

- **Parse the existing human output** — rejected. Wording and layout are presentation details, and
  spans cannot be recovered reliably from rendered prose.
- **Use JUnit XML** — rejected. It models Java test concepts poorly, does not fit compile-failure
  fixtures naturally, and would require a second diagnostics format. A JSON-to-XML adapter can be
  added later without making XML canonical.
- **Emit one JSON object per test** — rejected for the initial report. A single document is easier
  to validate and archive, and test suites are small enough that streaming is unnecessary. A
  line-delimited mode can be considered separately if suites grow much larger.
- **Make JSON the default** — rejected. Human output is the primary developer experience, and
  existing scripts expect it.
- **Reuse language-server JSON-RPC types for CLI diagnostics** — rejected. The CLI does not need
  JSON-RPC envelopes, and coupling the schemas would make compiler output depend on LSP protocol
  evolution. Span coordinates still follow the language server.
- **Add diagnostics to the test report only** — rejected. `zeron build` and `zeron run` need the
  same structured diagnostics without running tests.

## Implementation and validation

Implementation stages:

1. Define both version-1 schemas, their documentation, and golden fixtures. Settle the escaping,
   path, and span rules before exposing the flags.
2. Time ordinary tests in the generated runner and print durations in the human output. Verify that
   timing does not change execution order or pass/fail behavior.
3. Add the host-side report model, merge ordinary and compile-failure records, and implement
   `--report <path>` and `--report -`.
4. Add `--diagnostics json` to `zeron build`, `zeron run`, and the suite-compilation phase of
   `zeron test`, preserving the human path as the default.
5. Document the schemas, update the command-reference and testing guides, and add CI coverage for
   parsing the report and checking the exit status.

Validation should cover:

- durations present and non-negative for passed, failed, error, and skipped tests, with a compile-
  failure duration measured across compilation;
- report summary counts matching records, both test kinds merged, and compile-failure mismatch,
  missing fixture, and unexpected-compile cases represented as `failed` or `error`;
- JSON escaping for quotes, backslashes, newlines, and non-ASCII messages;
- `--report -` producing clean standard output and human lines on standard error;
- atomic replacement and no stale report remaining after a failed write;
- diagnostics with errors and warnings, multiple files, no diagnostics, and diagnostics without a
  span;
- UTF-16 line, column, and offset agreement with the language server for non-BMP source text;
- `zeron run --diagnostics json` leaving program output on standard output and keeping the program's
  exit status;
- unchanged default output, `--filter`, `--list`, `--fail-fast`, and suite exit codes;
- the existing Maven suite, the `stdlib-tests` suite, and the packaged release smoke tests.

## Open questions

- Should `--report -` be supported in the first slice, or should the initial surface require a file
  path to keep standard output and standard error behavior simple?
- Should the diagnostics document be emitted for every normal completion, including an empty array,
  or only when at least one diagnostic exists?
- Should report-level `durationMillis` include suite compilation, or remain test-phase time with a
  separate compilation duration added later if requested?
- Should the test report include compiler warnings produced while compiling the suite, or are
  those left to the diagnostics document?
- Is integer milliseconds sufficient for per-test durations, or should the schema use microseconds
  to represent very fast tests without reporting zero?
- Should `--diagnostics json` also accept a file path, or is standard error sufficient for the
  initial consumers?
