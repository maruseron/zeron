## Abstract

Replace the ordinary-class member model for effect payloads with a canonical payload declaration
plus derived behavior. An effect declares an ordered, immutable component list in its header, like a
transparent data class. Components define construction, read-only access, and the positional pattern
surface. Methods, contract conformances, and computed properties remain available as derived
behavior, but they cannot add storage or writable state. Effect identity, `under` subtyping,
`responds`, and handler behavior remain effect-specific and are not inferred from the payload shape.

## Motivation

Effects currently accept the full ordinary class member model: fields, public and private properties,
mutable properties, initializer blocks, named constructors, methods, and contract conformances. That
surface makes an effect payload behave like a long-lived object with an implementation-layout API,
even though the value exists to carry a signal to a handler. It also makes the payload surface
ambiguous:

- a positional pattern has to choose between fields, canonical properties, auxiliary properties, and
  derived members;
- non-public fields can be constructed but not reached through the public effect type, so the
  pattern surface and the runtime access surface diverge;
- mutable payload state makes handler observations depend on when the handler runs, especially for
  response-typed effects that resume;
- fields, initializers, and arbitrary named constructors enlarge the compiled-library record without
  adding information that effect identity or handler dispatch actually needs.

A recent compiler failure demonstrates the ambiguity: a field-only effect accepted one positional
pattern component because the resolver counted canonical constructor fields, while the emitter read
the property list and failed with an index error. Fixing only the two counts would leave the deeper
question — what belongs to an effect payload? — unresolved.

The canonical/derived split is the useful part of the data-class model. Effects should adopt that
split without adopting structural equality, transparent construction, or class-style storage.

## Goals

- Give every effect one canonical, ordered payload surface.
- Make that canonical surface the only source of construction arguments and positional pattern
  components.
- Keep useful derived behavior: methods, contract conformances, and computed read-only properties.
- Remove arbitrary fields, mutable payload slots, initializer storage, and class-style named
  constructors from effect declarations.
- Preserve exact nominal effect identity, generic application identity, `under` subtyping,
  `responds`, and existing handler/resumption semantics.
- Make payload inheritance through `under` explicit and consistent between source and bytecode.
- Keep the compiled-library representation and diagnostics aligned with the source model.

## Non-goals

- Introducing structural equality, hashing, or serialization for effects by default.
- Changing handler matching, effect-row polymorphism, or continuation behavior.
- Adding effect subtyping through ordinary class inheritance or contract conformance.
- Adding generic `under` ancestry or other deferred generic-effect work.
- Redesigning the runtime carrier or the stateless-effect interface representation.
- Assigning an implementation schedule or release version.

## Proposal

### Canonical payload header

An effect declares its payload components in the declaration header, in declaration order:

```zeron
public effect MissingUser(id: Int, reason: String?) responds Unit {
    public description(): String = "missing user " + id;
}
```

The header is the effect's canonical payload and canonical constructor signature:

- Every component is a read-only property with a generated getter.
- Components are immutable slots; their values may still refer to mutable objects, as with data-class
  components.
- Components must have unique names and no defaults. Canonical `.new` requires every component.
- Canonical components are readable anywhere the effect is nameable. The effect's visibility gates
  nameability; there are no private canonical components and no backing fields visible to source.
- Constructing an effect uses only the canonical constructor, for example `MissingUser.new(7, null)`
  or `MissingUser.new` where the language already supports constructor references.

The exact clause order relative to `is`, `under`, and `responds` is a syntax detail to settle during
implementation; the components always form one contiguous header list.

### Derived behavior

The effect body may contain:

- instance methods, which may read canonical components, call other methods, and declare raised
  effects under the ordinary callable rules;
- ordinary contract conformances, so handler code can use reusable payload APIs;
- computed read-only properties whose getters derive values from canonical components or methods.

The body may not contain:

- fields or other stored state outside the canonical header;
- mutable properties, setters, or mutating receiver methods;
- initializer blocks or direct field initializers;
- named constructors.

Construction helpers that do not fit canonical `.new` are ordinary static functions returning the
effect. This keeps them out of the payload representation and the compiled-library constructor
surface.

Derived members are behavior, not payload. They do not participate in positional patterns, effect
identity, handler matching, equality, or the canonical constructor signature.

### Pattern surface

Positional effect patterns bind exactly the canonical components, in declaration order:

```zeron
fn recover(): Unit = handle (load()) with {
    case MissingUser(id, reason) -> log(id);
};
```

- The arity is the canonical component count.
- The component types come from the canonical header, after generic substitution.
- The alias form (`case MissingUser(id, _) as failure`) exposes canonical component getters plus
  derived methods and computed properties; it does not expose storage.
- Named property patterns may target canonical component properties. Derived properties are not
  destructurable.
- A field-only effect declaration is no longer valid, so there is no field/property count to
  reconcile at pattern emission. Under the current transitional model, such a pattern is rejected
  with a resolution diagnostic rather than reaching the emitter.

### Effect identity and `under`

Effect identity remains nominal plus exact closed generic application. The effect marker, raised
sets, handler matching, most-specific selection, and `responds` are unchanged.

`under` remains an effect-only subtyping relation. Payload inheritance follows one explicit rule:

- If the single payload-bearing parent has canonical components, the child's canonical header must
  begin with exactly those components, in the same order, with the same names and types. The child
  may append its own components.
- A child may not redeclare inherited components in a separate storage layout, and the parent's
  constructor receives only the prefix.
- Stateless parents impose no payload prefix.
- At most one direct parent path may carry payload state, as today.

For example:

```zeron
public effect IOError(path: String) {}

public effect FileNotFound(path: String, code: Int) under IOError {}
```

A handler case typed as `IOError` sees the inherited `path` component and `IOError` behavior, not
subtype-only components. A handler case typed as `FileNotFound` sees both components.

### Generic effects

Generic effects keep closed, invariant applied identity and the existing runtime descriptor. Header
components may mention the effect's type parameters. The canonical constructor and payload-side
getters carry the same erased representation and descriptor validation as other effect
constructors. This proposal does not add applied `under` ancestry.

### Representation and diagnostics

- A payload-bearing effect remains a non-final JVM class so an `under` child can extend it.
- Canonical components lower to private final storage with generated read-only accessors. Positional
  pattern emission uses those accessors; it never reads a private field directly.
- A stateless effect keeps the current marker-interface plus package-private implementation shape.
  Method calls on a stateless effect use interface dispatch.
- Declaration diagnostics reject fields, mutable or stored non-canonical properties, initializer
  blocks, and named constructors with messages that identify the canonical-header replacement.
- Pattern diagnostics use the canonical component count for both arity and type checking.
- The compiled-library index records canonical component names and types, methods, contracts,
  effect parents, response type, and the effect marker. It does not need field or named-constructor
  metadata for effect payloads. Reuse the existing exported-class record where possible; add a
  schema revision only if the current record cannot round-trip the restricted model.

## Compatibility and impact

This is a source-breaking payload restriction if accepted.

- Effects that declare only canonical public properties migrate those properties into the header.
- Effects with private fields, mutable properties, initializer blocks, or stored auxiliary state must
  move that state into canonical components, a separate ordinary object referenced by a component,
  or a different design.
- Effects with named constructors must use canonical construction or ordinary static helpers.
- Positional effects patterns that counted fields or auxiliary properties change arity; patterns
  that only used public canonical properties keep their behavior.
- Methods and contract conformances remain source-compatible when they do not mutate payload state.
- The compiled-library surface changes for effects that used removed members. Consumers compiled
  against the old class-member record may need recompilation.

[ZEP-0054](./ZEP-0054.md) remains the historical record for the class-member implementation. If this
proposal is accepted, it supersedes ZEP-0054's ordinary-class member model for effects. It also
amends the payload-inheritance details of [ZEP-0013](./ZEP-0013.md); effect subtyping itself is
unchanged. The transitional diagnostic for field-only positional patterns does not implement this
model and does not make the current payload surface canonical.

## Alternatives

- **Keep the class-member model and only align the resolver and emitter.** Rejected because it
  leaves hidden state, mutable payloads, arbitrary constructors, and competing pattern surfaces.
- **Restrict effects to public properties without a canonical header.** This is a smaller migration,
  but it still permits stored auxiliary properties, initializers, and constructors, so the payload
  surface remains implicit.
- **Reuse data classes literally.** Rejected because effects need an effect marker, exact nominal
  identity, `under` subtyping, `responds`, and handler semantics. Structural equality and class-style
  construction are not desirable consequences.
- **Make effects sum-like with named cases.** Rejected for this proposal: an effect is one nominal
  signal with one payload, not a closed family of alternatives. Handler cases already provide the
  dispatch surface.
- **Keep named constructors as pure delegating factories.** Deferred; they are additive sugar once
  the representation is fixed, and the first slice does not need them.

## Implementation and validation

Implementation stages:

1. Add canonical effect components to the parser and AST, reusing the data-class component shape
   where practical, and reject removed class-member forms during resolution.
2. Make the declaration resolver expose one canonical component list for construction, property
   access, patterns, and compiled-library export.
3. Update pattern resolution and emission to use canonical components and generated accessors only.
4. Implement the `under` payload-prefix rule and parent-constructor delegation.
5. Remove effect field and named-constructor metadata from the exported effect record where the
   existing format no longer needs it.
6. Migrate standard-library and test effects to canonical headers and computed behavior.

Validation must cover:

- canonical construction, read-only access, methods, contracts, and computed properties;
- positional and named pattern arity, generic substitution, aliases, and nested patterns;
- field/mutable/initializer/named-constructor declaration rejection with diagnostics;
- stateless interface construction and method dispatch;
- `under` payload prefix, parent-typed handler views, and parent constructor delegation;
- generic effect identity, response typing, resumption, and separate compilation through the API
  index;
- `javap` inspection confirming canonical accessors and the absence of direct private-field reads
  from handler code.

## Open questions

- Should derived computed properties be readable only through handler aliases, or also support named
  property patterns while remaining excluded from positional arity?
- Is a compiled-library schema revision necessary, or does the existing exported-class record
  round-trip canonical components and derived members without one?
- What migration path should mutable effect payloads use? ZEP-0013 currently exercises mutation
  through a parent-typed view; this proposal removes that capability from effects.
