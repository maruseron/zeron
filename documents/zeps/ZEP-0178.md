## Abstract

Complete the exact generic-effect propagation layer left between ZEP-0005, ZEP-0166, and ZEP-0107.
The compiler already accepts open effect applications and forwards them through generic calls. This
proposal makes a reified effect variable usable as an exact handler case and allows applied handler
arguments to be omitted only when the protected effect set determines one unique application.

The proposal deliberately stops before applied ancestry. ZEP-0107 remains the owner of generic
`under` matching, applied subtyping, and ancestor-aware dispatch. This ZEP supplies the exact
identity and runtime descriptor plumbing those features need.

## Motivation

ZEP-0005 introduced generic effect declarations with exact closed applications. ZEP-0166 removed
the closed-argument restriction from type positions, so declarations such as
`body: () -> Unit performs Yield<T>` now type-check and preserve `T` through generic calls. The
remaining gaps are at handler boundaries:

- a handler cannot name an effect-kinded type parameter, even when the parameter is reified and its
  exact descriptor is available;
- a generic effect case must repeat every applied argument, even when the protected effect set
  contains exactly one application;
- coverage does not yet define when an effect-variable case handles a row variable or a concrete
  applied effect.

These gaps block ZEP-0107. Applied ancestry cannot be layered onto handler dispatch until there is
a defined exact match for a reified effect variable. They also make generic code that forwards an
effect have to erase or specialize at the handler, which defeats the point of open applications.

## Goals

- Allow an unguarded handler case to name a reified, effect-kinded type parameter.
- Match that case by the reified exact descriptor, using the same nominal behavior as a concrete
  case for non-generic effects.
- Infer omitted applied arguments in a handler case only when the protected effect set determines a
  unique closed application.
- Define row coverage and subtraction for effect-variable and omitted-argument cases.
- Preserve existing generic forwarding and open application behavior from ZEP-0166.
- Keep runtime dispatch deterministic and consistent across separate compilation.
- Give ZEP-0107 a defined exact-match base to extend with applied ancestry.

## Non-goals

- Applied `under` edges, applied ancestry, or generic subtype matching; those are ZEP-0107.
- Wildcard or existential effect cases such as `Failure<_>` or `case _`; ZEP-0107 excludes them and
  they need their own selection rules.
- Changing effect-row polymorphism from ZEP-0086.
- Changing response typing, tail resumption, or multi-shot continuations.
- Runtime construction of an applied effect from non-reified type arguments.
- Generic external (Java-bound) effects.
- Making an effect variable a wildcard for every effect. An effect-variable case matches its exact
  runtime identity unless ordinary nominal effect subtyping already applies.
- Adding a public runtime reflection API for descriptors.

## Proposal

### Reified effect variables as handler cases

A handler case may name a type parameter when the parameter is declared `reified T admits effect`.
The case uses the hidden descriptor already supplied by `reified`; no new descriptor slot is added.

```zeron
public effect Failure<T admits nullable> {
    public property value: T;
}

fn recover<T admits nullable, reified E: Responds<Never> admits effect>(
    body: () -> Unit performs Failure<T> | E
): Unit = handle (body()) with {
    case Failure<T>(value) -> log(value);
    case E -> ();
};
```

The parameter itself must denote one effect, not a row (`effect...`). A row variable cannot be
named by a handler case. A non-reified effect parameter remains unavailable for handler matching,
because there is no runtime identity to compare.

`case E` uses the same handler-selection rules as a concrete effect case:

- for a non-generic instantiation, ordinary nominal effect subtyping applies, so a parent-typed
  case still catches its declared subeffects;
- for an applied generic instantiation, the application is exact until ZEP-0107 adds applied
  ancestry;
- the case is not a catch-all for unrelated effects merely because they share a bound;
- an unguarded, irrefutable variable case covers the variable's contribution to the protected row.

The alias and payload syntax remain the ordinary effect-case syntax. A variable case may bind the
payload with `as`; it may not bind a resume token unless the variable's response type is statically
known and the existing tail-resumption rules apply.

### Omitted applied arguments

A generic effect case may omit its applied arguments:

```zeron
public effect Missing<T> {
    public property value: T;
}

fn first<T admits mutable>(
    body: () -> Unit performs Missing<T>
): Unit = handle (body()) with {
    case Missing(value) -> log(value);
};
```

Omission is inference from the statically known protected effect set, not runtime search. The
inference rule is:

1. Resolve the unapplied effect name in the protected set. If it is not a generic effect
   declaration, omission is the existing non-generic form.
2. If exactly one closed application of that effect is present in the protected set, use it.
3. If the protected set contains zero or several applications of that effect, reject the omission
   and require explicit arguments.
4. If the relevant set is open (a row variable or an unresolved application), reject the omission
   unless an enclosing explicit expected-type context determines the application.

Inference never uses handler source order, declaration order, or runtime observation. It is
performed before coverage is computed, so all cases and the resulting escaping row see one
deterministic protected set. Explicit arguments remain the canonical form and are always accepted.

The rule applies to the applied effect identity. Payload component patterns keep their existing
arity and type checking after the application is inferred.

### Propagation and coverage

Generic call substitution remains pointwise: an open application is closed by the caller's type
arguments, and a function value's raised row is preserved through generic forwarding. This is the
behavior ZEP-0166 shipped; this proposal adds tests and handler semantics rather than changing it.

For coverage:

- A case over a reified variable covers exactly the protected set entry named by that variable,
  subject to the nominal and exact behavior above.
- A case with inferred applied arguments covers the application selected by the inference rule.
- A case with explicit applied arguments keeps the existing exact-application coverage rules.
- A guarded case is refutable and does not remove its effect from the escaping row.
- An unhandled variable contribution remains in the escaping row and must be declared by the
  enclosing callable.

For the example above, `case Missing(value)` removes `Missing<T>` from the handler's protected
row. It does not remove another `Missing<U>` application, and it does not imply wildcard behavior.

### Runtime representation

- A reified effect variable reuses the existing descriptor hidden argument.
- A non-generic effect case continues to use ordinary payload-class dispatch.
- An exact applied case compares the payload descriptor through ZEP-0015 equality, as ZEP-0005
  already does for closed cases.
- An inferred application emits the same descriptor comparison as its explicit form; inference is
  erased before emission.
- No payload field, carrier field, or new runtime metadata is introduced.

### Library index and separate compilation

Open applications and reified effect variables already round-trip through the existing descriptor
and type-parameter metadata. The omitted-argument form is source-only and normalizes to an explicit
application before export. No API-index schema bump is expected; implementation must verify that
the normalized signature and reified variable metadata survive separate compilation. If the current
index cannot encode an effect-variable handler's inference anchor, reject the index version rather
than guessing.

## Compatibility and impact

This is additive for source programs. Existing concrete, closed-application, and generic-forwarding
programs keep their behavior. Previously rejected reified effect-variable cases and unambiguous
omitted-argument cases become valid.

The runtime changes are localized to descriptor comparisons already used by applied effects.
Compiled libraries retain the existing descriptor and admissibility metadata; no new ABI is
introduced. Diagnostics for ambiguous omitted arguments and non-reified variable cases must be
stable enough for library authors to correct signatures without inspecting handler order.

ZEP-0107 remains separate and still needs its ancestral metadata. This proposal only defines the
exact case that 0107 extends. It also does not reverse ZEP-0005's rejection of non-reified runtime
construction.

## Alternatives

- **Require explicit applied arguments forever.** Rejected for the common single-application case,
  where the protected set makes the application unambiguous. Explicit arguments remain available.
- **Infer the omitted application from runtime candidates.** Rejected because dispatch would depend
  on evaluation order and could silently choose a different application than coverage assumed.
- **Treat `case E` as a wildcard over all effects admitted by `E`.** Rejected: that conflates exact
  handler identity with applied ancestry, which belongs to ZEP-0107.
- **Use erased payload classes only.** Rejected because it cannot distinguish `Failure<Int>` from
  `Failure<String>` and would bind the wrong payload type.
- **Add a separate reflection or descriptor API.** Rejected; the reified descriptor is already an
  internal compile-time input and does not need a public query surface.
- **Fold this into ZEP-0107.** Rejected because exact effect-variable matching and omitted
  arguments are independently useful and must be validated before ancestry is layered on top.

## Implementation and validation

Implementation stages:

1. Accept an effect-kinded type-parameter case in the parser and resolve it against the handler's
   in-scope type parameters.
2. Require the parameter to be reified and effect-kinded; reject row variables and non-effect
   parameters with a diagnostic at the case.
3. Implement omitted applied-argument inference against the resolved protected effect set, before
   coverage and escaping-row calculation.
4. Emit exact descriptor comparisons for reified variable cases and normalized explicit
   applications.
5. Update coverage and escaping-row subtraction for variable and inferred cases.
6. Preserve the normalized form and reified metadata through the API index.

Validation must cover:

- non-generic effect subtyping through a parent-typed variable case;
- exact applied matching for `Failure<Int>` versus `Failure<String>`;
- a reified variable case with and without a guard, and its effect on the escaping row;
- explicit versus omitted applied arguments with one, zero, and multiple candidates;
- an open protected row that cannot determine an application;
- generic forwarding through nested calls and function values;
- response-typed variables only where the response type is statically known;
- separate compilation of a library declaring the effect and a client using the variable case;
- bytecode inspection showing descriptor comparison rather than a payload-class-only match for
  applied effects.

## Open questions

- Should the omitted-argument inference also apply when the protected set contains a subtype
  application, or should it require an exact application match?
- Should an effect-variable case be permitted with an alias but no payload pattern, and how should
  the alias type mention an applied argument that is not statically known?
- Should a `case E` over a reified variable be allowed to bind a resume token when `E` has a
  `Responds<R>` bound but its concrete response type is not otherwise known?
- Does the existing API index need an explicit inference-anchor field for omitted applications, or
  is normalization to the explicit application sufficient for all consumers?

## Decision

No decision recorded. This proposal is `Draft` and `Unscheduled`. It is the exact-propagation
prerequisite for [ZEP-0107](./ZEP-0107.md); ZEP-0107 remains the owner of applied ancestry and
wildcard/existential behavior.
