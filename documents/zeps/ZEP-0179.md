# ZEP-0179: Release Plans and Candidate Tracking

## Abstract

Add a temporary release plan between durable workstream planning and a published release. A release
plan records which workstream parts are candidates for one release, which are selected for its
frozen scope, and which release-local tasks are needed to publish it. Candidates are not version
commitments, selected parts must be `Ready`, and proposal and part statuses remain owned by their
existing sources of truth.

This preserves the useful visibility of an acceptance queue without reintroducing `Candidate` or
`Planned` as ZEP tracker states or assigning future versions to workstream parts.

## Motivation

Workstreams answer “what remains for this concern?” They do not answer “what are we trying to ship
next?” A release crosses workstreams, may include release-only work such as packaging and migration
notes, and needs an explicit place to show nominated work before it is complete.

The retired version-bundle model mixed those questions and made every accepted item look committed
to a version. Removing it fixed the false commitments, but it also removed the only place to list
work that is being considered for a release. Workstream pages alone cannot express a cross-workstream
release theme, a scope freeze, or the release engineering checklist.

The release plan should be the release-scoped view. It should be temporary, should not become a
second status system, and should disappear into an archived historical plan once the release ships.

## Goals

- Give each active release one visible candidate and selected-scope list.
- Let accepted, not-yet-ready work be nominated without implying a version commitment.
- Require `Ready` status and satisfied dependencies before a part enters selected scope.
- Track release-local work that is not a durable workstream part.
- Keep ZEP status, workstream part status, and release membership separate.
- Preserve historical plans after publication without keeping stale active plans.
- Make release scope reviewable at a single cross-workstream checkpoint.

## Non-goals

- Reintroducing `Candidate` or `Planned` as ZEP tracker release states.
- Adding release columns or future version assignments to workstream part tables.
- Changing the ZEP proposal lifecycle, workstream part statuses, or artifact versioning policy.
- Replacing the release ledger or the ZEP tracker as historical sources of truth.
- A general project-management system, estimates, sprints, or issue-tracker synchronization.
- Guaranteeing that a candidate is selected or that a selected part ships.

## Proposal

### Three distinct records

| Record | Owns |
| --- | --- |
| ZEP tracker | Proposal status and published release history |
| Workstream page | Durable concern, part scope, dependencies, and part status |
| Release plan | Candidate and selected release scope, release-local work, and publication checklist |

A release plan references workstream parts; it does not copy their full design or change their
status. The workstream page remains authoritative for whether a part is `Draft`, `Accepted`,
`Ready`, `Shipped`, or `Deferred`.

### Files and lifecycle

The release-plan home is `documents/releases/`:

```text
documents/releases/
  README.md
  current.md
  <version>.md
```

- `README.md` defines the policy and the current-plan link.
- `current.md` is the single active plan.
- `<version>.md` is the archived plan created when a release is published.

The target version may be `unassigned` while the plan is exploratory. Once maintainers explicitly
open a release, the plan may name the target version. Naming the target does not assign that version
to individual workstream parts; only selection and publication do.

Plan statuses are:

- **Planning** — candidates are being collected and reviewed.
- **Scope frozen** — selected scope is fixed; only `Ready` parts may remain selected.
- **Stabilization** — the release candidate is being built and validated.
- **Published** — the plan is archived and the release ledger is updated.
- **Abandoned** — the plan will not produce a release; record why and leave it outside the ledger.

### Candidate and selected scope

The plan uses release dispositions, not new ZEP or workstream statuses:

- **Candidate** — nominated for this release. A candidate may still be `Draft` or `Accepted`; the
  nomination is visibility, not a commitment.
- **Selected** — in the frozen release scope. A part is selected only when it is `Ready` and every
  dependency is `Shipped` or `Ready` as appropriate.
- **Dropped** — removed from this plan. Record the date and reason; the part itself is unchanged.

A candidate table records the part, ZEP, workstream, next gate, dependencies, owner or `—`, last
review date, and disposition. The next gate is the work needed before readiness, such as
“implementation,” “design acceptance,” or “dependency ZEP-0091.”

The selected scope is empty during planning unless the plan is already frozen. At the scope-freeze
checkpoint, every selected part must be `Ready`; anything still incomplete moves to candidates or
dropped/deferred. The plan may not silently add selected parts after freeze.

### Release-local work

Release notes, version bump, API-index checks, packaging, launcher smoke tests, and migration
documentation belong in a separate release-engineering table. These tasks use plan-local names and
must not be created as artificial workstream parts.

### Single active plan and update rules

- Exactly one `current.md` is active.
- The release lead updates release dispositions; workstream owners update part statuses.
- The plan records a last-reviewed date and should not duplicate part status beyond the disposition
  needed for release scope.
- A candidate that remains unselected across review checkpoints must be re-nominated or dropped;
  there is no indefinite candidate state.
- When the release publishes, mark included parts `Shipped`, add the release-ledger row, mark the
  corresponding ZEP rows with the published version, archive `current.md` as `<version>.md`, and
  restore `current.md` to an empty planning state.

### Relationship to the retired acceptance queue

The old acceptance queue listed accepted ZEPs against a future version. The candidate table keeps
the useful part — accepted work is visible before implementation — while removing the false
commitment:

- a candidate can be `Draft` or `Accepted`;
- its ZEP remains `Unscheduled` in the tracker;
- its workstream part keeps its own status;
- no workstream part gains a release column;
- selection happens only after the part is `Ready`.

## Compatibility and impact

This is a documentation and process change. It does not alter compiler behavior, artifact
versioning, the ZEP lifecycle, or workstream part statuses. Existing release history and the release
ledger remain valid. The first active plan records the current release candidates; no historical
row is rewritten.

## Alternatives

- **Add a target-release column to every workstream part.** Rejected: it recreates future version
  assignments, duplicates release scope across pages, and makes every workstream responsible for a
  cross-workstream decision.
- **Restore `Candidate` and `Planned` in the tracker.** Rejected: it conflates design acceptance
  with release commitment and was the problem ZEP-0176 removed.
- **Use a single flat backlog.** Rejected: it cannot express the release theme, selected scope,
  dependencies, or a scope freeze.
- **Use GitHub milestones only.** Rejected as the source of truth: release decisions belong in the
  repository with the workstream and ZEP records. External tooling may mirror the plan.
- **Keep only a release ledger.** Rejected: history records what shipped, not what is being
  considered or what remains before a release candidate is viable.

## Implementation and validation

The implementation adds:

1. This process ZEP and its tracker row.
2. `documents/releases/README.md` with the policy and current-plan link.
3. `documents/releases/current.md` with the active target, candidate table, selected scope,
   dependencies, release engineering, and checklist.
4. Links from the workstream index, ZEP process guidance, navigation, and release checklist.
5. The archive convention for published plans.

Validation:

- exactly one active release plan is linked;
- every candidate names an existing workstream part and ZEP;
- selected scope contains only `Ready` parts with satisfied dependencies;
- no future version is assigned in the tracker or workstream part tables;
- the archived plan and ledger agree after publication;
- `current.md` is reset to an empty planning state after archiving.

## Decision

Accepted and implemented on 2026-11-26. Release plans are release-scoped views over workstream
parts. They track candidates and selected scope, carry release-local work, and preserve the rule
that only `Ready` parts can be selected. ZEP tracker states and workstream part statuses are
unchanged.
