## Abstract

This proposal replaces the hidden `MethodHandle` parameter that the compiler currently emits for
every contract method slot with a generated witness interface and a witness object. A generic
function or method receives one evidence parameter per bounded type parameter: the witness interface
for a single bound, or a generated dictionary for multiple bounds. Contract calls inside generic code
become direct `invokeinterface` calls on the witness object. Evidence selection remains static and
compile-time; only the erased representation changes.

The proposal defines witness interfaces, witness classes, evidence dictionaries, HKT and
derived-witness migration, library-index and separate-compilation rules, and a staged migration from
`MethodHandle` evidence. Condy and `invokedynamic` linking of witness constants and factories are
defined by [ZEP-0181](./ZEP-0181.md); hidden-class anonymous constants are
[ZEP-0182](./ZEP-0182.md).

## Motivation

Zeron currently represents contract evidence as one hidden `MethodHandle` per contract method slot.
`BytecodeEmitter.evidenceFields`, `witnessSlots`, and `withEvidenceParameters` append those handles to
generic function and method descriptors; `emitEvidenceArguments` loads a direct method handle for
each slot and binds prerequisite evidence with `MethodHandles.insertArguments`; and calls through
evidence use `MethodHandle.invoke` at the exact erased signature. The class-file quality inventory
measured the result directly:

- a generic function with a `Numeric<T>` bound carries seven `MethodHandle` parameters;
- a generic function with an `Integral<T>` bound carries sixteen, because `Integral` requires
  `Numeric`, `Hashable`, and `Comparable`, and each requirement contributes its own slots;
- every call site loads one `ldc` method-handle constant per slot and may call
  `MethodHandles.insertArguments` for prerequisite evidence;
- every contract operation is a signature-polymorphic `MethodHandle.invoke` call rather than a
  nominal interface call that the JIT can profile and inline.

The cost is not limited to numeric helpers. The standard library is written generically, so
collection, sorting, hashing, serialization, and effect code inherit the same descriptor bloat and
dispatch. HKT operations use the same hidden-handle representation ([ZEP-0019](./ZEP-0019.md)), and
lambda templates carry evidence arrays of method handles. The representation also couples separately
compiled libraries to the exact handle kind and binding convention of each witness.

A witness interface gives the compiler a stable, nominal dispatch surface. The erased method table is
known from the contract, so generic code can use `invokeinterface` with an ordinary JVM call site. The
witness object carries the statically selected implementation and any prerequisite evidence. This
removes the per-slot handles, the signature-polymorphic call sites, and the `insertArguments`
composition at each use. It also gives the JVM a monomorphic receiver profile in the common case and
a normal polymorphic inline cache when a generic function is instantiated with several types.

## Goals

- Replace hidden `MethodHandle` evidence parameters with generated witness interfaces.
- Pass one evidence parameter per bounded type parameter, using a generated dictionary when the type
  parameter has multiple bounds.
- Emit one witness class per witness declaration, not one class per type argument.
- Dispatch contract operations with `invokeinterface` rather than `MethodHandle.invoke`.
- Preserve static evidence selection, coherence, orphan rules, and witness activation exactly.
- Preserve HKT evidence, derived witnesses, default methods, static contract methods, generic
  contract methods, effects, nullability, evaluation order, and exception behavior.
- Define the witness-interface, witness-class, and dictionary ABI for separate compilation.
- Define the library-index and versioning impact.
- Provide a staged migration from `MethodHandle` evidence without changing source programs.
- Keep the statically known direct-call path from [ZEP-0095](./ZEP-0095.md) and the specialized entry
  points from [ZEP-0096](./ZEP-0096.md) as preferred optimizations.

## Non-goals

- Primitive specialization, monomorphization, or primitive-backed collections; those remain owned by
  [ZEP-0096](./ZEP-0096.md).
- Inlining evidence when the concrete witness is statically known; that remains owned by
  [ZEP-0095](./ZEP-0095.md).
- Dynamic contract lookup, runtime type tokens, reflection-based witness discovery, or runtime
  dictionary search.
- Changing witness provision, requirement evidence, owner-directed dispatch, bundle selection,
  import activation, or explicit witness selection.
- Adding source syntax, source-level witness values, or first-class evidence.
- Removing erased generic entry points or the throwing evidence stubs.
- Condy and `invokedynamic` bootstrap details; those are owned by [ZEP-0181](./ZEP-0181.md).
- Hidden-class anonymous objects and handlers; those are owned by [ZEP-0182](./ZEP-0182.md).
- A stable Java interop or reflection API for generated witness types.
- Guaranteeing a particular JIT outcome or a fixed class-count reduction.

## Proposal

### 1. Selection and representation are separate

The proposal changes only how already-selected evidence is represented in generated bytecode.
Selection stays compile-time and deterministic:

- the resolver selects the same witness for the same contract and target type;
- the same coherence, overlap, orphan, import, default-witness, bundle, and explicit-selection rules
  apply;
- no runtime lookup, type test, or `Class` token participates in evidence selection;
- a generic caller forwards the evidence it received or a compile-time projection of it.

The new representation is a passive carrier for the selected witness. It is not a runtime dictionary
lookup, not a source-level value, and not a new dispatch model. This distinction is what keeps the
proposal compatible with the witness-model decisions in
[ZEP-0114](./ZEP-0114.md), [ZEP-0135](./ZEP-0135.md), [ZEP-0136](./ZEP-0136.md), and
[ZEP-0137](./ZEP-0137.md).

### 2. Witness interfaces

A **witness interface** is a generated public synthetic interface for a bound. It contains one
abstract instance method per flattened contract-method slot used by the current evidence fields. The
interface is erased over the bound's type arguments.

- The method descriptor is the erased contract-method descriptor. For an instance contract method,
  the receiver is the first parameter. For a static contract method, the witness interface method
  is still an instance method on the witness object and takes only the source parameters; this gives
  all operations one dispatch form.
- Generic contract methods append their own hidden evidence and reified-descriptor parameters after
  the source parameters, in the same order the current hidden parameters use.
- Method names are deterministic and collision-free: `$zeron$w$<slot>$<sourceName>` for a single
  bound, and `$zeron$w$<bound>$<slot>$<sourceName>` for a composed bound or dictionary. `$` is not
  legal in a Zeron identifier, so these names cannot collide with source methods.
- Default contract methods are declared abstract on the witness interface. The witness class
  implements them by delegating to the generated default helper. The interface carries no default
  method bodies.
- Mutating contract methods keep their existing restriction: a witness that cannot implement them
  cannot satisfy the bound. The witness interface mirrors the same slot set the current evidence
  fields use; no new admissibility rule is introduced.
- A bound with no evidence slots contributes no parameter, matching current behavior.

The witness interface is emitted by the contract's provider, not by each consumer. It is part of the
contract's generated ABI, like the contract interface itself. A consumer that declares a witness for
an imported contract implements the provider's witness interface, so cross-library witnesses work
without regenerating the interface. The interface is public only so generated code in other packages
and libraries can implement and invoke it; it is not nameable from Zeron source and has no reflection
or serialization contract.

### 3. Witness classes

A **witness class** is a generated public final synthetic class that implements the witness interface
for a witness declaration. It is emitted once per witness declaration, not once per type argument.

- The class holds final fields for the prerequisite evidence the witness needs. A generic witness
  such as `Eq<Array<T>>` holds an `Eq` witness for `T`; an `Integral` witness holds the witnesses for
  its required contracts. The fields use the same erased witness-interface types the current
  `insertArguments` composition binds.
- The class constructor takes those prerequisite witnesses, plus any reified descriptors or other
  hidden arguments the current evidence closure binds. The order and descriptors are deterministic
  and recorded in the library index.
- A witness with no prerequisite evidence and no other hidden state exposes a
  `public static final` singleton of the witness-interface type. The compiler may load it with
  `getstatic` or a condy constant ([ZEP-0181](./ZEP-0181.md)). A witness with prerequisites is
  constructed at the call site, or cached as a condy/indy constant when its prerequisites are
  constants.
- Each method delegates to the existing static witness helper. The helper remains the source of
  truth for the witness body, so default methods, delegated class implementations, derived
  witnesses, and user-written methods keep their current behavior. The helper is generated in the
  same compilation unit as before.
- The witness class adapts the erased interface descriptor to the helper descriptor. When the helper
  is primitive-specialized, the erased interface method boxes and unboxes at its boundary. That
  boxing is the same cost the current erased `MethodHandle.invoke` path pays; [ZEP-0095](./ZEP-0095.md)
  and [ZEP-0096](./ZEP-0096.md) remove it on statically known and specialized paths.
- The witness class never exposes the witness object as a source-visible value. Contract methods
  that return the receiver return the receiver parameter, not the witness object.

The witness class is emitted by the witness declaration's provider. A witness for an imported
contract implements the provider's witness interface but lives in the declaring library. A consumer
that selects an exported witness uses the exported witness class and its constructor/singleton, as
recorded in the library index.

### 4. Evidence parameters and generic code

A generic function or method appends one hidden evidence parameter per bounded type parameter, in
declaration order, after its source parameters and before reified-descriptor parameters. This
replaces the current one-parameter-per-slot layout.

| Type parameter | Evidence parameter |
| --- | --- |
| `T: Numeric<T>` | one `Witness$Numeric` parameter |
| `T: Numeric<T> + Hashable<T>` | one `Evidence$Numeric$Hashable` dictionary parameter |
| `T: Integral<T>` | one `Witness$Integral` parameter, whose witness object holds the prerequisite evidence |
| `T` with no contract bound | no parameter |

Inside generic code:

- A contract call loads the evidence local/parameter and emits `invokeinterface` on the witness
  interface method. There is no `MethodHandle.invoke`, no `ldc` method handle, and no
  `MethodHandles.insertArguments`.
- A call that forwards the same bound passes the evidence parameter unchanged.
- A call that needs a subset of a multi-bound dictionary reads the bound witness through a
  dictionary accessor. A call that needs a superset constructs a new dictionary from the available
  witnesses; if a required witness is not in scope, resolution fails exactly as it does today.
- A lambda or function value that captures evidence stores the witness object in its capture field.
  Witness objects are immutable and safe to share across closures.
- HKT operations use the same witness interfaces. The HKT witness class holds the constructor's
  prerequisite evidence; the HKT helper remains a static method. The HKT bridge in
  `DeclarationEmitter.generateHktImplementationBridge` copies witness-interface parameters instead of
  `MethodHandle` parameters.
- `Main<A>` and other compiler-owned contracts use the same evidence protocol. The launcher receives
  the `Main` witness object instead of a `MethodHandle`.
- Derived equality and hashing use the `Eq`/`Hashable` witness interfaces for unresolved type
  parameters. The direct component paths from [ZEP-0095](./ZEP-0095.md) remain unchanged.
- Lambda template specialization passes witness objects instead of a `MethodHandle[]`. The runtime
  template support validates the evidence shape and forwards the objects to the specialized body.

At a call site with statically known type arguments, the compiler selects the witness objects and
dictionaries, loads or constructs them, and appends them to the call. The construction/caching
strategy is defined by [ZEP-0181](./ZEP-0181.md). A statically known direct call may bypass evidence
entirely under [ZEP-0095](./ZEP-0095.md), and a primitive-specialized entry point may use a
specialized descriptor under [ZEP-0096](./ZEP-0096.md); the witness-interface path is the erased
fallback and the cross-library ABI.

### 5. Multi-bound dictionaries

A type parameter with more than one bound uses a generated **evidence dictionary**. The dictionary
interface has:

- one operation method per `(bound, slot)` pair, named `$zeron$w$<bound>$<slot>$<sourceName>`;
- one accessor method per bound, named `$zeron$bound$<bound>`, returning that bound's witness
  interface.

The dictionary class is generated at the call site or holder that constructs it. It holds one
witness-interface field per bound and implements the operation methods by delegating to the
corresponding witness object. The accessors return the fields. The dictionary interface is shared by
the bound set; the dictionary class is a local implementation. The index records the interface and
its bound order. A provider that exports a dictionary factory also records that factory descriptor.

The dictionary is a tuple of statically selected witnesses, not a lookup table. It has no names,
keys, or runtime search. This is the "dictionary" shape [ZEP-0096](./ZEP-0096.md) section 4
anticipated, with one deliberate difference: the entries are typed witness interfaces, not
`MethodHandle`s.

### 7. Library index and separate compilation

The API index must describe the new evidence ABI:

- For each exported contract, record the witness interface name and its ordered slot table
  `(slot, method name, descriptor)`.
- For each exported witness, record the witness class name, constructor or singleton descriptor, and
  the ordered prerequisite evidence it expects.
- For each generic function or method signature, record the ordered evidence parameter descriptors
  (witness interface or dictionary interface), not only a count.
- For each exported dictionary interface, record its bound order, operation method table, and
  accessor table.
- Record a witness-ABI version so a consumer can reject an incompatible provider.

This is a binary schema change. It requires an `API_INDEX_SCHEMA_VERSION` review and a
`STANDARD_LIBRARY_API_VERSION` review under [ZEP-0012](./ZEP-0012.md). Both values may be bumped only
once per release cycle, so the change must be consolidated with any [ZEP-0096](./ZEP-0096.md) schema
change that ships in the same cycle.

Compiled libraries have three possible compatibility rules:

1. **Dual ABI during migration.** Keep the existing `MethodHandle` entry points and add
   witness-interface entry points with a stable suffix. New consumers prefer the witness form; old
   consumers keep the handle form. Remove the old form after the compatibility window.
2. **Hard ABI break.** Rebuild every compiled library and reject old indexes through the schema
   check. This is simpler and is consistent with the pre-1.0 library policy, but it requires a
   release note and a coordinated standard-library rebuild.
3. **Per-contract compatibility.** Detect old contracts in the index and emit the old handle form
   only for those signatures. This has the highest complexity and should be used only if the
   migration window requires it.

The proposal recommends the dual-ABI or hard-break rule, chosen at release time. It does not require
per-contract mixing.

Java interop does not gain a stable API for witness types. Generic Zeron functions with evidence
parameters are compiler-internal entry points; Java callers continue to use the existing monomorphic
or erased bridges. Witness interfaces and classes are public synthetic types, but their names and
descriptors are not a reflection or serialization contract.

### 8. Migration stages

1. **Emit alongside.** Generate witness interfaces, witness classes, and dictionaries alongside the
   existing `MethodHandle` evidence. Keep the old descriptors and call sites. Validate witness
   classes against the existing helpers and record the new metadata in the index under a new schema
   version.
2. **Switch generic entry points.** Change generic function/method descriptors and call sites to
   witness-interface evidence. Keep old entry points as bridges for the compatibility window.
3. **Migrate HKT, derived witnesses, `Main`, and lambda templates.** Replace the remaining
   `MethodHandle` evidence paths.
4. **Remove the old representation.** Delete `MethodHandle` evidence fields, `insertArguments`
   composition, the handle-based stubs, and the old entry points after the compatibility window.
5. **Clean up the index and runtime support.** Remove obsolete metadata and update the quality
   baseline.

Each stage is independently testable. Stage 1 can land without changing source behavior; stage 2 is
the ABI switch.

## Compatibility and impact

Source compatibility is preserved. Observable behavior, including evaluation order, null checks,
exceptions, effect handling, and contract selection, must not change.

Class-file impact:

- Generic function and method descriptors change from per-slot `MethodHandle` parameters to
  per-type-parameter witness/dictionary parameters.
- New witness interfaces, witness classes, and dictionary interfaces/classes are emitted.
- HKT bridges, `Main` evidence, lambda template support, and derived equality/hashing helpers change
  their hidden parameter types.
- The old entry points may remain as bridges during migration.
- Witness class and interface names are synthetic and deterministic; they are not source names.

Library and API-index impact:

- The index schema and standard-library API version require a coordinated bump.
- Old compiled libraries either use the compatibility bridges or must be rebuilt.
- The standard-library JAR must be rebuilt with the new evidence ABI.
- The release notes must state the compatibility rule and the minimum compiler version.

Runtime impact:

- Witness objects are immutable and shared. Their identity is not observable from Zeron source.
- A capture-free witness can be a singleton; a witness with prerequisites is a small immutable
  object. Condy/indy caching ([ZEP-0181](./ZEP-0181.md)) controls allocation and startup cost.
- The erased witness-interface path still boxes primitive arguments at its boundary. This is not a
  regression relative to the current erased `MethodHandle` path; direct inlining and specialization
  remove the boxing on their paths.

Determinism and reproducible builds remain requirements. Witness interface/class names, dictionary
layouts, constructor descriptors, and evidence parameter order must not depend on hash-map iteration
order, call discovery order, or wall-clock state.

## Alternatives

- **Keep hidden `MethodHandle` evidence.** This is the current behavior. It preserves the ABI but
  keeps 7–16 parameter descriptors, per-slot handle constants, `insertArguments` composition, and
  signature-polymorphic dispatch. The JIT cannot treat the witness call as an ordinary interface
  call.
- **Use one `MethodHandle` per bound instead of per slot.** This shrinks the descriptor but still
  requires `MethodHandle.invoke` and still hides the operation table from the JIT. It does not give
  the compiler a nominal method table for HKT or derived witnesses.
- **Pass one `Object[]` of evidence.** This reduces the parameter count but loses type safety,
  requires casts and array allocation, and still needs `MethodHandle.invoke` or reflection to reach
  the operations.
- **Generate a `MethodHandle`-based dictionary.** A dictionary object holding handles would reduce
  parameters but keep signature-polymorphic dispatch. It is strictly worse than a witness interface
  for the same object shape.
- **Use an `invokedynamic` polymorphic inline cache for dispatch.** Evidence is statically selected,
  so there is no runtime type key to dispatch on. A hand-written PIC would duplicate the JVM's
  `invokeinterface` inline cache, add a bootstrap and a guard, and reintroduce the dynamic lookup the
  witness model forbids. [ZEP-0181](./ZEP-0181.md) records this as a non-goal.
- **Monomorphize every generic function.** This removes the erased path but conflicts with separate
  compilation and code-size goals. [ZEP-0096](./ZEP-0096.md) owns bounded specialization; this ZEP
  keeps the erased fallback.
- **Use a runtime dictionary lookup keyed by type name.** This would make evidence selection dynamic
  and violate the provision, requirement, and coherence model.
- **Generate one witness class per concrete type argument.** This gives specialized method
  descriptors but causes class explosion and duplicates generic witness bodies. One class per
  witness declaration with prerequisite fields is smaller and composes better.
- **Put default method bodies on the witness interface.** Interface default methods would move
  witness code into the interface and complicate cross-library evolution. Delegating to the existing
  static helper keeps one implementation.

## Implementation and validation

Likely implementation surfaces:

- `BytecodeEmitter.evidenceFields`, `witnessSlots`, `withEvidenceParameters`,
  `emitEvidenceArguments`, `emitEvidenceArray`, `emitHiddenArguments`, and the witness-call paths.
- `DeclarationEmitter` witness slots, default-argument wrappers, HKT bridges, `Main` evidence, and
  witness helper emission.
- `NominalTypeEmitter` evidence-slot declarations and class/method evidence handling.
- `TypeClassEvidence` witness selection and metadata; selection itself should not change.
- `Expr.EvidenceArgument` and the resolution metadata that records a selected witness, its target,
  and its prerequisite evidence.
- `LambdaCompilationPlan`, `LambdaSupportEmitter`, and `LambdaTemplateSupport` for captured evidence
  and template specialization.
- `ZeronLibraryIndex` and `ZeronVersions` for the new metadata and schema version.
- `RuntimeSupportEmitter` for generated witness/dictionary interfaces and any shared support.

Implement in the stages above. Validation must include:

- `javap -p -c` assertions that a generic function with `Numeric<T>` or `Integral<T>` has one
  witness/dictionary parameter per bounded type parameter and no `MethodHandle` parameters;
- `javap -c` assertions that contract calls use `invokeinterface` and contain no
  `MethodHandle.invoke`, no per-slot `ldc` method handle, and no `MethodHandles.insertArguments`;
- witness-class tests for explicit, default, delegated, derived, generic, and class-implementation
  witnesses;
- HKT tests, including constructor-family contracts and receiver-marked operations;
- derived `Eq`/`Hashable` composition tests for arrays, nullable values, and nested type parameters;
- `Main<A>` launcher tests;
- lambda capture and lambda-template specialization tests;
- cross-library tests in both directions: a provider with contracts/witnesses and a consumer with
  generic functions, plus a consumer-defined witness for a provider contract;
- runtime behavior tests for evaluation order, null checks, exceptions, effects, and contract
  selection;
- determinism tests that compile the same input twice and compare all output;
- quality-harness measurements for descriptor size, constant-pool size, class count, total bytes,
  startup, and allocation.

## Open questions

- Should a multi-bound type parameter always use a dictionary, or only when the flattened slot count
  exceeds a threshold? The proposal uses a dictionary for every multi-bound parameter for a uniform
  ABI.
- Should dictionary operation methods delegate through the bound witness objects, or should the
  dictionary class call the static helpers directly? Delegation keeps one witness implementation;
  direct calls may be smaller.
- Should witness classes be public synthetic types, or package-private with a public factory? Public
  classes and constructors simplify cross-library linking; the generated names remain outside the
  source contract.
- Should the witness interface live in the contract's package or in a compiler-owned package? The
  proposal leaves the exact package open but requires a deterministic, indexed name.
- Should the index record explicit witness/dictionary descriptors, or derive them from the contract
  and witness metadata? Explicit recording is safer but larger.
- Which compatibility rule should the first release use: dual ABI, hard break, or per-contract
  mixing?
- Should `Main<A>` and other compiler-owned contracts use a specialized witness shape, or the same
  general witness interface?
- How should a witness class represent a reified descriptor or other hidden state that is not a
  prerequisite witness? A final field and a constructor parameter are the default; the exact rule
  needs validation with the reification tests.
- Should witness object identity ever be observable through generated code, for example if a
  contract method returns the receiver? The design requires it not to be; tests should assert it.
- What quality thresholds should gate the migration: descriptor slots, constant-pool entries,
  `MethodHandle.invoke` count, class count, or total bytes?
