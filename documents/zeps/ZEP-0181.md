## Abstract

This proposal defines the `CONSTANT_Dynamic` (condy) and `invokedynamic` (indy) linking layer for the
witness objects of [ZEP-0180](./ZEP-0180.md) and the hidden-class anonymous constants of
[ZEP-0182](./ZEP-0182.md). It introduces a shared bootstrap runtime, defines condy witness constants
and dictionaries, indy witness factories for dynamic evidence, and the class-byte bootstrap hooks
used by hidden classes.

It also explains why indy polymorphic inline caches are not used for witness dispatch. Evidence is
statically selected and passed as a witness object, so there is no runtime type key to dispatch on.
The JVM's ordinary `invokeinterface` inline cache is the correct mechanism. Indy is used for
construction and factory call sites, where it removes reflective or `MethodHandle`-based
construction and lets the JIT inline the constructor.

## Motivation

[ZEP-0180](./ZEP-0180.md) replaces per-slot hidden `MethodHandle` parameters with witness interfaces
and witness objects. A naive emission of those objects has three problems:

1. **Allocation.** A witness with prerequisite evidence, such as `Eq<Array<T>>`, needs an object that
   holds the element witness. Constructing it at every call would allocate in hot generic code.
2. **Initialization.** A simple witness could be a `static final` singleton, but a static field
   requires class initialization and a `<clinit>` entry at every use site. A derived witness needs a
   composition step that the current code performs with `MethodHandles.insertArguments`.
3. **Linking.** A witness factory with captured evidence needs a call site that the JVM can link
   once and the JIT can inline. `MethodHandle.invoke` and reflection are both poor fits.

Condy solves the constant case: a condy entry is resolved once per constant-pool entry and cached by
the JVM. A simple witness can be a condy constant that returns a singleton; a derived witness or
dictionary can be a condy constant whose static arguments are the prerequisite witness constants. The
bootstrap constructs the object once and the JVM reuses it. Indy solves the dynamic case: a factory
call site captures the evidence arguments, links to the witness constructor or factory, and lets the
JIT inline the construction.

[ZEP-0182](./ZEP-0182.md) needs the same infrastructure for a different value: a hidden class defined
from bytes embedded in the host class. The class must be defined once per literal, and each
evaluation must construct a fresh instance. A condy/indy bootstrap can define the hidden class once
and link a constructor, while the indy call site constructs a new object per evaluation. Sharing one
bootstrap runtime and ABI avoids two incompatible class-definition mechanisms.

Finally, "indy polymorphic inline cache" is an appealing phrase but the wrong tool for witness
dispatch. A generic function receives one witness object per bound. The `invokeinterface` call inside
the function is already a JVM inline cache: it is monomorphic when one type is used, polymorphic when
a few are, and megamorphic when many are. A hand-written indy PIC would need a runtime key, a guard,
and a bootstrap, and would duplicate work the JVM already does. The durable fix for a megamorphic
generic function is a specialized entry point ([ZEP-0096](./ZEP-0096.md)), not a second dispatch
layer. This proposal records that decision explicitly so the option is not reopened by accident.

## Goals

- Define a shared bootstrap runtime for condy and indy constants used by generated Zeron bytecode.
- Define condy witness constants for simple, capture-free witnesses.
- Define condy composition for derived witnesses and multi-bound dictionaries.
- Define indy witness factories for evidence that is not a compile-time constant.
- Define the bootstrap hooks that [ZEP-0182](./ZEP-0182.md) uses to define hidden classes and link
  constructors.
- Keep witness selection static; no runtime type lookup or dynamic contract search.
- Define a stable bootstrap ABI and its versioning rules.
- Define a deterministic naming and static-argument convention.
- Provide a non-condy/non-indy fallback so the witness representation does not depend on the linking
  strategy.
- Record why indy PICs are not used for witness dispatch.
- Keep generated output deterministic and separate-compilation-safe.

## Non-goals

- Changing the witness-interface, witness-class, or dictionary representation from
  [ZEP-0180](./ZEP-0180.md).
- Changing the anonymous-object, handler, or hidden-class semantics from
  [ZEP-0182](./ZEP-0182.md).
- Dynamic contract selection, runtime type tokens, reflection-based witness lookup, or a runtime
  service registry.
- A general dependency-injection or serialization framework.
- Primitive specialization or monomorphization; those remain owned by
  [ZEP-0096](./ZEP-0096.md).
- Replacing `LambdaMetafactory` for ordinary lambdas. Handler values may use the hidden-class path
  defined by [ZEP-0182](./ZEP-0182.md); the existing lambda factory remains their fallback. This
  proposal only provides the shared linking infrastructure.
- A stable Java API for bootstrap methods or generated witness types.
- Guaranteeing a particular JIT outcome, startup time, or allocation count.

## Proposal

### 1. Shared bootstrap runtime

Add a compiler-owned runtime support class, for example `zeron.runtime.BytecodeBootstrap`. It is
emitted on demand by `RuntimeSupportEmitter.emitReferencedRuntimeSupport`, like the other support
classes, and is also present in the compiled standard-library/runtime artifact with the same ABI.

The class provides public static bootstrap methods for:

- a simple witness constant or singleton;
- a derived witness constant composed from prerequisite witness constants;
- a dictionary constant composed from bound witness constants;
- an indy witness factory with captured evidence;
- a hidden-class definition/factory used by [ZEP-0182](./ZEP-0182.md).

The exact method names and arities are implementation details, but the following rules are part of
the ABI:

- Every bootstrap method validates the requested type, the witness class, the constructor/factory
  descriptor, and the prerequisite evidence shape.
- Every bootstrap method rejects an unexpected witness-ABI version with a clear
  `BootstrapMethodError` or `IllegalArgumentException`.
- The bootstrap class has no mutable global state that depends on class-loader identity beyond
  ordinary static caching.
- The bootstrap methods are deterministic for identical inputs. They must not depend on wall-clock
  time, hash-map iteration order, or call discovery order.
- The bootstrap methods do not perform runtime contract selection. They materialize a witness that
  the compiler already selected.

The runtime support scanner must recognize a condy/indy constant's bootstrap class as a dependency.
A program that emits a witness constant but omits the bootstrap class must fail at build time, not at
first resolution.

### 2. Condy witness constants

A **witness constant** is a condy constant whose type is a witness interface or dictionary interface.
Its bootstrap receives:

- the lookup, constant name, and requested type;
- the witness implementation class;
- a constructor or factory method handle;
- zero or more prerequisite witness constants or reified constants;
- a witness-ABI version tag.

The bootstrap constructs the witness and returns it. The JVM caches the resolved value per condy
entry, so repeated `ldc` of the same entry returns the same object.

Two emission strategies are valid:

- **Shared singleton.** A witness with no prerequisite evidence exposes a
  `public static final INSTANCE` field. The condy bootstrap can use
  `ConstantBootstraps.getStaticFinal` with the witness class as the static argument, or a custom
  bootstrap that reads the field. This returns one object across all call sites and libraries that
  share the class loader.
- **Per-constant instance.** A witness with prerequisite evidence is constructed by the bootstrap
  from the prerequisite constants. Each condy entry resolves to one object. Separate call sites may
  resolve to separate objects; witness identity is compiler-internal and not observable, so this is
  semantically safe. The compiler should still measure and, if useful, share instances through a
  deterministic cache.

The condy constant name should encode the witness identity, for example `witness$<hash>`, so
diagnostics and stack traces can identify it. The name has no semantic effect.

### 3. Derived witnesses and dictionaries

A derived witness such as `Eq<Array<T>>` is a composition of its prerequisite witnesses. Its condy
constant has the prerequisite witness constants as static arguments. The bootstrap invokes the
witness constructor with the resolved prerequisites. This replaces the current
`MethodHandles.insertArguments` composition at the call site.

A multi-bound dictionary from [ZEP-0180](./ZEP-0180.md) is composed the same way: its condy constant
has one bound witness constant per bound, and the bootstrap constructs the dictionary class. The
dictionary is a tuple of statically selected witnesses; there is no name lookup or runtime search.

If a prerequisite is itself a condy constant, the JVM resolves it before invoking the outer
bootstrap. The outer bootstrap therefore receives an already-materialized witness object. The
compiler must keep the dependency graph acyclic. A witness cannot require itself, directly or
through a cycle; the resolver already rejects such evidence, and the emitter should assert it.

### 4. Indy witness factories

When a witness depends on evidence that is not a compile-time constant, the compiler emits an indy
factory call site. Typical cases:

- a generic function forwards a witness parameter into a derived witness;
- a lambda captures a witness and later needs a derived witness;
- a local witness selection produces a witness object that is not a static constant;
- a dictionary is projected or combined at runtime from evidence parameters.

The indy call site descriptor includes the captured evidence arguments and any ordinary arguments.
The bootstrap receives the lookup, name, call-site type, the witness class, and a constructor or
factory method handle. It returns a `ConstantCallSite` whose target is the constructor adapted to the
call-site type. The JIT can inline the constructor at the linked call site.

The simple constructor link constructs a fresh witness per call. That is correct because witness
identity is not observable, but it may allocate in a hot loop. The compiler should hoist a witness
construction out of a loop when its evidence is loop-invariant, or cache it in a local. A more
aggressive design can use a `MutableCallSite` or a `ClassValue`-keyed cache, but that is an
optimization to be justified by measurement, not a requirement of the ABI.

### 5. Why not indy PICs for witness dispatch

A witness call inside generic code is an `invokeinterface` on a witness object. The receiver is the
statically selected witness. The JVM already profiles and caches that call site:

- one witness type: monomorphic, inlinable;
- a few witness types: polymorphic, inlinable within the JIT's limit;
- many witness types: megamorphic, with a normal interface dispatch.

A hand-written indy PIC would need to:

- obtain a runtime key, such as the witness object's class or a type token;
- guard the key;
- cache a target method handle per key;
- invalidate on class loading or redefinition.

The witness object's class is already the receiver of `invokeinterface`, and the JVM's inline cache
already handles it. There is no erased type argument to use as a key, and introducing a runtime type
token would make evidence selection dynamic. That contradicts the static selection model in
[ZEP-0180](./ZEP-0180.md), [ZEP-0114](./ZEP-0114.md), [ZEP-0135](./ZEP-0135.md), and
[ZEP-0137](./ZEP-0137.md).

If measurements show a megamorphic witness dispatch bottleneck, the remedies are:

1. a specialized entry point or monomorphized variant ([ZEP-0096](./ZEP-0096.md));
2. direct inlining at statically known call sites ([ZEP-0095](./ZEP-0095.md));
3. a different witness representation, proposed separately.

A manual indy PIC is not on that list. Indy remains appropriate for construction/factory call sites
and for lambda/handler factories, where the call site links a target once and the JIT can inline the
body.

### 6. Hidden-class bootstrap hooks

[ZEP-0182](./ZEP-0182.md) needs to define a hidden class from bytes embedded in the host class and
link a constructor. This proposal owns the shared bootstrap ABI for that operation:

- a condy or indy bootstrap receives the embedded class bytes as one or more `String` constants
  (base64 or another deterministic encoding), the expected class/constructor descriptor, and a
  hidden-class option tag;
- the bootstrap decodes the bytes, calls
  `Lookup.defineHiddenClass(bytes, true, ClassOption.NESTMATE)`, finds the constructor, and returns
  either the `Class`, a constructor `MethodHandle`, or a linked `CallSite`;
- the bootstrap validates that the hidden class implements the expected contract interface and that
  the constructor descriptor matches the call-site descriptor;
- the bootstrap does not accept arbitrary class bytes from source code. The bytes are
  compiler-generated constants in the host class.

The class-byte encoding, chunking, size threshold, and fallback rules are specified by
[ZEP-0182](./ZEP-0182.md). This proposal only fixes the bootstrap method shape and the shared
runtime's versioning.

### 7. Fallback and feature selection

The witness representation from [ZEP-0180](./ZEP-0180.md) must not depend on condy/indy. The compiler
provides a fallback linking strategy:

- simple witnesses use `public static final` singleton fields and `getstatic`;
- derived witnesses and dictionaries use `new` plus a constructor call, or a cached local/static
  field;
- witness factories use a direct constructor call;
- hidden-class anonymous constants fall back to ordinary named classes (per
  [ZEP-0182](./ZEP-0182.md)).

A compiler flag or project setting may select `auto`, `bootstrap`, or `plain` linking during
migration. The default becomes `auto` after validation. The flag changes emission only; it does not
change the witness ABI or source behavior.

### 8. ABI and versioning

The bootstrap method signatures, static-argument conventions, and class-byte encoding are part of the
generated bytecode ABI. The shared runtime exposes a `BOOTSTRAP_ABI_VERSION` constant, and every
generated condy/indy constant carries or checks it. A change to the bootstrap ABI requires:

- a compiler/runtime version change;
- a `STANDARD_LIBRARY_API_VERSION` review under [ZEP-0012](./ZEP-0012.md);
- a release note explaining which compiled libraries must be rebuilt;
- a compatibility test that loads an older library against the new runtime and reports a clear
  error.

The bootstrap class itself is versioned with the standard-library/runtime artifact. A program that
uses the compiled standard library gets the artifact's bootstrap class; a source-mode program gets
the on-demand support class. Both must have the same ABI version. The existing standard-library
version check rejects a mismatched artifact before execution.

The API index does not need to record every condy/indy constant, but it should record the bootstrap
ABI version a library requires. A consumer or runtime can then reject an incompatible library before
linking a constant.

## Compatibility and impact

Source compatibility is preserved. Witness and anonymous-constant values are compiler-internal; no
source-level type, name, or identity changes.

Class-file impact:

- generated classes gain condy and indy constants, bootstrap method references, and static arguments;
- the shared bootstrap runtime is emitted or supplied by the standard-library artifact;
- the fallback strategy emits no condy/indy constants, so the same witness representation can be
  tested both ways;
- hidden-class byte constants add constant-pool entries to host classes (see
  [ZEP-0182](./ZEP-0182.md)).

Runtime impact:

- condy constants are resolved lazily and cached by the JVM; the first use pays the bootstrap cost;
- indy factories are linked once per call site and can be inlined by the JIT;
- a derived witness may be constructed once per condy entry rather than once per call;
- a global cache, if added, must avoid class-loader leaks; a per-constant cache is the safe default.

Library impact:

- compiled libraries that contain condy/indy constants require a compatible bootstrap runtime;
- the standard-library artifact and the compiler must agree on the bootstrap ABI version;
- a library compiled with the fallback strategy remains usable with a bootstrap-capable runtime,
  because the fallback emits no condy/indy constants.

Security and robustness:

- the bootstrap validates types, descriptors, and versions; it does not evaluate arbitrary source or
  load arbitrary classes;
- the class bytes are compiler-generated; a party that can modify the class file can already modify
  the program, so this is not a new sandbox boundary;
- a malformed constant must fail with a clear linkage error, not a silent `null` or a wrong witness.

Determinism:

- condy/indy names, static arguments, class-byte chunks, and bootstrap method references must be
  deterministic for identical inputs;
- runtime-assigned hidden-class names are not part of the output and are not compared by
  determinism tests.

## Alternatives

- **Use only static final fields and direct constructors.** This is the fallback and is simple, but
  it adds fields and `<clinit>` work to every holder and cannot compose derived witnesses without
  per-site code.
- **Use only per-call `new` for witness objects.** This avoids condy/indy but allocates in hot
  generic code and loses the JVM's constant caching.
- **Keep `MethodHandles.insertArguments` for derived witnesses.** This preserves the current
  composition mechanism but keeps method handles and signature-polymorphic dispatch in the evidence
  path.
- **Use an indy PIC for witness dispatch.** Rejected for the reasons in section 5.
- **Use a global witness registry keyed by contract and type name.** This introduces runtime lookup,
  class-loader coupling, and dynamic selection that the witness model forbids.
- **Use reflection to construct witnesses.** Reflection is slower, less predictable, and requires
  access configuration that generated code should not need.
- **Put every witness constant in a static field and rely on class initialization.** This is a valid
  fallback, but it makes startup eager and grows the holder's `<clinit>`.
- **Use a single `Object[]` static argument for all prerequisites.** The JVM passes static arguments
  individually; an array would require an extra allocation and a less precise bootstrap signature.
  A generated adapter or fixed-arity bootstrap is clearer.

## Implementation and validation

Implement in stages:

1. **Shared runtime and simple constants.** Add `zeron.runtime.BytecodeBootstrap`, the ABI version,
   and condy constants for capture-free witness singletons. Compare against the static-field
   fallback.
2. **Derived witnesses and dictionaries.** Add condy composition and validate prerequisite ordering,
   cycles, and cross-library witnesses.
3. **Indy factories.** Add factory call sites for dynamic evidence and validate captured arguments,
   loop hoisting, and JIT behavior.
4. **Hidden-class hooks.** Add the class-byte bootstrap methods used by
   [ZEP-0182](./ZEP-0182.md) and validate hidden-class definition, constructor linking, and fallback.
5. **Cleanup.** Make `auto` the default, keep `plain` for debugging, and remove any temporary
   duplicate paths.

Validation must include:

- `javap -v` assertions that a witness constant is a `CONSTANT_Dynamic` with the expected bootstrap
  method and static arguments;
- `javap -c` assertions that a witness factory is an `invokedynamic` call site and that the evidence
  path contains no `MethodHandles.insertArguments` or per-slot `MethodHandle.invoke`;
- runtime tests for simple, derived, dictionary, generic, HKT, and cross-library witnesses;
- tests for a witness with a prerequisite witness, a witness with two prerequisites, and a dictionary
  with three bounds;
- a test that a cycle in the prerequisite graph is rejected at compile time;
- a test that a mismatched bootstrap ABI version fails with a clear error;
- a test that the bootstrap rejects a witness class that does not implement the expected interface;
- cross-library tests where a provider emits condy constants and a consumer links them, and the
  reverse;
- determinism tests that compile the same input twice and compare output;
- startup, allocation, and class-size measurements against the [ZEP-0095](./ZEP-0095.md) corpus;
- a fallback test that compiles the same program with `plain` linking and verifies identical
  behavior;
- hidden-class integration tests from [ZEP-0182](./ZEP-0182.md).

## Open questions

- Should the shared runtime be one `BytecodeBootstrap` class or separate witness and anonymous-class
  bootstrap classes? One class simplifies versioning; separate classes isolate concerns.
- Should bootstrap methods be fixed-arity for 0–4 prerequisites plus a generated adapter, or should
  every shape get a generated adapter method? The JVM does not pack static arguments automatically.
- Should a simple witness constant use `ConstantBootstraps.getStaticFinal` or a custom bootstrap that
  constructs the singleton? `getStaticFinal` is simpler but requires a public static final field.
- Should derived witness constants be shared across call sites through a deterministic cache, or is
  one object per condy entry sufficient?
- If a cache is used, should it be keyed by witness class plus prerequisite classes, and how should
  class-loader lifetime be handled?
- Should indy factories cache the constructed witness for loop-invariant evidence, or should the
  compiler hoist the construction instead?
- What is the bootstrap flag's name and default, and how long should `plain` remain supported?
- How should the bootstrap ABI version be encoded: a static `int` argument, a `String` tag, a
  `Class` constant, or a runtime class version?
- Should the bootstrap class live in the standard-library artifact, the compiler runtime, or both?
  Both must agree on the ABI.
- Should `defineHiddenClassWithClassData` be used to attach the contract descriptor or factory
  metadata to a hidden class?
- What class-byte encoding and chunk size should be shared with [ZEP-0182](./ZEP-0182.md): base64,
  ISO-8859-1, or a mixed scheme?

## Decision

Draft created 2026-11-26. The proposal defines a shared condy/indy bootstrap runtime for witness
constants, witness factories, and hidden-class construction. It rejects indy PICs for witness
dispatch because evidence selection is static. The exact bootstrap arities, caching policy, ABI
version encoding, and fallback duration remain open.
