## Abstract

This proposal lowers compiler-generated anonymous values to **hidden classes** defined at runtime
from bytes embedded in the host class. It covers two value families:

- **object literals** from [ZEP-0017](./ZEP-0017.md), which currently become named synthetic classes
  such as `$zeron$anonymous$<sourceId>$<location>`;
- **handler values** from [ZEP-0057](./ZEP-0057.md), including anonymous handler literals and named
  handler declarations from [ZEP-0056](./ZEP-0056.md), which currently lower through the lambda
  machinery and top-level value fields.

Object literals and handler literals are constructed per evaluation. A hidden class may be defined
once and linked once, but each evaluation must produce a fresh object because reference identity and
mutable state are observable. A named handler declaration is a single immutable value, so it may use
a condy singleton when the value is capture-free and creation order is preserved.

Hidden classes cannot be named in other class files. They are therefore used only when the generated
anonymous type does not escape into a method descriptor, field descriptor, stack-map frame, exported
API, reified descriptor, or serialization metadata. Otherwise the existing named synthetic class or
the existing lambda path remains the fallback. The shared bootstrap runtime, condy/indy ABI, and
versioning are owned by [ZEP-0181](./ZEP-0181.md); this proposal defines the anonymous-value rules and
the class-byte embedding format.

## Motivation

Anonymous objects and handlers are deliberately non-denotable in Zeron source, yet the current
compiler gives each object literal a named class file. The class-file quality inventory and the
current emission paths show the costs:

- `Parser.anonymousObject` synthesizes a name from the source hash and source location, and
  `ExpressionFlowResolver.resolveAnonymousObject` registers a full `Stmt.ClassDecl` in
  `context.classes`. The class is emitted to `dist/` like a user class.
- Captured values become synthetic constructor fields. A capture that crosses a package or class
  boundary can require synthetic access bridges, because the generated class is not a nestmate of
  the code that created it.
- The generated class appears in generated output even though it has no source name, no stable
  library identity, and no reason to be a discoverable class.
- Handler literals are lowered as lambdas (`Expr.HandlerLiteral` wraps an `Expr.Lambda` containing
  an `Expr.HandlerDispatch`). Named handler declarations are immutable top-level or namespace
  `Stmt.Var` values initialized with a handler literal. The lambda machinery already uses
  `LambdaMetafactory` hidden classes internally, but the compiler does not control their bytes,
  cannot attach handler-specific metadata, and cannot offer a condy singleton for a named handler
  declaration without a separate path.
- Top-level values use non-final static fields, per-read initialized flags, accessors, and
  `<clinit>` initializers (`DeclarationEmitter.generateTopLevelValueMethods`). A named handler
  declaration therefore already has a single cached value; the representation can improve without
  changing that identity.

Hidden classes fit these values well. A hidden class is defined in the host's class loader and
package, is not discoverable by name, and can be a nestmate of the host. The host can pass captured
values through the constructor and the hidden class can access host-private members without public
synthetic bridges. The class bytes live in the host class file as constants, so the anonymous class
does not become a separate output file. The JVM's condy/indy machinery can define the class once,
cache it, and link a constructor call site that allocates a fresh instance per evaluation.

The restriction is equally important: a hidden class has no stable, nameable identity for other
class files. It cannot be used as a method parameter type, field type, return type, generic argument,
cast target, or API-index entry. The proposal therefore keeps a named fallback and makes eligibility
explicit rather than treating hidden classes as a universal replacement.

## Goals

- Lower eligible object literals to hidden classes with per-evaluation construction.
- Lower eligible handler values to hidden classes implementing the existing function-shape
  interfaces, with per-evaluation construction for handler literals.
- Preserve named handler declarations as single immutable values; allow a condy singleton only when
  identity and initialization order are preserved.
- Preserve object identity, handler identity, mutable per-object state, immutable captures,
  evaluation order, null checks, exceptions, effects, and contract dispatch.
- Embed hidden class bytes in the host class without creating a named output class.
- Use `NESTMATE` hidden classes to access host-private members and avoid synthetic access bridges.
- Define eligibility, fallback, reflection, serialization, reification, and separate-compilation
  rules.
- Keep generated output deterministic.
- Use the bootstrap runtime and ABI from [ZEP-0181](./ZEP-0181.md) rather than defining a second
  class-definition mechanism.
- Keep the current named synthetic class and `LambdaMetafactory` paths as fallbacks.

## Non-goals

- Changing anonymous object or handler source syntax, contract conformance, capture rules, effect
  typing, or handler shape identity.
- Structural typing or making an anonymous type denotable.
- Sharing object literal instances. Two evaluations of the same object literal must remain distinct
  objects.
- Sharing handler literal values by default. Handler identity is observable through `===`.
- Replacing `LambdaMetafactory` for ordinary lambdas. Handler values may use the hidden-class path;
  ordinary lambdas remain on the existing lambda lowering.
- Putting hidden classes into exported signatures, the API index, Java interop signatures, reified
  descriptors, annotations, or serialization metadata.
- A stable reflection or serialization contract for generated anonymous types.
- Primitive specialization, evidence representation, or witness dispatch; those are owned by
  [ZEP-0095](./ZEP-0095.md), [ZEP-0096](./ZEP-0096.md), and [ZEP-0180](./ZEP-0180.md).
- Bootstrap method signatures, static-argument conventions, and ABI version encoding; those are
  owned by [ZEP-0181](./ZEP-0181.md).
- Guaranteeing a particular class count, startup time, or allocation count.
- Extending hidden classes to model literals, witnesses, or other compiler-generated types in this
  proposal.

## Proposal

### 1. Value families and identity

The proposal distinguishes three shapes:

| Value | Evaluation | Identity rule | Lowering |
| --- | --- | --- | --- |
| Object literal | Once per evaluation of the expression | Fresh object each evaluation; mutable fields are per instance | Hidden class + indy constructor, or named fallback |
| Handler literal | Once per evaluation of the expression | Fresh function value each evaluation; `===` is observable | Hidden class + indy constructor, or lambda fallback |
| Named handler declaration | Once at declaration initialization | Single immutable value; every read returns the same object | Hidden class + condy singleton or indy factory in the initializer, stored in the existing field |

An **anonymous constant** in this proposal means a compiler-generated implementation class with no
source-level name. A named handler declaration has a source-level value name, but its implementation
class is still anonymous. The term does not imply that the value is a JVM constant or that it is
shared.

Object literal identity and mutability are observable. The following must produce two distinct
objects with independent state:

```zeron
fn counter(): Iterator<Int> =
    object : Iterator<Int> {
        index: Int = 0;

        public mut next(): Step<Int> {
            let current = this.index;
            this.index = this.index + 1;
            return Step.Yield(current);
        }
    };

let first = counter();
let second = counter();
// first !== second
```

A named handler declaration is a single value:

```zeron
handler EmptyString {
    case IoFailure(_): String = "";
}

let a = EmptyString;
let b = EmptyString;
// a === b
```

A handler literal is not shared:

```zeron
let h1: String ~> {IoFailure} = handler {
    case IoFailure(_) -> "";
};
let h2: String ~> {IoFailure} = handler {
    case IoFailure(_) -> "";
};
// h1 !== h2
```

The proposal preserves these rules exactly. The only new decision is where the implementation
class comes from.

### 2. Hidden-class eligibility

A hidden class is used only when the compiler can represent every use of the value without naming
the generated class in another class file. For an object literal, eligibility requires all of the
following:

- the generated anonymous type does not appear in a method descriptor, field descriptor, stack-map
  frame, exception-table entry, local-variable type table, annotation, reified descriptor, or API
  index entry of the host class or another class; the hidden class's own methods may use `this` as
  the current class;
- every use of the value is through one of the contracts listed on the object literal, through
  `Any`, or through reference operations that need no class name (`===`, `!=`, `ifnull`, `ifnonnull`,
  `Object` methods, and interface dispatch);
- no member outside the listed contracts is accessed through the anonymous type;
- no method or field signature mentions the anonymous type, including a method that returns `this`
  or a field whose type is the anonymous type;
- the object does not need a stable class name for Java reflection, Java serialization, Zeron
  serialization metadata, debugger class-name matching, or a reified `Class` token;
- the class bytes are below the configured embedding threshold.

If an expected contract type is present, the compiler uses that contract interface as the erased
type of the value. If several contracts are listed and no single expected type determines the view,
the compiler may use `Object` as the erased type and emit `checkcast` to the selected contract at
each use. The hidden class implements every listed contract, so those casts succeed. This keeps the
hidden class name out of descriptors while preserving source-level contract dispatch.

If the value has extra methods or properties that are not part of a listed contract, they can still
be emitted in the hidden class. The hidden path remains eligible only if no such member is accessed
through the anonymous type. If an extra member is accessed, the compiler cannot emit a `checkcast`
to the hidden class, so the literal uses the named fallback. The same rule applies when the anonymous
type is captured by a closure whose capture field would have to name it, or when the type is used as
a generic argument that is reified rather than erased.

For a handler value, eligibility is simpler because the value's source type is a function or handler
shape that erases to a generated function-shape interface:

- the handler shape must already have a function-shape interface under the existing lambda lowering;
- the hidden class implements that interface and all uses dispatch through it;
- the generated hidden class name must not appear in a host-class or other-class method descriptor,
  field descriptor, stack-map frame, reified descriptor, or API index entry; the hidden class's own
  methods may use `this` as the current class;
- the value must not need a stable class name for reflection or serialization;
- the class bytes must be below the embedding threshold.

Named handler declarations are eligible when the declaration's value type is a function or handler
shape and the hidden class is not exported by name. A public named handler declaration exports its
handler shape, not its hidden implementation class.

### 3. Object literals

An eligible object literal is compiled to a hidden class with the same members, fields, properties,
captures, and contract implementations that the current synthetic class has.

- The hidden class is `final` and `synthetic`. It extends `Object` and implements the listed
  contract interfaces. It has no source-visible name.
- The constructor takes the object's explicit field initializers, captured values, and property
  initializers in the same canonical order as the current resolver. Captures are immutable; object
  fields may be mutable.
- The constructor stores the values in private fields. The class's methods, property accessors, and
  contract bridges use the same bodies as the named synthetic class.
- The hidden class is defined as a nestmate of the host. It may access host-private members directly;
  no synthetic public access bridge is needed for captures or enclosing private state.
- Each evaluation of the object literal emits an `invokedynamic` call to a constructor factory. The
  call site's arguments are the evaluated initializer and capture values. The bootstrap links the
  hidden class constructor once; every invocation performs `new` plus the constructor call and
  returns a fresh instance.
- The call site's return type is an accessible contract interface or `Object`, never the hidden
  class. Uses that need a different listed contract insert `checkcast` to that interface.
- The hidden class is defined once per literal per host class loader. A condy `Class` constant or a
  condy constructor handle may cache the definition; the instance is never cached.
- Evaluation order is left-to-right across the call-site arguments, matching the current `new` plus
  constructor-argument sequence. Exceptions from initializer expressions propagate before
  construction; exceptions from the constructor propagate unchanged.

An object literal with no captures still allocates a new object on every evaluation. It must not be
lowered to a condy singleton, a static final field, or a shared `Object` instance. A top-level `let`
whose initializer is an object literal evaluates that literal once and stores the resulting object;
that is a property of the top-level value, not permission to share the literal.

### 4. Handler values

A handler literal is a function value whose implementation is an `Expr.Lambda` containing an
`Expr.HandlerDispatch`. The proposal keeps the existing function-shape interface and handler-shape
identity, but replaces the lambda implementation class with a compiler-generated hidden class when
eligible.

- The hidden class implements the function-shape interface selected by the existing lambda plan.
- It has private final fields for immutable captures, a constructor that stores them, and an
  `invoke` method with the shape's erased descriptor.
- The `invoke` method contains the handler dispatch body, or delegates to a private static helper in
  the host. A helper is accessible through nestmate private access, so no public bridge is required.
- Each evaluation of the handler literal emits an indy constructor factory and produces a fresh
  handler value. Captured values are passed as call-site arguments.
- A handler literal with no captures still produces a fresh value per evaluation. It is not a condy
  singleton by default, because `===` on function types is observable.
- The existing `LambdaMetafactory` path remains the fallback for handler values that are not
  eligible, and for ordinary lambdas that are not handler values.

A **named handler declaration** is different. It is an immutable top-level or namespace value, it is
evaluated once during initialization, and every read returns the same value. The proposal keeps the
existing top-level field and accessor, and stores the single handler value there.

- The hidden class is defined once. The handler value may be created by a condy singleton when the
  declaration is capture-free and creating the value has no user-observable side effect and no
  dependency on top-level initialization order. The `ldc` for the condy constant must execute inside
  the declaration's initializer, not at every read, so the existing initialization order and
  before-initialization diagnostics are preserved.
- If the declaration is not capture-free, or if the compiler cannot prove the condy creation is
  order-independent, the initializer uses the indy factory and stores the fresh value in the field.
  The field still guarantees a single value across reads.
- Replacing the field with a per-read condy load is not allowed: it would bypass the top-level
  initialization check and could change when the value is created.
- A named handler declaration remains immutable and cannot capture local values under
  [ZEP-0056](./ZEP-0056.md). A handler literal may capture immutable locals under
  [ZEP-0057](./ZEP-0057.md); that is the case that needs constructor fields.

The distinction is intentional: condy is safe for a named handler declaration because the source
declares exactly one value, and unsafe for a handler literal because each evaluation is a distinct
value.

### 5. Hidden class shape and class bytes

The compiler generates the hidden class bytes in memory after resolution. The bytes have the same
members and behavior as the named fallback class, with these differences:

- the class is `final` and `synthetic`, with no public source name;
- the class name is a deterministic compiler-generated name in the host's package, for example
  `$Zeron$Anonymous$<hash>`; `$` is not legal in a Zeron identifier;
- the bytes contain no `NestHost` or `NestMembers` attribute; the runtime supplies the nest host when
  the class is defined with `NESTMATE`;
- the constructor and private fields use nestmate access; no synthetic public accessors are
  generated solely for the hidden class;
- method descriptors and fields never mention the hidden class itself, per the eligibility rules;
- debug metadata, if emitted, points at the source location of the literal and not at the unstable
  runtime class name.

The class bytes are embedded in the host class as one or more `String` constants. A literal nested
inside another anonymous class uses that hidden class as its host; the same eligibility, embedding,
and fallback rules apply recursively. A condy or indy bootstrap cannot receive a `byte[]` directly as
a static argument, so the compiler encodes the bytes and the bootstrap decodes them. The encoding is
one of:

- **base64** — recommended default; ASCII-only, simple to validate, and no modified-UTF-8 edge cases;
- **ISO-8859-1** — smaller for byte values in the Latin-1 range, but NUL and other bytes need careful
  accounting because the constant pool stores strings in modified UTF-8.

Each chunk must stay below the 65,535-byte modified-UTF-8 limit. With base64, a conservative chunk
size (for example 32 KiB of raw bytes) leaves room for the encoding expansion and the constant-pool
entry. The bootstrap receives the chunks in order, concatenates them, decodes the bytes, validates
the expected class name, package, constructor descriptor, and implemented interface, and then calls
`Lookup.defineHiddenClass(bytes, true, ClassOption.NESTMATE)`.

The bootstrap may use `defineHiddenClassWithClassData` to attach a small metadata object containing
the source location, contract descriptors, or constructor descriptor. This is optional; the
eligibility rules do not depend on it. The bootstrap must reject truncated, oversized, or malformed
bytes with a clear `BootstrapMethodError` or `IllegalArgumentException`, never with a silent `null`
or a partially initialized object.

If the encoded bytes exceed the configured threshold, or if the host class would grow beyond the
quality budget, the literal uses the named fallback. The threshold is a quality decision, not a
semantic one; it must not depend on wall-clock time or hash iteration order.

### 6. Linking and construction

The linking shapes are:

- **Object literal.** A condy `Class` constant (or condy constructor handle) defines and caches the
  hidden class. An indy factory call site links the constructor. The call-site descriptor takes the
  initializer/capture values and returns the erased contract interface or `Object`. Each invocation
  constructs a new instance.
- **Handler literal.** A condy `Class` constant defines and caches the hidden class. An indy factory
  call site takes the captures and returns the function-shape interface. Each invocation constructs
  a new handler value.
- **Named handler declaration.** The initializer either loads a condy singleton (capture-free,
  order-independent) or calls the indy factory. The result is stored in the existing top-level field
  and returned by the existing accessor.

The bootstrap runtime, method signatures, static-argument conventions, and ABI version come from
[ZEP-0181](./ZEP-0181.md). This proposal only specifies the class-byte payload and the call-site
shapes. The bootstrap must not perform runtime contract selection or source-level lookup; it
materializes a class and constructor that the compiler already selected.

For a hidden class with no static state, `initialize=true` at definition is acceptable. If a future
hidden class needs lazy static initialization, the proposal can switch to `initialize=false` and
define the initialization point explicitly. The current anonymous values have no static state.

### 7. Identity, mutability, and equality

The JVM object identity of a hidden class instance is ordinary reference identity. No wrapper,
proxy, or indy call site may collapse two evaluations into one object.

- Two evaluations of the same object literal produce two objects; `===` is false.
- Two evaluations of the same handler literal produce two function values; `===` is false.
- Every read of a named handler declaration returns the same value; `===` is true.
- Object fields are per instance. A `mut` field changed through one object is not visible through
  another object created from the same literal.
- Captured values are immutable and shared by value under the existing capture rules. Two object
  literals that capture the same immutable local still have distinct object identity.
- A top-level `let` initialized with an object literal evaluates the literal once; the top-level
  value is one object. This is not a shared literal.
- A top-level `let` initialized with a handler literal also evaluates the literal once and stores
  one value. Only a named handler declaration may use the condy singleton optimization.
- Contract dispatch through a hidden class uses the same `invokeinterface` calls as the named
  fallback. `equals` and `hashCode` behavior is unchanged; `===` is not delegated to `equals`.

If the compiler cannot prove these identity rules for an optimization, it must not perform the
optimization.

### 8. Reflection, reification, and serialization

Hidden classes are not discoverable by name. The following rules apply:

- `Class.forName` cannot find a hidden class by its source-level name; there is no source-level name.
- `Class.getName()` for a hidden class is not stable and is not part of the Zeron API. It may contain
  a runtime-assigned suffix. Generated code and diagnostics must not depend on it.
- `Class.isHidden()` is true. Java reflection can inspect a hidden class if it has an instance or a
  `Class` object, but Zeron does not expose a stable `Class` token for an anonymous type.
- A hidden class cannot be used as a reified descriptor or a `Class` literal. If a program needs a
  reified anonymous type, the literal uses the named fallback.
- Zeron serialization metadata must describe the listed contract or an explicit serialized shape,
  not the hidden class name. A hidden class is not a stable serialization identity.
- Java serialization by class name is not supported for hidden classes. If an anonymous object or
  handler must be Java-serializable, it uses the named fallback or an explicit serialization
  contract.
- Debug metadata may refer to the source location of the literal; it must not require the runtime
  hidden class name to be stable.

The named fallback remains the escape hatch for any reflection, reification, serialization, or
debugger requirement that needs a stable class name.

### 9. Separate compilation and the API index

Anonymous implementation classes are not exported API. The proposal preserves that rule:

- Hidden class names are never written to the library index.
- A public named handler declaration exports its handler shape and accessor; the hidden
  implementation class stays in the provider's class file.
- A public function or field must not expose an anonymous object type. If a source declaration would
  do so, the compiler rejects it or uses the named fallback under the existing anonymous-type
  export rules.
- A consumer-defined object literal may implement a provider contract. The hidden class is defined
  in the consumer's class loader and implements the provider's interface; the provider does not need
  the hidden class bytes.
- A provider-defined named handler declaration may be used by a consumer through the handler shape
  interface. The consumer calls the interface; it never names the hidden class.
- The bootstrap ABI version and any runtime-support dependency are recorded as described by
  [ZEP-0181](./ZEP-0181.md). This proposal adds no anonymous-class entries to the index.
- If a marker is added to the index to say that a library uses hidden classes, it must be versioned
  with the same `API_INDEX_SCHEMA_VERSION` review as [ZEP-0180](./ZEP-0180.md) and
  [ZEP-0181](./ZEP-0181.md). The default is no new index entry.
- `STANDARD_LIBRARY_API_VERSION` needs a review only if the standard library's exported shapes or
  bootstrap dependency change. Hidden implementation classes alone do not change the exported API.

The named fallback remains binary-compatible with the current synthetic class output. A library that
uses hidden classes requires a runtime with the shared bootstrap ABI; a library that uses the
fallback does not.

### 10. Fallback

The named synthetic class remains the fallback for object literals. The current `LambdaMetafactory`
path remains the fallback for handler values. The compiler selects the hidden path only when the
eligibility rules hold.

Fallback is required when:

- the anonymous type escapes into a descriptor, stack-map frame, reified descriptor, or API index;
- an extra member outside the listed contracts is accessed;
- a method or field signature mentions the anonymous type;
- reflection, serialization, or a stable debugger name is required;
- the class bytes exceed the embedding threshold;
- the runtime or target does not support hidden classes;
- deterministic output or separate-compilation rules cannot be satisfied;
- the compiler cannot prove the identity or initialization rules for the optimization.

A compiler flag or project setting may select `auto`, `hidden`, or `named` for testing and
diagnostics. The default is `auto`: use hidden classes when eligible, otherwise fall back. The flag
changes emission only; it does not change source semantics.

### 11. Determinism and debugging

Hidden class bytes, synthetic names, chunk order, bootstrap static arguments, and indy call-site
descriptors must be deterministic for identical input. They must not depend on hash-map iteration
order, discovery order, wall-clock time, or runtime class-definition order.

Runtime-assigned hidden class names are not part of the generated output and are not compared by
determinism tests. The compiler's in-memory class bytes are compared instead. A deterministic test
should compile the same source twice and compare every output file plus the hidden-class byte
payloads.

Debug metadata should map hidden-class frames to the source location of the literal. Stack traces
may show an unstable hidden class name; that is acceptable for an anonymous value, but a debugger
that requires a stable class name uses the named fallback. The proposal does not add a source-level
name for anonymous types.

## Compatibility and impact

Source compatibility is preserved. Contract conformance, capture rules, handler shapes, effect
typing, evaluation order, null checks, exceptions, and `===` behavior must not change.

Class-file impact:

- Eligible object literals no longer produce a named synthetic class file; their bytes are embedded
  in the host class and defined at runtime.
- Eligible handler values produce hidden classes implementing the existing function-shape
  interfaces.
- Host classes gain condy/indy constants, bootstrap method references, and encoded class-byte
  strings.
- The named fallback keeps the current class-file shape and can be used for comparison.
- The runtime class count may be similar; the on-disk class count and cross-package bridge count
  should decrease. The host constant pool grows by the encoded bytes.

Runtime impact:

- Defining a hidden class costs work on first resolution. Condy caches the definition per constant;
  repeated evaluations only allocate and construct.
- Object and handler allocation counts are unchanged relative to the named/lambda paths.
- Nestmate access removes some synthetic accessor calls.
- Hidden classes are tied to their defining class loader for name resolution and lifetime; the
  proposal does not add a global cache that could retain class loaders.
- The bootstrap validates the payload and fails with a clear linkage error for malformed input.

Library and API-index impact:

- Anonymous implementation classes remain absent from the API index.
- A public named handler declaration exports only its handler shape and accessor.
- The bootstrap ABI dependency is covered by [ZEP-0181](./ZEP-0181.md).
- No `API_INDEX_SCHEMA_VERSION` or `STANDARD_LIBRARY_API_VERSION` bump is required solely for hidden
  anonymous classes; any marker or shared schema change must be consolidated with the evidence
  changes in [ZEP-0180](./ZEP-0180.md) and [ZEP-0181](./ZEP-0181.md).

Java interop:

- Java code can call an anonymous object through its contract interface.
- Java code cannot name the hidden class. If Java interop requires the concrete type, the named
  fallback is used.
- No new public Java API is introduced for generated anonymous classes.

Security and robustness:

- The bootstrap defines only compiler-generated bytes embedded in the host class. It does not load
  arbitrary bytes from source or user input.
- The bootstrap validates the class name, package, constructor descriptor, implemented interface,
  and payload length before defining the class.
- A party that can modify the host class can already modify the program; hidden classes do not add a
  new trust boundary.
- Malformed or truncated payloads fail with a linkage error, not a silent fallback at runtime.

## Alternatives

- **Keep named synthetic classes for object literals.** This is the current behavior and remains
  the fallback. It preserves stable names and reflection, but keeps one class file per literal and
  can require synthetic access bridges.
- **Keep `LambdaMetafactory` for all handler values.** This is the current behavior and remains the
  fallback. It preserves the existing lambda path but does not give the compiler control over
  handler class bytes or a condy singleton for named declarations.
- **Use a condy singleton for object literals.** Rejected: two evaluations must produce distinct
  objects, and mutable fields are per instance.
- **Use a condy singleton for handler literals.** Rejected: `===` on function types is observable,
  so two evaluations must produce distinct values. Only a named handler declaration denotes a single
  value.
- **Share one hidden class per literal shape.** Rejected for object literals: each literal has a
  distinct nominal identity and private field layout. Handler classes could theoretically share a
  shape when captures and dispatch are identical, but that would make class identity observable
  through reflection and complicate nominal rules; the proposal uses one class per literal.
- **Use `Unsafe.defineAnonymousClass`.** Rejected: it is unsupported and does not provide the
  standard hidden-class/nestmate model. The proposal uses `Lookup.defineHiddenClass`.
- **Use `Lookup.defineClass`.** Rejected: it defines a named class in the same loader, which does not
  remove the name or the output class file.
- **Use dynamic proxies for object literals.** Rejected: proxies are reflective, cannot hold
  arbitrary mutable state without an invocation handler, and have different performance and
  identity behavior.
- **Use hidden classes for every anonymous type, including exported ones.** Rejected: hidden classes
  cannot be named in method descriptors, field descriptors, or the API index.
- **Encode class bytes as a `byte[]` static argument.** Rejected: condy/indy static arguments do not
  include `byte[]`. The proposal uses chunked strings and a bootstrap decoder.
- **Use ISO-8859-1 without special handling for NUL.** Rejected as a default: modified UTF-8 makes
  NUL a two-byte sequence, so the chunk-size accounting is error-prone. Base64 is the safer default;
  ISO-8859-1 remains an option if measured and correctly bounded.
- **Use a global hidden-class cache keyed by bytes.** Rejected: it would share classes across
  literals and class loaders, make identity and unloading harder to reason about, and risk retaining
  class loaders.

## Implementation and validation

Likely implementation surfaces:

- `Parser.anonymousObject` and `Parser.handlerLiteral` for synthetic names and source locations.
- `Expr.AnonymousObject`, `Expr.HandlerLiteral`, `Expr.HandlerDispatch`, and the resolver paths
  `resolveAnonymousObject`, `resolveHandlerLiteral`, and `synthesizeFrameHandler`.
- `ExpressionFlowResolver` for anonymous class synthesis and handler shape resolution.
- `BytecodeEmitter` for anonymous object and handler emission, lambda planning, condy/indy call
  sites, and class-byte generation.
- `DeclarationEmitter.generateTopLevelValueMethods` for named handler declaration fields, accessors,
  and initialization order.
- `NominalTypeEmitter` for hidden class members, contract bridges, and capture fields.
- `LambdaCompilationPlan`, `LambdaSupportEmitter`, and `LambdaTemplateSupport` for handler shape
  interfaces and fallback lowering.
- `RuntimeSupportEmitter` for the shared bootstrap support and runtime dependency scanning.
- `ZeronLibraryIndex`, `ZeronVersions`, and the output staging pipeline for the absence of hidden
  class entries and the bootstrap ABI dependency.
- The class-file builder/API used by `RuntimeSupportEmitter` to generate bytes in memory.

Implement in stages:

1. **Byte generation and eligibility.** Generate hidden class bytes in memory with deterministic
   names, no `NestHost`/`NestMembers`, and a dry-run eligibility analysis. Keep the named fallback
   as the default.
2. **Object literals.** Emit hidden classes and indy constructor factories for eligible object
   literals. Validate captures, mutable fields, contract dispatch, and identity. Keep the named
   fallback for ineligible literals.
3. **Handler values.** Emit hidden classes implementing function-shape interfaces for eligible
   handler literals. Keep `LambdaMetafactory` as the fallback and for ordinary lambdas.
4. **Named handler declarations.** Add the condy singleton path in the initializer for capture-free,
   order-independent declarations; otherwise use the indy factory and the existing field.
5. **Class-byte embedding and cleanup.** Add chunked string encoding, thresholds, bootstrap
   validation, `auto` selection, and remove temporary duplicate paths.

Validation must include:

- `javap -v` assertions that an eligible host class contains the expected condy/indy bootstrap
  entries and chunked string constants, and no named anonymous class output file;
- `javap -c` assertions that an object literal uses an indy factory rather than `new` plus
  `invokespecial` on a named anonymous class;
- runtime tests that two evaluations of one object literal are distinct and have independent mutable
  state;
- runtime tests that two evaluations of one handler literal are distinct, while every read of a named
  handler declaration is the same value;
- capture tests for object literals and handler literals, including nested lambdas and host-private
  members;
- contract dispatch tests for single and multiple contracts, generic contracts, properties, and
  default methods;
- handler dispatch tests for abortive cases, guards, suppression, raised effects, and resumption;
- top-level initialization-order tests for named handler declarations, including reads before
  initialization and condy resolution inside the initializer;
- reflection tests that `Class.forName` cannot find a hidden class and that `Class.isHidden()` is
  true when a `Class` object is available;
- serialization/reification tests that require the named fallback and still behave correctly;
- cross-library tests in both directions: a consumer object literal implementing a provider
  contract, and a provider named handler declaration used by a consumer;
- fallback tests that compile the same source with `named`/`lambda` and `hidden` selection and compare
  observable behavior;
- determinism tests that compile the same source twice and compare all output files and hidden-class
  byte payloads;
- malformed, truncated, and oversized class-byte tests that fail with a clear linkage error;
- class-count, host-size, startup, and allocation measurements against the
  [ZEP-0095](./ZEP-0095.md) corpus;
- `mvn test` and `zeron build` verification, plus `javap` inspection of generated output.

## Open questions

- Should object literals with extra members outside their contracts be supported through a generated
  hidden interface, or always use the named fallback? The proposal uses the fallback because a hidden
  interface cannot be named in a `checkcast` or `invokeinterface` constant.
- Should handler values use the hidden-class path in the first implementation, or should the first
  stage keep `LambdaMetafactory` and apply hidden classes only to object literals? The proposal
  permits a staged rollout but defines the handler path as the target.
- Should a named handler declaration use condy at all, or is the existing top-level field sufficient?
  Condy is an optimization; the field remains the semantic source of the single value.
- What is the exact condy condition for a named handler declaration: capture-free only, or also a
  proof that the initializer has no order-dependent side effects? The proposal requires both.
- Should the class-byte encoding be base64 or ISO-8859-1? Base64 is the recommended default; the
  final choice should be measured against host-size and startup cost.
- What is the maximum embedded class size per literal and per host class? The threshold is a quality
  decision and should be set from measurements.
- Should hidden classes be defined with `ClassOption.STRONG`? The default weak hidden class is
  unloaded with its loader; a condy constant should keep it reachable while needed. This needs
  measurement and a class-loader lifetime review.
- Should `defineHiddenClassWithClassData` carry contract/source metadata, or should the bootstrap
  receive it as ordinary static arguments?
- Should hidden classes be defined eagerly when the host class is initialized, or lazily on first
  evaluation? Lazy condy resolution is the default; eager definition may simplify debugging but
  increases startup cost.
- Should a hidden class be shared between two literals with identical bytes? The proposal says no
  because nominal identity and reflection would become observable. This could be revisited only with
  a proof that class identity is unobservable.
- How should debug metadata name hidden-class frames without exposing the unstable runtime name?
- Should Java interop expose a stable interface-only view for anonymous values, or require the named
  fallback whenever Java code needs the concrete type?
- Should the compiler reject anonymous types in exported signatures, or automatically use the named
  fallback? The proposal prefers rejection or fallback under the existing anonymous-type export
  rules; the exact diagnostic is open.
- What quality thresholds should gate the migration: host constant-pool size, class count, startup
  time, allocation, or all of them?

## Decision

Draft created 2026-11-26. The proposal lowers eligible object literals and handler values to
hidden classes, constructs object and handler literals per evaluation, and permits a condy singleton
only for named handler declarations. Hidden classes are restricted to values whose generated type
does not escape into named signatures; the existing named synthetic class and `LambdaMetafactory`
paths remain fallbacks. The class-byte encoding, size thresholds, condy conditions, and staged
handler rollout remain open.
