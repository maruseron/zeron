## Abstract

This proposal replaces the linear `instanceof` chain that `match` currently emits for reference-root
alternatives with one `invokedynamic` call site bound to
`java.lang.runtime.SwitchBootstraps.typeSwitch` and a `tableswitch` over the returned label index.
The resolver's ordered top-level class tests become the bootstrap's label array. A restart index
preserves first-match order when a guard fails, a nested pattern is refuted, or an applied-identity
test fails. Nested extraction, applied descriptor identity, bindings, and arm bodies remain in the
host class.

The change is emission-only. Small matches, matches whose arms all test the same erased class,
literal and primitive roots, and matches containing labels that cannot be named in a class file keep
the existing chain. No source semantics, API-index schema, standard-library API, or version changes.

## Motivation

`ExpressionFlowEmitter.emitMatchExpression` currently stores the scrutinee once and then emits each
arm as an independent linear test. For a class pattern, `emitMatchPattern` emits:

```text
aload scrutinee
instanceof Target
ifeq next
[applied descriptor equality]
aload scrutinee
checkcast Target
astore matchedValue
[extract payloads or components]
[guard; ifeq next]
[arm body; goto done]
next:
```

An `N`-alternative match with only class-testing alternatives therefore contains `N` top-level
`instanceof` instructions, `N` conditional branches, and `N` branch targets with their stack-map
frames. For a sealed contract or sum type the set of runtime alternatives is closed and already
known to the resolver. Re-testing the same
scrutinee against each alternative in source order is the simplest correct lowering, but it is not
the cheapest one.

The standard library contains both shapes. Many matches are two-case `Option` or `Result` matches
where the chain is compact and should stay. Larger matches, such as the nine-alternative `CodeShape`
matches in the standard library and the query-engine sample, repeat the top-level test many times.
The class-file quality inventory records the general emission baseline; it does not yet isolate
match dispatch, so this proposal also adds that measurement.

The JDK exposes the same ordered-selection problem in `java.lang.runtime.SwitchBootstraps`, the
bootstrap used by Java's pattern `switch`. Its `typeSwitch` bootstrap accepts a selector and an
ordered array of `Class` labels, links a constant call site, and returns the index of the first label
matching a non-null selector. It returns `-1` for a null selector and the label count when no label
matches. The JDK defines a hidden nestmate class containing the decision method at link time; the
host class's top-level decision contains only the `invokedynamic` call site, the label constants,
and a `tableswitch`.

That contract matches Zeron's top-level match decision directly:

- the resolver has already established an ordered, exhaustive set of top-level class tests;
- the scrutinee is evaluated exactly once before the decision;
- a refuted nested pattern means "try the next top-level alternative"; a failed guard means "try the
  next arm";
- the label set is static and separate-compilation-safe;
- the host class does not need a new runtime support type or a new Zeron bootstrap ABI.

## Goals

- Replace eligible top-level `instanceof` chains with one `SwitchBootstraps.typeSwitch` call site and
  a `tableswitch` over the returned index.
- Preserve arm order, first-match semantics, guards, nested refutation, OR-pattern alternatives,
  duplicate top-level classes, aliases, bindings, sum payload extraction, product and data-class
  component extraction, named-pattern extraction, and applied descriptor identity.
- Preserve scrutinee evaluation once, left-to-right evaluation order, exceptions, null and
  no-match behavior, and reference identity.
- Define the label mapping, the restart protocol, and the selected-pattern emission path.
- Define the eligibility predicate and the fallback to the existing chain.
- Keep hidden and otherwise non-denotable classes out of bootstrap labels.
- Measure host-class bytes, instruction and frame counts, runtime hidden-class count, linkage and
  startup cost, and match throughput before and after the change.
- Keep generated output deterministic and separate-compilation-safe.
- Keep the API index, standard-library API version, and artifact version unchanged.
- Use the JDK bootstrap rather than extending the Zeron shared bootstrap runtime from
  [ZEP-0181](./ZEP-0181.md).

## Non-goals

- String-literal match roots. Their current `String.equals` chain is not an `instanceof` chain; a
  hash-based string switch is a separate optimization.
- Primitive roots (`Int`, `Long`, `Char`, `Boolean`) and `lookupswitch`/`tableswitch` lowering for
  literal values.
- Nested or recursive decision trees that group repeated top-level classes or dispatch on extracted
  payloads. The flat restart protocol in this proposal is the first slice.
- Product and data-class roots whose arms all test one erased class. A separate peephole may remove
  redundant top-level tests there.
- `SwitchBootstraps.enumSwitch` and `mappedEnumSwitch`. Zeron sum cases are classes, not enum
  constants, and there is no enum match root.
- Nullable match roots, `case null`, or changes to the current non-null match-root rule.
- Changes to match source syntax, coverage, exhaustiveness diagnostics, or the no-match exception
  type.
- Replacing `is` or `matches` tests.
- Changes to witness evidence, hidden anonymous values, or the Zeron bootstrap ABI from
  [ZEP-0180](./ZEP-0180.md), [ZEP-0181](./ZEP-0181.md), and [ZEP-0182](./ZEP-0182.md).
- Guaranteeing a particular JIT outcome, startup time, or runtime hidden-class count.
- Ahead-of-time or native-image support for link-time hidden-class definition. That remains an open
  compatibility question with a chain fallback.

## Proposal

### 1. Eligibility

The compiler uses the bootstrapped path only when all of the following hold:

- the scrutinee's erased type is a reference type;
- every arm's top-level pattern is a class-testing pattern (type, applied, product, data-class,
  sum-case, property, or named pattern), a binding, or a wildcard, with no top-level literal pattern;
- the label plan meets the size threshold in section 7;
- every class label is a named class that can be represented by a `CONSTANT_Class` entry;
- the target runtime provides the stable `SwitchBootstraps.typeSwitch` API and supports hidden-class
  definition at link time; a compiler option may force the bootstrapped path for A/B validation on
  such a runtime.

Otherwise the existing chain remains the lowering. The predicate is conservative: an unsupported or
ambiguous shape falls back rather than producing a different decision structure.

A label is not eligible when it denotes a hidden class. Hidden classes cannot be named in a class
file and `SwitchBootstraps` handles them through runtime extra arguments, which would add a runtime
dependency and a separate-compilation hazard. Anonymous classes from
[ZEP-0182](./ZEP-0182.md) are therefore not match labels. The existing chain remains the fallback if
a future pattern ever targets such a type.

### 2. Label model

The emitter builds an ordered label plan from the resolved arms. Each entry represents one top-level
alternative and carries:

- the arm it belongs to;
- the alternative pattern, or the arm pattern when it is not an OR-pattern;
- the erased class descriptor used as the bootstrap label;
- the case label in the generated `tableswitch`;
- the label index.

The mapping is:

- a type, product, data-class, sum-case, property, or named-pattern alternative uses the erased
  class of `pattern.resolvedType()` as its `Class` label;
- a binding or wildcard alternative uses the erased class of the scrutinee as its `Class` label,
  which is an always-true label for a non-null value of that static type;
- an OR-pattern contributes one entry per alternative, in source order;
- duplicate labels are allowed and remain distinct entries, because different alternatives may need
  different nested tests, bindings, or guards.

The label array preserves source order. The `tableswitch` case for an entry runs only that
alternative's selected-pattern emission and then reaches the shared arm body.

Applied descriptor identity is not encoded in the bootstrap label. A label selects the erased class;
the arm body still performs the [ZEP-0015](./ZEP-0015.md) descriptor equality before casting,
binding, or extracting. A failed equality restarts at the next label.

### 3. Call site

The emitter adds one `invokedynamic` call site per eligible match:

```text
invokedynamic typeSwitch:(L<selector>;I)I
```

The bootstrap method is:

```text
java.lang.runtime.SwitchBootstraps.typeSwitch:
  (MethodHandles.Lookup, String, MethodType, Object[]) -> CallSite
```

The invocation type is `(L<selector>;I)I`, where `<selector>` is the erased scrutinee type. The
bootstrap arguments are the label constants in plan order: `ClassDesc` constants for class labels.
Every bootstrap label is a `Class` constant; no `String`-constant, `Integer`-constant, `EnumDesc`,
primitive, or hidden-class label is emitted by this proposal.

The call site name is `typeSwitch`; the bootstrap ignores it. The emitter uses
`DynamicCallSiteDesc.of` with the bootstrap `MethodHandleDesc`, the invocation type, and the label
arguments, so the existing ClassFile API emits the `BootstrapMethods` entry and constant-pool
references.

The host class's constant pool therefore gains:

- a `MethodHandle` to `SwitchBootstraps.typeSwitch`;
- a `MethodType` for `(L<selector>;I)I`;
- the `Class` constants for the labels;
- one `InvokeDynamic` entry per eligible match.

The class-file version remains the project's Java 25 target. No preview feature is used.

### 4. Control flow

The general lowering uses a restart local and a loop. In pseudocode:

```text
scrutinee = evaluate once
restart = 0
loop:
  index = typeSwitch(scrutinee, restart)
  tableswitch index:
    0 -> case 0
    ...
    N-1 -> case N-1
    default -> noMatch

case i:
  emit selected alternative i, with failure -> restart[i + 1]
  goto armBody(arm of i)

armBody(arm):
  if guard: evaluate guard; if false -> restart[armEnd(arm)]
  evaluate arm expression; convert to the match result type; goto done

restart[k]:
  if k == N: goto noMatch
  restart = k
  goto loop

noMatch:
  throw IllegalStateException("No match case accepted the runtime value.")

done:
  result is on the stack
```

`typeSwitch` returns `-1` for a null selector and `N` for no match. Both values reach the
`tableswitch` default and then `noMatch`, so the explicit `ifnull` check that the chain emits before
its arms is redundant on this path. The chain keeps it; the bootstrapped path may omit it.

A failed nested test inside alternative `i` restarts at `i + 1`, which is the next alternative of the
same arm or the first alternative of the next arm. A failed guard restarts at the arm's end index, not
at the current alternative, because an OR-pattern arm that has already matched must not try its other
alternatives after the guard fails. A restart at `N` goes directly to `noMatch`; it does not call the
bootstrap again.

When no arm can fail after its top-level label has been selected, the loop and restart local are
unnecessary. The direct form emits one `typeSwitch` call with `restart = 0`, a `tableswitch`, and the
selected arm bodies. The implementation may start with the general form and add the direct form when
the plan proves that every selected alternative is total and every arm is unguarded.

### 5. Selected-pattern emission

The existing `emitMatchPattern` performs the top-level test itself. The bootstrapped path needs a
selected-pattern variant that starts after the top-level label has matched:

- a type, product, data-class, sum-case, property, or named-pattern alternative skips the top-level
  `instanceof`, performs applied descriptor equality when required, casts the scrutinee to the
  resolved class, stores the matched value, binds the alias, and then runs the existing nested
  extraction and nested pattern tests;
- a binding alternative stores the scrutinee into the binding;
- a wildcard alternative does nothing;
- an OR alternative is handled as its own label entry; on success it jumps to the shared arm body.

Nested failures use the restart block for the next label. The existing nested logic for sum payloads,
product components, data-class components, property patterns, named-pattern helpers, null helper
results, and nested OR-patterns is reused unchanged. The top-level test is the only step removed.

The arm's bindings are declared once for the whole arm, including all OR alternatives, as the current
emitter does. Each selected alternative stores the same binding slots on its success path. The shared
arm body evaluates the guard and the result expression with those slots live.

### 6. Example

For a sealed contract:

```zeron
sealed contract Shape permits Circle, Square, Dot {}

fn measure(shape: Shape): Int = match (shape) {
    case Circle(radius) if radius > 0 -> radius;
    case Circle(_) -> 0;
    case Square(side) -> side;
    case Dot() -> -1;
};
```

the current lowering tests `Circle`, then `Circle` again, then `Square`, then `Dot`. The proposed
lowering builds the label plan `[Circle, Circle, Square, Dot]` and emits one `typeSwitch` call. The
bootstrap routes a non-`Circle` value directly to the `Square` or `Dot` case; the host does not
re-test `Circle` for every arm. When a `Circle` value selects index 0 and its guard fails, the
restart index is 1, the end of that arm; the next `typeSwitch` call then selects index 1. A failed
nested test or applied-identity test restarts at the next label in the same way. The `tableswitch`
selects the case body directly. The second `Circle` entry is a duplicate label and is intentional.

The JDK's own pattern-switch lowering uses the same ordered-label and restart idea. This proposal
does not depend on javac's exact tree shape; it uses the flat restart protocol because it maps
directly to Zeron's ordered arms and is simpler to validate.

### 7. Threshold and fallback

`typeSwitch` is not free. Each linked call site causes the JDK to define one hidden nestmate class
containing a decision method, and the host class gains an `invokedynamic` entry, a bootstrap-method
reference, and a `tableswitch`. The JDK defines that class with strong reachability, so it remains
for the lifetime of the host class's loader; this is part of the per-call-site cost the threshold
must bound. For a two-arm match on two classes, the existing chain is usually smaller.

The initial threshold is:

- at least three distinct erased class labels; or
- at least four total label entries with at least two distinct erased classes.

The exact threshold is an open question and must be tuned from the measurements in section 9. The
compiler keeps an internal option to force the chain or the bootstrapped path for A/B tests; it is a
validation and troubleshooting switch, not a source-level compatibility promise.

The chain remains the lowering for:

- matches below the threshold;
- matches with top-level literal patterns, including String roots;
- primitive roots;
- matches whose labels are all one erased class, including ordinary product and data-class roots;
- matches containing a hidden or non-denotable label;
- runtimes or build modes where link-time hidden-class definition is unavailable.

### 8. Runtime, ABI, and separate compilation

The bootstrap is part of `java.base` and has been available since Java 21. Zeron targets Java 25, so
the generated class has no new module or library dependency. The host class does not reference
`java.lang.classfile`; only the JDK's bootstrap implementation uses it.

The call site is a constant call site. The JDK links it once and returns an `int` for each evaluation.
There is no per-evaluation allocation, no reflection, no runtime name lookup, and no Zeron runtime
support class. The host class's match logic stays in the host method; only the top-level test runs in
the JDK-generated hidden decision method.

The emitted class file is deterministic for identical input: label order is source order, label
constants are deterministic `ClassDesc` values, and the ClassFile API emits the `BootstrapMethods`
entries in call-site order. The JDK-generated hidden class's name and bytes are runtime artifacts
and are not part of the Zeron output or its determinism tests.

Separate compilation is preserved. A label is an ordinary class reference. A consumer's match already
depends on the permitted classes or sum cases it names; if a library removes or renames one, the
consumer's class file fails at link time in the same way as any other missing type reference. If a
library adds a permitted class, the consumer must be recompiled to restore exhaustiveness; that rule
is unchanged.

No exported type, method, field, API-index entry, `API_INDEX_SCHEMA_VERSION`, or
`STANDARD_LIBRARY_API_VERSION` changes. This proposal does not need the version consolidation
required by [ZEP-0180](./ZEP-0180.md) and [ZEP-0096](./ZEP-0096.md).

The proposal deliberately does **not** use the Zeron shared bootstrap runtime from
[ZEP-0181](./ZEP-0181.md). `SwitchBootstraps` is a JDK facility with its own linkage and versioning;
adding a second Zeron bootstrap ABI for match dispatch would duplicate that work and couple match
emission to the witness/bootstrap migration. If a later nested-decision-tree lowering needs a
compiler-owned bootstrap, it should be proposed separately and reuse the [ZEP-0181](./ZEP-0181.md)
runtime.

### 9. Measurement and validation

The implementation records, for the standard library, the test corpus, and representative user
programs:

- host-class bytes and total emitted bytes for eligible matches;
- top-level `instanceof`, `checkcast`, branch, and stack-map-frame counts;
- `invokedynamic` call-site count and bootstrap-argument count;
- runtime hidden-class count at link time, using the JVM's class-loading log or an equivalent
  diagnostic;
- linkage and startup time for a program with many matches;
- match throughput for 2, 3, 8, and 16 alternatives, with and without guards and nested patterns.

The comparison is against the same sources compiled with the chain path. The class-file quality
inventory gains a match-dispatch section with the before/after numbers. The design document's
compilation-strategy section is updated to describe the bootstrapped path and its fallback.

## Compatibility and impact

Source compatibility is unchanged: no syntax, typing, coverage, diagnostic, or evaluation-order rule
changes. The no-match path still throws the existing `IllegalStateException` with the existing
message.

Runtime compatibility is limited to the project's Java 25 baseline. `SwitchBootstraps` is stable API,
and the Class labels used here do not require preview features. A runtime that cannot define hidden
classes at link time (for example, some ahead-of-time or native-image configurations) needs the chain
fallback; this is an open compatibility item rather than a source-visible feature.

Library and API-index compatibility is unchanged. The generated class file gains constant-pool and
`BootstrapMethods` entries, but no new declarations. Compiled libraries remain usable under the same
rules as before.

The main runtime trade-off is one JDK-generated hidden class per linked call site. The host class
shrinks, but the process gains that class and its linkage cost. The threshold and fallback are
therefore part of the design, not an optional tuning detail. The measurement stage must show that the
eligible corpus improves or stays neutral in total artifact and startup cost; otherwise the threshold
is raised or the feature remains disabled by default.

Debugging is not materially worse: the arm bodies remain in the Zeron class, so stack traces for
guards, extractors, and result expressions still point at the Zeron method. The bootstrap-generated
hidden decision method performs only the top-level test. `javap` shows the `invokedynamic` entry and the
`tableswitch` in the host class.

## Alternatives

- **Keep the linear chain for every match.** This is simple, needs no runtime hidden class, and is
  best for two-arm matches. It is retained as the fallback, but using it for every match leaves the
  repeated top-level tests in larger sealed-contract and sum-type matches.
- **Write a Zeron-specific match bootstrap.** A compiler-owned bootstrap could generate a decision
  tree or a specialized dispatch method. It would duplicate `SwitchBootstraps`, add a bootstrap ABI
  and versioning burden, and overlap [ZEP-0181](./ZEP-0181.md). Rejected for this slice; a future
  tree lowering can revisit it if the JDK facility proves insufficient.
- **Assign integer type tags and use `tableswitch` directly.** This requires a tag on every value or
  a runtime type-to-tag table. It changes representations and cannot be derived from the closed
  permitted set alone without runtime lookup. Rejected.
- **Use `ClassValue`, reflection, or a method-handle cache.** These add runtime lookup, hidden state,
  class-loader lifetime concerns, and separate-compilation hazards, and they duplicate work the JVM's
  constant call site and inline caches already do. Rejected.
- **Use `SwitchBootstraps.enumSwitch`.** Zeron sum cases are classes with payloads, not enum
  constants. Rejected.
- **Use `LambdaMetafactory` or one method handle per arm.** This adds allocation and dispatch
  indirection without removing the ordered selection problem. Rejected.
- **Use a hash-based switch for String roots.** This is a useful separate optimization, but it does
  not replace an `instanceof` chain and is outside this proposal.
- **Use `MatchException` instead of the existing `IllegalStateException`.** The JDK's pattern switch
  uses `MatchException` for an unmatched exhaustive switch, but changing Zeron's exception type is an
  observable behavior change unrelated to dispatch quality. Rejected for this proposal.
- **Split a nested-decision-tree proposal out now.** Deferred. The flat restart protocol is complete
  for the eligible shapes; a tree lowering should be proposed with measurements showing that
  repeated top-level tests or repeated extraction remain a problem.

## Implementation and validation

The implementation is staged:

1. Refactor `emitMatchExpression` into a plan builder and the existing chain emitter. Keep the chain
   as the default and add bytecode-shape tests for the plan.
2. Add the `typeSwitch` call site, `tableswitch`, restart blocks, selected-pattern emission, duplicate
   labels, OR alternatives, binding and wildcard labels, guards, and applied descriptor equality.
   Start with the general restart form.
3. Add the direct form for plans with no post-label failure, then measure and tune the threshold.
4. Enable the eligible path by default, update the design document and inventory, and keep the chain
   as the documented fallback.

Validation includes:

- bytecode-shape assertions using the ClassFile API or `javap`: the bootstrap method, invocation
  type, label order, `tableswitch` cases, restart blocks, and the absence of top-level `instanceof`
  instructions on the bootstrapped path;
- behavioral tests for every arm shape, guards, nested refutation, OR-patterns, duplicate classes,
  aliases, bindings, applied descriptor mismatches, sum payloads, product and data-class components,
  named patterns, null and foreign runtime values, and exception propagation;
- evaluation-order tests with side-effecting guards and extractors, proving that the scrutinee is
  evaluated once and only the selected arm body runs;
- verification with `-Xverify:all` on the generated classes;
- separate-compilation tests for a library-defined sealed contract and a consumer match;
- deterministic-output tests that compile the same sources twice and compare the emitted class files;
- A/B runs with the chain forced, confirming identical behavior and measuring the threshold;
- measurements from section 9 recorded in the class-file quality inventory.

The acceptance criteria are: no source-visible behavior change; a smaller or neutral host class for
eligible matches; no regression for fallback matches; valid stack maps; deterministic output; no API
index or version change; and measured runtime hidden-class and linkage costs within the threshold
chosen for the default.

## Open questions

- What exact threshold should gate the default: distinct labels, total labels, estimated host-class
  bytes, or a combination?
- Should the direct form be part of the first implementation or a follow-up after the restart form is
  validated?
- Does the per-call-site hidden class cost outweigh the host-class savings for medium matches in
  short-lived processes or heavily loaded class loaders?
- Should a later proposal add nested decision trees for repeated top-level classes and repeated
  payload extraction? If so, should it use `SwitchBootstraps` recursively or a compiler-owned
  bootstrap?
- Should String roots use a hash-based switch, and should primitive roots use `lookupswitch` or
  `tableswitch`, as separate match-dispatch parts?
- What is the fallback policy for ahead-of-time or native-image runtimes that cannot define hidden
  classes at link time: compile-time option, runtime detection, or always-chain for those targets?
- Should the explicit null check be removed on the bootstrapped path, or retained as a defensive
  check even though `typeSwitch` returns `-1` for null?

## Decision

Draft created 2026-11-26. The proposal chooses a single ZEP for the flat, restart-based top-level
dispatch and keeps the existing chain as the fallback. Nested decision trees, String and primitive
roots, the exact threshold, and the ahead-of-time fallback remain open. No implementation has landed.
