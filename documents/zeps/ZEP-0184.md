## Abstract

Add `Self` as a contextual type name for the type of `this`. In a class body it expands to the
enclosing nominal type applied to its own type parameters, so `Self` is an alias rather than a new
type. In a contract it is late-bound: a `Self` result means the final class that declares
conformance, substituted at conformance time. Contract `Self` is allowed only in result position in
version 1. The type erases to the contract type in the generated interface, and an implementation
that returns its own class uses the class-side covariance bridge from
[ZEP-0168](./ZEP-0168.md). `Self` adds no inheritance, no F-bounded polymorphism, and no runtime
representation.

## Motivation

Three existing gaps converge on the same missing name.

[ZEP-0082](./ZEP-0082.md) deferred a general `Self` type. Fluent builder APIs therefore return a
concrete class name, and a generic builder must repeat its own type arguments:

```zeron
public class Box<T> {
    public fn tag(label: String): Box<T> = ...;
}
```

The repetition is mechanical and grows with every type parameter. A receiver-tied view has the same
problem: `File` must be written out even though the method already knows its receiver type.

Contracts have no way to say that a method returns the implementation's own type. Design
document-20 records “No `Self`” as a constraint on collection contracts: a contract method cannot
return “the same implementation”. A nominal `Self` closes that gap for final classes without
requiring class inheritance.

The scoped receiver work in [ZEP-0161](./ZEP-0161.md) needs the distinction most concretely. In a
`scoped fn`, a result written as `scoped Self`, `scoped &Self`, or `scoped Self?` is receiver-tied
and non-escaping; the same result written as plain `Self` or the class name is an ordinary value.
That rule needs a syntactic name for “the receiver's declared type”, not a repeated class name.
`Self` supplies it.

## Goals

- Add `Self` inside a class body as an alias for the enclosing nominal type, including its type
  arguments.
- Allow `Self` in every type position in a class body: fields, parameters, results, locals, type
  arguments, arrays, and nested generic instantiations.
- Name the receiver's declared type as `Self` in instance members. The existing mutability view
  (`Self` or `&Self`) is unchanged, and this is a typing statement, not a runtime change.
- Allow `Self` in result position in a contract: method requirements, read-only property getters,
  and default implementations.
- Substitute a contract `Self` with the final implementing class at conformance.
- Reuse the ZEP-0168 class-side covariance bridge for an implementation that returns its own class
  where the generated contract method returns the contract type.
- Record the contract result marker in the API index and the separate-compilation format.
- Support the formatter, highlighter, and LSP with the same contextual-name treatment as other type
  names.

## Non-goals

- F-bounded polymorphism, `Self` as a type-parameter bound, or `Self` as a constraint.
- `Self` in contract parameter position. Receiver-typed parameters need their own variance and
  dispatch design.
- `Self` nested inside a contract result type argument, such as `Option<Self>`.
- `Self` in extensions. An extension has no enclosing nominal type; it must name its receiver type.
- Outer-type qualification such as `Outer.Self`. A nested declaration binds `Self` to its nearest
  enclosing class or contract.
- Polymorphic `Self` that changes meaning in a subclass. Classes are final in the current language,
  and `Self` is nominal: it is the type in whose declaration it appears.
- A user-declared type named `Self`.
- Changing contract inheritance, variance, or the runtime type system.
- Reified or runtime `Self` identity separate from the expanded type.

## Proposal

### Surface

`Self` is a contextual type name, recognized only in type position inside a class or contract body.
It is not a keyword elsewhere, so existing identifiers named `self` or `Self` in non-type positions
remain valid. A class or contract declaration named `Self` is rejected, because it would make the
name ambiguous.

A class-side builder reads naturally:

```zeron
public class Box<T> {
    private var value: T?;

    public fn put(value: T): Self {
        this.value = value;
        return this;
    }

    public fn copy(source: Self): Self = ...;
    public fn maybeSelf(): Self? = ...;
    public fn mutableView(): &Self = ...;
}
```

Inside `Box<T>`, every `Self` is `Box<T>`. The alias participates in ordinary substitution: a
`Box<String>` has a `put` method whose result is `Box<String>`, and `copy` takes a `Box<String>`.

### Class-side resolution

`Self` expands during name resolution, before type checking and before the signature is exported.
The resolver records any scoped-result flag from [ZEP-0161](./ZEP-0161.md) while the written form is
still visible, then expands the type. The expansion is the enclosing class applied to its own type
parameters. As a result:

- `Self` is equal to the written class type for equality, assignability, variance, substitution,
  API-index export, and separate compilation;
- `Self` may appear under `&` and `?`, with the same canonical form as the expanded type;
- `Self` may appear in fields, parameters, results, local annotations, generic type arguments, and
  arrays;
- a `Self` result is an ordinary class-typed result. It is not receiver-tied by itself; inside a
  `scoped fn`, a receiver-tied result is written `scoped Self` ([ZEP-0161](./ZEP-0161.md)).

`this` already has the enclosing class type in instance members. This proposal names that type; it
does not change method dispatch, field layout, or descriptors. A static member may use `Self` as an
alias for the enclosing class even though it has no `this`.

A nested class binds `Self` to itself, not to an outer class. The outer type is still available by
name. There is no `Outer.Self` form in version 1.

Extensions are ordinary declaration containers without a nominal `Self`. Inside an extension,
`Self` is rejected with a diagnostic that asks for the explicit receiver type.

### Contract-side late binding

A contract may use `Self` as the complete result of a method requirement, a read-only property
getter, or a default implementation:

```zeron
public contract Cloneable {
    public fn duplicate(): Self;
    public property copy: Self;
}

public class File : Cloneable {
    public fn duplicate(): Self = ...;
    public property copy: Self = ...;
}
```

For a final class `File` conforming to `Cloneable`, the contract's `Self` is `File`. Conformance
checks the implementation's declared result against `File` using ordinary subtyping, including the
return covariance of [ZEP-0168](./ZEP-0168.md). Since classes are final, there is no subclass that
could inherit a result of the wrong type.

`Self` may appear under `&` or `?` at the top level: `&Self`, `Self?`, and `&Self?` are allowed.
Substitution replaces the `Self` leaf and leaves the wrapper in place.

The following are rejected in version 1:

- `Self` in a contract parameter: `fn merge(other: Self): Self`;
- `Self` inside a result type argument: `fn all(): Array<Self>`;
- `Self` in a contract field, setter, or effect payload;
- `Self` outside a contract result, such as a local or a static member of the contract.

The restriction to the top-level result is deliberate. A contract already has type parameters and
associated capability markers; adding a hidden self parameter would change contract identity,
inference, and API encoding. Result substitution covers the fluent and receiver-tied cases without
those consequences.

### Contract defaults and `this`

Inside a contract default implementation, `this` has type `Self`. The body may use the contract's
own members and may return `this` directly:

```zeron
public contract Readable {
    public fn view(): Self = this;
    public fn describe(): String = ...;
}
```

Without that rule, a default body would see only the contract type and could not return the
implementation's type. Typing `this` as `Self` is sound because `Self` is the conforming final class,
which is a subtype of the contract. The body cannot name the concrete class, so it still has only
the contract's members. This example is an ordinary default; a `scoped` default that returns `this`
must write `scoped Self` for a receiver-tied result ([ZEP-0161](./ZEP-0161.md),
[ZEP-0185](./ZEP-0185.md)).

A class may override a default method with its own implementation. The requirement's `Self` is
still substituted with the class, and the override must satisfy that result.

### Conformance, calls, and erasure

At conformance, the compiler substitutes the implementing class into each contract `Self` result and
checks the implementation. In an ordinary method, a class method may spell the result as `Self`
(meaning the class) or as the class name; both denote the same type. A separate declaration attribute
may distinguish the spellings: [ZEP-0161](./ZEP-0161.md) makes `scoped Self` receiver-tied inside a
`scoped fn`, while plain `Self` and the class name denote ordinary results.

The generated contract interface cannot mention the concrete class. A `Self` result therefore erases
to the contract type in the interface descriptor:

```text
interface Cloneable        Cloneable duplicate();
class File implements Cloneable   File duplicate();   // covariant override
```

The class-side bridge required by [ZEP-0168](./ZEP-0168.md) supplies the interface-typed method when
the class returns its own type. A contract default method is already compiled against the contract
type and needs no bridge unless a class overrides it.

A call through a contract-typed reference sees the contract type as the result, because the concrete
self type is not statically known. A call through the class type sees the class result. This matches
the existing covariance rule and keeps `Self` out of the runtime type system.

An anonymous object expression ([ZEP-0017](./ZEP-0017.md)) conforms through its hidden nominal class.
`Self` in a requirement is that hidden class. A default method returning `this` works; a method that
returns the hidden type explicitly cannot be written in source, so anonymous implementations
normally use the default. Callers see the contract type.

### API index and separate compilation

Class-side `Self` is fully expanded before export. The API index records the expanded type, so a
separate compilation sees no new syntax and no schema change for class members.

Contract-side `Self` is part of the contract's exported signature. The API index records a top-level
`self` result marker, including any `&` or `?` wrapper, so a consumer can:

- check conformance for a new implementation;
- keep the result opaque when calling through the contract type;
- reject a use that requires a non-denotable self type.

`API_INDEX_SCHEMA_VERSION` is bumped once when the feature lands. The bump is shared with the scoped
signature flags from [ZEP-0160](./ZEP-0160.md) and [ZEP-0161](./ZEP-0161.md); do not bump the schema
twice in one release cycle. `STANDARD_LIBRARY_API_VERSION` is bumped only if a standard-library
signature adopts `Self`.

## Compatibility and impact

- Additive for existing code. `Self` is recognized only in type position inside a class or contract;
  the repository has no existing type named `Self`.
- A declaration named `Self` becomes an error. That is the only source break, and it is deliberate:
  allowing a user type to shadow the contextual name would make the meaning position-dependent.
- The parser, formatter, highlighter, LSP, and completion need the contextual type name.
- The resolver expands class-side `Self`; the type model needs a self leaf only for contract
  results, substituted at conformance. No new runtime descriptor is introduced.
- Contract conformance and export gain the self marker. Existing contracts are unchanged.
- No JVM descriptor change beyond the ordinary covariant override and bridge that the class already
  emits for ZEP-0168.
- Documentation: classes and contracts, generics, builder APIs, and the scoped receiver chapters
  should use `Self` once it ships.

## Alternatives

- **General F-bounded `Self`.** Rejected: it changes variance, bounds, inference, and contract
  identity, and the motivating APIs do not need a bound.
- **Contract-only `Self`.** Rejected: builder and receiver-tied signatures need the class-side
  alias, and that is the cheaper half of the feature.
- **Repeat the enclosing type name.** Rejected: a generic class must repeat its type arguments, and
  [ZEP-0161](./ZEP-0161.md) needs a syntactic distinction between a receiver-tied result and an
  ordinary result.
- **Spell the name `This`.** Rejected: `Self` is the conventional spelling and reads correctly in
  contracts, where the type is the conforming class rather than the lexical container.
- **Make `Self` polymorphic across subclasses.** Rejected for version 1: classes are final, and a
  future inheritance design would need its own variance and override rules.
- **Make `Self` a hidden contract type parameter.** Rejected: it would change contract identity,
  inference, admissibility, and the API index for every contract.

## Implementation and validation

1. Extend the type-name grammar with the contextual `Self` in class and contract bodies. Reject it
   outside a body and reject a class or contract declaration named `Self`.
2. Expand class-side `Self` in the resolver before type checking. Confirm that equality,
   substitution, variance, formatting, and API export see the expanded type, and that no
   `Self`-specific descriptor reaches bytecode.
3. Add a self result leaf for contract signatures. Accept it only as a top-level result, optionally
   under `&` or `?`; reject it in parameters, setters, fields, and type arguments.
4. Substitute the implementing class at conformance and reuse the ZEP-0168 covariance check and
   class-side bridge. Type `this` as `Self` in contract defaults.
5. Encode and decode the `self` result marker in the API index and the separate-compilation format.
   Coordinate the schema bump with the scoped signature flags.
6. Update the formatter, highlighter, LSP, and completion. Add the misuse diagnostics.
7. Test: class-side `Self` in fields, parameters, results, locals, type arguments, arrays, generic
   classes, nested classes, and static members; contract `Self` in requirements, getters, and
   defaults; `&Self`, `Self?`, and `&Self?`; conformance success and failure; anonymous
   implementations; contract-typed and class-typed calls; misuse in parameters, type arguments,
   extensions, and outside bodies; API-index round trips; separate compilation; and `javap` checks
   that a default method returns the contract type and a covariant override emits the expected
   bridge.

## Open questions

- Should a later proposal allow `Self` in contract parameters? It needs receiver-typed argument
  variance and is not required by the scoped receiver surface.
- Should `Self` inside a contract result type argument be allowed once use-site variance and
  existential opening are settled?
- Should a nested declaration be able to qualify an outer self type, such as `Outer.Self`? Version 1
  binds to the nearest enclosing body.
- Should a type parameter be allowed to use `Self` as a bound? That is F-bounded polymorphism and
  remains out of scope.
- Is `Self` also useful in type-class witness declarations? Version 1 keeps it to classes and
  contracts.

## Decision

Accepted 2026-11-27. `Self` is nominal: an expanding alias in a class body and a late-bound,
result-only type in a contract, substituted with the final implementing class. F-bounded use,
contract parameters, nested self types, and outer qualification stay out of scope. The contract
result marker shares one API-index schema bump with the scoped signature flags.
