# ZEP-0185: Scoped Methods in Contracts and Extensions

## Abstract

Extend `scoped fn` and `scoped mut fn` beyond class methods to contract method requirements,
contract default implementations, class overrides of defaults, and extension methods. Contract
conformance compares the receiver and parameter flags monotonically and the result flag exactly; a
contract `Self` result is substituted with the final implementing class. A default body gives
`this` the type `Self`, so `return this` as `scoped Self` is the canonical receiver-tied default;
returning it as plain `Self` is an escape. Extensions have no `Self`; a receiver-tied result is
written explicitly and must be rooted at `this`. `scoped extension` remains rejected. This proposal depends on the class-method semantics of
[ZEP-0161](./ZEP-0161.md); it does not redefine them.

## Motivation

A resource type is often used through a contract. `Readable`, `Sink`, or a resource capability
contract must be able to promise that a method does not let its receiver escape; otherwise a sealed
value cannot call the method through the contract type even when the implementation is scoped.

Contract defaults need the same promise. A default such as

```zeron
public contract Readable {
    public scoped fn view(): scoped Self = this;
}
```

is the natural way to give every implementer a receiver-tied view. Without `Self` in the default,
the body would see only the contract type and could not return the implementation's own type.
[ZEP-0184](./ZEP-0184.md) supplies the substitution; this proposal supplies the conformance and
default rules.

Extensions need the modifier because helper APIs often live outside the resource type. An extension
has no `Self` and no nominal owner, so its receiver-tied result must be written explicitly. Keeping
extensions in a separate slice from class methods also keeps the contract conformance table out of
[ZEP-0161](./ZEP-0161.md), which otherwise only has to deal with a single class receiver.

## Goals

- Add `scoped fn` and `scoped mut fn` to contract method requirements.
- Add them to contract default implementations, with `this: Self` and explicit `scoped Self`
  results.
- Check conformance with monotone receiver and parameter flags and an exact result flag.
- Allow a class override of a default to strengthen the receiver or parameter flags and preserve
  the result flag.
- Substitute a contract `Self` result, scoped or plain, with the implementing final class.
- Allow scoped methods in ordinary extensions, with an explicit receiver and no `Self`.
- Require a receiver-tied extension result to be rooted at `this`.
- Reject `scoped extension` as a container declaration.
- Reuse the ZEP-0161 method/parameter/result flag encoding and the single API-index schema bump.
- Keep `mut` conformance unchanged.

## Non-goals

- Scoped properties, property getters, setters, fields, constructors, or globals in contracts.
- Scoped methods on generic contracts or generic extensions; [ZEP-0162](./ZEP-0162.md) owns their
  admissibility.
- `Self` in contract parameters; [ZEP-0184](./ZEP-0184.md) restricts contract `Self` to results.
- A nameable self type at a call through a contract-typed reference. The result is opaque and is
  seen as the contract type.
- `scoped extension` or any container-level scoping declaration.
- Redefining receiver access, sealing, receiver-tied results, or receiver stability; those are
  [ZEP-0161](./ZEP-0161.md).
- Host interop, Java SAM conversion, or exporting scoped contract methods to Java.
- Proving that ordinary member bodies do not publish aliases of the receiver.

## Proposal

### Contract requirements

A contract may declare a scoped method requirement:

```zeron
public contract Readable {
    public scoped fn checksum(): Long;
    public scoped fn view(): scoped Self;
}
```

The requirement's receiver is read-only; `scoped mut fn` declares a mutable receiver. The flags are
declaration metadata, not part of type equality. Conformance therefore compares them with a
deliberate direction:

| Position | Requirement | Implementation | Allowed? | Reason |
| --- | --- | --- | --- | --- |
| receiver | scoped | scoped | Yes | Same restriction |
| receiver | scoped | unscoped | No | The implementation receiver could escape |
| receiver | unscoped | scoped | Yes | The implementation restricts itself further |
| parameter | scoped | scoped | Yes | The implementation accepts a sealed argument |
| parameter | scoped | unscoped | No | The implementation could retain a sealed argument |
| parameter | unscoped | scoped | Yes | Callers pass ordinary values; the implementation restricts itself |
| result | scoped | scoped | Yes | Both are receiver-tied |
| result | scoped | unscoped | No | The contract promises a receiver-tied view |
| result | unscoped | scoped | No | Callers expect an independent value |
| result | unscoped | unscoped | Yes | Same result |

The receiver and parameter flags are monotone in the safe direction: an implementation may add a
restriction but may not remove one. The result flag is exact, because a scoped result is not
interchangeable with an ordinary one.

A contract `Self` result is substituted with the implementing final class
([ZEP-0184](./ZEP-0184.md)). A `scoped fn view(): scoped Self` requirement therefore requires a
receiver-tied result of that class; a plain `Self` result is an ordinary same-type result. A call
through a contract-typed reference sees the contract type as the result, not the concrete class;
a receiver-tied result is still sealed and may call the contract's `scoped` members.

`mut` conformance is unchanged. A `mut` requirement still needs a `mut` implementation; `scoped`
composes with that rule and does not relax it.

### Contract defaults

A default implementation is checked with the same receiver, parameter, and result rules as a class
method. Inside the default body:

- `this` has type `Self`;
- ordinary member access is limited to the contract's members;
- `this` carries the non-escape restriction from [ZEP-0161](./ZEP-0161.md);
- an explicit `scoped Self`, `scoped &Self`, `scoped Self?`, or `scoped &Self?` result is
  receiver-tied; a plain `Self` result is ordinary.

```zeron
public contract Readable {
    public scoped fn view(): scoped Self = this;
    public scoped fn description(): String = "readable";
}
```

Returning `this` as `scoped Self` is the canonical default. Returning it as plain `Self` is an
escape and gets the `scoped Self` fix-it from [ZEP-0161](./ZEP-0161.md). The default may call other
contract members, including `scoped` ones. It cannot name the concrete implementing class, so a
receiver-tied non-`Self` view must be written with an explicit scoped result of a type the contract
can name.

A class that overrides a default may strengthen the receiver or parameter flags and must preserve
the result flag. Since classes are final, there is no subclass override chain to reconcile. A class
cannot weaken a scoped requirement: `scoped` on the requirement means the class implementation must
also be scoped.

### Extensions

A scoped method may be declared inside an ordinary extension:

```zeron
public extension File {
    public scoped fn lineCount(): Long = ...;
    public scoped fn readerView(): scoped &Reader = this.reader;
}
```

The extension receiver is explicit, so `Self` is not available. A receiver-tied result is written
explicitly, such as `scoped &Reader`, and follows the rooted-at-`this` rule from
[ZEP-0161](./ZEP-0161.md). The extension body has the same receiver access and trusted-member
boundary as a class method: it may call ordinary members of its own receiver, but it may not let the
receiver escape.

`scoped` scopes the method, not the extension. `scoped extension` is rejected: it would have to
answer whether every method is scoped, it does not compose with contract requirements, and it would
scope a container rather than a receiver and result.

A sealed value may call a scoped extension method whose receiver type matches. It may not call an
ordinary extension method, even when that extension method returns an independent value.

### API index and runtime

The flag encoding is the one defined by [ZEP-0161](./ZEP-0161.md): the method modifier, the scoped
flag on each parameter, and the result flag. A contract result `Self` already carries the `self`
marker from [ZEP-0184](./ZEP-0184.md). No absolute scope identity is serialized.

A scoped contract method has no special runtime descriptor. The generated contract interface method
returns the contract type; an implementation returning its own class uses the ZEP-0168 class-side
bridge. A scoped extension method is an ordinary static method with the receiver as its first
argument.

Scoped contract methods and scoped extension methods are not exported to Java and do not participate
in SAM conversion. `API_INDEX_SCHEMA_VERSION` is bumped once for the whole scoped and `Self` surface;
do not bump it again for this slice.

## Compatibility and impact

- Additive declaration modifier. Existing contracts and extensions are unchanged.
- A contract that adds `scoped` to a requirement changes its implementation contract: existing
  implementations must become scoped. That is a source-level API change and should be treated as
  one.
- Conformance and default checks gain the flag rules. The existing `mut` rule is unchanged.
- No runtime representation change. A contract `Self` result keeps the ZEP-0184 erasure and the
  ZEP-0168 bridge.
- Documentation: contracts, extensions, and resource management need the requirement/default and
  extension forms.

## Alternatives

- **Keep contract conformance in ZEP-0161.** Rejected for reviewability: the class receiver
  semantics and the conformance matrix are independent decisions, and a reader should be able to
  accept one without the other.
- **`scoped extension`.** Rejected: it scopes a container rather than a receiver and result, does
  not compose with contract requirements, and makes mixed extensions ambiguous.
- **A hidden self type parameter on every contract.** Rejected: it changes contract identity,
  inference, admissibility, and the API index for every contract. [ZEP-0184](./ZEP-0184.md) uses a
  result-only marker instead.
- **Rely on plain `Self` as an implicit receiver tie.** Rejected: it conflates “same type” with
  “same origin”, rejects a safe default or implementation that returns a newly constructed value,
  and makes `Self` mean different things inside and outside a `scoped fn`.
- **Allow a contract requirement to weaken a scoped implementation.** Rejected: a caller holding a
  scoped value relies on the requirement's restriction; removing it would reopen the escape.

## Implementation and validation

1. Extend the contract grammar and resolver with `scoped` on requirements and defaults. Reject it on
   contract properties, fields, and setters.
2. Implement the conformance flag checks: monotone receiver and parameters, exact result. Preserve
   the existing `mut` check.
3. Type `this` as `Self` in contract defaults, apply the ZEP-0160 escape restrictions, and implement
   explicit `scoped Self` results while keeping plain `Self` ordinary.
4. Implement class overrides of defaults with the strengthening rules.
5. Implement scoped extension methods with explicit receiver types and rooted-at-`this` results.
   Reject `scoped extension`.
6. Reject scoped methods on generic contracts and generic extensions; those belong to ZEP-0162.
7. Reuse the ZEP-0161 flag encoding in the API index and separate compilation.
8. Test: every conformance table row; contract-typed and class-typed calls; `scoped Self` and plain
   `Self` substitution; defaults returning `this` as `scoped Self`; `this` returned as plain `Self`;
   overrides that strengthen and that illegally weaken; extension methods; `scoped extension`
   rejection; sealed calls through a contract and an extension; API-index round trips; separate
   compilation; and Java export rejection.

## Open questions

- Should a scoped contract property getter be designed later, or should receiver-tied properties
  remain `scoped fn` methods permanently? Version 1 uses methods.
- Should a later proposal allow `Self` in contract parameters? That depends on
  [ZEP-0184](./ZEP-0184.md)'s receiver-typed parameter design.
- Should scoped methods on generic contracts and generic extensions follow ZEP-0162's admissibility
  marker directly, or need their own origin propagation rules? Version 1 rejects them.
- Should a contract requirement be allowed to declare a scoped parameter without a scoped receiver?
  Version 1 allows it; the parameter flag is independent of the receiver flag.

## Decision

Accepted 2026-11-27. Contract requirements and defaults, class overrides, and ordinary extensions
adopt the ZEP-0161 scoped method semantics. Conformance is monotone on receiver and parameter flags
and exact on the result flag; `scoped Self` results use the ZEP-0184 substitution and plain `Self`
remains an ordinary same-type result. Extensions use explicit receiver-tied results, and
`scoped extension` remains rejected. Generic contracts and extensions
stay out of version 1.
