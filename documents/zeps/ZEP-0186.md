## Abstract

Add four expression operators that read from left to right:

- `lhs .> rhs` applies a unary stage to `lhs`;
- `lhs ./> rhs` maps `rhs` over the value inside `lhs` through the `Functor` witness;
- `lhs .?> rhs` filters `lhs` through the `Filterable` witness, keeping only values for which the
  Boolean predicate is true; and
- `lhs .>> rhs` binds `rhs` through the `Monad` witness, which is the `flatMap` operation.

The family has one meaning per operator. `.>` applies a value, `./>` maps inside one functor layer,
`.?>` removes elements while preserving the constructor, and `.>>` flattens one monadic layer. The
slash in `./>` marks the pure mapping step, the question mark in `.?>` marks the predicate step,
and the double chevron in `.>>` keeps bind short. This gives the old two-operator sketch a mapping
pipe without making either operator choose between `map` and `flatMap` from the stage's result
type, and it gives pipe expressions the same filtering capability as `do` guards.

A stage may be a function value, an expression using the pipeline placeholder `_`, or an extension
stage with its receiver omitted. An extension with no parameters after the receiver is written as
a reference with no parentheses, such as `String::trim`; an extension that needs arguments uses an
argument-bearing call, such as `Option.map(user -> user.name())`. Both denote the unary function
obtained by leaving the receiver open, and the pipe supplies the subject as that receiver.

```zeron
let names = users ./> String::trim;
let name = findUser(id) .> Option.map(user -> user.name());
```

The forms are available only inside a pipe stage and only for visible extension methods. The
no-argument reference form does not promise a first-class extension reference outside a pipe, and
neither form is general partial application.

The placeholder is `_`. It is recognized only in the right-hand side of a pipe stage, is not
captured by nested lambdas, and is not assignable. The change is syntax-only: it adds no runtime
data representation, descriptor, API-index entry, or standard-library contract. Synthetic stage
lambdas reuse the existing lambda-lowering machinery. The operators make free functions,
constructors, static functions, callable references, receiver methods, and extension methods
compose in source order without forcing every API into a fluent receiver-first shape.

## Motivation

### The composition gap

Zeron has two established ways to compose value-level operations, and each covers only part of the
space.

Receiver-first methods read in execution order:

```zeron
let slug = title.trim().toLowerCase().replace(" ", "-");
```

Free functions, constructors, and static functions do not read in that order. The same program
written with free functions reads from the inside out:

```zeron
let slug = replace(toLowerCase(trim(title)), " ", "-");
```

The language already ships `zeron.function.pipe` and `compose` for function composition, but they
compose functions, not values. Applying a composed function still requires a call, and adapting a
function with additional parameters often needs an eta-expanded lambda:

```zeron
let normalizeAndSlug = pipe(normalize, slugify);
let slug = normalizeAndSlug(title);
```

The gap is structural rather than stylistic. A functional core tends to expose small free
functions and constructors; an imperative shell reads top to bottom. Zeron currently asks the
author to choose between a receiver-first API (fluent chaining) and a functional API (nesting),
even when the operations themselves are the same.

A pipe operator gives the functional API the same reading order as the fluent one:

```zeron
let slug = title .> normalize .> slugify;
let slugWithPlaceholder = title .> _.trim() .> _.toLowerCase() .> _.replace(" ", "-");
```

The first form applies function values. The second uses `_` to adapt receiver-first methods and
arbitrary expressions without requiring those APIs to change. Both evaluate left to right.

### Mapping and binding are distinct steps

A pure transformation inside a structure is not the same operation as a dependent step that
produces another structure. `Option`, `Result`, and `Stream` already expose both operations through
their `Functor` and `Monad` witnesses. A single pipe operator cannot express both without choosing
by result type, which hides an important distinction and complicates inference.

The operator family therefore keeps the distinction visible:

```zeron
let upper = opt ./> _.toUpperCase();                 // map inside Option
let account = opt .>> User::account;               // bind Option-returning step
```

`./>` maps one layer and always returns the same constructor with a changed element. `.>>` binds
one layer and requires the stage to return that constructor. A stage that returns a plain value
belongs after `./>`; a stage that returns the same monad belongs after `.>>`. There is no
automatic lifting and no type-directed operator selection.

The operator family also makes the upgrade path clear. A pure stage can later become a dependent
stage by changing `./>` to `.>>`, and the type checker reports whether the stage actually returns
the required structure:

```zeron
let config = readText(path) ./> parseConfigValue;    // map String -> Config
let config = readText(path) .>> parseConfig;        // bind String -> Result<Config, E>
```

### Error handling at expression level

The same gap is sharper for `Option` and `Result`. A dependent chain currently needs nested
`match` expressions or an explicit `flatMap` chain:

```zeron
fn loadSettings(path: String): Result<Settings, ConfigError> =
    match (readText(path)) {
        case Result.Ok(text) -> match (parseConfig(text)) {
            case Result.Ok(config) -> match (validate(config)) {
                case Result.Ok(valid) -> resolve(valid);
                case Result.Err(error) -> Result.Err(error);
            };
            case Result.Err(error) -> Result.Err(error);
        };
        case Result.Err(error) -> Result.Err(error);
    };
```

The `do` expression from [ZEP-0111](./ZEP-0111.md) already removes this shape for blocks with
several binds. It is deliberately block-oriented: it needs at least one bind, a result clause,
and a constructor. It is a poor fit for a single dependent step or for a value that appears
inside a larger expression; mixing pure and monadic stages is possible in a block, but the
operator chain is lighter for an expression. The bind pipe is the expression-level counterpart:

```zeron
fn loadSettings(path: String): Result<Settings, ConfigError> =
    readText(path)
        .>> parseConfig
        .>> validate
        .>> resolve;
```

The same chain can finish with a pure stage through the mapping pipe:

```zeron
let settings = readText(path)
    .>> parseConfig
    .>> validate
    ./> Settings::fromConfig;
```

This is not a replacement for `do`. It is the one-step and expression-position notation that
`do` intentionally does not provide.

### Extension methods need a pipe form

A receiver-first extension is already the right shape for an operation:

```zeron
public extension<T> Option<T> {
    public fn map<B>(transform: (T) -> B): Option<B> = ...;
}
```

Calling `opt.map(transform)` reads well when `opt` is the syntactic receiver. A free-function or
qualified style does not:

```zeron
let name = Option.map(opt, user -> user.name());
```

The qualified form repeats the subject and puts it before the transform, so the chain no longer
reads in execution order. The pipe form lets the extension keep its receiver-first declaration
while the subject stays on the left:

```zeron
let name = opt .> Option.map(user -> user.name());
```

Here `Option.map(...)` is an argument-bearing extension stage. The pipe supplies `opt` as the
receiver, and the explicit argument is the transform. This is ordinary extension application, not
a new dispatch rule: the same extension is selected, with the same receiver and argument types,
and lowering emits the same receiver-first static call.

The same form works for mapping and binding:

```zeron
let names = users ./> String::trim;          // map a String extension over each element
let account = findUser(id) .>> User::account; // bind a User extension returning Option
```

Without this form, the author must write a lambda that repeats the receiver:

```zeron
let names = users ./> (name -> String.trim(name));
let account = findUser(id) .>> (user -> User.account(user));
```

That is workable, but it makes extension methods the one receiver-first surface that cannot join
the pipe directly. Extension support removes that exception without adding general partial
application or implicit first-argument insertion.

### Why the placeholder needs a decision

The user-visible ergonomics of `.>` depend on how the right-hand side receives the subject. Two
directions are possible:

- an implicit first-argument rule, where `value .> f(option)` means `f(value, option)`; or
- an explicit placeholder, where the subject is named only where it is used, as in
  `value .> f(_, option)`.

The first direction is shorter for ordinary calls but ambiguous for member calls, nested calls,
and operators. It also has no natural spelling for `value .> _.trim()` or `value .> _ + 1`. The
second direction is uniform: a stage is an ordinary expression, and `_` marks the subject.
This proposal chooses the explicit placeholder, with one deliberate exception: a qualified
extension call may omit its receiver, because the extension declaration already identifies the
receiver position unambiguously.

The placeholder spelling is also a decision. Zeron already gives `it` a meaning: it is the
implicit parameter of an arrowless unary trailing lambda ([ZEP-0083](./ZEP-0083.md)). Reusing
`it` would either change that meaning or create silent shadowing whenever a pipe stage contains a
trailing lambda. `_` is already the language's “hole” in patterns and type arguments, has no
expression meaning today, and cannot be declared or shadowed as a name. The proposal therefore
uses `_` and leaves `it` unchanged.

## Goals

- Add `.>` as a left-associative, low-precedence operator that applies a unary stage to a subject
  in source order.
- Add `./>` as the mapping counterpart, lowering to the existing `Functor` witness's `map`.
- Add `.?>` as the filtering counterpart, lowering to the existing `Filterable` witness's
  `filter`.
- Add `.>>` as the binding counterpart, lowering to the existing `Monad` witness's `flatMap`.
- Add `_` as a subject placeholder scoped to one pipe stage, including method calls, free calls,
  operators, nested calls, and multiple occurrences.
- Add extension stages with the receiver omitted: a no-argument `Type::member` reference and an
  argument-bearing `Type.member(args)` call, without a lambda or general partial application.
- Preserve evaluation order, evaluate the subject exactly once, and preserve `Option`/`Result`
  short-circuiting and `Stream` laziness, including lazy filtering.
- Preserve existing `it`, `_` wildcard, `.` member access, `..` range, `|` bitwise-or, `>>`/`>>>`
  shifts, operator precedence, and effect-row behavior.
- Keep the change syntax-only: no new runtime data representation, descriptor, API-index, or
  standard-library contract change.
- Define the resolver diagnostics and the formatter, highlighter, editor-grammar, and test
  surfaces that must move with the syntax.

## Non-goals

- Implicit nullable or `Result` propagation, automatic unwrapping, or an `?.`-style safe pipe.
- General partial application, currying, implicit first-argument insertion, or automatic
  eta-expansion.
- Piping extension properties, class-scoped statics, or ordinary namespace functions through the
  extension stage.
- A new monad hierarchy, a new `Monad` contract, or changes to `Functor`/`Applicative`/`Monad`.
- Replacing `do` notation, `for` expressions, or `zeron.function.pipe`.
- Operator overloading for `.>`, `./>`, `.?>` or `.>>`; all four are fixed syntax. `./>` uses the
  existing `Functor` witness, `.?>` uses the existing `Filterable` witness, and `.>>` uses the
  existing `Monad` witness, not user-defined operator contracts.
- Automatic conversion between functors or monads, or automatic selection of `map` versus
  `flatMap` from the stage's result type.
- Changes to `it`, `||`/`&&` Boolean operators, `|` bitwise-or, `.` member access, `..` range, or
  `>>`/`>>>` shifts.
- Pipe syntax in type, pattern, or declaration positions.
- Macros, preprocessors, or source rewriting outside the compiler pipeline.

## Proposal

### Tokens and grammar

`.>`, `./>`, `.?>` and `.>>` are four new operator tokens. The scanner uses longest match:
`.>>` before `.?>` before `./>` before `.>` before `.`. `./` and `.?` alone are not tokens, so
`./>` and `.?>` are always single operators. The leading dot is part of the operator, so none of
these tokens collides with `>>` or `>>>` shifts, with `..` range, with `?.` safe calls, or with
`.` member access. A member access such as `value.member` still tokenizes as `.` followed by an
identifier. `value > other` still tokenizes as a comparison; only the contiguous `.>` spelling is
the apply pipe.

The expression grammar changes at the level between `coalesce` and `logicOr`:

```ebnf
coalesce = pipeline, [ "??", coalesce ] ;
pipeline = logicOr, { ( ".>" | "./>" | ".?>" | ".>>" ), logicOr } ;
logicOr  = logicAnd, { "or", logicAnd } ;
```

`'_'` also becomes a `primary` expression so that the parser can build a placeholder node and the
resolver can report a precise diagnostic outside a pipe stage; all other `primary` alternatives
are unchanged. The parser produces a dedicated `Pipeline` node with an operator kind and a
dedicated `Placeholder` leaf rather than reusing the overloadable `Binary` node. `.>`, `./>`, and
`.>>` are fixed syntax; they must not participate in the operator contracts from
[ZEP-0036](./ZEP-0036.md).

An extension stage is not a new parse production. A zero-argument stage is an ordinary callable
reference, and an argument-bearing stage is an ordinary qualified call expression. The resolver
recognizes either stage only after its target resolves to a visible extension method.

### Precedence and associativity

`.>`, `./>`, `.?>` and `.>>` share one precedence level and are left-associative. They bind
tighter than `??`, assignment, and range, and looser than `or`, `and`, comparison, type tests,
arithmetic, bitwise, unary, and postfix operations. The practical consequences are:

- `a .> f ?? b` groups as `(a .> f) ?? b`.
- `a ?? b .> f` groups as `a ?? (b .> f)`.
- `a .> f .> g` groups as `(a .> f) .> g`.
- `a .> f ./> g` groups as `(a .> f) ./> g`.
- `a .>> f ./> g` groups as `(a .>> f) ./> g`.
- `a .?> p ./> f` groups as `(a .?> p) ./> f`.
- `a ./> f .?> p` groups as `(a ./> f) .?> p`.
- `a or b .> f` groups as `(a or b) .> f`.
- `a .> f or b` groups as `a .> (f or b)`.
- `a .> _ + 1` groups as `a .> (_ + 1)`, which is `a + 1`.
- `(a .> f) + 1` applies the addition after the stage.

The pipe is deliberately the outer data-flow form. Boolean, comparison, arithmetic, bitwise, and
unary operators are part of a stage expression, so `value .> _ + 1` and
`value .> _.isValid() == true` need no extra parentheses. When an operation should apply to the
pipe result instead, parenthesize the pipe: `(value .> f) + 1`,
`(value .> _.isValid()) or fallback`. A stage such as `a .> f or b` is usually a type error
because `f or b` is not a function; write `(a .> f) or b` when that is the intent.

`??` is looser than the pipe, so `x .> f ?? y` first applies the stage and then coalesces the
result. This matches the reading order of the chain and keeps null fallback at the outer edge.

The pipe operators do not bind like member access. `value .> _.member` is a pipe whose stage is a
placeholder expression; `value.member` is still ordinary member access. The formatter keeps the
spaces around the pipe operators so the distinction is visible.

### Three stage forms

A pipe stage has exactly one of three forms. The form is selected syntactically and by name
resolution, never by type-directed guessing. All four operators use the same stage forms; only
their witness requirement and result shape differ.

**Filtering stages** use the same three forms with a Boolean stage type. For `.?>`:

**Placeholder form.** The right-hand side contains a placeholder occurrence in the stage's own
scope. The placeholder is bound to the subject, and the stage is an ordinary expression:

- for `.>`, the stage type is the result type `B`;
- for `./>`, the stage type is `B` from the element type `A`;
- for `.?>` the stage type is `Boolean` from the element type `A`; and
- for `.>>`, the stage type is `M<B>` from the element type `A`.

The operator is spelled `.?>`; the stage type for it is `Boolean`, and the result is `F<A>`.

**Extension form.** The right-hand side contains no placeholder and is either a zero-argument
extension reference such as `String::trim`, or an argument-bearing extension call such as
`Option.map(transform)`. Both leave the extension receiver open and denote the unary function
`(receiver: R) -> result`:

- with no parameters after the receiver, the reference form has no parentheses because forwarding
the subject satisfies the exact parameter list;
- with parameters after the receiver, the call form supplies them and the receiver is elided; and
- the receiver type `R` must accept the subject type in `.>`, or equal the element type `A` in
  `./>`, `.?>` and `.>>`; the result follows the extension declaration and the selected pipe
  operator.

The extension must be visible through the existing extension import rules. The pipe form does not
activate an unimported extension.

**Function form.** The right-hand side contains no placeholder and is not an extension stage. It
must be a function value:

- for `.>`, the stage type must be `(A) -> B`, and the result is `B`;
- for `./>`, the stage type must be `(A) -> B`, and the result is `F<B>`;
- for `.?>`, the stage type must be `(A) -> Boolean`, and the result is `F<A>`; and
- for `.>>`, the stage type must be `(A) -> F<B>`, and the result is `F<B>`.

A filtering stage's Boolean result is required; a stage returning `Option<B>` is not accepted as
`.?>` even though `Filterable.mapFilter` has that shape. Keep the predicate form aligned with do
notation guards, and use `./>` or `.>>` for transformation.

The distinction is local. If a stage contains `_` only inside a nested lambda or a nested pipe,
that occurrence does not belong to this stage. A nested lambda occurrence is a diagnostic, and a
nested pipe has its own placeholder. A stage such as `value .> makeStage(_)` is therefore the
placeholder form: it calls `makeStage(value)` and yields whatever that call returns, even when the
result is itself a function.

There is no implicit first-argument insertion for ordinary calls. `value .> parse(_, options)`
passes `value` as the first argument of `parse`; `value .> parse(options)` is the function form and
requires `parse(options)` to evaluate to a unary function. Extension stages are the exception, and
they are not general first-argument insertion: a zero-argument reference forwards the subject as
the receiver, an argument-bearing call binds the explicit arguments after that receiver, and both
forms are available only as a pipe stage.

The operator does not perform member lookup on the subject for the function form:
`value .> trim` requires a function value named `trim`, while `value .> _.trim()` performs the
method call through the placeholder. `users ./> String::trim` selects the zero-argument extension
reference, and `opt .> Option.map(f)` selects the argument-bearing extension call; neither looks
for a `trim` or `map` member on the subject.

After a `./>` stage the value is still `F<B>`, not `B`. After a `.?>` stage the value is `F<A>`,
with some elements removed. After a `.>>` stage the value is `F<B>`. A following `.>` stage
receives the functor or monad, not the unwrapped value; use `./>` for a pure operation on the
elements, `.?>` to remove elements, or `.>>` for another dependent operation. This is why the
mixed example writes `./> Settings::fromConfig` rather than `.> Settings::fromConfig`.

A stage that is an ordinary call expression with a value result is not a function form. For
example, `value .> parseConfig(text)` is an error unless `parseConfig(text)` itself has a function
type; it never means `parseConfig(value, text)`.

### Subject placeholder

The placeholder is `_`. Its rules are:

1. In expression position inside a pipe stage's right-hand side, `_` denotes the subject.
2. Multiple occurrences in one stage are allowed and denote the same value. The subject is
   evaluated once, not once per occurrence.
3. `_` is read-only. Assigning to it, including through `=`, `+=`, `??=`, or another compound
   assignment, is a diagnostic.
4. `_` in type-argument position keeps its existing type-wildcard meaning. `_` in pattern
   position keeps its existing wildcard meaning. Neither is a pipe placeholder.
5. `_` in expression position outside a pipe stage's right-hand side is a diagnostic. This
   includes the left-hand side of a pipe.
6. `_` inside a nested lambda body, including an arrowless trailing lambda, is a diagnostic when
   it would refer to the enclosing stage. Name the lambda parameter instead. The stage's
   right-hand side is not itself a lambda; `_` is bound by the stage, and only a lambda nested
   inside the stage creates a barrier.
7. A nested pipe introduces its own placeholder scope, including when it appears inside a lambda.
   The outer placeholder is not visible in the nested stage, and the inner placeholder is not
   visible after it.
8. Nested expressions that do not introduce a function parameter—such as `if`, `match`, `for`,
   `do`, value-block, anonymous-object, and handler expressions—remain inside the stage's
   placeholder scope. Patterns in those constructs still treat `_` as a wildcard.
9. `_` is not a lambda parameter name. Forms such as `(_, value) -> ...` remain invalid.

The placeholder type is the subject type for `.>` and the element type for `./>`, `.?>` and
`.>>`:

```zeron
let trimmed = title .> _.trim();                  // _ : String
let upper = opt ./> _.toUpperCase();              // _ : String, inside Option
let email = findUser(id) .>> _.primaryEmail();   // _ : User, not Option<User>
```

The last two lines are the important ones: `./>` maps the value inside the functor, so the stage
works on `A`; `.>>` binds the value inside the monad, so the stage also works on `A` and returns
`M<B>`.

### Extension stages

An extension stage leaves the extension receiver open. It has two spellings, selected by the
extension's parameter list.

**Zero-argument extension reference.** When the extension has no parameters after the receiver,
write `Type::member` with no parentheses:

```zeron
let names = users ./> String::trim;
let account = findUser(id) .>> User::account;
```

Forwarding the subject satisfies the exact parameter list, so there is no argument list to write.
The reference resolves first as an ordinary callable reference. If that finds a member, the stage
is the ordinary function form. If it finds no member and a visible extension with no post-receiver
parameters exists, the extension reference stage is selected. Outside a pipe, `String::trim`
remains rejected under [ZEP-0100](./ZEP-0100.md); this is a stage-only fallback, not a first-class
extension reference.

**Argument-bearing extension call.** When the extension has parameters after the receiver, write
`Type.member(args)` and omit the receiver:

```zeron
let slugs = titles ./> String.replace(" ", "-");
let name = findUser(id) .> Option.map(user -> user.name());
```

The explicit arguments bind the post-receiver parameters. Parentheses are required because there
are arguments to supply. `Type.member()` with an empty list for a zero-parameter extension is not
the reference form; write `Type::member`.

Both spellings denote `(receiver: R) -> result`; the pipe supplies the receiver. If `Option.map`
has the declaration

```zeron
public fn map<B>(transform: (T) -> B): Option<B>
```

with an implicit receiver of type `Option<T>`, then `Option.map(user -> user.name())` denotes:

```zeron
(receiver: Option<T>) -> Option.map(receiver, user -> user.name())
```

and the whole expression is the direct application of that function to `findUser(id)`. It is
equivalent to `Option.map(findUser(id), user -> user.name())`, except that the subject is written
first and evaluated once. `String::trim` denotes `(String) -> String` by the same rule.

- In `./>`, `String::trim` denotes `(String) -> String`, and `users` supplies the `Functor`
  structure. Each element is passed as the receiver.
- In `.>>`, `User::account` denotes `(User) -> Option<Account>`, and `findUser(id)` supplies the
  `Monad` structure. The stage is invoked only when the option is present.

Rules for extension stages:

- The zero-argument reference form is selected only when ordinary reference resolution finds no
  member and a visible extension with no post-receiver parameters exists. It forwards the subject
  as the receiver. This is a pipe-only fallback; it does not make `Type::member` a first-class
  extension reference.
- The argument-bearing call form must resolve to a visible extension method. A class method,
  contract default method, ordinary namespace function, static function, or constructor is not an
  extension stage. Its explicit arguments bind the parameters after the receiver, using the
  ordinary default, variadic, and generic-inference rules for that extension.
- The receiver is not written. Passing an explicit receiver makes the expression an ordinary call,
  not an extension stage; it then falls back to the function form and must produce a unary
  function value.
- The extension must be imported or otherwise visible under the existing extension lookup rules.
  Importing the receiver type alone does not activate it. Resolution follows the same import tiers
  as a receiver-dot extension call, so changing imports can change the selected declaration or
  make the stage ambiguous.
- A mutating extension (`this: &T`) requires the subject to be a mutable view. A read-only
  subject is a diagnostic, and the fix is to pass a mutable reference or use a non-mutating
  operation.
- The extension stage is statically dispatched, like every other extension call. It does not use
  witness dispatch, even when the same receiver has a `Functor` or `Monad` witness.
- Extension properties are not pipe stages in this proposal. Use the property through ordinary
  member access or wrap it in a lambda.
- The forms are not general partial application. `Type::member(args)` is not a reference with bound
  arguments; it is the argument-bearing extension call form. This proposal does not add a general
  partial application expression.

Like any extension call, the stage resolves against the imports at its use site, and a different
import set can select a different extension or make the stage ambiguous. The stage is not a
first-class reference, so it has no stable `CallableId` and no cross-site identity. This is
deliberate: the pipe form is an expression, not a value that can be stored, compared, or
serialized. `String::trim` remains invalid outside a pipe even though the same spelling is a stage
inside one.

The extension's explicit arguments follow ordinary call evaluation. In `.>` the stage is applied
once, so the arguments are evaluated once. In `./>`, `.?>` and `.>>` the stage is a unary function
whose
body contains the extension call; its arguments are evaluated when the function is applied to an
element, just as they would be inside a hand-written lambda. The subject is still evaluated once,
before the stage function.

### Filtering semantics

`.?>` requires a `Filterable<F<_>>` witness for the left-hand constructor; it does not require
`Monad`. Its stage is a predicate `(A) -> Boolean`, not a `mapFilter` transform. The operator
lowers to the witness's `filter`, the same operation that `if (condition);` guards use in
`do`-notation ([ZEP-0174](./ZEP-0174.md)).

- A `Filterable` implementation decides what an empty or failed case means. `Option` skips the
  predicate for `None`; `Stream` filters lazily and preserves order.
- `Option` and `Stream` have standard `Filterable` witnesses. `Result<_, E>` does not have a
  default one: filtering out an `Ok` would need an error value, and the standard library does not
  choose one. A project may supply its own witness.
- A predicate must be pure. An effectful predicate is rejected, matching the guard rule.
- A false predicate removes the element or path; filtering never reorders or duplicates values.
- `.?>` does not make `mapFilter` a stage form. A transforming filter is written as `./>` followed by
  `.?>` when the transform and filter are separate, or through the constructor's own `mapFilter`
  operation.

### Typing and evidence

For `.>`:

```text
lhs : A
rhs[_ : A] : B                 (placeholder form)
-------------------------------
lhs .> rhs : B

rhs : (A) -> B                 (function form)
-------------------------------
lhs .> rhs : B
```

The extension form is the function form with `rhs` denoting `(R) -> B`, where `R` accepts `A`.
For `./>`:

```text
lhs : F<A>    Functor<F<_>> witness    rhs[_ : A] : B
------------------------------------------------------
lhs ./> rhs : F<B>

lhs : F<A>    Functor<F<_>> witness    rhs : (A) -> B
------------------------------------------------------
lhs ./> rhs : F<B>
```

For `.?>`:

```text
lhs : F<A>    Filterable<F<_>> witness    rhs[_ : A] : Boolean
--------------------------------------------------------------
lhs .?> rhs : F<A>

lhs : F<A>    Filterable<F<_>> witness    rhs : (A) -> Boolean
--------------------------------------------------------------
lhs .?> rhs : F<A>
```

For `.>>`:

```text
lhs : F<A>    Monad<F<_>> witness    rhs[_ : A] : F<B>
-------------------------------------------------------
lhs .>> rhs : F<B>

lhs : F<A>    Monad<F<_>> witness    rhs : (A) -> F<B>
-------------------------------------------------------
lhs .>> rhs : F<B>
```

The constructor `F` is fixed by the left-hand side. A `./>` stage must return a plain `B`; a
`.>>` stage must return the same `F<B>`. There is no conversion between `Option`, `Result`, and
`Stream`, and no automatic lifting. Generic code must carry the existing higher-kinded bounds:

```zeron
fn mapWith<F<_>: Functor<F>, A, B>(value: F<A>, step: (A) -> B): F<B> =
    value ./> step;

fn filterWith<F<_>: Filterable<F>, A>(value: F<A>, predicate: (A) -> Boolean): F<A> =
    value .?> predicate;

fn bindWith<F<_>: Monad<F>, A, B>(value: F<A>, step: (A) -> F<B>): F<B> =
    value .>> step;
```

Concrete types use their existing witnesses: `Functor<Option<_>>`, `Monad<Option<_>>`,
`Functor<Result<_, E>>`, `Monad<Result<_, E>>`, `Functor<Stream<_>>`, `Monad<Stream<_>>`,
`Filterable<Option<_>>`, `Filterable<Stream<_>>`, or a library-defined implementation. There is no
standard `Filterable<Result<_, E>>` witness, matching [ZEP-0174](./ZEP-0174.md). A type that has an instance `map` or `flatMap` with a different
shape but no witness is rejected, exactly as it is in `do` notation
([ZEP-0111](./ZEP-0111.md)). There is no fallback to the receiver method. This also means that
`.>>` on a `Stream` uses the `Monad<Stream<_>>` witness, whose stage returns `Stream<B>`; it does
not use the class's `flatMap` method, which accepts any `Iterable<B>`.

`./>`, `.?>` and `.>>` introduce no new algebraic laws. They are the existing `map`, `filter` and
`flatMap` operations written in pipe form, so the functor, filterable, and monad laws documented
on `Functor`, `Filterable` and `Monad` apply unchanged.

The expected type of the whole expression flows into `B`. That is useful for generic stages and
for callable references, and it does not change the three-form rule.

### Lowering

The semantic equations are:

```text
lhs .> rhs   ≡  (subject -> rhs[subject/_])(lhs)              placeholder form
lhs .> rhs   ≡  (subject -> rhs(subject))(lhs)                function form
lhs ./> rhs  ≡  Functor.map(lhs, subject -> rhs[subject/_])   placeholder form
lhs ./> rhs  ≡  Functor.map(lhs, rhs)                         function form
lhs .?> rhs  ≡  Filterable.filter(lhs, subject -> rhs[subject/_]) placeholder form
lhs .?> rhs  ≡  Filterable.filter(lhs, rhs)                    function form
lhs .>> rhs ≡  Monad.flatMap(lhs, subject -> rhs[subject/_]) placeholder form
lhs .>> rhs ≡  Monad.flatMap(lhs, rhs)                       function form
```

`rhs[subject/_]` means substituting the subject binding for each placeholder occurrence. It is
not textual duplication: the subject is evaluated once, and repeated occurrences read the same
binding.

An extension stage is sugar for a unary function with the receiver left open. The zero-argument
reference form forwards the receiver directly:

```text
lhs .> Ns::ext    ≡  let s = lhs; Ns.ext(s)
lhs ./> Ns::ext   ≡  let s = lhs; Functor.map(s, receiver -> Ns.ext(receiver))
lhs .?> Ns::ext   ≡  let s = lhs; Filterable.filter(s, Ns.ext)
lhs .>> Ns::ext   ≡  let s = lhs; Monad.flatMap(s, receiver -> Ns.ext(receiver))
```

The argument-bearing call form binds its explicit arguments after the receiver:

```text
lhs .> Ns.ext(args)   ≡  let s = lhs; Ns.ext(s, args)
lhs ./> Ns.ext(args)  ≡  let s = lhs; Functor.map(s, receiver -> Ns.ext(receiver, args))
lhs .?> Ns.ext(args) ≡  let s = lhs; Filterable.filter(s, receiver -> Ns.ext(receiver, args))
lhs .>> Ns.ext(args) ≡  let s = lhs; Monad.flatMap(s, receiver -> Ns.ext(receiver, args))
```

Each form lowers to a statically dispatched receiver-first call in the extension's namespace
owner. It is not witness-dispatched. In `.>` the subject is passed directly as the receiver; in
`./>`, `.?>` and `.>>` the synthetic lambda supplies the receiver for each mapped, filtered, or
bound element.

The emitted code follows the existing witness-dispatch path:

- `.>>` emits `lhs.flatMap(stage)` with the call marked witness-dispatched, exactly like the
  binds in [ZEP-0111](./ZEP-0111.md). The receiver is the left-hand side; the argument is the
  stage function.
- `./>` emits `lhs.map(stage)` with the call marked witness-dispatched for `Functor`.
- ` .?>` emits `lhs.filter(stage)` with the call marked witness-dispatched for `Filterable`; the
  predicate is checked as a pure `(A) -> Boolean`.
- `.>` placeholder form may emit a synthetic unary lambda applied to the subject, or a temporary
  binding followed by the substituted stage. Either is acceptable if the subject is evaluated
  once, first, and the stage is evaluated after it.
- `.>` function form must not emit a plain `rhs(lhs)` if that would evaluate the callee before
  the argument. A temporary binding or a synthetic lambda application preserves the required
  left-to-right order.
- `.>` extension form emits the receiver-first static call with the subject evaluated first.
- No new runtime representation is introduced. Synthetic lambdas use the existing lambda
  lowering and generated function shapes (design-document-03).

### Evaluation order, effects, and short-circuiting

The left-hand side is evaluated once, before the stage expression. In function form, the stage
expression is evaluated after the left-hand side and before the invocation. In placeholder form,
the stage expression is evaluated with the subject already bound. In extension form, the subject
is evaluated first and the explicit arguments follow ordinary call order.

For `.>`, the stage expression or extension call is applied exactly once. For `./>`, the stage
function is evaluated once and its body runs according to the selected `map`; for a `Stream`, that
is once per element per traversal. For `.?>`, the predicate is evaluated once per candidate
element or path, according to the selected `filter`; a `Stream` remains lazy. For `.>>`, the stage
function is evaluated once and its body runs according to the selected `flatMap`; for `Option` and
`Result`, it is skipped when the value is absent or failed.

`./>` preserves the structure of the selected `map`:

- `Option.None` and `Result.Err` do not invoke the stage;
- `Stream` remains lazy and maps once per element per traversal; and
- the result is the same constructor as the left-hand side.

`.?>` preserves the behavior of the selected `filter`:

- the predicate is not called for an empty case that the witness skips, such as `Option.None`;
- `Stream` remains lazy and order-preserving, and filtering happens during traversal; and
- a false result removes the element or path, never reorders or duplicates it.

`.>>` preserves the behavior of the selected `flatMap`:

- `Option.None` and `Result.Err` do not invoke the stage;
- `Stream` remains lazy, and the stage runs once per element per traversal, not when the operator
  is evaluated; and
- the result is the same constructor as the left-hand side.

`.>` is ordinary application. It adds no laziness, short-circuiting, null propagation, or
exception handling.

Effects are not rewritten. `.>` propagates the effects of the left-hand side, the stage
expression, and the application. `./>` propagates the effects of the left-hand side, the
`Functor` witness, and the stage as checked against the `map` parameter. `.?>` propagates the
effects of the left-hand side and the `Filterable` witness; its predicate must be pure, matching
the do-notation guard rule. `.>>` propagates the effects of the left-hand side, the `Monad`
witness, and the stage as checked against the `flatMap` parameter. An extension stage adds the
effects declared by that extension call. A stage that is effectful is accepted or rejected exactly
as an explicit `map`, `filter`, or `flatMap` argument would be. `do` remains the multi-bind form,
and this proposal does not change effect rows or handler semantics.

### Representative examples

Free functions and receiver methods compose in the same direction:

```zeron
fn normalize(text: String): String = text.trim().toLowerCase();
fn slugify(text: String): String = text.replace(" ", "-");

let slug = title .> normalize .> slugify;

let slugWithMethods = title
    .> _.trim()
    .> _.toLowerCase()
    .> _.replace(" ", "-");
```

A dependent `Result` chain needs no nested matches. Mapping finishes a pure stage:

```zeron
fn readText(path: String): Result<String, ConfigError> = ...;
fn parseConfig(text: String): Result<Config, ConfigError> = ...;
fn validate(config: Config): Result<Config, ConfigError> = ...;
fn resolve(config: Config): Result<Settings, ConfigError> = ...;

fn loadSettings(path: String): Result<Settings, ConfigError> =
    readText(path)
        .>> parseConfig
        .>> validate
        .>> resolve;

let preview = readText(path)
    .>> parseConfig
    .>> validate
    ./> Settings::fromConfig;
```

The same shape works for `Option`, with the placeholder bound to the unwrapped value:

```zeron
fn findCity(userId: Int): Option<City> =
    findUser(userId)
        .>> _.address()
        .>> _.city();
```

`Option` also shows the difference between applying an extension to the option and mapping over
its contents:

```zeron
// Apply Option.map to the whole option: Option<String>.
let name = findUser(id) .> Option.map(user -> user.name());

// Map a pure transformation over the contained value: Option<String>.
let upper = findUser(id)
    ./> _.name()
    ./> _.toUpperCase();
```

`Stream` keeps its laziness and its existing witnesses. Filtering applies to the stream; mapping
applies to each element:

```zeron
fn activeNames(users: Stream<User>): Stream<String> =
    users
        .?> _.active()
        ./> User.name();
```

`Option` filters the contained value while preserving `None`:

```zeron
let active = findUser(id) .?> User::isActive;
```

Extension stages keep the receiver-first declaration:

```zeron
let names = users ./> String::trim;
let account = findUser(id) .>> User::account;
let slug = title .> String::trim;
```

A mutating extension receives the mutable subject directly:

```zeron
values .> Array.replaceFirst(9);
```

Generic code uses the existing higher-kinded bounds:

```zeron
fn mapWith<F<_>: Functor<F>, A, B>(value: F<A>, step: (A) -> B): F<B> =
    value ./> step;

fn bindWith<F<_>: Monad<F>, A, B>(value: F<A>, step: (A) -> F<B>): F<B> =
    value .>> step;
```

Callable references fit the function form because a method reference already includes its
receiver as the first parameter ([ZEP-0100](./ZEP-0100.md)):

```zeron
let label = user .> User::label;
let email = findUser(id) .>> User::primaryEmail;
```

Arguments and repeated placeholders are ordinary expressions:

```zeron
let config = text .> parseConfig(_, options);
let square = value .> multiply(_, _);
```

Pure and monadic stages can be mixed. The pure stage uses `./>`; it does not use `.>>`, because
`.>>` requires the stage itself to return the monad:

```zeron
let settings = readText(path)
    .>> parseConfig
    .>> validate
    ./> Settings::fromConfig;
```

### Interaction with existing features

- **`zeron.function.pipe` and `compose`.** They remain the tools for composing functions. A
  pipe applies a value through stages; it does not replace function composition:

  ```zeron
  let normalizeAndSlug = pipe(normalize, slugify);
  let slug = title .> normalizeAndSlug;
  ```

- **`do` notation.** `do` remains the multi-bind form. `.>>` is its expression-level,
  one-step counterpart. The two are equivalent where both apply:

  ```zeron
  let profile = do<Option<_>> {
      let user <- findUser(id);
      let account <- user.account();
      let profile <- account.profile();
      yield profile;
  };

  let profileFromPipe = findUser(id) .>> _.account() .>> _.profile();
  ```

- **Do-notation guards.** `if (condition);` in a `do` block and `.?>` in a pipe are the same
  `Filterable.filter` operation at different scopes. A `do` block also needs `Monad` because it
  sequences binds; `.?>` needs only `Filterable`. Neither form has a default `Result<_, E>`
  `Filterable` witness.

- **`for` expressions.** A pipe is an ordinary expression, so it can appear in a `for` source or
  a clause without special grammar:

  ```zeron
  for user in users .?> _.active()
      yield user.name();
  ```

- **Callable references.** A method reference includes its receiver as the first parameter, so
  it fits the function form directly. Extension methods do not form first-class callable
  references. In a pipe stage, a zero-argument extension may use `Type::member` as a stage-only
  reference; outside a pipe that spelling remains rejected. Argument-bearing extensions use
  `Type.member(args)` or a lambda ([ZEP-0100](./ZEP-0100.md)).

- **Extension methods.** A zero-argument extension reference or an argument-bearing extension
  call with the receiver omitted is a pipe stage. The extension must be visible through the
  existing import rules, and neither form is general qualified call syntax. See
  [ZEP-0145](./ZEP-0145.md) for the unified namespace and extension container direction.

- **Nullability.** There is no implicit null propagation. The placeholder has the subject's
  nullable type, and safe calls remain explicit: `name .> _?.trim()`. A nullable value is not a
  functor, filterable, or monad, so `./>`, `.?>` and `.>>` reject it.

- **Mutability.** The placeholder is a read-only name, but it preserves the subject's reference
  and mutability qualifiers. A mutating receiver call through `_` follows the same rules as the
  same call on the subject expression. A mutating extension stage requires a mutable subject.
  The placeholder itself cannot be assigned.

- **Operator overloading.** `.>`, `./>`, `.?>` and `.>>` are fixed syntax. They do not consult
  operator contracts and cannot be overloaded. `|` remains bitwise-or and remains available to
  the existing operator rules.

- **Shifts and range.** `>>` and `>>>` remain shifts, `..` remains range, and `?.` remains safe
  call. The leading dot keeps `./>`, `.?>` and `.>>` lexically distinct from all of them.

- **`it`.** Unchanged. No pipe stage creates an implicit `it`.

- **`_` wildcard.** `_` in patterns and type arguments keeps its current meaning. The pipe
  placeholder is recognized only in expression position inside a stage's right-hand side.

### Diagnostics

The implementation should add catalog-backed diagnostics for at least these conditions. Exact
codes and messages belong to the diagnostics catalog, not to this proposal.

- Placeholder outside a pipe stage's right-hand side.
- Placeholder inside a nested lambda, including a trailing lambda.
- Placeholder used as an assignment target.
- `.>` function form where the right-hand side is not a unary function.
- `.>` stage whose parameter type does not accept the subject type.
- `./>` left-hand side that is not an application of a functor constructor, either a concrete
  constructor or an `F<_>` type parameter with a `Functor` bound.
- `./>` where the left-hand constructor has no `Functor` witness, even if it has an instance
  `map`.
- `./>` stage that returns the same functor instead of a plain `B`; suggest `.>>` when the stage
  is monadic.
- `.>>` left-hand side that is not an application of a monadic constructor, either a concrete
  constructor or an `F<_>` type parameter with a `Monad` bound.
- `.>>` where the left-hand constructor has no `Monad` witness, even if it has an instance
  `flatMap`.
- `.>>` stage that does not return the same monad constructor as the left-hand side; suggest
  `./>` when the stage is pure.
- `.?>` left-hand side that is not an application of a filterable constructor, either a concrete
  constructor or an `F<_>` type parameter with a `Filterable` bound.
- `.?>` where the left-hand constructor has no `Filterable` witness, even if it has an instance
  `filter` or `mapFilter`.
- `.?>` stage that is not a pure `(A) -> Boolean` predicate.
- `.?>` stage that returns `Option<B>`, which is the `mapFilter` shape; suggest `./>` followed by
  `.?>` or the constructor's own `mapFilter` operation.
- `.>>` function form where the right-hand side is not a function of the required shape.
- Zero-argument extension reference whose selected extension has parameters after the receiver;
  suggest the `Type.member(args)` call form.
- Zero-argument extension reference with an argument list, which is not supported; use the
  `Type.member(args)` call form.
- Argument-bearing extension call with an empty argument list for a zero-parameter extension;
  suggest `Type::member`.
- Extension stage whose qualified name does not resolve to a visible extension method.
- Extension stage whose explicit arguments do not match the parameters after the receiver.
- Extension stage whose receiver type does not accept the subject or element type.
- Ambiguous extension stage under the current import tier.
- Extension stage that passes an explicit receiver, making it an ordinary call rather than an
  extension stage.
- Extension reference outside a pipe that names only an extension; it remains rejected by
  [ZEP-0100](./ZEP-0100.md).
- Mutating extension stage with a read-only subject.
- Extension property used as a pipe stage, which is not supported in version 1.
- Qualified call outside a pipe that omits an extension receiver, unless separate qualified-call
  support exists.

A missing witness is not a reason to fall back to a receiver method. The notation means functor
map, filtering, or monadic bind, and the witness is the evidence that the type participates in the
abstraction. A missing extension import is not a reason to fall back to a member call.

## Compatibility and impact

**Source compatibility.** `.>`, `./>`, `.?>` and `.>>` are currently invalid source, so no valid
program changes meaning. `.` remains member access, `..` remains range, `|` remains bitwise-or,
`|=` remains its assignment form, and `||` remains invalid. `>>` and `>>>` remain shifts. `_` in
expression position outside a pipe stage remains invalid; `_` in patterns and type arguments
keeps its existing wildcard meaning. `it` is unchanged. Existing trailing lambdas, `do`
expressions, and `for` expressions are unaffected.

**Precedence.** The operators add one new level between `??` and `or`. No existing expression
contains `.>`, `./>`, `.?>`, or `.>>`, so no existing grouping changes. The formatter changes only for
source that uses the new syntax.

**Runtime and ABI.** The change is syntax-only. `.>` lowers to ordinary calls and the existing
lambda-lowering machinery; `./>`, `.?>` and `.>>` lower to the existing witness-dispatched
`map`, `filter` and `flatMap` paths. An extension stage lowers to the existing receiver-first static extension call.
A synthetic stage lambda may generate the same kind of function-shape interface
that a hand-written lambda would, but there is no new runtime data representation, descriptor,
library-index entry, or public standard-library declaration. No source-level API-index or
standard-library API change requires a version bump.

**Separate compilation.** Operators are not exported declarations. Compiled libraries are
unaffected, and generic `./>`, `.?>` and `.>>` use the same serialized `Functor`, `Filterable`
and `Monad` evidence that `map`, `filter` and `do` already use. Extension stages require the extension to be visible through the
ordinary import and library-index rules.

**Effects.** No effect-row or handler change. A stage is checked exactly as the corresponding
ordinary call, `map`, `filter`, or `flatMap` argument would be. `./>`, `.?>` and `.>>` add no
implicit lifting or handling.

**Tooling.** The implementation touches the grammar, scanner, AST, parser, resolver, compiler,
formatter, ANSI highlighter, TextMate grammar, diagnostics catalog, tests, and user guides. The
LSP keyword list does not change because none of the operators is a keyword. The syntax-surface
checklist in
[`syntax-surface-checklist.md`](../developer_guides/syntax-surface-checklist.md) is the
authoritative checklist for the implementation.

**Extension reference asymmetry.** Extension methods can be receiver-dot calls, argument-bearing
qualified calls, and pipe stages, but not first-class references. A zero-argument extension can
be written `String::trim` inside a pipe, but the same spelling remains invalid as a first-class
reference outside one. That is a real ergonomic and API-modeling cost. Removing it requires
accepting extension references with a stable identity independent of imports; the pipe-only
fallback does not do that. This proposal accepts the asymmetry for version 1; the stage has no
identity.

**Design-document-00.** That document records a low-priority sketch where `value |> f(option)`
means `f(value, option)`. This proposal supersedes that sketch if accepted: the explicit
placeholder removes the ambiguity of choosing which call receives the subject, and the extension
form handles the receiver-first case without general first-argument insertion. The sketch should
be updated when this proposal is accepted or implemented, not before.

**Documentation and release.** When implemented, the user-facing behavior belongs in the
expression/control-flow guide, the lambda guide (for `_` versus `it`), the extension guide (for
extension stages), and the functional abstraction guides. `CHANGELOG.md` is updated for the
user-visible language change. The proposal does not assign a release version; selection follows
the workstream and release-plan process.

## Alternatives

- **Keep `|>` and `||>`.** Rejected. `|` is bitwise-or and `||` is not a token, so the old
  spellings carry avoidable visual and lexical ambiguity. The dot-prefixed family reads as a
  receiver-oriented pipe and leaves shifts and range untouched.

- **Use `.->` for mapping.** Rejected. `->` already reads as a lambda or function arrow, and
  `a .-> f` is easy to confuse with a member access followed by an arrow. `./>` is visually
  distinct and keeps the dot-prefixed pipe family.

- **Use `.>>` for map and a longer token for bind.** Rejected. `.>>` is the shortest unambiguous
  bind spelling and keeps the old bind role short; a four-character bind such as `.>>>` was
  rejected as unergonomic. The slash in `./>` marks the pure mapping step, and the double
  chevron in `.>>` marks flattening.

- **Choose `map` or `flatMap` from the stage's result type.** Rejected. It is type-directed
  overloading, hides the difference between a pure stage and a dependent one, and complicates
  inference and error messages. The separate operators keep the distinction explicit.

- **Use `Filterable.mapFilter` as the filtering stage.** Rejected. A `mapFilter` stage transforms
  and filters at once, which is a different operation from a Boolean guard and overlaps `./>`.
  `.?>` stays a predicate stage, matching do-notation guards; a transforming filter is written as
  two explicit stages or through the constructor's own `mapFilter` operation.

- **Use a `.filter` member instead of `.?>`.** Rejected because it requires a member or extension
  on every receiver type and bypasses the `Filterable` evidence that do-notation already uses.

- **One pipe operator with automatic lifting.** Rejected. Auto-lifting makes a stage's meaning
  depend on its result type and can silently turn a pure expression into a monadic one. `./>`
  and `.>>` are explicit, and a pure stage in a bind chain uses `./>`.

- **Implicit first-argument insertion.** `value .> f(option)` would mean `f(value, option)`.
  Rejected because it is ambiguous for nested calls and member calls, cannot express
  `value .> _.trim()` or `value .> _ + 1`, and silently chooses which call in an expression
  receives the subject. The explicit `_` and the qualified extension form cover the useful cases.

- **General partial application.** Rejected. An argument-bearing extension call is a narrow,
  syntactically identifiable form. General partial application would need new function-value
  semantics, arity inference, and interactions with defaults and variadics that are outside this
  proposal.

- **Unqualified extension stages.** Rejected because an unqualified name can be a local function,
  namespace function, or function value. Requiring a qualified extension name makes the receiver
  position and the selected declaration explicit.

- **Use `Type::member(args)` for argument-bearing extension stages.** Rejected. `::` has no
  argument list; adding one would be a new partial-application form, not the reference fallback.
  `Type.member(args)` already spells an argument-bearing extension call with the receiver elided.

- **Require empty parentheses for zero-argument extension stages.** Rejected. `Type.member()`
  reads as a call with no arguments, while forwarding the subject satisfies the exact parameter
  list; `Type::member` states that directly.

- **Make `Type::member` a first-class extension reference.** Deferred. [ZEP-0100](./ZEP-0100.md)
  rejects extension references because their identity depends on the import set. Version 1 allows
  the spelling only as a zero-argument pipe stage and promises no identity.

- **Extension properties as pipe stages.** Deferred. Properties have no argument list to
  distinguish an extension stage from a function value, and qualified getter calls are
  already an open question in [ZEP-0145](./ZEP-0145.md). Version 1 supports extension methods.

- **`it` as the placeholder.** Rejected because [ZEP-0083](./ZEP-0083.md) already binds `it` in
  arrowless unary trailing lambdas. A pipe `it` would either change that rule or create silent
  shadowing in nested lambdas. `it` is also a normal identifier that can be captured. `_` cannot
  be declared or shadowed and already means “hole”.

- **Standard-library `pipe`/`compose` only.** Rejected because those functions compose functions,
  not values. Applying them at a value site still needs a call, and adapting an existing function
  often needs an eta-expanded lambda. They remain complementary, not sufficient.

- **Fluent methods and extensions only.** Rejected because they require every API to be designed
  receiver-first. Free functions, constructors, static functions, and callable references cannot
  join the chain without wrapper methods or extensions, which distorts API design.

- **Right-associative pipe.** Rejected because `a .> f .> g` must apply `f` first. Right
  associativity would group it as `a .> (f .> g)`, which is not a data pipe.

- **Pipe tighter than `or`/`and`.** Rejected because the chosen placement keeps `??` at the
  outer edge and treats Boolean operators as part of a stage expression. The trade-off is that
  `a .> f or b` groups as `a .> (f or b)`; parenthesize `(a .> f) or b` when the Boolean
  operation should apply to the pipe result.

- **A `.pipe(f)` method or extension.** Rejected because it needs a member or extension on every
  receiver type, adds API surface, and does not cover free functions uniformly. An operator works
  for every expression.

- **`$`, `@`, or `#` as the placeholder.** Rejected because those spellings introduce new
  punctuation with no existing “hole” meaning. `_` is already the language's wildcard in patterns
  and type arguments.

- **Do-notation only.** Rejected as a replacement. `do` is block-oriented, requires at least one
  bind, and does not cover pure `.>` or `./>` stages. It remains the better form for multi-bind
  blocks; `.>>` covers the single-step and expression-position cases. `.?>` covers the single
  filtering case without requiring a `do` block.

## Implementation and validation

Implementation should follow the syntax-surface checklist in order:

1. **Grammar and tokens.** Update
   [`design-document-01_grammar.ebnf`](../design_documents/design-document-01_grammar.ebnf),
   add `.>`, `./>`, `.?>` and `.>>` to `TokenType.java` and `Scanner.java`, and add the
   longest-match rules. Leave `.`, `..`, `>>`, `>>>`, and `?.` on their existing paths.
2. **AST and parser.** Add `Expr.Pipeline` with an apply/map/filter/bind kind and `Expr.Placeholder`
   (or equivalent dedicated nodes), parse the new precedence level, and keep `_` accepted as a
   primary expression for a precise resolver diagnostic. Do not route the operators through
   `Binary` or operator contracts.
3. **Resolver and type checking.** Implement the placeholder scope stack, the nested-lambda
   barrier, the three-form rule, the extension-stage resolution, the `Functor` witness lookup for
   `./>`, the `Filterable` witness lookup for `.?>`, the `Monad` witness lookup for `.>>`, and the
   diagnostics listed
   above. Keep `_` in type arguments and patterns on their existing paths.
4. **Lowering.** Emit the semantic equations in “Lowering”, preserving subject-first evaluation
   and exactly-once evaluation. Mark `./>`, `.?>` and `.>>` witness-dispatched, matching `map`,
   `filter` and `do` lowering. Lower an extension stage to the existing receiver-first static
   call.
5. **Tooling.** Update the formatter and, if the long-chain layout becomes a canonical rule,
   `CanonicalStyle.java` and `style.toml`; update the ANSI highlighter, TextMate grammar, and any
   editor grammar tests. The LSP keyword list does not change.
6. **Diagnostics and documentation.** Add catalog entries and explanation resources, update the
   relevant guides, and update `CHANGELOG.md` when the feature ships.

Validation should cover:

- **Scanner:** `.>`, `./>`, `.?>`, `.>>`, `.`, `..`, `>>`, `>>>`, `?.`, `|`, `|=`, and invalid `||`;
  longest-match behavior and token locations.
- **Parser:** every grouping in the precedence list, left associativity, mixed operator chains,
  placeholder in primary position, and `_` in type arguments and patterns.
- **Resolver:** placeholder outside a stage, in a nested lambda, on the left-hand side, and as an
  assignment target; multiple placeholders; nested pipe scoping; `it` unchanged; `.>` function
  form with a non-function; `./>` with a missing `Functor` witness; `.?>` with a missing
  `Filterable` witness, a non-Boolean predicate, and an effectful predicate; `.>>` with a missing
  `Monad` witness, a wrong constructor, and a non-monadic stage; generic `F<_>: Functor<F>` and
  `F<_>: Monad<F>`.
- **Extension stages:** zero-argument references where forwarding satisfies the exact parameter
  list, argument-bearing calls, empty-parentheses diagnostics for zero-argument extensions,
  reference diagnostics for argument-bearing extensions, missing import, wrong arity, explicit
  receiver passed, generic inference, mutating extension with mutable and read-only subjects,
  extension property rejected, and a qualified namespace function that is not an extension.
- **Compilation:** subject evaluated once and before the stage; stage evaluated after the
  subject; `Option`/`Result` short-circuiting; `Stream` laziness and per-traversal stage
  execution; filter behavior and predicate evaluation; a library-defined functor, filterable, and
  monad witness; callable references; free, static, and
  constructor functions; extension static dispatch; effect propagation.
- **Formatter:** spacing around all four operators, long-chain line breaking, and idempotence.
- **Editor grammar:** the TextMate test for the new operators and the placeholder.
- **Docs:** the expression, lambda, extension, and functional-abstraction guides, plus
  `CHANGELOG.md`.

Run focused tests first. Remove `dist/` before compiling Zeron source or tests that generate
Zeron programs, per the repository guidance, and reserve the full `mvn test` run for the point
where the change is ready for broad validation. If the synthetic lambda's generated shape
identity matters, inspect it with `javap -classpath dist` as described in the lambda-lowering
documentation.

This section records likely stages and verification, not a schedule or an implementation
commitment.

## Resolved design questions

The following decisions close the questions that were open while this proposal was a Draft.

- **Long-chain formatting.** The canonical intent is one stage per line when a pipe chain exceeds
  the configured line width, with the line break before the operator. Short chains remain on one
  line. The formatter implementation may tune the threshold and continuation indent, but it must
  not choose a different grouping.
- **Mixed chains.** No parentheses are required merely because `.>`, `./>`, `.?>` and `.>>` are
  mixed. They share one precedence level and associate left; the formatter may break a mixed chain
  like any other. Parentheses remain available when an author wants to make an intermediate result
  explicit. A compile-time mixed-chain warning is not part of version 1.
- **Extension properties.** Deferred. Version 1 continues to support extension methods only.
  Properties have no argument list to mark the receiver hole; a later proposal may define a
  getter-stage spelling.
- **Unqualified extension stages.** Not allowed in version 1. An extension stage must use
  `Type::member` or `Type.member(args)` so the selected declaration and receiver position remain
  explicit. Relaxing this requires a separate name-resolution rule for unambiguous imported
  extensions.
- **Generalized extension stages.** Not allowed. Version 1 keeps extension stages limited to
  extension methods. Ordinary namespace functions and class-scoped statics use the placeholder or
  function form instead; treating them as receiver-dot stages would add a second receiver rule.
- **First-class extension references.** Deferred. The zero-argument `Type::member` spelling remains
  a stage-only fallback with no `CallableId` or cross-site identity. A later proposal would need to
  give extension references a stable identity independent of imports.
- **Identity and repeated placeholders.** Repeated placeholders such as `value .> combine(_, _)` are
  valid, and the subject is still evaluated once. `value .> _` is also valid, though redundant. No
  compiler diagnostic is added; an optional style check belongs to style tooling and must not
  change semantics or formatting.
- **Handler expressions.** Handler arms are not lambdas and do not introduce a function-parameter
  barrier, so `_` inside a handler arm continues to denote the enclosing pipe subject. Pattern `_`
  remains a wildcard. Implementation must add a regression test for an outer placeholder inside a
  handler arm; if a future handler form introduces lambda-like parameter bindings, that form must
  declare its own barrier rather than silently capturing the outer subject.

## Decision

Accepted on 2026-11-28. The operator family is approved as specified: `.>` apply, `./>` map,
`.?>` filter, and `.>>` bind, with no automatic selection among `map`, `filter`, and `flatMap`.
The placeholder spelling (`_`), nested-lambda scope, extension-stage forms, precedence between
`??` and `or`, method-only extension restriction, and syntax-only runtime and API impact are also
accepted. The resolved design questions above settle formatting, mixed chains, extension
properties and unqualified or generalized stages, first-class extension references, repeated
placeholders, and handler-arm scope.

This decision approves the design direction; it does not assign a release version. Release
candidacy is recorded in the active 0.10.0 plan.
